# 四种认证方案对比

## 为什么需要认证

HTTP 是**无状态**协议——每次请求都是独立的，服务器不知道这次请求和上次请求来自同一个用户。

```
请求 1: GET /book/list        ← 服务器：你是谁？
请求 2: POST /borrow/borrow   ← 服务器：还是不知道你是谁

认证的目标：让服务器在每次请求时都能识别用户身份
```

## 前端类比

```
HTTP 无状态 ≈ 每次进店都是陌生客
认证机制   ≈ 会员卡

Session/Cookie ≈ 店员在后台登记册上查你名字（服务器存状态）
JWT           ≈ 会员卡上已经印好了你的信息（客户端存状态）
OAuth         ≈ 用微信扫码确认身份（第三方担保）
```

## 方案 1：Session + Cookie

```
┌─────────────────────────────────────────────┐
│  1. 用户登录                                  │
│     POST /login { username, password }       │
│                                              │
│  2. 服务器验证通过，创建 Session                │
│     session = { userId: 1, username: "alice" }│
│     存储在 Redis / 内存中                      │
│     返回 Set-Cookie: sessionId=abc123         │
│                                              │
│  3. 后续请求自动携带 Cookie                     │
│     Cookie: sessionId=abc123                 │
│                                              │
│  4. 服务器查 Session 表获取用户信息              │
└─────────────────────────────────────────────┘
```

```typescript
// Session 方案示例
@Post('login')
async login(@Body() dto: LoginDto, @Session() session: any) {
  const user = await this.userService.login(dto);
  session.userId = user.id;
  session.username = user.username;
  return { success: true };
}

@Get('profile')
async profile(@Session() session: any) {
  if (!session.userId) throw new UnauthorizedException();
  return this.userService.findById(session.userId);
}
```

**优点**：服务端可强制失效（踢人）、Session 数据不暴露给客户端
**缺点**：需要 Redis 等存储、跨域麻烦、多服务器需要共享 Session

## 方案 2：JWT（JSON Web Token）

```
┌──────────────────────────────────────────────┐
│  1. 用户登录                                   │
│     POST /login { username, password }        │
│                                               │
│  2. 服务器验证通过，签发 Token                    │
│     token = jwt.sign({ userId: 1 }, secret)   │
│     返回 { token: "eyJhbGci..." }             │
│                                               │
│  3. 客户端存储 Token（localStorage / cookie）    │
│                                               │
│  4. 后续请求在 Header 中携带 Token               │
│     Authorization: Bearer eyJhbGci...         │
│                                               │
│  5. 服务器验证签名，解析出用户信息（不查数据库）     │
└──────────────────────────────────────────────┘
```

```typescript
// JWT 方案示例
@Post('login')
async login(@Body() dto: LoginDto) {
  const user = await this.userService.login(dto);
  const token = this.jwtService.sign({ sub: user.id, username: user.username });
  return { token };
}

@Get('profile')
async profile(@Req() req: any) {
  // req.user 由 AuthGuard 从 JWT 解析得到
  return this.userService.findById(req.user.sub);
}
```

**优点**：无状态（服务器不需要存储）、天然跨域、适合微服务
**缺点**：无法强制失效（除非加黑名单）、Token 体积较大

## 方案 3：OAuth 2.0 / OpenID Connect

```
┌────────────────────────────────────────────┐
│  第三方登录（微信/GitHub/Google）             │
│                                            │
│  1. 用户点击"微信登录"                       │
│  2. 跳转微信授权页                          │
│  3. 用户确认授权                            │
│  4. 微信回调你的服务器，带上授权码            │
│  5. 服务器用授权码换 access_token           │
│  6. 用 access_token 获取用户信息             │
└────────────────────────────────────────────┘
```

**适用场景**：第三方登录、"使用微信登录"、开放平台 API

## 方案 4：Passport.js（Nest 中常用）

Passport 本身不是认证方案，而是一个**认证中间件框架**，提供统一的 API 包装各种认证策略：

```typescript
// Passport 策略生态
passport-local       // 用户名密码
passport-jwt         // JWT
passport-google-oauth20  // Google OAuth
passport-github2     // GitHub OAuth
passport-wechat      // 微信 OAuth
```

## 全面对比

| 维度 | Session + Cookie | JWT | OAuth 2.0 | Passport |
|------|:---:|:---:|:---:|:---:|
| 服务器存储 | 需要（Redis/DB） | 不需要 | 不需要 | 取决于策略 |
| 水平扩展 | 需要共享 Session | 天然支持 | 天然支持 | 取决于策略 |
| 强制失效 | ✅ 删 Session | ❌（需黑名单） | ❌ | 取决于策略 |
| 跨域支持 | ❌ 麻烦 | ✅ 天然 | ✅ 天然 | 取决于策略 |
| 移动端友好 | ❌ Cookie 限制 | ✅ Header 传递 | ✅ | 取决于策略 |
| 实现复杂度 | 简单 | 中等 | 高 | 中等 |
| 适用场景 | 传统 Web 应用 | SPA + API / 微服务 | 第三方登录 | 需要切换策略 |

## 图书管理系统的选择：JWT

理由：
1. 前后端分离架构（前端独立部署）
2. 未来可能扩展移动端
3. 无状态，水平扩展简单
4. 实现方案成熟，`@nestjs/jwt` 开箱即用
