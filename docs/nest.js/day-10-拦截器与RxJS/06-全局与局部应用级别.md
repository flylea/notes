# Interceptor 应用级别与 DI 支持

## 四种注册方式回顾

```typescript
// 1. 全局（不可注入依赖）
app.useGlobalInterceptors(new TransformInterceptor());

// 2. 全局（可注入依赖）
// 在 AppModule 的 providers 中：
{ provide: APP_INTERCEPTOR, useClass: TransformInterceptor }

// 3. Controller 级别
@Controller('book')
@UseInterceptors(LoggingInterceptor)
export class BookController {}

// 4. Handler 级别
@Get('list')
@UseInterceptors(CacheInterceptor)
list() {}
```

## useGlobalInterceptors vs APP_INTERCEPTOR 的核心差异

| 维度 | `useGlobalInterceptors()` | `APP_INTERCEPTOR` token |
|------|--------------------------|------------------------|
| 依赖注入 | ❌ 不支持（实例不在 DI 容器中） | ✅ 支持 |
| 注册位置 | main.ts | Module 的 providers |
| 使用场景 | 不需要注入依赖的 Interceptor | 需要注入 Reflector、PrismaService 等 |

示例——需要注入依赖时只能用 `APP_INTERCEPTOR`：

```typescript
// 需要注入 PrismaService
@Injectable()
export class CacheInterceptor implements NestInterceptor {
  constructor(
    private prisma: PrismaService,   // ← 需要注入
    private reflector: Reflector,    // ← 需要注入
  ) {}
}

// ❌ 不能用这个
app.useGlobalInterceptors(new CacheInterceptor());  // PrismaService 传不进去

// ✅ 只能用这个
@Module({
  providers: [
    { provide: APP_INTERCEPTOR, useClass: CacheInterceptor },
  ],
})
```

## 多个 Interceptor 的注册和顺序

```typescript
// 全局注册（在 main.ts 中 app.useGlobalInterceptors）
// 1. TransformInterceptor  → 最后执行（最先注册 = 最外层）
// 2. LoggingInterceptor
// 3. PerformanceInterceptor

// 实际执行顺序（洋葱模型）：
// TransformInterceptor.before → LoggingInterceptor.before → PerformanceInterceptor.before
//   → Controller
//   → PerformanceInterceptor.after → LoggingInterceptor.after → TransformInterceptor.after
```

## 排错：Interceptor 不生效的常见原因

### 1. 全局注册的 Interceptor 和 Controller 级别的冲突

```typescript
// 全局：TransformInterceptor（包装 { code: 0, data, message: 'ok' }）
app.useGlobalInterceptors(new TransformInterceptor());

// Controller 级别：CacheInterceptor
@Controller('book')
@UseInterceptors(CacheInterceptor)
export class BookController {
  @Get('list')
  list() { return this.bookService.findAll(); }
}

// CacheInterceptor 先执行（更接近 Handler）
// → 如果是缓存命中，直接 return of(cachedData)
// → TransformInterceptor 不会执行（Observable 链被替换了）
```

### 2. 手动处理了 Response 导致 Interceptor 被跳过

```typescript
@Get('download')
download(@Res() res: Response) {
  res.download('/path/to/file');  // ← 手动操作了 res
  // Interceptor 不会执行，因为 res 已经被手动发送
}

// 修复：使用 passthrough
@Get('download')
download(@Res({ passthrough: true }) res: Response) {
  res.setHeader('Content-Disposition', 'attachment');
  return { filename: 'file.pdf' };  // ← Interceptor 能正常处理返回值
}
```

### 3. 异常跳过了 Interceptor 的 tap

```typescript
// Controller 抛异常
// → 进入 ExceptionFilter
// → Interceptor 的 tap(next) 的 next 回调不会执行
// → Interceptor 的 tap(error) 会执行

intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
  return next.handle().pipe(
    tap({
      next: () => console.log('Controller 正常才执行'),
      error: (err) => console.log('Controller 异常才执行', err.message),
    }),
  );
}
```

## 实战：图书管理系统的 Interceptor 配置

```typescript
// ===== main.ts =====
async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // 不需要 DI 的 Interceptor
  app.useGlobalInterceptors(
    new TransformInterceptor(),        // 统一响应格式（最外层）
  );

  await app.listen(3000);
}

// ===== app.module.ts =====
@Module({
  providers: [
    // 需要 DI 的 Interceptor
    {
      provide: APP_INTERCEPTOR,
      useClass: RequestLoggingInterceptor,  // 需要 Logger
    },
  ],
})
export class AppModule {}

// ===== book.controller.ts =====
@Controller('book')
export class BookController {
  @Get('list')
  @UseInterceptors(CustomCacheInterceptor)  // 只有列表接口需要缓存
  list() {}
}
```

## 注册优先级总结

| 优先级 | 级别 | 使用场景 |
|--------|------|---------|
| 1（最高） | Handler 级 `@UseInterceptors()` | 个别接口的特殊处理 |
| 2 | Controller 级 `@UseInterceptors()` | 整个模块的通用处理 |
| 3 | 全局 `APP_INTERCEPTOR` token | 需要 DI 的全局 Interceptor |
| 4（最低） | 全局 `app.useGlobalInterceptors()` | 不需要 DI 的全局 Interceptor |

> Interceptor 是 Nest 最强大的切面——既可以做日志监控，也能改变响应格式，甚至能实现缓存。Day 10 后你应该能熟练地写出 4 种 Interceptor 了。
