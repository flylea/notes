# Nginx Upstream 负载均衡

## 为什么需要负载均衡

```
单实例时代：
  浏览器 → Nginx → Nest:3000
                      ↑ 挂了就全挂

多实例时代：
  浏览器 → Nginx → upstream ┬→ Nest:3001
                             ├→ Nest:3002
                             └→ Nest:3003
                      ↑ 挂一台，其他继续服务
```

负载均衡解决两个核心问题：
1. **高可用**：一台实例挂了，流量自动切到其他实例
2. **高性能**：请求分散到多台机器，每台压力降低

## 基本 upstream 配置

```nginx
# /etc/nginx/nginx.conf 的 http 块中定义
upstream book_api {
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}

server {
    listen 80;
    server_name api.bookmanagement.com;

    location / {
        proxy_pass http://book_api;   # ← 指向 upstream 名称
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

**关键点**：`proxy_pass` 后面跟的是 upstream 的名字，前面要加 `http://`。

## 六种负载均衡策略

### 1. 轮询（Round Robin）——默认

```nginx
upstream book_api {
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}
```

```
请求 1 → 3001
请求 2 → 3002
请求 3 → 3003
请求 4 → 3001  ← 循环
```

**适用**：所有服务器配置相同，无状态服务。

### 2. 加权轮询（Weighted Round Robin）

```nginx
upstream book_api {
    server 127.0.0.1:3001 weight=3;   # 接收 3/6 = 50% 流量
    server 127.0.0.1:3002 weight=2;   # 接收 2/6 = 33% 流量
    server 127.0.0.1:3003 weight=1;   # 接收 1/6 = 17% 流量
}
```

```
请求流：3001、3001、3002、3001、3002、3003、3001...
```

**适用**：服务器配置不同（4 核 vs 2 核），给高配机器更多权重。

### 3. IP Hash

```nginx
upstream book_api {
    ip_hash;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}
```

```
用户 A (IP: 1.2.3.4) → hash(1.2.3.4) % 3 = 1 → 始终访问 3002
用户 B (IP: 5.6.7.8) → hash(5.6.7.8) % 3 = 0 → 始终访问 3001
```

**适用**：需要 Session 粘性的场景（不过现在更推荐用 Redis 做共享 Session）。

> 前端类比：这跟 Vue Router 的 `scrollBehavior` 里的 `savedPosition` 类似——记住用户之前的状态，下次还回原来的位置。

**ip_hash 的局限性**：
- 同一局域网（NAT）用户共享同一个出口 IP，会打到同一台
- 某台机器下线后，该机器的用户会被重新分配，可能丢失 Session

### 4. Least Connections（最少连接）

```nginx
upstream book_api {
    least_conn;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}
```

把请求发给当前活跃连接数最少的服务器——适合长连接场景（WebSocket、文件上传/下载）。

### 5. Fair（响应时间优先）

```nginx
# 需要 nginx-upstream-fair 模块（第三方）
upstream book_api {
    fair;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}
```

把请求发给当前响应最快的服务器。需要额外编译 Nginx 模块，生产环境用得不多。

### 6. Hash（自定义 Key）

```nginx
upstream book_api {
    hash $request_uri consistent;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}
```

用任意变量做 hash，`consistent` 关键字启用一致性哈希——节点增减时重映射最少。

| 策略 | 核心算法 | 适用场景 | Session 粘性 |
|------|---------|---------|-------------|
| 轮询 | 依次分发 | 无状态 API | 无 |
| 加权轮询 | 按比例分发 | 异构服务器 | 无 |
| ip_hash | IP 取模 | 需要粘性 | 有（IP 级别） |
| least_conn | 最少连接 | 长连接/WebSocket | 无 |
| fair | 响应最快 | 计算密集型 | 无 |
| hash | 自定义 key | 缓存亲和性 | 自定义 |

## 后端健康检查

Nginx 默认只做**被动健康检查**——请求失败后才标记为不可用。但可以配置**主动健康检查**：

```nginx
upstream book_api {
    server 127.0.0.1:3001 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:3002 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:3003 backup;  # 备用服务器，其他全挂才启用
}
```

- `max_fails=3`：30 秒内失败 3 次，标记为 down
- `fail_timeout=30s`：标记为 down 后，30 秒再试
- `backup`：备用服务器，只在所有主服务器不可用时才接收请求
- `down`：手动标记下线，维护时用

**Nest 端配合**——健康检查端点：

```typescript
// src/health/health.controller.ts
import { Controller, Get } from '@nestjs/common';

@Controller('health')
export class HealthController {
  @Get()
  check() {
    return {
      status: 'ok',
      timestamp: new Date().toISOString(),
      uptime: process.uptime(),
    };
  }
}
```

## 会话保持（Session Sticky）问题

负载均衡后，同一个用户的多次请求可能落到不同服务器。如果 Session 存在本地内存中，就会出现"登录丢失"。

```
用户登录请求 → 3001（登录成功，Session 存在 3001）
用户后续请求 → 3002（没有 Session，返回 401）
```

**三种解决方案**：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| ip_hash | 同 IP 打到同机器 | 零成本 | NAT 下失效 |
| Session 复制 | 多播 Session 到所有节点 | 透明 | 性能差、网络开销大 |
| **共享存储（推荐）** | Session 存 Redis | 无状态、任意扩展 | 需要额外维护 Redis |

```typescript
// 方案 3：Redis 共享 Session（Day 27 详细讲过）
import RedisStore from 'connect-redis';
import * as session from 'express-session';
import { Redis } from 'ioredis';

const redisClient = new Redis({ host: 'redis', port: 6379 });

app.use(
  session({
    store: new RedisStore({ client: redisClient }),
    secret: 'your-secret',
    resave: false,
    saveUninitialized: false,
    cookie: { secure: true, maxAge: 1000 * 60 * 60 * 24 }, // 24h
  }),
);
```

## Docker Compose 多实例部署

```yaml
# docker-compose.yml
services:
  nginx:
    image: nginx:alpine
    ports:
      - '80:80'
      - '443:443'
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - api

  api:
    build: .
    # 不暴露 ports——只通过内部网络访问（安全）
    expose:
      - '3000'
    environment:
      NODE_ENV: production
      DATABASE_URL: mysql://root:password@mysql:3306/book_management
    deploy:
      replicas: 3   # ← 3 个实例
```

```
                    ┌─────────────┐
  浏览器 → :80  →   │   Nginx     │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ api:3000 │    │ api:3000 │    │ api:3000 │
    │ (容器 1) │    │ (容器 2) │    │ (容器 3) │
    └──────────┘    └──────────┘    └──────────┘
           │               │               │
           └───────────────┼───────────────┘
                           ▼
                    ┌──────────┐
                    │  MySQL   │
                    │  Redis   │
                    └──────────┘
```

## 策略选择速查

```
我有几台配置相同的服务器
  → 默认轮询

我的服务器配置不同（2 核 / 4 核 / 8 核）
  → 加权轮询

我有 WebSocket 长连接 / 大文件上传
  → least_conn

我需要 Session 粘性但不想引入 Redis
  → ip_hash

我需要按 URL 缓存亲和性
  → hash $request_uri consistent

我需要 Nginx 级健康检查和主动摘除
  → upstream 的 max_fails + fail_timeout
```
