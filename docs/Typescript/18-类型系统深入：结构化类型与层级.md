# 第18章 类型系统深入：结构化类型与层级

TypeScript 的类型系统有两个核心支柱：**类型如何被比较**（结构化类型系统）和**类型之间的兼容关系如何排列**（类型层级）。理解了这两者，你才能从根源上解释日常开发中各种"看起来不对但竟然可以"或者"明明一样为什么报错"的场景。本章从这两个维度深入 TypeScript 的底层设计。

## 结构化类型系统

先看一段令人困惑的代码：

```typescript
class Cat {
  eat() {}
}

class Dog {
  eat() {}
}

function feedCat(cat: Cat) {}

feedCat(new Dog()); // ✅ 居然不报错？
```

`feedCat` 需要一只 `Cat`，却能传入 `Dog`？在 Java 或 C# 中这绝对是错误。这就是 **结构化类型系统（Structural Typing System）**：TypeScript 比较两个类型**不是看名称**，而是看**类型的内部结构**——即类型拥有的属性和方法。

### 鸭子测试

结构类型的别称是**鸭子类型（Duck Typing）**，得名于鸭子测试：

> 如果一只鸟走起来像鸭子，游泳像鸭子，叫起来也像鸭子，那么它就是鸭子。

换句话说，`Dog` 拥有 `Cat` 需要的全部接口（`eat` 方法），在结构化视角下，`Dog` 就是合法的 `Cat`。

但如果给 `Cat` 增加一个独有的方法，检查就会恢复：

```typescript
class Cat {
  meow() {}
  eat() {}
}

class Dog {
  eat() {}
}

function feedCat(cat: Cat) {}

feedCat(new Dog()); // ❌ Property 'meow' is missing in type 'Dog'
```

### "至少满足"原则

结构化比较的核心规则是：**要赋值给目标类型，源类型至少需拥有目标类型要求的全部成员**。多余的属性不会影响兼容性：

```typescript
class Cat {
  eat() {}
}

class Dog {
  bark() {}   // 多了没关系
  eat() {}
}

function feedCat(cat: Cat) {}

feedCat(new Dog()); // ✅ 满足 Cat 的所有成员即可
```

`Dog` 的 `bark` 方法可以视为在 `Cat` 基础上的扩展——结构化视角下，`Dog` 就是 `Cat` 的子类型。

### 属性级比较

结构化检查也是递归的。函数参数、对象属性的每个子成员都会被逐一比较：

```typescript
interface Pet {
  name: string;
}

let pet: Pet;
let dog = { name: "Lassie", owner: "Rudd Weatherwax" };

pet = dog; // ✅ dog 有 name: string 且有额外属性 owner
```

这里 `dog` 的类型是 `{ name: string; owner: string }`，拥有 `Pet` 要求的 `name: string`，因此兼容。整个比较过程**递归探索每个成员及其子成员的类型**。

但要注意**字面量直接赋值时的额外属性检查**（excess property checking）是一个不同的机制：

```typescript
let pet: Pet = { name: "Lassie", owner: "Rudd Weatherwax" }; // ❌
```

这是 TypeScript 的特殊保护——当你直接将字面量赋值给有明确类型的变量时，不允许出现目标类型未声明的属性，目的是防止拼写错误。这**不是**结构化类型系统的部分，而是一个附加的安全检查。

### 结构化类型 vs 标称类型

与结构化相对的是**标称类型系统（Nominal Typing System）**：两个类型兼容的前提是它们的**名称必须一致**或存在**显式的继承关系**。C++、Java、Rust 主要使用标称类型。

```typescript
// 结构化系统的"漏洞"
type USD = number;
type CNY = number;

const usd: USD = 100;
const cny: CNY = 200;

function addCNY(a: CNY, b: CNY) {
  return a + b;
}

addCNY(cny, usd); // ✅ 结构化认为都是 number，不报错
```

从业务语义来说，人民币和美元不应该直接相加。标称类型系统会禁止这种操作，因为 `USD` 和 `CNY` 是不同的名字。

### 在 TypeScript 中模拟标称类型

有两种方式可以在 TypeScript 中实现类似标称类型的效果：

#### 方式一：交叉类型 + 私有标记（纯类型层面）

```typescript
declare class TagProtector<T extends string> {
  protected __tag__: T;
}

type Nominal<T, U extends string> = T & TagProtector<U>;

type USD = Nominal<number, "USD">;
type CNY = Nominal<number, "CNY">;

const usd = 100 as USD;
const cny = 200 as CNY;

function addCNY(a: CNY, b: CNY) {
  return (a + b) as CNY;
}

addCNY(cny, cny); // ✅
addCNY(cny, usd); // ❌ 不能将类型"USD"分配给类型"CNY"
```

核心原理：`TagProtector` 的 `__tag__` 是 `protected`，两个不同标记的 `Nominal` 类型不能互相赋值（`private`/`protected` 成员在结构化比较中有特殊规则，后面会介绍）。

#### 方式二：类 + private 标记（运行时 + 类型）

```typescript
class CNY {
  private __tag!: void;
  constructor(public value: number) {}
}

class USD {
  private __tag!: void;
  constructor(public value: number) {}
}

const cny = new CNY(100);
const usd = new USD(100);

function addCNY(a: CNY, b: CNY) {
  return a.value + b.value;
}

addCNY(cny, cny); // ✅
addCNY(cny, usd); // ❌ 类型"USD"的参数不能赋给类型"CNY"的参数
```

方式二不仅有类型检查，还可以在运行时进行逻辑校验。选择哪种取决于你需要的是轻量类型约束还是运行时保障。

## 类型兼容性的具体规则

### 函数参数数量的兼容性

在比较函数类型时，参数数量少的函数可以赋值给参数数量多的函数：

```typescript
let x = (a: number) => 0;
let y = (b: number, s: string) => 0;

y = x; // ✅ x 的每个参数在 y 中都有对应
x = y; // ❌ y 有第二个必选参数而 x 没有
```

这看似反直觉，但实际非常实用。考虑 `Array#forEach` 的回调：

```typescript
// forEach 的回调期望 3 个参数：(element, index, array)
let items = [1, 2, 3];

// 但通常我们只需要第一个
items.forEach((item) => console.log(item)); // ✅ 完全合法
```

如果参数数量的兼容性反过来，每个 `forEach` 回调都必须写满三个参数——这不符合 JavaScript 的惯用写法。

### 函数返回值的兼容性

返回值是协变的（covariant）：源函数的返回值必须是目标函数返回值的子类型：

```typescript
let x = () => ({ name: "Alice" });
let y = () => ({ name: "Alice", location: "Seattle" });

x = y; // ✅ { name, location } 是 { name } 的子类型
y = x; // ❌ { name } 缺少 location
```

### 函数参数的双变（Bivariance）

TypeScript 默认情况下，函数参数的比较是**双变**的——既允许协变也允许逆变。这是为了兼容 JavaScript 中的常见模式：

```typescript
enum EventType { Mouse, Keyboard }

interface Event { timestamp: number; }

interface MouseEvent extends Event {
  x: number;
  y: number;
}

function listenEvent(eventType: EventType, handler: (e: Event) => void) {
  // ...
}

// 虽然 handler 的参数类型是 MouseEvent（更窄），但依然可以传入
// 这是协变方向，理论上不安全但实践中非常常用
listenEvent(EventType.Mouse, (e: MouseEvent) => console.log(e.x, e.y));
```

如果不允许这种写法，你每次都需要手动断言：`(e) => console.log((e as MouseEvent).x, (e as MouseEvent).y)`，极其繁琐。

通过 `strictFunctionTypes: true`（推荐开启，包含在 `strict` 中）可以将**属性风格**的函数签名改为正确的逆变检查，但**方法简写**保持双变：

```typescript
interface T {
  // 属性风格——受 strictFunctionTypes 影响，参数正确逆变
  handler: (x: Dog) => void;

  // 方法简写——不受影响，始终双变
  handle(x: Dog): void;
}
```

### 可选参数与剩余参数

可选参数和必选参数在函数兼容性比较中**可以互换**——源函数多余的 optional 参数不算错误，目标函数有 optional 参数但源函数没有也不算错误。从类型系统角度看这确实不严谨，但运行时传递 `undefined` 在大多数情况下效果相同，TypeScript 选择向实际便捷性妥协。

剩余参数被视为无限个可选参数。

### 枚举的兼容性

枚举与 `number` 互相兼容，但不同枚举类型之间不兼容：

```typescript
enum Status { Ready, Waiting }
enum Color { Red, Blue, Green }

let s = Status.Ready;
s = Color.Green; // ❌ 不同枚举类型之间不兼容
s = 1;           // ✅ 枚举兼容 number
```

### Class 的兼容性

Class 的实例比较只比较**实例成员**，不比较静态成员和构造函数：

```typescript
class Animal {
  feet: number;
  constructor(name: string, numFeet: number) {}
}

class Size {
  feet: number;
  constructor(numFeet: number) {}
}

let a: Animal;
let s: Size;

a = s; // ✅ 构造函数不同不影响
s = a; // ✅ 实例结构一致即可
```

#### private 和 protected 成员的特殊规则

当实例比较涉及 `private` 或 `protected` 成员时，规则变得严格：**源类型的 private/protected 成员必须来自目标类型中的同一个类声明**。这意味着：

- 同一个类的实例之间可以赋值给它的父类
- 不同继承链中结构相同的类之间**不能**兼容

```typescript
class A {
  private x: number = 0;
}

class B {
  private x: number = 0;
}

let a: A = new B(); // ❌ 虽然结构相同，但 private 成员来源不同
```

这正是前面模拟标称类型时利用的特性——`private __tag__` 使得结构相同的两个类变得不兼容。

### 泛型的兼容性

泛型参数仅在被实际消费为成员类型时才影响兼容性：

```typescript
interface Empty<T> {}

let x: Empty<number>;
let y: Empty<string>;

x = y; // ✅ T 未被使用时，两个类型结构一致
```

一旦泛型参数被用于成员类型，具体类型参数就产生差异：

```typescript
interface NotEmpty<T> {
  data: T;
}

let a: NotEmpty<number>;
let b: NotEmpty<string>;

a = b; // ❌ number 和 string 不兼容
```

对于**未指定泛型参数**的泛型类型，TypeScript 将未指定的类型参数全部替换为 `any` 后再检查兼容性：

```typescript
let identity = function <T>(x: T): T {
  return x;
};

let reverse = function <U>(y: U): U {
  return y;
};

identity = reverse; // ✅ (x: any) => any 与 (y: any) => any 一致
```

## 子类型 vs 赋值兼容性

TypeScript 中存在两种兼容性概念：

- **子类型兼容（Subtype Compatibility）**：基础的结构化子类型判断
- **赋值兼容（Assignment Compatibility）**：子类型兼容 + `any` 的特殊规则 + 枚举与 `number` 的双向兼容

实际开发中的大多数场景（包括 `extends` 和 `implements` 子句）使用的是赋值兼容性。

## 类型层级全览

理解了兼容性比较的规则后，我们可以构建出 TypeScript 中的完整类型层级链——从最顶层的 Top Type 到最底层的 Bottom Type：

```
        any ───── unknown
              ↑
           Object
              ↑
      ┌───────┴────────┐
      │  装箱类型        │
      │ String Number   │
      │ Boolean Symbol  │
      └───────┬────────┘
              ↑
         原始类型
      string number boolean
      symbol bigint
              ↑
      ┌───────┴────────┐
      │ object (非原始)  │
      └───────┬────────┘
              ↑
      同一基础类型的字面量联合类型
              ↑
         字面量类型
     "hello"  42  true
              ↑
            never
```

### 层级逐段验证

用条件类型可以直观地验证每段层级关系：

```typescript
// 字面量 < 对应的原始类型
type R1 = "hello" extends string ? 1 : 2;   // 1
type R2 = 42 extends number ? 1 : 2;         // 1
type R3 = true extends boolean ? 1 : 2;      // 1

// 字面量 < 包含它的联合类型 < 同一基础类型
type R4 = "a" extends "a" | "b" ? 1 : 2;              // 1
type R5 = "a" | "b" extends string ? 1 : 2;            // 1

// 原始类型 < 装箱类型 < Object
type R6 = string extends String ? 1 : 2;   // 1
type R7 = String extends Object ? 1 : 2;   // 1

// Object < any / unknown
type R8 = Object extends any ? 1 : 2;      // 1
type R9 = Object extends unknown ? 1 : 2;  // 1

// never < 字面量类型
type R10 = never extends "hello" ? 1 : 2;  // 1
```

### any 的特殊行为

`any` 在条件类型中表现出特殊行为——当 `any extends X` 被计算时，TypeScript 直接返回**两个分支的联合类型**：

```typescript
type T1 = any extends string ? 1 : 2;     // 1 | 2
type T2 = any extends never ? 1 : 2;      // 1 | 2
type T3 = any extends Object ? 1 : 2;     // 1 | 2
```

这是因为 `any` 代表了**任何可能的类型**——它同时包含让条件成立和不成立的两种情况，编译器直接把两种结果合并。

但反过来（`X extends any`）总是成立：

```typescript
type T4 = string extends any ? 1 : 2;     // 1
type T5 = never extends any ? 1 : 2;      // 1
```

`any` 和 `unknown` 的互相比较也各自成立：

```typescript
type T6 = any extends unknown ? 1 : 2;    // 1
type T7 = unknown extends any ? 1 : 2;    // 1
```

### `{}` 和 `object` 的微妙位置

`{}` 是一个"空对象"类型，在类型层级中它处在奇特的位置：

```typescript
type T8 = string extends {} ? 1 : 2;      // 1
type T9 = String extends {} ? 1 : 2;      // 1
type T10 = {} extends object ? 1 : 2;     // 1
type T11 = object extends {} ? 1 : 2;     // 1
type T12 = {} extends Object ? 1 : 2;     // 1
type T13 = Object extends {} ? 1 : 2;     // 1
```

理解这些结果需要区分两种不同的比较视角：

- **类型信息视角**：`{} extends object` 成立是因为 `{}` 是更精确的类型（空对象字面量 < `object`），即字面量是基础类型的子类型
- **结构化比较视角**：`object extends {}` 成立是因为在结构化视角下，`{}` 是一个空接口（没有任何属性要求），所有对象类型都满足它——它几乎是所有对象类型的"基类"

`string extends object` 不成立：

```typescript
type T14 = string extends object ? 1 : 2; // 2
```

`object` 只包含**非原始类型**（数组、对象、函数），`string` 是原始类型，不在范围内。

### 联合类型的子集判定

联合类型之间的层级，核心规则是**子集判定**——一个联合类型的所有成员都必须能在另一个联合类型中找到：

```typescript
type T15 = 1 | 2 | 3 extends 1 | 2 | 3 | 4 ? 1 : 2;  // 1
type T16 = 1 | 2 | 5 extends 1 | 2 | 3 | 4 ? 1 : 2;  // 2（5 不在目标中）
type T17 = 2 | 4 extends 1 | 2 | 3 | 4 ? 1 : 2;      // 1
```

### 数组和元组的层级

```typescript
type T18 = [number, number] extends number[] ? 1 : 2;       // 1
type T19 = [number, string] extends number[] ? 1 : 2;       // 2
type T20 = [number, string] extends (number | string)[] ? 1 : 2; // 1
type T21 = [] extends number[] ? 1 : 2;                      // 1
type T22 = number[] extends (number | string)[] ? 1 : 2;     // 1
type T23 = any[] extends number[] ? 1 : 2;                   // 1
type T24 = unknown[] extends number[] ? 1 : 2;               // 2
```

- `[number, number]` 所有成员都是 `number`，所以是 `number[]` 的子类型
- 一旦混入非 `number` 成员（如 `string`），就不能赋值给 `number[]`
- `[]` 可以赋值给任何数组类型，因为没有元素需要检查
- `any[]` 是任何数组的子类型（`any` 的"我要什么我就是什么"特性）
- `unknown[]` **不是** `number[]` 的子类型（`unknown` 不会自动匹配任何类型）

## 特殊类型的可赋值性速查表

以下表格来自 TypeScript 官方手册，总结了 `any`、`unknown`、`object`、`void`、`undefined`、`null`、`never` 之间的赋值关系。行表示"该类型可以赋值给谁"，列表示"什么可以赋值给该类型"。✓ 表示仅在 `strictNullChecks` 关闭时成立：

|  | any | unknown | object | void | undefined | null | never |
|---|---|---|---|---|---|---|---|
| any → |   | ✓ | ✓ | ✓ | ✓ | ✓ | ✕ |
| unknown → | ✓ |   | ✕ | ✕ | ✕ | ✕ | ✕ |
| object → | ✓ | ✓ |   | ✕ | ✕ | ✕ | ✕ |
| void → | ✓ | ✓ | ✕ |   | ✕ | ✕ | ✕ |
| undefined → | ✓ | ✓ | ✓ | ✓ |   | ✓ | ✕ |
| null → | ✓ | ✓ | ✓ | ✓ | ✓ |   | ✕ |
| never → | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |   |

核心规律总结：

- **一切皆可赋值给自身**
- `any` 和 `unknown` 在"什么可以赋给它们"上一致（来者不拒），但 `unknown` 除了 `any` 外什么都不赋值给——`unknown` 和 `never` 互为镜像
- `never` 可以赋值给一切，什么也不能赋值给 `never`
- `void` 除了 `any`/`unknown`/`never`/`undefined`/`null` 外不与任何类型互通
- `strictNullChecks` 关闭时，`null` 和 `undefined` 类似 `never`——可以赋给大多数类型

## 类型兼容性判断的实操技巧

在开发中判断两个类型是否兼容，可以按这个流程操作：

1. **用赋值语句快速验证**：写 `let a: TargetType = sourceValue`，看编辑器是否报错
2. **用条件类型进行推理**：`type IsSub = Source extends Target ? true : false`
3. **结构化比较**：逐项检查源类型的成员是否满足目标类型的成员要求
4. **注意特殊类型**：`any`、`never`、`unknown` 有额外规则
5. **注意 strictNullChecks**：开启与否影响 `null`/`undefined` 的兼容范围

## 类型系统的可靠性（Soundness）

TypeScript 的类型系统并非完全可靠（sound）——它有意允许了一些编译时无法确定安全性的操作。这些"不可靠"的妥协都是经过深思熟虑的，目的是在类型安全和 JavaScript 生态的实际使用习惯之间找到平衡：

- 函数参数的双变（兼容大量 JS 回调模式）
- 可选参数/必选参数在比较中的互换
- `any` 类型的"逃逸舱"

当开启 `strict` 模式（包括 `strictFunctionTypes`、`strictNullChecks` 等）后，大部分不安全的缺口会被堵上，这也是官方强烈推荐开启 strict 的原因。

## 本章小结

- **结构化类型系统**基于类型的内部结构（成员名 + 成员类型）判断兼容性，对名称不敏感
- 核心原则：**源类型至少拥有目标类型要求的全部成员**，多了没关系
- **标称类型系统**基于类型名称和显式继承判断，可通过 `private`/`protected` 标记在 TS 中模拟
- **类型层级**：never → 字面量 → 字面量联合 → 基础类型 → 装箱类型 → Object → any/unknown
- `any` 在条件类型中的特殊行为、`{}` 在不同比较视角下的双重身份、联合类型子集判定等细节需要熟练掌握
- TypeScript 的类型系统有意做了"不可靠"的妥协以适应 JavaScript 生态，开启 `strict` 能弥补大部分缺口
