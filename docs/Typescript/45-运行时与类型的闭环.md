# 第 45 章 运行时与类型的闭环

`tsc --noEmit` 全部通过，不等于手上这份数据可信。类型在 emit 阶段被删掉，`JSON.parse` 的返回值在编译期是 `any`。要让类型在运行时成立，只有一条路：在系统边界解析一次，之后只在内部传递已经校验过的值。

这一章讲清三件事：擦除发生在哪一步，为什么类型挡不住外部输入，以及 schema 与类型如何绑定成一个事实源。

## 擦除发生在 emit

TypeScript 编译器分几步：扫描、解析成 AST、绑定符号、类型检查、生成 JavaScript。类型信息全部产生于检查阶段，生成阶段不读它。

生成器只做一件事：按 AST 删掉类型语法。删掉的东西包括 `interface`、`type` 别名、泛型参数和实参、参数与返回值的注解、`as` 断言、访问修饰符。

```ts
interface Account {
  id: string;
  balance: number;
}

type Id = string | number;

function add<T extends number>(a: T, b: T): T {
  return (a + b) as T;
}

class Ledger {
  private total = 0;
  add(n: number): void {
    this.total += n;
  }
}

const account: Account = { id: "a1", balance: 10 };
const key: Id = "a1";
const sum = add(1, 2);

console.log(account, key, sum, new Ledger());
```

用 TS 7.0.2 生成到 es2022：

```bash
tsc --ignoreConfig --target es2022 --module esnext --outDir out1 erasure.ts
```

产物里没有一个类型标识符：

```js
"use strict";
function add(a, b) {
    return (a + b);
}
class Ledger {
    total = 0;
    add(n) {
        this.total += n;
    }
}
const account = { id: "a1", balance: 10 };
const key = "a1";
const sum = add(1, 2);
console.log(account, key, sum, new Ledger());
```

`add<T extends number>` 只剩 `add(a, b)`，`as T` 消失，`private total` 变成普通字段 `total`。运行时看这个对象，只看到 `{ id, balance }` 两个键，没有 `Account` 这个名字，也没有字段类型。

同一份源码加上声明输出，能看到类型去了哪里：

```bash
tsc --ignoreConfig --declaration --emitDeclarationOnly --outDir dts erasure.ts
```

```ts
interface Account {
    id: string;
    balance: number;
}
type Id = string | number;
declare function add<T extends number>(a: T, b: T): T;
declare class Ledger {
    private total;
    add(n: number): void;
}
declare const account: Account;
declare const key: Id;
declare const sum: 1 | 2;
```

`sum` 的类型是 `1 | 2`，这是检查器从字面量算出来的，`.js` 里只有 `add(1, 2)`。类型只存在于 `.d.ts` 和检查器内存中，两处都不在运行时。

这样设计有明确的好处。产物是标准 JavaScript，任何引擎都能跑，不需要运行时库；删掉类型后代码体积不变，执行没有额外开销；Babel、esbuild、swc 只做语法转换也能得到同样结果。代价是类型无法在运行时读取。想按类型派发、按类型序列化、按类型生成表单，都要另建元数据。

### 有运行时产物的例外

`enum` 和 `namespace` 会生成真实的 JavaScript 对象，这是少数几种在运行时留下痕迹的语法。

```ts
enum Status {
  Draft,
  Paid,
}

namespace Billing {
  export const currency = "CNY";
}

interface Shape {
  kind: "circle" | "square";
}

const orderStatus: Status = Status.Paid;
console.log(orderStatus, Billing.currency);
```

产物：

```js
"use strict";
var Status;
(function (Status) {
    Status[Status["Draft"] = 0] = "Draft";
    Status[Status["Paid"] = 1] = "Paid";
})(Status || (Status = {}));
var Billing;
(function (Billing) {
    Billing.currency = "CNY";
})(Billing || (Billing = {}));
const orderStatus = Status.Paid;
console.log(orderStatus, Billing.currency);
```

`Status` 是一个双向映射对象，`Billing` 是一个挂 `currency` 的对象。`interface Shape` 什么也没留下。

运行时能用的判断工具也很有限。`typeof` 只返回几种固定字符串，`instanceof` 查原型链，`in` 和 `Object.keys` 看属性。三者都表达不了“这个对象符合某个 interface”，因为 interface 在运行时不存在。

`const enum` 是反例：成员被内联成字面量，运行时连对象都没有。`isolatedModules` 下访问环境里的 `const enum` 会报 `error TS2748: Cannot access ambient const enums when 'isolatedModules' is enabled.`。

用 `enum` 留下运行时对象有代价。产物是一段立即执行函数，打包器无法做常量折叠，跨包引用时容易产生重复定义。现代代码更常用 `as const` 对象加联合类型：运行时是普通对象，类型由 `typeof` 推导，`Object.values` 能直接遍历。

### 元数据不是类型

装饰器元数据是另一套机制。旧实验装饰器配 `emitDecoratorMetadata` 能生成参数类型等少量信息，标准装饰器（TS 5.0 起）不再生成这些元数据。两者都不改变擦除的事实：反射拿到的只是编译器挑出来的片段，不是完整的类型结构。

需要类型信息参与运行时逻辑时，通常有三种做法。手写一张元数据表，和类型一起维护；把 schema 当元数据，类型从 schema 推导；用代码生成器在构建时扫描类型并产出表。第一种容易漂移，第二种把两个问题合成一个，第三种工具链最重。选哪种取决于要拿类型做什么。

## 两套定义必然漂移

类型和 schema 各写一遍，就是两个独立的事实源，没有任何编译器保证一致。改一处漏一处的后果，往往要在线上才看见。

```ts
import { z } from "zod";

type User = { id: string; name: string; age?: number };

const UserSchema = z.object({ id: z.string(), name: z.string() });

const user: User = UserSchema.parse({ id: "u1", name: "Ada", age: 30 });
console.log("parsed:", JSON.stringify(user));

if (user.age === undefined) {
  console.log("age 缺失，走默认分支");
}
// 输出：
// parsed: {"id":"u1","name":"Ada"}
// age 缺失，走默认分支
```

`z.object` 默认丢弃未声明的键，`age` 在解析后消失。`tsc` 没有任何报错，因为 `age` 是可选的；运行时也没有报错，因为解析成功。数据被静默截断。

如果 `age` 是必填字段，问题会换一种形式出现：类型里有 `age: number`，schema 里没有，parse 结果的类型是 `{ id, name }`，赋值给 `User` 时报错。但这只发生在类型和 schema 真正绑在一起时。手写两遍、中间用 `as` 或 `any` 连接的代码，错误会被一路吞掉。

最常见的吞错写法是把解析结果断言成类型：`const user = UserSchema.parse(raw) as User`。断言一加，编译器就不再比较两侧，schema 缺字段也看不出来。正确的连接方式是 `satisfies`，或者让类型从 schema 推导，中间不出现 `as`。

漂移的原因不在类型系统，在结构：同一个形状被描述了两次，两次之间没有约束。消除漂移只有三条路。

1. 以 schema 为唯一事实源，类型用 `z.infer` 推导。
2. 以类型为唯一事实源，schema 用工具生成。
3. 两个源都保留，加 `satisfies` 做单向检查，再加测试或生成校验。

漂移的发现成本很高，因为多数漂移不会立刻报错。可行的防线有两道。一是 CI 里对生成物做 diff，schema 或类型改动必须同时更新另一侧。二是准备一份覆盖全部字段的 fixture，同时喂给 schema 与类型断言，字段增减时测试先失败。

## 类型不能替代运行时校验

类型检查的输入是源码文本。外部数据在编译期没有形状，只有到运行时才有值。

`JSON.parse` 的签名返回 `any`。`any` 赋值给带类型的变量不产生检查，这是编译器主动放弃的。

```ts
type User = { id: string; name: string };

const raw: unknown = JSON.parse('{"id":"u1"}');
const user = raw as User;
console.log(user.name.toUpperCase());
// 编译通过，运行时抛出：
// TypeError: Cannot read properties of undefined (reading 'toUpperCase')
```

`as User` 只是让检查器停止追问，没有读取任何字段。运行时 `name` 不存在，调用 `toUpperCase` 时崩溃。

外部输入的范围比多数人想的大：

- HTTP 请求体、query、header
- 环境变量与命令行参数
- `localStorage`、`sessionStorage`、IndexedDB
- 配置文件、JSON 文件、CSV
- 消息队列的消息体
- RPC 与第三方 API 的响应
- 数据库里存放 JSON 的列

这些位置的数据来自进程外，编译期只知道它们是 `string`、`unknown` 或 `any`。`lib.dom.d.ts` 里写的 `fetch` 返回类型，只描述浏览器实现的接口，不检查服务端返回了什么。

协议变化时，类型和运行时的差距会放大。服务端新增必填字段、改字段类型、删字段，类型定义如果没同步，编译照样通过，因为类型是本地写的。回滚、灰度、多版本共存时，同一份类型要同时描述多个版本的响应，这在静态类型上很难表达，运行时按版本解析反而容易。

因此运行时校验只能用代码做。校验器读真实值，判断类型、范围、必填项，失败时给出可定位的错误。

`any` 在项目里通常从三处进来：`JSON.parse`、`response.json()`、以及各种 DOM 与 Node 回调的参数。`noImplicitAny` 只能拦住没写类型的声明，拦不住显式标注的 `any`。`--noCheck` 更进一步，连类型错误都不看，只生成 JavaScript。这几条路径的共同点是：编译器主动放弃，运行时也没有别人接手。

## zod 4.6.7 的现状

项目里装 zod 4.6.7。先确认版本，再写 schema。

```bash
npm i zod@4.6.7
node -e "console.log(require('zod/package.json').version)"
# 输出
# 4.6.7
```

zod 的 schema 是普通对象，定义完可以传参、可以组合、可以挂到类上。它不依赖装饰器，也不需要编译插件，Node 直接能跑。

基础用法是 `z.object` 套原子 schema，`safeParse` 跑校验，不抛异常。

```ts
import { z } from "zod";

const CreateUserSchema = z.object({
  id: z.string().min(1),
  name: z.string().min(1),
  email: z.email(),
  age: z.int().min(0).max(150),
});

const ok = CreateUserSchema.safeParse({ id: "u1", name: "Ada", email: "ada@example.com", age: 36 });
console.log("ok", ok.success);

const bad = CreateUserSchema.safeParse({ id: "u1", name: "Ada", email: "ada@", age: 1.5 });
if (!bad.success) {
  for (const issue of bad.error.issues) {
    console.log(issue.code, issue.path.join("."), issue.message);
  }
}
```

真实输出：

```bash
z.email ok true bad false [{"origin":"string","code":"invalid_format","format":"email","pattern":"...","path":[],"message":"Invalid email address"}]
z.int false true
```

`z.email()` 是顶层函数，v3 的 `z.string().email()` 仍然能用，但已标记为废弃。`z.int()` 只接受安全整数，`1.5` 直接失败。

对象 schema 还能派生。`extend`、`pick`、`omit`、`partial` 都返回新的 schema，类型跟着变，适合从基础模型派生输入输出模型。读模型去掉内部字段，写模型去掉服务端生成的字段，两边共享一份基础定义，字段只维护一次。

派生链太长会拖慢编译。官方文档建议在字段合并场景里用对象展开代替 `extend`，理由是 `extend` 的泛型推导成本高。派生层级控制在两层以内，超过就显式写一个 schema。

### error 参数

错误消息可以按字段覆盖，支持字符串和函数两种形式。

```ts
import { z } from "zod";

const NameSchema = z.string({ error: "名字必填" }).min(3, { error: "至少 3 个字符" });
const PortSchema = z.coerce.number().int().min(1, { error: "端口从 1 开始" });

const a = NameSchema.safeParse(undefined);
const b = PortSchema.safeParse("0");
console.log(a.error?.issues[0].message);
console.log(b.error?.issues[0].message);
```

```bash
名字必填
端口从 1 开始
```

函数形式能拿到 `issue`，按 `issue.input` 区分“缺失”和“类型不对”：

```ts
import { z } from "zod";

const Field = z.string({
  error: (issue) => (issue.input === undefined ? "必填" : "类型不对"),
});
console.log(Field.safeParse(undefined).error?.issues[0].message);
// 输出：必填
```

### v3 到 v4 的迁移表

官方 changelog 里列出的破坏性变化，实际用到的有这些。

| v3 写法 | v4 写法 | 说明 |
| --- | --- | --- |
| `z.string().email()` | `z.email()` | 方法形式仍可用，已废弃 |
| `z.number().int()` | `z.int()` | `int()` 只接受安全整数 |
| `z.string().uuid()` | `z.uuid()` 或 `z.guid()` | `uuid()` 按 RFC 校验，`guid()` 宽松 |
| `z.object({}).strict()` | `z.strictObject({})` | 方法已废弃 |
| `z.object({}).passthrough()` | `z.looseObject({})` | 方法已废弃 |
| `z.nativeEnum(E)` | `z.enum(E)` | `nativeEnum` 已废弃 |
| `z.record(z.string())` | `z.record(z.string(), z.number())` | 单参数形式已移除 |
| `z.literal(Symbol())` | 无 | 不再支持 symbol |
| `ZodString.create()` | `z.string()` | 静态工厂移除 |
| `errorMap` | `error` | 参数名变化 |

包的导出结构也变了。zod 4 的 `package.json` 同时导出 `zod/v3`、`zod/v4`、`zod/mini` 等子路径，主入口 `zod` 指向 v4。迁移期可以一部分文件先用 `zod/v3`，逐个替换，不需要一次性改完。`zod/mini` 是压缩体积的变体，API 以函数组合为主，写法和完整版有差别。完整变更清单见 [Zod 4 变更日志](https://zod.dev/v4/changelog)。

### 输入类型与输出类型

校验器可能改变值的类型，`z.input` 和 `z.output` 因此不同。边界上要先想清楚拿的是哪一种。

```ts
import { z } from "zod";

const EnvSchema = z.object({
  DEBUG: z.stringbool().default(false),
  PORT: z.coerce.number().int(),
});

type EnvInput = z.input<typeof EnvSchema>;
type EnvOutput = z.output<typeof EnvSchema>;

const input: EnvInput = { PORT: "3000" };
const output: EnvOutput = { DEBUG: false, PORT: 3000 };
console.log(input, output);
```

`z.input` 里 `DEBUG` 可选、`PORT` 是字符串；`z.output` 里 `DEBUG` 是必填布尔值、`PORT` 是数字。把 `EnvInput` 传给内部函数，等于把未校验的字符串带进了业务层。

## 用 satisfies 绑定 schema 与类型

`satisfies` 检查表达式是否满足某个类型，但不改变表达式自身的类型。把它放在 schema 上，可以让编译器检查 schema 的产出能不能当作目标类型用。

不用 `satisfies` 也能绑，写法是给变量加类型注解：`const UserSchema: z.ZodType<User> = z.object({...})`。这种写法会把变量类型收窄成 `z.ZodType<User>`，schema 的具体形状丢了。之后再访问 `UserSchema.shape`、调用 `UserSchema.extend(...)` 都拿不到完整类型，`parse` 的返回值也变成 `User` 而不是更具体的字面量。`satisfies` 保留 schema 原类型，只做检查，所以更适合这个场景。

```ts
import { z } from "zod";

type User = { id: string; name: string };

const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
}) satisfies z.ZodType<User>;

const user: User = UserSchema.parse({ id: "u1", name: "Ada" });
console.log(user);
```

这个方向检查的是“schema 至少能产出 `User`”。少一个必填字段就报错：

```ts
import { z } from "zod";

type User = { id: string; name: string };

const Missing = z.object({ id: z.string() }) satisfies z.ZodType<User>;
```

```bash
error TS1360: Type 'ZodObject<{ id: ZodString; }, $strip>' does not satisfy the expected type 'ZodType<User, unknown, $ZodTypeInternals<User, unknown>>'.
  The types of '_zod.output' are incompatible between these types.
    Property 'name' is missing in type '{ id: string; }' but required in type 'User'.
```

反方向不检查。schema 多出的字段，`satisfies` 认为无所谓，因为多字段的对象仍然可以当 `User` 用。

```ts
import { z } from "zod";

type User = { id: string; name: string };

const Extra = z.object({
  id: z.string(),
  name: z.string(),
  role: z.enum(["admin", "member"]),
}) satisfies z.ZodType<User>;

const parsed = Extra.parse({ id: "u1", name: "Ada", role: "admin" });
const typed: User = parsed;
console.log(typed.role);
```

```bash
direction2.ts(13,19): error TS2339: Property 'role' does not exist on type 'User'.
```

第 8 行的 `satisfies` 没有报错，第 13 行访问 `role` 才报错。`role` 在运行时确实存在，类型把它弄丢了。

两个方向的差异可以写成一张表。

| 检查方向 | `satisfies z.ZodType<T>` 是否检查 | 结论 |
| --- | --- | --- |
| schema 产出覆盖 T 的必填字段 | 检查 | 缺字段报 TS1360 |
| T 覆盖 schema 的全部字段 | 不检查 | schema 可以多字段 |
| 字段类型是否一致 | 检查 | 类型不兼容报错 |
| 字段的可选性是否一致 | 部分检查 | schema 必填、T 可选能过 |

`satisfies` 不做反向检查，原因是结构类型的赋值规则：字段更多的对象可以赋给字段更少的类型。`{ id, name, role }` 能当 `{ id, name }` 用，所以 schema 多字段不违反约束。要检查两个类型完全相等，只能引入类型级断言，例如 `Expect<Equal<z.infer<typeof S>, User>>`，失败时报错信息可读性差，维护成本高。

`satisfies` 的价值是防止 schema 少字段，不保证 schema 与类型完全同构。要同构，只能保留一个事实源：以 schema 为准时用 `z.infer`，以类型为准时用生成器。

## Standard Schema：一个接口兼容多个库

框架和库经常需要接受“用户传入的校验器”。zod、valibot、arktype 的 API 各不相同，为每个库写一套适配器，维护成本会翻几倍。

[Standard Schema](https://github.com/standard-schema/standard-schema) 规范定义了统一的校验接口：任何实现该规范的库，都暴露一个 `~standard` 属性。框架只依赖这个属性，不关心背后是哪个库。

接口的核心是 `validate`：输入 `unknown`，返回带 `value` 的成功结果，或带 `issues` 的失败结果。`issues` 里每条有 `message` 和可选的 `path`。`version` 固定为 1，`vendor` 标明来源库。

规范还留了一个可选的 `types` 字段，用来携带输入类型与输出类型。需要从 schema 推导 TS 类型的框架可以读它，不需要的框架可以忽略。可选字段的设计让实现方有取舍空间，也避免了类型是 `any` 时强制要求。

一个最小实现只需要三十行左右：

```ts
import { z } from "zod";

interface StandardSchemaV1<Input = unknown, Output = Input> {
  readonly "~standard": {
    readonly version: 1;
    readonly vendor: string;
    readonly validate: (value: unknown) => Result<Output> | Promise<Result<Output>>;
  };
}

type Result<Output> =
  | { readonly value: Output; readonly issues?: undefined }
  | { readonly issues: ReadonlyArray<Issue> };

interface Issue {
  readonly message: string;
  readonly path?: ReadonlyArray<PropertyKey | { readonly key: PropertyKey }>;
}

function parseWith<T>(schema: StandardSchemaV1<unknown, T>, value: unknown): T {
  const result = schema["~standard"].validate(value);
  if (result instanceof Promise) {
    throw new TypeError("异步校验器请用 await 版本");
  }
  if (result.issues) {
    throw new TypeError(result.issues.map((issue) => issue.message).join("; "));
  }
  return result.value;
}

const UserSchema = z.object({ id: z.string(), name: z.string() });

const user = parseWith(UserSchema, { id: "u1", name: "Ada" });
console.log("ok:", user.id, user.name);

try {
  parseWith(UserSchema, { id: "u1" });
} catch (error) {
  console.log("failed:", (error as Error).message);
}
```

运行结果：

```bash
ok: u1 Ada
failed: Invalid input: expected string, received undefined
```

`parseWith` 的参数类型只写了接口，没有出现 `z.ZodType`。换成 valibot 或 arktype 的 schema，函数不用改，因为它们的 `~standard` 满足同一份接口。

zod 4 原生实现了这个规范，不需要额外包装：

```ts
import { z } from "zod";

const NumberSchema = z.object({ n: z.number() });
const standard = NumberSchema["~standard"];

console.log(Object.keys(standard));
console.log(standard.version, standard.vendor);
console.log(standard.validate({ n: 1 }));

const bad = standard.validate({ n: "x" });
if (bad instanceof Promise) {
  throw new Error("unexpected async validator");
}
console.log(bad.issues);
```

```bash
[ 'validate', 'vendor', 'version', 'jsonSchema' ]
1 zod
{ value: { n: 1 } }
[
  {
    expected: 'number',
    code: 'invalid_type',
    path: [ 'n' ],
    message: 'Invalid input: expected number, received string'
  }
]
```

`validate` 的返回值是联合类型，判断 `issues` 存在即可区分成功与失败。zod 还额外挂了 `jsonSchema`，用于生成 JSON Schema，不属于规范要求。

### 规范解决与没解决的问题

解决的是适配成本：框架层写一次 `parseWith`，库用户传任意兼容 schema 都能用。类型参数 `Output` 由 schema 推断，调用方拿到的返回值是有类型的。

没解决的有两类。第一是异步：`validate` 允许返回 Promise，同步函数 `parseWith` 遇到异步校验器会拿到 Promise 而不是结果。框架要支持异步，签名必须改成 `async` 并 `await`。第二是语义差异：各库对 `transform`、`default`、`coerce` 的支持不完全一致，规范只统一了“校验通过或失败”，没统一“值被怎样改写”。

因此规范适合库和框架的作者，应用代码直接用 zod 的 API 更省事。

规范的接口由几个校验库的作者共同提出，站点是 standardschema.dev。版本号写死为 1，是为了让框架按版本分支，未来出新版时不影响旧实现。判断一个库是否兼容，看它的 schema 上有没有 `~standard` 属性即可，不需要读文档确认。

## 从一方生成另一方

### 类型优先：从 OpenAPI 生成类型

接口契约以 OpenAPI 文档为准时，类型可以从文档生成。[openapi-typescript](https://github.com/openapi-ts/openapi-typescript) 7.13.0 读 JSON 或 YAML，输出 `.d.ts`。

```bash
npx openapi-typescript openapi.json -o api-schema.d.ts
# ✨ openapi-typescript 7.13.0
# 🚀 openapi.json → api-schema.d.ts [22.5ms]
```

生成的 `paths` 结构把路径、方法、参数、响应串在一起：

```ts
export interface paths {
    "/orders/{id}": {
        get: {
            parameters: {
                path: {
                    id: string;
                };
            };
            responses: {
                200: {
                    content: {
                        "application/json": {
                            id: string;
                            status: "draft" | "paid";
                        };
                    };
                };
            };
        };
    };
}
```

消费方用索引访问取出响应类型，写错的值会被编译器挡住：

```ts
import type { paths } from "./api-schema.js"; // 由上一段命令生成

type OrderResponse = paths["/orders/{id}"]["get"]["responses"][200]["content"]["application/json"];

export function statusOf(order: OrderResponse): string {
  return order.status;
}

const bad: OrderResponse = { id: "o1", status: "cancelled" };
```

`./api-schema.js` 是上一段命令生成的类型文件；单块编译报 `TS2307`，把生成结果放到同目录，下面的 `TS2322` 才复现得出来。

```bash
consume.ts(9,40): error TS2322: Type '"cancelled"' is not assignable to type '"draft" | "paid"'.
```

这套流程的边界很清楚：生成的是类型，不是校验器。运行时收到的 JSON 仍然是 `unknown`，符合类型只是约定。要在运行时确认响应，仍需一次 `safeParse` 或手写检查。生成物随契约更新，不需要手改，也不能手改。

### schema 优先：从类型生成 schema

反过来，`ts-to-zod` 5.1.0 读 TypeScript 源码，输出 zod schema。

```bash
npx ts-to-zod model.ts model.zod.ts
# ❯ Write files
# ✔ Write model.zod.ts
# 🎉 Zod schemas generated!
```

```ts
export interface Kind {
  at: Date;
  counts: Record<string, number>;
  labels: string[];
}
```

生成结果：

```ts
// Generated by ts-to-zod
import { z } from "zod";

export const kindSchema = z.object({
    at: z.date(),
    counts: z.record(z.string(), z.number()),
    labels: z.array(z.string())
});
```

`Date`、`Record`、数组都转对了，生成的代码用 TS 7.0.2 编译通过。`Record` 用的是 v4 的双参数形式，说明工具已经跟上新 API。

复杂类型会失败，失败方式还分两种。带泛型的类型直接在生成阶段终止：

```bash
✖ Generate zod schemas [FAILED: Type with generics are not supported!]
    Error: Type with generics are not supported!
```

品牌类型能生成，但工具自己校验时发现两侧不兼容：

```bash
✖ Validate generated types [FAILED: 'brandedIdSchema' is not compatible with 'BrandedId':
Argument of type 'string & Record<string, never>' is not assignable to parameter of type 'BrandedId'.
  Property '[brand]' is missing in type 'String & Record<string, never>' but required in type '{ readonly [brand]: true; }'.
```

生成器把品牌类型降级成了 `string & Record<string, never>`，运行时校验不回来。这类类型只能手写 schema 补 `brand`。

### 两种方向的取舍

| 维度 | 契约优先（生成类型） | 类型优先（生成 schema） |
| --- | --- | --- |
| 事实源 | OpenAPI 文档 | TypeScript 类型 |
| 生成物 | `.d.ts`，只参与编译 | zod schema，参与运行时 |
| 漂移方向 | 文档改了要重新生成 | 类型改了要重新生成 |
| 运行时保证 | 没有，需另配校验 | 有，schema 本身能校验 |
| 失败场景 | 文档与实现不一致 | 泛型、品牌、条件类型无法转换 |

生成的产物是起点，不是终点。类型优先路线要检查生成器支持哪些语法，把不支持的标注出来手写；契约优先路线必须在出口补一次校验，否则类型只是文档。

生成文件是否入库，两种做法都成立。入库的好处是 review 时能看到契约变化，坏处是容易忘记重新生成。构建时生成的好处是永远最新，坏处是构建依赖文档文件与工具链。选一种写进 README，别让后来的人猜。

## 边界解析

原则只有一条：数据进进程时解析一次，之后只在内部传递解析后的值。

```ts
import { z } from "zod";

const CreateOrderSchema = z.object({
  customerId: z.string().min(1),
  items: z.array(z.object({ sku: z.string(), qty: z.int().positive() })).min(1),
});

type CreateOrder = z.infer<typeof CreateOrderSchema>;

type OrderEvent = { type: "order.created"; customerId: string; total: number };

function createOrder(input: CreateOrder): OrderEvent {
  const total = input.items.reduce((sum, item) => sum + item.qty, 0);
  return { type: "order.created", customerId: input.customerId, total };
}

export function handle(raw: unknown): { status: number; body: unknown } {
  const parsed = CreateOrderSchema.safeParse(raw);
  if (!parsed.success) {
    const detail = parsed.error.issues.map((issue) => ({
      path: issue.path.join("."),
      message: issue.message,
    }));
    return { status: 400, body: { error: "invalid_request", detail } };
  }
  return { status: 201, body: createOrder(parsed.data) };
}

console.log(JSON.stringify(handle({ customerId: "c1", items: [{ sku: "s1", qty: 2 }] })));
console.log(JSON.stringify(handle({ customerId: "", items: [] })));
```

```bash
{"status":201,"body":{"type":"order.created","customerId":"c1","total":2}}
{"status":400,"body":{"error":"invalid_request","detail":[{"path":"customerId","message":"Too small: expected string to have >=1 characters"},{"path":"items","message":"Too small: expected array to have >=1 items"}]}}
```

`handle` 收 `unknown`，`createOrder` 收 `CreateOrder`。`as` 断言一次也没出现，类型是靠解析得到的，不是声明的。

### 边界清单

| 位置 | 解析对象 | 失败处理 |
| --- | --- | --- |
| HTTP handler | body、query、header | 返回 400，带 issues |
| 环境变量 | `process.env` | 启动即退出，打印缺失项 |
| 配置文件 | `JSON.parse` 的结果 | 启动即退出 |
| `localStorage` | `getItem` 的字符串 | 清除并回到默认值 |
| 消息队列 | 消息体 | 进死信队列 |
| 第三方 API | 响应 JSON | 重试或降级 |
| 数据库 | JSON 列、聚合结果 | 记录并跳过该行 |
| 命令行 | `process.argv` | 打印用法后退出 |

这些位置有一个共同点：数据的生产者不在当前进程里，类型系统看不到它。

入口函数的命名值得区分。`handleCreateOrder(raw: unknown)` 负责解析，`createOrder(input: CreateOrder)` 负责业务。两个名字并存时，code review 里能直接看出谁该处理 `unknown`。service 层不 import zod，只依赖推导出的类型，这样换校验库或写测试都不受影响。

数据库读出的 JSON 列常被忽略。ORM 返回的字段类型由模型声明，JSON 列的内容不在模型里，读出来是 `unknown` 或 `any`。在 repository 层解析一次，比在业务层到处断言干净。

内部函数不再重复校验。一个 service 接收 `CreateOrder`，说明上游已经解析过；再校验一次只会增加耗时，拿不到新信息。要区分“入口类型”和“内部类型”，可以给入口函数单独命名，例如 `handleCreateOrder` 与 `createOrder`。

这套结构对应领域驱动设计里的防腐层。外部模型在边界被翻译成内部模型，内部代码不感知外部协议。差别在于，这里的“翻译”由 schema 完成，失败时还能给出结构化错误。边界之外的数据格式变了，只改 schema 与翻译函数，业务代码不动。

### 出口也要解析

返回给外部之前，同样要对出口数据做一次检查。第三方 API 的响应、要写进数据库的 JSON 列、发给前端的 DTO，都属于出口。类型在这几处同样只是声明。

出口解析的代价比入口低，因为它校验的是自己构造的数据，失败通常意味着代码 bug，应当直接抛错让监控发现，而不是返回 400。

出口失败要单独计数。指标名可以是 `validation_failed_total`，加一个 `direction` 标签区分 inbound 与 outbound。inbound 上升说明客户端在发坏数据，outbound 上升说明数据源或代码出了问题，两种告警的处理人不同。

### 性能与位置

边界解析的量很小：一个请求一次，一条消息一次。真正拖慢吞吐的是在热路径里反复解析同一个对象，例如循环里对每个元素调一次 `safeParse`。这种情况改成循环外解析整批，或者解析一次后向下传引用。

校验失败的处理要放在边界内。handler 拿到失败结果就返回，不要继续调用业务函数。业务函数只接受解析后的类型，签名里没有 `unknown`，也就没有“忘了检查”的空间。

zod 4 的解析器有 JIT 优化，常规对象解析在微秒级。是否需要换更快的库，先测再决定，不要凭印象优化。

## 错误处理

`safeParse` 一次收集全部问题，不会在第一个错误处停下。

```ts
import { z } from "zod";

const AddressSchema = z.object({
  city: z.string().min(1),
  zip: z.string().regex(/^\d{5}$/),
});

const OrderSchema = z.object({
  id: z.string(),
  customer: z.object({ name: z.string().min(1), email: z.email() }),
  address: AddressSchema,
  items: z.array(z.object({ sku: z.string(), qty: z.int().positive() })).min(1),
});

const input = {
  id: "o1",
  customer: { name: "", email: "nope" },
  address: { city: "", zip: "12" },
  items: [],
};

const result = OrderSchema.safeParse(input);
if (!result.success) {
  for (const issue of result.error.issues) {
    console.log(`${issue.path.join(".") || "(root)"} | ${issue.code} | ${issue.message}`);
  }
  console.log(JSON.stringify(z.flattenError(result.error)));
  console.log(z.prettifyError(result.error));
}
```

```bash
customer.name | too_small | Too small: expected string to have >=1 characters
customer.email | invalid_format | Invalid email address
address.city | too_small | Too small: expected string to have >=1 characters
address.zip | invalid_format | Invalid string: must match pattern /^\d{5}$/
items | too_small | Too small: expected array to have >=1 items
```

五条问题各自带 `path`，前端能直接定位到字段。`path` 是数组，嵌套对象会给出完整路径。

`parse` 和 `safeParse` 的选择规则很简单。输入可能不合法时用 `safeParse`，因为失败是预期内的；输入应当合法时用 `parse`，失败意味着代码有 bug，抛异常正好进监控。服务端处理的用户输入属于前者，内部函数之间的调用属于后者。

zod 4 提供三个整理函数。`flattenError` 按顶层字段分组，`treeifyError` 保留嵌套结构，`prettifyError` 生成给人看的文本。

```bash
{"formErrors":[],"fieldErrors":{"customer":["Too small: expected string to have >=1 characters","Invalid email address"],"address":["Too small: expected string to have >=1 characters","Invalid string: must match pattern /^\\d{5}$/"],"items":["Too small: expected array to have >=1 items"]}}

✖ Too small: expected array to have >=1 items
  → at items
✖ Too small: expected string to have >=1 characters
  → at customer.name
✖ Invalid email address
  → at customer.email
✖ Too small: expected string to have >=1 characters
  → at address.city
✖ Invalid string: must match pattern /^\d{5}$/
  → at address.zip
```

`flattenError` 会把嵌套字段压到第二层，深层路径的信息会丢，前端要精确显示就用 `issues` 或 `treeifyError`。`prettifyError` 只适合日志和命令行。

schema 本身也需要测试。常规做法是准备合法与非法两份 fixture，合法样本解析后与期望对象深比较，非法样本断言失败的 `path` 与 `code`。字段一多，手写 fixture 容易漏，可以用属性测试工具生成随机输入，重点检查“解析器不抛意外异常”和“合法输入恒等”两条性质。

### 与 tsc 报错的分工

两类错误在时间上不重叠。

| 时间 | 工具 | 检查对象 | 例子 |
| --- | --- | --- | --- |
| 开发期 | tsc | 源码内部的类型关系 | 参数不匹配、缺少属性 |
| 运行期 | zod | 外部数据的形状 | 缺字段、类型错、格式错 |

错误还要分等级。字段级错误可以提示用户改；结构级错误说明调用方用错了接口，应当返回明确的协议错误；解析器自身抛出的异常属于程序 bug，要进错误监控。三类的日志级别、告警渠道、重试策略都不同，混在一起会让排查变慢。

`tsc` 通过只说明代码内部自洽。`zod` 通过只说明这一份数据当期符合 schema。两者都不能替代对方。

日志里要记录 `path` 与 `code`，不要回显原始输入值。用户输入可能包含密码、token、手机号，写进日志会造成泄漏。需要排查时记录输入的长度或哈希。

给前端的错误码直接用 `issue.code` 映射，不要透传库的英文原文。`too_small`、`invalid_format` 这类码是稳定接口，文案由前端按语言维护。`issue.message` 会随库版本变化，写进接口契约就要跟着升级。

## 四条判据与反模式

要不要运行时校验，按四条判据决定。

| 判据 | 判断 | 处理 |
| --- | --- | --- |
| 数据来自进程外 | 是 | 必须校验 |
| 格式由外部控制，可能变 | 是 | 必须校验 |
| 失败代价高（钱、权限、持久化） | 是 | 必须校验 |
| 编译期能证明形状 | 能 | 可以只用类型 |

四条判据从强到弱：第一、二条命中就校验，第三条命中要在写入前校验，第四条只在纯内部函数之间成立。

落地时把判据写进 review 清单，比写在文档里有效。可以加两条规则：入口参数是 `unknown` 或 `any` 的函数必须调用 `safeParse`；`as` 只允许出现在解析函数内部。这两条能用 grep 粗略检查，也能在 code review 里快速判断。

反模式清单：

| 反模式 | 后果 | 改法 |
| --- | --- | --- |
| 类型和 schema 各写一遍，没有绑定 | 静默漂移 | 用 `z.infer` 或生成器，保留一个源 |
| `as` 越过边界 | 编译通过、运行崩溃 | 换成 `safeParse` |
| 只校验顶层字段 | 嵌套字段漏检 | schema 嵌套写全 |
| 内部重复校验同一对象 | 白耗 CPU | 只在入口解析一次 |
| 用 schema 校验业务规则 | 形状对了，规则不对 | 形状用 schema，余额用业务代码 |
| 把校验失败当程序错误 | 用户输入错误打成 500 | 区分 400 与 500 |

最后一条容易被忽略。`safeParse` 的失败是预期内的，属于用户输入问题；`parse` 抛出的 `ZodError` 在服务端代码里通常意味着 schema 与数据源不一致，属于程序 bug。两种错误走不同的上报路径。

团队落地时先统一入口，再统一类型来源。入口统一之后，`unknown` 的流动范围就被限制在边界函数里；类型来源统一之后，`z.infer` 与手写类型不会同时存在。两件事分开做，每个 PR 的改动量都可控。

边界解析只解决形状问题，不解决业务规则。金额上限、库存是否足够、用户有没有权限，这些判断依赖数据库与当前状态，schema 表达不了，仍要写成独立函数并单独测试。

判据之外还有成本约束。引入校验器会增加依赖体积与启动时间，纯前端应用可以只在调用 API 的边界校验。服务端要处理不可信输入，范围更大。

### 迁移顺序

已有项目补运行时校验，按三步走效率最高。

第一步，找出所有入口，先加顶层 `safeParse`，失败返回 400。这一步不改类型定义，只加检查。

第二步，把手写的类型换成 schema 推导，删掉重复的 `type`。`z.infer` 生成的类型自动与 schema 同步。

第三步，删掉边界上的 `as` 与 `any`，让编译器检查入口函数只接收解析后的类型。改完之后，`unknown` 只出现在入口参数上，内部函数签名里不再有 `unknown`。

三步之间可以分批提交，每一步都能独立上线。

## 用不上的时候

### 数据全程由自己构造

内部数据结构由自己的代码创建，类型就是事实，运行时不会出现别的形状。这时再套一层 `z.object`，是把同一个约束写两遍。

### 边界已经被上游校验

请求体在网关或框架层已按 schema 校验，应用里再 `parse` 一次是重复开销。把校验通过的类型传进来，内部不再重复检查。

### 只用一家运行时校验库

项目只依赖 zod，不打算换库，也不需要和别的库互操作。Standard Schema 解决的是跨库问题，没有跨库需求时这层抽象不带来收益。
