# 第 44 章 装饰器元数据与依赖注入

装饰器元数据不是类型系统的产物。它是装饰器在运行时往一个普通对象里写的键值。类型只决定编译器愿意写什么，愿不愿意写，写到哪。依赖注入容器拿到这些键值，拼出构造参数表，再按 token 取出实例。两代装饰器机制的差别，就在写入口和存放位置。

## 元数据是挂在类上的普通对象

[reflect-metadata](https://github.com/rbuckton/reflect-metadata) 提供四个调用。`Reflect.defineMetadata` 写，`Reflect.getMetadata` 读，`Reflect.getOwnMetadata` 只读自身，`Reflect.getMetadataKeys` 列出键。键可以是字符串，也可以是 symbol。值不做限制，通常是对象、数组或函数引用。

```ts
import "reflect-metadata";

class Cache {
  ttl = 60;
}

class ChildCache extends Cache {}

const Key = Symbol("cache:options");

Reflect.defineMetadata("role", "singleton", Cache);
Reflect.defineMetadata(Key, { ttl: 60, warm: true }, Cache);

console.log(Reflect.getMetadata("role", Cache));
console.log(Reflect.getMetadata(Key, Cache));
console.log(Reflect.getOwnMetadataKeys(Cache).map(String));
console.log("Child own:", Reflect.getOwnMetadata("role", ChildCache));
console.log("Child lookup:", Reflect.getMetadata("role", ChildCache));
```

`ChildCache` 自己没有写元数据，`getOwnMetadata` 返回 `undefined`，`getMetadata` 沿原型链找到父类的值。这个区别在继承场景里很关键，后面讲新机制时会再碰到。

```bash
singleton
{ ttl: 60, warm: true }
[ 'role', 'Symbol(cache:options)' ]
Child own: undefined
Child lookup: singleton
```

`reflect-metadata` 的存储不是类属性。它用一张内部表，键是目标对象，值是元数据字典。`Reflect.metadata(...)` 是同一套 API 里的装饰器形式，等同于对目标调用 `defineMetadata`。编译器产出的 `__metadata` 调用，最终就落在这张表里。

这张表用 `WeakMap` 实现，键是对象，所以元数据不会拦住目标对象被回收。查找时先看目标自身的表项，找不到再沿原型链往上走，这就是 `getMetadata` 与 `getOwnMetadata` 的差别。元数据的查找没有缓存，原型链每深一层就多一次表查询。大规模使用反射的框架通常把读取结果再缓存到自己的一层，避免在热路径上反复走原型链。写入也不会触发任何类型检查，键写错、值写错，编译器都看不见，只有读的时候才发现拿到的是 `undefined`。

[TC39 装饰器提案](https://github.com/tc39/proposal-decorators) 选了另一个位置。元数据放在类自身的 `Symbol.metadata` 属性上，标准库里不需要额外库，也不需要全局注册表。这是两代机制最实际的分歧。

## 两代机制的分工

| 项目 | 旧机制 | 新机制 |
| --- | --- | --- |
| 开启方式 | `experimentalDecorators` 加 `emitDecoratorMetadata` | 默认行为，不需要开关 |
| 写入者 | 编译器在 emit 阶段插入调用 | 装饰器在运行时写 `context.metadata` |
| 存放位置 | `reflect-metadata` 的全局存储 | 类自身的 `Symbol.metadata` 属性 |
| 运行依赖 | 必须 `import "reflect-metadata"` | 引擎支持 `Symbol.metadata`，否则 polyfill |
| 自动类型信息 | 有，但只到运行时构造器一级 | 没有，存什么由装饰器决定 |
| 典型用户 | NestJS、TypeORM 旧写法、class-validator | 框架自定义元数据、表结构描述 |

旧机制的能力来自编译器。装饰器什么都没做，类型信息已经躺进存储。新机制把写入权交给装饰器，编译器只负责建好那个对象。

两代机制的提案状态也不同。TC39 的装饰器提案与元数据提案都停在第 3 阶段，TypeScript 5.0 先落地了装饰器语法，[TypeScript 5.2](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-2.html) 补上 `context.metadata`。语法进了 TypeScript，不等于进了 JavaScript 运行时。Node 26 的 V8 还没有 `Symbol.metadata`，代码里不 polyfill 就无法使用新机制。旧机制反过来，语法与元数据都靠 TypeScript 自己的编译产物，只要开着两个开关，在任何能跑 CommonJS 或 ESM 的运行时里都能工作，代价是永远绑定 `reflect-metadata`。

这个差异决定了生态迁移的节奏。框架可以把元数据搬到 `Symbol.metadata`，第三方库却要同时支持两种放置方式，于是常见做法是先封装一层读取函数，先查 `Symbol.metadata`，查不到再查 `Reflect.getMetadata`。应用代码感知不到这个分支，但它在每个依赖注入容器里都存在。

## 旧机制：编译器插入 __metadata

两个开关都要开。`experimentalDecorators` 打开旧语法，`emitDecoratorMetadata` 让编译器补类型信息。`target` 至少到 `es2015`，`es2022` 省去降级噪音。

```json
{
  "compilerOptions": {
    "target": "es2022",
    "module": "commonjs",
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,
    "strict": true
  }
}
```

两个开关的分量不同。TypeScript 5.0 起，不写 `experimentalDecorators` 就是 TC39 装饰器语义，写类型签名不同的装饰器会报 TS1240 系列错误。加上这个开关，语义切回旧版，编译产物改用 `__decorate` 辅助函数。`emitDecoratorMetadata` 只在旧语义下有意义，单独开启会报 TS5052，组合开关的顺序无关。`target` 至少到 `es2015`，因为产物的 `Reflect` 调用与 `Object.getOwnPropertyDescriptor` 用法依赖 ES2015 的运行时。

这套组合是 NestJS、TypeORM 一类项目的标准 tsconfig。它们的编译产物依赖 `__decorate` 与 `__metadata`，也依赖 `reflect-metadata` 的全局补丁。换到新装饰器，辅助函数消失，元数据对象由类自己携带，整个链路不需要这两个包，但需要目标运行时支持 `Symbol.metadata`，或者自己补一个 polyfill。

下面这段是旧机制的最小可用形态。类装饰器读取构造参数的类型，参数装饰器给个别位置换成显式 token。

```ts
import "reflect-metadata";

type Token = string;

const tokensKey = "repo:tokens";

function Inject(token: Token): ParameterDecorator {
  return (target, _key, index) => {
    const tokens = Reflect.getOwnMetadata(tokensKey, target) ?? [];
    tokens[index] = token;
    Reflect.defineMetadata(tokensKey, tokens, target);
  };
}

function Repo(target: Function): void {
  const args = (Reflect.getMetadata("design:paramtypes", target) ?? []).map(
    (type: Function, index: number) => {
      const token = (Reflect.getOwnMetadata(tokensKey, target) ?? [])[index];
      return token ?? type.name;
    },
  );
  console.log("wired:", args);
}

class Logger {
  log(message: string): void {}
}

interface Clock {
  now(): number;
}

@Repo
class ArticleRepo {
  constructor(
    private logger: Logger,
    @Inject("clock") private clock: Clock,
    private tags: string[] = [],
  ) {}
}
```

编译后的关键片段如下。`__decorate` 先应用参数装饰器，再应用类装饰器。`__metadata` 是普通函数调用，参数是真实的运行时值。

```js
var __metadata = (this && this.__metadata) || function (k, v) {
    if (typeof Reflect === "object" && typeof Reflect.metadata === "function")
        return Reflect.metadata(k, v);
};

ArticleRepo = __decorate([
    Repo,
    __param(1, Inject("clock")),
    __metadata("design:paramtypes", [Logger, Object, Array])
], ArticleRepo);
```

`Logger` 是类，拿到构造器。`Clock` 是接口，编译后不存在，退化成 `Object`。`tags` 的静态类型是 `string[]`，运行时的构造器只有 `Array`，元素类型丢了。类装饰器输出的参数表是 `['Logger', 'clock', 'Array']`，第一个靠推断，第二个靠显式 token。

`__decorate` 的循环从数组末尾往前，所以写在下面的装饰器先执行，`__param` 与 `__metadata` 都在真正装饰之前入栈。循环体里按参数个数分派：三个参数走属性装饰器调用，四个参数走方法装饰器调用并把返回值写回描述符。`r` 保存上一个装饰器返回的替换值，链式替换靠它传递。`Reflect.decorate` 存在时直接交给它，这是给旧版 polyfill 留的扩展点，现代实现不会走到那个分支。

`__param` 只是一个闭包工厂。它返回 `function (target, key) { decorator(target, key, paramIndex); }`，把参数下标补进调用参数。所以参数装饰器拿到的第三个参数永远是数字，类型签名里写成别的会报错。这层包装也解释了为什么参数装饰器不能改变参数的值，它只有写入元数据的能力，构造器调用发生在之后。

`__metadata` 的实现有一处守卫。`Reflect.metadata` 不是 JavaScript 内置方法，它来自 `reflect-metadata` 的 polyfill。没有引入这个库，条件为假，函数直接返回 `undefined`，元数据静默丢失。不会报错，容器随后拿不到任何类型。

```ts
function track(target: Function): void {}

class Logger {}

@track
class Repo {
  constructor(private logger: Logger) {}
}

const reflect = Reflect as unknown as {
  metadata?: unknown;
  getMetadata?: (key: string, target: Function) => unknown;
};

console.log("Reflect.metadata:", typeof reflect.metadata);
console.log("design:paramtypes:", reflect.getMetadata?.("design:paramtypes", Repo));
```

加一行 `import "reflect-metadata"` 之后，同样的代码输出完全不同。没有引入库时，`Reflect.metadata` 是 `undefined`，`design:paramtypes` 也读不到；引入之后，前者变成 `function`，后者是 `[ [class Logger] ]`。守卫的作用是让编译产物在没装库的环境里不崩，代价是问题被推迟到运行时。类型层面也不会提醒，因为 `Reflect.metadata` 的类型声明同样来自那个库。

旧装饰器的签名很严格。属性装饰器接收两个参数，目标是原型对象和属性键。方法装饰器接收三个，第三个是属性描述符。参数装饰器也接收三个，第三个是参数下标。写错参数个数，编译器报 TS1240 或 TS1241。下面是反例。

```ts
function brokenDec(value: Function): void {}

class Svc2 {
  @brokenDec
  name = "svc";

  @brokenDec
  run(): void {}
}
```

```bash
$ tsc --noEmit --experimentalDecorators broken.ts
broken.ts(4,4): error TS1240: Unable to resolve signature of property decorator when called as an expression.
  The runtime will invoke the decorator with 2 arguments, but the decorator expects 1.
broken.ts(7,4): error TS1241: Unable to resolve signature of method decorator when called as an expression.
  The runtime will invoke the decorator with 3 arguments, but the decorator expects 1.
```

错误信息里的参数个数来自调用约定，不是类型声明。编译器知道运行时一定会传两个或三个参数，于是拿这个约定去校验函数签名。返回值的规则也不同。类装饰器可以返回新的构造器来替换原类，方法装饰器可以返回新的描述符，属性装饰器与参数装饰器返回 `void`。这些约定在旧机制里由编译器强制，写错就编译失败，不会拖到运行时。

签名之外，还有一个粒度问题。`emitDecoratorMetadata` 只写三个键。`design:type` 给属性，`design:paramtypes` 给构造器和方法参数，`design:returntype` 给方法返回值。三个键的值都是运行时构造器。

```ts
import "reflect-metadata";

interface Clock {
  now(): number;
}

const mark = (target: object, key?: string | symbol, desc?: PropertyDescriptor): void => {};

@mark
class Sample {
  @mark
  clockRef!: Clock;

  constructor(
    private union: string | number,
    private time: Date,
    private clock: Clock,
    private list: string[],
    private literal: "a" | "b",
    private fn: () => void,
    private map: Map<string, number>,
  ) {}

  @mark
  find(id: string): string {
    return id;
  }
}

const types = Reflect.getMetadata("design:paramtypes", Sample) as unknown[];

console.log(types.map((type) => (type as Function).name));
console.log((Reflect.getMetadata("design:type", Sample.prototype, "clockRef") as Function).name);
console.log((Reflect.getMetadata("design:returntype", Sample.prototype, "find") as Function).name);
```

```bash
[
  'Object', 'Date',
  'Object', 'Array',
  'String', 'Function',
  'Map'
]
Object
String
```

`Date`、`Map`、`Array`、`Function` 是真实构造器，能还原。联合类型退化成 `Object`，接口退化成 `Object`，字面量联合退化成 `String`。泛型参数一个都没有，`Map<string, number>` 只知道是 `Map`。还有一个易错点：构造器参数属性只贡献 `design:paramtypes`，不产生 `design:type`。要读属性类型，得写独立的属性声明，并给它加装饰器。

## 信息损失如何影响容器

参数类型退化成 `Object` 不是小事。容器按 token 查表，`Object` 不是有效的应用 token。下面这个容器在解析接口参数时直接失败。

```ts
import "reflect-metadata";

interface Clock {
  now(): number;
}

class Logger {}

const wired = (target: Function): void => {};

@wired
class Repo {
  constructor(readonly logger: Logger, readonly clock: Clock) {}
}

const tokens = new Map<unknown, () => unknown>();
tokens.set(Logger, () => new Logger());

try {
  const args = (Reflect.getMetadata("design:paramtypes", Repo) ?? []).map(
    (type: Function) => {
      const factory = tokens.get(type);
      if (factory === undefined) throw new Error(`no provider for ${String(type)}`);
      return factory();
    },
  );
  new Repo(...(args as [Logger, Clock]));
} catch (error) {
  console.log((error as Error).message);
}
```

```bash
no provider for function Object() { [native code] }
```

错误信息里出现的不是 `Clock`，是 `Object`。接口在编译后没有运行时身份，任何依赖接口抽象的容器都必须准备显式 token。`@Inject("clock")` 做的就是这件事。参数装饰器把 token 写进另一份元数据，解析时优先用它。

token 的形态决定了查找方式。类可以直接当 token，运行时构造器天然唯一。接口没有构造器，只能造一个替代品。字符串 token 好读，容易撞名，适合小项目。symbol token 用 `Symbol("clock")` 创建，不会撞名，打印出来却看不出含义，通常配一个常量模块统一导出。抽象类可以当 token，编译后它仍是值，子类注册时把父类作为键。三种写法在容器里的处理一致，键只是 `Map` 的键，比较用的是引用相等。

注册表也要设计。`provide(token, factory)` 存的是工厂函数，惰性求值。`provideClass(ctor)` 存的是构造器本身，解析时再递归参数。两者共用一张表，值上带一个标记区分。查找时先命中缓存，再判类型。这种结构在几十行代码里就能写完，功能足够覆盖大多数手写容器。

还有一处容易踩。用 `fn.length` 数参数个数并不可靠。函数对象的 `length` 只统计第一个默认值或剩余参数之前的形参，`design:paramtypes` 统计全部形参。一个三参数构造器，第三个参数带默认值时，`Repo.length` 是 2，`paramtypes` 长度是 3。容器如果用 `length` 循环，最后一位永远拿不到注入值，而且不会报错，只会在运行时出现 `undefined`。

显式 token 的写法也有坑。参数装饰器按 `index` 写入数组，跳过的位置不会补 `undefined`，数组会变成稀疏形态。读取时必须按索引取值，不能用 `filter` 或 `for...of` 清理，否则下标整体错位。真实的容器一般先把 token 数组补齐成与 `paramtypes` 等长，再做一次覆盖，避免稀疏数组参与后续逻辑。

容器按 `paramtypes` 的顺序逐个注入，这是旧机制唯一可靠的参数表。`length` 只适合判断函数声明了几个形参，不适合做依赖解析。依赖接口抽象时，参数表里的 `Object` 必须被显式 token 覆盖，否则错误会以 `no provider for function Object` 的形式出现在运行时。

## 新机制：context.metadata 到 Symbol.metadata

TC39 装饰器的第二个参数是上下文对象，里面有 `kind`、`name`、`addInitializer` 和 `metadata`。`metadata` 是一个普通对象，同一个类上的所有装饰器拿到同一个引用。装饰器往里写键值，编译器在类定义结束时把对象挂到 `Symbol.metadata`。

```ts
interface SymbolConstructor {
  readonly metadata: symbol;
}

if (typeof Symbol.metadata !== "symbol") {
  Object.defineProperty(Symbol, "metadata", {
    value: Symbol.for("Symbol.metadata"),
  });
}

function table(name: string) {
  return function (value: Function, context: ClassDecoratorContext) {
    context.metadata!.table = name;
  };
}

function column(name: string) {
  return function (value: undefined, context: ClassFieldDecoratorContext) {
    const meta = context.metadata!;
    const columns = Object.hasOwn(meta, "columns") ? (meta.columns as string[]) : [];
    columns.push(name);
    meta.columns = columns;
  };
}

@table("repos")
class Repo {
  @column("id")
  id!: string;

  @column("title")
  title!: string;
}

const read = (target: object): Record<string, unknown> =>
  (target as unknown as Record<symbol, Record<string, unknown>>)[Symbol.metadata];

console.log(read(Repo));
console.log(JSON.stringify(read(Repo)));
```

```bash
[Object: null prototype] { columns: [ 'id', 'title' ], table: 'repos' }
{"columns":["id","title"],"table":"repos"}
```

这段没有 `import "reflect-metadata"`，没有 tsconfig 开关。`Symbol.metadata` 在 Node 26.13.1 里不存在，`typeof Symbol.metadata` 是 `undefined`，所以文件开头先 polyfill。没有这一步，`context.metadata` 是 `undefined`，装饰器里读属性会抛 `TypeError: Cannot read properties of undefined`。

polyfill 用 `Symbol.for("Symbol.metadata")` 而不是 `Symbol("metadata")`。前者是全局注册表里的键，多个模块、多个包加载同一份代码时会拿到同一个 symbol。后者每次调用都新建，两个包各自定义一次，元数据就分裂成两份。规范草案里这个 symbol 本身用 `Symbol.for` 定义，polyfill 照抄注册表语义，才能和未来的原生实现兼容。

编译器不会给所有类生成元数据对象。没有装饰器的普通类不产生 `_metadata`，类上也没有 `Symbol.metadata` 属性，读取结果是 `undefined`。只有参与装饰的类才需要这个对象，生成是惰性的。判断一个类有没有元数据，不能按「是不是类」来猜，要实际读一次。

编译器给每个类生成一个元数据对象。根类是 `Object.create(null)`，派生类在父类元数据之上再建一层。类定义结束时，如果 `Symbol.metadata` 可用，对象被定义为类的属性，可枚举、可配置、可写。

```js
const _metadata = typeof Symbol === "function" && Symbol.metadata
    ? Object.create(null)
    : void 0;
// 派生类
const _metadata = typeof Symbol === "function" && Symbol.metadata
    ? Object.create(_classSuper[Symbol.metadata] ?? null)
    : void 0;

if (_metadata) Object.defineProperty(_classThis, Symbol.metadata, {
    enumerable: true,
    configurable: true,
    writable: true,
    value: _metadata
});
```

派生类的元数据对象原型指向父类的元数据对象，读取会沿原型链走。写入时如果不加判断，会改到父类那份。

```ts
interface SymbolConstructor {
  readonly metadata: symbol;
}

if (typeof Symbol.metadata !== "symbol") {
  Object.defineProperty(Symbol, "metadata", {
    value: Symbol.for("Symbol.metadata"),
  });
}

function column(name: string) {
  return function (value: undefined, context: ClassFieldDecoratorContext) {
    const meta = context.metadata!;
    const columns = (meta.columns as string[] | undefined) ?? [];
    columns.push(name);
    meta.columns = columns;
  };
}

class Base {
  @column("id")
  id!: string;
}

class Child extends Base {
  @column("title")
  title!: string;
}

const read = (target: object): Record<string, unknown> =>
  (target as unknown as Record<symbol, Record<string, unknown>>)[Symbol.metadata];

console.log("Base:", read(Base).columns);
console.log("Child:", read(Child).columns);
```

```bash
Base: [ 'id', 'title' ]
Child: [ 'id', 'title' ]
```

`Child` 的装饰器读到的是继承来的数组，`push` 改的是 `Base` 的那份。父类的元数据被意外污染。正确写法要先判断是不是自有属性。

```ts
interface SymbolConstructor {
  readonly metadata: symbol;
}

if (typeof Symbol.metadata !== "symbol") {
  Object.defineProperty(Symbol, "metadata", {
    value: Symbol.for("Symbol.metadata"),
  });
}

function column(name: string) {
  return function (value: undefined, context: ClassFieldDecoratorContext) {
    const meta = context.metadata!;
    const inherited = (meta.columns as string[] | undefined) ?? [];
    const own = Object.hasOwn(meta, "columns") ? inherited : [];
    own.push(name);
    meta.columns = own;
  };
}

class Base {
  @column("id")
  id!: string;
}

class Child extends Base {
  @column("title")
  title!: string;
}

const read = (target: object): Record<string, unknown> =>
  (target as unknown as Record<symbol, Record<string, unknown>>)[Symbol.metadata];

console.log("Base:", read(Base).columns);
console.log("Child:", read(Child).columns);
```

```bash
Base: [ 'id' ]
Child: [ 'title' ]
```

如果希望子类包含父类字段，先复制再写。`const own = Object.hasOwn(...) ? [...inherited] : [...inherited, name]` 之类的写法都行，关键是不要原地改继承来的数组。

## 手写依赖注入容器

容器要做的三件事：登记 provider，按 token 解析，构造实例时把参数注入。旧机制的 `design:paramtypes` 给出参数类型，显式 token 覆盖推断结果。下面是一个能跑的最小实现。

```ts
import "reflect-metadata";

type Ctor<T = unknown> = new (...args: any[]) => T;
type Token = string | symbol | Ctor<unknown>;

const paramsKey = "di:params";
const propsKey = "di:props";
const factories = new Map<Token, () => unknown>();
const instances = new Map<unknown, unknown>();
const aliases = new Map<Token, Ctor<unknown>>();

export const Inject =
  (token: Token): ParameterDecorator & PropertyDecorator =>
  (target: object, key?: string | symbol, index?: number) => {
    if (index !== undefined) {
      const list = Reflect.getOwnMetadata(paramsKey, target) ?? [];
      list[index] = token;
      Reflect.defineMetadata(paramsKey, list, target);
      return;
    }
    if (key !== undefined) {
      const list = Reflect.getOwnMetadata(propsKey, target) ?? [];
      list.push({ key, token });
      Reflect.defineMetadata(propsKey, list, target);
    }
  };

export const provide = (token: Token, factory: () => unknown): void => {
  factories.set(token, factory);
};

export const provideClass = <T>(token: Token, ctor: Ctor<T>): void => {
  aliases.set(token, ctor as Ctor<unknown>);
  factories.set(token, () => instantiate(ctor));
};

export const resolve = <T>(token: Token): T => {
  const alias = aliases.get(token);
  if (alias !== undefined && instances.has(alias)) {
    return instances.get(alias) as T;
  }
  if (instances.has(token)) return instances.get(token) as T;
  const factory = factories.get(token);
  if (factory === undefined) {
    throw new Error(`no provider for ${String(token)}`);
  }
  return factory() as T;
};

export const instantiate = <T>(ctor: Ctor<T>): T => {
  const types = (Reflect.getMetadata("design:paramtypes", ctor) ?? []) as Token[];
  const explicit = (Reflect.getOwnMetadata(paramsKey, ctor) ?? []) as Token[];
  const args = types.map((type, index) => resolve(explicit[index] ?? type));
  const instance = new ctor(...args);
  instances.set(ctor, instance);
  const props = (Reflect.getOwnMetadata(propsKey, ctor.prototype) ?? []) as {
    key: string;
    token: Token;
  }[];
  for (const { key, token } of props) {
    Object.defineProperty(instance, key, {
      configurable: true,
      get: () => resolve(token),
    });
  }
  return instance;
};
```

四张表的分工要分清。`factories` 存工厂，键是 token。`instances` 存已经建好的单例，键也是 token。`aliases` 存「token 到构造器」的映射，用来支持字符串 token 指向一个类。`paramsKey` 与 `propsKey` 是元数据键，参数装饰器往里写 token 数组，属性装饰器往里写 `{ key, token }` 列表。

`resolve` 的顺序是先生成缓存键，再查缓存，再查工厂，最后走构造器。参数解析时先读 `design:paramtypes`，拿到构造器数组，再用显式 token 覆盖对应下标。覆盖发生在下标级别，没覆盖的位置保留推断值。构造完成后立刻写入缓存，这一步是循环依赖能被属性注入断开的前提，因为属性 getter 只有在实例已经进缓存之后才会触发。

`instantiate` 里有一个细节。属性注入用 `Object.defineProperty` 定义 getter，而不是直接赋值。直接赋值会立刻调用 `resolve`，循环依赖又回到栈溢出。getter 把解析推迟到第一次读取，容器初始化阶段就能顺利结束。代价是每次读属性都会走一次解析，虽然命中缓存，仍有一次 `Map` 查找。高频访问的字段可以在首次读取后改写成普通属性，这是一种常见的优化。

```ts
import { Inject, provide, provideClass, resolve } from "./container";

interface Clock {
  now(): number;
}

class Logger {
  log(message: string): void {}
}

class Repo {
  constructor(
    readonly logger: Logger,
    @Inject("clock") readonly clock: Clock,
    @Inject("tags") readonly tags: string[],
  ) {}
}

provide(Logger, () => new Logger());
provide("clock", () => ({ now: () => Date.now() }));
provide("tags", () => ["draft", "live"]);
provideClass(Repo, Repo);

const repo = resolve<Repo>(Repo);
console.log("logger:", repo.logger.constructor.name);
console.log("clock:", repo.clock.now() > 0);
console.log("tags:", repo.tags.length);
```

```bash
logger: Logger
clock: true
tags: 2
```

循环依赖在构造阶段就露馅。`RepoA` 要 `RepoB`，`RepoB` 又要 `RepoA`，深度优先解析会无限递归。

```ts
import { Inject, provideClass, resolve } from "./container";

class RepoA {
  constructor(@Inject("b") readonly b: unknown) {}
}

class RepoB {
  constructor(@Inject("a") readonly a: unknown) {}
}

provideClass("a", RepoA);
provideClass("b", RepoB);

try {
  resolve("a");
} catch (error) {
  console.log((error as Error).constructor.name + ": " + (error as Error).message);
}
```

```bash
RangeError: Maximum call stack size exceeded
```

修复办法是让一侧的依赖延迟到实例创建之后再取。属性注入可以写成惰性 getter，容器在构造完成时只定义属性，第一次访问才解析。配合实例缓存，第二次访问拿到同一个实例。

```ts
import { Inject, provideClass, resolve } from "./container";

class RepoA {
  @Inject("b") b!: unknown;
}

class RepoB {
  constructor(@Inject("a") readonly a: RepoA) {}
}

provideClass("a", RepoA);
provideClass("b", RepoB);

const a = resolve<RepoA>("a");
const b = a.b as RepoB;
console.log("b is RepoB:", b instanceof RepoB);
console.log("cycle closed:", b.a === a);
```

```bash
b is RepoB: true
cycle closed: true
```

关键在两处。属性注入不参与构造，`RepoA` 先建好并进缓存。`RepoB` 的构造参数解析 `"a"` 时，缓存命中，直接拿到已经建好的 `RepoA`。如果容器没有缓存，或者属性注入在构造前执行，循环仍然断不开。NestJS 的 `forwardRef` 解决的是同一个问题，只是把延迟写在了模块依赖声明里。

真实容器还要处理作用域。单例在第一次解析时缓存，请求级作用域每次新建，瞬态不做缓存。生命周期和 provider 抽象会再加一层，元数据的角色不变。

解析算法比上面那段多两步。第一步是查缓存，键不一定是构造器，也可能是字符串 token 或 symbol token。第二步是维护一个正在解析中的集合，进入某个 provider 时登记，离开时删除。下一次再遇到同一个 token 就说明有环，抛错比栈溢出好定位得多。构造函数注入的环无法靠延迟绕开，因为参数必须在实例创建前就绪，只能改结构。属性注入把依赖搬到实例创建之后，环就断在「还没准备好」这个窗口里。

元数据读取本身也要考虑性能。`Reflect.getMetadata("design:paramtypes", ctor)` 每次都会走一遍存储查找，容器在首次解析某个类之后，通常把参数表缓存成数组，后续直接复用。缓存键用构造器，不能用类名。同名类在不同模块里很常见，按名字查会串。

## 校验与序列化

`class-validator` 把规则写进自己的元数据存储。属性装饰器登记规则名、约束参数、验证函数，`validate` 遍历存储，收集失败项，组装成 `ValidationError`。它复用 `reflect-metadata` 的存储设施，键是属性名，值是规则数组。元数据的键名带方法名，`targetValidationMetadatas` 按目标构造器与分组过滤。

```ts
import "reflect-metadata";
import { IsInt, IsString, Min, validate } from "class-validator";
import { getMetadataStorage } from "class-validator";

class Article {
  @IsString()
  title!: string;

  @IsInt()
  @Min(1)
  size!: number;
}

const storage = getMetadataStorage();
const metas = storage.getTargetValidationMetadatas(Article, "", false, false);

for (const meta of metas) {
  console.log(meta.name, "->", meta.propertyName, "type:", meta.type);
}

const bad = Object.assign(new Article(), { title: 7, size: 0 });
validate(bad).then((errors) => {
  for (const error of errors) {
    console.log(error.property, Object.keys(error.constraints ?? {}));
  }
});
```

```bash
isString -> title type: customValidation
min -> size type: customValidation
isInt -> size type: customValidation
title [ 'isString' ]
size [ 'min' ]
```

规则存储和 `design:paramtypes` 是两套东西。`class-validator` 不靠参数类型工作，它靠装饰器登记的规则。所以接口、联合类型、泛型参数在规则层面都能表达，代价是规则要显式写。

`class-transformer` 的情况不同。`plainToInstance` 默认只做字段拷贝，不做类型转换。`@Type` 显式指定目标类型，才会把字符串转成数字或日期。

```ts
import "reflect-metadata";
import { Expose, plainToInstance, Type } from "class-transformer";

class ArticleDto {
  @Expose()
  title!: string;

  @Type(() => Number)
  size!: number;

  @Type(() => Date)
  createdAt!: Date;
}

const plain = { title: "发布", size: "3", createdAt: "2026-01-02" };
const dto = plainToInstance(ArticleDto, plain, { enableImplicitConversion: true });

console.log("size:", dto.size, typeof dto.size);
console.log("createdAt:", dto.createdAt.toISOString());
```

```bash
size: 3 number
createdAt: 2026-01-02T00:00:00.000Z
```

`enableImplicitConversion` 需要 `design:type` 元数据。类上没有任何装饰器时，编译器不写元数据，隐式转换什么也做不了。给属性加 `@Expose()` 之后，元数据出现，隐式转换生效。这条依赖链说明了一个事实：序列化库的类型转换能力，取决于装饰器有没有触发元数据生成。

`zod` 走的是另一条路。schema 是运行时对象，校验和类型推断都从它来，不需要装饰器，也不需要编译器开关。

```ts
import { z } from "zod";

const ArticleSchema = z.object({
  title: z.string().min(1),
  size: z.number().int().positive(),
  tags: z.array(z.string()).default([]),
});

type Article = z.infer<typeof ArticleSchema>;

const ok = ArticleSchema.safeParse({ title: "发布", size: 3 });
console.log("ok:", ok.success, ok.success ? ok.data : []);

const bad = ArticleSchema.safeParse({ title: "", size: 0 });
console.log("errors:", bad.success ? [] : bad.error.issues.map((issue) => issue.path.join(".") + ":" + issue.message));
```

```bash
ok: true { title: '发布', size: 3, tags: [] }
errors: [ 'title:Too small: expected string to have >=1 characters', 'size:Too small: expected number to be >0' ]
```

两条路的取舍很实在。

| 场景 | 装饰器元数据 | 运行时 schema |
| --- | --- | --- |
| 需要和类绑定，走反射式 DI | 合适 | 要额外桥接 |
| 需要校验来自网络的输入 | 可用，规则分散在属性上 | 合适，规则集中在一个对象 |
| 前端打包体积敏感 | 需要引入元数据存储 | 只引入用到的 schema 部分 |
| 跨前后端共享类型 | 类型与类绑定，导出麻烦 | `z.infer` 直接导出类型 |
| 不想开装饰器编译选项 | 不可用 | 可用 |

NestJS 选了装饰器路线。`@Injectable`、`@Controller` 标记类，参数装饰器声明依赖，`reflect-metadata` 提供存储。它的 `ValidationPipe` 又默认接 `class-validator`，同一套装饰器同时承担 DI 和校验。

校验库内部的流程值得看一眼。装饰器执行时只做登记，注册约束的类名、属性、选项。`validate` 被调用时，才按类名从登记表里取出规则，实例化约束对象，逐个跑 `validate(value)`。每个约束返回布尔值，失败就写一条 `ValidationError`，最后按属性分组。整个过程没有类型信息参与，`@IsInt` 判断的是运行时的 `typeof` 与 `Number.isInteger`，不是声明类型。声明类型只在写代码时提示，运行时校验必须显式写规则，二者不能互相替代。

序列化库补的是另一块。`plainToInstance` 拿到普通对象，按目标类的元数据决定哪个字段做转换。`@Type(() => Number)` 里的是一个函数，因为类型位置不能写值，只能靠闭包把构造器带进来。`@Expose` 控制字段是否参与，`@Transform` 做自定义映射。没有装饰器的类也能转换，但只能原样复制属性，字符串不会变成数字，日期字符串不会变成 `Date`。这就是示例里裸类输出 `size: string` 的原因。

zod 把规则和类型放在同一个值里。schema 本身可以组合、可以复用，类型由 `z.infer` 从 schema 推出，不需要类，也不需要编译器帮忙。代价是它看不见类的结构，要校验一个类实例，得先写对应的 schema，或者用 `z.instanceof` 做粗校验。DI 场景里 zod 帮不上忙，因为它不产生构造参数表。

## 装饰器与实例字段的执行顺序

元数据写入发生在类定义阶段。成员装饰器先执行，类装饰器最后执行。这解释了为什么在类装饰器里能读到全部参数元数据，也解释了它为什么适合汇总。

同一个目标上的多个装饰器，应用顺序与书写顺序相反。`@a @b method` 先执行 `b`，再执行 `a`。这是数学上的复合顺序，`a(b(method))` 从内向外求值。类上的多个装饰器同理。旧机制按目标分组：属性装饰器、方法装饰器、参数装饰器各自成组，最后才是类装饰器。参数装饰器在方法装饰器之前调用，因为 `__param` 包装在数组里排在前面，`__decorate` 从后往前遍历时它先跑。

```ts
function classDec(value: Function): void {
  console.log("class decorator");
}

function propDec(target: object, key: string): void {
  console.log("property decorator:", key);
}

@classDec
class Client {
  @propDec
  name = "default";

  constructor() {
    console.log("constructor");
  }
}

console.log("new Client");
const client = new Client();
console.log("instance name:", client.name);
```

```bash
property decorator: name
class decorator
new Client
constructor
instance name: default
```

旧机制里，属性装饰器在类定义时运行，早于类装饰器。实例字段的初始化在构造时运行，晚于所有装饰器。所以属性装饰器读不到实例，只能把信息写进原型或构造器的元数据。

新机制多了一层 `addInitializer`。它在装饰器执行完之后注册回调，回调的时机取决于装饰的是哪类成员。方法装饰器的回调在实例创建时、字段初始化之前运行。字段装饰器的回调在字段初始化之后运行。类装饰器的回调在类定义结束时运行。

```ts
function fieldDec(value: undefined, context: ClassFieldDecoratorContext) {
  console.log("field decorator:", String(context.name));
  context.addInitializer(() => {
    console.log("field hook:", String(context.name));
  });
}

function methodDec(value: Function, context: ClassMethodDecoratorContext) {
  console.log("method decorator:", String(context.name));
  context.addInitializer(() => {
    console.log("method hook:", String(context.name));
  });
}

function classDec(value: typeof Client, context: ClassDecoratorContext) {
  console.log("class decorator");
  context.addInitializer(() => {
    console.log("class hook");
  });
}

@classDec
class Client {
  @methodDec
  open(): void {}

  @fieldDec
  name = (console.log("field initializer"), "default");

  @methodDec
  close(): void {}

  constructor() {
    console.log("constructor body");
  }
}

console.log("--- new ---");
new Client();
```

```bash
method decorator: open
method decorator: close
field decorator: name
class decorator
class hook
--- new ---
method hook: open
method hook: close
field initializer
field hook: name
constructor body
```

顺序对依赖注入有直接影响。类装饰器最后执行，容器可以在这里读取所有已登记的元数据，决定如何构造实例。如果元数据在成员装饰器里逐步写入，类装饰器就是天然的收口点。初始化回调不适合创建依赖，原因很简单，它在实例创建过程中运行，此时容器的缓存和解析状态都不稳定。

## 边界：原生剥离与编译开关

Node 原生类型剥离不支持装饰器。直接运行带装饰器的 `.ts` 文件，报的是普通语法错误，连解析都没过。枚举、命名空间、参数属性走得远一点，能通过解析，被判定为不支持的语法，错误码是 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`。

```bash
$ node deco.ts
/private/tmp/aengb/meta/w/deco.ts:5
@logged
^

SyntaxError: Invalid or unexpected token

$ node enum.ts
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode

$ node ns.ts
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript namespace declaration is not supported in strip-only mode

$ node param.ts
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript parameter property is not supported in strip-only mode
```

两类错误的分界在词法层。装饰器是全新的语法节点，剥离器只做删除类型注解，遇到 `@` 就无路可走。枚举、命名空间、参数属性属于「能擦除但擦除后语义会变」的语法，剥离器认得它们，于是给出更明确的拒绝理由。这决定了一件事：依赖装饰器的项目不能用 `node app.ts` 直接跑，要么用 `tsx` 这类运行时转译工具，要么先 `tsc` 再跑产物。

`erasableSyntaxOnly` 是另一个边界。它禁止无法擦除的语法。旧装饰器里的参数属性会被拒绝。

```bash
$ tsc --noEmit --experimentalDecorators --emitDecoratorMetadata --erasableSyntaxOnly leg2.ts
leg2.ts(4,15): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
leg2.ts(4,16): error TS1239: Unable to resolve signature of parameter decorator when called as an expression.
  The runtime will invoke the decorator with 3 arguments, but the decorator expects 1.
```

新版装饰器本身通过 `erasableSyntaxOnly`。装饰器的类型签名不产生运行时代码，编译器只把它当语法处理。真正被禁的是 enum、namespace、参数属性、`import =` 这些有运行时产物的写法。

`isolatedModules` 和 `verbatimModuleSyntax` 不会直接报错，但会改变元数据的质量。类型导入被擦除后，`design:paramtypes` 里对应位置退化成 `Function`。

```ts
import type { Logger } from "./logger.js";

function sealed(target: Function): void {}

@sealed
class Service {
  constructor(private logger: Logger) {}
}

export { Service };
```

```js
Service = __decorate([
    sealed,
    __metadata("design:paramtypes", [Function])
], Service);
```

容器拿到 `Function`，查表失败。修法有两条。用普通 `import` 引入需要参与元数据的类，或者给参数加显式 token，让解析不依赖推断。前者省事，后者更稳，因为不要求目标类的值被引入。

`import type` 不是唯一退化成 `Function` 的情况。类值在当前作用域不可见时，结果相同。元数据只记录编译期能解析到的运行时值，解析不到就退化。

还有两个工程上的边界。打包器会把未被引用的类摇掉，`design:paramtypes` 里的构造器引用算不算引用，取决于打包器如何分析装饰器产物。安全做法是在入口显式引用这些类，或者让容器的注册表持有构造器。边缘运行时更麻烦，它们通常没有 `Symbol.metadata`，也没有 `reflect-metadata` 需要的全局对象，两代机制都可能失效。这类环境适合把元数据提前生成为静态表，运行时只查表。

最后看什么时候不该用元数据。

| 需求 | 建议 |
| --- | --- |
| 表单或接口输入校验 | 用 zod 或 valibot，schema 与类解耦 |
| 只在前端使用的组件属性 | 类型即可，不需要运行时元数据 |
| 配置对象注入 | 显式传参或工厂函数，比容器好调试 |
| 少量依赖、固定拓扑 | 手写工厂，不引入容器 |
| 需要运行时反射的框架 | 装饰器元数据，接受编译选项和库依赖 |

元数据适合框架层，不适合业务层。业务代码里大量依赖反射，调试成本会转移到运行时的隐式行为上。类型检查在编译期完成，元数据只解决运行时取值，两者的边界清楚，代码就好维护。

## 用不上的时候

### 依赖接口抽象

接口编译后没有运行时身份，`design:paramtypes` 里对应位置是 `Object`。容器按 token 查表时报 `no provider for function Object() { [native code] }`，每个接口都要补显式 token。

### 用 node 直接跑带装饰器的文件

Node 原生剥离遇到装饰器直接报语法错误，连解析都过不去。枚举、命名空间、参数属性能通过解析，但会报 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`。这类项目只能用 `tsx` 运行，或者先 `tsc` 再跑产物。

### 元数据靠隐式类型推断

`import type` 引入的类在 `design:paramtypes` 里退化成 `Function`，容器查表失败。`fn.length` 只统计默认值或剩余参数之前的形参，用参数装饰器按索引写 token 会留下稀疏数组。打包器摇掉未被引用的类、边缘运行时没有 `Symbol.metadata`，两代机制都会失效。
