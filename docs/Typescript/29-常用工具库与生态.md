# 第 29 章 常用工具库与生态

新建项目时 JSON 校验、构建、测试、lint 各选一个库，装完发现两个库的类型定义互相冲突。工具选型影响后续维护成本。这一章按开发阶段列出常用库和它们的边界。

TypeScript 的繁荣离不开其丰富的工具生态。这一章按开发阶段梳理 TypeScript 相关的工具库，帮助你快速找到适合自己项目的工具。

## 开发阶段

### 运行时工具

**tsx**（推荐）

基于 esbuild 的 TS 执行工具，启动极快，是当下新项目的首选：

```bash
npm install -D tsx
npx tsx src/server.ts
npx tsx --watch src/server.ts   # 监视模式
```

**ts-node** & **ts-node-dev**

老牌方案，ts-node-dev 在 ts-node 基础上增加了文件变更监听和自动重启：

```bash
npm install -D ts-node ts-node-dev
ts-node-dev --respawn src/server.ts
```

**tsc-watch**

监听 `tsc --watch` 并在编译成功/失败时执行自定义逻辑：

```bash
tsc-watch --onSuccess "node dist/server.js"
tsc-watch --onFailure "echo 'Compilation failed'"
```

**esno**

antfu 的作品，同样是执行 `.ts` 文件，底层使用 esbuild：

```bash
npx esno src/index.ts
```

### 辅助工具

**typed-install**

安装 npm 包时自动检查并安装对应的 `@types/` 类型定义包：

```bash
npx typed-install express
# 自动安装 express 和 @types/express
```

**ts-error-translator**

将 TypeScript 晦涩的错误信息翻译成更易读的版本，配合上下文说明错误原因。对于 Team 中的 TS 新手特别有帮助。

**suppress-ts-errors**

自动为所有类型报错添加 `@ts-expect-error` 注释。适合在向已有 JS 项目引入 TS 的过渡阶段使用。

### 代码生成与转换

**typescript-json-schema** / **json-schema-to-typescript**

TS 类型定义与 JSON Schema 之间的双向转换。适合需要共享类型定义给非 TS 消费者（如 API 文档生成）的场景：

```typescript
// 输入 TypeScript
export interface User {
  /** 用户昵称 @minLength 1 */
  name: string;
  age: number;
}

// 输出 JSON Schema
{
  "properties": {
    "name": { "type": "string", "minLength": 1, "description": "用户昵称" },
    "age": { "type": "number" }
  },
  "required": ["name", "age"],
  "type": "object"
}
```

## 类型工具库

这些库提供了比内置工具类型更丰富的通用工具类型，避免在不同项目中重复造轮子。

### type-fest

[Sindre Sorhus](https://github.com/sindresorhus) 出品，目前 star 数最多、最接地气的工具类型库。包含大量实用类型：

```typescript
import type { PartialDeep, ReadonlyDeep, SetRequired, CamelCasedProperties } from 'type-fest';

// 深层 Partial
type PartialConfig = PartialDeep<AppConfig>;

// 将某些属性设为必填
type UserWithId = SetRequired<User, 'id'>;

// 将下划线命名转为小驼峰
type ApiUser = CamelCasedProperties<SnakeCaseUser>;
```

### ts-toolbelt

目前包含工具类型数量最多的库，几乎覆盖所有类型操作场景。API 设计有一定学习曲线，但功能极其全面。

### utility-types

工具类型数量较少，但实现精巧，是学习类型编程的绝佳参考。其中 `FunctionKeys`、`RequiredKeys`、`OptionalKeys` 等类型的实现非常经典。

### ts-essentials

轻量级的工具类型集，包含 `DeepPartial`、`DeepRequired`、`DeepReadonly`、`MarkRequired`、`MarkOptional` 等高频使用的深层属性修饰类型。

### tsd

对类型进行单元测试的工具。编写类型测试可以确保你的工具类型在各种输入下产生预期结果：

```typescript
import { expectType, expectError } from 'tsd';

// 确认类型计算结果
expectType<Partial<{ a: number }>>({});

// 确认不应成立的类型
expectError<Required<{ a?: number }>>({});

// 确认函数返回值类型
expectType<Promise<number>>(fetchCount());
```

type-fest 等主流类型库都使用 tsd 来保证工具类型的正确性。（见 [tsd](https://github.com/tsdjs/tsd)）

## 运行时校验

TypeScript 的类型只在编译时存在，运行时无法保证外部数据的类型安全（API 响应、用户输入、localStorage 等）。运行时校验库填补了这一缺口，并提供"从 Schema 推导 TypeScript 类型"的能力。

### zod（推荐）

目前最流行的运行时校验库，与 TypeScript 的集成堪称完美：

```typescript
import { z } from 'zod';

// 定义 Schema
const UserSchema = z.object({
  username: z.string().min(3).max(20),
  email: z.string().email(),
  age: z.number().int().positive().optional(),
  role: z.enum(['admin', 'user']).default('user'),
});

// 从 Schema 提取类型，无需手动维护两份定义
type User = z.infer<typeof UserSchema>;

// 运行时校验
function createUser(input: unknown): User {
  return UserSchema.parse(input); // 校验失败会抛出 ZodError
}

function safeCreateUser(input: unknown) {
  const result = UserSchema.safeParse(input);
  if (result.success) {
    // result.data 的类型是 User
    return result.data;
  }
  // result.error 的类型是 ZodError
  return result.error.issues;
}
```

zod 在 tRPC、Blitz、Next.js Server Actions 等全栈框架中已经成为标准方案，因为它能同时提供编译时类型保障和运行时数据校验。（见 [Zod 4 变更日志](https://zod.dev/v4/changelog)）

### class-validator

基于装饰器的校验库，与 NestJS、TypeORM 紧密集成（见 [class-validator](https://github.com/typestack/class-validator)）：

```typescript
import { IsString, IsInt, Min, Max, IsEmail, Length } from 'class-validator';

// 字段由框架在构造后填充，用 ! 跳过严格属性初始化检查
export class CreateUserDto {
  @IsString()
  @Length(3, 20)
  username!: string;

  @IsEmail()
  email!: string;

  @IsInt()
  @Min(0)
  @Max(150)
  age!: number;
}

const dto = new CreateUserDto();
dto.username = 'ab'; // 太短

validate(dto).then(errors => {
  console.log(errors); // [{ property: 'username', constraints: {...} }]
});
```

### 其他运行时校验库

- **runtypes**：功能类似 zod，接口风格偏函数式
- **superstruct**：更轻量，适合简单场景
- **ow**：专注于函数参数校验，CLI 工具场景下非常好用

```typescript
import ow from 'ow';

function build(targetDir: string) {
  ow(targetDir, ow.string.nonEmpty);
  // ...
}
```

## 构建阶段

### esbuild

由 Go 编写的极速 bundler 和 transpiler。在构建时做 TS 转译（不做类型检查），速度比 tsc 快 10-100 倍（见 [esbuild 官网](https://esbuild.github.io/)）：

```bash
npm install esbuild
npx esbuild src/index.ts --bundle --outfile=dist/index.js
```

通过 [esbuild-loader](https://github.com/privatenumber/esbuild-loader) 可以替代 Webpack 的 ts-loader。

### SWC

基于 Rust 的编译工具，定位是替代 Babel。完整支持装饰器等 TypeScript 特性。在 Next.js 等框架中作为默认编译器。（见 [SWC](https://swc.rs/)）

### fork-ts-checker-webpack-plugin

将类型检查移到独立子进程中执行，不会阻塞 Webpack 的构建速度。如果你在 Webpack 中使用 ts-loader 或 esbuild-loader 做转译，加上这个插件来单独做类型检查是标准做法：

```js
// webpack.config.js
const ForkTsCheckerWebpackPlugin = require('fork-ts-checker-webpack-plugin');

module.exports = {
  module: {
    rules: [
      { test: /\.tsx?$/, loader: 'esbuild-loader' }
    ]
  },
  plugins: [
    new ForkTsCheckerWebpackPlugin({
      typescript: {
        configFile: './tsconfig.json',
      },
    }),
  ],
};
```

### rollup-plugin-dts

将分散的 `.d.ts` 声明文件打包成单一的入口声明文件，对 npm 库作者非常实用：

```js
// rollup.config.js
import dts from 'rollup-plugin-dts';

export default {
  input: './src/index.ts',
  output: { file: './dist/index.d.ts', format: 'es' },
  plugins: [dts()],
};
```

## 类型覆盖度检查

### type-coverage

检查项目中类型的覆盖率，即多少比例的值被显式标注了类型：

```bash
npx type-coverage --detail
# 输出：类型覆盖率 94.7%，以下位置未标注类型：
# src/utils/helper.ts:23:12
```

### typescript-coverage-report

基于 type-coverage 但提供了更友好的报告界面。可以集成到 CI 中，设定最低覆盖率阈值。

一般来说，**95% 左右是一个健康的平衡点**：低于 80% 说明 any 泛滥，追求 100% 则边际成本过高。

## 怎么判断一个库的类型质量

类型质量和功能、性能不是一回事，要单独看。下面四个维度按检查成本从低到高排。

维护状态看最近发布时间。停更三年的库，类型定义跟不上新版 TS 的严格选项，`strict` 一开就露馅。查法很简单，`npm view <包名> time.modified` 看最后发布，`npm view <包名> version` 看当前版本。

类型来源看它自带 `.d.ts` 还是走 `@types/*`。自带的版本和实现一起发布，走 `@types` 的靠社区补，主包升级后类型可能滞后。滞后时会出现类型检查通过、运行报错的组合，这类故障最难排查。

类型保真看泛型有没有被 `any` 吃掉。拿一个最小用例在 `strict` 下编译，看推导结果是否和文档承诺一致。工具库尤其要看这一条，泛型算错比不写类型更麻烦。验证方法是把工具类型的输出赋给一个预期类型，推导不对就报错。

接入成本看 `typesVersions`、`exports` 里的 `types` 条件、双格式包的类型文件是否齐全。`attw` 自动检查解析，`publint` 检查打包配置，两个配合能在装包前发现大部分问题。

类型质量要单独看，原因是类型声明是独立产物。主包发版不会强制更新 `@types`，两者版本号各走各的，`@types/foo@5` 配 `foo@6` 的情况很常见。版本错位之后，类型层看不出运行时差异，只能靠 `attw` 这类工具在边界上验。

覆盖度工具只统计自己的代码。`type-coverage` 报告的是项目内标注比例，依赖包里的 `any` 不进统计，别把它当成整体类型健康度。

## 两个真实的类型事故

第一个是没有类型声明的包。代码 `import { greet } from "no-types-lib"` 在 `strict` 下报 `error TS7016: Could not find a declaration file for module 'no-types-lib'.`，同一位置还会提示这个模块隐式为 `any`。

```typescript
import { greet } from "no-types-lib";

greet("task");
```

修法有两种，装对应的 `@types` 包，或者写一个最小声明 `declare module "no-types-lib" { export function greet(name: string): string; }`，放进项目里的 `.d.ts`。

第二个是库升级后的 API 迁移。zod 4 里 `result.error.errors` 报 `error TS2339: Property 'errors' does not exist on type 'ZodError<{ email: string; }>'.`，因为这个属性改名为 `issues`。

```typescript
import { z } from "zod";

const schema = z.object({ email: z.string() });
const result = schema.safeParse({ email: "a" });
if (!result.success) console.log(result.error.errors);
```

改法是把 `errors` 换成 `issues`。zod 4 同时弃用了 `format()` 与 `flatten()`，迁移时一起换。

## 一句话理解类型质量

类型定义像包裹里的说明书，主包换代后说明书可能没跟着改。选库时先看说明书新旧，再决定信不信。这个比喻在纯 JS 库上失效，没有说明书的时候，只能自己补 `declare module`。

## 推荐配置组合

### 前端项目（React / Vue）

```
开发: tsx + Vite (内置 esbuild)
校验: zod + ESLint (@typescript-eslint)
类型: type-fest
测试: vitest + tsd
构建: Vite (生产) / tsc --noEmit (CI 类型检查)
```

### Node.js 后端

```
开发: tsx --watch
校验: zod / class-validator (NestJS 项目)
类型: type-fest
构建: tsc
覆盖度: type-coverage (95% 目标)
```

### npm 库

```
开发: tsc --watch
测试: vitest + tsd
构建: rollup + rollup-plugin-dts
类型检查: tsc --noEmit + type-coverage
```

## 小结

- **开发阶段**：tsx（即时执行）、typed-install（自动装 @types）、ts-error-translator（报错翻译）
- **类型工具库**：type-fest（最实用）、ts-toolbelt（最全面）、tsd（类型测试）
- **运行时校验**：zod（首选的 Schema 校验 + 类型推导方案）、class-validator（NestJS 生态首选）
- **构建阶段**：esbuild/SWC（快速转译，不做类型检查）、fork-ts-checker-webpack-plugin（独立进程类型检查）
- **覆盖度**：type-coverage 追踪类型覆盖率，95% 是合理目标
- **黄金组合**：转译用 esbuild/SWC（快），类型检查用 tsc（稳），运行时校验用 zod（安全），类型工具用 type-fest（全面）

## 用不上的时候

### 小项目

校验、构建、测试各引一个库就够。工具越多，升级时的兼容问题越多。

### 类型与校验混用

zod 这类库同时给类型和运行时校验，但生成的类型只覆盖校验过的形状，没校验的字段仍是 `any`。

### 版本漂移

生态库的大版本经常带破坏性变更。锁版本并读 changelog，比追最新更省事。
