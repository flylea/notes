# 第 47 章 类型检查器内部原理

用了很久 TypeScript，有些事会一直别扭。改一个类型，另一个文件报错；明明写了 `as` 却不生效；某个泛型一嵌套就慢得离谱。

这些现象背后是同一套机制：类型检查器怎么建立类型、怎么判断兼容、什么时候放弃。

这一章不讲语法，讲编译器怎么干活。读完你应该能回答三个问题：

- 这个报错是哪个阶段产生的？
- 为什么这个类型比较这么慢？
- 为什么有些错误编译器不报？

先说明版本。这一章描述的是 5.9 版的 JavaScript 实现，文中引用的 `src/compiler/checker.ts` 行号都以 5.9.3 为准（[源码在 GitHub 上](https://github.com/microsoft/TypeScript/blob/v5.9.3/src/compiler/checker.ts)，按文中行号能直接跳过去）。7.0 换成 Go 之后代码结构大体对应，但文件、函数名和行号都对不上，`checker.ts` 也不再存在。想读 7.0 的实现，先看第 49 章。

## 一次编译经过四个阶段

`tsc` 拿到源码后，大致按下面的顺序走。

```text
.ts 文件
  ↓  1. 解析（parse）
语法树 SourceFile
  ↓  2. 绑定（bind）
符号表，每个名字指向一个 declaration
  ↓  3. 检查（check）
类型对象、兼容性判断、推断结果
  ↓  4. 输出（emit）
.js / .d.ts
```

前三个阶段合起来叫"前端"，emit 是"后端"。类型系统只活在前端，输出阶段只做语法到语法的转换。

`tsc --extendedDiagnostics` 会把每个阶段的耗时打出来。下面是一个真实输出。

```text
Files:              83
Lines:           58451
Identifiers:     49740
Symbols:         59789
Types:           35345
Instantiations:  34241
Memory used:    64781K
Memory allocs:  277009
Parse time:     0.015s
Bind time:      0.005s
Check time:     0.126s
Emit time:      0.000s
Total time:     0.146s
```

这里有一个反直觉的点：检查阶段（Check）通常比解析（Parse）慢一个数量级。文件大小差不多时，类型写得越复杂，Check 时间涨得越快。

`Types` 是这次编译里创建的**不同**类型对象的个数，`Instantiations` 是泛型、条件类型被实例化的次数。这两个数会随类型复杂度的增加而急剧上升，所以它们是排查类型性能的两个主要指标。

解析阶段做的事没有想象中多。它只负责把文本变成语法树，不判断类型对错。`const x: string = 1` 在 parse 阶段完全合法，报错发生在 Check。

顺带说一个容易误会的点：语言服务（编辑器里的高亮、补全）走的是另一条路径。它不输出文件，只跑前端，并且尽量增量更新。所以编辑器里不报错、`tsc` 报错，多半是增量检查与全量检查的范围不同，不是编译器坏了。

## 类型空间和值空间

TypeScript 有两个空间：类型空间和值空间。同一个名字可以只在前者存在，也可以只在后者存在。

```ts
interface Profile {
  id: string;
}

const profile = { id: "1" };

// 类型空间里用 Profile，没问题
const p: Profile = profile;

console.log(Profile);
```

第二行 `console.log(Profile)` 会报错。

```text
error TS2693: 'Profile' only refers to a type, but is being used as a value here.
```

反过来，只存在于值空间的名字不能当类型用。

```ts
const createProfile = () => ({ id: "1" });

type P = createProfile; // error TS2749: 'createProfile' refers to a value, but is being used as a type here. Did you mean 'typeof createProfile'?
```

`type P = createProfile` 会提示 TS2749。

有三类名字同时存在于两个空间：

| 声明 | 类型空间 | 值空间 |
| --- | --- | --- |
| `interface` | 有 | 无 |
| `type` | 有 | 无 |
| `const` / `let` / `function` | 无 | 有 |
| `class` | 有 | 有 |
| `enum` | 有 | 有 |
| `namespace` | 有 | 有 |

`class` 同时出现在两边，所以既能写 `const a: SomeClass`，也能写 `new SomeClass()`。这不是语法糖，是 binder 阶段真的建了两个声明。

理解两个空间，能解释一批怪现象：

- 为什么 `typeof` 只能接值，因为它取的是"这个值在类型空间里的类型"；
- 为什么 `import type` 只导入类型，编译后这一行被整行删掉；
- 为什么 `declare` 可以凭空造出一个类型，它只写符号表，不产生代码。

## 类型在编译器里是对象

类型不是字符串，也不是 AST 节点。检查器给每个类型建一个对象，带三个关键字段：标识、种类标记、结构信息。

种类标记在源码里叫 `TypeFlags`，是用位运算拼出来的整数。`String`、`Number`、`Union`、`Object` 各占一位，多种标记能同时存在。

标识是递增数字。同一类型只建一次，重复出现时复用同一个对象。这个复用是性能的基础，判断"这两个类型是不是同一个"退化成比较数字。

这里有一个和直觉冲突的地方：两个名字不同、结构相同的 `interface`，是两个不同的类型对象。

```ts
interface A {
  id: string;
}
interface B {
  id: string;
}

const a: A = { id: "1" };
const b: B = a;

// 运行时它确实只是一个对象
console.log(b.id);
```

这段能编译。`b` 的静态类型是 `B`，赋进去的却是 `A` 的对象，编译器允许，因为结构化比较不看名字。

也正因为结构化比较要逐属性走，编译器给每一次"兼容性判断"都加了缓存。

同一个类型对在同一个程序里可能被比较几百次。没有缓存时，深层嵌套的类型会把耗时推到指数级。源码里用 `assignableRelation`、`subtypeRelation` 这样的关系对象存结果，键是类型标识对。

这些细节来自编译器源码（就是开头那个链接指向的 `checker.ts`），不是官方文档的承诺。写在这里是为了解释行为，不是让你依赖它。

## 兼容性判断的算法

`const x: A = y` 能不能过，取决于 `y` 的类型是否可赋值给 `A`。检查器的方法叫 `isTypeAssignableTo`，大致按下面的顺序走。

1. 相同类型直接通过。
2. 目标或来源是 `any`，直接通过。
3. 来源是 `never`，直接通过。
4. 来源是联合，逐成员判断，全部通过才算通过。
5. 目标是联合，任一成员通过就算通过。
6. 目标是交叉，逐成员判断。
7. 对象对对象，逐个属性比较。
8. 函数对函数，比参数和返回值。
9. 以上都不行，判失败。

顺序很重要，先做便宜的判断，尽量不进入结构比较。这也是为什么 `any` 会让你少看见错误：它在第二步就短路了。

对象比较的规则可以概括成一句话：目标要的每一个属性，来源都得有，且类型兼容。

```ts
interface Named {
  name: string;
}

interface Employee {
  id: string;
  name: string;
  email: string;
}

const employee: Employee = { id: "1", name: "a", email: "a@example.com" };
const named: Named = employee;

// 反向不行，缺少 id 和 email
const back: Employee = named;
```

最后一行报错。

```text
error TS2739: Type 'Named' is missing the following properties from type 'Employee': id, email
```

函数比较更麻烦，因为参数有方向。看下面的例子。

```ts
type Handler = (event: { type: string }) => void;

const handlesAll = (event: { type: string; target: string }) => {
  console.log(event.target);
};

// 参数更具体的函数，不能赋给参数更宽的类型
const h: Handler = handlesAll;
```

这里会报错，提示参数类型不兼容。

```text
error TS2322: Type '(event: { type: string; target: string; }) => void' is not assignable to type 'Handler'.
  Types of parameters 'event' and 'event' are incompatible.
    Property 'target' is missing in type '{ type: string; }' but required in type '{ type: string; target: string; }'.
```

理由用运行时想最清楚：`Handler` 保证"给一个只有 type 的对象就能调用"。`handlesAll` 要求必须有 `target`，调用时会读到 `undefined`。所以更严格的参数不能顶替更宽松的参数。这就是参数逆变。

但方法参数是例外。写在对象字面量或 interface 里的方法，默认双变。

```ts
interface Store {
  put(item: { id: string }): void;
}

interface StrictStore {
  put(item: { id: string; name: string }): void;
}

declare const strict: StrictStore;

// 方法参数双变，这里不报错
const store: Store = strict;

store.put({ id: "1" });
```

这段能编译。`store.put({ id: "1" })` 实际调的是 `strict.put`，它需要 `name`，运行时拿到 `undefined`。TypeScript 知道这个洞，但为了兼容大量老代码，方法参数保留了双变。

`strictFunctionTypes` 只作用于"属性风格的函数类型"，也就是把函数写成一个属性而不是一个方法。

```ts
interface Store2 {
  put: (item: { id: string }) => void;
}

interface StrictStore2 {
  put: (item: { id: string; name: string }) => void;
}

declare const strict2: StrictStore2;

const store2: Store2 = strict2;
```

最后一行报 TS2322。方法写法的坑，很多人是读到源码才发现。

这条报错在实现里是一个 `Diagnostic` 对象。检查器调用 `error(location, message, ...args)` 生成它，`message` 是消息表生成的常量，形如 `Diagnostics.Type_0_is_not_assignable_to_type_1`，`args` 填占位符。嵌套原因放在 `messageChain` 里，所以一条 TS2322 下面还能带「属性 x 类型不兼容」。7.0 换成 Go 实现后，消息表仍由同一份 JSON 生成，码没变。

## 泛型推断：从实参反推类型参数

调用泛型函数时没写类型参数，编译器要自己推。做法是从实参位置收集候选，再从中挑一个"最佳公共类型"。

```ts
function first<T>(items: T[]): T {
  return items[0];
}

const n = first([1, 2, 3]);
const s = first(["a", "b"]);
const mixed = first([1, "a"]);
```

`n` 是 `number`，`s` 是 `string`，`mixed` 是 `number | string`。最后这个结果是联合，因为候选 `number` 和 `string` 没有公共的子类型，只能取并集。

推断不是万能的。看下面的例子。

```ts
function pair<T>(a: T, b: T): [T, T] {
  return [a, b];
}

const p1 = pair(1, 2);

const p2 = pair(1, "a");

// 想露出联合，显式标注
const p3 = pair<string | number>(1, "a");
```

`p1` 推成 `[number, number]`。`p2` 里 `T` 先按第一个实参定成 `number`，第二个实参就报错。

```text
error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```

推断不是"随便凑一个能过的类型"，它先定下第一处候选，后面冲突就报错。想让两个位置都接受联合，显式写 `pair<string | number>`。想保留每个位置各自的具体类型，就把类型参数拆成两个。

推断失败时，类型参数会落到它的约束上。没有约束就落到 `unknown`。这是为什么有时你会看到"参数类型是 unknown"的报错。

条件类型里的 `infer` 是另一种推断：它不是从实参收集，而是在匹配模式时绑定一个占位符。

```ts
type ElementOf<T> = T extends (infer U)[] ? U : never;

type A = ElementOf<string[]>;
type B = ElementOf<number>;
```

`A` 是 `string`，`B` 是 `never`，因为 `number` 不匹配数组模式。

`infer` 的绑定只在对应的条件分支里可见，出了分支就失效。这也是为什么嵌套 `infer` 需要一层层往外传。

## 条件类型：延迟、分配、实例化

条件类型不是一遇到就求值。当它依赖的类型参数还没确定时，结果是"延迟"的。

```ts
type IsString<T> = T extends string ? true : false;

// 这里 T 还没绑定，结果是延迟的条件类型
type Pending<T> = IsString<T>;

// 绑定了才求值
type R1 = Pending<"a">;
type R2 = Pending<number>;
```

`R1` 是 `true`，`R2` 是 `false`。声明 `Pending<T>` 的时候，检查器只建了一个"未实现的类型节点"，等到被引用且实参明确时才实例化。

分配规则是另一个容易踩的点。当条件左边是裸类型参数，且实参是联合，条件类型会逐个成员分配。

```ts
type Boxed<T extends string | number> = T extends string ? `s:${T}` : `o:${T}`;

type U1 = Boxed<string | number>;

const a1: U1 = "s:string";
const a2: U1 = "o:42";
```

`U1` 是两个成员的并集，每个成员各走一遍分支。`string` 那一支变成字面量 `"s:string"`，`number` 那一支变成模板模式 `o:${number}`。

原因在插值：模板字面量遇到 `number` 不会枚举所有数字，只保留"这里是个数字"这个模式。所以 `a2` 能接收 `"o:42"`，因为 `"o:42"` 落在 `o:${number}` 里。

不想分配，就把两边都包进元组。

```ts
type NotDistributed<T> = [T] extends [string] ? "all string" : "has non string";

type U2 = NotDistributed<string | number>;
type U3 = NotDistributed<string | "a">;
```

`U2` 是 `"has non string"`，`U3` 是 `"all string"`。包成元组后，联合被当成一个整体比较，不再拆分。

这个技巧值得记住：**凡是不想逐成员处理联合，就用 `[T] extends [U]`。**

模板字面量类型也参与分配。看下面的例子。

```ts
type Greet<T extends string> = `hello ${T}`;

type Names = "a" | "b";
type Greetings = Greet<Names>;
```

`Greetings` 是 `"hello a" | "hello b"`，模板字面量对联合做了笛卡尔展开。

## 递归的代价与 TS2589

类型体操写多了，一定会遇到这个错。

```text
error TS2589: Type instantiation is excessively deep and possibly infinite.
```

它不是"语法错了"，而是"算不完"。检查器有两个计数在管这件事：单次实例化的深度，以及整个程序的实例化总数。任何一项到顶，就抛这个错。

从 TypeScript 4.5 起，编译器对一种特定形状做了尾递归优化：条件类型的递归调用直接出现在分支末尾，且只有一个递归分支。符合这个形状的递归，可用深度比普通递归深得多。

实测数据（TypeScript 7.0.2，本机）：

| 形状 | 通过 | 失败 |
| --- | --- | --- |
| 尾递归拼接字符串 | 990 层 | 1000 层 |
| 非尾递归嵌套数组 | 600 层 | 1000 层 |

```ts
// 尾递归：递归调用在分支最后
type Join<T extends readonly unknown[], Acc extends string = ""> =
  T extends readonly [infer F extends string, ...infer R extends string[]]
    ? Join<R, `${Acc}${F}`>
    : Acc;

// 990 个元素能过
type Long = Join<["a", "a"]>;
```

上面只放了 2 个元素，是为了让代码能直接跑。真实测试用的是 990 个元素拼成的元组。

同样的逻辑写成非尾递归，深度会掉一个数量级。

```ts
// 非尾递归：递归结果还要再包一层
type Wrap<T, N extends number, Acc extends unknown[] = []> =
  Acc["length"] extends N ? T : Wrap<[T], N, [...Acc, 0]>;

type Shallow = Wrap<1, 10>;
```

`Shallow` 能算出来，但深度上限远低于尾递归版本。

要更深的处理，得换思路，不能硬递归：

1. 分块。把长元组切成几段，分别递归，再拼起来。
2. 记忆化。把中间结果存成 `interface`，同一组参数再访问时复用。
3. 改成运行时。深度超过几百层的类型，通常意味着这件事不该在类型层做。

判断一个类型是不是"算不完"，看 `--extendedDiagnostics` 的 `Instantiations` 最直接。改一行类型，这个数从 3 万涨到 300 万，基本可以确定写坏了。

## 输出阶段：类型怎么被删掉

emit 阶段做的事，可以概括成：保留值，删掉类型。

```ts
interface User {
  id: string;
}

function greet(user: User): string {
  return `hello ${user.id}`;
}

const user: User = { id: "1" };
console.log(greet(user));
```

编译出来的 JavaScript 如下。

```js
function greet(user) {
    return `hello ${user.id}`;
}
const user = { id: "1" };
console.log(greet(user));
```

`interface` 整个没了，函数参数的类型注解没了，变量的类型注解没了。`User` 这个名字在运行时不存在。

这解释了一串现象：

- 泛型实参在运行时拿不到，`function f<T>(x: T)` 编译后就是 `function f(x)`；
- 不能对 `interface` 用 `instanceof`，它没有运行时值；
- `import type` 必须显式写，否则编译器不知道这一行能不能删。

`verbatimModuleSyntax` 打开后，编译器不再猜哪些导入是类型。你写普通 `import`，它就原样保留。

下面按两个文件写，`./types` 里导出 `Profile`。

```ts
// verbatimModuleSyntax 下，这行会被保留，运行时执行
import { Profile } from "./types";

// 这行一定被删掉
import type { Profile as ProfileType } from "./types";
```

保留的普通导入如果指向一个只有类型的模块，运行时会报错。

```text
SyntaxError: The requested module './types.js' does not provide an export named 'Profile'
```

Node 原生剥离是同一条思路的另一种实现：只删类型，不做语法转换。所以凡是"类型语法里带着运行时代码"的写法，它都处理不了，比如 `enum`、带值的 `namespace`、构造函数参数属性。

这也解释了为什么 `erasableSyntaxOnly` 这个开关有意义：它在编译期就禁止这类写法，让代码天然可以被逐行剥离。

## 观察编译器：四个开关

四个开关都是命令行参数，也可以在 `tsconfig.json` 里写（[配置参考](https://www.typescriptlang.org/tsconfig)）。

遇到"为什么报错""为什么慢""为什么找不到模块"，先别猜，用开关看。

**`--extendedDiagnostics`** 打印阶段耗时与类型数量。适合比较改前改后。

**`--generateTrace <dir>`** 生成 trace 文件与 types.json，可以用 Chrome 的 `chrome://tracing` 打开看类型检查热点。适合定位"哪个类型把编译拖慢了"。

**`--traceResolution`** 打印模块解析过程。适合排查"为什么这个包解析到了另外一个版本"。

```text
======== Resolving module './utils' from '/app/src/main.ts' ========
Explicitly specified module resolution kind: 'NodeNext'.
```

**`--explainFiles`** 打印每个文件为什么被包含进来，以及为什么没被包含。适合排查"这个库的类型怎么进来了"。

四个开关都是只加日志，不改编译结果。排查时随便用，上线前记得去掉。

## 能编译不等于正确

TypeScript 的设计目标之一是"在 JavaScript 上加可选的类型检查"，不是"保证运行时安全"。有些地方它故意留了口子。

```ts
// 1. any 会短路整个检查
const raw: any = JSON.parse("{}");
const num: number = raw;

// 2. 断言可以绕过兼容性
const value = "1" as unknown as number;

// 3. 数组是协变的
const strings: string[] = [];
const anys: unknown[] = strings;
anys.push(1);

// 4. 可选属性读取时不检查
interface Options {
  timeout?: number;
}
const opts: Options = {};
const t = opts.timeout!.toFixed();
```

四段都能编译。前三段在运行时可能出错，第四段一定出错。

这些不是 bug。严格的动态检查需要运行时信息，而 TypeScript 的类型在编译后就不存在了。它只能保证"你写的类型之间自洽"，不能保证"数据符合类型"。

要补上运行时这一层，靠的是在系统边界做校验，见第 45 章。

## 绑定阶段：符号表与声明合并

解析只建语法树，不认名字。给名字建立关联的是绑定阶段（bind）。

绑定阶段遍历一次语法树，为每一处声明建一个 symbol，把名字、所在作用域、对应的声明节点串起来。检查阶段再查名字时，走的就是这张符号表。

这一步解释了声明合并。同一个作用域里出现多次同名声明，binder 把它们挂到同一个 symbol 上，checker 再把它们合成一个类型。

```ts
interface Profile {
  id: string;
}

interface Profile {
  name: string;
}

// interface 合并，两个字段都在
const p: Profile = { id: "1", name: "a" };
```

但 `type` 别名不能合并。原因是别名只能指向一个目标，第二次声明没有可合并的语义。

```ts
type Point = { x: number };
type Point = { y: number };

const pt: Point = { x: 1 };
```

两处都报 TS2300。

```text
error TS2300: Duplicate identifier 'Point'.
```

函数的重载也是绑定阶段的产物：多条只有签名的声明，加一条实现。实现签名对外不可见，调用时只看到前面几条。

```ts
function parse(value: string): number;
function parse(value: number): string;
function parse(value: string | number): string | number {
  return typeof value === "string" ? Number(value) : String(value);
}

const a = parse("1");
const b = parse(1);
```

声明合并是给第三方库补类型的基础写法。往一个模块里加字段，靠 module augmentation；往全局加字段，靠 global augmentation。

```ts
// 给 Express 的 Request 加一个字段
declare module "express-serve-static-core" {
  interface Request {
    userId?: string;
  }
}
```

这块要装 `@types/express`；没装时报 `TS2664: Invalid module name in augmentation, module 'express-serve-static-core' cannot be found`。

全局增强必须写在模块里。少了 `import` 或 `export`，文件会被当成脚本，全局增强就没有宿主。

```ts
// 这个文件里没有 import 和 export，会被当成脚本
declare global {
  interface Window {
    appVersion: string;
  }
}
```

这样写报 TS2669。

```text
error TS2669: Augmentations for the global scope can only be directly nested in external modules or ambient module declarations.
```

补一行 `export {}` 让文件成为模块，报错消失。

```ts
declare global {
  interface Window {
    appVersion: string;
  }
}

export {};
```

## 增量：`.tsbuildinfo` 和语言服务

大项目里全量编译很慢，`tsc` 为此提供了增量模式。开 `--incremental` 后，第一次编译会写一个 `.tsbuildinfo`。

这个文件里存的东西比想象的少：编译选项、文件列表、每个文件的版本哈希、上次的诊断和输出映射。它不存完整的类型图。

顶层有五个键：`version`、`root`、`fileNames`、`fileInfos`、`options`。下面是其中一次真实编译的节选。

```json
{
  "version": "16934abaab7026ac114da441aabea1a0",
  "fileInfos": [
    {
      "version": "33f317af5428801f944a478d2c1e38e5",
      "affectsGlobalScope": true,
      "impliedNodeFormat": 1
    },
    "4831d2abe47c0e457e9dd6fcdb27b20c"
  ],
  "options": { "module": 99, "outDir": "./", "skipLibCheck": true, "strict": true, "target": 12 }
}
```

`fileInfos` 和 `fileNames` 一一对应。有全局影响的文件写成对象，其余只留一个哈希字符串。`options` 里是枚举编号，不是名字。

字段的具体含义没有写成文档，不同版本可能变。所以它是一个缓存文件，不该提交进版本库，也不该手改。

下次编译时，`tsc` 比对文件哈希。哪些文件变了，哪些文件的依赖签名变了，只重算这些。没变的复用上次结果。

项目引用（project references）用的 `composite` 是同一套机制的更强版本：每个子项目单独产物与 `.tsbuildinfo`，上游没变就不重编下游。

编辑器走的是另一条路径。语言服务常驻，只维护内存里的语法树和类型缓存，每次按键只重算受影响的范围。

这带来一个常见困惑：编辑器不报错，`tsc` 却报错。原因通常是四个：

1. 文件没保存，语言服务用的是内存版本；
2. `tsc` 用的是 tsconfig 全量配置，编辑器可能只加载了部分；
3. 增量缓存过期，删掉 `.tsbuildinfo` 再试；
4. 全量与增量对未使用文件的检查范围不同。

还有一个和工具链有关的开关：`isolatedModules`。打开它，要求每个文件的类型信息能独立判断。原因是 Babel、SWC、esbuild 这类逐文件转换器看不到别的文件，无法判断一个导入到底是类型还是值。

```ts
// a.ts
export interface Foo {
  x: string;
}

// b.ts，在 isolatedModules 下必须写成 export type
export { Foo } from "./a";
```

这一块把 `a.ts` 和 `b.ts` 放在一起展示；拆成两个文件后 `./a` 才解析得到，单块编译报 `TS2307: Cannot find module './a'`。

```text
error TS1205: Re-exporting a type when 'isolatedModules' is enabled requires using 'export type'.
```

`isolatedDeclarations` 是同一思路的更强约束：每个导出都要能单文件推断出 `.d.ts`，所以不能依赖从别的文件推出来的类型。

```ts
export function add(a: number, b: number) {
  return a + b;
}
```

开启 `--isolatedDeclarations` 后报错。

```text
error TS9013: Expression type can't be inferred with --isolatedDeclarations.
```

补上返回类型 `: number` 就好。这类约束看着烦，但它让库能被逐文件构建，也让构建可以并行。

## 小结

- 一次编译分解析、绑定、检查、输出四段，类型系统只在前三段工作。
- 类型空间和值空间是两套符号表，`class` 同时在两边。
- 类型在编译器里是带标识的对象，兼容性判断按结构逐属性比较，结果会缓存。
- 函数参数的方向决定能不能赋值，方法参数双变，属性风格的函数在 `strictFunctionTypes` 下逆变。
- 条件类型会延迟、会对裸类型参数逐成员分配，`[T] extends [U]` 可以阻断分配。
- 递归深度有上限，尾递归写法能多撑一个数量级，但终究要换思路。
- 输出阶段只删类型，删不掉的语法就是不可剥离语法。
- 编译通过只是类型之间自洽，运行时安全要靠边界校验。

## 用不上的时候

### 正在排查业务逻辑错误

类型检查器怎么工作，帮不上定位取错字段、算错分支这类问题。读调用栈和日志更快。

### 项目没开 strict

检查器的一部分规则只在 `strict` 下生效，`strictFunctionTypes` 就是例子。没开之前读这些机制，看到的行为对不上号。先开 `strict`，再看原理。

### 只写业务页面、不碰类型库

日常改组件不需要知道兼容性算法的九步。等遇到一条报错说不清原因、或者要写给别人用的类型时，再回来看这一章。
