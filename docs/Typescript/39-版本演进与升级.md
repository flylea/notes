# 第 39 章 版本演进与升级

同事机器上 `tsc --noEmit` 全绿，升级到 7.0.2 后同一份代码报出十几条配置错误。6.0 改默认值，7.0 把弃用项变成硬报错。这一章按配置、编译器、类型语义三层讲升级顺序和判断标准。

2026 年 11 月的发布线：

| 版本 | 发布日期 | 状态 | 对你的影响 |
|---|---|---|---|
| 5.9 | 2025-08-01 | 旧线末版 | 最后一个不用迁移配置的版本 |
| 6.0 | 2026-03-23 | 过渡版 | 改默认值，弃用旧选项，用 `ignoreDeprecations` 缓冲 |
| 7.0 | 2026-07-08 | 当前 stable（7.0.2） | Go 原生编译器接管，弃用项直接报错 |
| 7.1 | 2026-10-20（beta） | 预览 | `es2026`、source phase imports、新 API |

升级到 7.0，第一件事不是改代码，是让 `tsconfig.json` 过得了 7.0 的硬报错。第二件事是把 `strict` 新开的报错分完类。第三件才是看类型语义变了哪里。

6.0 把默认值的拨盘拨到新位置，7.0 把旧拨盘拆掉。老项目里那行 `"target": "es5"`，7.0 直接报 TS5108，删掉才能启动。默认值和移除项是两件事：前者改行为不改配置，后者改配置不改行为。升级时先清配置，再看行为。

6.0 是一个过渡版本。它的代码库还是 JavaScript 写的，职责是把 7.0 要用的新默认值提前落地，让生态有时间改配置。官方在 [6.0 公告](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/)里写得很直接：6.0 桥接 5.9 和 7.0。所以升 6.0 不等于多花一次迁移成本，它是 7.0 的预演。在 6.0 下把弃用项清干净，7.0 的配置报错就是零。

## 为什么分两步

6.0 只改默认值，不删选项。显式写了旧值的项目照旧编译，只有依赖默认值的项目行为变了。这一步让生态有时间改模板里的旧值，也把靠默认值运行的项目暴露出来。

7.0 才删。删的时候分成两种报错。选项本身没了，比如 `downlevelIteration`、`baseUrl`、`outFile`，报 TS5102。选项还在但某个值没了，比如 `target: "es5"`、`moduleResolution: "node"`，报 TS5108。区别在读取方式：值被移除时，编译器还要读这个选项才能发现值不对；选项被移除时，连读都不读。

分两步是让升级路径短一点。5.9 直接跳 7.0，配置错误和行为变化一起出现，分不清哪条报错来自哪一类改动。先到 6.0 清配置，行为变化单独观察，到 7.0 剩下的只有配置报错。公告把这层关系写成桥接：6.0 铺路，7.0 落地。

反过来只改默认值不删选项也不行。旧值会一直留在模板和 CI 脚本里，生态没有动力改，默认值改了等于没改。

两步的节奏在公告里能看到。6.0 的公告给默认值表和弃用清单，7.0 的公告给移除清单和迁移入口。7.0 报错里那行 `Visit https://aka.ms/ts6 for migration information.` 就是给旧配置准备的。按公告排升级，比在报错里逐条试要快。

清配置的顺序按报错数排：先清 TS5108 和 TS5102，这两类不修就启动不了；再处理 TS5011 这类布局报错；最后才是行为变化引起的类型错误。每清一类重跑一次 `tsc -p`，报错会一层层露出来，不要一次改十几项。

## 改掉的默认值

6.0 把几个以前靠模板配置的选项变成了默认值。老项目如果显式写了旧值，7.0 会拒。

| 选项 | 5.9 默认 | 6.0 起默认 | 恢复旧行为 |
|---|---|---|---|
| `strict` | `false` | `true` | `"strict": false` |
| `module` | `commonjs`（随 target 变） | `esnext` | `"module": "commonjs"` |
| `target` | `es5` | `esnext` 前一个稳定版（当前 `es2025`） | 显式写 `"target": "es2019"` |
| `types` | 自动加载 `node_modules/@types` 全部包 | `[]` | `"types": ["*"]` |
| `rootDir` | 由输入文件推断 | `./` | 显式写 `"rootDir": "./src"` |
| `noUncheckedSideEffectImports` | `false` | `true` | 关掉或补齐声明 |
| `libReplacement` | `true` | `false` | 显式写 `"libReplacement": true` |
| `stableTypeOrdering` | 无此选项 | `true`，7.0 起不能关 | 无 |

`target` 的默认值写成「`esnext` 前一个稳定版」，实际就是当前 stable 的 ECMAScript 版本，7.0.2 下是 `es2025`。这个值会随发布变，所以 CI 里要显式写 `target`，否则换一个 TS 版本，默认 lib 也跟着变。验证办法是编译时看 `tsc --showConfig` 的 `target` 和 `lib` 两行。

`strict` 默认打开后，老代码里没标注参数类型的函数会直接报错：

```ts
export function tagOf(node) {
  return node.kind;
}
```

报错是 `error TS7006: Parameter 'node' implicitly has an 'any' type.`。补上入参和返回类型即可：

```ts
interface NodeLike {
  kind: string;
}

export function tagOf(node: NodeLike): string {
  return node.kind;
}
```

`types` 默认 `[]` 的动机写在 6.0 公告里：老行为会枚举 `node_modules/@types` 下所有包，一个大仓库能扫出上千个包。显式写 `types` 能让构建快 20% 到 50%。代价是 `process`、`__dirname` 这类 Node 全局直接消失：

```ts
export const env = process.env.NODE_ENV;
```

报错是 `error TS2591: Cannot find name 'process'. Do you need to install type definitions for node? Try npm i --save-dev @types/node and then add 'node' to the types field in your tsconfig.` 加上 `types` 即可：

```json
{
  "compilerOptions": {
    "types": ["node"]
  }
}
```

前提是 `npm i -D @types/node` 已经装过。没装会报 `TS2688: Cannot find type definition file for 'node'`。

跑测试的项目还会碰到第二类报错。`describe`、`it`、`expect` 这些全局来自 `@types/jest` 或 `vitest/globals`，`types: []` 之后同样找不到。解决办法是把它们加进 `types`，或者用 `import { describe, it, expect } from "vitest"` 显式导入。显式导入更稳，不依赖 tsconfig。

如果只想先跑通再慢慢收，用这组配置回到 5.9 行为。7.0.2 下可以编译：

```json
{
  "compilerOptions": {
    "strict": false,
    "module": "commonjs",
    "target": "es2019",
    "types": ["*"]
  },
  "include": ["./main.ts"]
}
```

`libReplacement` 和 `noUncheckedSideEffectImports` 见 6.0 公告的默认值清单，恢复写法就是表里那两行。

6.0 还补了两处 lib 变化。`es2025` 成为正式的 target 和 lib，`Promise.try`、`Iterator` 的辅助方法、`Set` 的集合运算从 `esnext` 转正。`dom` 这个 lib 合并了 `dom.iterable` 和 `dom.asynciterable`，只写 `"lib": ["dom"]` 就能 `for...of` 遍历 `NodeList`，不用再列三行。

`Temporal` 的类型在 `esnext` lib 里，属于预览。`Map` 和 `WeakMap` 的 `getOrInsert` 同样只在 `esnext`，要用得把 lib 提上去。

## 弃用、7.0 报错的选项

下面这些选项在 6.0 只是弃用，配 `"ignoreDeprecations": "6.0"` 还能用。7.0 不支持这个开关，见到就报错。

| 旧写法 | 替代写法 | 7.0 报错 |
|---|---|---|
| `"target": "es5"` | `es2015` 及以上，或交给打包器降级 | TS5108 |
| `"moduleResolution": "node"` / `"node10"` / `"classic"` | `"bundler"`、`"node16"`、`"nodenext"` | TS5108 |
| `"module": "amd"` / `"umd"` / `"systemjs"` / `"none"` | `"preserve"`、`"esnext"`、`"nodenext"` | TS5108 / TS6046 |
| `"baseUrl"` | 删掉，在 `paths` 里写完整相对路径 | TS5102 |
| `"outFile"` | 用打包器 | TS5102 |
| `"downlevelIteration"` | `target` 提到 `es2015` 以上 | TS5102 |
| `"esModuleInterop": false` | 删掉该行（固定为开） | TS5108 |
| `"alwaysStrict": false` | 删掉该行 | TS5108 |
| `import x from "y" assert { type: "json" }` | 换成 `with` | TS2880 |
| `/// <reference no-default-lib="true"/>` | 用 `lib` 控制 | 7.0 忽略 |
| `module Foo {}`（namespace 里的 module 关键字） | 用 `namespace` | 7.0 硬错 |

### 两个码怎么分

目录里有一个 `index.ts`，配置文件只留两个会被移除的选项：

```json
{
  "compilerOptions": {
    "target": "es5",
    "downlevelIteration": true
  },
  "files": ["index.ts"]
}
```

```bash
$ tsc -p tsconfig.json
tsconfig.json(3,15): error TS5108: Option 'target=ES5' has been removed. Please remove it from your configuration.
tsconfig.json(4,5): error TS5102: Option 'downlevelIteration' has been removed. Please remove it from your configuration.
```

一个文件里两个选项，报了两个不同的码。规律是：选项名还在、值被移除，报 TS5108；整个选项没了，报 TS5102。`moduleResolution: "node"` 属于前者，报 TS5108；`baseUrl` 属于后者，报 TS5102。

修法也按这条分。改值：`target` 提到 `es2019` 以上，`moduleResolution` 换成 `bundler` 或 `nodenext`。删项：`downlevelIteration` 直接删，迭代行为由 `target` 决定；`baseUrl` 删掉后把 `paths` 写成从配置文件算起的相对路径。

一份 5.9 风格的配置在 7.0.2 下会一次报一大片：

```json
{
  "compilerOptions": {
    "target": "es5",
    "module": "commonjs",
    "moduleResolution": "node",
    "baseUrl": "./src",
    "outFile": "./dist/bundle.js",
    "downlevelIteration": true
  },
  "include": ["./src"]
}
```

```text
tsconfig.json(3,15): error TS5108: Option 'target=ES5' has been removed. Please remove it from your configuration.
tsconfig.json(5,25): error TS5108: Option 'moduleResolution=node10' has been removed. Please remove it from your configuration.
tsconfig.json(6,5): error TS5102: Option 'baseUrl' has been removed. Please remove it from your configuration.
  Use '"paths": {"*": ["./src/*"]}' instead.
tsconfig.json(7,5): error TS5011: The common source directory of 'tsconfig.json' is './src'. The 'rootDir' setting must be explicitly set to this or another path to adjust your output's file layout.
  Visit https://aka.ms/ts6 for migration information.
tsconfig.json(7,5): error TS5102: Option 'outFile' has been removed. Please remove it from your configuration.
tsconfig.json(8,5): error TS5102: Option 'downlevelIteration' has been removed. Please remove it from your configuration.
```

注意 `TS5011`：`outFile` 没了以后，多个输入文件需要 `rootDir` 才能推出输出布局，报错里还给了迁移文档地址 `https://aka.ms/ts6`。

`baseUrl` 迁移是改动最多的一项。旧写法用 `baseUrl` 决定非相对导入的查找根，新写法把根写进 `paths`：

```json
{
  "compilerOptions": {
    "target": "es2025",
    "module": "preserve",
    "moduleResolution": "bundler",
    "paths": {
      "@app/*": ["./src/*"]
    },
    "noEmit": true
  },
  "include": ["./src"]
}
```

旧配置里常见的 `"baseUrl": "./src"` 加 `"paths": {"@app/*": ["app/*"]}`，两处路径是拼起来的。删掉 `baseUrl` 后，`paths` 里的每一项都要写成从 tsconfig 所在目录算起的相对路径，也就是 `"./src/app/*"`。如果不想逐项改，加一条 `"*": ["./src/*"]` 能把查找根补回来，但会同时放开所有包名，只在过渡期用。

`module: "amd"`、`"umd"`、`"systemjs"` 这几个输出格式没有平替，官方立场是交给打包器。库代码改成 `"module": "preserve"`，由使用方决定产物：

```json
{
  "compilerOptions": {
    "module": "preserve",
    "moduleResolution": "bundler",
    "target": "es2025"
  }
}
```

导入断言改导入属性，`assert` 留着会报 TS2880：

```ts
import data from "./data.json" assert { type: "json" };

export const id = data.id;
```

报错是 `error TS2880: Import assertions have been replaced by import attributes. Use 'with' instead of 'assert'.` 改成 `with`：

```ts
import data from "./data.json" with { type: "json" };

export const id = data.id;
```

这块和磁盘上的 `data.json` 一起才完整；单独编译报 `TS2307: Cannot find module './data.json'`。

第二段要在 `module: "esnext"`、`moduleResolution: "bundler"`、`resolveJsonModule: true` 下才通过。改成 `with` 但在 `module: "nodenext"` 的 CommonJS 文件里，会报 `TS2856: Import attributes are not allowed on statements that compile to CommonJS 'require' calls.`。

如果项目里还在用 `importsNotUsedAsValues` 或 `preserveValueImports`，这两个选项在 7.0 里是 `TS5023: Unknown compiler option`，平替是 5.0 的 `verbatimModuleSyntax`。它要求类型导入写 `import type`，混着写会报 `TS1484: 'OrderRow' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.`。

`verbatimModuleSyntax` 和 `isolatedModules` 不是一回事。后者要求每个文件能单独转译，前者进一步要求 import 语句原样输出。打包器和 Node 直跑 `.ts` 的场景用前者，只有 Babel 转译的项目用后者就够。

`tsc --init` 生成的模板已经是 7.0 风格，`module: "nodenext"`、`target: "esnext"`、`types: []`、`strict: true`、`verbatimModuleSyntax: true`。用这个模板起新项目，能避开上面大部分坑。

## 升级顺序

第 1 步，把版本换到 7.0 并跑一次类型检查，先看配置层面的报错。命令行直接传文件时，7.0 还会拦住你：

```bash
$ npx tsc --noEmit src/index.ts
error TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline. Use '--ignoreConfig' to skip this error.

$ npx tsc --noEmit --ignoreConfig src/index.ts
```

第 2 步，按错误码分批处理。`TS5102`、`TS5108` 是配置问题，`TS5112` 是调用方式问题，`TS5011` 是 `rootDir` 问题。这三类清完，配置就迁移完了。

配置类错误有个共同点：一次能报出十几条，改完一批会冒出下一批。因为 7.0 是先校验配置项本身，再解析文件，最后才做类型检查。按这个顺序改，每轮都会有进展。

`--ignoreConfig` 是 6.0 加的参数。7.0 里命令行只要带了文件路径，就必须显式加它，否则连一个文件都编不了。CI 脚本里那些 `tsc src/a.ts` 的写法都要检查一遍，改成 `tsc -p` 加 `--ignoreConfig`。

第 3 步，分 `strict` 新增的报错。`strict` 是一组开关的合集，成员有 `noImplicitAny`、`strictNullChecks`、`strictFunctionTypes`、`strictBindCallApply`、`strictPropertyInitialization`、`noImplicitThis`、`alwaysStrict`、`useUnknownInCatchVariables`、`exactOptionalPropertyTypes`。

其中 `exactOptionalPropertyTypes` 不在 `strict` 里，但 7.0 的 `tsc --init` 模板会带上它。它会把 `{ x?: number }` 和 `{ x: number | undefined }` 区分开，改的是可选属性的写法，不是空值检查。

报错量最大的是 `strictNullChecks` 和 `noImplicitAny`。按错误码统计一遍，`TS2531`、`TS2532`、`TS18047` 属于空值类，`TS7006` 属于隐式 any 类，两类分开处理。空值类优先修，隐式 any 类可以先加 `// @ts-expect-error` 挂账，但要在 CI 里统计数量，只减不增。

如果项目实在改不完，先关子开关而不是关整个 `strict`。`"strict": true` 加 `"strictNullChecks": false` 只丢掉空值检查，其他几项还在。关整个 `strict` 等于把已经改好的部分又放回去了。

第 4 步，看语义变化。7.0 有三处会改变现有代码的行为，都在下一节。

第 5 步，把 `ignoreDeprecations` 从配置里删掉，保证 CI 在 6.0 下也干净，否则升到 7.0 还会再撞一次。

6.0 公告里提到官方工具 `ts5to6`，能自动改 `baseUrl`、`rootDir` 这类机械迁移。手工改之前可以先跑一遍，再逐条看 diff。

## 换了编译器

7.0 的编译器用 Go 重写，[官方公告](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)的措辞是全量构建 8 到 12 倍提速。公告给的五个仓库实测：

| 仓库 | 6.x | 7.0 | 倍数 |
|---|---|---|---|
| vscode | 125.7s | 10.6s | 11.9x |
| sentry | 139.8s | 15.7s | 8.9x |
| bluesky | 24.3s | 2.8s | 8.7x |
| playwright | 12.8s | 1.47s | 8.7x |
| tldraw | 11.2s | 1.46s | 7.7x |

内存也有下降，公告给的范围是 6% 到 26%。首次报错的时间从 17.5s 降到 1.3s。

官方把提速归为三点：编译器本身是原生代码，没有 JS 引擎的解析与预热；类型检查在共享内存上多线程并行，默认 4 个检查器 worker；另有一批新的优化，涉及算法与内存布局。大仓库的内存占用跟着降，公告给的范围是 6% 到 26%。第一次报错变快是因为诊断不再等整个项目解析完。

并行怎么分、worker 之间怎么保持一致、移植为什么选 Go，第 49 章讲得完整。这一节只列升级时要动的东西。

机器核数少时，并行反而可能变慢。CI 容器只有 2 核，把 `--checkers` 设 1 或加 `--singleThreaded`，能避免 worker 之间抢 CPU。

7.0 新增了三个并行相关的命令行参数：

```bash
$ npx tsc --help --all | grep -A1 -E '^--(checkers|builders|singleThreaded)$'
--checkers
Set the number of checkers per project.
--
--singleThreaded
Run in single threaded mode.
--
--builders
Set the number of projects to build concurrently.
```

`--checkers` 默认 4 个类型检查 worker，机器核多可以调高。`--builders` 只对 `tsc -b` 生效，控制并行项目数。CI 机器核少或内存吃紧时，用 `--checkers 1` 或 `--singleThreaded`。

`--watch` 的实现也换了。旧实现是 `fs.watch` 加轮询兜底，7.0 把 `@parcel/watcher` 从 C++ 移植成 Go，大仓库里改一个文件后的重建时间明显缩短。`tsc -b` 的增量信息格式没变，因为该格式写进了 `tsconfig.tsbuildinfo`，跨版本还能读。

7.0 不带 API。所有依赖 `typescript` 包做类型操作的工具，在 7.0 下只能先装兼容包：

```bash
$ npm install -D typescript@npm:@typescript/typescript6
$ npx tsc6 --version
```

兼容包里的可执行文件叫 `tsc6`，参与构建但不参与日常 `tsc` 调用。nightly 走 `typescript@next`。

受影响的是直接 `import ts from "typescript"` 的工具：`ts-jest`、`ts-node`、`ts-node/esm`、部分 ESLint 插件、`dts-bundle-generator` 这类。它们要等作者把 API 迁到 7.1 的新模块。过渡期可以两套并存：日常 `tsc` 用 7.0，工具链侧用 `tsc6` 或继续留在 6.0。

`ts-node` 的维护状态本来就不推荐，新项目用 `tsx` 或 Node 自带的类型剥离，能绕开这块。

编辑器也有边界。7.0 的类型服务能覆盖 `.ts`、`.tsx`、`.js`，Vue、Svelte、Astro、MDX 的单文件组件和 Angular 模板还只能靠 6.0，因为这些工具用的是 6.0 的 JS API。

VS Code 有单独的 TypeScript 7 扩展。装了扩展的项目，编辑器里跑的是 7.0 的类型服务，命令行 `tsc` 可以是另一个版本。两个版本给出的错误不完全一样时，以 CI 的 `tsc` 为准，编辑器只用来提速。

Monorepo 里可以按包切版本。根目录锁 7.0，个别依赖旧 API 的工具包锁 6.0，pnpm 的 `overrides` 能按包名指定。

## 改了语义

### 声明文件里的类型顺序固定

6.0 加过 `stableTypeOrdering`，默认关；7.0 默认开，且不能关。效果是同一个项目反复编译，`.d.ts` 内容逐字节一致。

```ts
const baseWeight = 500;

export function pickWeight(heavy: boolean) {
  return heavy ? 100 : baseWeight;
}
// tsc --declaration 产出：
// export declare function pickWeight(heavy: boolean): 100 | 500;
```

在 6.0 里，联合顺序取决于类型第一次被创建的位置。把 `baseWeight` 挪到函数后面，输出会变成 `500 | 100`。7.0 固定按 `100 | 500` 输出，`--stableTypeOrdering false` 也不再接受。

这条会影响快照测试。升级后 `.d.ts` 的 diff 通常是顺序调整，不是类型真的变了。

对库作者更实际的意义是可复现构建。同一个源码在两个 CI 机器上生成完全相同的声明，缓存能命中，发布产物能对比。旧版因为类型顺序受声明位置影响，同样的代码换个文件顺序就产出不同的 `.d.ts`。

如果项目用 `api-extractor` 或 `attw` 校验导出面，升级后重跑一次基线，不要直接覆盖快照。

### 模板字面量按 Unicode code point 切

旧版按 UTF-16 码元切，emoji 会被切成两半。7.0 按 code point 切：

```ts
type HeadTail<S extends string> =
  S extends `${infer Head}${infer Tail}` ? [Head, Tail] : never;

type Result = HeadTail<"😀abc">;

const modern: Result = ["😀", "abc"];
const legacy: Result = ["\ud83d", "\ude00abc"];
```

`legacy` 那一行报 `error TS2322: Type '"\uD83D"' is not assignable to type '"😀"'`，它正是 6.x 的切法，7.0 下直接报错。处理用户输入的类型代码如果依赖 `infer` 切字符串，升级后要复核一遍按字符计数的逻辑。

受影响的是这些写法：`infer` 递归切字符串、按长度做类型校验、从路由模板里取参数名。全是模板字面量类型的用武之地。ASCII 输入的行为不变，只有代理对字符的切法变了。

### JavaScript 文件支持范围收窄

7.0 对 `.js` 的类型检查更接近 TypeScript 本体，Closure 那套写法砍掉了：

| 写法 | 7.0 |
|---|---|
| 把值当类型用（JSDoc 里写 `@type {someValue}`） | 报错 |
| `@enum` 注解 | 不再识别 |
| 单独的 `?` 类型 | 当成 `any` |
| `@class` 注解 | 不再当构造器 |
| 后缀 `!` 非空断言 | 不支持 |
| Closure 风格函数类型 | 不支持 |

关掉 `checkJs` 的纯 JavaScript 项目不受影响。开着 `checkJs` 的老项目，这块要单独跑一遍。

还有一处容易漏：`allowJs` 打开但 `checkJs` 关着时，`.js` 文件只参与编译不做类型检查，新规则不会报错，但生成的 `.d.ts` 会跟着变。发布类型定义的库要把这层产物也纳入对比。

### `--target es2026` 只有 7.1 有

7.0.2 下写 `es2026` 会被参数校验挡住：

```bash
$ npx tsc --noEmit --ignoreConfig --target es2026 lib.ts
error TS6046: Argument for '--target' option must be: 'es6', 'es2015', 'es2016', 'es2017', 'es2018', 'es2019', 'es2020', 'es2021', 'es2022', 'es2023', 'es2024', 'es2025', 'esnext'.
```

合法值到 `es2025` 为止，`esnext` 是唯一往前看的选项。

## Beta 的新东西

### ambient module 支持导入属性

库作者可以给非 JS 文件写带属性的模块声明：

```ts
declare module "*" with { type: "text" } {
  const content: string;
  export default content;
}
```

7.0.2 解析不了这行，报 `TS1005: ';' expected.`。7.1 里 `type` 可以写 `"text"`、`"css"`、`"bytes"`，使用方必须写全属性，否则报错。这类声明不校验磁盘文件是否真的存在，官方建议库不要发布，由使用方的打包器提供。

### source phase imports

导入模块的源码对象，不执行模块：

```ts
import source wasmModule from "./compute.wasm";

export async function load(): Promise<typeof wasmModule> {
  return await import.source("./compute.wasm");
}
```

7.0.2 下报 `TS1005: '=' expected.`。7.1 要求 `module` 为 `esnext`、`nodenext` 或 `preserve`，并加载 `esnext` lib。类型是新的全局类型 `AbstractModuleSource`。

### `es2026` 目标与 lib

7.1 稳定了 `es2026`，同时把一批新 API 加进 lib。7.0.2 下这些成员不存在：

```ts
export const precise = Math.sumPrecise([0.1, 0.2]);
export const isError = Error.isError(new Error("x"));
```

两行分别报 `error TS2339: Property 'sumPrecise' does not exist on type 'Math'` 和 `error TS2550: Property 'isError' does not exist on type 'ErrorConstructor'. Do you need to change your target library? Try changing the 'lib' compiler option to 'esnext' or later.` 7.1 的 `es2026` 包含 `Math.sumPrecise`、`Error.isError`、`Iterator.concat`、`JSON.rawJSON`、`JSON.parse` 带原文的重载、`Map` 和 `WeakMap` 的 `getOrInsert`、`Uint8Array` 的 base64 和 hex 方法、`Array.fromAsync`。

### 分布式类型参数检查变严

7.1 对类型参数分发后的约束检查更严格。这段代码在 7.0.2 下能过：

```ts
type Show<A extends number, B extends A> = `${B} extends ${A}`;

type Issue<A extends number, B extends A> =
  A extends B ? never : Show<A, B>;
```

7.1 报 `Type 'B' does not satisfy the constraint 'A'. 'B' is only assignable to the non-distributed 'A', but 'A' has been distributed here.` 依赖条件类型做分布式检查的库，升 7.1 前要跑一遍测试。

### 新 API 与性能

7.1 开始提供模块化的 API 子路径：`typescript/sync`、`typescript/async`、`typescript/fs`、`typescript/ast`、`typescript/ast/is`、`typescript/ast/factory`，资源用 `using` 释放。7.0 缺的那部分工具链能力开始补回来。

7.0 到 7.1 beta 的官方数据是 1.2 到 1.9 倍，内存降 15.8% 到 49.6%。

7.1 还加了 `contentMappers` 配置和 `--runExternalCode`，允许在 tsconfig 里声明自定义文件到内容的映射，给虚拟文件系统用。日常项目用不到，写构建工具时才有价值。

beta 不要上生产。7.1 beta 的定位是给库作者提前适配，`es2026` 和新的类型检查规则都可能在正式版前调整。等 `latest` 指向 7.1 再切，比抢 beta 省事。

## 5.x 里值得记住的变动

5.x 这条线跨了三年，下面只列会影响写法的节点。想查每一项的完整说明，去对应的 [release notes 页面](https://www.typescriptlang.org/docs/handbook/release-notes/overview.html)。

| 版本 | 关键特性 | 用在哪 |
|---|---|---|
| 5.0 | 标准装饰器、`const` 类型参数、`export type *`、`moduleResolution: "bundler"` | 写库、写组件库 |
| 5.2 | `using` 与 `Symbol.dispose` | 文件、锁、连接池 |
| 5.3 | 导入属性（`with`） | 读 JSON、CSS 模块 |
| 5.4 | `NoInfer<T>`、`Object.groupBy` 与 `Map.groupBy` | 给泛型默认值挡推断、按值分组 |
| 5.5 | 推断类型谓词、`isolatedDeclarations` | 单文件构建、并行 d.ts |
| 5.6 | 迭代器辅助方法 | 链式处理 `IteratorObject` |
| 5.7 | `--target es2024`、`--rewriteRelativeImportExtensions` | Node 直跑 `.ts` |
| 5.8 | `--module node18`、`libReplacement` | Node 项目 |
| 5.9 | `import defer`、`--module node20` | 懒加载、Node 新版本 |

`satisfies` 不在这个表里，它是 4.9 的特性，常被和 5.0 一起记。

几个会直接影响写法的特性，代码是这样的：

```ts
function collectIds<const T extends readonly string[]>(ids: T): T {
  return ids;
}

const picked = collectIds(["ord_1", "ord_2"]);
const literal: readonly ["ord_1", "ord_2"] = picked;
```

`const` 类型参数让返回值保留字面量，不写它会推成 `readonly string[]`。它的用途是构造配置表、路由表这类需要精确键的常量，返回值保留字面量以后，后面的类型运算才拿得到具体值。`interface` 和类型别名上不能加 `const`，写 `interface Box<const T>` 会报 `TS1277: 'const' modifier can only appear on a type parameter of a function, method or class`。

```ts
declare function configure<O>(options: O, overrides: NoInfer<O>): O;

export const ok = configure({ timeout: 3000 }, { timeout: 5000 });
export const bad = configure({ timeout: 3000 }, { timeout: 5000, retries: 2 });
```

报错是 `error TS2353: Object literal may only specify known properties, and 'retries' does not exist in type '{ timeout: number; }'`。没有 `NoInfer` 时，`O` 会从两处同时推断，报错点落在第一个参数上，看不出是第二个参数写错了。

同一个版本还加了 `Object.groupBy` 与 `Map.groupBy`。类型上要注意返回值可能缺键：

```ts
const groups = Object.groupBy([1, 2, 3, 4], (n) => (n % 2 === 0 ? "even" : "odd"));
const even: number[] | undefined = groups.even;
```

签名是 `Partial<Record<K, T[]>>`，所以取键的结果带 `undefined`。这是对的：运行时分组结果里只有实际出现过的键。想直接遍历就加 `?? []`，或者自己写一个返回完整 `Record` 的包装。

```ts
declare const ids: IteratorObject<number>;

export const doubled = ids.map((n) => n * 2).toArray();
```

迭代器辅助方法是 ES2025 的特性，默认的 `es2025` lib 里就有。`target` 写到 `es2020` 以下时会报 `TS2339: Property 'map' does not exist on type 'IteratorObject<number, unknown, unknown>'`，这时把 `lib` 提到 `es2025`。

迭代器辅助方法是惰性的，`map` 和 `filter` 只是包装，`toArray` 或 `for...of` 才真正求值。它替代的是 `Array.from(...).map(...)` 这种一次性数组，处理大文件流时省内存。

同一个版本还加了 `--noUncheckedSideEffectImports`，后来在 6.0 成了默认值。它检查 `import "./x.css"` 这类纯副作用导入的文件是否存在，跳过了以前静默通过的路径写错。

```ts
import defer * as logger from "./logger.js";

export function run(): void {
  logger.flush();
}
```

`./logger.js` 在别处给出；单独编译报 `TS2307: Cannot find module './logger.js'`。

`import defer` 把模块求值推迟到第一次访问成员。它要求 `module` 为 `esnext` 或 `preserve`，`nodenext` 也不行，否则报 `TS18060: Deferred imports are only supported when the '--module' flag is set to 'esnext' or 'preserve'`。运行时要确认当前 Node 版本支持 import defer。

它和动态 `import()` 的区别：`import defer` 的绑定是静态的，加载阶段就解析模块位置，只是不求值；动态导入连解析都推迟。启动快、模块里有副作用但大多数请求用不到的代码，适合这种写法。

`using` 的写法要配 `lib`。`Symbol.dispose` 和 `Disposable` 类型在 `esnext` 里，`es2025` 没有，只加 `target` 会报 `TS2318: Cannot find global type 'Disposable'`。

`--rewriteRelativeImportExtensions` 解决 Node 直跑 `.ts` 时的后缀问题：

```bash
$ npx tsc --ignoreConfig --rewriteRelativeImportExtensions --module esnext --target es2025 --outDir out main.ts

$ cat out/main.js | head -1
import { value } from "./dep.js";
```

源码里写 `./dep.ts`，产物自动改成 `./dep.js`。

## 团队怎么排升级

单人项目可以一步到 7.0。多人仓库要分四步走。

第一步，锁版本。把 `typescript` 的版本从 `^` 改成精确版本，先在 CI 里跑 7.0，本地不动。CI 报错清单就是这次迁移的工作量。

第二步，清配置。`TS5102`、`TS5108`、`TS5011`、`TS6046` 四类错误在配置层解决，这一批不碰业务代码。改完在 6.0 也跑一遍，确认两边都过。6.0 下要加 `"ignoreDeprecations": "6.0"` 才能忽略的那批选项，正好在这里一起删。

第三步，处理语义。把 `strict` 的报错按错误码分类，先修空值，再修隐式 any。语义变化那两节提到的模板字面量和声明顺序，单独安排一次回归。

第四步，切默认版本。本地和 CI 都换成 7.0，删掉 `ignoreDeprecations`，观察一周。出问题回退只需要改 `package.json` 一行，`tsbuildinfo` 可以删掉重生成。

库比应用麻烦。库的 `.d.ts` 是下游的编译输入，升级前先把 `types` 或 `exports` 指向的声明跑一遍 `arethetypeswrong`。7.0 生成的声明对下游是兼容的，但模板字面量那处切法变化可能让下游的 `infer` 结果变短。

## 跟踪版本

看 npm 的发布标签最快：

```bash
$ curl -s https://registry.npmjs.org/-/package/typescript/dist-tags
{"rc":"7.0.1-rc","latest":"7.0.2","beta":"7.1.0-beta","next":"7.1.0-dev.20261121.1"}
```

`latest` 是稳定版，`beta` 是下一个 minor 的预览，`rc` 是候选，`next` 是 nightly，`dev` 是很久以前的遗留标签。装 beta 用 `npm i -D typescript@beta`，装 nightly 用 `typescript@next`，两者都不要进 `dependencies`。

`next` 是 nightly，日期后缀就是构建日。CI 里锁 `devDependencies` 的精确版本（`"typescript": "7.0.2"`），不要写 `latest` 或 `^`。`^7.0.2` 会随 minor 漂移，模板字面量切法这类语义变化就藏在小版本里。

想知道下个版本会改什么，看[官方博客的 RSS](https://devblogs.microsoft.com/typescript/feed/)。每个 minor 的正式公告都在这里，比等 release notes 全。

码表也在长。5.0.4 到 5.9.3 新增 225 个码，另有 25 个不再出现，40 条文案被改写；TS5112 是 7.0 才有的码。升级后旧截图里的文案可能对不上，码一般还对得上。

升级完成的判断标准是三条：`tsc --noEmit` 无配置类报错，CI 里 `ignoreDeprecations` 已删除，`.d.ts` 快照的 diff 只有顺序调整。

迁移期间保持两套 CI 有用。一套跑 6.0 加 `ignoreDeprecations`，一套跑 7.0，两边都过才算迁移完成。6.0 那套在 7.0 稳定两周后删掉。

`tsc --showConfig` 可以把最终生效的配置打印成 JSON，`target`、`lib`、`moduleResolution` 的实际值都能看到。升级后对一遍，比读文档可靠。

## 用不上的时候

### 旧选项短期删不掉

`target: "es5"`、`baseUrl`、`module: "amd"` 在 7.0 直接报错，`ignoreDeprecations` 也不再支持。代码量大、短期改不完时，只能停在 6.0 继续用弃用项。硬升 7.0 等于同时做配置迁移和依赖升级，风险叠加。

### 工具还在用 6.0 的编译器 API

`ts-jest`、`ts-node`、部分 ESLint 插件直接 `import ts from "typescript"`，7.0 不提供 API，它们会崩。过渡期只能并行装 6.0 和 7.0，工具侧走 `tsc6`。7.1 补上 API 之前，这类项目不具备升级条件。

### 编辑器与单文件组件

Vue、Svelte、Astro、Angular 模板依赖 6.0 的 JS API，7.0 的类型服务覆盖不到。前端框架项目升到 7.0 后，模板里的类型提示会变少。升级范围要按语言和框架拆开，不能按仓库一刀切。
