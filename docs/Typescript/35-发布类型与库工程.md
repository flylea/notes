# 第 35 章 发布类型与库工程

`declaration: true` 已经打开，下游装包后 `import` 仍然报「找不到类型声明」。多数问题不在 `tsc`，在 `package.json` 的 `exports` 条件顺序或模块格式。这一章从生成 `.d.ts` 到发布前四条命令，按链路走一遍。

`declaration: true` 是发 npm 库的最低配置。要让下游拿到正确的类型，还要处理 `exports` 解析和双模块格式。发布前跑 [publint](https://publint.dev/) 和 `attw`，能拦住大部分「类型找不到」的 issue。

`.d.ts` 只写类型，不写实现。下游拿到的是一张收据：谁导出了什么，参数和返回值是什么。收据要能单独读懂，所以每个类型都得有名字。导出的匿名类里带私有成员时，收据写不出成员名，`tsc` 报 TS4094，不会替它编一个名字。一句话，声明文件是打印出来的，不是抄出来的。

## 先生成 .d.ts

一个能发布的最小配置，存成 `tsconfig.build.json`：

```json
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true,
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}
```

```bash
npx tsc -p tsconfig.build.json
```

`src/index.ts` 会产出 `dist/index.js`、`dist/index.d.ts`、`dist/index.d.ts.map`。`rootDir` 决定 `dist` 里的目录层级。少写这个字段，`dist` 可能多套一层 `src`。

### 声明是打印出来的

`.d.ts` 不是源码的副本。检查器给每个导出符号一个类型，emit 阶段把这个类型打印成文本。打印先找名字：接口名、类名、类型别名都算名字。有名字就写名字，没有就展开结构。结构里再遇到私有成员或不可见的模块路径，就写不下去。

写不下去时不会降级成 `any`，而是报错。TS4094 对应导出的匿名类的私有成员，TS4023 对应导出变量的类型来自别的文件里的未导出名字，TS2883 对应类型指向包内部路径、换台机器就失效。三个码说的是同一件事：这个名字打印不出来。

打印依赖推断。`export const payload = build()` 的类型要从 `build()` 的返回类型推出来，而 `build()` 可能在别的文件里。声明生成必须看到整个程序，这是它和单文件转译的根本差别，也是 `isolatedDeclarations` 要求显式注解的理由。

7.0 还换了一个编号：同一场景 5.9 报 TS2742，7.0.2 报 TS2883。报错文案不变，码变了，按错误码过滤 CI 日志的脚本要跟着改。

`.d.ts.map` 由 emit 一起写出，`sources` 里存的是相对 `rootDir` 的路径。`rootDir` 写错时，map 指向的文件就对不上，编辑器跳过去落在空处。

声明目录和 JS 目录分开时，`exports` 里 `types` 要指到声明目录，`main`、`import` 指到 JS 目录。两边的相对路径写错，`types` 会指到一个不存在的文件，下游按 `any` 处理。

`declarationMap` 让编辑器从 `.d.ts` 跳回 `.ts`。跳转依赖源码文件存在。发布时把 `src` 写进 `files`，否则关掉 `declarationMap`。下游拿到一份指向不存在路径的 map，体验比没有 map 更差。

声明要单独放一处，用 `declarationDir` 配 `emitDeclarationOnly`。这两个选项必须和 `declaration` 或 `composite` 同时出现。单独打开 `emitDeclarationOnly` 会报：

```bash
error TS5069: Option 'emitDeclarationOnly' cannot be specified without specifying option 'declaration' or option 'composite'.
```

## 声明生成阶段的两个报错

打开 `declaration` 后，下面这个文件编译失败：

```ts
import { format } from "./missing";

export const Store = class {
  private cache = new Map<string, number>();
};

export const label = format("store");
```

```bash
$ tsc --declaration --emitDeclarationOnly --strict --target es2022 --module esnext --moduleResolution bundler --outDir dist export-anon.ts
export-anon.ts(1,24): error TS2307: Cannot find module './missing' or its corresponding type declarations.
export-anon.ts(3,14): error TS4094: Property 'cache' of exported anonymous class type may not be private or protected.
```

两条报错都在 emit 阶段出现。第一条是模块缺失，属于代码问题，补文件就行。第二条只能改结构：给类起名再导出，或者去掉私有字段。

修法是 `class Store { private cache = new Map<string, number>(); }` 加 `export { Store };`。这段能过，因为 `Store` 有名字，导出的是名字而不是匿名类。这也解释了为什么给类起名不是风格问题：匿名类在声明文件里没有可打印的位置。

## 打包器出 JS，tsc 只出类型

库用 tsdown、tsup 或 esbuild 出 JS，再用 tsc 单独出声明。两边各管一段，职责清楚。

```json
{
  "extends": "./tsconfig.build.json",
  "compilerOptions": {
    "emitDeclarationOnly": true,
    "declaration": true,
    "declarationMap": false,
    "outDir": "dist"
  }
}
```

```json
{
  "scripts": {
    "build": "tsdown src/index.ts --dts false",
    "build:types": "tsc -p tsconfig.types.json",
    "prepublishOnly": "npm run build && npm run build:types"
  }
}
```

打包器负责删注释、压体积、生成 sourcemap。tsc 只管类型。两边输出必须落在同一个 `dist`，路径和 `package.json` 里的 `exports` 对齐。

容易踩的坑是 `outDir` 不一致。打包器输出到 `dist/index.js`，tsc 输出到 `dist/types/index.d.ts`，`exports.types` 却写 `./dist/index.d.ts`。文件不在，类型就解析不到。

## isolatedDeclarations：先写返回类型

普通的声明生成要等类型推断跑完。`isolatedDeclarations` 要求每个导出的声明只靠本文件就能写出类型。这样声明可以逐文件生成，不用先做全量推断。

打开后，推断不出来的导出直接报错：

```ts
// isolated-bad.ts
export function makeId(prefix: string) {
  return prefix + Math.random().toString(36).slice(2);
}

export const defaults = { retries: 3 };

export function pick<T>(list: T[], index: number) {
  return list[index];
}
```

```bash
$ tsc --noEmit --declaration --isolatedDeclarations isolated-bad.ts
isolated-bad.ts(3,10): error TS9013: Expression type can't be inferred with --isolatedDeclarations.
isolated-bad.ts(9,10): error TS9013: Expression type can't be inferred with --isolatedDeclarations.
```

`defaults` 没报错。对象字面量的类型可以直接写出来，不需要推断。报错集中在函数返回值。

补上类型就能过：

```ts
export function makeId(prefix: string): string {
  return prefix + Math.random().toString(36).slice(2);
}

export const defaults: { retries: number } = { retries: 3 };

export function pick<T>(list: T[], index: number): T {
  return list[index];
}
```

改法固定：函数写返回类型，导出的变量写类型，泛型参数保持原样。第三方 `.d.ts` 出现大面积 `TS9013`，说明那套声明生成方式还没适配这个选项。这个选项同样要挂靠 `declaration` 或 `composite`，否则报 `TS5069`。

## composite 与 project references

monorepo 里两个包，`core` 和 `app`，目录分开：

```text
packages/
  core/
    src/index.ts
    tsconfig.json
  app/
    src/main.ts
    tsconfig.json
```

`core` 的配置打开 `composite`：

```json
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "rootDir": "src",
    "outDir": "dist",
    "strict": true
  },
  "include": ["src"]
}
```

`app` 用 `references` 指向 `core`：

```json
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "rootDir": "src",
    "outDir": "dist",
    "strict": true
  },
  "references": [{ "path": "../core" }],
  "include": ["src"]
}
```

构建命令是 `tsc -b`，不是 `tsc -p`：

```bash
$ tsc -b packages/app/tsconfig.json --verbose
Building project 'packages/core/tsconfig.json'...
Building project 'packages/app/tsconfig.json'...

$ tsc -b packages/app/tsconfig.json --verbose
Project 'packages/core/tsconfig.json' is up to date because newest input 'packages/core/src/index.ts' is older than output 'packages/core/tsconfig.tsbuildinfo'
Project 'packages/app/tsconfig.json' is up to date because newest input 'packages/core/src/index.ts' is older than output 'packages/app/tsconfig.tsbuildinfo'
```

每个项目目录会多一个 `*.tsbuildinfo`。它记录每个输入文件的签名和输出时间，第二次构建直接跳过。`--force` 可以强制重建。CI 里别加 `--force`，否则增量信息白攒。

被引用的项目必须开 `composite`，否则报 `TS6306`。`composite` 会顺带打开 `declaration`，显式关掉报 `TS6304: Composite projects may not disable declaration emit.`。

`references` 只解决构建顺序和增量。运行时解析仍由 `package.json` 决定。`core` 的 `package.json` 要写 `types` 和 `main`，`app` 才 import 得到。

## package.json 决定能不能解析到类型

一个只有 ESM、`exports` 指向不存在文件的包：

```json
{
  "name": "tiny-ranges",
  "version": "0.0.1",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/missing.js"
    }
  }
}
```

```bash
$ npx publint
Running publint v0.3.25 for tiny-ranges...
Errors:
1. pkg.exports["."].import is ./dist/missing.js but the file does not exist.

$ npx attw --pack .
Import failed to resolve to type declarations or JavaScript files.
A require call resolved to an ESM JavaScript file, which is an error in Node and some bundlers.
```

两条报错指向两个不同问题。`publint` 检查 `exports` 里的路径和实际文件是否对得上。`attw`（[Are the types wrong?](https://arethetypeswrong.github.io/)）检查 Node 各版本、CJS 和 ESM 两种调用方式下能否解析到正确的 JS 和类型。

只支持 ESM，就把 `import` 指到真实文件，并补 `types` 顶层字段：

```json
{
  "name": "tiny-ranges",
  "version": "0.0.1",
  "type": "module",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    }
  },
  "files": ["dist"]
}
```

同时支持 CJS 和 ESM，就要两套类型：`.d.ts` 给 `import`，`.d.cts` 给 `require`。

```json
{
  "type": "module",
  "main": "./dist/index.cjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.ts",
        "default": "./dist/index.js"
      },
      "require": {
        "types": "./dist/index.d.cts",
        "default": "./dist/index.cjs"
      }
    }
  },
  "files": ["dist"]
}
```

条件顺序有讲究。Node 从上往下匹配，遇到第一个满足的就停。`types` 必须排在 `import`、`require`、`default` 前面。把 `default` 写最前，类型条件永远不会执行。

`main` 和 `types` 是给老解析器用的。`exports` 存在时，新版本 Node 只看 `exports`。两个字段都写，兼容面最大。老版本 TypeScript 支持不了新语法时，用 `typesVersions` 分流：

```json
{
  "typesVersions": {
    "<5.0": {
      "*": ["dist/types-legacy/*"]
    }
  }
}
```

`sideEffects: false` 只在该包确实没有副作用时写。写错会让打包器摇掉必要的初始化代码。

## 手写 .d.ts

全局声明要配 `export {}`。文件里没有 import 或 export，就不是模块，`declare global` 报 `TS2669: Augmentations for the global scope can only be directly nested in external modules or ambient module declarations.`

```ts
declare global {
  interface Window {
    appVersion: string;
  }
}
```

加一行 `export {}` 就变成模块：

```ts
export {};

declare global {
  interface Window {
    appVersion: string;
  }
}
```

给没有类型的包补声明，用 `declare module`，写法见 [声明文件指南](https://www.typescriptlang.org/docs/handbook/declaration-files/introduction.html)。文件名随意，放 `types/` 目录：

```ts
// types/legacy-lib.d.ts
declare module "legacy-lib" {
  export interface Options {
    retries?: number;
    timeout?: number;
  }

  export function request(path: string, options?: Options): Promise<string>;
}
```

这一块的文件名是 `types/legacy-lib.d.ts`。存成 `.ts` 时报 `TS2664`，存成 `.d.ts` 通过。

`tsconfig.json` 的 `include` 要包含 `types`。只写 `include: ["src"]`，这份声明不会被加载。

模块声明也能合并。已有声明里补字段，在另一个文件写同名模块，接口会合并。合并范围只限同一个包，跨包改类型应该在调用方做包装。

## 控制对外暴露的类型

`stripInternal` 配合 `@internal`，把内部符号从 `.d.ts` 里去掉：

```ts
// src/index.ts
/** @internal 内部计数器，不对外暴露。 */
export let counter = 0;

/** 对外 API。 */
export function bump(): number {
  counter += 1;
  return counter;
}
```

```bash
$ tsc --declaration --emitDeclarationOnly --stripInternal --outDir dist src/index.ts
```

`dist/index.d.ts` 只剩对外函数：

```ts
/** 对外 API。 */
export declare function bump(): number;
```

`counter` 还在 JS 里，只是类型声明里没有了。下游读 `counter` 会报「不存在此导出」。

`verbatimModuleSyntax` 强制类型导入加 `type`。开了这个选项，下面这行报 `TS1484: 'Entry' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.`：

```ts
import { Entry } from "./model";

export const e: Entry = { id: "a", size: 1 };
```

改成 `import type` 就过：

```ts
import type { Entry } from "./model";

export const e: Entry = { id: "a", size: 1 };
```

出口处用 `export type` 同理：

```ts
export type { Entry } from "./model";

export interface Page {
  entries: import("./model").Entry[];
}
```

这三段引用同一个 `./model`，模型文件在本节前面给出；单块编译报 `TS2307: Cannot find module './model'`。

## 发布前跑四条命令

```bash
npx tsc -p tsconfig.build.json
npx publint
npx attw --pack .
npm pack --dry-run
```

四条的用途不同。

| 命令 | 查什么 | 典型报错 |
|---|---|---|
| `tsc -p` | 声明能否生成、类型是否自洽 | `TS9013`、`TS5069` |
| `publint` | `exports` 路径是否存在、字段是否完整 | `pkg.exports["."].import ... does not exist` |
| `attw --pack .` | 打包产物在各解析模式下是否可用 | `Import failed to resolve to type declarations` |
| `npm pack --dry-run` | 发布清单里有没有漏文件 | 少 `dist`、少 `src` |

`attw` 默认读 `npm pack` 的产物。`--pack .` 表示打包当前目录，不会真的上传。四种解析模式全绿，再执行 `npm publish`。

`publint` 的提示分 Errors 和 Suggestions。Errors 必须改。Suggestions 看情况，比如缺 `engines.node`，加不加取决于包支持的 Node 范围。

## 用不上的时候

### 不发布的应用项目

应用不需要 `declaration`、`composite`、`exports` 条件和 `.d.cts`，也不跑 `publint` 与 `attw`。这些配置只在有下游、有解析器差异时产生价值。应用项目打开 `declaration`，只是多一次产物生成。

### 只在内部使用的私有包

`private: true` 的包不经过 npm，`files` 清单和 `exports` 的双格式都没有意义。workspace 内部靠软链解析，`typesVersions` 也用不上。为公开发布准备的检查项，在这里是空转。

### 第三方依赖的类型问题

`publint` 和 `attw` 只检查你自己的包。依赖包的 `exports` 写错、声明文件缺失，报错会出现在你的项目里，处理手段只有 `skipLibCheck`、补 `declare module` 或换包。发布检查管不到别人。

## 参考

- [publint](https://publint.dev/)：检查 `exports` 路径、字段完整性与文件是否存在。
- [Are the types wrong?](https://arethetypeswrong.github.io/)：按 Node 解析模式检查类型声明与 JS 是否配对。
- [TypeScript 手册：声明文件](https://www.typescriptlang.org/docs/handbook/declaration-files/introduction.html)：手写 `.d.ts`、`declare module` 与全局声明的官方写法。
