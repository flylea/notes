# 第 21 章 类型声明文件与命名空间

引入一个没有类型的 npm 包，编辑器里全是 `any`；给 `window` 加一个自定义属性，全局报 TS2339。声明文件负责补这些类型。这一章讲 `declare`、`.d.ts` 的写法、`declare global` 与 namespace 的使用范围。

TypeScript 项目中的一个核心需求是：如何为没有类型的 JavaScript 代码提供类型信息。[类型声明文件](https://www.typescriptlang.org/docs/handbook/declaration-files/introduction.html)（`.d.ts`）就是答案：它们只包含类型信息，不包含运行时代码。这一章介绍如何编写和使用声明文件，以及 `namespace` 命名空间的组织方式。

一句话：`declare` 只补类型，不生成代码；`declare global` 是一条模块增强语句。

`declare const VERSION: string` 编译后不留任何 JS，运行时的 VERSION 得由宿主提供。给 window 加字段必须写在模块里，文件末尾一句 `export {}` 就够。

这个说法在 `.d.ts` 上要加条件：没有 import/export 的 `.d.ts` 是全局声明文件，里面的声明直接进全局，不必再写 `declare global`。

## declare 关键字

`declare` 告诉 TypeScript"这个变量/函数/类在运行时一定存在，请信任它的类型"，它只声明类型，不产生任何 JavaScript 代码：

```typescript
// 声明全局变量
declare var jQuery: (selector: string) => any;
declare const VERSION: string;

// 声明全局函数
declare function greet(name: string): void;

// 声明全局类
declare class Animal {
  name: string;
  constructor(name: string);
  sayHello(): void;
}

// 声明全局枚举
declare enum Direction {
  Up, Down, Left, Right
}
```

编译后，上面的所有 `declare` 语句都不会出现在 JavaScript 输出中，它们只用于类型检查。

### declare 与模块解析各管一半

`declare` 给声明打上 ambient 标记。检查器照常建符号，emitter 跳过它，所以产物里没有对应代码。运行时的东西由别处提供：全局变量来自宿主环境或 `<script>`，模块来自真正的 JS 包。

模块解析负责“文件在哪”，`declare module "x"` 负责“没有文件时凭空造一个模块符号”。两者都能让 `import "x"` 通过：解析找到真实文件时，`declare module "x"` 只做增强；找不到时才当完整声明。`@types` 包能生效，靠的就是解析顺序里先找 `node_modules/@types/x`。

`declare global` 是模块增强语句，检查器要求它所在文件是外部模块：有顶层 `import` 或 `export`。判断点在 `checkModuleAugmentationElement` 附近，脚本文件直接报 TS2669（`src/compiler/checker.ts` 48251 行）。末尾 `export {}` 的唯一作用是把文件变成模块，产物里它仍是一句 `export {}`。

反过来不行。如果允许脚本文件写 `declare global`，全局增强就没有“属于哪个模块”的边界，合并顺序变成文件加载顺序，检查器给不出稳定结果。

还有一层顺序：`declare module "x"` 写在 `.d.ts` 里，类型检查按解析到该文件的顺序生效。如果真实模块也存在，增强先合并进真实模块的符号再检查，所以同名接口能并起来。

`declare` 声明不参与 emitter，但它们的类型仍参与检查，删掉编译就报找不到名字。两件事分开看：`skipLibCheck` 只跳过声明文件内部的检查，不改变哪些声明进入全局。

## .d.ts 文件

`.d.ts` 文件是 TypeScript 的类型声明文件。它只能包含类型声明，不能包含可执行代码：

```typescript
// types.d.ts
// User 沿用第 6 章的定义，实际项目里通常由共享类型包提供

declare function getUser(id: string): User;
declare function createUser(data: Omit<User, "id">): User;
```

### .d.ts vs .ts

| | .ts | .d.ts |
|---|---|---|
| 可执行代码 | ✅ | ❌ |
| 类型声明 | ✅ | ✅ |
| 编译输出 | .js | 无 |
| 用途 | 实现代码 | 类型描述 |

### 全局声明 vs 模块声明

`.d.ts` 文件中如果没有 `import`/`export`，所有声明都是**全局的**，在整个项目中可以直接使用：

```typescript
// global.d.ts（无 import/export，声明为全局）
interface Window {
  __CUSTOM_CONFIG__: Record<string, unknown>;
}

declare const APP_VERSION: string;
```

一旦文件包含 `import` 或 `export`，它就变成了模块，声明不会泄露到全局：

```typescript
// types.d.ts（有 export，是模块）
export interface Book {
  id: string;
  title: string;
}
```

使用方需要显式 import：

```typescript
// app.ts
import { Book } from "./types";
```

### 扩展全局类型

`.d.ts` 最重要的用途之一是扩展已有的全局类型，最常见的是扩展 `Window`：

```typescript
// global.d.ts
declare global {
  interface Window {
    __INITIAL_STATE__: Record<string, unknown>;
    gtag: (event: string, params: Record<string, unknown>) => void;
  }

  // 扩展 String 原型
  interface String {
    capitalize(): string;
  }
}

export {};  // 确保文件是模块（必须有至少一个 export 才能使用 declare global）
```

### 声明与增强的两个报错

```ts
declare global {
  interface Window {
    appVersion: number;
  }
}

const other: MissingNS.Thing = 1;
```

```text
decl.ts(1,9): error TS2669: Augmentations for the global scope can only be directly nested in external modules or ambient module declarations.
decl.ts(7,14): error TS2503: Cannot find namespace 'MissingNS'.
```

TS2669 说这个文件不是模块，`declare global` 没有可挂靠的边界；在文件末尾加 `export {}`，或者把增强放进 `.d.ts` 的 `declare module` 里。

全局声明文件也不行。没有 import/export 的 `.d.ts` 实跑同样报 TS2669，文件末尾加一句 `export {}` 才能用 `declare global`；只想要全局类型的话，直接写 `interface Window` 也进全局。

TS2503 说命名空间从来没声明过，检查器连符号都找不到；先写 `declare namespace MissingNS {...}`，或者从真实模块 `import type` 进来。

`declare global` 块里只写声明，不写语句，检查器也不会为它生成代码。块里的 `interface Window` 是增强已有全局类型，写一个新名字则由你负责保证运行时真的存在。

## 三斜线指令

三斜线指令（`/// <reference path="..." />`）是早期 TypeScript 中引用声明文件的方式，如今大多数场景都被 `import`/`export` 替代，但在某些特殊场景仍然有用：

```typescript
// 引用另一个声明文件
/// <reference path="./other-types.d.ts" />

// 引用库的声明文件
/// <reference types="node" />

// 引用 lib（内置库声明）
/// <reference lib="es2015.promise" />
```

## @types 包

[DefinitelyTyped](https://github.com/DefinitelyTyped/DefinitelyTyped) 是社区维护的最大的类型声明仓库。绝大多数流行的 npm 包都有对应的 `@types` 包：

```bash
npm install --save-dev @types/lodash
npm install --save-dev @types/react
npm install --save-dev @types/node
```

安装后，TypeScript 会自动从 `node_modules/@types` 中加载类型声明，无需手动引用。

### 类型声明文件的查找顺序

TypeScript 查找类型声明文件的顺序是：
1. 项目中的 `.d.ts` 文件（受 `include`/`exclude`/`files` 配置影响）
2. `node_modules/@types/` 下的包（按 `typeRoots` 配置）
3. npm 包自身的 `types`/`typings` 字段指向的文件

### 为自己的 npm 包提供类型声明

在 `package.json` 中指定 `types` 字段：

```json
{
  "name": "my-library",
  "version": "1.0.0",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts"
}
```

## namespace：命名空间

`namespace` 是 TypeScript 早期用于组织代码的方式（在 ES6 模块普及之前）。如今，大多数场景用 ES6 模块更合适，但 `namespace` 在声明文件中仍然有重要作用。

### 基本用法

```typescript
namespace Utils {
  export function formatDate(date: Date): string {
    return date.toISOString();
  }

  export function parseDate(str: string): Date {
    return new Date(str);
  }

  // 私有函数：不加 export 就不能在命名空间外访问
  function pad(n: number): string {
    return n < 10 ? `0${n}` : `${n}`;
  }
}

// 使用
Utils.formatDate(new Date());
```

### 嵌套 namespace

```typescript
namespace App {
  export namespace Models {
    export interface Book {
      id: string;
      title: string;
    }
  }

  export namespace Services {
    export function getBook(id: string): App.Models.Book {
      return { id, title: "TypeScript" };
    }
  }
}
```

### namespace 声明合并

同名 `namespace` 会自动合并，这也是它在声明文件中强大的原因：

```typescript
// 两个文件中的声明会自动合并
namespace App {
  export function init() {}
}

namespace App {
  export function destroy() {}
}
```

等价于：

```text
namespace App {
  export function init() {}
  export function destroy() {}
}
```

### namespace 在声明文件中的典型用途

为大型库或 jQuery 风格的插件系统声明类型：

```typescript
// jQuery 风格：构造函数 + 静态方法
declare function $<T extends HTMLElement>(selector: string): $Collection<T>;

declare namespace $ {
  function ajax(url: string, settings?: AjaxSettings): void;
  function get(url: string): Promise<unknown>;

  interface AjaxSettings {
    method?: string;
    data?: unknown;
  }
}

// 使用
$("#app").show();
$.ajax("/api/data", { method: "POST" });
```

### namespace vs ES6 模块

| | namespace | ES6 模块 |
|---|---|---|
| 使用场景 | 声明文件、全局组织 | 实现代码 |
| 编译输出 | IIFE 对象 | ES 模块语法 |
| 声明合并 | ✅ | ❌ |
| Tree-shaking | ❌ | ✅ |
| 运行时开销 | 有（生成对象） | 无（编译时解决） |

**建议**：实现代码中用 ES6 模块（`import`/`export`），声明文件中用 `namespace` 来组织全局类型。

## 声明文件的实战模式

### 模式一：为无类型的 JS 模块声明

你的项目中使用了一个没有 `@types` 的旧 JS 库：

```typescript
// src/types/legacy-lib.d.ts
declare module "legacy-lib" {
  export function doSomething(input: string): number;
  export const VERSION: string;
}
```

### 模式二：为非 JS 文件声明

为 CSS Modules、图片等非 JS 资源声明类型：

```typescript
// declarations.d.ts
declare module "*.module.css" {
  const classes: { readonly [key: string]: string };
  export default classes;
}

declare module "*.svg" {
  const content: string;
  export default content;
}

declare module "*.png" {
  const content: string;
  export default content;
}
```

### 模式三：扩展第三方库的接口

```typescript
// 扩展 Express 的 Request 对象
declare global {
  namespace Express {
    interface Request {
      user?: {
        id: number;
        role: string;
      };
    }
  }
}

// 没有 import 或 export 的文件是脚本，declare global 会报 TS2669
export {};
```

## 小结

- **`declare`** 声明某变量/函数/类在运行时存在，编译后不产生 JS 代码
- **`.d.ts` 文件** 只包含类型声明；无 `import`/`export` 的声明为全局
- **`declare global`** 用于扩展全局类型（如 `Window`、`String` 原型）
- **`@types` 包** 提供社区维护的第三方库类型声明
- **`namespace`** 用于组织全局声明，支持自动合并；实现代码中优先用 ES6 模块
- 声明文件的实战模式：为 JS 库写声明、为非 JS 资源写声明、扩展第三方类型

## 用不上的时候

### 项目内互引

同一仓库里直接 `export` 类型即可，无需再写 `.d.ts`，重复维护容易与实现脱节。

### namespace 与 ESM 混用

namespace 里的代码不会被打包工具做 tree-shaking。它只适合声明全局类型，业务代码用 ES 模块。

### 手写声明

手写 `.d.ts` 会随实现漂移。优先让 `tsc --declaration` 生成，补丁声明尽量上游解决。
