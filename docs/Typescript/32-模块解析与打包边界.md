# 第 32 章 模块解析与打包边界

组件库升级后，`tsc --noEmit` 全绿，`vite build` 却报找不到模块；换一个包，情况反过来。类型检查和打包各跑各的解析规则，两边都过才算真的过。这一章把两套规则对齐，从档位、扩展名讲到条件解析和打包边界。

把 `moduleResolution` 从 `node` 改成 `nodenext` 后，原来的 `import { readConfig } from "./config"` 会报 TS2835。这条报错来自 tsc 的解析器，和打包器能不能跑无关。tsc 要回答一个问题：这行 import 指向磁盘上哪个文件。它找不到，后面的类型检查就无从谈起。

同一个项目里，tsc 的解析规则和打包器的解析规则经常不是一个。类型检查通过，打包可能失败；打包能跑，类型可能全错。这一章按解析档位、扩展名、语法保留、打包器、发包五块拆开，每块都能用一条命令复现。

## 五个档位，只剩三个可用

`moduleResolution` 历史上出现过五个取值。TypeScript 7 只认三个：`node16`、`nodenext`、`bundler`。`node10`（旧写法 `node`）和 `classic` 已删除。（见 [模块解析参考](https://www.typescriptlang.org/docs/handbook/modules/reference.html)）

| 取值 | 状态 | 按什么解析 | 典型场景 |
|---|---|---|---|
| `node10` | 已删除，TS5108 | 扩展名补全、`main` 字段 | 无，升级时必须改 |
| `node16` | 可用 | Node 16 规则，固定 | 明确最低 Node 16 的项目 |
| `nodenext` | 可用 | 当前 Node 规则，随版本浮动 | Node 后端默认选它 |
| `bundler` | 可用 | 打包器规则，允许无扩展名 | Vite、Rspack 等前端项目 |

`classic` 更早退场。它按 TypeScript 自己的命名空间规则解析，连 `node_modules` 都不看，只在 AMD 时代有意义。留下来的三个档位都按真实运行时的规则工作。

`node10` 被删掉的原因不复杂。它按 CommonJS 的 `require` 规则工作：先补 `.js`、`.ts`、`.json`，再读 `package.json` 的 `main`。这套规则不认 `exports` 字段，也不区分 ESM 和 CommonJS。Node 自己从 12 起就走 `exports` 了，继续保留这个档位，等于让 tsc 和 Node 各说各话。

删除的选项直接报错，不会降级成警告。（见 [tsconfig 参考](https://www.typescriptlang.org/tsconfig)）

```bash
$ tsc --noEmit --moduleResolution node10 src/entry.ts
error TS5108: Option 'moduleResolution=node10' has been removed. Please remove it from your configuration.
$ tsc --noEmit --moduleResolution classic src/entry.ts
error TS5108: Option 'moduleResolution=Classic' has been removed. Please remove it from your configuration.
```

前端项目用 `bundler`，同时把 `module` 设成 `esnext`，只让 tsc 做类型检查。`noEmit: true` 是关键：类型检查不需要产物，产物由打包器生成。

```json
{
  "compilerOptions": {
    "target": "es2022",
    "module": "esnext",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,
    "noEmit": true,
    "strict": true
  },
  "include": ["src"]
}
```

Node 后端改用 `nodenext`，产物交给 Node 加载。这个档位按文件后缀和最近的 `package.json` 判断模块格式，`.mts`、`.cts`、`type` 字段都会影响结果。`node16` 的判定规则一样，只是把 Node 的版本语义钉在 16。

判定结果决定两件事：这个文件是否允许 ESM 语法，以及它的相对导入要不要写扩展名。同一份源码，放在 `type: "module"` 的目录下和放在 `type: "commonjs"` 的目录下，报错可以完全不同。

```json
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "verbatimModuleSyntax": true,
    "strict": true,
    "outDir": "dist"
  },
  "include": ["src"]
}
```

`module` 和 `moduleResolution` 有绑定关系。`moduleResolution` 设成 `node16` 时，`module` 必须是 `node16`、`node18`、`node20` 或 `nodenext`，否则报 TS5110。这条检查存在的原因是两个选项描述同一件事：源码按什么模块格式理解。一边写成 `esnext`，一边按 Node 的规则解析，结果没有意义。

反过来，`node18`、`node20` 是 `module` 的取值，不是 `moduleResolution` 的取值，写错报 TS6046。

```bash
$ tsc --noEmit --module esnext --moduleResolution node16 src/entry.ts
error TS5110: Option 'module' must be set to 'Node16' when option 'moduleResolution' is set to 'Node16'.
$ tsc --noEmit --moduleResolution node20 src/entry.ts
error TS6046: Argument for '--moduleResolution' option must be: 'node16', 'nodenext', 'bundler'.
```

`nodenext` 跟随当前安装的 TypeScript 版本内置的 Node 语义。Node 发布新的解析规则，升级 TypeScript 后行为跟着变。`module: node20` 锁定 Node 20 语义，官方承诺这个档位不再改。两者对 `target` 的推断也不同：`nodenext` 隐含浮动的 esnext，`node20` 隐含 es2023。

`module: node20` 要求 `moduleResolution` 留空或写 `node16`，配 `bundler` 会同时报两条错。

```bash
$ tsc --noEmit --module node20 --moduleResolution bundler src/entry.ts
error TS5095: Option 'bundler' can only be used when 'module' is set to 'preserve', 'commonjs', or 'es2015' or later.
error TS5109: Option 'moduleResolution' must be set to 'Node16' (or left unspecified) when option 'module' is set to 'Node20'.
```

不写 `moduleResolution` 时，tsc 按 `module` 推断。`nodenext` 推成 `nodenext`，`node16`、`node18`、`node20` 推成 `node16`，其余推成 `bundler`。推断结果不用猜，`--showConfig` 会打印最终生效的配置。

```bash
$ cat tsconfig.json
{ "compilerOptions": { "module": "node20" } }
$ tsc --showConfig
{
    "compilerOptions": {
        "module": "node20",
        "moduleResolution": "node16",
        "moduleDetection": "force"
    },
    "files": [
        "./a.ts"
    ]
}
```

输出里还多了一行 `moduleDetection: "force"`，这是 TypeScript 6 的默认值。每个文件都按模块处理，没有 `import` 或 `export` 的旧脚本要显式声明为全局脚本，否则报错。

升级 TypeScript 后先跑一遍 `--showConfig`，能省掉一半排查时间。很多配置冲突不是写错了，而是继承的预设里藏了一个旧值。

库作者为兼容老 Node 选 `node20`，行为稳定，不会因为消费者升级 TypeScript 而变。应用选 `nodenext`，跟随当前 Node 的规则，升级 Node 后解析行为可能变，这是升级的一部分。

## ESM 文件必须写 .js 扩展名

Node 的 ESM 加载器不做扩展名补全。`import "./config"` 在运行时直接报 ERR_MODULE_NOT_FOUND。tsc 的 `node16`、`nodenext` 按同样规则检查，所以在源码里就拦住。

Node 加载 ESM 时只做三步：把相对路径拼成 URL，检查文件是否存在，加载。没有补后缀这一步。tsc 复制了这个过程，所以扩展名错误在类型检查阶段就暴露。

```ts
// package.json 里有 "type": "module"
import { readConfig } from "./config";
export const cfg = readConfig();
// error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './config.mjs'?

// 改法：写成显式扩展名
import { readConfig } from "./config.js";
export const cfg2 = readConfig();
```

两块是错误写法与改法的对照：同一文件里两个 `readConfig` 并存报 `TS2300: Duplicate identifier 'readConfig'`；`./config` 是本节 `src/` 里的文件，单块编译报 `TS2307`。

注意报错建议的 `.mjs`。tsc 只看到 import 路径，不知道磁盘上究竟是 `config.ts` 还是 `config.mts`，只能按 ESM 的默认后缀猜。源码里写的 `.js` 指向磁盘上不存在的文件，这是正常的：解析器把 `.js` 映射回 `config.ts`，编译后两个路径重新对上。

```bash
$ tsc --noEmit --module nodenext --moduleResolution nodenext src/entry.ts
src/entry.ts(2,28): error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './config.mjs'?
$ tsc --noEmit --module nodenext --moduleResolution nodenext src/entry_fixed.ts
$                                                                    # exit 0
```

CommonJS 文件没有这条限制。`.cts` 文件，或 `type` 不是 `module` 的目录下的 `.ts`，可以省略扩展名，因为 `require` 本来就会补全。文件后缀比 `package.json` 的 `type` 优先级高：`.mts` 一定是 ESM，`.cts` 一定是 CommonJS。

后缀比 `package.json` 的 `type` 优先级高这条规则，在测试文件和工具配置上很实用。把文件名写成 `.mts`，它一定按 ESM 解析，不受根目录 `type` 字段影响。

`.ts` 后缀只在特定条件下能写。`allowImportingTsExtensions` 要求同时开 `noEmit`、`emitDeclarationOnly` 或 `rewriteRelativeImportExtensions`，否则报 TS5096。原因很直接：`.ts` 在运行时不存在，只做类型检查时写它没问题，要产出 JavaScript 就必须有人负责改写。

需要产出 JavaScript 时，用 `rewriteRelativeImportExtensions` 在 emit 阶段把 `.ts` 改写成 `.js`。它只处理相对路径，包名导入不受影响。

```bash
$ tsc --noEmit --module nodenext --moduleResolution nodenext src/entry_ts.ts
src/entry_ts.ts(1,22): error TS5097: An import path can only end with a '.ts' extension when 'allowImportingTsExtensions' is enabled.
$ tsc --noEmit --allowImportingTsExtensions --module nodenext --moduleResolution nodenext src/entry_ts.ts
$                                                                    # exit 0
$ tsc --allowImportingTsExtensions --rewriteRelativeImportExtensions \
    --module nodenext --moduleResolution nodenext --outDir dist src/entry_ts.ts
$ cat dist/entry_ts.js
import { util } from "./util.js";
export const v = util();
```

报错里的建议只是猜测，最终要看磁盘上的真实文件。遇到 `Did you mean './x.mjs'` 时先确认文件是 `.ts` 还是 `.mts`，再决定写 `.js` 还是 `.mjs`。猜错的建议照抄会把问题换个地方报。

实际产物是 `import { util } from "./util.js";`，`.ts` 被换成了 `.js`。这个组合适合不能改 import 写法的迁移项目，比如源码里的路径由别的工具生成。

## verbatimModuleSyntax 和 isolatedModules

`verbatimModuleSyntax` 的规则只有两条：带 `type` 修饰的导入导出全部擦除，不带的原样保留。它管源码到产物的转换，不负责判断模块格式。名字里的 verbatim 就是这个意思：源码写什么，产物就留什么。

```ts
// 类型标了 type 前缀，擦除
import { makeShape, type Shape } from "./types.js";
export const circle: Shape = makeShape("circle");

import { Shape, makeShape } from "./types.js"; // error TS1484: 'Shape' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
```

两段是前后对照：并存报 `TS2300`（`makeShape` 与 `Shape`）；`./types.js` 在别处给出，单块编译报 `TS2307`。

在 `verbatimModuleSyntax` 出现之前，控制保留行为的是 `importsNotUsedAsValues` 和 `preserveValueImports`。这两个选项在 TypeScript 5.0 弃用，7.0 删掉，写了报未知选项。

差别可以直接看产物。源码 `import { Shape } from "./types.js"; export const kind: Shape["kind"] = "circle";`，开 `verbatimModuleSyntax` 后产物保留这行 import，因为它语法上是值导入；不开时类型导入被擦除，产物只剩一行 export。

```bash
$ tsc --module nodenext --moduleResolution nodenext --verbatimModuleSyntax --outDir outv src/onlytype.ts
src/onlytype.ts(1,10): error TS1484: 'Shape' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
$ cat outv/onlytype.js
import { Shape } from "./types.js";
export const kind = "circle";
$ tsc --module nodenext --moduleResolution nodenext --outDir outn src/onlytype.ts
$ cat outn/onlytype.js
export const kind = "circle";
$ tsc --noEmit --importsNotUsedAsValues preserve src/entry.ts
error TS5023: Unknown compiler option '--importsNotUsedAsValues'.
$ tsc --noEmit --preserveValueImports src/entry.ts
error TS5023: Unknown compiler option '--preserveValueImports'.
```

第一条命令同时报了 TS1484，但它已经完成 emit。语法保留和类型检查是两件事：tsc 先按语法删掉不认识的导入，再做语义检查。这一点和 `import type` 的旧行为不同，旧行为会替开发者判断哪些导入是类型用途。

`import = require` 和 `export =` 是 CommonJS 的旧语法。`verbatimModuleSyntax` 下它们在 `.cts` 文件里照常工作，在 `.mts` 里报错。迁移时先把这类文件改成 `.cts`，再逐个换成 ESM 写法。

CommonJS 文件里写 ESM 语法会报两条错：TS1295 说这个文件不是 ESM，TS1287 说顶层 `export` 在 CommonJS 里不能用。修法是改 `package.json` 的 `type`，或把文件后缀改成 `.mts`。

`isolatedModules` 解决另一件事：每个文件必须能单独编译，不依赖其他文件的类型信息。esbuild、swc 这类工具一个文件一个文件转译，看不到整个项目的类型图。它只要求再导出类型时写 `export type`，不要求每个 import 都加 `type`。

两个选项通常一起开。`isolatedModules` 保证单文件能编译，`verbatimModuleSyntax` 保证产物和源码的导入导出一一对应。只开前者，类型导入仍可能被悄悄删掉，多文件编译和单文件编译的结果不一致。

```ts
export { Shape } from "./types.js";
// error TS1205: Re-exporting a type when 'isolatedModules' is enabled requires using 'export type'.

// 改法
export type { Shape } from "./types.js";

// ambient const enum
/// <reference path="./dir.d.ts" />
export const d: Dir = Dir.Up;
// error TS2748: Cannot access ambient const enums when 'isolatedModules' is enabled.
```

这块把错误写法、改法和另一个选项并排放在一起：同一文件里两种导出并存报 `TS2300`；`./types.js` 在别处给出报 `TS2307`，ambient 枚举那段里的名字单块编译报 `TS2304`。

ambient 常量枚举不可用，因为它的值藏在 `.d.ts` 里，单文件编译拿不到。普通 `const enum` 在同一个文件里使用没问题，跨文件时会被当成普通枚举，不能指望内联。这条限制常常在构建工具切换后才暴露。

## exports 和 imports 的条件解析

`package.json` 的 `exports` 决定包能暴露哪些入口。一旦写了 `exports`，没列出来的子路径全部不可见，不管文件是否真实存在。这是封装，不是文档约定，解析器真的会拒绝。

```json
{
  "name": "pkg",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./feature": {
      "types": "./dist/feature.d.ts",
      "import": "./dist/feature.js"
    }
  }
}
```

`exports` 的键必须以 `./` 开头，`.` 表示包根，`./feature` 表示一个公开子路径。条件对象可以嵌套，`import` 下面还能再分 `types` 和 `default`。解析器先匹配顶层条件，再往下走。

`types` 放在每个条件对象的第一位。解析器按顺序匹配，先命中 `types` 才能拿到声明文件。放到后面，命中的可能是 JavaScript，tsc 再去找同名 `.d.ts`，找得到算运气。条件键的通用顺序是 `types`、`import`、`require`、`default`。

包还可以用 `name` 字段自引用。包内的测试代码写 `import x from "pkg/feature"`，走的是同一套 `exports` 规则，不必退回到相对路径。

`exports` 还支持数组回退。写 `"import": ["./dist/node.js", "./dist/fallback.js"]`，第一个文件不存在时试第二个。数组里不要混用类型和值，否则解析结果依赖工具实现。

子路径没列出来时报 TS2307。包里没有声明文件时报 TS7016，这个错误只在 `strict` 或 `noImplicitAny` 下出现。两个错误的区别在来源：前者是 `exports` 的门禁，后者是包本身缺类型。前者该改包的 `exports`，后者该装 `@types/包名`，或者自己写一个 `declare module`。

```ts
import { internal } from "pkg/internal";
// error TS2307: Cannot find module 'pkg/internal' or its corresponding type declarations.

import { plainFn } from "plain";
// error TS7016: Could not find a declaration file for module 'plain'.
// '…/node_modules/plain/index.js' implicitly has an 'any' type.
```

`imports` 字段做包内私有别名，必须以 `#` 开头，`nodenext` 和 `bundler` 都支持。它只在本包内有效，发布出去也不会被消费者用到，适合替代一长串相对路径。

配置写在根 `package.json` 里：`"imports": { "#util/*": "./src/util/*.ts" }`。映射规则和 `exports` 相同，支持条件、通配符和数组回退。

```bash
$ tsc --noEmit --module nodenext --moduleResolution nodenext src/use_alias.ts
$                                                                    # exit 0
$ tsc --noEmit --module nodenext --moduleResolution nodenext src/use_alias_bad.ts
src/use_alias_bad.ts(1,24): error TS2307: Cannot find module '#util/missing' or its corresponding type declarations.
```

`customConditions` 用来打开自定义导出条件。库在 `exports` 里写 `development` 分支，应用编译时用 `--customConditions development` 选择它。React Native 用这套机制区分平台入口，一些 UI 库用它切换到未压缩的调试版本。条件是嵌套对象时，`types` 要写在每个分支里。

```json
{
  "name": "custom",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "development": { "types": "./dist/dev.d.ts", "default": "./dist/dev.js" },
      "default": { "types": "./dist/prod.d.ts", "default": "./dist/prod.js" }
    }
  }
}
```

```bash
$ tsc --noEmit --strict --module nodenext --moduleResolution nodenext src/main.ts
src/main.ts(2,14): error TS2322: Type '"prod"' is not assignable to type '"dev"'.
$ tsc --noEmit --strict --module nodenext --moduleResolution nodenext \
    --customConditions development src/main.ts
$                                                                    # exit 0
```

不加参数时解析到 `default` 分支，类型是 `"prod"`，赋值给 `"dev"` 就报错。加了参数才切到开发分支。这种错误只在两个分支的类型不一致时出现，也恰恰是最该检查的地方。

## 两套解析规则

tsc 解析模块是为了找类型，规则写在 `moduleResolution`。bundler 解析模块是为了找要打包的文件，规则来自 Node 的解析算法加插件。

目的不同，允许的写法就不同。tsc 可以走 `paths` 映射、`moduleSuffixes` 后缀、`.d.ts` 替代实现，这些映射只存在于类型层，产物里不留痕迹。bundler 必须落到磁盘上真实存在的文件，映射要么自己实现，要么不认。

`moduleSuffixes` 是最干净的差异。配置写 `[".native", ""]`，tsc 把 `./foo` 解析成 `./foo.native.ts`，检查通过：

```ts
// tsconfig: "moduleSuffixes": [".native", ""], "moduleResolution": "bundler"
import { platform } from "./foo";

export const label = `${platform()}/x`;
```

同一份代码交给 vite build：

```bash
$ tsc --noEmit -p .
$ npx vite build --ssr src/entry.ts
✗ Build failed in 8ms
error during build:
[UNRESOLVED_IMPORT] Could not resolve './foo' in src/entry.ts
```

tsc 拿到了 `foo.native.ts` 的类型，够了。bundler 要打包 `./foo`，磁盘上没有这个名字，直接失败。两边都没错，规则不同。

为什么 bundler 不实现这套映射？映射是给检查器的捷径，产物里没有对应文件，bundler 认了也找不到代码。反过来让 tsc 完全按 bundler 的规则解析，类型检查要依赖打包配置，单文件检查跑不起来。

对照报错是 TS2307。删掉 `moduleSuffixes` 再跑，同一行报 `error TS2307: Cannot find module './foo' or its corresponding type declarations.`。

排查顺序固定：先 tsc，再 bundler，两边都过才算过。CI 两个命令都要跑，少一个，差异留到上线才暴露。

还有一处容易忽略，条件导出的分支选择。`exports` 里 `import`、`require`、`default` 的顺序决定谁先命中，tsc 与 bundler 都照同一份映射找，但一个找 `.d.ts`，一个找 `.js`。同一分支下两类文件不齐，就会一边过一边不过。

`paths` 的处境不同。Vite 8 读 tsconfig 的 `paths`，`@/config` 能构建成功。其他 bundler 不一定读，esbuild 要插件，rollup 也要插件。所以 `paths` 不是可靠的跨工具契约，库代码里少用。

定位两边差异用 `--traceResolution`。它打印每个模块名的候选路径和命中原因，能和 bundler 的日志逐行对照。

tsc 的报告只说明类型可解析，不说明运行时可加载。两者之间的空档由 bundler 负责，这就是两边都要跑的原因。

单个模块失败时先做排除。把 import 换成带扩展名的真实文件路径，tsc 与 bundler 都过，说明问题在解析配置；只有 bundler 过，说明映射被它认了；两边都不过，说明文件本身不在那里。

bundler 的报错文案和前缀由工具自己定，Vite 8 走 Rolldown，esbuild 的措辞又不同。读法一样：报错里的模块名是什么，就去磁盘上找这个名字。

一句话，tsc 找类型从哪来，bundler 找代码从哪来。两件事大多重合，遇到映射、后缀、条件导出就分叉。比喻失效处在于两边都会读 package.json 的 exports，tsc 并非只看类型。

## 打包器边界：bundler 模式和 noEmit

`bundler` 模式的前提是打包器负责产出，tsc 只负责类型。它允许无扩展名导入，允许 `paths` 别名，不要求 `exports` 里的 `require` 条件。它也不强制 `import` 语句的扩展名，因为这些语句最终会被打包器改写。

`bundler` 不适合要被 Node 直接运行的项目。它允许的写法在 Node 里会直接崩，比如没写扩展名的相对导入。类型检查放行的东西，运行时不一定能跑，这类项目选 `nodenext`。

`bundler` 和 `nodenext` 的区别集中在扩展名和 `exports` 条件上。前端源码里写 `import "./Button"` 很常见，`bundler` 放行，`nodenext` 报错。项目一旦决定用打包器，类型检查就该跟着用 `bundler`，否则两边规则打架。

`module: preserve` 是另一种混写模式。它保留每条 import 的原始形态，允许 ESM 语法和 `import = require` 同时存在。它同时隐含 `moduleResolution: bundler`，适合从 CommonJS 迁移到 ESM 的中间阶段，源码里两种写法并存，由打包器决定最终格式。`module: esnext` 不允许这种混写。

```ts
import legacy = require("./legacy.cjs");
export const got: number = legacy.old();
```

这块要 `module` 为 `commonjs` 或 `preserve`；默认 ESM 配置报 `TS1202`，`./legacy.cjs` 在别处给出报 `TS2307`。

`module: commonjs` 配 `moduleResolution: bundler` 在 TypeScript 6 之后合法，产物是标准 CommonJS。这个组合适合给老消费方单独构建一份，类型解析仍按现代规则走。

打包器不查类型，这条边界可以用 esbuild 直接验证。源码里有一个明显的类型错误，tsc 报 TS2322，esbuild 照样产出。解析规则也不同：esbuild 能补全无扩展名导入，tsc 在 `nodenext` 下对同一个入口报 TS2835。

```bash
$ tsc --noEmit --module preserve src/mix.ts
$                                                                    # exit 0
$ tsc --noEmit --module esnext --moduleResolution bundler src/mix.ts
src/mix.ts(1,1): error TS1202: Import assignment cannot be used when targeting ECMAScript modules. Consider using 'import * as ns from "mod"', 'import {a} from "mod"', 'import d from "mod"', or another module format instead.
$ tsc --noEmit --strict src/bug.ts
src/bug.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
$ esbuild src/bug.ts --format=esm
const n = "not a number";
console.log(n.toFixed(2));
const double = (x) => x * 2;
export {
  double
};
$ esbuild src/entry_import.ts --bundle --format=esm
// src/bug.ts
var n = "not a number";
console.log(n.toFixed(2));
var double = (x) => x * 2;
// src/entry_import.ts
var v = double(2);
export {
  v
};
$ tsc --noEmit --module nodenext --moduleResolution nodenext src/entry_import.ts
src/entry_import.ts(1,24): error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './bug.js'?
```

esbuild 的输出用 `var` 声明变量，tsc 用 `const`。变量提升和块级作用域在这段代码里没有差别，但涉及循环闭包时要注意。esbuild 也会把 `console.log` 这样的副作用保留下来，删掉它需要显式配置。

tsc 自己也能跳过检查，只做转译。`--noCheck` 在 TypeScript 5.6 加入，行为接近打包器：输出 JavaScript，不报告类型错误。转译产物里的类型注解被剥掉，其余语句原样保留。

```bash
$ tsc --noCheck --outDir distnoc src/bug.ts
$                                                                    # exit 0
$ cat distnoc/bug.js
const n = "not a number";
console.log(n.toFixed(2));
export const double = (x) => x * 2;
```

`--noCheck` 的用途是救急：类型检查卡住发布，先把产物发出去。日常构建不要用它，它会把类型错误原样带进运行时。TypeScript 7 里它还有一个用途，配合 `--isolatedDeclarations` 让大型项目并行生成声明文件。

分工是：`bundler` 模式下 `tsc --noEmit` 进 CI 查类型，打包器负责解析和产出。两个工具各跑一遍，不要用打包器代替类型检查。

CI 里可以把两步串起来：先跑 `tsc --noEmit`，失败就停，类型通过后再跑打包。两个命令放在同一个 job 里，共用一次 `pnpm install`。顺序反过来，打包器会先把错误代码产出到 `dist`，类型检查失败时还得清理产物。

## import attributes、import defer、source phase

JSON 模块在 `nodenext` 下必须写 import attribute，否则报 TS1543。旧的 `assert` 写法作废，报 TS2880。属性不是装饰，它告诉引擎按什么格式解析文件，也顺便挡住了一部分副作用导入。

```ts
import data from "./data.json" with { type: "json" };
export const count: number = data.count;
```

`./data.json` 是示例文件；单块编译报 `TS2307`，配好 `resolveJsonModule` 与 `nodenext` 后通过。

```bash
$ tsc --noEmit --module nodenext --moduleResolution nodenext src/noattr.ts
src/noattr.ts(1,18): error TS1543: Importing a JSON file into an ECMAScript module requires a 'type: "json"' import attribute when 'module' is set to 'NodeNext'.
$ tsc --noEmit --module nodenext --moduleResolution nodenext src/assertattr.ts
src/assertattr.ts(1,32): error TS2880: Import assertions have been replaced by import attributes. Use 'with' instead of 'assert'.
```

旧代码里的 `assert { type: "json" }` 会逐个报 TS2880。数量多时用正则批量替换，把 ` assert {` 改成 ` with {`，再跑一遍 tsc 确认没有漏网。

JSON 导入不带 attribute 时，`bundler` 能通过，因为打包器自己处理。同一个文件换到 `nodenext` 就报 TS1543，配置跟着项目形态走，不能一套配置两边用。

`import defer` 把模块求值推迟到第一次访问。它只支持 `module` 为 `esnext` 或 `preserve`，并且不能带具名导入。适合那些加载成本高、又不一定用到的模块。

```ts
import defer * as mod from "./mod.js";
export const value: number = mod.n;
```

`./mod.js` 是示例文件，单块编译报 `TS2307`。`import defer` 只在 `module` 为 `esnext` 或 `preserve` 时可用，否则报 `TS18060`。

```bash
$ tsc --noEmit --module commonjs src/defer.ts
src/defer.ts(1,8): error TS18060: Deferred imports are only supported when the '--module' flag is set to 'esnext' or 'preserve'.
$ tsc --noEmit --module esnext --moduleResolution bundler src/defernamed.ts
src/defernamed.ts(1,8): error TS18059: Named imports are not allowed in a deferred import.
```

source phase imports 在 TypeScript 7.1 Beta 才有。7.0.2 把 `import source` 当成语法错误，报 TS1005。这个语法用于 WebAssembly 模块，源码阶段只拿模块对象，不求值。运行时支持要单独查兼容表，TypeScript 只负责语法和类型。

```ts
import source wasm from "./mod.wasm";
// 7.0.2: src/wasm.ts(1,15): error TS1005: '=' expected.
// 7.0.2: src/wasm.ts(1,20): error TS1005: ';' expected.
```

## 同时发布 CJS 和 ESM

双发需要两套编译。ESM 一份，`module` 和 `moduleResolution` 都用 `nodenext`，`declaration` 打开，`outDir` 指 `dist/esm`。CJS 一份，用 `commonjs` 配 `bundler`，`outDir` 指 `dist/cjs`。两份都带 `rootDir: "src"` 和 `strict: true`。

根目录的 `package.json` 写 `"type": "module"`。CJS 产物要改成 `.cjs` 后缀，声明文件改成 `.d.cts`，或者在 `dist/cjs` 里放一个 `{"type": "commonjs"}`。文件名和声明文件必须成对，否则解析器按 ESM 读 CJS 的声明。

CJS 分支的声明文件必须叫 `.d.cts`，和 `.cjs` 成对出现。类型解析先看同名声明文件，再读 `exports` 里的 `types` 条件，文件名和 JavaScript 对不上时，运行时能跑，类型全丢。

两份构建都产出 `.d.ts` 时，直接写 `types` 指向 ESM 那份是最常见的错误。CJS 消费方拿到 ESM 声明文件，运行时格式对不上。这类问题本地测试很难发现，attw 专门查它。

```json
{
  "name": "dual-lib",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/esm/index.d.ts",
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.js"
    }
  }
}
```

```bash
$ pnpm pack && attw ./dual-lib-1.0.0.tgz
dual-lib v1.0.0

💀 Import failed to resolve to type declarations or JavaScript files.
   https://github.com/arethetypeswrong/arethetypeswrong.github.io/blob/main/docs/problems/NoResolution.md

┌───────────────────┬────────────────────────┐
│                   │ "dual-lib"             │
├───────────────────┼────────────────────────┤
│ node10            │ 💀 Resolution failed   │
├───────────────────┼────────────────────────┤
│ node16 (from CJS) │ 👺 Masquerading as ESM │
├───────────────────┼────────────────────────┤
│ node16 (from ESM) │ 🟢 (ESM)               │
├───────────────────┼────────────────────────┤
│ bundler           │ 🟢                     │
└───────────────────┴────────────────────────┘
```

表里 node10 一直红，说明老解析器找不到声明文件，这在新版本里是可接受的结果。真正要盯的是另外三行，它们只要有红或黄，就得改 `exports`。

发包流程可以固定成三步：两次构建，`pnpm pack`，attw 加 publint。三步都过再 `npm publish`。attw 读的是打出来的包，不是源码目录，所以必须先 pack。

表里的 👺 是伪装：声明文件是 ESM，JavaScript 是 CommonJS。tsc 按声明文件理解类型，Node 按实际文件加载，两边不一致。修法是把 `types` 放进 `import` 和 `require` 分支，CJS 分支指向 `.d.cts`。

```json
{
  "name": "dual-lib",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "import": { "types": "./dist/esm/index.d.ts", "default": "./dist/esm/index.js" },
      "require": { "types": "./dist/cjs/index.d.cts", "default": "./dist/cjs/index.cjs" }
    }
  }
}
```

```bash
$ pnpm pack && attw ./dual-lib-1.0.0.tgz && publint
dual-lib v1.0.0

┌───────────────────┬──────────────────────┐
│                   │ "dual-lib"           │
├───────────────────┼──────────────────────┤
│ node10            │ 💀 Resolution failed │
├───────────────────┼──────────────────────┤
│ node16 (from CJS) │ 🟢 (CJS)             │
├───────────────────┼──────────────────────┤
│ node16 (from ESM) │ 🟢 (ESM)             │
├───────────────────┼──────────────────────┤
│ bundler           │ 🟢                   │
└───────────────────┴──────────────────────┘
Running publint v0.3.25 for dual-lib...
Packing files with `pnpm pack`...
Linting...
Suggestions:
1. The package does not specify the "engines.node" field. Consumers may install it on an unsupported Node.js version. Consider adding the field with your actual minimum supported Node.js version. (This may be a breaking change)
```

`node10` 那一行是给 TypeScript 5.x 的消费者看的。7.0 已经删掉 `node10` 解析，这一行只影响旧版本工具链。需要兼容旧版时，加 `typesVersions` 把老解析器指向另一份声明文件。

`exports` 的 `types` 条件 TypeScript 4.7 才支持。低于 4.7 的版本不认这个字段，会退回读顶层 `types`，所以老项目里经常要同时写顶层 `types` 和 `exports`。两个位置都写时以 `exports` 为准。

版本策略也要提前定。只发 ESM 的包写 `"type": "module"` 和一份声明即可，不必双发。双发的成本在维护两套构建和两套声明，收益是兼容还在用 `require` 的老项目。新项目可以直接跳过这一步。

发布前跑一遍 publint 和 attw。publint 检查 `package.json` 结构和文件是否存在，attw 检查解析结果和声明文件格式。两个工具互补，不能互相替代。attw 的输出里 node10 一行红是正常的，那代表老解析器解析失败，不影响新版本。

## 报错对照

| 错误码 | 触发条件 | 改法 |
|---|---|---|
| TS5108 | 用了 `node10`、`classic`、`amd`、`umd` 等已删除选项 | 换成 `nodenext` 或 `bundler` |
| TS5102 | 用了 `baseUrl`、`outFile` | 删掉，路径写相对路径 |
| TS5110 | `moduleResolution: node16` 配了别的 `module` | 把 `module` 改成 `node16` 或 `nodenext` |
| TS6046 | `moduleResolution` 写成 `node20` 这类不存在的取值 | 改成 `node16` 或 `nodenext` |
| TS5095 / TS5109 | `module: node20` 配了 `bundler` | `moduleResolution` 留空或写 `node16` |
| TS2835 | ESM 文件里相对导入没写扩展名 | 写成 `./x.js` |
| TS5097 | 导入路径写了 `.ts` | 加 `allowImportingTsExtensions` 加 `noEmit` |
| TS1484 | `verbatimModuleSyntax` 下类型没加 `type` | 写 `import type` 或 `{ type X }` |
| TS1295 / TS1287 | CommonJS 文件里写 ESM 语法 | 改 `package.json` 的 `type`，或换后缀 |
| TS1205 | `isolatedModules` 下再导出类型 | 用 `export type` |
| TS2748 | `isolatedModules` 下访问 ambient `const enum` | 改普通枚举，或把值搬进文件 |
| TS2307 | 子路径没写进 `exports`，或 `#` 别名写错 | 补 `exports` 条目，或修正别名 |
| TS7016 | 依赖没有声明文件 | 装 `@types/x` 或自己写 `.d.ts` |
| TS1543 | ESM 里导入 JSON 没写 attribute | 加 `with { type: "json" }` |
| TS2880 | 用了 `assert` | 改成 `with` |

升级时按这张表从前往后改。前六个是配置层，改完跑一次 `tsc --showConfig` 确认生效；后九个是代码层，tsc 一次全报出来，按文件批量修。

## 用不上的时候

### 类型检查与运行时各有一套解析

`bundler` 档位下 tsc 只做检查，产物由打包器生成，两边的解析规则不同。`tsc --noEmit` 通过不代表 `vite build` 能过，反过来也一样。判断模块能不能加载，要在实际运行的那条链路上验证。

### 依赖包内部的解析问题

`TS7016`、`TS2307` 出现在 `node_modules` 里的包上时，改自己的 `tsconfig` 没有用。要么装 `@types/x`，要么补一个 `declare module`，要么换包。这类报错的处理权不在你的配置里。

### 停在旧解析档位

`node10` 和 `classic` 在 TypeScript 7 已删除，报错是 `TS5108`，没有兼容写法。老项目继续用 `"moduleResolution": "node"` 会直接失败，迁移成本必须付。想少改代码，也得先把 `module` 和扩展名一起改。
