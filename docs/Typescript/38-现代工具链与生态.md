# 第 38 章 现代工具链与生态

刚接手的项目里 `tsc`、`tsx`、`vite`、`eslint` 各跑各的，改一个配置要动四个文件。这些工具处理的环节不同，混在一起会互相覆盖。这一章按运行、检查、转译、校验、格式化分层，给一张按场景选工具的表。

Node 26 能直接运行 `.ts` 文件，但它只删类型，不做检查，也不转译。类型检查交给 `tsc --noEmit`，转译交给打包工具。把这三件事分清楚，选型就不会乱。

转译器一次只看一个文件，看到 `enum` 就展开，看到别的文件里的 `const enum` 却无从下手。类型关系存在跨文件的符号表里，它没有这张表，所以不做类型判断。同一个 `const port: number = "8080"`，`tsx` 能跑出 8080，`tsc` 报 TS2322，差别就在这两条路径。

## 运行：三种方式

同一个文件，`node` 和 `tsx` 的结果可能不同。`node` 走的是原生剥离，遇到 `enum` 直接报语法错误。

```typescript
enum Level {
  Debug,
  Info,
}

const level: Level = Level.Info;
const label: string = level === Level.Info ? "info" : "debug";
console.log(label);
```

```bash
$ node app.ts
file:///project/app.ts:1
  > enum Level {
  > }

SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode

$ tsx app.ts
info
```

输出是节选，省略了调用栈。`tsx` 4.23.15 用 [esbuild](https://esbuild.github.io/) 转译，`enum` 能正常变成对象。代价是启动慢一点，多一层转译。

剥离模式有几条固定规则：导入本地模块必须写 `.ts` 扩展名，文件里的 `import type` 整行删除，`node_modules` 下的 `.ts` 文件直接拒绝处理，项目里的 `tsconfig.json` 被忽略，所以 `paths` 别名不可用。需要别名时交给打包工具或 tsx。

剥离模式不处理 `.tsx`，也不做装饰器转换，`node_modules` 里的 TS 文件一律跳过。直接用 `node` 跑 TS 时，语法层的问题会当场抛错，类型错误不会出现。文件能跑起来，不代表类型是对的。`--experimental-strip-types` 仍然接受，`--no-strip-types` 用来关掉剥离。用 tsx 也可以走 loader：`node --import=tsx src/main.ts`，由 Node 启动，转译交给 tsx。

第三种方式是先构建再运行。前端产物交给浏览器，库产物交给 npm，Node 服务可以先 `tsc` 编译出 `dist/`，也可以直接用 `node` 或 `tsx` 启动。

## 工具选型表

| 工具 | 版本 | 负责哪一段 | 什么时候用 |
|---|---|---|---|
| Node | 26.13.1 | 直接运行，剥离类型 | 服务端、脚本，代码里没有 `enum`、参数属性 |
| tsx | 4.23.15 | 直接运行，esbuild 转译 | 本地开发、需要 `enum` 或装饰器 |
| tsc | 7.0.2 | 类型检查，`--noEmit` | 所有项目，CI 必跑 |
| Vite | 8.3.8 | 前端开发服务器与构建，Rolldown | 浏览器项目 |
| tsdown | 0.23.7 | 库构建，Rolldown，生成 `.d.ts` | 新写的 npm 库 |
| tsup | 9.0.0 | 库构建，esbuild，生成 `.d.ts` | 已有的 npm 库 |
| esbuild | 0.28.2 | 底层转译 | 被 tsx、tsup 调用 |
| swc | 1.16.22 | 底层转译，Rust 实现 | 需要装饰器或极快冷启动 |

表中的版本是 2026 年 11 月的快照，装之前用 `npm view` 确认当前版本。`ts-node` 10.9.2 的更新时间停在 2023 年 12 月，不再跟进 Node 新的 loader 机制。新项目直接用 tsx。

表格里没有“全能”的工具。Vite 不做类型检查，tsc 不打包，tsx 不输出产物。转译器一次只看一个文件，跨文件的类型关系它看不到。`tsc` 会加载整个项目，所以最后的类型判断只能由它做。八种工具都读同一份 `tsconfig.json`，类型规则只维护一处。

逐文件处理带出一个限制：`const enum` 的成员本来要跨文件内联，转译器拿不到别的文件的信息。打开 `isolatedModules` 后，跨模块引用 `const enum` 报 TS2748，只能退化成运行时对象。这也是 `erasableSyntaxOnly` 存在的理由，语法层面就不给转译器出难题。

### 单文件处理的边界

转译器的流程是读一个文件，改语法，输出 JS，再下一个文件。它不建程序，不建符号表，不看别的文件。`tsc` 的流程是先建程序，绑符号，再检查。产物也不同：前者出 JS，后者出诊断。

单文件流程带出几类限制，根因是同一个：它拿不到别的文件的符号表。`const enum` 的成员要在使用处内联，内联需要枚举定义，跨文件就断。`import { X } from "./a"` 里 `X` 是类型还是值，单文件分不出来，只能按值保留，于是纯类型导入必须写 `type`。`enum`、参数属性、带值的 `namespace` 要在同一个文件里生成代码，转译器做得了这些变换，Node 的剥离器不做。

反过来让 `tsc` 逐文件跑也不行。跨文件的类型错误要拿两个文件的符号去对，逐文件跑必然漏掉这一类。CI 里那条 `tsc --noEmit` 补的就是这个缺口。

`erasableSyntaxOnly` 和 `verbatimModuleSyntax` 把这条边界写进编译器：前一个禁止任何要生成代码的语法，后一个按单文件视角处理导入。

打包器也会读 `tsconfig.json`，但只读影响代码生成的那几项：`jsx`、`target`、`paths`、`useDefineForClassFields`。`strict`、`noUncheckedIndexedAccess` 这类影响类型判断的字段，它读了也用不上。同一份配置被两边读，解读却不完全一样，选型时要知道这个差别。

选型时看一条：谁负责跨文件，谁就只能做检查。跑得快、不吃配置的工具，都放弃了跨文件信息；要跨文件，就得先建程序，代价是启动慢。这两件事没法靠配置同时拿到。

## 类型检查与转译分开

转译器只关心语法，不关心类型。下面这个文件 `tsx` 能跑，`tsc` 会报错。

```bash
$ cat bad.ts
const port: number = "8080";
console.log(port);

$ tsx bad.ts
8080

$ tsc --noEmit bad.ts
bad.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

修正后的写法能通过检查，运行时输出不变。

```typescript
const port: number = Number("8080");

if (!Number.isInteger(port) || port < 1 || port > 65535) {
  throw new RangeError(`invalid port: ${port}`);
}

console.log(port);
```

CI 里固定跑一条命令：`tsc --noEmit`。构建产物里不会出现类型错误，所以这条命令必须在构建之前跑。

```json
{
  "compilerOptions": {
    "target": "esnext",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true,
    "erasableSyntaxOnly": true,
    "verbatimModuleSyntax": true
  },
  "include": ["src"]
}
```

打开 `erasableSyntaxOnly` 后，编译期接受的语法和 Node 剥离模式一致。开了它，`enum`、参数属性、带运行时代码的 `namespace` 都会报 TS1294，写下的每行代码都能被 `node` 直接执行。

### 两个转译器边界的报错

打开 `isolatedModules` 后，下面这个文件两种失败同时出现：

```ts
declare const enum Level {
  Debug,
  Info,
}

const current: Level = Level.Info;

enum Mode {
  On,
  Off,
}

export const mode: Mode = Mode.On;
console.log(current, mode);
```

```bash
$ tsc --noEmit --isolatedModules --erasableSyntaxOnly dual.ts
dual.ts(6,24): error TS2748: Cannot access ambient const enums when 'isolatedModules' is enabled.
dual.ts(8,6): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
```

TS2748 指向外部 `const enum` 的成员访问，单文件跑不出内联结果。TS1294 指向 `enum` 声明，这种语法要生成代码。两条来自不同开关，说的是同一条边界：单文件处理不了的写法，编译器提前拒掉。

改法分两种。`const enum` 换成普通对象加 `as const`，跨文件也能用。确实需要 `enum` 的项目关掉 `erasableSyntaxOnly`，回到 `tsc` 出产物的路线。

TypeScript 7.0 的编译器用 Go 重写。官方公告给出的数字是整体快 10 倍，全量构建快 8 到 12 倍。命令行接口没有大改，`tsc --noEmit` 的使用方式不变。移植的过程、并行的两层参数、7.0 不带 API 的后果，见第 49 章。

6.0 是过渡版本，默认值已经改过：`strict` 默认 `true`，`module` 默认 `esnext`，`types` 默认 `[]`。一批选项直接报错：`target: "es5"`、`downlevelIteration`、`moduleResolution: "node"`、`module: "amd"`、`baseUrl`，这些组合在 7.0 里已经不存在。从旧项目升级时，先跑一次 `tsc --noEmit`，把报错清完再动构建。

新项目跑 `tsc --init` 得到的默认值也变了。实测 7.0.2 生成 44 行配置，`noUncheckedIndexedAccess` 与 `exactOptionalPropertyTypes` 默认打开，`moduleDetection` 为 `force`，`types` 是空数组。空数组意味着 `@types/node` 要自己加，否则 `process`、`console` 都找不到。

## 前端：Vite 8

Vite 8 的打包器换成了 [Rolldown](https://rolldown.rs/)。Rolldown 用 Rust 重写，插件钩子照 Rollup 的接口设计，旧插件大多能直接用。开发服务器仍然走原生 ESM，浏览器请求哪个模块就转译哪个模块，不做整包打包。`node_modules/vite/package.json` 的依赖里只有 `lightningcss`、`picomatch`、`postcss`、`rolldown`、`tinyglobby`，没有 `esbuild`。开发时仍然快，构建产物带 sourcemap。Vite 8.3.8 依赖里的 Rolldown 版本是 `~1.2.18`，插件生态按 Rollup 的钩子写，旧的 Rollup 插件大多能直接用。

```typescript
import { defineConfig } from "vite";

export default defineConfig({
  build: { target: "esnext", sourcemap: true },
});
```

要装 `vite` 才能解析导入；没装时报 `TS2307: Cannot find module 'vite'`。

```bash
$ vite build
vite v8.3.8 building client environment for production...
transforming...
✓ 4 modules transformed.
dist/index.html                0.21 kB │ gzip: 0.18 kB
dist/assets/index-DUMTvf3x.js  0.80 kB │ gzip: 0.48 kB │ map: 0.44 kB
✓ built in 17ms
```

开发服务器与构建产物走两条路径：开发时按需转译，改一个文件只更新一个模块；构建时整包分析，做 tree shaking 与压缩。从旧版本升级的改动见 [Vite 迁移指南](https://vite.dev/guide/migration)。`vite preview` 用来检查构建产物，它读 `dist/`，不经过开发服务器。

`dist` 写进 `.gitignore`，产物不进仓库。文件名里的 hash 每次构建都不同。产物用 `esnext` 目标，不做降级，老浏览器交给项目自己决定要不要加 polyfill。

## 库：tsdown 与 tsup

库要产出两样东西：运行代码和类型声明。tsdown 用 Rolldown，和 Vite 同源，配置见 [tsdown 文档](https://tsdown.dev/)；tsup 用 esbuild，生态更老。

```typescript
export function* range(start: number, stop: number, step = 1): Generator<number, void, undefined> {
  for (let i = start; i < stop; i += step) {
    yield i;
  }
}

export const take = <T>(source: Iterable<T>, count: number): T[] => {
  const out: T[] = [];
  for (const item of source) {
    if (out.length >= count) break;
    out.push(item);
  }
  return out;
};
```

```typescript
import { defineConfig } from "tsdown";

export default defineConfig({
  entry: ["src/index.ts"],
  format: ["esm"],
  dts: true,
  clean: true,
  outExtensions: () => ({ js: ".js", dts: ".d.ts" }),
});
```

这段要装 `tsdown`；没装时报 `TS2307`。

```bash
$ tsdown
ℹ tsdown v0.23.7 powered by rolldown v1.3.3
ℹ entry: src/index.ts
ℹ dist/index.js    0.29 kB │ gzip: 0.21 kB
ℹ dist/index.d.ts  0.18 kB │ gzip: 0.15 kB
✔ Build complete in 210ms
```

tsup（[tsup 文档](https://tsup.egoist.dev/)）的配置几乎一样，输出格式略有差别。

```typescript
import { defineConfig } from "tsup";

export default defineConfig({
  entry: ["src/index.ts"],
  format: ["esm"],
  dts: true,
  clean: true,
});
```

这段要装 `tsup`；没装时报 `TS2307`。

```bash
$ tsup
CLI Target: node16
ESM dist/index.js 115.00 B
DTS dist/index.d.ts 174.00 B
```

原输出每行带一个闪电符号，这里删掉了。两个工具都能生成 `.d.ts`，都能 `clean`，差别在底层打包器。

新库选 tsdown，和 Vite 共用 Rolldown，构建语义一致。已有项目用 tsup 就不必换，esbuild 稳定，配置不用动。只发 ESM 就把 `format` 写成 `["esm"]`，还要兼容旧调用方就写成 `["esm", "cjs"]`，两种格式各生成一份 `.d.ts`。

`package.json` 要把导出字段写清楚，否则 `d.ts` 生成了也找不到。`types` 条件放在 `import` 前面，条件按顺序匹配，`types` 放到后面可能永远命中不到。

```json
{
  "name": "num-kit",
  "version": "0.1.0",
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" }
  },
  "files": ["dist"],
  "scripts": {
    "check": "tsc --noEmit",
    "build": "tsdown",
    "test": "vitest run",
    "lint": "eslint ."
  }
}
```

## 校验运行时输入：zod 4

类型在运行时不存在。外部输入要靠 schema 校验，再用 `z.infer` 把类型倒推出来。

```typescript
import { z } from "zod";

const Env = z.object({
  PORT: z.coerce.number().int().min(1).max(65535),
  EMAIL: z.email().toLowerCase(),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  RETRY: z.int().nonnegative().default(3),
});

export type Env = z.infer<typeof Env>;

const parsed = Env.safeParse({ PORT: "8080", EMAIL: "Dev@Example.COM" });
if (parsed.success) {
  const env: Env = parsed.data;
  console.log(env);
} else {
  console.log(z.prettifyError(parsed.error));
}

const Name = z.string().min(2, { error: "名字至少两个字符" });
console.log(Name.safeParse("a").error?.issues[0]?.message);
```

```bash
$ tsx env.ts
{ PORT: 8080, EMAIL: 'dev@example.com', LOG_LEVEL: 'info', RETRY: 3 }
名字至少两个字符
```

`z.coerce.number()` 会先做类型转换再校验，环境变量里的 `"8080"` 变成 `8080`，`"abc"` 变成 `NaN` 后校验失败。`default()` 只在字段是 `undefined` 时生效，显式传 `null` 不走默认值。

v4 的改动集中在三处：`z.email()`、`z.int()` 这些校验器提到顶层，不再挂在 `z.string()` 上；自定义错误从 `message` 参数改成 `error`；`z.infer` 的用法不变。

schema 只在系统边界用：HTTP 入口、环境变量、配置文件、队列消息。内部函数之间传已经校验过的对象，同一份数据不要校验两遍。

`z.infer` 只在编译期生效。schema 和类型必须来自同一个地方，手写一份 `type Env` 再写一份 schema，两边迟早对不上。

`z.infer` 等价于 `z.output`，拿到的是校验之后的类型。`z.input` 是校验之前的类型，`coerce` 的字段在那里是 `unknown`，`"8080"` 与 `8080` 都能传。接表单、接配置文件时用 `z.input`，进到业务逻辑里用 `z.output`。

`safeParse` 失败时 `parsed.error` 是 `ZodError`，`issues` 里每条带 `path` 与 `message`。`z.prettifyError()` 把整份错误排成可读文本，适合直接打印到日志。

## 类型测试

类型写错时运行时没有报错，只有编辑器里一行红线。类型测试把红线变成 CI 里的失败。

`expect-type` 只做类型断言，编译时检查，没有运行时开销。文件用 `tsc --noEmit` 跑一遍就算测试。

```typescript
import { expectTypeOf } from "expect-type";

function* ticks(): Generator<number, void, undefined> {
  yield 1;
}

const pair = [1, "ok"] as const;

expectTypeOf(pair).toEqualTypeOf<readonly [1, "ok"]>();
expectTypeOf(ticks()).toMatchTypeOf<Iterable<number>>();
expectTypeOf(ticks().next()).toEqualTypeOf<IteratorResult<number, void>>();
```

要先装 `expect-type`；没装时报 `TS2307`。

这些断言写在普通的 `.ts` 文件里，文件本身也要能被 `tsc` 编译。`toEqualTypeOf` 比较完全相等的类型，多一个可选属性也会失败。`toMatchTypeOf` 只检查能不能赋值，适合写“至少满足这个接口”的断言。

`vitest` 5.1.1 把类型测试接进测试运行器，文件名用 `.test-d.ts`。这类文件只在类型检查阶段运行，不会出现在正常测试里。项目根必须有 `tsconfig.json`，否则编译器直接报错。

```typescript
import { expectTypeOf, test } from "vitest";

function* ticks(): Generator<number, void, undefined> {
  yield 1;
}

test("generator types", () => {
  const it = ticks();
  expectTypeOf(it).toEqualTypeOf<Generator<number, void, undefined>>();
  expectTypeOf(it.next()).toEqualTypeOf<IteratorResult<number, void>>();
  expectTypeOf(it.map((n) => n + 1).toArray()).toEqualTypeOf<number[]>();
});
```

这块要装 `vitest`；`Generator` 的 `map` 还要 `lib` 含 `esnext`，否则报 `TS2339` 和 `TS7006`。

```bash
$ vitest run --typecheck
 RUN  v5.1.1 /project

 ✓  TS  tests/iterator.test-d.ts (1 test)

 Test Files  1 passed (1)
      Tests  1 passed (1)
Type Errors  no errors
```

没有 `tsconfig.json` 时，`vitest` 报 `TypeScript compiler returned help text instead of type checking results`，后面的提示是找不到 tsconfig。

`tsd` 0.33.0 是独立命令行，适合给发布的包写类型测试。它读包里的 `types` 字段，必须在该包目录内运行。

```typescript
import { expectType, expectError } from "tsd";
import { pair } from "../index";

expectType<[number, string]>(pair(1, "a"));
expectError(pair(1));
```

`tsd` 与包的入口 `../index` 都要在；缺任一个报 `TS2307`。

```bash
$ tsd
$ echo $?
0
```

通过时没有任何输出。`expectError` 断言这行必须报错，类型改宽了就会失败。

| 工具 | 运行方式 | 适合 |
|---|---|---|
| `expect-type` | `tsc --noEmit` | 任意项目，只比类型 |
| `vitest --typecheck` | 测试运行器 | 已有 vitest 的项目 |
| `tsd` | 独立命令 | 要发布到 npm 的库 |

类型测试的价值在库的公开 API：声明文件改动后，调用方拿到的类型是否还符合预期。库项目值得写，业务代码里断言内部类型收益很低。三个工具都用 tsc 做检查，所以都吃 `tsconfig.json` 里的 `strict` 与 `lib`。选哪个看测试体系，不要同时上两套。

## Lint：ESLint 10 与 typescript-eslint 8

ESLint 10 只认 flat config。项目里放 `.eslintrc.json`，运行时报 `ESLint couldn't find an eslint.config.* file.`，退出码非零。

```bash
$ eslint src/a.ts

Oops! Something went wrong! :(

ESLint: 10.15.0

ESLint couldn't find an eslint.config.* file.
```

配置文件用 `eslint.config.ts` 需要 `jiti` 加载，否则报 `The 'jiti' library is required for loading TypeScript configuration files`。加上 `jiti` 之后，配置本身也能被类型检查。

```typescript
import { defineConfig } from "eslint/config";
import tseslint from "typescript-eslint";
import prettier from "eslint-config-prettier/flat";

export default defineConfig(
  tseslint.configs.recommendedTypeChecked,
  {
    languageOptions: {
      parserOptions: {
        projectService: true,
        tsconfigRootDir: import.meta.dirname,
      },
    },
    rules: {
      "@typescript-eslint/no-unsafe-member-access": "error",
    },
  },
  prettier,
  {
    ignores: ["dist/**"],
  },
);
```

要装 `eslint`、`typescript-eslint` 与 `eslint-config-prettier`；缺了报 `TS2307`。`import.meta.dirname` 还要 Node 20.11 以上的类型，且 `module` 为 `nodenext`，否则报 `TS2339`。

`defineConfig()` 接受任意多个配置对象，按数组顺序合并，后面的覆盖前面的。`projectService: true` 取代了旧的 `parserOptions.project`，不用手写 `tsconfig` 路径，也不会因为新增目录反复改配置。`recommendedTypeChecked` 里的规则需要类型信息，跑得慢一些，报得准一些。

忽略文件写在配置的 `ignores` 字段里，`.eslintignore` 在 10.x 不再读取。类型感知规则能发现只有类型信息才看得见的问题，比如 `no-floating-promises` 漏掉 `await`、`no-misused-promises` 把 async 函数塞进同步回调。这类规则占 lint 时间的大头，可以只对 `src` 开。

配置里的 `typescript-eslint` 和 CLI 用的 `tsc` 是两套东西。lint 读的是类型信息，检查的是代码风格与危险用法，不产出产物，也不替代 `tsc --noEmit`。

```bash
$ eslint src/a.ts

src/a.ts
  1:8   error  Async function 'load' has no 'await' expression  @typescript-eslint/require-await
  6:16  error  Unexpected any. Specify a different type         @typescript-eslint/no-explicit-any
  7:3   error  Unsafe return of a value of type `any`           @typescript-eslint/no-unsafe-return
  7:16  error  Unsafe member access .length on an `any` value   @typescript-eslint/no-unsafe-member-access

✖ 4 problems (4 errors, 0 warnings)
```

没有安装 `typescript-eslint` 时，`no-unsafe-*` 这类规则根本不存在，`any` 会一路溜过去。

TypeScript 7.0 不再提供编译器 API（见 [7.0 公告](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)）。typescript-eslint 8.73.0 装到 7.0.2 上会直接拒绝启动。

```bash
$ eslint src/a.ts
typescript-eslint does not support TS 7.0.
Please see https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6.0 to run typescript-eslint using the TS 6 API.
See also https://github.com/typescript-eslint/typescript-eslint/issues/10940 for tracking typescript-eslint's support for TS >=7.1

Oops! Something went wrong! :(

ESLint: 10.15.0

Error: typescript-eslint does not support TS 7.0.
```

7.0 只提供命令行，不带编译器 API；7.1 才补上。凡是调用 `typescript` 包 API 的工具，在 7.1 之前都要用 6.0。官方方案是同时装 6.0 的 API 和 7.0 的编译器。`typescript` 指向 6.0，工具链读到能用的 API。

```bash
$ npm install -D typescript@npm:@typescript/typescript6@^6.0.2
$ node -e "console.log(require('typescript/package.json').version)"
6.0.2
$ eslint src/a.ts
# 同样的 4 条类型感知错误，lint 正常退出
```

这个别名包提供 `tsc6` 命令。还要保留 7.0 的 `tsc`，再装 `@typescript/native`（`npm:typescript@^7.0.2`），两个命令各跑各的。

`eslint-config-prettier/flat` 放在配置末尾，关掉与格式化冲突的规则。顺序错了会重新打开被关的规则。

## 格式化：Prettier 3

Prettier 只管格式，不管逻辑。缩进、引号、换行、尾逗号都交给它，ESLint 不再管这些。项目里放一个 `.prettierrc.json` 就够。

```json
{
  "semi": true,
  "singleQuote": false,
  "printWidth": 100,
  "trailingComma": "all"
}
```

```bash
$ prettier --check .
Checking formatting...
[warn] src/a.ts
[warn] Code style issues found in the above file. Run Prettier with --write to fix.
```

编辑器保存时自动格式化，插件读同一份 `.prettierrc.json`，格式以配置为准。`--check` 只报不改，CI 里用；`--write` 本地用，一次改完。两个命令都只读文件内容，不执行代码。格式问题在保存与 CI 两处拦下。`printWidth` 改小会让长表达式提前换行，`trailingComma: "all"` 让 diff 更稳定，加一行不会改动上一行的逗号。`dist`、`coverage`、lock 文件写进 `.prettierignore`，不用每次扫描。

## 按场景选组合

| 场景 | 运行 | 构建 | 检查 |
|---|---|---|---|
| 浏览器应用 | `vite dev` | `vite build` | `tsc --noEmit` + ESLint |
| Node 服务，无 `enum` | `node src/main.ts` | `tsc` 输出 `dist/` | 同上 |
| Node 服务，有 `enum` | `tsx src/main.ts` | `tsc` 输出 `dist/` | 同上 |
| npm 库 | `vitest` | `tsdown` | 同上 + `tsd` |
| 一次性脚本 | `tsx script.ts` | 不需要 | 可跳过 lint |

“检查”一列在各场景里相同：类型检查、lint、格式化三件事都要做，只是库项目多一步类型测试。

CI 里的顺序固定成：`tsc --noEmit`、`eslint .`、`vitest run`、构建。类型检查排第一，它最便宜，失败最快。构建放最后，前面任何一步失败都不该产出产物。

## 老项目迁移顺序

先升类型检查，再升 lint，最后换构建。顺序反了会同时面对三类报错。

1. 装 TypeScript 7.0.2，跑 `tsc --noEmit`，清掉 6.0 默认值变更带来的报错。
2. 把 `.eslintrc` 改成 `eslint.config.ts`，`parserOptions.project` 换成 `projectService`。
3. 加 `eslint-config-prettier/flat`，`prettier --check .` 进 CI。
4. `ts-node` 换成 `tsx`。`ts-node` 10.9.2 在 2023 年后没有更新，新语法支持跟不上。
5. 库项目补 `tsd`，应用项目补 `vitest --typecheck`。

每步单独提交，单独回滚。迁移期间冻结大功能，只做工具替换，出问题时边界清楚。迁移完成的标准是四条：CI 全绿、`tsc --noEmit` 无报错、构建时间可接受、锁文件里不再出现旧工具。中间状态可以跑，只是暂时保留旧工具。

## 用不上的时候

### 单文件脚本或小工具

一个几十行的脚本，用 `node` 或 `tsx` 直接跑就行。装 ESLint 10、Vite 8、tsdown 这一套，配置文件比脚本长。工具链的收益在多人维护的项目里，规模不到时是纯成本。

### TypeScript 7.0 与调用编译器 API 的工具

`typescript-eslint` 8.73.0 装到 7.0.2 上会直接拒绝启动，报 `typescript-eslint does not support TS 7.0`。7.0 不带编译器 API，这类工具在 7.1 之前都要靠 6.0 的别名包。升级 TypeScript 之前，先查工具链的支持状态。

### 继续使用 ts-node

`ts-node` 10.9.2 的更新停在 2023 年 12 月，不再跟进 Node 新的 loader 机制。把它留在组合里，遇到 ESM 和新语法就要打补丁。新项目用 `tsx`，老项目迁移时一并换掉。
