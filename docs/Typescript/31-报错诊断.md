# 第 31 章 报错诊断

改完一处类型，`tsc` 又在新的位置冒出三条报错，越改越乱。原因常常是先看位置、后看类型，顺序倒过来能少走弯路。这一章按错误码分类整理十几种常见报错的读法，从 `TS2322` 到 `TS2589` 各给一条定位路径。

TypeScript 的报错有固定结构。读法有顺序：先看错误码，再看两个类型，最后看位置。顺序反了就会改错地方。

## 一条报错的结构

```text
src/user.ts(12,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

拆成四段：

| 片段 | 含义 | 怎么用 |
|---|---|---|
| `src/user.ts(12,7)` | 文件、行、列 | 位置常指向“接收方”，不一定是错误来源 |
| `error` | 级别 | 和 warning 分开看，`tsc` 默认没有 warning |
| `TS2322` | 错误码 | 检索键，比搜整句稳定 |
| `Type 'A' is not assignable to type 'B'` | 实际类型与期望类型 | `A` 是手里有的，`B` 是要求有的 |

关键在最后一段。`A` 是问题来源，`B` 是目标。改的时候要么改 `A`，要么改 `B`，不要先动位置指向的那一行。

类型一长就会被截断。加两个参数看全：

```bash
$ tsc --noEmit --pretty false --noErrorTruncation
```

`--pretty false` 输出纯文本，方便贴进 issue 或搜索。`--noErrorTruncation` 不省略长类型。

嵌套类型从最内层读：

```text
Type '{ a: string; }' is not assignable to type 'Record<string, Foo>'.
  Property 'b' is missing in type '{ a: string; }' but required in type 'Foo'.
```

第一句说外层不匹配，第二句才说清是 `Foo` 少 `b`。带缩进的后续行通常才是具体原因。

## 错误码从哪来

上面拆解里，`TS2322` 是编译器消息表里的编号。它不是严重等级，也不表示出现顺序。

消息表是编译器源码里的一个 JSON 文件，7.0.2 版本有 2,130 条：

```json
"Type '{0}' is not assignable to type '{1}'.": {
  "category": "Error",
  "code": 2322
}
```

`{0}`、`{1}` 是占位符，报错时换进实际类型。同一个码，消息正文会随类型变化：

```text
Type 'string' is not assignable to type 'number'.
Type '{ name: string; }' is not assignable to type '{ id: string; }'.
```

码按首位分段。下面的条数按 7.0.2 的表统计：

| 区段 | 条数 | 管什么 | 例子 |
|---|---|---|---|
| 1xxx | 465 | 语法、解析 | TS1005 少一个符号 |
| 2xxx | 539 | 类型检查 | TS2322 赋值不兼容 |
| 4xxx | 111 | 导入导出、声明引用 | TS4000 用了私有名 |
| 5xxx | 69 | 命令行选项、tsconfig | TS5102 选项已移除 |
| 6xxx | 490 | 帮助文本，类别是 Message | `tsc --help` 里的说明 |
| 7xxx | 55 | 隐式 any 一类 | TS7006 参数隐式 any |
| 8xxx | 36 | JS 文件里的非法写法 | TS8002 `import =` 只能用于 TS |
| 9xxx | 34 | 声明文件生成 | TS9013 推不出类型 |
| 17xxx / 18xxx | 21 / 52 | JSX、配置与文件发现 | TS17008 JSX 缺闭合标签 |
| 90xxx / 95xxx | 55 / 192 | 编辑器的代码修复项 | 插入 `super()` 调用 |

分段是多年追加形成的，不严格。2xxx 和 4xxx 里都有类型错误，1xxx 里也有检查阶段的码。

用数字做标识，因为文案会改。5.0.4 的表有 1,921 条，5.9.3 有 2,121 条：新增 225 条，另有 25 条不再出现。同一批码里，文案被改写的有 40 条。TS1121 从 `Octal literals are not allowed in strict mode.` 改成 `Octal literals are not allowed. Use the syntax '{0}'.`。TS5112 在 5.9.3 的表里还没有，7.0.2 才有。

搜 `TS2322` 能搜到新旧所有讨论，搜一句文案只能搜到一个版本。工具、issue、文档都按数字对齐。

使用上注意三条。

TypeScript 不能按码关闭报错。没有 ESLint 那种行内禁用，只能整行 `// @ts-expect-error`，或者改代码。

码不代表严重度。TS2322 和 TS2345 是同一类问题，一个在赋值，一个在传参，哪里错要看消息正文。

同一个码，不同版本的文案可能不同。书里的注释写成「码 + 原文」，对照时先认码，再看文案差异。

想查某个码，打开仓库里的 [diagnosticMessages.json](https://github.com/microsoft/TypeScript/blob/v7.0.2/src/compiler/diagnosticMessages.json)，码和文案一一对应。命令行加 `--pretty false` 得到纯文本，方便 grep。后面按码分类的十几节，都以这个编号为索引。

## 报错在哪个阶段产生

一次编译分四段：解析、绑定、检查、输出（见 [checker.ts](https://github.com/microsoft/TypeScript/blob/v5.9.3/src/compiler/checker.ts)）。解析把源码变成语法树，绑定建符号表，检查比较类型关系，输出生成 JS 和声明文件。前一段失败，后一段没有可靠输入。

程序里有语法错时，7.0.2 只输出语法错，语义错一条也不报，错在另一个文件也一样：

```bash
$ tsc --noEmit --strict --ignoreConfig syntax.ts sem2.ts
syntax.ts(3,1): error TS1005: '}' expected.
```

把文件拆开单跑，`sem2.ts` 会报 `error TS2322: Type 'string' is not assignable to type 'number'.`。同一批文件里它有错，却一个字都不提。

原因是语法树残缺时，类型检查会沿着残缺节点产生级联误报，噪声盖掉第一条真错。先修语法，再跑一次，语义错才露出来。看到一片红，先找有没有 TS1xxx 的解析错。

错误码前缀能猜阶段，不能当分类依据。TS1005 是解析期，TS5102、TS5108 是配置期，TS2322 是检查期，这些符合规律。反例也在：TS1205 和 TS1484 都在检查期，前缀却是 1xxx。前缀来自历史编号，不是阶段编码。

为什么不先跑语义检查、把语法错留到最后？类型检查依赖语法树的形状。少一个括号，后面整段都可能解析成别的结构，强行检查只会把解析歧义算成类型错。

绑定阶段也有自己的错。同名块级变量声明两次报 TS2451，和类型是否匹配无关，符号表建不起来。

同一阶段内的报错按文件参数顺序和位置排列，跨阶段的顺序由阶段决定。日志里要贴原文时加 `--pretty false` 关掉颜色，贴出来更干净。

报错被截断时加 `--noErrorTruncation`。长联合类型的赋值错误默认会省略中间成员，截断之后看不出到底缺哪一个。

报错顺序还决定修复策略。按顺序一条条改，每改一处重跑一次。一次改十处，后面的行号会整体平移，旧输出对不上新代码。

多文件项目的报错清单随 `include` 顺序变化。用 `-p` 指定配置跑，顺序稳定，输出可复现。手写文件列表排查时，把已确认的错先注释掉，剩下的才是新错。

一句话，报错也有先后，语法错是门槛，过不了就不进去量类型。这个比喻的边界在跨文件，一处语法错挡的是整个程序的语义阶段，不只是挡自己。

## 挂不上类型：TS2322

```ts
const n: number = "1";
```

```text
error TS2322: Type 'string' is not assignable to type 'number'.
```

改法只有两种：值改成 `1`，或者类型改成 `string`。用 `as number` 能消掉报错，但运行时 `n` 还是字符串，这是掩盖不是修复。

## 少属性：TS2741 与 TS2739

缺一个属性报 `TS2741`：

```ts
interface User { name: string; age: number }
const u: User = { name: "a" };
```

```text
error TS2741: Property 'age' is missing in type '{ name: string; }' but required in type 'User'.
```

缺多个报 `TS2739`：

```ts
type Point = { x: number; y: number; z: number };
const p: Point = {};
```

```text
error TS2739: Type '{}' is missing the following properties from type 'Point': x, y, z
```

两个字面量类型最容易混：`{}` 表示“任何非空值”，不是“空对象”。`const p: {} = 1` 是合法的。

## 多属性：TS2353

```ts
interface User { name: string }
const u: User = { name: "a", age: 1 };
```

```text
error TS2353: Object literal may only specify known properties, and 'age' does not exist in type 'User'.
```

这条只对对象字面量生效。先赋给变量再传就不报：

```ts
interface User { name: string }
const raw = { name: "a", age: 1 };
const u: User = raw;
```

原因是多余属性检查只做一层，赋值时类型已经放宽。想禁止这种情况，用 `exactOptionalPropertyTypes` 配合显式类型，或者干脆别让中间变量逃过检查。

## interface 合并冲突：TS2320 与 TS2430

两个父接口同名字段类型不同，`extends` 会报 `TS2320`：

```ts
interface A { x: string }
interface B { x: number }
interface C extends A, B {}
```

```text
error TS2320: Interface 'C' cannot simultaneously extend types 'A' and 'B'.
  Named property 'x' of types 'A' and 'B' are not identical.
```

子接口自己改父接口的字段类型，报 `TS2430`：

```ts
interface A { x: string }
interface C extends A { x: number }
```

```text
error TS2430: Interface 'C' incorrectly extends interface 'A'.
  Types of property 'x' are incompatible.
```

这两种报错都在说“接口的形状必须兼容父接口”。`type` 用交叉类型时不会报错，它会静默算出 `never`，更危险。

## 隐式 any：TS7006、TS7031、TS7053

参数没标注：`TS7006`。

```ts
function f(x) { return x; }
```

```text
error TS7006: Parameter 'x' implicitly has an 'any' type.
```

解构参数没标注：`TS7031`。

```ts
function g({ a }) { return a; }
```

```text
error TS7031: Binding element 'a' implicitly has an 'any' type.
```

用字符串索引对象：`TS7053`。

```ts
const o = { a: 1 };
const k = "b";
console.log(o[k]);
```

```text
error TS7053: Element implicitly has an 'any' type because expression of type '"b"'
  can't be used to index type '{ a: number; }'.
```

三个码都指向同一个开关 `noImplicitAny`，它是 `strict` 的一部分。修法是补注解，不是关开关。

`TS7053` 和 `TS18048` 不同。前者说索引本身不合法，后者说索引合法但结果可能是 `undefined`，需要 `noUncheckedIndexedAccess` 才会出现。

## 调用不匹配：TS2345、TS2554、TS2769

参数类型错：`TS2345`。

```ts
function f(x: number) {}
f("a");
```

```text
error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```

参数个数错：`TS2554`。

```ts
const t = new Date("2020-01-01");
t.getTime(1);
```

```text
error TS2554: Expected 0 arguments, but got 1.
```

重载全不匹配：`TS2769`。它会把每个重载的失败原因列出来，只看最后一条。

```ts
function f(a: string): void;
function f(a: number): void;
function f(a: string | number) {}
f(true);
```

```text
error TS2769: No overload matches this call.
  The last overload gave the following error.
    Argument of type 'boolean' is not assignable to parameter of type 'number'.
```

重载报错的信息量比 `TS2345` 大，优先看它。

## 空值与属性：TS18047、TS18048、TS2339

可能为 `null`：`TS18047`。

```ts
let o: { a: number } | null = null;
console.log(o.a);
```

```text
error TS18047: 'o' is possibly 'null'.
```

可能为 `undefined`：`TS18048`。

```ts
let s: string | undefined;
console.log(s.length);
```

```text
error TS18048: 's' is possibly 'undefined'.
```

属性真的不存在：`TS2339`。

```ts
const o = { a: 1 };
console.log(o.b);
```

```text
error TS2339: Property 'b' does not exist on type '{ a: number; }'.
```

这三种都先用收窄解决：`if (o !== null)`、`s?.length`、`"b" in o`。用 `!` 能消掉报错，但等于向编译器保证“不会是空”，保证错了就是运行时崩。

## 模块与配置：TS2307、TS2835、TS5102、TS5108、TS5112

找不到模块：`TS2307`。

```text
error TS2307: Cannot find module './nope' or its corresponding type declarations.
```

先确认路径拼写，再确认包是否带类型，最后看 `moduleResolution` 是否配对。

`nodenext` 下相对导入必须带扩展名，否则报 `TS2835`：

```text
error TS2835: Relative import paths need explicit file extensions in ECMAScript imports
  when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './a.js'?
```

注意提示里写的是 `.js`，不是 `.ts`。源码写 `./a.js`，指向的是 `a.ts`，这是 ESM 的规则。

配置项被移除时，报错直接给替代方案（见 [tsconfig 参考](https://www.typescriptlang.org/tsconfig)）：

```text
error TS5102: Option 'baseUrl' has been removed. Please remove it from your configuration.
error TS5108: Option 'moduleResolution=node10' has been removed. Please remove it from your configuration.
```

`baseUrl` 的替代是 `paths` 写成相对根路径：

```json
{
  "compilerOptions": {
    "paths": { "@/*": ["./src/*"] }
  }
}
```

命令行传文件时如果目录里有 `tsconfig.json`，报 `TS5112`：

```text
error TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline.
  Use '--ignoreConfig' to skip this error.
```

要么加 `--ignoreConfig`，要么用 `-p` 指定项目。

## 装饰器与可擦除语法：TS1241、TS1294

旧装饰器签名配新语义，报 `TS1241`：

```ts
function dec(target: any, key: string, desc: PropertyDescriptor) {}
class C { @dec m() {} }
```

```text
error TS1241: Unable to resolve signature of method decorator when called as an expression.
  The runtime will invoke the decorator with 2 arguments, but the decorator expects 3.
```

这条提示把根因写清楚了：运行时传 2 个参数 `(value, context)`，旧签名要 3 个。旧写法要开 `experimentalDecorators`，新写法改成两参数。

`erasableSyntaxOnly` 打开后用 `enum`，报 `TS1294`：

```text
error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
```

它拦的是所有会生成运行时代码的语法：`enum`、参数属性、带值的 `namespace`、`import x = require`。配合 Node 原生运行 TS 时建议打开，见第 33 章。

## 约束与深度：TS2344、TS2589

类型参数不满足约束：`TS2344`。

```ts
type Bad<T extends string> = T;
type Y = Bad<number>;
```

```text
error TS2344: Type 'number' does not satisfy the constraint 'string'.
```

它和 `TS2345` 是亲戚，一个在类型位置，一个在值位置。

递归过深：`TS2589`。

```ts
type U<T> = T extends any[] ? U<[...T, 0]> : never;
type X = U<[]>;
```

```text
error TS2589: Type instantiation is excessively deep and possibly infinite.
```

看到这个码，先把递归改成尾递归，再考虑加深度上限，最后一招是拆类型。具体手法见第 34 章。

## 抑制报错的两种写法

`@ts-ignore` 无条件忽略下一行。`@ts-expect-error` 只在下一行确实报错时忽略，没报错反而报 `TS2578`：

```ts
// @ts-expect-error
const ok: number = 1;
```

```text
error TS2578: Unused '@ts-expect-error' directive.
```

这个反向检查是它唯一比 `@ts-ignore` 强的地方：错误消失后，`@ts-expect-error` 会提醒你删掉它。

用法约定：

- `@ts-expect-error` 只出现在测试文件里，每处带一句原因。
- `@ts-ignore` 不进主干代码。
- `@ts-nocheck` 只用于迁移期的临时文件，并且登记在迁移清单里。
- 抑制注释必须有对应 issue 或 TODO，否则三个月后没人敢删。

## 定位流程

按顺序做，多数问题三步内能定位：

1. 看错误码，确定类别：赋值、调用、收窄、模块、配置。
2. 看 `A` 和 `B` 两个类型，`A` 是来源。
3. 加 `--noErrorTruncation` 展开长类型。
4. 把出错代码截成单文件复现：

```bash
$ tsc --noEmit --ignoreConfig case.ts
```

5. 报错消失就说明问题在上下文：`tsconfig`、全局声明、库版本。用注释法二分，一次注释一半。
6. 报 `Cannot find name 'process'` 这类，先看类型包：

```text
error TS2591: Cannot find name 'process'. Do you need to install type definitions for node?
  Try `npm i --save-dev @types/node` and then add 'node' to the types field in your tsconfig.
```

7. 确认版本：`npx tsc -v`。团队里版本不一致时，同一份代码在一台机器上过、另一台上不过，先对齐版本再查代码。

最后一条经验：报错信息在说“不兼容”，实际原因只有三种。类型写错了，值写错了，或者两边都写错了。不要为了消掉红波浪线去加 `any`，那是把定位成本推给三个月后的自己。

## 用不上的时候

### 报错出在配置或依赖

`TS2591`、`TS2835` 这类报错，改代码没有用，问题在 `types` 字段、`moduleResolution` 或依赖包版本。单文件复现消不掉，因为上下文就是原因。按错误码定位到配置文件，比逐行改代码快。

### 用 any 或抑制注释让报错消失

`@ts-ignore` 消掉一行，类型检查在那一行之后失去依据，后面报错的位置整体偏移。`@ts-expect-error` 在没报错时抛 `TS2578`，只提醒该删了，不解释原因。诊断的前提是保留原始报错。

### 报错不是赋值关系

`TS2344` 说类型参数不满足约束，`TS2589` 说实例化过深，它们不呈现为「A 不能赋给 B」。这时候先看约束声明和递归层数，套用赋值关系的读法会找错方向。
