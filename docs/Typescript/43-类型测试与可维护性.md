# 第 43 章 类型测试与可维护性

编译器只回答一个问题：这段代码在类型上能不能赋值。它不回答另一个问题：你期望的类型还在不在。类型被拓宽、被 `any` 吞掉、随版本改变结果，这三种情况都能编译通过。类型测试把“我以为的类型”写成断言，让 CI 替你盯着。

## 类型为什么会悄悄变宽

类型检查是单向判断。它检查手里的值能不能赋给标注的类型，能就通过。它不检查推断结果是不是预期之外的东西。后一种问题叫类型漂移，编译器没有意见，运行时也不一定立刻出错。

漂移有三个来源：推断失败后回落到默认值，`any` 沿着赋值链传播，以及推断规则本身把类型放宽。三者都不产生错误，只让后续检查失效。

漂移不改变运行时行为，只改变编译器对后续代码的判断。一个字段推断成 `any` 之后，下游所有基于它的检查都形同虚设。要发现这种问题，得把期望的类型写下来，再让编译器比对。

### 推断失败时回落到默认值

```ts
interface Profile {
  id: number;
  name: string;
}

interface Page<T = any> {
  items: T[];
}

export function titlesOf(page: Page): string[] {
  return page.items.map((item) => item.title);
}

export function loadProfile(text: string): Profile {
  return JSON.parse(text);
}

interface Emitter {
  on(handler: (event: { type: string }) => void): void;
}

const emitter: Emitter = {
  on(handler: (event: { type: string; code: number }) => void) {
    handler({ type: "ready", code: 0 });
  },
};

const loose = { id: "1", name: "n" };
export const profile = loose as unknown as Profile;
```

`Page` 的默认类型参数是 `any`。调用方写 `Page` 而不给实参，`T` 直接取默认值，`titlesOf` 里每个 `item` 都是 `any`，`item.title` 不检查，属性拼错不检查，缺字段也不检查。

默认值本来是给“推断不出来也要能用”留的后路。公开类型里用它，等于留给调用方一个关掉检查的开关。要禁止这种回退，就不写默认值，让调用方必须显式给实参。

兜底类型出现在很多位置：函数默认参数、可选属性、索引签名的返回值。凡是“可以先不写”的地方都有默认行为，默认越宽，漂移空间越大。

类型参数默认值最容易出事。`Page<T = any>` 让 `Page` 可以不带实参使用，`Page<Article>` 也可以。前者安静地走 `any`，后者才受检查。同一个类型名有两种使用方式，代码评审时很难看出差别。

### any 从别的接口流进来

上面那段还有三条通道。`JSON.parse` 的返回类型是 `any`，`any` 可以赋给任何类型，`loadProfile` 的返回标注拦不住它。`emitter.on` 的参数写错了方向，照样能赋值，因为方法简写的参数按双变检查，`strictFunctionTypes` 只管属性风格的函数类型。`as unknown as` 不检查任何关系，写什么类型都成立。

三条通道都通过了检查，`profile.name` 在类型上是 `string`，运行时可能是 `null`。下一层调用出错时，错误现场已经离源头很远。

编译器没有失职。它的规则是“能赋值就通过”，`any` 和双变都在规则允许范围内。代价是类型承诺变空，而这正是类型测试要补的位置。

`noImplicitAny` 只拦“没有注解的变量和参数”，拦不住 `any` 从别的接口流进来。前者是语法检查，后者是类型关系，两个机制管的事不同。

### 字面量放宽

```ts
const preset = { mode: "strict" };

function applyMode(mode: "strict" | "loose") {}

// error TS2345: Argument of type 'string' is not assignable to parameter of type '"loose" | "strict"'.
// applyMode(preset.mode);

const fixed = { mode: "strict" } as const;
applyMode(fixed.mode);
```

对象字面量赋给 `const` 时，属性类型仍然拓宽成 `string`，不是 `"strict"`。放宽是关键字的默认行为，不是 bug。`as const` 只对当前这个字面量生效，把 `mode` 收窄回字面量类型，`applyMode` 才通过。

读代码的人常把“值现在是 strict”当成“类型是 strict”，改一次赋值就露馅。

### 全绿也不代表类型没坏

```bash
$ npx tsc --noEmit --strict src/widen.ts
$ echo $?
0
```

上面这些写法放进同一个文件，`--strict` 下也没有一条错误。类型坏掉不会在构建里留下痕迹，只有断言能发现。

断言要放在公开边界上才有用。内部工具函数的类型随便改，没人依赖；导出的函数、包入口的类型一旦漂移，使用方全线受影响。

## 三行断言库

### Equal 与 Expect

```ts
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;

type Expect<T extends true> = T;
```

`Equal` 不直接比较 `A` 和 `B`，它构造两个泛型函数类型再比较可赋值性。两个函数类型互为子类型，要求返回类型对任意 `T` 都一致，也就是 `T extends A ? 1 : 2` 与 `T extends B ? 1 : 2` 结构相同。`A` 与 `B` 只要差一点，就存在让两边结果不同的 `T`，返回 `false`。

为什么不用 “`A` 能赋给 `B` 且 `B` 能赋给 `A`” 双向判断？双向可赋值比相等松。`{ a: 1 }` 与 `{ a: 1; b?: undefined }` 互相能赋值，但类型并不同，前者没有 `b` 这个键。函数签名比较能把这种差异纳入：`T` 取 `{ a: 1; b?: undefined }` 时，左边分支返回 `2`，右边返回 `1`，可赋值性不成立。

这把比较收紧到结构等价。`readonly` 修饰、可选标记、`undefined` 的显式与隐式写法都会被算进去。两个类型只要能互相赋值，就有一批成员差异被放过；函数签名比较把这类差异变成可判定的返回值。

`Expect<T extends true>` 把断言变成一条约束。传 `false` 就报错：

```ts
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

// error TS2344: Type 'false' does not satisfy the constraint 'true'.
// type Bad = Expect<Equal<string, number>>;

// error TS2322: Type 'true' is not assignable to type 'false'.
// const bad2: Equal<string, number> = true;

const ok: Expect<Equal<"a", "a">> = true;
```

两种写法的信息量不同。`Expect` 的报错带“约束”字样，指向断言库；赋值写法只有 `TS2322`，日志更短。团队统一一种即可，不要在同一个仓库里混用。

### 为什么比较要包一层元组

先看直接写的版本：

```ts
type EqualRaw<A, B> = A extends B ? (B extends A ? true : false) : false;
type EqualTuple<A, B> = [A] extends [B] ? ([B] extends [A] ? true : false) : false;

const raw: EqualRaw<"a" | "b", "a" | "b"> = false;
const tuple: EqualTuple<"a" | "b", "a" | "b"> = true;

type IsNever<T> = [T] extends [never] ? true : false;
type IsAny<T> = 0 extends 1 & T ? true : false;
type NotAny<T> = IsAny<T> extends true ? false : true;

type A = IsNever<never>;
type B = IsNever<never | string>;
type C = IsAny<any>;
type D = NotAny<string>;
```

两个相等的联合，在 `EqualRaw` 下得到 `false`。原因在条件类型的分配律：写在裸类型参数上的条件类型，参数是联合就按成员分发。`A` 先拆成 `"a"` 和 `"b"` 分别比较，两次都返回 `false`，结果合并成 `false`。

`[A] extends [B]` 把 `A` 装进元组。元组是单个类型，左侧不再是裸参数，分配关掉，于是整体比较。`IsNever` 必须用同样的写法：`never` 在裸位置当条件类型的检查对象时会立刻坍塌，`T extends never ? 1 : 2` 对 `never` 直接返回 `never`，拿不到 `true`。包一层元组才能先拿到这个类型本身。

`IsAny` 用的是交叉类型规则。`1 & T` 在 `T = any` 时是 `any`，`0 extends any` 成立。`T = unknown` 时 `1 & unknown` 是 `1`，`0 extends 1` 不成立。这一步利用的是 `any` 与任何类型求交叉都得到 `any`。

### 这套写法能区分什么

函数签名版 `Equal` 的实测结果：

| 比较对 | 结果 | 说明 |
|---|---|---|
| `any` 与 `string` | `false` | 能区分 `any` |
| `any` 与 `any` | `true` | 同一类型，必然相等 |
| `{ a?: 1 }` 与 `{ a: 1 \| undefined }` | `false` | 可选属性与显式 `undefined` 不同 |
| `{ a: 1 }` 与 `{ a: 1; b?: undefined }` | `false` | 多出的可选属性也算差异 |
| `{ a: 1 }` 与 `{ readonly a: 1 }` | `false` | `readonly` 参与比较 |
| `unknown` 与 `any` | `false` | 两者不等价 |
| `true` 与 `boolean` | `false` | 字面量与放宽后的类型不同 |

`Equal<any, any>` 仍然返回 `true`，两个 `any` 确实是同一类型。要表达“这个位置不许是 `any`”，用 `NotAny` 单独判断。把 `Equal`、`Expect`、`NotAny`、`IsNever` 放进一个 `assert.ts`，加起来不到 10 行，够用了。

### 断言也要分层

对公开 API 断言完整类型，对内部工具断言关键字段。完整断言一改就红，维护成本高；只断言关键字段又会漏掉新增的可选属性。折中的做法是对导出函数的返回类型做完整断言，对中间类型只断言用到的成员。

断言失败的位置跟写法有关。`Expect` 报在使用处，`Equal` 的赋值写法报在冒号后面。CI 日志里看到 `TS2344` 就去对应断言行，看到 `TS2322` 先看是不是把断言写成了赋值。

## 现成工具

### expect-type

```bash
$ npm i -D expect-type
$ npx tsc --noEmit --strict src/client.test-d.ts
$ echo $?
0
```

```ts
import { expectTypeOf } from "expect-type";
import { createClient } from "./client";

expectTypeOf(createClient).returns.toEqualTypeOf<string[]>();
expectTypeOf(createClient).parameter(0).toEqualTypeOf<{
  retries: number;
  baseDelayMs: number;
}>();
```

断言失败时，[expect-type](https://github.com/mmkal/expect-type) 在类型层面制造一个不可调用的表达式，报 `TS2349`：

```bash
$ npx tsc --noEmit --strict src/client-fail.test-d.ts
src/client-fail.test-d.ts(3,36): error TS2349: This expression is not callable.
  Type 'ExpectNumber<string[]>' has no call signatures.
```

`client-fail.test-d.ts` 是把第二条断言换成 `.returns.toBeNumber()` 的版本。错误信息不好读，位置是准的，第 3 行 36 列就是写错的那条断言。原理是把比较结果映射成带品牌名的函数类型：匹配时映射到可调用签名，不匹配时映射到不可调用签名，错误落在“调用”这一步。品牌名会出现在错误信息里，`ExpectNumber` 说明断言期望 `number`，实际拿到 `string[]`。

日常用法按调用点断言：`parameter(i)` 检查第几个参数，`returns` 检查返回类型，`toMatchTypeOf` 允许子类型。断言写到多细由你定，库不强制。

运行时什么也不做。`tsc` 把调用原样输出到 JS，`expect-type` 的运行时代码是空函数：

```bash
$ npx tsc --target es2022 --module esnext --outDir emit src/noop.ts
$ node emit/noop.js
$ echo $?
0
$ npm view vitest@5.1.1 dependencies --json | grep expect-type
    "expect-type": "^1.4.0",
```

`vitest` 里的 `expectTypeOf` 就是它，依赖里装着同一个包。项目里装了 `vitest`，类型断言不必再装一个。

### tsd

[tsd](https://github.com/tsdjs/tsd) 是更早的工具，断言写成函数调用，用独立命令跑。先把包的入口类型指清楚：

```json
{
  "types": "dist/index.d.ts",
  "tsd": {
    "directory": "test-d",
    "compilerOptions": {
      "strict": true,
      "target": "es2022",
      "module": "esnext",
      "moduleResolution": "bundler"
    }
  }
}
```

```ts
import { expectType, expectError } from "tsd";
import { createClient } from "../src/client";

expectType<string[]>(createClient({ retries: 2, baseDelayMs: 50 }));
// 这一行故意类型不通过，tsd 期望它报错
expectError(createClient({ retries: "2", baseDelayMs: 50 }));
```

断言失败时的输出：

```bash
$ npx tsd
  test-d/fail.test-d.ts:4:21
  ✖  4:21  Argument of type string[] is not assignable to parameter of type number[].
  Type string is not assignable to type number.
  ✖  5:0   Expected an error, but found none.

  2 errors
$ node -e "console.log(require('./node_modules/@tsd/typescript/package.json').version)"
5.9.3
```

`expectError` 里代码不报错时，会单独列出“Expected an error, but found none.”，这条信息比 `@ts-expect-error` 清楚。

`tsd` 的断言文件不能交给普通 `tsc` 检查。`expectError` 里那行本来就该报错，`tsd` 自己收集诊断再比对行号，这类文件只由 `tsd` 命令跑。

`tsd` 有一个容易忽略的问题：它不读项目里的 `typescript`，自带一份。0.33.0 依赖 `@tsd/typescript ^5.9.2`，实际装的是 5.9.3。项目用 TypeScript 7.0.2，`tsd` 用 5.9.3，两版之间行为有差异时 `tsd` 会漏掉。类型测试要在和目标编译器一致的版本上跑，`tsd` 不适合当唯一关卡。

除了 `expectType` 和 `expectError`，`tsd` 还有 `expectAssignable`、`expectNotAssignable`、`expectDeprecated`。前两个比 `expectType` 松，允许子类型通过，适合断言“能传进去”，而不是“类型完全相同”。

### 放进 CI

用一个单独的 `tsconfig.types.json` 收类型测试。它不开 `emit`，只检查：

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "esnext",
    "moduleResolution": "bundler",
    "noEmit": true,
    "skipLibCheck": true
  },
  "include": ["src/**/*.ts"]
}
```

`include` 把源码一起收进来，断言才能拿到真实的导出类型。`noEmit` 让这一步只做检查，命令是 `npx tsc -p tsconfig.types.json`，断言失败时非零退出，CI 不需要额外插件。

`skipLibCheck` 建议开着。第三方声明文件里的错误不该由你的 CI 负责，关掉只会让日志变长。

## 类型测试放哪、测什么

### 放哪

和源码同目录，命名 `*.test-d.ts`。放在一起的好处是改源码时同屏能看到断言，`import` 路径最短。单独放 `test-d/` 也可以，`tsd` 默认扫这个目录。

断言文件也要写注释。一条 `Expect<Equal<A, B>>` 看不出意图，旁边补一句“返回类型不能被拓宽成 any”，半年后接手的人才知道这条断言在防什么。

不要混进运行时测试文件。`vitest` 的 `expectTypeOf` 虽然能写在普通测试里，但运行时测试一旦被跳过或过滤，类型断言也跟着不跑。类型检查走 `tsc`，运行时断言走测试框架，两条路分开。

文件后缀 `.test-d.ts` 不是约定俗成的装饰。它让 `tsconfig.types.json` 和运行时测试的 `include` 可以各自收文件，两个检查互不干扰。

仓库有多个包时，每个包各建一份 `tsconfig.types.json`。`include` 只收本包源码，`references` 指向依赖包，`tsc -b` 按依赖顺序检查。不要在根目录放一份收全仓的配置，改一个包会触发全仓检查。

### 测什么

按收益排，从高到低：

1. 导出的函数返回类型。签名改动会让调用方全线报错，先锁住。
2. 字面量要不要保持。`const` 推断、`as const`、`satisfies` 的效果，换个人改就丢。
3. 错误输入必须报错。用 `@ts-expect-error` 或 `expectError` 锁住校验逻辑。
4. 联合类型的分发行为。`Extract`、`Exclude`、条件类型的结果。
5. `any` 不能出现在公开位置。用 `NotAny` 卡住。

覆盖前三条，能拦住绝大多数漂移。后两条按项目的类型复杂度决定，纯业务代码常常用不到。

### 一个能拦住的例子

```ts
export interface Article {
  slug: string;
  title: string;
}

export interface Page<T = any> {
  items: T[];
}

export function itemsOf(page: Page) {
  return page.items;
}
```

```ts
import type { Equal, Expect, NotAny } from "./assert";
import type { Article, itemsOf } from "./page";

type Item = ReturnType<typeof itemsOf>[number];
type _NotAny = Expect<NotAny<Item>>;
type _Exact = Expect<Equal<Item, Article>>;
```

不写测试文件时，`itemsOf` 的返回类型是 `any[]`，编译通过。加上测试文件后，两条断言都红：

```bash
$ npx tsc -p tsconfig.json
$ echo $?
0
$ npx tsc -p tsconfig.json
src/page.test-d.ts(5,23): error TS2344: Type 'false' does not satisfy the constraint 'true'.
src/page.test-d.ts(6,22): error TS2344: Type 'false' does not satisfy the constraint 'true'.
```

第一条命令跑在没有测试文件的版本上，第二条加上测试文件后重跑。把 `itemsOf` 的参数改成 `Page<Article>`，测试立刻变绿。改动只有一处，错误来自断言，不来自业务代码。

类型测试的价值在这里：没人调用错的时候，它也能发现问题。

## @ts-expect-error

`@ts-expect-error` 的意思是“下一行必须报错”。它断言错误存在，不断言代码正确：

```ts
import { createClient } from "./client";

// @ts-expect-error retries 只接受 number
createClient({ retries: "3", baseDelayMs: 100 });

// @ts-ignore 没检查，写错了也沉默
// @ts-ignore
const total: number = "not a number";

// @ts-expect-error 只要求这一行有错，不关心错的是哪条
const broken: number = "not a number" + undefinedName;
```

第三段里有两个错误：类型不匹配，还有未定义的名字。断言照样通过，因为确实报错了。想把错误钉死到某一条，用 `expectError` 包住整段表达式，或者断言具体的错误行。

断言存在还不够，错误原因也要对。一行写错导致 `TS2304`，把测试从“校验逻辑生效”变成了“名字拼错”，两个原因混在一起，断言就失去意义。

`@ts-ignore` 没有“必须报错”这条检查。下一行有错没错都通过，写错了也没人知道。两者的区别不在抑制错误这个动作上，而在失败模式：`@ts-expect-error` 会在错误消失时提醒你，`@ts-ignore` 只会一直沉默。

下一行没有错误时，编译器报 `TS2578`：

```bash
$ cat > unused-expect.ts <<'EOF'
// @ts-expect-error 这行没有错误
const text = "abc";
EOF
$ npx tsc --noEmit --strict unused-expect.ts
unused-expect.ts(1,1): error TS2578: Unused '@ts-expect-error' directive.
```

`eslint` 的 `@typescript-eslint/ban-ts-comment` 可以强制加说明，也能限制 `@ts-ignore`。CI 里打开它，比口头约定可靠。

断言的位置也有讲究。紧贴出错的上一行，中间不留空行，`@ts-expect-error` 只管下一行。写成块注释 `/* @ts-expect-error */` 不是有效指令，编译器会忽略它。

## 度量一次改动

### 四个数字

`--extendedDiagnostics` 在编译结束时打印指标。改类型前跑一次，改完再跑一次：

```bash
$ npx tsc --noEmit --strict --target es2022 --extendedDiagnostics src/paths-prefix.ts

Instantiations: 126086
Memory used:    69419K
Check time:     0.118s
$ npx tsc --noEmit --strict --target es2022 --extendedDiagnostics src/paths-join.ts
Types:           41596
Instantiations:  30448
Memory used:    63283K
Check time:     0.116s
```

`Instantiations` 从 126086 降到 30448。原因在类型参数：带前缀参数的版本里，每个节点都用不同的 `Prefix` 实例化一次，6 个键、4 层的树产生上千种参数组合；改成只递归节点类型后，`L0` 到 `L4` 是同一批具名类型，相同参数的实例化会被复用。

四个指标看什么：

| 指标 | 含义 | 什么时候警惕 |
|---|---|---|
| `Instantiations` | 泛型实例化次数 | 几万正常，超过二十万要查 |
| `Types` | 创建的类型对象总数 | 超过十万说明展开过多 |
| `Memory used` | 堆内存峰值 | 接近上限时先查深度递归 |
| `Check time` | 类型检查耗时 | 单文件超过 1 秒要看 |

`Memory used` 和 `Check time` 每次运行有波动，`Types` 与 `Instantiations` 稳定。`Types` 与 `Instantiations` 的稳定也来自缓存：同一份代码重复编译，缓存命中路径不变，计数就不变。比较时用稳定项下结论，波动项多看几个样本。

指标还随 `lib` 和编译器版本变化，比较只能在同版本、同 `target`、同 `lib` 下做。升级后数字整体变大，先确认原因，再判断是不是代码问题。

诊断输出的完整读法在第 34 章，这里只用它做前后对比。

### 差异小的时候不要下结论

同一组对照也有失效的时候。把 40 元组反转，非尾递归和累加器版本各编一次：

```bash
$ npx tsc --noEmit --strict --target es2022 --extendedDiagnostics src/rev-naive.ts
Instantiations:  29708
$ npx tsc --noEmit --strict --target es2022 --extendedDiagnostics src/rev-acc.ts
Instantiations:  29657
```

差 51 次，属于噪声。编译器对相同参数的实例化做缓存，教科书里的“尾递归更快”在小输入上体现不出来。判断标准是改动前后各跑三次，差异小于 5% 就不算改善。拿着一个数字宣布优化成功，容易改错方向。

### trace 产物里看什么

`--generateTrace` 输出时间线，适合定位“哪一类检查慢”：

```bash
$ npx tsc --noEmit --strict --target es2022 --generateTrace trace src/paths-prefix.ts
$ ls trace
legend.json  trace.json  types_0.json  types_1.json  types_2.json  types_3.json
```

文件分工：

- `trace.json` 是事件流，Chrome Trace 格式。可以拖进 `chrome://tracing`，也可以直接读 JSON。
- `types_N.json` 按检查器分文件，记录每个类型对象的来源。
- `legend.json` 把 `checkerId` 映射到文件名，同时给出 `tracePath`。

`sources_N.json` 里存源文件区间，和 `types_N.json` 用编号互相关联。查到慢的类型之后，按编号回溯到声明位置，才能知道是哪个写法引起的。

`trace.json` 里每个事件有 `name`、`cat`、`ph`、`ts`、`args`。`ph` 为 `B` 和 `E` 的事件成对出现，表示一段区间的开始和结束；`ph` 为 `X` 的事件自带 `dur`。有用的字段都在 `args` 里：`path` 是文件，`checkerId` 是检查器编号，`sourceId` 和 `targetId` 是类型编号，按编号去 `types_N.json` 里查。

`checkSourceFile` 套着 `checkSourceFile` 的递归调用，所以按 `B`、`E` 配对算出的时长包含子区间，不能横向相加。看总耗时就取最外层那一条，看热点才拆进子区间。

事件数量随文件规模增长。本例 524 条，几万行的项目能到几十万条，聚合脚本要按 `args.path` 过滤，只留自己的源码。trace 文件也不要每次构建都生成，定位一次就够。

用 Node 聚合各阶段耗时：

```js
import { readFileSync } from "node:fs";

const events = JSON.parse(readFileSync("trace/trace.json", "utf8"));
const stack = new Map();
const total = new Map();

for (const event of events) {
  if (event.ph === "B") {
    if (!stack.has(event.tid)) stack.set(event.tid, []);
    stack.get(event.tid).push(event);
  } else if (event.ph === "E") {
    const start = stack.get(event.tid)?.pop();
    if (!start) continue;
    total.set(start.name, (total.get(start.name) ?? 0) + (event.ts - start.ts));
  } else if (event.ph === "X" && event.dur) {
    total.set(event.name, (total.get(event.name) ?? 0) + event.dur);
  }
}

const rows = [...total].sort((a, b) => b[1] - a[1]).slice(0, 8);
for (const [name, micro] of rows) {
  console.log(name.padEnd(24), (micro / 1000).toFixed(1), "ms");
}
```

实测输出：

```text
checkSourceFile           199.1 ms
checkSourceFiles          134.6 ms
structuredTypeRelatedTo    83.0 ms
createSourceFile           31.2 ms
bindSourceFile             15.2 ms
createProgram              14.7 ms
processRootFiles           14.6 ms
findSourceFile             14.2 ms

按文件聚合：

lib.dom.d.ts              151.5 ms
paths-prefix.ts            46.5 ms
lib.es5.d.ts                9.7 ms
lib.es2015.core.d.ts        3.9 ms
lib.es2020.bigint.d.ts      3.3 ms
lib.es2022.intl.d.ts        2.3 ms
```

库文件占了大头。`lib.dom.d.ts` 的 151.5 毫秒和你的代码无关，看 trace 时先按路径过滤，只看自己的文件。`structuredTypeRelatedTo` 是类型关系判断，占 83 毫秒，说明这个文件的类型比较是主要工作。

`types_N.json` 里一条记录长这样：

```json
{
  "id": 249,
  "symbolName": "Record",
  "aliasTypeArguments": [250, 251],
  "firstDeclaration": {
    "path": ".../lib.es5.d.ts",
    "start": { "line": 1611, "character": 1 }
  },
  "flags": ["Object"]
}
```

`symbolName` 和 `firstDeclaration` 说明这个类型是什么、在哪声明；`aliasTypeArguments`、`instantiatedType`、`unionTypes` 是指向其他记录的编号，顺着编号能还原出类型怎么被实例化。本例的 `types_1.json` 有 26641 条记录。

trace 只在定位阶段用。一次编译多出几十兆文件，别提交进仓库，也别放进日常构建。需要反复对比时，把产物放临时目录，用完就删。

## isolatedDeclarations

### 原理

生成 `.d.ts` 需要知道每个导出符号的完整类型。普通 `tsc` 能看整个程序，遇到没写返回类型的函数，就从函数体推断，推断过程依赖其他文件的类型信息。

`--isolatedDeclarations` 把要求反过来：每个文件的声明必须只靠当前文件就能生成。单文件工具（esbuild、swc）可以并行生成声明，不必等类型检查器跑完整个项目。代价是任何依赖推断的写法都要补注解。

从编译流程看，声明生成发生在检查之后，要给每个导出符号打印一段类型文本。打印需要完整类型，而完整类型可能来自别的文件。限制的含义是：不进入跨文件检查，也能把这段文本写出来。

这个限制可以反过来用。`--isolatedDeclarations` 报错的地方，就是声明输出依赖推断的地方。代码不动，只打开这个选项，就能列出所有“类型靠猜”的导出。

单独开这个选项会先报配置错：

```bash
$ npx tsc --noEmit --isolatedDeclarations iso/pick.ts
error TS5069: Option 'isolatedDeclarations' cannot be specified without specifying option 'declaration' or option 'composite'.
```

加上 `declaration` 后再跑：

```ts
export function pick<T>(value: T, flag: boolean) {
  return flag ? value : null;
}

export const defaults = { retries: 3, timeout: 1000 };

function makeId(): string {
  return "id";
}

export const id = makeId();
```

```bash
$ npx tsc --noEmit --declaration --isolatedDeclarations iso/pick.ts
iso/pick.ts(2,10): error TS9013: Expression type can't be inferred with --isolatedDeclarations.
iso/pick.ts(11,14): error TS9010: Variable must have an explicit type annotation with --isolatedDeclarations.
```

`pick` 的返回类型是 `T | null`，要判断条件表达式的两个分支，`isolatedDeclarations` 的检查流程不做这件事。`id` 的类型来自 `makeId` 的调用结果，属于跨表达式推断。`defaults` 没有报错，对象字面量的结构直接写在当前文件里。

不同写法报不同错误码：

```ts
export function wrap<T>(value: T) {
  return { value };
}

export class Loader {
  async load() {
    return { ok: true };
  }
}

const key = "name";
export const record = { [key]: 1 };
```

```bash
$ npx tsc --noEmit --declaration --isolatedDeclarations iso/wrap.ts
iso/wrap.ts(2,12): error TS9016: Objects that contain shorthand properties can't be inferred with --isolatedDeclarations.
iso/wrap.ts(6,9): error TS9008: Method must have an explicit return type annotation with --isolatedDeclarations.
iso/wrap.ts(12,25): error TS9038: Computed property names on class or object literals cannot be inferred with --isolatedDeclarations.
```

按语句形态记错误码：变量声明是 `TS9010`，函数返回表达式是 `TS9013`，简写属性是 `TS9016`，类方法是 `TS9008`，计算属性名是 `TS9038`。迁移时按错误码分批修。至于内部怎么判定“能不能本地推断”，官方文档只给规则，不给实现；推测是走了一套只依赖当前文件符号表的简化推导。该选项在 [TypeScript 5.5 发布说明](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html) 中引入。

### 修法

```ts
export function pick<T>(value: T, flag: boolean): T | null {
  return flag ? value : null;
}

export const defaults = { retries: 3, timeout: 1000 };

export function wrap<T>(value: T): { value: T } {
  return { value };
}

export class Loader {
  async load(): Promise<{ ok: boolean }> {
    return { ok: true };
  }
}
```

生成的声明和普通模式一致：

```text
export declare function pick<T>(value: T, flag: boolean): T | null;
export declare const defaults: {
    retries: number;
    timeout: number;
};
export declare function wrap<T>(value: T): {
    value: T;
};
export declare class Loader {
    load(): Promise<{
        ok: boolean;
    }>;
}
```

标注要等于推断结果，不能只是能赋值。`export const n: number = 1 + 2` 能过检查，但声明文件里丢了字面量 `3`。使用方本来能拿到精确类型，现在只能拿到 `number`。改注解时把推断结果复制过来，别手写一个更宽的类型。

### 对谁有意义

库作者值得开。声明文件和 JS 能并行产出，发布流程可以拆成两步：先出类型，再出代码。CI 里加一条 `tsc --isolatedDeclarations`，能防止回归到依赖推断的写法。

配合 API 报告工具使用时，这个选项还有一个副作用：声明文件稳定，工具的差异输出就少噪声。类型文本每次构建都变，评审时很难看出真正的 API 变化。

应用项目不一定值得。业务代码不需要发布 `.d.ts`，开了这个选项只增加注解量。第 35 章讲发布流程时用了这个选项，那里针对的是库。

## 版本兼容锁

类型测试的另一个用途是挡版本变化。升级编译器时，类型行为可能变，运行时不变。

### 默认值会变

TypeScript 6.0 把 `strict` 改成默认开启。7.0.2 不传 `--strict` 也是严格模式：

```bash
$ npx tsc --noEmit src/implicit.ts
src/implicit.ts(1,24): error TS7006: Parameter 'value' implicitly has an 'any' type.
$ npx tsc --noEmit --strict false src/implicit.ts
$ echo $?
0
```

同一份代码，升级前后结论不同。项目里的 `tsconfig.json` 如果没显式写 `"strict": true`，升级时会突然多出一批错误。这不是代码退步，是默认值变了。

默认值变化还涉及 `module`、`target`、`types` 三项，改动清单在第 39 章。升级前先看那一章的对照表，比逐条试错快。

锁版本不等于锁死大版本。库的 `peerDependencies` 写 `typescript: ">=5.9"` 时，使用方可能装 5.9 或 7.0，两个版本的行为都要能跑。类型断言就是验证这件事的手段。

### 类型语义也会变

7.0 把模板字面量类型按 Unicode code point 切分，5.9 按 UTF-16 code unit 切分。同一个类型在两版下结果不同：

```ts
type Chars<S extends string> = S extends `${infer C}${infer R}`
  ? [C, ...Chars<R>]
  : [];

type Emoji = Chars<"😀">;

// 写法 A：按 Unicode code point 切分
const byPoint: Emoji = ["😀"];

// 写法 B：按 UTF-16 code unit 切分
// error TS2322: Type '"\uD83D"' is not assignable to type '"😀"'.
// const byUnit: Emoji = ["\ud83d", "\ude00"];
```

```bash
$ npx tsc --noEmit --strict --target es2022 src/chars.ts
$ echo $?
0
$ npx tsc --noEmit --strict --target es2022 src/chars.ts
src/chars.ts(11,24): error TS2322: Type '"\uD83D"' is not assignable to type '"😀"'.
```

第一条命令只含写法 A，7.0.2 下通过；把写法 B 的注释打开，同一份文件报错。

换成 5.9.3，结论反过来：写法 B 通过，写法 A 报错。

```bash
$ npx tsc --noEmit --strict --target es2022 src/chars.ts
src/chars.ts(8,25): error TS2322: Type '"😀"' is not assignable to type '"�"'.
```

这种变化不会在任何运行时测试里出现，只有类型层断言能发现。升级期间可以两版并行跑断言，把结果并排看，差异就是需要人工判断的地方。

### 用断言锁住

把期望结果写成断言：

```ts
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

type Chars<S extends string> = S extends `${infer C}${infer R}` ? [C, ...Chars<R>] : [];

// 把编译器对 emoji 的切分方式锁成契约
type Observed = Chars<"😀">;
type _Lock = Expect<Equal<Observed, ["😀"]>>;
```

```bash
$ npx tsc --noEmit --strict --target es2022 src/chars.test-d.ts
$ echo $?
0
$ npx tsc --noEmit --strict --target es2022 src/chars.test-d.ts
src/chars.test-d.ts(9,21): error TS2344: Type 'false' does not satisfy the constraint 'true'.
```

第一条命令是 7.0.2 下通过，第二条是 5.9.3 下的结果。这条断言就是版本锁：升级到不兼容版本时，CI 在具体位置告诉你哪条行为变了，不用翻 release notes 猜。

版本锁不是把所有类型都断言一遍。只锁公开契约和已知会随版本变化的行为：字面量切分、推断放宽的边界、`Partial` 之类的内置工具类型行为。

### 升级 checklist

1. 固定编译器版本。CI 和本地用同一个 `typescript`，不用 `npx tsc` 取最新。
2. 升级前给公开类型加断言，覆盖返回类型、字面量、错误输入三类。
3. 在旧版本上跑一遍，确认断言全绿。红的说明断言写错了，先修断言。
4. 升级后先跑 `tsc --noEmit`，把类型错误和配置错误分开处理。配置错误看第 39 章的弃用清单。
5. 类型断言失败的地方逐个判断：行为变好就更新断言，变坏就改实现。
6. 断言通过但数字变差的（`Instantiations`、`Check time`），记一条基线，别在同一版里顺手优化。
7. 类型测试工具也要看版本。`tsd` 自带 5.9.3，锁不住 7.0 的变化。

## 该删的体操

类型体操的成本不在首次实现，在后续维护。读一行类型要几分钟，改一处要重跑全链，成本会随嵌套层数上涨。

类型层的努力有上限。以下三种情况，类型写得再复杂也解决不了问题，该换成运行时校验或代码生成。判断的起点是问一句：这条类型要保护的行为，能不能用一行断言写出来。

### 判据一：数据来自系统外部

网络响应、文件内容、环境变量、用户输入，这些值在编译期不可知。类型只能描述“预期长什么样”，校验必须在运行时做。

```ts
import { z } from "zod";

const ArticleSchema = z.object({ slug: z.string(), title: z.string() });
type Article = z.infer<typeof ArticleSchema>;

export function parseArticle(input: unknown): Article {
  return ArticleSchema.parse(input);
}
```

类型从 schema 推导出来，只有一份定义。解析失败时抛错，边界之外的类型都是真的。想用类型体操把 `unknown` 变成 `Article`，写不出来。

### 判据二：同一个类型有三种写法还在猜

一个类型用条件类型、映射类型、重载各写了一版，还在比较哪个推断更准，说明需求本身没定清。这时换显式表：

```ts
const routes = {
  home: { path: "/", auth: false },
  settings: { path: "/settings", auth: true },
} as const satisfies Record<string, { path: `/${string}`; auth: boolean }>;

type RouteName = keyof typeof routes;
```

表可以读、可以测、可以用代码生成。条件类型嵌套三层之后，改一个字段要重新理解整条链路。

### 判据三：写完类型测试也说不清它保护什么

断言写不出来，或者要写 200 行辅助类型才能表达“这个类型是对的”，说明这个类型超出了团队能维护的范围。删掉它，换宽一点的类型加运行时校验，维护成本立刻下降。

判断方法是问一句：这条断言失败时，我知道该改哪里吗？答不上来，断言就没起到锁的作用。

删类型也有顺序。先把断言改成对运行时行为的测试，再删类型，中间留一次提交，出问题能回退。直接删类型再补测试，容易把已经工作的情况一起改坏。

### 保留边界

有一类类型体操值得留：把运行时的约定搬进类型，让错误在编译期暴露。品牌类型、可辨识联合、`satisfies` 校验常量表，这些都有明确的失败场景，测试也写得出。

区分标准是能不能写出一条断言。能写，说明行为可描述；不能写，说明行为只在脑子里。

品牌类型是典型的可测约定：`type UserId = string & { __brand: "UserId" }`，误把普通字符串传进去会报 `TS2322`，断言只写一行。

下一次改公开类型前，先加一条断言，再改实现。顺序反了，改动对不对就只能靠跑测试猜。

## 用不上的时候

### 项目还没有公开类型

类型只在内部流转，改错了编辑器立刻标红。这时写断言只是把一次检查做两遍。断言的价值在类型被多人、多个包引用之后才出现。

### 类型已经稳定

一个模块两年没改过公开签名，补断言等于增加维护成本。等下一次要改签名之前再补，补完改，改完跑。

### 团队没有 CI 关卡

断言要跑在 CI 上才有意义。没有那道关卡时，`tsc --noEmit` 都跑不全，断言只能留在本地，挡不住别人改坏。
