# 第 34 章 类型性能与调试

`tsc` 从 0.9 秒涨到 11 秒，删掉一批类型之后数字没动。类型检查的耗时由输入规模和展开深度共同决定，先量出哪一项超标再改。这一章讲费时的四类写法、两层递归上限和诊断输出的读法。

一个把元组倒过来的递归类型，48 个元素的元组能编译，49 个就报 TS2589。类型检查有硬上限，超过之后不是警告，是错误。这一章讲三件事：哪些写法费时、上限在哪里、怎么定位并降低开销。

类型检查的速度由两件事决定：输入规模多大，展开多深。输入规模是文件行数和符号数，改不动；展开深度由类型写法决定，可以改。调优的第一步不是删代码，是量出哪一项超标。

## 费时的四类写法

类型检查的开销主要来自展开和实例化。四类写法最容易把开销推到上限。

先确认是不是真的慢。中型项目全量检查在一秒到三秒之间是正常的，超过五秒再调。冷启动、无缓存、`skipLibCheck: false` 都会让数字变大，这些不是类型写法的问题。

交叉类型在每次成员访问时都要合并属性。交叉层数少时没感觉，几十层叠在一起、再取 `keyof`，tsc 需要遍历所有成员。

交叉类型没有名字，不会被缓存。每次访问成员，tsc 都把参与交叉的成员列表重新走一遍。同样的结构写成 `interface extends` 会被缓存一次，后面直接复用。

```ts
type Base = { id: number; name: string };
type Tagged = Base & { tag: "user" };
type WithMeta = Tagged & { createdAt: number };
type Keys = keyof WithMeta;
declare const key: Keys;
export const name: string = key;
```

分配式条件类型会对联合的每个成员分别求值。联合有 3000 个成员，条件类型就实例化 3000 次。写成 `T extends X` 就会分配，写成 `[T] extends [X]` 不会。

分配是有意的设计，用来逐成员过滤。不知道这一点时，把大联合传进工具类型会意外放大开销。`Extract`、`Exclude` 都建立在这个行为上，用对了很快，用错了很贵。

```ts
type Input = { kind: "a"; v: number } | { kind: "b"; v: string };
type Unwrap<T> = T extends { v: infer V } ? V : never;
export type Out = Unwrap<Input>;
```

映射类型套递归，每层都要新建一个对象类型。常见的 `DeepPartial`、`DeepReadonly` 都是这个形状。对象嵌套深、属性多时，类型数量按层数乘属性数增长。

映射类型对每个键都创建新类型，缓存的只有同名的 interface。嵌套到十层以上、每层几十个属性，`Types` 很快上十万。这类写法通常可以用一次的浅层映射代替，深层的交给运行时。

```ts
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};

interface TreeNode {
  id: number;
  children: TreeNode[];
}

declare const tree: DeepPartial<TreeNode>;
export const first: number | undefined = tree.id;
```

超大联合来自模板字面量和交叉组合。两个 30 成员的联合相乘，结果是 900 个成员；三个相乘就是 27000 个。数量到十万级时，tsc 直接拒绝。

模板字面量类型的展开在编译期完成，每个组合都是一个真实成员。用它给路由或事件名做约束很自然，但成员数按乘积增长，三个 60 成员的分段就是 21.6 万。

```ts
type Region = "cn" | "us" | "eu";
type Env = "dev" | "prod";
type Route = `${Region}/${Env}`;
declare const route: Route;
export const text: string = route;
```

四种形状的共同点是乘性增长。成员数、层数、属性数相乘，任何一个变大都会把总数推高。调优就是找到哪一项在乘。

本机实测的规模变化，文件只有一个类型加一个使用点，`tsc --extendedDiagnostics` 的数字：

| 联合规模 | Types | Instantiations | Check time |
|---|---|---|---|
| 单个 interface | 35527 | 34231 | 0.119s |
| 模板字面量 1000 成员 | 36505 | 35232 | 0.112s |
| 模板字面量 8000 成员 | 43875 | 42232 | 0.102s |
| 模板字面量 27000 成员 | 63445 | 61232 | 0.106s |
| 模板字面量 64000 成员 | 101215 | 98232 | 0.120s |
| 模板字面量 216000 成员 | 报 TS2590 | 不生成 | 立即失败 |

到 216000 成员时，报错是：

```bash
$ tsc --noEmit --strict routes.ts
routes.ts(4,22): error TS2590: Expression produces a union type that is too complex to represent.
```

注意 64000 成员只花 0.12 秒。说明在这台机器上，纯数量不是瓶颈，瓶颈在别的形状，比如深层递归和错误信息展开。

判断自己踩的是哪一类，看 `Types` 和 `Instantiations` 的比值。比值接近 1，成员在逐个创建，多半是分配式条件类型；比值明显小于 1，类型在复用，问题可能在个别深层类型。

## 递归上限：50 层和 1000 层

非尾递归的默认上限是 50 层。下面这个类型把元组反转，递归调用放在展开表达式里，不在尾位置。

```ts
type Reverse<T extends unknown[]> =
  T extends [infer H, ...infer R] ? [...Reverse<R>, H] : [];

type Tuple48 = [
  unknown, unknown, unknown, unknown, unknown, unknown, unknown, unknown,
  unknown, unknown, unknown, unknown, unknown, unknown, unknown, unknown,
  unknown, unknown, unknown, unknown, unknown, unknown, unknown, unknown,
  unknown, unknown, unknown, unknown, unknown, unknown, unknown, unknown,
  unknown, unknown, unknown, unknown, unknown, unknown, unknown, unknown,
  unknown, unknown, unknown, unknown, unknown, unknown, unknown, unknown,
];
type Tuple49 = [...Tuple48, unknown];

declare const fail: Reverse<Tuple49>;
declare const ok: Reverse<Tuple48>;
// error TS2589: Type instantiation is excessively deep and possibly infinite.
```

实测 48 个元素的元组通过，49 个报错。

```bash
$ tsc --noEmit --strict reverse48.ts
$                                                                    # exit 0
$ tsc --noEmit --strict reverse49.ts
reverse49.ts(14,21): error TS2589: Type instantiation is excessively deep and possibly infinite.
```

顺序也要注意。先写通过的那个类型，tsc 会缓存结果，49 个元素的那个反而可能不报错。上面把失败的那个放在前面，错误才稳定复现。

50 这个数字来自编译器的递归深度计数，不是元组长度（见 [checker.ts](https://github.com/microsoft/TypeScript/blob/v5.9.3/src/compiler/checker.ts)）。`[...Reverse<R>, H]` 每次递归都推迟到内层返回之后，计数随元组长度线性增长，到 49 就超过阈值。

尾递归形式的上限是 1000 层。把累积结果放进第二个参数，递归调用放在尾位置，编译器会做尾递归消除，不再压栈。

```ts
type ReverseTail<T extends unknown[], Acc extends unknown[] = []> =
  T extends [infer H, ...infer R] ? ReverseTail<R, [H, ...Acc]> : Acc;

type One = ReverseTail<[1, 2, 3]>;
declare const one: One;
export const length: 3 = one.length;
```

```bash
$ tsc --noEmit --strict reverse_tail_999.ts
$                                                                    # exit 0
$ tsc --noEmit --strict reverse_tail_1000.ts
reverse_tail_1000.ts(3,19): error TS2589: Type instantiation is excessively deep and possibly infinite.
```

上限和形状有关，不是一个统一数字。递归调用放在尾位置时，编译器会做尾递归消除，上限提到 1000 层；放在展开表达式里，50 层就停。惰性展开的嵌套 interface 能更深，因为它不要求一次算完。

上限不是可以配置的。`--generateTrace` 能看到实际实例化次数，但改不了阈值。能做的只有把递归改成尾递归、减少层数、或者换掉递归。

尾递归写法要多一个累积参数，第一次调用时传空值。改完之后函数签名变复杂，调用方需要给默认值，两者权衡后再动。

## 读诊断输出

`--extendedDiagnostics` 在编译结束时打印各项指标，不产出文件（见 [tsconfig 参考](https://www.typescriptlang.org/tsconfig)）。先看 Check time 和 Instantiations，再看 Types 和 Memory。

```bash
$ tsc --noEmit --strict --extendedDiagnostics src/bigunion.ts
Files:              83
Lines:           58450
Identifiers:     49734
Symbols:         63823
Types:           47334
Instantiations:  42233
Memory used:    69661K
Memory allocs:  321271
Parse time:     0.014s
Bind time:      0.005s
Check time:     0.121s
Emit time:      0.000s
Total time:     0.140s
```

各指标的含义，按排查顺序排：

- `Check time` 是类型检查耗时，调优主要看它。超过 1 秒就该查原因。
- `Instantiations` 是泛型实例化次数。几万属于正常，几十万要警惕。
- `Types` 是创建的类型对象总数。超过十万说明有大量展开。
- `Memory used` 是堆内存峰值。超过 1G 时 tsc 会明显变慢。
- `Parse time`、`Bind time` 通常很小，这两项高说明文件数量或体积有问题。

`Types` 和 `Instantiations` 要一起看。`Types` 高、`Instantiations` 低，说明类型对象多但复用少；两个都高，说明泛型在反复展开实例。只看一个数字容易判断错方向。

`--diagnostics` 是精简版，少了 `Lines`、`Identifiers`、`Symbols` 和 `Memory allocs`。CI 里用 `--extendedDiagnostics` 更划算。

`Memory used` 是峰值，不是平均。峰值高说明某个阶段一次创建了大量类型，通常是展开超大联合或深度递归。看到内存接近默认上限，先加 `--extendedDiagnostics` 找出触发阶段。

报错本身也会增加耗时。同一个文件加一条类型错误后，Check time 从 0.123 秒涨到 0.125 秒，差别不大。巨型联合真正贵的地方在生成错误信息，不在检查。CI 里把错误压到零，测出来的数字才稳定。

`Lines` 和 `Identifiers` 反映输入体积，`Types` 和 `Instantiations` 反映展开程度。两个文件的 `Lines` 接近，`Types` 差一个数量级时，问题在类型写法，不在文件大小。

`--generateTrace` 产出 Chrome Trace 格式的事件，配合 `@typescript/analyze-trace` 能看到哪个类型实例化最贵（见 [typescript-analyze-trace](https://github.com/microsoft/typescript-analyze-trace)）。这个工具只在定位阶段用，不要加进日常构建。

```bash
$ tsc --noEmit --strict --generateTrace trace src/bigunion.ts
$ ls -lh trace
legend.json      626B
trace.json       127K
types_0.json     7.2M
types_1.json     490K
types_2.json     2.1M
types_3.json     668K
$ npx @typescript/analyze-trace trace
```

按上面这组数字读：`Files` 83 说明项目不大，`Lines` 五万多说明单个文件很重。`Types` 四万多、`Instantiations` 四万多，两个数字接近，说明类型基本都在新创建，没有明显复用。

`types_*.json` 记录了每个类型的来源和实例化次数，是定位问题的关键文件。`trace.json` 记录阶段耗时，可以拖进 `chrome://tracing` 看时间线。

`analyze-trace` 的默认输出按耗时排序，列出最贵的类型和它出现的位置。看到 `duration` 高、`count` 也高的条目，直接去那个文件改写法。只高一次的条目通常是正常的大类型，不用动。

trace 文件体积不小，一个中型项目能到上百兆。跑完记得删掉，别提交进仓库。

三个命令的选择：日常改类型用 `--extendedDiagnostics` 看整体；定位具体类型用 `--generateTrace` 加分析工具；CI 回归用 `--diagnostics` 记录基线。

基线要按提交记录，不要按绝对值卡门禁。机器不同，`Check time` 能差两三倍；看趋势比看阈值可靠。

## Instantiations 在数什么

`--extendedDiagnostics` 输出里的 `Instantiations` 是检查器执行类型实例化的次数。每次把泛型参数换成具体类型，记一次。`Types` 是最终保留的类型对象数。两个数一起看才有意义。

空文件也有三万多次：

```bash
$ tsc --noEmit --extendedDiagnostics --strict --ignoreConfig empty.ts
Types:           35327
Instantiations:  34231
Check time:      0.147s
```

这些来自标准库里的泛型，加载 `lib.d.ts` 就要实例化一批。绝对值没有意义，要和同一项目的基线比，或者与改动前比。

组合能区分问题。Instantiations 大涨、Types 小涨，说明同一泛型被反复实例化，缓存没命中。两个一起涨，说明类型规模本身变大，要拆类型。

实测一组对照。400 个成员的类型放进条件类型，`inst_high.ts` 的 Instantiations 是 35434，普通写法 `inst_low.ts` 是 34232，多出 1202 次，Types 只多 403。

`--generateTrace` 把开销落到位置。先看 trace.json 的 check 段，再对比同目录 types_*.json 的体积，增长快的文件对应用例多。这些文件没有公开格式说明，读法属于推测。

递归推断是另一个信号。自引用又没有返回类型标注的箭头函数报 TS7023，两个递归很深的结构做赋值报 TS2321：

```ts
type Nest<N extends number, T, Acc extends unknown[] = []> =
  Acc["length"] extends N ? T : Nest<N, { next: T }, [...Acc, unknown]>;

type A = Nest<150, { v: number }>;
type B = Nest<150, { v: string }>;

declare const a: A;
const b: B = a;
const f = () => f();
export { b, f };
```

两处报错：`error TS2321: Excessive stack depth comparing types ...`（第 8 行）与 `error TS7023: 'f' implicitly has return type 'any' ...`（第 9 行）。改法都是加显式标注或拆层，别去调深度上限。

读 trace 的顺序固定。打开 trace.json 找 `check` 附近的长条，记下文件名。再到 types_*.json 里按文件名过滤，看实例化来自哪个类型别名。图形界面用 Chrome 的 tracing 查看器打开 trace.json。

经验比值可以当粗筛。Instantiations 除以 Types 超过 1.3 时，先怀疑重复实例化。低于这个值而两个数都大，多半是类型本身太大。这个比值没有官方阈值，只用来决定先查哪一头。

CI 里把 `--extendedDiagnostics` 的输出存成文件，和主干对比。只看 Types 与 Instantiations 两行就够，其他行随机器和文件数变化。

`Memory used` 也能当旁证。它随项目规模大致线性增长，翻倍时先查大类型是不是被重复展开。单次编译只看内存没有意义，两次对比才有。

基线的比法要统一。单文件跑一次和 `-p` 跑全项目，文件数差几十倍，数值不可比。固定用同一条命令，把输出存下来，和改动前的文件对照。

一句话，Instantiations 是检查器的工作量计数，不是类型个数。它涨得比 Types 快，就是重复劳动。这个比喻的边界在基线，新项目没有基线可对，只能看数值的相对变化。

## 降低复杂度的四种手法

第一种是让结果被缓存。`interface` 会被当成有名字的对象类型缓存起来，同名交叉类型每次都要重新合并。把重复出现的组合抽成 interface。

抽 interface 的代价是多一个声明，收益是后续所有引用共享同一个结果。组合在代码里出现三次以上，就值得抽。出现一次的地方抽出来反而增加阅读成本。

```ts
type WithId = { id: number };
type WithTime = { createdAt: number };
type WithOwner = { owner: string };

interface RecordBase extends WithId, WithTime, WithOwner {}

export function read(r: RecordBase): number {
  return r.id;
}
```

第二种是避开对裸类型参数做分配。条件类型写在裸的 `T` 上会按联合分发，写在元组里不分发。

这一条只影响性能，不改变结果的情况需要确认。分发和不分发的语义不同，改写法前先想清楚是否真的需要逐成员处理。需要逐成员时，接受开销，别硬改。

```ts
type Distribute<T> = T extends string ? T[] : never;
type NoDistribute<T> = [T] extends [string] ? T[] : never;

export type A = Distribute<"a" | "b">;
export type B = NoDistribute<"a" | "b">;
```

第三种是用索引访问代替深递归。需要取嵌套结构里的某一层时，直接索引，不要写递归遍历。

索引访问是 O(1) 的路径查找，递归遍历是逐层展开。两者结果可以一样，开销差几个数量级。路径固定时优先索引，路径由变量决定时才用递归。

```ts
interface ApiResponse {
  data: { items: { id: number; name: string }[] };
}

type Item = ApiResponse["data"]["items"][number];
declare const item: Item;
export const id: number = item.id;
```

第四种是把大类型拆小。一个包含 200 个属性的接口参与交叉、映射、条件判断时，任何操作都会遍历全部属性。按用途拆成几个小接口，再在需要的地方组合。

四种手法经常一起用。先抽 interface 拿到缓存，再拆小减少每次遍历的属性数，然后检查有没有裸类型参数在分配，最后把深递归换成索引访问。每改一处跑一次诊断，记录数字变化。

拆小之后，使用方只引用需要的那部分。属性仍然在，但类型操作的作用域缩小了。这是唯一一种既能降开销、又能改善可读性的改法。

```ts
interface UserBase { id: number; name: string }
interface UserContact { email: string; phone?: string }
interface UserSettings { theme: "light" | "dark"; locale: string }

type FullUser = UserBase & UserContact & UserSettings;
export const theme: FullUser["theme"] = "dark";
```

## DeepReadonly 会拆掉调用签名

朴素写法把每个属性递归映射成只读，问题出在函数属性和有方法的对象上。函数被映射后只剩属性，没有调用签名，调用时报 TS2349。

```ts
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};

interface Job {
  id: number;
  createdAt: Date;
  done: () => void;
}

declare const job: DeepReadonly<Job>;
job.createdAt.getTime();
job.done();
```

```bash
$ tsc --noEmit --strict deep.ts
deep.ts(12,15): error TS2349: This expression is not callable.
  Type 'DeepReadonly<() => number>' has no call signatures.
deep.ts(13,5): error TS2349: This expression is not callable.
  Type 'DeepReadonly<() => void>' has no call signatures.
```

`Date` 的 `getTime` 也坏了。`Date` 是对象，被递归映射后，方法变成了只读属性，`DeepReadonly<() => number>` 没有调用签名。

根因是映射类型只看键，不看值的类别。函数和类实例在结构上都是对象，`keyof` 都能展开。展开之后函数剩下的只有 `apply`、`call` 这些属性名，调用签名丢了。

修法是先判断函数和内置对象，命中就原样返回，不再往里递归。

```ts
type DeepReadonly<T> =
  T extends (...args: never[]) => unknown ? T :
  T extends Date ? T :
  T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } :
  T;

interface Job {
  id: number;
  createdAt: Date;
  done: () => void;
}

declare const job: DeepReadonly<Job>;
export const time: number = job.createdAt.getTime();
job.done();
```

判断顺序重要。函数判断放最前，否则函数会先命中 `object` 分支，又被映射一遍。`Date` 放在 `object` 之前，否则同上。

修复版也不是万能的。`Map`、`Set`、`RegExp` 这些内置对象同样有方法，需要各自判断。实际项目里 `DeepReadonly` 只该用在数据边界，不要套在带方法的对象上。

修复版里 `(...args: never[]) => unknown` 匹配任意函数，不关心参数和返回值。用 `Function` 也行，但 `Function` 是宽类型，在 `strictFunctionTypes` 下匹配更松。`never[]` 的写法能被所有函数赋值，是常用技巧。

## isolatedDeclarations 下的推断失败

`isolatedDeclarations` 要求每个导出的类型都能从当前文件单独推断出来，不依赖其他文件的类型信息。这是给 esbuild、swc 这类单文件工具生成 `.d.ts` 用的。

生成声明文件传统上要靠 tsc 全项目跑一遍。开启这个选项后，每个文件的声明可以并行生成，构建时间随核数下降。代价是所有导出都必须写清类型，写不出就报错。

单独开这个选项报 TS5069，必须同时开 `declaration` 或 `composite`。

```bash
$ tsc --noEmit --isolatedDeclarations src/index.ts
error TS5069: Option 'isolatedDeclarations' cannot be specified without specifying option 'declaration' or option 'composite'.
```

推断不出返回类型时报 TS9013。泛型函数返回条件表达式就是典型。

```bash
$ tsc --noEmit --declaration --isolatedDeclarations pick.ts
pick.ts(2,10): error TS9013: Expression type can't be inferred with --isolatedDeclarations.
```

```ts
export function pick<T>(value: T) {
  return value ? 1 : "a";
}
```

```ts
export function pick<T>(value: T): number | string {
  return value ? 1 : "a";
}
```

返回对象字面量时错误码是 TS9016，不是 TS9013。`export function wrap<T>(value: T) { return { value }; }` 报 TS9016，原因同样是推断不出跨文件可用的结构。

```ts
export function wrap<T>(value: T): { value: T } {
  return { value };
}
```

变量赋值给函数调用结果、运算结果、三元表达式时报 TS9010。原因是这些表达式的类型需要跨文件信息才能确定，单文件工具看不到。

字面量不受影响。`export const config = { retries: 3 };` 的结构直接来自字面量，不需要推断。区分标准是值的类型能否只从当前表达式读出。

```ts
function local(): { a: number } {
  return { a: 1 };
}

export const n = 1 + 2;
// error TS9010: Variable must have an explicit type annotation with --isolatedDeclarations.

export const z = local();
// error TS9010: Variable must have an explicit type annotation with --isolatedDeclarations.
```

这两处报错只在开启 `isolatedDeclarations` 与 `declaration` 时出现；按默认配置编译这块不报错。

修法是加类型标注，标注要和推断结果一致。

标注不是随便写一个宽类型。`export const n: number = 1 + 2` 可以过检查，但声明文件里就丢了字面量 `3` 这个信息，使用方拿不到精确类型。标注要等于推断结果，不能只是能赋值。

```ts
function local(): { a: number } {
  return { a: 1 };
}

export const n: number = 1 + 2;
export const z: { a: number } = local();
```

类方法没写返回类型时报 TS9008，计算属性名时报 TS9038。字面量直接赋给常量（`export const config = { retries: 3 }`）可以通过，因为字面量的结构不需要跨文件推断。

错误码按语句形态分工：TS9010 管变量声明，TS9013 管函数返回表达式，TS9016 管简写属性，TS9008 管方法签名，TS9038 管计算属性名。迁移时按错误码分批修，一批改完再跑下一批。

```ts
export class Loader {
  async load(): Promise<{ ok: boolean }> {
    return { ok: true };
  }
}
```

## 类型测试

类型写错了不一定有人发现，除非有断言。`expect-type` 提供编译期断言，断言失败时报 undefined 调用错误。

它的原理是在类型层面故意制造不兼容。断言通过时类型是 `ExpectString<T>` 这类空结构，不通过时编译器找不到可调用的成员，报 TS2349。错误信息不好读，但位置准确。

```bash
$ pnpm add -D expect-type
```

```ts
import { expectTypeOf } from "expect-type";

type Client = { retries: number };

declare function createClient(opts: Client): string;

expectTypeOf(createClient).returns.toBeString();
expectTypeOf(createClient).parameter(0).toEqualTypeOf<Client>();
expectTypeOf(createClient({ retries: 3 })).toBeString();
```

要装 `expect-type`；没装时报 `TS2307: Cannot find module 'expect-type'`。

把最后一行改成 `expectTypeOf(createClient).returns.toBeNumber();`，编译就失败。

```bash
$ tsc --noEmit --strict test.ts
test.ts(10,36): error TS2349: This expression is not callable.
  Type 'ExpectNumber<string>' has no call signatures.
```

`expectTypeOf` 的断言链在运行时不执行，产物里没有任何代码。测试文件放进 `tsc --noEmit` 就能在 CI 里拦住回归。

断言的粒度要合适。断言完整的对象类型，类型一改就红，维护成本高；断言关键字段和方法返回类型，改动能被覆盖，噪音少。对外 API 断言完整类型，内部工具断言关键行为。

类型测试适合两种情况：库的公开 API，和项目里反复复用的工具类型。业务代码一般不需要，改动的收益不如直接读类型报错。

`vitest` 的 `expectTypeOf` 是同一个 API，从 `vitest` 导入即可。断言写在普通测试文件里，`vitest` 运行时会把类型测试标记为跳过，不产生运行开销。`tsd` 是更早的方案，需要独立配置和运行命令，适合单独维护类型包的项目。

CI 里加一个 `tsc --noEmit` 步骤就够。类型测试文件和源码一起编译，断言失败就是一个类型错误。不需要单独的测试框架。

## 什么时候放弃类型体操

类型只活在编译期。数据从网络、文件、用户输入进来的那一层，类型体操无法验证。运行时校验必须自己写，或者用 zod 这类库。前者在编译期默认数据正确，后者在运行期确认，两者不能互相替代。

边界只有一处：外部数据进入系统的地方。内部的变换、组合、派发都可信，不需要再校验。把校验写进每个函数是最常见的过度设计。

校验函数返回 `Payload` 而不是 `unknown`，类型收窄发生在边界，后续代码不用再断言。校验失败就抛错，不要返回 `null` 再让调用方猜。

```ts
export interface Payload {
  id: number;
  tags: string[];
}

export function parsePayload(input: unknown): Payload {
  if (typeof input !== "object" || input === null) {
    throw new Error("payload must be an object");
  }
  const raw = input as { id?: unknown; tags?: unknown };
  if (typeof raw.id !== "number" || !Array.isArray(raw.tags)) {
    throw new Error("payload has wrong shape");
  }
  const tags = raw.tags.filter((tag): tag is string => typeof tag === "string");
  return { id: raw.id, tags };
}
```

判断标准有三条：

- 类型只用于内部变换、不影响对外 API 时，可以用类型体操，但要能说清输入输出。
- 类型需要在 IDE 里悬停可读、需要让别人维护时，写简单版本。

- 类型只在构建期存在、不进入公开 API 时，可以适当放宽精度，换取编译速度。
- 递归超过 50 层、联合超过几万成员、条件类型嵌套超过四层时，改设计。降低维度比优化类型便宜。

改设计指换数据形状。把三层嵌套的联合拍平成一层，把运行时的组合逻辑从类型层挪走，把校验交给 zod 这类库。类型体操解决的是表达问题，不是计算问题，超过一定复杂度就该换工具。

三条标准可以合成一条：这段类型有没有第二个人维护。只有自己看，怎么快怎么来；要被别人读，可读性优先；要对外发布，API 的类型必须写得稳。

## 用不上的时候

### 慢在文件规模而不是类型写法

文件行数、符号数、`skipLibCheck`、冷启动都会推高耗时，这些不是递归写法能修的。先看 `Types` 和 `Instantiations` 两项，它们不高就说明瓶颈在别处。优化类型之前，先确认量对了对象。

### 把 48 和 999 当成设计契约

上限随写法、版本和缓存状态变化。先编译通过的类型会让后面失败的用例不报错，同一份代码换个顺序结果就不同。依赖具体数字写边界，升级一次就可能整批报 `TS2589`。留一半余量只是保守做法，不是保证。

### 正常耗时区间内的调优

中型项目全量检查一到三秒是正常值，超过五秒再动手。把这段耗时继续往下压，收益是每人每天几秒，代价可能是类型精度。调优的目标是避开 `TS2589` 和内存上限，不是把数字压到最小。
