# 第 48 章 把类型讲成集合

类型检查器只做一件事：比较两个集合。`const x: A = y` 能通过，说明 y 的取值集合落在 A 的集合里面。报错则说明 y 里有 A 装不下的东西。

把类型当集合读，多数报错会立刻变成一句白话：你给的范围超出了声明的范围。这个读法不需要背规则表，只需要回答三个问题：需要什么，实际有什么，差在哪。

类型标注本身不产生运行时代码。编译之后，`const n: number = 1` 和 `const n = 1` 生成的 JavaScript 一样。集合只存在于检查阶段，用于判断某个值能不能放进某个位置。

下面用十二节把类型系统的主要机制过一遍。每节先给一句能想象的比喻，再给代码和实测结果，最后写明这个比喻在哪里失效。

## 类型是一组值

一个类型就是一张清单，清单上写着允许出现哪些值。

`string` 的清单装着所有字符串，无穷长。字面量类型 `"a"` 的清单只有一项。`unknown` 的清单装了所有值。`never` 的清单是空的。

```ts
type Letter = "a";
const one: Letter = "a";

const anything: string = "任意字符串";

declare const impossible: never;

let unknownValue: unknown = "hello";
unknownValue = 42;
unknownValue = { nested: true };
```

`Letter` 只认 `"a"`。`anything` 认任何字符串。`impossible` 没有任何值可以放进去，所以它只能出现在接收方。`unknownValue` 什么都能接。

字面量类型不常手写。它更多来自推导：`const letter = "a"` 得到的类型就是 `"a"`，因为 const 绑定的值不会再变，编译器就把集合收窄到那一个值。`let letter = "a"` 得到的是 `string`，因为将来可能被改成别的字符串。

集合的宽窄是一场取舍。标注写窄，编译器替你抓错；标注写宽，冲突更少。业务边界上取窄，边界内部允许宽一点。`unknown` 是宽到极限的写法，`never` 窄到极限。

读报错时也先问一句：这个位置要的是什么集合。`not assignable` 后面跟着两个类型，前一个是实际值，后一个是位置要求。习惯这个方向，报错就不再是噪音。

四张清单的关系画出来，两个极值就清楚了：

```text
unknown  ┌───────────────────────────┐  一切值
         │  string  ┌─────────────┐  │
         │          │ "a"  ●      │  │
         │          └─────────────┘  │
         │  number ● ● ●             │
         └───────────────────────────┘

never     ∅  空集
```

图上 `"a"` 落在 string 里面，说明单元素集是 string 的子集。string 和 number 都在 unknown 里面。never 不在图里，因为它没有任何元素。

`never` 的位置值得多看一眼。它不表示“未知类型”，也不表示“任意类型”。它表示“这里不可能有值”。一个函数如果永远抛错，返回类型就写 `never`。一个联合被过滤空了，结果也是 `never`。这两个场景都是“值不存在”，集合读法正好对上。

`never` 还用于穷尽检查。switch 把每个分支都写全后，`default` 里剩下的值收窄成 `never`。漏掉一个分支，那里就不再是 never，把值赋给 never 的检查会失败。

空集在并集里是单位元。`never | string` 就是 `string`，把空集并进任何集合，结果还是那个集合。工具类型过滤掉全部成员后落到 never，再参与联合时会被自动吸收。这条规则解释了不少看上去神奇的化简。

回到第一段代码：把 `one` 的标注换成 `"b"`，立刻报 TS2322，因为 `"b"` 不在那个单元素集合里。

这个比喻不成立的地方：unique symbol 和 branded type 会给形状相同的值加身份标签。两个集合看起来一样，赋值仍被拒绝，集合模型里没有“身份”这一栏。

## 赋值是子集判断

把值交给标注，等于问一句：这个值属于这张清单吗。这层对应关系在 [TypeScript Handbook 的类型兼容性一节](https://www.typescriptlang.org/docs/handbook/type-compatibility.html) 里有完整说明。

判断有方向。左边是声明要求，右边是实际值。要求可以比实际宽，反过来不行。

```ts
const lit: "a" = "a";
const wide: string = lit;      // {"a"} ⊆ string

let noMember: {} = "hello";    // 非 null 值都满足“没有成员要求”
noMember = 42;
```

`lit` 只有一个值，赋给 string 没问题。`{}` 常被误解成“空对象”，它的真实含义是“没有任何成员要求”，所以除了 `null` 和 `undefined`，任何值都满足。

三条最常见的赋值报错，用集合读一遍就懂了：

```ts
interface Point { x: number; y: number }

const n: number = "42";        // error TS2322: Type 'string' is not assignable to type 'number'.
const p: Point = { x: 1 };     // error TS2741: Property 'y' is missing in type '{ x: number; }' but required in type 'Point'.
const letter: "a" = "b";       // error TS2322: Type '"b"' is not assignable to type '"a"'.
```

第一条，string 和 number 两个集合不相交，字符串永远进不了 number 的门。

第二条稍微绕一点。`{ x: 1 }` 的类型是 `{ x: number }`，它的集合里有大量“只有 x 没有 y”的对象，范围比 Point 大。可 Point 要求两个成员都有，所以这个更大的集合里偏偏装不下 Point 要的东西。

第三条，`"b"` 不在只剩一个元素的集合里。

报错的文字长短也能读出信息。两个集合完全不相交时，编译器只说类型名，没有别的可说。差一个成员时，它会点名缺的是谁。这条规律对读长报错很有用：报错越具体，问题越局部。

函数实参位置也是赋值，规则完全一样。传参时左边是形参类型，右边是实参的集合。

赋值判断出现在很多位置。`return`、数组字面量、对象属性、默认参数，规则都一样，只是位置藏在语法里，报错时不容易联想到赋值。返回值位置稍有不同，函数体里 `return` 的值要落进返回类型的集合，方向从函数体指向签名。

可选属性等于把 `undefined` 并进允许值。`{ a?: string }` 接受 `{}`，也接受 `{ a: undefined }`。读的时候要多处理一种情况：属性可能不在。

strictNullChecks 直接改变集合大小。关掉它，`null` 和 `undefined` 能混进几乎所有集合，等于把每个类型都加宽。这是两套类型系统最明显的差别。

对象字面量直接赋值还有一条额外规则，容易和集合判断混在一起：

```ts
interface Point { x: number; y: number }

const direct: Point = { x: 1, y: 2, z: 3 };  // error TS2353: Object literal may only specify known properties, and 'z' does not exist in type 'Point'.
const temp = { x: 1, y: 2, z: 3 };
const viaVar: Point = temp;                    // 合法
```

第一行报错，因为对象字面量会做多余属性检查。第二行不报，因为中间变量已经丢掉字面量的“新鲜”身份。集合包含关系没有变，变的只是检查时机。

这个比喻不成立的地方：`{}` 能接住 `"hello"`，靠的是结构规则，加上 strictNullChecks 排除了 `null` 和 `undefined`，不是“字符串是对象”这种直觉。关掉 strictNullChecks，`null` 也会进 `{}`。

## never 与 unknown 在两个极值

空集是任何集合的子集，全集包含任何集合。这两句数学用语直接翻译成两条赋值规则。

`never` 是空集，可以赋给任何类型。反过来，任何值都装不进空集。`unknown` 是全集，任何值都能赋给它。反过来，它范围太大，不能直接当具体类型用。

```ts
declare const impossible: never;

const s: string = impossible;   // 空集 ⊆ string
const n: number = impossible;   // 空集 ⊆ number
let u: unknown = impossible;    // 空集 ⊆ 全集

let whole: unknown = "x";         // 任何值 ∈ 全集
// const bad: never = "x";      // error TS2322: Type '"x"' is not assignable to type 'never'.
// const bad2: string = whole;  // error TS2322: Type 'unknown' is not assignable to type 'string'.
```

结论落在两条报错上：往 never 里写东西必然失败，从 unknown 里直接取值也必然失败。后者是因为全集中有 string 装不下的值，比如对象。

`unknown` 的用法因此固定下来。接收参数时用它，表示什么都收。真正使用之前，先用 `typeof` 判断或显式断言，把范围从全集收窄到具体类型。这个流程麻烦，但每一步都有依据。

`any` 与 `unknown` 的差别也在集合上。`any` 不参与判断，它能进出任何位置，等于把这一处从检查里摘出去。`unknown` 参与判断，只是它的集合太大，大到不能直接当窄类型用。

`void` 是这套模型里的例外，得单独说。它的含义是“调用方不关心返回值”，不是“空集”，也不是“`undefined` 的别名”。

```ts
function log(msg: string): void { console.log(msg); }

const v: void = log("hi");         // 合法，函数返回 void
const fromUndef: void = undefined; // 合法，undefined 属于 void
const f: () => void = () => 42;    // 合法，返回值被忽略

// const w: void = 42;             // error TS2322: Type 'number' is not assignable to type 'void'.
// const back: undefined = v;      // error TS2322: Type 'void' is not assignable to type 'undefined'.
```

实测结论：`undefined` 能赋给 `void`，`void` 不能赋给 `undefined`。按宽度排队，`undefined` 比 `void` 窄。

void 常出现在三个位置：函数返回类型，表示只做事不产出值；变量类型，少见但合法，能放的值只有 `undefined` 这类空值；泛型实参，`Promise<void>` 表示异步操作没有结果可拿。泛型实参，`Promise<void>` 表示异步操作没有结果可拿。三处用的是同一个意思：这里不承载数据。

这个比喻不成立的地方：`() => number` 能赋给 `() => void`，这条是编译器对返回值的特例，集合解释不了。把 void 当成“空集”或“任何值”，都会撞上 `const w: void = 42` 这条报错。

## 联合是并集，交叉是交集

`|` 是并集，两个集合合起来，范围变大。`&` 是交集，只保留同时属于两边的部分，范围变小。

```ts
type Scalar = string | number;

const a: Scalar = "x";
const b: Scalar = 1;

interface Named { name: string }
interface Aged { age: number }

type Person = Named & Aged;
const p: Person = { name: "a", age: 1 };
const onlyNamed: Named = p;   // Person ⊆ Named
```

`Scalar` 里的值要么是字符串，要么是数字。`Person` 必须同时满足两个 interface，所以它比每个单独的都窄。

并集带来一条使用限制：只能做所有成员都支持的操作。

```ts
type Scalar = string | number;

declare const value: Scalar;
// value.toFixed(2);  // error TS2339: Property 'toFixed' does not exist on type 'Scalar'.
// value.toUpperCase();  // error TS2339: Property 'toUpperCase' does not exist on type 'Scalar'.
```

两个方法各属于一个成员，并集上没有共同保证，编译器一律拒绝。要用就先收窄：判断 `typeof value === "string"`，在对应分支里调用。这条限制和集合视角完全一致，并集里每个元素不一定都有某个成员。

联合的常见来源是参数的多形态。函数既接受字符串又接受数组时，要么在函数体里收窄，要么拆成两个重载。收窄更直观，重载更适合返回值也随输入变化的情况。

收窄写起来是这样的：

```ts
type Scalar = string | number;
declare const value: Scalar;

function describe(v: Scalar): string {
  if (typeof v === "string") return v.toUpperCase();
  return v.toFixed(2);
}
```

每个分支里，v 的集合被 `typeof` 缩到一个成员，方法就能调用了。

```text
        Named            Aged
     ┌─────────┐      ┌─────────┐
     │ name    │      │ age     │
     └────┬────┘      └────┬────┘
          │   Named & Aged  │
          │   ┌──────────┐  │
          └───┤ name age ├──┘
              └──────────┘
```

交叉常被当成“合并”，这个理解在属性不冲突时看起来成立，一冲突就露馅：

```ts
type Conflict = { tag: string } & { tag: number };

const c: Conflict = { tag: 1 };   // error TS2322: Type 'number' is not assignable to type 'never'.
```

`tag` 要同时满足 string 和 number，两个集合不相交，`tag` 的类型落到 never。整个对象类型就要求一个不可能存在的属性值。

`X & Y` 和 `interface Z extends X, Y` 在多数场合等价，因为继承也是在合并要求。差别在冲突时的报错位置与扩展能力，集合关系上两者都是交集。

这个比喻不成立的地方：属性不冲突时，交叉写出来像把两个对象合并成一个，代码看不出来它其实是“同时满足”。真正的合并要手写映射类型或工具类型，两者不是一回事。

## 泛型是类型层的函数

`Box<T>` 像一台机器，喂进去一个类型，吐出另一个类型。调用方传什么，机器就装配什么。

```ts
type Box<T> = { value: T };

const numBox: Box<number> = { value: 1 };
const strBox: Box<string> = { value: "x" };

type Page<T = string> = { items: T[] };
const page: Page = { items: ["a"] };
```

`Box<number>` 和 `Box<string>` 是这台机器的两次调用，各得一个新的对象类型。`Page` 那一行没传参数，用了默认值 `string`，等价于缺省参数。

用集合的话说，`Box<T>` 生成的是一族类型，T 每变一次就换一个集合。传入 number 得到一个装着 number 的集合，传入 string 得到另一个，两者互不相干。这解释了为什么 `Box<number>` 不能赋给 `Box<string>`。

这族类型的兼容性并不都按成员逐个判断。`Box<Dog>` 赋给 `Box<Animal>` 在 TypeScript 里能通过，因为属性位置被当作协变处理。Dog 是 Animal 的子类型，number 不是 string 的子类型，所以两种情况不矛盾。属性位置的协变是已知的不健全点，后面还会遇到同类问题。

约束 `extends` 相当于限制定义域。它保证两件事：传进来的类型必须满足条件，函数体里可以放心用条件里的成员。

```ts
function first<T extends { length: number }>(item: T): number {
  return item.length;
}

first("abc");
first([1, 2, 3]);
// first(1);   // error TS2345: Argument of type 'number' is not assignable to parameter of type '{ length: number; }'.
```

字符串和数组都有 `length`，能进定义域。数字没有，报 TS2345。函数体里写 `item.length` 是安全的，因为约束已经担保了这一点。

多参数泛型用来表达关系，而不只是类型本身。`function assign<T, U extends T>(target: T, source: U)` 里两个参数被绑在一起，调用方传什么就锁定什么，返回值也跟着确定。这种约束在库里很常见，用来保证“写进去的类型”和“读出来的类型”是同一个。

调用泛型函数时，类型参数常常不用写。编译器从实参反推 T，这是推断。推不出来才需要显式写出，写成 `first<number>(...)` 那样。

默认值解决的是“大多数调用不需要写参数”的情况。`type Params<T = any>` 让调用方省略时有一份兜底，需要精确时再显式传。

实例化报错通常指向约束不满足。看到 TS2345 或 TS2344，先看实参有没有约束要求的成员，再决定换实参还是放宽约束。

这个比喻不成立的地方：类型参数能从结果反推。`type ElementOf<T> = T extends (infer R)[] ? R : never` 里，R 不是传进去的，是从 T 的形状里读出来的。普通函数没有这种能力，所以只需把泛型当函数看“传参得类型”这一层。

## 条件类型是 if，对联合逐个分叉

`T extends U ? A : B` 是 if。T 是联合时，编译器相当于对每个成员各走一遍 if，再把结果并起来。

```ts
type IsString<T> = T extends string ? "yes" : "no";

const r1: IsString<"abc"> = "yes";
const r2: IsString<42> = "no";

type R = IsString<"a" | 1>;
const r3: R = "yes";
const r4: R = "no";
// const r5: R = "maybe";   // error TS2322: Type '"maybe"' is not assignable to type 'R'.
```

`IsString<"a" | 1>` 的结果不是 `"no"`，是 `"yes" | "no"`。`"a"` 走了一次 if 得 `"yes"`，`1` 走了一次得 `"no"`，两个结果并起来。

这条分配规则在写工具类型时天天用到：

```ts
type MyExclude<T, U> = T extends U ? never : T;

type Kept = MyExclude<"a" | "b" | "c", "a">;
const k: Kept = "b";
// const k2: Kept = "a";   // error TS2322: Type '"a"' is not assignable to type 'Kept'.
```

每个成员单独判断，落在 U 里的成员返回 never，其余保留。并集里没有 `"a"` 了，所以 `k2` 报错。

分配的好处是把集合运算落到了类型层。过滤一个联合，本质是对每个元素做一次成员判断，保留通过的那些。`Exclude` 与 `Extract` 就是这套操作的两个方向，一个剔掉，一个只留。

分配会改变预期。写 `T extends string ? A : B` 时，传入联合可能得到 `A | B`，而不是单个分支。看到结果里两个分支并起来，先检查 T 是不是联合，问题通常就清楚了。

分配还说明了另一件事：条件类型不是对“整个联合”判一次。写 `T extends never ? …` 时，如果 T 是空集，分配无法产出任何成员，结果只能是 never。这个现象在排查工具类型时经常撞见。

判断一个条件类型会不会分配，看 T 是不是光着出现的。光着就分配，包一层就不分配。

```ts
type Wrap<T> = [T] extends [string] ? "yes" : "no";

type W = Wrap<"a" | 1>;
const w: W = "no";
```

`["a" | 1]` 整体去比 `[string]`，结果是 false，所以 W 是 `"no"`。同一个联合换成裸参数，结果会变成 `"yes" | "no"`。两种写法差一对括号，行为完全不同。

这个比喻不成立的地方：分配只发生在裸类型参数上。写成 `[T] extends [U]` 时不再逐个成员分叉，if 的比喻会立刻误导。

## 映射类型是 for 循环

`keyof T` 是键的集合。`[K in keyof T]` 是对这个集合做 for。`T[K]` 是按键取值。

```ts
interface Account { id: string; balance: number }

type Optional<T> = { [K in keyof T]?: T[K] };
const draft: Optional<Account> = { id: "a1" };

type Keys = keyof Account;
const k1: Keys = "id";
const k2: Keys = "balance";

type IdType = Account["id"];
const id: IdType = "a1";
```

`keyof Account` 得到 `"id" | "balance"`，一个有两个成员的并集。映射类型遍历这个并集，每个键都生成一个属性，加上 `?` 变成可选。`Account["id"]` 是按键取值，得到 string。

`Optional<Account>` 允许 `{ id: "a1" }`，因为 `balance` 变成可选。这是把一张属性表按同一规则重写一遍的典型用法。

`keyof` 除了当遍历的源头，还常用来约束参数。`function get<T, K extends keyof T>(obj: T, key: K)` 把 key 限制在已有键的集合里，传错键名直接编译失败。这比在运行时查表更早发现问题。

`typeof` 常和 `keyof` 一起用。`keyof typeof config` 先从值取出它的类型，再取键的集合，得到的是键名联合。手写字符串联合容易漏改，这种写法跟着对象走。

映射的产出仍然是一个类型，可以继续参与联合、交叉、条件判断。写工具类型时把它当普通类型用，不必想成模板。`Partial` 与 `Required` 就是最基础的两个映射，一个加问号，一个去问号。

`T[K]` 的读法是按键取值。K 是键集合里的一个元素，取出来就是这个键对应的值类型。映射内部必须写 `T[K]`，不能写死一个类型。写死就把每个键都变成同一个类型，键与值的对应关系丢了。

映射不要求键来自 `keyof`。`[K in "a" | "b"]` 直接用一个字面量联合照样能遍历，因为 in 的右边可以是任意键集合。这个写法常用来生成固定字段的表结构。

这个比喻不成立的地方：映射类型还能用 `as` 重命名键，用 `-?` 去掉可选，用 `readonly` 加只读。这些是改写规则，不是遍历，for 的比喻只覆盖最基础的形态。

## infer 是解构

`const [head] = list` 从值里拿第一项。`T extends (infer R)[] ? R : never` 从类型里拿元素类型，思路一样。

```ts
type ElementOf<T> = T extends (infer R)[] ? R : never;

const e: ElementOf<string[]> = "x";
const n: ElementOf<number[]> = 1;

type FirstParam<T> = T extends (first: infer P, ...rest: any[]) => any ? P : never;
const id: FirstParam<(id: string) => void> = "x";
```

第一段从数组类型里解出元素类型。第二段把函数类型当成一个形状，`infer P` 占住第一个参数的位置，匹配成功就把 P 取出来。

同一个套路能解出返回类型。把函数类型写成 `(...args: any) => infer R`，R 就是返回值。内置的 `ReturnType` 正是这个形状，手写一遍能看清它为什么长那样。

元组也能解构。`T extends [infer A, infer B, ...any[]]` 取出前两项，位置固定时比数组解构更精确，因为长度也参与匹配。同一个模式里可以出现多个 `infer`，同时取出多个片段。

解构失败会落到 false 分支，所以默认值要选安全的类型。返回 `never` 表示“解不出来就等于空”，返回 `unknown` 表示“解不出来但要提醒调用方”，返回 `any` 则是放弃检查。三种选择对应三种态度，没有绝对的对错。

`infer` 只能写在条件类型的 `extends` 子句里，别的位置写不进去。这条限制决定了它的用法：先有一个待匹配的形状，再从里面抠出片段。

这个比喻不成立的地方：多个 `infer` 出现在同一模式里时，它是模式匹配，不是按顺序解构。位置对不齐就整个落到 false 分支，拿不到部分结果。

## 变型是方向

读位置顺着子类型箭头走，写位置逆着走。狗是动物，从狗数组里读出来的东西可以当动物用；但往一个声明成动物的容器里写，写进去的东西必须能用动物表示。

```ts
class Animal { name = "animal"; }
class Dog extends Animal { bark() {} }

let dogs: Dog[] = [new Dog()];
let animals: Animal[] = dogs;            // Dog[] ⊆ Animal[]，读位置

let animalFn: (a: Animal) => void = () => {};
let dogFn: (a: Dog) => void = animalFn;  // 参数位，方向反过来

// let wrong: (a: Animal) => void = dogFn;  // error TS2322: Type '(a: Dog) => void' is not assignable to type '(a: Animal) => void'.
// let wrongArr: Dog[] = animals;           // error TS2322: Type 'Animal[]' is not assignable to type 'Dog[]'.
```

`Dog[]` 赋给 `Animal[]` 合法。参数位置反过来：接收 `Animal` 的函数更宽容，能接收 `Dog`，所以能赋给接收 `Dog` 的函数类型。反过来就报 TS2322，因为窄的东西接不住宽的值。

两条报错都附带一句 `Property 'bark' is missing in type 'Animal'`，那是编译器在说明方向错的理由：拿 Animal 当 Dog 用，缺 `bark`。

为什么参数位要反过来，用运行时想一遍就明白。`dogFn` 的实参声明是 Animal，函数体只会用动物都有的成员。把它赋给“调用方保证传狗”的位置，传进来的确实是狗，那当然安全。反过来，`animalFn` 的实参声明是 Dog，函数体可能调用 bark。把它放到“调用方只保证传动物”的位置，运行时就可能拿到一只没有 bark 的动物。

这套方向在读写位置上的名字就是变型。产出位置（返回值）是协变，消费位置（参数）是逆变，同时读写的位置理论上要求两个方向都成立，实现里 TypeScript 按协变放行，留下了不健全点。

消费位置不止函数参数。接口里的方法参数、回调的形参、以及标了 `in` 的类型参数，都按同一条方向判断。读位置则包括返回值、只读属性，以及标了 `out` 的类型参数。

这也是库的类型声明里参数位常标逆变的原因。回调参数、事件处理器这类消费位置，方向写错会让调用方传不进想要的函数。

这个比喻不成立的地方：方法简写的参数位即使开了 strictFunctionTypes 仍然双变。方向表要按写法分开看，属性写法是逆变，`method(a: Animal) {}` 这种简写保持双变。

## 结构化类型认形状不认名字

插头和插座只看孔位对不对，不看牌子。两个 interface 名字不同，成员相同，就能互赋。

```ts
interface Point { x: number; y: number }
interface Vec { x: number; y: number }

const v: Vec = { x: 1, y: 2 };
const p: Point = v;      // 合法，形状相同
```

名字不参与判断，参与判断的是成员集合。这也解释了为什么多一个属性还能赋进去，只要目标类型的成员都被满足。

把变量传给函数也是同一套判断。函数要什么形状，你就得有哪些成员，名字无关。`implements` 只是把这种检查提前写出来，不写也照样成立，因为它只影响编译期，不产生运行时代码。

```ts
interface HasName { name: string }

function greet(target: HasName): string { return "hi " + target.name; }

class Person { name = "a"; }
greet(new Person());   // 合法，有 name 就够
```

`Person` 没有声明实现 `HasName`，照样能传。结构化类型看成员，不看族谱。

结构化也有代价。两个形状相同的类型会被当成可互换，哪怕业务含义完全不同。要区分身份，只能靠 branded type 这类技巧加一个不会重复的标记。

数组、函数、类都参与形状比较。函数签名也算形状：参数数量、参数类型、返回值类型都在比较范围内。

`class` 的 `private` 会在形状上加一条出处要求：

```ts
class A { private id = 1; }
class B { private id = 1; }

const a = new A();
// const b: B = a;   // error TS2322: Type 'A' is not assignable to type 'B'. Types have separate declarations of a private property 'id'.
```

两个类形状一模一样，仍然不能互赋。私有成员要求来自同一处声明，这是名义类型的规则从这道口子回来了。

这个比喻不成立的地方：`private` 和 `protected` 让形状比较多了一层“谁声明的”判断。孔位全对也不行，插座认牌子了。

## 这套模型失效的地方

地图不是地面。集合模型能解释大多数报错，解释不了编译器故意留的不安全点。类型系统不是完备的，官方在 [TypeScript Design Goals](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals) 里把它列为非目标。

`any` 和断言直接跳过判断：

```ts
const anyValue: any = 1;
const asString: string = anyValue;          // 编译通过，运行时仍是 number

const asserted = 42 as unknown as string;   // 断言同样绕过判断
```

`any` 是主动放弃检查，断言是主动说“我知道得比你多”。两种做法都把人放在了检查器前面，编译器不再验证。断言用错一次，后面所有推导都建立在错误前提上。

`satisfies` 提供了折中。它检查值是否满足某个类型，同时保留值本身的窄类型。需要“有校验但不要放宽类型”时用它，比断言安全。

数组协变是另一个口子。`Dog[]` 能赋给 `Animal[]`，这是读位置的方向，但数组同时是可写位置，于是能往 Dog 数组里塞进一只普通的 Animal：

```ts
class Animal { name = "animal"; }
class Dog extends Animal { bark(): string { return "woof"; } }

const dogs: Dog[] = [new Dog()];
const animals: Animal[] = dogs;
animals.push(new Animal());      // 编译通过

const d: Dog = dogs[1];          // 标注是 Dog
console.log("d 的类型标注是 Dog，实际是", d.constructor.name);
console.log("d.bark()", (d as any).bark);

const rec: Record<string, string> = {};
const missing: string = rec["not-there"];
console.log("missing 的类型标注是 string，实际是", typeof missing);
```

在 Node v26.13.1 下运行：

```bash
node --version
# v26.13.1
node unsafe.ts
# d 的类型标注是 Dog，实际是 Animal
# d.bark() undefined
# missing 的类型标注是 string，实际是 undefined
```

三行输出说明同一件事：类型只描述编译期的集合关系，运行时的对象不看声明。索引签名同理，`Record<string, string>` 承诺任何键都返回 string，实际可能是 `undefined`。

索引签名的口子有开关可关。打开 `noUncheckedIndexedAccess` 后，按键读取的结果会自动加上 `undefined`，调用方必须先判断。这条配置把“集合被高估”的地方收回一部分。

编译通过只是起点。检查器看不到网络返回、用户输入、第三方库内部，这些边界要靠运行时校验补上。类型是把关的第一层，不是唯一一层。

这个比喻不成立的地方：这一节本身就是失效清单。集合模型是理解工具，不是正确性证明。编译通过只说明类型层面自洽，能不能跑对要看代码。

## 读报错的顺序

报错像一句话：你要的集合比实际的窄，或者实际的集合没被要求包含。

先拿到一条真实输出：

```ts
interface Point { x: number; y: number }

function expectPoint(p: Point): number { return p.x; }

expectPoint({ x: 1 });
```

```bash
tsc --noEmit --strict example.ts
# example.ts(5,13): error TS2741: Property 'y' is missing in type '{ x: number; }' but required in type 'Point'.
```

TypeScript 7.0.2 的输出就是这一行。读它的顺序是固定的。

第一步，`(5,13)` 是位置，第 5 行第 13 列，直接跳过去看那个表达式。位置比错误码更有用，因为同一条报错常出现在多个地方，位置指向真正出问题的那一处。

第二步，看错误码。TS2322 是赋值不兼容，TS2345 是实参不兼容，TS2741 是缺必填成员，TS2339 是属性不存在。四个码覆盖了日常大部分报错。

再补三个常见的。TS2344 是类型参数不满足约束，TS2353 是对象字面量里出现了未知属性，TS18048 是被访问的值可能为 undefined。看到这几个码，方向基本能定。

错误码后面那句 `but required in type` 只在缺成员时出现。没有这句时，问题多半是两个类型整体不兼容，去比对集合而不是找缺哪个字段。

第三步，看 `in type A but required in type B` 的方向。A 是实际有的，B 是需要的。方向读反了，改法就会反过来。

两种措辞对应两种毛病。`is not assignable to` 说整体不兼容，`is missing` 说差成员。前者要比对两个集合，后者只要补上缺的那个。

第四步，用集合复述一遍。`{ x: number }` 少了 `y`，集合比 Point 大，可 Point 要求两个成员都有，所以装不下。结论是给对象补上 `y`，或者把 `y` 声明成可选。

改法只有两个方向：改值，或者改声明。先确认哪一边表达了真实意图。值不该有这个形状，就去改值。声明写得太严，就去放宽声明。最糟的做法是在报错那一行反复加断言，把问题往下游推。

一条报错常引发连锁。编译器遇到第一个不兼容就停在那处，后面的表达式跟着报错。先修最靠前、最内层的那条，再看剩下的还在不在。批量修报错时，这个顺序能省很多来回。

报错里出现 `never` 时，通常不是类型真的变成了空集。它多半是某个交叉冲突，或者穷尽检查发现了没处理的分支。先去那一层找“两边同时要求了什么”，比在最后一条报错上来回改快得多。

报错里的类型名有时会展开成结构，工具类型算出来的尤其长。看到一长串对象结构别急着改，先认它对应哪个业务类型，再去比较集合。

集合这个读法不能替你写类型，但能让你在两分钟内说清一条报错在说什么。剩下的工作是决定：是值错了，还是声明错了。

## 用不上的时候

### 排查运行时值与标注不一致

集合模型判断的是声明之间的关系。`Dog[]` 赋给 `Animal[]` 后往里 `push(new Animal())`，`d` 的标注仍是 `Dog`，运行时却是 `Animal`；`Record<string, string>` 读不存在的键，标注是 `string`，实际是 `undefined`。这些位置在集合里合法，要靠值层校验兜住。

### 两个形状相同、含义不同

结构化类型认形状不认名字，`Point` 和 `Vec` 成员一样就能互赋。要区分身份只能加品牌；`private` 成员要求来自同一处声明，这是名义规则回到形状比较里的一处例外。

### 代码里有 any 和断言

`any` 与断言直接跳过判断，集合关系在这两处不成立。断言写错一次，后面所有推导都建立在错误前提上。读报错时先确认有没有 `any` 或 `as` 挡在中间，再谈子集关系。
