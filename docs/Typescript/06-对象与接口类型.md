# 第 6 章 对象与接口类型

后端接口多返回一个字段，前端对象字面量赋值处直接报 TS2353；少一个必填字段报 TS2741。对象类型是业务代码里出现最多的类型。这一章讲 interface 的扩展、索引签名与额外属性检查的规则。

在第 3 章中我们初步了解了 `interface` 和 `type` 的基本用法。这一章深入对象类型的方方面面，包括索引签名、接口继承与声明合并、泛型接口，以及 `interface` 与 `type` 的完整对比和选择策略。

一句话：interface 是一张成员清单，值能不能放进这个变量，看清单上每一项在不在、类型对不对。`const order: { id: string } = { id: "a", extra: 1 }` 报 TS2353，把同一个对象先赋给中间变量再赋值就通过，差别只在字面量有没有直接写在赋值处。这个比喻失效的地方在类：两个类带 private 成员时，形状一样也不能互赋，名字重新参与比较。

## interface 的基本回顾

`interface` 声明描述对象的结构，对象应该具有哪些属性以及每个属性的类型：

```typescript
interface User {
  id: string;
  name: string;
  email: string;
}

const user: User = {
  id: "u_1024",
  name: "Alice",
  email: "alice@example.com",
};
```

全书示例统一用这个 `User`，后面章节直接引用，不再各写一份。形状选 `interface`：需要 `extends` 或声明合并时，它比 `type` 直接。`id` 用 `string`，数据库主键与接口返回的 id 多是字符串，也不会撞上 2^53 的精度上限。`email` 用 `string`，不额外引入格式类型。

interface 成员的写法有 5 种形式：
1. 对象属性：`x: number`
2. 属性索引：`[key: string]: unknown`
3. 方法（简写）：`method(): void`
4. 函数签名（Callable）：`(x: number): string`
5. 构造函数签名（Newable）：`new (x: number): Foo`

前三种在日常开发中使用最多，后两种将在后面的章节中讲解。

## 可选属性与只读属性

```typescript
interface Config {
  url: string;          // 必选
  method?: string;      // 可选
  readonly timeout: number;  // 只读
}
```

- `?` 标记可选，读取时类型会自动包含 `undefined`
- `readonly` 防止赋值后的修改，只在编译时有效

这两种修饰符在 `interface` 和 `type` 中用法完全相同。

## 索引签名

当对象的属性名无法提前确定时，使用**[索引签名（Index Signature）](https://www.typescriptlang.org/docs/handbook/2/objects.html)**来描述"任意键对应某种类型的值"：

```typescript
interface StringDict {
  [key: string]: string;
}

const dict: StringDict = {
  hello: "world",
  foo: "bar",
  // count: 42,  // error TS2322: Type 'number' is not assignable to type 'string'.
};
```

### 支持的索引类型

索引签名的键支持三种类型：`string`、`number`、`symbol`：

```typescript
interface StyledComponents {
  [classSelector: string]: CSSProperties;  // 字符串索引
}

interface NumberArray {
  [index: number]: string;  // 数字索引（数组风格）
}

interface SymbolTable {
  [id: symbol]: string;     // symbol 索引
}
```

### 索引签名与具体属性的约束

一旦定义了索引签名，所有**具体属性的类型**必须与索引签名的值类型兼容：

```typescript
interface MyObj {
  [key: string]: number;  // 值必须是 number
  count: number;          // 正确
  // name: string;  // error TS2411: Property 'name' of type 'string' is not assignable to 'string' index type 'number'.
}
```

这个约束的原因在于：TypeScript 知道通过 `myObj["name"]` 访问时获取的应该是 `number` 类型（根据索引签名），如果具体属性 `name` 的类型是 `string`，就产生了矛盾。

### 数字索引与字符串索引共存的约束

JavaScript 中有一个细节：`obj[0]` 实际上等价于 `obj["0"]`。因此，当数字索引和字符串索引同时存在时，**数字索引的值类型必须是字符串索引值类型的子类型**：

```typescript
interface Mixed {
  [index: number]: string;    // 数字索引：值类型 string
  [key: string]: string | number;  // 字符串索引：值类型 string | number
  // 正确：string 是 string | number 的子类型
}
```

### Record 类型：索引签名的便捷写法

对于"某个键集合对应某个值类型"的常见模式，`Record<K, V>` 更简洁：

```typescript
// 这两种写法等价
interface Dict1 {
  [key: string]: number;
}
type Dict2 = Record<string, number>;

// Record 的使用场景
type UserById = Record<string, User>;
type HttpHeaders = Record<string, string>;
```

`Record` 还能与联合类型键配合，约束"必须有这些键"：

```typescript
type StatusMap = Record<"loading" | "success" | "error", string>;
// 等价于 { loading: string; success: string; error: string; }
```

## interface 独有的特性

### 接口继承

`interface` 可以用 `extends` 继承另一个 interface：

```typescript
interface Animal {
  name: string;
}

interface Dog extends Animal {
  breed: string;
}

const dog: Dog = { name: "Buddy", breed: "Golden Retriever" };
```

可以同时继承多个接口：

```typescript
interface Flyable {
  fly(): void;
}

interface Swimmable {
  swim(): void;
}

// 同时继承多个接口
interface Duck extends Flyable, Swimmable {
  quack(): void;
}

const duck: Duck = {
  fly() {},
  swim() {},
  quack() {},
};
```

`extends` 后面也可以是 `type`（只要它是对象类型）：

```typescript
type Named = { name: string };

interface Employee extends Named {
  salary: number;
}
```

### 声明合并

这是 `interface` 区别于 `type` 的最重要特性：**同名的 interface 会自动合并**：

```typescript
interface Book {
  title: string;
}

interface Book {
  author: string;
}

// 自动合并为：
// interface Book {
//   title: string;
//   author: string;
// }

const book: Book = { title: "TS Handbook", author: "Anders" };
```

声明合并的最大价值在于**扩展已有类型**（这在 `type` 中做不到）：

```typescript
// 扩展全局 Window 对象：在项目中十分常见
declare global {
  interface Window {
    __CUSTOM_CONFIG__: Record<string, unknown>;
  }
}

// 扩展第三方库类型的字段
interface ImportMeta {
  readonly env: Record<string, string>;
}
```

合并规则：
- 同名属性必须类型一致（否则报错）
- 同名方法会按声明的先后顺序进行函数重载叠加
- 非 `export` 的 interface 在全局作用域下才能合并

### 合并发生在绑定期，匹配发生在检查期

同名 interface 合并靠的是编译器读文件时的符号表，不是运行时行为。所有文件读完后，同名的 interface 声明归到同一个符号，成员取并集，检查阶段拿到的已经是一张合并完成的清单。

这解释了三件看起来无关的事。两条同名 interface 给同一属性写了不同类型会报 TS2717，因为合并后属性只有一个位置。`type` 声明不参与合并，同名直接报 TS2300，因为别名只是把名字绑到一个类型表达式，没有成员表可以相加。合并只对未加 `export` 的全局声明生效，因为模块里的同名符号分属各自的表。

为什么不能做成相反的样子：假如类型比较按名字进行，两个形状相同、名字不同的 interface 就不能互赋，前端传字面量、后端返回 JSON 这类写法全都要先造一个名义类型。TypeScript 选择结构比较，代价是名字不提供区分度，需要区分时只能靠 private 成员或 branded type。

继承还有一个方向不对称的地方：`interface Bad extends Shape` 只要求 `Bad` 覆盖 `Shape` 的成员，不检查 `Shape` 这边多出什么。所以子接口可以加成员，不能改类型。加成员不伤害任何已有的使用方，改类型会让父接口的读取承诺失效。这和赋值兼容是同一条规则，只要求「至少有」，不要求「恰好是」。反过来用交叉类型写 `type Bad = Shape & { kind: "square" }`，报的是 TS2322，`kind` 当场被压成 `never`。

依据：[Declaration Merging 一节](https://www.typescriptlang.org/docs/handbook/declaration-merging.html)。符号归并的具体实现函数在 checker 内部，此处按官方文档概述，未引 checker.ts 行号。

### 三个必然撞上的报错

先看三条最小复现，写在同一个文件里：

```ts
interface Cache { mode: string }
interface Cache { mode: number }

type Options = { retry: number };
interface Options { timeout: number }

interface Shape { kind: "circle"; radius: number }
interface Bad extends Shape { kind: "square" }
```

tsc 7.0.2 的输出：

```text
merge.ts(2,19): error TS2717: Subsequent property declarations must have the same type.  Property 'mode' must be of type 'string', but here has type 'number'.
merge.ts(4,6): error TS2300: Duplicate identifier 'Options'.
merge.ts(5,11): error TS2300: Duplicate identifier 'Options'.
merge.ts(8,11): error TS2430: Interface 'Bad' incorrectly extends interface 'Shape'.
  Types of property 'kind' are incompatible.
    Type '"square"' is not assignable to type '"circle"'.
```

TS2717 说的是合并后的属性槽位冲突，改法是把两边类型统一，或者换个属性名。TS2300 是 `type` 与 `interface` 重名，改法是把其中一个改名，或把 `type` 换成 `interface` 让它真正参与合并。TS2430 是子接口改窄了父接口的成员，`kind` 在父接口已经是 `"circle"`，子接口再声明 `"square"` 与父接口矛盾；改法是父接口用联合类型，或拆成互不继承的两个接口。

三条报错背后是同一条规则：合并给出成员清单，继承与赋值只在清单上比类型。

## type 独有的特性

`type`（类型别名）的能力超出了对象结构的范畴：

### 基本类型别名

```typescript
type ID = string;
type Point = [number, number];
```

`interface` 不支持这种用法：它只能声明对象/函数/类的结构。

### 联合类型与交叉类型

```typescript
// 联合类型（interface 不能直接定义）
type Status = "loading" | "success" | "error";

// 交叉类型合并对象
type AdminUser = User & { permissions: string[] };
```

`interface` 的继承（`extends`）在功能上类似交叉类型，但两者有细微区别：当交叉类型的两个成员有同名属性时，结果取决于属性的具体类型；而 `extends` 遇到同名属性类型冲突时会直接报错。

### 映射类型和条件类型

这是 type 真正不可替代的地方：

```typescript
// 将 T 的所有属性变为只读
type Readonly<T> = {
  readonly [K in keyof T]: T[K];
};

// 提取函数返回值类型
type ReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
```

这些将在第 15、16 章详细展开。

## interface vs type 的全面对比

| | interface | type |
|------|-----------|------|
| 描述对象结构 | ✅ | ✅ |
| 描述函数签名 | ✅ | ✅ |
| 描述类结构 | ✅ | ✅ (含构造签名) |
| 继承/扩展 | `extends`（可多继承） | `&` 交叉类型 |
| 声明合并 | ✅ 同名自动合并 | ❌ 不允许重复 |
| 定义联合类型 | ❌ | ✅ |
| 定义基本类型别名 | ❌ | ✅ |
| 使用映射/条件类型 | ❌ | ✅ |
| 在错误信息中的名称显示 | 始终显示原名 | 可能被展开为匿名类型 |
| 编译器性能 | `extends` 检查更快 | 交叉类型需要展开 |

### 何时用哪个

官方的建议（[Everyday Types 原文](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html)）是：**"在 interface 能满足需求时优先用 interface，直到你需要 type 独有的功能"**。

这个建议背后有两个工程理由：

1. **性能更好**：TypeScript 内部对 `interface extends` 有专门的缓存机制，而交叉类型每次都需要重新计算所有成员的兼容性。在大型项目中，频繁使用 `&` 做复杂交叉会拖慢类型检查。
2. **错误信息更友好**：`interface` 在报错时会始终显示接口名称（如 `Type 'X' is not assignable to type 'User'`），而 `type` 别名在复杂组合中可能被展开为一长串匿名类型，难以定位问题。

在实践中，一个被广泛接受的策略是：
- **描述对象、类、函数的形状** → 用 `interface`
- **类型计算（联合、映射、工具类型）** → 用 `type`
- **需要声明合并（扩展全局类型、第三方库）** → 必须用 `interface`
- **函数签名** → 用 `type`（TypeScript 官方文档的标准做法）

在两个都能满足的场景，个人/团队风格选一个保持一致即可。React 社区中 `type` 比 `interface` 更常见，Node.js 社区则偏好 `interface`。

## 泛型接口

接口中的属性类型可以通过泛型参数来控制：

```typescript
interface ApiResponse<T> {
  code: number;
  data: T;
  message: string;
}

// 使用时指定具体类型
const userRes: ApiResponse<User> = {
  code: 200,
  data: { id: "u_1024", name: "Alice", email: "alice@example.com" },
  message: "ok",
};

const listRes: ApiResponse<string[]> = {
  code: 200,
  data: ["a", "b", "c"],
  message: "ok",
};
```

泛型接口可以嵌套使用：

```typescript
interface PaginatedResponse<T> {
  items: T[];
  total: number;
  page: number;
}

// 分页的用户列表
type UsersPage = PaginatedResponse<User>;
```

## 额外属性检查（Excess Property Checking）

对象字面量在直接赋值给有类型标注的变量时，TypeScript 会执行**额外属性检查**，多出的属性会报错：

```typescript
interface Person {
  name: string;
  age: number;
}

const p: Person = { name: "Alice", age: 25, height: 170 };  // error TS2353: Object literal may only specify known properties, and 'height' does not exist in type 'Person'.
```

这个检查是为了防止一种常见的场景：对象字面量中的拼写错误。比如你不小心把 `active` 写成了 `activ`，如果没有额外属性检查，这个错误会静默通过。

如果你确实需要额外属性的对象，有几种解决方法：

```typescript
// 方案一：先赋给中间变量（绕过对象字面量检查）
const temp = { name: "Alice", age: 25, height: 170 };
const p1: Person = temp;  // 正确

// 方案二：使用索引签名
interface FlexiblePerson {
  name: string;
  age: number;
  [key: string]: unknown;  // 允许任意额外属性
}

const p2: FlexiblePerson = { name: "Alice", age: 25, height: 170 };  // 正确

// 方案三：类型断言
const p3 = { name: "Alice", age: 25, height: 170 } as Person;  // 正确
```

## 小结

- `interface` 和 `type` 在描述对象结构时功能大部分重叠，但有各自的专属能力
- **索引签名**用 `[key: string]: V` 描述"任意键对应某种值"的模式
- `interface` 支持**继承**（`extends`）和**声明合并**，后者是扩展全局/第三方类型的利器
- `type` 支持联合类型、交叉类型、基本类型别名和类型计算（映射/条件类型）
- `Record<K, V>` 是索引签名的便捷语法糖
- 对象字面量的**额外属性检查**是防止拼写错误的刻意设计

## 用不上的时候

### 类实例有私有字段

`private` 成员让类型比较变成名义比较，两个结构相同的类不能互相赋值。interface 描述不了这种约束。

### 动态键的配置表

索引签名让每个键的值类型相同，拼错键名不报错。读取结果还可能是 `undefined`，需要 [`noUncheckedIndexedAccess`](https://www.typescriptlang.org/tsconfig)。

### 需要类型运算

联合、映射、条件类型都写不进 interface。这时用 `type`。
