# 第 46 章 类型层的设计模式

类型系统能做的不只是给变量贴标签。它还能表达「这个订单号来自哪里」「这笔转账处于哪个状态」「这个函数接受哪种容器」。这些约束不改变运行时，只在编译期成立。

模式的前提是类型擦除。类型只在检查阶段存在，emit 之后全部消失。所以每个模式都是「编译期约束加运行时空壳」。约束越强，边界处需要的构造和转换就越多。

这一章讲七种模式在 TypeScript 里怎么实现，重点是为什么能挡住错误，以及什么时候不该用。每次报错都用 TypeScript 7.0.2 实际编译过，括号里是真实错误码。

## 一、结构化类型的盲区

TypeScript 比较两个对象类型时，逐成员看兼容性。类型的名字不参与比较，来源也不参与。

```ts
interface Payment {
  amountCents: number;
}

class Refund {
  constructor(readonly amountCents: number) {}
}

function charge(payment: Payment): void {
  console.log(payment.amountCents);
}

charge(new Refund(1200));

interface Coupon {
  amountCents: number;
  code: string;
}

const coupon: Coupon = { amountCents: 500, code: "NEW100" };
charge(coupon);

const withExtra = { amountCents: 100, code: "NEW100" };
charge(withExtra);
```

`Refund` 是类，`Coupon` 是接口，两者都能传给 `charge`。`withExtra` 多了一个 `code` 字段，同样通过。多余属性检查只对直接写在调用处的对象字面量生效，先赋给变量再传就不检查。它是局部规则，不是后台保护。机制在「新鲜度」：编译器给对象字面量打一个内部标记，赋值时额外检查属性名是否都存在于目标类型。变量没有这个标记，走常规的子类型兼容。所以多写字段能否被拦住，取决于值是不是刚写的字面量，与类型本身无关。

这意味着付款金额、退款金额、优惠券金额在类型层是同一个东西。函数签名里写 `Payment`，调用方传什么都能进。要区分，只能在类型层加结构上真实存在的差异。

运行时也帮不上忙。断言、品牌、状态标记在 emit 时全部删除。下面这段在运行时看不到任何品牌痕迹：

```ts
declare const orderBrand: unique symbol;

type OrderId = string & { readonly [orderBrand]: "OrderId" };

const orderId = "ord_1" as OrderId;
console.log(typeof orderId, JSON.stringify(orderId), orderId.toUpperCase());
console.log(Object.keys(orderId), Object.getOwnPropertySymbols(Object(orderId)).length);
```

```bash
$ node brand-runtime.js
string "ord_1" ORD_1
[ '0', '1', '2', '3', '4' ] 0
```

`typeof` 是 string，JSON 序列化是普通字符串，`Object.keys` 拿到的是字符串下标，符号属性为零。品牌只活在类型里。

## 二、品牌类型

### 交叉类型加 unique symbol

最常用的一种写法，用交叉类型加一个只有类型层存在的属性。

```ts
declare const orderBrand: unique symbol;

type OrderId = string & { readonly [orderBrand]: "OrderId" };
type UserId = string & { readonly [orderBrand]: "UserId" };

declare function asOrderId(raw: string): OrderId;
declare function asUserId(raw: string): UserId;

const orderId = asOrderId("ord_1");
const asText: string = orderId;

const raw: OrderId = "ord_2";
const cross: OrderId = asUserId("u_1");
```

`asText` 那行通过，品牌是 string 的子类型，可以往回退。后两行报错：

```text
error TS2322: Type 'string' is not assignable to type 'OrderId'.
  Type 'string' is not assignable to type '{ readonly [orderBrand]: "OrderId"; }'.
error TS2322: Type 'UserId' is not assignable to type 'OrderId'.
  Type 'UserId' is not assignable to type '{ readonly [orderBrand]: "OrderId"; }'.
    Types of property '[orderBrand]' are incompatible.
      Type '"UserId"' is not assignable to type '"OrderId"'.
```

报错链说明了比较过程。目标是交叉类型，源必须同时满足 `string` 和 `{ readonly [orderBrand]: "OrderId" }`。普通字符串没有这个符号属性，第一层就失败。源类型的每个必需属性都要在目标里存在且兼容。`OrderId` 是交叉类型，展开后有两组属性：字符串的成员和那个符号属性。字符串成员这一层直接通过，符号属性在源里不存在，所以失败。换成 `UserId`，符号属性的键相同，属性值的字面量类型不同，比较继续下钻一层才失败。键相同是前提，`unique symbol` 的键在类型层唯一，两个不同声明的符号永远对不上。

唯一的构造入口是 `asOrderId`。它可以在内部检查格式，然后断言一次。所有订单号都从这里产生，错误的来源就在运行时被切断。

交叉类型不引入包装。`OrderId` 的值就是那个字符串，`typeof` 仍然是 string，`instanceof` 和 `in` 都查不出品牌。运行时不占额外字节，也不做任何校验。保护全部来自构造入口的约定：构造器之外只允许读取，不允许伪造。约定靠代码评审保证，类型系统只保证「没走构造入口的值进不来」。

### unique symbol 的唯一性

`unique symbol` 是一个只有一个值的类型，值就是那个符号本身。它只能出现在 `const` 声明或类的 `static readonly` 属性上。写成 `let mutable: unique symbol` 报 `TS1332`，提示变量必须是 const；写进索引签名报 `TS1335`，提示这里不允许 unique symbol 类型。`unique symbol` 在 [TypeScript 2.7 发布说明](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-7.html) 里引入。

符号做属性键时，键本身是类型的一部分。两个独立的符号声明是不同的键，结构上无法互相满足。

```ts
const orderTag = Symbol("order");
const userTag = Symbol("user");

interface OrderTagged {
  readonly [orderTag]: "order";
  readonly value: string;
}

const tagged: OrderTagged = { [orderTag]: "order", value: "ord_1" };
const wrong: OrderTagged = { [userTag]: "order", value: "ord_1" };  // error TS2353: Object literal may only specify known properties, and '[userTag]' does not exist in type 'OrderTagged'.
```

`wrong` 报 `TS2353`，对象字面量里的 `[userTag]` 被当作未知属性。换成变量就能绕过多余属性检查，但缺的仍然是 `[orderTag]` 这个属性，报 `TS2741`。符号值不在作用域里，外部代码无法凭空构造这个属性。

跨模块共享品牌时，要导出符号声明本身，而不是各自用 `Symbol.for` 取同一个符号。`Symbol.for` 在运行时返回注册表里的同一个符号，类型层却是两个不同的 `unique symbol` 类型。

```ts
const first = Symbol.for("lock");
const second = Symbol.for("lock");

const sameType: typeof first = second;  // error TS2322: Type 'typeof second' is not assignable to type 'typeof first'.
if (first === second) {  // error TS2367: This comparison appears to be unintentional because the types 'typeof first' and 'typeof second' have no overlap.
  console.log("运行时为 true");
}
```

`sameType` 报 `TS2322`，`Type 'typeof second' is not assignable to type 'typeof first'`；比较报 `TS2367`，提示两个类型没有重叠。运行时确实相等，类型层坚持认为它们没有重叠。这是类型系统按声明而不是按值工作的直接后果。

### interface 加 unique symbol

把符号属性放进接口，再用交叉类型组合。机制和上一种相同。声明 `interface Tagged<B extends string> { readonly [userTag]: B }`，再写 `type UserId = string & Tagged<"UserId">`，任何普通字符串赋给 `UserId` 都报 `TS2322`，报错链指向 `Tagged<"UserId">`。写法上的区别在声明合并：接口可以被其他模块扩展，类型别名不能。品牌符号从包里导出时，接口写法给外部留了扩展点。多数情况下这恰恰是缺点，外部加一个必填成员，包里已有的值就全部不满足。

### class 私有字段

类也能做品牌。两个类各自声明私有成员时，兼容性要求私有成员来自同一处声明。这条规则是名义性的残留。编译器看不到私有成员的实现，无法按结构比较两个私有成员是否兼容，于是要求它们来自同一声明。`protected` 成员同理。子类继承同一个声明，所以子类实例与父类实例可以互相赋值。`#` 字段比 `private` 更严：每个 `#tag` 声明都是独立成员，同一份源码里的两处声明也不共享，报错里直接说「指向了不同的成员」。

```ts
class OrderId {
  private readonly __tag!: void;
  constructor(readonly value: string) {}
}

class UserId {
  private readonly __tag!: void;
  constructor(readonly value: string) {}
}

declare function loadOrder(id: OrderId): void;
declare function loadUser(id: UserId): void;

loadOrder(new UserId("u_1"));
const literal: OrderId = { value: "ord_2" };
```

两处报错：

```text
error TS2345: Argument of type 'UserId' is not assignable to parameter of type 'OrderId'.
  Types have separate declarations of a private property '__tag'.
error TS2741: Property '__tag' is missing in type '{ value: string; }' but required in type 'OrderId'.
```

私有成员的声明来源不同，直接判定不兼容，比较在私有成员这一步就结束。对象字面量无法构造缺失的私有属性。

私有成员不会阻止类实例赋给结构接口。目标类型没有声明私有成员，只比较公开成员。

```ts
class OrderId {
  private readonly __tag!: void;
  readonly value = "ord_1";
}

interface HasValue {
  readonly value: string;
}

function log(value: HasValue): void {
  console.log(value.value);
}

log(new OrderId());
```

这段通过。品牌的保护只在「双方都是同一个类」或者「目标类型提到了私有成员」时生效。一旦中间经过一个宽松接口，品牌就丢了。保护不传递。接口 `HasValue` 只要求 `value: string`，私有成员不在它的描述范围内，类实例可以赋给它，拿到接口的地方就只剩公开结构。品牌类型不要出现在宽松接口的另一侧；泛型边界、参数、返回值都要写带品牌的类型，写成接口等于放弃保护。

`private` 和 `#` 的区别在运行时。`private` 是编译期修饰符，emit 后是普通属性，键名可见。`new OrderId("ord_1")` 的 `Object.keys` 输出 `[ 'value', '__tag' ]`，`"__tag" in order` 为 true，值是 undefined；JSON 序列化丢掉 undefined，所以只看到 `{"value":"ord_1"}`。字段真实存在，只是类型层禁止访问。`#` 字段的规则见 [TypeScript Handbook 的类一节](https://www.typescriptlang.org/docs/handbook/2/classes.html)。

换成 `#tag`：

```ts
class OrderId {
  readonly #tag = "order";
  constructor(readonly value: string) {}
}

class UserId {
  readonly #tag = "user";
  constructor(readonly value: string) {}
}

declare function loadOrder(id: OrderId): void;
loadOrder(new UserId("u_1"));
```

报错文本只提到私有成员不同：

```text
error TS2345: Argument of type 'UserId' is not assignable to parameter of type 'OrderId'.
  Property '#tag' in type 'UserId' refers to a different member that cannot be accessed from within type 'OrderId'.
```

运行时 `#tag` 真实存在但不可枚举，`Object.keys` 只返回 `[ 'value' ]`，外部无法读写，`#tag in order` 只能在类内部使用。

### 三种写法怎么选

| 写法 | 运行时痕迹 | `as` 能否伪造 | 构造方式 | 适用场合 |
|---|---|---|---|---|
| 交叉类型加符号 | 无 | 能，或在边界断言 | 构造函数或 as | 内部 ID、金额、字符串键 |
| interface 加符号 | 无 | 能 | 同上 | 需要声明合并的库 |
| class 私有成员 | 有实例，字段可见 | 不能，报 TS2352 | new 或工厂 | 跨模块强约束 |
| class 加 `#` 字段 | 有实例，不可枚举 | 不能 | new 或工厂 | 同上，且防篡改 |

class 写法挡住 `as` 是实际优势。对私有字段品牌的类，`"ord_1" as OrderId` 报 `TS2352`，提示两个类型没有充分重叠，要先转 unknown；`"ord_1" satisfies OrderId` 报 `TS1360`。`as unknown as` 仍然能绕过，类型断言本来就是逃生门，`satisfies` 只校验不改变类型。

交叉类型能挡住普通赋值，挡不住 `as`，JSON 边界更能说明问题。`JSON.parse` 返回 any，any 可以赋给任何类型，`const fromJson: OrderId = JSON.parse('"ord_2"')` 编译通过，哪怕解析出来的是数字。显式标成 `unknown` 之后再赋给品牌类型，报 `TS2322`，因为 unknown 必须先收窄。解析边界上的校验不能省，品牌只是把校验结果带进类型系统，本身不做校验。

### 品牌的代价

每个品牌都要构造和剥离。函数边界一多，代码里全是 `asOrderId`、`orderId.value` 这类转换。公共 API 暴露品牌，调用方必须导入构造器，否则没法传参。

品牌不传播运算。金额品牌相加得到 number，要重新构造；单位品牌乘除同样回退。这个问题在下一节展开。

经验规则：只给「跨三个以上模块、曾经混用过、混用的后果需要人工排查」的值加品牌。一个模块内部用的 ID，参数命名和 code review 足够。

## 三、幽灵类型与单位

单位是品牌最常见的应用。米和秒在运行时都是 number，类型层可以分开。

```ts
declare const metersBrand: unique symbol;
declare const secondsBrand: unique symbol;

type Meters = number & { readonly [metersBrand]: "Meters" };
type Seconds = number & { readonly [secondsBrand]: "Seconds" };

declare function meters(value: number): Meters;
declare function seconds(value: number): Seconds;
declare function addMeters(a: Meters, b: Meters): Meters;

const distance = meters(12.5);
addMeters(distance, seconds(3));
```

报错链指出缺少的是对方的品牌属性：

```text
error TS2345: Argument of type 'Seconds' is not assignable to parameter of type 'Meters'.
  Type 'Seconds' is not assignable to type '{ readonly [metersBrand]: "Meters"; }'.
    Property '[metersBrand]' is missing in type 'Number & { readonly [secondsBrand]: "Seconds"; }' but required in type '{ readonly [metersBrand]: "Meters"; }'.
```

加减乘除会把品牌丢掉。

```ts
declare const metersBrand: unique symbol;
type Meters = number & { readonly [metersBrand]: "Meters" };
declare function meters(value: number): Meters;
declare const distance: Meters;

const sum = meters(1) + meters(2);
const asMeters: Meters = sum;  // error TS2322: Type 'number' is not assignable to type 'Meters'.
const doubled: Meters = distance * 2;  // error TS2322: Type 'number' is not assignable to type 'Meters'.
```

`sum` 的类型是 number，`asMeters` 和 `doubled` 都报 `TS2322`。每个运算结果都要经过一次 `meters(...)` 重新打包，这是品牌不适合高频算术的数值的原因。品牌数字是 `number` 的子类型，方向只能是品牌到 number。加法和乘法接收 number，返回 number，品牌信息在运算里丢失。需要连续运算时，要么每次运算后重新构造，要么把数值装进带方法的对象，让方法返回带单位的对象。前者留下大量构造调用，后者多一层运行时对象和序列化逻辑。

可选属性不能当幽灵字段用。

```ts
interface Measured<T, Unit extends string> {
  readonly value: T;
  readonly unit?: Unit;
}

const noUnit: Measured<number, "m"> = { value: 3 };
const wrongUnit: Measured<number, "m"> = { value: 3, unit: "s" };  // error TS2322: Type '"s"' is not assignable to type '"m"'.
const stillWorks: Measured<number, "s"> = { value: 3 };
```

`wrongUnit` 报 `TS2322`，`noUnit` 和 `stillWorks` 都通过。可选属性可以省略，对象字面量不带 `unit` 时能匹配任意单位。保护只在写了 `unit` 值的赋值上生效，构造时反而失效。

要强制，必须用品牌，或者用必填的只读字段加构造器。

幽灵字段把约束编码成类型参数，不进入运行时形状。`Unit` 只参与比较，`unit` 是可选属性，所以 `Measured<number, "m">` 的值可以省略它，保护在省略处失效。要保留约束，`unit` 必须写成必填只读，或者改用品牌。

校验库的品牌接口走同一个机制。zod 4 的 brand 给输出类型交叉一个符号属性，解析成功后带上品牌，之后在模块之间传递。运行时 schema 校验，类型层标记，两者分工。

非空字符串是另一类常见约束。

```ts
declare const nonEmptyBrand: unique symbol;
type NonEmptyString = string & { readonly [nonEmptyBrand]: "NonEmptyString" };

function nonEmpty(raw: string): NonEmptyString | null {
  return raw.length > 0 ? (raw as NonEmptyString) : null;
}

const parsed = nonEmpty("hello");
if (parsed !== null) {
  console.log(parsed.toUpperCase());
}

const forged: NonEmptyString = "" as NonEmptyString;
const fake = "hello" satisfies NonEmptyString;  // error TS1360: Type 'string' does not satisfy the expected type 'NonEmptyString'.
```

`fake` 报 `TS1360`。`forged` 通过，`as` 是逃生门。空字符串能进入类型系统，只在代码里没有任何断言时成立。

校验库和品牌的结合点是「解析一次，之后传已校验的值」。schema 负责运行时校验，`parse` 的结果在类型上带品牌或收窄类型。品牌本身不是校验，它只是给校验结果做标记。把标记放在跨模块边界上，内部函数就不用重复校验。

过度品牌化的成本容易被低估。一个服务里二十个品牌，每个都要构造器、导入、转换；新人看代码先要理解二十个类型的关系；团队里不同人定义不同品牌的同名类型，最后靠 `as` 强行串起来。品牌的收益来自「少而关键」，不是「多而全」。

## 四、类型级状态机

状态机的目标是把非法迁移变成类型错误。做法是用联合表示状态，用一张映射表表示允许的迁移。

```ts
type TransferState = "pending" | "settled" | "failed";

interface Transfer<S extends TransferState> {
  readonly id: string;
  readonly amountCents: number;
  readonly state: S;
}

interface NextState {
  pending: "settled" | "failed";
  settled: never;
  failed: never;
}

declare function transition<S extends TransferState, T extends NextState[S]>(
  transfer: Transfer<S>,
  next: T,
): Transfer<T>;

declare const pendingTransfer: Transfer<"pending">;
declare const settledTransfer: Transfer<"settled">;

const settled = transition(pendingTransfer, "settled");
const again = transition(pendingTransfer, "pending");
transition(settledTransfer, "failed");
transition(settled, "failed");
```

`settled` 那行通过。后三行分别报错：

```text
error TS2345: Argument of type '"pending"' is not assignable to parameter of type '"failed" | "settled"'.
error TS2345: Argument of type '"failed"' is not assignable to parameter of type 'never'.
error TS2345: Argument of type '"failed"' is not assignable to parameter of type 'never'.
```

`S` 从第一个参数推断为 `"pending"`，`NextState["pending"]` 是 `"settled" | "failed"`，`T` 被约束在这个联合里。传 `"pending"` 不在联合内，报错文本列出候选。推断顺序是先由第一个实参定 `S`，再用 `NextState[S]` 算 `T` 的约束。`S` 是单个状态时，索引访问得到一个具体的联合；`S` 是 `TransferState` 时，索引访问把三个成员的结果再联合，`never` 在联合里被吸收，约束变成 `"settled" | "failed"`。never 在约束位置表示空集，任何值都不满足。类型系统没有「禁止」这个语义，只能用空集表达。

`settled` 和 `failed` 是终态，映射到 never。never 没有任何值，任何实参都不能满足约束，报错文本里出现 never。读报错的人需要知道 never 在这里表示「不允许迁移」，这个信息只能写进文档。

实现里没有校验。

```ts
type TransferState = "pending" | "settled" | "failed";

interface Transfer<S extends TransferState> {
  readonly id: string;
  readonly amountCents: number;
  readonly state: S;
}

interface NextState {
  pending: "settled" | "failed";
  settled: never;
  failed: never;
}

function transition<S extends TransferState, T extends NextState[S]>(
  transfer: Transfer<S>,
  next: T,
): Transfer<T> {
  return { ...transfer, state: next };
}

const pendingTransfer: Transfer<"pending"> = { id: "t_1", amountCents: 1200, state: "pending" };
const settled = transition(pendingTransfer, "settled");
console.log(settled.state, settled.id);

const forged = { ...pendingTransfer, state: "settled" } as Transfer<"settled">;
console.log(forged.state);
```

```bash
$ node fsm.js
settled t_1
settled
```

函数只做对象拷贝和状态覆盖。泛型在运行时不存在，`as` 也能伪造。类型层挡住的是手写调用，挡不住数据来源。

最明显的漏洞是联合状态。

```ts
type TransferState = "pending" | "settled" | "failed";

interface Transfer<S extends TransferState> {
  readonly id: string;
  readonly amountCents: number;
  readonly state: S;
}

interface NextState {
  pending: "settled" | "failed";
  settled: never;
  failed: never;
}

declare function transition<S extends TransferState, T extends NextState[S]>(
  transfer: Transfer<S>,
  next: T,
): Transfer<T>;

declare const stored: Transfer<TransferState>;

transition(stored, "settled");
transition(stored, "failed");
```

两行都通过。`S` 推断为 `TransferState`，`NextState[TransferState]` 展开成三个状态的迁移目标联合，等于 `"settled" | "failed"`。状态机认为「可能是任意状态，那就允许任意目标」。

从数据库或 JSON 读回来的转账，类型通常是 `Transfer<TransferState>` 或更宽。必须先运行时收窄，拿到精确状态，才能进入状态机。收窄靠类型谓词，声明 `declare function isSettled(transfer: Transfer<TransferState>): transfer is Transfer<"settled">`。有了这个类型谓词，收窄后的值才能调 `transition`。类型谓词本身要写对，写错等于绕过。

代价集中在维护上。迁移表是手写的类型，业务加一个状态，要改联合、改映射表、改所有 switch，漏改的地方由编译器指出来。错误信息里出现 never 和联合候选，对不熟悉实现的同事不友好。持久化数据可能带有历史状态，反序列化后要重新校验。

值得用的场合：状态集合稳定、迁移路径少、非法迁移代价高。支付、订单、审批流符合。频繁改版的业务流程不适合，类型表会变成负担。

## 五、链式 Builder

Builder 的常见需求是「必填字段没填完时，不能调用 build」。直觉写法是给 build 加 this 参数。

```ts
interface QuerySpec {
  table: string;
  limit: number;
  orderBy: string;
}

class QueryBuilder<Present extends keyof QuerySpec = never> {
  build(this: QueryBuilder<keyof QuerySpec>): QuerySpec {
    return { table: "", limit: 0, orderBy: "" };
  }
}

const incomplete = new QueryBuilder<"table">();
incomplete.build();
```

这段编译通过，检查没生效。this 参数声明的类型是 `QueryBuilder<keyof QuerySpec>`，调用时检查接收者能否赋给它。`Present` 只出现在类型参数位置，没有进入任何成员类型，于是两个实例的结构完全相同；方法比较又是双变的，strictFunctionTypes 不影响方法简写。结构类型不看名义，类型参数不落到成员上就等于不存在，检查无对象可比。

结论：光给 build 加 this 参数不够。类型参数必须出现在结构里，检查才有比较对象。

可行的写法是把「已经调用的字段」累积到类型上，再用条件类型决定 build 是否存在。

```ts
interface QuerySpec {
  table: string;
  limit: number;
  orderBy: string;
}

type Missing<Has extends keyof QuerySpec> = Exclude<keyof QuerySpec, Has>;

type QueryBuilder<Has extends keyof QuerySpec = never> = {
  table(table: string): QueryBuilder<Has | "table">;
  limit(limit: number): QueryBuilder<Has | "limit">;
  orderBy(column: string): QueryBuilder<Has | "orderBy">;
} & ([Missing<Has>] extends [never] ? { build(): QuerySpec } : {});

declare function builder(): QueryBuilder;

const complete = builder().table("orders").limit(20).orderBy("id").build();
builder().table("orders").build();
```

完整链通过。缺字段的链报 `TS2339`：

```text
error TS2339: Property 'build' does not exist on type '{ table(table: string): ...; limit(limit: number): ...; orderBy(column: string): ... }'.
```

`Missing<Has>` 算出还没调用的字段；`[Missing<Has>] extends [never]` 判断集合是否为空。外面包一层元组是为了避免条件类型分布，`Has` 是联合时判定才稳定。完成态类型是方法集合加 `build`，未完成态只有方法集合。类型层不执行，只归约。每调用一次方法，返回类型就是新的交叉类型，`Has` 累加一个键，`build` 是否出现由条件类型决定。

报错的缺点是不说缺哪个字段，只说 build 不存在。要在报错里列缺失字段，可以让条件分支返回一个带 `missing` 属性的对象类型，但调用处就得改成接收这个对象，API 变复杂。

Builder 的代价在类型体积，链越长，悬停和报错越长。步骤顺序可以自由累积，这一点比固定顺序的分步接口好，但类型层没有记录「哪个方法已经调用过」以外的信息。

必填字段三个以内、且是库的公开 API 时，这种写法值得。内部代码用 options 对象加运行时校验更省事：`interface QueryOptions { table: string; limit: number; orderBy: string }`，调用处 `query({ table: "orders", limit: 20, orderBy: "id" })`，参数缺字段或类型不符都会立刻报错。字段少的时候，一个对象参数加 `satisfies` 校验，可读性和报错都更好。

## 六、类型安全的事件总线

事件总线要保证两件事：`on` 注册的 handler 参数类型与事件名对应，`emit` 的 payload 类型与事件名对应。

```ts
interface Events {
  "order:paid": { orderId: string; amountCents: number };
  "user:created": { userId: string };
}

type Payload<K extends keyof Events> = Events[K];

declare class EventBus {
  on<K extends keyof Events>(event: K, handler: (payload: Payload<K>) => void): void;
  emit<K extends keyof Events>(event: K, payload: Payload<K>): void;
}

const bus = new EventBus();

bus.on("order:paid", (payload) => {
  console.log(payload.orderId, payload.amountCents);
});

bus.emit("order:paid", { orderId: "o_1", amountCents: 1200 });
```

handler 的 `payload` 由上下文推断成 `Events["order:paid"]`。`emit` 的第二个参数按同一个索引检查。

写错的三种情况都能拦住：

```ts
interface Events {
  "order:paid": { orderId: string; amountCents: number };
  "user:created": { userId: string };
}

type Payload<K extends keyof Events> = Events[K];

declare class EventBus {
  on<K extends keyof Events>(event: K, handler: (payload: Payload<K>) => void): void;
  emit<K extends keyof Events>(event: K, payload: Payload<K>): void;
}

const bus = new EventBus();

bus.emit("order:paid", { orderId: "o_1" });
bus.emit("refund:issued", { orderId: "o_1" });

bus.on("order:paid", (payload: { userId: string }) => {
  console.log(payload.userId);
});
```

三段报错：

```text
error TS2741: Property 'amountCents' is missing in type '{ orderId: string; }' but required in type '{ orderId: string; amountCents: number; }'.
error TS2345: Argument of type '"refund:issued"' is not assignable to parameter of type 'keyof Events'.
error TS2345: Argument of type '(payload: { userId: string; }) => void' is not assignable to parameter of type '(payload: { orderId: string; amountCents: number; }) => void'.
  Types of parameters 'payload' and 'payload' are incompatible.
    Property 'userId' is missing in type '{ orderId: string; amountCents: number; }' but required in type '{ userId: string; }'.
```

第三条是函数参数的逆变检查。`on` 声明要求 handler 能接受完整 payload，传入的 handler 只接受 `{ userId }`，调用方可能传不带 userId 的值，所以不兼容。这条规则和 `strictFunctionTypes` 下的函数类型一致。

实现时存储必须擦除。Map 的值类型不可能对不同事件名保持泛型，只能存成统一的函数类型。

```ts
interface Events {
  "order:paid": { orderId: string; amountCents: number };
  "user:created": { userId: string };
}

type Payload<K extends keyof Events> = Events[K];

class EventBus {
  readonly #handlers = new Map<keyof Events, Array<(payload: never) => void>>();

  on<K extends keyof Events>(event: K, handler: (payload: Payload<K>) => void): void {
    const list = this.#handlers.get(event) ?? [];
    list.push(handler as (payload: never) => void);
    this.#handlers.set(event, list);
  }

  emit<K extends keyof Events>(event: K, payload: Payload<K>): void {
    const list = this.#handlers.get(event) ?? [];
    for (const handler of list) {
      (handler as unknown as (payload: Payload<K>) => void)(payload);
    }
  }
}

const bus = new EventBus();
bus.on("order:paid", (payload) => console.log("paid", payload.orderId, payload.amountCents));
bus.on("user:created", (payload) => console.log("user", payload.userId));
bus.emit("order:paid", { orderId: "o_1", amountCents: 1200 });
bus.emit("user:created", { userId: "u_1" });
```

```bash
$ node bus.js
paid o_1 1200
user u_1
```

两处 `as` 是类型擦除的代价。Map 里存的是 `(payload: never) => void`，注册时把具体 handler 收窄成统一类型，分发时再还原成 `Payload<K>`。安全性依赖一个前提：注册和分发用同一张表，中间没有跨模块的字符串拼接。

和类型层的路由表相比，事件总线多了运行时容器。路由表的做法是从路径字符串算出参数和响应类型，没有注册动作，也没有 Map。事件总线必须保存 handler，类型只出现在 `on` 和 `emit` 的签名上，容器内部没有类型信息。

| 对比项 | 路由表 | 事件总线 |
|---|---|---|
| 类型来源 | 路径字面量推出参数和响应 | 事件名索引 payload 映射表 |
| 运行时容器 | 无 | 有，必须擦除 |
| 扩展方式 | 加一行类型 | 加一行类型，或模块增强 |
| 未知键 | 类型层拒绝 | 类型层拒绝，运行时静默 |

运行时静默是实际风险。`emit` 的事件名如果来自配置或网络，类型检查在运行时不存在，没有 handler 就直接丢掉。事件总线通常要加日志和默认 handler，把未注册的事件暴露出来。

`on` 和 `emit` 把事件名与 payload 绑在同一个 `K` 上。`K` 同时约束两边，写错一个，另一个跟着错。handler 是属性风格的函数类型，strictFunctionTypes 下参数按逆变检查。这也是为什么拿 `user:created` 的 handler 去监听 `order:paid` 会被拒绝。

## 七、HKT 模拟

想写一个对任意容器通用的 `map`，直觉写法是这样的：

```ts
interface Functor<F> {
  map<A, B>(fa: F<A>, f: (a: A) => B): F<B>;  // error TS2315: Type 'F' is not generic.
}
```

这行不通，报 `TS2315: Type 'F' is not generic.`。

TypeScript 的类型参数只能填完整类型，不能填「类型构造器」。`F<A>` 要求 F 本身是泛型，而 F 在声明里只是一个普通类型参数。语言层没有高阶类型量化。

社区的做法是把类型构造器编码成字符串键加映射接口。`URItoKind<A>` 给每个构造器定义一个成员，表示「给定 A 得到的类型」；`keyof` 得到名字集合；索引访问还原。`Apply<F, A>` 展开成 `URItoKind<A>[F]`。`F` 是字面量键时，索引访问立即得到具体类型；`F` 是类型参数时，求值推迟，等推断。推断失败的原因在位置：类型参数推断只看实参对应的参数类型，`F` 藏在索引访问里面，实参 `Maybe<number>` 无法反推出 `"Maybe"`。`A` 也因为同样的原因退化成 unknown。

```ts
type Maybe<A> = { readonly tag: "none" } | { readonly tag: "some"; readonly value: A };

interface URItoKind<A> {
  Maybe: Maybe<A>;
  List: ReadonlyArray<A>;
}

type URIS = keyof URItoKind<unknown>;
type Apply<F extends URIS, A> = URItoKind<A>[F];

interface Functor<F extends URIS> {
  map<A, B>(fa: Apply<F, A>, f: (a: A) => B): Apply<F, B>;
}

const maybeFunctor: Functor<"Maybe"> = {
  map: (fa, f) => (fa.tag === "some" ? { tag: "some", value: f(fa.value) } : { tag: "none" }),
};

const doubled = maybeFunctor.map({ tag: "some", value: 21 }, (n) => n * 2);
const fallback = maybeFunctor.map({ tag: "none" } as Maybe<number>, (n) => n.toFixed(1));
console.log(doubled, fallback);
```

`Apply<F, A>` 展开成 `URItoKind<A>[F]`，当 F 是 `"Maybe"` 时就是 `Maybe<A>`。Functor 的实例必须显式标注 `Functor<"Maybe">`。

代价之一是推断失败。

```ts
type Maybe<A> = { readonly tag: "none" } | { readonly tag: "some"; readonly value: A };

interface URItoKind<A> {
  Maybe: Maybe<A>;
}

type URIS = keyof URItoKind<unknown>;
type Apply<F extends URIS, A> = URItoKind<A>[F];

declare function mapValue<F extends URIS, A, B>(fa: Apply<F, A>, f: (a: A) => B): Apply<F, B>;

const result = mapValue({ tag: "some", value: 1 } as Maybe<number>, (n) => n + 1);  // error TS18046: 'n' is of type 'unknown'.
```

报 `TS18046: 'n' is of type 'unknown'.`

F 藏在 `Apply<F, A>` 的索引访问里，无法从实参反推出 `"Maybe"`。A 也推不出来，退化成 unknown。调用时要显式写 `mapValue<"Maybe", number, number>(...)`，使用者必须知道 URI 的名字。声明合并是扩展点：别的模块再声明一个 `interface URItoKind<A>`，加上 `Either: Either<A, string>`，`URIS` 自动多一个键，已有代码不改。这是它比具体泛型能扩展的地方，也是它的代价：键和类型的对应关系靠约定，编译器查不到拼错的 URI 是不是故意。

编译成本可以用 `--extendedDiagnostics` 量。各写 200 次调用，HKT 封装对比直接函数：

```bash
$ tsc --noEmit --strict --target es2025 --extendedDiagnostics stress-hkt.ts
Types:           35974
Instantiations:  34702
Check time:     0.127s

$ tsc --noEmit --strict --target es2025 --extendedDiagnostics stress-plain.ts
Types:           35955
Instantiations:  34473
Check time:     0.139s
```

实例化次数差 229，检查时间没有变慢。这个规模下 HKT 的编译代价可以忽略。类型体操慢的说法要靠测量，不能靠感觉。

真正的代价在可读性和推断。报错信息里出现 `Apply<F, A>`、URI 联合、推断失败；使用者要理解两层编码才能改代码。fp-ts 一类库用这种编码换来统一的抽象，业务代码通常不需要。

判断标准：容器类型两个以上、需要写通用组合子、且代码是库的一部分，才考虑 HKT。业务里直接写 `mapMaybe`、`mapList` 两个函数，推断和报错都更好。

## 八、Result 与 Effect

Result 把预期错误放进返回值。

```ts
type Result<T, E> =
  | { readonly ok: true; readonly value: T }
  | { readonly ok: false; readonly error: E };

const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });
const fail = <E>(error: E): Result<never, E> => ({ ok: false, error });

function map<T, U, E>(result: Result<T, E>, f: (value: T) => U): Result<U, E> {
  return result.ok ? ok(f(result.value)) : result;
}

function flatMap<T, U, E>(result: Result<T, E>, f: (value: T) => Result<U, E>): Result<U, E> {
  return result.ok ? f(result.value) : result;
}

const parsed = flatMap(ok("42"), (raw) => {
  const n = Number(raw);
  return Number.isNaN(n) ? fail("not_a_number" as const) : ok(n);
});

const shown = flatMap(parsed, (n) => (n > 10 ? ok(n * 2) : fail("too_small" as const)));
console.log(shown.ok ? shown.value : shown.error);
```

```bash
$ node result.js
84
```

`ok` 返回 `Result<T, never>`，`fail` 返回 `Result<never, E>`。never 在联合里不增加分支，合并时不会污染错误类型。`map` 只映射值，`flatMap` 展平嵌套结果。

错误类型会静默扩大。

```ts
type Result<T, E> =
  | { readonly ok: true; readonly value: T }
  | { readonly ok: false; readonly error: E };

const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });
const fail = <E>(error: E): Result<never, E> => ({ ok: false, error });

declare function flatMap<T, U, E>(result: Result<T, E>, f: (value: T) => Result<U, E>): Result<U, E>;

type OrderError = "not_found" | "out_of_stock";
declare function findOrder(id: string): Result<number, OrderError>;

const widened = flatMap(findOrder("ord_1"), (cents) =>
  cents > 1000 ? ok(cents) : fail("bad_gateway" as const),
);

const narrowed: Result<number, OrderError> = widened;  // error TS2322: Type 'Result<number, "bad_gateway" | OrderError>' is not assignable to type 'Result<number, OrderError>'.
```

`widened` 本身不报错，它的类型是 `Result<number, "bad_gateway" | OrderError>`。`narrowed` 赋值时才发现不对，报 `TS2322`：`Result<number, "bad_gateway" | OrderError>` 不能赋给 `Result<number, OrderError>`。

原因是 flatMap 的 E 同时从 `result` 和 `f` 的返回类型推断，两个来源取并集，新错误码悄悄混进去。不写注解时调用方不会发现，错误类型在调用链上越滚越大。公共 API 要显式标注返回类型，把这个扩散限制在函数内部。并集来自类型参数合并规则：`result` 贡献 `E1`，回调返回值贡献 `E2`，`E` 推断成 `E1 | E2`。这是推断的正常行为，不是 bug。显式标注等于把合并结果钉在函数边界上，调用方看到的错误类型不随实现细节变化。

异步场景加一层 Promise 包装。

```ts
type Result<T, E> =
  | { readonly ok: true; readonly value: T }
  | { readonly ok: false; readonly error: E };

const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });

declare function fetchAmount(orderId: string): Promise<Result<number, "not_found">>;

async function charge(orderId: string): Promise<Result<string, "not_found">> {
  const result = await fetchAmount(orderId);
  if (!result.ok) {
    return result;
  }
  if (result.value <= 0) {
    throw new RangeError("amount must be positive");
  }
  return ok(`charged ${result.value}`);
}

console.log(charge("ord_1"));
```

这段能编译。注意第三个分支仍然 throw。Result 只装预期错误，程序错误和不变量破坏应该抛异常，让进程或框架的顶层处理器接住。`Promise<Result>` 的 rejection 不在类型里，await 处仍然要用 try/catch 兜底。

Effect 一类库把并发、资源、依赖都编码进类型，组合子更完整，学习曲线和推断成本也更高。业务项目先从 Result 起步，需要托管副作用再考虑。

Result 的日常成本是每次调用都要分支。错误类型还要统一，否则每个函数返回一套错误码，调用方 merge 不完。团队要先定错误类型层级，再推广写法。

运行时表示是两个字段的普通对象，`ok` 是判别属性，分支靠它收窄。没有类，没有方法，序列化直接可用。函数式写法里 `map` 和 `flatMap` 是普通函数，可以组合，也可以写成方法挂在原型上，后者会有 this 类型推断的额外工作。

## 九、反模式清单

| 做法 | 症状 | 替代 |
|---|---|---|
| 给每个字符串加品牌 | 编码和剥离噪音，代码里全是 as | 只给跨模块混用过的值加 |
| 用可选幽灵字段表达单位 | 字面量省略字段，保护失效 | 品牌或包装对象 |
| 状态机覆盖全部业务状态 | 加状态改全仓，历史数据卡住 | 只管稳定核心，外围运行时校验 |
| 用 this 参数做 Builder 收尾 | 检查不生效 | 条件交叉类型或分步接口 |
| 在业务代码里用 HKT | 推断失败，报错难读 | 具体泛型加重载 |
| 用 as 绕过品牌 | 类型层保护归零 | 只在解析边界断言一次 |
| 配置和业务规则全塞进类型 | 编译变慢，改动扩散 | satisfies 校验加运行时 |

选型顺序可以按问题走。

值在运行时会不会混用。会，就加品牌，并且只加在跨模块边界上。

状态迁移会不会出错。会，且状态集合稳定，就用类型级状态机，并配运行时收窄。

容器是否两个以上且需要统一操作。是，且在写库，再考虑 HKT。

调用方是否需要处理错误。需要，就用 Result，同时保留异常处理程序错误。

每个模式都有编译期成本。品牌多一个类型参数，多一次构造和一次解包；状态机多一张要维护的映射表；HKT 多一层索引访问，实例化次数上升；业务规则进类型，改一条规则要重新编译整个依赖图。判断标准是「错误的代价是否高于维护成本」。跨模块混用 ID 会写错账户，值得加品牌。配置字段少且经常改，用 satisfies 校验更省事。类型层不处理数据，只描述已经成立的事实。

这些模式都在编译期生效，运行时没有保护。可靠性来自组合：边界处用 schema 校验一次，校验结果带上品牌，内部用 Result 传递，状态机保证迁移路径。组合之后，类型层描述的是「已经发生的事实」，而不是「希望发生的事实」。

团队落地时先选一个收益明确的点。最常见的是订单号、账户号这类跨模块标识，加一个品牌，构造器集中在数据访问层。跑一段时间，如果有人在 code review 里问「这个值从哪来」，说明品牌在起作用。如果没人受益，只多了转换调用，就撤掉。类型层的模式也是代码，要按收益维护。

## 用不上的时候

### 值要做运算

品牌不传播运算。两个 `Meters` 相加得到 `number`，要重新构造；单位乘除同样回退。链式计算的每一步都要解包和包装，转换调用会盖住业务逻辑。

### 值从运行时进来

`JSON.parse` 返回 `any`，`any` 可以赋给任何品牌类型，编译照样通过。品牌只把校验结果带进类型层，本身不校验，`as unknown as` 也能绕过。解析边界上仍要 schema，品牌放在校验之后。

### 状态集合还在变

类型级状态机把状态迁移写在类型里。加一个状态要改映射表，改一条规则要重编译整个依赖图，历史数据的迁移不在类型层。状态没稳定或要兼容旧数据时，用它只会让每次改动变慢。
