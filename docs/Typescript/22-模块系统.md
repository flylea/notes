# 第 22 章 模块系统

`import` 路径不带扩展名时 Node 的 ESM 报 ERR_MODULE_NOT_FOUND；`import type` 写错位置会报 TS1361；同一份代码在 bundler 和 Node 下解析结果不同。模块系统决定这些行为。这一章讲 ESM 与 CJS 的类型处理、解析策略和互操作。

TypeScript 对 JavaScript 的模块系统提供了完整的类型支持：包括 ES Module 和 CommonJS。这一章将介绍 TypeScript 中的模块类型处理、`import type`、模块解析策略以及如何在不同模块系统之间安全地使用类型。

一句话：NodeNext 先用文件格式定编译目标，再按 Node 规则找文件。

`.mts` 永远是 ESM，`.cts` 永远是 CJS；`.ts` 跟着最近的 `package.json` 的 `"type"` 走。格式定了，`import` 才知道编译成 `import` 还是 `require`。

这个说法在裸包上多一步：包里的 `exports` 会按格式挑入口，挑不到就报找不到模块，不会退回 `main`。

## ES Module 中的类型

### 导入和导出类型

```typescript
// user.ts：导出
export interface User {
  id: number;
  name: string;
}

export function createUser(name: string): User {
  return { id: Math.random(), name };
}

// app.ts：导入
import { User, createUser } from "./user";

const user: User = createUser("Alice");
```

### import type：仅导入类型

`import type` 是 TypeScript 3.8 引入的特性，它**只导入类型信息，不导入运行时代码**。编译后这类 import 会完全消失：

```typescript
// 只导入类型
import type { User } from "./user";

// 可以用于类型标注，但不能当值使用
const user: User = { id: 1, name: "Alice" };
// 若把 createUser 写成 import type，再调用：
// import type { createUser } from "./user";
// createUser("Alice");  // error TS1361: 'createUser' cannot be used as a value because it was imported using 'import type'.

// 混合导入：类型和值分开
import { type User, createUser } from "./user";
```

为什么用 `import type`？
1. **明确意图**：阅读者一眼就知道这个导入只用于类型
2. **避免循环依赖**：纯类型导入不产生运行时代码，某些循环依赖（值 → 类型 → 值）可以借助 `import type` 解开
3. **编译优化**：某些构建工具（如 Babel、esbuild）可以利用它跳过不必要的导入
4. **`isolatedModules` 兼容**：当启用 `isolatedModules` 时，类型导出（`export type`）是必需的

### export type：仅导出类型

```typescript
// 同名有值和类型时，可以用 export type 明确导出类型
export type { User };
export { createUser };
```

等价于：
```typescript
export type { User };
export { createUser };
```

### inline type 导入（TS 4.5+）

```typescript
// 在同一个 import 语句中混合值和类型
import { createUser, type User } from "./user";
```

## import attributes

JSON 这类非 JS 文件，导入时要写 `with { type: "json" }`（[TS 5.3](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-3.html) 起）：

```typescript
import data from "./data.json" with { type: "json" };

export const orderId = data.id;
```

`module: "nodenext"` 下，ESM 里的 JSON 导入不写 attribute 直接报错：

```typescript
import data from "./data.json";

// error TS1543: Importing a JSON file into an ECMAScript module requires a
//   'type: "json"' import attribute when 'module' is set to 'NodeNext'.
```

`assert` 是 TS 4.5 引入的写法，5.3 换成 `with`，TS 7 里已经移除：

```typescript
import data from "./data.json" assert { type: "json" };

// error TS2880: Import assertions have been replaced by import attributes.
//   Use 'with' instead of 'assert'.
```

attribute 和 `resolveJsonModule` 管的是两件事。`resolveJsonModule` 决定 tsc 读不读 `.json`、给不给类型；attribute 决定运行时加载器认不认这个文件。

两个条件都要满足。关掉 `resolveJsonModule` 报 `error TS2732: Cannot find module './data.json'. Consider using '--resolveJsonModule' to import module with '.json' extension.`。7.0 的 bundler 和 nodenext 配置默认开着它。

运行时这边不用额外配置。实测 Node 26.13.1 直接执行编译产物，JSON 导入正常返回。

## import defer

`import defer` 让模块延迟求值，第一次访问成员时才执行（TS 5.9 起支持语法）：

```typescript
import defer * as logger from "./logger.js";

export function readLevel(): string {
  return logger.level;
}
```

默认配置下 tsc 报 `error TS18060: Deferred imports are only supported when the '--module' flag is set to 'esnext' or 'preserve'.`。加 `--module esnext` 或 `preserve` 才过。

但 tsc 只做语法和类型检查，产物原样保留这条语句：

```javascript
import defer * as logger from "./logger.js";
```

Node 还不认这条语法。Node 26.13.1 直接执行产物报 `SyntaxError: Unexpected token '*'`。

所以 `import defer` 现在的可用范围是：编译通过，运行时交给打包器降级，或等目标运行时实现。tsc 不报错不等于能上生产。

## source phase imports（7.1 Beta）

[7.1 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/) 加入 `import source`，用来直接拿模块对象本身，主要给 WebAssembly 用：

```typescript
import source wasmModule from "./mod.wasm";

export const mod = wasmModule;
```

7.0.2 解析不了这段，报 `error TS1005: '=' expected`。等 7.1 稳定后再写进项目。

## CommonJS 的类型处理

CommonJS 使用 `require` 和 `module.exports`，TypeScript 有两种方式为它们提供类型：

### 方式一：使用 ES Module 语法编译为 CommonJS

这是推荐做法：写 ES Module 语法，通过 tsconfig 的 `module: "commonjs"` 编译为 CJS：

```typescript
// 编写时用 ES Module 语法
import express from "express";
export const app = express();

// 编译后（module: "commonjs"）
// const express = require("express");
// exports.app = express();
```

### 方式二：CommonJS 类型标注

`import x = require()` 和 `export =` 是 CommonJS 专用的类型语法。把它们写进 ESM 文件，编译期直接报错：

```bash
$ tsc --noEmit --module esnext --moduleResolution bundler app.ts
app.ts(1,1): error TS1202: Import assignment cannot be used when targeting ECMAScript modules. Consider using 'import * as ns from "mod"', 'import {a} from "mod"', 'import d from "mod"', or another module format instead.
app.ts(2,1): error TS1203: Export assignment cannot be used when targeting ECMAScript modules. Consider using 'export default' or another module format instead.
```

只有 `module` 为 `commonjs`，或 `module` 与 `moduleResolution` 都设为 `node16`、`nodenext` 且文件按 CJS 解析时，这段才通过。注意 `commonjs` 与 `moduleResolution: node16` 不能组合，会报 TS5110。它用来给已有 CommonJS 包补类型：

```typescript
// tsconfig: { "module": "commonjs" }，且装了 @types/express
import express = require("express");

const app = express();
export = app;
```

`export =` 对应运行时的 `module.exports =`。导入方用 `import x = require()`，或用 `esModuleInterop` 打开后的默认导入。新代码用 `export default` 和具名 `export`，两边都不需要这套写法。

## 模块解析策略

TypeScript 需要知道如何查找 `.ts`/`.d.ts` 文件。`moduleResolution` 配置控制这一行为：

### node 策略（Node.js 风格）

模拟 Node.js 的模块解析逻辑：
- 相对路径：逐级向上查找 `node_modules`
- 非相对路径：从 `node_modules` 目录查找
- 按顺序尝试 `.ts`、`.tsx`、`.d.ts`、`.js` 扩展名
- 查找 `package.json` 的 `types`/`typings` 字段
- 查找目录下的 `index.ts`/`index.d.ts`

### bundler 策略（推荐用于现代项目）

[TypeScript 5.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html) 引入了 `moduleResolution: "bundler"`，专门为 Vite、Webpack、esbuild 等打包工具设计：

- 支持 `package.json` 的 `exports` 字段
- 不需要写文件扩展名（打包工具会处理）
- 与打包工具的实际解析行为一致

```json
{
  "compilerOptions": {
    "module": "esnext",
    "moduleResolution": "bundler"
  }
}
```

### nodenext 策略（TypeScript 4.7+）

`moduleResolution: "nodenext"` 完全遵循 Node.js 的 ESM 模块解析规则：

- `.ts` 文件如果是 ESM，必须显式写 `.js` 扩展名：
  ```typescript
  // ESM 模式下必须写完整扩展名
  import { User } from "./user.js";  // ⚠️ 注意是 .js 不是 .ts
  ```
- 支持 `package.json` 的 `"type": "module"` 控制

### NodeNext 的判定顺序

NodeNext 按 Node 的真实规则分三步。

第一步定文件格式。`.mts`、`.cts` 由扩展名决定；`.ts`、`.tsx` 看最近的 `package.json`，`"type": "module"` 是 ESM，缺省或 `"commonjs"` 是 CJS。格式决定 `import` 编译成什么，也决定后面按哪套条件挑包入口。

第二步定相对路径。ESM 里相对导入必须写扩展名，写 `.js` 而不是 `.ts`，因为 Node 按真实文件名解析，编译产物就是 `.js`。TS2835 由此而来。

第三步定裸包。先读 `exports`，再挑条件：类型走 `types`，运行时按当前格式走 `import` 或 `require`，都不匹配时看 `default`。`exports` 存在时 `main` 被忽略。官方说明见 [4.7 发布说明](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html) 的 ECMAScript Module Support in Node.js 一节。

版本还会改动这条链。TS 5.8 起 `--module nodenext` 允许 CJS 里 `require` ESM，因为 Node 22 支持 `require(esm)`，官方 5.8 发布说明的标题是 Support for require() of ECMAScript Modules in --module nodenext。同样的代码换 `node16`、`node18` 会报 TS1479，那两个模式仍按旧规则判定。

条件顺序要记牢：先看 `types`，再看当前格式的 `import` 或 `require`，最后 `default`。顺序错了会出现类型能过、运行时找不到入口的情况。

`--moduleResolution bundler` 不走这套判定，它按打包器的习惯允许省略扩展名，也不看 `exports` 的格式条件，所以同一份代码换 bundler 能过、换 nodenext 就报 TS2835。

一个包同时提供 `import` 和 `require` 入口时，两个入口的类型要分别声明，否则 CJS 那边只能拿到 ESM 的声明，检查器会按 `require` 条件重新挑类型文件。

### 策略速查表

| 策略 | 适用场景 | 需写扩展名 | 支持 exports |
|------|---------|-----------|-------------|
| `node` | 传统 Node.js | ❌ | ❌ |
| `bundler` | Vite/Webpack 等 | ❌ | ✅ |
| `nodenext` | Node.js ESM | ✅ (.js) | ✅ |
| `classic` | 已过时 | — | — |

### 解析失败的两个报错

项目结构：`package.json` 写 `"type": "module"`，`src/util.ts` 导出函数，`src/main.ts` 相对导入时不带扩展名；`src/legacy.cts` 写 `import dep from "dep"`，而 `node_modules/dep/package.json` 的 `exports` 只有 `"import": "./index.js"`，没有 `require` 入口，也没有类型声明。

```ts
import { twice } from "./util";

console.log(twice(2));
```

```text
src/main.ts(1,23): error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './util.js'?
src/legacy.cts(1,17): error TS2307: Cannot find module 'dep' or its corresponding type declarations.
```

TS2835 说 ESM 的相对导入必须带扩展名；改成 `./util.js`，TypeScript 会自己找到 `util.ts`。

TS2307 是条件导出一个都没命中：检查器按 CJS 的条件集（`require`、`types`）找入口，找不到就报缺模块。让包补一个 `require` 入口并加类型声明，或者把这个文件改成 ESM。条件导出里每个入口都要有对应的类型声明，检查器只按当前格式挑一份。

两端入口的类型不一致时，检查器会在各自文件里使用对应的声明，跨入口传值可能拿到两种不同的类型。改包时把两个入口的声明一起更新，别只改一个。

## 类型导入导出的最佳实践

### 1. 开启 isolatedModules

当使用 Babel、esbuild、Vite 等非 tsc 编译器时，建议开启 `isolatedModules: true`。它要求：
- 每个文件都被独立编译（不能依赖跨文件的类型信息）
- 类型导出必须用 `export type`
- 常量枚举不能使用

### 2. 开启 verbatimModuleSyntax（TS 5.0+）

`verbatimModuleSyntax: true` 强制要求 `import type` 用于纯类型导入（在 ESM 输出中这些导入会被移除）。这比 `importsNotUsedAsValues` 和 `isolatedModules` 更严格，也更能防止运行时错误。

```typescript
// verbatimModuleSyntax 开启时：
import type { User } from "./user";  // 正确，纯类型，编译后消失
import { createUser } from "./user";  // 正确，值导入，编译后保留
// import { User } from "./user";  // error TS1484: 'User' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
```

### 3. 路径别名

通过 tsconfig 的 `paths` 配置路径别名（需要与打包工具的 alias 保持一致）：

```json
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"],
      "@components/*": ["./src/components/*"],
      "@utils/*": ["./src/utils/*"]
    }
  }
}
```

`paths` 的取值相对于 tsconfig 所在目录，不需要 `baseUrl`。TypeScript 7.0 已移除 `baseUrl`，写了会报 `error TS5102: Option 'baseUrl' has been removed. Please remove it from your configuration.`

## 动态导入的类型

动态导入 `import()` 返回 `Promise`，TypeScript 会自动推导模块的类型：

```typescript
async function loadUserModule() {
  const { createUser } = await import("./user");
  const user = createUser("Alice");
  return user;
}
```

## 小结

- **ES Module**：用标准 `import`/`export` 语法，推荐开启 `verbatimModuleSyntax`
- **`import type`**：让类型导入编译后完全消失，避免循环依赖
- **CommonJS**：推荐用 ES Module 写法 + `module: "commonjs"` 编译，避免裸写 CJS 语法
- **模块解析**：现代项目推荐 `bundler`；纯 Node.js ESM 用 `nodenext`
- **路径别名**：tsconfig `paths` 需与打包工具的 alias 保持一致

## 用不上的时候

### 单文件脚本

不需要被 import 的脚本不加 `import`/`export` 就是全局脚本，模块解析规则都不适用。

### 双包发布

同一包同时发 ESM 与 CJS，容易出现两份实例、类型条件写错的问题。能只发 ESM 就别发两份。

### 路径别名

`paths` 只影响 tsc 的类型解析，运行时要 bundler 或 loader 支持，否则运行时报找不到模块。
