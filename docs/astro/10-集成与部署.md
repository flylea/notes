# 第 10 章 集成、构建与上线

## 10.1 集成是怎么工作的

集成就是一个带 `astro:config:setup` 等钩子函数的对象，能改配置、注入路由、加 Vite 插件、扩展渲染流程：

```js
// astro.config.mjs
import { defineConfig } from 'astro/config';
import mdx from '@astrojs/mdx';
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  site: 'https://example.com',
  integrations: [mdx(), sitemap()],
});
```

`integrations` 数组的**顺序有意义**。同名钩子按数组顺序执行，前一个改了配置，后一个看到的是改过的版本。比如同时用 MDX 和自定义 Markdown 插件，插件顺序会影响最终输出的 HTML。出问题时先试调整顺序，这是最容易被忽略的排查手段。

`npx astro add <名字>` 会做三件事：装依赖、改 `astro.config.mjs`、按需创建文件。它对官方集成有内置映射表，第三方集成则要求你手写 `integrations`。

集成能带来功能的代价：

- 每个集成都是一层构建期插件，构建时间会累加。
- 集成升级可能带 breaking change，和 Astro 主版本不完全同步。
- 集成失效时排查链路长：Astro 核心 → 集成 → Vite 插件 → 底层包。

所以能不用集成就不用。一个 `<Image />` 组件不需要集成，Astro 自带了；一个 RSS 生成也不需要集成，写个端点就行。

## 10.2 常用官方集成

| 集成 | 包名 | 用途 |
|---|---|---|
| React | `@astrojs/react` | 用 React 组件 |
| Preact | `@astrojs/preact` | 用 Preact 组件，体积小 |
| Vue | `@astrojs/vue` | 用 Vue 组件 |
| Svelte | `@astrojs/svelte` | 用 Svelte 组件 |
| Solid | `@astrojs/solid-js` | 用 Solid 组件 |
| Alpine.js | `@astrojs/alpinejs` | 用指令做轻量交互 |
| MDX | `@astrojs/mdx` | Markdown 里写组件 |
| Markdoc | `@astrojs/markdoc` | 结构化文档格式 |
| Sitemap | `@astrojs/sitemap` | 生成 `sitemap-index.xml` |
| Partytown | `@astrojs/partytown` | 把第三方脚本挪到 Web Worker |
| RSS | `@astrojs/rss` | 生成 RSS 源（是库，不是集成） |
| Node | `@astrojs/node` | 自托管适配器 |
| Vercel | `@astrojs/vercel` | Vercel 适配器 |
| Netlify | `@astrojs/netlify` | Netlify 适配器 |
| Cloudflare | `@astrojs/cloudflare` | Cloudflare Workers 适配器 |

几个使用上的注意：

- **MDX** 是"Markdown 里能用组件"，用了它会接管 `.mdx` 的渲染，`.md` 仍走默认 Markdown 处理器。v7 起默认 Markdown 处理器换成了 Sätteri，插件生态和以前不完全一致，老项目升级时要注意自定义 remark/rehype 插件是否还能用。
- **Sitemap** 必须配 `site`，否则生成不了。产物是 `sitemap-index.xml` 和 `sitemap-0.xml`，还要自己在 `robots.txt` 里加一行 `Sitemap: https://example.com/sitemap-index.xml`，搜索引擎才容易发现。
- **Partytown** 适合把分析脚本、客服插件这类重脚本挪出主线程。代价是这类脚本里不能再用 `document`、`localStorage` 等主线程 API，很多第三方脚本直接跑不了。
- **Tailwind** 现在不用集成：`npx astro add tailwind` 装的是 `@tailwindcss/vite` 插件（Tailwind 4）。`@astrojs/tailwind` 是 Tailwind 3 时代的遗留集成，只有旧项目还需要它。

## 10.3 构建与检查

```bash
astro build          # 产出 dist/
astro preview        # 本地起服务预览 dist/
astro check          # 类型检查
```

`astro build` 会先把路由、内容集合类型同步好，再逐页渲染。v7.4 起可以加 `--timings` 看构建各阶段耗时：

```bash
astro build --timings
```

报告会列出 Vite 插件、Markdown 处理、语法高亮、图片优化、集成钩子各自的耗时。构建慢的时候先看这个，比盲猜插件有用。

`astro check` 需要额外装依赖：

```bash
npx astro add check
```

它依赖 `@astrojs/check` 和 `typescript`，检查 `.astro` 文件里的类型。有问题时退出码是 1，适合放进 CI：

```yaml
- run: npx astro check
- run: npx astro build
```

`astro build` 本身**不做类型检查**。TS 类型错的代码照样能构建成功，只是运行时报错或者出现 `undefined`。这是很多人踩的坑：本地能构建、CI 能过、上线后白屏。

构建产物的结构：

```
dist/
├── index.html
├── about/
│   └── index.html       # build.format: 'directory' 时
├── _astro/
│   ├── index-abc123.css
│   └── hoisted-xyz789.js
└── sitemap-index.xml
```

`_astro/` 下的文件名带内容哈希，可以放心设长期缓存。

`astro preview` 只用于本地验证构建产物，不能当生产服务器。它不做压缩、不做缓存、不支持并发。

## 10.4 静态部署

静态站点就是一堆文件，传到任何能托管静态文件的地方即可：

```bash
astro build
```

然后把 `dist/` 传上去。

### Netlify

```toml
# netlify.toml
[build]
  command = "npm run build"
  publish = "dist"
```

Netlify 会自动识别 Astro 项目，通常不需要这个文件。要按需渲染时再装适配器。

### Vercel

导入 Git 仓库即可，Vercel 自带 Astro 预设。按需渲染的项目要装 `@astrojs/vercel` 并把 `output` 设为 `'server'`。

### Cloudflare Pages

静态站点零配置。构建命令 `npm run build`，输出目录 `dist`。

### GitHub Pages

用官方 Action，不要自己写 `gh-pages` 推送脚本：

```yaml
# .github/workflows/deploy.yml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: withastro/action@v6
```

仓库设置里把 Pages 的来源改成 "GitHub Actions"。项目页的地址是 `https://<用户名>.github.io/<仓库名>/`，必须在配置里声明这个前缀，否则所有资源路径都会 404：

```js
// astro.config.mjs
export default defineConfig({
  site: 'https://username.github.io',
  base: '/my-repo',
});
```

`site` 和 `base` 是两个不同的东西：

- `site` 是完整站点地址，用来生成 sitemap、canonical、OG 标签的绝对 URL。没配的话 `Astro.site` 是 `undefined`，拼字符串时会变成 `"undefined/about"`。
- `base` 是站点挂在域名下的哪一层。配了 `base: '/my-repo'`，页面里的内部链接要写成 `import.meta.env.BASE_URL + 'about/'`，或者用 `new URL(...)` 拼，硬编码 `/about/` 会指到域名根。

部署到子路径是最常见的上线事故来源，本地一切正常、线上样式全丢、图片 404，基本都是 `base` 没配对。

## 10.5 按需部署

需要服务端渲染时，适配器的差异会直接影响能不能跑：

| 适配器 | 运行环境 | 注意 |
|---|---|---|
| `@astrojs/node` | 自己的服务器 | 最自由，能读写文件、用 `fs`、长连接 |
| `@astrojs/vercel` | Vercel Functions | 冷启动、函数时长限制、文件系统只读 |
| `@astrojs/netlify` | Netlify Functions | 同上，注意函数体积上限 |
| `@astrojs/cloudflare` | Cloudflare Workers | 无 `fs`、无原生二进制、Sharp 不可用 |

Cloudflare 是最需要提前确认的。它没有 Node 的文件系统和原生模块，图片优化默认跑不了，要换图片服务：

```js
// astro.config.mjs
import { defineConfig } from 'astro/config';
import cloudflare from '@astrojs/cloudflare';

export default defineConfig({
  output: 'server',
  adapter: cloudflare(),
  image: {
    service: passthroughImageService(),
  },
});
```

`passthroughImageService()` 从 `astro/config` 导入。它的意思是"不做处理，原样输出"，`<Image />` 的宽高裁切、格式转换全部失效。要用 Cloudflare 的图片服务就得走它自己的 Image Resizing 产品，这已经超出 Astro 的范围了。

换成 Serverless 或边缘运行时之前，先搜一遍代码里有没有：`fs`、`path`、`node:crypto`、`process.cwd()`、`Buffer`。这些在 Workers 里都没有，本地能跑，部署就炸。

## 10.6 缓存与安全响应头

站点能跑起来只是第一步，上线后还有第二个问题：好不好、稳不稳。两块配置绕不过去。

### 缓存

Astro 构建出的文件名带内容哈希（`index-abc123.css`），所以静态资源可以设一年长缓存：

```
Cache-Control: public, max-age=31536000, immutable
```

HTML 不能这么设。HTML 里引用的是带哈希的资源名，一旦 HTML 被缓存久了，新版本资源就上不了线：

```
Cache-Control: public, max-age=0, must-revalidate
```

按需渲染的页面在代码里控制：

```astro
---
export const prerender = false;

Astro.response.headers.set(
  'Cache-Control',
  'public, s-maxage=60, stale-while-revalidate=300',
);
---
```

`s-maxage` 给 CDN 用，`stale-while-revalidate` 允许先返回旧内容、后台再刷新。用户看到 60 秒内的数据，回源压力降一个量级。缓存时长就是你能接受的数据陈旧上限，别拍脑袋填 3600。

平台侧一般用配置文件设头。Netlify 写在 `netlify.toml`：

```toml
[[headers]]
  for = "/_astro/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

[[headers]]
  for = "/*"
  [headers.values]
    Cache-Control = "public, max-age=0, must-revalidate"
```

Vercel 用 `vercel.json` 的 `headers`，Cloudflare Pages 用 `_headers` 文件，语法类似。

### 安全头

至少加三条：

```
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Strict-Transport-Security: max-age=63072000; includeSubDomains
```

HSTS 要等 HTTPS 稳定后再加，加早了会把自己锁在浏览器里。

### CSP

v6 起 Astro 能自动生成 Content Security Policy：

```js
// astro.config.mjs
export default defineConfig({
  security: {
    csp: true,
  },
});
```

构建时给每个页面注入 `<meta http-equiv="content-security-policy">`，`script-src` 和 `style-src` 里带上 Astro 产出的脚本和样式的哈希。想补规则用对象形式：

```js
security: {
  csp: {
    algorithm: 'SHA-512',
    directives: ["img-src 'self' data: https:"],
  },
}
```

代价不小，用之前先确认这些限制能接受：

- `<ClientRouter />` 的视图过渡不支持，CSP 和它二选一。
- Shiki 语法高亮不支持，因为 Shiki 输出内联样式。需要高亮就换 Prism。
- 外部脚本、外部样式不自动带哈希，要自己算好加进 `scriptDirective.hashes`。
- 开发模式下不生效，只能在 `build` + `preview` 里验证。

要 CSP 就不要视图过渡，要语法高亮就换高亮方案。这是内联样式哈希这套机制的必然结果，不是 Astro 的疏漏。

另外两个和请求有关的配置：

- `security.checkOrigin` 默认开启，按需渲染页面上的表单类请求会做 CSRF 校验，跨站来源返回 403。
- `security.allowedDomains` 用来限制 `X-Forwarded-Host`，防止反向代理场景下的 Host 头注入。部署在 CDN 后面时按实际域名配置。

## 10.7 上线前检查清单

按顺序过一遍，能拦掉大部分事故：

- [ ] `astro check` 无错误，`astro build` 成功。
- [ ] `site` 和 `base` 配置正确，本地用 `base` 路径访问一遍链接。
- [ ] 跑 `astro preview`，检查构建产物下的图片、CSS、字体都能加载。
- [ ] 确认哪些页面是预渲染的。`astro build` 输出里会列出来，该按需的页面漏了 `prerender = false` 会变成静态快照，上线后数据永不更新。
- [ ] 环境变量在部署平台配好。`PUBLIC_` 开头的会打进构建产物，改了要重新构建。
- [ ] 密钥没有出现在 `dist/` 里：`grep -r "sk_live" dist/` 之类查一遍。
- [ ] 404 页面存在，`src/pages/404.astro` 会被自动使用。
- [ ] `<html lang>`、`<title>`、`<meta name="description">`、canonical、OG 标签齐全。
- [ ] sitemap 已生成，`robots.txt` 指向它。
- [ ] 首屏 JS 预算：打开 DevTools 看 Network，首屏 JS 超过 100KB 就要检查是不是有组件用错了 `client:load`。
- [ ] 按需渲染页面设了 `Cache-Control`，静态资源是长缓存 + 哈希文件名。
- [ ] 安全头齐全：`X-Content-Type-Options`、`Referrer-Policy`、HSTS；要 CSP 就确认已放弃视图过渡和 Shiki。
- [ ] 自定义域名配了 HTTPS，重定向规则（`redirects` 或平台配置）能跳对。

清单里最容易被跳过的是"确认哪些页面是静态的"。`output: 'server'` 的项目里默认全部按需，你可能以为自己写了静态页；`output: 'static'` 的项目反之。构建日志是唯一可靠的确认方式。

## 10.8 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| 构建报 `Cannot use server-rendered pages without an adapter` | 用了 `prerender = false` 但没装适配器 | 装适配器，或去掉按需渲染 |
| 构建报 `Found legacy content config file in "src/content/config.ts"` | 内容集合配置文件放在旧路径 | 移到 `src/content.config.ts` 并给每个集合加 `loader` |
| 线上样式全丢、图片 404 | `base` 没配或内部链接硬编码了 `/` | 配 `base`，链接用 `BASE_URL` 或 `new URL()` 拼 |
| 页面能打开但数据是旧的 | 页面被静态预渲染了 | 加 `export const prerender = false` |
| 本地正常，线上 `window is not defined` | 浏览器 API 写在了服务端执行的代码里 | 挪进 `<script>` 或客户端组件 |
| 客户端组件报 `Cannot read properties of undefined` | 传了不可序列化的 props（函数、类实例） | 只传可 JSON 序列化的数据 |
| `astro check` 通过但运行时报 `undefined` | 类型断言掩盖了真实的空值 | 查 `as` 和 `!` 的使用 |
| 升级后构建失败，报未闭合标签 | v7 的 Rust 编译器不再容忍非法 HTML | 给所有非空元素补闭合标签 |

最后一条值得单独说。v7 把编译器换成了 Rust 实现，比之前严格：未闭合的标签直接报错，非法的 HTML 嵌套不再被自动修正。升级后如果渲染结果和以前不一样，多半是模板里有 `<p>` 套 `<div>` 这类问题，以前被静默修好了。

## 10.9 版本升级

```bash
npx @astrojs/upgrade
```

它会升级 Astro 和官方集成到匹配版本，并提示需要手动处理的项。不要直接 `npm install astro@latest`，集成版本对不上会出奇怪的问题。

升级前先看目标主版本的升级指南，重点看三块：依赖升级（Node、Vite、Zod 版本要求）、实验性标志（哪些已转正、哪些被移除）、移除项。

最近三个主版本的关键变化：

| 版本 | 要注意的变化 |
|---|---|
| v5 | `output: 'hybrid'` 移除；`<ViewTransitions />` 改名 `<ClientRouter />`；CSRF 校验默认开启；Squoosh 图片服务移除 |
| v6 | Node 22+；Vite 7；Zod 4；旧版内容集合 API 移除；`fonts`、`csp`、`liveContentCollections` 转正；`import.meta.env` 一律内联 |
| v7 | Rust 编译器成为默认且唯一编译器；默认 Markdown 处理器换成 Sätteri；`compressHTML` 默认 `'jsx'`；`@astrojs/db` 移除；`astro:transitions` 内部 API 移除 |

升级到 v7 尤其要注意：

- 模板里的非法 HTML 会变成构建错误。
- `@astrojs/db` 的项目要迁到 Drizzle 或 `node:sqlite`。
- 自定义 Markdown 插件可能因为处理器更换而行为变化。
- `src/fetch.ts` 是保留文件名，项目里有同名文件要改名。

升级流程建议：开分支 → 升依赖 → `astro check` → `astro build` → 本地 `preview` 逐页点一遍 → 部署到预览环境 → 合并。

## 10.10 版本与特性对照

| 版本 | 关键特性 |
|---|---|
| v1 | 首个稳定版本，静态站点生成 |
| v2 | 内容集合（实验）、图像优化雏形 |
| v3 | 图像优化稳定、视图过渡（实验）、混合渲染雏形 |
| v4 | 视图过渡稳定、i18n 路由、Actions（实验）、Dev Toolbar |
| v5 | 内容层与 loader 稳定、服务器群岛、Sessions、`<ClientRouter />`、CSRF 默认开启 |
| v6 | Node 22、Vite 7、Zod 4、字体/CSP/live collections 稳定、移除旧内容集合 API |
| v7 | Rust 编译器、Sätteri Markdown、`compressHTML: 'jsx'` 默认、移除 `@astrojs/db` |

这张表用来判断"某篇教程/某段代码属于哪个年代"。看到 `getStaticProps` 是 Next 的；看到 `output: 'hybrid'`、`entry.render()`、`post.slug`、`src/content/config.ts`，基本都是 v4 及以前的写法，在 v7 上跑不通。

## 10.11 本章小结

- 集成是带钩子的对象，`integrations` 顺序会影响结果。
- Tailwind 4 不再用 `@astrojs/tailwind`，改用 `@tailwindcss/vite`。
- `astro build` 不做类型检查，`astro check` 要单独装和跑。
- 部署到子路径必须同时配 `site` 和 `base`。
- 按需部署前确认目标运行时：Cloudflare 没有 `fs` 和 Sharp。
- 静态资源配一年长缓存，HTML 配 must-revalidate，按需页面用 `s-maxage` 控制回源。
- 开 `security.csp` 就不能用 `<ClientRouter />` 的视图过渡，Shiki 也要换成 Prism。
- 上线前确认每个页面到底是静态还是按需，构建日志是唯一依据。
- 升级用 `npx @astrojs/upgrade`，重点看依赖要求、实验标志、移除项。
- v7 的 Rust 编译器更严格，非法 HTML 会直接构建失败。

到这里，从安装、组件、路由、样式、内容、图片、群岛、服务端能力、数据获取到部署，一条完整的链路就过完了。剩下的部分（自定义集成、适配器开发、内部渲染流程）属于扩展 Astro 本身，用不到就先不碰，遇到具体需求再查官方 API 参考。
