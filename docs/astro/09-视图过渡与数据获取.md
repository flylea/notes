# 第 9 章 数据获取与环境变量

## 9.1 数据在哪一层取

同一个数据源有三种取法，代价完全不同：

| 取数位置 | 执行时机 | 结果 | 适合 |
|---|---|---|---|
| 构建期（frontmatter） | `astro build` 时一次 | 写进 HTML | 内容、配置、变化慢的数据 |
| 请求期（按需渲染页面） | 每次请求 | 每次现生成 | 登录后的数据、实时价格、搜索结果 |
| 浏览器（客户端脚本） | 组件挂载后 | 异步填进页面 | 用户交互后才有意义的数据、轮询 |

判断顺序是：

1. 数据在构建时是否已知且不常变？是，构建期取。
2. 数据是否依赖当前用户或请求？是，请求期取。
3. 数据是否只跟用户的操作有关，首屏不需要？是，浏览器取。

三条都有坑。构建期取数意味着内容更新要重新部署；请求期取数意味着每次请求都要等上游接口；浏览器取数意味着首屏会有一段空白。选之前先想清楚你能接受哪种代价。

## 9.2 构建期取数

组件的 frontmatter 里直接 `await`：

```astro
---
// src/pages/blog.astro
const res = await fetch('https://api.example.com/posts');
if (!res.ok) {
  throw new Error(`拉取文章失败：HTTP ${res.status}`);
}
const posts = await res.json();
---

<ul>
  {posts.map((post: { id: string; title: string }) => (
    <li><a href={`/blog/${post.id}`}>{post.title}</a></li>
  ))}
</ul>
```

生成的 HTML 里直接就是文章列表，访问者拿到的是一个静态页面，没有额外的数据请求。

要点：

- `fetch` 在构建时执行，部署后不再执行。上游数据更新了，站点不会自动更新，要重新构建。这就是为什么内容类项目通常用内容集合（第 5 章）而不是外部 API：内容跟代码一起进 Git，改动有记录，构建结果可复现。
- `fetch` 只在**构建的那次**执行一次，`Promise.all` 的并行是有效的。而在按需渲染页里，每个请求都重新执行。
- `res.ok` 必须手动判断。`fetch` 只在网络层失败时抛错，HTTP 404、500 都算"成功返回"，`res.json()` 会拿到一个错误对象，页面不报错但内容是错的。
- 构建期失败等于构建失败。上游接口不稳定时，要么加重试，要么把数据落成内容集合。

## 9.3 请求期取数

页面声明按需渲染后，`fetch` 挪到每次请求：

```astro
---
// src/pages/stock/[sku].astro
export const prerender = false;

const { sku } = Astro.params;

const res = await fetch(`https://api.example.com/stock/${sku}`, {
  headers: { 'X-API-Key': import.meta.env.STOCK_API_KEY },
  signal: AbortSignal.timeout(3000),
});

if (res.status === 404) {
  return new Response(null, { status: 404, statusText: '商品不存在' });
}

if (!res.ok) {
  Astro.response.status = 502;
  throw new Error(`上游不可用：HTTP ${res.status}`);
}

const stock = await res.json();
Astro.response.headers.set('Cache-Control', 'public, max-age=10');
---

<p>库存：{stock.count}</p>
```

注意几处：

- `AbortSignal.timeout(3000)` 给上游设超时。不设的话，慢接口会把页面的响应时间拖到几十秒，用户只看到白屏。
- `Astro.response.status` 和 `Astro.response.headers` 在页面代码里改，影响最终响应。
- 缓存头只对按需渲染的响应有意义。`max-age=10` 表示 10 秒内同一个 URL 的请求直接走 CDN，不再打到上游。缓存的时长就是你能接受的"数据陈旧"上限。
- 404 用 `return new Response(...)`，不要再渲染页面。返回 `Response` 时页面模板不会执行。

页面内部请求自己的接口时，用 `new URL()` 拼绝对地址：

```astro
---
const res = await fetch(new URL('/api/posts', Astro.url));
const posts = await res.json();
---
```

相对路径的 `fetch` 在 Node 环境里会报 `Failed to parse URL from /api/posts`。服务端没有"当前域名"的概念，必须给完整 URL。

## 9.4 并行与错误处理

多个独立数据源用 `Promise.all` 并行：

```astro
---
const [posts, tags, config] = await Promise.all([
  fetch('https://api.example.com/posts').then((r) => r.json()),
  fetch('https://api.example.com/tags').then((r) => r.json()),
  fetch('https://api.example.com/config').then((r) => r.json()),
]);
---
```

`Promise.all` 的特点是一个失败，整体失败。这里三个数据都是页面必需，失败就该让页面失败，这是对的。

如果某个数据源可以缺失，用 `Promise.allSettled`：

```astro
---
const results = await Promise.allSettled([
  fetch('https://api.example.com/posts').then((r) => r.json()),
  fetch('https://api.example.com/recommend').then((r) => r.json()),
]);

const posts = results[0].status === 'fulfilled' ? results[0].value : [];
const recommend = results[1].status === 'fulfilled' ? results[1].value : [];
---

{recommend.length > 0 ? (
  <aside>推荐：{recommend.length} 条</aside>
) : (
  <aside>暂无推荐</aside>
)}
```

要逐个处理错误，就写一个薄封装：

```ts
// src/lib/fetch-json.ts
export async function fetchJson<T>(url: string, init?: RequestInit): Promise<T | null> {
  try {
    const res = await fetch(url, { signal: AbortSignal.timeout(5000), ...init });
    if (!res.ok) return null;
    return (await res.json()) as T;
  } catch {
    return null;
  }
}
```

返回 `null` 而不是抛错，调用方用 `?? 默认值` 兜底。这比在每个页面写 `try/catch` 干净。

一个常见的性能陷阱是**请求瀑布**：先取用户 ID，再用 ID 取订单，再用订单取商品。三步串行，延迟是三倍。能在一次请求里带上的参数就别分三次，或者用 `Promise.all` 把能并行的部分拆出来。

## 9.5 客户端取数

只有这几种情况才该在浏览器里取数：

- 数据依赖用户输入（搜索建议、表单校验）。
- 数据需要轮询或实时推送。
- 首屏不需要，滚动到某个位置才加载。

用框架组件写：

```tsx
// src/components/Comments.tsx
import { useEffect, useState } from 'react';

type Comment = { id: string; author: string; body: string };

export default function Comments({ postId }: { postId: string }) {
  const [comments, setComments] = useState<Comment[]>([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    let cancelled = false;

    fetch(`/api/posts/${postId}/comments`)
      .then((r) => (r.ok ? r.json() : []))
      .then((data) => {
        if (!cancelled) setComments(data);
      })
      .finally(() => {
        if (!cancelled) setLoading(false);
      });

    return () => {
      cancelled = true;
    };
  }, [postId]);

  if (loading) return <p>加载评论中…</p>;

  return (
    <ul>
      {comments.map((c) => (
        <li key={c.id}>
          <strong>{c.author}</strong>：{c.body}
        </li>
      ))}
    </ul>
  );
}
```

页面里挂载：

```astro
---
import Comments from '../components/Comments.tsx';
---

<Comments postId={Astro.params.id!} client:load />
```

代价要说清楚：

- 首屏会先显示"加载中"，然后才出内容。墓碑布局（预留高度）没做好，会造成页面跳动。
- 每个客户端组件都带一份框架运行时。评论列表不值得引入整个 React，能静态渲染就静态渲染。
- 客户端取数只能访问公开接口。要鉴权的数据走 Actions 或按需端点，不要把密钥放进浏览器。
- `useEffect` 里发请求要处理组件卸载（上面的 `cancelled` 标志），否则卸载后 `setState` 会报警告。

## 9.6 环境变量

`.env` 文件放在项目根目录：

```ini
# .env
# 只在服务端可用
DATABASE_URL="postgres://..."
STRIPE_SECRET_KEY="sk_live_..."

# 客户端也能访问
PUBLIC_SITE_URL="https://example.com"
PUBLIC_ANALYTICS_ID="G-XXXXXXXXXX"
```

规则很简单：`PUBLIC_` 前缀的变量会打进客户端包，没有前缀的只在服务端可用。

```astro
---
// 服务端可用
const secret = import.meta.env.STRIPE_SECRET_KEY;

// 服务端和浏览器都可用
const siteUrl = import.meta.env.PUBLIC_SITE_URL;
---

<script>
  // 浏览器里只能拿到 PUBLIC_ 变量
  console.log(import.meta.env.PUBLIC_ANALYTICS_ID);
</script>
```

几个必须知道的点：

- 环境变量在**构建时内联**。改了 `.env` 要重启开发服务器；静态构建改了 `.env` 要重新构建，产物里写死的是构建时的值。
- 没有 `PUBLIC_` 前缀的变量在客户端是 `undefined`，不会报错。把密钥变量误用在前端，页面不会报错，密钥也不会泄漏，但功能会静默失效，这个坑排查起来很费时间。
- `import.meta.env.SSR` 可以判断当前是服务端还是客户端（`true` 表示服务端），用它写同构代码。
- `astro.config.mjs` 里**不能**用 `import.meta.env` 读 `.env`。配置文件在加载 `.env` 之前就被求值了，要用 `process.env` 配合 `loadEnv`，或者干脆只在运行时读取。

TypeScript 想要补全，在 `src/env.d.ts` 里声明：

```ts
// src/env.d.ts
/// <reference types="astro/client" />

interface ImportMetaEnv {
  readonly PUBLIC_SITE_URL: string;
  readonly PUBLIC_ANALYTICS_ID: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}
```

只声明 `PUBLIC_*` 就够了，服务端变量直接用 `process.env` 读，类型更清楚。

区分环境用模式文件：

```ini
# .env.development
PUBLIC_API_BASE="http://localhost:8787"

# .env.production
PUBLIC_API_BASE="https://api.example.com"
```

```bash
astro dev                          # 读 .env.development
astro build                        # 读 .env.production
astro build --mode staging         # 读 .env.staging
```

## 9.7 用 astro:env 做类型安全

`import.meta.env` 的问题是所有变量都是字符串，拼错了也不报错。`astro:env` 把环境变量变成带类型的模块：

```js
// astro.config.mjs
import { defineConfig, envField } from 'astro/config';

export default defineConfig({
  env: {
    schema: {
      API_URL: envField.string({ context: 'client', access: 'public' }),
      PORT: envField.number({ context: 'server', access: 'public', default: 4321 }),
      API_SECRET: envField.string({ context: 'server', access: 'secret' }),
      LOG_LEVEL: envField.enum({
        context: 'server',
        access: 'public',
        values: ['debug', 'info', 'warn', 'error'],
        default: 'info',
      }),
    },
  },
});
```

`context` 是 `'client'` 或 `'server'`，`access` 是 `'public'` 或 `'secret'`，两两组合出三种变量：

| 组合 | 可用位置 | 是否进客户端包 |
|---|---|---|
| `client` + `public` | 服务端和浏览器 | 是 |
| `server` + `public` | 服务端 | 否，但在服务端包里 |
| `server` + `secret` | 服务端 | 否，运行时读取 |

`client` + `secret` 不允许配置，因为没法安全地把密钥送到浏览器。

使用：

```astro
---
import { API_URL } from 'astro:env/client';
import { API_SECRET, PORT } from 'astro:env/server';

const res = await fetch(`${API_URL}/users`, {
  headers: { Authorization: `Bearer ${API_SECRET}` },
});
---

<p>端口：{PORT}</p>
```

类型在 `astro dev`、`astro build` 时自动生成，也可以单独跑 `astro sync`。

变量值不合法时构建直接失败：

```
The following environment variables defined in `env.schema` are invalid.
```

这比 `import.meta.env` 返回 `undefined` 好得多：在构建时就失败，而不是线上静默出错。

几个细节：

- secret 默认在运行时校验：只要导入了 `astro:env/server`，所有 secret 都会被检查。想提前到启动或构建时报错，设 `env.validateSecrets: true`，CI 里可以靠它在部署前发现漏配的密钥。
- 需要动态读未声明的密钥时，用 `getSecret()`：

```ts
import { getSecret } from 'astro:env/server';
const key = getSecret('SOME_UNSCHEMA_KEY'); // string | undefined
```

- `astro:env` 是虚拟模块，只能在 Astro 上下文里用：中间件、页面、端点、组件、普通模块。`astro.config.mjs` 和独立脚本里用不了，那里只能用 `process.env`。

什么时候用它：项目配置项超过三五个、多人协作、部署到多个环境。小项目用 `import.meta.env` 也够，别为了一个变量引入 schema。

## 9.8 国际化路由

配置：

```js
// astro.config.mjs
import { defineConfig } from 'astro/config';

export default defineConfig({
  site: 'https://example.com',
  i18n: {
    defaultLocale: 'zh',
    locales: ['zh', 'en', 'ja'],
    routing: {
      prefixDefaultLocale: false,
    },
  },
});
```

`prefixDefaultLocale: false` 表示默认语言不带前缀：`/about/` 是中文，`/en/about/` 是英文。设为 `true` 则三种语言都带前缀，默认语言也要放在 `src/pages/zh/` 下。

目录必须和 `locales` 一一对应：

```
src/pages/
├── index.astro          → /
├── about.astro          → /about/
├── en/
│   ├── index.astro      → /en/
│   └── about.astro      → /en/about/
└── ja/
    └── index.astro      → /ja/
```

生成链接用 `astro:i18n` 的辅助函数，不然路径拼错很难发现：

```astro
---
import { getRelativeLocaleUrl } from 'astro:i18n';

const enAbout = getRelativeLocaleUrl('en', 'about');
const jaHome = getRelativeLocaleUrl('ja', '/');
---

<a href={enAbout}>English</a>
<a href={jaHome}>日本語</a>
<a href={getRelativeLocaleUrl(Astro.currentLocale, 'contact')}>联系</a>
```

页面里能拿到的：

- `Astro.currentLocale`：根据当前 URL 算出来的语言，所有页面都有，静态页面也能用。
- `Astro.preferredLocale`：根据浏览器 `Accept-Language` 算出的语言，只在按需渲染页面可用，没有匹配时是 `undefined`。
- `Astro.preferredLocaleList`：浏览器和站点都支持的语言列表。

按需渲染的首页可以据此跳转：

```astro
---
export const prerender = false;

if (Astro.preferredLocale && Astro.preferredLocale !== Astro.currentLocale) {
  return Astro.redirect(getRelativeLocaleUrl(Astro.preferredLocale, '/'));
}
---
```

翻译还没写全时用 fallback，缺页不会 404：

```js
i18n: {
  defaultLocale: 'zh',
  locales: ['zh', 'en'],
  fallback: { en: 'zh' },
  routing: { fallbackType: 'rewrite' },
}
```

`fallbackType: 'rewrite'` 表示直接渲染中文内容但不改 URL，`'redirect'` 则跳到中文地址。前者对 SEO 友好一点，后者用户能明确知道自己在看备用语言。

三个容易忘的点：

- `<html lang={Astro.currentLocale}>` 要自己写，i18n 配置不会自动加到 HTML 上。
- `<link rel="alternate" hreflang="..." />` 也要自己加，配合 `Astro.site` 生成绝对地址。
- `locales` 里写 `zh` 还是 `zh-CN` 是任意字符串，但要和目录名一致，且 URL 里会原样出现。

需要完全自定义语言判定（比如按国家、按 cookie、按子域名）时，配置 `i18n.routing.manual` 或 `i18n.domains`，自己写中间件。内置路由覆盖大部分场景，先别上手动模式。

## 9.9 数据库方案的选择

三条路，按复杂度排序：

1. **内容集合**（第 5 章）：数据在 Git 里，构建时读取。博客、文档、产品目录够用，没有运行时数据库。
2. **SQLite 文件**：Node 适配器下用内置的 `node:sqlite`（Node 22.5 起提供），适合小型站点、单实例、数据量不大。
3. **外部数据库 + ORM**：Postgres、MySQL、Turso 等，配 Drizzle、Prisma 之类的 ORM。数据量大、有写入、多实例部署时选这条。连接串放服务端环境变量，在按需渲染页面或端点里用。

`@astrojs/db`（Astro DB）在 v7 已从代码库移除，不再维护。旧项目还在用它的，升级到 v7 前要换成上面三条路之一：原本当本地 SQLite 用的换 `node:sqlite`，原本用它的 Drizzle 风格 schema 的，直接上 Drizzle。

## 9.10 本章小结

- 构建期取数写进 HTML，部署后不更新；请求期取数每次现取，要自己处理超时、错误和缓存。
- `fetch` 不会因为 HTTP 4xx/5xx 抛错，必须判断 `res.ok`。
- 服务端 `fetch` 相对路径会失败，用 `new URL(path, Astro.url)`。
- 客户端取数只用于交互和实时数据，代价是首屏空白和框架运行时。
- 没有 `PUBLIC_` 前缀的变量在浏览器里是 `undefined`，静默失效。
- 环境变量构建时内联，`astro.config.mjs` 里读不到 `.env`。
- `astro:env` 提供类型和构建期校验，适合配置项多的项目。
- i18n 靠目录结构 + 配置，链接用 `astro:i18n` 的辅助函数生成。
- 数据库优先考虑内容集合，其次外部数据库，Astro DB 只适合小站点。
