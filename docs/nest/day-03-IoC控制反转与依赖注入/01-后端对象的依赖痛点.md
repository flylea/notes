# 后端对象的依赖关系痛点

## 一个简单的场景

假设你在写图书管理系统的后端。最简单的写法：把所有逻辑写在一个文件里。

```typescript
// 一个文件搞定（原生 http 风格）
import * as http from 'http';
import * as fs from 'fs';

const server = http.createServer(async (req, res) => {
  if (req.url === '/api/users/register' && req.method === 'POST') {
    // 读 Body → 校验 → 查重（读 JSON 文件）→ 写入 → 返回
    let body = '';
    req.on('data', c => body += c);
    req.on('end', async () => {
      const { username, password } = JSON.parse(body);

      // 参数校验
      if (!username || !password) {
        res.writeHead(400);
        return res.end(JSON.stringify({ message: '参数不完整' }));
      }

      // 查重（读文件）
      const data = JSON.parse(await fs.promises.readFile('users.json', 'utf-8'));
      if (data.users.find(u => u.username === username)) {
        res.writeHead(400);
        return res.end(JSON.stringify({ message: '用户已存在' }));
      }

      // 写文件
      data.users.push({ username, password });
      await fs.promises.writeFile('users.json', JSON.stringify(data));

      res.writeHead(201);
      res.end(JSON.stringify({ username }));
    });
  }
});

server.listen(3000);
```

**这段代码的问题是什么？**

## 问题一：无法单独测试

你想测试"查重逻辑"——它和 `http` 请求解析、`fs` 文件读写、响应发送**全部耦合在一起**。测试一个简单的 "if username exists" 逻辑需要模拟整个 HTTP 层。

## 问题二：一个改动牵连全身

文件存储从 JSON 改为 MySQL？你需要改**所有**读/写文件的地方（这个简单例子只有 2 处，真实项目可能有 20 处）。日志记录变更为 Winston？又得改 20 处。

## 问题三：代码无法复用

`BookService` 也需要读文件？你得把读文件的逻辑**复制粘贴**过去。或者抽个函数？那函数放哪个文件？什么命名约定？

## 传统的"解决方案"及其局限

### 尝试 1：抽成类

```typescript
// user.service.ts
export class UserService {
  private db = new JsonDatabase('users.json');

  async register(username: string, password: string) {
    const users = await this.db.read();
    // ... 业务逻辑
  }
}

// book.service.ts
export class BookService {
  private db = new JsonDatabase('books.json');

  async findAll() {
    return this.db.read();
  }
}
```

好了一点，但 `new JsonDatabase` 是**硬编码**的——它直接写死了依赖的**具体实现**。将来换成 `MysqlDatabase`，你又得改所有 `new JsonDatabase` 的地方。

### 尝试 2：抽接口

```typescript
// database.interface.ts
interface Database {
  read(): Promise<any[]>;
  write(data: any[]): Promise<void>;
}

// user.service.ts
export class UserService {
  constructor(private db: Database) {}  // 依赖接口，不依赖具体实现

  async register(username: string, password: string) {
    const users = await this.db.read();
    // ...
  }
}

// 组装（在某个地方手动 new）
const db = new JsonDatabase('users.json');
const userService = new UserService(db);
```

这个方向对了——依赖抽象（`Database` 接口）而不是具体实现（`JsonDatabase`）。但还有一个问题：

**组装代码由谁写？放哪里？**

在一个有 5 个 Service、3 个 Controller 的应用里，组装代码会变成：

```typescript
const config = new ConfigService();
const db = new MysqlDatabase(config.get('DB_URL'));
const cache = new RedisCache(config.get('REDIS_URL'));
const userRepo = new UserRepository(db);
const bookRepo = new BookRepository(db);
const userService = new UserService(userRepo, cache);
const bookService = new BookService(bookRepo, userService);  // 循环依赖！
const userController = new UserController(userService);
const bookController = new BookController(bookService);
// ... 30 行之后还在 new
```

这种手动组装的代码被称为**"装配地狱"**。当你修改了一个依赖时，装配代码也要跟着改。

## IoC 容器的答案

不用手动 new，而是**声明你的依赖**，然后由框架自动创建和注入：

```typescript
// 不需要这行：const db = new JsonDatabase(...)
// 只需要声明：

@Injectable()
export class UserService {
  constructor(private readonly db: Database) {}  // 声明："我需要一个 Database"
  // Nest IoC 容器会自动找到 Database 的实现 → 创建实例 → 注入进来
}
```

这就是 IoC 的核心价值：**你不再控制对象的创建，容器替你控制。你只需要声明你需要什么。**
