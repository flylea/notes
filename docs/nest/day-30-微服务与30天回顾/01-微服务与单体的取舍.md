# 微服务 vs 单体架构的取舍

## 什么是单体架构

```
┌──────────────────────────────┐
│        单体应用 (Monolith)     │
│                              │
│  ┌────────┐  ┌────────────┐  │
│  │ 用户模块│  │  图书模块   │  │
│  └────────┘  └────────────┘  │
│  ┌────────┐  ┌────────────┐  │
│  │ 借阅模块│  │  统计模块   │  │
│  └────────┘  └────────────┘  │
│                              │
│     共享同一个数据库、同一个进程  │
└──────────────────────────────┘
```

图书管理系统到目前为止就是单体——所有功能模块跑在一个进程里，共享一个数据库。这是最自然的架构方式，也是 90% 项目最正确的选择。

## 什么是微服务架构

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  user-service │    │ book-service │    │borrow-service│
│   用户服务     │    │   图书服务    │    │   借阅服务    │
│   DB: user    │    │   DB: book   │    │  DB: borrow  │
└──────┬───────┘    └──────┬───────┘    └──────┬───────┘
       │                   │                   │
       └───────────────────┼───────────────────┘
                           │
                    ┌──────┴───────┐
                    │  API Gateway │  ← 统一入口
                    └──────┬───────┘
                           │
                        浏览器
```

每个服务独立部署、独立数据库、独立缩容扩容。服务间通过 HTTP/RPC/消息队列 通信。

## 单体 vs 微服务对比

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 开发效率 | 高（一个项目，改完即跑） | 低（多个服务，联调复杂） |
| 部署复杂度 | 低（一个包，一个进程） | 高（多个服务，编排部署） |
| 调试难度 | 低（本地直接 debug） | 高（远程调用链路追踪） |
| 团队规模 | 2-10 人 | 20-200+ 人 |
| 数据库事务 | 简单（本地事务） | 复杂（分布式事务） |
| 资源利用率 | 低（整体扩缩） | 高（热点服务单独扩） |
| 技术异构 | 受限（同一语言） | 自由（每个服务选不同语言） |
| 故障隔离 | 差（一个模块 OOM 全挂） | 好（故障隔离） |
| 代码复用 | 简单（直接引用） | 复杂（共享库版本管理） |

## 什么时候不该用微服务

```
❌ 团队只有 3-5 个人 → 微服务的管理成本远超收益
❌ 项目刚起步，需求不确定 → 边界画错，后面全要重拆
❌ 数据强一致要求高 → 分布式事务极其复杂
❌ 业务逻辑简单 → 没必要
❌ 基础设施不足（没有 K8s/监控/链路追踪） → 运维灾难
```

> 前端类比：就像你不会在 Admin 管理后台这种 3 个页面的项目里上微前端（qiankun）——过度工程是最大的浪费。

## 什么时候可以考虑微服务

```
✅ 团队 20+ 人，单体代码冲突频繁
✅ 某个模块需要独立扩缩容（比如秒杀模块流量是其他模块的 100 倍）
✅ 部分模块需要不同技术栈（AI 推理用 Python，核心用 Nest）
✅ 需要独立部署节奏（核心系统稳定，创新功能快速迭代）
✅ 组织架构就是按业务线分的（康威定律）
```

## 从单体到微服务的演化路径

```
阶段 1：好好写单体（1-3 人）
  做好模块边界
  Module 之间通过 Service 调用，不直接访问对方的数据库
  ← 你现在在这里

阶段 2：模块化单体（3-10 人）
  严格模块边界
  Module 之间用 EventEmitter 解耦（Day 26）
  提取共享库到 libs/（Day 29）

阶段 3：抽出第一个微服务（10-20 人）
  找一个边界最清晰、变更最频繁的模块
  数据库也拆出去
  用消息队列同步数据

阶段 4：逐步拆分（20+ 人）
  按业务域逐个拆分
  引入 API Gateway
  建立服务发现、配置中心、链路追踪
```

**最重要的原则**：不要一开始就建微服务。先写单体，等真正痛了再拆。

没人会因为"我们的项目是单体架构"而羞愧——但很多人会为"我们的项目是微服务架构，只有 3 个用户"后悔。
