# Nest 项目目录结构详解

## 每个文件的职责

### main.ts — 应用生命周期的起点

```typescript
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  // 全局配置在这里
  // app.useGlobalPipes(...)
  // app.useGlobalFilters(...)
  await app.listen(3000);
}
bootstrap();
```

一次性的全局配置放在这里：全局 Pipe、全局 Filter、全局 Interceptor、CORS 配置、静态文件服务等。

### app.module.ts — 应用的装配中心

```typescript
@Module({
  imports: [
    PrismaModule,   // 全局模块（数据库）
    UserModule,     // 用户模块
    BookModule,     // 图书模块
  ],
})
export class AppModule {}
```

AppModule 不做业务逻辑，只负责**组装**——把各个业务模块引入进来。

### xxx.module.ts — 业务模块的组织单元

```typescript
@Module({
  imports: [],           // 依赖的其他模块
  controllers: [...],    // 该模块处理的路由
  providers: [...],      // 该模块的服务/逻辑
  exports: [...],        // 给其他模块共享的 Provider
})
export class XxxModule {}
```

### xxx.controller.ts — 路由和请求处理

```typescript
@Controller('users')    // 路由前缀
export class UserController {
  constructor(private userService: UserService) {}

  @Get()                 // GET /users
  @Post()                // POST /users
  @Get(':id')            // GET /users/:id
}
```

Controller **只做两件事**：
1. 解析请求参数（`@Body/@Query/@Param`）→ 传给 Service
2. 返回响应数据（直接 return，Nest 自动序列化为 JSON）

> Controller 不应该包含业务逻辑。如果 Controller 方法超过 5 行，大概率是把 Service 的活写这里了。

### xxx.service.ts — 业务逻辑

```typescript
@Injectable()
export class UserService {
  constructor(private prisma: PrismaService) {}

  async create(dto: CreateUserDto) { /* 业务逻辑 */ }
  async findById(id: number) { /* 业务逻辑 */ }
}
```

Service 是**业务逻辑的唯一归属**——校验、计算、数据库操作都在这里。

### dto/ — 数据传输对象

```typescript
// create-user.dto.ts
export class CreateUserDto {
  @IsNotEmpty()
  username: string;

  @MinLength(6)
  password: string;
}
```

DTO 定义**输入数据的结构和校验规则**。每个需要接收客户端数据的操作都应该有对应的 DTO。

### entities/ — 实体定义

```typescript
// user.entity.ts
export class User {
  id: number;
  username: string;
  password: string;
  createdAt: Date;
}
```

Entity 定义**业务实体的属性结构**。在用 Prisma 时，Entity 的类型可以直接用 Prisma 生成的类型（`Prisma.User`），不需要手动维护。

## 前端项目结构对比

### Create React App / Vite + React

```
src/
├── main.jsx              # 应用入口 ←→ main.ts
├── App.jsx               # 根组件 ←→ app.module.ts
├── api/                  # API 请求层 ←→ Service
├── components/           # 可复用 UI ←→ 无直接对应
├── pages/               # 页面级组件 ←→ Controller
│   ├── UserList.jsx
│   └── UserDetail.jsx
├── store/               # 状态管理 ←→ 无直接对应（后端数据在数据库）
└── utils/               # 工具函数 ←→ utils/
```

### Vue + Vite

```
src/
├── main.ts               # 应用入口 ←→ main.ts
├── App.vue               # 根组件 ←→ app.module.ts
├── views/               # 页面 ←→ Controller
│   ├── UserView.vue
│   └── BookView.vue
├── composables/         # 组合式逻辑 ←→ Service
│   ├── useUser.ts
│   └── useBook.ts
├── stores/              # Pinia 状态 ←→ 数据库
└── utils/               # 工具函数 ←→ utils/
```

### 关键思维转变

| 前端关心 | 后端关心 |
|---------|---------|
| 页面路由（URL → 组件） | API 路由（URL → Controller 方法） |
| 组件状态（ref/reactive/useState） | 数据库记录（表中的行） |
| API 调用（fetch/axios） | 数据库查询（Prisma/SQL） |
| 用户交互（onClick/onSubmit） | HTTP 请求（GET/POST） |
| UI 渲染（v-for/map） | JSON 序列化（Nest 自动） |
| localStorage | 文件系统 / Redis |
