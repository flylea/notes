# 五大切面全景图

## 一张图看懂所有切面

```
HTTP 请求
  │
  ▼
┌─────────────────────────────────────────────────────────────────┐
│                     Middleware （中间件）                         │
│  职责：请求/响应的底层处理（body-parser、CORS、Session）            │
│  能拿到：原始 Request/Response 对象                               │
│  不能拿到：handler 的元数据（不知道调的是哪个 Controller）            │
│  特点：与 Express 中间件兼容                                      │
└──────────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────┐
│                     Guard （守卫）                                │
│  职责：鉴权——"你能不能访问这个路由？"                              │
│  能拿到：ExecutionContext（可以知道调的是哪个 handler）             │
│  典型场景：检查 token、检查角色权限、返回 401/403                   │
│  返回：boolean | Promise<boolean> | Observable<boolean>           │
└──────────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
┌─ Interceptor (前) ──────────────────────────────────────────────┐
│  职责：方法调用前的通用逻辑                                       │
│  典型场景：记录请求开始时间、缓存命中直接返回                       │
└──────────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────┐
│                     Pipe （管道）                                 │
│  职责：参数校验 + 类型转换——'"输入是否合法？"                      │
│  能拿到：方法参数（Body/Query/Param 等）                           │
│  典型场景：ValidationPipe 校验 DTO、ParseIntPipe 转换类型          │
│  返回：转换后的值 | 抛出异常                                       │
└──────────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────┐
│                Controller （路由处理器）                          │
│  职责：协调请求/响应，调用 Service                                 │
│  ⭐ 这里才是你的业务代码                                          │
└──────────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
┌─ Interceptor (后) ──────────────────────────────────────────────┐
│  职责：方法调用后的通用逻辑                                       │
│  典型场景：统一响应格式包装、记录请求耗时                          │
└──────────────────────────────────┬──────────────────────────────┘
                                  │
                                  │   如果 Controller 中抛出异常
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────┐
│                  ExceptionFilter （异常过滤器）                    │
│  职责：异常捕获 + 统一错误响应格式                                 │
│  能拿到：Controller 中抛出的任何异常                               │
│  典型场景：BadRequestException → 规范的 JSON 错误响应              │
└──────────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
                            HTTP 响应
```

## 五切面对比速查表

| 切面 | 执行时机 | 主要职责 | 能否知道 Handler | 能否阻止请求 | 典型产出 |
|------|---------|---------|:---:|:---:|---------|
| Middleware | 最早 | 请求预处理 | ❌ | 能 | 修改 req/res 对象 |
| Guard | Middleware 之后 | 鉴权 | ✅ | 能 | 返回 true/false |
| Interceptor(前) | Guard 之后 | 请求前逻辑 | ✅ | 能 | 可替换返回值 |
| Pipe | Interceptor 之后 | 参数校验 | ✅ | 能 | 转换后的值或抛异常 |
| Controller | Pipe 之后 | 业务处理 | — | — | 业务数据 |
| Interceptor(后) | Controller 之后 | 响应后逻辑 | ✅ | — | 包装响应格式 |
| ExceptionFilter | 任何阶段 | 异常处理 | ✅ | — | 统一错误格式 |

## 为什么要分 5 种？

### 1. 单一职责

如果只有一种切面，你会写出这样的代码：

```typescript
// 反模式：所有切面逻辑堆在一个类里
@Injectable()
export class GodMiddleware implements NestMiddleware {
  use(req: any, res: any, next: () => void) {
    // 1. 日志（属于 Interceptor）
    console.log(`${req.method} ${req.url}`);

    // 2. Session 解析（属于 Middleware）
    if (req.cookies.session) {
      req.user = parseSession(req.cookies.session);
    }

    // 3. 权限检查（属于 Guard）
    if (!req.user && !req.path.startsWith('/public')) {
      return res.status(401).json({ error: 'Unauthorized' });
    }

    // 4. 参数校验（属于 Pipe）
    if (req.method === 'POST' && !req.body.username) {
      return res.status(400).json({ error: 'username required' });
    }

    next();
  }
}
```

问题：这个类把所有事情都干了——日志、Session、权限、校验混在一起，哪天只需要改校验逻辑，却要改一个包含所有职责的大文件。

### 2. 正确的分离

```typescript
// Middleware：只管 Session 解析
// Guard：只管 token 校验
// Pipe：只管参数校验
// Interceptor：只管日志
// ExceptionFilter：只管异常处理
```

每个切面只做一件事，代码清晰、可测试、可单独替换。

### 3. 每个切面有正确的"上下文"信息

Middleware 拿不到"哪个方法被调用了"这个信息（它只知道 req/res），而 Guard/Pipe/Interceptor 通过 ExecutionContext 可以精确知道：

```typescript
@Injectable()
export class RoleGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const handler = context.getHandler();  // 拿到被调用的方法
    const requiredRoles = this.reflector.get<string[]>('roles', handler);
    // 这时就能检查：这个接口需要什么角色？当前用户有没有这个角色？
    return true;
  }
}
```

Middleware 做不到这一点——这是 Nest 为什么需要 Guard/Pipe/Interceptor 这些"更高级的切面"的核心原因。

## 各切面的核心接口

| 切面 | 需实现的接口 | 核心方法 |
|------|------------|---------|
| Middleware | `NestMiddleware` | `use(req, res, next)` |
| Guard | `CanActivate` | `canActivate(context: ExecutionContext)` |
| Interceptor | `NestInterceptor` | `intercept(context, next: CallHandler)` |
| Pipe | `PipeTransform` | `transform(value, metadata)` |
| ExceptionFilter | `ExceptionFilter` | `catch(exception, host: ArgumentsHost)` |

## 注册方式对比

每个切面都可以在 4 个级别注册：

```
全局 (app.useGlobalXxx())           → 应用于所有路由
Module (在 @Module 中配置)          → 应用于该模块的所有路由
Controller (@Controller 级别)       → 应用于该 Controller 的所有路由
Handler (@UseGuards 等方法级别)      → 只应用于该 Handler
```

级别越具体，优先级越高（Handler 级别 > Controller 级别 > Module 级别 > 全局）。
