# 11.01 用 Swagger 自动生成 api 文档

到这里项目已经有一批接口：登录、会议室、预订、统计。现在换一个视角——**前端同事、联调方、三个月后的你自己，怎么知道这些接口长什么样**？答案不是「写个 Word」，而是让代码生成文档，并让它成为可校验的契约。这一节用 `@nestjs/swagger` 把这件事做对，包括 Nest 12 才有的两个新姿势（延迟生成的工厂函数、OpenAPI 3.1），以及「生成出来的文档是错的」这类最常见的问题。

> 环境对照 `@nestjs/swagger` 12.1.0（12.1.x 为当前线）、Nest 12.6、ESM + `nodeNext`；接口地址以本书示例项目 `setGlobalPrefix('api')` 为准。

## 一、文档为什么会烂

三种「文档腐烂」的死法，你大概率见过：

1. **手写 Markdown**：改字段忘了改文档，联调时前端按文档传参、后端报 400，然后开始互相甩锅；
2. **只有注释**：注释不上类型，也不生成可交互页面，联调还得靠 Postman 一个个试；
3. **只生成不校验**：文档是自动生成的，但没人看差异，某次重构把字段从 `name` 改成 `nickname`，文档跟着变了，前端悄悄崩了。

Swagger（OpenAPI）能解决的是一、二，第三种要靠「文档进 CI」——这一节最后会讲。先把它跑起来。

```mermaid
flowchart LR
    D[装饰器 + TS 类型] --> P[编译期插件]
    P --> S[SwaggerScanner<br/>启动时/首次请求时扫描]
    S --> O[OpenAPI 文档对象]
    O --> U[Swagger UI /api/docs]
    O --> J[/api/docs-json]
    J --> C[前端 codegen]
    J --> K[CI 契约 diff]
```

## 二、最小可用：五行代码换一个可点的文档站

```bash
pnpm add @nestjs/swagger
# Fastify 适配器还需要 @fastify/static
```

```ts
// src/main.ts
import { NestFactory } from '@nestjs/core';
import { DocumentBuilder, SwaggerModule } from '@nestjs/swagger';
import { AppModule } from './app.module.js';

const app = await NestFactory.create(AppModule);
app.setGlobalPrefix('api');

const config = new DocumentBuilder()
  .setTitle('会议室预订系统 API')
  .setDescription('成功响应统一为 `{ data, meta? }`，错误统一为 `{ statusCode, message, error, requestId }`。')
  .setVersion('1.0.0')
  .addBearerAuth({ type: 'http', scheme: 'bearer', bearerFormat: 'JWT' }, 'access-token')
  .build();

const document = SwaggerModule.createDocument(app, config);
SwaggerModule.setup('api/docs', app, document);

await app.listen(Number(process.env.PORT ?? 3000));
```

访问 `http://localhost:3000/api/docs` 就是可交互的 UI；再记住它的两个「副产品」：

- `http://localhost:3000/api/docs-json`：OpenAPI JSON。**这才是给机器看的东西**——前端 codegen、Apifox 导入、CI 契约 diff 都靠它；
- `http://localhost:3000/api/docs-yaml`：同样内容的 YAML（Nest 12 默认就提供，路径可用 `yamlDocumentUrl` 改）。

`addBearerAuth` 的第二个参数 `'access-token'` 是**安全方案的名字**，后面 `@ApiBearerAuth('access-token')` 必须引用同一个名字，否则 UI 上的 Authorize 按钮和接口对不上——这是新手最常踩的一处。

## 三、Nest 12 的新姿势：把文档生成推迟到第一次请求

上面的写法在启动时就扫描全部路由、构建文档。项目一大会拖慢启动（几百毫秒到几秒），而且 `enableVersioning()` 如果放在 `createDocument()` 之后，生成的路径会**缺版本前缀**。Nest 12 的推荐做法是传一个工厂函数：

```ts
// 不在启动时生成，第一次访问文档时才构建（并缓存）
const documentFactory = () => SwaggerModule.createDocument(app, config);
SwaggerModule.setup('api/docs', app, documentFactory);
```

工厂模式顺带解决了版本前缀的顺序坑：document 在首次请求时才构建，此时 `app.enableVersioning()` 早已执行完。如果你坚持立即生成，就确保 `enableVersioning()` 写在 `createDocument()` 之前。

## 四、装饰器分层：控制器管接口，DTO 管数据

生成文档的元数据来自两类装饰器，**不要混用**：

```ts
// bookings.controller.ts
@ApiTags('bookings')                       // 分组，UI 上变成一个折叠面板
@ApiBearerAuth('access-token')             // 声明本控制器需要 bearer 认证
@Controller('bookings')
export class BookingsController {
  @Post()
  @ApiOperation({ summary: '创建预订', operationId: 'createBooking' })
  @ApiCreatedResponse({ type: BookingResponseDto })
  @ApiBadRequestResponse({ description: '时间格式错误或会议室不可用' })
  @ApiConflictResponse({ description: '时间段冲突' })
  create(@Body() dto: CreateBookingDto, @CurrentUser() user: AuthUser) { /* ... */ }
}
```

```ts
// bookings/dto/create-booking.dto.ts
export class CreateBookingDto {
  @ApiProperty({ format: 'uuid', description: '会议室 ID' })
  @IsUUID()
  roomId!: string;

  @ApiProperty({ example: '2026-11-20T09:00:00+08:00', description: 'ISO 8601 开始时间' })
  @IsISO8601()
  startTime!: string;

  @ApiPropertyOptional({ maxLength: 500, description: '备注' })
  @IsOptional()
  @IsString()
  @MaxLength(500)
  remark?: string;

  @ApiHideProperty()                     // 内部字段，不进文档
  internalNote?: string;
}
```

几条实践经验：

- **`@ApiTags` 就是导航结构**。名字用复数名词（`bookings`、`rooms`），别用中文——codegen 出来的客户端类名会用它；
- **`operationId` 决定 codegen 的函数名**。默认是 `Controller_method` 拼出来的，能跑但不好看；显式写成 `createBooking`，前端生成的就是 `createBooking()`；
- **`@ApiProperty` 的 `example` 比 `description` 有用**。UI 上「Try it out」会拿 example 预填，联调时少打很多字；
- **不要给每个字段都写 `required`**：`?` 可选、`@IsOptional()` 就已经表达了，手写 `required: false` 容易与实际校验不一致。

## 五、CLI 插件：让 DTO 一个装饰器都不用写

DTO 一多，`@ApiProperty` 的重复劳动就很烦。Nest 提供一个**编译期插件**，从 TypeScript 类型和 class-validator 装饰器反推文档：

```json
// nest-cli.json
{
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "plugins": [
      {
        "name": "@nestjs/swagger",
        "options": {
          "classValidatorShim": true,
          "introspectComments": true
        }
      }
    ]
  }
}
```

打开之后，`classValidatorShim: true` 会把 `@IsEmail()`、`@MaxLength(500)`、`@IsOptional()` 映射成 OpenAPI 的 `format`/`maxLength`/`required`；`introspectComments: true` 会把 JSDoc 的注释变成 `description`，`@example` 标签变成 `example`：

```ts
export class CreateRoomDto {
  /** 会议室名称 */
  @IsString() @MaxLength(50)
  name!: string;

  /** 可容纳人数 */
  @IsInt() @Min(1) @Max(200)
  capacity!: number;
}
```

四个必须知道的边界：

1. **只对特定后缀的文件生效**：默认 `*.dto.ts` 和 `*.entity.ts`。你的文件叫 `create-room.input.ts` 就不会被处理，要用 `dtoFileNameSuffix` 加后缀；
2. **`PartialType`/`PickType`/`OmitType` 必须从 `@nestjs/swagger` 导入**，不能从 `@nestjs/mapped-types` 导入，否则插件拿不到 schema；
3. **它只影响文档，不影响运行时校验**——`@IsEmail()` 还得留着；
4. **它是黑盒**：插件基于 AST 改写代码，出错时（联合类型、条件类型、泛型套太深）报错信息很难懂。建议**中途开启而不要一开始就全量开**，先在 `bookings` 模块试，确认生成结果符合预期再推广；`esmCompatible`、`skipAutoHttpCode` 这类选项在 ESM + 自定义状态码项目里可能需要调。

还有一个常被忽略的工程问题：**插件产物只存在于编译结果**。`tsc` 编译一次没问题，但 `nest start --watch` 的增量编译、`SWC` 编译、以及 Vitest 直接跑 TS 源码这三条路径，行为并不完全相同——SWC 不执行 TS 的 AST 变换，所以必须显式配置插件；而单元测试直接 import 源码时，没有经过插件处理，用文档断言（比如测试里读 `SwaggerModule.createDocument`）就会拿不到自动生成的 `@ApiProperty`。**结论：把「文档快照」交给构建后的产物去生成，不要在每个测试里重新生成。**

> 另一条路是 **Standard Schema**：Nest 12 的 `SwaggerDocumentOptions.standardSchemaConverter` 可以把路由参数上的 Zod/Valibot schema 转成 OpenAPI schema，配合 09 章写的 `StandardSchemaValidationPipe`，能省掉 DTO 类。但它对「类 + class-validator」的项目是增量选项，不是替代——本书示例项目两者都用，你选一种坚持即可。

## 六、OpenAPI 3.1：值得开，但要先对齐工具链

`@nestjs/swagger` 默认吐 3.0.0，Nest 12 支持 3.1：

```ts
const config = new DocumentBuilder()
  .setOpenAPIVersion('3.1.0')
  // ...
  .build();
```

3.1 带来的实际差别（不是营销词）：

- **Webhook 能表达了**：3.0 的 `paths` 无法同时描述「路由」与「回调」，3.1 有 `webhooks`，支付回调这类接口终于能写进契约（scanner 会对 3.0 下的 webhook 冲突给 warning）；
- **`nullable` 语义变了**：3.0 用 `nullable: true`，3.1 用 `type: ['string', 'null']`，生成的客户端要理解这一点，否则可选字段会被当成必填；
- **schema 支持 `$ref` 兄弟属性、`if/then` 等更完整语义**。

代价是**下游工具链**：Apifox/YApi/Scalar/`openapi-typescript` 对 3.1 的支持程度不一，公司里如果还有人用老版本 Postman 导入，会静默丢掉一部分字段。结论：新项目 + 自己控制 codegen，直接 3.1；需要对接一堆外部工具时，先留在 3.0.0。

## 七、文档里最容易错的两件事：包装结构与分页

示例项目的响应都包了一层 `{ data }`（全局 ResponseInterceptor），但 `@ApiCreatedResponse({ type: BookingResponseDto })` 只会生成 BookingResponseDto 本身——**文档说返回 `{id, roomId...}`，实际返回 `{data: {...}}`**，前端按文档写必错。正确做法是用 `getSchemaPath` 组合：

```ts
// common/swagger/api-wrapped-response.decorator.ts
import { applyDecorators, Type } from '@nestjs/common';
import { ApiExtraModels, ApiOkResponse, getSchemaPath } from '@nestjs/swagger';

export const ApiWrappedResponse = <T extends Type<unknown>>(model: T) =>
  applyDecorators(
    ApiExtraModels(model),
    ApiOkResponse({
      schema: {
        type: 'object',
        required: ['data'],
        properties: { data: { $ref: getSchemaPath(model) } },
      },
    }),
  );
```

分页同理：`{ data: Room[], meta: { page, pageSize, total } }` 要写成 `allOf` + 泛型包装，或者干脆单独定义一个 `PaginatedRoomsDto` 并在 `extraModels` 里注册，让 UI 展开能看到结构。**「文档里的响应结构和真实响应不一致」是联调事故的第一大来源**，写完务必打开 Swagger UI 点一次 Try it out 对照。

## 八、安全与暴露边界

- **认证按钮**：`addBearerAuth()` + 控制器/方法上的 `@ApiBearerAuth()`，两者名字要一致；公开接口（登录、注册）不要加，否则 UI 会要求填 token；
- **别把内部接口写进文档**：`@ApiExcludeEndpoint()` 可以把某个路由排掉，`SwaggerDocumentOptions.include` 可以只包含指定模块；更彻底的是**按环境挂载**：

```ts
if (config.get('environment') !== 'production' || config.get('exposeDocs')) {
  SwaggerModule.setup('api/docs', app, documentFactory);
}
```

- **helmet 的 CSP**：Nest 内置的 Swagger UI 能通过默认 CSP；一旦你用 `customJs`/`customCss` 注入脚本，或者用 Fastify 自己注册 helmet，UI 会白屏——要么加 `scriptSrc`/`styleSrc` 白名单，要么只在开发环境开启。别为了「线上也能看文档」把 CSP 整个关掉；
- **废弃接口要显式标注**：改接口时不要直接删路由，先 `@ApiOperation({ deprecated: true })` + `@ApiResponse({ status: 410, description: '将于 2026-12-01 下线' })`，给前端留迁移窗口。OpenAPI 的 `deprecated` 会让 Swagger UI 和 codegen 客户端都打上删除线，比群发通知有效得多；
- **文档本身是信息泄露**：接口路径、字段名、枚举值都是攻击面。生产环境如果需要外部可见，把它放在内网/加 HTTP Basic，而不是公开 `/api/docs`。

## 九、文档的三个消费方，需求完全不同

同一份 OpenAPI，三类人关注的东西完全不一样，文档设计要同时照顾：

**1. 前端**：他要的是「类型 + 请求函数」，不是网页。所以 `operationId`、`example`、响应包装结构比排版重要；`/api/docs-json` 直接喂给 `openapi-typescript`/`orval` 就能生成 `types.d.ts` 和 TanStack Query hooks（11.02 展开）。

**2. 联调/测试**：他要的是「能点」。`example` 决定 Try it out 的预填值，`@ApiBadRequestResponse` 这类错误响应决定他敢不敢传脏数据；「成功 200 但文档没写 409 冲突」会让他以为冲突不存在。

**3. 外部合作方/甲方**：他要的是「稳定」。字段 `description` 要写人话，枚举要列出全部值，`deprecated: true` 要标出来——这些在内部项目里可以糊弄，对外就是合同。所以 `@ApiProperty({ enum: BookingStatus, enumName: 'BookingStatus' })` 里的 `enumName` 别省，否则生成的客户端里会出现 `BookingStatus1` 这种名字。

一个实用建议：**文档页面只对开发/测试环境开放，`docs-json` 按需开放**。UI 是给人看的，JSON 是给机器用的，后者的暴露面更大（能被爬、能被扫描器发现），别一起公开。

## 十、让文档变成契约：进 CI

自动生成的文档如果没有校验，等于没生成。三件低成本的事：

1. **提交 `openapi.json` 快照**：`GET /api/docs-json` 输出到 `docs/openapi.json`，进 git；PR 里能直接看到 diff；
2. **CI 里比较 breaking change**：用 `oasdiff breaking old.json new.json`（或 `openapi-diff`）判定「删字段/改类型/加必填参数」为失败，其他变更只提示；
3. **文档与实现同源**：CI 起一个无数据库的 app 实例（`NestFactory.create` 后不连库、不监听端口）生成文档，避免「文档来自某个旧分支」。

```yaml
# .github/workflows/openapi.yml 摘要
- run: pnpm build
- run: node dist/main.js & sleep 3 && curl -s localhost:3000/api/docs-json -o new.json
- run: npx oasdiff breaking docs/openapi.json new.json
```

这套跑起来之后，「文档腐烂」就从「靠自觉」变成「过不了 CI」。

## 十一、Checkpoint

```bash
# 1) 文档页能打开且返回 200
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/api/docs

# 2) JSON 里有你的路径、且带 api 前缀
curl -s http://localhost:3000/api/docs-json | jq -r '.paths | keys[]' | head -5
# 期望：/api/auth/login 等

# 3) 组件与安全方案都在
curl -s http://localhost:3000/api/docs-json | jq '.components.securitySchemes'
# 期望：{ "access-token": { "type": "http", "scheme": "bearer" ... } }

# 4) 改一个 DTO 字段（加字段），不重启、刷新 JSON，确认新字段出现
#    （工厂函数模式下文档在首次请求时生成并缓存，改代码后仍需要重启进程；
#     这一点要讲清楚：它省的是启动时间，不是热更新）
```

## 十二、坑表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| UI 上 Authorize 填了 token 仍 401 | `addBearerAuth` 的名字与 `@ApiBearerAuth` 不一致 | 两边都用 `'access-token'` |
| 文档里路径缺 `/api` 前缀 | `createDocument` 早于 `enableVersioning`，或漏了全局前缀处理 | 用工厂函数，或调整调用顺序 |
| 文档响应结构少了 `{data}` 包裹 | 装饰器直接标了 DTO | `getSchemaPath` + 包装装饰器 |
| 新加的 DTO 字段没出现 | 文件名后缀不在 `*.dto.ts` | 加 `dtoFileNameSuffix` |
| 用 `PartialType` 后文档空 | 从 `@nestjs/mapped-types` 导入 | 改从 `@nestjs/swagger` 导入 |
| 线上 Swagger 白屏 | helmet/Fastify 的 CSP 拦了内联脚本 | 放宽 CSP 白名单，或只在开发环境开 |
| 生成的文档字段特别多/很乱 | 未用 `include` 限制模块，内部接口也进来了 | `include` + `@ApiExcludeEndpoint` |
| 前端 codegen 类名难看 | 默认 `operationId` 是拼接式 | 显式写 `operationId` |
| 枚举在客户端里变成 `Status1` | 多个同名枚举未指定 `enumName` | `@ApiProperty({ enum, enumName: 'XxxStatus' })` |
| 测试里生成的文档缺字段 | Vitest 直接跑 TS，没经过 CLI 插件 | 用构建产物生成文档快照 |

文档能生成了，但它长什么样、给谁用、怎么和前端契约对齐，是另一层问题——11.02 换成 Scalar/Redoc 这类更现代的 UI，并接上 `openapi-typescript`/`orval` 的 codegen，让「文档」直接变成前端的类型与请求函数。
