# 11.09 短链服务自己写一个

短链服务看起来是个「字符串换一下」的小功能：存一个映射，访问时查出来 302 过去。真写起来，问题集中在四个地方——**编码怎么生成**（会不会撞、能不能猜）、**跳转用哪个状态码**（决定能不能统计、能不能改）、**查询怎么扛住读多写少**、**开放跳转带来的安全风险**。

这一节从表设计写到上线检查，全部用 Prisma 8 + Redis 实现。

## 一、短链的四个真实需求

先说清楚短链到底要满足什么，否则很容易写出「能跳但没法运营」的版本：

1. **短**：越短越好，但不是越短越安全——6 位 base62 有 568 亿种，够用；4 位只有 1477 万种，很快会见底；
2. **不撞**：同一个短码只能指向一个目标地址，撞了就是串号事故；
3. **可统计**：点击次数、来源、地区，这些是短链产品的主要价值；
4. **可撤销**：目标地址变了、活动结束了，链接要能失效——**这条直接决定状态码的选择**。

## 二、编码方案：三种做法，各有代价

```mermaid
flowchart LR
    A[创建请求] --> B{编码策略}
    B -->|自增 ID + base62| C[code = base62(id)]
    B -->|随机 7 位| D[随机生成, 唯一索引兜底]
    B -->|哈希取前 N 位| E[sha256(url) 截断]
    C --> F[可预测, 需混淆]
    D --> G[不可猜, 需重试]
    E --> H[必然碰撞, 需冲突处理]
```

- **自增 ID + base62**：把数据库自增 id 转成 62 进制，天然不碰撞、长度可控。缺点是**可预测**——别人拿到 1、2、3 就能顺推出全部短码。缓解办法是给 id 加一个固定偏移再编码（比如 `id * 1000003 + 20261122`），或者用 Feistel 网络做可逆混淆；
- **随机 7 位**：`randomBytes` 取 7 位 base62，不可猜，但必须靠唯一索引兜底重试。7 位空间 = 3.5 万亿，撞的概率极低，重试一次就够；
- **哈希截断**：`sha256(target_url)` 取前 N 位，同一个 URL 得到同一个短码（这点很实用），但不同 URL 会碰撞，必须处理冲突。

这一节用**自增 + base62 + 偏移混淆**：不碰撞、长度短、实现简单，也顺便讲清楚「可预测」这个隐患怎么处理。

```ts
// src/links/base62.ts
const ALPHABET = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';

export function toBase62(value: bigint): string {
  if (value === 0n) return ALPHABET[0];
  let n = value;
  let out = '';
  while (n > 0n) {
    out = ALPHABET[Number(n % 62n)] + out;
    n /= 62n;
  }
  return out;
}

/** 偏移 + 打散：让相邻 id 的短码看起来毫无规律 */
const OFFSET = 1_000_003n;
const SALT = 20_261_122n;

export function encodeId(id: bigint): string {
  return toBase62(id * OFFSET + SALT);
}
```

注意 `BigInt`：JS 的 `number` 在大整数上会丢精度，自增 id 迟早会超出安全范围，从第一行代码就用 `bigint`。

## 三、表设计：短码唯一，目标地址可以有多个

```prisma
// prisma/contract.prisma（片段）
model Link {
  id        BigInt    @id @default(autoincrement())
  code      String    @unique @db.VarChar(12)
  targetUrl String    @map("target_url") @db.VarChar(2048)
  expiresAt DateTime? @map("expires_at")
  disabled  Boolean   @default(false)
  createdAt DateTime  @default(now()) @map("created_at")

  @@index([createdAt])
  @@map("links")
}

model LinkClick {
  id        BigInt   @id @default(autoincrement())
  linkId    BigInt   @map("link_id")
  clickedAt DateTime @default(now()) @map("clicked_at")
  referer   String?
  userAgent String?  @map("user_agent")
  ipHash    String?  @map("ip_hash")

  @@index([linkId, clickedAt])
  @@map("link_clicks")
}
```

几个决定：`code` 加唯一索引（冲突的最终裁判）、`target_url` 用 `VarChar(2048)`（浏览器实际限制）、`expires_at` 用可空时间（不填表示永久）、点击日志单独一张表（跳转路径只写入队列，不直接写这张表）。

## 四、创建：先写入，再拿 id 编码

自增 ID 方案有一个顺序问题：id 要等 INSERT 之后才有，但 `code` 是必填的唯一列。两个解法：

- 先插入一个临时 code（比如 UUID），拿到 id 后再算真实 code 并 update；
- 用一次事务：`INSERT ... RETURNING id`，然后在同一事务里更新 code。

```ts
// src/links/links.service.ts
@Injectable()
export class LinksService {
  constructor(private readonly db: Database) {}

  async create(targetUrl: string, expiresAt: Date | null): Promise<string> {
    return this.db.transaction(async (tx) => {
      const created = await tx.orm.public.Link.create({
        data: { code: crypto.randomUUID(), targetUrl, expiresAt },
        select: ['id'],
      });
      const code = encodeId(created.id);
      await tx.orm.public.Link.updateAll({
        where: { id: created.id },
        data: { code },
      });
      return code;
    });
  }
}
```

如果重试方案用「随机 code + 唯一索引」，那就是另一种写法：循环生成、`INSERT` 撞唯一索引就重试，最多 3 次。两种都行，**关键是让数据库的唯一索引当最终裁判**，不要先查「这个 code 存在吗」再插入——并发下这个检查一定会失效。

## 五、跳转：为什么是 302，不是 301

这是短链最容易被忽略的决定。

- **301 永久重定向**：浏览器、CDN、企业代理都会缓存。缓存之后，用户再点就不再经过你的服务器——点击统计丢失、目标地址改了也改不掉；
- **302 临时重定向**：每次都会回源（除非你自己设了缓存头），你能统计、能改目标、能随时下线。

短链产品几乎都用 302（或 307）。代价是每次都要查一次映射——用 Redis 缓存扛住。

```ts
@Controller()
export class RedirectController {
  constructor(private readonly links: LinksService) {}

  @Get(':code')
  @Redirect()
  async redirect(@Param('code') code: string): Promise<{ url: string; statusCode: number }> {
    const target = await this.links.resolve(code);
    return { url: target, statusCode: 302 };
  }
}
```

Nest 的 `@Redirect()` 装饰器要求返回 `{ url, statusCode }`，比手动 `res.redirect()` 更好测——它不影响返回值结构，测试里可以直接断言。

如果确实想减少回源，可以给 302 加 `Cache-Control: max-age=60`：一分钟内的重复点击不落库，但统计误差可接受、地址变更一分钟生效。别设更长。

还有一个细节：响应头里加 `Referrer-Policy: no-referrer`，避免把短链页面上的来源信息带到目标站点。如果需要把来源传过去（有些活动页需要），就显式拼在目标 URL 的 query 里，而不是依赖浏览器默认行为。

自定义域名与路径前缀也要在这一层想清楚：短码挂在根路径（`/abc123`）最简单，但会和所有其它路由抢空间；挂在 `/r/abc123` 下就永远不会冲突。后者更稳，代价是长两个字符——选后者的人更多。

## 六、解析：Redis 缓存 + 缓存穿透保护

读多写少，缓存是刚需。键用 `link:code:{code}`，值是目标地址或一个 JSON（含过期时间、是否禁用）。

```ts
async resolve(code: string): Promise<string> {
  const cacheKey = `link:code:${code}`;
  const cached = await this.redis.get(cacheKey);
  if (cached === NEGATIVE) {
    throw new NotFoundException('短链不存在');
  }
  if (cached) return cached;

  const row = await this.db.orm.public.Link.where({ code }).select(['targetUrl', 'expiresAt', 'disabled']).first();

  if (!row || row.disabled || (row.expiresAt && row.expiresAt < new Date())) {
    // 不存在的短码也缓存一个短 TTL 的空值，挡住扫描器
    await this.redis.set(cacheKey, NEGATIVE, 'EX', 60);
    throw new NotFoundException('短链不存在');
  }

  const ttl = row.expiresAt
    ? Math.max(1, Math.floor((row.expiresAt.getTime() - Date.now()) / 1000))
    : 86_400;
  await this.redis.set(cacheKey, row.targetUrl, 'EX', Math.min(ttl, 86_400));
  return row.targetUrl;
}
```

三个细节：

- **空值也要缓存**（60 秒），否则被扫描器刷不存在的短码时，每个请求都会打到数据库；
- **TTL 不能超过链接自身的过期时间**，否则链接过期了缓存还在跳；
- **禁用/删链之后要主动删缓存**（`DEL link:code:{code}`），别等 TTL。

## 七、安全：短链天生是一个开放跳转

`https://your.domain/abc123` 跳到任意地址，意味着攻击者可以用你的域名做钓鱼——用户看到的是你的域名，落地页却是别人的。防护四件事，按必要性排序：

1. **只允许 `http`/`https`**：拒绝 `javascript:`、`data:`、`file:` 等协议，否则就是 XSS 入口；
2. **拒绝内网地址**：解析目标域名，禁止 `127.0.0.1`、`10.0.0.0/8`、`169.254.169.254`（云元数据地址）等，否则你的服务变成 SSRF 跳板；
3. **可疑链接人工审核**：开放注册的短链服务必须要有，否则很快会被用来发垃圾信息，域名也会进黑名单；
4. **管理接口鉴权**：创建、删除、看统计都要登录态，别做成匿名可用。

```ts
function assertAllowedTarget(raw: string): URL {
  let url: URL;
  try {
    url = new URL(raw);
  } catch {
    throw new BadRequestException('目标地址不是合法 URL');
  }
  if (url.protocol !== 'http:' && url.protocol !== 'https:') {
    throw new BadRequestException('只支持 http/https');
  }
  if (/^(localhost|127\.|10\.|192\.168\.|169\.254\.|172\.(1[6-9]|2\d|3[01])\.)/.test(url.hostname)) {
    throw new BadRequestException('目标地址不允许指向内网');
  }
  return url;
}
```

这段校验在**创建时**做一次，在**跳转时**不要做（每次跳转都解析 DNS 太贵）；上线新链接前跑一遍存量数据的巡检，把历史脏数据清出来。

## 八、点击统计：别在跳转路径上写库

每次点击写一条 `link_clicks`，热门链接会把跳转接口的 P99 拖到几百毫秒。正确做法是**跳转只负责返回**，统计异步化：

- 进程内：`setImmediate` / 一个小的内存队列批量 flush（够用，但进程重启丢最后一批）；
- 生产做法：写 Redis 的 Hash 计数（`click:{code}:{yyyymmdd}` 用 `HINCRBY` + TTL），再由定时任务批量落库——就是 11.07 的刷盘模式；
- 更完整的链路：点击事件推进消息队列（BullMQ），消费者写明细表并更新聚合表。

短链的统计精度要求通常不高，「分钟级延迟、允许丢极少量」完全可以接受，所以 Redis 计数 + 定时刷盘是性价比最高的方案。

## 九、过期与清理

过期链接有两种处理：

- **懒删除**：`resolve` 时判断 `expires_at`，过期就当不存在；简单，但数据会一直留着；
- **定时清理**：每天凌晨跑一个 `@Cron` 任务，把过期超过 7 天的链接及其点击明细归档/删除。

清理要注意两点：**分批删**（一次 1000 条，避免长事务和锁表）、**先归档再删**（点击明细可能还要用于对账）。删除后别忘了 `DEL` 对应缓存。

## 十、自定义短码与保留字

运营经常要「这个链接用 `spring2026`」。自定义短码的实现比想象中多两个细节：

```ts
const CUSTOM_CODE = /^[a-z0-9][a-z0-9-]{3,15}$/;
const RESERVED = new Set(['api', 'admin', 'static', 'assets', 'docs', 'health', 'login', 'logout', 'links']);

function assertCustomCode(code: string): void {
  if (!CUSTOM_CODE.test(code)) {
    throw new BadRequestException('短码只能用小写字母、数字和连字符，4–16 位');
  }
  if (RESERVED.has(code)) {
    throw new ConflictException('该短码为系统保留字');
  }
}
```

第一，**必须拦掉路由保留字**。你的跳转路由是 `/:code`，用户真建了一个 `api` 或 `docs` 的短码，就会和真实路由抢匹配——这种 bug 上线后很难查，因为它取决于路由注册顺序。

第二，**字符集要收窄**。只用小写字母、数字、连字符，可以避免大小写不敏感的路由/代理把 `AbC` 和 `abc` 当成同一个；也避免 `%2F`、`?`、`#` 这类字符在 URL 解析里搞事。

第三，**自定义短码和自动短码共用一个唯一索引**。别用两张表或两个命名空间——`spring2026` 被自动生成器撞上的概率虽然低，但一旦撞上就是两套逻辑打架。唯一索引发 `23505` 时，自定义短码返回「已被占用」，自动短码重试。

判断方式很简单：看请求里有没有 `customCode` 字段，有就返回 409，没有就重试。

## 十一、容量与性能：先算再优化

短链是典型的「写少读多」，容量估算能帮你决定要不要提前分片：

- 每天新增 10 万条短链，一年 3650 万行，`links` 表在 `code` 唯一索引下完全撑得住；
- 每天 1 亿次跳转，峰值按 5 倍算约 5800 QPS。单实例 Node + Redis 缓存命中率 95% 以上，这个量级很轻松；真正的瓶颈在缓存未命中的那 5%（约 290 QPS 打数据库），用本地缓存（进程内 LRU，TTL 5 秒）再挡一层；
- 点击明细每天 1 亿行就需要分区或归档了，按 `clicked_at` 月分区是最省事的做法。

如果读 QPS 再上一个量级，加 CDN：把 302 换成 302 + 短 TTL 缓存，或者干脆用「边缘计算」在 CDN 层查映射。但注意，一旦缓存到 CDN，统计就变成了采样——产品能接受再这么做。

压测的起点永远是「缓存命中率」和「数据库 QPS」两个数。命中率 99% 和 95%，数据库压力差 5 倍。

## 十二、Checkpoint

```bash
# 1) 创建一条短链
curl -s -X POST localhost:3000/api/links \
  -H 'content-type: application/json' \
  -d '{"targetUrl":"https://docs.nestjs.com","expiresAt":null}' | jq

# 2) 访问短码，应该 302 且 Location 正确（-I 只看头）
curl -sI localhost:3000/$CODE | grep -E "HTTP/|location"

# 3) 第二次访问应该命中缓存（观察 Redis 里是否有 link:code:xxx）
redis-cli GET "link:code:$CODE"; redis-cli TTL "link:code:$CODE"

# 4) 不存在的短码应该 404，且 Redis 里有 60 秒的空值缓存
curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/does-not-exist

# 5) 内网地址应被拒绝
curl -s -X POST localhost:3000/api/links -H 'content-type: application/json' \
  -d '{"targetUrl":"http://169.254.169.254/latest/meta-data/"}'
```

## 十三、坑表

| 写法 | 后果 |
| --- | --- |
| 用 301 做跳转 | 浏览器永久缓存，改地址失效、统计丢失 |
| 用 `number` 存自增 id | 超过 2^53 精度丢失，短码开始串号 |
| 先查 code 存在再插入 | 并发下两个请求同时通过检查，撞唯一索引报错 |
| 不缓存「不存在」的结果 | 扫描器把数据库打满 |
| 缓存 TTL 长于链接过期时间 | 链接过期了还能跳 |
| 允许 `javascript:` 等协议 | 变成 XSS 入口 |
| 不拦内网地址 | 变成 SSRF 跳板，能读云元数据 |
| 跳转路径同步写点击明细 | 热门链接把接口 P99 拖到几百毫秒 |
| 删链后不删缓存 | 删了还在跳，直到 TTL 到期 |
| 清理任务一次删全表 | 长事务锁表，业务查询跟着超时 |
