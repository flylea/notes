# 11.08 Nest的3种定时任务

Nest 的定时任务包 `@nestjs/schedule` 提供三个装饰器：`@Cron`、`@Interval`、`@Timeout`。名字看起来只是「写法不同」，实际上对应三种不同的时间模型——选错模型，后面补多少锁都不顺。

这一节把三个装饰器放在一起讲：各自的语义、参数里真正重要的那几个、以及它们共有的三个坑。写完你会知道什么任务该用哪种，以及为什么「定时任务」在多副本部署下默认是错的。

## 一、三种调度器是三种时间模型

```mermaid
timeline
    title 三种装饰器的时间语义
    10:00 : 应用启动
    10:00 : @Timeout(5000) 只在 10:00:05 触发一次
    10:00 : @Interval(60000) 在 10:01、10:02、10:03… 触发（从启动时刻起算）
    10:01 : @Cron("0 * * * *") 在整点 11:00 触发（与启动时刻无关）
```

区别一句话说清：

- `@Cron`：**日历时间**驱动。指定「每天 3 点」「每 5 分钟」，与进程什么时候启动无关；
- `@Interval`：**间隔**驱动。从应用启动开始，每隔 N 毫秒跑一次，间隔之间可能有漂移；
- `@Timeout`：**一次性延迟**。启动后等 N 毫秒跑一次，之后再也不跑。

选型规则很直接：需要和钟点对齐（对账、日报、清理）用 `@Cron`；只是「定期做点事」（刷新缓存、拉状态）用 `@Interval`；预热、延迟补偿用 `@Timeout`。

## 二、@Cron：表达式、枚举与时区

```ts
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression } from '@nestjs/schedule';

@Injectable()
export class ReportsService {
  private readonly logger = new Logger(ReportsService.name);

  // 每天凌晨 3 点
  @Cron(CronExpression.EVERY_DAY_AT_3AM, { timeZone: 'Asia/Shanghai', name: 'daily-report' })
  async dailyReport(): Promise<void> {
    this.logger.log('generating daily report');
    // ...
  }

  // 工作日每 5 分钟
  @Cron('0 */5 * * * *', { name: 'sync-orders' })
  async syncOrders(): Promise<void> {
    // ...
  }
}
```

`@nestjs/schedule` 12.0.4 依赖 `cron` 4.4.0，`CronExpression` 枚举覆盖了常见组合：`EVERY_MINUTE`（`*/1 * * * *`）、`EVERY_5_MINUTES`（`0 */5 * * * *`）、`EVERY_DAY_AT_3AM`（`0 03 * * *`）、`MONDAY_TO_FRIDAY_AT_2AM`（`0 0 02 * * 1-5`）等。注意它的星期字段是 0–6（0 是周日），而 `cron` 库解析六段表达式时最前面多一个秒字段——`CronExpression` 里的值已经带秒了，别再自己加。

**时区是最容易踩的一脚。** 容器里默认 `TZ=UTC`，你在代码里写的「凌晨 3 点」指的是 UTC 3 点，也就是北京时间 11 点。两个办法：给容器设 `TZ=Asia/Shanghai`，或者给每个任务显式写 `timeZone: 'Asia/Shanghai'`。后者更稳——同一份镜像部署到不同时区也不会错。

`timeZone` 和 `utcOffset` 不要同时给，官方文档明确说会出怪事；`utcOffset` 只适合「固定偏移、不含夏令时」的场景。

其余参数里，这三个值得记住：

| 参数 | 作用 |
| --- | --- |
| `waitForCompletion: true` | 上一轮没跑完时，跳过这一轮的触发，而不是叠加执行 |
| `threshold`（默认 250ms） | 机器忙导致触发延迟超过阈值时，这一次直接丢弃并告警 |
| `initialDelay` | 应用启动后先等多久才开始调度，适合依赖还没就绪的任务 |

`name` 不是装饰品：有了名字，才能通过 `@InjectCronRef(name)` 拿到任务引用，或者用 `SchedulerRegistry` 动态停掉它。

## 三、@Interval：从启动时刻起算的固定间隔

```ts
import { Interval } from '@nestjs/schedule';

@Injectable()
export class CacheWarmupService {
  // 每 30 秒刷新一次热点缓存
  @Interval('cache-warmup', 30_000)
  async warmup(): Promise<void> {
    // ...
  }
}
```

`@Interval` 有重载：`@Interval(30_000)` 或 `@Interval('cache-warmup', 30_000)`。底层就是 `setInterval`，所以有两个特点：

- **起算点是启动时刻**。10:00:07 启动、间隔 60 秒，触发点就是 10:01:07、10:02:07……不是整分钟；
- **上一轮没跑完，下一轮照样触发**。`@Interval` 没有 `waitForCompletion` 选项，长任务会堆叠。要么任务本身很短，要么自己加一个「正在执行」的标志：

```ts
private running = false;

@Interval('sync-third-party', 10_000)
async sync(): Promise<void> {
  if (this.running) return; // 上一轮还没完，直接跳过
  this.running = true;
  try {
    await this.doWork();
  } finally {
    this.running = false;
  }
}
```

这个布尔标志只在单进程内有效。多副本时每个进程都可以跑，需要锁——第 11.07 节讲的分布式锁就是这个位置用的。

## 四、@Timeout：只跑一次的延迟任务

```ts
import { Timeout } from '@nestjs/schedule';

@Injectable()
export class BootstrapService implements OnApplicationBootstrap {
  @Timeout('warmup', 5_000)
  async warmup(): Promise<void> {
    // 启动 5 秒后执行一次，用来预热连接池/字典表
  }
}
```

适合的只有两类事：**预热**（延迟几秒等依赖就绪）和**一次性补偿**（比如启动时补发一条没发出去的邮件）。

不要用它做「重试」：`@Timeout` 不会因为失败而重排。要重试就在任务里写 `while` + 退避，或者干脆用队列（BullMQ 的延迟任务才是干这个的）。

## 五、三个装饰器共有的三个坑

**坑一：调度器是进程内的。** 三个装饰器都只是把任务注册到当前进程的定时器里。起 4 个副本，任务就执行 4 次。对幂等任务（刷缓存）无所谓，对「给用户发提醒」「生成账单」就是事故。

**坑二：重启即丢失。** 任务是内存状态，进程重启时没跑完的那次就没了；错过的触发也不会补。要求「至少跑一次」的业务，必须把「要做什么」先落库/入队，定时任务只负责「扫描并触发」。

**坑三：异常不会自动重试。** 装饰器方法抛出的异常会被 `@nestjs/schedule` 捕获并记录日志，但不会重新排队。要么任务内部自己 `try/catch` 并决定是否下一轮补偿，要么用队列的重试机制。

这三条合起来指向同一个结论：**`@nestjs/schedule` 适合做「低价值、可重复、丢了不心疼」的周期动作**（清缓存、刷计数、探活）。真正不能丢的调度，用 BullMQ 的重复任务或数据库里的任务表 + 轮询。

## 六、把任务变成可管理的对象：SchedulerRegistry

有时候需要在运行时控制任务：运营后台点「暂停同步」、配置变更后改间隔、优雅关闭前先停掉任务。

```ts
import { Injectable, Logger } from '@nestjs/common';
import { SchedulerRegistry } from '@nestjs/schedule';
import { CronJob } from 'cron';

@Injectable()
export class JobsAdminService {
  private readonly logger = new Logger(JobsAdminService.name);

  constructor(private readonly registry: SchedulerRegistry) {}

  pause(name: string): void {
    const job = this.registry.getCronJob(name);
    job.stop();
    this.logger.warn({ name }, 'cron job paused');
  }

  resume(name: string): void {
    this.registry.getCronJob(name).start();
  }

  /** 运行时新建一个 cron 任务 */
  addDynamic(name: string, cronTime: string, fn: () => Promise<void>): void {
    const job = CronJob.from({
      cronTime,
      onTick: fn,
      start: true,
      timeZone: 'Asia/Shanghai',
      waitForCompletion: true,
    });
    this.registry.addCronJob(name, job);
  }

  list(): string[] {
    return [...this.registry.getCronJobs().keys()];
  }
}
```

配合 `@InjectCronRef('daily-report') job: CronJob` 可以直接在业务代码里拿到某个命名任务的引用，不必经过 registry 查找。

`CronJob.from({...})` 是 `cron` 4.x 的构造方式；`addCronJob(name, job)` 之后，任务的启停、下一次触发时间（`job.nextDate()`）都能查。注意动态任务同样只存在于当前进程——它不会写进任何配置文件，重启就没了。

## 七、动态任务：从配置或数据库读调度

真正需要「运营能改调度」时，别把 cron 表达式写死在装饰器里，改成启动时读配置/数据库再注册：

```ts
@Injectable()
export class DynamicJobsBootstrap implements OnApplicationBootstrap {
  constructor(
    private readonly registry: SchedulerRegistry,
    private readonly config: ConfigService,
  ) {}

  onApplicationBootstrap(): void {
    for (const item of this.config.get<JobSpec[]>('jobs') ?? []) {
      if (!item.enabled) continue;
      this.registry.addCronJob(
        item.name,
        CronJob.from({
          cronTime: item.cron,
          onTick: () => this.run(item.name),
          start: true,
          timeZone: 'Asia/Shanghai',
        }),
      );
    }
  }

  private async run(name: string): Promise<void> {
    // 按 name 分发到具体 handler
  }
}
```

要点：**注册前校验表达式**（`CronTime` 解析失败会抛错，直接让应用起不来）、**同一个 name 注册两次会覆盖**、**改完配置要重启或显式重注册**。这套做法适合「调度项不多、变更不频繁」的场景；如果调度项本身是业务数据（用户创建的提醒），应该存在数据库里，由扫描任务处理。

## 八、错误处理：没人接住的异常

`@nestjs/schedule` 会把装饰器方法包一层 try/catch，异常不会让进程崩，但也没有重试。所以每个任务自己要有明确的失败语义：

```ts
@Cron(CronExpression.EVERY_MINUTE, { name: 'views-flush', waitForCompletion: true })
async flush(): Promise<void> {
  try {
    await this.views.flush();
  } catch (error) {
    // 记上下文，别只记 message；下一轮会自然重试
    this.logger.error({ err: error }, 'views flush failed');
    this.metrics.increment('cron.views_flush.failed');
  }
}
```

两个细节：任务里的日志要带 `name` 或任务标识，否则几十个任务混在一起排障很痛苦；失败指标要比失败日志更早接告警——日志是给人看的，指标是给机器看的。

还有一类更隐蔽的失败：**任务「成功」了，但什么都没做**。比如查数据库返回 0 行、第三方接口返回空数组。加一个「处理条数」日志或指标，`processed: 0` 连续出现本身就是信号。

## 九、关机时任务在干什么

`SchedulerOrchestrator` 实现了 `OnApplicationBootstrap` 和 `BeforeApplicationShutdown`：启动时挂载任务，关机时停掉并等待收尾。带 `waitForCompletion: true` 的任务，关机时会等当前这一轮跑完。

这就带来一个判断题：如果任务要跑 5 分钟，而容器的 `stop_grace_period` 只有 10 秒，等待会超时、进程被 `SIGKILL`——任务被腰斩，可能留下半截状态。

两个处理方式：

- 长任务拆成可重入的小批次（每次处理 100 条，记游标），超时被杀也无所谓，下次从游标继续；
- 长任务别放在 API 进程里，交给独立 worker/队列，关机时 worker 先停止取新任务、跑完当前任务再退出。

`@nestjs/schedule` 的任务默认跟着 API 进程生老病死，这一点在写任务的第一天就要想清楚。

## 十、多副本：调度器是进程内的

再强调一遍，因为这是定时任务上线后最常见的事故：**四个副本 = 任务执行四次**。

处理顺序建议这样：

1. 先让任务**幂等**（重复执行结果相同）——这是最便宜的保险；
2. 再加**分布式锁**（Redis `SET NX EX`，TTL 略小于任务间隔），保证同一时刻只有一个执行者；
3. 规模再大就**拆独立 worker**，API 进程只处理请求，调度进程只跑任务，互不影响。

锁本身也有坑：锁过期时间比任务执行时间短，会导致两个实例同时跑；所以要么让 TTL 明显大于最长执行时间，要么在任务里续期（看门狗）。这些在 11.07 里有完整代码，这里不重复。

## 十一、启用开关与选型清单

还有两个容易漏的配置项。

第一，**`ScheduleModule.forRoot()` 必须注册**。三个装饰器只负责把方法标记出来，真正的挂载发生在 `ScheduleModule` 初始化时。忘了 import 这个模块，任务一个都不会跑，而且没有任何报错——代码看起来完全正常。

第二，`forRoot()` 可以按类型关掉：

```ts
ScheduleModule.forRoot({
  cronJobs: true,
  intervals: false, // 本项目不用 @Interval，误加的装饰器不会生效
  timeouts: true,
});
```

这适合「约定只允许用某一种调度方式」的团队，误用会直接不跑，比跑到线上才发现好。

选型清单收个尾：

| 需求 | 用什么 |
| --- | --- |
| 每天凌晨对账、生成报表 | `@Cron` + `timeZone` |
| 每分钟刷一次计数/缓存 | `@Cron` + `waitForCompletion` |
| 启动后预热、延迟补偿 | `@Timeout` |
| 定期拉第三方状态（短任务） | `@Interval` |
| 运营可停/可改的任务 | 动态注册 + `SchedulerRegistry` |
| 不能丢、要重试、要延迟 | BullMQ 重复任务 / 任务表轮询，不用装饰器 |
| 多副本只允许一个执行 | 装饰器 + 分布式锁，或独立 worker |

## 附：三个装饰器的签名与默认值速查

```ts
// 时间参数
function Cron(cronTime: string | Date, options?: CronOptions): MethodDecorator;
function Interval(timeout: number): MethodDecorator;
function Interval(name: string, timeout: number): MethodDecorator;
function Timeout(timeout: number): MethodDecorator;
function Timeout(name: string, timeout: number): MethodDecorator;
```

`CronOptions` 的默认值：`disabled: false`、`threshold: 250`、`waitForCompletion: false`、`unrefTimeout: false`。`unrefTimeout` 打开后，定时器不阻止进程退出——容器里不需要，本地脚本里有用。

## 十二、Checkpoint

```bash
# 1) 应用启动后 5 秒，@Timeout 应该只打一条日志
# 2) @Interval 每 30 秒打一条，观察时间戳（应是从启动时刻起算的 30 秒倍数）
docker compose logs -f api | grep -E "warmup|cache-warmup"

# 3) 动态任务：调管理接口暂停，再观察日志是否停止
curl -X POST localhost:3000/api/admin/jobs/daily-report/pause

# 4) 重启应用，动态任务应该消失（只在启动配置里存在的才会回来）
docker compose restart api
```

## 十三、坑表

| 写法 | 后果 |
| --- | --- |
| 多副本直接用 `@Cron` 发提醒/生成账单 | 同一件事执行 N 次，用户收到 N 条 |
| 依赖「重启会补跑」 | 不补，错过的触发永远丢失 |
| 任务里抛异常就当重试了 | 不重试，只记一条日志 |
| 长任务用 `@Interval` | 上一轮没完下一轮又来，内存与连接池被拖垮 |
| 容器 `TZ=UTC` 却写「凌晨 3 点」 | 实际在北京时间 11 点执行 |
| `timeZone` 和 `utcOffset` 同时给 | 触发时间变得难以预测 |
| 动态任务用 `addCronJob` 却忘了关 | 同一 name 被覆盖，旧任务仍在跑（要 `deleteCronJob`） |
| 长任务放在 API 进程 + 短 `stop_grace_period` | 关机时被 SIGKILL，留下半截状态 |
| 只在装饰器里写死表达式 | 运营想改调度只能改代码发版 |
