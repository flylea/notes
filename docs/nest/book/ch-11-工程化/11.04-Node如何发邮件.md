# 11.04 Node如何发邮件

验证码、密码重置、告警、账单——后端总要发信。这件事看起来只是「调一个库」，实际上最容易踩的坑不在代码里：**信发出去了，但进了垃圾箱**。这一节按「能不能发出去 → 能不能进收件箱 → 能不能在 Nest 里长期稳定地用」三步走。

## 一、发信这条链路到底经过谁

```mermaid
sequenceDiagram
    participant App as Nest 应用
    participant SMTP as SMTP 服务（第三方或自建）
    participant MX as 收件方 MX
    participant Box as 收件箱/垃圾箱
    App->>SMTP: AUTH + MAIL FROM + RCPT TO + DATA
    SMTP-->>App: 250 queued（这只代表我收下了）
    SMTP->>MX: 投递（查 MX、TLS、重试）
    MX->>MX: SPF / DKIM / DMARC / 声誉 检查
    MX->>Box: 放行或标记垃圾
```

三个关键事实：

1. **`sendMail` 成功只代表「SMTP 服务器收下了」**，不代表对方收到。真正的投递结果（退信）是异步回来的，可能几分钟后才到。
2. **垃圾箱判定发生在收件方**，由 SPF/DKIM/DMARC、发信 IP 声誉、内容、投诉率共同决定，你的代码控制不了其中大部分。
3. 因此「发信功能」的验收标准不是「代码不报错」，而是「在自己的邮箱里能从收件箱看到它」。

## 二、三种发信方式，先选对路

| 方式 | 代表 | 适合 | 代价 |
| --- | --- | --- | --- |
| 第三方 SMTP 中继 | 阿里云邮件推送、腾讯云 SES、Amazon SES、Resend、SendGrid | 绝大多数业务 | 要配域名验证（SPF/DKIM），有配额与限速 |
| 自建 MTA | Postfix + 独立 IP | 量极大、有运维能力 | IP 声誉从零养、退信处理、被当垃圾邮件源的长期风险 |
| 服务商 HTTP API | Resend / SES API | 只需发信、不想管 SMTP | 换成 SDK，但错误码更清晰、更容易重试 |

**结论：先用第三方 SMTP 或 API。** 自建 MTA 是运维工程，不是后端功能开发；在没有专职运维和独立出口 IP 的情况下，自建发出去的信大概率直接进垃圾箱。SMTP 路线在第五节展开，HTTP API 路线（以 Resend 为例）在第六节展开——两条路的取舍标准放在那一节末尾的对照表里。

选服务商时问清四个数：**日发信上限、单域名限速（封/秒）、单封大小上限、退信率红线**。其中限速最容易被忽略——验证码场景在晚高峰会瞬间打满，超出后服务商返回 4xx（`421`/`450`），你的代码如果当成「发送失败」直接给用户报错，体验就是「点了没反应」。正确做法是把它当可重试错误，并给同一用户加 60 秒冷却，避免用户连点把配额烧光。

国内业务还有一层合规：营销类邮件需要退订入口、发信域名要备案，验证码/通知类相对宽松。**别用营销通道发验证码**，也别用验证码通道发促销，两条通道的信誉是分开养的。

## 三、让信能进收件箱：SPF、DKIM、DMARC

这部分和 Node 无关，但决定成败。三条 DNS 记录：

| 记录 | 作用 | 典型值 |
| --- | --- | --- |
| SPF（TXT） | 声明「哪些 IP 有权用我的域名发信」 | `v=spf1 include:spf.mail.aliyun.com -all` |
| DKIM（TXT） | 用私钥签名，收件方用公钥验签，防篡改 | 由服务商给出 `selector._domainkey` 记录 |
| DMARC（TXT） | 告诉收件方「SPF/DKIM 失败怎么办」，并收报告 | `v=DMARC1; p=none; rua=mailto:dmarc@example.com` |

实操顺序：

1. **先上 `p=none` 的 DMARC**，只收报告不拦截，观察两周；
2. 确认 SPF 对齐、DKIM 通过后，升到 `p=quarantine`；
3. 有把握再 `p=reject`。

一个常见错误：SPF 里 `-all` 却没把服务商的 include 写全，导致自己的信被判失败。**发信域名和收信域名最好分开**（`noreply@mail.example.com` 发信，`example.com` 收信），这样发信声誉出问题不会影响主域名收信。

## 四、发信身份分层：别用一个地址发所有信

一个域名上的「发信身份」是会被一起评价的。把验证码、订单通知、营销邮件混在同一个子域发，只要营销邮件被投诉几次，验证码就开始进垃圾箱。**按用途拆子域**是成本最低的隔离手段：

| 用途 | 发信身份 | 说明 |
| --- | --- | --- |
| 验证码/安全通知 | `noreply@notify.example.com` | 只发事务性邮件，退订率必须为 0 |
| 业务通知 | `notice@notify.example.com` | 订单、审批、账单 |
| 营销 | `news@mail.example.com` | 必须有退订，投诉率高也不影响事务通道 |

这样做的直接好处：SPF 里两个子域各自 `include` 对应服务商；某个通道声誉崩了，切换到备用发信服务商时只改 DNS，不动主域名。

另外两个小细节：

- **`from` 的显示名不要用纯英文品牌名**，用「会议室预订」这类能让人一眼认出的名字，收件方判定垃圾时会参考「是否像正常业务邮件」；
- **`replyTo` 指向真实可收信地址**，很多反垃圾系统会做「回信探测」，`noreply` 又不给 `replyTo` 的邮件更容易被扣分。

## 五、nodemailer 10 的最小可用

`nodemailer` 当前 **10.6.1**（2026-11-20）。10.0.0（2026-09-03）是一次大改：**用 TypeScript 重写、同时产出 ESM 与 CJS、要求 Node 20+**，并且保留了 `@types/nodemailer` 的类型布局（所以不用再装 `@types/nodemailer`）。9.0.0 起，抓取远程内容（附件 URL、OAuth2 token 端点）**默认校验证书**，自签证书要显式关掉。

```bash
pnpm add nodemailer
```

```ts
// src/mail/mail.transporter.ts
import nodemailer, { type Transporter } from 'nodemailer';

export function createTransporter(env: {
  host: string; port: number; secure: boolean;
  user: string; pass: string;
}): Transporter {
  return nodemailer.createTransport({
    host: env.host,
    port: env.port,
    secure: env.secure,          // 465 用 true（隐式 TLS），587 用 false（STARTTLS）
    auth: { user: env.user, pass: env.pass },
    pool: true,                  // 连接池：验证码场景一秒钟几十封时非常关键
    maxConnections: 3,
    maxMessages: 100,            // 单连接复用上限，避免长连接被对端踢
    connectionTimeout: 10_000,
    greetingTimeout: 10_000,
    socketTimeout: 20_000,
  });
}
```

参数里三个最容易搞错：

- **`secure`**：465 是「连上就是 TLS」，要 `true`；587 是先明文再 STARTTLS，要 `false`。写反了要么超时，要么报 `wrong version number`。
- **`pool`**：不开池，每封信建立一次 TCP + TLS + AUTH，几十毫秒到几百毫秒；验证码场景必须开。
- **三个超时**：不设的话，对端挂住时请求会一直悬着，把 Node 的事件循环和连接都拖死。

发一封：

```ts
const info = await transporter.sendMail({
  from: '"会议室预订" <noreply@mail.example.com>',  // 显示名与地址都要有，减少被判垃圾的概率
  to: user.email,
  replyTo: 'support@example.com',
  subject: '【会议室预订】登录验证码',
  text: '你的验证码是 834921，10 分钟内有效。',      // 纯文本版：很多客户端与反垃圾都看它
  html: '<p>你的验证码是 <b>834921</b>，10 分钟内有效。</p>',
  headers: {
    'X-Entity-Ref-ID': requestId,                  // 方便在服务商后台按 ID 查投递
    'List-Unsubscribe': '<https://example.com/unsubscribe?u=1>', // 通知类邮件建议带
  },
});

// info.accepted / info.rejected / info.response 是投递诊断的唯一来源
logger.log({ accepted: info.accepted, rejected: info.rejected, response: info.response }, 'mail:sent');
```

## 六、另一条路：服务商 HTTP API（以 Resend 为例）

SMTP 的问题不在协议，而在它太「通用」：所有错误都被拍平成 `5xx` 加一句英文，想区分「收件人不存在」和「临时限流」只能读字符串；连接池、超时、重试全得自己写。服务商 HTTP API 把这件事收窄成一次 JSON 请求：错误码是结构化的、重试边界清楚、还带幂等和投递回执。

什么时候值得换：

- 部署在 Serverless / Edge 上，跑不了长连接 SMTP；
- 需要「发信这件事到底成没成」——不只是 `250 queued`，而是送达、退信、被标垃圾；
- 想用同一套代码做重试，而不用自己猜 `4xx` 还是 `5xx`。

Resend 是这一类里 API 最轻的：`resend@6` 要求 Node 20+，只需一个 API Key，域名在后台验完 SPF/DKIM 就能发。

```ts
// src/mail/resend-mail.service.ts
import { Injectable, Logger } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { Resend } from 'resend';

@Injectable()
export class ResendMailService {
  private readonly logger = new Logger(ResendMailService.name);
  private readonly client: Resend;

  constructor(private readonly config: ConfigService) {
    this.client = new Resend(this.config.getOrThrow<string>('mail.resendApiKey'));
  }

  async sendOtp(to: string, code: string, requestId: string): Promise<void> {
    const { data, error } = await this.client.emails.send(
      {
        from: 'no-reply@notify.example.com',
        to,
        subject: '【会议室预订】登录验证码',
        text: `你的验证码是 ${code}，10 分钟内有效。`,
        html: `<p>你的验证码是 <b>${code}</b>，10 分钟内有效。</p>`,
      },
      {
        // 同一个 requestId 在 24 小时内只会真正发一封，重试安全
        idempotencyKey: `otp/${requestId}`,
      },
    );

    // 关键：SDK 不会抛异常，错误在返回值里
    if (error) {
      this.logger.error({ err: error, to, requestId }, 'resend send failed');
      throw new Error(`resend: ${error.name}`);
    }

    this.logger.log({ id: data.id, to, requestId }, 'resend accepted');
  }
}
```

三处和 SMTP 路线不一样的写法：

1. **返回值即结果**：`emails.send()` 返回 `{ data, error }`，成功时 `error` 为 `null`。不判 `error` 就等于把失败当成功；
2. **幂等键**：`idempotencyKey` 会变成 `Idempotency-Key` 请求头（≤256 字符），服务商在 24 小时内对同一个键只发一次。键要用业务事件拼，别用 `Date.now()`——`otp/${requestId}`、`welcome/${userId}` 这种才可重放；
3. **错误码分层**：`validation_error`(400)、`missing_api_key`(401)、`invalid_attachment`(422) 都是配置或代码问题，重试无用；只有 `rate_limit_exceeded`(429) 和网络错误才值得退避重试。

投递回执靠 webhook，不靠轮询。把 Resend 回调打到自己的接口，验签后用 `svix` 解事件：

```ts
// src/mail/mail-webhook.controller.ts
import { Controller, Post, Req, Headers, HttpCode } from '@nestjs/common';
import { Webhook } from 'svix';
import type { RawBodyRequest } from '@nestjs/common';
import type { Request } from 'express';

@Controller('webhooks/resend')
export class MailWebhookController {
  @Post()
  @HttpCode(200)
  handle(
    @Req() req: RawBodyRequest<Request>,
    @Headers() headers: Record<string, string>,
  ): void {
    // 验签必须用原始字节，不能用 JSON.parse 之后的对象
    const payload = new Webhook(process.env.RESEND_WEBHOOK_SECRET ?? '').verify(
      req.rawBody?.toString('utf8') ?? '',
      headers,
    );

    switch (payload.type) {
      case 'email.delivered':
        break;                                   // 送达，正常
      case 'email.bounced':
        // 永久退信：把地址加入抑制名单，别再发
        break;
      case 'email.complained':
        // 用户标了垃圾：立刻从营销列表移除
        break;
    }
  }
}
```

`rawBody` 要在创建应用时打开：

```ts
const app = await NestFactory.create(AppModule, { rawBody: true });
```

不打开就只能拿到解析后的对象，签名必然对不上——这是接入 webhook 最常见的一处踩坑。验签通过后还要做两件事：用事件里的 `data.email_id` 做幂等（同一个事件可能重投），以及只信任 webhook 来维护抑制名单，别让「发信返回 250」冒充送达。

最后是对照表：

| | nodemailer + SMTP | Resend HTTP API |
| --- | --- | --- |
| 连接方式 | 长连接 + 连接池，需自己管理 | 每次一次 HTTPS 请求 |
| 错误信息 | `5xx` + 服务商英文描述 | 结构化 `name` + HTTP 状态码 |
| 重试策略 | 自己解析响应码 | 明确：只重试 429/网络错误 |
| 幂等 | 不支持 | `Idempotency-Key`，24 小时窗口 |
| 投递回执 | 需另配 webhook / 查日志 | 内置事件，`svix` 验签 |
| 供应商锁定 | 低（换 SMTP 即可） | 中（要换 SDK 与事件模型） |

选择标准不是「哪个更现代」，而是**你是否愿意为「发信结果可观测」付供应商锁定的代价**。发验证码、发票这类必须知道送达结果的信，值得；纯通知类、丢了也无所谓的信，SMTP 更省。

## 七、封进 Nest：一个 MailService，别到处 new transporter

transporter 必须是单例（连接池在它身上），所以放进 Provider，并把「配置读取、启动校验、优雅关闭」一起做掉：

```ts
// src/mail/mail.module.ts
import { Global, Module } from '@nestjs/common';
import { MailService } from './mail.service.js';

@Global()
@Module({ providers: [MailService], exports: [MailService] })
export class MailModule {}
```

```ts
// src/mail/mail.service.ts
import { Injectable, Logger, OnApplicationShutdown, OnModuleInit } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import type { Transporter } from 'nodemailer';
import { createTransporter } from './mail.transporter.js';

@Injectable()
export class MailService implements OnModuleInit, OnApplicationShutdown {
  private readonly logger = new Logger(MailService.name);
  private readonly transporter: Transporter;

  constructor(config: ConfigService) {
    this.transporter = createTransporter({
      host: config.getOrThrow('smtp.host'),
      port: config.getOrThrow('smtp.port'),
      secure: config.getOrThrow('smtp.secure'),
      user: config.getOrThrow('smtp.user'),
      pass: config.getOrThrow('smtp.pass'),
    });
  }

  async onModuleInit(): Promise<void> {
    try {
      await this.transporter.verify();      // 启动即验证账号可用，别等第一封验证码才发现密码错
      this.logger.log('SMTP 连接验证通过');
    } catch (err) {
      this.logger.error({ err }, 'SMTP 连接验证失败，邮件功能将不可用');
      // 这里不 throw：邮件不是核心链路，不该让整个应用起不来；但必须告警
    }
  }

  async onApplicationShutdown(): Promise<void> {
    this.transporter.close();               // 不关池，热更新时会留下僵尸连接
  }

  async sendCode(to: string, code: string, requestId: string): Promise<void> {
    await this.transporter.sendMail({
      from: '"会议室预订" <noreply@mail.example.com>',
      to,
      subject: '【会议室预订】登录验证码',
      text: `你的验证码是 ${code}，10 分钟内有效。`,
      html: `<p>你的验证码是 <b>${code}</b>，10 分钟内有效。</p>`,
      headers: { 'X-Entity-Ref-ID': requestId },
    });
  }
}
```

四个设计决定值得说明：

1. **`verify()` 放在 `onModuleInit` 且失败不抛**：邮件挂了不该拖垮登录（登录还有密码、Session 路径），但要立刻告警；
2. **`onApplicationShutdown` 里 `close()`**：容器重启/滚动发布时释放连接池；
3. **`from` 用常量**：smtplib 层面的发信人必须与 SPF/DKIM 的域名对齐，不能让业务方随意传；
4. **模板不做「用户输入直接拼 HTML」**：验证码是数字还好，一旦带用户名/备注，必须转义（见下节）。

## 八、三个安全细节

**1. HTML 注入。** 用户名里放 `<a href="http://evil">点这里</a>`，拼进邮件 HTML 就是一个钓鱼入口：

```ts
const escapeHtml = (s: string): string =>
  s.replace(/[&<>"']/g, (c) => ({ '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' })[c]!);
```

**2. 附件路径不能用用户输入。** `attachments: [{ path: req.body.file }]` 等于把服务器文件系统开放给攻击者（nodemailer 会读任意本地路径）。要发附件，先按业务 ID 查库拿到受控路径。

**3. 日志里不能有验证码。** 邮件正文一旦进日志，等于把「第二因素」写进了日志系统，任何有日志权限的人都能登录任意账号。日志只记 `to`（脱敏）、`template`、`messageId`、`response`。

## 九、模板怎么管：字符串、模板引擎还是 MJML

三种做法，按项目阶段选：

```ts
// A. 纯字符串（小项目、1–2 个模板）
const html = `<p>你的验证码是 <b>${code}</b>，10 分钟内有效。</p>`;

// B. 模板引擎（模板变多、需要复用布局）
const html = await renderFile('templates/code.hbs', { code, expireMinutes: 10 });

// C. MJML / react-email（需要跨客户端一致的排版）
const html = mjml2html(`
  <mjml><mj-body><mj-section><mj-column>
    <mj-text>你的验证码是 ${code}</mj-text>
  </mj-column></mj-section></mj-body></mjml>`).html;
```

选择的判据是「排版要求」而不是「技术洁癖」：

- 验证码/告警类邮件**纯文本 + 极简 HTML** 最好，反垃圾系统对复杂排版的图片邮件更敏感，用户也只需要一个数字；
- 订单/账单类需要表格与品牌视觉，用模板引擎 + 一套共享布局即可；
- 真要「和设计稿一致」，用 MJML（输出内联样式的表格布局，兼容 Outlook）或 react-email（用 React 写模板，适合前端同栈团队）。

无论哪种，都要准备**纯文本版本**（`text` 字段）：只给 HTML 的邮件在不少客户端与反垃圾规则下评分更低，而纯文本版对读屏软件也更友好。

## 十、投递失败怎么办：分清 4xx 与 5xx

```ts
import { isSmtpError } from './smtp-error.js';

try {
  await transporter.sendMail(opts);
} catch (err) {
  if (isSmtpError(err) && err.responseCode) {
    // 4xx：临时失败（限流/对端忙），可以退避重试
    // 5xx：永久失败（收件人不存在/被拒），重试没意义，直接标记
    const permanent = err.responseCode >= 500;
    logger.warn({ code: err.responseCode, permanent, err }, 'mail:failed');
    if (!permanent) throw err;   // 交给上层重试
  }
  throw err;
}
```

判断一个错误是否可重试的规则很简单：**`4xx` 重试、`5xx` 记录并放弃、网络错误（`ETIMEDOUT`/`ECONNRESET`）重试**。重试要带退避，并且同一个验证码不要重复发（用户点两次「发送」不是两次重试，是要被频控拦住的）。

真正大规模发信（订单通知、周报）应该走队列，而不是在请求里同步发——这个模式在《Redis 与缓存》一章的 BullMQ 部分会展开：任务入队、worker 消费、失败重试、死信。

## 十一、退信、投诉与地址清理

发信是双向的：你收不到退信通知，就不知道名单里有多少死地址，而高退信率会直接拉低发信声誉。

- **硬退信（hard bounce，5xx）**：地址不存在。立刻把该地址标记为无效，之后不再发；
- **软退信（soft bounce，4xx）**：邮箱满、临时拒收。退避重试几次仍失败再降级；
- **投诉（complaint）**：用户点「举报垃圾邮件」。营销通道必须能做到「投诉即退订」，否则服务商会限流甚至封号。

落地方式：服务商后台配置 webhook / 事件通知，把 `bounce`、`complaint` 事件写入自己的 `email_suppressions` 表（邮箱 + 原因 + 时间），发信前查一次。这张表比任何模板优化都更能保住送达率。

## 十二、开发环境：别用真实邮箱调试

本地开发要能看到「发出去长什么样」。两种做法：

**A. Mailpit（推荐，带 Web UI）**

```yaml
# docker-compose.override.yml
services:
  mailpit:
    image: axllent/mailpit:v1.34
    ports: ['8025:8025', '1025:1025']   # 8025 是 Web UI，1025 是 SMTP
```

`.env` 里把 SMTP 指向 `127.0.0.1:1025`，`secure=false`、不填 auth。打开 `http://localhost:8025` 就能看到每封邮件、附件和原始头。

**B. `streamTransport`（零依赖，适合单元测试/预览）**

```ts
const preview = nodemailer.createTransport({ streamTransport: true, buffer: true, newline: 'unix' });
const { message } = await preview.sendMail({ from: 'a@example.com', to: 'b@example.com', subject: 's', text: 't' });
console.log(message.toString());   // 完整的 MIME 原文，直接断言头与正文
```

**不要在生产用测试邮箱服务**（如 Ethereal）：它的凭据是公开的，邮件内容会被任何人看到。

## 十三、Checkpoint

判定发信是否「发出去了」，只看三个字段：`accepted`（SMTP 接受投递的地址）、`rejected`（被中继拒收的地址）、`response`（服务商原始回执）。`messageId` 一定要记进日志或数据库——它是和服务商投递日志对账的唯一钥匙，用户说「没收到」时，先拿它去后台查，比猜有用。

```bash
# 1) 用本地 SMTP sink 验证代码路径（不依赖任何真实服务商）
node --experimental-strip-types scripts/mail-probe.ts
# 期望输出：accepted=[...] messageId=true verify=true

# 2) 服务启动时能看到 SMTP 验证日志
pnpm start:dev 2>&1 | grep -i 'SMTP'

# 3) 用 Mailpit 看真邮件（可选）
docker compose up -d mailpit
curl -s -X POST http://localhost:1025/send 2>/dev/null || true
# 打开 http://localhost:8025 检查：From/Subject/正文/自定义头 X-Entity-Ref-ID

# 4) 误配时的报错要能看懂（把端口改成 465 但 secure 写 false）
# 期望：连接失败/超时，而不是「发送成功」
```

## 十四、坑表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 发送成功但收不到 | `250 queued` 只代表中继收下，后续被退信或判垃圾 | 查服务商投递日志 + 收件方 SPF/DKIM/DMARC |
| `wrong version number` | 465 配了 `secure:false`，或 587 配了 `true` | 465→`true`，587→`false` |
| 启动正常但第一封信超时 | 企业网/云主机封了 25 端口 | 用 465/587，别用 25 |
| 验证码邮件进垃圾箱 | 发信域名未配 SPF/DKIM、`from` 域名与 DNS 不一致 | 配三条 DNS 记录，`from` 用同域名 |
| 并发几十封后卡死 | 未开 `pool`、或 `maxConnections` 太大触发对端限流 | 开池、限并发、加超时 |
| 热更新后连接泄漏 | 没在 `onApplicationShutdown` 里 `close()` | 关池 |
| 邮件正文被记进日志 | 直接 `logger.log(opts)` | 只记 `to`(脱敏)/模板名/messageId |
| 本地调试发到真实用户 | `.env` 里配了生产 SMTP | 用 Mailpit + 环境隔离 |
| 用 nodemailer 9 的写法装 10 | 10 要求 Node 20+，且是 ESM/CJS 双构建 | 升级 Node，导入用默认导出 |
| 大批量发送时偶发 `421 4.7.0 Too many connections` | 未开池或并发超过服务商单 IP 连接上限 | 控制 `maxConnections`，退避重试 |
| 邮件里中文主题乱码 | 手写原始头、未让 nodemailer 编码 | 用 `subject` 字段传原文，不要手拼 `Subject:` |
