# 11.13 Nest的REPL模式

排查一个「本地复现不了」的问题时，最烦的是：明明 `BookingService` 里逻辑就几行，但你没法在运行时直接调它——要么写个临时接口，要么写个脚本 new 一堆依赖，要么加日志重新部署。

Nest 给了一个很实用的东西：**REPL 模式**。它把你整个依赖图装进一个 Node REPL 里，你可以直接 `get(BookingService).create(...)`，交互式地调用任何 provider/controller 的方法。

这一节讲怎么用、它能做什么、以及几个用错就会出事的地方。

## 一、REPL 到底是什么

它不是一个 HTTP 接口，也不是调试器。启动后：

- 应用**以 application context 方式启动**（没有 HTTP 监听、没有端口）；
- 所有 provider 被实例化、依赖注入完成（等价于 `app.init()`）；
- 你得到一个终端，里面预置了 `get()`、`debug()`、`methods()` 等函数；
- 退出时 `app.close()`，生命周期钩子正常走。

换句话说：**你拿到的是一份「活的容器」**。这比 `node --inspect` 断点调试更适合「我想直接调一下这个方法看看返回什么」的场景。

```mermaid
flowchart TD
  A["pnpm start --entryFile repl"] --> B["NestFactory.createApplicationContext(AppModule)"]
  B --> C["实例化全部 provider<br/>cron / 队列 / 数据库连接池"]
  C --> D["app.init()：生命周期钩子"]
  D --> E["node:repl.start()<br/>注入 get / debug / methods"]
  E --> F{"终端里输入命令"}
  F -->|get(token).method()| G["直接调用 service 方法"]
  F -->|debug()| H["打印模块树"]
  F -->|.exit| I["app.close()：钩子 + 连接关闭"]
```

注意图的中间那步：**副作用发生在你敲命令之前**。所以「REPL 一启动，定时任务就跑起来了」不是 bug，是设计使然。

## 二、接入：一个文件 + 一条命令

在 `src/main.ts` 旁边建 `src/repl.ts`：

```ts
import { repl } from '@nestjs/core';
import { AppModule } from './app.module.js';

async function bootstrap(): Promise<void> {
  const server = await repl(AppModule);
  server.setupHistory('.nestjs_repl_history', (err) => {
    if (err) console.error(err);
  });
}

await bootstrap();
```

启动：

```bash
pnpm start -- --entryFile repl
```

`repl()` 内部做的是 `NestFactory.createApplicationContext(AppModule, { abortOnError: false, logger: new ReplLogger() })` 再 `app.init()`，然后起一个 Node REPL，把原生函数和依赖图注入进去。注意 `abortOnError: false`——某个 provider 初始化失败时 REPL 不会整个退出，你能进去看看是哪个坏了。

`repl()` 的第二个参数是 Node 原生 REPL 的选项，可以传 `{ prompt: 'booking> ', useColors: false }` 之类。返回值是 Node REPL server，所以 `setupHistory`、`on('exit')` 这些都能用；`repl()` 内部也注册了 `exit` 事件去 `app.close()`，保证你退出时连接和定时器被正确关闭。

启动后你会看到：

```text
[Nest] LOG [NestFactory] Starting Nest application...
[Nest] LOG [InstanceLoader] AppModule dependencies initialized
[Nest] LOG REPL initialized
>
```

## 三、六个原生函数

`help()` 可以列出全部：

| 函数 | 作用 |
| --- | --- |
| `get(token)` / `$(token)` | 取 provider/controller 实例，取不到抛异常 |
| `resolve(token, contextId)` | 解析 transient/request-scoped 实例，需要传 contextId |
| `methods(token)` | 列出某个类上的公开方法 |
| `debug(module?)` | 打印模块树、controller、provider |
| `select(DynamicModule \| ClassRef)` | 按模块树选择，拿到该模块的 context |
| `help()` | 列出以上函数 |

每个函数还能查签名：

```text
> $.help
Retrieves an instance of either injectable or controller, otherwise, throws exception.
Interface: $(token: InjectionToken) => any
```

`debug()` 在排查「这个 provider 到底注册在哪」时特别好用——依赖注入报错 (`Nest can't resolve dependencies of ...`) 时，先 `debug()` 看一眼模块树，比读代码快：

```text
> debug(BookingsModule)
BookingsModule:
- controllers:
  ◻ BookingsController
- providers:
  ◻ BookingsService
  ◻ BookingsPolicy
```

`select()` 用于多模块同名 token 的场景：比如 `UsersModule` 和 `AdminModule` 各有一个 `UsersService`，`get(UsersService)` 拿到的是根容器那个（或者直接报错），要拿子模块里的：

```text
> const adminCtx = select(AdminModule)
> adminCtx.get(UsersService)
```

`resolve()` 平时用得少，只在你要调 request-scoped provider 时需要——它要求传 `contextId`，而 REPL 里没有真实请求上下文，所以通常得自己造一个（`ContextIdFactory.create()`），调完记得释放，否则内存里会挂着这个「虚拟请求」的资源。

## 四、能做的事：四个典型场景

**1. 直接调业务方法，看返回什么。**

```text
> const svc = get(BookingsService)
> await svc.create({ roomId: '...', startTime: '...', endTime: '...', userId: '...' })
{
  id: '...',
  status: 'PENDING',
  ...
}
```

**2. 验证一个数据问题。** 线上有人报「看到的预订列表少了」，进 REPL 用同一个 userId 调 `bookingsService.listForUser(id)`，看返回什么；再 `get(Database)` 直接跑一条 SQL 对账。

**3. 判断配置到底读到了什么。**

```text
> get(ConfigService).get('database.url')
'postgresql://meeting:***@127.0.0.1:5432/meeting_booking'
```

这比在代码里 `console.log` 再重启快得多。注意它会打印明文密码，别在共享终端里截屏。要安全一点就直接问具体键：

```text
> const cfg = get(ConfigService)
> cfg.get('database.url')    // 含密码
> cfg.get('port')            // 无害
> cfg.getOrThrow('jwt.accessExpiresIn')
```

`getOrThrow` 在生产里是「启动即失败」的守卫，在 REPL 里则是「快速确认这个键有没有配」。

**4. 手动触发一次「定时任务」或「刷盘」。**

```text
> await get(ViewsFlushService).flushOnce()
{ flushed: 12, rows: 37 }
```

比等 `@Cron` 到点快，也顺便验证了幂等性（连跑两次，第二次应该 `flushed: 0`）。

## 五、REPL 绕过了什么

这是必须明确的边界。你在 REPL 里调的是 **service 方法本身**，所以：

| 层 | 是否执行 |
| --- | --- |
| Controller 路由 | ❌ 不走 |
| Guard（鉴权/角色） | ❌ 不走 |
| Pipe（DTO 校验/转换） | ❌ 不走 |
| Interceptor（日志/响应包装/事务） | ❌ 不走 |
| ExceptionFilter | ❌ 不走（异常直接抛到 REPL） |
| Service 内部逻辑 | ✅ 走 |
| 事务边界 | 取决于事务在 service 外层还是内层 |

所以 REPL 里调用**不能当作「接口测试」**。它适合验证「服务层逻辑对不对」，不适合验证「接口在没鉴权时会不会被越权访问」——那种必须走 HTTP。

反过来说，这正是它的价值：想单独测 service 逻辑时，不用构造一整套 HTTP 上下文。

还有一个容易踩的点：**请求级上下文（AsyncLocalStorage）在 REPL 里是空的**。如果你的日志拦截器、审计、多租户能力依赖 ALS 里的 userId/traceId，那 REPL 里调 service 时这些值都是 `undefined`——不是代码错了，而是没有请求这个前提。要验证这类逻辑，只能在 REPL 里手动把上下文包起来（`als.run({ userId }, () => svc.doWork())`），或者老实走 HTTP。

事务边界这一点值得单独提醒：如果事务是在 controller/interceptor 里开的（`@Transactional()` 装饰器包在路由方法上），那 REPL 里直接调 service 就是**没有事务**的，多条写操作可能各提交各的。判断方法很简单——看 service 方法内部有没有 `db.transaction(...)`。example 项目里事务在 service 内部（`execTransaction`），所以 REPL 调用是安全的；如果你的项目用路由级事务，REPL 里的写操作要格外小心。

## 六、危险操作：REPL 连的是真数据库

REPL 里的每一个写操作都直接落库，**没有「预演」模式**。所以：

- **只连本地或测试库**。用 `.env.local` 覆盖 `DATABASE_URL`，或者在启动前显式检查：

```ts
// src/repl.ts
const url = process.env.DATABASE_URL ?? '';
if (!/localhost|127\.0\.0\.1/.test(url)) {
  throw new Error('REPL 只允许连本地数据库，请检查 DATABASE_URL');
}
```

- 别在生产 REPL 里跑 `deleteMany` / 批量 `updateAll`；
- 别把 REPL 暴露成网络服务（它没有鉴权，本质是任意代码执行）；
- 打印 token/密码/密钥时注意终端历史和录屏。

如果确实要在预发环境调，建议单独建一个只读数据库账号，启动时用 `REPL_DB_READONLY=1` 切过去——写操作直接报错，比靠自觉可靠：

```sql
-- 只读账号：能 select，不能写
CREATE ROLE repl_ro LOGIN PASSWORD '***';
GRANT CONNECT ON DATABASE meeting_booking TO repl_ro;
GRANT USAGE ON SCHEMA public TO repl_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO repl_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO repl_ro;
```

用了只读账号之后，`onModuleInit` 里的写检查也会失败——这时候把 `abortOnError` 相关的报错当成提示，而不是「REPL 坏了」。

## 七、副作用：它会启动所有 provider

`repl()` 用的是 `createApplicationContext`，**不监听端口，但会实例化全部 provider**。这意味着：

- `@Cron` 任务会真的开始跑；
- 队列消费者（BullMQ Worker）会连上并抢消息；
- 数据库连接池、Redis 连接都会占资源；
- `onModuleInit` / `onApplicationBootstrap` 里的副作用都会执行。

两个处理办法：

**办法一：加开关。**

```ts
@Module({
  imports: [
    ScheduleModule.forRoot({ cronJobs: false }), // 关掉 cron，interval/timeout 仍可单独关
    BullModule.forRoot({ /* ... */ }),
  ],
})
export class ReplModule {}
```

**办法二：环境变量守卫。** 在任务/消费者里判断：

```ts
if (process.env.REPL_MODE === 'true') return; // 不注册消费者
```

启动时 `REPL_MODE=true pnpm start -- --entryFile repl`。

这个开关也顺手解决了「REPL 和开发服务器同时跑」的问题：你一边开着 `pnpm start:dev` 做接口调试，一边开 REPL 查数据，如果两边都跑 cron，同一个任务会执行两次（比如刷盘、发通知）。给 REPL 侧加 `REPL_MODE=true`，只保留开发服务器的后台任务，就不会互相打架。

更彻底的做法是单独建一个 `ReplModule`，只 import 你要调的模块。代价是 `get()` 拿不到没导入的 provider——这时 `select()` 也帮不了你，因为容器里根本没有它。

还有个更隐蔽的副作用：**`onModuleInit` 里的「启动检查」会跑**。比如「启动时校验数据库版本」「启动时加载缓存」「启动时注册定时任务」——REPL 都会执行一遍。如果这些检查里有写操作（比如写一条「服务启动」日志、刷新一次配置表），在 REPL 里就会多写一条。排查时先看一遍 `onModuleInit`/`onApplicationBootstrap` 的实现，能省掉很多「怎么多了一条数据」的困惑。

## 八、watch 模式与历史记录

开发时让 REPL 跟着代码重载：

```bash
pnpm start -- --watch --entryFile repl
```

缺点是每次重载历史都丢。用 `setupHistory` 存到文件（上面第二节的写法），文件加进 `.gitignore`：

```bash
echo '.nestjs_repl_history' >> .gitignore
```

watch 模式下还要注意：重载会 `app.close()` 再重建，**没断开的数据库连接/定时器可能泄漏**，连开几次后 `pg_stat_activity` 里能看到一堆空闲连接。频繁改代码时，重载几次就手动退出重进一次。

## 九、在 example 项目里接一遍

把 REPL 接进会议室预订系统，只需要两个文件。

`src/repl.ts`：

```ts
import { repl } from '@nestjs/core';
import { AppModule } from './app.module.js';
import { ReplModule } from './repl.module.js';

async function bootstrap(): Promise<void> {
  // 业务模块照常启动，但把定时任务/队列消费者换成空实现
  const server = await repl(process.env.REPL_FULL === '1' ? AppModule : ReplModule);
  server.setupHistory('.nestjs_repl_history', (err) => void (err && console.error(err)));
}

await bootstrap();
```

`src/repl.module.ts`：

```ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';
import { ScheduleModule } from '@nestjs/schedule';
import { PrismaModule } from './database/prisma.module.js';
import { RedisModule } from './redis/redis.module.js';
import { BookingsModule } from './modules/bookings/bookings.module.js';
import { RoomsModule } from './modules/rooms/rooms.module.js';
import { UsersModule } from './modules/users/users.module.js';

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true, envFilePath: ['.env.local', '.env'] }),
    ScheduleModule.forRoot({ cronJobs: false, intervals: false, timeouts: false }),
    PrismaModule,
    RedisModule,
    UsersModule,
    RoomsModule,
    BookingsModule,
  ],
})
export class ReplModule {}
```

`package.json` 加一条方便的命令：

```json
{
  "scripts": {
    "repl": "nest start --watch --entryFile repl"
  }
}
```

跑起来后典型的排查流程：

```text
> debug(BookingsModule)
> const users = get(UsersService)
> const alice = await users.findByEmail('alice@example.com')
> const rooms = get(RoomsService)
> const room = (await rooms.list())[0]
> const bookings = get(BookingsService)
> await bookings.create({ userId: alice.id, roomId: room.id, startTime: '2026-12-01T10:00:00+08:00', endTime: '2026-12-01T11:00:00+08:00' })
```

如果这一步报「时间冲突」，就说明业务规则是对的；如果成功创建了冲突预订，问题就定位在 service 的冲突检查上——**不用写接口、不用造 token、不用重启应用**，这就是 REPL 最值钱的地方。

## 十、容器里怎么用

镜像里只有 `dist/`，所以跑 `dist/repl.js`：

```bash
# 需要 TTY，否则没有交互
docker compose exec -it api node dist/repl.js
```

生产镜像通常不建议带 REPL——它是任意代码执行入口。要留调试能力，用「一次性容器 + 只读副本库」的方式，跑完就删：

```bash
# 用只读账号起一个临时容器，跑完自动删除
docker run --rm -it   -e DATABASE_URL="postgresql://readonly:***@db-replica:5432/meeting_booking"   -e REPL_MODE=true   meeting-booking-api:latest node dist/repl.js
```

注意 `docker run` 必须带 `-it`（分配 TTY + 保持 stdin），否则 REPL 读不到输入，容器会立刻退出。用 `docker compose exec` 时同理，少了 `-t` 就只能看它闪一下。

## 十一、和别的调试方式怎么选

| 方式 | 适合 | 不适合 |
| --- | --- | --- |
| REPL | 调 service 方法、看依赖图、验证配置 | 复现 HTTP 层问题、跑完整请求链 |
| `node --inspect` + 断点 | 逐步跟逻辑、看变量、复现时序 bug | 快速看「这个方法返回什么」 |
| 临时脚本（`tsx script.ts`） | 可重复的批处理、迁移、数据修复 | 需要完整容器（DI/配置）时太重 |
| 自动化测试 | 回归、CI | 一次性排查 |

一个实际建议：把常用的排查动作写成 REPL 片段存起来（比如 `scripts/repl-cheatsheet.md`），下次排查直接粘贴，比每次重新想「怎么取到那个 provider」快。

还有个容易被忽略的用途：**验证迁移后的数据是否兼容**。跑完 `db:migrate` 后，用 REPL 的 `get(UsersService).findByEmail(...)` 走一遍新代码路径，比跑一个 curl 更早发现问题——因为 service 层才是大部分业务逻辑的所在，HTTP 层只是壳。

## 十二、Checkpoint

```bash
# 1) 启动 REPL（本地库）
pnpm start -- --entryFile repl

# 2) 看模块树
> debug()

# 3) 取服务、列方法
> const svc = get(BookingsService)
> methods(svc)

# 4) 调一个只读方法
> await svc.listForUser('user-uuid')

# 5) 看配置（注意脱敏）
> get(ConfigService).get('jwt.accessExpiresIn')

# 6) 退出，确认进程干净退出
> .exit
```

## 十三、坑表

| 写法 | 后果 |
| --- | --- |
| REPL 连生产库 | 一条 `deleteMany` 就是事故 |
| 以为 REPL 会走 Guard/Pipe | 误判「接口安全」，实际只是没走路由 |
| 不关 cron/消费者 | REPL 一开，定时任务和消息消费就动了 |
| 把 REPL 起在 0.0.0.0 或加 HTTP 包装 | 无鉴权的任意代码执行 |
| watch 模式长时间反复重载 | 连接/定时器泄漏，数据库连接数涨 |
| 历史文件提交进 git | 密钥、token 进了仓库 |
| `select()` 选了个没 import 的模块 | 报「找不到 token」，白折腾 |
| 在共享终端打印 ConfigService | 密码、密钥上屏、进 shell 历史 |
