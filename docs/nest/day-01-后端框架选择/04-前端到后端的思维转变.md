# 从 Vue/React 到 Nest：前端视角的全栈思维转变

## 你已有的前端知识是巨大优势

两年以上的 Vue/React 经验意味着你已经掌握了：

- **组件化思维**：把 UI 拆成可复用的组件
- **状态管理**：理解数据如何在组件间流动
- **路由设计**：URL → 组件的映射关系
- **工程化能力**：Webpack/Vite 构建、ESLint/Prettier 规范、Git 协作

这些能力的"后端版本"几乎是一一对应的。你已经有了思维模型，只需要学会新的词汇。

## 前端 → 后端 概念映射表

### 组件化 → 模块化

```
Vue SFC（单文件组件）           Nest Module
┌─────────────────────┐       ┌─────────────────────┐
│ <template>           │       │ Controller          │
│   <UserList />       │       │   @Get() findAll()  │
│   <UserForm />       │       │   @Post() create()  │
│ </template>          │       │                     │
│                      │       │ Service             │
│ <script setup>       │       │   findAll() {}      │
│ import useUserStore  │       │   create() {}       │
│ const users = ...    │       │                     │
│ </script>            │       │ Module              │
│                      │       │   imports: [...]    │
│ <style scoped>       │       │   providers: [...]  │
│   .user-list { ... } │       │   exports: [...]    │
│ </style>             │       │                     │
└─────────────────────┘       └─────────────────────┘
```

**核心理念一致**：一个"组件/模块"封装了一个关注点的所有逻辑。Vue SFC 封装了 UI+逻辑+样式，Nest Module 封装了路由+业务+数据访问。

### Props / Event → DTO（Data Transfer Object）

```typescript
// 前端：父组件传给子组件的数据
interface UserListProps {
  users: User[];
  loading: boolean;
  onDelete: (id: number) => void;
}

// 后端：客户端传给服务端的数据
class CreateUserDto {
  @IsNotEmpty() username: string;
  @IsNotEmpty() @MinLength(6) password: string;
}
```

DTO 本质上就是"API 层面的 Props"。前端用 TypeScript interface 约束组件间的数据传递，后端用 DTO class + 装饰器约束客户端输入。

### Provide / Inject → 依赖注入（DI）

```typescript
// Vue 3：祖先组件 provide，后代组件 inject
// 祖先组件
provide('userService', userService);

// 后代组件（任意层级）
const userService = inject('userService');

// Nest：完全一样的思想，但由框架自动完成
// Module 中声明（相当于 provide）
@Module({
  providers: [UserService],  // 声明：这个 Service 可用
})

// Controller 中注入（相当于 inject）
constructor(private userService: UserService) {}  // 自动拿到实例
```

Vue 的 provide/inject 是解决"跨层级组件传值"的方案。Nest 的 DI 是解决"跨模块对象共享"的方案。**核心思想完全一致：声明提供者 → 声明消费者 → 框架自动连接**。

### Vue Router / React Router → Controller 路由

```typescript
// 前端：Vue Router
const routes = [
  { path: '/users', component: UserList },
  { path: '/users/:id', component: UserDetail },
];

// 后端：Nest Controller
@Controller('users')
export class UserController {
  @Get()        // GET /users
  list() {}

  @Get(':id')   // GET /users/:id
  detail(@Param('id') id: string) {}
}
```

路由的本质都是：**URL Pattern → Handler**。前端路由映射到组件（渲染 UI），后端路由映射到方法（返回数据）。

### Vuex / Pinia Store → Service

```typescript
// 前端：Pinia Store 管理业务逻辑
export const useUserStore = defineStore('user', () => {
  const users = ref<User[]>([]);

  async function fetchUsers() {
    users.value = await api.getUsers();
  }

  async function createUser(data: CreateUserDto) {
    const newUser = await api.createUser(data);
    users.value.push(newUser);
  }

  return { users, fetchUsers, createUser };
});

// 后端：Service 管理业务逻辑
@Injectable()
export class UserService {
  async findAll() {
    return this.prisma.user.findMany();
  }

  async create(dto: CreateUserDto) {
    return this.prisma.user.create({ data: dto });
  }
}
```

Store 和 Service 都是**业务逻辑的集中地**。区别是 Store 管理前端状态（内存中的数据），Service 操作后端数据（数据库中的数据）。

### Axios / Fetch → Prisma Client

```typescript
// 前端：用 axios 请求后端 API
const { data: users } = await axios.get('/api/users');
const { data: newUser } = await axios.post('/api/users', { name: 'John' });

// 后端：用 Prisma 操作数据库
const users = await prisma.user.findMany();
const newUser = await prisma.user.create({ data: { name: 'John' } });
```

两者的 API 设计惊人地相似——都是**声明式的数据操作**。区别是 axios 发 HTTP 请求到后端，Prisma 生成 SQL 请求到数据库。

### 导航守卫 / 拦截器 → Guard / Interceptor

```typescript
// 前端：Vue Router 导航守卫
router.beforeEach((to, from) => {
  if (!store.isLoggedIn && to.meta.requiresAuth) {
    return '/login';  // 未登录跳转登录页
  }
});

// 后端：Nest Guard
@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    if (!request.user) {
      throw new UnauthorizedException('请先登录');
    }
    return true;
  }
}
```

**本质是同一个模式**：在请求到达目标之前，插入一段检查逻辑。前端守卫检查"能否进入这个页面"，后端 Guard 检查"能否调用这个接口"。

## 思维转变的三个关键

### 1. 从"无状态 UI"到"有状态服务"

前端组件渲染完就等着用户操作了，但后端服务一直在运行、一直连着数据库、一直在等待请求。你需要关注：
- 数据库连接池的管理
- 内存中缓存的生命周期
- 进程的启动和优雅关闭

### 2. 从"客户端安全"到"服务端安全"

前端的所有校验都是 UX（用户体验），绕开前端校验是 trivial 的（打开 DevTools / curl）。后端的校验才是真正的**安全边界**：
- 永远不要信任客户端传来的数据
- 密码必须 hash，永远不要明文存储
- SQL 注入、XSS、CSRF 是真实存在的攻击

### 3. 从"同步操作"到"异步并发"

前端的大部分操作是同步的（更新 DOM、处理用户点击），遇到异步用 `await` 就解决了。后端的一个请求可能涉及：
- 查数据库（IO 等待）
- 调第三方 API（网络等待）
- 写日志文件（磁盘 IO）
- 发消息队列（网络 IO）

这些操作可以**并行执行**——你能用 `Promise.all` 把 100ms 的串行 IO 变成 30ms 的并行 IO。

## 作为前端工程师，你的优势在哪里？

不要觉得学后端是"从零开始"。你其实已经有：
- **API 设计直觉**：你调过几百个接口，知道什么样的 API 好用、什么难用
- **异步思维**：`Promise`、`async/await`、事件循环——这些概念前端已经从 callback hell 到 React Server Components 嚼了三遍了
- **工程化经验**：ESLint 规则、TypeScript 泛型、CI/CD 管道、Git 分支策略——后端工程化没比前端复杂
- **用户体验视角**：你知道前端想要什么样的数据和格式，这让你设计的 API 比纯后端开发者设计的更好用
