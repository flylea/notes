# 为什么从 JSON 迁移到数据库

## 当前状态回顾

Day 6-12 我们的图书管理系统使用 DbModule 将数据存储在 JSON 文件中：

```typescript
// Day 12 的架构
@Injectable()
export class BookService {
  constructor(private dbService: DbService) {} // ← JSON 文件读写

  async findById(id: number) {
    const books = await this.dbService.read<Book>('books');
    return books.find(b => b.id === id); // ← 全量加载到内存过滤
  }
}
```

这在原型阶段可以工作，但随着系统演进会遇到严峻问题：

## JSON 文件存储 vs 数据库对比

| 维度 | JSON 文件 | MySQL/PostgreSQL |
|------|----------|-----------------|
| **并发写入** | 进程锁/文件锁，高并发下会丢失数据 | MVCC 机制，支持真正并发 |
| **查询性能** | 全量读入内存，O(n) 遍历 | B+Tree 索引，O(log n) |
| **数据量** | 10MB 以内勉强可用 | TB 级别游刃有余 |
| **关联查询** | 手动 join（多次读+内存匹配） | SQL JOIN，一次查询 |
| **数据完整性** | 手动校验，无约束 | 外键、唯一约束、CHECK |
| **事务** | 不支持 | ACID 事务保证 |
| **备份恢复** | 手动 cp 文件 | 成熟的备份/主从/集群方案 |
| **Schema 管理** | 无（代码即 Schema） | Migration 版本管理 |

## 具体问题演示

```typescript
// 问题 1：并发写入——两个用户同时注册
// 用户 A 和用户 B 同时请求注册，都读取到 users.json（同版本）
// A 写入 → 覆盖
// B 写入 → 覆盖（A 的数据丢失！）

// 问题 2：模糊搜索——找标题含 "NestJS" 的书
async search(keyword: string) {
  const books = await this.dbService.read<Book>('books');  // 全量加载 10 万条
  return books.filter(b => b.title.includes(keyword));      // 内存遍历 10 万次
}
// 每次搜索都要加载整个文件——10 万本书 ≈ 50MB JSON ≈ 每次请求 50MB 内存

// 问题 3：关联查询——查一本书的借阅记录和借阅人
async findDetail(bookId: number) {
  const books = await this.dbService.read<Book>('books');
  const records = await this.dbService.read<BorrowRecord>('borrowRecords');
  const users = await this.dbService.read<User>('users');
  // 三次全量读取 + 手动 join
  const book = books.find(b => b.id === bookId);
  const borrows = records.filter(r => r.bookId === bookId);
  return {
    ...book,
    borrows: borrows.map(b => ({
      ...b,
      user: users.find(u => u.id === b.userId),
    })),
  };
}
```

## 数据库的优势

```typescript
// 问题 1 解决：数据库唯一约束 + 并发控制
// MySQL/PostgreSQL 保证同一时刻只有一个写入成功
await this.prisma.user.create({ data: { username: 'john' } });
// 另一个并发请求会收到 P2002 错误，而不是静默覆盖

// 问题 2 解决：数据库 LIKE + 索引
await this.prisma.book.findMany({
  where: { title: { contains: 'NestJS' } },
  take: 20,
});
// SQL: SELECT * FROM book WHERE title LIKE '%NestJS%' LIMIT 20
// 数据库在存储层完成过滤，只返回 20 条

// 问题 3 解决：一次 JOIN 查询
await this.prisma.book.findUnique({
  where: { id: bookId },
  include: {
    borrows: { include: { user: true } },
  },
});
// 一条 SQL 完成所有关联查询
```

## 迁移策略：接口不变，只换底层

```
┌─────────────────────────────────────────────────┐
│                                                   │
│  迁移前（Day 12）          迁移后（Day 19）           │
│                                                   │
│  Controller              Controller               │
│     │                       │                     │
│     ▼                       ▼                     │
│  Service                 Service                  │
│     │                       │                     │
│     ▼                       ▼                     │
│  DbModule (JSON)    →    PrismaModule (Database)  │
│                                                   │
│  外部接口不变！         底层实现变化巨大！              │
│  GET /book/list        原来：全量读取 1000 行 JSON    │
│  POST /book/create     现在：SELECT * ... LIMIT 20 │
│                        性能提升 10-100 倍           │
│                                                   │
└─────────────────────────────────────────────────┘
```

> 这就是 DI（依赖注入）的威力——Service 只依赖抽象，切换底层实现只需改注入，不触动业务逻辑。

## 数据库选型建议

| 场景 | 推荐 | 理由 |
|------|------|------|
| 个人项目/原型 | MySQL 8.0 | 生态最大，资料最多，免费 |
| 需要高级分析 | PostgreSQL 16 | 窗口函数、CTE、JSONB 更强 |
| 需要全文搜索 | PostgreSQL | 内置 tsvector，不需要 Elasticsearch |
| 需要地理空间 | PostgreSQL + PostGIS | 开源 GIS 领域标准 |
| 需要极致兼容 | MySQL 8.0 | 几乎所有云厂商都提供 |
| 国产化要求 | TiDB / OceanBase | 兼容 MySQL 协议 |

> 本教程以 MySQL 为主要示例，PostgreSQL 差异处会特别标注。Prisma 让你可以轻松切换两种数据库——改一行 datasource provider 即可。
