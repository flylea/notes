## 二、事实性错误（按严重度）

### 1. `book/ch-03-请求链路/03.01-Nest和Express的关系，如何切到fastify.md:155`（P0，会误导）

原文：「`app.use()` 是 Express 的方法，Fastify 实例上根本没有。」

**半错**。裸 Fastify 实例确实没有 `.use`，但**Nest 的 Fastify 适配器支持 `app.use()`**：

- `@nestjs/platform-fastify@12.6.0` 源码 `adapters/fastify-adapter.js:1155` 有 `use(...args)` 实现；
- 它依赖 `@fastify/middie`（同文件 :10 `import middie from '@fastify/middie'`），未注册时把中间件排队、`init` 阶段再注册（:1160-1161 注释）；
- `INestApplication` 接口本身声明了 `use()`，所以 `NestFastifyApplication` 上调用 `app.use()` 合法。

建议改为：「裸 Fastify 实例没有 `.use`；Nest 的 Fastify 适配器通过 `@fastify/middie` 支持 `app.use()`，但 **Fastify 插件**必须用 `register()`，两者不能混。」同节 :141 的表述要与这句一起改，否则读者会以为 Nest+Fastify 完全不能用中间件。

### 2. `book/ch-02-核心概念/02.02-全局模块和生命周期.md:78`（P1，已过时）

原文：「同一个模块里，多个 Provider 的钩子调用顺序没有稳定契约。」

Nest 12 迁移指南原文：

> Lifecycle hooks are now called by component hierarchy level. This can change the execution order of hooks such as `onModuleInit`, `onApplicationBootstrap`, and the shutdown hooks when multiple providers or modules depend on one another.

即 v12 起钩子**按组件层级（依赖关系）**排序，已经不是「没有稳定契约」。建议改为：「v12 起按组件层级（被依赖者先）排序；但同级、互不依赖的 Provider 之间仍不应依赖相对顺序。」

### 3. `book/ch-06-PostgreSQL与SQL/06.02-SQL查询语句的所有语法和函数PostgreSQL版.md:100`（P1，方向说反）

原文：「别用 `BETWEEN`，它对 `timestamptz` 是闭区间，最后一毫秒会被算进第二天。」

闭区间是**两端都含**，所以陷阱是：写 `BETWEEN '2026-11-04' AND '2026-11-05'` 会把**次日 00:00:00** 算进来；另外 `timestamptz` 是微秒精度，`<= '23:59:59.999'` 会漏掉 `.999xxx` 的微秒部分。「最后一毫秒算进第二天」既不是闭区间的含义，也不是真实失败模式。建议改为：「`BETWEEN` 两端都含，写 `BETWEEN 当天 AND 次日` 会把次日零点算进来；而且时间戳有微秒精度，用 `23:59:59.999` 会漏微妙 —— 所以统一用左闭右开。」

### 4. `book/ch-05-容器化/05.03-Nest项目如何编写Dockerfile.md:38`（P1，基线自相矛盾）

原文：「Nest 12.3.x、Node 22、ESM…」

全书新基线是 **Nest 12.6.x / Node 22·24·26 LTS**（README、STYLE-GUIDE 已同步）。这里是全书唯一一处 `12.3.x`；另 `book/` 下 `node:22` 仍有 **21 处**（05.02 / 05.03 / 05.04 为主）。不算错，但读者对照 README 会困惑，建议统一改 `node:24`（或保留 22 但显式说明「22/24/26 都行，示例固定 24」）。

### 5. `book/ch-10-配置与部署/10.09-基于Redis实现分布式session.md:48`（P1，正文与代码矛盾）

原文：「注意 **ESM 下 `connect-redis` 是默认导出**，`RedisStore` 要解构」——但紧接着的代码是 `import { RedisStore } from 'connect-redis'`（命名导入）。

实测 `connect-redis@11.0.0`：`package.json` 的 `exports` 只有 `import` 条件，`dist/connect-redis.d.ts` 只有 `export declare class RedisStore`，**没有 default export**。代码是对的，散文解释是错的。建议删掉这句，或改为「connect-redis 11 是纯 ESM 包，导出命名类 `RedisStore`」。

## 三、错误引导风险（非错误，但容易带偏）

- **绝对化断言 17 处**（如「根本没有」「绝对不」），这类句子最容易随版本失效，本次已踩中 2 处（03.01、02.02）。
- `07.01`–`07.07` 多节把 `prisma@8.0.0-rc.29 + @prisma/orm-postgres@8.0.0-rc.21` 写成固定组合，而 registry 现状是 rc.34 + rc.24（书里有「必须配对」说明，但没写「这两个版本是 2026-10 的快照，rc 会往前走」）。
- `05.06` 的 PM2 数字（246 次请求 / 72 次被拒 / 1.3s）标注为实测，我复测（pm2 7.1.2、2 实例）：**restart 期间 754 次请求 239 次失败，reload 期间 800 次请求 0 失败**——定性结论成立，数字随机器变化，建议改成「本机测得，换机器数字会变」。

## 八、虚假构造场景

统计（74 节）：

- 首段导入方式：概念直接讲 46、需求式 20、事故/时间线叙事 4、提问 4。
- 角色类场景（老板/运营/同事/客服/值班群）31 次 / 23 节；时间线（凌晨/上线第二天/半夜）25 次 / 21 节；「曾经出现过」1 处（`10.10:182`）。
- 伪统计 3 处：`10.03:447`、`10.04:355`、`10.08:396`（都是 90%/60–80% 这类经验值）。

问题比「没标注」更具体：**有 16 节直接用「真实」二字给场景背书**（「一个真实事故」「三个真实事故」「一次真实的越权」「两个真实场景」），共 **16 处**命中（`真实事故` 13、`真实场景` 2、`真实的越权` 1），分布在 16 节；其中 **11 节用同一句式开场**（「先看一个真实事故。」/「现在看一个真实事故。」），本身就是一种模板化。

| 节 | 措辞 |
| --- | --- |
| `01.03`（:14「## 一个真实事故」） | 凌晨一点，发布流水线停在第十四步 |
| `02.02`、`02.07`（:19）、`02.08`（:19）、`02.09`（:19） | 「先看一个真实事故」 |
| `03.01`、`05.06`、`04.01`、`04.05`、`07.06` | 「真实事故/真实案例」类表述 |
| `06.02`（:32）、`06.09`（:20） | 「现在看一个真实事故」 |
| `06.07`（:3） | 「## 先看两个真实场景」 |
| `09.01`（:171） | 「## 三个真实事故，全在细节上」 |
| `09.04`（:336） | 「## 一次真实的越权：换个 UUID 就读到别人的订单」 |
| `01.06` | 真实场景类表述 |

这些场景读起来是构造的（时间、人物、报错文本都很具体）。「真实」是一个可被证伪的事实主张：如果作者没亲身经历过，用「真实」就是在制造虚假背书，也正好对上你担心的「虚假构造场景」。

建议二选一：

- **方案 A（轻）**：在每章 `_chapter.md` 或第一章加一句总声明——「书中的事故、角色、时间线均为教学假设，用于说明机制，不是真实案例记录」；同时把 3 处最具体的场景首句改成「假设一个场景：」。
- **方案 B（细）**：只给这 3 处加行内标注，其余不动。

另外「实测」与「示例」的边界也要一次说清：真正实测的只有 `05.06`（PM2）、`04.01`（Express+multer）、`04.02`（ConfigService 返回值）、`04.05`（Winston），其余带数字的段落要么是经验值、要么是「预期输出」。
