# 场景改写规则（去虚构化）

适用范围：`book/` 下所有已写小节。目标是把「虚构具体事故」的写法改成「条件 + 机制」的写法，**不减少信息量、不新增编造细节**。

## 一、判定：什么算虚构场景

出现任一即需改写：

1. 具体时间点/时段：`凌晨一点`、`第二天`、`上线第二周`、`上周`、`三个月后`、`那个月`；
2. 具体人物/角色：`值班群`、`客服`、`老板`、`运营`、`同事`、`review 里有人提`、`产品经理`；
3. 声称真实性：`真实事故`、`真实场景`、`真实的越权`、`真实案例`、`某个项目`、`有团队`、`有人把…改成…`；
4. 具体事件链：`发布流水线停在第十四步`、`Pod 全是 Running 却 502`、`注册接口上线三天，运营连点两次`；
5. 无来源的统计：`90% 的问题…`、`60–80% 的带宽…`。

## 二、改写方式（按优先级选一种）

| 原写法 | 改写为 | 例 |
| --- | --- | --- |
| 「凌晨一点，流水线断了」 | 「在开发/发布时，如果…就会…」 | 「在发布时，如果镜像里没有 `nest` 命令，启动会直接报 `sh: nest: not found`」 |
| 「运营要求加一列」 | 「一个常见需求是…」 | 「一个常见需求是给列表加『当前占用』列，这会引出循环依赖」 |
| 「上线第二周数据库连接被打满」 | 「连接池默认值 × 实例数，会把 `max_connections` 吃满」 | 直接给算式和后果 |
| 「值班群弹出一条消息」 | 删掉消息，直接给现象 | 「同一请求出现三条日志，说明中间件挂了两遍」 |
| 「某个项目把密钥写进仓库」 | 「一种常见错误是把密钥写进 compose 文件」 | 保留修复动作 |
| 「真实事故」「真实场景」 | 「典型故障」「常见问题」「一类问题」 | 标题与正文都要改 |

**禁止**：不要写「假设一个场景」「我们虚构一个案例」——这是自曝式补丁，仍显得在编故事。直接陈述机制即可。

## 三、硬约束

- 不新增任何日期、版本号、耗时、百分比、主机名、人名；原有数字要么有来源（npm/源码/官方文档/本机复跑），要么改成定性描述（「明显变慢」）；
- 技术结论、命令、代码块、表格、图**一律保留**；
- 每节正文汉字不得低于改写前（可用 `python3 _meta/audit/style-scan.py <章>` 复核）；
- 只改自己负责范围内的 `.md`，不动 `_meta/`、`README.md`、`_chapter.md`；
- 改完自检：`grep -nE "真实事故|真实场景|真实的越权|凌晨|第二天|值班群|客服转来|上线第" <你的文件>` 应为空（术语性用法如「前台的客服权限」可保留，但要说明是角色权限而非叙事）。

## 四、交付

1. 直接改文件（小步 edit，不整篇重写）；
2. 写 `_meta/audit/scene-rewrite-<你的名字>.md`：文件 → 行号 → 原文片段（≤40 字）→ 改写类型（A 条件式 / B 需求式 / C 现象式 / D 删除真实性声明）；
3. 给 Lead 一份 ≤20 行摘要：改了几节、每类几条、有无新增数字。
