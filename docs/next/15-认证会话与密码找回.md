# 第 15 章 认证、会话与密码找回

这一章讲登录之后发生的事情。用户提交邮箱和密码，验证通过，然后呢？这个“然后”就是会话。会话决定了服务器如何在一串无状态的 HTTP 请求里认出同一个人，决定了凭证存在哪里、什么时候过期、怎么作废。

涉及四个概念。认证是确认“你是谁”，会话管理是让服务器记住这个确认结果，授权是判断“你能做什么”，密码找回是凭证丢失后的恢复路径。四个概念经常被混成一件事，混起来之后写出的代码通常有两个后果：退出之后旧凭证还能用，密码改了别的设备还登录着。

这一章按四层展开。第一层是凭证本身，选无状态 token 还是数据库会话；第二层是凭证放在哪，也就是 cookie 的属性；第三层是服务端怎么验，`getClaims()` 和 `getSession()` 的区别；第四层是凭证的生命周期，验证邮箱、续期、退出、找回密码。每一层都有明确的失败模式，最后一节逐条列出。

先给结论。项目用 Supabase Auth 作为认证服务，会话凭证是 JWT，放在 httpOnly cookie 里，cookie 名是 `sb-<ref>-auth-token`。服务端鉴权一律用 `getClaims()`，不用 `getSession()`。退出登录时想清楚作用域，默认的 `global` 会把所有设备踢下线。

## 15.1 认证、会话管理、授权

认证（authentication）回答“你是谁”。邮箱加密码、第三方登录、一次性验证码，都是认证手段。认证的结果是一个身份主张：这次请求来自用户 `8f3a1c2e`。

会话管理（session management）回答“服务器怎么记住这个身份主张”。HTTP 是无状态的，每个请求都独立。要在第二个请求里认出同一个人，就得有一份凭证在客户端和服务端之间传递。

授权（authorization）回答“这个身份能做什么”。看哪个团队的数据、能不能改账单、能不能邀请成员。授权发生在认证之后，输入是身份，输出是权限判断。

三者混写的典型症状是：把授权判断塞进登录逻辑，把会话数据当成权限来源，把 cookie 里的用户 id 直接当作可信输入。第 17 章会用行级安全把第三层接到数据库上，这一章只管前两层。

## 15.2 会话数据的两种存放方式

会话凭证放在 cookie 里，cookie 里放什么有两类做法。

无状态（stateless）：cookie 里放一段签名过的 JSON，用户 id、过期时间、角色都写在里面。服务端每次请求验签，不查库。优点是快，一次签名验证在微秒级；缺点是无法撤销，签出去的凭证一直有效到过期。

有状态（database session）：cookie 里放一个随机字符串，服务端拿它去数据库查会话记录。优点是能立刻作废，删掉那行记录，会话当场失效；缺点是每个请求多一次查询。

下面的代码是手写 JWT 方案的核心，用 `jose` 库，二十行能跑。写它是为了看清无状态会话的边界，项目里不会这么用。

```bash
pnpm add jose
```

```ts
// src/lib/session/jwt.ts
import { SignJWT, jwtVerify } from 'jose'

const secret = new TextEncoder().encode(process.env.SESSION_SECRET!)

export type SessionPayload = {
  userId: string
  email: string
}

export async function signSession(payload: SessionPayload, maxAgeSeconds = 60 * 60 * 24 * 7) {
  return new SignJWT(payload)
    .setProtectedHeader({ alg: 'HS256' })
    .setIssuedAt()
    .setExpirationTime(`${maxAgeSeconds}s`)
    .sign(secret)
}

export async function verifySessionToken(token: string) {
  try {
    const { payload } = await jwtVerify(token, secret, { algorithms: ['HS256'] })
    return payload as SessionPayload & { exp: number; iat: number }
  } catch {
    return null
  }
}
```


注意 `exp` 的写法。JWT 的过期时间是绝对时间戳，单位秒。签出去之后无法修改，也无法提前吊销。要让某个 token 失效，只能换签名密钥，而那会把所有用户的 token 都废掉。

有状态的方案多一张表，多一次查询，换来撤销能力。表结构至少要有会话 id、用户 id、过期时间，以及一个能定位设备的字段。

```sql
-- 会话表
create table sessions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users (id) on delete cascade,
  token_hash text not null unique,
  expires_at timestamptz not null,
  last_used_at timestamptz not null default now(),
  ip text,
  user_agent text,
  revoked_at timestamptz
);
create index sessions_user_id_idx on sessions (user_id);
```

```ts
// src/lib/session/db-session.ts
import { createHash, randomBytes } from 'node:crypto'
import { db } from '@/lib/db'

const SESSION_DAYS = 30

function hash(token: string) {
  return createHash('sha256').update(token).digest('hex')
}

export async function createSession(userId: string, meta: { ip?: string; userAgent?: string }) {
  const token = randomBytes(32).toString('base64url')
  const expiresAt = new Date(Date.now() + SESSION_DAYS * 86400_000)
  await db.insertInto('sessions').values({
    user_id: userId,
    token_hash: hash(token),
    expires_at: expiresAt,
    ip: meta.ip,
    user_agent: meta.userAgent,
  })
  return { token, expiresAt }
}

export async function readSession(token: string) {
  const rows = await db
    .selectFrom('sessions')
    .selectAll()
    .where('token_hash', '=', hash(token))
    .where('revoked_at', 'is', null)
    .where('expires_at', '>', new Date())
    .executeTakeFirst()
  if (!rows) return null
  return { userId: rows.user_id, sessionId: rows.id }
}
```


两种方案没有优劣，只有取舍。判断标准是两个问题：第一，用户退出之后，旧凭证还能用多久，业务能接受吗？第二，每个请求多一次查询，在现有 QPS 下扛得住吗？

teamstack 用的是第三条路。Supabase 的 JWT 是无状态的，但它额外维护了一份 refresh token 记录。`signOut({ scope: 'global' })` 删掉这条记录，下一次刷新就失败。所以“踢下线”的窗口等于 access token 的剩余寿命，默认一小时。想缩短，就调短 access token 的有效期。

## 15.3 cookie 的五个属性

凭证最终通过 `Set-Cookie` 响应头写到浏览器。这个头有五个属性，每一个都在防一类攻击，漏掉哪个都有对应的失效场景。

`HttpOnly` 让 JavaScript 读不到 cookie。少了它，页面里任何一段注入的脚本都能用 `document.cookie` 把凭证发到外站。XSS 从“页面被篡改”升级成“账号被接管”。

`Secure` 让 cookie 只在 HTTPS 连接中发送。少了它，用户在公共 WiFi 下的一次登录，凭证就会明文经过网络。

`SameSite` 控制跨站请求是否带 cookie。`lax` 是默认值，允许顶级导航带 cookie，阻止跨站的 POST 与 iframe 请求。`strict` 更严，从外站点链接进来也不带。`none` 必须配合 `Secure`，用于确实需要跨站的场景。

`Max-Age` 或 `Expires` 决定凭证寿命。不写就是会话 cookie，关掉浏览器就没了，用户每次都要重新登录。

`Path` 限定 cookie 的作用路径。一般写 `/`，写成 `/admin` 会导致其它路径拿不到。

```ts
// src/lib/supabase/server.ts（cookie 选项片段）
const cookieOptions = {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "lax" as const,
  path: "/",
  maxAge: 60 * 60 * 24 * 7,
};
```

`secure` 在本地开发时要关掉。`http://localhost` 属于非安全上下文，带 `Secure` 的 cookie 不会被浏览器保存。这就是很多人在本地登录不上、部署后正常的原因。

## 15.4 客户端与密钥的四种角色

Supabase 项目里有四份配置，权限边界各不相同，混用是安全事故的常见来源。

`NEXT_PUBLIC_SUPABASE_URL` 是项目地址，公开的。

`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` 是匿名密钥，会进入浏览器产物。它的权限由行级安全约束。开了 RLS，它只能读该读的行；没开 RLS，它等于数据库的万能钥匙。第 17 章整章讲这件事。

`SUPABASE_SECRET_KEY` 是管理员密钥，绕过所有 RLS。它只能出现在服务端，变量名里绝不能有 `NEXT_PUBLIC_` 前缀。

`NEXT_PUBLIC_SITE_URL` 用来拼邮件里的链接和 OAuth 回调地址。配错不会泄密，但会让用户点开 404。

三个客户端对象分别对应三种运行环境，职责不要交叉。

浏览器端只做登录、退出、刷新这类会话操作。它导出同步的 `createClient()`，内部用 `createBrowserClient`。

```ts
// src/lib/supabase/client.ts
import { createBrowserClient } from '@supabase/ssr'

export function createClient() {
  return createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
  )
}
```


服务端组件和 Server Action 里用异步的 `createClient()`，内部 `await cookies()`，每个请求创建一个实例。这是 `@supabase/ssr` 0.12 的用法，别在模块顶层创建，那样会把上一个请求的 cookie 带到下一个请求。

```ts
// src/lib/supabase/server.ts
import { cookies } from 'next/headers'
import { createServerClient } from '@supabase/ssr'

export async function createClient() {
  const cookieStore = await cookies()

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll()
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) => {
              cookieStore.set(name, value, options)
            })
          } catch {
            // 在 Server Component 里调用时不能写 cookie，
            // 真正的写入由 proxy.ts 负责，这里吞掉即可
          }
        },
      },
    },
  )
}
```


第三个是 proxy 里用的 `updateSession`，它同时负责刷新会话和把新 cookie 写回响应。第 16 章会用这个函数，这一章只讲它为什么必须把 cookie 写到响应对象上，不能写到独立的 cookie store 里。

```ts
// src/lib/supabase/proxy.ts
import { createServerClient } from '@supabase/ssr'
import { NextResponse, type NextRequest } from 'next/server'

export async function updateSession(request: NextRequest) {
  let response = NextResponse.next({ request })

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        getAll: () => request.cookies.getAll(),
        setAll: (cookiesToSet) => {
          cookiesToSet.forEach(({ name, value }) => request.cookies.set(name, value))
          response = NextResponse.next({ request })
          cookiesToSet.forEach(({ name, value, options }) => {
            response.cookies.set(name, value, options)
          })
        },
      },
    },
  )

  // 不要在这两个调用之间插入其它逻辑，
  // 否则可能拿到已经过期的身份
  const { data } = await supabase.auth.getClaims()

  const user = data?.claims
    ? { id: data.claims.sub as string, email: (data.claims.email as string) ?? '' }
    : null

  return { response, user }
}
```


## 15.5 getSession 与 getClaims

三个 API 名字相近，安全性差一个量级。

`getSession()` 从 cookie 里解码出 session 对象，不验证签名。它相信 cookie 里写的内容。拿它做服务端鉴权，等于让用户自己声明身份。

`getClaims()` 验证 JWT 签名和过期时间，返回 claims。签名验证用 JWKS，公钥会缓存，所以它比每次请求打 Auth 服务快得多。

`getUser()` 会请求 Auth 服务，确认用户存在、没被封禁。最准，也最慢。

```ts
// 错误：把解码结果当成身份
const { data } = await supabase.auth.getSession();
const userId = data.session?.user.id; // 这里没有任何验证
```

上面这段代码在正常请求里能工作，因为 cookie 是我们自己签的。攻击者手工改一个字符，`getSession()` 依然会解出内容，`getClaims()` 会直接报 `invalid JWT`。

```ts
// 正确：验证签名后再用
const { data, error } = await supabase.auth.getClaims();
if (error || !data?.claims) return null;
const userId = data.claims.sub;
```

`getClaims()` 的返回值是 `{ data: { claims }, error }`。`claims.sub` 是用户 id，`claims.email` 是邮箱，`claims.aal` 是认证等级，`claims.exp` 是过期时间。这些字段来自 JWT，签名验证通过之后可以信任。

对称密钥（HS256）下，`getClaims()` 仍然会请求 Auth 服务验签，因为对称密钥的验证方必须持有同一把密钥。非对称密钥（ES256、RS256）下，本地用 JWKS 验签即可。Supabase 新项目默认用非对称密钥，老项目可能是对称的，性能差别在这里。

## 15.6 服务端鉴权函数

项目里所有服务端取值都走这一层，不要在页面里各写一遍。文件放在 `src/lib/auth.ts`，两个导出函数：`getCurrentUser()` 返回用户或 null，`requireUser()` 返回用户或跳转登录页。

```ts
// src/lib/auth.ts
import 'server-only'

import { cache } from 'react'
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export type CurrentUser = {
  id: string
  email: string
}

/**
 * 读当前用户；未登录返回 null。
 * 用 cache 包住，同一棵 RSC 树里只会真正跑一次。
 */
export const getCurrentUser = cache(async (): Promise<CurrentUser | null> => {
  const supabase = await createClient()
  const { data, error } = await supabase.auth.getClaims()

  if (error || !data?.claims) return null

  return {
    id: data.claims.sub as string,
    email: (data.claims.email as string | undefined) ?? '',
  }
})

/**
 * 需要登录的页面用它；未登录直接跳登录页。
 */
export async function requireUser(): Promise<CurrentUser> {
  const user = await getCurrentUser()
  if (!user) redirect('/login')
  return user
}
```


三个细节。

第一，`import "server-only"` 放在文件顶部。这个包在被客户端组件导入时会让构建失败，等于一个编译期护栏。少了它，某天有人在客户端组件里 import 这个文件，密钥和查询逻辑就进了浏览器产物。

第二，`cache()` 包一层。它让同一次渲染里的多次调用只执行一次，`layout`、`page`、多个组件都调 `requireUser()`，实际只验一次签名。注意 React 的 `cache` 只在一次 render pass 内去重，Server Action 和 Route Handler 不在 render pass 内，包了也每次真跑，这是正常的。

第三，`redirect()` 抛的是特殊异常，不要用 `try/catch` 把它吞掉。要捕获，先判断 `error.digest.startsWith("NEXT_REDIRECT")` 再重新抛出。

## 15.7 滑动续期

JWT 有过期时间。默认一小时。用户在页面上连续操作，一小时后突然被踢到登录页，体验很差。解决办法是滑动续期：每次请求发现 access token 快过期，就用 refresh token 换一个新的，把新 cookie 写回响应。

刷新必须发生在响应生成之前，并且新 cookie 必须写到那个响应上。这就是 `updateSession` 返回 `{ response, user }` 的原因：调用方拿到 response，继续往里写字，新的 cookie 跟着响应一起回去。

```ts
// src/proxy.ts（节选）
import { createServerClient } from '@supabase/ssr'
import { NextResponse, type NextRequest } from 'next/server'

export async function proxy(request: NextRequest) {
  let response = NextResponse.next({ request })

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll()
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value }) => request.cookies.set(name, value))
          response = NextResponse.next({ request })
          cookiesToSet.forEach(({ name, value, options }) => {
            response.cookies.set(name, value, options)
          })
        },
      },
    },
  )

  await supabase.auth.getClaims() // 关键：这一步会顺手续期
  return response
}
```


`setAll` 是 `@supabase/ssr` 提供的回调，刷新后会调用它，参数是新的 cookie 列表。要遍历写回，一漏就出现“刷新成功但下次请求还是旧 token”的现象。

这里还有一个容易忽略的顺序：在 proxy 里重定向时，要把 `response` 上的 cookie 复制到重定向响应上。否则用户登录成功的那一次跳转会把新 token 丢掉，下一个请求又变成未登录。

```ts
// src/lib/supabase/proxy.ts（重定向时带上新 cookie）
if (needsRedirect) {
  const url = request.nextUrl.clone();
  url.pathname = "/login";
  const redirect = NextResponse.redirect(url);
  response.cookies.getAll().forEach((c) => redirect.cookies.set(c));
  return { response: redirect, user: null };
}
```

## 15.8 路由层的乐观检查

proxy 里能读到 cookie，也能验签，所以可以做一个便宜的判断：有没有会话。这个判断只用来决定“要不要把人送到登录页”，不承担授权职责。

理由有三条。proxy 在每个请求上执行，包括预取请求，这里查库会让页面导航变慢。proxy 拿不到完整的团队上下文，判断不了“这个人能不能看这个团队”。Server Action 是 POST 到页面路由，proxy 的 matcher 覆盖不到每一个 action 的调用点。

这些内容第 16 章展开。这里只强调一句：proxy 做粗筛，页面和数据层做真正的判断。

## 15.9 邮箱验证

注册之后要验证邮箱，否则用户可以随便填一个地址。Supabase 的流程是：注册时发一封带 `token_hash` 的邮件，用户点链接回到你的站点，站点用这个 token 换会话。

发送端在注册 action 里，`signUp` 时传 `emailRedirectTo`。

```ts
// src/app/(auth)/signup/actions.ts
'use server'

import { redirect } from 'next/navigation'
import { headers } from 'next/headers'
import { createClient } from '@/lib/supabase/server'

export async function signUp(formData: FormData) {
  const email = String(formData.get('email'))
  const password = String(formData.get('password'))
  const origin = (await headers()).get('origin')!

  const supabase = await createClient()
  const { error } = await supabase.auth.signUp({
    email,
    password,
    options: {
      emailRedirectTo: `${origin}/auth/confirm?next=/dashboard`,
    },
  })

  if (error) {
    redirect(`/signup?error=${encodeURIComponent(error.message)}`)
  }
  redirect('/signup/check-email')
}
```


接收端是一个 Route Handler，路径写在 `emailRedirectTo` 里。这里用 `token_hash`。邮件链接可能被扫描器提前打开，`token_hash` 的校验发生在服务端，不消耗一次性的 PKCE code。

```ts
// src/app/auth/confirm/route.ts
import { type EmailOtpType } from '@supabase/supabase-js'
import { redirect } from 'next/navigation'
import { type NextRequest } from 'next/server'
import { createClient } from '@/lib/supabase/server'

export async function GET(request: NextRequest) {
  const { searchParams } = new URL(request.url)
  const token_hash = searchParams.get('token_hash')
  const type = searchParams.get('type') as EmailOtpType | null
  const next = searchParams.get('next') ?? '/dashboard'

  // 只允许站内相对路径，防止被拿来做开放重定向
  const safeNext = next.startsWith('/') && !next.startsWith('//') ? next : '/dashboard'

  if (token_hash && type) {
    const supabase = await createClient()
    const { error } = await supabase.auth.verifyOtp({ type, token_hash })
    if (!error) {
      redirect(safeNext)
    }
  }

  redirect('/login?error=link_invalid')
}
```


`verifyOtp({ token_hash, type: 'email' })` 成功后返回 session，`setAll` 会把 cookie 写进响应。之后 `redirect` 到目标页。失败时不要直接抛错给用户看，统一跳到 `/login?error=confirm`。

三个边界。第一，`token_hash` 是一次性的，用过就失效，用户重复点链接会报错，这是预期行为。第二，链接有效期默认 24 小时，超时后要重新发。第三，`emailRedirectTo` 的域名必须在 Supabase 的 Redirect URLs 白名单里，不在白名单里会被静默改成 Site URL，表现为“点链接回到首页但没登录”。

## 15.10 退出与会话作用域

`signOut()` 的默认行为是退出所有设备。这是 Supabase 的设计：不传 scope 时按 `global` 处理。

```ts
// 三种作用域
await supabase.auth.signOut()                       // global，所有设备
await supabase.auth.signOut({ scope: "local" })     // 只退当前设备
await supabase.auth.signOut({ scope: "others" })    // 踢其它设备，保留当前
```

只想退当前设备，必须显式写 `{ scope: 'local' }`。这个坑很常见：测试时发现“点退出之后手机也被踢了”，原因就是没写 scope。

退出必须用 POST。用 GET 的话，一个 `<img src="/logout">` 就能让用户被动退出，这是 CSRF。

```ts
// src/app/(auth)/logout/actions.ts
'use server'

import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

// 顶部头像菜单的「退出登录」：只退这一台
export async function logoutCurrent() {
  const supabase = await createClient()
  await supabase.auth.signOut({ scope: 'local' })
  redirect('/login')
}

// 安全设置页的「退出所有设备」：全退
export async function logoutEverywhere() {
  const supabase = await createClient()
  await supabase.auth.signOut({ scope: 'global' })
  redirect('/login?reason=signed_out_everywhere')
}

// 安全设置页的「退出其它设备」：保留当前
export async function logoutOthers() {
  const supabase = await createClient()
  await supabase.auth.signOut({ scope: 'others' })
  redirect('/settings/security?revoked=1')
}
```

```ts
// src/app/api/logout/route.ts
import { NextResponse } from 'next/server'
import { createClient } from '@/lib/supabase/server'

export async function POST(request: Request) {
  const supabase = await createClient()
  await supabase.auth.signOut({ scope: 'local' })

  const response = NextResponse.redirect(new URL('/login', request.url), 303)
  response.headers.set('Cache-Control', 'no-store, max-age=0')
  return response
}
```


`local` 只删当前设备的 refresh token 记录，access token 在过期前仍然有效。也就是说，退出之后，如果攻击者已经拿到了 access token，他还能用最多一小时。这是无状态 token 的固有代价，接受它，或者把有效期调短。

## 15.11 退出全部设备

账户安全页需要一个“退出所有设备”的按钮。实现是 `signOut({ scope: 'global' })`，它删掉该用户所有 refresh token 记录。

注意两件事。第一，这个操作会把当前设备也踢下线，前端要处理跳转。第二，如果用户有多个标签页，其它标签页在下一次请求时才会发现会话失效。

JWT 无法提前吊销，这一小时的窗口是设计使然，靠调短 access token 有效期来缩小。代价是刷新更频繁，每次刷新多一次 Auth 服务请求。

## 15.12 找回密码

找回密码本质是一次凭证重置，流程分两段：请求重置邮件、用邮件里的链接设置新密码。两段都要防滥用。

请求段只做一件事：给邮箱发链接，无论邮箱是否存在都返回同样的结果。这一点必须做到，否则接口变成账号枚举工具。

```ts
// src/app/(auth)/forgot-password/actions.ts
'use server'

import { headers } from 'next/headers'
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export async function requestPasswordReset(formData: FormData) {
  const email = String(formData.get('email'))
  const origin = (await headers()).get('origin')!
  const supabase = await createClient()

  await supabase.auth.resetPasswordForEmail(email, {
    redirectTo: `${origin}/auth/confirm?next=/reset-password&type=recovery`,
  })

  // 无论邮箱存不存在，都返回同一句提示
  redirect('/forgot-password?sent=1')
}
```


链接里带 `token_hash`，`redirectTo` 指向站点的重置页并且带上 `next` 参数。用户的邮箱不存在时，Supabase 不报错，直接返回成功。界面上也显示“已发送”，不要提示“该邮箱未注册”。

设置新密码的 action 要重新读一次会话。`updateUser({ password })` 需要当前会话，而邮件链接换来的会话是临时的一次性会话。

```ts
// src/app/reset-password/actions.ts
'use server'

import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export async function updatePassword(formData: FormData) {
  const password = String(formData.get('password'))
  const confirm = String(formData.get('confirm'))

  if (password.length < 12) {
    redirect('/reset-password?error=too_short')
  }
  if (password !== confirm) {
    redirect('/reset-password?error=mismatch')
  }

  const supabase = await createClient()

  // 必须确认：能走到这里，说明已经通过邮件链接建立了会话
  const { data, error: claimsError } = await supabase.auth.getClaims()
  if (claimsError || !data) {
    redirect('/login?error=session_expired')
  }

  const { error } = await supabase.auth.updateUser({ password })
  if (error) {
    redirect(`/reset-password?error=${encodeURIComponent(error.message)}`)
  }

  // 密码换了，旧设备全部下线
  await supabase.auth.signOut({ scope: 'others' })
  redirect('/login?reset=1')
}
```


改完密码之后，有两个选择：把其它设备踢下线，或者保持。安全默认是踢掉，用 `signOut({ scope: 'others' })`。

还有一条容易被忽略：重置成功后，旧密码不应再能登录，但已有的 refresh token 仍然有效。想彻底断掉，改密码之后调 `signOut({ scope: 'global' })`，让用户重新登录。

## 15.13 改密码与改邮箱

登录状态下的敏感操作，第一步都是确认是本人。确认方式是让用户重新输入当前密码，然后调 `reauthenticate()` 或者用当前密码走一次 `signInWithPassword`。

```ts
// src/app/settings/security/actions.ts
'use server'

import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'
import { requireUser } from '@/lib/auth'

export async function changePassword(formData: FormData) {
  const user = await requireUser()
  const current = String(formData.get('current'))
  const next = String(formData.get('next'))

  if (next.length < 12) redirect('/settings/security?error=too_short')

  const supabase = await createClient()

  // 1. 用旧密码重新登录一次，失败说明身份不符
  const { error: reauthError } = await supabase.auth.signInWithPassword({
    email: user.email,
    password: current,
  })
  if (reauthError) redirect('/settings/security?error=wrong_password')

  // 2. 改密码
  const { error } = await supabase.auth.updateUser({ password: next })
  if (error) redirect('/settings/security?error=update_failed')

  // 3. 其它设备下线
  await supabase.auth.signOut({ scope: 'others' })
  redirect('/settings/security?changed=password')
}
```

```ts
// src/app/settings/security/actions.ts（续）
await supabase.from('activity_logs').insert({
  team_id: null,
  actor_id: user.id,
  action: 'user.password_changed',
  target_type: 'user',
  target_id: user.id,
  metadata: {},
})
```


改邮箱更麻烦，因为它涉及两段验证：旧邮箱收一封确认信，新邮箱再收一封。Supabase 的 `updateUser({ email })` 会触发这两封信，两边都确认之后才生效。中间状态是 `email_change` 字段，不要自己写。

## 15.14 邮件为什么发不出去

邮件投递失败有四个常见原因，按排查顺序排列。

Spam 判定。用 Resend、Postmark 这类服务，域名要做 SPF、DKIM、DMARC。少一条都会进垃圾箱，用户说“没收到”时先查这里。

重定向白名单。Supabase 的 Redirect URLs 里没有你的域名，链接会被改成 Site URL，用户点开落在首页。

频率限制。Supabase 免费档对邮件发送有速率限制，短时间大量发送会被拒。批量邀请要排进队列，第 18 章会用到。

本地开发。`localhost` 无法接收外部邮件，测试时用 Supabase 的 Inbucket（`http://localhost:54324`）或者直接把链接从日志里复制出来。

## 15.15 Cache Components 下读会话

开启 `cacheComponents: true` 之后，页面默认走“静态外壳 + 流式填充”。读会话属于请求时行为，不能出现在静态部分，否则构建失败。

错误长这样：

```
Error: Route "/dashboard" used `cookies().getAll()` outside of a Suspense boundary.
```


写法是把读会话的组件下沉，用 `<Suspense>` 包住。

```tsx
// src/app/(app)/dashboard/page.tsx
import { requireUser } from '@/lib/auth'
import { createClient } from '@/lib/supabase/server'

export default async function DashboardPage() {
  const user = await requireUser()
  const supabase = await createClient()

  const { data: memberships } = await supabase
    .from('team_members')
    .select('team_id, role, teams(name, slug, plan)')
    .eq('user_id', user.id)

  return (
    <section>
      <h1>欢迎回来，{user.email}</h1>
      {memberships?.length ? (
        <ul>
          {memberships.map((m) => (
            <li key={m.team_id}>
              {m.teams?.name} · {m.role}
            </li>
          ))}
        </ul>
      ) : (
        <p>你还没有加入任何团队。</p>
      )}
    </section>
  )
}
```


`<Suspense>` 的 fallback 是静态的，先发出去；`UserMenu` 在服务端读 cookie，流式补进来。布局层保持静态，页面外壳可以被 CDN 缓存。

如果整个页面都需要会话，另一个选择是 `'use cache: private'`。它的结果只存在浏览器里，不跨用户共享，所以可以读 cookie。

```ts
// src/lib/viewer.ts
import { cacheLife } from 'next/cache'
import { createClient } from '@/lib/supabase/server'

export async function getViewer() {
  'use cache: private'
  cacheLife('minutes')

  const supabase = await createClient()
  const { data } = await supabase.auth.getClaims()
  if (!data) return null

  const { data: profile } = await supabase
    .from('profiles')
    .select('id, email, full_name, avatar_url')
    .eq('id', data.claims.sub)
    .single()

  return profile
}
```


`cacheComponents` 的配置：

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  experimental: {
    partialPrefetching: true,
  },
}

export default nextConfig
```


`instant = false` 是一个逃生口。有些页面改造成本太高，先关掉 instant navigation 校验，让构建通过，之后再改。

还有一处容易踩：布局顶层直接 `await` 会话，会把布局和它下面的所有子页面挡在请求之后，等于整段变成动态。会话只在用户菜单里用到时，把 `await` 下沉到菜单组件。

## 15.16 反向代理后的三处失效

自托管时应用跑在 Nginx 或 Caddy 后面，三处会坏。

第一，`request.url` 里的 host 变成内网地址，拼出来的回调地址是 `http://0.0.0.0:3000`。要读 `x-forwarded-host` 和 `x-forwarded-proto`，或者统一用环境变量拼站点地址。

```ts
// src/lib/site-url.ts
export function siteUrl() {
  if (process.env.NEXT_PUBLIC_SITE_URL) return process.env.NEXT_PUBLIC_SITE_URL
  if (process.env.VERCEL_URL) return `https://${process.env.VERCEL_URL}`
  return 'http://localhost:3000'
}
```


第二，`Secure` cookie 依赖协议判断。代理终止了 TLS，应用看到的是 HTTP，如果不信任 `x-forwarded-proto`，cookie 就不会带 `Secure`，或者反过来在本地被拒绝。

第三，cookie 的 `Domain` 属性。主域和子域共享会话时，要显式设置 `Domain=.example.com`，否则 `app.example.com` 和 `api.example.com` 各有一套会话。

## 15.17 登录表单的几个细节

登录表单本身没有技术含量，但几个细节影响体验和安全。

提交按钮在请求期间要禁用，防止重复提交。用 `useFormStatus` 或 `useTransition`。

错误提示统一。邮箱不存在和密码错误返回同一句话“邮箱或密码不正确”，避免账号枚举。

`next` 参数要校验。登录后跳回原页面，这个参数是用户可控的，必须只允许站内路径。

```ts
// src/lib/safe-redirect.ts
export function safeNext(raw: string | null | undefined, fallback = '/dashboard') {
  if (!raw) return fallback
  // 必须是以 / 开头的相对路径，且排除 //evil.com 和 /\evil.com
  if (!raw.startsWith('/') || raw.startsWith('//') || raw.startsWith('/\\')) return fallback
  return raw
}
```


密码框加 `autoComplete="current-password"`，注册加 `"new-password"`。这一项必须加，密码管理器靠这两个值决定要不要填充。

## 15.18 会话凭证的三种攻击面

凭证放在浏览器里，就要面对三种攻击。每种攻击的防线不同，混在一起谈会漏。

第一种是读取。攻击者想办法读到 cookie 的值，之后拿着它冒充用户。防线是 `HttpOnly`，再加 CSP 限制页面能执行的脚本。`HttpOnly` 让 `document.cookie` 读不到，CSP 让注入的脚本执行不了。两条同时有效，漏一条都能被绕过。

第二种是借用。攻击者读不到 cookie，但可以让受害者的浏览器带着 cookie 发请求。防线是 `SameSite` 和 CSRF token。`SameSite=lax` 挡住跨站的 POST，CSRF token 挡住同站内的伪造请求。

第三种是重放。攻击者截获一个请求，原样再发一次。防线是一次性 token 和幂等设计。邀请链接、找回密码链接都是一次性的，用第二次就失败。

三种攻击的共同点是：凭证一旦离开服务端，就不再完全受控。缩短有效期只能算最后一道保险。前两道防线是 `HttpOnly` 和 `SameSite`。

## 15.19 token 有效期定多长

access token 的有效期是一个权衡，两端都有代价。

有效期长，用户不容易被踢，服务端不用频繁刷新。代价是凭证泄漏之后可利用的时间也长，退出之后旧 token 还在飘。

有效期短，泄漏窗口小，退出更彻底。代价是刷新更频繁，每次刷新多一次 Auth 服务请求，多一次写 cookie。

Supabase 默认一小时。这个值在多数产品里合适：用户一次会话通常不超过一小时，刷新成本可以接受。

需要更短的时候：后台管理、财务操作、能导出大量数据的页面。做法是这些路由额外要求一次 `getUser()` 确认，或者要求 AAL2（第 20 章）。

需要更长的时候：移动端、低频使用的工具。做法是加长 refresh token 的寿命，access token 仍然短。

不要做的事：把 access token 设成 30 天。那等于放弃撤销能力。

## 15.20 密码怎么存

Supabase Auth 内部用 bcrypt 存密码，应用层看不到哈希，也不需要自己校验。这一节说的是原理和边界。

密码哈希有三个要求：慢、加盐、不可逆。慢是为了让暴力破解成本高，加盐是为了让相同的密码得到不同的哈希，不可逆是基本要求。

bcrypt 的代价因子默认 10，一次哈希约 50–100 毫秒。argon2id 更现代，内存开销更大，抗 GPU 破解更强。两者都可以用，不要用 MD5、SHA-1、SHA-256 直接哈希密码，那些太快了。

不要自己写密码校验。常见错误有三处：用 `===` 比较哈希（时序攻击）、把盐存在密码字段旁边却没有版本号、升级哈希算法时无法平滑迁移。

如果确实要自己实现（比如对接遗留系统），存一个 `password_hash` 字段，格式带算法前缀，例如 `$argon2id$v=19$m=65536,t=3,p=4$...`。登录时按前缀选算法，验证成功后如果算法过期，顺手升级一次。

## 15.21 注册流程的四条规则

注册比登录更容易出错，因为它要处理“账号已存在”这个分支。

第一条，注册接口不透露邮箱是否已注册。已注册时要么发一封“有人尝试用你的邮箱注册”的提示信，要么什么都不做，接口返回成功。

第二条，先写库再发信。用户记录创建失败时不要发信，否则用户点开链接找不到账号。

第三条，邮箱未验证的账号不能进后台。用一个中间状态标记，登录成功后检查，未验证就跳到验证页。

第四条，注册要限流。同一 IP、同一邮箱都有次数上限，否则接口变成短信/邮件轰炸器。第 20 章会给具体实现。

## 15.22 会话与审计日志

会话的变化要留痕，出问题时才有据可查。

值得记录的四个事件：登录成功、登录失败、退出、密码修改。每条记录包含用户 id、时间、IP、User-Agent、结果。

登录失败也要记。连续失败是撞库的信号，第 20 章的限流会用到这个数据。

审计写入失败时不要让登录失败。日志是辅助，登录是主流程。写日志的代码用 `try/catch` 包住，失败只打一条 `console.error`。

## 15.23 测试登录流程

三条命令足够验证主链路。**未验证**：这些命令依赖本地 Supabase 实例，命令本身没有在写作环境里执行。

```bash
# 1. 登录，拿到 cookie
curl -i -X POST http://localhost:3000/api/login \
  -H 'content-type: application/json' \
  -d '{"email":"lin@example.com","password":"correct-horse"}'
```

## 15.24 这一章与第 16、17 章的分工

三章都在讲权限，边界要分清。

这一章回答“你是谁”，产出是一个可信的 `user` 对象。它不判断“你能看哪个团队”。

第 16 章回答“请求要不要放进来”，产出是一个重定向或放行。proxy 做粗筛，不做授权。

第 17 章回答“你能看数据库里的哪些行”，产出是 RLS policy。它兜住所有绕过应用层的访问。

三层的关系是漏斗：proxy 挡掉未登录的陌生人，页面和数据函数挡掉不属于这个团队的已登录用户，RLS 挡掉所有直接打数据库的请求。任何一层缺失，另外两层都不能完全替代它。

## 15.25 三种登录方式，共用一条会话

密码登录、第三方登录、邮件魔法链接，三种方式生成的会话是同一个东西：一双 access token 与 refresh token，写进同名 cookie。

差别在认证那一步。密码登录校验密码哈希，第三方登录换 OAuth code，魔法链接校验 `token_hash`。认证通过之后，都走 `signInWith*` 的收尾逻辑，返回同样的 session。

理解这一点有实际用处。给产品加一种登录方式，不需要动会话层；给会话加一条规则（比如要求 AAL2），三种登录方式自动生效。

也有例外。OAuth 登录的 provider token 是另一套凭证，用来调 GitHub API，与你的会话无关。它存在 `provider_token` 字段里，不要拿它当登录凭证，也不要用它判断身份。

## 15.26 会话失效的排查顺序

用户反馈“莫名被踢”，按四步排查，命中率从高到低。

第一步看 cookie。DevTools 的 Application → Cookies 里有没有 `sb-<ref>-auth-token`，过期时间对不对。没有就是没写进去，或者是浏览器的隐私设置拦了。

第二步看响应头。登录请求的响应里有没有 `set-cookie`，`Path` 和 `Domain` 对不对。`Path=/admin` 的 cookie 在其它路径下读不到。

第三步看服务端日志。`getClaims()` 返回的错误是 `invalid JWT`（签名不对或过期）还是 `no session`（cookie 没带上来）。两者原因完全不同。

第四步看时钟。服务器时间比真实时间快几分钟，会让刚签发的 token 立刻“过期”。容器环境里常见。

## 15.27 cookie 的体积上限

浏览器的单条 cookie 上限是 4 KB，超出会被丢弃，而且是静默丢弃。

Supabase 的 session cookie 里放了 access token 和 refresh token，两者加起来接近 2 KB。用户信息多的时候会更大。

触及上限的表现是“登录成功但立刻退出”。排查时看 cookie 的值长度，超过 4000 字符就要处理。

处理方式有三种。减少写入 cookie 的字段，只存 token 不存完整的 user；把会话拆成多条 cookie；改用服务端会话，cookie 里只放一个 id。

`@supabase/ssr` 已经做了分片，一条 cookie 超过阈值会拆成 `sb-<ref>-auth-token.0`、`.1`。看到这种名字属于正常情况。

## 15.28 首屏的登录态

服务端渲染的首屏要正确反映登录状态，否则会出现“页面先显示未登录，一秒后跳成已登录”。

原因通常是把会话读取放在了客户端。客户端组件在 hydration 之后才知道有没有会话，中间有一帧未登录状态。

正确做法是在服务端读会话，把结果作为 props 传给客户端组件。首屏 HTML 就已经是登录态，没有闪烁。

代价是这一层要动态渲染。整个页面不需要登录态时，把需要的那部分拆成独立组件，用 `<Suspense>` 包住，外层保持静态。

## 15.29 账号锁定与失败计数

连续登录失败要限制，但锁定策略要克制。

按账号锁定会被滥用：攻击者知道你的邮箱，故意输错五次，就能把你锁在外面。

按 IP 锁定也会误伤：公司、学校、运营商 NAT 后的用户共享出口 IP。

可用的折中：同一账号 5 次失败后要求验证码，10 次后进入 15 分钟冷却。同一 IP 每分钟最多 20 次尝试。两个维度同时限制。

失败计数存在 Redis 里，带过期时间，不要写数据库。第 20 章给出实现。

## 15.30 会话层的四个默认值

把这一章的默认值汇总，方便对照自己的实现。

密码哈希用 bcrypt，代价因子 10。access token 有效期 1 小时，refresh token 7 天。cookie 用 `httpOnly`、`secure`（生产）、`sameSite=lax`、`path=/`。服务端鉴权用 `getClaims()`。

四个值都可以调，调之前想清楚代价。每个值对应一类失败模式，改动等于换了一组失败模式。

## 15.31 列出登录的设备

“查看我的登录设备”是一个常见需求，实现难度取决于会话存放在哪。

数据库会话方案里，会话表每行带 device、ip、last_seen，查一次就有列表。删行即踢下线，能做到精确到单台设备。

Supabase 的 JWT 方案没有这个能力。它只知道 refresh token 记录，不对外暴露设备列表。`signOut({ scope: 'others' })` 能踢掉其它设备，但踢不掉指定的某一台。

要这个功能，只能自己维护一张设备表：登录成功时写一行，记录 `user_agent`、ip、refresh token 的哈希；退出时删行；过期清理。踢单台设备的实现是删除对应的 refresh token 记录，Supabase 的 admin API 支持按 session id 删除（**未验证**：该接口在免费档的可用性没有实测）。

## 15.32 验签的成本

`getClaims()` 在非对称密钥下用 JWKS 验签，公钥缓存在内存里。单次开销约 0.1–0.5 毫秒，比查一次数据库便宜一个量级。

对称密钥下每次都要请求 Auth 服务，开销变成一次网络往返，通常 5–20 毫秒。如果项目跑在多个区域，这个成本会放大。

一个页面里可能有五处调用 `requireUser()`。用 `cache()` 包一层之后只验一次，其余拿到缓存值。这是 `src/lib/auth.ts` 里那行 `cache()` 的实际作用。

不要在循环里调用。列表页要给每一行判断权限时，先取一次当前用户，再把用户传进判断函数。

## 15.33 会话的默认安全姿态

最后汇总四条姿态，用来检查现有实现是否“默认安全”。

默认拒绝。取不到会话就当作未登录，不要有“取不到就放行”的分支。

默认短命。有效期选短的那一档，需要长会话时用 refresh token 换。

默认服务端判断。客户端的登录态只用于显示，不用于授权。任何“前端已经判断过了”的地方，服务端都要再判断一次。

默认留痕。登录、退出、改密码、失败尝试都写日志，出问题时才有据可查，复盘也有材料。

## 15.34 会话数据不能进共享缓存

`'use cache'` 缓存的结果会跨用户共享。把按用户不同的数据放进去，第一个人看到的内容会发给所有人。

典型错误是在带 `'use cache'` 的函数里读 `cookies()`。构建期会直接报错，因为缓存函数不允许访问请求 API。运行时如果绕过了，结果是串号。

正确的分工是：会话在缓存函数外面读，把用户 id 当参数传进去。缓存键由参数决定，每个用户一份，互不干扰。

`'use cache: private'` 是例外。它的结果只存在浏览器里，不跨用户共享，可以读 cookie。代价是只在客户端命中，服务端拿不到。

## 15.35 检查点

1. 退出之后，用 DevTools 把旧的 cookie 值写回去，访问 `/dashboard`。在 access token 过期前能进，过期后被踢到登录页。这个窗口的长度等于 token 有效期。
2. 走一遍找回密码。同一封邮件里的链接点第二次，返回 `Email link is invalid or has expired`。
3. 在 `src/lib/auth.ts` 里把 `getClaims()` 换成 `getSession()`，手工改 cookie 里 token 的最后一个字符，`/dashboard` 仍能打开。换回去之后，同样操作跳到登录页。
4. `pnpm build` 通过，`/dashboard` 不在静态路由列表里，或者它的会话读取被 Suspense 包住。
5. 在浏览器里删掉 `sb-<ref>-auth-token`，刷新页面，跳到 `/login?next=/dashboard`。
6. 登录后关掉标签页，重新打开，仍然登录。cookie 的 `maxAge` 生效。

## 15.36 常见错误

1. 在 Server Action 里用 `getSession()` 判断身份

现象：改过的 cookie 也能通过，或者某天发现越权。原因：`getSession()` 只解码不验签。改法：统一用 `getClaims()`，并把取值封装进 `requireUser()`。

2. 退出只删了 cookie，没调 `signOut()`

现象：退出后旧设备还能用，或者重新打开页面又登录了。原因：服务端 refresh token 记录还在，access token 也没过期。改法：调 `signOut({ scope: 'local' })`，需要踢所有设备时用 `global`。

3. `setAll` 里没把 cookie 写到响应

现象：刷新 token 成功但下一次请求还是旧的，反复刷新。原因：`@supabase/ssr` 把新 cookie 交给回调，回调没有写进响应头。改法：`setAll` 里遍历 `cookiesToSet`，逐个 `response.cookies.set`。

4. 本地登录不上，部署后正常

现象：`http://localhost:3000` 登录后立刻跳回登录页。原因：cookie 带了 `Secure`，浏览器拒绝在 HTTP 下保存。改法：`secure: process.env.NODE_ENV === "production"`。

5. 布局里读会话，整页变成动态

现象：构建输出里所有路由都是 `ƒ`，首屏 TTFB 变高。原因：layout 顶层 `await cookies()` 把整段挡在请求后面。改法：把读会话的组件下沉，用 `<Suspense>` 包住。

6. 邮件链接点开跳到首页，没登录

现象：注册确认后回到 `/`，会话是空的。原因：`emailRedirectTo` 的域名不在 Supabase 白名单，被静默改成 Site URL。改法：在 Authentication → URL Configuration 里加上站点地址和通配子域。
