# 第 27 章 定时任务与调度

有些事不该由用户请求触发：回收卡住的任务、把过期的邀请标成 expired、删掉一天前的历史记录、清理存储里没人认领的对象。这些工作没有对应的按钮，只能按时间自己跑。

这类需求有两种实现方式。一种是把任务排进队列，指定未来某个时刻执行，第 26 章的 `jobs` 表就能做。另一种是让一个外部调度器定期调用一个受保护的接口，接口自己判断哪些任务到期了。

这一章选第二种。原因是“错过”这件事必须能被补上：排好的队列任务在进程挂掉后没人重排，而“每次打进来检查到期”的模型里，调度状态由数据库推导，挂一次下次自动补回来。

涉及四个概念：调度入口、执行记录、咨询锁、幂等清理。前置条件是第 26 章的 `/api/cron/jobs` 路由与 `jobs` 表、第 22 章的 `invitations`、第 23 章的文件存储、第 25 章的 `stripe_events`。

## 27.1 调度模型：每次打进来检查到期

调度器的入口是一个受保护的 HTTP 接口，外部每分钟调用一次。每次调用做三件事：消费队列里到期的任务、检查哪些定时任务到期、把到期的逐个执行并记录。

“哪些到期”由上次成功时间推导，不依赖额外的调度状态表。

```ts
// src/lib/cron.ts（片段）
async function lastRuns(): Promise<Map<string, Date>> {
  const { rows } = await sql<{ task: string; last_started: Date | null }>`
    select task, max(started_at) as last_started
    from public.cron_runs
    where status in ('ok', 'failed')
    group by task
  `.execute(db)

  return new Map(rows.filter((r) => r.last_started).map((r) => [r.task, r.last_started!]))
}
```

判断规则很直接：没有记录，或者距离上次执行已经超过任务声明的间隔，就执行。这样不需要维护 `next_run` 字段，也不会因为一次失败导致后续全部错位。

为什么不用队列排未来的任务。可以排，但“错过一次”就永久错过：进程在排好的时刻之前挂了，那条任务还停在 `queued`，`run_at` 已过，理论上会被领取。问题出在“排未来”的写入时机：如果本轮调度挂了，下一轮根本没人排。用“检查到期”的模型，调度器本身是无状态的，状态全在 `cron_runs` 表里。

这个调度模型有代价：最小粒度等于外部调用的频率，任务间隔只能取它的整数倍。外部每分钟打一次，任务的间隔只能是一分钟的整数倍。清理类任务不需要更高精度。

## 27.2 执行记录表

调度最怕的问题是没有报错。cron 表达式配错、环境变量没设、接口返回 401，表现完全一样：什么都没发生。所以每次执行都要落一行。

```sql

  id bigint generated always as identity primary key,
```

四个状态各有含义。`running` 是正在执行，`ok` 是跑完，`failed` 是抛错，`skipped` 是因为别的实例正在跑而跳过。

`skipped` 单独记录，不用直接返回代替，是因为它能反映锁的竞争情况。偶发跳过正常，持续大量跳过说明两个实例在抢同一批任务，或者锁泄漏了。

为什么不复用 `jobs` 表。语义不同。`jobs` 有重试、有租约，失败会重新排队；一次 cron 运行没有“重试”的概念，下一分钟的调用就是重试，它要的是留证。混在一张表里，查的时候要一直区分“这条 running 是队列任务还是 cron 运行”。

`detail` 存每次运行的统计，比如 `{"scanned_objects":1240,"orphan_candidates":3}`。三个月后有人问“这个文件为什么没被清掉”，看这一行就知道当时的判断依据，不用翻日志。

用 jsonb 并非拆成多列，是因为每个任务的字段不同：清理任务写 `scanned_objects`，对账写 `teams_checked`，硬拆会得到一张大部分列永远为空的表。代价是查询要写 `detail->>'orphan_candidates'`，没法给单个字段加约束。排查够用。

运行记录自身也会增长。五分钟一次的任务一天 288 行，四个任务一天接近 300 行，一年十万行。所以保留 90 天，由清理任务自己删自己，保留期也写在同一张表里。

## 27.3 任务注册表与执行器

先让一条链路跑通，再补齐其他任务。任务定义成一个数组，每项有名字、间隔、处理函数。

```ts
// src/lib/cron/tasks.ts
import 'server-only'
import { sql } from 'kysely'
import { db } from '@/lib/db'

export interface CronTaskContext {
  now: Date
}

export type CronTaskResult = Record<string, unknown>

export interface CronTask {
  name: string
  intervalSeconds: number
  handler: (ctx: CronTaskContext) => Promise<CronTaskResult>
}

// run_at 兼作租约：running 且租约过期，说明执行它的进程挂了。
async function recoverStuckJobs(): Promise<CronTaskResult> {
  const result = await sql<{ id: string }>`
    update public.jobs
    set status = 'queued',
        last_error = coalesce(last_error, 'lease expired'),
        run_at = now()
    where status = 'running'
      and run_at < now() - interval '10 minutes'
    returning id::text
  `.execute(db)

  return { recovered: result.rows.length }
}

export const CRON_TASKS: CronTask[] = [
  { name: 'jobs.recover_stuck', intervalSeconds: 5 * 60, handler: recoverStuckJobs },
]
```

执行器负责选任务、执行、写记录。失败也要记录，这是它存在的意义。

```ts
// src/lib/cron.ts
import 'server-only'
import { sql } from 'kysely'
import { db } from '@/lib/db'
import { CRON_TASKS, type CronTask } from '@/lib/cron/tasks'

export interface CronTaskSummary {
  task: string
  status: 'ok' | 'skipped' | 'failed'
  detail?: Record<string, unknown>
  error?: string
}

async function executeTask(task: CronTask): Promise<CronTaskSummary> {
  const inserted = await sql<{ id: string }>`
    insert into public.cron_runs (task, status)
    values (${task.name}, 'running')
    returning id::text
  `.execute(db)
  const runId = inserted.rows[0].id

  try {
    const detail = await task.handler({ now: new Date() })
    await sql`
      update public.cron_runs
      set status = 'ok',
          finished_at = now(),
          duration_ms = (extract(epoch from (now() - started_at)) * 1000)::int,
          detail = ${JSON.stringify(detail ?? {})}::jsonb
      where id = ${runId}::bigint
    `.execute(db)
    return { task: task.name, status: 'ok', detail }
  } catch (error) {
    const message = error instanceof Error ? error.message : String(error)
    await sql`
      update public.cron_runs
      set status = 'failed',
          finished_at = now(),
          duration_ms = (extract(epoch from (now() - started_at)) * 1000)::int,
          error = ${message.slice(0, 2000)}
      where id = ${runId}::bigint
    `.execute(db)
    return { task: task.name, status: 'failed', error: message }
  }
}

export async function runDueTasks(options: {
  now: Date
  only?: string
}): Promise<CronTaskSummary[]> {
  const { now, only } = options
  const since = await lastRuns()
  const due = CRON_TASKS.filter((task) => {
    if (only) return task.name === only
    const last = since.get(task.name)
    return !last || now.getTime() - last.getTime() >= task.intervalSeconds * 1000
  })

  const results: CronTaskSummary[] = []
  for (const task of due) {
    results.push(await executeTask(task))
  }
  return results
}
```

入口复用第 26 章的路由，加一条“跑到期任务”的分支，不新起路由。两条路径各自鉴权、各自记日志，迟早有一边被忘掉。

## 27.4 多实例只执行一次

生产环境里同时触发是常态：自托管三台机器的 crontab 同时响，Vercel 的超时重试也可能再打一次。调度器只保证“大致按点调用”，不保证只调用一次。

两个请求同时跑同一个清理任务，会重复删除、重复统计。业务上不一定出错，但重复执行的次数多了，问题就难查。

用 Redis 做锁是常见选择，`SET key value NX EX 60`。要处理好三件事：锁过期而任务没跑完要续期；续期进程挂了要 fencing token；解锁时可能误删别人的锁。这些都能做，但复杂。Postgres 自带咨询锁，语义正好：锁属于数据库连接，连接断开锁就没了，不需要 TTL。

```ts
// src/lib/cron.ts（追加）
import { pool } from '@/lib/db'

export async function withTaskLock<T>(name: string, fn: () => Promise<T>) {
  const client = await pool.connect()
  try {
    // hashtextextended 是 64 位，碰撞概率远低于 32 位的 hashtext。
    const { rows } = await client.query<{ locked: boolean }>(
      'select pg_try_advisory_lock(hashtextextended($1, 0)) as locked',
      [name],
    )
    if (!rows[0]?.locked) return { acquired: false as const }

    try {
      return { acquired: true as const, value: await fn() }
    } finally {
      // 必须用同一个 client 解锁，换一条连接解的是别人的锁。
      await client.query('select pg_advisory_unlock(hashtextextended($1, 0))', [name])
    }
  } finally {
    client.release()
  }
}
```

执行循环改成先拿锁。

```ts
// src/lib/cron.ts（替换循环体）
for (const task of due) {
  const lock = await withTaskLock(task.name, () => executeTask(task))
  if (!lock.acquired) {
    // 自动触发撞车是常态，记 skipped 会刷屏；手动触发才记一行。
    if (only) await recordSkipped(task.name, 'locked by another instance')
    results.push({ task: task.name, status: 'skipped' })
    continue
  }
  results.push(lock.value)
}
```

三个细节决定这把锁是否有效。

必须从连接池里拿同一个连接加锁和解锁。用两次 `pool.query()`，两次可能落到不同连接上，解锁那条连接上没有这把锁，`pg_advisory_unlock` 返回 `false` 而不报错，锁就永远挂着。这个任务从此每次都 skipped，接口一直返回 200，很难发现。

用会话级 `pg_advisory_lock`，不用事务级 `pg_advisory_xact_lock`。事务级锁在提交时自动释放，看着省事，但一个任务要跨多个独立事务，比如写记录、删数据、调外部接口，事务一提交锁就没了，等于没锁。

锁的粒度是每个任务一把，并非全局一把。清理文件和回收任务互不相干，没理由排队。名字就是锁的键，所以任务重命名等于换锁，发布期间新旧版本并存会各跑一次。

错误写法长这样，问题在第二行。

```ts
// 反例：加锁与解锁拿的并非同一条连接
await pool.query('select pg_advisory_lock(hashtextextended($1, 0))', [task.name])
try {
  await runTask()
} finally {
  await pool.query('select pg_advisory_unlock(hashtextextended($1, 0))', [task.name])
}
```

确认是否泄漏，直接查锁表。

```sql
select l.objid, l.pid, a.state, a.query
from pg_locks l
join pg_stat_activity a using (pid)
where l.locktype = 'advisory';
```

正常情况下，任务结束后这张表里不该有你的咨询锁。每次 tick 后都留着一行就是泄漏。清掉它的唯一办法是断开那条连接，重启进程或 `pg_terminate_backend`。

进程崩溃时锁自动释放，因为连接断了。但 `cron_runs` 里那行 `running` 不会自己变，下一节处理。

## 27.5 失败与残留

handler 抛错时，执行器把记录改成 `failed`，写入 `error` 和 `duration_ms`。下一次调用时，因为上次状态是 `failed`，`lastRuns` 认为它“跑过”，会等一个完整间隔再重试。这样避免一个持续失败的任务每分钟重试一次，把记录刷满。

失败后立即重试没有必要。定时任务的“重试”就是下一次调用，间隔本身就是退避。

还有一类失败不会留下 `failed`：任务跑完了，但结果不对。孤儿清理扫到 0 个对象，状态是 `ok`，`detail` 里 `scanned_objects` 是 0。桶里明明有一千个对象、扫出来是 0，说明列举权限或路径约定坏了。`detail` 里的数字比 `status` 更早暴露这类问题，所以每个任务都要写“扫了多少”。

进程在 handler 中途被杀，`running` 行会永远停在那里。它还会挡住到期判断：`lastRuns` 只看 `ok` 和 `failed`，`running` 不算跑过，任务会一直显示到期、一直被锁挡回来。每个 tick 顺手收一下。

```sql
update public.cron_runs
set status = 'failed',
    finished_at = now(),
    error = coalesce(error, 'stale run (process likely crashed)')
where status = 'running'
  and started_at < now() - interval '15 minutes';
```

十五分钟的依据：单次 tick 的预算通常是六十秒，一个任务正常不可能跑十五分钟。超过这个数，基本可以判定进程没了。

单次 tick 的预算是 60 秒，来自路由里的 `maxDuration = 60`。这个预算要分给队列消费和所有到期的任务，所以任务越到后面越容易超时。任务数量涨上来之后，要么把 tick 拆成两个接口，要么让每个任务自己控制耗时并分批处理。判据是 `duration_ms`：某个任务的耗时接近 10 秒，就该考虑拆出去。

错误截断到 2000 字符也有原因。handler 抛出的往往是带完整 SQL 和参数的 `PostgresError`，一条塞进去，日志查询会变得没法读，而真正需要的信息就在前两百字里。

## 27.6 三个清理任务

注册表里现在只有一项，把剩下几项补齐。共同原则：条件本身收窄，重复跑结果一样。

```ts
// src/lib/cron/tasks.ts（续）
import { createAdminClient } from '@/lib/supabase/admin'

// 过期邀请：只改“已过期但还标 pending”的行，重复跑不会多改。
async function expireInvitations(): Promise<CronTaskResult> {
  const result = await sql<{ id: string }>`
    update public.invitations
    set status = 'expired'
    where status = 'pending' and expires_at < now()
    returning id::text
  `.execute(db)

  return { expired: result.rows.length }
}

// 历史清理：done 任务留 7 天，已处理事件留 30 天，运行记录留 90 天。
async function pruneHistory(): Promise<CronTaskResult> {
  const jobs = await sql<{ id: string }>`
    delete from public.jobs
    where status = 'done' and created_at < now() - interval '7 days'
    returning id::text
  `.execute(db)

  const events = await sql<{ id: string }>`
    delete from public.stripe_events
    where processed_at is not null and processed_at < now() - interval '30 days'
    returning id::text
  `.execute(db)

  const runs = await sql<{ id: string }>`
    delete from public.cron_runs
    where started_at < now() - interval '90 days'
    returning id::text
  `.execute(db)

  return {
    jobs_deleted: jobs.rows.length,
    events_deleted: events.rows.length,
    runs_deleted: runs.rows.length,
  }
}
```

第三个任务碰对象存储。存储没有“列出全部”的接口，只能逐层进文件夹。

```ts
// src/lib/cron/tasks.ts（续）
interface StorageObject {
  path: string
  createdAt: number
}

async function listObjects(
  admin: ReturnType<typeof createAdminClient>,
  prefix = '',
  depth = 0,
): Promise<StorageObject[]> {
  const out: StorageObject[] = []
  let offset = 0

  for (;;) {
    const { data, error } = await admin.storage.from('files').list(prefix, { limit: 100, offset })
    if (error) throw new Error(`storage list failed: ${error.message}`)
    if (!data || data.length === 0) break

    for (const item of data) {
      const path = prefix ? `${prefix}/${item.name}` : item.name
      if (item.id === null) {
        // 文件夹项没有 id，metadata 也是 null，要再进一层。
        if (depth < 2) out.push(...(await listObjects(admin, path, depth + 1)))
      } else {
        out.push({ path, createdAt: new Date(item.created_at ?? 0).getTime() })
      }
    }

    if (data.length < 100) break
    offset += 100
  }

  return out
}

async function cleanupOrphanObjects(): Promise<CronTaskResult> {
  const admin = createAdminClient()
  // 一小时的宽限：正在上传的人，pending 行在，对象可能已经在了。
  const cutoff = Date.now() - 60 * 60 * 1000

  const known = new Set<string>()
  const rows = await db
    .selectFrom('files')
    .select(['storage_path'])
    .where('status', '<>', 'deleted')
    .execute()

  for (const row of rows) {
    known.add(row.storage_path)
    // 衍生图不在 files 表里，路径是推出来的，也要算“认识”。
    known.add(row.storage_path.replace(/\/original$/, '/thumb.webp'))
    known.add(row.storage_path.replace(/\/original$/, '/preview.webp'))
  }

  const objects = await listObjects(admin)
  const orphans = objects.filter((o) => o.createdAt < cutoff && !known.has(o.path))

  // 先只读。确认一周没有误判，再打开下面这行。
  // for (const orphan of orphans) await admin.storage.from('files').remove([orphan.path])

  return {
    scanned_objects: objects.length,
    orphan_candidates: orphans.length,
    sample: orphans.slice(0, 5).map((o) => o.path),
  }
}

]
```

一小时的宽限并非装饰。用户点了上传，`pending` 行已经插入，浏览器正在把文件传上去，对象可能已经在存储里，这一小时内必须放过它。更隐蔽的情况是前端传完了、`confirmUpload` 还没跑，行仍然是 `pending`。如果 `known` 集合只收 `ready` 的行，这个刚传完的对象会被判成孤儿删掉，前端再确认只会拿到 `Object not found`。宽限一小时与 `known` 包含 `pending` 两个保护叠加，缺一不可。

反过来也要防误判。一个对象如果真的没人认领，会在下一次、下下一次运行里反复出现在候选清单。连续三天都是同一批路径，才说明它是真孤儿。这就是“先只读一周”的意义：看的是稳定性，并非数量。

连续跑三次，数字应该一致。

```bash
curl -s -X POST "http://localhost:3000/api/cron/jobs?task=files.cleanup_orphans" \
  -H "authorization: Bearer $CRON_SECRET" | jq '.tasks[0].detail'
```

```json
{
  "scanned_objects": 1240,
  "orphan_candidates": 3,
  "sample": ["3f2a.../9c1b.../original"]
}
```

数字不一致，说明有别的流程在写对象，先查清楚原因再打开删除。

第 23 章的 `scripts/cleanup-orphans.mjs` 做同一件事。同一个判断维护两套删除规则是事故来源：改了一边忘了另一边，某天脚本删掉的对象 cron 还以为存在。更稳妥的做法是把判断抽成共享函数，脚本和 cron 都调它。这里为了章节独立复制了一份，真实项目里不要这样。

## 27.7 长任务放进队列

对账要不要放进 `CRON_TASKS`。不要。它要逐个团队调 Stripe 接口，几百个团队就是几分钟，很容易撞上 `maxDuration = 60`。cron 只负责发现该做的团队，把它们塞进队列。

```ts
// src/lib/cron/tasks.ts（续）
import { enqueue } from '@/lib/jobs'

async function enqueueBillingReconcile(): Promise<CronTaskResult> {
  const teams = await db
    .selectFrom('subscriptions')
    .select(['team_id'])
    .where('status', 'in', ['active', 'past_due', 'trialing'])
    .limit(200)
    .execute()

  for (const team of teams) {
    await enqueue(db, 'billing.reconcile', { teamId: team.team_id })
  }

  return { enqueued: teams.length }
}
```

前提是先在 `src/lib/jobs.ts` 的 `JobKind` 联合类型里加上 `'billing.reconcile'`，再在分派表里注册 handler。第 26 章留的扩展点就是为这种场景准备的。

分工很清楚：cron 负责“什么时候做”，jobs 负责“做完为止”。把长任务直接塞进 cron，等于放弃重试、退避和死信。

`limit(200)` 也是这个思路。一次塞太多会把其他 `kind` 的队列挤到后面，多出来的团队下次 tick 还会被扫到。凡是批量操作都要问一句：分两次做会不会漏。这里的查询条件是“当前所有 active 团队”，重跑天然覆盖，不会漏。

## 27.8 谁来触发

入口是一个受保护的 HTTP 接口，谁调用都行。四种常见方式，差别不小。

| 方式 | 特点 | 适合 |
| --- | --- | --- |
| 自托管 crontab | 最简单，按服务器时区解释 | 一台机器、能改系统配置 |
| systemd timer | `Persistent=true` 会补跑错过的触发 | 需要补跑的自托管 |
| Vercel Cron | 只发 GET，Hobby 最快每天一次 | 每天一次的对账、清理 |
| Kubernetes CronJob | 起容器去 curl，重试与历史归平台 | 已有集群的部署 |

自托管 crontab 最省事，但别把 secret 写在 crontab 行里。文件对其他用户可读，`%` 在 crontab 里还有特殊含义。包一层脚本。

```bash
#!/usr/bin/env bash
# scripts/cron-tick.sh
set -euo pipefail

# 只有 root 和部署用户可读
# shellcheck disable=SC1091
source /etc/teamstack/cron.env

curl --fail --silent --show-error --max-time 50 \
  -X POST "https://app.example.com/api/cron/jobs" \
  -H "authorization: Bearer ${CRON_SECRET}" \
  >> /var/log/teamstack-cron.log 2>&1
```

```bash
# crontab -e（部署用户）
* * * * * /opt/teamstack/scripts/cron-tick.sh
```

systemd timer 比 crontab 多一件事：`Persistent=true` 会在机器重启后补跑错过的触发。停机维护两小时，crontab 那两小时就是空白，timer 会补。

```ini
# /etc/systemd/system/teamstack-cron.timer
[Unit]
Description=Run Teamstack cron every minute

[Timer]
OnCalendar=*:0/1
Persistent=true

[Install]
WantedBy=timers.target
```

Vercel Cron 只需要一个文件。

```json
// vercel.json
{
  "crons": [
    { "path": "/api/cron/jobs", "schedule": "0 * * * *" }
  ]
}
```

三个注意点：`path` 必须对应 `GET` 处理函数，Vercel 发 GET；设置 `CRON_SECRET` 后平台请求会自动带 `Authorization: Bearer …`（平台行为，未在本机验证）；Hobby 计划最快每天一次，写成每小时可能部署失败或按天执行，未验证。

所以 Vercel 适合每天一次的对账与清理，分钟级的队列消费要靠外部定时服务或自托管。这也是把“触发”和“执行”拆开的原因：入口只是一个受保护的接口，谁打都行。

Kubernetes CronJob 本质是起一个容器去 curl，失败重试、历史记录、资源限制都归平台管（未在本机验证）。注意用同一个镜像、只覆盖启动命令，否则 cron 容器的版本可能落后 Web 服务。

```yaml
# k8s/cron-tick.yaml（片段）
apiVersion: batch/v1
kind: CronJob
metadata:
  name: teamstack-cron
spec:
  schedule: "* * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: tick
              image: registry.example.com/teamstack:latest
              command: ["/bin/sh", "-c", "/opt/teamstack/scripts/cron-tick.sh"]
              envFrom:
                - secretRef:
                    name: teamstack-cron-env
```

时区要提醒一次。crontab 按服务器时区解释，容器默认 UTC。写“每天 9 点”在 UTC 机器上就是北京时间 17 点。这一章的路由每分钟被调用，具体任务什么时候跑由 `intervalSeconds` 决定，不靠改 cron 表达式。增任务不用动部署配置，也不会几个任务抢同一个整点。

## 27.9 监控：最近一次成功时间

最难发现的故障是根本没跑：没报错、没日志、什么都没发生，等发现时数据已经脏了一周。判断标准只有一个，最近一次成功时间。

```sql
select task,
       max(started_at) filter (where status = 'ok') as last_ok_at,
       now() - max(started_at) filter (where status = 'ok') as since_last_ok
from public.cron_runs
group by task
order by since_last_ok desc nulls first;
```

```text
      task           |         last_ok_at         |   since_last_ok
---------------------+----------------------------+-------------------
 invitations.expire  |                            |
 files.cleanup_orphans | 2026-11-23 02:10:00+08  | 09:42:11
 jobs.recover_stuck  | 2026-11-23 11:51:20+08  | 00:01:02
```

从没成功过的任务这一列是空的，排在最前面。五分钟的任务超过十五分钟没有 `ok` 就该告警，六小时的任务十八小时。

阈值按间隔的三倍设，不要按“一天没跑”设。告警进值班群，不要进邮件列表。第一次部署时故意把 `CRON_SECRET` 改错一次，确认告警真的会响，否则你不知道监控是通的，还是它自己也坏了。

监控数据保留 90 天，和运行记录的清理周期一致。想留更久就把指标导出到外部系统，不要让业务库承担长期存储。

再配一个反向指标：`select count(*) from jobs where status = 'dead'`。定时任务失败留记录，队列任务失败进死信，两者都不算报错，都是安静积累。把这两个查询放进同一个健康检查接口，一个请求看两类问题。

还有一个数字值得每天看：`cron_runs` 里 `skipped` 的比例。偶发跳过正常，持续偏高说明锁泄漏或者两个实例在抢同一批任务。两种都不报错，只会让清理越来越慢。

告警要带上下文：任务名、最后状态、最后一条错误。只发一句“cron 失败”，收到的人还得自己查，查两次之后这个告警就没人看了。

## 27.10 幂等与删除顺序

清理任务重复跑不能出事，靠的是条件本身收窄。

删除条件永远带时间边界，`created_at < now() - interval '7 days'`，晚跑一小时不会多删。判断依据是数据库里明确的记录，不能靠猜“这个对象看起来没人用”。分批处理，`limit 500` 循环，避免长事务锁表，也避免超时后删了一半。每次记录扫了多少、删了多少，两次运行可以对照。

删除顺序有方向：先软删数据库行，后删对象。对象删了行还在，用户会看到一个打不开的文件；行删了对象还在，只是浪费空间，下次脚本能补。所有清理逻辑都朝“残留停在可恢复那一侧”设计。

可恢复有下限：`delete from jobs` 是真删，没有回收站。所以只删确定没价值的数据：`done` 任务七天、已处理事件三十天、运行记录九十天。业务数据一律软删或归档，清理任务只碰边角。拿不准的，先只统计不删除，观察一周。

这里最忌讳“先查 id 列表，再循环删”。中间隔几秒，某条数据可能已经被另一个流程改了。删除条件必须写进 `delete` 语句本身，让数据库一次性判定。

一个反例。`delete from files where status = 'pending' and created_at < now() - interval '1 day'` 看起来没问题，重跑也不会多删，但它只删了行，没删对象。对象永远留在桶里，而孤儿清理的 `known` 集合来自 `files` 表，行没了，对象就变成数据库不认识的孤儿，要等到某次扫到、超过一小时宽限、又确认稳定，才会被捡走。清理行与清理对象必须成对，或者明确只有一边负责。

手动触发是排障手段，必须设边界。开发和 staging 用 curl 就够了；生产把“能立刻跑清理”的钥匙留在 curl 历史里等于留了个后门。它只能触发已有任务，但“立刻删孤儿文件”这种能力不该谁都能按。生产排障优先看 `cron_runs`，确实要补跑，用部署平台的一次性命令，跑完即弃。

也不做“补跑某一天”的参数。真正需要按日期补算的任务，比如对账、日报，应该读自己的数据源，并非被塞进通用入口。通用 `?date=` 会诱导大家写只能跑一次的任务，补跑时重复记账。补历史用一次性脚本，跑完就删，别做成常驻能力。

## 27.11 检查点

1. 多实例同时跑只执行一次。把两个带 `&` 的 curl 一起发，一个返回 `"status":"ok"`，另一个返回 `"status":"skipped"`；`select count(*) from cron_runs where task='jobs.recover_stuck' and started_at > now() - interval '1 minute'` 只有一行 `ok`。
2. 失败有记录。给某个 handler 加一行 `throw new Error('boom')`，触发后查 `cron_runs`：`status = 'failed'`、`error` 含 `boom`、`duration_ms` 不为空。改回代码再跑，两条记录都在。
3. 能手动触发。`curl -X POST ".../api/cron/jobs?task=jobs.prune_history" -H "authorization: Bearer $CRON_SECRET"` 返回 `detail`，`cron_runs` 立刻多一行；不带 secret 返回 401。

4. 清理任务重复跑结果一致：连跑两次 `?task=jobs.prune_history`，第二次的 `detail` 里三个删除计数都接近 0。
5. 锁不泄漏：跑完一次后执行 `select * from pg_locks where locktype = 'advisory'`，没有属于当前连接的咨询锁。
## 27.12 常见错误

`{"error":"unauthorized"}`，401

脚本里 `CRON_SECRET` 没被 `source` 进来，拼成了 `Bearer ` 后面为空。解法：`echo "$CRON_SECRET"` 确认变量非空，用 `curl -v` 看实际请求头。Vercel 侧则是环境变量没在项目里设置。

`relation "cron_runs" does not exist`

迁移没跑。解法：`pnpm supabase migration up`。不要在有数据的库上随手 `db reset`，它会重放全部迁移并清空数据。

两个实例都执行了，`cron_runs` 出现两行 `ok`

锁加在 `pool.query()` 上并非固定 `client` 上，加锁、解锁各拿一条连接，锁从没释放过；或者用了 `pg_advisory_xact_lock`，事务一提交锁就没了。还有一种：两个任务名哈希碰撞，改用 `hashtextextended` 并给每个任务固定整数键。

`405 Method Not Allowed`（Vercel Cron 调用时）

只导出了 `POST`。Vercel 发 GET，补一个 `GET` 处理函数复用同一段逻辑，不要复制一份。

`canceling statement due to statement timeout`

一次删太多行。把 `delete` 拆成 `limit 500` 的循环，每次提交；或给清理任务单独调 `statement_timeout`，更推荐分批。

**时间不对，任务在凌晨三点跑**

容器和数据库默认 UTC，`now()` 也是 UTC。用 `interval` 的相对时间没问题；代码里写死“每天 9 点”必须显式换算成 `Asia/Shanghai`，否则差八小时。

## 27.13 这一章在做什么

到这里，“没人点也会跑”这件事齐了：一个受保护的入口 `/api/cron/jobs`、一把不依赖外部的锁（Postgres advisory lock）、一张能追责的表 `cron_runs`、一组幂等的清理任务，以及四种触发方式。第 26 章的队列和第 27 章的调度共用同一个消费者，任务语义只有一套。

以后加功能很轻：新定时任务往 `CRON_TASKS` 里加一行，新异步任务往 `jobs` 里加一个 `kind` 和分派表里加一条。锁、重试、留痕、监控这些麻烦事都沉在下面，上面只管写业务。
