# 26 · 国际化 i18n

> **一句话结论**：路由式 i18n 的骨架是 `app/[lang]/` 目录——`lang` 成为根参数，所有页面和布局都能读到。locale 检测与重定向放在 **`proxy.ts`** 里（不是 `middleware.ts`），字典用动态 `import()` 按语言拆包。因为是服务端组件，字典再大也不会进客户端 bundle。

## 最小可运行示例

```
app/
└─ [lang]/
   ├─ layout.tsx
   ├─ page.tsx
   └─ dictionaries/
      ├─ en.json
      └─ zh.json
```

```ts
// app/[lang]/dictionaries.ts
import 'server-only'

const dictionaries = {
  en: () => import('./dictionaries/en.json').then((module) => module.default),
  zh: () => import('./dictionaries/zh.json').then((module) => module.default),
}

export type Locale = keyof typeof dictionaries

// 类型守卫：把 string 收窄成受支持的 Locale
export const hasLocale = (locale: string): locale is Locale =>
  locale in dictionaries

export const getDictionary = async (locale: Locale) => dictionaries[locale]()
```

```tsx
// app/[lang]/page.tsx
import { notFound } from 'next/navigation'
import { getDictionary, hasLocale } from './dictionaries'

export default async function Page({ params }: PageProps<'/[lang]'>) {
  const { lang } = await params

  if (!hasLocale(lang)) notFound()

  const dict = await getDictionary(lang)
  return <button>{dict.products.cart}</button>
}
```

访问 `/zh` 和 `/en` 会渲染不同语言的按钮。

## 术语与路由策略

**Locale（区域标识）** 是一组语言和格式偏好的标识，通常包含语言和地区：

| 值 | 含义 |
|---|---|
| `en-US` | 美式英语 |
| `zh-CN` | 简体中文 |
| `zh` | 中文，不指定地区 |

两种路由策略：

| 策略 | 形态 | 取舍 |
|---|---|---|
| 子路径 | `acme.com/zh/products` | 一套部署、一套 SEO 资产、配置简单 |
| 独立域名 | `acme.cn/products` | 更强的区域信号，但要多套部署和证书 |

子路径是默认推荐。本章以子路径为主。

## locale 检测与重定向：在 proxy 里做

浏览器会在 `Accept-Language` 头里带上用户的语言偏好。语言匹配本身有细节（q 值排序、`zh-Hant` 这类变体、`nl-BE` 回退到 `nl`），用官方示例推荐的两个库比自己写字符串比较可靠：

```ts
// lib/locale.ts
import { match } from '@formatjs/intl-localematcher'
import Negotiator from 'negotiator'

const locales = ['zh', 'en']
const defaultLocale = 'zh'

export function getLocale(acceptLanguage: string): string {
  const headers = { 'accept-language': acceptLanguage }
  const languages = new Negotiator({ headers }).languages()

  return match(languages, locales, defaultLocale)
}
```

proxy 只负责「路径里有没有 locale 前缀，没有就补上并重定向」：

```ts
// proxy.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'
import { getLocale } from './lib/locale'

const locales = ['zh', 'en']

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  // 路径里已经有受支持的 locale 前缀，直接放行
  const pathnameHasLocale = locales.some(
    (locale) => pathname.startsWith(`/${locale}/`) || pathname === `/${locale}`
  )
  if (pathnameHasLocale) return

  // 没有前缀：重定向到带 locale 的地址
  const locale = getLocale(request.headers.get('accept-language') ?? '')
  request.nextUrl.pathname = `/${locale}${pathname}`
  return NextResponse.redirect(request.nextUrl)
}

export const config = {
  // 跳过所有内部路径
  matcher: ['/((?!_next|api|favicon.ico|.*\\..*).*)'],
}
```

`match()` 会处理「用户偏好 `nl-BE`，站点只有 `nl-NL` 和 `nl`」这类回退，比手写的字符串比较可靠得多。

> **注意**：这里用的是 `proxy.ts`，不是 `middleware.ts`。改名和运行时的变更是 16 的核心变化之一，见 [`MIGRATION-16.md`](../../MIGRATION-16.md) 第 1 条。

### 为什么 matcher 要排除带点的路径

`.*\\..*` 这个负向匹配排除了所有「路径里含点」的请求——也就是静态文件（`logo.png`、`robots.txt`、`sitemap.xml`）。不排除的话，proxy 会把 `/favicon.ico` 重定向成 `/zh/favicon.ico`，导致 404。

### 用 `rewrite` 而不是 `redirect`？

也可以不重定向，而是把 `/products` **重写**成 `/zh/products`（URL 保持不带前缀）：

```ts
// proxy.ts —— 重写方案
import { NextResponse } from 'next/server'

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  if (locales.some((l) => pathname.startsWith(`/${l}/`) || pathname === `/${l}`)) {
    return
  }

  // URL 不变，内容换成默认语言版本
  request.nextUrl.pathname = `/${defaultLocale}${pathname}`
  return NextResponse.rewrite(request.nextUrl)
}
```

| 方案 | 优点 | 缺点 |
|---|---|---|
| `redirect` | 每个语言有独立可索引的 URL | 首次访问多一次跳转 |
| `rewrite` | 无跳转，默认语言 URL 干净 | 各语言共用同一 URL，SEO 上无法区分 |

要做多语言 SEO 就用 `redirect`——搜索引擎需要能区分不同语言的 URL。官方文档的示例也是 `redirect`。

## 目录结构

把所有特殊文件放进 `app/[lang]/`：

```
app/
└─ [lang]/
   ├─ layout.tsx          # 根布局（含 <html lang>）
   ├─ page.tsx
   ├─ about/
   │  └─ page.tsx         # /zh/about、/en/about
   ├─ blog/
   │  └─ [slug]/
   │     └─ page.tsx      # /zh/blog/xxx
   ├─ dictionaries.ts
   └─ dictionaries/
      ├─ en.json
      └─ zh.json
```

`[lang]` 成为**根参数**，`lang` 会传给每一个布局和页面。

```tsx
// app/[lang]/layout.tsx
export default async function RootLayout({
  children,
  params,
}: LayoutProps<'/[lang]'>) {
  const { lang } = await params

  return (
    <html lang={lang}>
      <body>{children}</body>
    </html>
  )
}
```

`<html lang>` 用实际的 locale 值，这对屏幕阅读器和搜索引擎都有意义。

### 静态生成各语言页面

```tsx
// app/[lang]/layout.tsx
export async function generateStaticParams() {
  return [{ lang: 'zh' }, { lang: 'en' }]
}

export default async function RootLayout({
  children,
  params,
}: LayoutProps<'/[lang]'>) {
  return (
    <html lang={(await params).lang}>
      <body>{children}</body>
    </html>
  )
}
```

在根布局里声明，一次覆盖所有子路由。

## 字典的组织方式

### 基础形态：一个语言一个 JSON

```json
// app/[lang]/dictionaries/zh.json
{
  "products": {
    "cart": "加入购物车",
    "checkout": "去结算"
  },
  "nav": {
    "home": "首页",
    "about": "关于"
  }
}
```

```json
// app/[lang]/dictionaries/en.json
{
  "products": {
    "cart": "Add to Cart",
    "checkout": "Checkout"
  },
  "nav": {
    "home": "Home",
    "about": "About"
  }
}
```

关键点是 `getDictionary` 用**动态 `import()`**：

```ts
// app/[lang]/dictionaries.ts
import 'server-only'

const dictionaries = {
  en: () => import('./dictionaries/en.json').then((module) => module.default),
  zh: () => import('./dictionaries/zh.json').then((module) => module.default),
}

export type Locale = keyof typeof dictionaries

export const hasLocale = (locale: string): locale is Locale =>
  locale in dictionaries

export const getDictionary = async (locale: Locale) => dictionaries[locale]()
```

**为什么用动态 import 而不是静态 import 全部语言**：静态 import 会把所有语言的字典都打进同一个 chunk。动态 import 让打包器为每种语言生成独立的 chunk，只有被请求的那个会被加载。

`import 'server-only'` 是保险——如果有人不小心在客户端组件里 import 了这个文件，构建会直接失败，而不是把字典泄露到浏览器。

### 服务端组件意味着字典不进客户端 bundle

因为 `app/` 下的布局和页面默认都是服务端组件，字典文件只在服务端读取，浏览器只收到渲染后的 HTML。所以**翻译文件的体积不影响客户端 JS 大小**。

但如果把 `getDictionary` 的结果传给客户端组件当 props，那部分数据就会进 payload。注意只在必要的地方传：

```tsx
// app/[lang]/page.tsx
import { getDictionary, hasLocale } from './dictionaries'
import { AddToCartButton } from './add-to-cart-button'

export default async function Page({ params }: PageProps<'/[lang]'>) {
  const { lang } = await params
  if (!hasLocale(lang)) notFound()

  const dict = await getDictionary(lang)

  return (
    <>
      <h1>{dict.nav.home}</h1>
      {/* 只把按钮需要的那个字符串传过去，而不是整个 dict */}
      <AddToCartButton label={dict.products.cart} />
    </>
  )
}
```

### 按命名空间拆分

字典变大之后（几百个键），一个文件会变成冲突热点——多个人同时改同一个 JSON，合并冲突不断。按**命名空间拆文件**：

```
app/[lang]/dictionaries/
├─ zh/
│  ├─ common.json
│  ├─ products.json
│  └─ blog.json
└─ en/
   ├─ common.json
   ├─ products.json
   └─ blog.json
```

```ts
// app/[lang]/dictionaries.ts
import 'server-only'

type Namespace = 'common' | 'products' | 'blog'

const loaders: Record<Namespace, (lang: string) => Promise<unknown>> = {
  common: (lang) => import(`./dictionaries/${lang}/common.json`).then((m) => m.default),
  products: (lang) => import(`./dictionaries/${lang}/products.json`).then((m) => m.default),
  blog: (lang) => import(`./dictionaries/${lang}/blog.json`).then((m) => m.default),
}

export async function getNamespace<T extends Namespace>(
  lang: string,
  namespace: T
) {
  return loaders[namespace](lang)
}
```

> **注意**：`import()` 的路径必须是**静态可分析**的前缀。`./dictionaries/${lang}/common.json` 里 `./dictionaries/` 是静态前缀，打包器会把该目录下所有匹配文件都打进去——这正是我们要的。但反过来，如果整个路径都是变量（`import(someVar)`），打包器无法分析，会失败或把整个项目都打包进去。

### 用 `next/root-params` 免去层层传参

`lang` 需要在很多地方用到（共享的数据获取函数、深层组件）。逐层传 props 很啰嗦，可以用 `next/root-params` 直接读：

```ts
// app/[lang]/dictionaries.ts
import { lang } from 'next/root-params'
import { notFound } from 'next/navigation'

const dictionaries = {
  en: () => import('./dictionaries/en.json').then((module) => module.default),
  zh: () => import('./dictionaries/zh.json').then((module) => module.default),
}

export type Locale = keyof typeof dictionaries

export const hasLocale = (locale: string): locale is Locale =>
  locale in dictionaries

export const getDictionary = async () => {
  const locale = await lang()
  if (!hasLocale(locale)) notFound()
  return dictionaries[locale]()
}
```

调用方不再需要传参：

```tsx
// app/[lang]/page.tsx
import { getDictionary } from './dictionaries'

export default async function Page() {
  const dict = await getDictionary()
  return <button>{dict.products.cart}</button>
}
```

三条行为约束：

1. **import 了 `next/root-params` 的文件不需要再写 `import 'server-only'`**——在客户端组件里使用它会在构建期直接失败。
2. 根参数 getter 只在**服务端组件和服务端工具函数**里可用，**在客户端组件、Server Actions、Route Handler 里不可用**。
3. `lang` 是根参数，因为每条路由都嵌套在 `app/[lang]` 下。

`next/root-params` 是 `unstable_rootParams()` 的正式替代。

## 本地化协作流程

代码结构只是三分之一，剩下的问题是「翻译文本怎么进来、怎么保持同步」。

### 流程的四个环节

```
1. 开发阶段    代码里只写 key，不写任何自然语言文本
2. 提取阶段    从源语言文件提取待翻译内容，导出给翻译方
3. 翻译阶段    翻译方在 TMS（翻译管理系统）里工作
4. 回写阶段    TMS 产出各语言的 JSON，提交回仓库或通过 CI 拉取
```

### 关键约束：源语言字典是唯一事实来源

`en.json`（或 `zh.json`）由开发者维护，其他语言由翻译方维护。两边不要互相覆盖。

```json
// app/[lang]/dictionaries/en.json —— 开发者维护
{
  "products": {
    "cart": "Add to Cart"
  }
}
```

```json
// app/[lang]/dictionaries/zh.json —— 翻译方维护
{
  "products": {
    "cart": "加入购物车"
  }
}
```

### 缺失 key 要显性失败

不要写「找不到就回退到 key 本身」的兜底——那会让缺失的翻译在生产环境里悄悄显示成 `products.cart`，而没人发现。

```ts
// app/[lang]/dictionaries.ts
import { notFound } from 'next/navigation'

// 严格查找：key 不存在时抛错，构建期就能暴露
export function t(dict: Record<string, unknown>, key: string): string {
  const value = key.split('.').reduce<unknown>(
    (acc, part) =>
      acc && typeof acc === 'object' ? (acc as Record<string, unknown>)[part] : undefined,
    dict
  )

  if (typeof value !== 'string') {
    throw new Error(`Missing translation key: ${key}`)
  }

  return value
}
```

配合类型化的字典（从源语言 JSON 推导类型），缺 key 在编译期就能发现：

```ts
// app/[lang]/dictionaries.ts
import type en from './dictionaries/en.json'

export type Dictionary = typeof en
```

```tsx
// app/[lang]/page.tsx
const dict = (await getDictionary(lang)) as Dictionary
// dict.products.cart 有类型提示，拼错立刻报错
```

### 翻译方拿不到代码时的做法

| 做法 | 说明 |
|---|---|
| 导出源语言 JSON 给对方 | 最简单，靠人工同步 |
| 接 TMS（Crowdin、Lokalise、Phrase 等） | 自动拉取源文件、自动回写译文，适合多语言多团队 |
| CI 里做 key 一致性校验 | 每次 PR 检查各语言 key 集合是否一致，缺 key 直接失败 |

CI 校验是最小成本的防线。核心思路是递归拍平两边的 key，比较集合差集，有差异就 `process.exit(1)`：

```ts
// scripts/check-i18n.ts
import en from '../app/[lang]/dictionaries/en.json'
import zh from '../app/[lang]/dictionaries/zh.json'

function flatten(obj: Record<string, unknown>, prefix = ''): string[] {
  return Object.entries(obj).flatMap(([key, value]) => {
    const path = prefix ? `${prefix}.${key}` : key
    return typeof value === 'object' && value !== null
      ? flatten(value as Record<string, unknown>, path)
      : [path]
  })
}

const missing = [...new Set(flatten(en))].filter((k) => !new Set(flatten(zh)).has(k))
if (missing.length) {
  console.error('缺失的翻译：', missing)
  process.exit(1)
}
```

### 复数与格式化

不同语言的复数规则不同（中文没有复数变化，阿拉伯语有六种形式）。不要自己拼 `item + 's'`：

```ts
// lib/format.ts
export function formatItems(lang: string, count: number) {
  // 用 Intl 而不是手写复数逻辑
  return new Intl.NumberFormat(lang, {
    style: 'unit',
    unit: 'item',
    unitDisplay: 'long',
  }).format(count)
}
```

`Intl` 系列 API 在 Node.js 和浏览器里都内置，且覆盖所有 locale 的规则。日期、货币、数字分组同理。

### 右到左（RTL）

阿拉伯语、希伯来语需要 `dir="rtl"`：

```tsx
// app/[lang]/layout.tsx
const RTL_LOCALES = ['ar', 'he', 'fa']

export default async function RootLayout({
  children,
  params,
}: LayoutProps<'/[lang]'>) {
  const { lang } = await params
  const dir = RTL_LOCALES.includes(lang) ? 'rtl' : 'ltr'

  return (
    <html lang={lang} dir={dir}>
      <body>{children}</body>
    </html>
  )
}
```

样式里用逻辑属性（`margin-inline-start` 而不是 `margin-left`），Tailwind 用 `ms-*` / `me-*` 而不是 `ml-*` / `mr-*`。

## 常见坑

- **现象**：把 locale 检测逻辑写进了 `middleware.ts`，升级到 16 后不执行了；或者 `params.lang` 打印出来是 `undefined`。
  **原因**：16 起文件名和导出函数名改成 `proxy.ts` / `export function proxy`；`params` 也从同步对象变成了 Promise。
  **解法**：改名（或跑 `npx @next/codemod@canary middleware-to-proxy .`），并把 `params.lang` 改成 `(await params).lang`。见 [`MIGRATION-16.md`](../../MIGRATION-16.md) 第 1、7 条。

- **现象**：proxy 里的 matcher 没排除静态文件，`/favicon.ico` 被重定向成 `/zh/favicon.ico` 并 404。
  **原因**：matcher 覆盖了所有路径。
  **解法**：加 `.*\\..*` 负向匹配排除带点的路径，同时排除 `_next` 和 `api`。

- **现象**：访问 `/fr` 时页面报运行时错误，而不是 404。
  **原因**：`lang` 的类型是 `string`，不受支持的值直接透传到了字典查找。
  **解法**：用 `hasLocale(lang)` 收窄类型，不匹配时 `notFound()`。

- **现象**：所有语言的翻译文本都出现在了首屏 bundle 里。
  **原因**：字典用了静态 import，或者把整个 `dict` 对象传给了客户端组件。
  **解法**：`getDictionary` 用动态 `import()`；只把需要的字符串传给客户端组件。

- **现象**：`import(\`./dictionaries/${lang}/common.json\`)` 构建报错，说无法分析动态导入。
  **原因**：`import()` 的路径缺少静态前缀。
  **解法**：确保路径里有固定的静态部分（如 `./dictionaries/`），变量只出现在末尾。

- **现象**：用了 `next/root-params` 的 `lang()`，在 Server Action 里报错。
  **原因**：根参数 getter 只在服务端组件和服务端工具函数里可用。
  **解法**：Server Action 里显式接收或从 `params` 里读 locale，不要依赖 root params。

- **现象**：用户切换语言后刷新又跳回原来的语言。
  **原因**：proxy 每次都按 `Accept-Language` 重定向，而用户的语言选择没有持久化。
  **解法**：把用户选择写进 cookie（例如 `NEXT_LOCALE`），proxy 里优先读 cookie，没有才看 `Accept-Language`。

- **现象**：中文页面的搜索排名掉了。
  **原因**：各语言页面的 canonical 都指向了默认语言版本。
  **解法**：canonical 自指，并用 `alternates.languages` 建立 hreflang 关联（见第 25 章）。

- **现象**：某个语言少了一个翻译 key，生产环境页面上直接显示了 `products.cart`。
  **原因**：字典查找做了「找不到就返回 key」的兜底。
  **解法**：缺失时抛错，并在 CI 里做各语言 key 集合一致性校验。

- **现象**：阿拉伯语站点布局错乱。
  **原因**：只设了 `lang` 没设 `dir`，或者样式用了物理方向属性。
  **解法**：`<html lang={lang} dir={dir}>`，样式改用逻辑属性。

## 旧写法 vs 新写法

| 场景 | 旧 | 新（16.3） |
|---|---|---|
| locale 检测的位置 | `middleware.ts` 里的 `middleware` 函数 | **`proxy.ts` 里的 `proxy` 函数** |
| 路由参数 | `params.lang` | **`(await params).lang`** |
| 类型标注 | 手写泛型 | **`PageProps<'/[lang]'>` / `LayoutProps<'/[lang]'>`** |
| 跨层读 locale | `unstable_rootParams()` | **`next/root-params` 的 `lang()`** |

详见 [`MIGRATION-16.md`](../../MIGRATION-16.md) 第 1、7 条。

## API / 配置速查

| 文件 / API | 作用 |
|---|---|
| `app/[lang]/layout.tsx` | 根布局，设置 `<html lang>` 和 `dir` |
| `app/[lang]/dictionaries.ts` | 字典加载器 |
| `app/[lang]/dictionaries/*.json` | 各语言翻译文本 |
| `proxy.ts` | locale 检测与重定向 |
| `generateStaticParams` | 为每个 locale 生成静态页面 |
| `hasLocale(locale)` | 类型守卫，收窄 `string` 到受支持的 Locale |
| `notFound()` | 不受支持的 locale 返回 404 |
| `next/root-params` 的 `lang()` | 跨层读取根参数 |

| 可选依赖 | 用途 |
|---|---|
| `@formatjs/intl-localematcher` | 语言匹配算法 |
| `negotiator` | 解析 `Accept-Language` |
| `Intl.NumberFormat` / `Intl.DateTimeFormat` | 数字、货币、日期本地化（内置） |

| 常用 i18n 库 | 说明 |
|---|---|
| `next-intl` | 功能最全，支持消息格式化与复数 |
| `next-international` | 轻量，类型安全 |
| `lingui` | 提取式工作流 |
| `paraglide-next` | 编译期优化 |
| `gt-next` | 托管翻译服务 |
