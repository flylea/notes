# 第 44 章 依赖与供应链

一个 Next.js 项目通常有一百多个直接依赖，加上传递依赖，`node_modules` 里可能有八千到一万个包。这些包的代码跑在你的服务器上，能读环境变量，能访问数据库，能在构建时执行任意命令。

依赖风险有三个来源。

第一个来源是已知漏洞。某个包被披露了原型污染、路径穿越、正则拒绝服务，你的版本落在受影响区间里。这类风险有公开数据库可查，`pnpm audit` 能发现一部分。

第二个来源是恶意代码。攻击者拿下某个包的发布权限，在补丁版本里塞一段安装脚本，读走 CI 的 token，或者把用户的密码发到外部服务器。这类风险通常查不到，因为漏洞库不收恶意包，要等社区发现。

第三个来源是供应链的间接关系。你没直接装那个出问题的包，是某个库依赖了它。升级自己的直接依赖不会修复它，因为中间那个库没动。

这一章讲四件事：怎么看清装了什么，怎么把安装固定下来，怎么发现并处理高危依赖，以及怎么在 CI 里把这些变成每次提交都检查的门禁。

先说结论性的判断标准：绝大多数项目不需要一套复杂的供应链安全体系，需要的是三条纪律。锁文件进仓库且 CI 用 `--frozen-lockfile`；每次加依赖前看一眼它是谁维护的、会拉进来多少；高危漏洞在两周内处理完，处理方式写进提交信息。

## 44.1 直接依赖与传递依赖

`package.json` 里的 `dependencies` 和 `devDependencies` 是直接依赖，你写的。

直接依赖自己依赖的包叫传递依赖，你没写，但会装。`pnpm why` 可以查一个包为什么被装进来。

```bash
pnpm why lodash
```

输出是一条链，形如：

```
@supabase/auth-helpers-nextjs@0.10.0
└─ lodash@4.17.20
```

链的长度说明距离。上面这个例子只有两层。长一点的例子：

```
next@16.4.6
└─ @vercel/xxx@x.y.z
   └─ postcss@8.x
      └─ nanoid@3.x
```

四层的依赖，改自己代码里的任何一行都不会影响它。要处理只能升级中间那个包，或者用 `overrides` 强制指定版本。

传递依赖的数量通常比想象的多。对比两个数字：

```bash
cat package.json | grep -c '":'
ls node_modules/.pnpm | wc -l
```

第一个是 `package.json` 里的字段数（含 scripts、engines 等），第二个是实际安装的包版本数。两者差一个量级是正常的。

数量的意义在于攻击面。八千个包，任何一个的发布者账号被盗，你的构建就可能被执行任意代码。这不代表要删到只剩几十个包，而是说每一次新增依赖都值得多想一下。

三个高风险位置要特别留意。

一是服务端代码里的依赖。它们能访问数据库密码、Stripe 密钥、用户数据。一个服务端依赖被投毒，损失是数据泄露。

二是处理用户输入的依赖。解析 Markdown、解析 YAML、解析 CSV、处理上传文件的库，直接面对不可信内容，漏洞更容易被利用。

三是有安装脚本的依赖。`postinstall`、`prepare` 在 `pnpm install` 时自动执行，不需要你 import 任何东西。这类包在 CI 里跑的时候，环境变量里通常有数据库地址和部署密钥。

## 44.2 看清装进来的是什么

在改任何东西之前，先把现状查清楚。

```bash
pnpm why lodash
pnpm list --depth=0
git diff --stat pnpm-lock.yaml
```

第一条查某个包从哪来。第二条列出所有直接依赖和版本。第三条在锁文件变动后看改了多少行，超过五十行的变动值得看一眼具体内容。

锁文件的 diff 能暴露顺手升级带来的连带变化。一次 `pnpm up` 可能改动几百行，其中多数是补丁版本，但偶尔会有一个包换了主版本，行为变了。

看某个依赖拉进来的完整子树：

```bash
pnpm why --depth 3 lodash
```

看一个包在哪些地方被 import：

```bash
grep -rn "from \"lodash\"" src/ | head
```

如果输出为空，说明你的代码没直接用，它是被别的库拖进来的。这种情况下不能删，只能换版本或者换掉那个上层库。

## 44.3 锁文件与可复现安装

`pnpm-lock.yaml` 必须进 git。它记录了每个包的精确版本、下载地址、完整性哈希，以及依赖关系。

没有锁文件时，`pnpm install` 会按 `package.json` 里的范围重新解析版本。`^4.17.21` 在今天是 4.17.21，三个月后可能是 4.17.25。这会造成「在我机器上能跑」的经典问题，也会让 CI 和线上跑不同的代码。

有一个锁文件，两台机器、两次构建、CI 和线上，装的都是同一批版本。

CI 里的安装命令要加 `--frozen-lockfile`。

```bash
pnpm install --frozen-lockfile
```

这个参数的意思是：锁文件和 `package.json` 不一致时直接失败，不许自动更新。失败信息是：

```
ERR_PNPM_OUTDATED_LOCKFILE  Cannot install with "frozen-lockfile" because pnpm-lock.yaml is not up to date with package.json
```

出现这个错误说明有人改了 `package.json` 却没提交更新后的锁文件。本机跑一次 `pnpm install`，把锁文件一起提交。

pnpm 在 CI 环境（`CI=true`）下默认就走 frozen 模式，但显式写出来更清楚，也避免本地脚本误判。

`package.json` 里加 `packageManager` 字段，把 pnpm 版本也固定下来。

```json
// package.json
{
  "name": "teamstack",
  "private": true,
  "packageManager": "pnpm@10.12.1",
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "test": "vitest run"
  }
}
```

Corepack 会按这个字段启用对应版本。团队里有人用 pnpm 9，会得到版本不匹配的提示，避免装出另一个版本的 `node_modules`。

锁文件里还有完整性校验。每个包条目带 `integrity` 字段，是 tarball 的 sha512。下载后哈希对不上，pnpm 会拒绝安装：

```
ERR_PNPM_TARBALL_INTEGRITY  Cannot find matching integrity
```

手工编辑锁文件最容易触发这个错误。锁文件不要手改，改 `package.json` 让它重新生成。

合并分支时锁文件经常冲突。正确处理方式是取一边的版本，重新 install。

```bash
git checkout --theirs pnpm-lock.yaml
pnpm install
git add pnpm-lock.yaml
```

`--theirs` 拿到的是对方的锁文件，`pnpm install` 会按当前 `package.json` 重算，冲突行自动消失。不要试图手工解决锁文件里的冲突标记。

## 44.4 审计已知漏洞

`pnpm audit` 查的是公开漏洞库，和 `npm audit` 同一套数据。

```bash
pnpm audit
```

默认会报所有级别的漏洞。日常用 `--audit-level` 过滤，只在达到指定级别时才返回非零退出码。

```bash
pnpm audit --audit-level=high
```

只报 high 和 critical 时返回非零，moderate 和 low 只提示。CI 里用这一条，避免因为一个 low 级别问题让构建红掉。

生产依赖优先。

```bash
pnpm audit --prod --audit-level=high
```

`--prod` 只看 `dependencies`，不看 `devDependencies`。理由是 devDependencies 不进生产镜像，风险低一档。但这条规则有两个例外：一是构建阶段会执行 devDependencies 的代码（`next build` 用到它们），二是有些项目把工具库误放进了 devDependencies 却在运行时代码里 import。

报告要读四个字段：严重级别、受影响版本区间、修复版本、依赖路径。

```bash
pnpm audit --json | head -40
```

JSON 输出里 `vulnerabilities` 字段是对象，键是包名，值里有 `severity`、`via`、`range`、`fixAvailable`。`via` 可能是一个字符串数组，说明这条漏洞由哪些 CVE 或上层包引起。

`fixAvailable` 为 `true` 表示可以直接升级修复；为 `false` 表示还没有修复版本；是一个对象时，里面写着要升哪个包、升到哪个版本、是否跨大版本。

审计有三个局限，要知道。

第一，它只查公开数据库。零日漏洞、还没收录的漏洞、恶意包，它都发现不了。

第二，它依赖版本区间。有些漏洞的修复版本标错了，或者受影响的用法在你的代码里根本不存在。报告说 high，实际风险可能是 low。

第三，离线环境下 `pnpm audit` 不可用。它要请求 registry 的审计接口。

第三个局限在 CI 里会变成问题。某些镜像源没有实现审计接口，请求会返回错误：

```
ERR_PNPM_AUDIT_BAD_RESPONSE  The audit endpoint returned an unexpected response
```

处理方式是指定官方 registry 只做审计。

```bash
pnpm audit --registry https://registry.npmjs.org/ --audit-level=high
```

## 44.5 修复高危依赖的三条路

审计报告里出现 high，处理方式有优先级。

第一条路：直接依赖，`pnpm up` 升级。

```bash
pnpm up lodash@latest
pnpm install
pnpm test
```

`pnpm up` 只改 `package.json` 里指定的那一个包，保留其他依赖不动。范围写法也可以：

```bash
pnpm up "lodash@^4.17.21"
```

第二条路：传递依赖，用 `overrides` 强制指定版本。

```json
// package.json
{
  "pnpm": {
    "overrides": {
      "lodash@<4.17.21": "4.17.21"
    }
  }
}
```

键是「包名+版本范围」，值是强制使用的版本。上面的写法表示：所有依赖链里的小于 4.17.21 的 lodash，都替换成 4.17.21。

overrides 有代价，要写清两件事。

一是注释。`package.json` 不支持注释，所以在 `pnpm-workspace.yaml` 或附近放一个 `docs/overrides.md`，写清哪一条为什么加、谁加的、什么时候到期。

二是范围要窄。`"lodash": "4.17.21"` 这种无条件覆盖会让所有版本的 lodash 都变成 4.17.21，包括未来某个需要更高版本的依赖。用 `lodash@<4.17.21` 只覆盖受影响区间。

第三条路：移除。如果那个库只为一个功能服务，功能可以用二十行代码重写，删掉依赖更彻底。

```bash
pnpm remove lodash
pnpm install
pnpm build
```

三条路走完都要验证：`pnpm install --frozen-lockfile` 能过，`pnpm test` 能过，`pnpm build` 能过，`pnpm audit --prod --audit-level=high` 返回零。

跨大版本的升级要单独开分支，一次只升一个包。两个包同时升，出问题时无法判断是哪个引起的。

## 44.6 安装脚本

`postinstall`、`preinstall`、`prepare` 是安装阶段自动执行的脚本。它们由包的作者编写，在你的机器和 CI 上以你的权限运行。

风险在于权限。CI 里跑 `pnpm install` 时，环境变量里有数据库连接串、部署 token、npm 发布 token。一个恶意 `postinstall` 只要几行代码就能把它们发出去。

pnpm 10 起默认不执行依赖的安装脚本。装完会看到提示：

```
Ignored build scripts: esbuild, sharp, @tailwindcss/oxide.
Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
```

这个变化让一些包装完不可用。`sharp` 需要编译原生模块，不执行脚本就没有二进制文件，运行时报 `Cannot find module 'sharp'`。

处理方式是在 `pnpm-workspace.yaml` 里显式允许。

```yaml
# pnpm-workspace.yaml
packages:
  - "."

onlyBuiltDependencies:
  - esbuild
  - sharp
  - "@tailwindcss/oxide"
```

也可以在交互式环境跑 `pnpm approve-builds`，它会列出所有带脚本的包，逐个选择。

批准之前先看脚本内容。

```bash
node -p "require('./node_modules/sharp/package.json').scripts"
```

输出应该只有 `install`、`prebuild-install` 这类正常的构建命令。如果看到 `curl`、`nc`、把环境变量写进文件的语句，停下来查这个包的来源。

`prepare` 脚本还多一层风险：从 git 仓库安装依赖时（`pnpm add user/repo`），`prepare` 会执行，即使这个包不在 registry 上。

CI 的锁文件 diff 是一道有效防线。依赖变动导致锁文件改动超过五十行，或者出现一个没见过的包名，都值得扫一眼。这种事靠人盯不可靠，可以在 CI 里加一条检查：锁文件里新增的包必须在白名单里。

## 44.7 自动更新

手工盯着二十个依赖的版本不现实。Dependabot 或 Renovate 能自动开 PR。

Dependabot 的配置放 `.github/dependabot.yml`。

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
    open-pull-requests-limit: 5
    groups:
      dev-minor:
        dependency-type: "development"
        update-types: ["minor", "patch"]
    ignore:
      - dependency-name: "next"
        update-types: ["version-update:semver-major"]
      - dependency-name: "react"
        update-types: ["version-update:semver-major"]

  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "monthly"
```

几个参数值得解释。

`open-pull-requests-limit: 5` 限制同时打开的 PR 数。不限的话，一次可能开二十个，评审不过来，最后全部堆积。

`groups` 把开发依赖的补丁和次版本合并成一个 PR。这类升级通常无风险，逐个开 PR 是浪费注意力。生产依赖的升级不分组，一个一个来。

`ignore` 里排除了 next 和 react 的大版本。大版本升级要读迁移指南，不能靠自动 PR 合并。

GitHub Actions 的版本也要更新。注意 action 的引用方式：`uses: actions/checkout@v4` 用的是 tag，tag 可以被移动；更严格的做法是钉 commit SHA。

```yaml
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
```

Dependabot 有几个管不到的地方。

一是撤版。包被作者 `unpublish` 之后，锁文件里的地址会 404，`pnpm install` 直接失败。这种问题要人工处理，从锁文件里移除该包并换替代品。

二是维护者转让。包换了 owner，新 owner 在下一个版本里加后门。Dependabot 只按版本号升级，不判断 owner 变化。

三是安全公告。Dependabot 有安全更新功能，但它依赖 GitHub 的漏洞数据库，收录有延迟。高危公告发布后，最好同时订阅包的安全公告页。

## 44.8 可复现构建

同一份代码、同一份锁文件，两次构建出来的产物应该一致。实际做不到完全一致，Next.js 的构建产物里包含时间戳和随机 ID。目标是「可追溯」，出了问题能定位到是哪个提交、哪次构建。

第一步，把 git 提交号注入构建。

```ts
// next.config.ts
import type { NextConfig } from "next";

const config: NextConfig = {
  env: {
    APP_VERSION: process.env.GIT_SHA ?? "dev",
  },
};

export default config;
```

```bash
GIT_SHA=$(git rev-parse --short HEAD) pnpm build
```

页面或健康检查接口输出这个值，线上出问题时能和提交对上。

```ts
// src/app/api/health/route.ts
export async function GET() {
  return Response.json({
    ok: true,
    version: process.env.APP_VERSION ?? "dev",
  });
}
```

第二步，理解 `.next/BUILD_ID`。每次构建都会生成一个新的随机 ID。它变了，客户端的所有缓存都会失效，用户下次访问会重新下载全部资源。这是正常的，但要在部署窗口里考虑，别在流量高峰发版。

第三步，Dockerfile 里的 COPY 顺序。先复制依赖清单，再安装，最后复制源码。

```dockerfile
# Dockerfile
FROM node:22-alpine AS deps
WORKDIR /app
RUN corepack enable
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN pnpm install --frozen-lockfile

FROM node:22-alpine AS builder
WORKDIR /app
RUN corepack enable
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NEXT_TELEMETRY_DISABLED=1
RUN GIT_SHA=$(git rev-parse --short HEAD 2>/dev/null || echo unknown) pnpm build
```

顺序反了（先 `COPY . .` 再 install），任何源码改动都会让依赖层缓存失效，构建时间从三分钟变成十一分钟。

`pnpm-workspace.yaml` 不能漏。漏了的话 `onlyBuiltDependencies` 不生效，`sharp` 装不出二进制，构建在打包阶段失败。

第四步，多实例部署时要固定 Server Action 的加密密钥。

```bash
# .env.production
NEXT_SERVER_ACTIONS_ENCRYPTION_KEY=<32 字节 base64>
```

不固定的话，每次部署 action ID 都会变，正在填表的用户提交时报：

```
Failed to find Server Action "xxx". This request might be from an older or newer deployment.
```

## 44.9 加依赖前先问四个问题

新增一个依赖之前，用四个问题过滤。

第一个问题：谁维护。

```bash
npm view <包名> time.modified maintainers
```

输出里有最后发布时间和维护者列表。最后发布在两年前，说明可能已经弃坑；维护者只有一个个人账号，风险比一个有组织的团队高；维护者列表在近期换过人，要警惕。

第二个问题：多大。

装之前先看包体积。可以用 `npm view <包名> dist.unpackedSize` 看压缩前大小，或者去 bundlephobia 这类站点查引入后的体积。一个 300KB 的日期库，如果只用来格式化一次日期，用 `Intl.DateTimeFormat` 三行就够了。

第三个问题：会拉进来什么。

```bash
pnpm why <包名>
```

装完之后查它的子树。有些库为了一个功能拉进十几个子依赖，其中一个可能就是你审计报告里那个高危包。

第四个问题：许可证。

```bash
pnpm licenses list --prod
```

未验证：pnpm 10 上这个子命令的输出格式以实际为准。GPL、AGPL、UNLICENSED 的包要停下来看。商业项目里用 AGPL 库，可能触发开源义务。

四个问题都过了，再装。装完把许可证清单存一份到 `docs/licenses.md`，方便以后审查。

能用内置 API 解决的，不装库。格式化日期用 `Intl.DateTimeFormat`，处理 URL 用 `URL` 和 `URLSearchParams`，深拷贝用 `structuredClone`，生成 UUID 用 `crypto.randomUUID()`。这些都在 Node 和浏览器里原生支持。

## 44.10 三个真实事故

三个案例说明「依赖本身没漏洞，也可能出事」。

2018 年 event-stream。这个包被原维护者转让给一个陌生人，新维护者在依赖里加了 `flatmap-stream`，这个子包的 `postinstall` 会读环境变量里的 npm token 和钱包地址并发到外部。事件持续了两个多月才被发现。

教训有三条。传递依赖的 `postinstall` 也会执行，你在 `package.json` 里看不到它；`pnpm why` 输出里出现陌生的小包是一个信号；`devDependencies` 也会中招，因为攻击者要的是维护者机器上的 token，生产环境并非目标。

2022 年 colors 和 faker。作者对项目被商业公司使用不满，在 1.4.44 版本里加了无限循环，任何调用都会卡死。锁文件写着 `^1.4.43` 的项目，删掉锁文件重装就会拿到 1.4.44。

教训：`^` 允许自动安装新的补丁版本，补丁版本不保证行为兼容；锁文件是防线，但有人会删掉它重装；CI 里 `--frozen-lockfile` 能挡住意外升级，挡不住有人主动更新。

2022 年 node-ipc。作者在 11.0.2 里加了条件性破坏代码，检测到特定地区的 IP 就覆盖文件。这次是补丁版本里的行为变化，没有被任何漏洞库收录。

教训：升级补丁版本也要跑测试；锁文件 diff 要有人看；单点依赖（只此一家的基础库）要有替代方案预案。

三个案例的共同点：出问题的都是没直接 import 的包，或者被间接依赖的包。防线只能是流程，不能靠代码审查。

## 44.11 私有源与镜像

国内访问 npm 官方源慢，常见做法是换 npmmirror。

```bash
# .npmrc
registry=https://registry.npmmirror.com
```

代价有两个。

一是延迟。镜像同步有分钟级延迟，刚发布的版本可能拿不到。

二是审计接口。部分镜像没有实现 `/-/npm/v1/security/audits`，`pnpm audit` 会失败。解决办法是审计时指定官方源。

```bash
pnpm audit --registry https://registry.npmjs.org/
```

私有包用 scope 分开。

```ini
# .npmrc
registry=https://registry.npmmirror.com
@teamstack:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NPM_TOKEN}
```

token 不要写进 `.npmrc` 提交，用环境变量注入。CI 里从 secret 读。

## 44.12 CI 里的四道门禁

把前面几节变成每次提交都跑的检查。

```yaml
# .github/workflows/deps.yml
name: Dependencies

on:
  pull_request:
  schedule:
    - cron: "0 3 * * 1"

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 10.12.1
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: "pnpm"

      - run: pnpm install --frozen-lockfile

      - name: Audit
        run: pnpm audit --prod --audit-level=high --registry https://registry.npmjs.org/

      - name: Lockfile unchanged
        run: git diff --exit-code pnpm-lock.yaml
```

四件事：安装用 frozen，审计只看生产依赖的 high 以上，锁文件和提交一致，pnpm 版本固定。

第一次接入审计，构建几乎一定会红。这是正常的，历史遗留的漏洞需要时间清理。处理顺序：先看有几条 high，按 `fixAvailable` 分成「能直接升」和「还没修复」两组，能升的当天处理，没修复的写进文档并设定期限。

确需豁免的项目，在 `package.json` 里配置忽略列表。

```json
{
  "pnpm": {
    "auditConfig": {
      "ignoreCves": ["CVE-2024-xxxxx"]
    }
  }
}
```

未验证：`ignoreCves` 的字段名以 pnpm 10 的实际文档为准。豁免必须有人复查，每条豁免写清理由和到期时间，否则半年后没人知道为什么忽略它。

## 44.13 边界与失败模式

依赖管理有几个容易忽略的边界。

工作区（monorepo）里，`pnpm-lock.yaml` 只有一个，放在根目录。子包的 `package.json` 改动都要重新 install 并提交根锁文件。

`onlyBuiltDependencies` 只在 `pnpm-workspace.yaml` 里生效，放进 `package.json` 的 `pnpm` 字段无效。这个坑很常见，表现是构建时 `sharp` 找不到。

`pnpm up` 会连带升级范围内的其他包。升级单个包用 `pnpm up <包名>`，不要用 `pnpm up` 全量升。

`overrides` 会覆盖所有依赖链，包括你想保留旧版本的地方。写窄范围，加期限，到期复查。

替换源（`resolutions` 或 `overrides` 指向 git 仓库或 tarball 地址）会让 `--frozen-lockfile` 校验失效，因为地址采用非标准 registry 格式。这类替换要尽量避免。

CI 的 `node_modules` 缓存按锁文件哈希命中。锁文件一改，缓存全部失效，构建时间会变长。这是正常代价，不要为了缓存命中而跳过 install。

## 44.14 检查点

1. 跑 `pnpm audit --prod --audit-level=high`，输出为空（退出码 0）。有输出的话，每条都要能说出处理方式：已升级、用 overrides 覆盖、还是写进了豁免文档。

2. 在一个干净目录验证可复现安装：

```bash
rm -rf node_modules
pnpm install --frozen-lockfile
pnpm build
```

两件事都要过：安装不报 `ERR_PNPM_OUTDATED_LOCKFILE`，构建不报缺原生模块。

3. 随便挑一个直接依赖，能回答四个问题：谁维护、多大、拉进来几个包、什么许可证。答不上来的去查，`pnpm why` 和 `npm view` 各一条命令。

4. 改一行 `package.json` 里的版本号，不更新锁文件，跑 `pnpm install --frozen-lockfile`，应当失败。这说明门禁有效。

5. 能说出你项目里哪三处是供应链的高风险位置（服务端依赖、处理用户输入的库、有安装脚本的包），以及各自的缓解措施。

## 44.15 常见错误

**1. `ERR_PNPM_OUTDATED_LOCKFILE  Cannot install with "frozen-lockfile" because pnpm-lock.yaml is not up to date with package.json`**

现象：CI 安装阶段直接失败。
原因：有人改了 `package.json` 没提交锁文件，或者手工编辑过锁文件。
改法：本机跑 `pnpm install`，把 `pnpm-lock.yaml` 一起提交。不要用 `--no-frozen-lockfile` 绕过。

**2. `ERR_PNPM_NO_MATCHING_VERSION  No matching version found for lodash@4.17.30`**

现象：安装时找不到指定版本。
原因：`overrides` 里写的版本不存在，或者镜像源还没同步。
改法：`npm view lodash versions` 看可用版本；确认版本号写对；换官方源重试。

**3. `Ignored build scripts: esbuild, sharp. Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.`**

现象：安装成功但运行时报缺模块。
原因：pnpm 10 默认不执行依赖的安装脚本，原生模块没编译。
改法：在 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies` 里加入这几个包；或本地跑 `pnpm approve-builds` 交互批准。

**4. `Cannot find module 'sharp'` 或 `sharp: Installation error: ...`**

现象：构建或运行时报 sharp 找不到。
原因：安装脚本被忽略；或 `onlyBuiltDependencies` 写在了 `package.json` 里，未写进 `pnpm-workspace.yaml`。
改法：把允许列表移到 `pnpm-workspace.yaml`，删 `node_modules` 重装。Docker 里还要确认 `pnpm-workspace.yaml` 已复制进镜像。

**5. `ERR_PNPM_AUDIT_BAD_RESPONSE  The audit endpoint returned an unexpected response`**

现象：`pnpm audit` 在 CI 里报错，或者返回 HTML。
原因：当前 registry（镜像源或私有源）没实现审计接口。
改法：审计命令加 `--registry https://registry.npmjs.org/`，只让审计走官方源。

**6. `Failed to find Server Action "xxx". This request might be from an older or newer deployment.`**

现象：用户提交表单时报这个错，刷新后又能用。
原因：多实例部署时 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 每个实例不同，或者发版期间新旧实例同时在线。
改法：在环境变量里固定一个 32 字节的密钥，所有实例共用；发版时先起新实例再杀旧实例。

## 44.16 这一章在做什么

这一章把依赖当成会变的外部输入来管理，不能装一次就不管。

三个动作是核心。锁文件进仓库，CI 用 `--frozen-lockfile`，让每次构建装的包完全一致。`pnpm audit --prod --audit-level=high` 进 CI，让高危漏洞在合并前暴露。安装脚本显式批准，让 `postinstall` 不再有静默执行的机会。

剩下的都是判断。传递依赖要不要修、用 overrides 还是换库、补丁版本能不能自动升、新依赖值不值得加，这些没有统一答案，只能按「攻击面大小 × 出事后的损失」来估。

下一章是本书的最后一章，讲流式输出和 MCP。两件事都和接口行为有关：怎么把一个大模型的回答边生成边发给浏览器，以及怎么用 Next.js 自带的开发工具让编码代理读懂你的项目。依赖这章的原则在那一章同样适用：任何外部服务都当作不可靠输入处理。
