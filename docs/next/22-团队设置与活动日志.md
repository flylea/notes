# 第 22 章 团队设置与活动日志

团队设置页看起来只是一个表单页，实际要处理四类问题：页面在加载、出错、为空、有数据时分别显示什么；活动日志如何保证只追加；当前团队从哪里来，查询怎样按租户隔离；哪些操作只有所有者能做。

这一章涉及四个概念：路由段状态文件（`loading.tsx`、`error.tsx`）、只追加的审计表、cookie 偏好与成员校验的配合、数据库事务与唯一索引。

前置条件如下：第 8 章建好的表结构，第 15 章的 `requireUser()`，第 9 章的 Kysely 连接。项目目录是 `teamstack`，代码在 `src/` 下。

## 22.1 一个页面有四种状态

凡是需要查数据库的页面，都在四种状态之间切换：

| 状态 | 触发条件 | 界面上该有什么 |
| --- | --- | --- |
| 加载 | 请求还没回来 | 骨架，形状接近真实内容 |
| 错误 | 查询抛异常、权限失败 | 一句人话、错误编号、重试按钮 |
| 空 | 查询成功但返回 0 行 | 解释为什么空、下一步做什么 |
| 有数据 | 查询成功且有行 | 正常内容 |

框架负责前两种的默认值，后两种要自己写进页面。最容易被吃掉的是“空”：`if (!data) return null` 会把加载、错误、空压成同一块白屏。用户分不清发生了什么，排错的人也分不清。

四种状态的代码归位方式不同。加载状态放在路由段的 `loading.tsx`，错误状态放在 `error.tsx`，空状态写在页面组件内部，有数据状态就是默认渲染结果。

这四种状态并非同一层的东西。加载和错误由路由段文件接管，空和有数据由页面组件的返回值决定。把它们混成一个 `if` 分支，是新手最常见的写法：

```tsx
// 反例，不要这样写
const data = await load()
if (!data) return null
```

`data` 为 `null` 时页面是白屏，用户不知道是在加载、出错，还是本来就没有数据。三种情况要三种不同的界面，判断条件就不能合并。

## 22.2 加载态与错误态

`loading.tsx` 由框架自动包一层 Suspense。导航到该路由段时，框架先发送这份 UI。

```tsx
// src/app/(dashboard)/settings/team/loading.tsx
export default function Loading() {
  return (
    <div className="mx-auto max-w-3xl animate-pulse space-y-6 p-6">
      <div className="h-8 w-48 rounded bg-gray-200" />
      <div className="h-10 w-full rounded bg-gray-200" />
      <div className="h-40 w-full rounded bg-gray-200" />
    </div>
  )
}
```

骨架要占住最终内容的位置，宽高和间距与真实页面一致。数据回来时整块替换，页面不跳动。用全页转圈代替骨架会带来重排：用户的手指可能正好点在刚移过来的按钮上。

`loading.tsx` 只覆盖跨路由导航。页内提交表单走 Server Action，不会触发它，这段等待要用 `useActionState` 的 `pending` 自己画。

错误边界放在同一层：

```tsx
// src/app/(dashboard)/settings/team/error.tsx
'use client'

export default function TeamSettingsError({
  error,
  reset,
}: {
  error: Error & { digest?: string }
  reset: () => void
}) {
  return (
    <div className="mx-auto max-w-3xl space-y-4 p-6">
      <h2 className="text-xl font-semibold">团队设置没能加载出来</h2>
      <p className="text-sm text-gray-600">
        可能是网络抖动，也可能是你没有这个团队的访问权限。
      </p>
      {error.digest && (
        <p className="text-xs text-gray-400">错误编号：{error.digest}</p>
      )}
      <button
        onClick={() => reset()}
        className="rounded bg-black px-4 py-2 text-sm text-white"
      >
        重试
      </button>
    </div>
  )
}
```

它有三个硬性要求：必须是客户端组件；必须接收 `error` 和 `reset`；必须放在要捕获错误的那一层路由段。它捕获渲染、数据获取、Server Action 抛出的异常，捕获不到事件处理器里的异常，也接不住 `notFound()`。

错误页不要渲染 `error.message`。生产环境的错误信息可能带表名、SQL 片段、文件路径。给用户一句人话加 `digest`，完整堆栈去服务端日志按 `digest` 查。

错误边界的粒度按路由段选。放在根布局，一个小组件出错整站白屏；放在每个页面，页面之间互不影响。团队设置页的做法是页面级一个，表单级不再另设：表单错误用返回值画红字，不用抛异常。异常留给“真出事了”的情况，业务规则用返回值表达。

骨架实际有两份：`loading.tsx` 一份，页面里 `<Suspense fallback>` 一份。前者管跨路由导航，后者管该路由首次渲染。两份长得一样是刻意的，用户不该察觉中间换过一次。内容多起来后把骨架抽成组件，避免两份慢慢漂移。

## 22.3 日志表只允许插入

活动日志的用途是事后回答“当时谁做了什么”。它要能当证据，证据的第一要求是不能改。这个规则先写进数据库，再写页面。

迁移文件：

```sql
-- supabase/migrations/20261120100000_team_settings.sql

-- 浏览器侧角色只能读日志，不能改、不能删。
revoke update, delete on public.activity_logs from anon, authenticated;

-- 查“某个人在这个团队做了什么”。
create index if not exists activity_logs_team_actor_idx
  on public.activity_logs (team_id, actor_id, created_at desc);

-- 查“某个对象的历史”。
create index if not exists activity_logs_team_target_idx
  on public.activity_logs (team_id, target_type, target_id, created_at desc);
```

应用迁移：

```bash
pnpm supabase db reset
```

`db reset` 会重放全部迁移再灌 seed，本地数据会清空。只想增量应用时用 `pnpm supabase migration up`。

用 psql 验证权限：

```bash
psql "$DATABASE_URL"
```

```sql
update public.activity_logs set action = 'hacked' where true;
```

输出：

```text
ERROR:  permission denied for table activity_logs
```

`delete` 同样被拒。`anon` 和 `authenticated` 是浏览器侧角色，已经没有改和删的权限。服务端连接是表所有者，不受这条规则影响，第 27 章的清理任务会用到这个差别。

只靠界面不画按钮不够。任何人拿到 publishable key 都能直接打 PostgREST 的 `PATCH` 和 `DELETE`，权限必须收在数据库这一层。

不加触发器拦截改删，原因是第 27 章要按保留期删除旧日志。触发器会把清理任务一起拦死，到时候只能临时 `disable trigger`，风险更大。`revoke` 已经挡住了所有外部角色。

追加语义还有两个细节。其一，日志允许补写“当时没记全”的字段，例如事后补上对象名称，这属于新增行或在同一事务里改还没提交的行，不改历史。其二，日志的查询只读，界面不提供任何写入口，运营需要的“标注误操作”放在另一张表，不动原始记录。

日志会一直增长。一个团队每天几十条，一年上万行，按 `created_at` 排序不加索引会越来越慢。复合索引的列顺序跟查询的排序一致：`(team_id, created_at desc)` 能直接支撑按团队的倒序扫描，`(team_id, actor_id, created_at desc)` 支撑按人的过滤。

主键 `id` 不参与索引排序，但游标分页的次要排序需要它。列表查询统一按 `created_at desc, id desc`，索引的最后可以再补 `id`，数据量大时能省一次排序。第 27 章会加清理任务，把超过 180 天的记录归档后删除。它删的是“老的”，不修改“某一条”，仍然符合只追加的语义。

### 22.3.1 RLS 是第二道防线

`revoke` 管住改和删，读还要靠 RLS。第 15 章给九张表都开了 RLS，这里补上 `activity_logs` 的读策略，追加到同一个迁移文件：

```sql
-- supabase/migrations/20261120100000_team_settings.sql（追加）

drop policy if exists "members can read team activity" on public.activity_logs;

create policy "members can read team activity"
  on public.activity_logs
  for select
  to authenticated
  using (
    exists (
      select 1
      from public.team_members m
      where m.team_id = activity_logs.team_id
        and m.user_id = (select auth.uid())
    )
  );
```

用 publishable key 直接请求 PostgREST 验证：

```bash
curl "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/activity_logs?select=team_id,action&limit=5" \
  -H "apikey: $NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY" \
  -H "Authorization: Bearer $NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY"
```

返回结果只包含你所在团队的记录。把 `team_id=eq.<别家 id>` 加进查询串，返回空数组。

`(select auth.uid())` 外面那层括号有用。直接写 `auth.uid()` 时，Postgres 可能逐行求值；包成子查询后按常量处理，只算一次。表大了以后，这个差别按行数放大。

应用层的 `where team_id = ?` 仍然要写。服务端连接是表所有者，绕过 RLS，RLS 管不到它。两层管的是两条路：

| 防线 | 管住谁 | 失效方式 |
| --- | --- | --- |
| 应用层 `where team_id = ?` | 服务端自己的查询 | 漏写条件、参数传错 |
| RLS 策略 | 浏览器直连 PostgREST | 服务端特权连接 |

失效原因不同，所以不能互相替代。

## 22.4 写日志收成一个函数

日志必须和业务变更在同一个事务里。先改名再插日志，中间崩溃会出现“改了没记录”；先插日志再改名，会出现“有记录但没改成”。两种都会让日志失去证据价值。

```ts
// src/lib/activity.ts
import type { Kysely } from 'kysely'
import type { Database } from '@/lib/db'
import { db } from '@/lib/db'

export interface ActivityInput {
  teamId: string
  actorId: string | null
  action: string
  targetType?: string | null
  targetId?: string | null
  metadata?: Record<string, unknown>
}

// 传 db 是独立写入，传事务对象 trx 就跟业务一起提交。
type Executor = Kysely<Database>

export async function logActivity(executor: Executor, input: ActivityInput) {
  await executor
    .insertInto('activity_logs')
    .values({
      team_id: input.teamId,
      actor_id: input.actorId,
      action: input.action,
      target_type: input.targetType ?? null,
      target_id: input.targetId ?? null,
      metadata: input.metadata ?? {},
    })
    .execute()
}

export function logActivityNow(input: ActivityInput) {
  return logActivity(db, input)
}
```

`action` 用点号分层，例如 `team.renamed`、`team.owner_transferred`、`member.joined`。它给查询和统计用，要稳定，别把变量拼进去。细节放 `metadata`。

`metadata` 用 `jsonb`，因为每种动作要记的字段不同：改名记 `from` 和 `to`，邀请记 `email` 和 `role`。给每种动作加一列，这张表会变成竖着长的稀疏表，每加一个动作都要改结构。

日志写失败时，业务应该一起失败。同一个事务里插日志失败，通常意味着表结构、权限或连接出了问题，让改名也失败比留下无法追溯的变更更好。代价是日志表的可用性变成了写操作的可用性，这个项目可以接受。

“顺便记一下”的行为不要进这张表。审计要求不丢，统计允许丢，两者分开。

日志写入只暴露一个函数，调用方不直接写表。这样以后要加字段、改 `action` 命名、加采样，只改一处。函数签名里 `actorId` 允许 `null`，是因为删号后外键会置空，历史记录仍然保留行为，只是不知道是谁做的。

`target_id` 不加外键。对象可能已被删除，加外键会让删除失败，或者级联把日志一起删掉。日志要活到对象消失之后，它存的是当时的 id。

## 22.5 当前团队从哪里来

日志页按团队过滤，先要确定当前团队。团队切换器把选中的团队 id 存进 cookie。cookie 用户可以随便改，所以不能直接当查询条件。

正确顺序是三步：读 cookie 拿候选 id；用当前用户 id 去 `team_members` 确认成员关系；用查出来的团队 id 查业务数据。

这套逻辑收进一个文件，后面各章都从这里取团队。

```ts
// src/lib/teams.ts
import 'server-only'
import { cache } from 'react'
import { cookies } from 'next/headers'
import { notFound, redirect } from 'next/navigation'
import { db } from '@/lib/db'
import { getCurrentUser, requireUser } from '@/lib/auth'

export const ACTIVE_TEAM_COOKIE = 'active_team_id'

export type TeamRole = 'owner' | 'member'
export type TeamPlan = 'free' | 'pro' | 'team'

export interface ActiveTeam {
  id: string
  name: string
  slug: string
  plan: TeamPlan
  role: TeamRole
}

async function findTeamForUser(userId: string, teamId?: string) {
  let query = db
    .selectFrom('team_members as m')
    .innerJoin('teams as t', 't.id', 'm.team_id')
    .select(['t.id', 't.name', 't.slug', 't.plan', 'm.role'])
    .where('m.user_id', '=', userId)
    .where('t.deleted_at', 'is', null)

  if (teamId) query = query.where('t.id', '=', teamId)

  const row = await query.orderBy('m.created_at', 'asc').executeTakeFirst()
  if (!row) return null

  return {
    id: row.id,
    name: row.name,
    slug: row.slug,
    plan: row.plan as TeamPlan,
    role: row.role as TeamRole,
  }
}

// 一次渲染里可能调用多次，cache() 让查询只执行一次。
export const getActiveTeam = cache(async (): Promise<ActiveTeam | null> => {
  const user = await getCurrentUser()
  if (!user) return null

  const cookieStore = await cookies()
  const fromCookie = cookieStore.get(ACTIVE_TEAM_COOKIE)?.value

  if (fromCookie) {
    const team = await findTeamForUser(user.id, fromCookie)
    // cookie 指向的团队已不属于该用户，回退到第一个团队。
    if (team) return team
  }

  return findTeamForUser(user.id)
})

export async function requireTeam(): Promise<ActiveTeam> {
  const team = await getActiveTeam()
  if (!team) redirect('/onboarding')
  return team
}

// 需要指定团队时用它，不要相信传进来的 id。
export async function requireMembership(teamId: string) {
  const user = await requireUser()
  const row = await db
    .selectFrom('team_members')
    .select(['team_id', 'role'])
    .where('team_id', '=', teamId)
    .where('user_id', '=', user.id)
    .executeTakeFirst()

  if (!row) notFound()
  return { teamId: row.team_id, role: row.role as TeamRole }
}
```

`cache()` 只在一次渲染过程里去重。Server Action 和 Route Handler 不在渲染过程里，每次调用都会真查一次库。这是必要的：action 可以被任何人直接 POST，必须重新验证身份和成员关系。

### 22.5.1 租户过滤的第一条件是 team_id

多租户系统里，业务查询的第一个条件都该是 `team_id`。按 `actor_id` 查询会把多个团队的数据混在一起：

```sql
-- 错误示范：这是“我的活动”，并非“这个团队的活动”。
select team_id, action, created_at
from public.activity_logs
where actor_id = '<user_id>'::uuid
order by created_at desc;
```

正确写法是先确定租户，再谈人：

```sql
select team_id, action, created_at
from public.activity_logs
where team_id = '<team_id>'::uuid
order by created_at desc, id desc;
```

确实需要“我的活动”时，两个条件都写：`team_id = $1 and actor_id = $2`。

切换团队的 action 只写 cookie，不碰数据库：

```ts
// src/app/(dashboard)/settings/team/switch-team-action.ts
'use server'

import { cookies } from 'next/headers'
import { redirect } from 'next/navigation'
import { db } from '@/lib/db'
import { requireUser } from '@/lib/auth'
import { ACTIVE_TEAM_COOKIE } from '@/lib/teams'

export async function switchTeam(teamId: string) {
  const user = await requireUser()

  const membership = await db
    .selectFrom('team_members')
    .select('team_id')
    .where('user_id', '=', user.id)
    .where('team_id', '=', teamId)
    .executeTakeFirst()

  if (!membership) return

  const cookieStore = await cookies()
  cookieStore.set(ACTIVE_TEAM_COOKIE, teamId, {
    httpOnly: true,
    sameSite: 'lax',
    path: '/',
    maxAge: 60 * 60 * 24 * 30,
  })

  redirect('/dashboard')
}
```

不存在的团队直接返回，不写 cookie。用户从别处粘贴一个 id 进来，也不该得到“已切换”的假象。`httpOnly` 让脚本读不到这个 cookie，减少 XSS 顺手改租户的机会。

## 22.6 活动日志页

页面分页用游标，不用 `offset`。日志一直在写，`offset 20` 在翻页时可能因为新增记录而重复或漏行。游标带上上一页最后一条的 `(created_at, id)`，中间插入多少条都从那个位置往后接。

```tsx
// src/app/(dashboard)/settings/team/activity/page.tsx
import Link from 'next/link'
import { Suspense } from 'react'
import { db } from '@/lib/db'
import { requireTeam } from '@/lib/teams'

const PAGE_SIZE = 20

const ACTION_LABELS: Record<string, string> = {
  'team.renamed': '修改了团队名',
  'team.owner_transferred': '转移了所有权',
  'member.joined': '加入了团队',
  'invitation.created': '发出了邀请',
}

type ActivitySearchParams = Promise<{ before?: string }>

export default function ActivityPage({
  searchParams,
}: {
  searchParams: ActivitySearchParams
}) {
  return (
    <div className="mx-auto max-w-3xl space-y-6 p-6">
      <div className="flex items-center justify-between">
        <h1 className="text-2xl font-semibold">活动日志</h1>
        <Link href="/settings/team" className="text-sm text-blue-600">
          返回团队设置
        </Link>
      </div>
      <Suspense fallback={<ActivitySkeleton />}>
        <ActivityList searchParams={searchParams} />
      </Suspense>
    </div>
  )
}

function decodeCursor(value?: string) {
  if (!value) return null
  const index = value.lastIndexOf('_')
  if (index < 0) return null
  const createdAt = new Date(value.slice(0, index))
  const id = value.slice(index + 1)
  if (Number.isNaN(createdAt.getTime()) || !id) return null
  return { createdAt, id }
}

async function ActivityList({
  searchParams,
}: {
  searchParams: ActivitySearchParams
}) {
  const team = await requireTeam()
  const { before } = await searchParams
  const cursor = decodeCursor(before)

  let query = db
    .selectFrom('activity_logs as l')
    .leftJoin('profiles as p', 'p.id', 'l.actor_id')
    .select([
      'l.id',
      'l.action',
      'l.target_type',
      'l.target_id',
      'l.metadata',
      'l.created_at',
      'p.full_name',
      'p.email',
    ])
    .where('l.team_id', '=', team.id)
    .orderBy('l.created_at', 'desc')
    .orderBy('l.id', 'desc')
    .limit(PAGE_SIZE + 1)

  if (cursor) {
    query = query.where((eb) =>
      eb.or([
        eb('l.created_at', '<', cursor.createdAt),
        eb.and([
          eb('l.created_at', '=', cursor.createdAt),
          eb('l.id', '<', cursor.id),
        ]),
      ]),
    )
  }

  const rows = await query.execute()
  const hasMore = rows.length > PAGE_SIZE
  const items = hasMore ? rows.slice(0, PAGE_SIZE) : rows

  if (items.length === 0 && !cursor) {
    return <EmptyState />
  }

  const last = items.at(-1)
  const nextHref = last
    ? `/settings/team/activity?before=${encodeURIComponent(
        `${last.created_at.toISOString()}_${last.id}`,
      )}`
    : null

  return (
    <div className="space-y-4">
      <ol className="divide-y rounded-lg border">
        {items.map((item) => (
          <li key={item.id} className="space-y-1 p-4">
            <p className="text-sm">
              <span className="font-medium">
                {item.full_name || item.email || '已注销用户'}
              </span>{' '}
              {ACTION_LABELS[item.action] ?? item.action}
            </p>
            <p className="text-xs text-gray-400">
              {new Intl.DateTimeFormat('zh-CN', {
                dateStyle: 'medium',
                timeStyle: 'short',
                timeZone: 'Asia/Shanghai',
              }).format(item.created_at)}
            </p>
          </li>
        ))}
      </ol>
      <div className="flex justify-between text-sm">

        </Link>

          <Link href={nextHref} className="text-blue-600">

          </Link>
        )}
      </div>
    </div>
  )
}

  return (

```

`action` 存稳定标识，界面用 `ACTION_LABELS` 翻译。表里查不到的动作原样显示键名，这样新动作上线时旧页面不会白屏。

每一行可以展开看 `metadata`，但默认收起。日志列表是扫读场景，一屏二十行，每条都摊开 JSON 会让人找不到重点。详情里只显示白名单字段，避免把内部 id、token 之类的东西渲染出来。

这一页没有编辑、没有删除、没有勾选框。产品定义就是这样，并非漏做。

日期格式化固定 `Asia/Shanghai` 和 `zh-CN`，否则服务端与浏览器的时区不同，同一行会显示两个时间。

访问控制放在数据查询之前。`requireTeam()` 已经确认当前用户是团队成员，查不到团队时跳转引导页。对不属于自己的团队，接口层统一返回 404，不用 403：403 等于告诉对方“这个团队存在，只是你看不了”，多租户系统里这本身就是信息泄露。

空状态要回答三个问题：这里会出现什么；为什么现在是空的；用户能做什么。缺第三个就只是一句废话。成员列表、文件列表、邀请列表都有空状态，后面会抽成 `EmptyState` 组件，这里先写成页面内的局部组件。

## 22.7 改团队名

改名的完整流程分六步：校验身份、校验角色、校验输入、查重名、事务写入、写日志。

```ts
// src/app/(dashboard)/settings/team/actions.ts
'use server'

import { db } from '@/lib/db'
import { logActivity } from '@/lib/activity'
import { requireUser } from '@/lib/auth'
import { requireTeam } from '@/lib/teams'

export interface TeamNameState {
  error?: string
  ok?: boolean
}

export async function updateTeamName(
  _prev: TeamNameState,
  formData: FormData,
): Promise<TeamNameState> {
  const user = await requireUser()
  const team = await requireTeam()

  if (team.role !== 'owner') {
    return { error: '只有所有者可以修改团队名' }
  }

  const name = String(formData.get('name') ?? '').trim()
  if (name.length < 1 || name.length > 60) {
    return { error: '团队名需要 1 到 60 个字符' }
  }
  if (name === team.name) return { ok: true }

  try {
    await db.transaction().execute(async (trx) => {
      await trx
        .updateTable('teams')
        .set({ name })
        .where('id', '=', team.id)
        .execute()

      await logActivity(trx, {
        teamId: team.id,
        actorId: user.id,
        action: 'team.renamed',
        targetType: 'team',
        targetId: team.id,
        metadata: { from: team.name, to: name },
      })
    })
  } catch (error) {
    if ((error as { code?: string }).code === '23505') {
      return { error: '这个名字已经被别的团队用了' }
    }
    throw error
  }

  return { ok: true }
}
```

校验的边界：`trim()` 放在长度检查之前，复制粘贴常带前后空格；上限 60 与数据库的 `check (char_length(btrim(name)) between 1 and 60)` 保持一致；字符数按 Unicode 字符算，不要用字节数。

重名检查交给唯一约束，不要先查再写。先查再写有竞态窗口，两个人同时改成同一个名字仍会撞车。`teams_name_active_uniq` 是第 8 章建的 `lower(name)` 部分唯一索引，所以 `Acme` 和 `acme` 算同一个名字。数据库返回 `23505`，这里翻译成人话。

改名不动 `slug`。`slug` 在 URL 和邀请链接里，已经发出的邮件带着它，改了会有一批链接失效。名字给人看，`slug` 给地址用。

这里没有 `revalidatePath`。页面渲染时读了 cookie 和数据库，属于动态渲染，Server Action 返回后框架会重新渲染当前路由。只有 `use cache` 的数据和静态页面才需要显式失效。

并发提交由唯一索引兜底。两个人同时把团队改成同一个名字，第二条会拿到 `23505`，返回红字。不先查再写，是因为查和写之间的窗口足以让两条请求都通过检查。

### 22.7.1 乐观更新

默认情况下要等服务端返回，标题才变。慢网络下这两秒很明显。用 `useOptimistic` 让界面先相信用户：

```tsx
// src/app/(dashboard)/settings/team/team-name-form.tsx
'use client'

import { useActionState, useOptimistic } from 'react'
import { updateTeamName, type TeamNameState } from './actions'

const initialState: TeamNameState = {}

export function TeamNameForm({
  name,
  canEdit,
}: {
  name: string
  canEdit: boolean
}) {
  const [state, formAction, pending] = useActionState(
    updateTeamName,
    initialState,
  )
  const [optimisticName, setOptimisticName] = useOptimistic(name)

  return (
    <form
      action={(formData) => {
        const next = String(formData.get('name') ?? '').trim()
        // 先更新界面，再把请求发出去。
        if (next) setOptimisticName(next)
        formAction(formData)
      }}
      className="space-y-2"
    >
      <div className="flex items-end gap-3">
        <label className="flex-1 space-y-1">
          <span className="text-sm text-gray-600">团队名</span>
          <input
            name="name"
            defaultValue={name}
            disabled={!canEdit || pending}
            maxLength={60}
            className="w-full rounded border px-3 py-2 disabled:bg-gray-50"
          />
        </label>
        <button
          type="submit"
          disabled={!canEdit || pending}
          className="rounded bg-black px-4 py-2 text-sm text-white disabled:opacity-50"
        >
          {pending ? '保存中…' : '保存'}
        </button>
      </div>
      <p className="text-xs text-gray-500">当前显示：{optimisticName}</p>
      {state.error && <p className="text-sm text-red-600">{state.error}</p>}
      {state.ok && <p className="text-sm text-green-700">已保存</p>}
    </form>
  )
}
```

三个约束：

`setOptimisticName` 必须在 action 或 transition 里调用。放进 `onClick` 会抛 `An optimistic state update occurred outside a transition or action.`。`<form action>` 的函数体在 transition 里执行，所以合法。

action 结束后，乐观值回到真实值。成功时是新名字，失败时是旧名字，回滚由 React 处理，不需要手写。

输入框用 `defaultValue`，不用受控值。用户打字时被一次渲染覆盖掉输入是最烦的 bug。

`pending` 期间禁用按钮和输入框，防止连点两次。第二次请求可能先到，最终名字会变成第一次提交的值。

## 22.8 转移所有权

转移比改名危险。降级旧所有者成功、升级新所有者失败，团队就没有 owner 了：没人能改设置、没人能转移、没人能删团队。两条语句必须在一个事务里。

```ts
// src/app/(dashboard)/settings/team/actions.ts（追加）
export interface TransferState {
  error?: string
  ok?: boolean
}

export async function transferOwnership(
  _prev: TransferState,
  formData: FormData,
): Promise<TransferState> {
  const user = await requireUser()
  const team = await requireTeam()

  if (team.role !== 'owner') {
    return { error: '只有所有者可以转移所有权' }
  }

  const nextOwnerId = String(formData.get('userId') ?? '')
  if (!nextOwnerId || nextOwnerId === user.id) {
    return { error: '请选择另一位成员' }
  }

  try {
    await db.transaction().execute(async (trx) => {
      const target = await trx
        .selectFrom('team_members')
        .select('role')
        .where('team_id', '=', team.id)
        .where('user_id', '=', nextOwnerId)
        .executeTakeFirst()

      if (!target) throw new Error('NOT_A_MEMBER')

      // 先降级旧所有者，再升级新所有者。
      await trx
        .updateTable('team_members')
        .set({ role: 'member' })
        .where('team_id', '=', team.id)
        .where('user_id', '=', user.id)
        .execute()

      await trx
        .updateTable('team_members')
        .set({ role: 'owner' })
        .where('team_id', '=', team.id)
        .where('user_id', '=', nextOwnerId)
        .execute()

      await logActivity(trx, {
        teamId: team.id,
        actorId: user.id,
        action: 'team.owner_transferred',
        targetType: 'team',
        targetId: team.id,
        metadata: { from: user.id, to: nextOwnerId },
      })
    })
  } catch (error) {
    if (error instanceof Error && error.message === 'NOT_A_MEMBER') {
      return { error: '对方已经不在这个团队里了' }
    }
    throw error
  }

  return { ok: true }
}
```

顺序不能换。先升级新所有者时，第一条语句执行完的瞬间团队有两个 owner，`team_members_one_owner` 这个部分唯一索引会拒绝。先降后升，中间那一瞬是零 owner，索引允许，事务兜底。

两个约束合起来才完整：唯一索引保证任何时刻最多一个 owner，事务保证提交后不会零个 owner。

表单：

## 22.9 边界与失败模式

**cookie 被篡改**。把 `active_team_id` 改成别家团队的 id，`findTeamForUser` 查不到成员关系，回退到自己的第一个团队。界面不会跳到别家，也不会报错。

**`cache()` 的边界**。`getActiveTeam` 在一次渲染里只查一次库。同一个请求里的多个组件可以放心调用。跨请求不会共享，Server Action 里调用会重新查库。

读 cookie 的组件必须在 Suspense 边界内。开启 Cache Components 后，读 `cookies()` 的组件不在边界内是构建错误。所以页面外壳保持同步，异步内容包在 `<Suspense>` 里。

**日志保留与清理**。日志按保留期删除，不提供单条删除。删除由第 27 章的定时任务分批执行，每批几千行，走 `created_at` 索引。

**游标失效**。用户会手改 URL、收藏旧链接、在两版部署之间切换。解不出来的游标回第一页，不要抛错。筛选或排序变化时也要清掉游标，否则旧位置在新排序里没有意义。

**错误信息泄露**。生产环境不把 `error.message` 渲染到页面。它可能带表名、SQL、文件路径。用户看到 `digest`，开发者按 `digest` 查服务端日志。

**权限判定放在服务端**。`canEdit` 只用来禁用控件，真正的判定在 action 里重做一次。前端禁用挡不住直接 POST。

名字与 `slug` 不一致。改名后 URL 还是旧的 `slug`。这是刻意的：`slug` 一旦发出去就是外部地址，改它等于让所有书签和邮件里的链接失效。需要“地址也跟着名字走”的产品，要单独做跳转表和过渡期。

**团队只剩一个所有者**。转移所有权前要确认新所有者还在团队里。目标成员刚被移出、页面还没刷新时提交，事务里的成员查询返回空，action 返回“对方已经不在这个团队里了”，原所有者身份保持不变。

## 22.10 检查点

1. 用 publishable key 直接发 `PATCH /rest/v1/activity_logs?id=eq.<某条日志>`，返回 401/403 或影响行数为 0；页面里找不到编辑、删除入口。
2. 账号同时属于 A、B 两个团队，在 A 团队触发一条日志，切到 B 团队打开 `/settings/team/activity`，看不到那条记录；把 `active_team_id` 改成不存在的 uuid，页面回退到第一个团队。
3. 改团队名后，`activity_logs` 里出现一条 `team.renamed`，`metadata` 含 `from` 和 `to`；改成另一个团队已用的名字，表单出现红字“这个名字已经被别的团队用了”。
4. 提交改名时，标题立刻变成新名字；请求返回后按钮恢复；名字重复时标题回到旧值。
5. 转移所有权后，原所有者刷新页面，改名表单变成只读；把目标成员先移出团队再转移，返回“对方已经不在这个团队里了”，原所有者身份不变。
6. 执行 `pnpm build`，`/settings/team` 相关路由构建通过，没有 cookie 边界错误。

## 22.11 常见错误

`Error: cookies() was called outside a request scope.`

在模块顶层调用 `getActiveTeam()`，或把它放进普通工具函数、`generateStaticParams`。`cookies()` 只能在请求上下文里用。改法：只在页面、Server Action、Route Handler 内调用，页面里放进 `<Suspense>` 边界。

`Error: An optimistic state update occurred outside a transition or action.`

在 `onClick` 里直接调 `setOptimisticName`。改法：把更新放进 `<form action={...}>` 的函数体，或用 `startTransition` 包住。

`error: duplicate key value violates unique constraint "teams_name_active_uniq"`

新名字已被其他团队占用，比较的是 `lower(name)`。改法：捕获 `error.code === '23505'`，返回中文提示，不让异常冒到错误页。

`error: permission denied for table activity_logs`

执行 `revoke update, delete` 之后，仍有代码用浏览器侧客户端写日志。改法：日志只走服务端连接，即 `logActivity` 加 `db`；客户端不直接写这张表。

`error: relation "activity_logs" does not exist`

本地库没应用迁移，或 `DATABASE_URL` 指向了另一个库。改法：`pnpm supabase db reset` 重放迁移，确认环境变量。

`Error: NEXT_REDIRECT`

把 `redirect('/onboarding')` 写进了 `try` 块，`catch` 把框架用来控制跳转的特殊错误当成业务异常吞了。改法：`redirect()` 放在 `try` 外，或在 `catch` 里判断后原样抛出。

## 22.12 这一章在做什么

这一章把团队设置拆成三层。

界面层：四种状态各有归处，日志页没有写入口，空状态说清下一步做什么。权限层：当前团队来自 cookie，但必须回 `team_members` 验证；所有业务查询以 `team_id` 为第一条件。数据层：日志只追加，变更和日志在同一事务里，所有权转移靠事务加唯一索引守住“恰好一个 owner”。

后面几章都从 `src/lib/teams.ts` 取当前团队。过滤条件写对一次，后面十几章都省事；写错一次，每隔几章就会漏一次租户数据。
