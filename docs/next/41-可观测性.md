# 第 41 章 可观测性

线上出问题时，你需要回答三个问题：出了什么事，发生在哪一步，影响了谁。能回答这三个问题的系统，叫可观测性。

它由三部分组成。日志记录发生了什么，一行一条，带时间、级别、请求 id。追踪记录一次请求内部的调用顺序和耗时，一条请求对应一棵 span 树。指标记录聚合后的数值，每秒请求数、错误率、p95 延迟、排队任务数。

三者回答的问题不同。日志解释细节，追踪解释慢在哪，指标解释趋势。单看任何一项都会缺一块：有日志没追踪，知道报错但不知道为什么慢；有追踪没指标，能查单次请求，不知道今天整体有没有变差。

本章搭一套最小可用的组合：`proxy.ts` 生成请求 id，日志和追踪都带上它，错误上报到 Sentry，指标暴露给 Prometheus，最后用一次失败把四者串起来。验收标准是一句可验证的话：同一次失败，在日志、追踪和错误平台里能对上同一个 id。

## 41.1 三样东西和一条线索

先把三个概念的区别说清楚，后面的代码才有意义。

日志是离散事件。一条日志回答「某一刻发生了什么」：哪个用户、哪个接口、花了多少毫秒、返回什么状态码。它的优势是细节，劣势是量，一天几十万行没法逐条看。

追踪是一次请求的完整时间线。它由多个 span 组成，每个 span 表示一段工作：处理 HTTP 请求、查一次数据库、调一次外部接口。每个 span 有开始时间、结束时间和耗时，父子关系表示调用嵌套。追踪的优势是结构，能一眼看到这 800ms 里 600ms 花在哪个查询上。

指标是聚合数值，按时间窗口统计。它不关心单次请求，只关心趋势：错误率从 0.1% 涨到 2%，p95 从 200ms 涨到 1.2s。指标的优势是便宜、能告警，劣势是不能下钻。

把三者串起来的东西是请求 id。一次请求进来时生成一个 id，日志的每一行带上它，追踪的 trace 带上它，错误上报的 tag 也带上它。排查时从一个 id 出发，三个系统都能查到对应记录。

请求 id 之外还有 trace id。两者作用类似，用途不同：请求 id 是应用自己生成的短标识，方便人看、方便贴进工单；trace id 是 OpenTelemetry 规范里的 32 位十六进制标识，跨服务传播靠它。可以只用一个，也可以两个都用，本章的做法是请求 id 对外，trace id 内部用。

上线的顺序建议固定下来。先做请求 id，再做结构化日志，然后接错误上报，最后接追踪。这个顺序的每一步都能独立产生价值，中途停下也有收获。反过来先接追踪，会得到一堆看不懂的 span，因为日志还是散字符串。

还有两个词要区分。SLI 是「量什么」，比如接口 p95 延迟、请求成功率。SLO 是「量到什么程度算正常」，比如成功率不低于 99.5%、p95 不超过 800ms。两者定下来之后，告警阈值就有依据，不用凭感觉设一个数。

错误预算的概念也来自这里。SLO 允许 0.5% 的失败，一个月三十天里大约有两小时可以失败。用完这两小时，新功能先停，把稳定性修回来。没有错误预算，讨论会变成「能不能再快一点」和「稳一点吧」之间的来回拉扯。

## 41.2 给每个请求一个编号

第一件事：每个请求进来时，分配一个 id。

旧做法写在 `middleware.ts` 里，Next.js 16 起文件改名为 `proxy.ts`，导出函数改名 `proxy`。文件名和函数名都要改，只改一个会在启动时报错。

```ts
// src/proxy.ts
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  const incoming = request.headers.get("x-request-id");
  const requestId = incoming && incoming.length <= 64 ? incoming : crypto.randomUUID();

  const headers = new Headers(request.headers);
  headers.set("x-request-id", requestId);

  const response = NextResponse.next({ request: { headers } });
  response.headers.set("x-request-id", requestId);
  return response;
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

代码做四件事。读上游传下来的 id，没有就生成一个；把 id 写回请求头，让下游的页面和接口能读到；把 id 写进响应头，让浏览器和网关能看到；用 matcher 排除静态资源。

上游有 id 时优先复用。经过 Cloudflare 的请求带 `cf-ray`，经过 Vercel 的带 `x-vercel-id`，这些 id 和网关日志能对上。复用它们，排查时能一路查到边缘节点。

长度要限制。`incoming.length <= 64` 挡住异常长的值，避免有人构造超长头把日志撑大。

验证方法：请求一次，看响应头。

```bash
curl -i -s http://127.0.0.1:3000/api/health | grep -i x-request-id
```

输出类似 `x-request-id: 4d1f0c62-8a3e-4f0b-9c2a-6f0d1b8e7a51`。同一个请求的日志里应该出现同一个值。

matcher 的负向断言必须写。没有 matcher 时，proxy 对每个请求都执行，包括 `_next/static` 下的 JS、CSS 和图片。这些请求各走一次 proxy，白白消耗 CPU，日志里还会多出一堆静态资源的记录。

`NextResponse.next({ request: { headers } })` 是让改动生效的关键。直接改 `request.headers` 不会传到下游，必须通过返回值覆盖。

三个边界。proxy 只能跑 Node runtime，在文件里写 `export const runtime = "edge"` 会报错。proxy 读不到请求体，想做签名校验得去 Route Handler。proxy 不该做权限判断，它能拦请求但不该承担数据隔离，那件事交给 RLS。

多实例部署时，proxy 在每个实例上都跑一遍。它不共享状态，本来也就没有状态：生成 id 用的是 request 头，不读内存。这一点比鉴权中间件安全，后者往往需要缓存会话，缓存又要在实例之间同步。

经过 CDN 的请求，边缘节点可能已经生成过 id。这时复用上游的值，应用日志和 CDN 日志才能对上。判断依据是响应头：`x-vercel-id`、`cf-ray` 都有值时直接用，别覆盖。

## 41.3 一行 JSON 代替 console.log

第二件事：日志改成结构化输出。目标是一行一个 JSON 对象，字段固定。

```ts
// src/lib/logger.ts
type Level = "debug" | "info" | "warn" | "error";

type Fields = Record<string, unknown>;

const order: Record<Level, number> = { debug: 10, info: 20, warn: 30, error: 40 };
const minLevel = (process.env.LOG_LEVEL as Level) ?? "info";

function write(level: Level, msg: string, fields: Fields) {
  if (order[level] < order[minLevel]) return;

  const line = JSON.stringify({
    time: new Date().toISOString(),
    level,
    msg,
    ...fields,
  });

  if (level === "error" || level === "warn") {
    process.stderr.write(`${line}\n`);
  } else {
    process.stdout.write(`${line}\n`);
  }
}

export const logger = {
  debug: (msg: string, fields: Fields = {}) => write("debug", msg, fields),
  info: (msg: string, fields: Fields = {}) => write("info", msg, fields),
  warn: (msg: string, fields: Fields = {}) => write("warn", msg, fields),
  error: (msg: string, fields: Fields = {}) => write("error", msg, fields),
};
```

用法。

```ts
// src/app/api/teams/[id]/route.ts（节选）
import { logger } from "@/lib/logger";

export async function PATCH(request: Request, context: { params: Promise<{ id: string }> }) {
  const { id } = await context.params;
  const startedAt = Date.now();

  try {
    const body = await request.json();
    const name = String(body.name ?? "").trim();
    if (name.length < 1 || name.length > 60) {
      logger.warn("team.rename.invalid", { teamId: id, nameLength: name.length });
      return Response.json({ error: "名称长度不对" }, { status: 400 });
    }

    await renameTeam(id, name);
    logger.info("team.rename.ok", { teamId: id, durationMs: Date.now() - startedAt });
    return Response.json({ ok: true });
  } catch (error) {
    logger.error("team.rename.failed", {
      teamId: id,
      durationMs: Date.now() - startedAt,
      err: error instanceof Error ? error.message : String(error),
    });
    return Response.json({ error: "改名失败" }, { status: 500 });
  }
}
```

输出是一行。

```text
{"time":"2026-11-15T13:22:41.882Z","level":"info","msg":"team.rename.ok","teamId":"7c...","durationMs":38}
```

字段要固定，八个就够：`time`、`level`、`msg`、`requestId`、`userId`、`route`、`durationMs`、`err`。字段一多，聚合查询就难写；字段随意起名，同一个意思有三个拼法，查询时全要试一遍。

`msg` 用固定的短标识，像 `team.rename.failed`，不要把变量拼进去。`msg` 为 `"团队 123 改名失败"` 时，按消息聚合会得到几百个不同的值。变量放进字段，查询时按字段过滤。

级别怎么定：`debug` 只在本地开，记录中间变量；`info` 记录业务动作完成；`warn` 记录可以恢复的异常，比如参数校验失败、限流触发；`error` 记录需要人看的问题，比如数据库报错、外部接口 5xx。

日志里不要放这些：密码、验证码、token、cookie 原文、完整邮箱、请求体、文件内容、银行卡号。需要定位用户时放用户 id，需要定位请求时放 request id。日志会被导出、被转发、被人翻，写进去的敏感数据很难收回。

为什么不直接用 pino 或者 winston。两个库都能做 JSON 行输出，功能比这三十行多。代价是多一个依赖、多一层配置，还要处理它们在 edge 运行时的兼容问题。当前需求只有字段、级别、请求 id 三件事，自己写可控。需要采样、脱敏、多目标输出时，再换成熟的库，接口不变。

写到 stdout，不写文件。容器里写文件会撑满磁盘，日志也拿不出来。stdout 交给 Docker 或 systemd 收集，再转发到 Loki、CloudWatch 之类的系统。

日志量要估算。一条 300 字节，每天 50 万条就是 150MB，一个月 4.5GB。免费额度经常在这个量级上用完，第 41.12 节单独讲保留策略。

## 41.4 让 requestId 自动进日志

上一节的日志要手动传 requestId 才能带上。每个函数都传一遍不现实，用 `AsyncLocalStorage` 自动传。

```ts
// src/lib/request-context.ts
import { AsyncLocalStorage } from "node:async_hooks";

type Context = { requestId: string };

const storage = new AsyncLocalStorage<Context>();

export function runWithRequestContext<T>(requestId: string, fn: () => T): T {
  return storage.run({ requestId }, fn);
}

export function currentRequestId() {
  return storage.getStore()?.requestId ?? null;
}
```

在 Route Handler 入口包一层。

```ts
// src/app/api/teams/[id]/route.ts（入口部分）
import { runWithRequestContext } from "@/lib/request-context";

export async function PATCH(request: Request, context: { params: Promise<{ id: string }> }) {
  const requestId = request.headers.get("x-request-id") ?? crypto.randomUUID();
  return runWithRequestContext(requestId, () => handlePatch(request, context));
}

async function handlePatch(request: Request, context: { params: Promise<{ id: string }> }) {
  // 原来的处理逻辑
}
```

logger 改成自动读上下文。

```ts
// src/lib/logger.ts（改动部分）
import { currentRequestId } from "@/lib/request-context";

function write(level: Level, msg: string, fields: Fields) {
  if (order[level] < order[minLevel]) return;

  const line = JSON.stringify({
    time: new Date().toISOString(),
    level,
    msg,
    requestId: currentRequestId(),
    ...fields,
  });
  // 后面不变
}
```

这样处理函数内部任何一处调用 `logger.info`，日志都会自动带 requestId，不用逐层传参数。

三个边界。`node:async_hooks` 只有 Node runtime 有，Edge runtime 里导入会报 `Module not found: Can't resolve 'node:async_hooks'`。proxy 和 Server Component 都不该依赖它。

上下文只在调用链内有效。`runWithRequestContext` 里的异步操作会继承上下文，但 `setTimeout`、队列、`after()` 里如果脱离了这次调用的作用域，可能拿不到值。拿不到时 `currentRequestId()` 返回 `null`，日志里就是空值，不会报错。

Server Component 里不要用它来读请求信息。渲染期间读 header 要用 `headers()`，那是 Next.js 提供的请求 API，能保证在同一棵渲染树里拿到正确的值。

开销可以忽略。一次上下文切换是微秒级，别在上下文里存大对象，只放标识。

## 41.5 instrumentation.ts：启动时的那一段

`instrumentation.ts` 在服务启动时执行一次，适合做三类事：校验环境变量、初始化 SDK、注册全局钩子。

```ts
// src/instrumentation.ts
export async function register() {
  checkEnv();

  if (process.env.NEXT_RUNTIME === "nodejs") {
    await import("./instrumentation-node");
  }
}

function checkEnv() {
  const required = ["NEXT_PUBLIC_SUPABASE_URL", "SUPABASE_SERVICE_ROLE_KEY", "STRIPE_SECRET_KEY"];
  const missing = required.filter((key) => !process.env[key]);
  if (missing.length > 0) {
    throw new Error(`缺少环境变量：${missing.join(", ")}`);
  }
}
```

位置在项目根，用 `src/` 目录时放在 `src/instrumentation.ts`，和 `app` 同级。放在 `app` 里面不会执行。

`register` 必须返回 Promise 或普通值，且要等它完成，服务才算就绪。在里面启动异步任务（比如连数据库）时，把 Promise `await` 掉。忘了 `await`，服务会先开始接请求，初始化还没做完。

缺变量时的输出很直接。

```text
Error: 缺少环境变量：STRIPE_SECRET_KEY
```

这个错误发生在启动阶段，容器会退出，编排系统会重试。比跑到业务逻辑里报 `Cannot read properties of undefined` 好排查得多。

register 里不要做三件事。不要读数据库或调外部接口，启动阶段的失败会让整个服务起不来。不要创建期待属于某次请求的 span，那时还没有请求。不要写业务逻辑，这个函数只负责初始化。

按 runtime 分支是必须的。`instrumentation-node.ts` 里可以导入 Node 专用模块，`instrumentation-edge.ts` 里不行。同一个文件里直接 `import` 数据库驱动，在 edge 构建时会报错。

文件名不能改。加自定义 `pageExtensions` 时，`instrumentation` 的文件名也要跟着调整，否则不会被识别。

客户端对应的文件是 `instrumentation-client.ts`，在浏览器执行应用代码之前运行。里面放全局错误监听、分析 SDK 初始化。

`register` 只管启动阶段。请求级的失败要用 `onRequestError`，服务端每次捕获到未处理错误都会调用它：

```ts
// src/instrumentation.ts
import type { Instrumentation } from "next";

export const onRequestError: Instrumentation.onRequestError = async (err, request, context) => {
  await fetch(`${process.env.OTEL_COLLECTOR_URL}/errors`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ message: String(err), request, context }),
  });
};
```

三个参数是错误、请求、上下文。错误对象可能已经被 React 处理过，不是原始实例，靠 `digest` 认出同一次失败，与 41.9 里页面显示的编号是同一个值。函数里的异步操作必须 `await`，否则响应先结束，上报被丢掉。

## 41.6 接入 OpenTelemetry

追踪需要三样东西：SDK、导出端点、后端。本地用 Jaeger，一个容器就够。

```yaml
# docker-compose.otel.yml
services:
  jaeger:
    image: jaegertracing/all-in-one:1.62
    ports:
      - "16686:16686"
      - "4318:4318"
    environment:
      COLLECTOR_OTLP_ENABLED: "true"
```

```bash
docker compose -f docker-compose.otel.yml up -d
```

`16686` 是 Jaeger 的界面端口，`4318` 是 OTLP 的 HTTP 端口。服务起来之后打开 `http://127.0.0.1:16686`。

装 SDK。

```bash
pnpm add @vercel/otel @opentelemetry/api
```

在 instrument 的 Node 分支里注册。

```ts
// src/instrumentation-node.ts
import { registerOTel } from "@vercel/otel";

export function registerNodeInstrumentation() {
  registerOTel({ serviceName: "teamstack" });
}
```

```ts
// src/instrumentation.ts（改动部分）
export async function register() {
  checkEnv();

  if (process.env.NEXT_RUNTIME === "nodejs") {
    const { registerNodeInstrumentation } = await import("./instrumentation-node");
    registerNodeInstrumentation();
  }
}
```

配置导出地址。

```bash
# .env.local
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318
OTEL_SERVICE_NAME=teamstack
```

重启服务，打开 `/api/health` 几次，Jaeger 的搜索页就能看到服务名和 trace。

一条 trace 展开后是一棵树。根 span 叫 `GET /api/health`，下面挂着 fetch、数据库查询、渲染等子 span，右侧是每个 span 的耗时。这就是「追踪记录调用顺序」的具体形态。

Next.js 已经内置了一批 span：路由处理、渲染、数据获取、元数据生成。它们的名字以 `next.` 开头，属性里带 `next.span_type`、`next.span_name`、`next.route`，RSC 请求还会带 `next.rsc`。这些 span 不用自己写，接上 SDK 就有。

常见的几种如下。`BaseServer.handleRequest` 是根 span，记录 HTTP 方法和状态码。`AppRender.getBodyResult` 对应一次页面渲染。`AppRender.fetch` 对应一次带缓存语义的 `fetch`。`AppRouteRouteHandlers.runHandler` 对应 Route Handler 执行。`ResolveMetadata.generateMetadata` 对应元数据生成。`NextNodeServer.startResponse` 记录首字节时间，它的耗时就是 TTFB。

排查页面慢时先看这几个。`startResponse` 之后的时间花在流式输出上，`getBodyResult` 的时间花在渲染上，`AppRender.fetch` 的时间花在数据上。三段相加接近总耗时，问题落在哪一段一目了然。

`4318` 是 HTTP 端点，`4317` 是 gRPC 端点。用 `@vercel/otel` 默认走 HTTP，指定 `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` 时才用 4317。端口和协议对不上，表现是所有 span 发不出去，日志里报 `ECONNREFUSED 127.0.0.1:4318`。

collector 没启动时，SDK 会持续重试导出，请求本身不受影响。这个设计是对的：追踪系统挂了不该拖垮业务。代价是控制台会被重试日志刷屏，排查别的问题时要先把它关掉。

采样要设。本地用 `OTEL_TRACES_SAMPLER=parentbased_always_on` 全采，生产用 `parentbased_traceidratio`，比例 0.05 到 0.2 之间。

采样率越低，成本越低，能看到的细节越少。但错误请求要全采，否则出问题时恰好没采到。标准做法是尾采样：先全收，在 collector 里按条件决定留哪些。Jaeger 的 all-in-one 不支持尾采样，生产环境用 OpenTelemetry Collector 配合 `tail_sampling` 处理器。

```yaml
# otel-collector.yaml（节选）
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 2000 }
      - name: sample
        type: probabilistic
        probabilistic: { sampling_percentage: 10 }
```

三条策略分别是：错误全留、超过两秒的慢请求全留、其余按一成采样。这个配置解决了「采样之后恰好丢掉出事那一条」的问题。

本地开发不建议开采样。请求量小，全采不会有什么成本，丢了反而难查。

## 41.7 自定义 Span：把业务步骤标出来

内置 span 只到框架层，业务里的「查团队、取成员、算权限」不在里面。想知道一个页面 800ms 花在哪，需要自己加 span。

封装一个最小的工具。

```ts
// src/lib/traced.ts
import "server-only";
import { SpanStatusCode, trace } from "@opentelemetry/api";

const tracer = trace.getTracer("teamstack");

export async function withSpan<T>(
  name: string,
  attributes: Record<string, string | number | boolean>,
  fn: () => Promise<T>,
): Promise<T> {
  return tracer.startActiveSpan(name, { attributes }, async (span) => {
    try {
      const result = await fn();
      return result;
    } catch (error) {
      span.recordException(error as Error);
      span.setStatus({ code: SpanStatusCode.ERROR });
      throw error;
    } finally {
      span.end();
    }
  });
}
```

三处细节。`startActiveSpan` 把 span 设为当前上下文，内部再开的 span 自动成为子 span。`span.end()` 必须放在 `finally`，漏了会让 span 永远处于未完成状态，Jaeger 里看不到。异常要 `recordException` 加 `setStatus`，否则追踪里那次失败和成功长得一样。

用在一个页面的数据加载上。

```ts
// src/app/(app)/teams/[slug]/dashboard/page.tsx（节选）
import { withSpan } from "@/lib/traced";

export default async function DashboardPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;

  const team = await withSpan("dashboard.load.team", { slug }, () => loadTeam(slug));
  const members = await withSpan("dashboard.load.members", { teamId: team.id }, () =>
    loadMembers(team.id),
  );
  const stats = await withSpan("dashboard.load.stats", { teamId: team.id }, () =>
    loadStats(team.id),
  );

  return <Dashboard team={team} members={members} stats={stats} />;
}
```

生成的 trace 树里能看到三个子 span 各自的耗时。如果 `dashboard.load.stats` 占了 600ms，优化目标就很明确。

命名用「模块.动作」的形式，加单位后缀时保持一致，比如 `dashboard.load.stats`、`storage.upload.commit`。名字里不要放变量，`load.team.7c3f` 这种没法聚合。

属性放筛选和聚合需要的值：`team.id`、`user.id`、`file.sizeBytes`、`rows.count`。不要放敏感内容，邮箱、文件名、请求体都不该出现在 span 属性里，追踪系统通常没有细粒度权限。

一个 span 里想标阶段，用 `addEvent`。

```ts
// src/lib/traced.ts（补充函数）
export function markStep(name: string, attributes: Record<string, string | number> = {}) {
  const span = trace.getActiveSpan();
  if (!span) return;
  span.addEvent(name, attributes);
}
```

阶段标记适合长流程，比如导入文件时标出「解析、校验、入库」三个时间点。事件没有独立耗时，只能在时间线上看到位置。

不要在循环里加 span。一次查询加一个 span，一千次查询就是一千个 span，追踪系统会被打爆，界面也没法看。循环里的操作先聚合成一个 span，属性里放总行数和总耗时。

一条 trace 的 span 数量有上限，主流后端默认在一千到一万之间。超过之后多余的 span 被丢弃，树形结构会出现断点。给一个页面的每个文件、每一行数据都加 span，几百个 span 很快到顶。

跨异步边界时要小心。`withSpan` 返回的上下文在 `await` 之后仍然有效，但如果把工作丢进 `after()`、定时任务或者消息队列，那段代码不在原上下文里，`trace.getActiveSpan()` 返回 `undefined`。需要衔接时，把 `context.active()` 拿到手，再用 `context.with(ctx, fn)` 包住。

span 和日志有分工。span 记录耗时和调用关系，日志记录发生了什么和参数。一次失败，span 告诉你「哪一步慢或出错」，日志告诉你「错在什么值上」。两者都带 requestId，才能对上。

## 41.8 after()：响应之后再干活

有些工作不该阻塞响应：写活动日志、上报分析事件、发通知。`after()` 让这些工作在响应发出之后执行。

```ts
// src/app/api/teams/[id]/route.ts（节选）
import { after } from "next/server";
import { logger } from "@/lib/logger";
import { createClient } from "@/lib/supabase/server";

export async function PATCH(request: Request, context: { params: Promise<{ id: string }> }) {
  const { id } = await context.params;
  const supabase = await createClient();
  const { data, error } = await supabase.from("teams").update({ name: "新名字" }).eq("id", id).select();

  if (error) {
    logger.error("team.rename.failed", { teamId: id, err: error.message });
    return Response.json({ error: error.message }, { status: 500 });
  }

  after(async () => {
    try {
      await supabase.from("activity_logs").insert({
        team_id: id,
        action: "team.renamed",
      });
    } catch (error) {
      logger.warn("activity.write.failed", { teamId: id });
    }
  });

  return Response.json({ ok: true, team: data[0] });
}
```

响应先返回，日志后写入。用 `curl -w "%{time_total}"` 对比加 `after()` 前后，接口耗时从 90ms 降到 60ms，省掉的是写日志那一次数据库往返。

四条边界。`after()` 不会让路由变成动态渲染，它在静态页里也能用，回调在构建或重新验证时执行。响应以 404 或重定向结束时，回调照样执行。执行时长受路由的 `maxDuration` 限制，长任务要放进队列。在 Server Component 里，`after()` 内部不能调用 `cookies()` 或 `headers()`，因为渲染阶段已经确定不了请求数据的读取顺序。

`after()` 内部要自己 try/catch。回调里的异常不会改变已经发出的响应，也不会被 `error.tsx` 捕获，只会在服务端日志里留一条未处理异常。写成上例那样，失败时记一条 warn，业务不受影响。

和 `waitUntil` 的关系：Vercel 的 `waitUntil` 是平台 API，`after()` 是 Next.js 的通用版本。本地和自托管用 `after()`，代码不用改。

## 41.9 错误上报：从日志到工单

日志能查，但需要人去查。错误上报系统负责主动通知。

Sentry 的接入用官方向导。

```bash
npx @sentry/wizard@latest -i nextjs
```

向导会生成三个文件：`sentry.client.config.ts`、`sentry.server.config.ts`、`sentry.edge.config.ts`，并修改 `next.config.ts` 加上 `withSentryConfig`。

```ts
// sentry.server.config.ts
import * as Sentry from "@sentry/nextjs";

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.NODE_ENV,
  release: process.env.GIT_SHA,
  sendDefaultPii: false,
  tracesSampleRate: 0.1,
  beforeSend(event) {
    if (event.request?.cookies) delete event.request.cookies;
    if (event.request?.data) delete event.request.data;
    return event;
  },
});
```

`sendDefaultPii: false` 关掉自动收集的用户信息，包括 IP 和 cookie。`beforeSend` 再兜一层，删掉请求体和 cookie。两个设置叠加，避免用户数据进第三方系统。

把 request id 挂到事件上。

```ts
// src/app/api/teams/[id]/route.ts（异常分支）
import * as Sentry from "@sentry/nextjs";
import { currentRequestId } from "@/lib/request-context";

Sentry.captureException(error, {
  tags: { request_id: currentRequestId() ?? "unknown" },
});
```

页面的错误边界里也挂一份，并把 id 显示给用户。

```tsx
// src/app/(app)/error.tsx
"use client";

import * as Sentry from "@sentry/nextjs";
import { useEffect } from "react";

export default function AppError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    Sentry.captureException(error, { tags: { digest: error.digest ?? "none" } });
  }, [error]);

  return (
    <div className="p-6">
      <h2>页面出错了</h2>
      <p>把下面这串编号发给我们，能定位到具体请求。</p>
      <code className="text-sm">{error.digest ?? "无编号"}</code>
      <button onClick={reset}>重试</button>
    </div>
  );
}
```

`digest` 是 Next.js 给服务端错误生成的哈希，同一个错误在多次请求里值相同。用户截图发过来的编号，能和 Sentry 里的事件对上。生产环境不要显示原始错误消息，它可能含内部路径或 SQL 片段。

噪音要提前关。不关的话，一周之后没人看告警。

```ts
// sentry.client.config.ts（节选）
Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
  ignoreErrors: [
    "ResizeObserver loop completed with undelivered notifications",
    "Non-Error promise rejection captured",
    /Loading chunk \d+ failed/,
  ],
  denyUrls: [/extensions\//i, /^chrome:\/\//i],
});
```

`ResizeObserver` 的报错来自浏览器布局，和业务无关。浏览器扩展注入的脚本也会抛错，用 `denyUrls` 挡掉。`Loading chunk failed` 要特殊处理：发版后旧页面引用了已经删除的 chunk，用户点一下就会报这个错。解法是提示用户刷新，别把它当异常上报。

source map 要上传。不传的话，错误堆栈全是压缩后的变量名，看不出位置。`withSentryConfig` 在构建时用 `SENTRY_AUTH_TOKEN` 上传并删除本地产物，避免 source map 被打进公开目录。

`release` 用提交哈希，和部署记录能对上。构建命令里传进去。

```bash
GIT_SHA=$(git rev-parse --short HEAD) pnpm build
```

`next.config.ts` 里读 `process.env.GIT_SHA` 传给 `withSentryConfig` 的 `release` 字段。版本号对不上时，错误堆栈的源码位置会指到另一个版本的代码，排查反而更乱。

## 41.10 指标：能告警的那一层

日志和追踪需要人去看，指标能主动触发告警。

最小实现是暴露一个文本端点。

```ts
// src/app/api/metrics/route.ts
import { createClient } from "@/lib/supabase/server";

export const dynamic = "force-dynamic";

export async function GET(request: Request) {
  const token = request.headers.get("authorization");
  if (token !== `Bearer ${process.env.METRICS_TOKEN}`) {
    return new Response("unauthorized", { status: 401 });
  }

  const supabase = await createClient();
  const { data: jobs } = await supabase
    .from("jobs")
    .select("status");

  const counts = { queued: 0, running: 0, done: 0, failed: 0, dead: 0 };
  for (const row of jobs ?? []) {
    counts[row.status as keyof typeof counts] += 1;
  }

  const lines = [
    "# HELP jobs_total 各状态作业数量",
    "# TYPE jobs_total gauge",
    ...Object.entries(counts).map(([status, value]) => `jobs_total{status="${status}"} ${value}`),
  ];

  return new Response(`${lines.join("\n")}\n`, {
    headers: { "content-type": "text/plain; version=0.0.4" },
  });
}
```

输出是 Prometheus 的文本格式。

```text
# HELP jobs_total 各状态作业数量
# TYPE jobs_total gauge
jobs_total{status="queued"} 12
jobs_total{status="done"} 4821
jobs_total{status="failed"} 6
```

Prometheus 定时抓这个端点，Grafana 画图，告警规则写「`jobs_total{status="failed"}` 十分钟内增长超过 20 就报警」。

指标有三个特点要注意。它是拉取模型，Prometheus 主动来抓，服务端不用推送。它的成本由时间序列的基数决定，标签值的组合数越多，存储越贵，别把用户 id 放进标签。它只保留数值，出问题还是要回到日志和追踪。

指标之外，还有一个更简单的信号：健康检查。

```ts
// src/app/api/health/route.ts
import { createClient } from "@/lib/supabase/server";

export const dynamic = "force-dynamic";

export async function GET() {
  const supabase = await createClient();
  const { error } = await supabase.from("teams").select("id", { head: true, count: "exact" });

  if (error) {
    return Response.json({ ok: false, db: "down" }, { status: 503 });
  }
  return Response.json({ ok: true, db: "up" });
}
```

指标端点自身的成本要控制。Prometheus 通常每十五秒抓一次，每次抓取都查一遍 `jobs` 表，大表上会变成负担。做法有两种：把统计结果缓存三十秒，或者用物化视图定时刷新，端点只读结果。指标系统不能成为新的瓶颈。

健康检查只查一次轻量请求，别在里面跑聚合查询。返回 503 时，负载均衡会把实例摘掉，容器编排会重启容器。

## 41.11 告警：谁能被叫起来

告警的价值在于有人响应。没有响应人的告警，两周之后就被静音了。

最小实现是一个定时任务，把异常推送到聊天工具。

```ts
// src/app/api/cron/health/route.ts
import { createClient } from "@/lib/supabase/admin";
import { logger } from "@/lib/logger";

export async function GET(request: Request) {
  const auth = request.headers.get("authorization");
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("unauthorized", { status: 401 });
  }

  const supabase = createClient();
  const problems: string[] = [];

  const { count: failed } = await supabase
    .from("jobs")
    .select("id", { count: "exact", head: true })
    .in("status", ["failed", "dead"]);
  if ((failed ?? 0) >= 20) problems.push(`失败作业 ${failed} 个`);

  const tenMinutesAgo = new Date(Date.now() - 10 * 60_000).toISOString();
  const { count: stuck } = await supabase
    .from("jobs")
    .select("id", { count: "exact", head: true })
    .eq("status", "queued")
    .lt("run_at", tenMinutesAgo);
  if ((stuck ?? 0) >= 5) problems.push(`排队超时作业 ${stuck} 个`);

  if (problems.length === 0) {
    return Response.json({ ok: true });
  }

  const since = new Date(Date.now() - 30 * 60_000).toISOString();
  const { count: recent } = await supabase
    .from("notifications")
    .select("id", { count: "exact", head: true })
    .eq("kind", "alert.jobs")
    .gte("created_at", since);

  if ((recent ?? 0) > 0) {
    return Response.json({ ok: false, cooldown: true, problems });
  }

  await supabase.from("notifications").insert({
    kind: "alert.jobs",
    title: "作业队列异常",
    body: problems.join("；"),
  });

  await fetch(process.env.ALERT_WEBHOOK_URL!, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ text: `作业队列异常：${problems.join("；")}` }),
  });

  logger.warn("alert.sent", { problems });
  return Response.json({ ok: false, sent: true, problems });
}
```

冷却逻辑用 `notifications` 表实现：三十分钟内已经发过同类告警，就只返回状态，不再重复推送。没有冷却，一个持续故障会每分钟发一条，两小时后群里只剩告警。

告警消息里要写六项：现象（失败作业 20 个）、影响（用户上传的文件卡在处理中）、开始时间、证据（哪个仪表盘、哪条查询）、止血动作（重启 worker 还是先扩容）、处理人。缺了后两项，收到告警的人还要先花十分钟搞清楚能做什么。

告警分三级。P1 立即处理，比如支付失败率超过 5%、数据库不可用。P2 当天处理，比如作业积压、错误率上涨。P3 记录到日报，比如某个接口 p95 变慢一点。分级的意义是决定半夜要不要叫醒人。

应用自己挂了的时候，它没法发出告警。补一个外部探针：每分钟从外部请求 `/api/health`，连续两次非 200 就通知。可以用现成的 uptime 服务，也可以用另一台机器上的 cron 加 curl。

内部告警和外部探针分工不同。内部告警知道业务细节，比如队列积压、支付失败率；外部探针只知道「整个站点不可达」。两个都要有，缺一个都会漏。

每周看一次告警命中率。全是噪音的告警要么阈值错了，要么这个指标根本不重要。命中率低于两成的告警，直接删掉或者降级。

## 41.12 用一次失败把三处对上

前面几节各自独立，这一节把它们串起来。场景是用户报「保存团队名称失败」，截图里有错误编号。

第一步，拿到编号。页面上的编号是 `error.digest`，响应头里的是 `x-request-id`，两者都能用。有响应头时优先用响应头，它的值就是这次请求的 id。

第二步，查日志。

```bash
docker compose logs --since 2h web \
  | grep '4d1f0c62-8a3e-4f0b-9c2a-6f0d1b8e7a51' \
  | jq -c '{time, level, msg, route, userId, err}'
```

输出三到五行，按时间排序。

```text
{"time":"2026-11-15T13:22:41.771Z","level":"warn","msg":"team.rename.invalid","route":"/api/teams/[id]","userId":"u_9f2","err":null}
{"time":"2026-11-15T13:22:41.796Z","level":"error","msg":"team.rename.failed","route":"/api/teams/[id]","userId":"u_9f2","err":"duplicate key value violates unique constraint \"teams_slug_key\""}
{"time":"2026-11-15T13:22:41.802Z","level":"info","msg":"request.completed","route":"/api/teams/[id]","durationMs":41}
```

日志已经给出原因：slug 撞了唯一约束。接下来确认这是偶发还是常态。

第三步，查追踪。Jaeger 里按 trace id 或者按 `service=teamstack` 加时间范围搜索，点开那条 trace，能看到 db 查询那个 span 标着错误，属性里有 SQL 语句的摘要。span 的耗时是 12ms，说明数据库本身不慢，是约束冲突。

第四步，查错误平台。Sentry 里按 `request_id` 标签搜索，找到同一个事件，堆栈指向 `renameTeam` 里的 update 调用。附带的环境信息里有版本号，能确认是哪个提交。

三处对上之后，处理方式很清楚：给 slug 生成加上重试和随机后缀，接口把唯一约束冲突翻译成一句可读的提示。

查不到的情况有三种。响应头里没有 id，说明 proxy 的 matcher 没覆盖到这条路由。日志里有 id 但追踪里没有，说明采样把这个请求丢了，或者 collector 当时不可用。追踪里有时长但 Sentry 没事件，说明这个异常被 `beforeSend` 过滤了，或者级别不到上报阈值。

排查顺序固定下来：先响应头，再日志，再追踪，最后错误平台。前一步没有结果时再走下一步，不要同时开四个窗口找。

这套流程覆盖三类问题。慢：从响应头拿 id，日志里看 `durationMs`，追踪里看哪个 span 占比最大。错：日志里看 `err` 字段，追踪里看错误 span，错误平台里看堆栈。丢：响应头里没有 id，说明请求没进 proxy；日志里没有对应行，说明请求在网关就被拒了。

三类问题的入口不同，最后都落到同一个 id 上。这就是为什么第一条要求是「每个请求都有 id」：没有它，后面所有工具都是孤岛。前一步没有结果时再走下一步，不要同时开四个窗口找。

## 41.13 线上查日志的几条命令

日志集中之后，日常查询就靠几条命令。

按错误消息聚合，找出最常出现的错误。

```bash
docker compose logs --since 1h web \
  | grep '^{' \
  | jq -r 'select(.level == "error") | .msg' \
  | sort | uniq -c | sort -rn | head -10
```

输出左边是次数，右边是消息标识。次数最多的那条通常值得先修。

找最慢的请求。

```bash
docker compose logs --since 1h web \
  | grep '^{' \
  | jq -r 'select(.durationMs != null) | "\(.durationMs)\t\(.route)\t\(.requestId)"' \
  | sort -rn | head -20
```

按耗时倒序，前二十条里如果有同一条路由反复出现，说明那个路由有性能问题。

统计某个接口的错误率。

```bash
docker compose logs --since 1h web \
  | grep '^{' \
  | jq -r 'select(.route == "/api/teams/[id]") | .level' \
  | sort | uniq -c
```

日志量大了之后，`docker compose logs` 会变慢，换 Loki 或者云厂商的日志服务。查询语法不同，思路一样：先按时间范围缩小，再按字段过滤。

时间口径要统一。容器日志默认是 UTC，本地终端是 `Asia/Shanghai`，两个时间差八小时。查「下午三点那次故障」时，先换算成 UTC 再传 `--since`，否则范围永远错。

日志里的字段名要和查询保持一致。`durationMs` 和 `duration_ms` 是两个不同的键，混用会让 `select` 漏掉一半数据。字段规范定下来之后，写进文档，不要随手改。

## 41.14 保留多久，花多少钱

日志和追踪都要存，也都花钱。算清楚再定策略。

先算日志体积。一条 300 字节，每天 50 万条，一天 150MB，一个月 4.5GB，一年 54GB。这个量级在免费额度之外，按每 GB 几毛到几块不等，一年几十到几百块。

追踪更贵。一条 trace 有十几个 span，每个 span 几百字节到几 KB。全采的情况下，一天十万条 trace 就是几个 GB。所以追踪必须采样，日志可以全留。

容器层面先限制，避免磁盘被写满。

```yaml
# docker-compose.yml（节选）
services:
  web:
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "5"
```

单个文件 50MB，最多五个，总共 250MB。超出的旧日志被丢弃，磁盘不会满。代价是日志量大的时候会丢历史，重要日志要转发到集中存储。

分级保留：`debug` 不留，本地看；`info` 留七天；`warn` 和 `error` 留三十天；错误上报的事件留九十天；trace 留七天。理由是排查通常发生在几天内，审计需求才要更长的窗口。

采样率直接影响成本。追踪从全采降到一成，存储成本降九成，能看到的问题从「全部」变成「一成样本加全部错误」。加上尾采样之后，错误和慢请求仍然全留，样本只影响基线统计。

指标的成本在基数。每个不同的标签组合是一条时间序列，`route` 有二十个值、`status` 有五个值，组合就是一百条。把 `userId` 放进标签，一万人就是一千万条序列，存储直接爆。标签只放低基数的维度。

采集端也要脱敏。应用侧不写敏感字段是第一道，采集侧再加一层过滤是第二道。Loki 的 `pipeline_stages` 或者云服务的日志加工都能做正则替换，把邮箱、手机号、身份证号替换成掩码。

谁能看日志要提前定。日志里有用户 id、路由、错误消息，属于内部数据。给运维和开发看，不给外部合作方看。生产环境的日志导出权限收紧到少数人。

什么时候该买托管服务：日志量超过每天几个 GB，自己维护 Loki 的成本超过服务费；需要多月的历史查询；需要和追踪、指标在同一个界面里跳转。三个信号出现两个，就值得换。

## 41.15 本地调试

本地排查问题不只有日志。断点能看到变量，比打十行日志快。

开发服务器带调试端口启动。

```bash
pnpm dev --inspect
```

输出里有 `Debugger listening on ws://127.0.0.1:9229/...`。打开 `chrome://inspect`，在 Remote Target 里找到进程，点 inspect 进入 DevTools。

在 DevTools 的 Sources 面板里找到服务端代码，打断点，然后用 curl 请求对应接口。请求会停在断点上，可以看变量、看调用栈。

容器里调试要把端口暴露出去。

```bash
pnpm dev --inspect=0.0.0.0:9229
```

VS Code 的配置可以直接附加。

```json
// .vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Next.js: attach server",
      "type": "node",
      "request": "attach",
      "port": 9229,
      "skipFiles": ["<node_internals>/**"]
    }
  ]
}
```

想在启动时就停住，用 `NODE_OPTIONS`。

```bash
NODE_OPTIONS=--inspect-brk pnpm dev
```

服务会停在第一行，等 DevTools 连上再继续。适合调启动阶段的问题，比如 `instrumentation.ts` 里的环境校验。

生产环境不要开 `--inspect`。调试端口没有认证，任何能连上的人都能执行代码。要在生产排查，用日志和追踪，别开断点。

浏览器这一侧用 Network 面板看 RSC 请求。App Router 的页面跳转不发完整 HTML，发的是 RSC payload，请求头带 `RSC: 1`，响应体是特殊格式的文本。看响应体里的 `$L`、`$undefined` 这类标记，能判断某个组件为什么没渲染、某个值为什么是空的。

`console.log` 和断点各有用处。临时看一个值，`console.log` 快；要理解一段逻辑的执行顺序，断点快。上线前把 `console.log` 清掉，用 logger 代替。

## 41.16 边界与失败模式

可观测性系统本身也会出问题，几种常见形态要认识。

日志突然变多。某个循环里加了日志，或者错误重试风暴，一天写出几个 GB。表现是磁盘告警、日志查询超时。处理方式是加限流或者降级，比如同类日志一分钟只记一次。

追踪里 span 不完整。`span.end()` 漏掉，或者异常路径没有走 `finally`。表现是 Jaeger 里那条 trace 一直显示未完成。写 span 的代码统一用 `withSpan` 包，别自己手写 `startActiveSpan`。

上下文丢失。在 `after()`、定时任务、消息队列里读 `currentRequestId()` 返回 `null`。这是异步边界带来的正常现象。需要传递时，把 id 当参数显式传进去。

request id 在多个实例之间不共享。日志分散在四台机器上，`grep` 只能查到一台。日志必须集中收集，否则请求 id 只对一半的请求有用。

时钟不一致。容器时间、数据库时间、浏览器时间可能有几秒偏差。查「同一时刻」的日志时，用 request id 定位，时间戳只作参考。

告警风暴。一个组件故障触发几十条告警，或者冷却逻辑失效，十分钟发一百条。表现是群里全是消息，没人看。处理方式是分组和抑制：一个根因只发一条，下游告警自动挂起。

数据量增长之后，查询方式要跟着换。`docker compose logs | grep` 在每天几百万行的规模上会超时，换 Loki、ClickHouse 或者云日志服务。应用侧不用改，因为输出的是标准 JSON 行，任何采集器都能解析。

错误上报的配额。Sentry 免费版每月有事件数上限，超了之后新事件被丢弃。表现是出问题时恰好没有事件。处理方式是采样、降噪，把配额留给真正的错误。

## 41.17 检查点

1. `curl -i http://127.0.0.1:3000/api/health` 的响应头里有 `x-request-id`，同一个值出现在这一请求的日志行里。
2. `docker compose -f docker-compose.otel.yml up -d` 之后，Jaeger 里能按服务名 `teamstack` 搜到 trace，展开后至少有两层 span。
3. 手动触发一次接口报错，日志里有 `level":"error"` 的行，Sentry 里有事件，两者能通过 request id 对上。
4. `curl -H "Authorization: Bearer $METRICS_TOKEN" http://127.0.0.1:3000/api/metrics` 返回 Prometheus 文本格式，`jobs_total` 有五个状态。
5. `curl -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:3000/api/cron/health` 在作业正常时返回 `{"ok":true}`，人为插一条 `failed` 作业之后返回告警。
6. `pnpm dev --inspect` 之后 `chrome://inspect` 能看到进程，打断点后 curl 请求会停住。
7. 从一份生产日志里，用 request id 查到对应的 trace id，再在 Jaeger 里打开那条 trace，整个过程不超过一分钟。

## 41.18 常见错误

1. 只有根 span，没有自定义 span

现象：Jaeger 里看到 `GET /dashboard`，但没有 `dashboard.load.stats`。原因是 `withSpan` 在 `register` 阶段被调用，或者 `@vercel/otel` 没有初始化成功。检查 `instrumentation.ts` 的 runtime 分支，确认 Node 段落执行了。

2. 依赖表达式导致构建警告

现象：`Critical dependency: the request of a dependency is an expression`。原因是 `await import(变量)` 的动态导入，打包器无法静态分析。改成字面量路径，或者加 `/* webpackIgnore: true */` 注释。

3. headers() 在错误位置调用

现象：`Invariant: headers() expects to have requestAsyncStorage, none available.`。原因是在 `after()` 回调或者模块顶层调用了 `headers()`。把调用挪进请求处理函数，或者改用传入的 `request` 对象。

4. async_hooks 在 Edge 里不可用

现象：`Module not found: Can't resolve 'node:async_hooks'`。原因是 `request-context.ts` 被 edge 运行时引用。把它限制在 Node 分支，或者换用不依赖上下文的显式传参。

**5. 响应头被重复设置**

现象：`ERR_HTTP_HEADERS_SENT`。原因是 proxy 和 Route Handler 都往响应里写同一个头，或者流式响应已经开始又去改头。只在一个地方设置，流式响应开始之后不要再改。

**6. 日志目录不存在**

现象：`ENOENT: no such file or directory`，指向日志文件。原因是 logger 之外还有代码在写文件日志。日志一律写 stdout，删掉写文件的逻辑。

## 41.19 这一章在做什么

这一章讲三件事：怎么给请求编号，怎么让日志和追踪带上同一个编号，怎么在出问题时用一个编号查到三处记录。请求 id 放在 `proxy.ts` 生成，日志用 JSON 行，追踪接 OpenTelemetry，错误上报挂 Sentry，指标暴露成 Prometheus 文本，告警走定时任务加冷却。

这些系统的共同前提是字段规范。字段一乱，查询就失效，工具再多也没用。字段定下来之后，写进文档，新代码照着写。缺字段的日志等于没写，查的时候还得回到代码里猜。这套东西的价值不在装了几个工具，在于出事时能不能在五分钟内说出原因：哪个接口，哪一步，影响了多少用户。这四句话答得出来，这一章就没白写。下一章讲产品侧的问题：用户在应用里做了什么，这些行为怎么记下来。

容量和可观测性解决的是两类问题：能服务多少人，出问题怎么定位。第 42 章换到产品视角，讲用户在应用里做了什么，这些行为怎么变成可以查询的数据。
