# 第 34 章 图片、字体与第三方脚本

这一章处理页面上的三类外部资源：图片、字体、第三方脚本。它们的共同点是都要走网络，都影响首屏，配置写错都不会报错。

需要单独讲的原因有两条。图片通常占页面传输量的一大半，也是 Largest Contentful Paint 的常客；字体和第三方脚本决定 cookie 弹窗、统计、视频能不能晚一点加载。这两件事都不靠业务代码解决，靠框架提供的三个组件和一份域名白名单。

涉及的概念有五组。`next/image` 与图片优化管线；`remotePatterns` 白名单与尺寸候选；`next/font` 的构建期下载与自托管；`next/script` 的三种加载策略；第三方嵌入与 Content-Security-Policy 的关系。

## 34.1 三类资源各影响什么

浏览器性能有三项常用指标，各自对应不同资源。

这三项指标的阈值来自 Core Web Vitals。LCP 低于 2.5 秒算良好，2.5 到 4 秒需要改进，超过 4 秒是差。CLS 低于 0.1 算良好。TBT 在移动端低于 200 毫秒算良好。数字会随设备和网络波动。判断趋势看同一台机器上的前后对比，别跨设备比较。

LCP 是最大内容绘制时间，指首屏最大的那块内容渲染完成的时间。它通常是一张英雄图、一个视频封面，或者一大段文字。图片的字节数、发现时间、优先级都作用在这项指标上。

CLS 是布局偏移分数，指页面渲染过程中元素位置跳动的累计量。图片和视频没写宽高、字体替换导致行高变化，是它的两个主要来源。

TBT 是总阻塞时间，指主线程被长任务占用的时长。第三方脚本是主因：统计、客服挂件、A/B 测试都会在加载后占用主线程。

一个页面从多少外部域名取资源，可以直接数出来。图片可能在存储域名，字体可能在字体服务域名，统计和客服各自一个域名，视频平台一个。每多一个域名就多一次连接建立，移动网络下每次 100 毫秒起步。把域名数量压到五个以内，首屏通常能省下两三百毫秒，这条改动不需要改任何业务代码。

三类资源对应三组手段，指标怎么变要从这三处找原因。图片靠格式、尺寸、优先级；字体靠移除外部请求、控制替换行为；脚本靠调整加载时机、限制来源。

## 34.2 next/image 做了什么

浏览器原生 `<img>` 只做一件事：按 `src` 下载。它不会换格式，不会按屏幕尺寸给不同大小的文件，也不会替你预留空间。

`next/image` 在 `<img>` 外面加了一层，做四件事。

第一件是按需转格式。浏览器支持 AVIF 或 WebP 时，服务端把原图转成对应格式再发。一张 2.4MB 的 JPEG 换成 AVIF 通常在 80KB 到 200KB 之间，具体取决于画面复杂度。

图片优化是服务端行为，会消耗计算和带宽。自托管部署时这层压力落在自己的机器上；托管平台按优化后的图片数量计费。使用量大的站点要做缓存，或者在上传阶段就把图压到合理尺寸，别把原图直接交给优化器。

上传端也应该有约束。用户传 8MB 的原图，每次优化都要解码一次。上传时限制边长、统一转成一种格式，后续所有环节都省事。

第二件是按候选尺寸生成多个文件。`srcset` 里列出 640w、750w、828w、1080w 等宽度，浏览器按当前布局宽度和设备像素比挑一个。手机不需要下载桌面宽度的那份。

第三件是缓存。优化后的图片地址带参数，内容不变时地址不变，CDN 和浏览器都能长期命中。

第四件是预留空间。给了 `width` 和 `height`，浏览器在图片下载完成前就按比例占好位置，CLS 因此接近 0。

```tsx
// src/components/file-card.tsx
import Image from "next/image";

export function FileCard({ file }: { file: { name: string; previewUrl: string } }) {
  return (
    <figure className="overflow-hidden rounded-lg border border-neutral-200">
      <Image
        src={file.previewUrl}
        alt={file.name}
        width={640}
        height={360}
        sizes="(max-width: 640px) 100vw, (max-width: 1024px) 50vw, 320px"
        className="h-auto w-full"
      />
      <figcaption className="p-3 text-sm">{file.name}</figcaption>
    </figure>
  );
}
```

本地图片可以走静态导入，宽高和模糊占位自动带上：

```tsx
// src/app/(marketing)/page.tsx
import Image from "next/image";
import hero from "@/assets/hero.jpg";

export default function MarketingPage() {
  return <Image src={hero} alt="团队协作界面" preload placeholder="blur" />;
}
```

静态导入时不要手写 `width` 和 `height`，图片文件本身就是来源。手写的值会和真实尺寸对不上，比例一错就会变形。

`fill` 用于尺寸未知的场景。它让图片填满父容器，父元素必须是定位元素：

```tsx
// src/components/cover-image.tsx
import Image from "next/image";

export function CoverImage({ src, alt }: { src: string; alt: string }) {
  return (
    <div className="relative aspect-video w-full overflow-hidden rounded-lg">
      <Image src={src} alt={alt} fill sizes="(max-width: 768px) 100vw, 480px" className="object-cover" />
    </div>
  );
}
```

SVG 默认不走优化管线。它本身是矢量图，转码没有意义，框架会原样发送。图标一类适合用 SVG，位图用 `next/image`。

`unoptimized` 是单张图的开关，也可以用 `images.unoptimized: true` 全局关掉。全局关掉之后 `sizes`、格式协商、缓存都不生效，只在完全自己管图片的场景使用。

父元素没写 `relative`，`fill` 的图会覆盖整个页面。这类问题在开发时容易漏，因为图片确实显示了，只是位置不对。

## 34.3 remotePatterns 是白名单

远程图片必须显式允许，否则请求返回 400。配置在 `next.config.ts`：

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  images: {
    remotePatterns: [
      {
        protocol: "https",
        hostname: "abcdefghijklm.supabase.co",
        pathname: "/storage/v1/object/public/**",
        search: "",
      },
      {
        protocol: "https",
        hostname: "images.teamstack.example.com",
        pathname: "/avatars/**",
      },
    ],
    formats: ["image/avif", "image/webp"],
    qualities: [50, 75, 90],
  },
};

export default nextConfig;
```

不匹配任何一条时，页面上的图片位置显示裂图，控制台报：

```text
Invalid src prop (https://example.com/a.png) on `next/image`, hostname "example.com"
is not configured under images in your `next.config.js`
```

白名单的通配符只有两种：`*` 匹配单个路径段或单个子域，`` 匹配末尾任意多段，或者开头的任意多级子域。`` 放在中间不生效。

配错这一项的风险比想象中大。把 `hostname` 写成 `"**"`，等于把图片优化接口变成公开代理：任何人都能让你服务器去抓任意地址、转码、再发回给他。这带来三个后果。服务器成为别人绕过网络限制的跳板；请求带着你服务器的 IP 和额度；带宽账单按别人的用量增长。

具体场景是这样的：攻击者构造 `/ _next/image?url=https://内部地址/admin&w=640&q=75`，你的服务器去请求内网的服务，把响应内容转成图片返回。内网接口如果只靠“外网访问不到”做防护，这一层就被绕过了。

`pathname` 支持通配，`/avatars/**` 能匹配子目录，`/avatars/*` 只匹配一层。`search` 用来锁查询串，签名 URL 带固定参数时可以直接匹配整串，避免放开所有查询。

配好之后用一个不在名单里的地址验证一次，确认真的返回 400。只看配置文件不算验证。

白名单要写到路径级别。只写域名，同一域下所有路径都放行，用户上传目录和后台接口在同一个域时就出问题。

```ts
// next.config.ts（片段，只允许公开读取的存储目录）
images: {
  remotePatterns: [
    { protocol: "https", hostname: "abcdefghijklm.supabase.co", pathname: "/storage/v1/object/public/**" },
  ],
}
```

私有图片不要走优化接口。图片优化服务取图时不转发请求头，带鉴权的地址在优化器那边拿到的是 401。这类图片加 `unoptimized`，让浏览器直接请求原地址，鉴权信息跟着过去。

自托管部署要自己准备优化服务。Next.js 内置的优化器在 Node 进程里跑，图片多时会占满 CPU；也可以接外部服务，用 `images.loader` 指定地址，把活儿交给图片 CDN。

重定向也是同类问题。优化器会跟随远端返回的重定向，跟随之后不再校验白名单。`maximumRedirects` 可以限制次数，默认 3，设成 0 就完全不跟。

## 34.4 sizes 决定下载哪一张

比例要在容器上定，不要在图片上定。容器用 `aspect-video` 或 `aspect-square` 占住空间，图片用 `object-cover` 填满。反过来把比例写在图片上，容器高度仍然会在加载前塌掉，CLS 还是会涨。

`sizes` 告诉浏览器：这张图在不同断点下占多宽。浏览器据此从 `srcset` 里挑一个文件。

```tsx
// src/components/team-avatar.tsx
import Image from "next/image";

export function TeamAvatar({ name, src }: { name: string; src: string | null }) {
  if (!src) {
    return (
      <span className="flex size-10 items-center justify-center rounded-full bg-neutral-200 text-sm">
        {name.slice(0, 1)}
      </span>
    );
  }
  return (
    <Image
      src={src}
      alt={`${name} 的头像`}
      width={40}
      height={40}
      sizes="40px"
      className="rounded-full"
    />
  );
}
```

固定尺寸的组件写固定值就行。写 `100vw` 会让浏览器按整屏宽度挑图，一张 40px 的头像下载一个 1080w 的文件。

响应式卡片用媒体查询语法：

```tsx
// src/components/file-card.tsx（节选）
sizes="(max-width: 640px) 100vw, (max-width: 1024px) 50vw, 320px"
```

读法是：视口不超过 640px 时这张图占满宽度，不超过 1024px 时占一半，再宽就固定 320px。计算时要扣掉容器的内边距，写 100vw 往往比实际宽度大一点，多下载一档。

没有 `sizes` 时，浏览器按 `100vw` 估算，也就是假设这张图铺满整屏。这是最常见的浪费来源：移动端按 390px 宽的屏下载 1200px 的图。

同时给了 `width` 却没给 `sizes`，框架只生成 1x 和 2x 两个候选，响应式效果消失。`fill` 又没给 `sizes` 时，只用设备宽度档位。

候选尺寸的档位可以在配置里改。`deviceSizes` 是设备宽度档，默认 640 到 3840 共八档；`imageSizes` 是固定宽度档，用于 `sizes` 里的小尺寸。默认值覆盖了常见屏幕，改动前先确认真的有必要，档位越多构建产物越多。

`quality` 默认 75。视觉要求高的页面可以给 90，体积会明显增加。配置了 `qualities` 白名单后，超出范围的值会被就近收敛到最近的合法值，开发环境有警告。

验证方法在开发者工具的 Elements 面板：选中 `<img>`，看 `currentSrc` 指向哪个 `w=` 参数，再对比图片实际渲染宽度。差两档以上就要改 `sizes`。

## 34.5 preload 与首屏优先级

浏览器解析 HTML 时逐行发现资源。图片在 `<img>` 标签处才被发现，如果前面有一大段 JS 或 CSS，发现时间会被推后。

`preload` 把图片提前到 `<head>` 里声明，浏览器一拿到 HTML 就开始下载。

```tsx
// src/app/(marketing)/page.tsx
import Image from "next/image";
import hero from "@/assets/hero.jpg";

export default function MarketingPage() {
  return (
    <section className="relative">
      <Image src={hero} alt="团队协作界面" preload sizes="100vw" className="h-auto w-full" />
    </section>
  );
}
```

`preload` 优化的是发现时间，下载速度取决于文件大小和带宽。

使用范围要收窄。一张页面只对确定的那张 LCP 图用 `preload`。多张图都加，浏览器并发数被占满，真正的首屏图反而更慢。

Next.js 16 起 `priority` 属性已废弃，改用 `preload`。老代码里的 `priority` 还能跑，会给出警告。官方更推荐的做法是用 `loading="eager"` 加 `fetchPriority="high"`，它对浏览器原生行为的控制更细。

```tsx
// src/app/(marketing)/page.tsx
<Image src={hero} alt="团队协作界面" loading="eager" fetchPriority="high" sizes="100vw" />
```

判断哪张是 LCP 图有个笨办法：跑一次 Lighthouse，报告里会直接写出 LCP 元素的选择器。看不懂报告就在 Performance 面板录制一遍，找最大那块内容的绘制时间。

字体也会影响 LCP。文字块是 LCP 元素时，字体没加载完，文字可能还没绘制。这种情况优化方向是减字体体积、用 `display: swap`，继续压图没有用。

首屏之外的一律保持默认的懒加载。判断标准是：页面不滚动就能看到的位置需要立即加载，其余位置等滚到附近再加载。

用 PerformanceObserver 可以量到真实结果：

```ts
// src/lib/report-lcp.ts
export function reportLcp() {
  if (typeof PerformanceObserver === "undefined") return;
  new PerformanceObserver((list) => {
    const entries = list.getEntries();
    const last = entries[entries.length - 1];
    console.log("LCP", Math.round(last.startTime), (last as PerformanceEntry & { element?: Element }).element);
  }).observe({ type: "largest-contentful-paint", buffered: true });
}
```

还有一个误区是把 `preload` 当成提速开关。图片是首屏图时它有用；图片根本不在首屏，它只是把带宽从别的资源手里抢过来。

图片元素出现在输出里，说明 LCP 是图片；元素是空值，说明是文字块，优化方向要换成字体和渲染阻塞资源。

## 34.6 next/font：把字体文件收回来

从 Google Fonts 引入字体的常规写法是一个 `<link>` 指向 `fonts.googleapis.com`。这带来三个代价：多一次 DNS 解析和 TLS 握手；多一个外部依赖，对方慢你就慢；访客 IP 会发给第三方。

`next/font` 在构建时下载字体文件，转成自托管资源，与其它静态文件一起发。浏览器不再请求 Google 的域名。

```tsx
// src/app/layout.tsx
import { Inter, JetBrains_Mono } from "next/font/google";
import "./globals.css";

const inter = Inter({
  subsets: ["latin"],
  display: "swap",
  variable: "--font-inter",
});

const mono = JetBrains_Mono({
  subsets: ["latin"],
  display: "swap",
  variable: "--font-mono",
});

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN" className={`${inter.variable} ${mono.variable}`}>
      <body className="font-sans">{children}</body>
    </html>
  );
}
```

```css
/* src/app/globals.css */
@import "tailwindcss";

@theme inline {
  --font-sans: var(--font-inter), "PingFang SC", "Microsoft YaHei", system-ui, sans-serif;
  --font-mono: var(--font-mono), ui-monospace, monospace;
}
```

字体文件通常是页面里第二大的静态资源，仅次于图片。它阻塞文字绘制，所以优先级高，但字节数必须小。

`display` 有三个常用值。`swap` 先用备用字体显示，字体到了再替换，有轻微跳动；`optional` 在网络慢时直接不换，跳动最少，代价是这次的字体可能没生效；`block` 会短暂空白，通常不选。

中文页面的字体策略要单独考虑。Inter 这类英文字体只覆盖拉丁字符，汉字会落到系统字体。整站的中文字体文件通常 3MB 到 15MB，全量加载的代价超过收益。

三条可选路径：用系统字体，零成本，跨平台有差异；只加载英文字体，汉字用系统字体，这是多数项目的选择；对中文字体做子集，只保留实际用到的字，需要构建期处理。

字体文件不要放 `public/`。`next/font` 会把文件接到构建产物里并生成 `@font-face`，手动放进 `public/` 就绕开了这套处理，预加载、字符集、回退度量全都要自己写。

中文字体做子集需要构建期工具，`fontmin` 或 `subset-font` 都能按给定字符集裁。裁完之后 3MB 能到 300KB 上下，代价是内容里有生僻字时会出现缺字，需要定期重跑。

本地字体用 `localFont`：

```tsx
// src/app/fonts.ts
import localFont from "next/font/local";

export const brand = localFont({
  src: [
    { path: "./fonts/Brand-Regular.woff2", weight: "400", style: "normal" },
    { path: "./fonts/Brand-Bold.woff2", weight: "700", style: "normal" },
  ],
  display: "swap",
  variable: "--font-brand",
  fallback: ["system-ui", "sans-serif"],
});
```

路径相对调用它的文件，写 `@/` 别名会解析失败。

预加载的范围和调用位置有关。字体在根布局调用，全站预加载；在某个页面调用，只在该路由预加载。页面级调用能减少无关下载。

字体替换时的度量差异会造成视觉跳动。备用字体的 x 高度、行高与目标字体不同，文字块的高度就变了。`adjustFontFallback` 会按目标字体的度量调整备用字体，默认开启，关掉之后跳动更明显。

可变字体一个文件覆盖多个字重，优先选它。非可变字体每个字重一个文件，`weight` 必须显式列出。

## 34.7 next/script 的三种策略

第三方脚本要控制两件事：什么时候下载，什么时候执行。

| 策略 | 下载时机 | 执行时机 | 适用 |
| --- | --- | --- | --- |
| `beforeInteractive` | 首屏 HTML 中 | 任何 Next.js 代码之前 | 必须在水合前跑的拦截器、同意管理 |
| `afterInteractive` | 水合后立刻 | 与页面交互并行 | 统计、标签管理，默认值 |
| `lazyOnload` | 浏览器空闲 | 资源取完之后 | 客服挂件、聊天、低优先级统计 |

```tsx
// src/app/layout.tsx
import Script from "next/script";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN">
      <body>
        {children}
        <Script id="gtm" strategy="afterInteractive">
          {`(function(w,d,s,l,i){/* GTM 片段 */})(window,document,'script','dataLayer','GTM-XXXX');`}
        </Script>
        <Script
          src="https://cdn.example-chat.com/widget.js"
          strategy="lazyOnload"
          data-widget-id="teamstack"
        />
      </body>
    </html>
  );
}
```

三条硬规则：

- 内联脚本必须给 `id`，否则框架无法跟踪和优化这段脚本。
- `beforeInteractive` 只能放在根布局，放在页面里不生效。
- `onLoad`、`onReady`、`onError` 只能在客户端组件里用，并且不能和 `beforeInteractive` 搭配。水合前执行的回调没有客户端组件可挂。

`lazyOnload` 不适合任何影响首屏功能的东西。客服挂件晚三秒出现可以接受，支付 SDK 晚三秒会出现按钮点不动。

`worker` 策略在 App Router 不可用，它依赖 Partytown，目前只支持 Pages Router。想在 App Router 里把第三方脚本挪出主线程，只能自己接 Partytown。

脚本之间存在依赖时，顺序由策略和引入位置共同决定。同意管理必须在水合前跑完，否则统计脚本会先发请求；反过来把统计也放 `beforeInteractive`，首屏会被拖慢。常见的组合是同意管理 `beforeInteractive`，统计 `afterInteractive` 并根据同意状态决定是否加载。

开发环境不要把统计脚本打开。本地请求会污染真实数据，而且每次热更新都触发一次上报。

额外属性会透传到最终标签。`nonce` 就靠这条通道接上 CSP：

```tsx
// src/app/layout.tsx
<Script src="https://cdn.example-analytics.com/a.js" strategy="afterInteractive" nonce={nonce} />
```

同意管理要跟脚本加载顺序配合。统计脚本在用户点“接受”之前不该发请求，做法有两种：先不渲染 `<Script>`，用状态控制挂载；或者照常加载，但在初始化时读同意状态，未同意就不上报。前者少下载一个文件，后者实现简单，选一种就行。

## 34.8 第三方嵌入与 CSP

视频、地图、表单这类嵌入用 iframe。iframe 一进页面就会加载对方的整个运行时，YouTube 播放器大约 1MB，地图更大。

三个必给的属性：`title`（无障碍，读屏用它说明这个框是什么）、宽高或 CSS 比例（否则 iframe 在加载前高度为 0，内容到达后整页往下推）、`loading="lazy"`（视口外先不加载）。

再往前一步是门面组件。先用一张封面图代替 iframe，用户点了才真正加载：

```tsx
// src/components/video-facade.tsx
"use client";

import Image from "next/image";
import { useState } from "react";

export function VideoFacade({ id, title }: { id: string; title: string }) {
  const [active, setActive] = useState(false);

  if (!active) {
    return (
      <button
        type="button"
        onClick={() => setActive(true)}
        className="relative block aspect-video w-full overflow-hidden rounded-lg"
        aria-label={`播放视频：${title}`}
      >
        <Image
          src={`https://i.ytimg.com/vi/${id}/hqdefault.jpg`}
          alt=""
          fill
          sizes="(max-width: 768px) 100vw, 720px"
          className="object-cover"
        />
      </button>
    );
  }

  return (
    <iframe
      src={`https://www.youtube-nocookie.com/embed/${id}?autoplay=1`}
      title={title}
      loading="lazy"
      allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture"
      allowFullScreen
      className="aspect-video w-full rounded-lg"
    />
  );
}
```

`@next/third-parties` 提供了同类封装，`YouTubeEmbed`、`GoogleMapsEmbed`、`GoogleTagManager` 都按这条思路实现：点击后才加载真正的 iframe。

上线新策略前可以先跑 `Content-Security-Policy-Report-Only`，它只报告不拦截。观察一周报告里的 `violated-directive`，把漏掉的域名补齐，再切成正式策略。直接上强制策略，第三方脚本会被静默拦掉，页面功能缺失但页面本身正常。

CSP 与这一切直接相关。启用 `script-src` 白名单后，没有列进去的域名会被浏览器拦掉，控制台报：

```text
Refused to load the script 'https://www.googletagmanager.com/gtag/js' because it violates
the following Content Security Policy directive: "script-src 'self'".
```

CSP 要按实际用到的域名逐项放行：脚本域名进 `script-src`，iframe 域名进 `frame-src`，图片域名进 `img-src`，字体走 `font-src 'self'`。用 nonce 可以只放行带 nonce 的脚本，比维护域名列表稳。

顺序上先接 CSP 再加脚本。反过来做，每次上线新脚本都要改策略、重新验证。

还有一类失败发生在构建阶段。`next.config.ts` 里 `images` 的字段名拼错，例如把 `remotePatterns` 写成 `remotePattern`，构建不会报错，配置直接失效，运行时才看到 400。改完配置必须重启开发服务器，热更新不会重新加载这份文件。

## 34.9 边界与失败模式

**未验证**：本章的 Lighthouse 分数、`curl` 的 400 反证与 Network 面板计数来自官方文档与常见实测区间，本地未跑 teamstack 实例，数字仅作量级参考。

以下几类问题不会在开发时暴露。

私有存储的图片在优化接口下必然失败。优化器取图不带 cookie 和 Authorization，返回 401，页面上是裂图。加 `unoptimized` 或改用签名 URL。

远程白名单和实际域名差一个子域。`images.example.com` 与 `cdn.example.com` 是两个 hostname，要各写一条。

`sizes` 与服务端生成的 `srcset` 不匹配时，不会报错，只是下载了偏大的一档。这类浪费只能靠看 `currentSrc` 发现。

`preload` 用在非 LCP 图上，会把并发让给次要资源。表现是首屏完成时间变差，其它指标正常。

字体只写了 `subsets: ["latin"]` 却期望中文生效。汉字不在这个子集里，渲染出来是系统字体，观感与设计稿不一致。

第三方脚本没有 `id` 时，内联内容仍然会执行，但框架无法去重。同一段代码在多个页面引入，可能执行两次。

CSP 上线后第三方嵌入变空白。iframe 被 `frame-src` 拦掉时页面没有任何报错，只在控制台有一行。这类问题要在上线前用浏览器控制台过一遍。

图片和字体之外还有一类资源容易被忘：用户上传的 PDF、表格、压缩包。它们不参与首屏渲染，但下载体验由响应头决定。文件名要带 `Content-Disposition`，长度要提前显示，别让用户点下去才发现是 40MB。

## 34.10 检查点

1. `grep -n "remotePatterns" next.config.ts` 能看到配置，且 `hostname` 里没有 `"**"`。用 `curl -sI "http://localhost:3000/_next/image?url=https://example.com/a.png&w=640&q=75"` 验证，返回 400。
2. 打开图片最多的页面，Network 面板筛 `Img`，看每张图的 `w=` 参数与渲染宽度是否匹配，差两档以上的改成正确 `sizes`。
3. Network 面板搜 `gstatic`、`fonts.googleapis`，结果为 0 条。页面源码里字体文件是相对路径的 `/_next/static/media/*.woff2`。
4. Lighthouse 的 Mobile 报告里，CLS 低于 0.1，LCP 低于 2.5 秒。图片和 iframe 都写了宽高或比例。
5. 打开一个带 YouTube 嵌入的页面，Network 里搜 `youtube`，首屏只有封面图请求；点击之后才出现 iframe 相关请求。
6. 浏览器控制台无 CSP 报错，`frame-src` 白名单覆盖所有嵌入域名。

## 34.11 常见错误

1. `hostname "xxx.supabase.co" is not configured under images`。 远程图域名没进 `remotePatterns`。加一条，写全 `protocol`、`hostname`、`pathname`。

2. 图片返回 400，但配置看着没问题。 多半是路径不匹配：`pathname` 写成了 `/storage/**`，实际地址在 `/storage/v1/object/public/` 下面。用 `curl` 打印完整 URL 逐段对比。

3. `Image with src "..." has legacy prop "layout"`。 用的是 13 之前的写法。改成 `fill` 加父容器定位，或直接给 `width`、`height`。

4. `Image with src "..." is missing required "width" property`。 远程图既没给宽高也没用 `fill`。补上，或者用静态导入让框架从文件读尺寸。

5. 字体没生效，检查器里显示系统字体。 `localFont` 的路径按调用文件解析，`@/` 别名不生效；或者 `subsets` 没包含实际字符。改相对路径，确认 `@theme` 里的变量名与 `variable` 一致。

6. `Cannot find module '@next/third-parties/google'`。 这个包要单独装：`pnpm add @next/third-parties`。它标记为实验性，升级时留意破坏性变更。

## 34.12 这一章在做什么

这一章建立三条判断。远程图片必须按路径白名单放行，`hostname: "**"` 等于开放代理。图片的下载量由 `sizes` 和断点决定，写错就是白下载。外部资源要晚加载、少请求，字体自托管、脚本按策略、iframe 用门面。

验收看一组数字：首屏传输量、LCP、CLS、外部域名请求数。四项都在合理区间，配置才算写对。

下一章处理同一批页面的另一半质量：窄屏布局、键盘操作、读屏语义，这些不体现在性能指标里，但决定页面能不能被别人用。
