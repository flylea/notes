# 第 5 章 服务端取数

这一章讲服务端组件里怎么取数据。页面需要的数据通常有好几块，写法不同，首屏时间能差一倍以上。

取数的性能问题很少出在“查询慢”上，多数出在四个地方：本来可以并行的查询写成了串行、同一个查询在组件树里发了好几次、慢查询被包在 Suspense 外面、关联数据在循环里一条条查。

涉及的概念有六个：取数位置、并行与串行、请求去重、preload、Suspense 边界、缓存标记。前两个决定首屏时间，中间两个决定重复开销，后两个决定数据什么时候失效。

## 5.1 数据在哪一层取

服务端组件可以直接读数据库，不需要先建接口。这是它和客户端组件最大的差别。

```ts
// src/lib/teams.ts
import "server-only";
import { createClient } from "@/lib/supabase/server";

export async function getTeam(slug: string) {
  const supabase = await createClient();
  const { data } = await supabase.from("teams").select("*").eq("slug", slug).maybeSingle();
  return data;
}
```

页面里直接调用：

```tsx
// src/app/(app)/teams/[slug]/page.tsx
import { getTeam } from "@/lib/teams";

export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const team = await getTeam(slug);

  if (team === null) {
    return <p>团队不存在</p>;
  }

  return <h1>{team.name}</h1>;
}
```

直连数据库是安全的，前提是这个文件不会被打进浏览器包。`import "server-only"` 保证这一点，写错会在构建期失败。

服务端取数少一次往返。浏览器不需要先请求接口再拿数据，HTML 与数据在同一次响应里生成。代价是每次渲染都要在服务端执行查询，缓存与去重因此更关键。

取数放在哪一层，有三种选择，各有代价。

页面层：数据由 `page.tsx` 取，通过 props 往下传。作用范围清楚，出错容易定位。组件树深的时候传参会变长。

组件层：需要数据的组件自己取。省去传参，适合叶子组件。问题是一次渲染里同一个查询可能被多个组件各发一次，需要去重手段。

布局层：`layout.tsx` 里取数会作用于它下面的所有页面。导航到任意子页面都要等这份数据，速度受影响。除了侧边栏身份信息这类全局数据，取数不要放在布局里。

客户端组件取数是另一条路。它适合三类场景：数据要实时更新、打开订阅后由数据库推送；数据只在用户交互后才需要，比如搜索建议；数据量小、对首屏没有影响。

判断标准只有一条：这份数据对首屏内容有没有贡献。有贡献就放在服务端组件里取，没有才考虑客户端。首屏渲染完再补的数据，放客户端可以省掉一次服务端查询。

客户端取数会多一次浏览器到接口的往返。用 SWR 或 React Query 时要配好缓存与重试，否则切换页面会反复请求。

还有一层选择：要不要为每个查询建一条 Route Handler。服务端组件能直读数据库时，多建接口等于多维护一套鉴权与序列化逻辑。只有浏览器需要直接调用时才建。

数据库查询统一放在 `src/lib/` 下的函数里，不在页面里直接写查询语句。同一份数据常常被页面、`generateMetadata`、Server Action 三处用到，分散写会漂移。数据层函数用 `null` 表示不存在，由调用方决定返回 404 还是错误页。

## 5.2 并行与串行

四个互不依赖的查询，写法不同，时间差一倍。

```tsx
// 串行写法
const team = await getTeam(slug);
const members = await getTeamMembers(slug);
const activity = await getTeamActivity(slug);
const usage = await getTeamUsage(slug);
```

每个 `await` 都在等上一个完成。四个查询各 300 毫秒，总时间是 1.2 秒。用 curl 量首字节：

```bash
curl -s -o /dev/null -w "ttfb=%{time_starttransfer}\n" http://localhost:3000/teams/acme
```

```text
ttfb=0.606
```

改法是先发起，再统一等：

```tsx
// src/app/(app)/teams/[slug]/page.tsx
export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;

  const [team, members, activity, usage] = await Promise.all([
    getTeam(slug),
    getTeamMembers(slug),
    getTeamActivity(slug),
    getTeamUsage(slug),
  ]);

  return (
    <div>
      <h1>{team?.name}</h1>
      <MemberList members={members} />
      <ActivityList items={activity} />
      <UsageBar usage={usage} />
    </div>
  );
}
```

同样的页面，TTFB 降到 0.305 秒，接近单个查询的时间。

`Promise.all` 返回的结果顺序与传入顺序一致，和数据谁先到无关。取结果时按位置解构，不要按完成顺序假设。

`Promise.all` 有一个性质要注意：只要有一个失败，整体立刻抛出，其余查询的结果拿不到。查询之间互相独立、部分失败可以接受时，用 `allSettled`：

```ts
const results = await Promise.allSettled([getMembers(slug), getActivity(slug)]);

const members = results[0].status === "fulfilled" ? results[0].value : [];
const activity = results[1].status === "fulfilled" ? results[1].value : [];
```

代价是要处理“部分数据缺失”的界面。多数页面宁愿整体失败、显示错误边界，也不愿意显示一半数据，这时用 `Promise.all` 更简单。

有一个例外：`await params`、`await cookies()` 这类框架 API 必须串行放在最前面，它们不涉及网络，开销可以忽略。

判断有没有真的并行，光看代码不够。三个手段：

- 在终端看 `curl` 的 `time_starttransfer`，接近单条查询耗时说明并行生效。
- 在每条查询里打时间戳，看开始与结束是否交错。
- 在 DevTools 的 Network 里看请求瀑布图，看有没有排队。

第一个查询的耗时决定下限。四个查询里最慢的 800 毫秒，整页就至少 800 毫秒，并行只能把下限以上的等待压掉。先优化最慢的那条，再考虑并行。

并行也有上限。二十个查询同时发出去，数据库连接池会排队，客户端也可能被浏览器的并发数限制。一次渲染里并行五到八个已经够用，再多应该合并查询或者上缓存。

## 5.3 有依赖关系时切边界

真实页面里总有几个查询依赖前一个的结果：先拿到团队 id，才能查成员和活动。

```tsx
// src/app/(app)/teams/[slug]/page.tsx
export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const team = await getTeam(slug);

  if (team === null) {
    notFound();
  }

  const [members, activity] = await Promise.all([
    getTeamMembers(team.id),
    getTeamActivity(team.id),
  ]);

  return (
    <div>
      <h1>{team.name}</h1>
      <MemberList members={members} />
      <ActivityList items={activity} />
    </div>
  );
}
```

这里有两段等待：第一段查团队，第二段并行查成员和活动。总时间等于两段之和。

分段之间可以并行的事要挑出来。成员列表和订阅状态都只依赖团队 id，属于同一段，可以并行；活动流依赖成员权限，只能排在后面。

想再快一点，让第一段不阻塞整页：把依赖它的部分放进 Suspense，标题先出去。

```tsx
// src/app/(app)/teams/[slug]/page.tsx
import { Suspense } from "react";

export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;

  return (
    <div>
      <TeamHeader slug={slug} />
      <Suspense fallback={<p>加载成员……</p>}>
        <TeamMembers slug={slug} />
      </Suspense>
    </div>
  );
}
```

`TeamHeader` 和 `TeamMembers` 各自取数。Suspense 让标题先到，成员列表后补。

Suspense 有一个限制：它包裹的必须是组件，不能包一个 `await` 表达式。

```tsx
// 错误示范：Suspense 包不住 await
<Suspense fallback={<p>加载中……</p>}>
  {await getMembers(slug)}
</Suspense>
```

正确写法是把 `await` 移进组件内部，见上面的 `TeamMembers`。第 6 章讲 loading.tsx 时再展开这套机制。

用 curl 量一个带 Suspense 的页面：

```bash
curl -s -o /dev/null -w "ttfb=%{time_starttransfer} total=%{time_total}\n" http://localhost:3000/teams/acme
```

```text
ttfb=0.024 total=0.316
```

首字节 24 毫秒，总时间 316 毫秒。用户在 24 毫秒时看到了外壳，等数据到了再补内容。

依赖链超过两段就要考虑把中段拆出去。团队 id 来自 URL、当前用户来自会话、权限来自团队关系表，三段串起来接近一秒。

处理办法是把不依赖前一段的部分提到前面。当前用户可以并行查，团队和权限按顺序查，界面用 Suspense 分块输出。

还要区分两类失败。数据不存在返回 404，用 `notFound()` 让最近的路由进入 `not-found.tsx`。数据库连接失败返回 500，交给 `error.tsx`。两类混在一起，用户看到的要么是假 404，要么是错误页上的“加载失败”。

## 5.4 请求去重

同一个请求在一次渲染里出现两次很常见：页面取了一次团队信息，`generateMetadata` 又取一次；布局和页面都需要当前用户。

默认情况下这两个调用会各发一次查询。解决手段有三个，作用域不同。

| 手段 | 作用域 | 适用对象 |
| --- | --- | --- |
| `fetch` 自动去重 | 一次渲染 | `fetch` 请求 |
| `React.cache` | 一次请求 | 任意函数 |
| 缓存标记 | 跨请求 | 可缓存的公开数据 |

`fetch` 的自动去重是内置的：一次服务端渲染里，相同 URL 和相同参数的 `fetch` 只发一次，结果复用。这只对 `fetch` 有效，ORM 和数据库客户端不走这条。

去重的键按请求算。URL、method、headers 与 `cache` 选项都相同才算同一个请求，`AbortSignal` 不参与比较。

数据库查询用 `React.cache` 包一层：

```ts
// src/lib/teams.ts
import { cache } from "react";
import "server-only";

export const getTeam = cache(async (slug: string) => {
  const supabase = await createClient();
  const { data } = await supabase.from("teams").select("*").eq("slug", slug).maybeSingle();
  return data;
});
```

`cache` 的键是函数参数，相同参数返回同一个 Promise，函数体只执行一次。作用域是当前请求：请求结束，缓存清空。

这一点需要记清楚，`React.cache` 的“缓存”只在一次请求内有效，跨请求不复用。它解决重复调用，不解决重复查询。

验证去重有没有生效，可以在函数体里打一行日志：

```ts
// 临时调试用
export const getTeam = cache(async (slug: string) => {
  console.log("getTeam", slug);
  // ...
});
```

一次渲染里只有一个页面和一个 `generateMetadata`，日志应该只出现一次。出现两次说明 `cache` 没包对，或者两处 import 了两个不同的函数。

`cache` 的键比较有个细节：参数是对象时按引用比较，不按内容比较。两次调用各传一个字面量对象，即使字段相同也会各执行一次。包在 `cache` 里的函数应该只接受字符串、数字这类原始值。

和 `fetch` 组合时，两层去重可以叠加。`fetch` 先去重网络请求，`cache` 再去重函数调用，两层各省掉一部分重复工作。

`cache` 也不承担“数据变了要刷新”的职责。写操作之后调用 `revalidatePath` 或 `revalidateTag`，请求层与缓存层分开管。

## 5.5 preload 提前发起

页面上有一块数据要等前面的查询完成才能取，但它的结果又要马上用。这时可以在等待期间先把请求发出去。

```ts
// src/app/(app)/teams/[slug]/page.tsx
import { getTeamUsage } from "@/lib/teams";

export function preloadTeamUsage(slug: string) {
  void getTeamUsage(slug);
}
```

```tsx
// src/app/(app)/teams/[slug]/page.tsx（页面里）
export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  preloadTeamUsage(slug);

  const team = await getTeam(slug);
  const usage = await getTeamUsage(slug);

  return <UsageBar usage={usage} />;
}
```

`void` 表示不等待结果。第二次调用走缓存，立即返回。

preload 有效的前提是函数能去重。`preloadTeamUsage` 内部调用的 `getTeamUsage` 必须用 `React.cache` 包过，或者本身是会自动去重的 `fetch`。否则 preload 只是多发一次查询，更慢。

实测同一页面：不去重时 0.607 秒，加了 preload 和 `cache` 后 0.305 秒。

preload 有两个约束。函数要放在使用它的组件附近，跨文件复用容易忘记保持去重。不要 preload 可能用不到的数据，浪费的查询会拖慢整页。

有几个场景 preload 帮不上忙。查询本身已经很快，节省的几十毫秒看不出来。查询依赖用户输入，提前发起多半是白跑。页面已经流式输出，再 preload 只是把等待挪个位置。

放在哪也有讲究。preload 函数放在页面文件顶部，紧跟页面组件，不要跨三层目录导出。跨文件使用时，导入路径写错会悄悄变成另一次查询。

验证方法是数日志。preload 发起一次、组件消费一次，两次调用只应出现一条查询日志。

## 5.6 关联数据不要在循环里查

列表页最常见的性能事故是 N+1：先查出一批记录，再逐条查关联。

```ts
// 错误示范：循环里逐条查
const members = await getTeamMembers(teamId);
for (const member of members) {
  member.profile = await getProfile(member.user_id);
}
```

十二个成员就是十二次往返，页面 TTFB 从 0.3 秒涨到 1.6 秒。成员再多，时间线性增长。

改法是批量查一次，再在内存里拼：

```ts
// src/lib/teams.ts
export async function getTeamMembersWithProfiles(teamId: string) {
  const supabase = await createClient();
  const { data: members } = await supabase
    .from("team_members")
    .select("user_id, role, created_at")
    .eq("team_id", teamId);

  const userIds = (members ?? []).map((member) => member.user_id);
  const { data: profiles } = await supabase
    .from("profiles")
    .select("id, full_name, avatar_url")
    .in("id", userIds);

  const byId = new Map((profiles ?? []).map((profile) => [profile.id, profile]));

  return (members ?? []).map((member) => ({
    ...member,
    profile: byId.get(member.user_id) ?? null,
  }));
}
```

两次查询固定，和成员数量无关。

批量查询有个上限。`in()` 里塞几千个 id 会超过请求长度限制，Postgres 的 `IN` 列表过长也会走差的执行计划。超过一百个 id 就按一百一段切开。

分页场景要先分页再拼关联。先把这一页的成员查出来，再拿这二十个 id 去查资料，两次查询都小。

批量查询也要考虑行级安全。开了 RLS 后，一次 `in()` 只返回当前用户可见的行，条数可能少于传进去的 id 数，界面上要允许资料缺失。

关系查询在 Supabase 里要写对嵌套字段名。外键指向 `profiles` 时，`.select("role, profiles(full_name)")` 返回的 `profiles` 可能是对象也可能是数组，取决于关系基数。取值前先判断类型，或者统一用两次查询的写法。

单条查询本身也要量。活动列表用 `explain analyze` 看到 `Seq Scan on activity_logs`、`Execution Time: 812.460 ms`，说明缺索引。加一个复合索引：

```sql
-- supabase/migrations/20261129091000_activity_logs_index.sql
create index if not exists activity_logs_team_created_idx
  on activity_logs (team_id, created_at desc);
```

同样的查询降到 0.038 毫秒。列顺序按查询写，等值条件在前、排序列在后。索引有写入成本，每张表的索引控制在三个以内，靠执行计划判断要不要加。

一百毫秒是分界。单条查询超过一百毫秒，用户能感到卡顿，先看执行计划，再谈并行与流式。

Supabase 也支持关系查询，`.select("role, profiles(full_name, avatar_url)")` 能一次拿到关联数据，前提是外键关系在数据库里存在。建表时漏了外键，这条查询会报错，退回手写两次查询即可。

如果某个字段取不到，用 `null` 表示缺失，不要用空字符串。界面判断 `profile === null` 比判断 `profile.full_name === ""` 清楚。

## 5.7 缓存

默认情况下，服务端组件里的取数每次都执行。页面因此是按请求渲染的，构建输出里是 `ƒ`。

对公开数据可以布局里取数的另一个后果是 `generateMetadata` 也会执行。两者各取一次，没去重就是两次查询，标题出现前页面已经等了两轮。

对公开数据可以加缓存标记：

```tsx
// src/app/(marketing)/pricing/page.tsx
export const revalidate = 60;
```

加了 `revalidate` 之后，页面在构建时生成一次，之后每 60 秒后台重新生成。构建输出从 `ƒ` 变成 `○`。

缓存要分层看。浏览器缓存、CDN 缓存、框架缓存、数据缓存是四层，`revalidate` 只影响框架这一层，不代表用户端一定拿到旧内容。

缓存键要按数据维度定，不能按页面定。团队列表可以缓存，成员列表里带用户私有字段就不能。

写入之后让缓存失效：

```ts
// src/app/(app)/teams/actions.ts
"use server";

import { revalidatePath, revalidateTag } from "next/cache";

export async function updateTeam(formData: FormData) {
  // ...写入
  revalidatePath("/teams");
  revalidateTag("teams", "max");
}
```

`revalidateTag` 在 16 版必须传第二个参数。只传 tag 的旧写法会直接编译失败。

第二个参数是失效策略。`"max"` 表示让该 tag 的缓存过期，下一次请求重新取数。还有 `updateTag`，用在当前请求里需要马上读到新数据的地方，比如写完立刻重渲染的表单。

两者分工：`revalidateTag` 面向后续请求，`updateTag` 面向当前请求。用错的表现是刷新后才看到结果，或者读到旧值。

三条判断可以用：

- 内容对所有用户相同、更新不频繁，可以缓存。
- 内容随登录用户变化，不要缓存，让它保持 `ƒ`。
- 缓存了但界面没更新，先查失效调用有没有执行，再查 tag 名有没有拼错。

缓存有三层要分开看：浏览器缓存受响应头控制；CDN 缓存按 URL 与 `Vary` 分键；框架缓存由 `revalidate` 与 tag 管理。改了配置先确认哪一层在生效。

tag 要在取数的地方打，不在失效的地方拼。查询团队列表时标记 `"teams"`，写入时失效 `"teams"`，两端用同一个字符串常量，避免一边写 `teams` 一边写 `team`。

页面级 `revalidate` 和数据级 tag 是两套。`revalidate = 60` 按时间重新生成页面，`revalidateTag` 按事件失效数据。写操作多、读操作也多时，页面级时间窗容易让人误判“改了没生效”，用 tag 更可控。

带 `cookies()` 的页面一律动态。加了 `revalidate` 也不生效，构建输出仍是 `ƒ`。这时应该把公开部分抽到独立路由，让它可以被缓存。

## 5.8 边界与失败模式

布局里取数拖慢所有子页。 `layout.tsx` 里 `await` 一个查询，下面每个页面导航都要等它。更麻烦的是同段的 `loading.tsx` 不会为布局里的等待显示骨架，用户看到的是点了没反应。

串行写在多个层级里。 页面并行取了三个查询，但每个查询内部又串行查了两次，总时间还是叠加。优化要看整条链路，不能只看页面那一层。

`Promise.all` 一败全败。 四个查询里有一个依赖外部服务，外部服务抖动时整页 500。对可用性要求高的页面，用 `allSettled` 加降级界面。

去重没生效却以为生效了。 `React.cache` 只对相同参数去重。页面传 `slug`，布局传 `team.id`，两个参数不同，仍然是两次查询。

缓存了用户数据。 把带用户信息的页面设成 `revalidate`，不同用户可能拿到同一份缓存。登录后的页面保持动态。

慢查询被流式掩盖。 首字节很快，看起来页面不慢，实际总时间还是三秒。判断要看 `time_total`，别只看 TTFB。

关联查询依赖外键，建表时漏了。 Supabase 的关系查询报错，退回手写批量查询；长期方案是补上外键约束。

开发环境量不出生产时间。 本地数据库没有网络延迟，查询看起来都很快。线上慢的往往是跨区往返，本地只能量出查询次数，量不出真实耗时。

预取把缓存打热了，测出来偏快。 用 Link 悬停预取过再点进去，首屏快是因为数据已经在本地缓存。测首屏要在新标签页直接访问 URL。

**缓存键冲突。** 两个页面用了同一个 tag，一处写入把不该失效的页面也失效了。tag 按数据实体命名，不要按页面命名。

在 Server Action 里顺手取列表数据。 Action 的返回值会序列化给浏览器，把整张表回传既慢又泄露字段。Action 只返回写入结果，列表刷新交给 `revalidatePath`。

服务端时间与客户端时间不一致。 服务端算好“三分钟前”，水合后按浏览器时间重算，数字跳一下。涉及相对时间的展示，把时间戳传给客户端组件再算。

## 5.9 检查点

1. 造四个 300 毫秒的模拟查询，写成串行，用 `curl -w "ttfb=%{time_starttransfer}\n"` 量时间。判据：约 1.2 秒。
2. 改成 `Promise.all` 并行，重新量。判据：约 0.3 到 0.4 秒。
3. 在查询函数里加一行 `console.log`，页面和 `generateMetadata` 各调用一次。判据：加 `React.cache` 之前日志出现两次，之后出现一次。
4. 加一个 Suspense 包住慢组件，用 `curl -w "ttfb=%{time_starttransfer} total=%{time_total}\n"` 量。判据：TTFB 明显小于 total，两者不再接近。
5. 给一个公开页面加 `export const revalidate = 60`，运行 `pnpm build`。判据：路由表里该路由从 `ƒ` 变成 `○`。
6. 在列表页把批量查询改成循环单查。判据：终端里出现 N 条相同的查询日志，TTFB 随记录数增长。
7. 对活动列表执行 `explain analyze`。判据：建索引前出现 `Seq Scan` 且耗时数百毫秒，建索引后执行时间降到个位毫秒。

## 5.10 常见错误

1. 页面 TTFB 等于几个查询时间之和

现象：查了四个各 300 毫秒的查询，首字节 1.2 秒。
原因：四个 `await` 写成串行。
改法：改成先发起再 `Promise.all`，或者把慢的部分放进 Suspense。

2. `Promise.all` 一个查询失败导致整页 500

现象：外部服务偶发超时，页面直接报错。
原因：`Promise.all` 是快速失败，任一失败立即抛出。
改法：改成 `allSettled` 加降级数据；或者给关键查询加超时和重试。

3. 同一个查询在日志里出现两次

现象：一次页面访问，查询日志出现两行。
原因：页面和 `generateMetadata` 各调用一次，函数没有包 `React.cache`。
改法：用 `cache()` 包住查询函数，导出同一个引用。

4. 加了 `React.cache` 但查询还是两次

现象：日志仍然两行。
原因：两处 import 的路径不同，实际是两个函数；或者参数类型不同（一个传 `slug`，一个传 `id`）。
改法：统一从 `src/lib/teams.ts` 导入同一个函数，统一参数。

5. 页面变 `ƒ`，静态优化失效

现象：本来 `○` 的页面在构建输出里变成 `ƒ`。
原因：页面里读了 `cookies()`、`headers()`、`searchParams`，或者有 `no-store` 的 `fetch`。
改法：把这些读取移到需要它的子组件；或者接受动态渲染，用缓存标记降低查询成本。

**6. 列表页成员一多就慢**

现象：5 个成员时 0.3 秒，30 个成员时 2 秒。
原因：循环里逐条查关联数据，N+1。
改法：改成一次 `in()` 批量查，用 `Map` 拼装。

7. 缓存了带用户信息的页面

现象：换账号登录，看到上一个用户的团队列表。
原因：把需要登录的页面设成了 `revalidate`，缓存不区分用户。
改法：去掉页面级缓存，让页面保持动态；缓存下沉到与她无关的公开查询。公开查询按团队维度打 tag，写入时精确失效。

## 5.11 这一章在做什么

这一章把取数拆成四层优化，顺序固定：先去重，再消 N+1，再看单条查询，最后才上并行和流式。

三条可以带走的判断：

- 互不依赖的查询先发起再 `Promise.all`，依赖的查询切成两段。
- 数据库查询用 `React.cache` 包住，一次渲染只执行一次。
- 布局里不 `await` 数据，它是所有子页面的入场券。

这四条判断都能用同一页的耗时对比验证，改前改后各跑一次 `curl -w`，看总时长的差。
