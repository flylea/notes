# 第 42 章 产品分析埋点

埋点回答的是产品问题：用户从进来到付费，中间每一步走了多少人，在哪一步掉得最多。这一章讲怎么把用户行为记成可以查询的数据，怎么算漏斗，以及哪些数据不该记。

涉及三个概念。事件是用户做的一件事，注册、建团队、上传文件都算。属性是这件事的上下文，文件多大、从哪个页面来、用了什么设备。漏斗是按顺序串起来的一组事件，用来算转化率。

工具层面有两条路：接第三方分析平台，或者自己在数据库里建一张事件表。本章选后者，因为事件表能和业务表 join。要算「建了团队的人里有多少付费」，自己的表一条 SQL 就行，第三方平台通常要导出数据再对。

自建也有代价：查询要自己写，看板要自己做，数据量大了要处理存储。这些代价在用户量不大时都可以接受，本章会给出量级判断。

## 42.1 先定义事件模型

埋点最容易犯的错，是随手往数据库里塞字符串。三个月之后想查「注册到付费的转化率」，发现事件名有 `signup`、`register`、`user_registered` 三种写法，谁也说不清哪个是哪个。

事件模型先定三件事：事件名、必填字段、属性规则。

事件名用「对象加过去式动词」的形式：`team_created`、`invitation_sent`、`file_uploaded`、`subscription_started`。过去式表示这件事已经发生，和命令式的函数名区分开。带状态的词不要出现在名字里，`team_created_pro` 这种把套餐写进名字的写法，套餐一变，历史数据就对不上了。

五类必填字段：事件名、用户 id、团队 id、发生时间、属性对象。用户和团队允许为空，比如匿名访问时还没有用户，但字段本身要在，值写 null。

属性只放枚举值和数值。`mime_type` 存 `image/png`，`file_size` 存字节数，`source` 存 `invite_link`。不要存文件名、邮箱、请求体，原因在 42.9 节讲。

属性只增不改。新增一个属性可以，改一个已有属性的含义不行。比如 `size_bucket` 原本按 1MB 分档，后来改成 10MB 分档，同名字段里就混了两种口径，查询结果没法解释。要改就加新字段，旧字段停写。

一条事件的形态。

```json
{
  "name": "file_uploaded",
  "user_id": "0b6f8c1e-...",
  "team_id": "7c3f2a91-...",
  "occurred_at": "2026-11-15T13:22:41.771Z",
  "properties": {
    "mime_bucket": "image",
    "size_bucket": "1m_10m",
    "source": "drag_drop"
  }
}
```

事件模型定下来之后，写进 `docs/analytics-events.md`。后面每一节都围绕这份定义展开。

## 42.2 自建表还是接第三方

三种常见方案，差别在查询能力和成本。

第一种，自己在 Postgres 里建表。优点是能和 `teams`、`subscriptions` 直接 join，权限复用 RLS，没有额外服务。缺点是查询要自己写，看板要自己做，事件量到千万级之后要分区或者换列存。

第二种，PostHog 这类开源自托管平台。优点是自带漏斗、留存、会话回放，界面现成。缺点是多一套服务和数据库，回放功能还会采集 DOM，隐私评审要过一遍。

第三种，GA4。优点是免费、渠道归因成熟。缺点是事件数据在 Google 那边，导出有延迟，和业务表 join 要先落地到本地。

选自建的理由是查询自由度。这套教程里的问题大多是「建了团队的人里有多少付费」「邀请了几个人之后流失率下降多少」，这类问题需要把事件表和业务表放在一起算。事件量在百万级以内，Postgres 完全够用。

GA4 仍然装上，只用来回答渠道问题：用户从搜索来还是从推荐来。两套数据各管一段，不要试图合并成一个真相。

量级判断可以给个粗数：每天一万条事件、保留一年，大约三百万行，加上索引不到 1GB。单表加时间索引能撑住。每天百万条以上，再考虑按月分区或者转 ClickHouse。

## 42.3 建事件表

新建迁移文件。项目里迁移编号已经排到 `0013`，这里从 `0014` 开始。

```sql
-- supabase/migrations/20261128090000_events.sql
create table public.events (
  id uuid primary key default gen_random_uuid(),
  name text not null check (char_length(name) between 3 and 64),
  user_id uuid references public.profiles (id) on delete set null,
  team_id uuid references public.teams (id) on delete set null,
  anonymous_id text,
  properties jsonb not null default '{}'::jsonb,
  occurred_at timestamptz not null default now(),
  created_at timestamptz not null default now()
);

create index events_team_time_idx on public.events (team_id, occurred_at desc);
create index events_user_time_idx on public.events (user_id, occurred_at desc);
create index events_name_time_idx on public.events (name, occurred_at desc);
create index events_properties_idx on public.events using gin (properties jsonb_path_ops);

alter table public.events enable row level security;

create policy "team members can read own events"
  on public.events for select
  using (
    team_id is not null
    and exists (
      select 1 from public.team_members m
      where m.team_id = events.team_id and m.user_id = auth.uid()
    )
  );

revoke all on public.events from anon, authenticated;
grant select on public.events to authenticated;
grant all on public.events to service_role;
```

几个设计决定要解释。

`user_id` 和 `team_id` 用 `on delete set null`，不用 `cascade`。用户注销时事件要保留，只是不再关联到人。级联删除会把统计数据一起删掉，漏斗曲线会突然断层。

`anonymous_id` 用来串未登录到登录的路径。用户先浏览落地页再注册，注册前的行为挂在匿名 id 上，注册后把两者关联起来。

四个索引各有用途。`(team_id, occurred_at desc)` 支持团队维度的漏斗，`(user_id, occurred_at desc)` 支持单用户路径，`(name, occurred_at desc)` 支持按事件名统计趋势，`jsonb_path_ops` 的 GIN 索引支持按属性过滤。

RLS 只开 select，写入路径走服务端。策略里用 `team_id is not null` 加成员判断，个人事件（还没有团队时）只有服务端能看到。写完立刻收紧权限：`revoke all` 再按需 `grant select`，默认权限不会自动收回。

验证。

```bash
supabase db reset
psql "$DATABASE_URL" -c '\d public.events'
```

`\d` 的输出里能看到四个索引、约束和 RLS 状态。再用匿名身份查一次，确认被拒。

```bash
curl -s "$SUPABASE_URL/rest/v1/events?select=id" \
  -H "apikey: $SUPABASE_ANON_KEY" | head -c 200
```

返回 `permission denied for table events` 是对的。如果返回空数组或者数据行，说明 grant 没收回。

## 42.4 服务端埋点

大部分事件在服务端记：注册、建团队、发邀请、上传完成、订阅变更。服务端知道真实结果，客户端只知道用户点了按钮。

写一个记录函数。

```ts
// src/lib/analytics/track.ts
import "server-only";
import { after } from "next/server";
import { createAdminClient } from "@/lib/supabase/admin";
import { logger } from "@/lib/logger";

const ALLOWED_PROPERTY_KEYS = new Set([
  "source",
  "mime_bucket",
  "size_bucket",
  "invitee_domain_hash",
  "plan",
  "seats",
  "reason",
]);

type PropertyValue = string | number | boolean | null;

function sanitize(properties: Record<string, unknown>) {
  const out: Record<string, PropertyValue> = {};
  for (const [key, value] of Object.entries(properties)) {
    if (!ALLOWED_PROPERTY_KEYS.has(key)) continue;
    if (typeof value === "string" && value.length <= 120) out[key] = value;
    else if (typeof value === "number" && Number.isFinite(value)) out[key] = value;
    else if (typeof value === "boolean") out[key] = value;
  }
  return out;
}

export function track(input: {
  name: string;
  userId: string | null;
  teamId: string | null;
  properties?: Record<string, unknown>;
}) {
  after(async () => {
    try {
      const supabase = createAdminClient();
      const { error } = await supabase.from("events").insert({
        name: input.name,
        user_id: input.userId,
        team_id: input.teamId,
        properties: sanitize(input.properties ?? {}),
      });
      if (error) logger.warn("analytics.insert.failed", { name: input.name, err: error.message });
    } catch (error) {
      logger.warn("analytics.insert.threw", { name: input.name });
    }
  });
}
```

四个设计点。

白名单过滤。只允许预定义属性落库，写错字段名不会污染数据，也不会把新加的敏感字段带进去。

`after()` 让它不阻塞响应。埋点失败不影响业务，这是埋点应有的优先级。反过来，注册成功但埋点失败，业务数据仍然正确。

用 admin client 写。事件表的写入没有开放给登录用户，避免客户端伪造事件。服务端用 service role 写入，权限收口在一处。

函数返回 `void`，调用方不用 `await`。写成 `async` 也能用，但会让调用方误以为需要等待结果。

调用示例。

```ts
// src/app/api/teams/route.ts（节选）
import { track } from "@/lib/analytics/track";
import { requireUser } from "@/lib/auth";

export async function POST(request: Request) {
  const user = await requireUser();
  const body = await request.json();
  const team = await createTeam({ name: body.name, ownerId: user.id });

  track({
    name: "team_created",
    userId: user.id,
    teamId: team.id,
    properties: { source: body.source ?? "app" },
  });

  return Response.json({ team }, { status: 201 });
}
```

查一下刚写进去的事件。

```bash
psql "$DATABASE_URL" -c \
  "select name, user_id, team_id, occurred_at from events order by occurred_at desc limit 5;"
```

输出里能看到 `team_created` 一行，时间和刚才的请求对得上。

不要用数据库触发器自动记事件。触发器能看到数据变化，看不到意图：一次后台脚本批量导入也会触发，数据里就混进了非用户行为的事件。触发器还会让写操作变慢，出错时回滚整个业务事务。

## 42.5 客户端埋点

有一类事件只在浏览器里能记：页面浏览、按钮点击、表单放弃。它们没有服务端请求，只能从客户端发。

客户端不能直接连数据库，要先发到自己服务端的接口。接口做两件事：校验白名单、按用户限流。

```ts
// src/app/api/track/route.ts
import { createAdminClient } from "@/lib/supabase/admin";
import { requireUser } from "@/lib/auth";
import { checkRateLimit } from "@/lib/redis";

const CLIENT_EVENTS = new Set(["page_viewed", "cta_clicked", "form_abandoned", "invite_link_copied"]);

export async function POST(request: Request) {
  const user = await requireUser();
  const body = await request.json().catch(() => null);
  if (!body || typeof body.name !== "string" || !CLIENT_EVENTS.has(body.name)) {
    return Response.json({ error: "unknown event" }, { status: 400 });
  }

  const allowed = await checkRateLimit(`track:${user.id}:${body.name}`, 60, 60);
  if (!allowed) {
    return Response.json({ error: "too many" }, { status: 429 });
  }

  const supabase = createAdminClient();
  const { error } = await supabase.from("events").insert({
    name: body.name,
    user_id: user.id,
    team_id: typeof body.teamId === "string" ? body.teamId : null,
    properties: typeof body.properties === "object" && body.properties ? body.properties : {},
  });

  if (error) return Response.json({ error: "insert failed" }, { status: 500 });
  return Response.json({ ok: true });
}
```

白名单在这里比服务端更要紧。服务端代码是我们自己写的，客户端代码可以被改。不限制事件名，任何人都能往表里灌任意数据，一周之后表就废了。

限流按「用户加事件名」做，每分钟 60 次。页面浏览这类事件在快速切换时会连发，额度太小会丢数据；额度太大又挡不住脚本。60 是一个折中值。

属性没有白名单过滤，因为客户端的属性组合更多。这个缺口用 42.9 节的审计 SQL 补，定期检查有没有敏感字段混进去。

客户端发送用 `sendBeacon`，失败时退回 `fetch`。

```ts
// src/lib/analytics/client.ts
type ClientEvent = {
  name: string;
  teamId?: string | null;
  properties?: Record<string, string | number | boolean>;
};

export function trackClient(event: ClientEvent) {
  const body = JSON.stringify(event);
  if (typeof navigator !== "undefined" && navigator.sendBeacon) {
    const ok = navigator.sendBeacon("/api/track", new Blob([body], { type: "application/json" }));
    if (ok) return;
  }
  void fetch("/api/track", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body,
    keepalive: true,
  }).catch(() => undefined);
}
```

`sendBeacon` 的价值在页面卸载时。用户点了外链离开，普通 `fetch` 会被取消，`sendBeacon` 由浏览器接管，能发出去。`keepalive: true` 是 `fetch` 的对应能力，限制是请求体不超过 64KB。

不要在 `useEffect` 里裸调。React 的开发模式会执行两次副作用，同一次浏览记成两条。加一个去重标记，或者把触发点放在路由变化的回调里。

客户端埋点的成本要控制。每多一个事件就多一次请求，页面加载时的请求数会涨。页面浏览这类高频事件按 10% 采样，点击和转化类事件全量记。

## 42.6 用 SQL 算漏斗

漏斗的定义：一组有先后顺序的事件，按用户去重，算每一步剩下多少人。

五个关键步骤对应五个事件：注册 `user_registered`、建团队 `team_created`、发邀请 `invitation_sent`、传文件 `file_uploaded`、订阅 `subscription_started`。

```sql
-- docs/sql/funnel.sql
with steps as (
  select
    user_id,
    min(occurred_at) filter (where name = 'user_registered') as s1,
    min(occurred_at) filter (where name = 'team_created') as s2,
    min(occurred_at) filter (where name = 'invitation_sent') as s3,
    min(occurred_at) filter (where name = 'file_uploaded') as s4,
    min(occurred_at) filter (where name = 'subscription_started') as s5
  from events
  where occurred_at >= now() - interval '30 days'
    and user_id is not null
  group by user_id
)
select
  count(*) filter (where s1 is not null) as registered,
  count(*) filter (where s2 >= s1) as created_team,
  count(*) filter (where s3 >= s2) as sent_invite,
  count(*) filter (where s4 >= s2) as uploaded_file,
  count(*) filter (where s5 >= s4) as subscribed
from steps;
```

`filter (where ...)` 是 Postgres 的聚合过滤语法，等价于 `count(case when ... then 1 end)`，写起来短。

`s2 >= s1` 这条件保证顺序。只写 `s2 is not null` 会把先建团队后注册的脏数据算进转化，虽然业务上不该出现，但数据总会给你惊喜。

结果。

```text
 registered | created_team | sent_invite | uploaded_file | subscribed
------------+--------------+-------------+---------------+------------
       1284 |          612 |         214 |            96 |         11
```

注册到建团队 47.7%，建团队到发邀请 35%，发邀请到上传 44.9%，上传到订阅 11.5%。掉得最狠的是发邀请这一步，产品上值得看看邀请流程的阻力。

同一个查询按周分组，能看出趋势：转化率在涨还是在跌，改动上线前后有没有变化。分组之后记得看样本量，一周只有二十个注册时，百分比波动很大，别拿它下结论。样本量小于五十时，更适合看绝对数字，比如这周建了三个团队，上周建了两个。数字小的时候，人眼比图表更可靠。

漏斗要数人，不数次。一个用户建了三个团队，只算一个人。这就是 `group by user_id` 加 `min()` 的原因，`count(*)` 数的是行，会重复计算。

窗口要给。不限定时间范围，两年前注册的用户也会被算进来，数字会虚高。常用窗口是三十天，也可以按注册当周分组算。

## 42.7 漏斗算错的四个原因

第一个原因，顺序没校验。代码里只判断「有没有这个事件」，没判断「在哪个事件之后」，结果是并发操作、补录数据都会被算成转化。修法是每一步都和前一步比时间。

第二个原因，时间窗口不对。事件表和业务表的时间口径不同，一个是数据库 `now()`，一个是应用服务器时间，两台机器差几秒。跨零点的请求会被分到两天。统一用 `occurred_at`，并且在应用侧写 UTC 时间。

第三个原因，重复计算。一次请求重试写了两条事件，或者客户端 `sendBeacon` 和 `fetch` 都成功了。修法有两种：写入时按 `(name, user_id, 时间窗)` 去重，或者查询时用 `min(occurred_at)` 天然去重。前者更干净，需要给事件加一个 `dedupe_key` 字段并建唯一索引。

第四个原因，时区。`created_at` 存的是 UTC，报表按本地时区看，`date_trunc('day', occurred_at)` 会按 UTC 切天。北京时间上午八点之前的数据会落到前一天。要按本地天统计，先 `occurred_at at time zone 'Asia/Shanghai'` 再切。

还有一个隐蔽的坑：把「看到」和「做到」混在一起。用户打开了邀请弹窗，记了 `invitation_sent`，其实没发出去。事件名必须描述结果，不要描述意图。要记意图就单独开一个 `invitation_form_opened`，两个事件分开统计。

匿名到登录的路径也要处理。用户先浏览，注册后行为归属到账号上。实现方式是注册时把 `anonymous_id` 和 `user_id` 一起写进第一条事件，查询时用 `coalesce(user_id, anonymous_id)` 做关联。

## 42.8 隐私边界

埋点表是全库最容易被当成用户数据副本的表。它字段自由、写入路径多、经常被导出到第三方。边界要提前划。

不记这些内容：密码、验证码、token、cookie 原文、完整邮箱、完整 IP、文件名、文件内容、请求体、支付信息。

需要定位邀请转化时，用域名哈希代替邮箱。`invitee_domain_hash = sha256(domain + salt)`，能回答「企业邮箱的接受率是否更高」，不能反推出具体是谁。

需要统计文件大小时，用分档代替精确值：`size_bucket` 存 `lt_1m`、`1m_10m`、`gt_10m`。精确大小能配合时间戳推断出是哪次上传，分档不能。

客户端传上来的属性要做审计。定期跑一条 SQL，找出属性里出现敏感字段名的事件。

```sql
-- 检查属性键，发现不该出现的字段
select distinct jsonb_object_keys(properties) as key
from events
where occurred_at >= now() - interval '7 days'
order by key;
```

输出应该只有白名单里的键。多出来的，要么是客户端漏过滤，要么是有人手动写入了数据。

用户注销时的处理：`update events set user_id = null, anonymous_id = null where user_id = $1`。事件本身保留，用于统计趋势，但不再关联到人。

保留期要定。事件表保留十三个月，够算同比。超过期限的分批删除，别用一条 `delete` 把表锁住。

数据导出要审批。事件表可以导出给分析师，但要脱敏：去掉 `user_id` 和 `anonymous_id`，只留聚合结果。导出的文件不能进 git。

合规层面，欧盟用户的行为数据属于个人数据，采集前要有同意。落地页的 cookie 提示要真的控制采集开关，不能只是弹窗点一下。

## 42.9 事件字典与治理

事件定义散在代码里，三个月后没人说得清每个字段的含义。用一份文档收口。

```markdown
<!-- docs/analytics-events.md 节选 -->
| 事件名 | 触发时机 | 必填属性 | 谁在写 |
| --- | --- | --- | --- |
| user_registered | 注册接口成功后 | source | 服务端 |
| team_created | 团队创建事务提交后 | source | 服务端 |
| invitation_sent | 邀请邮件发出后 | invitee_domain_hash | 服务端 |
| file_uploaded | 文件状态改为 ready 后 | mime_bucket, size_bucket | 服务端 |
| subscription_started | Stripe webhook 处理成功后 | plan, seats | 服务端 |
| page_viewed | 路由变化后 | source | 客户端 |
```

三条规则写进文档开头：事件名只加不改；属性只加不改含义；删除事件要先停写一个月，再删数据。

新增一个事件走五步：先写文档条目，再写代码，然后跑一次确认落库，接着在漏斗 SQL 或看板里用上，最后观察一周有没有异常量。跳过第一步的事件，半年后大概率没人认得。

上线之后检查一次。

```sql
select name, count(*) as n
from events
where occurred_at >= now() - interval '1 day'
group by name
order by n desc;
```

如果新事件一条都没有，说明白名单没加、调用点没走到，或者 `after()` 里报错被吞掉了。

看板的最小形态是一个页面，直接查聚合结果，不把明细暴露给普通用户。

```tsx
// src/app/(app)/analytics/page.tsx
import { createClient } from "@/lib/supabase/server";

export default async function AnalyticsPage() {
  const supabase = await createClient();
  const { data } = await supabase

    .select("day, name, total")
    .order("day", { ascending: false })
    .limit(30);

  return (
    <table>
      <thead>
        <tr><th>日期</th><th>事件</th><th>数量</th></tr>
      </thead>
      <tbody>
        {(data ?? []).map((row) => (
          <tr key={`${row.day}-${row.name}`}>
            <td>{row.day}</td><td>{row.name}</td><td>{row.total}</td>
          </tr>
        ))}
      </tbody>

```

页面用普通客户端，走 RLS，用户只能看到自己团队的数据。看板只显示聚合，不显示单条事件，避免把用户行为明细暴露给同事。

## 42.10 事件多了之后

每天几千条时，直接查 `events` 表很快。涨到几十万条，看板打开要等三秒，SQL 里带 `group by` 的查询开始拖慢数据库。

第一层处理是物化视图。把按天按事件的聚合结果存下来，查询只读视图。

```sql
-- supabase/migrations/20261128091000_daily_events.sql
create materialized view public.daily_events as
select
  date_trunc('day', occurred_at)::date as day,
  name,
  count(*) as total
from public.events
group by 1, 2;

create unique index daily_events_day_name_idx on public.daily_events (day, name);

create or replace function public.refresh_daily_events()
returns void language sql security definer set search_path = public as $$
  refresh materialized view concurrently public.daily_events;
$$;

revoke all on public.daily_events from anon, authenticated;
grant select on public.daily_events to authenticated;
```

唯一索引是 `refresh ... concurrently` 的前提，没有它只能在视图上拿排他锁，刷新期间查询会阻塞。

刷新交给定时任务。

```ts
// src/app/api/cron/refresh-events/route.ts
import { createAdminClient } from "@/lib/supabase/admin";
import { logger } from "@/lib/logger";

export const dynamic = "force-dynamic";

export async function GET(request: Request) {
  const auth = request.headers.get("authorization");
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("unauthorized", { status: 401 });
  }

  const supabase = createAdminClient();
  const { error } = await supabase.rpc("refresh_daily_events");
  if (error) {
    logger.error("events.refresh.failed", { err: error.message });
    return Response.json({ ok: false }, { status: 500 });
  }
  return Response.json({ ok: true });
}
```

定时任务跑在每小时第十分钟。刷新失败要有告警，否则看板停在昨天，没人发现。

两层查询分工要写进文档：看趋势和总量读物化视图；算漏斗和查单用户读原始表，带上时间范围。视图只存了按天聚合，漏斗需要事件顺序，视图里没有。

再往上一层是按月分区。`events` 表按月切分，查询自动裁剪分区，删除历史数据用 `drop partition`，不用 `delete`。这一步在单表超过五千万行时再做，提前分区会让迁移和查询都变复杂。

## 42.11 边界与失败模式

埋点系统失效时通常很安静，业务照常跑，数据悄悄断了。几种常见形态要能识别。

数据突然掉零。可能的原因：`after()` 里抛异常被吞、白名单拒绝了新事件、迁移把 `insert` 权限收掉了。排查方式看日志里有没有 `analytics.insert.failed`，以及事件表里最近一条记录的时间。

数字对不上业务。事件表说注册一千，`profiles` 表说注册一千二。原因是部分注册路径没埋点，比如第三方登录回调。修法是按注册入口分组比对，找出漏掉的路径。

事件暴涨。某个事件一天几十万条，多半是客户端在渲染循环里调用，或者 `useEffect` 重复触发。表现是磁盘涨得快、查询变慢。处理方式是加采样和前端去重。

属性里出现敏感数据。客户端传了 `email`、`filename` 之类的键。发现之后要立刻清理历史数据，再补白名单。清理语句按 `properties ? 'email'` 定位，删掉整条或者只删这个键。

时区错位。报表显示某天转化率异常低，实际是那天跨了夏令时切换，或者容器时区和业务时区不一致。所有时间统一存 UTC，展示时再转换。

多实例重复写。服务端重试机制导致同一次操作写入两条事件。给事件加 `dedupe_key`（业务主键加事件名的哈希），建唯一索引，冲突时忽略。

删除权限。有人用 service role 手动 `delete from events`，历史数据断层。生产环境的 service role key 只给后端服务，人的操作用只读账号。

埋点的数量要克制。每加一个事件，就多一个要维护的定义、多一段查询、多一份隐私风险。先回答「这个数据会改变哪个决定」，答不上来的就别加。

还有一个容易被忽略的失败：埋点和业务表对不上账，但没人定期核对。做法是每周跑一次对账 SQL，把当天的新注册数、新团队数和事件表里的对应事件数放在一起比。差异超过五个百分点就去查原因，别等到季度汇报时才发现数字对不上。

对账 SQL 很简单，两个 `count` 加一个 `full join`。成本很低，价值在于它能在数据断层的第一周就发现问题。等三个月后再回头看，中间那段数据已经补不回来了。

## 42.12 检查点

1. `supabase db reset` 之后 `psql "$DATABASE_URL" -c '\d events'` 能看到四个索引和 RLS 开启状态。
2. 用匿名 key 查 `events` 返回 `permission denied`，用登录用户查自己团队的事件能返回数据。
3. 注册一个新账号，`select name, user_id from events order by occurred_at desc limit 3;` 里能看到 `user_registered`，`user_id` 是新账号。
4. 跑 `docs/sql/funnel.sql`，五列数字单调递减，最后一步是订阅数。
5. 跑属性审计 SQL，输出的键全部在白名单里，没有邮箱、文件名、IP。
6. `curl -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:3000/api/cron/refresh-events` 返回 `{"ok":true}`，`daily_events` 里有当天的聚合行。

## 42.13 常见错误

**1. 写入被 RLS 拒绝**

现象：`new row violates row-level security policy for table "events"`。原因是服务端用了登录用户的客户端，而事件表只对 service role 开放写。改用 `createAdminClient()`，或者给登录用户加一条 `with check` 策略。

2. 权限被 revoke 之后查询失败

现象：`permission denied for table events`。原因是迁移里执行了 `revoke all` 但忘了 `grant select`。补上 `grant select on public.events to authenticated`。

**3. 属性写入格式错误**

现象：`invalid input syntax for type json`。原因是把对象 `JSON.stringify` 了两次，传给 `jsonb` 列的是字符串。直接传对象，让驱动做序列化。

**4. 字段名不存在**

现象：`column "event_name" does not exist`。原因是 SQL 里用了习惯叫法，表里的列名是 `name`。按 `\d events` 的输出核对列名。

5. 漏斗第一步比注册数还大

现象：注册一千二，漏斗第一步一千五。原因是事件表里包含测试账号和历史导入数据，或者查询没限定时间窗口。加测试标记属性，查询时过滤。

**6. 客户端事件没落库**

现象：接口返回 200，表里没有数据。原因是事件名不在 `CLIENT_EVENTS` 白名单里，接口静默返回了 400，前端没检查响应。让接口的错误返回显式一点，前端在开发环境打日志。

## 42.14 这一章在做什么

这一章讲用户行为怎么变成可查询的数据。事件模型定三件事：事件名、必填字段、属性规则。表结构用 `events`，写入走服务端白名单加 `after()`，客户端事件经过一个限流接口。漏斗用 SQL 算，每一步校验顺序和窗口。隐私边界靠白名单、哈希、分档和审计 SQL 守住。

数据量大了之后，聚合结果进物化视图，原始表按需分区。治理靠一份事件字典，新增事件走五步流程。

到这里，应用能跑、能测、能压、能查。第 43 章换到性能视角，讲怎么量一个页面到底慢在哪，以及怎么把体积和延迟降下来。
