# 第 3 章 请求链路与渲染模型

这一章讲一次请求的完整链路。从地址栏里敲下 URL 开始，到页面可以点击结束，中间经过 DNS 解析、建立连接、服务端渲染、传输、水合几个环节。

需要这条链路，是因为三类问题都落在这里：首屏慢、点击后页面闪一下、预取了却还是慢。知道每一步在做什么，才能判断时间花在哪一段，再决定改哪里。

涉及的概念有七个：服务端渲染出的 HTML、RSC Payload、流式响应、水合、客户端导航、静态与动态的判定、Server Action 的调用路径。前五个解释一次页面访问，后两个解释页面里的交互。

## 3.1 两条路径

同一个页面有两种到达方式，链路完全不同。分清这两条路径，后面所有现象才解释得通。

第一条是首次访问。在地址栏敲回车、刷新页面、从外部链接进来，都走这条。浏览器发一个普通的 HTTP 请求，服务端返回 HTML。

第二条是客户端导航。在应用内点 `<Link>`、调用 `router.push`，走这条。浏览器不发页面请求，只请求一份 RSC Payload，然后用 JavaScript 把新内容渲染进现有 DOM。

首次访问的顺序如下：

1. 浏览器解析域名，得到 IP 地址（DNS）。
2. 建立 TCP 连接，做 TLS 握手（HTTPS 时）。
3. 发送 `GET /teams`，带上 Cookie、`Accept` 等请求头。
4. 服务端执行 React 组件，查询数据库，生成 HTML 和 RSC Payload。
5. 响应开始传输。HTML 可以边生成边发送，先到的部分先被浏览器解析。
6. 浏览器解析 HTML，同时下载 JS。JS 执行后把事件绑定挂上，页面变得可交互。

第 6 步就是水合（hydration）。在第 6 步完成之前，页面能看，但按钮点不动、输入框没反应。

客户端导航的顺序短得多：

1. 点击触发路由切换，读取已缓存的 RSC Payload，或者发一个 RSC 请求。
2. 服务端只渲染变化的部分，返回 Payload。
3. 客户端把新节点挂进现有树，替换掉旧页面的部分。
4. 共享的 layout 保持不动，状态、滚动位置都保留。

没有 HTML 生成，没有整页解析，没有重新水合。这是客户端导航比分页跳转快的原因，也是布局里的状态不会丢的原因。

衡量这两条路径，看三个时间点。FCP 是首次绘制，对应 HTML 到达；TTI 是可交互时间，对应水合完成；导航耗时对应 RSC 请求加上渲染。

首屏优化大多在缩短 FCP 到 TTI 之间的间隔。HTML 早就到了，JS 还在下载，这段时间里页面能看不能用。只看 TTFB 会漏掉这段。

## 3.2 抓两段响应

两段响应可以直接用 curl 对比。先看首次访问返回什么：

```bash
curl -s -D - -o /tmp/page.html http://localhost:3000/teams | head -20
```

```text
HTTP/1.1 200 OK
content-type: text/html; charset=utf-8
vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch, Accept-Encoding
x-nextjs-cache: HIT
```

响应类型是 `text/html`，正文是完整的页面。`vary` 头列出了四五个维度，说明同一 URL 的响应会随请求头变化，缓存键要把这些算进去。

再请求一次，带上 RSC 标记：

```bash
curl -s -D - -o /tmp/rsc.txt http://localhost:3000/teams -H "RSC: 1" | head -20
```

```text
HTTP/1.1 307 Temporary Redirect
location: /teams?_rsc=1nj0q
```

服务端先把请求重定向到带 `_rsc` 参数的地址。这是 Next.js 的约定：RSC 请求要走一个独立的 URL，避免和页面请求共用缓存键。`_rsc` 的值是一次请求的随机标识，每次不同，只用于区分这一条请求，不参与长期缓存。跟随重定向：

```bash
curl -s -D - -o /tmp/rsc.txt "http://localhost:3000/teams?_rsc=1nj0q" | head -20
```

```text
HTTP/1.1 200 OK
content-type: text/x-component
vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch, Accept-Encoding
```

`text/x-component` 是 RSC Payload 的媒体类型。正文里没有 HTML 标签，只有一行行 `id:值` 的文本。

一个页面在磁盘上因此有两份产物：`.next/server/app/teams.html` 和同目录下的 `.next/server/app/teams.rsc`。前者给首次访问，后者给客户端导航和预取。

## 3.3 Payload 的格式

Payload 的每一行是 `id:值`。id 是十进制数字，值是 JSON，或者一段带引号的字符串。

```text
2:"[project]/node_modules/next/dist/client/components/segment-explorer-node.js [app-client] (ecmascript)"
3:"/_next/static/chunks/1ymj_next_dist_1ati0k4qc_rxy._.js"
4:I["$2",["$3"],"SegmentViewNode"]
6:"$Sreact.fragment"
```

三种行对应三样东西。

字符串行描述模块。第 2 行给出模块的绝对路径和编译目标，第 3 行给出它在浏览器里加载的 chunk 地址。

`I` 开头的行是客户端组件引用。`I["$2",["$3"],"SegmentViewNode"]` 表示这个组件由模块 `$2` 提供，它依赖模块 `$3`，导出名是 `SegmentViewNode`。

带 `$` 前缀的值是引用，指向同一份 Payload 里的另一行。`"$Sreact.fragment"` 指向 React 提供的内置符号。

组件树本身也是 JSON 数组，形式是 `["$", 类型, key, props]`：

```text
7:[["children",{"s":"__PAGE__",...["$","$L9",null,{"token":"sb_secret_FAKE_1234567890"}],...]
```

`"$L9"` 指向第 9 行的客户端组件。`{"token":"..."}` 是从服务端传过去的 props，明文。

因此有一条重要结论：传给客户端组件的所有 props，都会出现在浏览器能拿到的文本里。数据库里不该出现的东西、服务端密钥、其他用户的字段，都不要通过 props 传给客户端组件。第 4 章展开这条边界。

Payload 有两个用途。首次访问时，它内联在 HTML 的 `<script>` 里，用于水合时核对组件树；客户端导航时，它作为独立响应传输，用于渲染新页面。同一份数据，两种投递方式。

HTML 里那份内联 Payload 是逐条 `push` 进去的，所以能在源码里看到 `self.__next_f.push([1, "..."])` 这样的行。这也是为什么“查看源代码”里会出现大段转义过的 JSON：那些就是 payload 内容。

Payload 的大小也值得关注。每一行客户端组件引用都伴随着下载和执行成本，行数越多，页面需要的 JS 越多。排查首屏 JS 体积时，先数 payload 里的 `I` 行和 `$L` 引用。

## 3.4 首屏是流式的

服务端不必等所有内容渲染完再发第一个字节。React 可以先把能确定的部分发出去，剩下的等数据到了再补。

一个慢页面在 DevTools 里能看到四个块：

```text
chunk 0 (+0ms)     静态壳
chunk 1 (+170ms)   Payload 开始
chunk 2 (+1000ms)  天气模块完成
chunk 3 (+3000ms)  仪表盘模块完成
```

第一个块里没有真实内容，只有占位标记：

```html
<template id="B:0"></template>
<p>加载中……</p>
```

`B:0` 是一个待补的洞，编号 0。等对应数据就绪，服务端再推送一段：

```html
<div hidden id="S:0"><p>今天 26 度</p></div>
<script>$RB=[];$RV=function(a){...}</script>
```

`<div hidden id="S:0">` 是真正的片段，`$RV` 是替换脚本，它在浏览器里把 `B:0` 换成 `S:0` 的内容。整个过程不需要重新请求。

这个机制带来几个必须知道的边界。

第一，流式响应一开始就是 `200`。状态码在第一个字节发出时就定了，后面不能再改。页面中途调 `notFound()`，浏览器收到的是 200 状态码加一个 404 界面，爬虫看到的是 200。要拿到真正的 404，内容必须在首字节之前确定。

第二，中间层会缓冲。nginx 默认会缓冲代理响应，需要加 `X-Accel-Buffering: no`。部分 CDN 和 gzip 中间件也会攒够一段再发。Safari 在响应不足 1024 字节时同样会等。

第三，抓流式不能用 `curl -N`。curl 按行缓冲，输出看起来还是一整块。判断有没有流式，看 DevTools 里 document 请求的 Timing：TTFB 很早，Content Download 很长。

第四，爬虫拿到的是一次性渲染完的完整页面。服务端识别出来访者是爬虫时不走流式，等全部渲染完再发。所以日志里偶尔会看到一批没有分块的请求，来自搜索爬虫。

流式缩短的是首字节时间，不缩短总时长。慢查询依然慢，只是用户先看到了外壳。数据量大的页面用完流式后，TTFB 从 3 秒变成 0.2 秒，整页加载仍然要 3 秒，感受上的差别主要来自“有东西可看”。

如果慢的原因是 CPU 密集计算，流式帮不上忙。服务端被计算占住时，连外壳都发不出来。

## 3.5 水合

水合是把 HTML 变成可交互页面的过程，分三步：

1. HTML 到达，浏览器解析并绘制。此时页面可见，但事件处理器还没绑定。
2. RSC Payload 到达，React 用它核对服务端渲染的组件树。
3. 客户端的 JS 下载完成，React 把事件监听挂到 DOM 上，执行 `useEffect`。

第三步完成之前，点击按钮不会触发任何逻辑。用户在这几百毫秒里的点击会丢失。

如果客户端渲染的结果和服务端 HTML 不一致，水合会失败：

```text
Hydration failed because the server rendered text didn't match the client.
```

常见原因有四类：渲染了当前时间或随机数；用了 `toLocaleString()`，服务端和浏览器的时区、语言不同；读了 `localStorage`、`window` 这类只有浏览器才有的对象；在 HTML 里插入了浏览器插件改写过的内容。

水合失败不会白屏，但会付出代价：React 会丢弃出错位置所在的整棵子树，改为纯客户端渲染。界面上表现为闪一下，控制台里是一条多条堆栈的报错。看起来能继续用，实际上那一块的内容已经和 HTML 里的不一样了。

一个最小复现：

```tsx
// src/app/(app)/clock.tsx
"use client";

export function Clock() {
  return <span>{new Date().toLocaleTimeString()}</span>;
}
```

服务端渲染时得到一个时间，客户端渲染时得到另一个时间，两者对不上。修法是等挂载后再渲染时间，或者用 `suppressHydrationWarning` 接受不一致。第 6 章专门讲这类闪烁。

React 的水合按 Suspense 边界分片执行。用户点到哪个区域，那个区域优先水合，其余的等空闲。所以大页面里先点的按钮不一定等整页 JS 下载完，这是选择性水合的收益。

页面的水合成本等于客户端组件树的规模。把整页标成客户端组件，等于让浏览器重新渲染一遍所有内容。控制客户端组件的范围，是控制 TTI 的主要手段。

## 3.6 客户端导航与预取

客户端导航不发页面请求，只发 RSC 请求。判断依据在 Network 面板里：

```text
teams?_rsc=1nj0q    fetch    200    text/x-component
```

请求头里带 `Next-Router-State-Tree`，它描述了当前的路由树。服务端据此只渲染变化的部分，payload 因此比分页加载小。

导航能快到几乎没有等待，靠的是预取。规则有三条：

- 静态路由，整条预取。用户鼠标还没点，目标页的 payload 已经在本机。
- 动态路由，默认不预取。
- 动态路由但有 `loading.tsx`，预取共享 layout 和骨架，页面内容现取。

预取结果放在内存缓存里，有效期几分钟。这就是有时点击瞬间到达、有时仍旧要等的原因：目标页是静态的，或者之前预热过。

预取的行为可以改：

```tsx
// src/components/team-link.tsx
import Link from "next/link";

export function TeamLink({ slug, name }: { slug: string; name: string }) {
  return (
    <Link href={`/teams/${slug}`} prefetch={false}>
      {name}
    </Link>
  );
}
```

`prefetch={false}` 关掉预取。列表很长时有用，避免一次性预取几十个页面、把带宽占满。

需要“悬停才预取”时，用状态控制：

```tsx
// src/components/team-link.tsx
"use client";

import Link from "next/link";
import { useState } from "react";

export function TeamLink({ slug, name }: { slug: string; name: string }) {
  const [hovered, setHovered] = useState(false);

  return (
    <Link
      href={`/teams/${slug}`}
      prefetch={hovered ? null : false}
      onMouseEnter={() => setHovered(true)}
    >
      {name}
    </Link>
  );
}
```

`prefetch={null}` 表示用默认策略。首次悬停时预取，之后保持预取。

预取在慢网下可能没有完成。用户点击时如果缓存里没有目标页，导航就开始等。这时可以用 `useLinkStatus` 显示反馈：

```tsx
// src/components/team-link.tsx
"use client";

import Link, { useLinkStatus } from "next/link";

function Pending() {
  const { pending } = useLinkStatus();
  return pending ? <span className="text-xs">加载中……</span> : null;
}

export function TeamLink({ slug, name }: { slug: string; name: string }) {
  return (
    <Link href={`/teams/${slug}`}>
      {name}
      <Pending />
    </Link>
  );
}
```

`useLinkStatus` 必须在 `<Link>` 内部使用，返回 `pending` 布尔值。它比整页 loading 骨架更轻，适合行内链接。

`pending` 在预取命中时几乎不出现。它反映的是“这次导航在等服务端”，因此只在动态路由、缓存过期、慢网这三种情况下可见。

默认预取只在生产构建里生效。`pnpm dev` 下不预取，本地测不出预取带来的差异。验证预取要在 `pnpm build && pnpm start` 之后做。

## 3.7 静态与动态

构建输出的路由表里，每个路由前面有一个符号：

```text
○  (Static)   prerendered as static content
●  (SSG)      prerendered as static HTML (uses generateStaticParams)
ƒ  (Dynamic)  server-rendered on demand
```

`○` 和 `●` 都是在构建时生成 HTML，`ƒ` 是每次请求现算。`●` 和 `○` 的区别只在于是否带动态参数：`/posts/[slug]` 用 `generateStaticParams` 列出所有 slug，构建时逐个生成，符号就是 `●`。

判定标准只有一条：这个页面用没用到请求级别的信息。

用到 `cookies()`、`headers()`、`searchParams`，或者 `await connection()`，就是动态。用了 `fetch` 且显式设成 `no-store`，也是动态。什么都没用，就是静态。

```tsx
// src/app/(app)/dashboard/page.tsx
import { cookies } from "next/headers";

export default async function DashboardPage() {
  const store = await cookies();
  const teamId = store.get("team_id")?.value;
  // ...
}
```

这个页面读到 Cookie，内容随登录用户变化，构建时无法确定，符号是 `ƒ`。

同一个页面里，静态和动态的边界可以细到组件。页面外壳静态，右下角的在线人数按请求渲染，这在支持 Cache Components 之后是常态。第 14 章讲组件级缓存，本章的判定只需要记住：请求级别的 API 一旦被调用，调用处及其上层都会变成动态。

有三个配置项可以手动覆盖判定：

```tsx
// src/app/(app)/teams/page.tsx
export const dynamic = "force-dynamic";
export const revalidate = 60;
```

`dynamic` 有四个值：`auto`（默认）、`force-dynamic`（强制按请求渲染）、`force-static`（强制静态）、`error`（出现动态 API 就报错）。

`force-static` 有一个安静的行为：它会把 `cookies()`、`headers()`、`searchParams` 压成空值，页面照样构建成功。用错时会得到“登录用户永远是 null”这类问题，且没有任何报错。

`revalidate = 60` 让静态页面每 60 秒重新生成一次，符号仍然是 `●` 或 `○`，但内容会更新。

写入之后让页面失效，用 `revalidatePath` 或 `revalidateTag`：

```ts
// src/app/(app)/teams/actions.ts
"use server";

import { revalidatePath } from "next/cache";

export async function createTeam(formData: FormData) {
  // ...写入数据库
  revalidatePath("/teams");
}
```

`revalidateTag` 在 16 版要传第二个参数，写成 `revalidateTag("teams", "max")`。只传一个参数是旧写法，编译直接报错。

静态页面有三种失效方式。按时间：`revalidate` 到点后，下一次请求触发重新生成，用户拿到旧页面，后台同时更新。按路径：`revalidatePath("/teams")` 让指定路由立即失效。按标签：给 `fetch` 或 `cache` 函数打 tag，`revalidateTag` 按 tag 失效。

按标签失效要传第二个参数，取值是缓存配置名。团队的实践是写 `"max"`，表示最长保留窗口。传错名字时编译不报错，运行时命中不了缓存，表现为“数据改了但页面没变”且没有任何日志。

## 3.8 Server Action 的调用链

表单提交、按钮点击背后的写入操作，多数用 Server Action。它的调用链和普通函数调用完全不同。

```ts
// src/app/(app)/teams/actions.ts
"use server";

export async function createTeam(formData: FormData) {
  const name = String(formData.get("name") ?? "");
  // ...校验与写入
  revalidatePath("/teams");
}
```

```tsx
// src/app/(app)/teams/new-team-form.tsx
import { createTeam } from "./actions";

export function NewTeamForm() {
  return (
    <form action={createTeam}>
      <input name="name" required />
      <button type="submit">创建</button>
    </form>
  );
}
```

点击提交时发生这些事：

1. 浏览器向当前页面地址发一个 `POST` 请求，请求体是表单数据，请求头里带一个 action 标识。
2. 服务端找到对应函数，执行。
3. 函数里的 `revalidatePath` 让缓存失效，框架顺手重新渲染当前路由。
4. 响应里同时带上函数返回值和新页面的 RSC Payload。
5. 客户端用这份 payload 更新界面。

一个请求完成写入和界面更新，不需要再发一次查询。这也是 Server Action 相比“接口加手动 refetch”少一次往返的原因。

触发重新渲染的条件有四个：调用 `revalidatePath` 或 `updateTag`、调用 `refresh`、通过 `cookies()` 改 Cookie、调用 `redirect`。只返回值、不做这些的 action，响应里没有新 payload。

四条边界必须知道。

第一，客户端连续调用时按顺序执行，一次一个。连点三次提交，第二个请求等第一个完成。因此不能靠并行 action 提升速度，需要并行就放一个 action 内部处理。

自己修改的数据要立刻看到时，用 `updateTag`。它比 `revalidateTag` 更强：调用它的 action 响应会带上重新渲染后的 payload，提交完就能看到新内容。`revalidateTag` 只做后台刷新，当前响应里没有新界面。

第二，action 就是当前页面的一个公开 POST 入口。任何能构造同样请求的人都可以调用它，函数内部必须自己鉴权、自己校验输入。

第三，参数和返回值都会序列化。返回整条数据库记录等于把字段发给浏览器，只返回界面需要的部分。

第四，action 的标识每次部署都会变。旧页面还开着，用户点击时报 `[Failed to find Server Action]`。这是版本切换期的常见错误，修法是滚动发布加提示用户刷新。

框架层还有几道保护：校验 `Origin` 和 `Host`，不一致就拒绝；请求体默认上限 1 MB；action 标识加密，未使用的 action 不进产物。反向代理改写了域名时，要在 `serverActions.allowedOrigins` 里列出这些域名，否则请求被拒。

多实例部署时还要固定 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`。不固定的话，每个实例用不同的密钥加密标识，请求落到另一台机器就解不开，同样报找不到 action。

## 3.9 边界与失败模式

CDN 缓存返回错类型。 页面 HTML 和 RSC Payload 是同一个 URL 的两个变体，靠 `vary` 里的请求头区分。CDN 忽略这些头、只按 URL 缓存，就会出现客户点导航却收到 HTML 的情况。表现是导航后页面被整页替换，或者报 payload 解析失败。配置缓存时要把 `rsc`、`next-router-state-tree` 这些头纳入缓存键。

流式开始后改不了状态码。 前面说过，`notFound()`、`redirect()` 在流式开始后只能改界面。判断页面能否返回真正的 404，看它在第一个 `await` 之前有没有发数据。

水合错误之后子树被替换。 报错位置所在子树改为客户端渲染，同一边界内其他内联脚本的修正会一起丢失。修法是消除不一致的来源，不要靠 `suppressHydrationWarning` 大面积压制。

预取引发突发流量。 一屏二十个链接全部可见，浏览器会同时预取二十条路由。列表页要按需关掉预取，或者改成悬停触发。

action 重试导致重复写入。 网络超时后用同一请求重试，服务端可能已经执行过一次。写操作要么设计成幂等，要么在服务端用唯一约束挡住重复。

空闲页面偶发慢。 静态页面在首次访问后还需要下载 JS 水合。JS 体积大时，TTFB 很快但可交互很晚。用 Lighthouse 的 TTI 指标看，别只看 TTFB。

开发环境测不出生产行为。 预取、静态优化、缓存命中在 `pnpm dev` 下都不生效。判断性能问题要在 `pnpm build` 之后用 `pnpm start` 跑，再打开 Network 面板。


## 3.10 检查点

1. 右键查看网页源代码，搜索 `self.__next_f`。判据：能找到 `<script>(self.__next_f=self.__next_f||[]).push([0])`，说明 Payload 内联在 HTML 里。
2. 执行 `curl -s http://localhost:3000/teams -H "RSC: 1" -D - -o /dev/null`。判据：返回 307，`location` 里带 `?_rsc=`。
3. 带上 `_rsc` 参数再请求一次，查看响应头。判据：`content-type` 是 `text/x-component`。
4. 打开 Network 面板点一个站内链接，筛选 Fetch。判据：出现带 `_rsc=` 的请求，响应类型是 `text/x-component`，页面没有整页刷新。
5. 运行 `pnpm build`，在路由表里找出一个 `ƒ` 和一个 `○`。判据：删掉 `○` 页面里的 `cookies()` 调用后重新构建，它仍然是 `○`；在 `ƒ` 页面里加一次 `cookies()` 调用，它变成 `ƒ`。
6. 提交一次表单，在 Network 面板看请求。判据：请求方法是 `POST`，地址是当前页面地址，响应类型是 `text/x-component`。

## 3.11 常见错误

1. `Hydration failed because the server rendered text didn't match the client.`

现象：页面能打开，控制台报水合失败，界面闪一下。
原因：服务端和客户端渲染出的文本不同。常见于时间、随机数、`toLocaleString()`、读 `localStorage`。
改法：把这类渲染移到 `useEffect` 之后，或者用 `suppressHydrationWarning` 只标记必要元素；时区问题在服务端固定时区。

**2. 点击站内链接整页刷新**

现象：点击后浏览器地址栏转圈，页面重新加载，布局状态丢失。
原因：用了原生 `<a>` 标签，或者 `<Link>` 写在客户端组件之外，被当成了普通锚点。
改法：改用 `next/link` 的 `<Link>`；需要程序化跳转时用 `useRouter`。

3. 动态页面没有 `loading.tsx`，导航卡住不动

现象：点击后界面停在旧页面，几百毫秒到几秒后突然切换，中间没有任何反馈。
原因：动态路由不预取，目标页又没有加载态，导航要等服务端渲染完。
改法：给该路由段加 `loading.tsx`；或者把慢的部分放进 `<Suspense>`，让外壳先到。

4. `[Failed to find Server Action]`

现象：部署新版本后，还开着旧页面的用户提交表单报错。
原因：action 标识每次部署都会变，旧页面里的标识在新实例上找不到。
改法：滚动发布；多实例固定 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`；界面上给刷新提示。

**5. 表单重复提交**

现象：网络慢时用户连点提交，数据库里出现两条记录。
原因：每次点击都发一次请求，按钮没有禁用。
改法：用 `useFormStatus` 读提交状态并禁用按钮；数据库层加唯一约束兜底。

6. 页面 TTFB 很快，但按钮一直点不动

现象：首屏瞬间出现，点击没反应，过一两秒才正常。
原因：HTML 和 Payload 早到了，JS 还在下载和执行。
改法：查首屏 JS 体积，把不必要的大组件改成服务端组件；用 Network 面板看 JS 的下载完成时间。

## 3.12 这一章在做什么

这一章拆开一次请求的链路。首次访问返回 HTML，并内联 Payload。客户端导航只取 Payload。服务端可以边渲染边发。浏览器拿到 HTML 之后还要水合才能交互。交互的写操作走 Server Action。

四个可以观察的位置：`self.__next_f` 在 HTML 里，`text/x-component` 在 Link 导航里，`○` 和 `ƒ` 在构建输出里，`POST` 加 `text/x-component` 在表单提交里。

这七个概念连起来，解释了首屏为什么先可见后可用，也解释了站内跳转为什么快。
