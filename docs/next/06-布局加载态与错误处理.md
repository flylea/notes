# 第 6 章 布局、加载态与错误处理

这一章讲页面在“不全顺利”的时候怎么显示。内容有六个约定文件：`layout.tsx`、`template.tsx`、`loading.tsx`、`error.tsx`、`global-error.tsx`、`not-found.tsx`，以及一种目录写法：并行路由槽位。

需要单独讲这些文件，是因为它们决定三种用户可见的状态。数据还没到的时候显示什么，请求失败的时候显示什么，地址不存在的时候显示什么。这三种状态如果没有对应的文件，用户看到的是白屏或者浏览器的默认错误页，体验和排错都会变差。

这些文件之间还有覆盖关系：哪个 `loading.tsx` 生效、哪个 `error.tsx` 接住异常、`not-found` 返回什么状态码。写错位置会让骨架不出现，或者让错误页变成 200。

## 6.1 约定文件的作用范围

App Router 里每个约定文件都按目录生效，作用范围是它所在的路由段以及下面所有子段。

`layout.tsx` 包住同段的页面与子段，导航时不重新挂载。`template.tsx` 同样包住子树，但每次导航都重新挂载。`loading.tsx` 是页面加载中的兜底，`error.tsx` 是渲染失败的兜底，`not-found.tsx` 是数据不存在的兜底。

包装顺序从外到内依次是布局、模板、错误边界、加载边界、未找到边界、页面。理解这个顺序，就能判断异常会被谁接住。

用文件表达这些状态，是为了让作用范围与目录结构一致。配置文件里写规则，读者要在两个地方对照；目录里放文件，走到哪一层就看得到哪一层的兜底。

约定文件可以只写一个，也可以每层都写。写得越靠近页面，范围越小。大型项目常见做法是根级放一套通用的加载页与错误页，业务分区再各自覆盖。

每个约定文件都必须导出默认组件。文件名区分大小写，`Loading.tsx` 不会被识别。

```text
src/app/
├── layout.tsx          # 根布局，必须包含 html 与 body
├── template.tsx        # 每次导航重新挂载
├── error.tsx           # 接住下面所有段的异常
├── loading.tsx         # 下面所有段的加载态
├── not-found.tsx       # 下面所有段的 404
└── (app)/
    ├── layout.tsx
    └── dashboard/
        ├── page.tsx
        ├── loading.tsx
        └── error.tsx
```

就近原则：子段有自己的 `loading.tsx` 就用子段的，没有才用父段的。错误边界同样就近，最近的 `error.tsx` 先接住。

约定文件不需要每个目录都写。只写根级一套，整站共用；写到业务分区，该分区单独覆盖。文件越多，阅读目录时越容易看清每个区域的行为。

层级顺序有一处容易记错：`error.tsx` 在 `loading.tsx` 外层。异常发生时，加载边界里已经渲染的部分被错误边界整体替换，骨架随之消失。

`layout.tsx` 有一个硬性要求：根布局必须渲染 `<html>` 和 `<body>`。使用多个根布局时，每个根布局各自写一份，页面之间不能共享。

```tsx
// src/app/layout.tsx
import type { Metadata } from "next";
import "./globals.css";

export const metadata: Metadata = {
  title: "TeamStack",
  description: "团队协作与文件管理",
};

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN">
      <body>{children}</body>
    </html>
  );
}
```

布局可以读取路由参数，因为参数在导航时已经确定；布局不能读取 `searchParams`，因为查询字符串变化不会重新渲染布局，读到的值会停在首次渲染时的状态。

```tsx
// src/app/(app)/teams/[slug]/layout.tsx
export default async function TeamLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  return (
    <div className="flex">
      <TeamSidebar slug={slug} />
      <main>{children}</main>
    </div>
  );
}
```

需要在布局里做查询串相关的逻辑，只有一种办法：把布局拆成客户端组件，用 `useSearchParams` 读。代价是这块界面进入客户端包，服务端渲染的优势减少。

多根布局用于几块完全不同的区域，比如后台与官网各用一套 HTML 外壳。做法是删掉最外层布局，在每个路由组里各写一份。

代价是页面之间跳转时整页重新渲染，布局共享带来的即时切换消失。两套外壳的重复样式也要各自维护。只有确实需要不同 `<html>` 属性或不同全局脚本时才拆。

### 6.1.1 两个实验性约定文件

`unauthorized.tsx` 和 `forbidden.tsx` 是 16 版新增的约定文件，分别接住 401 与 403。它们在启用 `experimental.authInterrupts` 之后才可用：

```ts
// next.config.ts
const nextConfig = {
  experimental: {
    authInterrupts: true,
  },
};

export default nextConfig;
```

在需要拦截的页面里调用函数，而不是自己返回状态码：

```tsx
// src/app/(app)/teams/[slug]/settings/page.tsx
import { forbidden } from "next/navigation";

export default async function TeamSettingsPage() {
  const user = await requireUser();
  const role = await getMemberRole(user.id);

  if (role !== "owner") {
    forbidden();
  }

  return <SettingsForm />;
}
```

需要 401 的场景用 `unauthorized()`，界面写在 `unauthorized.tsx`。两者通常配合：没有会话时给 401，有会话但角色不够时给 403。

两个函数抛出的异常由最近的约定文件接管两个函数抛出的异常由最近的约定文件接管，渲染 `unauthorized.tsx` 或 `forbidden.tsx`。状态码取决于流式输出有没有开始：流式之前返回真实的 401 或 403，流式开始之后状态码已经发出，只能返回 200 并渲染对应界面。两种情况框架都会插入 `noindex`。

这两个文件是实验性功能，要开配置位，未来 API 可能变。本书的鉴权失败统一走 `redirect("/login")` 或 `notFound()`，因为它们稳定、可被缓存、不依赖配置位。等这两个约定文件转正，再把 401 与 403 的界面接过去，改动集中在被调用的那几行。它们的目录位置与 `error.tsx` 一致，作用于所在段及其子段。

## 6.2 loading.tsx

`loading.tsx` 的作用是在页面数据还没到时先显示内容。它会自动把同段的页面与子页面包进一个 Suspense 边界，浏览器拿到的是先渲染好的外壳加占位。

```tsx
// src/app/(app)/teams/[slug]/dashboard/loading.tsx
export default function DashboardLoading() {
  return (
    <div className="space-y-4">
      <div className="h-8 w-48 animate-pulse rounded bg-neutral-200" />
      <div className="grid grid-cols-3 gap-4">
        <div className="h-24 animate-pulse rounded bg-neutral-200" />
        <div className="h-24 animate-pulse rounded bg-neutral-200" />
        <div className="h-24 animate-pulse rounded bg-neutral-200" />
      </div>
    </div>
  );
}
```

`loading.tsx` 不需要写 `"use client"`，它是一个普通的服务端组件。骨架里的动画由 CSS 完成，不依赖 JavaScript。

骨架的尺寸要和真实内容接近。高度差太多，内容出现时页面会跳一下，阅读位置丢失。列表骨架按真实行高留出间距，标题骨架按字号设宽度。

加载态能否出现，取决于阻塞发生在哪里。阻塞发生在页面内部，`loading.tsx` 会让外壳先出去；阻塞发生在同段布局里，骨架不会出现。

这一点最容易被忽略。布局需要等数据才能渲染，那么整个段的输出都被卡住，浏览器收到的第一块内容里没有骨架。用户点击导航后看到的是一次停顿，然后整页内容一起出现。

```tsx
// 错误示范：布局里等数据，骨架不会出现
export default async function TeamLayout({ children }: { children: React.ReactNode }) {
  const team = await getTeamSlow();
  return <div data-team={team.id}>{children}</div>;
}
```

处理办法有两种。把取数移到页面里，让布局只渲染结构；或者接受布局变慢，在布局内部用 Suspense 包住需要数据的部分。

```tsx
// src/app/(app)/teams/[slug]/layout.tsx
import { Suspense } from "react";

export default function TeamLayout({ children }: { children: React.ReactNode }) {
  return (
    <div className="flex">
      <Suspense fallback={<div className="h-16 w-48 animate-pulse rounded bg-neutral-200" />}>
        <TeamSidebar />
      </Suspense>
      <main>{children}</main>
    </div>
  );
}
```

`loading.tsx` 还有一种性质：它的内容是会被预取的。链接进入视口时，框架会提前取下这个骨架，用户点击时几乎立即切换。骨架本身要轻，塞太多内容反而拖慢预取。

加载态与流式输出是同一套机制的两面。服务端组件把已完成的部分先发给浏览器，未完成的部分留占位，数据到了再补。`loading.tsx` 提供的是整段级别的占位。

首字节时间与总时间可以差很远。首字节很快，说明外壳已经到；总时间仍然等于最慢的那个查询。

爬虫与自动化工具拿到的往往是完整渲染后的响应，不经过流式分块。用脚本抓页面时看不到骨架，不要用它判断加载态是否生效。

把 `loading.tsx` 放进路由组，骨架只作用于该组的路由。`(overview)` 组里放一份骨架，`(settings)` 组不受影响。这是控制作用范围最方便的手段。

## 6.3 error.tsx

`error.tsx` 接住渲染过程中抛出的异常。它必须是客户端组件，因为要用 `retry` 重新渲染。

```tsx
// src/app/(app)/teams/[slug]/dashboard/error.tsx
"use client";

import { useEffect } from "react";

export default function DashboardError({
  error,
  retry,
}: {
  error: unknown;
  retry: () => void;
}) {
  useEffect(() => {
    console.error("dashboard error", error);
  }, [error]);

  return (
    <div className="rounded border border-red-200 p-6">
      <h2 className="text-lg font-medium">这块内容加载失败</h2>
      <p className="mt-2 text-sm text-neutral-600">
        可以重试，也可以先返回列表。
      </p>
      <button
        type="button"
        onClick={() => retry()}
        className="mt-4 rounded bg-neutral-900 px-4 py-2 text-white"
      >
        重试
      </button>
    </div>
  );
}
```

`error` 的类型是 `unknown`，读 `message` 或 `digest` 之前要先收窄。服务端组件抛出的错误是 `Error` 实例；客户端组件抛出的值可能是字符串或对象。

```tsx
"use client";

export default function DashboardError({
  error,
  retry,
}: {
  error: unknown;
  retry: () => void;
}) {
  const digest = error instanceof Error ? error.digest : undefined;
  const message = error instanceof Error ? error.message : "未知错误";

  return (
    <div>
      <p>{message}</p>
      {digest !== undefined && <p className="text-xs text-neutral-500">错误编号 {digest}</p>}
      <button onClick={() => retry()}>重试</button>
    </div>
  );
}
```

生产环境里，服务端组件抛出的错误只带一个 `digest`，不带原始消息。原始消息留在服务端日志里，用 `digest` 对账。开发环境会显示完整消息，方便定位。

`digest` 是一串数字字符串，服务端日志里会出现同样的值。接错误上报服务时把它一起发出去，就能把浏览器上的报错与服务端堆栈对上。

错误页不要展示 `error.message` 给终端用户。面向内部人员的管理后台可以展示，公开页面只给编号。

错误边界会替换整块界面的内容。放在页面级，出错时整页变成错误页；放在卡片级，只有一张卡片被替换。粒度按业务需要定，太细会让错误页到处出现，太粗会丢掉整个页面。

`retry` 会重新取数并重新渲染失败的那部分。`reset` 仍然存在，它只清除错误状态，不重新取数。多数场景用 `retry`，因为失败的原因常常是数据源抖动，重试一次就能好。

错误边界的作用范围有一个边界要记清：它不包同段的 `layout.tsx` 与 `template.tsx`。布局抛出的异常往上冒，由更外层的 `error.tsx` 或根级 `global-error.tsx` 接住。

重试不一定有效。数据不存在、权限不足这类错误，重试结果相同。错误页里给两条出路：重试与返回列表。

```tsx
// src/app/global-error.tsx
"use client";

export default function GlobalError({
  error,
  retry,
}: {
  error: unknown;
  retry: () => void;
}) {
  return (
    <html lang="zh-CN">
      <body>
        <h2>页面出错了</h2>
        <button onClick={() => retry()}>重新加载</button>
      </body>
    </html>
  );
}
```

`global-error.tsx` 替换根布局，因此必须自己渲染 `<html>` 和 `<body>`。它不继承全局样式与字体，出错时的界面会退回浏览器默认样式。对错误页来说这是可接受的。

`error.tsx` 有一件事不能做：在里面取数。错误页本身再失败，问题会变得更难排查。

页面里的局部异常也可以用 `try/catch` 处理。预期内的失败（表单校验、外部服务超时）适合捕获后转成返回值，交给界面提示；预期外的异常交给错误边界。两者分工明确，错误边界不负责业务分支。

错误页的按钮文案要具体。“重试”比“确定”有用，“返回列表”给了另一条出路。

## 6.4 not-found.tsx

`notFound()` 用来表示数据不存在。它在服务端组件里调用，抛出控制流异常，最近的 `not-found.tsx` 负责渲染。

```tsx
// src/app/(app)/teams/[slug]/not-found.tsx
import Link from "next/link";

export default function TeamNotFound() {
  return (
    <div className="py-16 text-center">
      <h2 className="text-xl font-medium">团队不存在</h2>
      <p className="mt-2 text-sm text-neutral-600">它可能已被删除，或者地址有误。</p>
      <Link href="/teams" className="mt-6 inline-block underline">
        返回团队列表
      </Link>
    </div>
  );
}
```

```tsx
// src/app/(app)/teams/[slug]/page.tsx
import { notFound } from "next/navigation";
import { getTeam } from "@/lib/teams";

export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const team = await getTeam(slug);

  if (team === null) {
    notFound();
  }

  return <h1>{team.name}</h1>;
}
```

状态码会随输出时机变化。页面在首字节发出之前就判定不存在，响应是真实的 404；页面已经流式输出了一部分，判定发生在中途，响应码已经锁定为 200，只能换一段界面。

流式输出时的 404 会在响应里带上 `<meta name="robots" content="noindex">`，避免搜索引擎收录。这个细节不能替代状态码，接口消费者看到的仍然是 200。

状态码只在首字节之前决定，这是流式响应的工作方式。响应头发出之后，服务端无法再把 200 改成 404。

需要在任何情况下都返回真实状态码的地址，有两种做法：把不存在判定提前到所有取数之前；或者用 Route Handler 处理，它不参与流式渲染。

`not-found.tsx` 与 `error.tsx` 都按目录就近生效。根级的 `not-found.tsx` 兜住所有未匹配的地址，业务分区可以各自覆盖。

地址里的参数要校验。`id` 是 uuid 类型时，把 `hello` 直接丢给数据库会报类型错误：

```text
invalid input syntax for type uuid: "hello"
```

这类错误会在服务端抛出 500，用户看到的是错误页，而地址问题本该是 404。数据层里先判断格式：

```ts
// src/lib/teams.ts
const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;

export async function getTeamById(id: string) {
  if (!UUID_RE.test(id)) {
    return null;
  }
  const supabase = await createClient();
  const { data } = await supabase.from("teams").select("*").eq("id", id).maybeSingle();
  return data;
}
```

`not-found.tsx` 也会被根级的文件兜住。没有定义任何 `not-found.tsx` 时，Next.js 使用内置的默认页。

404 页面按请求渲染，状态码与内容一起返回。需要给搜索引擎明确信号的站点，保持 404 状态码比更换页面文案更重要。

## 6.5 并行路由槽位

并行路由让同一个布局里同时渲染多块互相独立的页面。目录名以 `@` 开头，它不进入 URL，只作为布局的一个属性传下去。

```text
src/app/(app)/teams/[slug]/
├── layout.tsx
├── page.tsx
├── @members/
│   ├── page.tsx
│   ├── loading.tsx
│   └── default.tsx
└── @activity/
    ├── page.tsx
    └── default.tsx
```

```tsx
// src/app/(app)/teams/[slug]/layout.tsx
export default function TeamLayout({
  children,
  members,
  activity,
}: {
  children: React.ReactNode;
  members: React.ReactNode;
  activity: React.ReactNode;
}) {
  return (
    <div className="grid grid-cols-3 gap-6">
      <div className="col-span-2">{children}</div>
      <aside>{members}</aside>
      <section>{activity}</section>
    </div>
  );
}
```

每个槽位是独立的渲染单元。它有自己的 `loading.tsx` 与 `error.tsx`，一块慢不会拖住另一块。

`default.tsx` 是槽位的兜底。刷新页面或直接访问地址时，没有匹配到具体页面的槽位会渲染 `default.tsx`，没有这个文件就直接 404。

```tsx
// src/app/(app)/teams/[slug]/@activity/default.tsx
export default function ActivityDefault() {
  return <div className="text-sm text-neutral-500">当前分区没有内容</div>;
}
```

`children` 也是一个槽位，它对应目录里平级的 `page.tsx`。给 `children` 配兜底时，在平级放 `default.tsx`。

槽位的常见用途是让一块内容独立加载，不影响主内容。团队页的成员、活动、用量各占一块，谁的查询慢谁显示骨架。

槽位也可以用来组织不同权限的界面。管理区与成员区各自渲染，权限判断写在各自的数据层，互不依赖。

调试槽位时先看目录结构。`@members` 下面必须有 `page.tsx` 才有内容，只有 `default.tsx` 时显示兜底界面，不报错。

槽位的名字直接成为布局的 props 名，`@members` 对应 `members`。名字带连字符时，props 名也要按同样的字符串取。

几条限制要记住。同一层的槽位不能一个静态一个动态，只要有一个槽位读了 `cookies()`，整层都会变成按请求渲染。槽位名不能与路由段重名。槽位与拦截路由是两种机制，后者才负责弹窗路由这类场景。

槽位之间的边界是独立的错误域。`@members` 抛错时只有这一块被替换，`@activity` 不受影响。这一点与整页错误边界不同。

槽位与加载态可以组合。给 `@members` 单独放一个 `loading.tsx`，主内容不受影响，骨架只出现在那一列。

## 6.6 template.tsx

`template.tsx` 与布局类似，区别在挂载行为。导航到新页面时，布局保持已挂载的状态，模板会卸载再挂载。

```tsx
// src/app/(app)/template.tsx
"use client";

import { useEffect } from "react";

export default function AppTemplate({ children }: { children: React.ReactNode }) {
  useEffect(() => {
    console.log("template mounted");
    return () => console.log("template unmounted");
  }, []);

  return <div>{children}</div>;
}
```

切换团队地址时，模板会重新挂载，`useEffect` 再执行一次。切换查询字符串不会触发重新挂载，因为路由段没有变化。

模板适合三个场景：页面访问埋点、进入动画、依赖挂载的初始化。用不上的时候写布局，避免不必要的重挂载开销。

模板还会重置界面状态。列表的选中项、展开状态在挂载时清空。需要保留的状态要提到布局，或者放进 URL。

模板与布局可以同时存在。模板包在布局内部，布局保持挂载，模板重新挂载，两层职责分开。

埋点用模板最稳。布局只在首次挂载执行一次，后续导航不触发，访问统计会漏。

## 6.7 水合前的闪烁

服务端渲染的 HTML 先到，JavaScript 后到。这中间有一段时间页面已经显示但还不能交互。如果用 `useEffect` 改样式，用户会看到先亮后暗的一跳。

处理办法是在 HTML 里内联一段脚本，在解析阶段同步执行，把最终效果直接写进 DOM。

```tsx
// src/app/layout.tsx
const themeScript = `
  try {
    const t = localStorage.getItem("theme");
    if (t === "dark" || (!t && matchMedia("(prefers-color-scheme: dark)").matches)) {
      document.documentElement.classList.add("dark");
    }
  } catch {}
`;

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN" suppressHydrationWarning>
      <head>
        <script dangerouslySetInnerHTML={{ __html: themeScript }} />
      </head>
      <body>{children}</body>
    </html>
  );
}
```

`suppressHydrationWarning` 放在 `<html>` 上，表示这个元素的属性差异以 DOM 为准，不报水合错误。

内联脚本在 HTML 解析到它时就执行，早于首帧绘制。`useEffect` 要等 React 水合完成才执行，那时页面已经画出来了，改动会表现为闪烁。

`useLayoutEffect` 也晚一步。它在浏览器绘制之前执行，前提是 JavaScript 已经下载并执行，HTML 刚到时它还没运行。

`suppressHydrationWarning` 只对当前元素生效，不会传染给子元素。需要的地方逐个加，不要挂在根节点上一次性盖住所有差异。

用 cookie 读主题也能避免闪烁，代价是页面变成按请求渲染，静态优化失效。内联脚本的代价是页面里多一段字符串，取舍按访问量决定。

脚本要包 `try/catch`。无痕模式或禁用存储时 `localStorage` 会抛异常，不捕获会让后续脚本中断。

服务端渲染时间也会闪。`new Date().toLocaleString()` 在服务端按服务器时区格式化，浏览器按用户时区渲染，两边文本不同就会报水合不匹配。这类展示要么交给客户端组件，要么在元素上加 `suppressHydrationWarning`。

调试时区问题可以固定环境：`TZ=UTC LANG=ja_JP.UTF-8 pnpm dev`。两边都跑一遍，差异会立刻出现。

## 6.8 边界与失败模式

布局里取数拖慢整个段。 布局要等数据，骨架不出现，导航像卡住。判断方法是看是否只有这个段慢，其他段正常。

错误被上层的边界接住。 子段没有 `error.tsx`，异常冒到父级，父级整块界面被替换。给需要独立失败的区块补一个就近的边界。

错误边界接不住事件处理器的异常。 按钮点击里抛出的错误不会进 `error.tsx`，它在浏览器控制台里，页面不变化。事件处理器里自己 `try/catch`。

错误边界接不住渲染之后的异步错误。 `setTimeout` 里抛出的错误同样不会被接住，要包在 `startTransition` 里才会向上冒。

流式输出让状态码失效。 页面流式开始后，`notFound()` 与 `redirect()` 只能改变界面，状态码仍是 200。需要真实状态码的地址，让它尽量在首字节前完成判断。

槽位缺 `default.tsx` 变成 404。 刷新时未匹配的槽位没有兜底，整页进入 404。给每个槽位都补一个 `default.tsx`。

`global-error.tsx` 忘写 `html` 与 `body`。 构建能过，出错时页面结构异常。把它当成一个完整页面来写。

模板与布局混用导致状态丢失。 把带输入框的表单放在 `template.tsx` 里，切一次页面输入就没了。需要保留状态的界面放布局。

错误页里再取数。 错误页渲染时又发查询，数据源故障时错误页本身也失败，用户看到白屏。错误页只展示静态文案。

`loading.tsx` 放进错误的目录。 放在根级会覆盖所有页面，导航时出现不属于当前页面的骨架。按段放置，范围与目录一致。

错误边界包住了不应该出现的区域。 根级 `error.tsx` 一旦触发，导航栏也一起消失。把全局外壳放布局，错误边界下移到内容区。

以为 `error.tsx` 能接住接口请求的异常。 在事件处理器里 `fetch` 失败不会进错误边界，界面毫无反应。请求失败要么返回错误状态，要么自己捕获后提示。

## 6.9 检查点

1. 在页面里故意 `throw new Error("boom")`，访问该地址。判据：终端打印 `⨯ Error: boom` 与 `digest: '...'`，浏览器显示自定义错误页，`curl -i` 返回 500。
2. 去掉 `error.tsx` 的 `"use client"`，运行 `pnpm build`。判据：构建失败，报错指出该文件必须是 Client Component。
3. 在一个不存在的 `id` 上调用 `notFound()`，用 `curl -i` 看响应。判据：状态码 404，HTML 含 `<meta name="robots" content="noindex">`。
4. 给页面加一个 1.2 秒的查询，在布局里也加一个查询。判据：布局取数时骨架不出现，把查询移进页面后骨架出现。
5. 建两个槽位，其中一个不写 `default.tsx`，刷新页面。判据：缺少兜底的槽位导致 404；补上后同一地址返回 200。
6. 切换团队地址，观察模板日志。判据：模板重新挂载；只改查询字符串时日志不变。
7. 给一个槽位单独加 `loading.tsx`，让它的查询慢 1 秒。判据：只有该槽位显示骨架，其他列正常渲染。

## 6.10 常见错误

1. `Error: src/app/.../error.tsx must be a Client Component.`

现象：构建失败，提示加指令。
原因：`error.tsx` 要接收 `retry` 并绑定点击事件，必须在客户端运行。
改法：文件首行加 `"use client";`，且放在所有 import 之前。

**2. 页面报错后整页白屏**

现象：没有 `error.tsx`，异常冒到最外层。
原因：缺少错误边界，或者最近的 `error.tsx` 在更外一层。
改法：在出错的路由段放 `error.tsx`；根布局的问题用 `global-error.tsx`。

**3. 骨架屏从不出现**

现象：点导航后停顿，然后整页内容一起出现。
原因：阻塞发生在 `layout.tsx` 里，`loading.tsx` 包不到那段等待。
改法：把取数移到 `page.tsx`，或者在布局内用 Suspense 包住慢的部分。

4. `notFound()` 之后状态码是 200

现象：页面显示 404 内容，`curl -i` 却返回 200。
原因：响应已经开始流式输出，判定发生在中途。
改法：把不存在判定放在所有 await 之前；需要严格 404 的接口用 Route Handler。

5. `invalid input syntax for type uuid: "hello"`

现象：访问 `/teams/hello` 返回 500。
原因：参数格式未校验就传给数据库。
改法：数据层先做格式校验，不合法时返回 `null`，页面里转成 `notFound()`。

6. 槽位页面刷新后 404

现象：直接访问地址，某个分区整页进入 404。
原因：槽位缺少 `default.tsx`，初次加载没有可匹配的页面。
改法：每个槽位补一个 `default.tsx`，`children` 槽位同样需要。

## 6.11 这一章在做什么

这一章把页面的三种非正常状态各交给一个约定文件：加载中交给 `loading.tsx`，出错交给 `error.tsx`，不存在交给 `not-found.tsx`，全局崩溃交给 `global-error.tsx`。

三条判断可以带走：

- 骨架不出现，先查同段布局有没有等数据。
- 错误页范围不对，先查最近一层 `error.tsx` 的位置。
- 状态码不对，先查判定发生在首字节之前还是之后。

约定文件的默认导出必须是组件。写成具名导出不会被识别，构建也不报错，表现为该状态直接缺失。
