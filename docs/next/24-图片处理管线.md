# 第 24 章 图片处理管线

第 23 章把文件原样存进了桶里，字节是什么样，用户后来拿到的就是什么样。相机拍出来的图片带着一串额外信息，还会比展示需要的大小大几十倍。这一章在确认上传时插一段服务端处理，让列表拿到正着的缩略图，让下载者拿到干净的小图，原图保持不动。

涉及四个概念：EXIF 方向、图像解码器、衍生图档位、像素上限。

这一章单独讲，是因为方向、体积、隐私这三件事没有一件能靠 CSS 修。方向要重写像素，体积要重新编码，EXIF 要在输出时丢掉，三个动作都发生在服务端，而且必须发生在文件变成 `ready` 之前。晚一步，列表里就会出现一段时间的原图，或者一段时间的歪图。

前置条件：第 23 章的 `confirmUpload` 已经会把对象下载下来做校验，这一章复用同一份字节，不额外下载。

## 24.1 处理要解决的四个问题

先明确要解决什么，再决定代码写在哪里。

- 方向：手机竖拍时，传感器其实是横着记录的，然后在 EXIF 里写一个 `Orientation` 值，通常是 6 或 8，意思是“显示时旋转 90 度或 270 度”。看图软件读这个值，所以照片是正的；图像库不读这个值，转出来的缩略图就是横躺的。修方向要重写像素，不能只改一个字段。

- 体积：一张手机照片 4MB，页面上只显示 64×64。直接拿原图当缩略图，首屏传输十几 MB，解码时每张占几十 MB 内存。图片列表是最容易被原图拖垮的页面。

- 隐私：相机原图带着 GPS 坐标、机型、拍摄时间。用户把照片发给客户，等于把拍摄地点一起发了。这类信息一旦泄露就是事故，而用户通常不知道它的存在。

- 解码安全：图片要被 libvips 这类库解码，解码器是攻击面，历史上出过构造一张图就能读内存的漏洞。处理管线必须假设输入不可信，用魔数先筛一遍，再用像素上限和超时兜住解码过程。

验证这些信息不需要写代码，一条命令就够：

```bash
npx exiftool ./photo.jpg | head -20
```

输出里能看到 `Orientation`、`GPS Latitude`、`GPS Longitude`、`Make`、`Model`。同一个文件用 sharp 读：

```bash
node -e "require('sharp')('./photo.jpg').metadata().then(m=>console.log(m.orientation, m.exif?.length))"
```

输出类似 `6 2604`，表示方向值是 6，EXIF 段有 2604 字节。处理完之后，这两个数字都应该消失或归零。

## 24.2 处理放在哪一步

位置有三个候选，只有一个是合适的。

- 放在上传前，浏览器端：浏览器能压缩，但用户可以绕过：直接调 `beginUpload` 传原图。剥 EXIF 这种安全要求尤其不能交给客户端，客户端是被审计的一方。

- 放在展示时：每次列表渲染都转码，CPU 成本乘以访问量，还要处理缓存失效。图片是一次写、多次读的典型，处理应该在写入路径上。

- 放在确认那一步：`confirmUpload` 本来就要下载对象，同一份字节顺手处理，不多一次下载。而且 `ready` 的含义因此变成“字节在、校验过、衍生图也齐了”，列表页看到 `ready` 就敢直接引用缩略图，不用猜“缩略图生成了没有”。

如果改成后台任务异步处理，`ready` 之后会有一段时间没有缩略图，前端要处理 404、要轮询、要显示占位。这些复杂度在图片量小时不值得背。

并发要算一笔账。一张 4MB 的图处理 300ms，单核一秒处理 3 张。4 核机器上，20 个人同时点上传，20 个确认请求排队，最后一个人等 1.5 秒左右，还能忍。200 个人同时传，队列变成十几秒，这段时间还占着数据库连接和 Server Action 的并发额度。图片功能刚上线通常没事，做一次活动就会撞上。P95 抬头就是迁队列的信号，24.10 会讲清楚边界。

这段处理不放在 `beginUpload`：那时候字节还没上传，没有东西可处理；也不能在上传链接签发后、浏览器还没传完时抢跑。确认是唯一一个“字节已经在桶里、且还没对外可见”的时刻。

代价是确认变慢。一张 4MB 的图转两档大约 200–500ms，50MB 的超大图可能几秒。自托管没有硬超时，Vercel 上受函数时长限制，Hobby 是 300 秒。同时上传 20 张时，20 个确认请求一起抢 sharp 的线程池，libvips 默认按 CPU 核数开线程，服务器会被打满。这个限制先接受。

## 24.3 两档尺寸与像素闸

“缩略图”是一组按用途分的档位，并非一张图。这一章定两档。

| 名字 | 宽度 | 用途 | quality |
| --- | --- | --- | --- |
| `thumb` | 320 | 列表、卡片、头像 | 72 |
| `preview` | 1280 | 详情页大图 | 82 |

宽度定死，高度按比例，不裁成正方形。列表里的方形用 CSS 的 `object-fit: cover`，不要把裁切写进文件：同一张图在不同位置需要不同比例，存死了就改不动。

`resize` 有两个行为要知道。`withoutEnlargement: true` 让小图不放大，100px 的图放大到 320px 只会更糊、还更占空间。默认的 `fit: 'inside'` 保持比例，长边不超过给定宽度。

还要给输入加闸：`limitInputPixels: 40_000_000`。一张 20000×20000 的 PNG 解压后是 1.6GB 内存，解码时进程直接没了。这个检查发生在解码前，并非解完再判断。

上限定在 40MP 而不取更高，原因是主流手机 4800 万像素正好 48MP，会超。要么提到 60MP 并接受一台机器同时处理几张就 OOM，要么拒绝并给一句人话。这一章选后者：手机直传 48MP 原图的场景很少，拒绝比 OOM 好。

档位宽度按“最大显示尺寸乘 2”定。列表里显示 64–96px，1x 屏取 96，2x 屏要 192，320 够，还留了余量。某个位置要显示 300px，2x 屏需要 600px，320 那张会糊，那个位置改用 `preview`。

## 24.4 处理函数

先加路径工具。衍生图路径从原图路径推导，不改表结构。

```ts
// src/lib/storage.ts（追加）
export type ImageVariant = 'thumb' | 'preview'

// 原图路径是 teamId/fileId/original，衍生图放同目录。
export function variantPath(storagePath: string, variant: ImageVariant) {
  return `${storagePath.replace(/\/original$/, '')}/${variant}.webp`
}
```

再写处理函数。两档、转正、WebP、不保留元数据。

```ts
// src/lib/images.ts
import 'server-only'
import sharp from 'sharp'
import type { ImageVariant } from '@/lib/storage'

export const THUMB_WIDTH = 320
export const PREVIEW_WIDTH = 1280
const MAX_INPUT_PIXELS = 40_000_000

export interface RenderedVariant {
  name: ImageVariant
  buffer: Buffer
  width: number
  height: number
}

export async function renderVariants(input: Buffer): Promise<RenderedVariant[]> {
  const variants: RenderedVariant[] = []

  for (const [name, width] of [
    ['thumb', THUMB_WIDTH],
    ['preview', PREVIEW_WIDTH],
  ] as const) {
    const { data, info } = await sharp(input, {
      limitInputPixels: MAX_INPUT_PIXELS,
      failOn: 'error',
    })
      // 先按 EXIF 方向转正，再算尺寸。
      .rotate()
      .resize({ width, withoutEnlargement: true })
      // 不调用 withMetadata / keepExif，输出就没有元数据。
      .webp({ quality: name === 'thumb' ? 72 : 82, effort: 4 })
      .timeout({ seconds: 20 })
      .toBuffer({ resolveWithObject: true })

    variants.push({ name, buffer: data, width: info.width, height: info.height })
  }

  return variants
}
```

然后改 `confirmUpload`，在改成 `ready` 之前插入处理：

```ts
// src/app/(dashboard)/files/actions.ts（替换 confirmUpload 的后半段）
import { renderVariants } from '@/lib/images'
import { scanBuffer } from '@/lib/scan'
import { FILES_BUCKET, storageAdmin, variantPath } from '@/lib/storage'

// ...前面下载、大小校验、魔数校验都不变

const isImage = file.mime?.startsWith('image/')

if (isImage) {
  const input = Buffer.from(await blob.arrayBuffer())

  // 扫描必须在 sharp 解码之前，见 24.7。
  const scan = await scanBuffer(input)
  if (scan === 'infected') {
    await bucket.remove([file.storage_path])
    await markDeleted(file.id)
    return { error: '文件没有通过安全检查' }
  }

  let variants
  try {
    variants = await renderVariants(input)
  } catch {
    // 解不开就是坏图，留着一个打不开的对象没有意义。
    await bucket.remove([file.storage_path])
    await markDeleted(file.id)
    return { error: '图片已损坏或格式不支持，换一张试试' }
  }

  await Promise.all(
    variants.map((variant) =>
      bucket.upload(
        variantPath(file.storage_path, variant.name),
        new Blob([variant.buffer], { type: 'image/webp' }),
        { contentType: 'image/webp', upsert: true },
      ),
    ),
  )
}

await db
  .updateTable('files')
  .set({ status: 'ready', size_bytes: blob.size })
  .where('id', '=', file.id)
  .execute()
```

三个细节。

`upsert: true` 是给重试用的。确认接口会被重复调用，第二次会覆盖同名衍生图；不开 upsert 会报“already exists”。

衍生图上传和改状态并非原子的。中间失败会留下“有衍生图但状态 `pending`”的行，清理脚本会收拾它，前提是 24.9 把脚本改了。

用 `new Blob([buffer])`，不要直接传 `Buffer`。supabase-js 按浏览器类型判断二进制体，Node 的 `Buffer` 在部分版本里不被认成文件内容，包一层 Blob 最稳。

两档循环跑两次，不一次 decode 出两个尺寸：sharp 的每个管道是独立的 libvips 实例，`clone()` 能共享输入，但每档仍然各走一遍 resize 和编码。单张 4MB 的图，两档各 100–200ms，加起来比“先 decode 一次再产两档”多花一点点，换来的是代码直白、每档参数独立。图片量上来之后可以再优化，但那时多半已经在队列里了。

处理失败要给对用户看的理由。解不开的图，也就是截断、伪装的 HTML、HEIC，走“图片已损坏或格式不支持”；像素超限走“图片太大”；扫描命中走“没有通过安全检查”。三种都删对象、标 `deleted`。把所有失败都写成“上传失败，请重试”，用户重试一百次也不会成功。

## 24.5 顺序：rotate 在 resize 之前

`.rotate()` 不带参数，意思是“按 EXIF 的方向转正”。把这一行注释掉再处理那张竖拍照片，`thumb.webp` 还是横的，而且宽高比也不对：竖图被当成 1280 宽的横图缩了，人更小。

顺序不能换。先 resize 的话，算出来的宽高是未旋转的，转完就超了；先 rotate 的话，后面每一步看到的都是转正后的像素。

`.rotate()` 必须写在管道最前面，还有一个原因：它一执行就把方向应用到像素上，后面的步骤不会再去读 EXIF。如果先调用了会丢弃元数据的步骤，方向信息就没了，`rotate()` 也就无能为力。

## 24.6 EXIF 默认就不保留

sharp 的输出默认不保留任何元数据。EXIF、XMP、IPTC 全部丢掉，除非显式调用 `withMetadata()`、`keepMetadata()` 或 `keepExif()`。所以这段代码里没有“剥 EXIF”的语句，不写就是剥。

读一下两个文件确认：

```bash
node -e "require('sharp')('./photo.jpg').metadata().then(m=>console.log('原图 exif:', m.exif?.length))"
node -e "require('sharp')('./thumb.webp').metadata().then(m=>console.log('缩略图 exif:', m.exif?.length))"
```

第一条打印几百到几千的数字，第二条打印 `undefined`。

这个默认值很容易被一次复制粘贴破坏。有人为了保留 ICC 色彩配置，在管道里加了 `.withMetadata()`，本意是让广色域照片不发灰，结果 GPS 也跟着回来了，而代码评审时没人会注意这一行。确实需要色彩配置时，用 `.withIccProfile('srgb')`，或者在输出的 WebP 参数里处理，不要用保留全部元数据的开关。

剥的范围要想清楚：这一章剥的是衍生图，原图保留完整元数据。原图是用户的资产，他可能只是想下载回去存档，把拍摄参数剥了属于数据损坏。代价是，如果产品提供“下载原图”，用户之间互传的照片仍然带着 GPS。

三条路选一条写进产品文档。原图保留，只在界面提示“原图可能包含位置信息”，适合内部工具；原图也剥，下载给清洗版，适合对外分享；两份都留，`original` 加 `original-clean`，下载默认给干净的。这一章走第一条，因为 `files` 里的原图就是用户上传的那份字节，不该被静默修改。

详情页至少要写一句“原图可能包含拍摄地点等信息”。这句话放在下载按钮旁边，比放在帮助文档里有效十倍。

## 24.7 转 WebP 的数字

实测体积别靠猜。选三张真实用户会传的图，一张手机照片、一张截图、一张带文字的海报，各跑一遍，记录原图、`thumb`、`preview` 的大小，写进验收标准。不同内容类型的压缩率差很远，截图转 WebP 常常只剩十分之一，噪点多的夜景照片可能只省 30%。

同一张 1280 宽的图，JPEG 质量 85 大约 180KB，24 位 PNG 大约 900KB，WebP 质量 82 大约 90KB。WebP 在同画质下通常比 JPEG 小 25%–35%，比 PNG 小一个数量级。

照片类内容用 WebP 的有损模式，不要用 `lossless: true`。有损模式才会得到上面那些数字，无损模式适合截图和图标，对照片的体积几乎没帮助，甚至翻倍。`effort` 取 4，取值范围 0 到 6，越高压缩越慢、体积越小，4 是速度和体积的平衡点。

不直接上 AVIF：压缩率更好，但编码慢一个数量级，同一张图可能要几秒，在同步确认流程里不可接受，兼容性也还差一截。更实际的做法是现在存 WebP，等处理迁到队列、有 CPU 预算之后，再做“WebP 兜底加 AVIF 优先”的双格式，让浏览器用 `<picture>` 自己选。

也不要在上传时把同尺寸 JPEG 再存一份当回退。两份意味着两倍空间、两套生命周期，而 WebP 的覆盖已经足够。格式是手段，目标是在可接受的时间内把体积降到移动网络能接受的范围。

## 24.8 扫描放在魔数之后、解码之前

描述符校验挡不住精心构造的文件，而图片一定会被解码。扫描并非可选项，只是优先级和成本问题。

位置很关键：魔数校验之后、交给 sharp 解码之前。先解码再扫描，等于先把可疑字节喂给最容易出问题的组件。

```ts
// src/lib/scan.ts
import 'server-only'

export type ScanResult = 'clean' | 'infected' | 'unavailable'

// 真实实现：连接 clamd 的 INSTREAM 接口，把 buffer 分块写进去。
// 接哪家引擎由部署环境决定，这一章只留接口。
export async function scanBuffer(_buffer: Buffer): Promise<ScanResult> {
  if (process.env.VIRUS_SCAN !== 'on') return 'unavailable'
  throw new Error('扫描引擎尚未接入：本地用 docker 起 ClamAV，生产用托管扫描服务')
}
```

本地起 ClamAV 的命令（**未验证**，镜像和端口以实际环境为准）：

```bash
docker run -d --name clamav -p 3310:3310 clamav/clamav:stable
```

`unavailable` 怎么处理是产品决定，并非技术决定。图片可以 fail-open，放行但记日志，风险是解码器漏洞，概率低；文档类文件必须 fail-closed，PDF 里能嵌 JS，风险高得多。无论哪种，都要有“扫描不可用”的告警。扫描服务挂了三天，fail-open 就悄悄生效了三天，日志里只有 `unavailable`，没人会去看。

扫描会拖慢确认。ClamAV 扫一个 5MB 的图通常几百毫秒，和 sharp 处理叠加，一张图从点上传到 `ready` 要接近一秒。这是安全成本。这一章的示例默认关闭扫描，真上线前至少把 PDF 那条路径接上，PDF 是文件分享里最常见的攻击载体。

## 24.9 展示：稳定 URL 加 next/image 只做布局

桶里有两档 WebP，最直觉的交付方式是用第 23 章的签名链接，但签名链接每次渲染都不一样，随机签名加 60 秒过期，`next/image` 会把每个 URL 当成新资源，缓存永远不命中。

所以走一条稳定的应用路由：

```ts
// src/app/api/files/[id]/[variant]/route.ts
import { db } from '@/lib/db'
import { requireTeam } from '@/lib/teams'
import { FILES_BUCKET, storageAdmin, variantPath } from '@/lib/storage'

const VARIANTS = new Set(['thumb', 'preview'])

export async function GET(
  _request: Request,
  { params }: { params: Promise<{ id: string; variant: string }> },
) {
  const { id, variant } = await params
  if (!VARIANTS.has(variant)) {
    return new Response('not found', { status: 404 })
  }

  const team = await requireTeam()

  const file = await db
    .selectFrom('files')
    .select(['storage_path', 'mime', 'status'])
    .where('id', '=', id)
    .where('team_id', '=', team.id)
    .executeTakeFirst()

  if (!file || file.status !== 'ready' || !file.mime?.startsWith('image/')) {
    return new Response('not found', { status: 404 })
  }

  const { data, error } = await storageAdmin()
    .storage.from(FILES_BUCKET)
    .download(variantPath(file.storage_path, variant as 'thumb' | 'preview'))

  if (error || !data) return new Response('not found', { status: 404 })

  return new Response(data, {
    headers: {
      'Content-Type': 'image/webp',
      'Cache-Control': 'private, max-age=60',
      'X-Content-Type-Options': 'nosniff',
    },
  })
}
```

这条路由做三件事：验当前团队、按文件 id 查归属、从桶里取对应档。URL 形如 `/api/files/<id>/thumb`，稳定、可被 `next/image` 引用、不泄露签名。别人的 id、不存在的 id、非图片文件，一律 404，本身也是信息最小化。

`Cache-Control` 必须是 `private`，不能是 `public`。响应取决于“当前登录用户属于哪个团队”，同一个 URL 对不同用户结果不同。标成 `public` 会让 CDN 把一个团队的缩略图缓存下来发给另一个团队，这是私有资源最典型的事故。`private` 只允许浏览器缓存，60 秒足够滚动列表时命中，也能让权限变更很快生效。

60 秒还照顾了一个场景：用户刚换完头像，刷新页面看到的还是旧图。觉得它短之前先想一遍，权限被收回的人最长还能看到多久的旧图。

把桶设成公开、路径加一段随机串，看起来就不必走这条路由了。公开桶的 URL 一旦泄露就永久有效，而且无法按团队隔离；随机串只有 128 位熵，进了浏览器历史、日志、referrer 之后就不再随机。

展示时第 34 章会这样写：

```tsx
// 示例：列表里的缩略图（第 34 章展开）
import Image from 'next/image'

<Image
  src={`/api/files/${file.id}/thumb`}
  alt={file.name}
  width={320}
  height={320}
  unoptimized
  className="h-16 w-16 rounded object-cover"
/>
```

关键是 `unoptimized`。这一章的管线已经替代了 `next/image` 的优化器，两者分工如下。

| | 本章的管线 | `next/image` |
| --- | --- | --- |
| 处理时机 | 写入时，一次 | 首次请求时按需转码并缓存 |
| 产出 | 320 与 1280 两档 WebP，无元数据 | 按 deviceSizes 生成多个宽度，存平台缓存 |
| 权限 | 走应用路由，按团队校验 | 优化器请求不带用户 cookie |
| 负责 | 规范化、隐私、尺寸档位 | 响应式选择、懒加载、占位、防抖 |

不直接让 `next/image` 优化，原因是它取图是服务器到服务器的请求，不带用户 cookie。应用路由要求登录，优化器取不到图，报 `upstream response is invalid`。要绕过去就得把图做成公开可猜的 URL，那是拿权限换缓存。

正确组合是自己产出合适的尺寸，用 `unoptimized` 让 `next/image` 只做布局和懒加载。第 34 章讲外链图片和 `loader` 时，才轮到优化器上场。

## 24.10 边界与失败模式

**确认变慢的边界**。处理时间乘以并发数，不能超过单个请求能承受的范围。确认请求的 P95 超过 1 秒、图片里开始出现视频或 PDF 预览、需要重试、需要多档尺寸或人工审核，出现任意一条就该把处理移出请求路径。

**迁队列时状态机要一起改**。状态变成 `pending`、`processing`、`ready`，`files.status` 的 check 约束要加值，界面要显示“处理中”，清理脚本要知道 `processing` 超时也要回收，展示路由对 `processing` 的响应是 404 还是占位图要提前定。队列只解决“谁来跑”，不解决“跑一半崩了算什么”，那是第 26 章的主题。

`after()` 只适合锦上添花。它让代码在响应发送之后继续执行，适合写处理耗时、发一条“文件已就绪”的站内信。但它不保证执行完成，进程重启、平台回收实例，回调就没了。承载“文件必须处理”这种承诺要用任务队列。

**HEIC 不在白名单里**。iPhone 默认存 HEIC，sharp 要额外编译 libheif 才能解。这一章的 MIME 白名单不含它，确认阶段就会拒。产品上要么提示用户“请导出为 JPEG”，要么单独接一条转码路径。

**透明图在深色主题下看不见**。带透明通道的 PNG 转 WebP 默认保留 alpha，不用额外开关。缩略图的透明背景如果落在深色卡片上，看起来像空图，这是 CSS 要处理的事。

截断的 JPEG 会“成功”一半。sharp 默认可能输出一张下半截是灰的图并返回成功。`failOn: 'error'` 让警告直接失败，删对象、标 `deleted`，不要留下半张图。

**长图与截图**。手机截图 1170×2532，缩到 320 宽是 692 高，列表里显示成细长条，`object-fit: cover` 会裁掉大半。给列表一个固定宽高比的容器，或者长图用 `preview` 加 `object-contain`。

## 24.11 清理脚本必须同步

第 23 章的清理脚本用“对象路径是否等于某个 `files.storage_path`”判断孤儿。现在桶里多了 `thumb.webp` 和 `preview.webp`，它们不等于任何 `storage_path`，会被当成孤儿删掉，用户会发现缩略图时有时无。

把已知路径扩成三类：

```js
// scripts/cleanup-orphans.mjs（替换已知路径那一段）
const { rows: known } = await pool.query(
  `select storage_path from public.files where status <> 'deleted'`,
)

const knownPaths = new Set()
for (const row of known) {
  knownPaths.add(row.storage_path)
  const base = row.storage_path.replace(/\/original$/, '')
  knownPaths.add(`${base}/thumb.webp`)
  knownPaths.add(`${base}/preview.webp`)
}

const orphans = objects.filter((object) => !knownPaths.has(object.path))
```

顺手把查询条件从“全部行”改成 `status <> 'deleted'`。`deleted` 的行对应的对象本来就该被删，把它们的路径算进已知集合，那些对象会永远留在桶里。

改完先 dry-run 一遍，注释掉 `remove`，确认列出的孤儿是 0，再让它真删。

这类“改了一处、忘了另一处”是管线功能最常见的回归。判断方法很简单：新增一种写对象的路径，就要检查所有列举对象的代码。这一章只有清理脚本一处，以后可能有对账、备份、迁移任务，都要跟着改。

## 24.12 检查点

1. 传一张手机竖拍的 JPEG（带 GPS），确认完成后：桶里出现 `<teamId>/<fileId>/thumb.webp` 和 `preview.webp`；`thumb.webp` 是正的、几十 KB；列表首屏传输明显变小。用 sharp 读 `thumb.webp` 的 `metadata().exif`，是 `undefined`。
2. 把一张 HTML 改名成 `.png` 再传，或者传一个截断的 JPEG：确认失败，`files.status` 是 `deleted`，桶里没有残留的 `original`、`thumb.webp`、`preview.webp`。
3. 账号 A 打开 `/api/files/<自己文件 id>/thumb` 返回 200 和 `image/webp`；账号 B（不在该团队）打开同一 URL 返回 404；随机 uuid 也返回 404。再跑一遍清理脚本 dry-run，孤儿数量是 0。

4. 传一张 2400×1600 的原图：`thumb.webp` 宽 320，`preview.webp` 宽 1280，两张都不大于原图；传一张 200×200 的小图，两张都不放大。
5. 非图片文件（比如 PDF）走同一条确认路径：不产生 `thumb.webp`，`files.status` 是 `ready`，列表页用文件图标，不用缩略图。
## 24.13 常见错误

`Error: Input buffer contains unsupported image format`

sharp 收到的并非它能解码的图片。常见三种：HEIC（iPhone 默认格式，sharp 要额外编译 libheif）、文件被截断、改后缀混进来的非图片。解法：魔数白名单本来就不含 HEIC，确认阶段就会拒；截断的文件靠 `failOn: 'error'` 抛错，按“图片已损坏”提示。

`Error: Input image exceeds pixel limit`

像素数超过 `limitInputPixels`。解法：要么提高上限并接受内存风险，要么直接拒绝并提示“请先压缩”。别在上限之外偷偷 resize，超限的图在 decode 阶段就已经把内存吃掉了。

`VipsJpeg: Premature end of JPEG file`

JPEG 不完整，通常是上传中断或源文件坏了。sharp 默认会输出一张下半截是灰的图并“成功”。解法：`failOn: 'error'`，遇到警告直接失败，删对象、标 `deleted`。

`Error: Image with src "/api/files/..." is missing required "width" property`

`next/image` 的静态布局必须知道宽高，否则没法预留空间，会布局抖动。解法：给 `width` 与 `height`，或者用 `fill` 加定位容器。

`Error: Image Optimization "url" parameter is valid but upstream response is invalid`

优化器去取 `/api/files/...`，被登录校验挡了，它不带 cookie。解法：私有图片加 `unoptimized`，让浏览器直接请求应用路由，尺寸档位交给本章的管线。

`ENOENT: no such file or directory`（桶里找不到 `thumb.webp`）

衍生图没生成，或者路径拼错。检查两处：确认时 `variantPath` 用的 `storage_path`，展示路由用同一个函数；`renderVariants` 失败被 catch 掉时，状态绝不能改成 `ready`。

## 24.14 这一章在做什么

这一章在确认这一步加了一段有顺序的处理。先按 EXIF 方向转正，再缩到 320 与 1280。输出 WebP，不调用任何保留元数据的 API，EXIF 和 GPS 自然消失。用像素上限和超时保护进程，坏图直接拒绝，不产出半张。扫描放在魔数之后、解码之前。

展示走稳定的应用路由，`next/image` 只做布局和懒加载，不做二次转码。新增了衍生图路径，孤儿清理脚本必须同步认识它们。

没有新表、没有新迁移，改动全在确认那段代码和一条展示路由里。把处理放在写入路径的好处是：状态机只有一个入口，衍生图跟着原图走，不需要额外的状态同步。

到这里，文件从“能传”变成了“传进来的东西是规范的”。下一章换一个方向：把团队从免费档变成付费档，涉及外部系统的回调、幂等和状态同步，比图片管线难，因为你不控制对面什么时候发请求。
