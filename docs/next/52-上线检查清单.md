# 第 52 章 上线检查清单

这一章给出一份上线前逐条过的清单：路由与渲染、数据获取与缓存、UI 与可访问性、安全、元数据与 SEO、类型与构建、Core Web Vitals、包体积，再加运维七项。

检查项分两类。一类是框架行为，官方清单里有：路由、缓存、图片、字体、脚本、元数据。另一类是项目行为，得自己写：健康检查、迁移顺序、回滚步骤、备份验证。两类都要有：只做框架检查，上线后倒在前者之外的地方；只做项目检查，框架层的性能与安全又没人管。

清单的作用是把“觉得可以了”换成“逐条有结论”。每一项只允许三种结论：通过（附证据）、不适用（说明为什么）、没做（排期）。不允许空着，也不允许写“应该没问题”。

检查项来自 Next.js 官方 production-checklist 与本书前面各章。官方清单只覆盖框架层面，部署、备份、迁移、证书这些要自己补。执行时复制模板到 `docs/release-<日期>.md`，上线前一周开始填，发布当天只看没通过和没做的项。

## 52.1 三种结论与证据

“通过”要有证据。命令输出、截图、URL、日志片段，放一行在结论后面。没有证据的通过等于没检查。

“不适用”要写原因。比如项目没有多语言，i18n 相关项就不适用；原因写清楚，下次评审不用再讨论。

“没做”要写负责人与日期承诺。上线可以带着没做项发，前提是知道风险在哪；最怕的是没做却以为做了。

还有一种结论是“本轮跳过”。跳过与没做的区别是：跳过有理由（比如需要压测环境），没做是遗漏。三种结论之外不要自创分类，分类越少执行越稳。

检查项要能判定，写“视情况而定”的项说明还没想清楚。

清单本身要版本化。每次发布复制一份，改动留在新文件里；历史文件是事故复盘的输入。

## 52.2 路由与渲染

检查每个路由的渲染方式。错误边界要覆盖到段一级。`error.tsx` 放在路由段里，某个组件崩了只影响那一块；只放根级，一崩全白。

水合错误也要看。服务端渲染的 HTML 与客户端首次渲染不一致时，控制台会报 hydration 错误；这类错误通常被 React 恢复掉，但交互可能已经坏了。

路由检查分两步。先看构建输出，符号对不对；再打开页面看实际行为，静态页刷新两次内容一致，动态页每次请求时间不同。

`pnpm build` 的输出会列出符号：`○` 静态、`●` 静态但带数据、`ƒ` 动态。启用 Cache Components 后符号变成 `○`、`◐`、`ƒ`。

```bash
# 构建并查看路由表
pnpm build
# 输出里每个路由前有一个符号：
# ○  Static        静态
# ●  SSG           预渲染
# ƒ  Dynamic       每次请求渲染
```

要确认三件事。营销页是 `○`，登录后的页面是 `ƒ`，没有该动态的页面被误标成动态。

`ƒ` 的量要能解释。用户相关页面动态是正常的；营销页、文档页动态，机会成本是每次请求都回源，缓存与 CDN 都帮不上。

误标的原因通常是布局里用了 `cookies()` 或 `headers()`。一个动态 API 会把整棵子树拉成动态，检查从布局开始。

```bash
# 找出所有客户端组件
# 哪些文件是客户端组件
rg -l "^'use client'" src/app src/components

# 有没有本该用 Link 却用了 a 的内部链接
rg -n '<a href="/' src/

# 错误边界覆盖情况
find src/app -name "error.tsx" -o -name "global-error.tsx" -o -name "not-found.tsx"
```

`'use client'` 的必要性要逐个问。能拆成服务端组件加一个小的客户端叶子，就不要整页下沉；拆不动时，至少在 PR 里说明理由。

客户端组件数量要有预算。首屏路径上超过十个，就要回头看哪些可以下沉；`'use client'` 一旦写在顶层，整棵子树都进客户端包。

## 52.3 数据获取与缓存

缓存策略在项目里通常是三种：静态页面按时间重新验证、用户数据不缓存、列表按标签失效。三种策略对应三类风险：过期时间太长导致内容旧、缓存了私有数据导致串号、标签漏掉导致改了看不到。

检查方法是逐页问一句：这个页面的数据多久变一次，变了之后谁需要立刻看到。答案写在代码注释里，评审时能看到判断依据。

缓存要能说清“谁在什么时候看到旧数据”。`revalidateTag` 的两个参数必须写全，第二个参数是 profile，缺了会报类型错。

```ts
// src/app/(app)/teams/[slug]/page.tsx 片段
# 找所有缓存相关的声明
rg -n "use cache|revalidate|cacheTag|revalidateTag|updateTag" src

# 找所有绕过缓存的写法
rg -n "dynamic = 'force-dynamic'|noStore\(\)|cache: 'no-store'" src
```

标签名要统一管理。拼字符串的标签容易写错一个字母，失效就不生效；把标签放进常量文件，`revalidateTag` 与写入侧共用同一份。

检查缓存头。静态页应该是 `public` 加 `s-maxage`，登录后的响应必须是 `private`，带 `Set-Cookie` 的响应不能被 CDN 缓存。

```bash
# 看响应头与 CDN 命中状态
curl -sI https://teamstack.dev | head -1
```

数据获取的顺序也要检查。并行发起的查询要真的并行，`Promise.all` 写成串行 `await` 会让首屏慢一倍。

缓存键容易被忽略。同一个 URL 对不同用户返回不同内容时，要么标记 `private`，要么把用户标识放进键；靠 Cookie 区分而 CDN 不认，结果就是串号。

串号是缓存最严重的事故。用两个账号在同一个浏览器配置里交替访问，确认看不到对方的数据；有疑点时清 Cookie 再测一次。

缓存的另一面是过期。`revalidate` 取一个业务能接受的值：首页五分钟、列表页一分钟、详情页不缓存；数值写死在代码里，改的时候要重新评估。

缓存失效要有触发点。写了数据之后调用 `revalidateTag` 或 `updateTag`，改完立刻刷新页面能看到新值。

## 52.4 UI 与可访问性

表单的必填与格式校验要在客户端与服务端各做一次。只做客户端，绕过前端就能提交脏数据。

表单错误提示要能被读屏读到。错误文案放在 `aria-live` 区域，焦点移到第一个错误字段；只标红不提示，视障用户不知道发生了什么。

可访问性检查不靠感觉。Lighthouse 的 a11y 分数是起点，重点看四个具体项：可点击元素的名称、表单控件的 label、焦点顺序、颜色对比度。

```bash
# 跑一次 Lighthouse（需要 Chrome）
# 用 Lighthouse 的可访问性审计（会启动 Chrome）
pnpm dlx lighthouse http://localhost:3000 \
  --only-categories=accessibility \
  --chrome-flags="--headless" \
  --output=json --output-path=./lighthouse-a11y.json

# 看分数和失败项
node -e "const r=require('./lighthouse-a11y.json');console.log(r.categories.accessibility.score);console.log(r.categories.accessibility.auditRefs.filter(a=>r.audits[a.id].score!==1).map(a=>a.id))"
```

对比度用工具量。正文 4.5:1、大字号 3:1 是底线；浅灰说明文字最容易不达标，改深一档即可。

键盘走一遍是最快的检查。按 Tab 从头走到尾，看焦点是否可见、顺序是否合理、能否触发所有按钮；这一步能发现一半的问题。

分数低于 90 时看具体条目，不要只看总分。团队协作工具的表单多，label 缺失是最常见的问题。

图片与字体也要过一遍。`next/image` 的 `alt` 不能为空字符串除非图片纯装饰；字体用 `next/font` 自托管，避免第三方请求。

```bash
# 找出没用 next/image 的图片标签
rg -n "<img " src/app src/components || echo "none"
```

小屏检查项包括：导航能否打开、表格是否横向溢出、长单词会不会撑破布局、底部按钮会不会被键盘遮住。

移动端单独跑一次。桌面通过、移动端失败的项通常是触控区域太小或横向溢出。

## 52.5 安全

上线前最容易被跳过的是鉴权实测。代码里写了权限判断，不等于每个入口都调用了；复制粘贴出来的 Route Handler 经常漏掉一行。

做法是把入口列出来，逐个构造越权请求：换 `teamId`、换 `userId`、换成未登录、换成低角色。四个身份各测一轮，结果记在清单里。

安全项分四类：响应头、依赖、鉴权、速率限制。

CSP 配错会白屏。先在 Report-Only 模式收集违规，常见来源是内联样式与第三方脚本；确认清单后再切强制，并保留 `report-uri`。

响应头至少有四个：`Content-Security-Policy`、`Strict-Transport-Security`、`X-Content-Type-Options`、`Referrer-Policy`。CSP 先上 Report-Only，观察一周没有违规再切强制。

```bash
# 查看线上响应头
# 1. 响应头有没有安全策略
curl -sI https://teamstack.dev | grep -iE "content-security-policy|strict-transport|x-frame|x-content-type"

# 2. 前端产物里有没有疑似密钥
rg -i "service_role|sk_live|SUPABASE_SERVICE" .next/static || echo "clean"

# 3. 依赖漏洞
pnpm audit --prod --audit-level=high
```

依赖的时间也要看。半年没更新的包，即使没有已知漏洞，也可能不再兼容新版本 Node；升级成本会随时间上涨。

依赖漏洞用 `pnpm audit` 扫，高危必须有处理结论：升级、替换、或者记录为什么可以接受。

```bash
# 扫描生产依赖
pnpm audit --prod --audit-level=high
```

CSRF 的防线在 Server Actions 内置的 Origin 校验。自托管且反代改了 Host 时，要在 `experimental.serverActions.allowedOrigins` 写精确域名，否则合法请求也会被拒。

鉴权要实测，不能只看代码。把请求里的 `teamId` 换成别人的，确认返回 403；把 Server Action 的请求重放一次，确认服务端仍然校验权限。

上传与导出要单独审。上传检查文件类型与大小，导出检查行数上限；这两个入口最容易变成数据外带通道。

速率限制放在登录、注册、邀请、上传四个入口。实现用 Redis 计数，固定窗口够用。

```ts
// src/lib/rate-limit.ts
import { redis } from '@/lib/redis'

type Result = { ok: boolean; remaining: number; resetAt: number }

export async function rateLimit(key: string, limit: number, windowSec: number): Promise<Result> {
  const window = Math.floor(Date.now() / 1000 / windowSec)
  const redisKey = `rl:${key}:${window}`

  // INCR 与 EXPIRE 分两步执行，存在窗口边界，这里可接受：
  // 最坏情况是窗口末尾多放行一次，不会造成批量绕过
  const count = await redis.incr(redisKey)
  if (count === 1) await redis.expire(redisKey, windowSec)

  return {
    ok: count <= limit,
    remaining: Math.max(0, limit - count),
    resetAt: (window + 1) * windowSec * 1000,
  }
}
```

```ts
// src/app/(auth)/login/actions.ts 片段
const ip = (await headers()).get('x-forwarded-for')?.split(',')[0]?.trim() ?? 'unknown'
const rl = await rateLimit(`login:${ip}`, 10, 60)

if (!rl.ok) {
  return { error: '尝试过于频繁，请一分钟后再试' }
}
```

`service_role` 密钥不能出现在客户端包。构建后搜一遍静态文件，命中就是泄露。

```bash
# 在构建产物里搜索服务端密钥
rg -l "service_role|SUPABASE_SERVICE" .next/static .next/server || echo "clean"
```

## 52.6 元数据与 SEO

canonical 要写绝对地址。相对地址在预览环境会指错域名，搜索引擎可能把预览页当正本。

标题要有区分度。所有页面共用站点名，搜索结果里看不出差异；列表页、详情页各自带业务信息。

每个页面要有 `title`、`description`、`canonical`。用 curl 检查渲染后的 HTML，不看源码里的模板。

```bash
# 检查标题、描述、canonical
# 抓 head，看标题、描述、canonical、og
curl -s https://teamstack.dev | grep -oE "<title>[^<]*</title>|<meta[^>]*(description|og:image|canonical)[^>]*>"

# sitemap 里有没有不该出现的路径
curl -s https://teamstack.dev/sitemap.xml | grep -c "settings"
```

预览环境必须禁止索引。用 `robots.ts` 按环境返回不同的规则，预览环境全站 `disallow`。

```ts
// src/app/robots.ts
import type { MetadataRoute } from 'next'

export default function robots(): MetadataRoute.Robots {
  // 预览部署一律全站禁止抓取；生产只挡后台路径
  if (process.env.VERCEL_ENV === 'preview') {
    return { rules: { userAgent: '*', disallow: '/' } }
  }

  return {
    rules: { userAgent: '*', allow: '/', disallow: ['/app/', '/api/', '/settings/'] },
    sitemap: 'https://teamstack.dev/sitemap.xml',
  }
}
```

```bash
# 确认预览环境的 robots
curl -s https://teamstack-git-main-xxx.vercel.app/robots.txt
# 预期：User-Agent: *  /  Disallow: /
```

Open Graph 图要检查。社交平台抓不到图时，分享出去只有标题；用调试工具看抓取结果。

结构化数据按需加。公开的营销页可以加 `Organization` 与 `WebSite`，应用内页面不加；加错了会被搜索引擎判为垃圾信息。

站点地图要能访问。`/sitemap.xml` 返回 200 且包含预期 URL；返回 500 或空文件，搜索引擎会反复重试。

`sitemap.ts` 只列公开页面。设置页、团队内部页不进 sitemap；登录后的页面即使被索引也打不开，只会浪费抓取预算。

## 52.7 类型与构建

环境变量也要检查。代码里读了 `process.env.X`，部署环境没配，构建能过、运行时才炸；启动时做一次校验，缺失就退出。

类型检查要覆盖脚本与测试。`tsconfig` 的 `include` 漏掉 `scripts/` 目录时，迁移脚本里的类型错误要到运行时才暴露。

类型检查必须是独立一步，不能依赖构建时的宽松设置。

```bash
# 类型检查
pnpm tsc --noEmit && echo "types ok"
```

构建配置里搜 `ignoreBuildErrors` 与 `ignoreDuringBuilds`。有这两项等于关掉了闸门，上线前要确认它们不存在。

```bash
# 检查是否关闭了检查
rg "ignoreBuildErrors|eslint.ignoreDuringBuilds" next.config.ts
```

构建时间也要记录。从五分钟涨到二十分钟，通常意味着某个依赖或页面失控。

构建告警也要看。`pnpm build` 里的 deprecation 与 bundle 过大提示，多数会在半年后变成事故。

锁文件要提交，CI 用 `--frozen-lockfile`。本地能装、CI 装不上，通常是锁文件没更新。

## 52.8 Core Web Vitals

INP 差多数是主线程被占。大列表渲染、同步计算、第三方脚本都会拖慢交互；把重计算移进 Web Worker 或服务端，比调参数有效。

指标要分设备看。桌面端达标、移动端不达标是常态；4G 网络下的 LCP 与本地 WiFi 差一个数量级。

三项指标：LCP、INP、CLS。本地 Lighthouse 给参考值，真实数据靠 `useReportWebVitals` 上报。

```bash
# 移动端跑一次
# 移动端 Lighthouse，输出摘要
pnpm dlx lighthouse https://teamstack.dev \
  --only-categories=performance \
  --preset=desktop=false \
  --chrome-flags="--headless" \
  --output=json --output-path=./lighthouse-perf.json

node -e "const r=require('./lighthouse-perf.json');for (const k of ['largest-contentful-paint','cumulative-layout-shift','total-blocking-time']) console.log(k, r.audits[k].displayValue)"
```

上报接口要轻。用 `sendBeacon` 在页面隐藏时发，避免影响交互。

```ts
// src/app/layout.tsx 片段
'use client'

import { useReportWebVitals } from 'next/web-vitals'

export function WebVitals() {
  useReportWebVitals(metric => {
    // 只在同意分析时上报，见 51.5
    if (document.cookie.includes('"analytics":true')) {
      navigator.sendBeacon('/api/vitals', JSON.stringify(metric))
    }
  })
  return null
}
```

CLS 的检查方法是慢速滚动。图片没写宽高、字体加载后行高变化、横幅后插入，都会让内容跳动。

LCP 差的常见原因是首屏大图没有 `priority`、字体阻塞、服务端响应慢。CLS 差通常是图片没写尺寸、广告位后插入。

## 52.9 包体积

包体积的增长是渐进的。每次合并涨十 KB，一年后翻倍；没有预算就没有理由拒绝某个“方便”的依赖。

预算落地靠 CI。构建后读 `.next/static/chunks` 的总大小，超过阈值让检查失败；阈值允许按分支调整，但要在 PR 里写原因。

首屏 JavaScript 要有预算。超过预算的提交要说明理由，不能悄悄涨。

| 页面 | 预算（gzip 后） |
| --- | --- |
| 营销首页 | 120 KB |
| 登录注册 | 150 KB |
| 团队列表 | 200 KB |
| 编辑器 | 350 KB |

分析工具用 `@next/bundle-analyzer`，看 chunk 组成。只看总数会漏掉“某个页面悄悄变大”的情况。

```bash
# 安装并生成分析报告
# 装分析器（一次性）
pnpm add -D @next/bundle-analyzer

# next.config.ts 里包一层 withBundleAnalyzer 后：
ANALYZE=true pnpm build
# 会打开两个 HTML，看 client 那张图里最大的块
```

```bash
# 看各 chunk 大小
# 构建后按大小排 .next/static/chunks
du -sh .next/static/chunks/* | sort -rh | head -10
```

拆包要按路由。Next.js 自动按路由拆，但共享依赖会进公共 chunk；把只在设置页用的编辑器挪进动态导入，首屏能少几十 KB。

预算按页面算，不按整站算。整站总数会被少数重页面拉高，掩盖首屏变慢；按页面看，才知道该优化哪一条路径。

大依赖的典型来源：日期库、图标库全量引入、Markdown 编辑器、图表库。按需引入或换轻量实现，效果立竿见影。

## 52.10 运维七项

第一项，健康检查。接口要真的查库，查不到返回 503；只返回 200 的接口没有意义。

```ts
// src/app/api/health/route.ts
import { sql } from 'kysely'
import { db } from '@/lib/db'

export const dynamic = 'force-dynamic'

export async function GET() {
  try {
    await sql`select 1`.execute(db)
    return Response.json({ ok: true, db: 'ok' }, { headers: { 'cache-control': 'no-store' } })
  } catch (error) {
    return Response.json(
      { ok: false, db: 'down', error: (error as Error).message },
      { status: 503, headers: { 'cache-control': 'no-store' } },
    )
  }
}
```

健康检查要区分“进程活着”与“能服务”。只检查端口，数据库挂了仍然返回 200，负载均衡不会摘流量。

运维项要能自动跑。手工检查的项目一定会被跳过，能写进 CI 的就写进去。

第二项，迁移状态。上线前确认数据库的迁移版本与代码一致，差一个版本就可能报列不存在。

```sql
-- 检查已应用的迁移
psql "$DIRECT_URL" -c "select version from supabase_migrations.schema_migrations order by version desc limit 1;"
```

第三项，回滚方案。回滚代码不倒数据库；迁移必须是向后兼容的，删列、改类型要分两次发布。

第三项的回滚要演练过。回滚命令写在手册里，但没跑过就不算；演练时顺便确认旧镜像还在本地或仓库里。

备份验证看三件事：文件存在、大小合理、能恢复。前两件每天自动检查，第三件每季度演练一次。

第四项，备份。上线前手动跑一次备份，确认文件大小与时间戳正常。

运维七项里，健康检查与迁移最容易形式化。健康检查只返回 200、迁移只比版本号不比对内容，都会在真出事时失效。

第五项，证书。`openssl s_client` 看有效期，剩余不足 14 天先续。

第六项，告警。错误率、响应时间、磁盘、证书到期，至少四项有告警。

告警要分级。磁盘 90%、证书 7 天、错误率突增，处理时限不同；全部发到同一个群，真正紧急的会被淹没。

七项里前五项是“有没有”，后两项是“管不管用”。演练一次，能暴露手册里所有想当然的步骤。

第七项，演练。上线后一周内做一次故障演练：停掉应用、看告警、按手册恢复。

## 52.11 清单模板与执行

模板要短。超过两页的清单没人填；把稳定不变的项目收进“默认通过”区块，每次只需确认“无变化”。

模板放 `docs/release-template.md`，每次发布复制成带日期的文件。

```markdown
<!-- docs/release-2026-12-01.md 片段 -->
## 5. 缓存策略明确
$ pnpm build | grep -E "^(○|●|ƒ)"
○ /                    静态
○ /pricing             静态
ƒ /app/teams           动态
时间：2026-11-20 14:03
```

发布前把回滚命令贴在群里，出问题时照抄，不用现查文档；同时约定一个停止发布的条件，比如错误率超过 1%。没有绝对安全的窗口，但工作日上午比周五晚上好；出问题时有人、有时间。

发布记录写三行：版本号、变更摘要、回滚命令。三个月后回看，这三行比重跑一次 CI 有用。

发布后 24 小时是观察期。错误率、P95 延迟、数据库连接数、队列积压，每两小时看一次；异常时优先回滚，再排查。

发布当天按顺序做五件事：确认清单没有空项、跑冒烟命令、看错误率、看关键接口耗时、留一条发布记录。

```bash
# 五条冒烟命令
# 1. 首页 200
curl -s -o /dev/null -w "%{http_code}\n" https://teamstack.dev

# 2. 健康检查含 DB
curl -s https://teamstack.dev/api/health

# 3. 登录页能打开
curl -s -o /dev/null -w "%{http_code}\n" https://teamstack.dev/login

# 4. 受保护页面未登录会跳转
curl -s -o /dev/null -w "%{redirect_url}\n" https://teamstack.dev/app

# 5. 静态资源带缓存头
curl -sI https://teamstack.dev/_next/static/chunks/main-app.js | grep -i cache-control
```

清单要持续维护，半年没人改的清单基本可以作废。每次事故之后补一条检查项，清单会越来越贴合这个项目；抄来的通用清单，三个月后就没人看。

下面七条覆盖清单、渲染、缓存、安全、类型、健康检查与回滚，全部可在发布前跑完。

## 52.12 边界与失败模式

清单全绿仍然出事，通常卡在环境差异与演练缺失。

1. 本地通过，生产失败。环境变量、Node 版本、数据库版本三处差异最常见，逐项比对后再上线。
2. 勾了“通过”但拿不出证据。没有命令输出或截图，等于没做；每项后面附一行证据。
3. 回滚脚本没演练。真出事时才发现脚本引用了不存在的镜像 tag。上线前在预发环境跑一次。
4. 迁移不可回退。删列、改类型的迁移没有反向脚本，回滚只能靠备份，恢复时间从分钟变成小时。
5. 缓存导致旧页面。发布后 CDN 仍返回旧 HTML，用户看到旧按钮；按路径清理缓存并验证响应头。
6. 监控缺失。故障由用户先发现，修复时间被拉长；健康检查与错误告警要在上线前接好。

## 52.13 检查点

1. `docs/release-<日期>.md` 里每一项都有结论，没有空行。判据：`grep -c "| *$"` 为零。
2. `pnpm build` 的路由表与预期一致，营销页静态、登录后动态。判据：符号对得上。
3. 两个账号交替访问，没有看到对方数据。判据：刷新三次结果稳定。
4. 响应头里四个安全头齐全，CSP 处于 Report-Only 或强制状态。判据：curl 输出可查。
5. `pnpm tsc --noEmit` 与 `pnpm lint` 都是零错误。判据：退出码 0。
6. 健康检查在数据库不可用时返回 503。判据：停库测试一次。
7. 回滚演练成功，旧镜像能起来且数据可读。判据：`docker compose ps` 正常。

## 52.14 常见错误

**1. `HTTP/2 502` 但容器都是 Up**

现象是域名打不开，容器状态正常。原因是反向代理指向的服务名或端口错了。改法是 `docker compose exec caddy wget -qO- http://app:3000/api/health` 逐段验证。

**2. 清单全绿，上线后接口 500**

现象是检查都通过，真实请求失败。原因是检查用的是本地环境，线上环境变量缺失。改法是把环境变量也列进清单，逐项对比。

**3. `Module not found: Can't resolve '@/...'`**

现象是 CI 构建失败，本地正常。原因是 `tsconfig` 的 paths 没被构建工具读到，或者大小写不一致。改法是统一别名配置，Linux 上区分大小写。

**4. 预览环境被搜索引擎收录**

现象是搜索结果里出现预览域名。原因是 `robots.txt` 没按环境区分。改法是 `robots.ts` 按 `VERCEL_ENV` 返回 `disallow`，并在 Cloudflare 加一条规则。

**5. `Error: Cannot find module 'sharp'`**

现象是生产环境图片优化报错。原因是 standalone 产物没带上可选依赖。改法是在 Dockerfile 的 runner 阶段安装 `sharp`，或用 `outputFileTracingIncludes` 显式包含。

**6. 回滚后数据库报列不存在**

现象是代码回滚了，页面 500。原因是迁移已经删了列，旧代码还在查。改法是迁移分两次发布，先停用再删除。

## 52.15 这一章在做什么

这一章把散在各章的检查项收成一张表：渲染与缓存、可访问性、安全、SEO、类型、性能、运维。每项都有命令与判据。

它建立三条判断。第一，清单的价值在“没有空项”，不在“看起来很全”。第二，缓存与鉴权的检查必须用两个账号实测。第三，回滚的前提是迁移向后兼容。

这一章不覆盖业务逻辑正确性，那靠测试。也不覆盖容量规划，那靠压测。
