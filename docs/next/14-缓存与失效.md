# 第 14 章 缓存与失效

这一章讲 Next.js 16 的缓存模型，以及数据变化之后怎么让用户看到新值。

缓存失效的问题通常不以「慢」出现，而以「旧」出现。团队改了名，导航栏还是旧名。两个团队的数据串了，A 的活动记录出现在 B 的页面。给页面加了缓存，数据库 QPS 一点没降。三种现象对应三个不同层面的错误：缓存寿命、缓存键、以及这条路由压根没有参与缓存。

Next.js 16 的缓存与 13、14、15 是两套模型。`cacheComponents` 打开之后，数据默认是动态的，缓存变成显式选择；路由段配置 `revalidate`、`dynamic`、`fetchCache` 被移除；PPR 成为默认行为。

涉及的概念有四个：缓存层（浏览器客户端路由、服务端进程、CDN、数据库）、缓存键（由什么决定两次读取是否命中）、缓存寿命（`cacheLife` 的 stale、revalidate、expire）、失效手段（`updateTag`、`revalidateTag`、`revalidatePath`）。顺序是键、寿命、失效。顺序反了，会得到「缓存很新鲜，内容是别人的」。

基线是 Next.js 16.4.6，`cacheComponents: true` 与 `partialPrefetching: true` 同时开启。示例接在 teamstack 的团队页与文档站上。本机只能起一个 Node 进程，多实例与 CDN purge 的行为标「未验证」。

---

## 14.1 缓存的四层结构

同一个团队名至少存在四个地方，它们的失效规则各不相同。

第一层在用户标签页里，是 Next 客户端路由持有的 RSC payload，按 `stale` 时长留在 JS 堆内存中。硬刷新、换标签页、超过 stale 时间、或者在 Server Action 里调用了失效函数，它才会更新。这一层有一个下限：客户端路由缓存至少保留 30 秒，配置得再短也压不下去，这个值通过 `x-nextjs-stale-time` 响应头从服务端传到浏览器。

第二层在服务端进程内存里，或者在你配置的 `cacheHandlers` 指向的共享存储里。`'use cache'` 的条目、ISR 生成的页面、旧 fetch 缓存都写在这里。失效靠 `updateTag`、`revalidateTag`、`revalidatePath`，或者自然到期。

第三层是 CDN 与反向代理，包括 Cloudflare、Vercel Edge、Nginx 的 `proxy_cache`。它只读响应头 `cache-control`，不关心谁写的缓存。失效方式有两种：等 `s-maxage` 过期，或者手动 purge。tag 对它无效。

第四层是 Postgres 的 shared buffers 与查询计划缓存。这一层基本不用管，但要知道它存在，否则会为了一个「查询忽快忽慢」的现象去怀疑前三层。

缓存函数返回什么，也要像接口一样审一遍。`getTeamCached` 只取 `id`、`name`、`slug`、`plan`、`version` 五列，因为返回值会进服务端缓存，也会随 RSC payload 发到浏览器。把整行 `select *` 塞进去，等于把 `stripe_customer_id`、内部备注这类字段一起缓存、一起下发。查询语句里写清楚列名，比事后靠序列化过滤可靠。

判断旧数据出在哪一层，先看响应头。一条命令能看到这一页被当成哪一类：

```bash
curl -sI http://localhost:3000/teams/acme/activity | grep -iE 'cache-control|x-nextjs-stale-time'
```

输出有三种形状。静态页是 `cache-control: s-maxage=31536000`；ISR 页是 `cache-control: s-maxage=3600, stale-while-revalidate=82800`；动态页是 `cache-control: private, no-cache, no-store, max-age=0, must-revalidate`。`x-nextjs-stale-time` 说明客户端还能拿旧副本多久。

## 14.2 打开 Cache Components

开关写在 `next.config.ts` 里，两行要一起写。

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
  cacheLife: {
    // 团队资料这类偶尔改一次的数据
    team: { stale: 300, revalidate: 3600, expire: 86400 },
    // 活动流这类一直在变、但能容忍旧值的数据
    feed: { stale: 30, revalidate: 60, expire: 300 },
  },
}

export default nextConfig
```

只写 `cacheComponents` 不写 `partialPrefetching`，`next dev` 会打印一条警告，提示需要显式设置。只写 `partialPrefetching` 不写 `cacheComponents`，配置校验直接失败，`next dev` 和 `next build` 都起不来。

官方口径是：`partialPrefetching` 在 Cache Components 的第一版里还不存在，为了兼容老项目允许设成 `false`；两者会在下一个大版本默认开启并移除选项。新项目没有理由设 `false`。

打开之后，下面四件事同时改变，不做就报错。

第一，不能再导出 `runtime`。`export const runtime = 'nodejs'` 与已废弃的 `'edge'` 都会让构建报错。Cache Components 只支持 Node runtime。

第二，`dynamic`、`dynamicParams`、`revalidate`、`fetchCache` 四个路由段配置被移除，这是 v16.0.0 的显式变更。旧代码里的 `export const revalidate = 60` 要改写成 `'use cache'` 作用域里的 `cacheLife('minutes')`。

第三，PPR 成为默认行为，`experimental.ppr` 与 `experimental_ppr` 已经删除。每个路由先输出一份静态壳，动态部分用 `<Suspense>` 流式补进去。

第四，导航时用 React 的 `<Activity>` 保留状态。离开一个页签时组件不卸载，而是切成 `hidden` 模式，输入内容、滚动位置、展开的折叠面板都还在。好处是来回切换不丢输入，代价是依赖卸载的清理逻辑失效，定时器与订阅要改成在 `useEffect` 的清理函数里处理。

页面里的静态壳与动态洞按下面的形状拼：

```tsx
// src/app/(app)/teams/[slug]/page.tsx（节选）
import { Suspense } from 'react'

export default function TeamPage({ params }: PageProps<'/(app)/teams/[slug]'>) {
  return (
    <div className="space-y-6">
      <Suspense fallback={<HeaderSkeleton />}>
        {params.then(({ slug }) => (
          <TeamHeader slug={slug} />
        ))}
      </Suspense>

      <Suspense fallback={<PresenceSkeleton />}>
        <LivePresence teamId={teamId} />
      </Suspense>
    </div>
  )
}
```

还有一条常被踩的边界：在 `layout.tsx` 里 `await params` 或读 `cookies()`，会让整层布局变成动态，下面所有页面跟着失去静态壳。把这类读取压到叶子组件、再包一层 Suspense，静态壳才能覆盖到布局。

规则只有一条：任何读请求时 API 的东西，要么包在 `<Suspense>` 里，要么这条路由无法预渲染。没包时，`next dev` 会给出阻塞路由的提示，`next build` 之后该路由退化成全动态渲染。「加了缓存但 QPS 没降」的一大半原因在这里：整页没有参与预渲染，缓存从头到尾没上场。

还有一个方向要扭过来：Cache Components 下数据默认是动态的。不写 `'use cache'`，每次请求都真的去查库。缓存是显式选择，与旧模型里 fetch 默认被缓存相反。这个方向对 teamstack 合适：成员列表、活动流本来就该看最新，只有团队资料、账单摘要这类内容值得缓存。

`next dev` 每次启动都会重建输出目录，缓存从空开始，本地预热出来的命中率没有参考价值，真实数字要从预发环境按天统计，观察窗口至少一周，否则季节与活动带来的波动会把结论带偏。本地看到「第一次慢、第二次快」属于正常现象，不要当成生产表现；生产进程常驻，缓存才会真正积累。

`partialPrefetching` 的效果也要记住：每个路由有一个可复用的 App Shell，读 `cookies()`、`headers()` 的部分按会话缓存在客户端；只有 `<Link prefetch={true}>` 才会解析 `params`、`searchParams` 并预取被 `'use cache'` 包住的真实内容。默认预取拿到的是骨架与侧边栏，不含数据。验证方式是在 Network 面板看预取请求里有没有 `_rsc` 变体。

## 14.3 use cache 与缓存键

`'use cache'` 可以写在三个位置。

```ts
// 位置一：函数体第一行，缓存这个函数的返回值
export async function getTeam(teamId: string) {
  'use cache'
  // ...
}

// 位置二：组件体第一行，缓存这个组件的渲染结果
export async function TeamHeader({ teamId }: { teamId: string }) {
  'use cache'
  // ...
}

// 位置三：文件第一行，这个文件里所有导出都被缓存
'use cache'
```

位置三最省事，也最容易出错。它要求文件里每个导出的函数都是 async，包括 `generateMetadata` 与 `generateStaticParams`，漏一个就构建失败。实践中用位置三包住纯读数据的 `lib` 文件，页面与组件里用前两种。被缓存的函数与组件必须是 async，这是硬性要求。

缓存键决定两次读取是否命中，它由四部分组成：

1. Build ID，配置了 `deploymentId` 时用后者。每次构建都变，所以缓存不跨部署。
2. 函数 ID，由函数在代码里的位置与签名算出。
3. 可序列化的参数，也就是组件的 props 或函数的入参。
4. 开发环境的 HMR 刷新哈希。

被缓存函数闭包里引用的外部变量会被自动捕获成参数，一起进入缓存键。官方示例的形状是这样的：

```ts
async function Component({ userId }: { userId: string }) {
  const getData = async (filter: string) => {
    'use cache'
    // 缓存键同时包含 userId（闭包）与 filter（参数）
    return (await fetch(`https://api.example.com/users/${userId}/data?filter=${filter}`)).json()
  }
  return getData('active')
}
```

没有进入缓存键的变量，会被上一个请求的值覆盖。这是数据串层的机制，全程零报错。所以「缓存键里有没有 teamId」取决于你把它放在参数还是闭包里，两者都会进键；放在函数外、又不在闭包里的变量才会丢。

teamstack 的写法是让 teamId 显式当参数，并且把鉴权放在缓存函数外面。

```ts
// src/lib/teams.ts（在已有文件里追加）
import { cacheLife, cacheTag } from 'next/cache'
import { activityCache } from '@/lib/cache-keys'
import { db } from '@/lib/db'

export type TeamRow = {
  id: string
  name: string
  slug: string
  plan: 'free' | 'pro' | 'team'
  version: number
}

export async function getTeamCached(teamId: string): Promise<TeamRow | null> {
  'use cache'
  cacheLife('team')
  cacheTag(activityCache.tag(teamId))

  const { rows } = await db.query<TeamRow>(
    `select id, name, slug, plan, version
       from public.teams
      where id = $1 and deleted_at is null`,
    [teamId],
  )
  return rows[0] ?? null
}
```

调用它的地方必须先鉴权，再取缓存。

```ts
// src/app/(app)/teams/[slug]/layout.tsx（节选）
const user = await requireUser()
const membership = await requireMembership(teamId, user.id) // 每次查，不进缓存
const team = await getTeamCached(membership.teamId)
```

顺序不能反过来。鉴权结果依赖会话与 cookies，它不能进 `'use cache'`。缓存作用域里读不到 `cookies()`、`headers()`、`searchParams`，这个限制沿调用栈向下追：缓存函数里调了 helper，helper 里读了 cookie，同样报错，错误码是 `next-request-in-use-cache`。在动态渲染的路由上，这个错误可能躲过 `next build`，等到 `next start` 跑起来才出现。

正确做法只有一种：在外面把值读出来，当参数传进去。

```ts
// 反例：缓存作用域里读 cookie，直接报错
export async function TeamActivity({ teamId }: { teamId: string }) {
  'use cache'
  const cookieStore = await cookies() // next-request-in-use-cache
}

// 正例：cookie 在外面读，值当参数传进去
const tz = (await cookies()).get('tz')?.value ?? 'UTC'
return <TeamActivity teamId={teamId} tz={tz} />
```

两个例外。`draftMode().isEnabled` 可以在缓存作用域里读，草稿模式下所有缓存都会重跑，结果也不写入缓存。`'use cache: private'` 是留给「确实要读 cookie、又要缓存」的场景的逃生门，它把缓存放在浏览器侧，每个用户一份，代价是服务端无法跨用户复用。

参数有序列化限制。`string`、`number`、`boolean`、`null`、`undefined`、纯对象、数组、`Date`、`Map`、`Set`、`TypedArray`、`ArrayBuffer` 都可以；类实例、函数、`Symbol`、`URL` 实例不行。`children` 与 Server Action 可以传过去但不读取，这叫 pass-through：

```tsx
async function CachedShell({ children }: { children: React.ReactNode }) {
  'use cache'
  // 只原样渲染，不读取、不遍历 children
  return <section className="rounded-xl border p-6">{children}</section>
}
```

返回值可以包含 JSX 元素，但不能把 JSX 当参数收进来，除非 pass-through。缓存组件返回 `<TeamCard />` 没问题；`<CachedShell>{children}</CachedShell>` 能工作，是因为 children 只被原样塞进输出。一旦在缓存组件里对 children 做 `React.Children.map`，序列化就失败。

`React.cache` 在 `'use cache'` 边界内是隔离的。父组件用 `React.cache` 存的值，缓存函数里看不到。想让数据进入缓存作用域，只有参数这一条路。

## 14.4 cacheLife：缓存活多久

`cacheLife` 只能在 `'use cache'` 作用域里调用，写在模块顶层直接报错。三个字段各管一段。

`stale` 管浏览器。客户端拿着旧副本多久不问服务端。它同时决定这块内容能不能进 App Shell。

`revalidate` 管服务端。多久在后台重新生成一次。到点先发旧值，后台刷新，用户不等待。

`expire` 管最坏情况。完全没有流量时，多久之后必须同步重新生成。到点后的下一次请求阻塞等新数据。

`expire` 必须大于 `revalidate`，否则配置校验阶段直接报错。手调参数时很容易撞上。

内置档位以秒计：

| 预设 | stale | revalidate | expire |
| --- | --- | --- | --- |
| `default` | 5 分钟 | 15 分钟 | 永不过期 |
| `seconds` | 30 秒 | 1 秒 | 1 分钟 |
| `minutes` | 5 分钟 | 1 分钟 | 1 小时 |
| `hours` | 5 分钟 | 1 小时 | 1 天 |
| `days` | 5 分钟 | 1 天 | 1 周 |
| `weeks` | 5 分钟 | 1 周 | 30 天 |
| `max` | 5 分钟 | 30 天 | 1 年 |

不写 `cacheLife` 就用 `default`。官方建议每个 `'use cache'` 都显式写一行，理由很实际：不写时缓存寿命是隐式的，页面上出现旧数据时，无法从代码里读出它应该在多久之后过期。

预渲染有一套阈值，不知道就会写出「看起来缓存了、其实每次都动态」的代码。`revalidate` 为 0，或 `expire` 小于 5 分钟，被算作短命缓存，不参与预渲染，变成请求时的动态洞。`stale` 小于 30 秒，不参与预渲染。`stale` 在 30 秒到 5 分钟之间，可以预渲染，但不进 App Shell。

嵌套还有一条规则：短命缓存嵌在一个没有显式写 `cacheLife` 的外层 `'use cache'` 里，预渲染阶段会抛错。原因是短命会通过嵌套传染外层，让外层的寿命悄悄变短，Next 选择报错，避免出现无法解释的动态洞。修法两种：给外层也显式写 `cacheLife`，或者把短命那块拆到 `<Suspense>` 里单独流式渲染。

不知道填什么，就从「用户能容忍多旧」倒推。改完必须马上看到，不要缓存，或者用请求时的动态读取；能忍几分钟，用 `minutes`；一小时，用 `hours`；一天，用 `days`。三个数各管一头：`revalidate` 决定别人多久能等到变化，`stale` 决定同一个会话多久才会去问服务端，`expire` 决定冷数据最晚什么时候必须重算。

填得比业务容忍度更短并不会更安全，只会增加数据库查询。缓存是用「允许旧」换「少查库」，按业务底线填即可。容忍度越低，数字越小，数据库压力越大，这三者只能同时满足两个。

teamstack 的分配是这样。

- 团队资料用 `team`：stale 5 分钟、revalidate 1 小时、expire 1 天。团队名一天改不了几次。
- 活动流用 `feed`：stale 30 秒、revalidate 1 分钟、expire 5 分钟。成员能接受一分钟延迟，这块数据还会被 `revalidateTag` 主动打掉。
- 账单摘要用 `hours`。

显式写 `cacheLife('team')` 之后，`curl -sI` 出来的 `x-nextjs-stale-time` 会跟着 `team` 的 stale 走。把 `revalidate` 改成 60，再等一分钟刷新，团队名的变化才会自己冒出来，这就是后台刷新的体感。

## 14.5 cacheTag 与 cache-keys.ts

`cacheTag` 同样只能在 `'use cache'` 作用域里调用，一个作用域可以打多个 tag。

```ts
'use cache'
cacheLife('team')
cacheTag(activityCache.tag(teamId), 'team-directory')
```

限制有三条。单次最多 128 个 tag，每个不超过 256 字符，tag 区分大小写。超长的 tag 会被跳过，永远赋不上值，失效时也找不到它；超量的会被丢弃，控制台打一条警告。

多租户项目里 tag 要带 `teamId`，让失效只影响一个团队。图省事打全局 tag（例如 `'teams'`），任何一个团队改名都要清所有人的缓存，高峰期缓存等于摆设。这种大锤 tag 与没有 tag 在性能上差不多，在排障上更糟，因为它看起来像精确失效。

命名由 `src/lib/cache-keys.ts` 统一生成，不要在别处另起一套。

```ts
// src/lib/cache-keys.ts（已有文件，节选本章要用的部分）
export const activityCache = {
  // 列表数据用这个 tag
  list: (teamId: string) => `team:${teamId}:activity`,
  // 某个团队相关的所有缓存用这个 tag
  tag: (teamId: string) => `team:${teamId}`,
}
```

细粒度 tag 有代价。一条数据变化要打三四个 tag，写 action 的人早晚漏一个，表现就是「改完这个页面变了，另一个没变」。团队项目里按数据表分就够了：一个团队的 `list`、`detail`、`billing` 三种，再多就要有清单管理，否则没人记得住该清哪个。

tag 该叫什么，只问一句：按数据集失效，还是按页面失效。按数据集打 tag（「这个团队的所有活动」），改名、加成员、删文件各自动各自的数据集。按页面打 tag（`page:team-settings`），最后会变成「这个页面上的数据来自哪几个查询」的猜谜，而且同一份数据出现在另一个页面时一定会漏。

用页面路径当失效单位还有一个直接的坑：`revalidatePath` 只清掉那个路径的缓存。另一个页面如果也用了同一份数据，不会跟着失效，因为它与那个 tag 没有关系。

## 14.6 三种失效手段

三个函数都能让缓存过期，差别在于谁知道、谁要等。

`updateTag` 立即过期，下一次读等新数据，也就是 read-your-own-writes。它只能用在 Server Action 里，在 Route Handler 里调用会抛 `updateTag can only be called from within a Server Action`。

```ts
// src/app/(app)/teams/[slug]/settings/actions.ts（节选）
'use server'

import { updateTag } from 'next/cache'
import { activityCache } from '@/lib/cache-keys'

export async function renameTeamAction(formData: FormData) {
  const user = await requireUser()
  const team = await requireMembership(/* ... */)

  await db.query(
    `update public.teams
        set name = $2, version = version + 1, updated_at = now()
      where id = $1`,
    [team.id, String(formData.get('name'))],
  )

  updateTag(activityCache.tag(team.id))
}
```

`updateTag` 只保证当前这次请求的当前路由立刻重渲染。同事的标签页、同事正在看的另一个路由，仍按各自的节奏刷新。前者是 `updateTag` 的职责，后者属于客户端 stale 时间与 `revalidateTag` 的职责，两件事要分开讨论。

`revalidateTag` 的签名是 `revalidateTag(tag: string, profile: string | { expire?: number })`，第二个参数必填，这是 v16 的变化，不传是类型错误。

第二参决定旧数据还能被发多久。`'max'` 是推荐值，SWR 语义：标记后立刻返回旧值，后台重新生成，窗口期按一年算。其他 `cacheLife` 档位名只使用它的 `expire` 当窗口。`{ expire: 0 }` 不服务任何旧值，下一次请求阻塞等新数据，适合 Route Handler 与外部 webhook，那里用不了 `updateTag`。

两个常见误解要一次说清。它只做标记，不触发重渲染：stale 窗口内继续发旧值，真正重新生成发生在下一次读。在 action 里调完 `revalidateTag(tag, 'max')`，当前页面不会像 `updateTag` 那样立刻变化。另一个误解是 tag 打错了它也不报错，名字写错、超长、大小写不一致，都是安静地不生效。

调用位置同样有限制：不能在任何 Client Component 里，也不能在 `proxy.ts` 里。

没有登录用户的场景用它：

```ts
// src/app/api/webhooks/payment/route.ts（节选）
import { revalidateTag } from 'next/cache'

await db.query(
  `update public.subscriptions set status = $2 where stripe_subscription_id = $1`,
  [subscriptionId, status],
)

// 别人刷新时能看到新状态，但不阻塞这次 webhook 的响应
revalidateTag(`team:${teamId}:billing`, 'max')
```

`revalidatePath` 的签名是 `revalidatePath(path: string, type?: 'page' | 'layout')`。路径含动态段时必须传 type，例如 `revalidatePath('/teams/[slug]', 'page')`；路由组要写进路径，例如 `'/(app)/teams/[slug]'`。路径用路由文件结构，不带 `/page`，长度上限 1024，大小写敏感；rewrites 场景使用目标路径，不用源路径。

它在 Server Function 里调用会立刻更新当前页面，并且顺带刷新该用户访问过的页面，官方标注这是临时行为。在 Route Handler 里只是标记，下次访问才重新生成。

底层仍然是 tag。Next 给每个路径生成软标签，内部前缀 `_N_T_`，例如 `/blog/hello` 会生成 `/layout`、`/blog/layout`、`/blog/hello/layout`、`/blog/hello` 这几个软标签。`revalidatePath` 让这些软标签失效，所以它能失效路径，失效不了数据。同一份数据出现在别的路径下，那边不会变。团队改名用 tag 不用 path 的原因就在这里：一次改名影响导航栏、设置页、团队列表三个位置。

`revalidatePath('/', 'layout')` 会清掉客户端缓存并失效全部数据，属于核按钮，不要写在正常业务路径里。

四种手段与一个补充 API 的对照：

| 手段 | 能用在哪 | 何时生效 | 下一次读 | 典型场景 |
| --- | --- | --- | --- | --- |
| `updateTag(tag)` | 仅 Server Action | 立即过期 | 等新数据 | 改自己的资料、自己的团队名 |
| `revalidateTag(tag, 'max')` | Server Action、Route Handler | 标记 stale，窗口内发旧值 | 后台刷新，不阻塞 | 别人触发的数据变化、webhook |
| `revalidateTag(tag, { expire: 0 })` | 同上 | 标记，不服务旧值 | 阻塞等新数据 | 外部系统要求立刻一致 |
| `revalidatePath(path, type?)` | Server Action、Route Handler | 按路径标记 | 下次访问重生成 | 页面级内容、CMS 发布 |
| `refresh()` | Server Action | 不失效任何 tag | 只重取当前路由 | 只需要重画一下 |

选型顺序是先问「谁需要立刻看到」，再问「能不能等」。改名的人要立刻看到，用 `updateTag`；旁观者等一两秒无所谓，用 `revalidateTag(tag, 'max')`；外部系统要求强一致，用 `{ expire: 0 }`；只想让页面重新渲染、数据没变，用 `refresh()`。

客户端组件拿不到前三个函数。客户端想刷新，用 `useRouter().refresh()`：重新请求当前路由的 RSC payload，不失效任何缓存。它与服务端 action 里的 `refresh()` 是一对：`router.refresh()` 是客户端 API，`refresh()` 只能在 Server Action 里，两者都不失效 tag。想让别人的数据更新属于服务端的事，所以所有失效调用集中在 action 与 Route Handler 里。

## 14.7 ISR 的两种再生成

Cache Components 下的 ISR 由预渲染与再生成两部分组成。

构建期预渲染由 `generateStaticParams` 决定，列出的路径在 `next build` 时生成静态壳并写入缓存。

```tsx
// src/app/(marketing)/docs/[slug]/page.tsx
import { Suspense } from 'react'
import { notFound } from 'next/navigation'
import { cacheLife, cacheTag } from 'next/cache'
import { getDoc, listDocSlugs } from '@/lib/docs'

export async function generateStaticParams() {
  const slugs = await listDocSlugs()
  return slugs.map((slug) => ({ slug }))
}

export async function generateMetadata({ params }: PageProps<'/(marketing)/docs/[slug]'>) {
  const { slug } = await params
  const doc = await getDoc(slug)
  return { title: doc?.title ?? '文档' }
}

async function DocBody({ slug }: { slug: string }) {
  'use cache'
  cacheLife('days')
  cacheTag(`doc:${slug}`)

  const doc = await getDoc(slug)
  if (!doc) notFound()
  return <article dangerouslySetInnerHTML={{ __html: doc.html }} />
}

export default function DocPage({ params }: PageProps<'/(marketing)/docs/[slug]'>) {
  return (
    <Suspense fallback={<p className="text-sm text-neutral-500">加载中</p>}>
      {params.then(({ slug }) => (
        <DocBody slug={slug} />
      ))}
    </Suspense>
  )
}
```

`params` 是 Promise，要 `await`。这里把 `params.then(...)` 留在 `<Suspense>` 内部，App Shell 不必知道 slug 就能先发出去。

没列进 `generateStaticParams` 的路径在第一次访问时生成。服务器先发 App Shell，在后台渲染这个 URL 并写入 ISR 缓存，下一次访问直接拿到升级后的结果。前提是开了 `partialPrefetching`，并且 `await params` 在 Suspense 或 `loading.tsx` 内部。在外面 await 时，第一个未列路径的请求必须等 URL 渲染完才能返回；没有 `partialPrefetching` 时更糟，永远只发共享 fallback，不生成 URL 级的缓存条目。

再生成有两条路，不要混。时间驱动：`cacheLife` 的 `revalidate` 到点后台刷新，`expire` 到点强制同步生成。按需驱动：`cacheTag` 配 `revalidateTag` 或 `updateTag`，或者 `revalidatePath`。

按需那条在文档站长这样：

```ts
// src/app/api/webhooks/cms/route.ts（节选：CMS 发布后，下次访问用新内容）
import { revalidateTag } from 'next/cache'

await verifyCmsSignature(request) // 别省，这个接口没有登录用户
const { slug } = await request.json()

// 标记 stale：窗口内继续发旧文档，后台生成新版本，不阻塞这次回调
revalidateTag(`doc:${slug}`, 'max')
return Response.json({ ok: true })
```

用 `'max'` 而不用 `{ expire: 0 }` 的理由：文档发布后，访问者多看几秒旧版本没有业务损失；让发布回调等一次页面生成、超时还失败，问题更大。确实要求发布即生效的场景，才用 `{ expire: 0 }`。

旧的 `export const revalidate = 3600` 在 `cacheComponents` 下不存在，应改写成 `cacheLife('hours')` 这类档位。

## 14.8 旧 fetch 缓存的对照

现有项目多半是 13、14 的缓存模型，迁移时最容易把两套混着用。

旧模型里 fetch 默认被缓存；新模型默认 `auto no cache`，开发环境每次请求都取，路由被静态预渲染时在构建期取一次。

`fetch(url, { cache: 'force-cache' })` 仍然可用，属于显式选入，缓存键匹配 URL、method、headers、body，只存 200 响应。`fetch(url, { cache: 'no-store' })` 也仍然可用，每次都取；Draft Mode 下整条缓存被绕过，不读也不写。

`fetch(url, { next: { revalidate: 60 } })` 能用，但不推荐当主模型，新代码用 `'use cache'` 配 `cacheLife`。`next: { tags: ['x'] }` 同理，新代码用 `cacheTag('x')`。

两个路由段配置直接没了。`export const revalidate = 60` 改成 `cacheLife('minutes')`；`export const dynamic = 'force-dynamic'` 删掉，因为不写 `'use cache'` 本来就是动态的。

`unstable_cache(fn, keys, { tags, revalidate })` 的位置被 `'use cache'` 加 `cacheTag` 加 `cacheLife` 取代，但它没有被删，主要留给需要跨部署存活的非 fetch 数据。

有两个行为仍然要注意。

`fetch` 的 memoization 与持久缓存是两件事。GET 请求只要 URL 与参数相同，在同一次服务端渲染过程中会被自动去重，多个 Server Component 调同一个 fetch 只执行一次，这个去重不跨请求。Route Handler 不参与组件树，所以没有 memoization。

开发环境的假象更常见。Next 在 dev 下会把 fetch 响应放进 HMR 缓存，连 `cache: 'no-store'` 的请求都会命中它。本地改完接口发现数据没变，先确认这是 dev 缓存，再去看代码。清掉它的方式是导航或整页刷新，也可以用 `serverComponentsHmrCache: false` 关掉。

前端看到的旧数据还可能来自 CDN。静态页的响应头是 `s-maxage=31536000`；ISR 页是 `s-maxage={revalidate}, stale-while-revalidate={expire - revalidate}`；动态页是 `private, no-cache, no-store, max-age=0, must-revalidate`。`curl -I` 看一眼就知道这一页被当成哪一类。团队设置页如果出现 `s-maxage`，说明它被误判成静态，检查一下那一层有没有漏掉读 cookie。

迁移老项目按下面的顺序做，不要一次全改。

1. 打开 `cacheComponents`，先删掉所有 `export const revalidate`、`dynamic`、`fetchCache`。在这个模型下它们是构建错误。
2. 逐个路由跑 `next build`，先修「读了 cookies/headers 却没包 Suspense」与「页面有请求时数据但根本没缓存」这两类问题。
3. 最后给热点数据加 `'use cache'`，每加一个同时写 `cacheLife` 与 `cacheTag`，并测一次失效。

反过来做会让两类错误混在一起，分不清一次失败是缓存写错，还是路由仍在使用被移除的配置。上面顺序的目的是一次只让一类错误出现。

## 14.9 多实例与 cacheHandlers

默认的 `'use cache'` 存在每个 Node 进程自己的内存里。本地跑一个进程一切正常；部署成三个 Pod，每个 Pod 各有一份缓存，也各自独立失效。

内存缓存的行为随部署形态变化很大。Serverless 环境下，运行期缓存通常不跨请求保留，每次可能是新实例；自托管或容器里跨请求保留，用 `cacheMaxMemorySize` 控制上限。

还有一个经常被忽略的边界：`'use cache'` 包括 `'use cache: remote'`，都不跨部署。缓存键里有 Build ID，新构建等于换了一套键，旧条目自然读不到。想让数据跨部署存活，只有 `unstable_cache` 与 fetch 缓存。

多实例共享缓存要配 `cacheHandlers`：

```ts
// next.config.ts（在 14.2 的基础上加）
const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
  cacheHandlers: {
    default: require.resolve('./cache-handlers/shared.js'),
  },
}
```

handler 要实现五个方法，与「失效不到底」直接相关的是两个。

`updateTags(tags, durations?)` 在有人调用 `revalidateTag` 时被调用。`durations` 不存在表示立即失效；存在表示只标 stale，允许继续发旧值直到 `durations.expire` 秒。`revalidateTag(tag, 'max')` 走的是后者。

`refreshTags()` 在每个请求第一次读缓存之前调用一次，用于从共享存储同步其他实例写下的失效时间。不实现它，实例永远不知道别的实例失效过什么，表现就是「A 改名了，B 的机器还发旧名」。

共享 tag 状态的最小实现如下，复用 `src/lib/redis.ts` 的思路。

```ts
// cache-handlers/shared.ts（节选：只写 tag 协调，get()/set() 里换成你的 KV 读写）
import { createClient } from 'redis'

const client = createClient({ url: process.env.REDIS_URL })
client.connect().catch(() => {})

const localTagTimestamps = new Map<string, number>()

module.exports = {
  async refreshTags() {
    const tagKeys = await client.sMembers('revalidated-tags')
    if (tagKeys.length === 0) return
    const values = await client.mGet(tagKeys.map((k) => `tag:${k}`))
    tagKeys.forEach((k, i) => localTagTimestamps.set(k, Number(values[i] ?? 0)))
  },

  async getExpiration(tags: string[]) {
    const timestamps = tags.map((t) => localTagTimestamps.get(t) ?? 0)
    return Math.max(...timestamps, 0)
  },

  async updateTags(tags: string[], durations?: { expire?: number }) {
    const now = Date.now()
    const pipeline = client.multi()
    for (const tag of tags) {
      pipeline.set(`tag:${tag}`, String(now))
      pipeline.sAdd('revalidated-tags', tag)
      localTagTimestamps.set(tag, now)
    }
    await pipeline.exec()
    if (durations?.expire !== undefined) {
      await client.set('tags:expire-window', String(now + durations.expire * 1000))
    }
  },
}
```

handler 的 `set()` 拿到的值是一个只能读一次的 `ReadableStream<Uint8Array>`。读完必须自己重建流再交给 `get()`；不要把它存起来等下次用，也不要 `.tee()` 之后只消费一支。官方专门警告过这两点，症状是缓存命中后内容为空，或者内存一直涨。

不想自己写 handler，可以用 `'use cache: remote'`。它是平台提供的远程缓存，支持 Redis、KV 等，代价是每次读一次网络往返、可能有平台费用。它适合限流计数、慢后端响应这类舍不得每请求都打一次的数据，不适合每请求都不同的键，例如搜索结果与过滤条件。

```ts
// src/lib/rate-limit.ts（节选：跨实例共享的限流规则）
import { cacheLife, cacheTag } from 'next/cache'

export async function getRateLimitRule(plan: 'free' | 'pro' | 'team') {
  'use cache: remote'
  cacheLife('minutes')
  cacheTag('rate-limit:rules')

  return loadRuleFromDatabase(plan)
}
```

这份规则被所有实例反复读、几分钟才变一次，正好是 remote 的适用范围：写一次，所有 Pod 命中同一份。把 `searchParams` 拼出来的查询塞进 remote，等于每请求造一个只读一次的新键，还要为这些键付存储费。

handler 的实现质量直接决定站的响应时间。每次读缓存都多一次 Redis 往返，20 毫秒的延迟在 50 个请求上就是额外一秒的等待；Redis 超时没设上限时，一个慢节点能把整页拖到超时。给客户端设 `commandTimeout`，失败时回落内存缓存并打日志，比让整站等一个 Redis 更稳。

CDN 是最后一层，也是最容易被忘的一层。CDN 不支持基于 tag 的按需失效。`revalidateTag`、`revalidatePath` 只清 Next 服务端缓存，CDN 会继续发自己的副本直到 `s-maxage` 过期。要让用户立刻看到，必须同时调 CDN 的 purge API，而且 HTML 与 RSC 两个变体都要 purge。CDN 用 `_rsc` 查询参数区分变体，`Vary` 头里还有 `rsc`、`next-router-state-tree`、`next-router-prefetch`、`next-router-segment-prefetch`、`next-url`。只 purge HTML 时，客户端导航走 RSC，仍然拿旧内容。

## 14.10 边界与失败模式

看到旧数据时按固定顺序排查，不要从「清缓存」开始试。

1. 哪个用户、哪个浏览器、哪个标签页。同一个人的两个标签页各有一份客户端内存缓存，无痕窗口是干净的。
2. 服务端有没有失效。看 action 里调的是 `updateTag` 还是 `revalidateTag(tag, 'max')`，后者在 stale 窗口内本来就该发旧值。
3. 有没有别的实例持有一份旧副本。有几个 Pod，`cacheHandlers` 配了没有，`refreshTags()` 实现了没有。
4. CDN 清了没有。`curl -I` 看 `age`、`x-cache`、`cf-cache-status`，purge 是否覆盖 `_rsc` 变体。
5. 有没有可能根本没缓存。用响应头判断这一页被当成静态、ISR 还是动态。第三类事故就在这里：页面是动态的，缓存从头到尾没参与。

响应头对不上时，最快的确认方法是先看分类，再给缓存函数加一行日志。

```ts
// src/lib/teams.ts（调试期临时加，验完删）
export async function getTeamCached(teamId: string) {
  'use cache'
  cacheLife('team')
  cacheTag(activityCache.tag(teamId))
  console.log('[cache] getTeamCached', { teamId })
  // ...
}
```

命中缓存时这行不打印，因为函数体没有执行。打印了说明没命中。这个观察方式比任何缓存面板都直接。

命中率也能顺手算：同一个页面请求 100 次，日志出现 3 次，命中率 97%。低于 80% 时先别怀疑缓存配置，先看缓存键。把每次请求都不同的东西放进参数（`Date.now()`、随机串、原始 `searchParams`），等于给缓存造了无数个只读一次的新键：命中率恒为 0，内存或 Redis 还会一直涨。缓存的第一个问题永远是键对不对，寿命排在后面。

还有一个容易忽略的限制：同一个 URL 对不同用户返回不同内容时，CDN 绝对不能缓存。`Cache-Control: private` 是这条边界的标记，团队页面、设置页都应带上它。反过来，把带个人化数据的页面配成 `s-maxage`，第一个访问者的数据会被发给后面所有人，这类事故不会报错，只会被人截图发到群里。

其余边界。客户端 stale 有 30 秒下限，任何配置都无法让它更短。真正决定别人多久看到变化的是 `cacheLife` 的 `revalidate`，`'max'` 只决定标记之后旧值还能发多久。`updateTag` 之后紧接着的读一定拿到新数据，但那只限于当前请求之后的读，其他会话按自己的 stale 走。

内存缓存有上限，`cacheMaxMemorySize` 控制总量，默认几十 MB，满了按最近最少使用逐出。命中率突然下降时先看内存，再看键；条目太大（整页 HTML、大列表）会把别的条目挤出去，表现为「刚缓存的东西马上又没了」。

时间驱动的再生成需要流量触发。`revalidate` 到点只是标成过期，第一个访问者负责触发后台刷新，没有访问就一直是旧值，直到有人来。低流量页面不要指望「改完一分钟自动生效」，那种场景要用 `revalidateTag` 主动打。

缓存条目被逐出或部署更新后重新计算，计算耗时与数据库查询会同时回来，流量尖峰时容易把数据库打满。给缓存函数加超时与降级，比事后扩容便宜。

## 14.11 检查点

1. 改名自我可见。用 owner 账号在设置页把团队名改成 `Acme Labs`，提交后不刷新，导航栏与设置页标题立刻变新。Network 里这次 Server Action 的响应同时带返回值与重渲染后的 RSC payload。把实现换成 `revalidateTag(tag, 'max')` 应看到停留旧值。

2. A 的数据不进 B 的页面。两个团队各造一条活动记录，A 叫 `A-only`，B 叫 `B-only`，用两个账号分别抓页面。

```bash
curl -s -H "Cookie: $ALICE_COOKIE" http://localhost:3000/teams/acme/activity | grep -c "B-only"
curl -s -H "Cookie: $BOB_COOKIE" http://localhost:3000/teams/globex/activity | grep -c "A-only"
```

两条都应为 `0`。再做一次回归：故意删掉 `listTeamActivity` 的 `teamId` 参数，让缓存键只剩分页参数，重跑应看到非 0。这一步证明测试能抓到「缓存键漏字段」这个零报错错误。

3. 证明 `revalidateTag` 是标记。在 webhook 里调 `revalidateTag(activityCache.list(teamId), 'max')`，立刻连续三次请求同一页面并打印内容里的时间戳。第一次可能仍是旧值，几秒后变成新值。如果调用瞬间就变了，说明实际命中的是 `updateTag` 或客户端缓存被清。

4. 说清哪一层没失效。本机只有一个进程，多实例边界验证不了，按预期写下来：改 A 团队名，本实例立刻新，第二个实例旧，直到 `refreshTags` 或缓存到期；CDN 旧，直到 `s-maxage` 过期或 purge；新部署全清，因为 Build ID 变了。需要两个容器与一个共享 Redis 才能实测，标「未验证」。

5. 三种响应形态各就各位。营销首页是 `s-maxage=31536000`，文档页是 `s-maxage=3600, stale-while-revalidate=82800`，团队设置页是 `private, no-cache, no-store, max-age=0, must-revalidate`。三条都对，说明静态、ISR、动态三种形态没有互相串。

6. 旧配置清干净。全库搜索 `export const revalidate`、`export const dynamic`、`fetchCache`，在 `cacheComponents` 下应为零命中，否则 `next build` 会报错。

## 14.12 常见错误

**`Error: updateTag can only be called from within a Server Action`**

在 Route Handler、`proxy.ts` 或 Client Component 里调了 `updateTag`。它的语义是「自己写的数据，自己下一次读要看到」，只有 Server Action 有「自己」这个概念。webhook、cron、外部回调改用 `revalidateTag(tag, { expire: 0 })`。

**`Route "/teams/[slug]" used "cookies" inside "use cache"`（错误码 `next-request-in-use-cache`）**

缓存作用域里直接或间接读了 `cookies()`、`headers()`、`searchParams`。提示措辞随版本变化，按错误码搜索文档最稳。它可能沿调用栈追到 helper 里，而且在动态路由上可能躲过 `next build`，到 `next start` 才报。把读取挪到缓存函数外面，用参数传进去。

**`Expected 2 arguments, but got 1.`**

`revalidateTag` 的第二参在 v16 必填。它决定旧值还能发多久：`'max'` 走 SWR，`{ expire: 0 }` 要求下一次读阻塞。这条来自 TypeScript；绕过类型检查时运行期走的是已废弃的旧行为，等价 `{ expire: 0 }`。

**`Error: connect ECONNREFUSED 127.0.0.1:6379`**

配了 Redis 版 `cacheHandlers`，Redis 没起，或者 `REDIS_URL` 没进环境变量。handler 在第一次读写时连接，表现为页面 500、日志里全是 ECONNREFUSED。本地用 `docker run -p 6379:6379 redis` 起一个；生产里检查容器网络与 secret 注入。handler 连接失败最好降级为内存缓存，别让缓存挂了拖垮整站。

**页面响应头是 `cache-control: private, no-cache, no-store, max-age=0, must-revalidate`**

期望是静态或 ISR，实际是动态。原因三选一：路由里有请求时 API 没被 `<Suspense>` 包起来；数据读取没写 `'use cache'`，默认就是动态；页面没有预渲染条件，例如 `generateStaticParams` 返回空。先 `curl -I` 确认分类，再去页面里找漏网的动态调用。

**开发模式终端警告 `fetch` 的 `cache` 与 `next.revalidate` 冲突，两个选项都会被忽略**

官方文档只说这种情况在开发模式会打印警告，没给固定文案。严重性在于 Next 不报错，直接把两边都忽略，于是本地看到「缓存时长不生效」很可能就是它。逐个请求检查：`cache: 'force-cache'`、`next: { revalidate }`、`'use cache'` 配 `cacheLife` 三种模型不要混在同一个请求上。

## 14.13 这一章在做什么

这一章做了三件事。

第一，把缓存拆成四层，并给每层确定失效手段：客户端路由的最小 30 秒 stale、服务端的 `'use cache'` 与 ISR、实例之间的 tag 协调、CDN 的 `s-maxage` 与 purge。遇到旧数据时先看响应头，按五问顺序排查，不再靠硬刷新碰运气。

第二，把缓存键讲成正确性问题。缓存键由 Build ID、函数 ID、可序列化参数与闭包捕获组成，没进键的变量会被上一个请求的值覆盖。`getTeamCached(teamId)` 的参数参与权限边界：鉴权在缓存外面，`teamId` 在参数里。

第三，把失效讲成「谁知道、谁要等」的选择题。`updateTag` 给自我可见，`revalidateTag(tag, 'max')` 给旁观者，`{ expire: 0 }` 给外部系统，`revalidatePath` 给页面级内容，`refresh()` 给只想重画。同一份数据出现在多个页面时，tag 按数据集打，不按页面打。

至此 teamstack 的读写链路完整。表结构在第 8 章，连接与迁移在第 9 章，并发与事务在第 10 章，时间与金额在第 11 章，写入表单在第 12 章，列表分页与批量在第 13 章，缓存层在这里。下一章进入身份：`requireUser()` 背后的会话存储、cookie 签名、密码找回，以及 OAuth 回调为什么总在 `state` 参数上出问题。
