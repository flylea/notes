# 第 43 章 性能测量与优化

性能问题分两类，量法不同。

第一类是体积：用户打开页面前要下载多少 JavaScript、CSS、图片。体积影响首屏出现的时间，指标是 LCP 和传输字节数。第二类是延迟：服务端处理一次请求要多久，数据库查询占多少。延迟影响点击之后的等待，指标是接口耗时和 INP。

两类问题的共同点是：不先量，改哪里全靠猜。删掉一个依赖可能省 200KB，也可能一点没变，因为它在服务端包里。加一个索引可能把查询从 800ms 降到 30ms，也可能毫无作用，因为慢的是网络。

这一章按「建基线 → 找大头 → 改 → 复测」的顺序走，每一步都给可执行的命令和可比较的数字。重点在怎么读结果，以及哪些优化看起来有道理、实际没用。

Next.js 16 有一处变化要先知道：`next build` 不再输出每个路由的 `size` 和 `First Load JS`。官方给出的理由是在 RSC 架构下这两个数字不再准确，一个客户端组件被多个路由共享时，算不进单一路由的体积。所以本章不用这两个数字，改用分析器和服务端统计。

## 43.1 性能的三个层次

在动手之前，先分清三个层次的指标，对应的工具也不一样。

页面层：用户能看到内容的时间。核心指标是 LCP（最大内容绘制）、INP（交互到下一次绘制）、CLS（累计布局偏移）。这三个由浏览器测量，采集方式是 `useReportWebVitals`，第 43.7 节讲。

资源层：页面下载了什么。JavaScript 包、CSS、字体、图片，各自的体积和数量。工具是打包分析器和浏览器 Network 面板。

服务端层：请求处理花了多久。数据库查询、外部接口调用、渲染时间。工具是慢查询日志和追踪系统。

三层的因果链是：资源多导致页面层指标差；服务端慢导致首屏时间差和接口延迟高。排查时从页面层往资源层和服务端层拆。

一个常见的误判：页面加载慢，第一反应是加缓存。但如果慢的原因是客户端下载了 1.9MB 的 JS，加服务端缓存不会改变任何东西。先看 Network 面板的传输体积，再决定方向。

另一个误判：只看平均值。平均 LCP 1.8 秒看起来正常，但 p75 可能是 3.4 秒，四分之一用户在你的页面上等了三点四秒。性能指标看分位数，通常用 p75。

## 43.2 建立基线

优化的第一步是记下当前状态。没有基线，后面无法判断改动有没有效。

先看本地开发服务器和生产构建的差别。`pnpm dev` 的首次编译很慢，页面上的数字也不代表生产。所有性能数字都要在 `pnpm build && pnpm start` 之后测。

```bash
pnpm build
pnpm start
```

构建输出会列出每个路由的渲染类型（静态、动态、部分预渲染）。大小数字在 16 起不再显示，别去找它。

启动之后在浏览器打开页面，开 DevTools 的 Network 面板，勾上 Disable cache，刷新。记录四个数字：传输总量（transferred）、请求数、DOMContentLoaded 时间、LCP 时间。这四个数字是基线。

再打开 Performance 面板，点一次录制，刷新页面，停录。看主线程的时间分布：黄色是 Scripting，紫色是 Rendering，绿色是 Painting。如果 Scripting 占了大半，问题在客户端 JavaScript。

## 43.3 分析报告怎么读

treemap 的第一眼只看一个东西：最大的方块是什么。

打开 client 产物，按体积排序，前十个模块里通常有两三个是预期内的（React、路由框架），剩下的是可优化的。可优化的模块有几个特征：来自 UI 库、体积超过 100KB、只在少数页面用到。

第二眼看引用链。点开一个大模块，分析器会显示它被谁 import，一路到页面入口。引用链回答「为什么这个包会在首屏」。常见形态是：页面组件 import 了一个预览组件，预览组件 import 了 Markdown 渲染器，渲染器拖进了语法高亮库。首屏根本不需要高亮，但它跟着整条链下来了。

第三眼区分 client 和 server。服务端包里的大模块不会下载到浏览器，对首屏体积没有影响。`pg`、`sharp`、`ioredis` 这类只能在服务端跑的包出现在 server 产物里是正常的。

一个包同时出现在两边时要注意。判断方法是看 client 产物里有没有它，有就说明被打进了浏览器。

看清之后，改动有三个方向：把工作搬到服务端、按需加载、减少依赖本身。

第一个方向最彻底。一个只在服务端需要的库，根本不该进浏览器包。第二个方向适合用户要交互才用到的组件。第三个方向是换掉体积大的库，代价是重写逻辑。

改之前先判断值不值。一个 30KB 的包，压缩后传输 10KB，在 4G 网络上的下载时间约 100ms，优先级不高。一个 500KB 的包，传输 150KB，值得处理。

判断标准还有一条：这个包在多少个页面的首屏出现。出现在所有页面，优化收益乘上所有访问量；只出现在设置页，收益小得多。

## 43.4 把重活搬到服务端

最常见的体积问题：一个只在展示时用到的库，被打进了客户端包。

典型例子是 Markdown 预览。渲染 Markdown 需要解析器，解析器带语法高亮，语法高亮带几十种语言的规则，加起来 500KB 以上。用户打开文件页只是看一眼内容，不需要这个库。

改法是把它放到服务端，只把渲染好的 HTML 发到浏览器。

先装服务端的渲染库。

```bash
pnpm add shiki
```

```ts
// src/lib/markdown.ts
import "server-only";
import { codeToHtml } from "shiki";

export async function renderMarkdown(source: string): Promise<string> {
  const segments = source.split(/```/);
  const parts: string[] = [];

  for (let i = 0; i < segments.length; i += 1) {
    const segment = segments[i];
    if (i % 2 === 0) {
      parts.push(`<p>${escapeHtml(segment).replace(/\n/g, "<br />")}</p>`);
    } else {
      const [firstLine, ...rest] = segment.split("\n");
      const lang = firstLine.trim() || "text";
      const code = rest.join("\n");
      parts.push(await codeToHtml(code, { lang, theme: "github-dark" }));
    }
  }

  return parts.join("");
}

function escapeHtml(input: string) {
  return input
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;");
}
```

组件改成异步的服务端组件。

```tsx
// src/components/FilePreview.tsx
import { renderMarkdown } from "@/lib/markdown";

export async function FilePreview({ file }: { file: { id: string; content: string } }) {
  const html = await renderMarkdown(file.content);
  return <div className="prose" dangerouslySetInnerHTML={{ __html: html }} />;
}
```

页面里直接用。

```tsx
// src/app/(app)/teams/[slug]/files/[id]/page.tsx
import { FilePreview } from "@/components/FilePreview";

export default async function FilePage({ params }: { params: Promise<{ slug: string; id: string }> }) {
  const { id } = await params;
  const file = await loadFile(id);
  return <FilePreview file={file} />;
}
```

验证客户端的包变小了。

```bash
grep -rn "shiki" .next/static/chunks/ | head
```

输出为空，说明这个库没有进浏览器包。命令要写在构建之后，`.next/static` 目录是构建产物。

`escapeHtml` 不能省。`dangerouslySetInnerHTML` 会把内容当 HTML 执行，Markdown 里的普通文本如果含 `<script>`，就会被注入。先转义，再让 shiki 生成代码块的 HTML。

50 个代码块串行渲染会慢。`await` 放在循环里，每个块等一次。改成 `Promise.all` 并发，或者先取前十个渲染，剩下的滚动加载。

服务端渲染的代价是每次请求都要跑一遍。文件内容不变时，用 `cache()` 做单次请求内的去重，用 `"use cache"` 做跨请求缓存，缓存键带上文件 id 和版本号。文件更新后要能失效。

为什么不用 `react-markdown`：它也可以做服务端渲染，但生态里常见的配置是放到客户端，解析器加插件的体积在 200KB 以上。shiki 的优点是只输出 HTML，客户端零成本，代价是服务端要有额外的 CPU 时间。

## 43.5 按需加载

第二个方向是让「用户要用才下载」。适合体积大、触发时机明确的组件：编辑器、图表、文件预览弹窗。

Next.js 用 `next/dynamic` 做这件事。

```tsx
// src/app/(app)/teams/[slug]/files/[id]/page.tsx（部分）
import dynamic from "next/dynamic";

const FileEditorPanel = dynamic(() => import("@/components/FileEditorPanel"), {
  ssr: false,
  loading: () => <div className="h-96 animate-pulse rounded bg-muted" />,
});

export function EditorSlot({ fileId }: { fileId: string }) {
  return <FileEditorPanel fileId={fileId} />;
}
```

`dynamic` 会把组件拆成独立的 chunk，用户点开编辑时再下载。`loading` 给一个骨架，避免空白。

`ssr: false` 只对客户端组件有效。在服务端组件里写它会直接报错。

```text
`ssr: false` is not allowed with `next/dynamic` in Server Components. Please move it into a Client Component.
```

原因是服务端组件在服务端渲染，没有「不服务端渲染」这个选项。要跳过预渲染，只能把动态导入放进一个 `"use client"` 文件里。

按需加载的代价是等待。用户点「编辑」，要等 chunk 下载、解析、执行，才能看到界面。在快的网络上是 200ms，在慢网络上是两秒。两秒的白屏可能比一开始多下载 300KB 更糟。

两个缓解办法。预取：鼠标移上去就开始下载。

```tsx
// src/components/FileRow.tsx（部分）
"use client";

import { useState } from "react";
import dynamic from "next/dynamic";

const FileEditorPanel = dynamic(() => import("@/components/FileEditorPanel"), { ssr: false });

export function FileRow({ file }: { file: { id: string; name: string } }) {
  const [open, setOpen] = useState(false);
  const [warm, setWarm] = useState(false);

  return (
    <div onMouseEnter={() => setWarm(true)}>
      <button onClick={() => setOpen(true)}>{file.name}</button>
      {open ? <FileEditorPanel fileId={file.id} /> : null}
    </div>
  );
}
```

`warm` 状态在这里只用来触发布局，把悬停和点击的时机分开。列表里每一行都挂一个动态组件时，预取的收益会被摊薄，改成「整页一个编辑面板、点击时传 id」更划算。

骨架：`loading` 给的占位要和真实内容尺寸接近，否则布局会跳一下，CLS 变差。

三种情况不要懒加载。第一，组件在首屏就可见，懒加载只是把下载推迟了几百毫秒。第二，组件很小，拆包带来的请求开销大于收益。第三，组件是首屏内容的父级，拆开会打断流式渲染。

`dynamic` 和 `Suspense` 的分工要清楚。`dynamic` 管代码下载，`Suspense` 管数据等待。

```tsx
// src/app/(app)/teams/[slug]/dashboard/page.tsx（部分）
import { Suspense } from "react";
import { TeamActivity } from "@/components/TeamActivity";

export default function DashboardPage() {
  return (
    <Suspense fallback={<div className="h-40 animate-pulse rounded bg-muted" />}>
      <TeamActivity />
    </Suspense>
  );
}
```

`TeamActivity` 是异步服务端组件，`Suspense` 让页面先出骨架，数据到了再填充。这里没有用 `dynamic`，因为代码本来就在服务端。

## 43.6 减少依赖体积

第三个方向是减少库本身。做法之一是让打包器只引入用到的部分。

```ts
// next.config.ts
import type { NextConfig } from "next";

const config: NextConfig = {
  experimental: {
    optimizePackageImports: ["lucide-react", "@heroicons/react"],
  },
};

export default config;
```

这个配置告诉 Next.js：这些库的具名导入要按模块拆分，只打包真正用到的。图标库一个包有上千个图标，全打进去是 121KB，只用一个箭头图标时是 31KB。

为什么需要它：很多库的入口文件把所有模块都重新导出（barrel file），打包器看到 `import { ArrowRight } from "lucide-react"` 时，要先分析整个入口才能 tree shaking。分析成本和副作用标记经常导致失败，最后全量打进来。`optimizePackageImports` 绕过这个分析，按导入名直接取对应文件。

Next.js 对一部分常见库默认开启这个优化，名单在官方文档里。自己加的库要确认它真的支持按模块拆分，否则配置没有效果。

开发模式的首次编译会变慢，因为要处理更多模块。生产构建的产物会小。

只对分析器里明显大的包加，别一次性加二十个。加错的结果是构建变慢、体积不变。

另一种减少依赖的方式是把包排除在打包之外，让它保持为运行时的 `require`。App Router 用 `serverExternalPackages`。

```ts
// next.config.ts（部分）
const config: NextConfig = {
  serverExternalPackages: ["sharp"],
};
```

这个配置只影响服务端包，客户端组件引用的库不能这样处理。用错地方的表现是构建时报 `Module not found`，或者运行时找不到模块。

## 43.7 采集 Web Vitals

前面几节在本地量，这一节量真实用户。用户设备、网络、浏览器各不相同，本地数字只代表你的机器。

Next.js 提供 `useReportWebVitals` 钩子。

```tsx
// src/components/web-vitals.tsx
"use client";

import { useReportWebVitals } from "next/web-vitals";

export function WebVitals() {
  useReportWebVitals((metric) => {
    const body = JSON.stringify({
      name: metric.name,
      value: metric.value,
      id: metric.id,
      rating: metric.rating,
      path: location.pathname,
    });

    if (navigator.sendBeacon) {
      navigator.sendBeacon("/api/vitals", new Blob([body], { type: "application/json" }));
      return;
    }
    void fetch("/api/vitals", { method: "POST", body, keepalive: true });
  });

  return null;
}
```

挂到根布局。

```tsx
// src/app/layout.tsx（部分）
import { WebVitals } from "@/components/web-vitals";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN">
      <body>
        {children}
        <WebVitals />
      </body>
    </html>
  );
}
```

五个指标各管一段。LCP 是最大内容元素出现的时间，衡量首屏。INP 是从交互到画面响应的延迟，衡量流畅度。CLS 是布局偏移累计分数，衡量稳定性。TTFB 是首字节时间，反映服务端。FCP 是首次绘制时间，反映白屏时长。

接收端要做白名单和范围校验，否则表会被脚本灌满。

```ts
// src/app/api/vitals/route.ts
import { createAdminClient } from "@/lib/supabase/admin";

const NAMES = new Set(["LCP", "INP", "CLS", "TTFB", "FCP"]);
const LIMITS: Record<string, number> = {
  LCP: 30000,
  INP: 30000,
  CLS: 10,
  TTFB: 30000,
  FCP: 30000,
};

export async function POST(request: Request) {
  const body = await request.json().catch(() => null);
  if (!body || !NAMES.has(body.name) || typeof body.value !== "number") {
    return new Response("bad request", { status: 400 });
  }

  const value = Math.min(Math.max(body.value, 0), LIMITS[body.name] ?? 60000);
  const supabase = createAdminClient();
  await supabase.from("vitals").insert({
    name: body.name,
    value,
    rating: typeof body.rating === "string" ? body.rating : null,
    path: typeof body.path === "string" ? body.path.slice(0, 200) : null,
  });

  return new Response(null, { status: 204 });
}
```

表结构。

```sql
-- supabase/migrations/20261129090000_vitals.sql
create table public.vitals (
  id uuid primary key default gen_random_uuid(),
  name text not null check (name in ('LCP', 'INP', 'CLS', 'TTFB', 'FCP')),
  value double precision not null,
  rating text,
  path text,
  created_at timestamptz not null default now()
);

create index vitals_created_idx on public.vitals (created_at desc);
create index vitals_name_created_idx on public.vitals (name, created_at desc);

alter table public.vitals enable row level security;
revoke all on public.vitals from anon, authenticated;
grant all on public.vitals to service_role;
```

这张表没有给登录用户开放任何权限。数据只进不出，查询走 service role 或者只读账号。

算 p75。

```sql
select
  name,
  percentile_cont(0.75) within group (order by value) as p75,
  count(*) as samples
from vitals
where created_at >= now() - interval '7 days'
group by name;
```

判读标准：LCP 小于 2.5 秒算好，2.5 到 4 秒需要改进，超过 4 秒算差；INP 小于 200ms 算好；CLS 小于 0.1 算好。

为什么用 p75 不用平均：平均值被极快的请求拉低，掩盖了慢的那部分用户。p75 的含义是四分之三的用户在这个数字以内，更接近真实体验。

两个指标要一起看。LCP 变差但 TTFB 没变，说明问题在客户端渲染；TTFB 变差但 LCP 没变，说明服务端慢但被并行请求掩盖了。

采样要控制。页面浏览量大的站点，10% 采样足够看趋势，全量采会撑爆表。采样在客户端做：`if (Math.random() > 0.1) return;`。

隐私要注意。上报路径会带用户 id 或者查询参数，要归约成路由模板，比如把 `/teams/7c3f/files` 上报成 `/teams/[slug]/files`。不要发 UA、完整 URL、cookie。

本地开发不要往生产表写。用 `process.env.NODE_ENV === "production"` 判断，或者给上报端点加一个环境标记字段。

## 43.8 归因：慢在哪个元素上

知道 LCP 是 3.4 秒还不够，要知道是哪张图、哪个元素拖的。

`useReportWebVitals` 的 metric 对象里带归因信息。开启方式是 `next.config` 里打开实验项。

```ts
// next.config.ts（部分）
const config: NextConfig = {
  experimental: {
    webVitalsAttribution: ["LCP", "CLS"],
  },
};
```

上报的数据里会多一个 `attribution` 字段，LCP 的归因里有 `largestShiftTarget`，值可能是 `img.hero-illustration`。这个值直接指向元素。

拿到元素名，问题就好定位了：是首屏插画图没压缩，还是字体加载慢导致文字最后才出现。

图片是最常见的 LCP 元素。Next.js 的 `next/image` 会自动处理尺寸、格式、懒加载。

```tsx
// src/app/(marketing)/page.tsx（部分）
import Image from "next/image";
import hero from "@/public/hero.png";

export default function HomePage() {
  return (
    <Image
      src={hero}
      alt="团队协作界面预览"
      priority
      sizes="(max-width: 768px) 100vw, 720px"
      placeholder="blur"
    />
  );
}
```

`priority` 表示这张图是首屏关键资源，要提前加载，不要懒加载。`sizes` 告诉浏览器不同视口下的显示宽度，浏览器据此选合适的文件。`placeholder="blur"` 给一个模糊占位，减少 CLS。

不写 `sizes` 时，浏览器按 `100vw` 估算，可能选一张过大的图。首屏图片加上 `priority` 和 `sizes` 之后，LCP 从 3.4 秒降到 1.6 秒是常见结果。

改完要复测。滚动窗口取两三天，因为 p75 是滚动的，当天的数据样本太少。按小时分组能看到改动上线的时间点。

```sql
select
  date_trunc('hour', created_at) as hour,
  percentile_cont(0.75) within group (order by value) as p75
from vitals
where name = 'LCP' and created_at >= now() - interval '3 days'
group by 1
order by 1;
```

曲线在某个小时明显下降，那个时间点就是上线时刻。

INP 的优化方向不同。INP 高说明主线程被占住了，常见原因是点击后同步做了大量计算、或者一次渲染了上千行列表。改法是 `startTransition` 包住状态更新、把计算搬到服务端、列表用虚拟滚动。

`attribution` 和 `rating` 的区别：`rating` 是浏览器给的分档（good、needs-improvement、poor），`attribution` 是元素或者阶段信息。前者用于统计，后者用于定位。

## 43.9 服务端慢查询

页面体积优化完，可能还剩一两秒的等待。这部分多半在服务端。

先看哪个查询慢。开 `pg_stat_statements`。

```sql
create extension if not exists pg_stat_statements;
```

```sql
select
  calls,
  round(total_exec_time::numeric, 1) as total_ms,
  round(mean_exec_time::numeric, 1) as mean_ms,
  left(query, 80) as query
from pg_stat_statements
order by total_exec_time desc
limit 10;
```

`total_exec_time` 是累计时间，`mean_exec_time` 是单次平均。两个都要看：一个查询单次 5ms 但每天跑十万次，累计时间可能比单次 800ms 的查询还高。

找到可疑查询，用 `explain analyze` 看执行计划。

```sql
explain analyze
select * from activity_logs
where team_id = '7c3f...' and created_at >= now() - interval '30 days'
order by created_at desc
limit 50;
```

关注三处：`Seq Scan` 表示全表扫描；`Rows Removed by Filter` 数字大表示扫了很多行才筛出结果；`Buffers: shared hit` 表示命中缓存，`read` 表示读磁盘，后者贵得多。

`activity_logs` 表的索引在第 8 章建过：`(team_id, created_at desc, id desc)`。查询条件里 `team_id` 在前，能走这个索引。如果查询变成 `order by id desc`，索引就用不上，因为排序字段和索引顺序不一致。

索引不生效的两个常见原因。一是统计信息过期，跑一次 `analyze activity_logs`。二是条件里对列做了运算，`where created_at::date = current_date` 会让索引失效，改成范围比较。

另一个常见问题是 N+1 查询。页面上列 50 个文件，每个文件查一次上传者，就是 50 次往返。

```ts
// 反例：每个文件查一次
for (const file of files) {
  const { data: profile } = await supabase.from("profiles").select("full_name").eq("id", file.uploader_id).single();
}
```

改成一次查询带关联。

```ts
// src/lib/files.ts（部分）
const { data } = await supabase
  .from("files")
  .select("id, name, size_bytes, profiles(full_name)")
  .eq("team_id", teamId)
  .order("created_at", { ascending: false })
  .limit(50);
```

51 次查询变成 1 次，接口耗时从 800ms 降到 120ms。这个例子的收益比大多数包体积优化都大。

只查需要的列。`select("*")` 会把大字段也拉回来，`content`、`metadata` 这类列有时几十 KB。列表页只查 `id, name, size_bytes` 就够。

连接池的问题在第 9 章讲过。并发上不去时先看 `pg_stat_activity` 里有没有大量 `idle in transaction`。一个请求占一个连接，事务里调外部接口会让连接被占住几秒。

对比要控制变量。五项改动一起上，就分不清哪项有效。至少在改之前把清单列出来，每项单独记一次 LCP 或者体积，实在懒得分开测，也要在文档里写清「本次是打包改动」。

判断什么时候停下来。三条信号够了：p75 进入 good 区间；继续优化要动架构（比如引入 CDN 或者拆服务），收益小于成本；剩下的瓶颈不在我们能改的范围（用户网络、第三方脚本）。

CI 里可以加体积预算。思路是把当前体积当基线，超过 5% 就让构建失败。

```js
// scripts/check-bundle.mjs
import { readdirSync, statSync } from "node:fs";
import { join } from "node:path";

const BUDGET = 300 * 1024;
let total = 0;

function walk(dir) {
  for (const entry of readdirSync(dir)) {
    const full = join(dir, entry);
    const stat = statSync(full);
    if (stat.isDirectory()) walk(full);
    else if (entry.endsWith(".js")) total += stat.size;
  }
}

walk(".next/static/chunks");
console.log(`client js: ${(total / 1024).toFixed(0)} KB / budget ${BUDGET / 1024} KB`);
if (total > BUDGET) {
  console.error("体积超预算");
  process.exit(1);
}
```

```bash
node scripts/check-bundle.mjs
```

预算按当前值加 5% 定，不要按理想值定。定得太严，正常的依赖升级都会失败，团队会直接忽略这个检查。

本地数字不能当结论。本地是空数据库、无并发、网络快；真实环境有并发、有慢查询、有第三方脚本。三类数字分工：本地构建用于比体积，RUM 用于看用户体验，压测用于看容量上限。

## 43.11 边界与失败模式

优化过程里有几个坑容易踩。

Turbopack 和 webpack 配置冲突。16 起 Turbopack 是默认构建器，项目里有自定义 webpack 配置时构建会失败，提示不支持。处理方式是改成 Turbopack 支持的配置，或者显式切回 webpack。两种构建器的产物不同，体积数字不能互相比较。

分析器看错产物。默认展示的可能是服务端包，看到大模块其实不会下载到浏览器。切 client 那一栏再判断。

`ssr: false` 用在服务端组件里。报错原文在第 43.5 节，改法是把动态导入搬进客户端组件。

依赖装错位置。`shiki` 装成 devDependency 时，生产构建找不到模块，报 `Module not found`。服务端运行时用到的包必须在 dependencies 里。

WAF 或者 CDN 干扰。生产环境的 `/api/vitals` 可能被拦、被限流、被缓存。上报端点要加 `cache-control: no-store`，确认网关不会把 POST 缓存。

采样率设得太低。1% 采样在每天一万次访问时只有一百个样本，p75 抖动很大。至少 5%，数据量大时再降。

缓存把改动盖住了。本地测改动，浏览器缓存了旧 chunk，看到的是旧数字。测之前清缓存或者开无痕窗口。

服务端渲染的隐性成本。把渲染搬到服务端之后，CPU 用量上升，低配机器上可能变成新的瓶颈。改完看一次 `docker stats`。

## 43.12 检查点

1. `pnpm build` 之后 `.next/static/chunks` 的总大小被记进 `docs/perf.md`，作为基线。
2. `ANALYZE=true pnpm build` 能打开分析器，client 产物里能指出最大的三个模块和它们的引用链。

5. 跑一次访问，`select name, value from vitals order by created_at desc limit 5;` 能看到五个指标记录。
6. 跑 p75 查询，LCP 的 p75 有具体数字，能说清它是 good、需要改进还是差。

## 43.13 常见错误

**1. Turbopack 不支持自定义 webpack 配置**

现象：`Webpack is configured while Turbopack is not, which may cause problems.`，或者构建直接失败。原因是 `next.config` 里有 `webpack` 字段。去掉配置，或者显式用 `--webpack` 构建并接受体积口径变化。

**2. 服务端组件里用了 ssr: false**

现象：`` `ssr: false` is not allowed with `next/dynamic` in Server Components ``。原因是 `dynamic` 调用写在服务端组件文件里。把调用搬进 `"use client"` 文件。

**3. 服务端渲染依赖装成开发依赖**

现象：`Module not found: Can't resolve 'shiki'`，只在生产构建出现。原因是 `pnpm add -D shiki`。改成 `pnpm add shiki`。

**4. 指标上报被拒**

现象：`POST /api/vitals 400`。原因是上报了白名单外的事件名，比如 Pages Router 才有的 `Next.js-hydration`。按五指标白名单过滤，或者补上白名单。

**5. 改了代码线上指标没变**

现象：p75 一周后还是老数字。三个可能：采样率太低、CDN 缓存了旧页面、改动没覆盖到主要路由。先看按小时的曲线有没有断点，再确认构建版本。

**6. 执行计划走了索引还是慢**

现象：`explain analyze` 显示用了索引，耗时仍然很高。原因可能是返回行数太多、或者 `select *` 拉了大字段。看 `Buffers` 和返回的数据量，只查需要的列，加 `limit`。

## 43.14 这一章在做什么

这一章按三层拆性能问题：页面层的 LCP、INP、CLS，资源层的包体积，服务端层的查询耗时。工具分别是 `useReportWebVitals`、打包分析器、`pg_stat_statements`。

流程是：先建基线，再用分析器找最大的模块和它的引用链，然后把重活搬到服务端、按需加载、减少依赖，最后用 p75 复测并记录前后对比。每一项改动都要有数字，没有数字的改动无法判断是否有效。

到这里，应用的体积和延迟有了可量化的改进路径。第 44 章换到供应链视角，讲装进来的这些依赖怎么管，怎么保证每次构建装的是同一批代码。
