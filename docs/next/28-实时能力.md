# 第 28 章 实时能力

实时能力指服务端数据变化后，浏览器在几百毫秒内收到通知。用户不用刷新页面，代码也不用定时发请求。

teamstack 里有四处需要它：团队设置页的团队名、成员在线名单、输入提示、通知角标。前三个在本章完成，通知角标放在第 29 章。

本章涉及四个概念。Realtime 的三种推送模式：Postgres Changes、Broadcast、Presence。频道的订阅生命周期：建立、连接、断开、重连。断线之后如何补齐状态。免费档的连接与消息限额。

四条都会影响实现方式，顺序不能颠倒。

## 28.1 三种模式各管什么

Supabase Realtime 在一个 WebSocket 连接上复用多个频道。频道是订阅的容器，每种模式决定了频道里推什么。

| 模式 | 推送内容 | 数据来源 | 授权位置 | teamstack 的用处 |
| --- | --- | --- | --- | --- |
| Postgres Changes | 表的增删改记录 | WAL 逻辑复制 | 表的 RLS 策略 | 团队名、成员列表、通知 |
| Broadcast | 任意 JSON 消息 | 客户端或数据库触发器 | `realtime.messages` 的 RLS | 输入提示、光标位置 |
| Presence | 谁在线、在线状态 | 客户端 `track()` | `realtime.messages` 的 RLS | 在线成员名单 |

Postgres Changes 的优点是省事：不写发送代码，数据库写完就推。缺点是每个事件要对每个订阅者做一次授权，订阅者多了会拖慢写入。

Broadcast 的优点是轻：不查表、不做行级判断，一条消息扇出给频道里所有人。代价是消息内容要自己保证正确，服务端不校验。

Presence 是 Broadcast 的特例，状态由客户端上报，频道里所有人可见。它适合表达“谁在”，不适合当数据存储。页面关掉之后状态会过期，不能用来判断“这个用户现在有没有权限”。

选型可以按三个问题走。这条数据写不写进数据库？写，用 Postgres Changes；不写，用 Broadcast。这条消息要不要按行鉴权？要，用 Postgres Changes；不要，用 Broadcast。要表达的是“谁在线”吗？是，用 Presence。

反过来问也成立。Postgres Changes 不适合表达“正在输入”，因为它要求先落库，而输入状态没有落库的价值。Broadcast 不适合推订单状态，因为客户端无法验证消息真假。

## 28.2 一条变更怎么走到浏览器

要让 Postgres Changes 生效，表必须先加入 publication。publication 是 Postgres 逻辑复制的出口，没登记的表的写入不会进复制流。

Realtime 服务是一个常驻进程。它订阅这份复制流，按客户端的订阅关系分发。所以实时能力不需要客户端轮询，也不需要 Webhook，数据库写完就有人接着。

分发之前有一次授权。服务端按订阅者的身份查 RLS 策略，判断这一行能不能给他。这个动作对每个事件、每个订阅者各做一次。一百个人订阅同一张表，一次写入就是一百次授权判断。

publication 是表级开关，加进去的每一张表都参与逻辑复制，写入路径多一次解码开销。把不需要实时的表排除在外，别整库加进去。本地开发环境 `supabase start` 自带一个复制槽，长时间不消费会让 WAL 积压占盘，调试完记得停容器。

官方在扩展性说明里给了一组实测数字，环境是开启 RLS 的表。500 个并发连接时，每秒约 30 个变更，p95 延迟 228ms。1500 个连接时降到每秒 10 个，p95 356ms。3000 个连接时每秒 5 个，p95 616ms。数字随版本和硬件变化，趋势稳定：订阅者越多，单个变更越慢。

这组数字定了一条线：同一个变更的订阅者超过约 3000 个，改用数据库触发的 Broadcast。触发器里调一次 `realtime.broadcast_changes()`，由 Realtime 扇出，绕过逐订阅者的行级授权。

`filter` 参数不能省授权成本。它在分发阶段做过滤，授权判断已经发生过了。用它减少网络流量可以，想靠它降低服务端开销不行。

publication 漏登记是排第一的故障源。订阅会返回 `SUBSCRIBED`，事件一条不来，控制台也没有报错。自查一条 SQL 就够：

```bash
psql "$DATABASE_URL" -c "select schemaname, tablename from pg_publication_tables where pubname = 'supabase_realtime';"
```

DELETE 事件还有一个缺口。行级安全策略不适用于 DELETE，服务端无法确认订阅者有没有权限读一条已经删掉的行，所以这类事件按保守方式处理。teamstack 的解法是软删除：删团队不执行 DELETE，改为写 `deleted_at`，让删除走 UPDATE 事件。

UPDATE 事件默认只带主键和改动列。表的 `replica identity` 是 `default` 时，`old` 里只有主键。需要完整的旧值，执行 `alter table public.teams replica identity full;`，代价是每次写入的 WAL 体积变大。

## 28.3 前置条件与迁移

三张表要推：`teams`、`team_members`、`notifications`。前两张本章用，第三张第 29 章用。一次加完。

```sql
-- supabase/migrations/20261124090000_realtime.sql
alter publication supabase_realtime add table public.teams;
alter publication supabase_realtime add table public.team_members;
alter publication supabase_realtime add table public.notifications;
```

私有频道要单独授权。Broadcast 和 Presence 的权限写在 `realtime.messages` 上，按 topic 判断。topic 用 `team:<team_id>:<用途>` 的格式，策略里取第二段拿团队 id。

```sql
-- 20261124090000_realtime.sql（继续）

-- 订阅（读）权限：只能进自己团队的频道
create policy "team members can read team channels"
  on realtime.messages for select
  to authenticated
  using (
    exists (
      select 1 from public.team_members m
      where m.team_id = split_part((select realtime.topic()), ':', 2)::uuid
        and m.user_id = (select auth.uid())
    )
  );

-- 发送（写）权限：同上
create policy "team members can write team channels"
  on realtime.messages for insert
  to authenticated
  with check (
    exists (
      select 1 from public.team_members m
      where m.team_id = split_part((select realtime.topic()), ':', 2)::uuid
        and m.user_id = (select auth.uid())
    )
  );
```

`realtime.messages` 已经开了行级安全，不要再执行 `alter table realtime.messages enable row level security`。这条命令会报 `42501 must be owner of table messages`，并且把当前事务一起中断。同理，`realtime` schema 下不能建表、不能建函数，会报 `permission denied for schema realtime`。

不加 `private: true` 的频道是公开频道。公开频道不查 `realtime.messages` 的策略，任何人拿到 topic 就能进。团队频道必须声明私有。

策略在连接建立时缓存，连接期间不重查。官方文档的原话是「Client access policies are cached for the duration of the connection」。把某人移出团队后，他已有的连接仍能收消息，直到断开重连。要立即生效，服务端把该用户踢下线，或者前端在权限变更后主动 `removeChannel` 再重建。

回滚 publication 用 `alter publication supabase_realtime drop table public.teams;`。反复加减同一张表不会报错，但每加一次都要确认控制台的 Realtime 设置里没有重复条目。

客户端连接时还要带上用户身份。匿名连接的订阅在授权阶段拿不到 `auth.uid()`，策略一律不通过。

```ts
// src/lib/realtime.ts
import type { SupabaseClient } from "@supabase/supabase-js";

export async function ensureRealtimeAuth(supabase: SupabaseClient) {
  const { data } = await supabase.auth.getSession();
  if (!data.session) {
    await supabase.realtime.setAuth();
    return;
  }
  // 把当前 JWT 交给 Realtime，后续授权用这个身份
  await supabase.realtime.setAuth(data.session.access_token);
}
```

JWT 默认一小时过期。过期后不断开连接，但新的订阅会被拒。页面要在 `onAuthStateChange` 里重新调用 `setAuth()`，否则用户挂着页面超过一小时就会静默收不到新事件。

## 28.4 写第一个订阅

浏览器端客户端做成单例。`createBrowserClient` 内部已经做了缓存，反复调用不会新建连接，但每个调用点各写一次容易在依赖数组里引发重复订阅。统一从一处导出。

```ts
// src/lib/supabase/client.ts
import { createBrowserClient } from "@supabase/ssr";

let client: ReturnType<typeof createBrowserClient> | undefined;

export function createClient() {
  if (!client) {
    client = createBrowserClient(
      process.env.NEXT_PUBLIC_SUPABASE_URL!,
      process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    );
  }
  return client;
}
```

订阅组件接收团队 id，监听这一行的 UPDATE。

```tsx
// src/app/(app)/t/[slug]/settings/team-name-live.tsx
"use client";

import { useEffect, useRef } from "react";
import { useRouter } from "next/navigation";
import { createClient } from "@/lib/supabase/client";
import { ensureRealtimeAuth } from "@/lib/realtime";

export function TeamNameLive({ teamId }: { teamId: string }) {
  const router = useRouter();
  const subscribedOnce = useRef(false);

  useEffect(() => {
    const supabase = createClient();
    let cancelled = false;

    const channel = supabase
      .channel(`team:${teamId}:settings`)
      .on(
        "postgres_changes",
        {
          event: "UPDATE",
          schema: "public",
          table: "teams",
          filter: `id=eq.${teamId}`,
        },
        () => {
          // 事件只说明“变了”，具体值重新取
          router.refresh();
        },
      )
      .subscribe(async (status) => {
        if (status === "SUBSCRIBED") {
          await ensureRealtimeAuth(supabase);
          // 首次订阅不补状态，重连才补
          if (subscribedOnce.current) router.refresh();
          subscribedOnce.current = true;
        }
        if (cancelled) return;
      });

    return () => {
      cancelled = true;
      void supabase.removeChannel(channel);
    };
  }, [teamId, router]);

  return null;
}
```

三处细节决定这段代码是否可靠。

`filter` 写成 `id=eq.<uuid>`，服务端只推这一行。操作符支持 `eq`、`neq`、`lt`、`lte`、`gt`、`gte`、`in`、`like`、`ilike`、`match`、`imatch`、`is`、`isdistinct`，可以用 `not.` 前缀，逗号分隔表示同时满足。

回调里只拿事件类型，不拿新值。新值是事件的 `new` 字段，但 UPDATE 事件默认只带主键和改动列，缺列时前端拼不出完整对象。重新走一次服务端请求最稳，代价是一次 RSC 请求。

`subscribedOnce` 用来区分首次订阅和重连。首次进来页面已经有服务端渲染的数据，再补一次是浪费。断线重连时页面数据可能是旧的，必须补。

回调的第一个参数是事件对象，字段固定：

- `eventType`：`INSERT`、`UPDATE`、`DELETE` 之一。
- `new`：新行，DELETE 时为空对象。
- `old`：旧行，默认只有主键，DELETE 时可能是空对象。
- `schema`、`table`：来源表和 schema。
- `commit_timestamp`：事务提交时间，字符串格式的 ISO 时间。

`new` 不保证字段齐全。需要完整行时不要拼，重新查一次。

一个频道可以挂多个 `.on()`。团队设置页要同时听团队名和成员变化，挂两个监听即可，共用一个连接：

```ts
// src/app/(app)/t/[slug]/settings/team-name-live.tsx（片段）
supabase
  .channel(`team:${teamId}:settings`)
  .on("postgres_changes", { event: "*", schema: "public", table: "teams", filter: `id=eq.${teamId}` }, onTeamChange)
  .on("postgres_changes", { event: "*", schema: "public", table: "team_members", filter: `team_id=eq.${teamId}` }, onMemberChange)
  .subscribe();
```

`filter` 只在单表上生效，跨表条件写不了。要按角色过滤，只能在回调里判断。

频道也可以指定只推部分列。`select: ['id', 'name']` 会告诉服务端只序列化这几列，主键总是包含在内。列多的表加上它，能省掉大量无用字段的传输。

不要在事件回调里直接写业务逻辑。回调可能被同一个事件触发多次，重连时会补一次全量刷新，重复执行会出错。回调只做一件事：标脏，然后让上层重新取数。

## 28.5 订阅的生命周期

`subscribe()` 返回频道对象，不返回 Promise。状态通过回调给出，四种取值：

- `SUBSCRIBED`：连接成功，可以收事件。
- `CHANNEL_ERROR`：连接建立失败，通常是网络或鉴权问题。
- `TIMED_OUT`：握手超时。
- `CLOSED`：连接已关闭，主动调用 `removeChannel` 后出现。

在没有网络的环境里 `subscribe` 不会抛异常，只在回调里给 `CHANNEL_ERROR`。判断写 `status !== "SUBSCRIBED"` 最省事，别逐状态枚举。

清理必须调 `removeChannel(channel)`。只清定时器不清频道，组件卸载后频道还在收事件，每次路由切换泄漏一个。调试时用 `supabase.getChannels()` 看当前连接上的频道数，切五次页面数字不变才算干净。

依赖数组里只放原始值。放对象会每次渲染都建立新引用，effect 反复执行，频道反复建删。团队 id 是字符串，放进数组没问题。

订阅回调里不要直接改 React 状态，除非组件已经写了卸载标记。组件卸载后回调仍可能触发一次，那时改状态会在控制台打印 “Can't perform a React state update on an unmounted component”。用一个 `cancelled` 布尔变量在 cleanup 里置位，回调开头判断它。

开发环境下 React 的严格模式会把 effect 挂载两次。第一次建频道、马上清理、再建一次，控制台会看到两次 `SUBSCRIBED`。这不算 bug，但会掩盖真正的泄漏，排查时以生产构建为准。

重连补状态时，别在回调里直接发请求。一次断线重连可能触发多个频道同时刷新，浏览器会并发出五六个 RSC 请求。用一个 300ms 的防抖，把这段时间的重连合并成一次刷新。

浏览器切到后台，连接可能被系统挂起。移动端表现更明显：切回来时连接还显示 `SUBSCRIBED`，实际已经收不到消息。处理办法是监听 `visibilitychange`，回到前台时先 `router.refresh()` 再检查频道状态，异常就重建。

## 28.6 断线之后，状态不会自己回来

Realtime 推的是事件，没有事件日志。断线期间发生的变更不会在重连后补发。

这是实现上最容易误判的一点。开发时网络好，看不出问题；用户在地铁里切一次网络，页面就停在旧数据上。

处理方式是重连时主动取一次。上面代码在第二次及以后的 `SUBSCRIBED` 里调 `router.refresh()`，把 RSC 数据重取一遍。

还有一种乱序要处理。两个窗口几乎同时改名，先发的事件后到，页面会停在旧名字。给数据加版本号或者比较 `updated_at`：

```ts
// src/lib/realtime/order.ts
export function isNewer(
  incoming: { updated_at: string },
  current: { updated_at: string } | null,
) {
  if (!current) return true;
  return new Date(incoming.updated_at) > new Date(current.updated_at);
}
```

两条记录时间戳完全相同时按 id 比较，选大的那个。时间戳精度到微秒时撞车概率低，但存在。

页面隐藏时可以退订，省一条连接配额：

```ts
// src/lib/use-page-visible.ts
"use client";

import { useEffect, useState } from "react";

export function usePageVisible() {
  const [visible, setVisible] = useState(true);

  useEffect(() => {
    const onChange = () => setVisible(document.visibilityState === "visible");
    onChange();
    document.addEventListener("visibilitychange", onChange);
    return () => document.removeEventListener("visibilitychange", onChange);
  }, []);

  return visible;
}
```

把它放进 effect 的依赖，隐藏时清理、可见时重建。代价是切回来要重新握手，两百毫秒左右。

## 28.7 Presence 与 Broadcast

在线名单用 Presence。状态由客户端上报，频道里所有人可见。

```tsx
// src/app/(app)/t/[slug]/settings/online-members.tsx
"use client";

import { useEffect, useState } from "react";
import { createClient } from "@/lib/supabase/client";

type Online = { userId: string; name: string };

export function OnlineMembers({
  teamId,
  userId,
  name,
}: {
  teamId: string;
  userId: string;
  name: string;
}) {
  const [online, setOnline] = useState<Online[]>([]);

  useEffect(() => {
    const supabase = createClient();
    const channel = supabase.channel(`team:${teamId}:presence`, {
      config: {
        private: true,
        presence: { key: userId },
      },
    });

    channel
      .on("presence", { event: "sync" }, () => {
        const state = channel.presenceState<{ name: string }>();
        setOnline(
          Object.entries(state).map(([key, metas]) => ({
            userId: key,
            name: metas[0]?.name ?? "未命名",
          })),
        );
      })
      .subscribe(async (status) => {
        if (status === "SUBSCRIBED") {
          await channel.track({ name });
        }
      });

    return () => {
      void channel.untrack();
      void supabase.removeChannel(channel);
    };
  }, [teamId, userId, name]);

  return (
    <ul>
      {online.map((item) => (
        <li key={item.userId}>{item.name}</li>
      ))}
    </ul>
  );
}
```

只监听 `sync`。`join` 和 `leave` 也提供增量回调，但两条路径维护同一份状态容易分叉。`sync` 每次都给出全量，直接覆盖最省心。

Presence 的离开有延迟。客户端正常关页面会发 `leave`，进程被杀或断网时只能靠服务端心跳超时，通常几十秒后才从名单消失。界面上的“在线”要当成近似值，不能用来做权限判断。

Presence 的成本比看上去高。每次状态变化会同步给频道里所有人，二十个人的频道里一个人掉线就是二十条消息。免费档限制 Presence 每秒 20 条消息、每个客户端每 30 秒最多 5 次调用、每个对象最多 10 个 key。别拿它做鼠标位置这类高频更新。

输入提示用 Broadcast。它不落库，也不做行级授权，一条消息扇出即可。

```tsx
// src/app/(app)/t/[slug]/settings/typing-indicator.tsx
"use client";

import { useEffect, useRef, useState } from "react";
import { createClient } from "@/lib/supabase/client";

export function TypingIndicator({ teamId, userId }: { teamId: string; userId: string }) {
  const [who, setWho] = useState<string | null>(null);
  const lastSent = useRef(0);

  useEffect(() => {
    const supabase = createClient();
    const channel = supabase.channel(`team:${teamId}:typing`);

    channel
      .on("broadcast", { event: "typing" }, ({ payload }) => {
        if (payload.userId === userId) return;
        setWho(payload.name as string);
      })
      .subscribe();

    return () => {
      void supabase.removeChannel(channel);
    };
  }, [teamId, userId]);

  async function notifyTyping(name: string) {
    const now = Date.now();
    if (now - lastSent.current < 2000) return;
    lastSent.current = now;

    const supabase = createClient();
    // 只发不收时用 httpSend，不占 WebSocket
    await supabase.channel(`team:${teamId}:typing`).httpSend({
      type: "broadcast",
      event: "typing",
      payload: { userId, name },
    });
  }

  return (
    <div>
      <input onChange={() => notifyTyping("你")} />
      {who ? <span>{who} 正在输入</span> : null}
    </div>
  );
}
```

三个边界。

Broadcast 默认不回显给发送者。需要在同一个页面看到自己发的消息时，频道配置加 `broadcast: { self: true }`。

`send()` 在频道未订阅时走 HTTP，订阅后走 WebSocket。服务端只发不收，用 `httpSend()` 更合适，它不占用本地连接。

数据库触发的广播依赖按天分区的 `realtime.messages`。当天分区由第一个客户端连接创建，没有连接时触发器插入失败，日志里出现 `WarnSendingBroadcastMessage`。要用这条路，得保证至少一个客户端常连着。

## 28.8 容量限额

免费档的限制很具体，超了会直接断连：

- 并发连接 200 个，超出报 `too_many_connections`。
- 每秒 100 条消息，超出报 `tenant_events`，当前连接被断开，supabase-js 在速率回落后自动重连。
- 每个连接 100 个频道，超出报 `too_many_channels`。
- 每秒 100 次频道加入，超出报 `too_many_joins`。
- Broadcast payload 上限 256KB，Postgres Changes payload 上限 1024KB。
- 每月 200 万条消息。

算一个真实的预算。一百人的团队，日活三十人，每人平均开两个标签页，峰值同时在线的比例按三成算：30 × 2 × 0.3 ≈ 18 个连接。加上移动端和后台页面，按两倍留余量，约 40 个连接。免费档的两百个连接能撑住。

每月消息量也要估。一条变更推给十个订阅者，计十条消息。按每天两千条变更、平均八个订阅者算，一个月约四十八万条，占免费档两百万额度的四分之一。这个比例超过一半时，就该考虑减少订阅范围或者换触发的 Broadcast。

订阅人数涨到两百人时，连接数会先到顶。升级路径有两条：升到 Pro 放宽连接数，或者把 Postgres Changes 换成数据库触发的 Broadcast，减少每连接的事件量。两条可以同时做。

连接数是硬上限，超了影响所有人，不只影响新来的。一个用户开五个标签页就有五个连接，二十个活跃用户能占满一百。做容量估算时按标签页数算，不按登录用户数算。

payload 超限时 Postgres Changes 的行为特殊：`new` 和 `old` 里只保留不超过 64 字节的字段，其余字段被丢掉。前端不能假设事件里一定有完整数据。

## 28.9 和轮询比

轮询也能实现，人数少、变化慢时更简单。

算一笔账。五个人的团队，每 5 秒轮询一次，每人每天开 8 小时，一天 5760 次请求，五个人 28800 次。这些请求大部分返回“没有变化”。换成 Realtime，连接保持，只在真有变更时推一两条消息。

但 Realtime 有自己的成本：每个连接占一个配额，断线要处理，移动端切后台会断。判断标准可以简化成三条：

- 变化频率低于每分钟一次，轮询够用。
- 同时在线超过 200 人，免费档不够，需要升配或改用数据库触发的 Broadcast。
- 数据错过一条会导致错误操作，任何推送方案都要加上重连后重取。

teamstack 的做法是混合：通知和团队名用 Realtime，列表页、分页、权限校验走普通请求。实时只负责让已经显示的数据变新，首屏数据仍然由服务端渲染给出。

部署形态不影响连接路径。WebSocket 从浏览器直连 Supabase，不经过 Next.js 服务端，所以应用部署在 Vercel 的函数里也能用。反过来，函数不持有连接，进程重启不会打断订阅。

还有一种替代方案是 SSE。单向推送、协议简单，服务端一个 HTTP 流就能推到浏览器。但它要求服务端进程常驻，部署到无服务器的函数后没法维持长连接。teamstack 的服务端在函数里，所以用 Supabase 提供的 WebSocket。

前置代理要放行 WebSocket。Cloudflare 默认支持 `wss://`，但自建的 nginx 需要显式配置 `proxy_set_header Upgrade $http_upgrade;` 和 `proxy_set_header Connection "upgrade";`，否则握手返回 400。

## 28.10 从数据库直接发广播

订阅者超过几千个时，Postgres Changes 的逐订阅者授权成为瓶颈。这条路改成一次写库、一次扇出：触发器里调 `realtime.broadcast_changes()`，把变更作为 Broadcast 发到频道。

```sql
-- supabase/migrations/20261124090000_realtime.sql（继续）
create or replace function public.broadcast_activity()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
  perform realtime.broadcast_changes(
    'team:' || new.team_id::text || ':activity',  -- 频道 topic
    tg_op,                                        -- 事件名
    tg_op,                                        -- 操作类型
    tg_table_name,
    tg_table_schema,
    new,
    old
  );
  return null;
end;
$$;

create trigger activity_broadcast
after insert on public.activity_logs
for each row execute function public.broadcast_activity();
```

函数必须 `security definer`，因为调用 `realtime` schema 下的函数需要更高权限。策略仍然生效：客户端要能订阅这个私有频道，`realtime.messages` 的读策略必须放行。

客户端换成监听 Broadcast，不再声明 `postgres_changes`：

```ts
// src/lib/realtime/activity.ts
supabase
  .channel(`team:${teamId}:activity`, { config: { private: true } })
  .on("broadcast", { event: "INSERT" }, ({ payload }) => {
    console.log("新活动", payload);
  })
  .subscribe();
```

这条路的代价是授权前移。触发器不知道谁该收到，扇出由 Realtime 按频道完成，细粒度过滤要在客户端做。数据敏感时不要用。

它适合的场景很窄：扇形广播、订阅者多、内容不敏感。团队动态流、在线协作的光标、看板上的状态灯属于这类。带权限的行数据仍然走 Postgres Changes，两种方式可以在同一个应用里共存。

**未验证**：`broadcast_changes` 推给客户端的 payload 具体字段以实际抓包为准，本节按官方函数签名书写，本机没有起 3000 订阅者做对照测试。

## 28.12 常见错误

1. `42501 must be owner of table messages`

执行了 `alter table realtime.messages enable row level security`。这张表已经开了行级安全，直接加 policy 即可，不要改表属性。

2. `permission denied for schema realtime`

在 `realtime` schema 里建表或建函数。这个 schema 归 Realtime 服务所有，策略里的 `realtime.topic()` 可以直接用，额外对象只能建在 `public`。

3. 订阅返回 `SUBSCRIBED`，但收不到任何事件

三种原因按顺序查：表没进 publication；当前用户被 RLS 挡掉；`filter` 的语法不对。用 `set local role authenticated;` 加 `set local request.jwt.claims = '{"sub":"<uuid>"}';` 在 psql 里模拟用户查一次，能查到的行才会推。

4. `too_many_channels`

清理时只清了定时器，没调 `removeChannel`。每个 effect 的 cleanup 里都要清理频道，开发环境下 React 会故意挂载两次，泄漏会立刻暴露。

5. `too_many_connections`

连接数按标签页累计。检查是否在多个组件里各自调用了 `createClient()` 并订阅，改为共享单例，并在页面隐藏时退订。

6. `tenant_events`，连接被断开

消息速率超过每秒 100 条。常见原因是 Presence 状态里放了高频变化的值，或者把每次按键都发成 Broadcast。加节流，Presence 只上报频率低的状态。

## 28.13 这一章在做什么

这一章把数据库的变更接到浏览器。三个模式各有边界：Postgres Changes 省事但按订阅者授权，Broadcast 轻便但要自己保证内容正确，Presence 只表达“谁在”。

四条结论可以直接复用：

- 表要进 publication，否则订阅成功但零事件。
- 订阅有生命周期，卸载必须 `removeChannel`。
- 事件不补发，重连后自己重取一次。
- 限额按连接算，标签页会叠加。

下一章讲通知与搜索。通知的写入由触发器完成，角标靠本章的订阅机制更新；搜索把数据查询从 `LIKE` 换到 `tsvector`，是另一条完全不同的路径。

判断一个功能要不要实时，问一句：这条数据晚十秒到，用户会不会做错事？不会，就用普通请求。会，才值得付出连接和重连的复杂度。

实时属于体验层，正确性靠普通请求保证。所有依赖它的地方都要有退路。

**未验证**：连接数、消息速率、payload 上限引自 Supabase 官方 Realtime limits 页面（免费档）。本机没有做 500、1500、3000 连接的压测，那组数字来自官方扩展性说明。具体数值随版本变化，上线前以控制台报错为准。
