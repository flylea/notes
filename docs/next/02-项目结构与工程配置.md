# 第 2 章 项目结构与工程配置

这一章讲两件事：Next.js 如何把文件夹变成 URL，以及一个新项目在写功能之前必须配好的几项工程设置。

路由规则由文件系统决定，不需要注册路由表。工程设置包括 TypeScript 严格模式、路径别名、ESLint、Tailwind 和构建脚本。这两部分都在写业务代码之前定下来，改起来牵连面大。

涉及的概念有六个：路由段、约定文件、路由组、私有目录、路径别名、构建输出符号。前四个决定文件放在哪，后两个决定代码怎么写、怎么验证。

先给结论：一个文件夹要变成可访问的 URL，只需要一个 `page.tsx`；不想让它变成 URL，用括号或下划线。其余规则都从这两条推出来。

## 2.1 路由段与 page.tsx

`app/` 目录下的每个文件夹都是一个路由段（segment），嵌套关系就是 URL 的嵌套关系。

```text
app/
├── page.tsx                    → /
├── dashboard/
│   ├── page.tsx                → /dashboard
│   └── settings/
│       └── page.tsx            → /dashboard/settings
└── teams/
    └── [slug]/
        └── page.tsx            → /teams/acme、/teams/other
```

三条规则决定了这套映射。

第一，文件夹本身不产生路由。`app/dashboard/` 这个文件夹存在，`/dashboard` 不存在；只有放进去 `page.tsx`，这个路径才可访问。

第二，`page.tsx` 是页面入口，文件名固定，大小写敏感。写成 `Page.tsx`、`index.tsx`、`page.ts`，都不会被当成页面。

第三，同一个段里 `page.tsx` 和 `route.ts` 只能留一个。前者返回 HTML，后者返回 HTTP 响应，两个都放会构建失败。

```tsx
// src/app/dashboard/page.tsx
export default function DashboardPage() {
  return <h1>仪表盘</h1>;
}
```

同一位置也可以放一个接口：

```ts
// src/app/api/health/route.ts
export async function GET() {
  return Response.json({ ok: true });
}
```

`route.ts` 导出的函数名就是 HTTP 方法：`GET`、`POST`、`PUT`、`PATCH`、`DELETE`。`GET` 对应读取，`POST` 对应写入。这些都放在 `app/api/` 下面，地址由目录决定，不写额外的路由映射。

接口不返回 HTML，也不参与预渲染。构建路由表里它总是 `ƒ`。

规则之外还有一个性质：`app/` 里可以放别的文件，只有 `page.tsx` 和 `route.ts` 的输出会进入响应。组件、工具函数、类型、测试文件都可以和页面放在同一个目录，这叫 colocation。

```text
app/dashboard/
├── page.tsx
├── _components/          # 不在 URL 里
│   └── stat-card.tsx
└── queries.ts            # 不在 URL 里
```

放在 `app/` 里的组件文件不会暴露成 URL，`queries.ts` 也不会。所以不需要为了隐藏文件而把它挪到 `app/` 外面，放在页面旁边反而更容易找到。

### 2.1.1 动态段

方括号目录表示这一段的值不固定：

```text
src/app/teams/[slug]/page.tsx        → /teams/acme
src/app/files/[...path]/page.tsx     → /files/a/b/c
src/app/docs/[[...slug]]/page.tsx    → /docs、/docs/a/b
```

`[slug]` 匹配一段，`[...path]` 匹配一段或多段，`[[...slug]]` 也匹配零段。文件名两侧的方括号只是语法标记，和正则无关。

页面的 `params` 参数在 Next.js 16 里是 Promise，要 `await`：

```tsx
// src/app/teams/[slug]/page.tsx
import { notFound } from "next/navigation";
import { getTeamBySlug } from "@/lib/teams";

export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const team = await getTeamBySlug(slug);

  if (team === null) {
    notFound();
  }

  return <h1>{team.name}</h1>;
}
```

写成 `params.slug` 直接取，构建期不报错，运行时会得到 `undefined`。这是 16 版最常撞的一处。

也可以让 Next.js 生成类型：

```tsx
// src/app/teams/[slug]/page.tsx（另一种写法）
export default async function TeamPage({ params }: PageProps<"/teams/[slug]">) {
  const { slug } = await params;
}
```

`PageProps` 由 Next.js 写入 `.next/types` 并在下次构建或启动时可用。

多个文件匹配同一个地址时，优先级固定：静态段优先于动态段，动态段优先于捕获全部段。

```text
src/app/teams/new/page.tsx       → /teams/new（优先）
src/app/teams/[slug]/page.tsx    → /teams/acme
src/app/teams/[...rest]/page.tsx → /teams/a/b（最后）
```

因此 `new` 这类保留字不会被 `[slug]` 抢走。代价是团队 slug 不能叫 `new`，否则永远进不去详情页；团队创建表单要拦掉这个值。

### 2.1.2 可选捕获段

`[[...slug]]` 的意思是“这一段可以没有，也可以有好几层”。用它就能让父路径本身也成为页面，而不是 404：

```text
src/app/docs/[[...slug]]/page.tsx
  → /docs
  → /docs/install
  → /docs/install/docker
```

典型用途是文档站的同一套布局切换分区。`/docs` 显示概览，`/docs/install` 显示安装，两者共用一个侧边栏布局，地址里不多一层。

代价是 `slug` 在父路径下是 `undefined`，代码必须处理这一种情况：

```tsx
// src/app/docs/[[...slug]]/page.tsx
export default async function DocsPage({ params }: { params: Promise<{ slug?: string[] }> }) {
  const { slug } = await params;
  const path = slug?.join("/") ?? "index";
  const doc = await getDoc(path);

  if (doc === null) {
    notFound();
  }

  return <DocView doc={doc} />;
}
```

不写 `?? "index"` 这一步，访问 `/docs` 时就会把一个 `undefined` 拼进查询条件，页面报错。这是可选捕获段最常漏的一行。

同一层不要再放 `[...slug]`，两个目录都能匹配多段路径，会撞在一起。用哪个取决于父路径要不要独立成页：要，就用可选的；不要，就用普通的捕获段。

## 2.2 约定文件与嵌套顺序

一个路由段里能放的文件是固定的，名字固定，作用固定。

| 文件 | 作用 | 是否必须 |
| --- | --- | --- |
| `layout.tsx` | 包住本级和下级页面，导航时不重新挂载 | 根布局必须 |
| `page.tsx` | 页面本体，让目录成为 URL | 是 |
| `loading.tsx` | 加载态，自动给子内容包一层 Suspense | 否 |
| `error.tsx` | 错误边界，必须是客户端组件 | 否 |
| `not-found.tsx` | 该段的 404 界面 | 否 |
| `template.tsx` | 类似 layout，每次导航重新挂载 | 否 |
| `route.ts` | HTTP 接口，不能与 page 同段 | 否 |
| `default.tsx` | 并行路由槽位的兜底 | 并行路由用 |

这些文件按固定顺序包裹页面：

```text
layout.tsx
└── template.tsx
    └── error.tsx
        └── loading.tsx
            └── not-found.tsx
                └── page.tsx
```

记这个顺序有实际用处。`error.tsx` 在 `loading.tsx` 外面，所以加载过程抛错能被它接住；`not-found.tsx` 在 `page.tsx` 外面，所以页面里调 `notFound()` 会渲染它。第 6 章逐层展开。

根布局是唯一必须手写的：

```tsx
// src/app/layout.tsx
import type { Metadata } from "next";
import { Geist } from "next/font/google";
import "./globals.css";

const geist = Geist({ subsets: ["latin"], variable: "--font-geist" });

export const metadata: Metadata = {
  title: "teamstack",
  description: "多租户团队管理后台",
};

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN" className={geist.variable}>
      <body>{children}</body>
    </html>
  );
}
```

`<html>` 和 `<body>` 只在这个文件里出现。子布局只写自己的包裹结构：

```tsx
// src/app/(app)/layout.tsx
import { Sidebar } from "@/components/sidebar";

export default function AppLayout({ children }: { children: React.ReactNode }) {
  return (
    <div className="flex min-h-screen">
      <Sidebar />
      <main className="flex-1 p-6">{children}</main>
    </div>
  );
}
```

子布局嵌套在根布局内部。访问 `/dashboard` 时，实际渲染的是根布局 → 应用布局 → 页面。导航到 `/teams` 时，两个布局都不重新挂载，只有页面部分被替换。侧边栏的滚动位置、展开状态因此能保留。

布局拿得到 `params`，拿不到 `searchParams`。原因是布局会在多个页面之间复用，而 `searchParams` 每个页面不同。需要读查询参数时，在 `page.tsx` 里读。

```tsx
// src/app/(app)/teams/[slug]/layout.tsx
export default async function TeamLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  return (
    <section data-team={slug}>
      <TeamTabs slug={slug} />
      {children}
    </section>
  );
}
```

布局里读 `params` 会把整个子树变成按请求渲染。确实需要按团队切换外壳时才这么做，否则把这段取数放到页面里。

## 2.3 路由组与私有目录

有些需求跟 URL 无关：营销页和管理后台用不同的布局，但都不想在地址里多一层 `/marketing`。

用括号目录解决：

```text
src/app/
├── (marketing)/
│   ├── layout.tsx
│   ├── page.tsx              → /
│   └── pricing/
│       └── page.tsx          → /pricing
├── (app)/
│   ├── layout.tsx
│   ├── dashboard/
│   │   └── page.tsx          → /dashboard
│   └── teams/
│       └── page.tsx          → /teams
└── layout.tsx                根布局
```

括号里的名字不进入 URL。`(marketing)/pricing` 的地址是 `/pricing`，`(app)/dashboard` 的地址是 `/dashboard`。两组各自有自己的 `layout.tsx`，切换时只替换页面和对应布局。

路由组还有一个用途：让不同分组用完全不同的根布局。删掉 `app/layout.tsx`，在每个组里各写一个带 `<html>` 的布局即可。

```tsx
// src/app/(marketing)/layout.tsx
export default function MarketingLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN">
      <body className="bg-white">{children}</body>
    </html>
  );
}
```

代价是全局样式、字体、脚本要在每个根布局里各配一遍。只有两组页面的外壳差异很大时才值得这么做。

两个组的路径撞车会直接构建失败。`(marketing)/about` 和 `(app)/about` 都解析到 `/about`，报错文字是 `You cannot have two parallel pages that resolve to the same path`。加组的时候留一份路径清单能少踩一次。

私有目录用下划线前缀，作用是从路由系统里排除：

```text
src/app/_components/button.tsx      # 不会成为路由
src/app/dashboard/_charts/line.tsx  # 也不会
```

私有目录可以不加。colocation 已经保证组件文件不会变成 URL，加下划线的作用是让“这是内部实现”在目录树里看得见，同时避开未来的约定文件名。`_components`、`_lib` 这类名字还提示别人不要从外面 import。

如果想保留一个真的以 `_` 开头的 URL 段，用 URL 编码 `%5F` 当文件夹名。

## 2.4 TypeScript 严格模式与路径别名

`create-next-app` 生成的 `tsconfig.json` 已经够用：

```json
{
  "compilerOptions": {
    "target": "ES2017",
    "lib": ["dom", "dom.iterable", "esnext"],
    "allowJs": true,
    "skipLibCheck": true,
    "strict": true,
    "noEmit": true,
    "esModuleInterop": true,
    "module": "esnext",
    "moduleResolution": "bundler",
    "resolveJsonModule": true,
    "isolatedModules": true,
    "jsx": "preserve",
    "incremental": true,
    "plugins": [{ "name": "next" }],
    "paths": { "@/*": ["./src/*"] }
  },
  "include": ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts", ".next/dev/types/**/*.ts"],
  "exclude": ["node_modules"]
}
```

三个关键项。

`strict: true` 打开全部严格检查。关掉它，`undefined` 会在运行时才暴露，代价是一堆本可以在编辑器里发现的错误。不要为了消几个红线去关。

`paths` 定义别名。`@/lib/env` 指向 `src/lib/env.ts`。项目一变大，相对路径 `../../../lib/env` 就很难读。别名只影响编译和打包，Node 直接跑脚本时读不到，单独跑测试要再配一次。

`include` 里的 `.next/types` 和 `.next/dev/types` 是 Next.js 生成的路由类型。删掉这两行，`PageProps` 一类类型会失效。

`strict` 是一组开关的合集。团队里可以在此基础上再加两个：

```json
{
  "compilerOptions": {
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true
  }
}
```

`noUncheckedIndexedAccess` 让数组下标取值返回 `T | undefined`，能挡住一类越界访问。代价是老代码会冒出一些红线，适合新项目一开始就开。

`verbatimModuleSyntax` 不要随手打开。它要求类型导入写成 `import type`，和 Next.js 的部分生成文件一起用会多出一堆无意义的改动。

`jsx: "preserve"` 也不要改。它保证 TSX 原样交给 Turbopack 处理，类型检查只负责类型。改成 `react-jsx` 会让两边的转换规则打架，报错通常出现在构建后期。

`isolatedModules: true` 要求每个文件的导出自洽，因为打包器逐个文件转译，没有全局类型信息。它带来的实际约束是把类型再导出时必须用 `export type`。

```ts
// src/lib/teams.ts（片段）
export type { Team } from "./types";
```

写成 `export { Team }` 在开启 `isolatedModules` 时会报错，因为运行时那个名字不存在。

还有一种情况：装类型包时用 `devDependencies`，不要装进 `dependencies`。`@types/react` 这类包只在构建时用，进了运行依赖只会增加安装体积。

`next-env.d.ts` 由 Next.js 生成和维护，不要手改。它应当出现在 `.gitignore` 里，但磁盘上必须有文件，因为 `tsconfig.json` 的 `include` 引用了它。`pnpm install` 之后第一次 `pnpm dev` 会重新生成。

改了 `paths` 要重启开发服务器。Turbopack 的模块解析缓存不会自动感知 `tsconfig.json` 的变化。

还有一个可选开关 `typedRoutes`。开启后，`<Link href>` 和 `router.push` 的参数会被校验成真实存在的路由：

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  typedRoutes: true,
};

export default nextConfig;
```

开启之后，非字面量的地址要显式断言类型，写法会变啰嗦：

```tsx
// src/components/nav-item.tsx
import type { Route } from "next";
import Link from "next/link";

export function NavItem({ href, label }: { href: string; label: string }) {
  return <Link href={href as Route}>{label}</Link>;
}
```

中小项目可以先不开，路由多了再打开。

## 2.5 ESLint 的 flat config

Next.js 16 移除了 `next lint` 子命令。继续用旧命令会得到一条奇怪的报错：

```text
Invalid project directory provided, no such directory: /path/to/project/lint
```

它把 `lint` 当成了目录名去匹配路由。解法是不再用这个命令，改为直接跑 ESLint。

项目根目录的配置是一个 `eslint.config.mjs`，采用 flat config 格式：

```js
// eslint.config.mjs
import { defineConfig, globalIgnores } from "eslint/config";
import nextVitals from "eslint-config-next/core-web-vitals";
import nextTs from "eslint-config-next/typescript";

const eslintConfig = defineConfig([
  ...nextVitals,
  ...nextTs,
  globalIgnores([".next/**", "out/**", "build/**", "next-env.d.ts"]),
]);

export default eslintConfig;
```

`package.json` 里的脚本改成直接调用 ESLint：

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "eslint"
  }
}
```

运行 `pnpm lint` 会扫描整个项目。需要只检查改动过的文件，加参数即可：`pnpm lint src/app`。

`eslint-config-next` 需要 ESLint 9 或 10。ESLint 10 要求 Node.js `^20.19`、`^22.13` 或 `>=24`。版本对不上时，报错出现在加载配置阶段，和规则无关。

16 起 `next build` 不再自动跑 ESLint 和类型检查之外的 linter。构建通过不代表 lint 通过，CI 里要把两个命令分开跑。

第三条配置 `nextTs` 是可选的。只用 `core-web-vitals` 时，TypeScript 相关的规则不生效，`any` 也不会被提示。团队决定是否引入。

规则冲突时按行关闭，避免全文件关闭：

```tsx
// src/app/(app)/teams/team-row.tsx
// eslint-disable-next-line @next/next/no-img-element
<img src={team.avatarUrl} alt={team.name} />
```

全文件关闭用 `/* eslint-disable */` 写在文件第一行。适合从旧项目搬过来的文件，后面再逐步清理。

编辑器里装的 ESLint 插件和 `pnpm lint` 用的是同一份配置，报错应当一致。编辑器不报错而 CI 报错，先检查插件有没有读到项目根目录，再去动规则。

## 2.6 Tailwind 4 的配置模型

Tailwind 4 和 3 的配置方式完全不同。3 的核心是一个 `tailwind.config.ts`，4 把它换成了 CSS 里的 `@theme`。

所以第一步要接受一件事：Tailwind 4 项目里没有 `tailwind.config.ts`。从旧项目拷一份过来，不会生效。

安装与接入：

```bash
pnpm add -D tailwindcss @tailwindcss/postcss
```

```js
// postcss.config.mjs
const config = {
  plugins: {
    "@tailwindcss/postcss": {},
  },
};

export default config;
```

样式入口改成一行导入：

```css
/* src/app/globals.css */
@import "tailwindcss";

@theme {
  --color-brand-50: oklch(0.97 0.02 250);
  --color-brand-500: oklch(0.62 0.18 250);
  --color-brand-900: oklch(0.32 0.12 250);
}
```

`@import "tailwindcss";` 导入全部基础样式和工具类。`@theme` 里定义的变量会同时生成 CSS 变量和对应的工具类，`--color-brand-500` 自动带来 `bg-brand-500`、`text-brand-500`、`border-brand-500`。

Tailwind 4 自动扫描项目文件，不需要配置 `content` 数组。扫描范围排除 `.gitignore` 里的目录和二进制文件。从 monorepo 外部引入样式时，用 `@source` 显式指定：

```css
/* src/app/globals.css（片段） */
@import "tailwindcss";
@source "../../../packages/ui/src";
```

要忽略某些目录，写 `@source not "../../legacy";`。

插件也移到 CSS 里声明：

```css
/* src/app/globals.css（片段） */
@plugin "@tailwindcss/typography";
```

自带变体不够用时，用 `@custom-variant` 定义：

```css
/* src/app/globals.css（片段） */
@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));
```

这样 `dark:bg-zinc-900` 会按 `data-theme` 属性生效，不再只看系统的颜色偏好。

旧写法在 4 里必须替换。下面三段指令已经废弃：

```css
/* 错误示范：Tailwind 3 的写法 */
@tailwind base;
@tailwind components;
@tailwind utilities;
```

换成这三行，`pnpm build` 依然成功，控制台没有任何警告，但生成的 CSS 会小一半以上，所有工具类丢失。实测同一份样式文件，4 的产物 14,581 字节，换成 3 的写法后 6,347 字节。

判断样式有没有真正生效，看构建产物的体积：

```bash
ls -l .next/static/chunks/*.css
```

工具类没生成时，这个文件会明显偏小。

`globals.css` 在根布局里导入一次：

```tsx
// src/app/layout.tsx（片段）
import "./globals.css";
```

组件级样式用 CSS Modules：文件名以 `.module.css` 结尾，导入后按对象取类名。

```css
/* src/app/(app)/dashboard/metrics.module.css */
.grid {
  display: grid;
  grid-template-columns: repeat(3, minmax(0, 1fr));
  gap: 1rem;
}
```

```tsx
// src/app/(app)/dashboard/page.tsx（片段）
import styles from "./metrics.module.css";

export default function Page() {
  return <div className={styles.grid}>{/* ... */}</div>;
}
```

全局样式在客户端导航时不会被移除，所以页面级样式不要写进 `globals.css`，否则离开页面后还在。样式顺序由 import 顺序决定，不要开启自动排序 import 的 lint 规则。

从 Tailwind 3 迁到 4 的改动集中在三处：删掉 `tailwind.config.ts`，把 `theme.extend` 搬进 CSS 的 `@theme`，把 `content` 数组删掉。插件从 JS 里的 `plugins: [...]` 改成 CSS 里的 `@plugin`。自定义变体从 `addVariant` 改成 `@custom-variant`。

搬 `theme` 时有一处易错：`@theme` 里的变量名要带命名空间，`--color-*`、`--spacing-*`、`--font-*` 才会生成对应的工具类。写成 `--brand-500` 只得到 CSS 变量，`bg-brand-500` 不存在。

## 2.7 dev 与 build 是两条流水线

`pnpm dev` 按需编译：启动时只做最少的准备，访问哪个路由才编译哪个。所以第一次打开某个页面会慢一两秒，之后走热更新。

```text
▲ Next.js 16.4.6 (Turbopack)
- Local:         http://localhost:3000
- Environments: .env.local

✓ Ready in 157ms
```

请求日志会拆开两个耗时：

```text
 GET /about 200 in 93ms (next.js: 42ms, application-code: 51ms)
```

`next.js` 是框架自身的开销，`application-code` 是组件执行的时间。页面慢的时候先看后一个数字，它大说明查询或渲染有问题。

开发模式默认开启 React Strict Mode。组件函数会执行两次，`useEffect` 的挂载和卸载也会各跑一遍，目的是提前暴露副作用写错的问题。日志里出现两次同样的输出，先确认有没有这个原因，别急着去查数据层。

开发模式的错误覆盖层也只在这里出现。页面抛错时浏览器里能看到红色堆栈和完整源码位置；构建之后的错误只留下错误边界界面和白屏，因为生产模式不把堆栈发到浏览器。线上排错要靠服务端日志和 `digest`，第 6 章展开。

`pnpm build` 是另一条路，一次把所有路由编译并预渲染：

```text
Creating an optimized production build ...
✓ Compiled successfully in 369ms
Running TypeScript ...
Finished TypeScript in 623ms ...
Collecting page data using 8 workers ...
Generating static pages using 8 workers (8/8) in 180ms
Finalizing page optimization ...
```

构建结束会打印路由表，每个路由前面有一个符号：

```text
┌ ○ /
├ ○ /about
├ ƒ /dashboard
└ ● /posts/[slug]
    ├ ● /posts/hello
    └ ● /posts/world

○  (Static)   prerendered as static content
●  (SSG)      prerendered as static HTML (uses generateStaticParams)
ƒ  (Dynamic)  server-rendered on demand
```

`○` 是构建时预渲染的静态页，`●` 是带 `generateStaticParams` 生成的动态路由，`ƒ` 是按请求渲染。这套符号只在 `next build` 出现，`next dev` 下看不到。第 3 章讲判定规则。

产物有两种部署形态，由 `next.config.ts` 的 `output` 决定。

```ts
// next.config.ts（片段）
const nextConfig: NextConfig = {
  output: "standalone",
};
```

配了 `standalone` 之后，`.next/standalone` 里会生成一份自带运行时依赖的产物，部署时只需要拷贝这个目录，不必带整个 `node_modules`。Docker 镜像从 1 GB 降到一两百兆，主要靠这一项。

不配 `output` 时用 `pnpm start` 启动，它读取 `.next` 里的标准产物，需要完整的 `node_modules`。

静态导出用 `output: "export"`，产出纯 HTML 和 JS，可以直接放到任意静态托管上。代价是服务端能力全部消失：没有 Server Action、没有 Route Handler、没有按请求渲染，`cookies()` 和 `headers()` 也不能用。teamstack 需要登录态，因此不使用这个模式。

构建分阶段执行，每个阶段的失败信息不一样：编译阶段报模块解析错误，类型检查阶段报 `error TSxxxx`，预渲染阶段报的是数据获取或渲染错误。定位问题时先看最后一行是哪个阶段。

`.next/` 目录的分工：

- `.next/dev` 放开发模式下的增量编译状态。
- `.next/types` 和 `.next/dev/types` 放生成的路由类型，被 `tsconfig.json` 引用。
- `.next/static/chunks` 放生产环境的 JS 和 CSS，文件名带内容哈希。
- `.next/server` 放服务端产物，包括预渲染的 HTML 和 RSC Payload。
- `.next/standalone` 只在配置了 `output: "standalone"` 时出现。

这个目录不要手改，出问题就整个删掉重建：

```bash
rm -rf .next
```

本书第 2 到第 13 章的 `next.config.ts` 都关闭 Cache Components：

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  cacheComponents: false,
};

export default nextConfig;
```

16.4 的 `create-next-app` 默认会写入 `cacheComponents: true` 和 `partialPrefetching: true`。这里手动关掉，是为了让前十二章的构建输出只有 `○`、`●`、`ƒ` 三种符号，判定规则更容易看清。第 14 章再打开，那时才会出现 `◐` 和缓存函数的写法。

## 2.8 teamstack 的目录基线

前面几节讲的是规则，这一节给出本书从头用到尾的目录结构。

```text
teamstack/
├── src/
│   ├── app/
│   │   ├── (marketing)/
│   │   │   ├── layout.tsx
│   │   │   ├── page.tsx
│   │   │   └── pricing/page.tsx
│   │   ├── (app)/
│   │   │   ├── layout.tsx
│   │   │   ├── dashboard/page.tsx
│   │   │   └── teams/
│   │   │       ├── page.tsx
│   │   │       └── [slug]/
│   │   │           ├── layout.tsx
│   │   │           ├── page.tsx
│   │   │           ├── loading.tsx
│   │   │           └── error.tsx
│   │   ├── api/
│   │   │   └── health/route.ts
│   │   ├── layout.tsx
│   │   └── globals.css
│   ├── components/
│   │   └── ui/
│   │       └── button.tsx
│   ├── lib/
│   │   ├── auth.ts
│   │   ├── teams.ts
│   │   └── supabase/
│   │       ├── server.ts
│   │       └── client.ts
│   └── proxy.ts
├── supabase/
│   └── migrations/
│       └── 2026xxxxxxxxxx_init.sql
├── public/
├── next.config.ts
├── tsconfig.json
├── eslint.config.mjs
├── postcss.config.mjs
└── package.json
```

这份结构对应四条约定。

路由层只做两件事：从 `src/lib` 取数，把数据交给组件。页面里不直接写 SQL，也不直接 new 客户端。

数据访问集中在 `src/lib`。`src/lib/teams.ts`、`src/lib/auth.ts`、`src/lib/supabase/` 是后续所有章节的公共依赖。理由有三条：同一个查询会被页面、布局、Server Action 复用；数据层可以单独测；将来换数据库只改这一层。

组件分两类。`src/components/ui/` 放与业务无关的基础组件，按钮、输入框、弹窗。带业务语义的组件放在路由段的 `_components/` 里，例如 `src/app/(app)/teams/_components/team-card.tsx`，它只服务这一组页面。

迁移文件放在 `supabase/migrations/`，文件名由命令生成：

```bash
supabase migration new init
```

命名规则是时间戳加下划线加描述，Next.js 不读这个目录，但部署脚本会按文件名顺序执行。

文件命名用 kebab-case，组件导出用 PascalCase。`team-card.tsx` 导出 `TeamCard`。这条约定能避免 macOS 上文件系统不区分大小写带来的问题：本地 `TeamCard.tsx` 改成 `teamcard.tsx` 不会报错，推到 Linux 服务器上构建就找不到文件。

`public/` 存原样提供的静态文件：`public/logo.svg` 对应 `/logo.svg`。文件名直接成为 URL，所以不能带内容哈希，也不该放会被组件导入的资源。组件里用的图标走 import，让打包器处理哈希和 tree-shaking。

`src/proxy.ts` 是请求拦截入口。16 版把文件名从 `middleware.ts` 改成 `proxy.ts`，位置在 `src/` 下。`instrumentation.ts` 放服务启动时执行的代码，通常用来校验环境变量，第 7 章写这个文件。两者都和路由无关，不参与 URL 映射。

## 2.9 边界与失败模式

删掉页面后类型报错不消失。 删除 `src/app/foo/page.tsx` 之后，`.next/dev/types/validator.ts` 里还留着对它的引用，构建报：

```text
.next/dev/types/validator.ts(82,39): error TS2307: Cannot find module '../../../src/app/foo/page.js' or its corresponding type declarations.
```

原因是生成的路由类型没有跟着更新。执行 `rm -rf .next` 再重新构建即可。

文件名大小写在本地不敏感。 macOS 默认的文件系统不区分大小写，Linux 区分。开发机上是 `page.tsx`，部署后引用成 `Page.tsx`，构建时报 `Module not found`。CI 必须在 Linux 上跑一次构建，这条错误才会提前暴露。

webpack 配置静默失效。 Next.js 16 起 `next dev` 和 `next build` 都默认使用 Turbopack。`next.config.ts` 里写的 `webpack(config)` 函数只有在加 `--webpack` 参数时才被调用，平时不会执行，也不会报错。

```ts
// next.config.ts（在 Turbopack 下不会被调用）
const nextConfig = {
  webpack: (config) => {
    config.resolve.alias["@legacy"] = "/legacy";
    return config;
  },
};
```

需要沿用 webpack 配置时，命令改成 `next dev --webpack` 或 `next build --webpack`。长期方案是把自定义 loader 换成 Turbopack 支持的写法。

`next.config.ts` 不能写顶层 `await`。 配置文件按 CommonJS 解析。需要 ESM 语义时，把文件名改成 `next.config.mts`。

`pnpm start` 之前必须 `pnpm build`。 `next start` 读的是 `.next` 目录里的生产产物，没有构建产物时启动失败。改完代码忘了构建，看到的还是上一次的结果。

**端口被占用。** 3000 被别的进程占着时，`next dev` 报 `EADDRINUSE`。换端口：`pnpm dev --port 3001`。

文件监听在挂载卷上不可靠。 Docker Desktop 和虚拟机的共享目录层会延迟或丢失文件事件，表现为改了代码页面不刷新。项目要放在容器自己的文件系统里。Windows 下用 WSL2 的 Linux 文件系统，或者 Dev Drive。

`watchOptions.pollIntervalMs` 是最后手段：用轮询换可靠性，代价是 CPU。官方文档明确说多数情况不该用它。

Linux 下监听文件数有上限（`fs.inotify.max_user_watches`），大型 monorepo 可能触顶，表现为部分文件不触发重建。具体上限值随内核和发行版变化，本节未验证，需要时用 `cat /proc/sys/fs/inotify/max_user_watches` 查本机值。

多根布局会重复全局资源。 每个根布局都要自己导入 `globals.css`、字体、统计脚本。两组页面外壳差异不大时，用同一个根布局加路由组更省。

## 2.10 检查点

1. 运行 `pnpm build`，输出里能找到 `○`、`ƒ`、`●` 三种符号，并且末尾有图例。判据：至少有一个 `ƒ` 路由，对应读了 `cookies()` 的页面。
2. 新建 `src/app/(marketing)/about/page.tsx`，访问 `/about`。判据：页面能打开，地址里没有 `marketing`。
3. 在 `src/app/dashboard/` 下新建 `_components/card.tsx` 并被页面引用，访问 `/dashboard/_components/card`。判据：返回 404。
4. 把 `src/app/dashboard/page.tsx` 临时改名为 `Dashboard.tsx`，重新构建。判据：`/dashboard` 变成 404，构建路由表里消失。
5. 在页面里 `import { x } from "@/lib/nope"`，运行 `pnpm build`。判据：报 `Module not found: Can't resolve '@/lib/nope'`。
6. 运行 `pnpm lint`，再运行 `npx next lint`。判据：前者正常，后者报 `no such directory: .../lint`。
7. 删掉 `globals.css` 里的 `@import "tailwindcss";`，重新构建并访问页面。判据：布局全部失效，`.next/static/chunks` 下的 CSS 体积明显变小。

## 2.11 常见错误

1. 访问新目录得到 404

现象：创建了 `src/app/settings/`，放了一个 `Settings.tsx`，访问 `/settings` 是 404。
原因：文件名必须是 `page.tsx`，大小写敏感。
改法：改成 `src/app/settings/page.tsx`，默认导出组件。

2. 构建报 `You cannot have two parallel pages that resolve to the same path`

现象：`app/(marketing)/about/page.tsx` 和 `app/(app)/about/page.tsx` 同时存在。
原因：路由组不进 URL，两个文件解析到同一个 `/about`。
改法：删掉一个，或者把其中一个的路径改掉。

3. `Module not found: Can't resolve '@/lib/...'`

现象：编辑器里能跳转，`pnpm build` 报找不到模块。
原因：`tsconfig.json` 的 `paths` 改了但没重启开发服务器；路径大小写和磁盘上的文件不一致；文件放到了 `app/` 里却按 `@/lib` 引用。
改法：重启 `pnpm dev`；确认 `paths` 是 `"@/*": ["./src/*"]`；确认文件真的在 `src/lib` 下。

4. `Cannot find module '../../../src/app/xxx/page.js'`

现象：删了页面之后，构建在 `.next/dev/types/validator.ts` 上报错。
原因：生成的路由类型残留。
改法：`rm -rf .next`，重新构建。

5. 样式类名全部不生效，构建没有报错

现象：页面是裸 HTML，`bg-zinc-50` 之类的类名不起作用。
原因：`globals.css` 里还在用 Tailwind 3 的 `@tailwind` 指令，没有改成 `@import "tailwindcss";`；或者根布局没有导入 `globals.css`。
改法：换成一行导入，确认根布局导入了 `globals.css`，重新构建后检查 CSS 体积。

6. `webpack` 配置始终不执行

现象：在 `next.config.ts` 里加了自己的 loader 或 alias，`pnpm dev` 和 `pnpm build` 都没反应。
原因：16 起默认使用 Turbopack，`webpack` 字段被跳过。
改法：命令加 `--webpack`，或者改用 Turbopack 支持的配置方式。

## 2.12 这一章在做什么

这一章确定两件事：文件放在哪，工程怎么配。涉及的内容有：路由段与 `page.tsx` 的关系、动态段与优先级、约定文件的嵌套顺序、路由组和私有目录的差别、TypeScript 与 ESLint 的配置、Tailwind 4 的新模型、`dev` 与 `build` 两条流水线。最后给出 teamstack 的目录基线。

三条可以带走的判断：

- 一个目录有没有成为路由，看里面有没有 `page.tsx` 或 `route.ts`。
- 一个目录进不进 URL，看名字有没有括号；它是私有的，看有没有下划线。
- 一个页面是静态还是动态，看 `pnpm build` 路由表里的符号，不看代码里有没有 `await`。

下一章进入请求链路：一次点击从 DNS 到 RSC Payload 到水合，中间经过哪些步骤，哪些步骤会变慢。
