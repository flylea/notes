# 第 8 章 表、索引与约束

这一章建立本书的数据底座：九张表的结构、主键与外键怎么选、唯一约束怎么和软删除配合、索引的列顺序怎么定，最后落成一份可以重放的迁移文件。第 9 章到第 14 章的所有 SQL 都用这一章定下的表名与列名。

需要单独用一章讲表结构，原因有三层。表结构决定删掉一个团队时哪些行跟着消失，这属于产品语义，写错以后只能靠改数据补回来。唯一约束决定用户删掉团队后能不能用同一个名字重建，这里少写一个 `where`，正常操作会被长期挡住。索引决定一次列表请求要读多少行，十万行的表上，读几千个缓冲区和读二十行的差别就是用户等待的时间。

这一章涉及五个概念：主键选型、外键的删除动作、部分唯一索引与软删除、复合索引的列顺序、EXPLAIN 输出的读法。前两个决定数据怎么组织，中间两个决定数据怎么找，最后一个决定你怎么验证前四个做对了。

基线是 Postgres 15 以上，Supabase 本地默认如此。这一章没有 Next.js 代码，所有 SQL 都能在 `psql "$DATABASE_URL"` 里逐段执行。本机没有安装 Supabase CLI，凡是依赖 `supabase` 命令的输出都标了「未验证」，需要你在自己的环境跑一次确认。

## 8.1 主键：为什么整本书都用 uuid

主键是每一行的身份，它在建表那天定下来，之后改动的代价随数据量增长。默认写法是 `id uuid primary key default gen_random_uuid()`，随机生成，不由数据库排号。

选 uuid 的第一条理由来自外部约束：Supabase 的 `auth.users.id` 就是 uuid，`profiles.id` 必须与它一一对应。一半表用 bigint、一半表用 uuid，每次登录都要做一次映射，外键也没法直接连。

第二条理由是信息暴露。团队 id 会出现在接口参数、分享链接、邀请落点里。自增主键意味着 `/api/teams/17/files` 这串地址告诉对方你有十几个团队，改成 15、16 挨个试只是举手之劳。权限校验该做还得做，但攻击成本从猜一个 128 位随机数，降到改一个数字。

第三条理由是生成时机。`gen_random_uuid()` 可以在应用层、在表单提交前、在离线场景先生成，不需要先问数据库。第 12 章给邀请预生成 id 做幂等键，靠的就是这一点。

代价要一起看。uuid 占 16 字节，bigint 占 8 字节，差距落在三处。

| 方案 | 占字节 | 插入形状 | 主要问题 |
| --- | --- | --- | --- |
| `bigint generated always as identity` | 8 | 递增，写入集中在 B-tree 右端 | 可被枚举，暴露数据量 |
| `uuid` 加 `gen_random_uuid()`（v4） | 16 | 完全随机，写入分散 | 索引更大，随机 IO 多 |
| `uuid` 加 `uuidv7()`（Postgres 18 起） | 16 | 时间前缀递增 | 版本要求高，托管库未必有 |

第一处是索引体积。Postgres 的每一条二级索引都存一份主键值，主键从 8 字节涨到 16 字节，所有二级索引跟着变胖。`teams` 几千行时感觉不到，`activity_logs` 上百万行时，这个差值是实打实的磁盘与缓存占用。

第二处是写入形状。自增主键永远插在 B-tree 最右端，一页一页往后长，缓存命中好。uuid v4 随机插入，一页写满后下一次可能又落回前面某一页，触发页分裂，索引碎片变多。同一份数据，uuid 主键的表通常比 bigint 主键的表大百分之二三十，全表扫描时差值直接变成 IO。

第三处是排序语义。uuid 随机，`order by id` 等于把数据洗牌，读不出插入顺序。本书的时间线一律按 `created_at` 排，`id` 只当同秒数据的 tie-breaker。如果某张表需要「按 id 排序就是插入顺序」，那张表才应该用 bigint。

三个常见错答案要排掉。别用 `slug` 当主键：slug 会随团队改名而变，所有外键都要级联更新，它还承担唯一性与软删除，两套规则互相牵制。别用 `email` 当主键：邮箱会换，账号合并、企业接管、离职交接时人没变邮箱变了，所有引用都要改。别用 `serial`：它是 integer 加序列的语法糖，权限与所有权容易出问题，Postgres 10 之后统一写 `generated always as identity`。

`uuidv7()` 看起来更合适，时间前缀让写入有序，又能离线生成。它有两个边界。Supabase 托管的 Postgres 版本未必到 18，函数可能不存在；主键类型很难改，把已有的 uuid 表换成 uuidv7 要 `alter table` 改类型，所有外键与二级索引一起重建，表越大锁得越久。这个决定要在建表当天做对。

折中办法不换主键：保留 v4 主键，另加一列 `created_at` 并让它参与索引，索引按时间有序，主键只当身份。`activity_logs` 与 `files` 就是这么做的。

## 8.2 外键：删除动作是产品决定

外键声明两件事：子行的值必须存在于父表，以及父行消失时子行怎么办。后半句没有默认答案，九张表要逐条定。

| 外键 | 删除父行时 | 理由 |
| --- | --- | --- |
| `profiles.id` → `auth.users.id` | cascade | 用户注销，档案没有保留理由 |
| `team_members.team_id` → `teams.id` | cascade | 团队没了，成员关系是垃圾数据 |
| `team_members.user_id` → `profiles.id` | cascade | 用户没了，他在各团队的身份也没了 |
| `invitations.team_id` → `teams.id` | cascade | 团队没了，邀请链接必须失效 |
| `invitations.invited_by` → `profiles.id` | set null | 邀请记录要留，不能因个人离职删历史 |
| `activity_logs.team_id` → `teams.id` | cascade | 团队没了，日志没有归属 |
| `activity_logs.actor_id` → `profiles.id` | set null | 审计日志不能因删用户而消失 |
| `files.team_id` → `teams.id` | cascade | 记录跟着团队走，对象存储另说 |
| `subscriptions.team_id` → `teams.id` | cascade | 订阅与团队一对一 |
| `notifications.team_id` 与 `user_id` | cascade | 没人收的通知没有意义 |
| `jobs` | 不建外键 | 队列是独立系统，任务可能指向已删除的目标 |

`cascade` 在同一个事务里递归执行，团队删除与子行删除要么都成功，要么都不发生。它读起来省事，代价藏在性能里：父行一删，数据库要去每张子表找出全部引用行，子表没有索引就是全表扫描。一个团队攒了五十万条 `activity_logs`，`delete from teams` 会锁住这些行，跑几十秒，期间相关请求排队。

`set null` 用在审计类表。日志如果跟着用户 cascade，员工离职删号，他半年前删掉团队的全部记录一起消失，账查不了，当时发生了什么也说不清。把 `actor_id` 置空，行留下，责任人一栏显示为已注销账号。

`restrict` 用在「删之前必须有明确动作」的表。以后加发票表，团队欠着钱就不能删，写 `on delete restrict`，让数据库拒绝，不要指望应用层每次都记得先查。约束比自觉可靠。它拒绝时的输出：

```sql
delete from public.teams where slug = 'acme';
-- ERROR: update or delete on table "teams" violates foreign key constraint
--        "invoices_team_id_fkey" on table "invoices"
-- DETAIL: Key (id)=(a3f1c0de-...) is still referenced from table "invoices".
```

`jobs` 不建外键的理由不同。任务异步执行，跑的时候目标团队可能已被删。执行器要自己处理「目标不存在」并标成 `dead`。让数据库在插入任务时直接拒绝，代价是队列无法接受将来可能失败的工作。

外键列必须有索引，除非它已被某个复合索引的最左前缀覆盖。`team_members` 的主键是 `(team_id, user_id)`，`team_id` 在前，级联删除能直接定位；`invitations` 只有一个 `(team_id, lower(email))` 的部分索引，谓词是 `status = 'pending'`，删除团队时它匹配不全，只能全表扫。这类漏索引平时看不出来，因为查邀请都是按 token 查，直到某天删团队。

软删除把这个坑绕开了。团队删除写成 `update public.teams set deleted_at = now() where id = $1`，只动一行，一毫秒结束，清理交给后台任务。级联不触发，并发删除也不会死锁。代价是每条查询都要记得 `where deleted_at is null`，漏一条用户就会在列表里看到已删除的团队。

并发下的级联还有一个失败模式。两个管理员同时删同一个团队，第一个拿走团队行，第二个等待；第一个级联删子行时锁住 `team_members`，第二个此时已持有另一张子表的锁。两张表的加锁顺序相反时就死锁，Postgres 会杀掉其中一个，报 `deadlock detected`。处理方式在应用层串行，或者先 `select ... for update` 锁团队行，第 10 章展开。

## 8.3 唯一约束与软删除

唯一约束保证「这一列不重复」，但它管的是表里的全部行，包括已删除的。用户软删团队后用同名重建，会撞上一条已经删掉的记录：

```sql
insert into public.teams (name, slug) values ('Acme', 'acme');
update public.teams set deleted_at = now() where slug = 'acme';
insert into public.teams (name, slug) values ('Acme', 'acme');
-- ERROR: duplicate key value violates unique constraint "teams_slug_key"
-- DETAIL: Key (slug)=(acme) already exists.
```

业务要的语义是「在所有活着的团队里唯一」，全局唯一会把重建挡在门外。对应的结构叫部分唯一索引，谓词写清「哪些行算数」：

```sql
alter table public.teams drop constraint teams_slug_key;

create unique index teams_slug_active_uniq
  on public.teams (slug)
  where deleted_at is null;
```

索引用上谓词以后，软删的行自动退出唯一性判断，同一个 slug 可以反复创建、软删、再创建。这条索引必须在迁移里定义，不能指望建完普通约束再拆，两种东西的依赖关系不同。

新规则带来一个易错点：`on conflict` 必须把 `where` 一起写上。

```sql
insert into public.teams (name, slug) values ('Acme', 'acme')
on conflict (slug) where deleted_at is null do nothing;
```

漏掉谓词的报错：

```
ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification
```

这条报错不指出少了什么，第一次遇到很难判断。记法是：`on conflict` 的目标是哪个索引，就要把那个索引的列和谓词原样抄过去。

团队显示名同理。多数产品不允许两个同名团队，否则成员在列表里分不清。用表达式索引把大小写拍平：

```sql
create unique index teams_name_active_uniq
  on public.teams (lower(name))
  where deleted_at is null;
```

表达式索引要求查询也写同样的表达式，`where lower(name) = lower($1)` 才命中；`on conflict (lower(name))` 也必须原样写表达式，写成 `on conflict (name)` 会报找不到匹配约束。

邮箱要拆成两件事。`profiles.email` 终身唯一且不做软删：用户注销就硬删，`auth.users` 删掉，`profiles` 跟着 cascade。账号体系里同一个邮箱两个档案，登录、找回密码、订阅全部无法推理，这里用普通 `unique`。

`invitations` 是另一回事。同一个邮箱可以被同一个团队反复邀请：第一次过期，第二次撤销，第三次接受。要防的只是「同一个团队同时有两封 pending 邀请给同一个人」：

```sql
create unique index invitations_pending_email_uniq
  on public.invitations (team_id, lower(email))
  where status = 'pending';
```

状态改成 `revoked` 或 `accepted`，行就从索引里消失，重新邀请立刻成功。

约束与索引在用法上还有一处区别。唯一约束可以被外键引用，也能 `drop constraint`；唯一索引不能被 `references` 指向，但可以带谓词和表达式。slug、name、邀请邮箱都没有被别的表引用，所以用部分唯一索引没问题。将来某列需要被外键引用时，只能建成约束，这个判断看的是依赖方，与写法无关。

软删除还必须提前决定恢复逻辑。团队软删后 slug 从索引里退出，别人可以注册同名。几天后原主人找回来，直接 `update ... set deleted_at = null` 会撞：

```
ERROR: duplicate key value violates unique constraint "teams_slug_active_uniq"
```

数据库没有错，缺的是产品规则。三条路可选：恢复时检查 slug，被占就要求改名；自动加后缀 `acme-2`；永不释放旧 slug（另建 `reserved_slugs` 表）。本书选第一条，恢复前先查：

```sql
select id, name, deleted_at is null as active
from public.teams
where slug = $1 or lower(name) = lower($2);
```

slug 和显示名都要查，两个都空着才放行。原因在于 `teams_name_active_uniq` 也会拦人：显示名被占用时，报错里是 `Key (lower(name))=(acme) already exists`。这类「多一个唯一索引就多一条恢复路径」的问题，在软删系统里会反复出现。先查再改必须放在同一个事务里，否则两个并发恢复会同时通过检查，第 10 章处理这个窗口。

## 8.4 索引：列顺序决定用途

索引是额外维护的有序结构。B-tree 像一本按多个字段排好的花名册：先按 `team_id` 排，同一个团队内部再按时间倒序。查询 `where team_id = $1 order by created_at desc` 正好是「跳到某个团队的区段，从区段头部取 20 行」，取完就停，不需要额外排序。

```sql
create index activity_logs_team_created_idx
  on public.activity_logs (team_id, created_at desc, id desc);
```

列顺序反过来写成 `(created_at, team_id)` 会失效。索引先按时间排，`team_id` 的过滤只能在时间序列里挑行，数据库要么扫完整个索引，要么退回顺序扫描加排序。同样的两列，顺序换一下就变成两个用途。

末尾的 `id desc` 是给分页准备的 tie-breaker。`created_at` 会重复，批量上传常常落在同一秒，只按时间排序时第 2 页会重复第 1 页的最后一条。第 13 章讲游标时，这个 `id` 是主键之外的第二坐标。

九张表需要的索引，每一行都能对应一句查询：

```sql
-- supabase/migrations/20261115090000_init_schema.sql（索引段，与建表在同一文件）

-- 我在哪些团队
create index team_members_user_idx on public.team_members (user_id);

-- 团队活动流
create index activity_logs_team_created_idx
  on public.activity_logs (team_id, created_at desc, id desc);

-- 文件列表
create index files_team_status_created_idx
  on public.files (team_id, status, created_at desc, id desc);

-- 队列取任务
create index jobs_pick_idx on public.jobs (status, run_at) where status = 'queued';

-- 未读通知
create index notifications_unread_idx
  on public.notifications (user_id, created_at desc)
  where read_at is null;
```

`team_members` 的主键 `(team_id, user_id)` 已按 `team_id` 排好，查「这个团队有哪些人」不用额外索引；查「我在哪些团队」用 `user_id`，它在主键第二位，吃不到最左前缀，所以单独建。

`jobs_pick_idx` 是部分索引。完成的任务越积越多，索引若收录全部行，每次取任务都要跳过几百万条已完成记录。加上 `where status = 'queued'`，索引里通常只有几十条，取任务接近常数时间。队列表的索引形状与数据分布绑定，清理策略变了要回来看它。

覆盖索引用 `include`。查询只要索引里已有的列时，Postgres 可以走 Index Only Scan，不回表：

```sql
create index teams_list_cover_idx on public.team_members (user_id) include (team_id);
```

`include` 的列只随行带着，不参与排序，所以它省回表，不省排序，两者不能互相替代。也不要滥用。每个索引都是写入成本：一条 `insert into activity_logs` 不只写一行，还要更新这张表上的每个索引。测过的表上，每多一个索引，批量导入耗时大约涨百分之十。

几种让索引直接失效的写法，代码评审看见就改：

```sql
-- 函数包住索引列，建在 created_at 上的索引用不上
where created_at::date = '2026-11-15'
-- 改成半开区间才对得上索引
where created_at >= '2026-11-15' and created_at < '2026-11-16'

-- 前导通配符，B-tree 只能从左往右找
where name like '%invoice%'

-- 类型不匹配，team_id 是 uuid，这里传了 text
where team_id = 'a3f1c0de-...'
```

第三种最难发现。参数类型不对时 Postgres 会隐式转换，索引用不上，查询结果却完全正确，测试永远报绿。只能看 `explain` 里的 `Filter`。

还有两条列顺序规则。排序方向要和索引一致：`order by created_at desc, id desc` 对应索引的 `desc, desc`，两列方向混写，B-tree 的区间扫描就服务不了，只能排序。范围条件后面的列用不上索引：`where team_id = $1 and created_at > $2 and action = 'file.upload'` 走到 `created_at >` 就进入区间扫描，后面的 `action` 只能回表过滤。列顺序按「等值、范围、排序」排，不按字段的重要性排。

## 8.5 写成迁移文件

结构定好以后写进迁移文件。文件名别手敲，用 CLI 生成，它会带时间戳：

```bash
supabase migration new init_schema
# 生成 supabase/migrations/20261115090000_init_schema.sql
```

时间戳前缀决定执行顺序，迁移按文件名排序运行。已经推送到远程的迁移不要回头改：本地 `db reset` 与线上已经跑过的库会对不上。要改结构就新加一个文件。

文件内容如下，这是全书地基，第 9 章到第 14 章的所有 SQL 都依赖这里的表名与列名。

```sql
-- supabase/migrations/20261115090000_init_schema.sql

-- gen_random_uuid() 从 Postgres 13 起内置，不需要 pgcrypto。
-- create extension if not exists pgcrypto;

-- ---------- profiles ----------
create table public.profiles (
  id         uuid primary key references auth.users (id) on delete cascade,
  email      text not null unique,
  full_name  text,
  avatar_url text,
  created_at timestamptz not null default now()
);

create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  insert into public.profiles (id, email, full_name)
  values (new.id, new.email, coalesce(new.raw_user_meta_data ->> 'full_name', ''))
  on conflict (id) do nothing;
  return new;
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();

-- ---------- teams ----------
create table public.teams (
  id         uuid primary key default gen_random_uuid(),
  name       text not null check (char_length(btrim(name)) between 1 and 60),
  slug       text not null check (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'),
  plan       text not null default 'free' check (plan in ('free', 'pro', 'team')),
  -- 乐观锁版本号，每次更新加一。第 10 章用它检测并发覆盖。
  version    integer not null default 1,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  deleted_at timestamptz
);

create unique index teams_slug_active_uniq
  on public.teams (slug)
  where deleted_at is null;

create unique index teams_name_active_uniq
  on public.teams (lower(name))
  where deleted_at is null;

create or replace function public.touch_updated_at()
returns trigger
language plpgsql
as $$
begin
  new.updated_at = now();
  return new;
end;
```

## 8.6 用 EXPLAIN 验证索引

索引建完必须验证，唯一可靠的方式是让数据库给出执行计划。

```sql
explain (analyze, buffers)
select id, action, created_at
from public.activity_logs
where team_id = '00000000-0000-0000-0000-000000000000'
order by created_at desc, id desc
limit 20;
```

`analyze` 会真的执行查询，不要随手加在 `update`、`delete` 上；`buffers` 表示读了几个数据块。计划是一棵树，从内往外读，先认三个节点：`Seq Scan` 顺序扫全表，`Index Scan` 走索引找行再回表，`Index Only Scan` 只读索引。再看两组数字：`rows=` 是估算行数，`actual rows=` 是实际行数，差一个数量级就执行一次 `analyze`。外层出现 `Limit`、且它下面直接是 `Index Scan`，说明取满 20 条就停；外层出现 `Sort`，说明索引没服务排序。

数据少时优化器会故意选 `Seq Scan`。三条测试数据走索引要多读一次索引页再回表，反而更慢。看到 `Seq Scan` 不代表索引建错。想确认索引可用，临时关闭顺序扫描：

```sql
set enable_seqscan = off;
explain select id from public.activity_logs
where team_id = (select id from public.teams limit 1)
order by created_at desc, id desc
limit 20;
set enable_seqscan = on;
```

这个开关只影响当前会话，不要写进应用代码。

`Index Scan` 后面挂着 `Filter`、`Rows Removed by Filter` 数字很大，通常说明列顺序不对，过滤没有吃到最左前缀，索引只帮了一部分。

还有一种常见节点 `Bitmap Index Scan`。匹配行较多但不到全表时，Postgres 先把命中位置记成位图，再按页顺序回表，减少随机 IO，它上面通常挂着 `Bitmap Heap Scan`。看到它说明索引生效了，只是匹配面宽，不要因此改索引。

`cost=0.43..8.72` 里的数字是相对单位，并非毫秒，默认「读一页算 1、读一行算 0.01」。它用来比较两个计划谁更便宜，不预测耗时。真实耗时看 `actual time`，而 `loops=N` 表示该节点被嵌套循环执行了 N 次，总时间要把 `actual time` 乘以 `loops`，这是读大计划时最常算错的一处。

想在 `update`、`delete` 上做 analyze，包一层事务再回滚：

```sql
begin;
explain (analyze, buffers)
update public.teams set name = name where id = '00000000-0000-0000-0000-000000000000';
rollback;
```

上线后有两个运维查询常用。找从没被用过的索引（统计每次重启清零，先跑一两周）：

```sql
select relname as table_name, indexrelname as index_name, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) as index_size
from pg_stat_user_indexes
where schemaname = 'public' and idx_scan = 0
order by pg_relation_size(indexrelid) desc;
```

唯一索引的 `idx_scan` 也可能是 0，它主要维护唯一性，不服务查询，删之前先确认用途。

找最慢的查询：

```sql
select calls, round(mean_exec_time::numeric, 2) as avg_ms,
       round(total_exec_time::numeric) as total_ms, left(query, 120) as query
from pg_stat_statements
order by total_exec_time desc
limit 10;
```

`total_exec_time` 比 `mean_exec_time` 更能说明问题：平均 2 毫秒但每秒 500 次的查询，比平均 800 毫秒但一天一次的更值得优化。`pg_stat_statements` 是扩展视图，Supabase 默认安装；本地自托管没装会报 `relation "pg_stat_statements" does not exist`，那是 `create extension pg_stat_statements;` 没执行，或者 `shared_preload_libraries` 没配。要让程序读计划，用 `explain (format json) select ...`，输出可以直接 `JSON.parse`，不要用正则解析文本计划，文本格式每个大版本都会变。

## 8.7 边界与失败模式

迁移重放失败有三种常见原因。第一种是 `ERROR: relation "teams" already exists`：这段建表被跑过两次，`db reset` 没清干净，或者同一段 SQL 曾被贴进 Dashboard 执行。这时别加 `if not exists` 糊过去，那会让第二次建表悄悄跳过，约束和索引仍是旧的。直接 `db reset` 重来。

第二种是 `ERROR: column "version" of relation "teams" already exists`：有人改了已合并的迁移文件，本地库还是旧结构。规矩是改结构就新加迁移，不改历史。

第三种是 `db reset` 卡在 `Seeding data`：`supabase/seed.sql` 不幂等，第二次插入撞主键。第 9 章把 seed 改成可重复执行。

重放日志里如果出现 `WARNING`，通常是某个唯一索引因为重复数据建不起来，不要放过。

外键漏索引的表现是删除变慢。删团队时要到子表找全部引用行，没有索引就是全表扫；数据越多锁得越久。上线后才发现时，补救要多花一次建索引的锁窗口。

`restrict` 漏建的表现相反：删除成功，发票挂在不存在的团队上。这类数据错误不会立刻报错，只在用户查账时暴露。

主键用 uuid 之后，`order by id` 没有业务意义，按时间排序要写 `created_at`（并让索引与之一致）。

## 8.8 检查点

**一、九张表都在**

```sql
select count(*) from pg_tables where schemaname = 'public';
-- 期望 9
```

二、软删后同一个 slug 能重建

```sql
insert into public.teams (name, slug) values ('Acme', 'acme');
update public.teams set deleted_at = now() where slug = 'acme';
insert into public.teams (name, slug) values ('Acme', 'acme');
select count(*) from public.teams where slug = 'acme';
-- 期望 2；第二句 insert 不报错
```

`count` 为 2 是故意的：软删的行还在，只是不参与唯一性判断。第二句 `insert` 报 `duplicate key` 就回去检查索引谓词。

三、邀请撤销后同一个邮箱能重邀

```sql
insert into public.invitations (team_id, email, token, expires_at)
values ('<team_id>', 'a@example.com', 'tok-1', now() + interval '7 days');
update public.invitations set status = 'revoked' where token = 'tok-1';
insert into public.invitations (team_id, email, token, expires_at)
values ('<team_id>', 'a@example.com', 'tok-2', now() + interval '7 days');
-- 期望成功；未撤销时第二条应报 duplicate key
```

**四、三条部分唯一索引都在**

```sql
select indexname from pg_indexes
where schemaname = 'public' and indexname like '%_active_uniq' or indexname like '%_pending_%';
-- 期望包含 teams_slug_active_uniq、teams_name_active_uniq、invitations_pending_email_uniq
```

**五、查询计划走到你建的索引**

```sql
analyze public.activity_logs;
explain (analyze, buffers)
select id, action from public.activity_logs
where team_id = (select id from public.teams limit 1)
order by created_at desc, id desc
limit 20;
```

期望出现 `Index Scan using activity_logs_team_created_idx`，`Limit` 在它外层。数据只有几十条时出现 `Seq Scan` 属正常，`set enable_seqscan = off` 再跑一次确认索引可用即可。

**六、约束拒绝非法 slug**

```sql

```

## 8.9 常见错误

`ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification`

`on conflict` 的目标是部分唯一索引，你没有把索引的 `where` 抄过去。完整写法：

```sql
insert into public.teams (name, slug) values ($1, $2)
on conflict (slug) where deleted_at is null do nothing;
```

`ERROR: duplicate key value violates unique constraint "teams_slug_key"`

两种可能：建的是普通 `unique (slug)`，没有建部分唯一索引；或者库里留着迁移之前的旧约束。先查：

```sql
select conname, pg_get_constraintdef(oid)
from pg_constraint
where conrelid = 'public.teams'::regclass;
```

有旧约束先 `alter table public.teams drop constraint teams_slug_key;`，再建部分唯一索引。

`ERROR: insert or update on table "team_members" violates foreign key constraint "team_members_user_id_fkey"`

`auth.users` 里有这个人，`public.profiles` 里没有。多半是 `handle_new_user` 触发器没建，或者建在了别的 schema。查：

```sql
select tgname from pg_trigger where tgrelid = 'auth.users'::regclass;
```

没有就补上触发器，再回填一次：`insert into public.profiles (id, email) select id, email from auth.users on conflict (id) do nothing;`

`ERROR: new row for relation "teams" violates check constraint "teams_slug_check"`

slug 只接受 `^[a-z0-9]+(-[a-z0-9]+)*$`。用户输入「我的团队」「Acme Team」「acme_team」都不合法。不要在前端偷偷 `toLowerCase()` 了事，`Acme Team` 转小写后中间仍有空格。写一个明确的 slug 生成函数：转小写、非字母数字换连字符、合并连续连字符、去掉首尾，结果为空就加随机后缀。

`ERROR: relation "auth.users" does not exist`

迁移被跑在了普通 Postgres 上。`auth.users` 是 Supabase 的 schema，本地必须 `supabase start` 之后才能迁移。也正因为这条外键，这份 DDL 不能直接搬到别的托管 Postgres，第 9 章讲连接边界时再展开。

`ERROR: cannot drop constraint teams_slug_key on table teams because other objects depend on it`

slug 的唯一约束被别的表拿去做了外键引用。本书没有这种依赖；如果你自己加了引用 `teams.slug` 的表，先删那边。另一个提醒：某列的唯一性将来若要允许软删除，从一开始就建成部分唯一索引，不要先建约束再拆。

## 8.10 这一章在做什么

数据库的形状在这里定死：九张表、三条部分唯一索引、五个按查询形状排好列的复合索引，再加一份能重放的迁移文件。

需要记住三件事。主键用 uuid 是因为 `auth.users` 就是 uuid，与时髦无关。外键的删除动作是产品决定：cascade 会连坐，set null 留证据，restrict 把问题挡在写入时。唯一性要不要包含已删除的行，取决于业务语义，部分唯一索引就是为这件事存在的。

这份 DDL 最容易抄错的三处：`teams.version` 默认值是 1；`lower(name)` 与 `lower(email)` 是表达式索引，查询和 `on conflict` 都要原样写表达式；`jobs` 故意不建外键。

剩下的问题是这份文件只能跑一次，跑第二次报「表已存在」。两个人同时加列、合并之后怎么重放，本地与线上的迁移记录怎么保持一致，连接数怎么不炸。这些是第 9 章的内容。
