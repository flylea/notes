# 第 51 章 合规最小集

这一章讲团队协作工具要上线时，工程侧必须做到的最小合规集：Cookie 同意、隐私政策与实现一致、数据保留期限、删除请求流程、子处理者清单、日志脱敏。

这一章讲工程动作：哪些数据被收集、存在哪、留多久、谁能删。它不构成法律意见。具体条款是否适用，要看运营主体与用户所在地，必要时咨询律师。

涉及的组件有四个：前端的同意横幅与分析脚本加载、服务端的同意状态读取、数据库里的同意记录与保留期、文档侧的隐私政策与子处理者清单。

一个判断标准：隐私政策里写的每一句，代码里都要有对应的实现；代码里做的每一件事，政策里都要能读到。对不上的地方就是风险。

## 51.1 先列出数据流

合规的起点是数据清单。用户注册后，哪些数据离开浏览器、去了谁那里。

三类数据要分开看。账号数据：邮箱、密码哈希、会话，存 Supabase。业务数据：团队、项目、附件，存 Supabase 与 Storage。行为数据：页面访问、点击、错误，通常进分析服务与日志。

第三方按用途列。Supabase 存数据，Resend 发邮件，Stripe 收款，Cloudflare 做 CDN 与防护，Vercel 跑对照环境。每家在什么条件下收到什么数据，要写清楚。

```text
// docs/third-parties.md
| 域名 | 用途 | 是否存 cookie | 是否可拒绝 |
| teamstack.dev | 本站 | 是（会话） | 否，登录必需 |
| xxx.supabase.co | 认证、数据、文件 | 是（sb-xxx-auth-token） | 否，功能必需 |
| challenges.cloudflare.com | 人机校验 | 是（cf_clearance 之类） | 否，安全必需 |
| fonts.gstatic.com | 字体 | 否 | 是 |
| googletagmanager.com | 统计 | 是（_ga） | 是 |
```

清单要按“数据进、数据出”两个方向写。进：用户填了什么、系统自动采集什么；出：发给谁、以什么形式、保留多久。两个方向都写全，才看得出哪些第三方拿到了不必要的字段。

列清单时会发现一些“顺手加的”脚本：统计、客服、热图。它们多数不在最初的设计里，是后来贴进去的。每一个都要有同意依据。

```text
// docs/third-parties.md
| 域名 | 用途 | 是否存 cookie | 是否可拒绝 |
| teamstack.dev | 本站 | 是（会话） | 否，登录必需 |
| xxx.supabase.co | 认证、数据、文件 | 是（sb-xxx-auth-token） | 否，功能必需 |
| challenges.cloudflare.com | 人机校验 | 是（cf_clearance 之类） | 否，安全必需 |
| fonts.gstatic.com | 字体 | 否 | 是 |
| googletagmanager.com | 统计 | 是（_ga） | 是 |
```

数据最小化要主动做。注册只要邮箱，就不要顺手收集手机号；统计只要页面路径，就不要带 `user_id`。少收集一项，后面就少一项要说明、要删、要保护。

清单要落到文档并进仓库。散落在某个人脑子里的数据流，换人之后就消失了。

## 51.2 最小集是五件事

这五件事对应五类风险：未同意就跟踪、政策与实现不符、数据永久留存、删除请求不响应、无法证明做过。小团队通常先做前三件，出事最多的却是后两件。

五件事之外还有一件基础设施：数据清单要能更新。新加一个第三方、新收集一个字段，清单跟着改；清单过期，后面四件事都会失准。

第一件，Cookie 同意。非必要 Cookie 在用户同意前不能写，分析脚本不能加载。

第二件，隐私政策。写清收集范围、用途、期限与联系人。写明收集什么、为什么、存多久、交给谁、用户怎么删。

第三件，保留期限。每类数据写一个到期日，到点自动清。每类数据有明确期限，到期自动清理，不能“永久保留”。

第三件的难点在“自动”。手工清理一定会漏，尤其是用户量上来之后；把期限写成清理任务，比写进文档可靠。

第四件，删除请求。有入口、有回执、有时限，能真的删掉。

第五件，记录。同意与删除都要留痕，能拿出来证明。同意、删除、数据导出都要留痕，用于证明做过。

五件事之间有依赖。没有同意记录就证明不了同意；没有保留期限，删除流程就没有判断依据；没有文档，删除范围就说不清。顺序按“先能证明、再能执行、最后能解释”推进。

五件事的难度递增。同意横幅两小时能做完，删除流程要动数据库与对象存储，记录要设计表结构。

## 51.3 Cookie 同意横幅

横幅要满足四个条件。同意前不写非必要 Cookie；拒绝与同意同样容易点；选择能被服务端读到；用户能改主意。

同意状态分三类存储：必要 Cookie 不询问；分析类要询问；广告类默认关闭，即使同意也要能单独关掉。teamstack 只有前两类。

组件用客户端组件，读写 `document.cookie`，180 天过期，`SameSite=Lax`，非 HttpOnly。

```tsx
// src/components/cookie-consent.tsx
'use client'

import { useEffect, useState } from 'react'

type Consent = { analytics: boolean; decidedAt: string }

const COOKIE = 'consent'

function readConsent(): Consent | null {
  const raw = document.cookie
    .split('; ')
    .find(row => row.startsWith(`${COOKIE}=`))
    ?.split('=')[1]
  if (!raw) return null
  try {
    return JSON.parse(decodeURIComponent(raw))
  } catch {
    return null
  }
}

function writeConsent(analytics: boolean) {
  const value: Consent = { analytics, decidedAt: new Date().toISOString() }
  // 180 天过期；SameSite=Lax 防止跨站读取；不用 HttpOnly，因为前端要读
  document.cookie = `${COOKIE}=${encodeURIComponent(JSON.stringify(value))}; path=/; max-age=${180 * 24 * 3600}; SameSite=Lax`
  window.dispatchEvent(new Event('consent-changed'))
}

export function CookieConsent() {
  const [consent, setConsent] = useState<Consent | null>(null)
  const [open, setOpen] = useState(false)

  useEffect(() => {
    const stored = readConsent()
    setConsent(stored)
    setOpen(stored === null)
  }, [])

  if (!open) return null

  return (
    <div role="dialog" aria-label="Cookie 设置" className="fixed inset-x-0 bottom-0 z-50 border-t bg-white p-4">
      <p className="text-sm">
        我们用必要 Cookie 维持登录，用分析 Cookie 了解页面使用情况。你可以拒绝分析，不影响使用。
        详见 <a href="/legal/privacy" className="underline">隐私政策</a>。
      </p>
      <div className="mt-3 flex gap-2">
        <button
          className="rounded bg-neutral-900 px-4 py-2 text-sm text-white"
          onClick={() => { writeConsent(true); setOpen(false) }}
        >
          接受分析
        </button>
        <button
          className="rounded border px-4 py-2 text-sm"
          onClick={() => { writeConsent(false); setOpen(false) }}
        >
          拒绝分析
        </button>
        <a href="/legal/cookies" className="px-4 py-2 text-sm underline">
          管理偏好
        </a>
      </div>
    </div>
  )
}
```

挂到根布局，位置在 `body` 末尾。它只在没有同意记录时出现，已选择过的不再打扰。

```tsx
// src/app/layout.tsx 片段
import { CookieConsent } from '@/components/cookie-consent'

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN">
      <body>
        {children}
        <CookieConsent />
      </body>
    </html>
  )
}
```

横幅的文案要写清楚用途。写“我们使用 Cookie 改善体验”等于没说；写“分析访问以改进功能，数据存于 Cloudflare，保留 14 天”，用户才能判断。

三个细节容易做错。默认值不能预设为“同意”，否则拒绝率再高也没意义；横幅不能挡住主要内容，移动端要点得到；拒绝后要给一个入口改回同意。

## 51.4 服务端读取同意状态

横幅只解决客户端。服务端渲染时如果不知道用户是否同意，会在 HTML 里带上分析脚本，用户点了拒绝也晚了。

`cookies()` 在 Next.js 16 是异步的，必须 `await`。读不到时按“未同意”处理。

```ts
// src/lib/consent.ts
import { cookies } from 'next/headers'

export type Consent = { analytics: boolean; decidedAt: string }

export async function getConsent(): Promise<Consent | null> {
  // Next.js 16：cookies() 是异步的，必须 await
  const store = await cookies()
  const raw = store.get('consent')?.value
  if (!raw) return null

  try {
    const parsed = JSON.parse(decodeURIComponent(raw)) as Consent
    if (typeof parsed?.analytics !== 'boolean') return null
    return parsed
  } catch {
    return null
  }
}

export async function allowsAnalytics() {
  const consent = await getConsent()
  return consent?.analytics === true
}
```

服务端判断要放在渲染之前。等组件挂载后再读 Cookie，首屏已经发出去了；用服务端组件读，HTML 里就不会出现分析标签。

读取函数要区分“未选择”与“拒绝”。前者可以再问，后者不要再弹；两者都当作不允许分析。

## 51.5 分析脚本按同意加载

`next/script` 有三种加载策略：`beforeInteractive` 尽早加载、`afterInteractive` 水合后加载、`lazyOnload` 空闲时加载。分析脚本用后两种，都不该阻塞首屏。

脚本用 `next/script` 的 `afterInteractive`，条件渲染：同意才渲染，不同意连标签都不出现。

```tsx
// src/components/analytics.tsx
'use client'

import Script from 'next/script'
import { useEffect, useState } from 'react'

export function Analytics() {
  const [allowed, setAllowed] = useState(false)

  useEffect(() => {
    function check() {
      const raw = document.cookie
        .split('; ')
        .find(row => row.startsWith('consent='))
        ?.split('=')[1]
      if (!raw) return setAllowed(false)
      try {
        setAllowed(JSON.parse(decodeURIComponent(raw)).analytics === true)
      } catch {
        setAllowed(false)
      }
    }

    check()
    window.addEventListener('consent-changed', check)
    return () => window.removeEventListener('consent-changed', check)
  }, [])

  if (!allowed) return null

  return (
    <Script
      src="/analytics.js"
      strategy="afterInteractive"
      data-domain="teamstack.dev"
    />
  )
}
```

用户在同一次会话里改主意时，监听 `consent-changed` 事件重新渲染。已经加载的脚本无法卸载，这一点要在隐私政策里如实写：同意后加载的脚本，撤回同意后停止上报，但代码仍在页面里。

脚本要支持撤回。加载时给一个全局标记，撤回同意时置为 false，上报函数先查标记；这样已加载的脚本停止工作，不用刷新页面。

“不上报”与“不加载”是两种承诺。前者靠脚本配合，后者靠不渲染标签；对外说明时按实际做法写。

## 51.6 政策与代码一致

最大的风险是政策写得漂亮、代码没做。检查方法是逐条对照：政策里的每一句，找到对应的实现位置。

```text
// docs/privacy-mapping.md
政策第 3 节「我们使用 Cookie 分析访问行为」
  → src/components/analytics.tsx
  → src/components/cookie-consent.tsx
  → Cookie: _ga（180 天）

政策第 5 节「附件保存至团队删除后 30 天」
  → scripts/cleanup-deleted-teams.mjs
  → storage.objects 删除逻辑

政策第 6 节「注销后 30 天内删除账号数据」
  → src/app/(app)/settings/actions.ts deleteAccount
  → cron scripts/purge-deleted-accounts.mjs
```

对照表按政策章节组织，每一行三列：政策原文、实现位置、验证方式。验证方式写成命令或页面路径，评审时能当场点开。

对照表要进代码评审。改隐私政策时同步改代码，改代码收集行为时同步改政策；两件事在同一个 PR 里完成。

```text
// docs/privacy-mapping.md
政策第 3 节「我们使用 Cookie 分析访问行为」
  → src/components/analytics.tsx
  → src/components/cookie-consent.tsx
  → Cookie: _ga（180 天）

政策第 5 节「附件保存至团队删除后 30 天」
  → scripts/cleanup-deleted-teams.mjs
  → storage.objects 删除逻辑

政策第 6 节「注销后 30 天内删除账号数据」
  → src/app/(app)/settings/actions.ts deleteAccount
  → cron scripts/purge-deleted-accounts.mjs
```

政策更新要留版本。每次改动记日期、改动点、生效时间；老用户看到的是新版，同意记录里存的是旧版本号，两者要能对上。

找不到实现的那一句，要么删掉，要么补实现。写“我们使用行业标准加密”但数据库没开 TLS，是典型的不一致。

## 51.7 每类数据定期限

保留保留期限和备份策略要一致。库里删了 30 天，备份里还留 12 个月，等于没删；备份的保留期要么缩短，要么在政策里说明“备份为灾备目的保留，不用于业务”。

期限按用途定，不按“方便”定。账号数据在账号存续期间保留，注销后 30 天内删除；会话 30 天；审计日志 180 天；访问日志 14 天；备份 7 天加 4 周加 12 个月；发票按税法 10 年。

| 数据 | 期限 | 依据 |
| --- | --- | --- |
| 账号与资料 | 注销后 30 天 | 删除请求处理窗口 |
| 会话与令牌 | 30 天 | 安全需要 |
| 审计日志 | 180 天 | 追责需要 |
| 访问日志 | 14 天 | 排障需要 |
| 发票 | 10 年 | 税法 |

每类数据要能找到位置。账号在 `auth.users`，资料在 `profiles`，团队在 `teams`，附件在 Storage 的 bucket 与 `attachments` 表；写不出去处的数据，通常也没人清理。

期限的设计要留缓冲。法律规定“不超过必要期限”，工程上按略短执行；写 30 天的就按 25 天清理，避免边界日期出问题。

期限要写进清理任务。每个期限对应一条 SQL 或一个脚本，跑在定时任务里；没有清理任务的期限只是文档上的一句话。

到期不删的常见原因是“怕删错”。做法是软删加宽限：标记删除，30 天后硬删；回收站只对管理员可见。

## 51.8 删除请求从入口到回执

时限要分层。确认 24 小时、处理 30 天、复杂情况可延长到 90 天并告知用户；延长要有理由，不能默认拖着。

入口放在设置页，文案直接写“删除账号与数据”，不要藏在三级菜单。提交后返回受理页，给出预计完成时间与撤回方式。

```tsx
// src/app/(app)/settings/data-request/page.tsx
export default function DataRequestPage() {
  return (
    <main className="prose mx-auto max-w-2xl px-6 py-16">
      <h1>数据访问与删除请求</h1>
      <p>
        你可以在应用内「设置 → 账号」直接导出或删除数据，立即生效。
        如果无法登录，请用注册邮箱发信至 privacy@teamstack.dev，标题写「数据请求」。
      </p>
      <h2>我们会怎么处理</h2>
      <ol>
        <li>24 小时内确认收到，并请你完成一次身份验证。</li>
        <li>验证通过后 30 天内完成访问、更正或删除，并邮件告知结果。</li>
        <li>依法必须保留的记录（如发票）会说明保留范围和期限。</li>
      </ol>
      <p>最后更新：2026-11-15</p>
    </main>
  )
}
```

入口的位置要在设置页一级，用户找得到，但要点两下才提交；删除是低频高风险操作，便利性让位于确认。删除按钮用危险色，点击后要求输入邮箱确认；提交后进入待处理状态，期间可以撤回。

处理流程分四步。24 小时内确认收到；30 天内完成删除；完成后发回执邮件；回执里说明删了什么、保留了什么。

保留的部分要能解释。发票、审计日志、反欺诈记录按法规保留，且不能用于其他目的。回执里列清楚，比含糊地写“部分数据依法保留”可信。

删除要有回执模板。模板里写清申请时间、完成时间、删除的数据类别、依法保留的类别、联系人；不要写“已彻底删除一切数据”这种无法验证的表述。

删除范围要覆盖：数据库行、Storage 对象、认证记录、分析服务里的用户标识。最后一项最容易被忘，删了库但分析平台还留着 `user_id`。

## 51.9 子处理者与 DPA

子处理者指替你处理用户数据的第三方。每家都要有数据处理协议（DPA），并在隐私政策里列出。

| 子处理者 | 用途 | 数据位置 |
| --- | --- | --- |
| Supabase | 数据库、认证、存储 | 按项目区域 |
| Resend | 事务邮件 | 美国 |
| Stripe | 支付 | 全球 |
| Cloudflare | CDN、防护 | 全球边缘 |
| Vercel | 对照部署 | 按区域 |

子处理者的选择标准有两条：能不能签 DPA，能不能说清数据存在哪。两条都答不上来的服务，不适合处理用户数据。

清单变化时更新政策，并通知用户。新增一家子处理者就悄悄上线，是常见的合规漏洞。

DPA 要存档。多数服务商在控制台提供标准 DPA，签署后存进合规文件夹；没有 DPA 的服务商不适合处理用户数据。

备案信息要一致。页脚的公司名、备案号、域名要与备案主体一致；换了主体不更新，检查时会对不上。

数据出境要单独看。用户在中国大陆、数据存境外，属于出境场景；标准合同、评估这些路径按运营主体判断，改一行配置解决不了。

## 51.10 备案与等保的两条分支

面向中国大陆用户、服务器在大陆，需要 ICP 备案。备案在接入商处提交，周期通常两到四周；备案号要展示在页脚，链接到工信部查询页。

等保的工程动作是“三件套”：定级备案、差距评估、整改。技术侧要做的是日志留存、访问控制、边界防护；这些在本书的认证、日志、部署三章里已有实现，按等级补强度即可。

公安联网备案在 ICP 之后 30 天内完成，拿到备案号同样展示。等保按系统等级定级，二级以上要做测评；团队协作工具通常按二级准备。

服务器在境外，不做 ICP 备案，但要注意数据出境与内容合规。支付通道也不同：境内用微信支付与支付宝，境外用 Stripe。

两条分支的差别写在部署文档里，别让运维猜。同一套代码通过环境变量切换页脚与支付方式。

## 51.11 日志里不能出现的字段

日志用于排障，不该成为第二份用户数据库。禁止写入：密码与哈希、令牌与密钥、完整 IP、身份证号、银行卡号、邮件正文。

日志的访问权限也要收紧。生产日志只有运维能看，导出要审批；日志平台的管理员账号开双因素。

脱敏放在写入前，用统一函数，不靠调用方自觉。

```ts
// src/lib/logger.ts
type Level = 'info' | 'warn' | 'error'

const REDACT_KEYS = [
  'password', 'passwordHash', 'token', 'access_token', 'refresh_token',
  'authorization', 'cookie', 'set-cookie', 'secret', 'apiKey',
  'stripeSecret', 'cardNumber', 'cvc', 'email',
]

function redactIp(ip: string) {
  // IPv4 保留前三段，IPv6 保留前三组
  if (ip.includes(':')) return ip.split(':').slice(0, 3).join(':') + '::'
  return ip.split('.').slice(0, 3).join('.') + '.0'
}

function scrub(value: unknown, depth = 0): unknown {
  if (depth > 4 || value === null || typeof value !== 'object') return value
  if (Array.isArray(value)) return value.slice(0, 20).map(v => scrub(v, depth + 1))

  const out: Record<string, unknown> = {}
  for (const [key, val] of Object.entries(value as Record<string, unknown>)) {
    const lower = key.toLowerCase()
    if (REDACT_KEYS.includes(lower)) {
      out[key] = '[redacted]'
    } else if (lower === 'ip' && typeof val === 'string') {
      out[key] = redactIp(val)
    } else {
      out[key] = scrub(val, depth + 1)
    }
  }
  return out
}

export function log(level: Level, message: string, meta?: Record<string, unknown>) {
  const line = JSON.stringify({
    level,
    message,
    time: new Date().toISOString(),
    ...(meta ? { meta: scrub(meta) } : {}),
  })
  if (level === 'error') console.error(line)
  else console.log(line)
}
```

IP 保留前三段，用于定位城市与运营商；完整 IP 只在安全事件里临时记录，且单独加密存储。

错误堆栈里可能带请求体。记录前先过一遍 `scrub`，把已知字段替换掉；未知字段按白名单处理，不在白名单里的不写。

## 51.12 出事之后的 72 小时

数据泄露的通报时限按法规与合同定，GDPR 是 72 小时。工程侧要准备的是：能判断影响范围、能通知到人、能留下记录。

第一步是止血。撤销泄露的令牌、关闭受影响的接口、保留现场日志。

评估要有清单。用户数、数据类别、是否含敏感信息、是否已加密、泄露原因，逐项填；填不出来的项就是还不知道的风险。

第二步是评估。哪些数据、多少用户、是否可识别；从审计日志与访问日志里查，时间范围精确到小时。

第三步是通报。给监管机构与用户的通知模板提前写好，出事时只填事实；模板里不要承诺未验证的结论。

通报渠道要提前定。监管机构的入口、用户的邮件模板、站内公告的位置，出事时按清单执行，不要临时找。

第四步是复盘。复盘文档要能公开给用户看，删掉内部细节后发在状态页；透明本身能降低信任损失。

第四步是复盘。根因、影响、修复、防止复发的措施，写成一页文档。

## 51.13 同意记录

“用户同意过”要有证据。记录内容：谁、什么时候、同意了什么版本的政策、从哪个 IP 与设备。

## 51.14 边界与失败模式

合规问题多数出在“文档写了、代码没做”，或者反过来。

1. 隐私政策列了收集字段，代码里还在收集别的。上线前按政策逐条对照代码，多出来的字段删掉或补进政策。
2. 用户点了拒绝，分析脚本已经加载。脚本一旦执行就无法卸载，正确做法是同意之前不渲染。
3. 删除请求只删主表。附件、日志、审计记录仍在，用户复查时能看到残留。删除要按清单逐项执行。
4. 日志里出现邮箱、IP、令牌。排障方便与合规冲突时，先脱敏，需要原文时用受控的临时日志。
5. 大陆访问的站点缺备案号。页脚没有备案号，域名可能被拦截，支付通道也无法开通。
6. 同意记录缺失。用户投诉时无法证明当时同意过，需要保留时间、版本、来源三要素。

## 51.15 检查点

1. 清空 Cookie 后访问首页，Network 面板里没有分析请求。判据：只有页面与静态资源请求。
2. 点“拒绝”后刷新，横幅不再出现，分析请求仍然没有。判据：两次访问一致。
3. 隐私政策里的每一条，在 `docs/privacy-mapping.md` 里能找到实现位置。判据：没有空行。
4. 提交删除请求，24 小时内收到确认邮件，30 天内收到完成回执。判据：两封邮件都在。
5. 日志里搜 `@` 与 `Bearer`，没有命中。判据：脱敏生效。
6. `select count(*) from consent_events` 有记录，且带上政策版本。判据：版本号与常量一致。

## 51.16 常见错误

**1. `cookies() should be awaited before using its value`**

现象是构建或运行时报错。原因是 Next.js 16 的 `cookies()` 是异步 API。改法是 `const store = await cookies()`。

**2. 横幅每次都出现**

现象是用户点了同意，刷新后还弹。原因是写 Cookie 的 `path` 或 `max-age` 配错，或者读的是另一个域名。改法是统一 `path=/`、180 天过期，并确认读写同域。

**3. 拒绝后仍有分析请求**

现象是 Network 里还有上报。原因是脚本在布局里静态引入，没按同意条件渲染。改法是条件渲染 `Script`，并在服务端也判断一次。

**4. `NEXT_PUBLIC_` 变量泄露密钥**

现象是构建产物里能搜到密钥。原因是把服务端密钥加了 `NEXT_PUBLIC_` 前缀。改法是密钥只在服务端使用，前缀变量只放公开配置。

**5. 隐私政策里的邮箱不存在**

现象是用户发删除请求被退信。原因是政策里写的 `privacy@` 没有配置邮箱。改法是先建邮箱与自动回复，再发布政策。

**6. 备案号点不开**

现象是页脚有备案号但链接 404。原因是链接写成相对路径或错域名。改法是链接到 `https://beian.miit.gov.cn/`，新窗口打开。

这套最小集不追求“完全合规”，追求“能解释、能执行、能证明”。做到这三点，检查与问询时就不会手忙脚乱。

## 51.17 这一章在做什么

这一章把合规拆成五个工程动作：同意、政策、期限、删除、记录。每个动作都有对应的代码位置与检查方法。

它建立三条判断。第一，合规的核心是“说到的做到”，政策与实现要对得上。第二，删除要覆盖数据库、对象存储、认证与分析四个位置。第三，记录是举证材料，同意与删除都要留痕。

这一章不构成法律意见，也不覆盖行业特殊要求（医疗、金融）。涉及这些领域时，工程侧的最小集只是起点。
