# 附录 A 不写的内容与换实现对照

这份附录列两件事。第一，本书明确不写的三十一个主题，以及不写的理由。第二，二十五个常见替代实现，说明它们与书中选择的关系。两件事各自独立，可以分开读。

列出来的作用是划边界。读者遇到某个主题时，能判断是该在本书里找，还是该另找资料；也能判断某个技术选型换掉之后，哪些章节要重读。

两份清单都基于同一个前提：书里的团队协作工具 teamstack 有明确的规模与预算，选型围绕它展开。规模变化，结论也会变，附录里会说明变化的方向。

挑选标准有三条。第一，主题与本书主线相关，读者读到某章时可能顺带问起；与主线无关的主题不列。第二，主题本身有独立的技术栈或运维体系，用一节讲不清。第三，省略之后仍能靠公开资料补上，不会形成知识断层。没有列进清单的主题，不等于不值得学；清单只回答一个问题：这本书为什么在这里停住。

## 一、不写的内容

三十一项按来源分五组：渲染与构建九项，路由与运行时五项，缓存与协议两项，基础设施七项，数据与产品八项。MDX 归在渲染与构建这一组，为了不打乱已有编号，列在末尾。组与组之间的边界不严格，同一主题换个角度看可能落在别组；分组只为了方便查找。

每项写两句：第一句说它是什么，第二句说不写的理由。理由集中在三处：与本书的单体架构冲突、需要独立的技术栈、收益与维护成本不匹配。

### 1. 静态导出

`output: 'export'` 把整站导出为静态文件，没有服务端。本书的应用有登录、数据库写入与实时消息，导出后这些功能全部失效；只在纯展示站有意义。

### 2. 纯 SPA

把 Next.js 当单页应用用，路由全在客户端。这样做放弃了服务端渲染与流式输出，首屏与 SEO 都退化。需要 SPA 的项目直接用 Vite 更轻。

### 3. PWA 与离线

Service Worker 缓存与离线可用是独立主题。本书有一章讲缓存，但讲的是服务端缓存与 CDN，与浏览器离线缓存是两套机制；混在一起讲两边都不透。

### 4. 多 zone

多个 Next.js 应用合成一个域名，需要反向代理与路由约定。本书单应用单域名，多 zone 属于平台架构问题，超出教程范围。

### 5. 自建 custom server

用 Express 或 Fastify 接管 `next` 的请求处理。自建之后 standalone 产物、中间件、缓存都失效，运维成本上升；平台托管与 Docker 已经覆盖绝大多数场景。

### 6. Sass

Tailwind 与原生 CSS 变量足够覆盖本书的样式需求。引入 Sass 会增加一层编译，且与 Tailwind 4 的配置模型并行，收益不明显。

### 7. CSS-in-JS

styled-components、emotion 这类运行时方案与 React 服务端组件配合有额外约束，还需要客户端运行时。本书用 Tailwind，样式在构建期生成。

### 8. Tailwind v3 兼容

Tailwind 4 换了配置模型：`@tailwindcss/postcss`、`@theme`、取消 `tailwind.config.ts`。写 v3 的兼容页会让读者混用两套配置，出错难查。

### 9. 多语言路由

`[locale]` 段加词典是完整主题：路由、元数据、日期格式、RTL 都要处理。本书只做中文界面，多语言留给需要的人另找资料。

### 10. Edge Runtime

Edge Runtime 不支持 Node 原生模块，数据库驱动与文件系统都用不了。本书的数据访问依赖 Postgres 连接，放在 Node runtime；Edge 只适合轻量鉴权与重写。

### 11. webpack 调优

Next.js 16 默认用 Turbopack 构建，自定义 webpack 配置会直接构建失败。调优应转向 Turbopack 的配置项，webpack 时代的 splitChunks 经验多数失效。

### 12. codemod 升级

`@next/codemod` 能自动改一部分 API，但迁移的判断（哪些页面该改成服务端组件、缓存怎么设）无法自动完成。本书讲手动升级的检查顺序，不逐条讲 codemod。

### 13. 从 Vite 或 CRA 迁入

迁移涉及路由重写、数据获取改写、构建配置重建，工作量按项目规模差异极大。本书从零开始建项目，迁入是另一条路径。

### 14. 平台 PPR 协议

PPR（部分预渲染）在 16 里由 Cache Components 启用，平台侧还有一套协议与适配。本书讲应用侧怎么写，不讲平台如何实现。

### 15. migrating-to-cache-components

官方有专门的迁移指南，处理旧缓存模型到新模型的差异。本书从第一章就用新模型，不涉及迁移；从旧版本升级的项目应直接读官方指南。

### 16. Kubernetes

K8s 解决的是大规模编排与多服务治理。teamstack 单机 Docker Compose 足够，引入 K8s 会让部署复杂度上升一个数量级，收益为零。

### 17. 微服务

拆分服务的前提是团队规模与独立发布需求。本书是单体应用，模块按目录分；过早拆分会把事务、鉴权、日志都变成分布式问题。

### 18. Kafka

消息队列在本书用 Redis 与数据库表实现，量级在每天几千条。Kafka 适合高吞吐与多消费者场景，运维成本与当前需求不匹配。

### 19. GraphQL

GraphQL 解决的是多端取数差异与过度获取。本书的客户端只有 Web，Route Handler 加 Server Actions 已经够用；引入 GraphQL 要维护 schema 与解析器。

### 20. tRPC

tRPC 提供端到端类型安全，代价是前后端必须同为 TypeScript 且共享代码。本书的服务端以 Server Actions 与 Route Handler 为主，类型通过手写契约保证。

### 21. 分库分表

分库分表在单表过亿后才有意义。本书的数据量在百万级以下，索引与查询优化就能解决；提前分片会让事务与关联查询变得复杂。

### 22. 读写分离

读写分离要求主从复制与延迟处理，适合读多写少且读流量大的系统。本书规模用单个 Postgres 实例，Supabase 的连接池已经能支撑。

### 23. 自建 Supabase

官方自托管需要至少 4 GB 内存、2 核、40 GB 磁盘，且不含日志分析等托管能力。本书用免费托管项目，自建的成本与维护量都不划算。

### 24. CMS

接内容管理系统适合营销站与内容站。本书的营销页是代码里的静态页面，产品数据在数据库；引入 CMS 会增加一套内容模型与预览流程。

### 25. 富文本编辑器

富文本涉及粘贴清洗、协作光标、存储格式。本书的附件与评论用 Markdown 与纯文本，编辑器用轻量方案；完整富文本是独立产品级主题。

### 26. 地图

地图需要地图服务商的密钥、配额与合规要求。本书没有地理位置功能；需要时接一家服务商的 SDK，与框架无关。

### 27. 音视频

上传、转码、播放、CDN 分发是独立链路。本书只处理图片与普通附件；音视频要引入转码服务与播放器，超出教程范围。

### 28. 移动端与小程序

React Native、Expo、小程序各有构建与发布体系。本书只做 Web；同一套 API 可以被移动端复用，但客户端不在范围内。

### 29. 机器学习训练

训练需要 GPU、数据管道与实验管理。本书里 AI 只作为调用方出现（生成摘要、补全文本），训练与微调不在范围内。

### 30. 低代码建站

低代码平台用配置生成页面，与写代码是两条路径。本书教的是写代码建应用；需要低代码的团队应直接选平台，不必先学框架。

### 31. MDX 与文档站

MDX 让 Markdown 里能写组件，适合文档站、博客、课程站。本书做的是有登录、写入和实时消息的应用；接 MDX 要配 loader、内容目录、远程内容源和预览流程，是另一套工程。需要内容站的读者，官方 `@next/mdx` 指南够用。

## 二、换实现对照

每个条目四行。第一行指向书中对应章节，方便回查上下文。第二行说明两种实现的差别，只写影响使用的部分。第三行描述触发替换的条件。第四行给出本书不替换的理由。

四行里的判断都针对 teamstack 的规模。项目变大或合规要求变化时，第四行可能翻转，前三行仍然成立。

规模变化时，先看第二行与第四行是否还成立。第二行描述两种实现的差别，通常稳定；第四行描述取舍，会随规模与预算变。

### Prisma

- 对应：第八章（表与索引）、第十五章（会话）。
- 差在哪：Prisma 用 schema 文件生成客户端，迁移由 `prisma migrate` 管理；本书用 SQL 迁移加 Kysely，SQL 就是事实来源。
- 谁会换：团队更看重类型生成与迁移工具链，且能接受多一层生成步骤。
- 为什么这本不换：Supabase 的迁移与 RLS 都基于 SQL，多一层 schema DSL 会让两套定义并存。

### Neon

- 对应：第九章（数据库连接）、第四十九章（备份）。
- 差在哪：Neon 是分支式 Postgres，支持按分支建库与秒级恢复；Supabase 免费档没有 PITR。
- 谁会换：需要频繁建预览库、或需要时间点恢复的团队。
- 为什么这本不换：本书还用到 Supabase 的认证与存储，换库要拆掉两件事，成本高于收益。

### Firebase

- 对应：第五至七章（认证）、第八章（数据）。
- 差在哪：Firebase 是文档数据库加托管认证，客户端直接读写；本书是关系库加服务端鉴权。
- 谁会换：以移动端为主、数据结构松散的团队。
- 为什么这本不换：团队协作工具的角色与权限是关系型的，用文档库要自己维护一致性。

### Appwrite

- 对应：全书的数据与认证层。
- 差在哪：Appwrite 是自托管优先的后端平台，提供数据库、认证、存储、函数；生态比 Supabase 小。
- 谁会换：要求数据完全自控、又不想自己拼组件的团队。
- 为什么这本不换：本书的 SQL 迁移与 RLS 是教学主线，换成抽象层会藏掉关键细节。

### 整套 Supabase 自建

- 对应：第九章、第四十六章（自托管）。
- 差在哪：自建要跑 Postgres、GoTrue、Storage、Realtime 等服务，最低 4 GB 内存。
- 谁会换：有合规要求或已有 Kubernetes 平台的团队。
- 为什么这本不换：教程的目标是让读者把应用跑起来，自建平台的运维会淹没主线。

### Auth.js

- 对应：第五至七章（认证与会话）。
- 差在哪：Auth.js 是认证库，接多种 OAuth 提供商；会话与用户表要自己建。它由 Better Auth 团队维护，仍在收安全补丁。
- 谁会换：不想绑定 Supabase、需要多家登录方式的团队。
- 为什么这本不换：本书用 Supabase 认证，省掉令牌与回调的实现，篇幅可以留给业务。

### Better Auth

- 对应：第五至七章。
- 差在哪：Better Auth 是 TypeScript 优先的认证框架，插件化，自带组织与权限模型。
- 谁会换：新项目、想要类型安全且可控的认证实现。
- 为什么这本不换：本书的认证与 RLS 绑定，换框架要同时改数据库策略。

### Clerk

- 对应：第五至七章。
- 差在哪：Clerk 是托管认证服务，组件开箱即用，免费档有 MAU 限制。
- 谁会换：想最快上线登录、接受按用户计费的团队。
- 为什么这本不换：本书要讲清会话与 cookie 的细节，托管服务会把这些藏起来。

### BullMQ

- 对应：第二十六章（邮件队列）、第二十七章（定时任务）。
- 差在哪：BullMQ 基于 Redis，提供重试、延迟、并发控制；本书用数据库表加轮询实现队列。
- 谁会换：任务量大、需要复杂重试与优先级的团队。
- 为什么这本不换：免费档的 Redis 容量有限，数据库队列在本书量级够用，且少一个组件。

### Cloudflare Queues

- 对应：第二十六章。
- 差在哪：托管队列，与 Workers 集成，按消息计费。
- 谁会换：已经在 Cloudflare 上跑 Workers 的团队。
- 为什么这本不换：本书的应用跑在 Node 上，队列放在数据库里更容易排障。

### SQS

- 对应：第二十六章。
- 差在哪：AWS 托管队列，按请求计费，需要 IAM 与 VPC 配置。
- 谁会换：基础设施已在 AWS 的团队。
- 为什么这本不换：引入 AWS 账号体系与本书的极简部署目标冲突。

### Kafka

- 对应：第二十六章、第二十八章（实时）。
- 差在哪：高吞吐日志式消息系统，适合多消费者与重放。
- 谁会换：数据管道与事件驱动架构的团队。
- 为什么这本不换：本书的事件量小，Realtime 与数据库表已经覆盖。

### S3

- 对应：第二十三章（文件上传）。
- 差在哪：对象存储标准，生态最全，按存储与请求计费。
- 谁会换：需要归档、生命周期策略、跨区域的团队。
- 为什么这本不换：Supabase Storage 与数据库权限同源，省掉一套签名与鉴权。

### R2

- 对应：第二十三章、第四十九章（备份）。
- 差在哪：Cloudflare 的对象存储，出网免费，兼容 S3 API。
- 谁会换：出网流量大、想省带宽费的团队。
- 为什么这本不换：本书用它存备份，不存用户附件；附件要走 Supabase 的权限体系。

### MinIO

- 对应：第二十三章。
- 差在哪：自托管的对象存储，兼容 S3 API，要自己运维磁盘与副本。
- 谁会换：数据必须留在自有服务器的团队。
- 为什么这本不换：单机自建对象存储的可靠性不如托管服务，备份还要另做。

### 国内对象存储

- 对应：第二十三章、第四十六章（备案）。
- 差在哪：阿里云 OSS、腾讯云 COS 等，访问快、合规好，需要备案域名与实名。
- 谁会换：主要用户在中国大陆、已备案的团队。
- 为什么这本不换：本书的主线是免费档起步，国内对象存储按量计费且要备案。

### 微信支付

- 对应：第二十五章（订阅与支付）。
- 差在哪：需要商户号、证书、回调验签，个人开发者难申请。
- 谁会换：面向中国大陆用户、有企业主体的团队。
- 为什么这本不换：本书用 Stripe 讲订阅模型，支付渠道可以替换，模型不变。

### 支付宝

- 对应：第二十五章。
- 差在哪：与微信支付类似，沙箱完善，需要企业资质。
- 谁会换：同上，或需要多种支付方式的团队。
- 为什么这本不换：同一套订阅逻辑，换渠道是接适配层的工作。

### 短信

- 对应：第五章（验证码）、第二十六章（通知）。
- 差在哪：国内短信需要模板报备与签名，按条计费；Resend 只发邮件。
- 谁会换：注册流程依赖手机号的团队。
- 为什么这本不换：本书用邮箱注册，短信是可选增强。

### Elasticsearch

- 对应：第二十九章（搜索）。
- 差在哪：全文检索能力强，要单独部署与同步数据。
- 谁会换：搜索是核心功能、数据量大的产品。
- 为什么这本不换：Postgres 的全文检索在本书量级够用，少一个集群。

### Kubernetes

- 对应：第四十六章（自托管）。
- 差在哪：容器编排，提供滚动发布、自动扩缩、服务发现。
- 谁会换：多服务、多环境、需要弹性伸缩的团队。
- 为什么这本不换：单机 Compose 已经能滚动发布，K8s 的学习与运维成本过高。

### 微服务

- 对应：全书架构。
- 差在哪：按业务拆服务，独立部署与数据库。
- 谁会换：团队规模大到单体无法协作时。
- 为什么这本不换：本书的模块化单体已经能支撑，拆分带来的分布式事务问题更贵。

### GraphQL

- 对应：第三十章（对外 API）。
- 差在哪：单一端点、按需取字段，需要 schema 与解析器。
- 谁会换：多客户端、字段需求差异大的产品。
- 为什么这本不换：REST 与 Server Actions 已经覆盖，GraphQL 会增加一层维护。

### tRPC

- 对应：第三十章。
- 差在哪：端到端类型安全，前后端共享类型定义。
- 谁会换：全栈 TypeScript、内部应用为主的团队。
- 为什么这本不换：对外 API 需要语言无关的契约，tRPC 只适合内部调用。

### Upstash

- 对应：第三十一章（客户端取数）、第三十八章（限流）。
- 差在哪：托管 Redis，按请求计费，有免费额度。
- 谁会换：不想自建 Redis、需要全球低延迟的团队。
- 为什么这本不换：本书的 Redis 跑在同一台 VPS 上，延迟更低且不计请求数。

### 替换的成本怎么估

换实现前先估三笔成本。

第一笔是迁移成本：数据要搬、接口要改、测试要重跑。数据库替换通常最大，认证替换次之，支付渠道替换最小，但对账流程要重新走一遍。

第二笔是持有成本：托管服务按月计费，自建服务按人计费。托管把运维转成账单，自建把账单转成人力；两者都要算进预算，不能只比标价。

第三笔是故障成本：多一个组件就多一个故障点。托管服务的故障由服务商承担，恢复时间不受自己控制；自建可以自己修，前提是有人会修、知道怎么修。

三笔成本相加，再和收益比。收益通常来自三处：更低的延迟、更少的维护、更强的能力。只为“更新”而换，多数时候不划算。

还有一笔隐性成本：学习时间。团队里第一个人摸清新组件，通常要一周以上；这段投入不会写进账单，但会推迟其他工作。

回滚成本常被忽略。换完之后要能退回旧实现，数据格式、接口契约、部署配置都要留退路；没有退路的替换，本质是一次单向迁移。

### 换之前常问的几个问题

第一，换掉之后，哪几章要重读？数据访问换了，第八、九、十五章都要重读；只换支付渠道，第二十五章改一节即可。

第二，换掉之后，免费档还够用吗？托管服务通常按用量计费，免费额度比自建低；先算清月成本，再决定。

第三，换掉之后，排障路径变长还是变短？多一个托管服务，就多一个控制台与一套日志；出问题时要在两处对照。

第四，团队里有人维护吗？自建组件需要有人负责升级与备份；没有明确负责人，自建会在半年后变成无人区。

第五，迁移是一次性的还是长期的？换数据库要写迁移脚本并验证数据，换支付渠道要重新走一遍对账；评估工作量时按长期算。

第六，能不能先用适配层隔离？把外部依赖包在一个模块里，换实现时只改一处；这比一开始就追求“可替换”更实际。

### 怎么用这两份清单

遇到本书没写的主题，先看第一份清单：如果主题在列，说明是刻意省略，按给出的方向另找资料。

拿到一个新需求，先判断它落在哪一章。落在清单里的，说明本书没有对应实现，需要另找资料；落在某章里的，回到该章看边界。

考虑替换某个组件时，看第二份清单的对应章节与差异，判断影响范围；四行里“谁会换”最有用，它描述的是触发条件。

两条原则。第一，先跑通再替换，没有可用的基线，替换后无法判断是否变好。第二，一次只换一个，同时换数据库与认证，出问题无法定位。

清单会过时。版本、价格、免费额度都在变，使用前核对官方页面；本书写作时的事实以正文标注的版本为准。

把决定写下来。替换了哪个组件、什么版本、什么日期、当时为什么，四条记在 `docs/decisions.md`。半年后回看，能判断当时的理由是否还成立。

复核的时机有三个：免费额度调整、用量翻倍、故障复盘。三个时机之外，不要为了跟版本而升级；升级会带来新的边界，边界要重新测。
