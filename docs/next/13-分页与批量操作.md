# 第 13 章 分页与批量操作

这一章处理列表页的两类操作：读出下一批数据，以及一次修改多条记录。

分页的常见写法是 `limit 20 offset 40`。数据量小的时候它工作正常，数据量一大就暴露三个问题：深页查询变慢，翻页期间有人插入会看到重复行，有人删除会漏掉行。游标分页（keyset pagination）把「跳过前 N 行」换成「从某一行之后开始」，三个问题一起消失。

批量操作的问题在失败之后。循环里逐条删除，删到第 93 条时数据库报错，前 93 条已经删了，后 7 条没删，用户看到一句「删除失败」，刷新之后数量对不上。正确做法是用一条语句改完一批，或者明确接受「尽力而为」并把逐条结果告诉用户。

涉及的概念有 OFFSET 与 keyset 的取舍、排序键与 tie-breaker、游标编解码、`limit + 1` 判断下一页、`= any($1::uuid[])` 的数组比较、单语句的原子性、把大任务转成后台 job。

基线是 Next.js 16.4.6 与 Postgres 15，示例接在第 8 章的 `files` 表上。本机没有 `psql` 与本地 Supabase，涉及查询计划的数字标「未验证」，形状与判断方法可以照用。

## 13.1 两种分页的代价

`offset 40 limit 20` 的语义是「按排序跳过前 40 行，取接下来 20 行」。数据库必须真的数出前 40 行，再丢掉。翻到第 800 页时，它要读 16000 行才能返回 20 行。

成本随页码线性增长，这是第一个代价。可以用 `explain (analyze, buffers)` 验证：

```sql
-- 需要本地库和若干万行数据，标「未验证」
explain (analyze, buffers)
select id from public.files
where team_id = 'aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa'::uuid
  and status = 'ready'
order by created_at desc, id desc
limit 20 offset 16000;
```

`Index Scan` 节点的 `actual rows` 会远大于 20，说明它真的读了 16020 行然后丢掉 16000 行。把 `offset` 改成 0 再跑，两个数字的差就是深页的代价。

第二个代价是插入导致的重复。用户停在第 2 页，此时有新人上传三个文件，这三个排在最前面，整个窗口往下推了三行。用户点「下一页」时，第 2 页末尾的三行会重新出现在第 3 页开头。

第三个代价是删除导致的漏。翻页期间删掉三行，窗口上移三行，有三行从来没有在任何一页显示过。用户说「我明明有四个文件，怎么只看到三个」，查库四个都在。

这三个代价只在「数据多 + 有人同时写」时出现。后台报表类页面两个条件都不满足，用 offset 更简单，也能跳页。游标分页的取舍见下表。

| 维度 | OFFSET | 游标（keyset） |
| --- | --- | --- |
| 深页成本 | 随页码线性增长 | 与页码无关，固定读一页 |
| 翻页期间插入 | 出现重复行 | 不重复 |
| 翻页期间删除 | 漏行 | 不漏 |
| 跳页 | 支持 | 不支持 |
| 精确总数 | 可以单独 count | 需要额外查询或估算 |

判断标准只有一条：这个列表会不会在深页被频繁读取，同时又在被并发写入。两个条件都满足才换。

## 13.2 游标分页的规则

游标分页换了一个问法。原来的问法是「跳过前 40 行」，新问法是「找到上一页最后一行，从它后面取 20 行」。

坐标必须能唯一定位一行。只用 `created_at` 不够，批量上传的文件时间戳可能完全相同，`where created_at < $2` 会把同一时刻的其它行一起跳过。因此排序末尾要带主键：

```sql
create index files_team_ready_created_idx
  on public.files (team_id, status, created_at desc, id desc)
  where status = 'ready';
```

`id` 在这里叫 tie-breaker。有了它，`(created_at, id)` 构成全序，任意两行都能比出先后。索引的列顺序要与查询匹配：`team_id` 与 `status` 是等值条件，`created_at` 与 `id` 是排序，顺序反了就用不上索引。

查询要写成两条，不要合并。

```sql
-- 第一页
select id, name, mime, size_bytes, status, created_at::text
from public.files
where team_id = $1 and status = 'ready'
order by created_at desc, id desc
limit $2;

-- 后续页：$2 是上一页最后一行的 created_at 文本，$3 是它的 id
select id, name, mime, size_bytes, status, created_at::text
from public.files
where team_id = $1 and status = 'ready'
  and (created_at, id) < ($2::timestamptz, $3::uuid)
order by created_at desc, id desc
limit $4;
```

`(created_at, id) < ($2, $3)` 是行比较，语义是「时间更早，或者时间相同但 id 更小」，正好等于「排在它后面」。写成 `created_at < $2 or (created_at = $2 and id < $3)` 结果一样，但行比较能让 Postgres 直接用索引定位。

不要图省事写成一条带 `($2 is null or ...)` 的 SQL。这种写法会让优化器放弃索引，两条 SQL 各走各的计划才是游标分页快的前提。

`created_at` 取 `::text` 有具体原因。`timestamptz` 在库里精确到微秒，node-postgres 默认把它转成 JS `Date`，精度只剩毫秒。微秒被截断后，同一毫秒内的多行会算出相同坐标，翻页时被跳过。取文本可以让数据库的原始字符串一路传到下一次查询，不经过 `Date`。

`limit` 设成「每页条数 + 1」,一次查询同时判断有没有下一页。返回 N+1 行说明还有下一页，砍掉最后一行，用第 N 行的坐标当 `nextCursor`；只返回 N 行说明到底了。

总数是游标分页的弱点。三条路各有代价：直接 `count(*)` 在几十万行上是几百毫秒到几秒；`pg_class.reltuples` 免费但误差可能几倍，只适合「约 1.2 万条」这种文案；维护计数表准确，代价是每条写路径都要记得更新。

文件列表不显示总数，只显示「有没有下一页」。用户来这里是为了继续找文件，精确总数在这里换不来什么，却要付一次全表扫描。

游标也有失效的时刻。翻页期间某一行被更新，它可能从后面跑到前面，用户会跳过它；某一行被删掉，它原来的位置空出来，前后两页都不会重复，也不会漏。前者偶尔发生，接受即可；要求严格一致的场景（导出对账、结算）用事务加快照读，把整批读放在一个 `repeatable read` 事务里。

游标分页不适合「按热度排序」。热度会变，昨天排第 50 的行今天可能排第 3，用户翻到第 5 页时，它已经不在那个位置。可变排序键只适合 offset，或者先把排序结果物化到一张表再翻页。

排序字段变了，旧游标就失效。游标记录的是「这一行在某个排序下的位置」，换成按文件名排序之后，同一个坐标毫无意义。处理方式有两种：排序变化时丢掉游标回第一页，或者把排序方式编进 URL，游标只在同一排序内有效。

筛选条件变化同理。用户点了「只看图片」，URL 多了筛选参数却保留旧游标，他会从「全部文件」的某个位置开始看图片，前面的图片永远看不到。任何筛选、搜索、排序、团队切换都要清掉游标。

边界情况还有一个：团队里只有 3 个文件，少于每页条数。此时 `limit + 1` 取回 3 行，`hasMore` 为假，`nextCursor` 是 `null`，页面显示「没有更多了」。这个分支要专门测，空列表、刚好一页、正好整页这三种情况各跑一次，返回值互不相同。

## 13.3 游标的编解码与列表函数

编解码只写一次，三个列表页才不会长出三种行为。

```ts
// src/lib/cursor.ts
export type Cursor = { createdAt: string; id: string }

export function encodeCursor(cursor: Cursor): string {
  return Buffer.from(JSON.stringify(cursor), 'utf8').toString('base64url')
}

/**
 * 解不出来返回 null，不抛。
 * 用户会手改 URL，会收藏旧链接，会在两版部署之间来回切。
 */
export function decodeCursor(raw: string): Cursor | null {
  try {
    const parsed: unknown = JSON.parse(
      Buffer.from(raw, 'base64url').toString('utf8'),
    )
    if (typeof parsed !== 'object' || parsed === null) return null
    const { createdAt, id } = parsed as Record<string, unknown>
    if (typeof createdAt !== 'string' || typeof id !== 'string') return null
    if (Number.isNaN(Date.parse(createdAt))) return null
    if (
      !/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i.test(id)
    ) {
      return null
    }
    return { createdAt, id }
  } catch {
    return null
  }
}
```

用 `base64url`，不要明文拼 `?after=2026-11-14T15:40:00Z,abc`。冒号与加号在 query string 里要转义，且以后加排序字段时 URL 结构要改，老链接全部失效。

游标不加签名。它只决定「从哪一行之后开始」，`team_id` 永远由服务端从会话里取，改游标最多把自己翻到本团队的另一个位置，翻不出权限边界。真正防越权的是查询里的 `where team_id = $1`，签名不承担这个职责。

列表函数把两种查询封在一起。

```ts
// src/lib/files.ts
import { query } from '@/lib/db'
import { decodeCursor, encodeCursor } from '@/lib/cursor'

export type FileRow = {
  id: string
  name: string
  mime: string
  sizeBytes: number
  status: 'pending' | 'ready' | 'deleted'
  createdAt: string
}

export type Page<T> = { items: T[]; nextCursor: string | null }

export const PAGE_SIZE = 20
export const MAX_PAGE_SIZE = 50

const COLUMNS =
  'id, name, mime, size_bytes, status, created_at::text as created_at_text'

export async function listTeamFiles(
  teamId: string,
  options: { cursor?: string; limit?: number } = {},
): Promise<Page<FileRow>> {
  // limit 来自 URL，是不可信输入：非数字、负数、巨大值都要夹住
  const limit = Math.min(
    Math.max(Number(options.limit) || PAGE_SIZE, 1),
    MAX_PAGE_SIZE,
  )
  const cursor = options.cursor ? decodeCursor(options.cursor) : null

  const { rows } = cursor
    ? await query<Record<string, unknown>>(
        `select ${COLUMNS} from public.files
         where team_id = $1 and status = 'ready'
           and (created_at, id) < ($2::timestamptz, $3::uuid)
         order by created_at desc, id desc
         limit $4`,
        [teamId, cursor.createdAt, cursor.id, limit + 1],
      )
    : await query<Record<string, unknown>>(
        `select ${COLUMNS} from public.files
         where team_id = $1 and status = 'ready'
         order by created_at desc, id desc
         limit $2`,
        [teamId, limit + 1],
      )

  const hasMore = rows.length > limit
  const items = (hasMore ? rows.slice(0, -1) : rows).map((row) => ({
    id: String(row.id),
    name: String(row.name),
    mime: String(row.mime),
    // bigint 列被驱动读成字符串，不转会渲染成 "1024"，比较也会翻车
    sizeBytes: Number(row.size_bytes),
    status: row.status as FileRow['status'],
    // 原样保留数据库文本，不要 toISOString()
    createdAt: String(row.created_at_text),
  }))

  const last = items.at(-1)
  return {
    items,
    nextCursor:
      hasMore && last
        ? encodeCursor({ createdAt: last.createdAt, id: last.id })
        : null,
  }
}
```

`limit + 1` 与 `rows.slice(0, -1)` 配合，省掉一次 `exists` 查询。`Number(row.size_bytes)` 同样必要：`bigint` 列被 node-postgres 读成字符串，React 渲染成带引号的数字，比较大小会得到错误结果。

## 13.4 接到页面与无限滚动

页面只负责取参数、调函数、渲染。

```tsx
// src/app/(app)/teams/[slug]/files/page.tsx
import Link from 'next/link'
import { requireUser } from '@/lib/auth'
import { requireMembership } from '@/lib/teams'
import { listTeamFiles } from '@/lib/files'
import { formatDateOnly } from '@/lib/format'

export default async function FilesPage({
  params,
  searchParams,
}: PageProps<'/(app)/teams/[slug]/files'>) {
  const user = await requireUser()
  const { slug } = await params
  // Next.js 16：searchParams 是 Promise，必须 await
  const { cursor } = await searchParams
  const { team } = await requireMembership(slug, user.id)

  const page = await listTeamFiles(team.id, {
    cursor: typeof cursor === 'string' ? cursor : undefined,
  })

  return (
    <section>
      <h1>文件</h1>
      <ul>
        {page.items.map((file) => (
          <li key={file.id}>
            {file.name} · {formatDateOnly(file.createdAt)}
          </li>
        ))}
      </ul>
      {page.nextCursor ? (
        <Link
          href={`/t/${slug}/files?cursor=${encodeURIComponent(page.nextCursor)}`}
        >
          下一页
        </Link>
      ) : (
        <span>没有更多了</span>
      )}
    </section>
  )
}
```

翻到第 200 页时，第一次点击仍走首页查询，之后的每次「下一页」都只读 21 行，耗时与页码无关。URL 里会出现类似 `?cursor=eyJjcmVhdGVkQXQiOi...` 的字符串，它是可读的 base64 编码，不要当成安全 token，也不要放进权限判断。

翻页链接默认会被预取。视口内的 `<Link>` 会提前请求目标路由，等于每次多看一页都在后台多查一次数据库。列表页翻页频繁，给「下一页」加 `prefetch={false}`，用户真的点了才查。第一页正常预取，它是最常回访的位置。

URL 只保留游标，不要顺手把已加载的条目也塞进去。游标能让页面在任何设备上复现同一位置，把 `items` 序列化进 URL 只会让链接变长，刷新时还要丢弃。

要改成无限滚动，逻辑不变，换一个触发时机。先加一个给客户端调用的接口。

```ts
// src/app/api/files/route.ts
import { NextResponse } from 'next/server'
import { requireUser } from '@/lib/auth'
import { getActiveTeam } from '@/lib/teams'
import { listTeamFiles } from '@/lib/files'

export async function GET(request: Request) {
  const user = await requireUser()
  const team = await getActiveTeam()
  if (!team) return NextResponse.json({ error: '没有团队' }, { status: 403 })

  const { searchParams } = new URL(request.url)
  const page = await listTeamFiles(team.id, {
    cursor: searchParams.get('cursor') ?? undefined,
  })
  return NextResponse.json(page)
}
```

客户端把已加载的条目攒在 state 里，用哨兵元素触发加载。

```tsx
// src/components/files-feed.tsx
'use client'

import { useCallback, useEffect, useRef, useState } from 'react'

type FileRow = { id: string; name: string; createdAt: string }
type Page = { items: FileRow[]; nextCursor: string | null }

export function FilesFeed({ initial }: { initial: Page }) {
  const [items, setItems] = useState(initial.items)
  const [cursor, setCursor] = useState(initial.nextCursor)
  const [loading, setLoading] = useState(false)
  const sentinel = useRef<HTMLDivElement>(null)

  const loadMore = useCallback(async () => {
    if (!cursor || loading) return
    setLoading(true)
    try {
      const res = await fetch(`/api/files?cursor=${encodeURIComponent(cursor)}`)
      if (!res.ok) return
      const next = (await res.json()) as Page
      // 用 id 去重：网络重试或重复请求不会出现两份
      setItems((prev) => {
        const seen = new Set(prev.map((item) => item.id))
        return [...prev, ...next.items.filter((item) => !seen.has(item.id))]
      })
      setCursor(next.nextCursor)
    } finally {
      setLoading(false)
    }
  }, [cursor, loading])

  useEffect(() => {
    const node = sentinel.current
    if (!node || !cursor) return
    const observer = new IntersectionObserver(
      (entries) => {
        if (entries[0]?.isIntersecting) void loadMore()
      },
      { rootMargin: '200px' },
    )
    observer.observe(node)
    return () => observer.disconnect()
  }, [loadMore, cursor])

  return (
    <ul>
      {items.map((file) => (
        <li key={file.id}>{file.name}</li>
      ))}
      <div ref={sentinel} aria-hidden />
      {loading ? <li>加载中……</li> : null}
      {!cursor ? <li>没有更多了</li> : null}
    </ul>
  )
}
```

`rootMargin: '200px'` 是提前量，等哨兵真的进入视口才加载会有明显停顿。`id` 去重应对并发触发：快速滚动时观察器可能回调两次，同一个游标取回同一批数据。`!cursor` 时不再观察，否则滚到底部会无限请求。

首屏由服务端直接传第一页进去，不用多一次请求。

```tsx
// src/app/(app)/teams/[slug]/files/page.tsx（片段）
import { FilesFeed } from '@/components/files-feed'

return <FilesFeed initial={page} />
```

## 13.5 批量操作：一条语句改完

批量删除最常见的写法是循环。

```ts
// 错误示范：循环里逐条删，不要这样写
export async function deleteFilesWrong(ids: string[]) {
  for (const id of ids) {
    await query('update public.files set status = $1 where id = $2', [
      'deleted',
      id,
    ])
  }
  revalidatePath('/files')
}
```

一百个文件就是一百次数据库往返。中间任何一次失败，前面的已经删了，后面的没删，用户看到「删除失败」，刷新发现少了一大半。

正确写法是一条语句。

```ts
// src/lib/files.ts
export async function softDeleteFiles(
  teamId: string,
  ids: string[],
): Promise<number> {
  if (ids.length === 0) return 0
  const { rows } = await query<{ id: string }>(
    `update public.files
        set status = 'deleted', deleted_at = now()
      where team_id = $1
        and status = 'ready'
        and id = any($2::uuid[])
      returning id`,
    [teamId, ids],
  )
  return rows.length
}
```

`id = any($2::uuid[])` 是一次往返改完一批。`where team_id = $1` 是防越权的关键：即使前端塞进别的团队的 id，也一条都改不到。

批量也有上限。界面上一次最多选 100 个，有三个理由。一次点太多，说明用户已经看不完这些行，误操作的概率上升。请求体要装下 100 个 uuid，加上其他字段仍在 1MB 的 action body 上限之内。真删错时，100 行的恢复成本还能接受。

`rows.length` 是真正改到的条数，可能小于传入的数量。有些文件已经被别人删了，有些不属于这个团队。两个数字都要告诉用户。

```ts
// src/app/(app)/teams/[slug]/files/actions.ts
'use server'

import { revalidateTag } from 'next/cache'
import { requireUser } from '@/lib/auth'
import { requireMembership } from '@/lib/teams'
import { softDeleteFiles } from '@/lib/files'
import { activityCache } from '@/lib/cache-keys'

export async function deleteFilesAction(slug: string, formData: FormData) {
  const user = await requireUser()
  const { team, role } = await requireMembership(slug, user.id)
  if (role !== 'owner' && role !== 'admin') {
    return { error: '只有管理员能删除文件' }
  }

  const ids = formData.getAll('ids').map(String).filter(Boolean)
  if (ids.length === 0) return { error: '没有选中文件' }

  const deleted = await softDeleteFiles(team.id, ids)

  // 第二个参数是必填的 cacheLife 档位，不传会直接报错
  revalidateTag(activityCache.tag(team.id), 'max')

  return deleted === ids.length
    ? { ok: `已删除 ${deleted} 个文件` }
    : { ok: `已删除 ${deleted} 个，另外 ${ids.length - deleted} 个已被别人删过` }
}
```

单条 `update` 在数据库层面是原子的，匹配到的行一起改，不存在改一半。真正的不确定性只剩「匹配到几条」，这个数字直接回给用户。勾三个文件，在另一个标签页先删掉其中一个，再回来提交，返回的是「已删除 2 个，另外 1 个已被别人删过」，，避免只给一句「失败」。

多选状态放在客户端。`useState` 存 id 集合，`useOptimistic` 让删除立刻从界面消失。

```tsx
// src/components/file-selection.tsx
'use client'

import { useOptimistic, useState, useTransition } from 'react'
import { deleteFilesAction } from '@/app/(app)/teams/[slug]/files/actions'

type FileRow = { id: string; name: string }

export function FileSelection({ slug, files }: { slug: string; files: FileRow[] }) {
  const [selected, setSelected] = useState<Set<string>>(new Set())
  const [hidden, setHidden] = useOptimistic<Set<string>, string[]>(
    new Set(),
    (state, removed) => new Set([...state, ...removed]),
  )
  const [pending, startTransition] = useTransition()

  const visible = files.filter((file) => !hidden.has(file.id))

  function toggle(id: string) {
    setSelected((prev) => {
      const next = new Set(prev)
      if (next.has(id)) next.delete(id)
      else next.add(id)
      return next
    })
  }

  function remove() {
    const ids = [...selected]
    startTransition(async () => {
      setHidden(ids)
      const formData = new FormData()
      ids.forEach((id) => formData.append('ids', id))
      const result = await deleteFilesAction(slug, formData)
      setSelected(new Set())
      if ('error' in result) return
    })
  }

  return (
    <div>
      {visible.map((file) => (
        <label key={file.id}>
          <input
            type="checkbox"
            checked={selected.has(file.id)}
            onChange={() => toggle(file.id)}
          />
          {file.name}
        </label>
      ))}
      <button onClick={remove} disabled={pending || selected.size === 0}>
        删除选中的 {selected.size} 个
      </button>
    </div>
  )
}
```

`useOptimistic` 解决「点了删除要等一秒才消失」的体感问题。它只在 transition 期间生效：请求成功，真实数据替换乐观状态；失败或抛错，界面自动回滚。

先查后改永远有间隙。如果流程是「先 select 确认都是 ready，再逐条 update」，两条语句之间可能有人把某行改成 deleted。把条件写进 `update ... where status = 'ready'`，让它和修改发生在同一条语句里，间隙就不存在了。这也是���条语句优于循环的第二个理由，第一个是往返次数。

客户端不做权限判断。按钮显示与否是体验问题，删不删得掉由 `requireMembership` 加 `where team_id` 决定。客户端判断永远不能当权限。

同样的形状可以套到批量改角色、批量归档、批量导出。批量改角色容易写错，因为它改的是关系，还要防最后一个 owner 被降级。

```ts
// src/lib/teams.ts
export async function bulkChangeRole(
  teamId: string,
  userIds: string[],
  role: 'admin' | 'member',
): Promise<{ changed: number; blocked: number }> {
  const { rows } = await query<{ user_id: string }>(
    `update public.team_members m
        set role = $3
      where m.team_id = $1
        and m.user_id = any($2::uuid[])
        and m.role <> 'owner'
      returning user_id`,
    [teamId, userIds, role],
  )
  return { changed: rows.length, blocked: userIds.length - rows.length }
}
```

`and m.role <> 'owner'` 把 owner 排除在外。转让 owner 是独立流程，两件事混在一起，早晚出现「团队没有 owner」的状态。`blocked` 是正常业务结果，界面显示「已改 7 人，3 人是 owner 未改动」。

## 13.6 数量再大就转后台

一千条以内，上面的写法够用。产品提到「支持全选」时，一个团队可能有两万个文件，请求里做完会同时遇到超时与没有进度反馈两个问题。

改成入队。复用 `jobs` 表。

```ts
// src/lib/jobs.ts
export async function enqueue(kind: string, payload: unknown) {
  const { rows } = await query<{ id: string }>(
    `insert into public.jobs (kind, payload, status, run_at)
     values ($1, $2::jsonb, 'queued', now())
     returning id`,
    [kind, JSON.stringify(payload)],
  )
  return rows[0].id
}
```

Action 只做三件事：校验、入队、返回 `jobId`。

```ts
// src/app/(app)/teams/[slug]/files/actions.ts（片段）
export async function deleteAllSelectedAction(slug: string, formData: FormData) {
  const user = await requireUser()
  const { team, role } = await requireMembership(slug, user.id)
  if (role !== 'owner' && role !== 'admin') {
    return { error: '只有管理员能删除文件' }
  }

  const ids = formData.getAll('ids').map(String).filter(Boolean)
  if (ids.length > 1000) {
    const jobId = await enqueue('files.soft_delete', { teamId: team.id, ids })
    return { jobId, ok: '文件较多，已转入后台处理' }
  }
  return { ok: `已删除 ${await softDeleteFiles(team.id, ids)} 个文件` }
}
```

消费者按 `kind` 分支，每次取 500 个 id，逐批调用 `softDeleteFiles`，把 `attempts` 与 `last_error` 写回 `jobs`。

前端拿 `jobId` 之后轮询状态，间隔逐步退避。

```tsx
// src/components/job-progress.tsx
'use client'

import { useEffect, useState } from 'react'

export function JobProgress({ jobId, onDone }: { jobId: string; onDone: () => void }) {
  const [status, setStatus] = useState<'queued' | 'running' | 'done' | 'failed'>(
    'queued',
  )

  useEffect(() => {
    let cancelled = false
    let delay = 1000

    async function poll() {
      const res = await fetch(`/api/jobs/${jobId}`)
      if (cancelled) return
      const data = (await res.json()) as { status: typeof status }
      setStatus(data.status)
      if (data.status === 'done' || data.status === 'failed') {
        if (data.status === 'done') onDone()
        return
      }
      delay = Math.min(delay * 1.5, 5000)
      setTimeout(poll, delay)
    }

    void poll()
    return () => {
      cancelled = true
    }
  }, [jobId, onDone])

  return (
    <p>{status === 'running' ? '正在删除……' : status === 'queued' ? '排队中……' : '完成'}</p>
  )
}
```

任务粒度要按「一段能重试的工作」切。一次给一万个 id，消费者中途被重启，重跑时整批重来；切成每批 500，失败只影响一批，`attempts` 也更有参考价值。批与批之间没有事务边界，中途失败时前面的批次已经生效，这符合「尽力而为」的语义，返回值里要带上进度。

三个细节决定轮询是体验还是事故。退避：固定 200 毫秒时，一百个用户同时删文件就是每秒五百次请求。卸载时停：`cancelled` 标记防止组件卸载后继续 `setState`。只信 `done`：HTTP 200 只代表查到了状态，不代表任务完成。

轮询接口要鉴权，并且只能查自己提交的任务。`/api/jobs/[id]` 里先 `requireUser()`，再在返回前核对 `payload.teamId` 与当前团队一致。job id 是 uuid，猜不出来，但泄露一次就会变成长期可读的状态接口。

任务多到轮询不划算时换成 SSE 或 WebSocket，把「每 5 秒问一次」改成「服务端推一次」。前提是实例之间能广播，单实例的内存广播多副本下会漏，需要 Redis 的发布订阅或队列。

任务侧要幂等。消费者可能被重启，同一个 job 被执行两次。`softDeleteFiles` 本身幂等，第二次匹配不到 `status = 'ready'` 的行，返回 0；如果任务里有发邮件、扣配额这类副作用，就要靠 `jobs.status` 的条件更新或标记表兜底。

## 13.7 软删除之后

`status = 'deleted'` 只让行从列表消失。对象存储里的字节还在，团队配额也不会自动下降。

清理必须异步做，并且幂等。

```ts
// src/app/api/cron/jobs/route.ts（在原有 kind 分支里加一段）
case 'files.cleanup': {
  const { rows } = await query<{ id: string; storage_path: string }>(
    `select id, storage_path from public.files
      where status = 'deleted' and deleted_at < now() - interval '7 days'
      order by deleted_at
      limit 500`,
  )
  if (rows.length === 0) break

  const paths = rows.map((row) => row.storage_path)
  const { error } = await admin.storage.from('files').remove(paths)
  if (error) throw new Error(error.message)

  await query('delete from public.files where id = any($1::uuid[])', [
    rows.map((row) => row.id),
  ])
  break
}
```

留七天有原因。窗口内用户点错还能找回，七天之后真删，存储才回落。

计数会偏。如果在 `teams` 上维护了 `file_count`，删除时忘了减，列表页显示「12 个文件」而实际只剩 9 个。要么每次 `count(*)`，要么把计数更新放进同一个事务。

七天窗口还能免费换来撤销。

```ts
// src/app/(app)/teams/[slug]/files/actions.ts（片段）
export async function restoreFilesAction(slug: string, formData: FormData) {
  const user = await requireUser()
  const { team, role } = await requireMembership(slug, user.id)
  if (role !== 'owner' && role !== 'admin') {
    return { error: '只有管理员能恢复文件' }
  }

  const ids = formData.getAll('ids').map(String).filter(Boolean)
  const { rows } = await query<{ id: string }>(
    `update public.files
        set status = 'ready', deleted_at = null
      where team_id = $1 and status = 'deleted' and id = any($2::uuid[])
      returning id`,
    [team.id, ids],
  )
  revalidateTag(activityCache.tag(team.id), 'max')
  return { ok: `已恢复 ${rows.length} 个文件` }
}
```

界面上在删除成功的提示里加一个「撤销」按钮。它比二次确认对话框有用：用户已经做完了，不打断他，给一条退路。

## 13.8 边界与失败模式

游标指向的行被删了不影响结果。`(created_at, id) < (x, y)` 比较的是值，不会去查那一行，照样能筛出更靠后的行。

游标被手改成格式正确但不存在的 id 时，查询返回空数组。用户看到「没有更多了」，比看到 500 好。

两版部署之间游标格式变了，旧书签会解不出来。`decodeCursor` 返回 `null`，页面回到第一页，不抛错。

团队被删或用户被移出之后，`requireMembership` 会先拦下来，走不到分页查询。

`limit` 来自 URL，必须夹在 1 到 50 之间。直接信任它时，请求 `?limit=100000` 会让数据库一次返回十万行，同时消耗内存与带宽。

排序字段与索引不匹配时，游标分页会退化成全表扫描加排序。判断方法是 `explain` 看有没有 `Sort` 节点，有就说明索引没被用上。

批量操作失败的语义要写清楚。单语句是原子，但对「尽力而为」的业务，部分成功是正常结果，要在返回值里带上成功数与失败原因。要求全有或全无的场景（扣配额、转移所有权）必须包事务，不能靠单语句蒙混。

`revalidateTag` 的第二参在 Next.js 16 是必填的。漏传会直接报 `Expected 2 arguments, but got 1.`，界面上的表现是删除成功但列表不刷新。

计数对不上时先确认口径。列表页查的是 `status = 'ready'`，`count(*)` 把 deleted 的行也算进去，两个数字天然不同。一条 SQL 能看出差在哪：

```sql
select status, count(*)
from public.files
where team_id = $1
group by status
order by status;
```

三个数字加起来才是这张表的真实行数。界面上显示哪个，取决于界面想表达什么。

软删除不会触发级联。如果 `files` 之外还有引用文件的表，真删那一批行时会撞外键，清理任务要按依赖顺序进行，或者先确认没有引用。

## 13.9 检查点

1. 深页不再变慢

造到三十万行，翻到第 200 页，看 Network 里该请求的 TTFB。改造后应在 200 毫秒以内，改造前是秒级。标「未验证」，具体数字随机器与数据分布变化，形状稳定。

2. 翻页期间插入不重复

两个标签页都停在第 2 页，用脚本插入三行，B 页点「下一页」。新插入的三行不出现，原来的行也不重复。

```sql
insert into public.files
  (team_id, uploader_id, name, mime, size_bytes, storage_path, status)
select
  'aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa'::uuid,
  '11111111-1111-4111-8111-111111111111'::uuid,
  'race-' || g || '.png', 'image/png', 1, 'demo/x.png', 'ready'
from generate_series(1, 3) as g;
```

3. 坏游标回到第一页

把 URL 的 `cursor` 手动改成 `abc`，页面应回到第一页，不出现 500。

4. 批量删除只发一次数据库往返

勾选 100 个文件删除，服务端日志里只有一条 `update` 语句。返回文案里的数字等于实际删除数，避免「全部成功」这类笼统说法。

5. 超过上限时被夹住

把 `MAX_PAGE_SIZE` 改成 50，请求 `?limit=10000`，返回条数不超过 50。

6. 筛选切换时游标被清掉

点「只看图片」，URL 里不再带 `cursor`，列表从第一张图片开始。

7. 两种分页的成本差

对同一个列表分别跑 offset 版与游标版的 `explain (analyze)`，比较 `actual rows`。差值就是评审分页代码时要看的数字。标「未验证」。

## 13.10 常见错误

`operator does not exist: uuid = text`

`id = any($2::uuid[])` 里的数组参数忘了写 `::uuid[]`，Postgres 把字符串数组当 text 处理。补上类型转换即可。

**翻页后顺序不稳定**

`order by created_at desc` 少了 `id desc`。时间相同的行在不同查询里顺序不固定，加了 tie-breaker 才稳定。

**第 2 页之后少一行**

`limit` 写成了每页条数，没有 `+1`。多取的那一行被当成「下一页的第一行」之后又没还回来，结果就是每页都少一行。

`Expected 2 arguments, but got 1.`

`revalidateTag` 在 Next.js 16 的第二个参数必填，传 cacheLife 档位（`'max'`、`'hours'`、`'days'` 等）。不传不会取默认值，编译期或运行期直接报错。

**删除成功但列表没变**

忘了 `revalidateTag`，或者 tag 拼错。tag 由 `activityCache.tag(teamId)` 统一生成，不要手写字符串。

`Number(row.size_bytes)` 之后仍是字符串

那一列的类型是 `numeric`。`numeric` 被驱动读成字符串并保留小数位，先在 SQL 里 `size_bytes::bigint`，再 `Number()`。

## 13.11 这一章在做什么

分页与批量操作看起来是两个功能，其实是同一个目标的两面：让一次请求的工作量不随数据量增长。

分页把「读多少行」固定成每页条数，用游标换掉 offset。批量把「往返多少次」固定成一次，用 `= any(array)` 换掉循环。两者都是把数量从变量变成常量。

三个判断可以复用。需要跳页、又没人同时写，offset 够用。需要「下一页」、又有并发写，用游标加 tie-breaker，索引列顺序跟着查询形状走。一次操作涉及多行，用一条 SQL 或一个事务，不要在循环里逐条执行。

游标分页有不适用场景。后台报表要「第 3 页 / 共 12 页」，用户要跳页，数据几万行，没人同时写，offset 更简单也更好用。

下一章讲缓存。这一章算出来的「下一页」，如果缓存策略写错，用户看到的可能是上一版的数据。
