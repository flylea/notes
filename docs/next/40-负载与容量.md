# 第 40 章 负载与容量

压测要回答三个问题：这台机器能同时服务多少人，超过哪里开始变慢，慢下来时先垮的是哪一层。三个问题各有对应的量：并发上限、延迟拐点、瓶颈位置。

本章讲怎么把这三个数测出来、记下来，并换算成 VPS 规格。涉及的概念有并发与吞吐、延迟分位、错误率、连接池和排队。

先说明边界。压测出来的数字只在被测环境成立，换机器、换数据库规格、改一次索引，结论都会变。比起某个具体数字，更重要的是流程：在哪个环境压、压哪条链路、怎么读结果、结果记在哪里。

## 40.1 四个指标与三条链路

四个指标要分开看。

并发数（connections）是同时在处理的请求数。请求速率（RPS）是每秒完成的请求数。两者的关系由延迟决定：并发等于速率乘以平均延迟。同样的并发，延迟翻倍，速率就减半。

延迟看分位数，不看平均值。p50 是中位数，p95 表示一百个请求里有五个比它慢。用户感知到的卡顿由 p95 和 p99 决定，平均值会把长尾摊平。p95 够用的场景是普通页面浏览，p99 要看的场景是支付和登录，这类操作卡一次用户就走了。压测报告里至少要有 p50、p95、p99 三列。

错误率要分类。4xx 说明请求本身有问题，压测参数写错了或者登录态过期；5xx 说明服务端出错；超时说明请求被排队或者卡住。并发和用户数还要换算一次。一个用户平均每 30 秒发一个请求，40 req/s 大约对应 1,200 个在线用户，峰值集中在整点还会更高。

三类混在一起看，会得出错误结论。错误率超过百分之一，这一轮的延迟数据基本不可用。

平均值会骗人。十个请求里九个 20ms、一个 3s，平均是 318ms，看起来还能接受；p99 是 3s，那个用户的页面卡了三秒。压测报告里写平均值的，通常是没有认真看结果。

链路要分开压。一个站点至少有三类请求：静态页、动态渲染页、写接口。混在一起压，得到一个平均数，没法归因。静态页碰不到数据库，动态页每个请求都要查库，写接口还要加锁和写日志。三者的容量差一个数量级很正常。

还有一个容易忽略的上限：带宽。响应体 1MB、速率 40 req/s，就是 40MB/s，折合 320Mbps，多数 VPS 的出口带宽先在这里打满。压测时看 `docker stats` 的网络流量，和标称带宽对一下。

## 40.2 压测环境的四条纪律

第一条，不在开发服务器上压。`next dev` 带热更新和源码映射，渲染速度比生产慢三到五倍，压出来的数字没有参考价值。用 `pnpm build && pnpm start` 跑构建产物。

第二条，不经过 CDN 和反向代理。压测机直接打应用端口，测的是应用本身。经过 Cloudflare 时，请求在边缘被缓存，测到的是 CDN 的容量。

第三条，给应用限资源。压测机的 CPU 会抢被测进程的时间，本机压本机时尤其明显。用容器限制 CPU 和内存，让数字更接近 VPS。注意 cgroup 配额和核数不完全等价：给 2 个核的配额，进程仍然能看到宿主机的核数，Node 的线程池会按宿主机核数开，调度上会有抖动。

```bash
docker run --rm -p 3000:3000 \
  --cpus=2 --memory=4g \
  -e NODE_ENV=production \
  -e NEXT_PUBLIC_SUPABASE_URL="$NEXT_PUBLIC_SUPABASE_URL" \
  -e SUPABASE_SERVICE_ROLE_KEY="$SUPABASE_SERVICE_ROLE_KEY" \
  teamstack:latest
```

第四条，压测机与被测机分开。有条件的话放到另一台机器，至少放到另一个容器。数据库与应用的相对位置也要记下来：数据库同机时，压测过程中两者抢 CPU，容量数字偏乐观。数据库也要限规格，否则本地 Postgres 用掉四个核，应用只剩两个核的量。

压测前固定三个变量：代码版本、数据量、缓存状态。代码版本用 `git rev-parse --short HEAD` 记下来；数据量写清楚被测表有多少行，一万行和一百万行的结论完全不同；缓存状态写清楚是冷启动还是预热过。三个变量没记，第二轮就无从对比。

压测前先确认接口通。

```bash
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" \
  -H "Cookie: $SESSION_COOKIE" \
  http://127.0.0.1:3000/api/teams
```

返回 `200 0.082`，说明登录态和路由都对。返回 401 时不要直接压，压出来的错误率百分之百，没有任何信息量。

## 40.3 autocannon：单接口探底

autocannon 用 Node 写，装一次就能用，适合快速探一个接口的极限。

不用 ab 和 wrk 的原因很实际：ab 单线程，压不满多核；wrk 要写 Lua 脚本，改一个请求头都要查文档。两者都不支持 HTTP/2，压出来的并发模型和线上差一截。

```bash
pnpm add -D autocannon
```

```bash
# 50 个并发连接，持续 20 秒，测动态接口
pnpm exec autocannon -c 50 -d 20 \
  -H "Cookie: $SESSION_COOKIE" \
  http://127.0.0.1:3000/api/teams
```

输出是一张表，关键几行如下。

```text
Running 20s test @ http://127.0.0.1:3000/api/teams
50 connections

┌─────────┬──────┬──────┬───────┬───────┬─────────┬─────────┬──────────┐
│ Stat    │ 2.5% │ 50%  │ 97.5% │ 99%   │ Avg     │ Stdev   │ Max      │
├─────────┼──────┼──────┼───────┼───────┼─────────┼─────────┼──────────┤
│ Latency │ 41ms │ 88ms │ 402ms │ 610ms │ 112.4ms │ 96.2ms  │ 1204ms   │
└─────────┴──────┴──────┴───────┴───────┴─────────┴─────────┴──────────┘
┌─────────┬─────────┬─────────┬─────────┬─────────┬──────────┬─────────┐
│ Stat    │ 1%      │ 2.5%    │ 50%     │ 97.5%   │ Avg      │ Stdev   │
├─────────┼─────────┼─────────┼─────────┼─────────┼──────────┼─────────┤
│ Req/Sec │ 312     │ 388     │ 442     │ 467     │ 438.6    │ 21.4    │
└─────────┴─────────┴─────────┴─────────┴─────────┴──────────┴─────────┘
```

`Req/Sec` 的中位数是 442，`Latency` 的 p99 是 610ms。`Stdev` 大说明波动大，同样 442 的中位数，标准差 21 和 120 是两种系统。这两个数先记下来，它们是一轮压测的基线。

`-p` 参数会按固定并发发起请求，容易失真，测延迟时不要加。

`-c` 的值要试出来。先从 10 开始，每轮翻倍，直到 p99 明显跳起来。连接数超过服务端的并发处理能力之后，多出来的连接只是在排队，数字不会更好看。想要阶梯压测，用下一节的 k6。

带登录态的接口必须在请求头里带 cookie，或者在压测脚本里先登录拿 token。用未登录的请求压受保护接口，等于在压 proxy 的重定向逻辑。

同一个接口要压两遍：冷缓存和热缓存。第一轮把缓存打热，数据状态稳定之后再记录数字。ISR 页面在压测过程中会触发后台再生成，那一瞬间的 CPU 峰值会被算进延迟，这个现象要单独记一笔。

### 写接口怎么压

写接口的脚本要多做两件事：造唯一数据，跑完清理。

```js
// k6/write.js（节选）
import http from "k6/http";
import { check } from "k6";

export default function () {
  const stamp = `${Date.now()}-${__VU}-${__ITER}`;
  const res = http.post(
    `${__ENV.BASE_URL}/api/teams`,
    JSON.stringify({ name: `压测团队 ${stamp}`, slug: `load-${stamp}` }),
    {
      headers: { "Content-Type": "application/json", Cookie: __ENV.SESSION_COOKIE },
    },
  );
  check(res, { "已创建": (r) => r.status === 200 || r.status === 201 });
}
```

`__VU` 和 `__ITER` 是 k6 的内置变量，和时间戳组合能保证名称唯一。名字重复会撞唯一约束，错误率虚高。

跑完用 SQL 清掉。

```bash
psql "$DATABASE_URL" -c "delete from activity_logs where team_id in (select id from teams where slug like 'load-%');"
psql "$DATABASE_URL" -c "delete from teams where slug like 'load-%';"
```

先删子表再删父表，反过来会被外键挡住。压一万个团队会连带写几万条日志，清理脚本要提前准备好。

## 40.4 k6：阶梯负载

k6 用 JavaScript 写脚本，支持按到达率发起请求，能画出负载与延迟的关系。

```bash
brew install k6
```

```ts
// k6/load.js
import http from "k6/http";
import { check, sleep } from "k6";
import { Rate } from "k6/metrics";

const serverErrors = new Rate("server_errors");
const clientErrors = new Rate("client_errors");

export const options = {
  scenarios: {
    ramp: {
      executor: "ramping-arrival-rate",
      startRate: 2,
      timeUnit: "1s",
      preAllocatedVUs: 20,
      maxVUs: 200,
      stages: [
        { target: 10, duration: "30s" },
        { target: 40, duration: "60s" },
        { target: 80, duration: "60s" },
        { target: 0, duration: "15s" },
      ],
    },
  },
  thresholds: {
    http_req_failed: ["rate<0.01"],
    http_req_duration: ["p(95)<800", "p(99)<2000"],
  },
};

const cookie = __ENV.SESSION_COOKIE;

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/api/teams`, {
    headers: { Cookie: cookie },
  });

  check(res, {
    "status 200": (r) => r.status === 200,
    "返回团队数据": (r) => r.body.includes("teams"),
  });

  if (res.status >= 500) serverErrors.add(1);
  if (res.status >= 400 && res.status < 500) clientErrors.add(1);

  sleep(1);
}
```

```bash
BASE_URL=http://127.0.0.1:3000 \
SESSION_COOKIE="$SESSION_COOKIE" \
k6 run k6/load.js --summary-export=k6/result.json
```

输出末尾是一段汇总。

```text
http_req_duration........: avg=204ms  p(90)=512ms  p(95)=824ms  p(99)=1.9s
http_req_failed..........: 1.24%  ✓ 0.00%  ✗ 1.00%
```

`1.24%` 已经超过阈值百分之一，这一轮不达标。`check` 失败只记录次数，不影响退出码，要卡住流水线得靠 `thresholds`。再看 `rps`，如果速率在阶段升到 80 之后反而下降，说明系统进入过载：请求排队，完成的更少。

到达率模型更接近真实用户。固定并发在系统变慢时会自动降低发送速率，掩盖过载；到达率模型按时间发请求，压出来的拐点更清楚。

`preAllocatedVUs` 是预分配的虚拟用户，`maxVUs` 是上限。

`thresholds` 可以接进 CI：`k6 run` 的退出码在阈值不达标时非零，流水线会红。放进 CI 的压测只跑短时版本，压 30 秒，覆盖单接口，不做完整的阶梯。设得太小，脚本自己会成为瓶颈，压不出服务端的极限。

每轮结果存一份，文件名带日期和版本：`k6/results/20261115-abc1234.json`。脚本和结果都进仓库，下次改完代码用同一条命令重跑，才有可比性。数字要带单位和口径：p95 是单请求耗时，RPS 是完成数，错误率按状态码分段统计。口径不同，两个数字放在一张表里就会误读。

## 40.5 读曲线：找到拐点

压测的价值在于找出曲线从哪里开始弯。下面是一轮阶梯压测的结果。

| 到达率 | p50 | p95 | p99 | 错误率 | 判断 |
| --- | --- | --- | --- | --- | --- |
| 10 req/s | 45ms | 90ms | 130ms | 0% | 线性区 |
| 20 req/s | 52ms | 110ms | 160ms | 0% | 线性区 |
| 40 req/s | 78ms | 210ms | 340ms | 0% | 开始变弯 |
| 60 req/s | 210ms | 780ms | 1.6s | 0.4% | 拐点 |
| 80 req/s | 900ms | 2.4s | 5.1s | 4.8% | 过载区 |

40 req/s 是这一段还能接受的上限，60 req/s 是拐点，80 req/s 之后错误率快速上升。规划容量取 40 的七成，也就是 28 req/s，作为常态负载的上限。

曲线为什么会弯，有三个常见原因。CPU 跑满之后，请求在操作系统的运行队列里等；连接池用尽之后，请求等一条空闲连接；垃圾回收触发时，主线程暂停，所有请求一起变慢。三种原因在曲线上长得像，用 40.6 节的方法区分。

七折的理由是排队。系统利用率到七成之后，延迟开始按排队公式上升，一点流量波动就会推动延迟翻倍。压测时看到的「还能跑」，是因为负载均匀；真实流量有尖峰，尖峰一来就进入过载。

再算并发上限。利特尔法则：并发等于吞吐乘以延迟。取 40 req/s 和 p95 的 210ms，并发约等于 8.4。这个数字是平均在途请求数，实际峰值要高一些，按两倍估算，约 17。

```bash
# 用 jq 从导出的结果里取关键指标
jq -r '.metrics | to_entries[]
  | select(.key | test("http_req_duration|http_req_failed|http_reqs"))
  | "\(.key)\t\(.value.values.p95 // .value.values.rate // .value.values.count)"' \
  k6/result.json
```

这条命令从 `result.json` 里摘出 p95、失败率和请求总数，贴进文档之前先自己核一遍单位。

## 40.6 瓶颈定位：先看进程，再看连接

压测中延迟上升时，按顺序查四层。

第一层看进程的 CPU 和内存。

```bash
docker stats --no-stream
```

输出里 `CPU %` 接近 100 而 `MEM USAGE` 平稳，瓶颈在 CPU。`docker stats` 的百分比按单核算，四个核跑满会显示 400%。看到 400% 说明进程已经用满全部核，再加负载只会排队。

CPU 不高但延迟高，看上下文切换：`pidstat -w 1` 里的 `cswch/s` 突然升高，说明线程在等锁或者等 IO，应用层有阻塞操作。内存持续上涨到上限，随后出现 `Reached heap limit`，瓶颈在内存或者存在泄漏。

第二层看火焰图。Node 自带 CPU 采样，不需要额外工具。

```bash
node --cpu-prof --cpu-prof-dir=./profile .next/standalone/server.js
```

压测结束后打开 `chrome://inspect` 的 Profiler 标签，载入生成的 `.cpuprofile`。火焰图里最宽的那一列就是热点。看两列数字：self 是函数自身耗时，total 是包含子调用的耗时。self 高说明这一行代码本身慢，total 高而 self 低说明慢在下游。常见的热点是 JSON 序列化、日期格式化、正则匹配，还有同步的加密运算。

第三层看连接池。每个应用实例有一个连接池上限，数据库有一个总连接数上限。两者相乘不能超过数据库的限制。

```text
应用实例 4 个 × 每池 15 条 = 60 条
Postgres max_connections = 100
Supavisor 池上限 = 80
```

三个数里最小的是 60，说明还没到数据库上限。实例数加到 8 个时就是 120，超过 100，会出现 `sorry, too many clients already`。

```bash
psql "$DATABASE_URL" -c "select state, count(*) from pg_stat_activity group by state;"
```

输出里 `active` 的数量就是正在执行的查询数。`idle in transaction` 不为零，说明有事务开着没提交，连接被占住。这个状态持续存在，连接池很快会被耗尽。

第四层看具体查询。

```bash
psql "$DATABASE_URL" -c "select calls, round(mean_exec_time::numeric, 2), left(query, 60) from pg_stat_statements order by total_exec_time desc limit 5;"
```

按总耗时排序，排第一的查询最值得优化。`calls` 特别大而单次耗时不高的，通常是缺索引的循环查询。

```bash
psql "$DATABASE_URL" -c "explain (analyze, buffers) select * from activity_logs where team_id = '...' order by created_at desc limit 50;"
```

输出里出现 `Seq Scan` 且 `Rows Removed by Filter` 很大，说明索引没命中。`shared read` 远大于 `shared hit`，说明缓存没热，需要加索引或者缩小扫描范围。

数据库之外还有一层：外部依赖。压测中每个请求都要调 Stripe 或 Resend，延迟由对方决定，测出来的容量里含对方的耗时。做法是把环境变量指向一个本地假服务，或者把外部调用挪进 `after()` 异步做。外部服务超时的降级也要测：把假服务设成延迟两秒，看页面能不能正常降级。

Redis 也是同样的道理。限流计数、会话、缓存都走 Redis，压测时它的 QPS 可能比数据库还高。`redis-cli info stats` 里的 `instantaneous_ops_per_sec` 和 `rejected_connections` 要一起看。

## 40.7 从压测结果换算 VPS 规格

一轮压测得到的是单进程的容量，换算到规格还要乘实例数，再打折。

| 规格 | 单实例容量（动态页） | 建议部署实例 | 规划容量 |
| --- | --- | --- | --- |
| 1 核 2G | 15 req/s | 1 | 10 req/s |
| 2 核 4G | 40 req/s | 2 | 28 req/s |
| 4 核 8G | 90 req/s | 4 | 63 req/s |
| 8 核 16G | 180 req/s | 8 | 126 req/s |

表里的单实例容量来自本章的压测，换成别的机器要重新测。

容量不随核数线性增长。双核到四核，容量通常只涨一倍多一点，原因是数据库连接、内存带宽和锁竞争。往上加实例之前，先确认数据库能承受连接数的增长。

多实例用 PM2 起。

```js
// ecosystem.config.cjs
module.exports = {
  apps: [
    {
      name: "teamstack",
      script: ".next/standalone/server.js",
      instances: "max",
      exec_mode: "cluster",
      env: {
        NODE_ENV: "production",
        PORT: 3000,
        NEXT_SERVER_ACTIONS_ENCRYPTION_KEY:
          process.env.NEXT_SERVER_ACTIONS_ENCRYPTION_KEY,
      },
    },
  ],
};
```

`instances: "max"` 按 CPU 核数起进程。每池连接数按这个公式定：数据库上限除以实例数，再除以二，留一半给迁移、监控和手工查询。实例数是动态的时候，把每池上限写死，别用默认值。有一个前提必须满足：所有实例用同一个 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`。这个值每个实例随机生成时，请求落到另一个实例会报 `Failed to find Server Action`。

前面加 nginx，注意两处配置。

```nginx
upstream teamstack {
  server 127.0.0.1:3000;
  server 127.0.0.1:3001;
  keepalive 64;
}

server {
  listen 443 ssl;
  http2 on;

  location / {
    proxy_pass http://teamstack;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
  }
}
```

`keepalive 64` 让 nginx 和后端复用连接，省掉三次握手。`Connection ""` 必须清空，否则每个请求都新建连接。`proxy_buffering off` 是为流式响应准备的，开了缓冲，SSE 会被攒成一整块再发。

压测走 HTTP 还是 HTTPS 也要统一。TLS 握手有开销，会话复用之后差异缩小，但首字节时间会多几毫秒。线上跑 HTTPS，压测就用 HTTPS，别拿 HTTP 的数字往上套。

横向扩展有三个前提。会话不能存在进程内存里，要放 cookie 或者 Redis。ISR 的本地缓存每个实例一份，要换共享的 cache handler。定时任务和队列消费者要单独跑一个进程，否则每个实例都会执行一遍。

换规格还是加实例，要看瓶颈在哪一层。单进程 CPU 打满、p99 随负载上升，加实例能摊平；单进程 CPU 不高而 p99 高，多半卡在数据库或外部依赖，加实例只会让它们更挤。判断方法很简单：加一个实例再压一轮。容量接近翻倍，瓶颈在应用层；几乎没变，瓶颈在下游。

## 40.8 结果记录

压测结果写进仓库，格式固定，后来的人才能对比。

记录里必须有环境和已知失真。

每轮压测加一条记录，别覆盖旧的。两次记录之间只改一个变量（实例数、索引、代码版本），否则数字变了也说不清是哪个改动带来的。报告写给两个人看：决策的人只看结论和当前容量，执行的人看复现命令和瓶颈位置。

三个月后复测一次。依赖升级、数据量增长、加了一个索引，任何一个都会让旧数字失效。复测结果追加到同一份文件，保留历史。半年后回头看，没有环境信息的数字等于没测。

## 40.9 边界与失败模式

写接口的压测要造数据，造出来的数据会留在库里。团队名加时间戳后缀，跑完用脚本删掉。压测写接口会同时写 `activity_logs`，一轮几千条，日志表会膨胀，记得清理。

k6 的 `sleep(1)` 会限制每个虚拟用户的请求间隔。想去掉间隔做极限压测，把 `sleep` 删掉，同时把 `maxVUs` 调大。忘记删会让速率上不去，误判为容量到顶。

压测期间不要看日志的实时输出。终端渲染几千行日志会占用 CPU，影响被测进程。用 `docker logs --tail 100` 事后看。

压测脚本本身也要进仓库。谁都能跑、跑完结果能对比，容量数字才会被持续维护。写在个人机器上的脚本，两个月后就没人知道怎么复现了。

压测会给真实数据留下痕迹，尽量在预发环境跑。必须在生产压时，挑低峰时段，压测账号单独建，出问题能立刻停。

尖峰测试用另一份配置。

```ts
// k6/spike.js（节选）
export const options = {
  scenarios: {
    spike: {
      executor: "constant-arrival-rate",
      rate: 200,
      timeUnit: "1s",
      duration: "20s",
      preAllocatedVUs: 100,
      maxVUs: 600,
    },
  },
};
```

200 req/s 打 20 秒，观察恢复时间：负载撤掉之后，延迟用多久回到基线。恢复慢说明队列里堆了活，或者连接池没释放。

突发流量和均匀负载的结论不同。均匀 40 req/s 不垮，十秒内从 0 冲到 200 req/s 可能直接崩。有余力的话补一轮尖峰测试，用 `constant-arrival-rate` 把速率固定在高位，观察恢复时间。

Node 的堆内存上限要和容器限制匹配。容器给 4G，Node 默认堆上限可能只有 2G，压测中提前触发垃圾回收，延迟曲线出现周期性尖峰。

压测报告里写清楚测的是哪个版本、哪台机器、哪条链路。缺一项，数字就没法复用。下次有人问「这台机器能扛多少」，答案应当是一份文件，能直接拿给后来的人看。

## 40.10 检查点

1. `docker stats --no-stream` 里被测进程的 CPU 上限与 VPS 规格一致，内存上限不超过机器内存的八成。
2. `k6 run k6/load.js` 跑完，`result.json` 里有 `p95`、`http_req_failed`、`http_reqs` 三项，错误率有明确数值。
3. 结果表里至少三档到达率，能指认拐点那一行，例如「60 req/s 时 p95 从 210ms 涨到 780ms」。
4. 压测峰值时执行 `psql -c "select count(*) from pg_stat_activity"`，输出不超过数据库上限的七成。
5. `docs/capacity.md` 里有环境、结果表、结论、已知失真四段，别人按复现命令能跑出同一量级的数字。
6. `node --cpu-prof` 生成的 profile 能在 `chrome://inspect` 打开，火焰图里能指出一个具体的热点函数。

## 40.11 常见错误

**1. 连接被打满**

现象：压测中报 `sorry, too many clients already`。原因是实例数乘以每池连接数超过 `max_connections`。改法：调小每池上限，或者降实例数，两个参数一起看。

2. 连接 6543 端口超时

现象：日志里 `ETIMEDOUT`，指向 6543 端口。Supabase 的 6543 是事务模式连接池，长时间运行的查询会被断开。改法：连接串加 `?pgbouncer=true`，或者把长查询挪到 5432 直连。

**3. 速率很高但错误率也高**

现象：`rps` 数字好看，`http_req_failed` 是百分之三。原因是压测脚本没带登录态，或者接口限流把请求挡回去了。改法：先用 curl 确认返回 200，再看错误体的具体消息。

**4. 堆内存打满**

现象：进程退出，日志里 `Reached heap limit Allocation failed`。原因是容器内存限制与 Node 堆上限不匹配，或者存在泄漏。改法：把 `--max-old-space-size` 设到容器内存的七成，然后用火焰图找持续增长的分配点。

5. socket hang up

现象：压测输出里大量 `socket hang up`。原因是连接复用的 keepalive 超时，或者 nginx 的 `Connection` 头没清空。改法：nginx 配置里加 `proxy_set_header Connection ""`，并把 `keepalive_timeout` 调到比上游空闲超时更长。

**6. 启动瞬间被压垮**

现象：压测第一秒就出现 `connection refused`。原因是应用还没监听端口，k6 已经开始发请求。改法：脚本里加一个等待循环，或者用 `docker healthcheck` 确认端口就绪再开始。

以上六个问题都能回答，这一节的练习就算完成。测得准，才能规划得准。

## 40.12 这一章在做什么

这一章把容量问题拆成四个指标和三条链路：并发、吞吐、延迟分位、错误率，静态页、动态页、写接口分别压。工具用 autocannon 探单接口，k6 跑阶梯。读结果时找拐点，按七折定规划容量，用利特尔法则换算并发。瓶颈按进程、连接池、数据库、具体查询的顺序查，最后把数字换算成 VPS 规格和实例数，写进 `docs/capacity.md`。

压测最大的价值是暴露假设。你以为瓶颈在数据库，压出来发现是 JSON 序列化；你以为 4 核能扛两倍，压出来发现连接池先满。做一轮，把结论写下来，比记住任何一个数字都有用。

第 41 章讲系统跑起来之后的另一面：出了问题怎么定位。请求 id、结构化日志、分布式追踪和错误上报，四件事配合起来，才能把一次失败还原成一条时间线。
