# 第 23 章 文件上传与对象存储

文件功能要保存两样东西：文件的字节，以及关于文件的元数据（名字、大小、类型、属于哪个团队、谁传的）。这一章讲这两样东西分别放在哪里，以及一条上传从开始到结束要经过哪几步。

涉及四个概念：对象存储、预签名 URL、`pending` 到 `ready` 的状态机、文件魔数。

上传值得单独用一章讲：最直觉的写法在这个项目里跑不通。把文件塞进表单、交给 Server Action 接收，请求体默认上限是 1MB。把上限调大能过本地测试，但部署到 Serverless 平台后，平台的请求体上限是 4.5MB。把字节存进 Postgres 的 `bytea` 列也能跑，但备份、复制、内存都会被它拖慢。

正确的形状是把字节直接送进对象存储，应用服务器只负责发通行证和事后核对。这一步跨出去，后面所有的状态、权限、清理问题都跟着变了。

前置条件：第 8 章的 `files` 表、第 15 章的 `requireUser()`、第 22 章的 `requireTeam()`。对象存储用 Supabase Storage，本地由 Supabase CLI 提供。

## 23.1 元数据与字节分开放

`files` 表里没有存字节的列，只有 `storage_path` 指向桶里的对象。这个决定要先算三笔账。

第一笔是请求体上限。Server Action 的默认上限是 1MB，配置项是 `experimental.serverActions.bodySizeLimit`。调到 2MB 或 10MB 都能配，但请求体要先落进 Node 进程的内存，50MB 乘上并发数就是几百 MB 常驻。部署到 Vercel 这类平台，平台自己还有 4.5MB 的请求体上限，改配置绕不过去。

第二笔是带宽。字节从浏览器到应用服务器，再从应用服务器转发到存储，同样的内容走两遍网络。50MB 的文件传 100 次是 5GB 出网流量，其中一半是重复的。

第三笔是数据库的代价。`bytea` 列会把大字段放进 TOAST 存储，读一行小元数据也可能顺带触发大对象读取；备份、恢复、主从复制全跟着变大；浏览器没法用 Range 只取一段，也没法交给 CDN。这些字节本来不需要事务保护。

| 方案 | 请求体上限 | 带宽 | 数据库压力 | 适合的文件 |
| --- | --- | --- | --- | --- |
| 存进 `bytea` | 受数据库连接与内存限制 | 一份 | 备份、复制一起变大 | 头像、图标，几十 KB |
| 经应用服务器转发 | Server Action 1MB，平台 4.5MB | 两遍 | 无 | 小文件、必须逐字节处理的场景 |
| 浏览器直传对象存储 | 存储服务自己的限制 | 一遍 | 无 | 大多数用户上传 |

`bytea` 并没有被完全排除。头像、图标这类几十 KB、只由服务端读取、不需要 CDN 的文件，放数据库里反而省事：备份一份就全有了，不用管两个存储的一致性。判断用三个问题：会不会超过几 MB、要不要让浏览器直接取、要不要独立于数据库管生命周期。三个里有一个答案是“要”，就该用对象存储；三个都答“不要”，放进数据库反而少一处要维护的存储。

对象存储提供四样东西：按对象独立设置访问权限、给单个对象签发临时链接、按前缀列举与删除、支持 HTTP Range 只取一段。这四样正好对应上传功能的需要。

应用服务器中转也并非完全没有位置。需要在服务端逐字节处理的场景，比如加密、加水印、转码，字节必须经过进程。这类处理通常也在上传之后异步做，直接让请求体扛着大文件穿过应用层，收益很小。这里的判断标准是：处理能不能放到对象存好之后，能放就直传。

直传还有一个前提：存储服务要允许浏览器跨域 PUT。本地 Supabase 默认放开，线上换成自定义域名后要检查 CORS 配置，未验证的部分以实际后台为准。跨域被拦时的表现是预检请求失败，控制台报 CORS 错误，并非 401。

## 23.2 三段式状态机

浏览器要写一个私有桶，需要服务端先签一个带过期时间的上传链接。光有链接还不够，真正难的是“传了一半”这种情况。

先看两种朴素的顺序各自留下什么。

先传字节、再写数据库行：用户传完 40MB，浏览器崩了，没来得及写行。桶里多了一个没人认领的对象，连它属于哪个团队都不知道。

先写行、再传字节：行写好了，用户在上传阶段关了页面。数据库里多一行 `pending`，指向一个不存在的对象，用户点下载 404，还占着配额。

两种顺序都在赌中间不会断。真实环境里断网、切热点、代理超时、手机锁屏都会断。所以要承认它是一段可能中断的流程，用状态机描述：

```
pending  ──(对象存在 + 校验通过)──▶  ready
   │
   └──(超时未确认 / 校验失败)──▶  deleted
```

对应三个动作。登记：服务端校验名字、大小、类型，插一行 `pending`，签一个上传链接。传字节：浏览器拿着链接直传对象存储。确认：浏览器说传好了，服务端去桶里核实对象存在、大小对、魔数对，改成 `ready`。

`pending` 行先于字节存在，所以哪怕后面全失败，也有一行记录说明谁、哪个团队、打算传多大的什么文件。反过来先传字节，失败时连线索都没有。

把中断点列全，才知道每一步谁负责收尾：

| 中断在哪 | 留下什么 | 谁收拾 |
| --- | --- | --- |
| 登记后、签链接失败 | 一行 `pending`，没有对象 | 登记代码当场标 `deleted` |
| 签了链接、还没传 | `pending` 行加一个有效链接 | 清理脚本，超时标 `deleted` |
| 传到一半 | `pending` 行，通常没有对象 | 清理脚本；用户重试复用同一个 `fileId` |
| 传完、没确认 | `pending` 行加完整对象 | 清理脚本，或用户重试确认 |
| 确认校验失败 | 对象删掉，行标 `deleted` | 当场处理完 |

原则是能当场处理的错误别留给清理脚本。清理脚本最快也要一小时才跑，它是兜底，并非主通道。

不能让前端直接写 `files` 表：写表需要服务端连接，服务端连接一给浏览器，等于把整个数据库交出去。也不能让前端决定 `storage_path`：路径里带着团队 id，前端可以填别家的，对象就写进了别人的目录。路径、配额、状态全都要在服务端算。

`pending` 行还有第二个用处：配额。团队用量按 `status in ('pending', 'ready')` 求和，在登记时拦住超额请求，不用等 50MB 传完才说超了。

三个状态够用，是因为中间过程不需要持久化。传到多少字节、还剩几秒，这些信息浏览器自己知道，服务端不关心；服务端只关心两个事实：对象在不在、校验过没过。要展示进度，前端读 `XMLHttpRequest` 的上传事件就够了，不必写库。多一个 `uploading` 状态，就多一处需要清理的中间态，也意味着多一条超时规则。

## 23.3 建桶、加索引、准备服务端客户端

桶是对象存储里的顶层目录。它的限制应该设在桶上，不要只写在应用代码里，因为上传链接一旦泄露，别人可以绕过页面直接 PUT。

```toml
# supabase/config.toml（追加）
[storage.buckets.files]
public = false
file_size_limit = "50MiB"
allowed_mime_types = ["image/png", "image/jpeg", "image/webp", "application/pdf", "text/plain"]
```

改完要重启本地服务才生效：

```bash
pnpm supabase stop
pnpm supabase start
```

`file_size_limit` 由存储服务自己执行，超了直接返回 413，应用代码拦不住的它也能拦。`allowed_mime_types` 检查的是请求里声明的 `Content-Type`，挡不住改过后缀的 HTML，那要靠 23.7 的魔数。

线上没有 `config.toml`。去 Dashboard 的 Storage 页面新建桶，名字 `files`，关闭 public，同样填 50MB 和五个类型。本地和线上最容易在这里对不上：本机设了白名单，线上一个没填，上线后才发现本机能传、线上 413。

再补一个索引，给“找超时未确认的行”用：

```sql
-- supabase/migrations/20261121100000_files_storage.sql
create index if not exists files_pending_created_idx
  on public.files (created_at)
  where status = 'pending';
```

部分索引只收 `pending` 的行，`ready` 的行不进索引，所以它比全表索引小得多。清理任务只关心 `pending`，就只索引 `pending`。

`storage_path` 上有唯一约束，它保证一个对象只被一行引用。哪天清理脚本算错，插入重复路径会直接失败，不会悄悄出现两个指向同一对象的“文件”。

服务端访问存储用 service_role 密钥，做成惰性单例：

```ts
// src/lib/storage.ts
import 'server-only'
import { createClient } from '@supabase/supabase-js'

export const FILES_BUCKET = 'files'

// service_role 会绕过 Storage 的 RLS，只在服务端用。
let admin: ReturnType<typeof createClient> | null = null

export function storageAdmin() {
  if (!admin) {
    admin = createClient(
      process.env.NEXT_PUBLIC_SUPABASE_URL!,
      process.env.SUPABASE_SERVICE_ROLE_KEY!,
      { auth: { persistSession: false, autoRefreshToken: false } },
    )
  }
  return admin
}

// 路径完全由服务端拼，不含用户输入。
export function originalPath(teamId: string, fileId: string) {
  return `${teamId}/${fileId}/original`
}
```

三个决定。

用 service_role，不用登录用户的会话。桶是私有的，走用户会话就得给 `storage.objects` 写一套 RLS；而所有读写都在服务端，成员关系已经用 `requireTeam()` 验过。少一套策略就少一处写错的地方。代价是这条连接权限极大，所以第一行 `import 'server-only'`：它一旦被打进客户端 bundle，构建立刻失败。

惰性初始化。`createClient()` 在模块加载时就要读环境变量，写成模块顶层常量，构建阶段还没有运行时变量，会报错。放进函数、第一次调用才读，构建就过。

路径形如 `teamId/fileId/original`。用户的文件名不进路径：中文、空格、`../`、超长名字都要处理，而展示用的名字已经在表里。

如果坚持让浏览器直接读桶，就要给 `storage.objects` 写 RLS，常见写法是用 `storage.foldername(name)[1]` 取路径第一段当团队 id，再查成员关系。这套策略能工作，但多一套策略就多一处可能写错的地方，而且每次查询都多一次成员判断。本项目所有读写都在服务端，用 service_role 加应用层校验更直接。路径的第二段就是文件 id，从路径能反推出归属。每个文件一个目录也并非为了整齐，是为了删除：删一个文件只需 `remove([path])`，清理脚本也能按目录判断对象齐不齐。第 24 章会往同一目录里加缩略图，平铺存放的话删单个文件就要精确知道它有几个衍生对象，漏一个就是孤儿。

service_role 绕过的是所有表的 RLS，不只是 Storage。这个客户端一旦被错误地 import 进页面组件，`server-only` 会拦住；但有人为了省事把它包一层再导出，就拦不住。团队里定一条规则：`src/lib/storage.ts` 只允许 Server Action、Route Handler 和脚本引用。

## 23.4 第一段：登记一行 pending

```ts
// src/app/(dashboard)/files/actions.ts
'use server'

import { randomUUID } from 'node:crypto'
import { db } from '@/lib/db'
import { requireUser } from '@/lib/auth'
import { requireTeam } from '@/lib/teams'
import { FILES_BUCKET, originalPath, storageAdmin } from '@/lib/storage'
import { storageLimitBytes, usedBytes } from '@/lib/quota'

const MAX_BYTES = 50 * 1024 * 1024

const ALLOWED_MIME = new Set([
  'image/png',
  'image/jpeg',
  'image/webp',
  'application/pdf',
  'text/plain',
])

export interface BeginUploadResult {
  error?: string
  upload?: { fileId: string; path: string; token: string }
}

export async function beginUpload(input: {
  name: string
  size: number
  mime: string
}): Promise<BeginUploadResult> {
  const user = await requireUser()
  const team = await requireTeam()

  const name = input.name.trim().slice(0, 255)
  if (!name) return { error: '文件名不能为空' }
  if (!ALLOWED_MIME.has(input.mime)) {
    return { error: '只支持 PNG / JPEG / WebP / PDF / TXT' }
  }
  if (!Number.isInteger(input.size) || input.size <= 0) {
    return { error: '文件是空的' }
  }
  if (input.size > MAX_BYTES) {
    return { error: '单个文件不能超过 50MB' }
  }

  const used = await usedBytes(team.id)
  if (used + input.size > storageLimitBytes(team.plan)) {
    return { error: '团队的存储空间不够了，先删掉一些文件' }
  }

  const fileId = randomUUID()
  const path = originalPath(team.id, fileId)

  await db
    .insertInto('files')
    .values({
      id: fileId,
      team_id: team.id,
      uploader_id: user.id,
      name,
      mime: input.mime,
      size_bytes: input.size,
      storage_path: path,
      status: 'pending',
    })
    .execute()

  const { data, error } = await storageAdmin()
    .storage.from(FILES_BUCKET)
    .createSignedUploadUrl(path)

  if (error || !data) {
    // 链接都没签出来，这行没有存在意义。
    await db
      .updateTable('files')
      .set({ status: 'deleted' })
      .where('id', '=', fileId)
      .execute()
    return { error: '没能创建上传链接，请重试' }
  }

  return { upload: { fileId, path: data.path, token: data.token } }
}
```

四个细节。

文件 id 在应用里用 `randomUUID()` 生成，不用数据库的 `default gen_random_uuid()`。因为路径需要 id，而路径要和行在同一次 `insert` 里写进去。先插入再拿返回值更新路径，多一次写，还多一段不一致窗口。

`size_bytes` 先写声明的值，不写 0。列表在确认前也要显示大小，写 0 会让用户看到“0 B”以为传坏了。声明值只是临时占位，确认时用真实大小覆盖。

大小和 MIME 全部来自客户端，不可信。它们的作用是快速失败、记下用户声明了什么。真正的核实在确认那一步，这里绝不能直接写 `ready`。

文件名只用于展示和下载时的 `Content-Disposition`，不参与路径拼接。把用户文件名拼进路径会带进两类问题：`../` 之类的路径穿越，以及不同系统对非法字符的规则不一致。`slice(0, 255)` 是为了和表上的长度约束一致，超长名字在数据库那一步会报错，提前截断能给出更好的提示。

签名失败时把行标 `deleted`，不要留着。留着就是一条永远无法完成的 `pending`，一小时后再被脚本收走，期间一直占配额。

## 23.5 配额在登记时拦

```ts
// src/lib/quota.ts
import { sql } from 'kysely'
import { db } from '@/lib/db'

export function storageLimitBytes(plan: string) {
  return plan === 'free'
    ? 5 * 1024 * 1024 * 1024
    : 100 * 1024 * 1024 * 1024
}

export async function usedBytes(teamId: string) {
  const row = await db
    .selectFrom('files')
    .select(sql<number>`coalesce(sum(size_bytes), 0)::bigint`.as('total'))
    .where('team_id', '=', teamId)
    .where('status', 'in', ['pending', 'ready'])
    .executeTakeFirst()

  return Number(row?.total ?? 0)
}
```

`pending` 也计入用量。如果只算 `ready`，同时发起十个上传，每个都看到还有空间，最后一起穿透配额。

按字节求和，不按文件个数。一个 50MB 的 PDF 和十个 5MB 的图片占用一样，但后者是十个对象、十次请求、十行记录。

并发下仍然有竞态：两个人同时读到 4.9GB，都通过检查，都传 50MB，总量超一点。要严格就得锁：`select ... from teams where id = $1 for update` 锁住团队行，或者维护一张 `team_storage_usage` 计数表。这一版先接受超一点点，第 27 章的对账任务会把真实用量和 `sum` 校准。

界面上直接显示 `usedBytes(team.id)` 和 `storageLimitBytes(team.plan)`，不需要额外字段。超过 80% 变黄，让用户在点上传之前就知道会不会被拒。

## 23.6 第二段：字节从浏览器直传

```tsx
// src/app/(dashboard)/files/upload-form.tsx
'use client'

import { useRouter } from 'next/navigation'
import { useRef, useState } from 'react'
import { createClient } from '@/lib/supabase/client'
import { beginUpload, confirmUpload } from './actions'

export function UploadForm() {
  const router = useRouter()
  const inputRef = useRef<HTMLInputElement>(null)
  const [busy, setBusy] = useState(false)
  const [status, setStatus] = useState<string | null>(null)
  const [error, setError] = useState<string | null>(null)

  async function handleChange(event: React.ChangeEvent<HTMLInputElement>) {
    const file = event.target.files?.[0]
    if (!file) return

    setBusy(true)
    setError(null)

    try {
      setStatus('登记中…')
      const begun = await beginUpload({
        name: file.name,
        size: file.size,
        mime: file.type,
      })
      if (begun.error || !begun.upload) {
        setError(begun.error ?? '上传失败')
        return
      }

      setStatus('上传中…')
      const supabase = createClient()
      const { error: uploadError } = await supabase.storage
        .from('files')
        .uploadToSignedUrl(begun.upload.path, begun.upload.token, file)

      if (uploadError) {
        setError('上传中断了，文件没有保存，可以重试')
        return
      }

      setStatus('校验中…')
      const confirmed = await confirmUpload(begun.upload.fileId)
      if (confirmed.error) {
        setError(confirmed.error)
        return
      }

      setStatus(null)
      router.refresh()
    } finally {
      setBusy(false)
      if (inputRef.current) inputRef.current.value = ''
    }
  }

  return (
    <div className="space-y-2">
      <input
        ref={inputRef}
        type="file"
        accept="image/png,image/jpeg,image/webp,application/pdf,text/plain"
        disabled={busy}
        onChange={handleChange}
        className="block text-sm"
      />
      {busy && status && <p className="text-sm text-gray-600">{status}</p>}
      {error && <p className="text-sm text-red-600">{error}</p>}
      <p className="text-xs text-gray-500">单个文件最大 50MB，不支持 SVG。</p>
    </div>
  )
}
```

浏览器端只有 publishable key，能写一个私有桶靠的是 URL 里的令牌，并非登录会话。`uploadToSignedUrl` 把 token 放进请求路径，存储服务验这个 token，不验你是谁。所以这一步即使用户退出登录也能完成，这正是签名的语义：签发那一刻已经把权限赋予了这段 URL。

注意这里没有进度条。`uploadToSignedUrl` 内部是一次 `PUT`，没有进度回调，只能显示阶段文案。要真实百分比得自己用 `XMLHttpRequest` 往 `signedUrl` 上 PUT，代价是绕开 SDK 封装。这一版先要正确。

`accept` 只是给文件选择框的建议，用户可以切到“所有文件”，也可以直接改请求。真正的白名单在 `beginUpload` 里，和 23.7 的魔数。

直传还有一个失败模式值得知道：PUT 成功、响应丢失。网络在服务端写完之后断掉，浏览器认为失败，桶里其实已经有对象。用户点重试时走 `reissueUpload`，它会先删对象再重签，把这种半成功状态收干净。

## 23.7 第三段：确认时才写 ready

```ts
// 追加到 src/app/(dashboard)/files/actions.ts
import { detectMime } from '@/lib/file-type'

async function markDeleted(fileId: string) {
  await db
    .updateTable('files')
    .set({ status: 'deleted' })
    .where('id', '=', fileId)
    .execute()
}

export async function confirmUpload(
  fileId: string,
): Promise<{ error?: string; ok?: boolean }> {
  const team = await requireTeam()

  const file = await db
    .selectFrom('files')
    .selectAll()
    .where('id', '=', fileId)
    .where('team_id', '=', team.id)
    .executeTakeFirst()

  if (!file) return { error: '找不到这个文件' }
  if (file.status === 'ready') return { ok: true }
  if (file.status === 'deleted') return { error: '这个文件已经失效了' }

  const bucket = storageAdmin().storage.from(FILES_BUCKET)

  // 对象真的存在吗？大小对不对？只信存储服务的返回。
  const { data: blob, error } = await bucket.download(file.storage_path)
  if (error || !blob) {
    await markDeleted(file.id)
    return { error: '文件没有传上来，请重试' }
  }

  if (blob.size > MAX_BYTES) {
    await bucket.remove([file.storage_path])
    await markDeleted(file.id)
    return { error: '文件超过 50MB，已拒绝' }
  }

  const head = new Uint8Array(await blob.slice(0, 16).arrayBuffer())
  const detected = detectMime(head)

  if (detected !== file.mime) {
    await bucket.remove([file.storage_path])
    await markDeleted(file.id)
    return { error: '文件内容与类型不符，已拒绝' }
  }

  await db
    .updateTable('files')
    .set({ status: 'ready', size_bytes: blob.size })
    .where('id', '=', file.id)
    .execute()

  return { ok: true }
}
```

`where('team_id', '=', team.id)` 和 id 一起用。只按 id 查的话，任何人拿一个别人的 `fileId` 都能触发确认，把别人的 `pending` 行改掉。虽然看不到内容，但这是越权写。

只信 `requireTeam()` 拿到的团队，不信客户端传来的团队 id。传一个别家的 id，查询返回空，直接“找不到”，也不会泄露那个文件是否存在。

失败就删对象。校验不通过的对象留在桶里就是垃圾，而且它可能是个伪装成图片的 HTML。删掉，行标 `deleted`，两个存储保持一致。

`size_bytes` 用 `blob.size` 覆盖，不用客户端声明值。否则按大小计的配额就是摆设。

`ready` 直接返回成功。确认接口会被重复调用（刷新、网络重试、用户手快），幂等让它安全。

用三态字段而不加一个 `is_uploaded` 布尔，是因为布尔丢掉“失败过”这个事实。`deleted` 的行留着，能回答用户传过几次、被拒了几次，配额统计也能排除它。确认失败就物理删行的话，用户重试时文件会凭空消失，售后无从解释。异步流程的通用解法是保留记录、改状态。

代价是确认时把整个对象下载了一遍。50MB 的文件确认时占 50MB 内存，上传流量又走一次服务端。图片可以接受，第 24 章本来就要下载一次做裁剪，两件事合并成一次。50MB 的 PDF 不理想，生产上更常见的是只取前几百字节（对象存储支持 HTTP Range），或者浏览器先算哈希、服务端拿哈希核对。这一章先选完整下载一次这个最保守的写法，因为它不依赖任何没验证过的 API。

### 魔数校验

浏览器给 `File` 的 `type` 是从扩展名猜的。把 `evil.html` 改成 `photo.png`，`file.type` 就是 `image/png`。声明校验只能挡掉手滑，挡不住故意的。

真正的格式指纹在文件开头的字节里，改扩展名改不掉：JPEG 是 `FF D8 FF`，PNG 是 8 字节签名 `89 50 4E 47 0D 0A 1A 0A`，WebP 以 `RIFF` 开头、偏移 8 处是 `WEBP`，PDF 以 `%PDF` 开头。

```ts
// src/lib/file-type.ts

const ascii = (head: Uint8Array, from: number, length: number) =>
  String.fromCharCode(...head.slice(from, from + length))

export function detectMime(head: Uint8Array): string | null {
  const startsWith = (bytes: number[]) =>
    bytes.every((byte, index) => head[index] === byte)

  // JPEG：FF D8 FF，第三字节是段标记
  if (startsWith([0xff, 0xd8, 0xff])) return 'image/jpeg'

  // PNG：8 字节固定签名
  if (startsWith([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a])) {
    return 'image/png'
  }

  // WebP：RIFF 容器 + 偏移 8 处的 WEBP
  if (ascii(head, 0, 4) === 'RIFF' && ascii(head, 8, 4) === 'WEBP') {
    return 'image/webp'
  }

  if (ascii(head, 0, 4) === '%PDF') return 'application/pdf'

  // 文本没有魔数，只能反向判断：没有 NUL、没有控制字符。
  const looksLikeText = head.every(
    (byte) =>
      byte === 0x09 ||
      byte === 0x0a ||
      byte === 0x0d ||
      (byte >= 0x20 && byte !== 0x7f),
  )
  if (looksLikeText) return 'text/plain'

  return null
}
```

只读前 16 字节，是因为所有格式签名都在前 12 字节内。读更多没有额外信息，只是多传几 KB。

`looksLikeText` 是启发式，并非证明。它只能说明前 16 字节看起来像文本，不能保证整个文件是 UTF-8。文本的风险低，因为浏览器不会执行它，所以够用；要接受 HTML、JS 这类文件，必须换更严格的方案。

这个顺序不能反：先扫魔数，再做任何图片处理。第 24 章会用 sharp 解码图片，而解码器的解析器面对畸形文件时出过内存越界的问题。拿未验证的字节喂解码器，等于把攻击面交给第三方库。魔数校验很便宜，先做。

明确禁 SVG。SVG 是 XML，可以内嵌 `<script>`，当图片被浏览器内联打开时就是可执行文档，等价于一个存储型 XSS。真需要矢量图，让用户传 PNG，或者走单独的清洗流程。

下载响应还要带 `Content-Disposition: attachment`，浏览器只下载不渲染。签名时显式传 `{ download: name }`，不依赖存储服务的默认行为。以后真要做在线预览 PDF，用 iframe 指向一个不同域名的签名链接，别用主域渲染用户内容。

## 23.8 预签名链接的性质

浏览器没有桶的密钥，写对象靠预签名链接。服务端用密钥对“操作加路径加过期时间”签名，把签名拼进 URL；存储服务自己验签，通过就放行。

```ts
const { data, error } = await storageAdmin()
  .storage.from(FILES_BUCKET)
  .createSignedUploadUrl(path)
// data: { signedUrl, token, path }
```

上传链接不接受有效期参数。官方给的有效期是固定的 2 小时，从签发那一刻算。这个长度够用户传完 50MB，也不至于泄露后长期可用。别去找“能不能调成 5 分钟”的参数，没有。

下载链接相反，有效期由你指定，单位是秒：

```ts
const { data } = await storageAdmin()
  .storage.from(FILES_BUCKET)
  .createSignedUrl(path, 60, { download: name })
```

第二个参数 60 就是 60 秒，并非毫秒。写成 `Date.now() + 3600` 这种毫秒时间戳，会得到一个几万年之后才过期的链接，等于永不过期。这个错误很常见，因为它看起来是对的。

两种链接的差别：

- 签发方法：上传用 `createSignedUploadUrl(path)`，下载用 `createSignedUrl(path, expiresIn)`。
- 有效期：上传固定 2 小时不可配，下载由调用方按秒指定。
- 允许的操作：上传链接只写这一个路径，下载链接只读这一个路径。
- 泄露后果：上传链接让别人能往团队目录里塞一个对象，下载链接让别人拿走文件内容。
- 撤销方式：两者相同，删或移动对象、轮换签名密钥、等过期。

最后一条要单独说：单个签名链接撤不掉。

签名链接是自包含的凭证。验签发生在对象存储那一侧，它不会回头问数据库“这个链接还有效吗”。所以没有“吊销某一个链接”这个动作。能做的只有三件：删掉或移动对象，链接指向的路径没了；轮换签名密钥，所有链接一起失效，包括正在用的；等它过期。

这也决定了有效期的取舍方式。上传链接泄露，损失是一个能往团队目录里塞文件的口子，2 小时可以接受；下载链接泄露，损失是文件内容本身，60 秒就够浏览器打开。有效期按泄露后的最坏损失倒推，不按“用户大概多久能传完”倒推。

所以签名 URL 不要写进日志、不要塞进 analytics、不要放进 HTML 注释。日志系统往往比文件本身被更多人看到。

时钟偏差也值得注意。签名里带时间戳，客户端时钟比服务端快太多，链接会立刻被判过期；慢太多，会被判未生效。本地调试时如果链接一签出来就失效，先看系统时间。

轮换密钥是唯一能一次废掉全部链接的操作。它同时会让所有正在使用中的链接失效，包括用户已经打开但还没提交的上传表单。轮换要挑低峰，并且提前把表单里的“重新选择文件”路径准备好。这件事不适合自动化，属于事故响应手段。

## 23.9 列表页：每条链接只活 60 秒

```tsx
// src/app/(dashboard)/files/page.tsx
import Link from 'next/link'
import { Suspense } from 'react'
import { db } from '@/lib/db'
import { requireTeam } from '@/lib/teams'
import { FILES_BUCKET, storageAdmin } from '@/lib/storage'
import { UploadForm } from './upload-form'

export default function FilesPage() {
  return (
    <div className="mx-auto max-w-3xl space-y-6 p-6">

      <UploadForm />

function formatBytes(bytes: number) {
  if (bytes < 1024) return `${bytes} B`
  if (bytes < 1024 * 1024) return `${(bytes / 1024).toFixed(1)} KB`
  return `${(bytes / 1024 / 1024).toFixed(1)} MB`
}

async function FileList() {
  const team = await requireTeam()

  const files = await db
    .selectFrom('files')
    .select([
      'id',
      'name',
      'mime',
      'size_bytes',
      'storage_path',
      'status',
      'created_at',

  if (files.length === 0) {
    return (
      <div className="rounded-lg border border-dashed p-10 text-center">

        </p>
      </div>
    )
  }

  const bucket = storageAdmin().storage.from(FILES_BUCKET)

  const rows = await Promise.all(
    files.map(async (file) => {
      if (file.status !== 'ready') return { ...file, href: null }
      const { data } = await bucket.createSignedUrl(file.storage_path, 60, {
        download: file.name,
      })
      return { ...file, href: data?.signedUrl ?? null }
    }),
  )

  return (
    <ul className="divide-y rounded-lg border">

              {file.status === 'pending' && ' · 等待上传确认'}
            </p>
          </div>
          {file.href ? (
            <Link href={file.href} className="shrink-0 text-sm text-blue-600">

            </Link>

          )}
        </li>
      ))}
    </ul>
  )
}

function FilesSkeleton() {
  return (
    <div className="animate-pulse space-y-2">

```

60 秒是有意的。链接撤不掉，所以只能短。页面每次渲染都重新签，用户不会感觉到过期这件事。右键复制链接，等一分钟再粘到地址栏，返回 400，响应体里有 `InvalidJWT` 和 `jwt expired`。

`download: name` 让响应带 `Content-Disposition: attachment`，浏览器不内联渲染。对 PDF 和纯文本尤其重要，内联打开等于给了文件内容一个在站点域名下执行的机会。

不在服务端把桶设成公开、让浏览器直接拼地址，是因为公开桶意味着路径泄露就能永久访问，也无法按团队隔离。签名链接把谁、什么时候、能取哪个对象写进令牌，代价是每次取都要一次服务端调用。

100 个文件签 100 次，是 100 次 API 调用。文件多了换成 `createSignedUrls(paths, expiresIn)` 批量接口，一次签完。列表本身也要分页，别用 `offset`：上传持续插入新行，翻页时会重复或漏。用 `(created_at, id)` 游标，和活动日志一样。

列表里保留 `pending` 的行，显示“等待上传确认”。这并非 bug，它让用户知道有一个上传没成功。超过一小时没确认的会被脚本标成 `deleted`，从列表里消失。

列表页还可以顺手显示两个数字：已用空间和上限。`usedBytes()` 已经在配额检查里写过，复用它就行。数字比一句“空间不足”更早让人采取行动：看到 4.8 GB / 5 GB，用户会先删旧文件，不会等到传完 50MB 被拒。

## 23.10 失败与重试

重试要复用同一个 `pending` 行和同一个 `fileId`。重新登记会产生两行指向两个对象，用户看到重复文件，配额被算两次。

```ts
// 追加到 src/app/(dashboard)/files/actions.ts
export async function reissueUpload(
  fileId: string,
): Promise<BeginUploadResult> {
  const team = await requireTeam()

  const file = await db
    .selectFrom('files')
    .select(['id', 'storage_path', 'status'])
    .where('id', '=', fileId)
    .where('team_id', '=', team.id)
    .executeTakeFirst()

  if (!file) return { error: '找不到这个文件' }
  if (file.status !== 'pending') {
    return { error: '这个文件不在等待上传的状态' }
  }

  const bucket = storageAdmin().storage.from(FILES_BUCKET)

  // 签名上传不支持覆盖写，先删掉可能残留的对象。
  await bucket.remove([file.storage_path])

  const { data, error } = await bucket.createSignedUploadUrl(file.storage_path)
  if (error || !data) return { error: '没能重新创建上传链接' }

  return { upload: { fileId: file.id, path: data.path, token: data.token } }
}
```

把 `UploadForm` 的错误分支接上 `reissueUpload`，拿到新 token 重新 PUT，再调 `confirmUpload`。对用户是重试一次，对数据始终只有一行。

失败时不立刻把行标 `deleted`，是为了让用户还能重试。标了 `deleted`，`reissueUpload` 会拒绝，用户只能重新选文件，列表里还会多一条灰记录。留 `pending`，重试路径最短；一小时之后还没成功，才交给脚本收尾。

`remove` 那一步并非多余的。上一次 PUT 可能已经把对象写出来了，只是确认没跑完。`uploadToSignedUrl` 不支持覆盖已有对象，文档明确说 upsert 无效，不先删就会拿到“已存在”的错误。

`created_at` 是超时判据。没有它，分不清“刚开始传”和“卡了三小时”，清理脚本没有依据。所有带状态的流程都要有一个能算“多久算超时”的时间戳。

## 23.11 孤儿清理

上传会中断，中断会留下两种孤儿。行孤儿：`pending` 行指向的对象不存在，用户看到一个永远等待确认的文件。对象孤儿：对象传上去了但行没建成，或者行被删了，字节白占空间。

```js
// scripts/cleanup-orphans.mjs
// 用法：node --env-file=.env.local scripts/cleanup-orphans.mjs
import { Pool } from 'pg'
import { createClient } from '@supabase/supabase-js'

const BUCKET = 'files'
const PENDING_TIMEOUT_MS = 60 * 60 * 1000

const pool = new Pool({ connectionString: process.env.DATABASE_URL })
const storage = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.SUPABASE_SERVICE_ROLE_KEY,
  { auth: { persistSession: false, autoRefreshToken: false } },
)

// 1) 超时未确认的 pending：对象不存在就标 deleted。
const { rows: stale } = await pool.query(
  `select id, storage_path from public.files
   where status = 'pending' and created_at < now() - interval '1 hour'
   limit 500`,
)

let closedRows = 0
for (const row of stale) {
  const folder = row.storage_path.split('/').slice(0, 2).join('/')
  const { data, error } = await storage.storage.from(BUCKET).list(folder)
  const exists = (data ?? []).some((item) => item.name === 'original')
  if (error || !exists) {
    await pool.query(
      `update public.files set status = 'deleted'
       where id = $1 and status = 'pending'`,
      [row.id],
    )
    closedRows += 1
  }
}

// 2) 递归列出桶里所有对象，和 files 表对账。
async function listObjects(prefix = '', out = []) {
  let offset = 0
  for (;;) {
    const { data, error } = await storage.storage.from(BUCKET).list(prefix, {
      limit: 100,
      offset,
      sortBy: { column: 'name', order: 'asc' },
    })
    if (error) throw new Error(`list ${prefix} 失败: ${error.message}`)
    if (!data || data.length === 0) break

    for (const item of data) {
      const path = prefix ? `${prefix}/${item.name}` : item.name
      // 文件夹没有 id 和 metadata
      if (item.id === null || item.metadata === null) {
        await listObjects(path, out)
      } else {
        out.push({ path, size: item.metadata.size ?? 0 })
      }
    }
    if (data.length < 100) break
    offset += data.length
  }
  return out
}

const objects = await listObjects()
const { rows: known } = await pool.query(`select storage_path from public.files`)
const knownPaths = new Set(known.map((row) => row.storage_path))

const orphans = objects.filter((object) => !knownPaths.has(object.path))
const orphanBytes = orphans.reduce((sum, object) => sum + object.size, 0)

if (orphans.length > 0) {
  const { error } = await storage.storage
    .from(BUCKET)
    .remove(orphans.map((object) => object.path))
  if (error) throw new Error(`删除孤儿失败: ${error.message}`)
}

console.log(
  `pending 超时关闭 ${closedRows} 行；孤儿对象 ${orphans.length} 个，${(
    orphanBytes / 1024 / 1024
  ).toFixed(1)} MB，已删除`,
)
await pool.end()
```

```bash
node --env-file=.env.local scripts/cleanup-orphans.mjs
```

输出：

```text
pending 超时关闭 1 行；孤儿对象 1 个，0.2 MB，已删除
```

脚本用 service_role，因为要列出整个桶、读全部行，这两件事都不该给业务请求的权限。它跑在机器或运维容器里，不对外暴露端点。第 27 章会把它挂到定时任务上，那时候入口变成一个带 `CRON_SECRET` 的 Route Handler。

第一次跑建议先把 `remove` 那一段注释掉，只打印数量，确认清单对再真删。

脚本必须幂等：跑一次、两次、十次结果一样。定时任务可能因为超时重跑，清理逻辑一旦不幂等，重跑就是灾难。

只删创建超过一小时的孤儿。刚传完、还没确认的对象，行一定存在，所以不会误删；真正要防的是另一个方向的竞态：对象刚被删、行还没来得及标 `deleted`，脚本看到对象没了就动手。限制在一小时之后，任何正常流程都已走完。

删对象、保留行，是因为行是审计线索：谁在什么时候传了什么、为什么被清理。物理删行会让文件凭空消失，用户来问时查不到痕迹。配额统计也要靠这些行把 `deleted` 排除掉。真要按隐私法规彻底删除，是另一个流程：删行、删对象、写一条“已按要求删除”的审计记录，只留最小事实。

用户点删除时也一样：先把行改成 `deleted`、再删对象，不要 `delete from files`。顺序不能反：先删对象再改行，中间那一小段会让清理脚本看到“对象没了但行还在”，如果脚本按对象判断就会重复处理。先改行，再删对象，方向反过来是安全的。

单次删 500 个对象是上限，别一次清几万个：批量删除接口有请求体上限，删到一半失败很难受。真正的清理任务分批跑，批与批之间留间隔，第 27 章这么安排。

对账还可以在数据库侧先看一眼规模，避免脚本拉全量：

```sql
-- 每个团队的用量与文件数
select team_id, count(*) as files, sum(size_bytes) as bytes
from public.files
where status in ('pending', 'ready')
group by team_id
order by bytes desc;
```

```sql
-- 卡住超过一小时的 pending
select count(*) from public.files
where status = 'pending' and created_at < now() - interval '1 hour';
```

第一条能发现“某个团队悄悄占了 80% 空间”，第二条是清理任务该关注的量。两个查询都走索引，几十万行也很快。

## 23.12 边界与失败模式

单文件 50MB 是这一章的边界。超过 50MB 要分片上传，Supabase Storage 提供 resumable upload 端点，浏览器用 `tus-js-client` 分片传，断网后从断点续。这部分未在本机验证过，接口细节以所用的 `@supabase/storage-js` 版本和官方文档为准。分片上传的复杂度不在协议，在状态：分了几个片、断在哪、服务端怎么知道上传已经完成。这些状态要么存进存储服务，要么自己建表，两边都要处理过期清理。50MB 以内用一次 PUT 就够，别提前引入。

**桶配置与应用代码要一致**。桶上设了 `allowed_mime_types`，应用里也要有同样的白名单，否则用户拿到的是存储服务返回的 400，并非一句中文提示。两边不一致时，以桶为准，因为它拦得住绕过页面的请求。

**RLS 管不到服务端连接**。`files` 表的 RLS 只对浏览器直连生效。服务端用 `db` 查询时，租户条件必须写在 SQL 里。第 22 章的两条防线在文件表上同样成立。

**确认接口的越权**。确认时只按 `fileId` 查、不带 `team_id`，任何人拿到别人的 id 都能把对方的 `pending` 改成 `ready` 或 `deleted`。`team_id` 条件不能省。

**并发确认**。两个标签页同时确认同一个文件，两边都下载、都校验、都更新。结果一致，因为更新的是同一行的同一状态，幂等。真正需要注意的是衍生文件：第 24 章会在确认时生成缩略图，并发确认可能重复生成，那时要用 `upsert: true` 让第二次覆盖。

**清理脚本与业务请求的竞态**。脚本列出对象和表行之间有时间差，可能把刚上传成功的对象当成孤儿。用“创建超过一小时”的宽限把窗口让过去，这是这类对账任务的通用做法。

**日志与监控**。签名 URL 不能进日志，但“签发失败”“校验失败”“孤儿清理数量”要进日志和指标。后者能回答“最近上传失败率有没有涨”。

**删除的传播**。删掉存储对象后，CDN 或浏览器缓存里可能还有副本。私有桶的签名链接带 60 秒有效期，影响有限；公开桶要主动刷新缓存。

**存储用量的统计口径**。`usedBytes()` 按 `size_bytes` 求和，`pending` 行写的是声明值。声明 50MB、实际传 5MB 的用户，在确认前会被多算 45MB。这个偏差只持续到确认，可接受；如果发现配额经常被误判，改用确认后的真实值单独维护一张计数表。

**清理与审计的取舍**。物理删除对象是不可逆的。对需要保留证据的场景（合同、发票），删除前先导出对象清单和哈希，再删。哈希用 SHA-256，存在审计表里，能证明“某个时间点存在过这个文件”。

## 23.13 检查点

1. 传一个文件后执行 `select id, name, size_bytes, storage_path, status from public.files`，能看到行；表里没有任何存字节的列，`select pg_column_size(files.*) from files` 每行只有几百字节。
2. 签一个 `expiresIn = 5` 的下载链接，等十秒再打开：返回 400，内容里有 `InvalidJWT` / `jwt expired`。把参数写成 `Date.now() + 60000` 再签，链接在几万年后才过期。
3. 用 psql 造一行指向不存在路径的 `pending`（`created_at` 改成两小时前），再往桶里放一个表里没有的对象，跑 `node --env-file=.env.local scripts/cleanup-orphans.mjs`：前者被标 `deleted`，后者被删掉，输出里有计数。

4. 把 `storageLimitBytes` 临时改成 10MB，再传一个 12MB 的文件：`beginUpload` 直接报“存储空间不足”，`files` 表没有新行；改回后重传成功。
5. 传一半关掉网络再点确认：可以调 `reissueUpload` 重新签发上传链接，重传后同一行变成 `ready`，不会多出第二条记录。
## 23.14 常见错误

`Body exceeded 1 mb limit. To configure the body size limit for Server Actions, see: ...`

把文件当 `FormData` 提交给了 Server Action，默认上限 1MB。解法：别在 action 里收文件，按三段式做，action 只收名字、大小、MIME 三个字段，字节直传对象存储。

`StorageApiError: Object not found`

确认时 `download()` 找不到对象。九成是路径拼错：登记时写的是 `teamId/fileId/original`，确认时用了文件名或少了 `/original`。解法：路径只由 `originalPath()` 生成，读取时直接用 `files.storage_path`，不要重新拼。

`new row violates row-level security policy for table "files"`

用浏览器端客户端（publishable key）往 `files` 表插数据。这张表只允许服务端写。解法：登记走 Server Action 里的 `db`，浏览器只负责 PUT 字节和调确认。

`duplicate key value violates unique constraint "files_storage_path_key"`

两个请求生成了同一个 `storage_path`。通常是 `fileId` 复用了（拿文件名当 id），或者失败后重试又插了一行。解法：`randomUUID()` 每行唯一；重试复用原来的 `fileId`，走 `reissueUpload`。

`InvalidJWT: jwt expired`（打开下载链接时）

签名链接过期，或者本机时钟偏差太大。解法：`createSignedUrl` 第二个参数是秒；页面每次渲染重新签，不要把链接存进缓存或数据库。

`Error: supabaseKey is required.`

`SUPABASE_SERVICE_ROLE_KEY` 没配。它不能带 `NEXT_PUBLIC_` 前缀，只能放服务端。解法：`.env.local` 里加这一行，确认没被提交到仓库。

## 23.15 这一章在做什么

这一章把文件拆成两半，再用一条状态机缝起来。

字节在对象存储，元数据在 `files` 表，表里没有 `bytea`。顺序是登记 `pending`、直传字节、确认 `ready`，每一步中断都留下可追溯、可清理的状态。权限靠预签名链接，链接有效期按秒计、单个撤不掉，所以下载只给 60 秒，当密码对待。声明的 MIME 只用于快速失败，真正的类型靠魔数在确认时核实。孤儿分行孤儿和对象孤儿，同一个脚本幂等收拾。

故意没做的是拖拽、进度条、多文件并发。这些都能加，但加之前得先有一条对的状态机，否则体验越好，出错时留下的烂摊子越多。

还有一条边界要提前说清：这里所有的校验都发生在服务端，客户端的 `accept`、大小提示、进度文案都只是体验，绕过它们不需要任何技巧。

下一章在这条链路中间插一段：图片传上来之后，服务端自动裁缩略图、剥 EXIF、转 WebP。本章“确认时完整下载一次”的代价，正好被图片处理复用掉。
