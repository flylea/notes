# 第 29 章 站内通知与全文搜索

站内通知要解决两个问题：谁该收到，以及怎么知道用户看没看。前者靠写库时的规则，后者靠未读状态。

全文搜索要解决的是另一个问题：用户输入几个字，从日志、成员、文件三类数据里找出相关的记录，按相关度排序。

两件事放在一章，因为它们的触发点相同：一次写操作之后，既要告诉相关的人，也要让这条记录能被搜到。

本章涉及的概念有：未读状态的时间表示、部分索引、行级安全下的写入限制、`tsvector` 与 GIN 索引、中文分词的限制、`pg_trgm` 三元组索引、相关性排序。

## 29.1 通知的数据模型

表在第 8 章已经建好。`notifications` 的字段是：`id`、`user_id`、`team_id`、`kind`、`title`、`body`、`read_at`、`created_at`。

未读用 `read_at` 为空表示，不用布尔字段。时间能回答“什么时候读的”，布尔只能回答“读没读”。列表按未读在前排序时，时间还能当次级排序键。

这张表的读取方式固定：按用户取最近若干条，按用户数未读。索引照着这两个查询建，别加用不上的组合索引。

通知是快照。标题和正文在写入时定稿，之后不跟随源数据变化。团队改名了，三个月前的通知仍显示旧名字。这是有意的：通知记录的是“当时发生了什么”。

写入只允许服务端完成。表的插入和删除权限从普通用户手里收回，只保留查询和更新。

`kind` 存动作名，和 `activity_logs.action` 用同一套命名，值是 `member.joined`、`member.removed`、`invitation.created`、`subscription.updated` 四类。前端按 `kind` 决定图标和跳转目标，后端按它做过滤。加新类型时两边都要改，所以它只放稳定动作，不放自由文本。

通知表只存站内消息，不发邮件也不发推送。邮件走第 24 章的 Resend，推送要接第三方服务，两者都以站内通知为事实来源：先写通知，再由异步任务决定要不要发出去。这样“用户看过没有”只有一处记录。

同一件事在短时间内重复发生时要去重。判断条件是 `user_id`、`kind`、`team_id` 三个值相同，且最近十分钟内已有记录。去重放在触发器里做，业务代码仍然只管写日志。

团队大起来之后会出现通知洪水。二十人的团队，一周的成员变动能产生几十条通知，用户就不再看了。三种抑制手段：同类通知在时间窗口内合并成一条、按 `kind` 提供静音开关、只对与自己有关的动作发通知。teamstack 先用第三条，其余两条留到有真实反馈再加。

```sql
-- supabase/migrations/20261124091000_notifications.sql

-- 未读列表与计数都用这个索引
create index if not exists notifications_unread_idx
  on public.notifications (user_id, created_at desc)
  where read_at is null;

-- 全部通知的列表页
create index if not exists notifications_feed_idx
  on public.notifications (user_id, created_at desc);

alter table public.notifications enable row level security;

-- 只能看自己的
create policy "users read own notifications"
  on public.notifications for select
  to authenticated
  using (user_id = (select auth.uid()));

-- 只能标记自己的为已读，且不许改 user_id
create policy "users update own notifications"
  on public.notifications for update
  to authenticated
  using (user_id = (select auth.uid()))
  with check (user_id = (select auth.uid()));

-- 用户不能自己造通知，也不能自己删
revoke insert, delete on public.notifications from authenticated, anon;
```

`with check` 不能省。只写 `using` 时，更新可以把 `user_id` 改成别人，等于把自己的通知转给别人。两个子句都写，行级安全才约束得住。

## 29.2 未读计数

计数就是一条带条件的查询。Supabase 的 `count: "exact", head: true` 只返回数字，不返回行。

```ts
// src/lib/notifications.ts
import "server-only";
import { cache } from "react";
import { createClient } from "@/lib/supabase/server";

export const countUnread = cache(async (userId: string) => {
  const supabase = await createClient();
  const { count, error } = await supabase
    .from("notifications")
    .select("id", { count: "exact", head: true })
    .eq("user_id", userId)
    .is("read_at", null);

  if (error) throw error;
  return count ?? 0;
});

export async function listNotifications(userId: string, limit = 30) {
  const supabase = await createClient();
  const { data, error } = await supabase
    .from("notifications")
    .select("id, kind, title, body, read_at, created_at")
    .eq("user_id", userId)
    .order("read_at", { ascending: true, nullsFirst: true })
    .order("created_at", { ascending: false })
    .limit(limit);

  if (error) throw error;
  return data;
}
```

`read_at` 升序、空值在前，未读自然排在顶部。再按时间倒序，最新的未读最靠前。

通知列表和计数用同一个 `user_id` 过滤，不共用查询。列表要字段，计数只要行数，合并成一次查询会把列表的行拉回来再数一遍。

`cache()` 包一层，同一次渲染里布局和页面都调计数时只查一次。它的作用域是单次请求，不跨请求缓存，所以不存在数据过期问题。

计数查询的代价随未读条数增长，不随总条数增长。部分索引只包含 `read_at` 为空的行走，用户读完之后这些行从索引里消失。未读常年保持在两位数，查询就是读几十个索引项。

列表要分页时用 `limit` 加游标，不用 `offset`。`offset` 在深翻页时要扫过前面的行，通知列表翻到第十页就开始慢。

不用另存一个 `unread_count` 字段。计数器要和通知表在同一个事务里加减，任何一次失败都会让两边对不上。真要优化到极限，再考虑物化视图，前提是先能保证一致性。

用 `explain (analyze, buffers)` 确认索引被用上：

```bash
psql "$DATABASE_URL" -c "explain (analyze, buffers) select count(*) from public.notifications where user_id = '11111111-1111-1111-1111-111111111111' and read_at is null;"
```

输出里应出现 `Index Only Scan using notifications_unread_idx`。出现 `Seq Scan` 说明索引没建上，或者查询条件和索引的 `where` 不匹配。

## 29.3 通知由触发器写入

通知不要写在业务代码里。每个业务动作各写一次插入，早晚会漏。写在数据库触发器里，写日志和发通知在同一个事务，要么都成功，要么都失败。

`activity_logs` 是团队活动的记录表，第 8 章建好。通知从它派生。

```sql
-- 20261124091000_notifications.sql（继续）

create or replace function public.notify_activity()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
declare
  v_actor_name text;
begin
  -- 只处理这四类，其余动作不产生通知
  if new.action not in (
    'member.joined',
    'member.removed',
    'invitation.created',
    'subscription.updated'
  ) then
    return new;
  end if;

  select coalesce(full_name, email, '有人')
    into v_actor_name
    from public.profiles
   where id = new.actor_id;

  insert into public.notifications (user_id, team_id, kind, title, body)
  select
    m.user_id,
    new.team_id,
    new.action,
    v_actor_name || ' 更新了团队',
    left(coalesce(new.metadata ->> 'summary', ''), 200)
  from public.team_members m
  where m.team_id = new.team_id
    and m.user_id <> new.actor_id;  -- 操作者不通知自己

  return new;
end;
$$;

create trigger activity_notify
after insert on public.activity_logs
for each row execute function public.notify_activity();
```

三个细节。

函数必须 `security definer`。触发器由写日志的用户触发，而读 `profiles` 和插 `notifications` 需要更高权限。加上这个标记，函数以定义者身份执行。

`set search_path = public` 必写。`security definer` 函数不加这一句，调用方可以通过改 `search_path` 让函数里的表名指向别的 schema，这是常见的提权手法。

白名单用 `not in` 列出来，不用黑名单。新加的动作默认不通知，需要通知时显式加进来。

插入用 `insert ... select`，一次写完所有成员。循环逐条插入在成员多时会明显变慢。

触发器跑在写日志的事务里。它抛异常，整个写日志的操作一起回滚，业务侧看到的是 500。这属于预期行为：日志没写成功，通知也不该发出去。排查时先看 `activity_logs` 有没有落库，再看通知表有没有对应行。

单独测触发器，直接插一条日志即可：

```bash
psql "$DATABASE_URL" -c "insert into public.activity_logs (team_id, actor_id, action, target_type, metadata) values ('<team>', '<user>', 'member.joined', 'member', '{"summary":"张三加入"}');"
```

插完查 `notifications`，成员数减一（去掉操作者）就是应插入的行数。测试要在事务里做，`begin;` 开头、`rollback;` 结尾，别把测试数据留在库里。

## 29.4 标记已读

用户点开一条通知，写 `read_at`。这个动作放在 Server Action 里。

```ts
// src/app/(app)/t/[slug]/notifications/actions.ts
"use server";

import { revalidatePath } from "next/cache";
import { createClient } from "@/lib/supabase/server";
import { requireUser } from "@/lib/auth";

export async function markNotificationRead(slug: string, notificationId: string) {
  const user = await requireUser();
  const supabase = await createClient();

  const { error } = await supabase
    .from("notifications")
    .update({ read_at: new Date().toISOString() })
    .eq("id", notificationId)
    .eq("user_id", user.id)
    .is("read_at", null);  // 已经读过的不覆盖时间

  if (error) throw error;

  revalidatePath(`/t/${slug}/notifications`, "page");
  revalidatePath(`/t/${slug}`, "layout");
}
```

权限校验不进应用层。Server Action 里没有 `if (notification.user_id !== user.id)` 这类判断，条件直接写在 SQL 的 `eq` 和行级安全策略里。两条路径都约束，漏一条也不至于越权。

`.is("read_at", null)` 保证幂等。重复点击不会把第一次的已读时间改掉，统计“多久之内读了通知”时这很重要。

两个路径都要刷。列表在 `/t/[slug]/notifications`，角标在布局里。只刷其中一个，另一个会显示旧状态，直到下一次导航。传了动态段路径时不给类型，缓存标记会落到意料之外的位置。`/t/[slug]` 这类带参数的路径用 `"page"`。

已读之后要更新的界面有两处：通知列表和角标。列表靠 `revalidatePath` 重渲染，角标在下一节接实时。

已读有三种粒度，实现方式不同。单条已读写一个 id，上面就是。全部已读写一个批量更新：

```ts
// src/app/(app)/t/[slug]/notifications/actions.ts（继续）
export async function markAllRead(slug: string) {
  const user = await requireUser();
  const supabase = await createClient();

  const { error } = await supabase
    .from("notifications")
    .update({ read_at: new Date().toISOString() })
    .eq("user_id", user.id)
    .is("read_at", null);

  if (error) throw error;
  revalidatePath(`/t/${slug}/notifications`, "page");
  revalidatePath(`/t/${slug}`, "layout");
}
```

按时间已读，用于“三天前的自动清空”，放在定时任务里执行，走服务端角色，不经过行级安全。

批量更新要带 `is("read_at", null)`。少了它，每次点“全部已读”都会刷新全部时间戳，已有的阅读时间被覆盖。

## 29.5 角标跟着变

角标是客户端组件，订阅自己的通知表。

```tsx
// src/app/(app)/t/[slug]/notification-badge.tsx
"use client";

import { useEffect, useState } from "react";
import { createClient } from "@/lib/supabase/client";

export function NotificationBadge({ userId, initial }: { userId: string; initial: number }) {
  const [count, setCount] = useState(initial);

  useEffect(() => {
    const supabase = createClient();
    let timer: ReturnType<typeof setTimeout> | undefined;

    const channel = supabase
      .channel(`user:${userId}:notifications`)
      .on(
        "postgres_changes",
        {
          event: "*",
          schema: "public",
          table: "notifications",
          filter: `user_id=eq.${userId}`,
        },
        () => {
          if (timer) clearTimeout(timer);
          timer = setTimeout(async () => {
            const { count: next } = await supabase
              .from("notifications")
              .select("id", { count: "exact", head: true })
              .eq("user_id", userId)
              .is("read_at", null);
            setCount(next ?? 0);
          }, 300);
        },
      )
      .subscribe();

    return () => {
      if (timer) clearTimeout(timer);
      void supabase.removeChannel(channel);
    };
  }, [userId]);

  if (count === 0) return null;
  return <span className="badge">{count > 99 ? "99+" : count}</span>;
}
```

收到事件后重新查一次计数，不在本地加减。事件不带完整行，加减会算错：一次操作可能给同一个人插入多条通知。

300ms 的合并窗口处理批量插入。导入邀请时一次可能写十条通知，没有合并就是十次查询。

订阅过滤条件用 `user_id=eq.<uuid>`，只有自己的行会推过来。行级安全同样生效，别人即使知道频道名也收不到你的通知。

角标只有一个数字，用户切到别的页面时还在跑订阅。页面隐藏时退订，回到前台再建，能省下连接配额。判断方式用 `document.visibilityState`，监听 `visibilitychange` 事件。

通知数还要同步到标题栏，格式是 `(3) teamstack`。这件事放在同一处更新，别在另一个组件里再订阅一次，一个页面两条连接不划算。

## 29.6 搜索：ILIKE 的三个问题

最初级的写法是 `like` 或 `ilike`：

```sql
select id, action, metadata
from public.activity_logs
where team_id = '11111111-1111-1111-1111-111111111111'
  and metadata ->> 'summary' ilike '%预算%';
```

三个问题。

前导的 `%` 让 B-tree 索引失效。索引按前缀排序，`'%预算%'` 没有前缀可用，只能全表扫描。数据到十万行时，这条查询变成几百毫秒。

子串匹配不等同于语言匹配。搜“预算”能匹配“季度预算”，也会匹配“预算外”和“预算表模板”。用户想要的是包含这个词的记录，不区分它出现在哪。

没有相关性排序。所有命中行平权，只能按时间排。最相关的那条可能排在第三页。

`like '预算%'` 这种带前缀的写法能用索引。搜索框里做不到：用户不会从第一个字开始输入。

看一眼执行计划，问题很直接：

```bash
psql "$DATABASE_URL" -c "explain (analyze, buffers) select id from public.activity_logs where team_id = '11111111-1111-1111-1111-111111111111' and metadata ->> 'summary' ilike '%预算%';"
```

输出里的 `Seq Scan on activity_logs` 就是全表扫描。`rows=` 后面的数字是全表行数，`actual time=` 是耗时。同一张表改用 `search @@ query` 之后，同样的查询会出现 `Bitmap Index Scan on activity_logs_search_idx`。

判断索引有没有被用，看 `Scan` 那一行。`Bitmap Index Scan` 加 `Bitmap Heap Scan` 是 GIN 的典型形态。`Seq Scan` 出现时，先确认查询条件和索引定义是否可以匹配，再确认表规模，行数太少时规划器会主动选择全表。


## 29.7 tsvector 生成列与 GIN

Postgres 的全文检索把文本切成词元，存成 `tsvector`，用 GIN 索引加速。

`activity_logs` 加一个生成列。生成列由数据库在写入时计算，不需要应用层维护。

```sql
-- supabase/migrations/20261124092000_search.sql

alter table public.activity_logs
  add column if not exists search tsvector
  generated always as (
    setweight(to_tsvector('simple', coalesce(action, '')), 'A') ||
    setweight(to_tsvector('simple', coalesce(metadata ->> 'summary', '')), 'B') ||
    setweight(to_tsvector('simple', coalesce(metadata ->> 'target_name', '')), 'C')
  ) stored;

create index if not exists activity_logs_search_idx
  on public.activity_logs using gin (search);
```

`setweight` 给不同来源的词元打不同权重，`A` 最高，`D` 最低。`ts_rank` 系列函数按权重加权，让动作类型比摘要更容易命中。

`to_tsvector` 必须用两个参数的形式：`to_tsvector('simple', text)`。只传文本的单参数版本依赖数据库默认配置，会被判定为非 `IMMUTABLE`，生成列和表达式索引都不接受。这是最常见的一条建表失败原因。

`'simple'` 是文本搜索配置，按空白和标点切分，不做词形还原。选它的理由在下一节。

查询用 `websearch_to_tsquery`：

```sql
select
  id,
  action,
  ts_rank_cd(search, query) as rank,
  ts_headline('simple', coalesce(metadata ->> 'summary', ''), query,
    'StartSel=[[[, StopSel=]]], MaxWords=30, MinWords=10') as snippet
from public.activity_logs, websearch_to_tsquery('simple', $1) as query
where team_id = $2
  and search @@ query
order by rank desc, created_at desc, id desc
limit 20;
```

相关性由两样东西决定：词元是否命中，命中的词落在哪个字段。`ts_rank_cd` 还考虑词之间的距离，同一句话里相邻的两个词得分更高。它比 `ts_rank` 更贴近人的判断，代价是计算量略大。

三种构造 `tsquery` 的函数区别很大：

- `to_tsquery` 要手写运算符，遇到 `a &` 或不配对的括号直接报 `syntax error in tsquery`。不能接用户输入。
- `plainto_tsquery` 把空格分隔的词用 AND 连起来，不报错，但不支持短语和排除。
- `websearch_to_tsquery` 支持引号短语、`or`、负号排除，非法输入也不报错。面向用户的搜索框用它。

排序必须有稳定的次级键。`rank` 相同的行很多，只按 `rank` 排序时，翻页会出现同一条记录出现两次或者漏掉。加 `created_at desc, id desc` 兜底。

`ts_headline` 生成摘要片段。片段里保留原文内容，直接当 HTML 插入会有 XSS 风险。用 `[[[` 和 `]]]` 当标记，前端按标记切开渲染，不拼 HTML。

建索引在已有数据的大表上要加 `concurrently`：

```sql
create index concurrently if not exists activity_logs_search_idx
  on public.activity_logs using gin (search);
```

加了这个关键字就不锁表，代价是耗时更长，失败时留下一个 invalid 索引，需要先 `drop index` 再重建。

GIN 索引的写入成本比 B-tree 高。每次插入生成列时，还要把词元写进索引。GIN 默认开启 `fastupdate`，新条目先进 pending list，后台再合并。表现是刚写入的行偶尔搜不到，几十毫秒后恢复。这是设计如此，批量导入之后立刻搜索才会撞上。

大量更新之后 GIN 会膨胀，查询变慢。用 `pg_stat_user_indexes` 看索引大小，必要时重建：

```sql
reindex index concurrently public.activity_logs_search_idx;
```

`reindex ... concurrently` 不锁写，代价是执行时间长、需要额外磁盘。

## 29.8 中文分词的限制

`to_tsvector` 按配置切词。`'english'` 配置对英文做词干还原、去停用词，对中文几乎不做切分：

```sql
select to_tsvector('simple', '张三修改了季度预算');
```

结果是整句作为一个词元，`'simple'` 也一样。配置没选错，问题出在内置分词器：它只认空白和标点，中文没有空格。

后果是：搜“预算”匹配不到这条记录，因为词元是“张三修改了季度预算”，两者不相等。

四条可选路径：

- 应用层先分词，把空格分隔的结果写进另一个列，再用 `'simple'` 配置索引。改动可控，但词表要自己维护。
- 装 `zhparser` 或 `pg_jieba` 扩展。需要数据库超级用户权限，托管服务大多不允许。**未验证**：本机 Supabase 本地环境没有安装过这两个扩展。
- 退回 `pg_trgm`，用三元组相似度匹配。对中文有效，容量差一些。
- 上外部搜索引擎。见 29.10。

teamstack 用的是 `pg_trgm` 兜底。

如果选择应用层分词，做法是在写入时算好一份空格分隔的词，存进独立列，索引这一列。分词器可以用 `nodejieba` 之类的库，代价是把它加进构建产物，冷启动变重。

```ts
// scripts/segment.ts（离线回填用）
import { cut } from "nodejieba";

export function segment(text: string) {
  return cut(text, true).join(" ");  // true 表示搜索引擎模式，长词再切
}
```

回填之后仍要维护：写入路径上补一次分词，改了词典就全量重跑。三条路径（写入、搜索、回填）用的分词器必须是同一个，否则搜不到。

```sql
-- 20261124092000_search.sql（继续）
create extension if not exists pg_trgm;

create index if not exists activity_logs_summary_trgm_idx
  on public.activity_logs
  using gin ((coalesce(metadata ->> 'summary', '')) gin_trgm_ops);

create index if not exists team_members_name_trgm_idx
  on public.profiles
  using gin (coalesce(full_name, '') gin_trgm_ops);

create index if not exists files_name_trgm_idx
  on public.files
  using gin (name gin_trgm_ops);
```

查询用相似度算子：

```sql
select id, metadata ->> 'summary' as summary, similarity(metadata ->> 'summary', $1) as score
from public.activity_logs
where team_id = $2
  and coalesce(metadata ->> 'summary', '') % $1
order by score desc
limit 20;
```

`%` 在这里是相似度算子，与取模无关。它返回布尔值，判断相似度是否超过阈值，默认阈值 0.3，可以用 `set pg_trgm.similarity_threshold = 0.4` 调整。

三元组索引的局限是短查询。三个字符才能形成一个三元组，搜一个字或两个字凑不出来，只能退回顺序扫描。中文里两个字正好是一个常用词，所以两字搜索在实际使用中会慢。可以用 `like '%预算%'` 配合 `gin_trgm_ops` 索引，它在字符串足够长时也能走索引，短查询仍然不行。

## 29.9 一个函数搜三处

搜索要覆盖三类数据：活动日志、成员、文件。放在一个 SQL 函数里，一次请求返回三组结果，前端按分组展示。

```sql
-- 20261124092000_search.sql（继续）
create or replace function public.search_team(
  p_team_id uuid,
  p_query text,
  p_limit int default 10
)
returns table (
  source text,
  id uuid,
  title text,
  snippet text,
  score real,
  created_at timestamptz
)
language sql
stable
security invoker
as $$
  with q as (
    select websearch_to_tsquery('simple', p_query) as tsq,
           p_query as raw
  )
  select * from (
    -- 活动日志：全文索引 + 权重
    select
      'log'::text as source,
      a.id,
      a.action as title,
      ts_headline('simple', coalesce(a.metadata ->> 'summary', ''), q.tsq,
        'StartSel=[[[, StopSel=]]], MaxWords=30, MinWords=8') as snippet,
      (ts_rank_cd(a.search, q.tsq) * 4
        + coalesce(similarity(coalesce(a.metadata ->> 'summary', ''), q.raw), 0)) as score,
      a.created_at
    from public.activity_logs a, q
    where a.team_id = p_team_id
      and (a.search @@ q.tsq
        or coalesce(a.metadata ->> 'summary', '') % q.raw)

    union all

    -- 成员：姓名相似度
    select
      'member'::text,
      p.id,
      coalesce(p.full_name, p.email) as title,
      coalesce(p.full_name, p.email) as snippet,
      similarity(coalesce(p.full_name, p.email), q.raw) as score,
      p.created_at
    from public.profiles p
    join public.team_members m on m.user_id = p.id
    cross join q
    where m.team_id = p_team_id
      and coalesce(p.full_name, p.email) % q.raw

    union all

    -- 文件：文件名相似度
    select
      'file'::text,
      f.id,
      f.name as title,
      f.name as snippet,
      similarity(f.name, q.raw) as score,
      f.created_at
    from public.files f, q
    where f.team_id = p_team_id
      and f.status = 'ready'
      and f.name % q.raw
  ) results
  order by score desc, created_at desc, id desc
  limit least(greatest(p_limit, 1), 50);
$$;
```

`security invoker` 让函数以调用者身份执行，行级安全照常生效。改成 `security definer` 会绕过 RLS，搜索能搜到别的团队的数据。

`limit least(greatest(p_limit, 1), 50)` 把上限夹在 1 到 50 之间。参数来自 URL，不能直接拼进 SQL 当行数。

应用层调 RPC：

```ts
// src/lib/search.ts
import "server-only";
import { createClient } from "@/lib/supabase/server";

export type SearchHit = {
  source: "log" | "member" | "file";
  id: string;
  title: string;
  snippet: string;
  score: number;
  created_at: string;
};

export async function searchTeam(teamId: string, query: string) {
  const q = query.trim().slice(0, 100);  // 超长输入直接截断，不报错
  if (q.length === 0) return [] as SearchHit[];

  const supabase = await createClient();
  const { data, error } = await supabase.rpc("search_team", {
    p_team_id: teamId,
    p_query: q,
    p_limit: 10,
  });

  if (error) throw error;
  return (data ?? []) as SearchHit[];
}
```

页面从 URL 取搜索词。`searchParams` 是 Promise，必须 `await`：

```tsx
// src/app/(app)/t/[slug]/search/page.tsx
import { searchTeam } from "@/lib/search";
import { Highlight } from "@/components/highlight";

export default async function SearchPage({
  params,
  searchParams,
}: {
  params: Promise<{ slug: string }>;
  searchParams: Promise<{ q?: string | string[] }>;
}) {
  const { slug } = await params;
  const { q } = await searchParams;

  // 同名参数出现多次时是数组，取第一个
  const query = (Array.isArray(q) ? q[0] : q) ?? "";
  const hits = await searchTeam(slug, query);

  return (
    <ul>
      {hits.map((hit) => (
        <li key={`${hit.source}:${hit.id}`}>
          <strong>{hit.title}</strong>
          <Highlight text={hit.snippet} />
        </li>
      ))}
    </ul>
  );
}
```

摘要的渲染按标记切分，不拼 HTML：

```tsx
// src/components/highlight.tsx
export function Highlight({ text }: { text: string }) {
  const parts = text.split(/\[\[\[|\]\]\]/);
  return (
    <p>
      {parts.map((part, i) =>
        i % 2 === 1 ? <mark key={i}>{part}</mark> : <span key={i}>{part}</span>,
      )}
    </p>
  );
}
```

搜索条件放 URL，不用组件状态。URL 能分享、能前进后退、能被服务端渲染读取。这一点和表单筛选、分页一致。

搜索入口放在顶栏，占位文字写“搜索活动、成员、文件”。输入框不做联想，结果页负责展示，减少一次网络往返。

界面上还有几个小决定。

输入框加 300ms 防抖，用 `useRouter().replace()` 更新 URL，避免每敲一个字符就发一次请求。空查询直接返回空结果，不查库。

结果按 `source` 分组展示，日志、成员、文件各一栏。混在一个列表里，用户很难判断该点哪个。

无结果时给一句“没有找到包含这个词的记录”，别显示空的列表容器。

搜索接口要防刷。按用户每分钟 30 次限流，超了返回 429，和第 30 章的公共接口用同一套限流设施。

结果条数固定每类最多 10 条，不做无限滚动。搜索用来找东西，浏览交给列表页。

## 29.10 什么时候换外部搜索引擎

Postgres 全文检索的边界很清楚：数据量在百万行以内，查询是关键词匹配，排序要求不高，它够用。teamstack 的数据量远低于这个量级。

出现下面几种情况，再考虑 Meilisearch、Typesense 或 Elasticsearch：

- 需要拼写纠错、同义词、拼音搜索。这些要维护词典，Postgres 没有内置支持。
- 需要按多个字段的复杂相关度打分，还要 A/B 调权。
- 单表超过千万行，GIN 索引的写入开销开始影响业务写入。
- 需要高亮、聚合、分面统计一体的结果。

换引擎的主要成本不在查询，在同步。数据库每次写入都要推到搜索引擎，管道断了就搜不到新数据。还要处理删除、权限过滤、重建索引。数据量不大时，这些都是净增加。

搜索引擎的索引和数据库是两份数据，任何一次写入失败都会让两边短暂不一致。用户搜到一条刚被删掉的记录，点进去是 404。这种错要能容忍，前端对 404 做兜底提示。搜索引擎通常不认识数据库的行级安全，搜索结果的过滤要在应用层做，或者把权限规则复制一份到索引里。复制之后要保证两边一致，工作量比想象的大。

同步管道的基本形态是：写库成功后发一条消息，消费者读出来推给索引服务。消息丢了要能补，所以还要有一张同步状态表，记录每行最后同步的版本。这套东西加起来比搜索本身复杂。

数据量在十万行以下，先用 Postgres。换外部引擎的时机由查询延迟决定，不由流行度决定。

## 29.11 检查点

1. 执行 `select indexname from pg_indexes where tablename = 'notifications';`，结果里出现 `notifications_unread_idx`。
2. 点开一条未读通知，列表里它变灰，角标数字减一，刷新页面后状态保持。
3. 在另一个标签页触发一条新通知，本页角标三秒内加一，不刷新页面。
4. 搜索“预算”，结果包含活动日志；搜索“张”，结果包含成员。两种查询都不报错。
5. 执行 `explain (analyze, buffers)` 看搜索查询，中文两字查询允许出现 `Seq Scan`，英文查询应出现 `Bitmap Index Scan`。
6. 把 `search_team` 的函数体改成 `security definer` 后，用另一个团队的账号搜索，确认能搜到别人的数据；改回 `security invoker` 后确认搜不到。
7. 插入一条 `member.joined` 日志后，`select count(*) from notifications where team_id = '<team>';` 的数量等于团队成员数减一。

## 29.12 常见错误

1. `functions in index expression must be marked IMMUTABLE`

生成列或索引里用了单参数的 `to_tsvector('...')`。改成两参数 `to_tsvector('simple', text)`，配置名显式传入才是 `IMMUTABLE`。

2. `cannot use generated column in ...` 或建列后查询报列不存在

生成列的表达式不能通过 `alter column` 修改。要改权重或字段，只能加新列、回填、建索引、切查询、删旧列，分四步上线。

3. `operator does not exist: text % unknown`

`pg_trgm` 扩展没装。执行 `create extension if not exists pg_trgm;`，需要数据库的建扩展权限，托管环境一般允许。

4. `syntax error in tsquery`

把用户输入直接传给了 `to_tsquery`。改用 `websearch_to_tsquery`，非法输入不会抛错。

**5. 中文搜不到东西**

`to_tsvector('simple', '张三修改了季度预算')` 整句是一个词元，搜“预算”匹配不上。确认查询走的是 `pg_trgm` 那条路径，或者接受两字查询的扫描代价。

6. 两个标签页的角标数字不同

角标订阅只在本页生效，另一页要靠它自己的订阅更新。检查两页是否都渲染了 `NotificationBadge`，以及 `user_id` 是否传对。

## 29.13 这一章在做什么

这一章把“通知”和“搜索”放回数据库解决。

通知部分的三条规则：未读用时间表示，写入只在触发器里做，用户权限用行级安全加 `revoke` 收紧。角标靠第 28 章的订阅机制更新，收到事件后重新计数，不做本地加减。

搜索部分从 `ILIKE` 换到 `tsvector`。生成列加 GIN 索引解决前缀匹配的问题，`websearch_to_tsquery` 解决非法输入，`ts_rank_cd` 解决排序。中文分词是这套方案的短板，用 `pg_trgm` 兜底，短查询接受顺序扫描。
