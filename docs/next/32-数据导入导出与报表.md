# 第 32 章 数据导入导出与报表

CSV 看起来是最简单的数据格式：逗号分隔，一行一条记录。实际处理起来，它是这本书里坑最多的一块。

中文 Windows 导出的 CSV 带 BOM，Excel 打开正常，代码读出来第一列名多了三个不可见字节。字段里带逗号要加引号，带引号要写两个引号，带换行的字段本身就是多行。用户另存时可能存成 GBK，也可能是分号分隔。

导出方向也有类似的坑：Excel 不认识 UTF-8 的 BOM 就会乱码，公式开头的单元格会被当作公式执行。

本章讲四件事：怎么把外部文件读成可靠的行、怎么逐行校验并给出可下载的错误报告、怎么导出 Excel 能直接打开的 CSV、怎么让报表数字和列表页对得上。

涉及的概念有：编码与 BOM、CSV 的引号规则、逐行校验与部分成功、幂等（同一份文件导入两次结果一致）、流式输出、时区与统计口径。

## 32.1 CSV 的真实格式

CSV 用了几十年还没被替掉，原因是它是纯文本：任何语言都能读写，出问题能用记事本打开，传输不需要协议。代价是格式本身没有标准，各家实现有差异。

先把规则列清楚，后面所有实现都从这里来。

- 字段之间用分隔符分开，逗号是最常见的，Excel 在部分地区用分号。
- 字段里有分隔符、引号或换行时，整个字段用双引号包起来。
- 字段里的双引号写成两个双引号。
- 第一行通常是表头，也可能没有。
- 行尾是 CRLF 或 LF，两种都要能读。
- 文件开头可能有 BOM（字节顺序标记），三个字节，肉眼看不见。

团队通讯录这份文件是从 Excel 另存的，用户很可能做了这些操作：改成中文表头、加了备注列、把某一列设成日期格式、导出时选了 GBK。



表头是另一个变量。同一份数据，A 用户导出的列名是 `email`、`role`，B 用户的 Excel 自动翻译成了“邮箱”“角色”。硬编码英文列名会让一半人失败。做法是维护一张别名表，比较前先转小写、去空格。

列顺序不能假设。用户可能删掉一列，也可能插入一列备注。按表头名找索引，不按位置取值。

多余的空列和空行要容忍。Excel 常在末尾留一行全空，解析出来是一行空字符串，直接跳过，不报错。这些都不该让导入失败，但也不该静默跳过。处理原则是：能确定的自动纠正，不确定的报错让人看。

## 32.2 解码与解析

第一步把字节变成字符串，同时处理编码问题。

```ts
// src/lib/csv/decode.ts
const UTF8_BOM = "\uFEFF";

export function decodeCsv(bytes: Uint8Array): { text: string; encoding: "utf-8" } {
  // 先看 BOM，有就剥掉
  let start = 0;
  if (bytes[0] === 0xef && bytes[1] === 0xbb && bytes[2] === 0xbf) {
    start = 3;
  }

  try {
    const decoder = new TextDecoder("utf-8", { fatal: true });
    const text = decoder.decode(bytes.subarray(start));
    return { text: text.replace(UTF8_BOM, ""), encoding: "utf-8" };
  } catch {
    // 解不出来就当非 UTF-8 处理，交给上层拒绝
    throw new Error("文件编码无法识别，请另存为 UTF-8 编码的 CSV");
  }
}
```

`fatal: true` 是关键。默认的 `TextDecoder` 遇到非法字节会用替换字符 `�` 顶上，不报错。加上这个选项，非法编码直接抛异常，我们能给出明确提示，不会把乱码存进数据库。

BOM 有三种变体：UTF-8 是三个字节 `EF BB BF`，UTF-16 是 `FF FE` 或 `FE FF`。只处理第一种，其余直接拒绝。UTF-16 的 CSV 在 Windows 上不常见，遇到了提示用户另存。

不猜 GBK。猜编码需要字符频率统计，`chardet` 这类库在短文本上准确率不高，猜错的后果是把一整批邮箱存成乱码。让用户另存为 UTF-8，一句话的提示比一堆猜测代码可靠。

还有一类文件与 CSV 无关：Excel 的 `.xlsx` 是压缩包，前两个字节是 `PK`。用户改扩展名的情况很常见。

```ts
// src/lib/csv/decode.ts（继续）
export function assertLooksLikeCsv(bytes: Uint8Array) {
  if (bytes[0] === 0x50 && bytes[1] === 0x4b) {
    throw new Error("这是 xlsx 文件，请在 Excel 里另存为 CSV 后再上传");
  }
}
```

自己切会在第一个反例上出错：字段里带逗号。`"张三, 财务",member` 这种行按逗号切会变成三列，后面全部错位。引号、转义、换行这些规则都有边界，交给成熟的库。

第二步切行。用 `csv-parse`，不要自己 `split(",")`。

```ts
// src/lib/imports/invitations.ts
import { parse } from "csv-parse/sync";

export type RawInviteRow = {
  email: string;
  role: string;
  lineNo: number;  // 物理行号，报错用
};

const HEADER_ALIASES: Record<string, string> = {
  email: "email",
  邮箱: "email",
  "e-mail": "email",
  role: "role",
  角色: "role",
  权限: "role",
};

export function parseInvitationCsv(text: string) {
  const records: string[][] = parse(text, {
    bom: true,
    skip_empty_lines: true,
    relax_column_count: true,
    trim: true,
  });

  if (records.length === 0) {
    throw new Error("文件是空的");
  }

  const header = records[0].map((h) => HEADER_ALIASES[h.trim().toLowerCase()] ?? "");
  if (!header.includes("email")) {
    throw new Error("找不到 email 列，表头需要用 email 或 邮箱");
  }

  const emailIndex = header.indexOf("email");
  const roleIndex = header.indexOf("role");

  const rows: RawInviteRow[] = [];
  records.slice(1).forEach((cells, index) => {
    rows.push({
      email: cells[emailIndex] ?? "",
      role: roleIndex >= 0 ? (cells[roleIndex] ?? "") : "member",
      // 表头占第一行，所以数据从第二行开始
      lineNo: index + 2,
    });
  });

  return rows;
}
```

`bom: true` 让库自己处理 BOM。`relax_column_count: true` 容忍某行列数不一致，缺的列读成空串，多的列丢掉。`trim: true` 去掉单元格首尾空格。

行号用 `index + 2`。用户看到的行号从 1 开始算，表头占第 1 行，第一条数据在第 2 行。

这个行号只在字段里没有换行时准确。一旦某个字段包含换行，`records` 的索引和文件的物理行号就对不上了，报错会指向错误的位置。要精确，用 `info.lines` 累加：

```ts
// 需要精确行号时
const records: string[][] = [];
parse(text, {
  bom: true,
  skip_empty_lines: true,
  trim: true,
  info: true,
}).forEach((record: { record: string[]; info: { lines: number } }) => {
  records.push([...record.record, String(record.info.lines)]);
});
```

通讯录里一般没有换行，先用简单版本；报错对不上时再换。两个版本的解析逻辑一致，只是行号来源不同，切换成本低。

`info.lines` 给出这条记录占用的物理行数，累加就是起始行号。通讯录里一般没有换行，先用简单版本；报错对不上时再换。

## 32.3 逐行校验与错误报告

解析出来的行可能有问题：邮箱格式不对、角色不在允许的取值里、同一份文件里重复、邮箱已经存在。

校验要逐行做，错误要能定位到行号，好行继续处理。

```ts
// src/lib/imports/invitations.ts（继续）
import { z } from "zod";

const rowSchema = z.object({
  email: z.string().trim().toLowerCase().email("邮箱格式不正确"),
  role: z.enum(["owner", "member"]).catch("member"),
});

export type RowError = { lineNo: number; message: string };
export type ValidRow = { email: string; role: "owner" | "member"; lineNo: number };

export function validateRows(rows: RawInviteRow[]) {
  const valid: ValidRow[] = [];
  const errors: RowError[] = [];
  const seen = new Map<string, number>();

  for (const row of rows) {
    const parsed = rowSchema.safeParse({ email: row.email, role: row.role });

    if (!parsed.success) {
      errors.push({
        lineNo: row.lineNo,
        message: parsed.error.issues[0]?.message ?? "格式不正确",
      });
      continue;
    }

    const firstSeen = seen.get(parsed.data.email);
    if (firstSeen !== undefined) {
      errors.push({
        lineNo: row.lineNo,
        message: `与第 ${firstSeen} 行重复`,
      });
      continue;
    }

    seen.set(parsed.data.email, row.lineNo);
    valid.push({ ...parsed.data, lineNo: row.lineNo });
  }

  return { valid, errors };
}
```

`role` 用 `.catch("member")`。角色写错的成本低，默认成普通成员比整行拒绝更合适。邮箱写错必须报错，发错邀请的代价高。



错误要能导出。每条带行号、列名、原因，用户下载之后在 Excel 里对照修改，改完再传一次。这一步不做，用户只能一行行找回出错的位置。

错误信息只描述原因，不回显整行内容。请求体的内容是用户数据，可能含敏感信息，写进日志和错误表会扩大泄漏面。



为什么不让整批失败。一份两百行的通讯录，中间有一行邮箱写错，整批拒绝的话用户要改完重传。逐行处理让另外一百九十九行照常生效，坏行单独修。

错一行报一行也不合适。十万行的文件出几千条错误，列表刷屏，用户看不出重点。做法是错误表只显示前一百条，完整的错误文件可供下载。

预览和写入分两步，是因为误导入的代价高。邀请一旦发出，收回要人工处理。预览页列出“将邀请 42 人”，用户点确认才写库，多一次点击换一次确认。调用方拿到 `valid` 和 `errors` 之后，先展示预览：多少行可以导入，多少行有问题，问题在哪几行。用户确认之后再写库。

## 32.4 导入的幂等

用户点两次“导入”，或者网络超时后重试，同一份文件可能处理两次。结果必须一致。

幂等的实现方式：对文件内容算哈希，同一份内容只处理一次。

```sql
-- supabase/migrations/20261126090000_imports.sql

create table if not exists public.imports (
  id uuid primary key default gen_random_uuid(),
  team_id uuid not null references public.teams(id) on delete cascade,
  kind text not null,
  content_hash text not null,
  status text not null default 'done'
    check (status in ('queued', 'running', 'done', 'failed')),
  total_rows int not null default 0,
  success_rows int not null default 0,
  failed_rows int not null default 0,
  created_by uuid not null references public.profiles(id),
  created_at timestamptz not null default now()
);

create unique index if not exists imports_team_hash_uidx
  on public.imports (team_id, content_hash);

create table if not exists public.import_errors (
  id bigint generated always as identity primary key,
  import_id uuid not null references public.imports(id) on delete cascade,
  line_no int not null,
  message text not null
);

alter table public.imports enable row level security;
alter table public.import_errors enable row level security;

create policy "members read team imports"
  on public.imports for select
  to authenticated
  using (
    exists (
      select 1 from public.team_members m
      where m.team_id = imports.team_id
        and m.user_id = (select auth.uid())
    )
  );

create policy "members read import errors"
  on public.import_errors for select
  to authenticated
  using (
    exists (
      select 1
        from public.imports i
        join public.team_members m on m.team_id = i.team_id
       where i.id = import_errors.import_id
         and m.user_id = (select auth.uid())
    )
  );
```

唯一索引 `(team_id, content_hash)` 保证同一团队同一内容只留一条导入记录。重复提交时会撞唯一约束，捕获之后返回上一次的结果。

写入用事务型函数，逐行插入会慢：

```sql
-- 20261126090000_imports.sql（继续）
create or replace function public.import_invitation_rows(
  p_import_id uuid,
  p_team_id uuid,
  p_rows jsonb
)
returns int
language plpgsql
security invoker
as $$
declare
  v_count int;
begin
  insert into public.invitations (team_id, email, role, token, status, expires_at, invited_by)
  select
    p_team_id,
    r.email,
    r.role::text,
    encode(gen_random_bytes(24), 'hex'),
    'pending',
    now() + interval '7 days',
    r.invited_by
  from jsonb_to_recordset(p_rows)
    as r(email text, role text, invited_by uuid)
  on conflict (team_id, lower(email)) where status = 'pending' do nothing;

  get diagnostics v_count = row_count;
  return v_count;
end;
$$;
```

批次大小有上限。一条 SQL 展开两千行时，执行计划可能退化成慢查询，参数体积也大。两百行是实测比较稳的值，再大就开始不稳定。`jsonb_to_recordset` 把整批数据一次展开，一条 SQL 插入两百行。`on conflict` 依赖一个部分唯一索引：

```sql
create unique index if not exists invitations_pending_uidx
  on public.invitations (team_id, lower(email))
  where status = 'pending';
```

`on conflict` 的冲突目标必须和索引定义完全一致，包括 `lower(email)` 和 `where` 条件。写错了会报 `there is no unique or exclusion constraint matching the ON CONFLICT specification`。

函数用 `security invoker`，行级安全照常生效。用 `security definer` 会绕过权限，等于开一个任意邀请的口子。

应用层分批调用：

```ts
// src/lib/imports/run.ts
import "server-only";
import { createHash } from "node:crypto";
import { createClient } from "@/lib/supabase/server";
import type { RowError, ValidRow } from "@/lib/imports/invitations";

const BATCH_SIZE = 200;
const MAX_ROWS = 2000;

export async function importInvitations(input: {
  teamId: string;
  userId: string;
  contentHash: string;
  rows: ValidRow[];
  errors: RowError[];
}) {
  const supabase = await createClient();

  if (input.rows.length > MAX_ROWS) {
    // 超过阈值改走后台任务
    const { data, error } = await supabase
      .from("jobs")
      .insert({ kind: "import_invitations", payload: { ...input, status: "queued" } })
      .select("id")
      .single();
    if (error) throw error;
    return { mode: "queued" as const, jobId: data.id };
  }

  const { data: record, error: insertError } = await supabase
    .from("imports")
    .insert({
      team_id: input.teamId,
      kind: "invitations",
      content_hash: input.contentHash,
      total_rows: input.rows.length + input.errors.length,
      failed_rows: input.errors.length,
      created_by: input.userId,
    })
    .select("id")
    .single();

  if (insertError?.code === "23505") {
    // 撞唯一索引：这份文件已经导入过
    return { mode: "duplicate" as const, importId: null };
  }
  if (insertError) throw insertError;

  let inserted = 0;
  for (let i = 0; i < input.rows.length; i += BATCH_SIZE) {
    const batch = input.rows.slice(i, i + BATCH_SIZE);
    const { data, error } = await supabase.rpc("import_invitation_rows", {
      p_import_id: record.id,
      p_team_id: input.teamId,
      p_rows: batch.map((row) => ({
        email: row.email,
        role: row.role,
        invited_by: input.userId,
      })),
    });
    if (error) throw error;
    inserted += typeof data === "number" ? data : 0;
  }

  if (input.errors.length > 0) {
    await supabase.from("import_errors").insert(
      input.errors.slice(0, 1000).map((e) => ({
        import_id: record.id,
        line_no: e.lineNo,
        message: e.message,
      })),
    );
  }

  await supabase
    .from("imports")
    .update({ success_rows: inserted, status: "done" })
    .eq("id", record.id);

  return { mode: "done" as const, importId: record.id, inserted };
}

export function hashContent(bytes: Uint8Array) {
  return createHash("sha256").update(bytes).digest("hex");
}
```

三个细节。

哈希算的是文件字节，与解析后的行无关。同一份内容换个文件名，哈希不变，仍然判重。

`success_rows` 是实际插入数，可能小于提交数（已存在的邮箱被 `on conflict` 跳过）。这两个数字都要显示出来，用户才知道发生了什么。



已存在的邮箱不必报错。之前邀请过、对方还没接受，再次导入时 `on conflict do nothing` 直接跳过，不产生新记录。用户看到的是“成功 42 行”，不会出现“42 行失败，原因：已存在”。

邀请 token 由数据库生成，不用应用层拼。`gen_random_bytes(24)` 出 192 位随机数，转成十六进制字符串。token 要唯一索引，重复概率低但仍要约束。

过期时间写死在函数里，七天。这个值应该来自配置表，写死在 SQL 里改起来要发迁移。第一版接受这个代价，别为一次配置加一张表。错误表不加索引也能用。一张导入最多一千行记录，按 `import_id` 查的时候全表扫也够快。数据量涨上来再加索引，现在别为将来优化。

错误只存前 1000 条。十万行的文件可能有几万条错误，全存没意义，展示时也只给前 100 条。

## 32.5 大文件走队列

两千行以上的导入不放在请求里。浏览器等不了几十秒，函数也会超时。

排队之后要能看进度。前端轮询导入记录的状态：

```ts
// src/app/api/t/[slug]/imports/[importId]/route.ts
import { NextRequest } from "next/server";
import { createClient } from "@/lib/supabase/server";
import { apiError } from "@/lib/api/errors";

export async function GET(
  _request: NextRequest,
  context: RouteContext<"/api/t/[slug]/imports/[importId]">,
) {
  const { slug, importId } = await context.params;

  const supabase = await createClient();
  const { data: auth } = await supabase.auth.getClaims();
  if (!auth?.claims) return apiError(401, "unauthorized", "未登录");

  const { data, error } = await supabase
    .from("imports")
    .select("id, status, total_rows, success_rows, failed_rows")
    .eq("id", importId)
    .maybeSingle();

  if (error) return apiError(500, "internal_error", "查询失败");
  if (!data) return apiError(404, "not_found", "导入记录不存在");

  return Response.json(
    { ...data, slug },
    { headers: { "Cache-Control": "no-store" } },
  );
}
```

队列里的导入要能看到“卡住”。状态有 `queued`、`running`、`done`、`failed` 四种，运行超过十分钟的标记为失败，写一条原因。用户刷新页面能看到当前状态，不用猜。

重试次数要设上限。文件本身有问题时，重试多少次都会失败，三次之后停止，把失败原因展示给用户。重试逻辑和第 30 章的 `claim_jobs` 共用一套，不另写。

任务由第 30 章的 cron worker 领取。worker 里按 `kind` 分发，`import_invitations` 走同一个分批插入逻辑，完成后把 `imports.status` 改成 `done` 或 `failed`。

失败时的重试要小心。分批插入的每一批都在独立事务里，第三批失败时前两批已经提交。重跑整份文件会撞唯一索引，`on conflict do nothing` 跳过已有行，剩下的继续插。这种语义正好是幂等的。

## 32.6 导出：Excel 能打开才算数

导出的 CSV 要满足三件事：Excel 双击打开不乱码、字段里的逗号和换行不破坏结构、以公式开头的单元格不被执行。

```ts
// src/lib/csv/write.ts
const BOM = "\uFEFF";
const CRLF = "\r\n";

export function escapeCsvCell(value: unknown): string {
  if (value === null || value === undefined) return "";

  let text = String(value);

  // 公式注入：以这些字符开头的单元格会被 Excel 当公式执行
  if (/^[=+\-@\t\r]/.test(text)) {
    text = `'${text}`;
  }

  if (/[",\r\n]/.test(text)) {
    text = `"${text.replace(/"/g, '""')}"`;
  }

  return text;
}

export function toCsv(headers: string[], rows: unknown[][]): string {
  const lines = [
    headers.map(escapeCsvCell).join(","),
    ...rows.map((row) => row.map(escapeCsvCell).join(",")),
  ];
  return BOM + lines.join(CRLF) + CRLF;
}
```

BOM 放在最前面。没有它，Excel 按系统默认编码解析，中文变乱码。这三个字节是 Windows 版的必需项，macOS 的 Numbers 无所谓，两边都加。



数字和日期要按文本处理，别让 Excel 自作主张。手机号以 0 开头，Excel 会把前导零吃掉；长数字被转成科学计数法，后几位变成 0。这两种情况在导出 ID、订单号时特别常见。

处理方式是加前导单引号，或者把列格式固定成文本。CSV 没有格式的概念，只能靠前导单引号：`\`'0123456789\``。代价是用户复制出来会带引号，要接受这一点。

日期统一输出 ISO 格式。`2026-11-15T08:30:00.000Z` 这种格式 Excel 能识别成日期，也能当文本读。别输出本地化格式，`11/15/2026` 在不同地区解释不同。行尾用 CRLF。LF 在 Excel 里也能打开，个别老版本会粘成一行。统一 CRLF 最稳。

公式注入是最容易被忽略的一条。单元格的值来自用户输入，形如 `=HYPERLINK("http://evil","点我")` 的内容会被 Excel 执行。加一个前导单引号，Excel 就当普通文本处理。这一点在导出用户提交的内容时必须做。

导出端点：

```ts
// src/app/api/t/[slug]/export/activity/route.ts
import { NextRequest } from "next/server";
import { createClient } from "@/lib/supabase/server";
import { toCsv } from "@/lib/csv/write";

export async function GET(
  _request: NextRequest,
  context: RouteContext<"/api/t/[slug]/export/activity">,
) {
  const { slug } = await context.params;
  const supabase = await createClient();

  const { data: team } = await supabase.from("teams").select("id").eq("slug", slug).maybeSingle();
  if (!team) return Response.json({ error: "not_found" }, { status: 404 });

  const { data, error } = await supabase
    .from("activity_logs")
    .select("created_at, action, actor_id, metadata")
    .eq("team_id", team.id)
    .order("created_at", { ascending: false })
    .limit(5000);

  if (error) return Response.json({ error: "internal_error" }, { status: 500 });

  const csv = toCsv(
    ["时间", "动作", "操作者", "摘要"],
    (data ?? []).map((row) => [
      row.created_at,
      row.action,
      row.actor_id,
      row.metadata?.summary ?? "",
    ]),
  );

  const filename = `activity-${slug}-${new Date().toISOString().slice(0, 10)}.csv`;

  return new Response(csv, {
    headers: {
      "Content-Type": "text/csv; charset=utf-8",
      "Content-Disposition": `attachment; filename="${filename}"; filename*=UTF-8''${encodeURIComponent(filename)}`,
      "Cache-Control": "no-store",
    },
  });
}
```

文件名带日期，用户下载多次不会互相覆盖。

文件名同时给 `filename` 和 `filename*`。前者是 ASCII 兜底，后者带 UTF-8 编码的文件名，浏览器优先用后者。只写一个的话，中文名在某些浏览器里会变成乱码。



只导出当前筛选范围，不导出整个团队。用户筛了十一月，导出就只给十一月的数据，行为要和列表一致。

导出列要有白名单。用户传 `?columns=email,name` 时按这个列表输出，不在白名单里的列直接忽略。拼 SQL 时列名不能参数化，只能从映射表里取，否则就是注入点。

导出量要限。默认五千行，超过就提示用户缩小时间范围。一次性导出整表是运维事故的常见起点，数据库要扫全表，内存和网络都会被拖住。导出要有权限。完整数据导出的风险比查看页面高，只给 owner 角色。这条判断放在 SQL 里，和查询一起完成。

导出和删除都要写日志。导出动作记一条 `activity_logs`，`action` 是 `export.activity`。审计时能回答“谁在什么时候导出了什么”。

## 32.7 十万行也不该爆内存

`toCsv` 把整份数据拼成一个字符串。五千行没问题，十万行就是几十 MB，函数内存吃不消。

流式导出的做法是边查边写，不把结果集整体拿到内存里：

```ts
// src/lib/csv/stream.ts
import { Readable } from "node:stream";
import { escapeCsvCell } from "@/lib/csv/write";

const BOM = "\uFEFF";
const CRLF = "\r\n";

export function csvStream(headers: string[], fetchPage: (cursor: string | null) => Promise<{
  rows: unknown[][];
  nextCursor: string | null;
}>): ReadableStream {
  const encoder = new TextEncoder();

  return new ReadableStream({
    async start(controller) {
      controller.enqueue(encoder.encode(BOM + headers.map(escapeCsvCell).join(",") + CRLF));

      let cursor: string | null = null;
      for (;;) {
        const page = await fetchPage(cursor);
        for (const row of page.rows) {
          controller.enqueue(encoder.encode(row.map(escapeCsvCell).join(",") + CRLF));
        }
        if (!page.nextCursor) break;
        cursor = page.nextCursor;
      }

      controller.close();
    },
  });
}
```

游标用 `created_at`。每批取一千行，记下最后一条的时间，下一批从它之后取：

```ts
// 每批的查询
const { data } = await supabase
  .from("activity_logs")
  .select("created_at, id, action")
  .eq("team_id", teamId)
  .lt("created_at", cursor ?? new Date().toISOString())
  .order("created_at", { ascending: false })
  .limit(1000);
```



每批一千行是折中。太小，往返次数多；太大，单次查询的内存占用高。按行宽估算，一千行大约是几百 KB。

也可以不用应用层循环，直接在 psql 里用 `\copy` 导出，速度最快。代价是它只能在服务器上执行，权限模型和 Web 应用不同，也没法走行级安全。运营导数据用它，面向用户的导出用接口。`lt("created_at", cursor)` 严格小于，避免同一条重复出现。同一毫秒有多条记录时，这个条件会漏掉一部分。要精确，用 `(created_at, id)` 复合游标，查询写成 `or(created_at.lt.X,and(created_at.eq.X,id.lt.Y))`。

导出结束后可以顺便压缩。响应头写 `Content-Encoding: gzip`，用 `zlib` 包一层流，十万行文本能压到原体积的十分之一。代价是客户端解压，浏览器自动处理。

流式响应有三个前提。

不要设 `Content-Length`。长度要在数据全部生成后才知道，流式响应直接不写这个头，浏览器按 chunked 接收。

反代要关闭缓冲。nginx 默认会攒够一定大小再往客户端发，流式响应看起来像卡住。配置里加 `proxy_buffering off;`，或者在响应头里加 `X-Accel-Buffering: no`。

函数有时长上限。Vercel 的 Hobby 计划函数最长 300 秒，几十万行的导出会超时。超过这个量级的导出改走“生成文件 + 存对象存储 + 邮件通知下载”的异步流程。

`"use cache"` 不能用在流式响应上。缓存要完整的结果，流式的结果只能消费一次。

## 32.8 报表和列表对不上

先别改代码，先把两边的查询语句贴在一起对比。多数时候差一行 `where`，少数时候是聚合和列表用了不同的时间范围。

报表页显示“本周 128 条活动”，活动列表翻完只有 121 条。三个原因，按出现频率排：

时区。数据库存的是 UTC，列表按用户本地时间显示，报表按天分组时要指定时区。用 `at time zone` 把 UTC 转成业务时区再截断到天。

软删除。团队表有 `deleted_at`，报表的聚合查询忘了加 `where deleted_at is null`，把已删除的团队也算进去了。

权限。列表查询带用户过滤（只能看自己的），报表用聚合函数时漏了这一条，或者用了 `security definer` 绕过行级安全。

把口径写进一个函数，报表页和导出都调它：

```sql
-- supabase/migrations/20261126091000_reports.sql
create or replace function public.team_activity_daily(
  p_team_id uuid,
  p_from date,
  p_to date
)
returns table (day date, total bigint)
language sql
stable
security invoker
as $$
  select
    (a.created_at at time zone 'Asia/Shanghai')::date as day,
    count(*) as total
  from public.activity_logs a
  where a.team_id = p_team_id
    and a.created_at >= (p_from::timestamptz)
    and a.created_at < ((p_to + 1)::timestamptz)
  group by 1
  order by 1;
$$;
```

`security invoker` 让行级安全生效。`at time zone 'Asia/Shanghai'` 先换时区再取日期，跨零点的记录会归到正确的本地日期。

范围用左闭右开：`>= p_from` 且 `< p_to + 1 天`。两端都用 `between` 会把结束当天的零点之后的数据漏掉，也会因为时区换算多算一天。

应用层调用：

```ts
// src/lib/reports.ts
import "server-only";
import { cacheLife, cacheTag } from "next/cache";
import { createClient } from "@/lib/supabase/server";

export async function getTeamActivityDaily(teamId: string, from: string, to: string) {
  "use cache";
  cacheTag(`report:${teamId}`);
  cacheLife("minutes");

  const supabase = await createClient();
  const { data, error } = await supabase.rpc("team_activity_daily", {
    p_team_id: teamId,
    p_from: from,
    p_to: to,
  });

  if (error) throw error;
  return (data ?? []) as { day: string; total: number }[];
}
```

页面上给一个时间范围选择器，默认最近七天。范围放 URL，刷新可还原，链接能分享给同事。

报表页和导出都调 `getTeamActivityDaily`，不各写一份 SQL。两处数字对不上，先查它们有没有调同一个函数。

页面上的日期格式化用固定 locale，不用浏览器默认：

```ts
new Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Shanghai" }).format(new Date(day));
```

`en-CA` 输出 `2026-11-15`，与数据库的 `date` 类型一致，排序也对。



数据量大到聚合查询变慢时，再考虑物化视图。物化视图存的是算好的结果，按天刷新，查询是读一张很小的表。代价是数据有延迟，刷新期间不更新。

```sql
create materialized view if not exists public.team_activity_mv as
select team_id, (created_at at time zone 'Asia/Shanghai')::date as day, count(*) as total
  from public.activity_logs
 group by 1, 2;

create unique index on public.team_activity_mv (team_id, day);
```

刷新用 `refresh materialized view concurrently`，加 `concurrently` 需要唯一索引，好处是刷新时不锁读。物化视图不继承行级安全，查询时要在外面套一层带权限的视图，或者只在服务端角色里读。

缓存也有边界。报表数据按团队隔离，公开缓存会把 A 团队的报表发给 B 团队。

报表不要设 `Cache-Control: public`。数据按团队隔离，公开缓存会把 A 团队的报表发给 B 团队。

## 32.9 检查点

1. 上传一份包含三条坏行的 CSV，页面显示“成功 7 行，失败 3 行”，错误报告能下载，每条带行号和原因。
2. 同一份文件再上传一次，提示“这份文件已经导入过”，`imports` 表不新增记录。
3. 导出活动列表的 CSV，用 Excel 直接打开，中文不乱码，字段里的逗号没有让列错位。
4. 在单元格里填 `=1+1`，导出的文件用 Excel 打开显示 `'=1+1`，没有被计算成 2。
5. 执行 `select * from team_activity_daily('<team>', '2026-11-01', '2026-11-15');`，总和与列表页显示的一致。
6. 导出十万行数据，浏览器下载正常结束，函数内存没有超过 1GB。

## 32.10 常见错误

1. 导入后所有邮箱都是乱码

文件是 GBK 编码，按 UTF-8 解码得到乱码。`TextDecoder` 用 `fatal: true` 会直接抛错，给出“另存为 UTF-8”的提示，别静默替换字符。

2. `there is no unique or exclusion constraint matching the ON CONFLICT specification`

`on conflict (team_id, lower(email)) where status = 'pending'` 与索引定义不一致。索引必须包含同样的表达式和 `where` 条件。

3. `invalid input syntax for type integer: "3行"`

CSV 里某一列带有单位或千分位。解析时先去掉非数字字符，或者在校验阶段报错并给出行号。

4. 导出的中文在 Excel 里乱码，Notepad 打开正常

缺 BOM。在文件开头加 `\uFEFF`，并把 `Content-Type` 写成 `text/csv; charset=utf-8`。

**5. 导出十万行时函数超时**

同步拼字符串的方式内存和时长都撑不住。改用流式输出，或者把导出改成异步任务：生成文件存对象存储，完成后发通知。

**6. 报表数字比列表多**

报表 SQL 漏了行级安全或软删除条件。检查函数是 `security invoker` 还是 `security definer`，以及查询里有没有 `deleted_at is null`。

## 32.11 这一章在做什么

这一章处理应用边界上的数据。

进入方向：先解码再解析，编码不确定就拒绝，不猜。逐行校验，错误带行号和原因，好行照常导入。同一份文件按内容哈希去重，重复提交返回上一次的结果。大文件走队列，进度靠轮询。

出去方向：BOM 和 CRLF 保证 Excel 能打开，引号转义保证结构不破，前导单引号挡住公式注入。数据量大时改成流式，边查边写。导出动作记日志。

检查点里的第六条最重要。流式导出失败时页面通常没有明显错误，用户拿到一个下载中断的文件，看不出少了多少行。让它跑一次十万行，才算验证过。

报表方向：口径写进一个 SQL 函数，报表页和导出共用。时区、软删除、行级安全是三个固定检查点，数字对不上时按这个顺序查。
