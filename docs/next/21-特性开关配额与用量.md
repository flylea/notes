# 第 21 章 特性开关、配额与用量

这一章讲三件与商业规则有关的事：功能能不能用（特性开关）、能用多少（配额）、已经用了多少（用量）。

需要它们的原因是上线之后的变化比上线时多。新功能要灰度给一部分团队，付费档要限制席位和存储，超限时要拦住并且说清楚原因。这些规则如果散落在各处，前端显示的和后端判断的会不一致。

涉及三个概念。开关（flag）控制功能是否可见，按环境、按团队灰度。配额（limit）是套餐的硬上限，按席位、存储、请求数计量。用量（usage）是当前实际消耗，需要实时或准实时统计。

这一章先给开关的实现与读法，再讲配额的三种指标与超限行为，最后讲前后端如何共用同一份判断，以及一批容易算错的边界。

## 21.1 开关的三种存储

开关可以放三个地方，用途不同。

环境变量：适合发布前的总开关，改一次要重新部署。按环境区分开发和生产。

数据库：适合按团队灰度，可以实时改。teamstack 用这张表。

第三方服务：适合非技术人员操作，带审计和审批流。小团队没必要。

这一章用环境变量加数据库的组合：环境变量做总开关，数据库做灰度名单。

## 21.2 开关的定义

所有开关集中在一个文件里，带默认值和灰度比例。

```ts
// src/lib/flags.ts
import 'server-only'

export type FlagName = 'pdf_export' | 'ai_summary' | 'webhooks'

type FlagConfig = {
  /** 环境变量名，值为 'true' 时开启 */
  env: string
  /** 灰度百分比 0-100，0 表示只有 env 打开时全量开启 */
  rollout: number
}

const FLAGS: Record<FlagName, FlagConfig> = {
  pdf_export: { env: 'FLAG_PDF_EXPORT', rollout: 100 },
  ai_summary: { env: 'FLAG_AI_SUMMARY', rollout: 10 },
  webhooks: { env: 'FLAG_WEBHOOKS', rollout: 0 },
}

/** 显式解析：只认 'true' / '1'，其余一律 false */
function envEnabled(name: string) {
  const raw = process.env[name]
  return raw === 'true' || raw === '1'
}

export function isFlagEnabled(flag: FlagName, teamId?: string | null): boolean {
  const config = FLAGS[flag]
  if (!config) return false
  if (!envEnabled(config.env)) return false

  // 没开灰度，或灰度 100%：全量
  if (config.rollout >= 100) return true
  if (config.rollout <= 0) return false

  // 有灰度但没有团队 id：保守起见不发
  if (!teamId) return false

  return bucketOf(teamId, flag) < config.rollout
}

/** 把字符串稳定映射到 0-99，同一个 team + flag 永远得到同一个值 */
function bucketOf(seed: string, salt: string): number {
  let h = 2166136261 // FNV-1a
  const input = `${salt}:${seed}`
  for (let i = 0; i < input.length; i++) {
    h ^= input.charCodeAt(i)
    h = Math.imul(h, 16777619)
  }
  return Math.abs(h) % 100
}
```


`envEnabled` 只认 `"true"` 和 `"1"` 两个值。写 `"yes"`、`"on"` 都会当成关闭，避免不同人写不同格式。

`bucketOf` 用 FNV-1a 哈希把字符串映射到 0–99。相同的 seed 和 salt 永远得到同一个分桶，用户不会在灰度中来回跳。

salt 用开关名，让不同开关的灰度人群不一样。同一个用户可以命中一个开关，不命中另一个。

## 21.3 三种读法

服务端组件直接调 `isEnabled`。

```tsx
// src/app/(app)/dashboard/layout.tsx（片段）
import { isFlagEnabled } from '@/lib/flags'
import { getActiveTeam } from '@/lib/teams'

export default async function DashboardLayout({ children }: { children: React.ReactNode }) {
  const team = await getActiveTeam()
  const canExport = isFlagEnabled('pdf_export', team?.id)

  return (
    <div className="flex">
      <Sidebar canExport={canExport} />
      <main>{children}</main>
    </div>
  )
}
```


Server Action 里必须再查一次。客户端可以把按钮藏起来，但不能阻止直接调用。

```ts
// src/app/(app)/export/actions.ts
export async function exportPdf(teamSlug: string) {
  const user = await requireUser()
  const { team } = await requireMembership(user.id, teamSlug)

  if (!isFlagEnabled('pdf_export', team.id)) {
    return { ok: false as const, error: '这个功能暂未开放' }
  }
  ...
}
```


客户端组件拿不到开关函数的真实值，因为它的数据源可能是服务端环境变量。只能由父级服务端组件把布尔值作为 props 传下去。

```tsx
// src/components/sidebar.tsx
export function Sidebar({ canExport }: { canExport: boolean }) {
  return (
    <nav>
      <Link href="/dashboard">概览</Link>
      {canExport && <Link href="/export">导出</Link>}
    </nav>
  )
}
```


## 21.4 关掉之后

开关关掉有三种表现，要区分清楚。

导航项不渲染。页面返回 404。Server Action 返回 `{ ok: false, error: "feature_disabled" }`。

不要抛异常。异常会被当成 500，监控里一片红，实际只是开关关了。

```tsx
// src/app/(app)/export/page.tsx
import { notFound } from 'next/navigation'
import { getActiveTeam } from '@/lib/teams'
import { isFlagEnabled } from '@/lib/flags'

export default async function ExportPage() {
  const team = await getActiveTeam()
  if (!team || !isFlagEnabled('pdf_export', team.id)) notFound()

  return <ExportForm teamSlug={team.slug} />
}
```


页面层用 `notFound()`，返回 404。403 会告诉用户“这里有个功能你无权访问”，404 什么都不说。

## 21.5 开关与套餐是两件事

开关控制上线节奏，套餐控制商业权益。

举例：`ai_summary` 是开关，先给 10% 的团队用；同时它是付费档的功能，免费档即使开关打开也不能用。

两者都要判断：`isEnabled("ai_summary") && plan.features.ai_summary`。

混在一起的后果是：想给免费档做个限时体验，得改套餐定义；想回滚功能，得改套餐定义。改错一次就是资损。

## 21.6 配额的三类指标

配额按指标分三类。

数量型：席位（成员数）、项目数、API 密钥数。直接 count 行数。

容量型：存储字节数。`sum(size_bytes)`，排除已删除的。

速率型：请求数、导出次数。按时间窗口计数，用 Redis 的日计数。

三类指标的统计方式不同，超限处理也不同，写代码之前先分清属于哪一类。数量型在创建时检查，容量型在写入时检查，速率型在入口检查。

## 21.7 套餐定义

套餐与上限集中在一处，前后端共用。

```ts
// src/lib/entitlements.ts
import 'server-only'

import { cache } from 'react'
import { createClient } from '@/lib/supabase/server'
import { isFlagEnabled } from '@/lib/flags'
import type { FlagName } from '@/lib/flags'

export type Plan = 'free' | 'pro' | 'team'

export type Entitlements = {
  plan: Plan
  seats: { used: number; limit: number }
  storage: { usedBytes: number; limitBytes: number }
  requests: { used: number; limit: number }
  features: Record<'pdf_export' | 'ai_summary' | 'webhooks', boolean>
}

const LIMITS: Record<Plan, { seats: number; storageBytes: number; requests: number }> = {
  free: { seats: 3, storageBytes: 1 * 1024 ** 3, requests: 10_000 },
  pro: { seats: 20, storageBytes: 50 * 1024 ** 3, requests: 500_000 },
  team: { seats: 100, storageBytes: 500 * 1024 ** 3, requests: 5_000_000 },
}

const PLAN_FEATURES: Record<Plan, FlagName[]> = {
  free: [],
  pro: ['pdf_export'],
  team: ['pdf_export', 'ai_summary', 'webhooks'],
}
```


`LIMITS` 是唯一真相，所有显示与判断都从它出发。前端显示进度条用它的 `limit`，后端判断超限也用它的 `limit`。

不要在组件里写死 `1024 * 1024 * 1024` 这种数字，改套餐时要改十几个地方。

## 21.8 统计用量

席位用一次 count 查询，`head: true` 只返回数量不返回数据。

```sql
-- 团队的当前席位数
select count(*) from public.team_members where team_id = $1;
```


注意 `head: true` 时 `data` 是 `null`，数量在 `count` 字段里。写成 `data?.length` 会永远得到 0，这个 bug 很难发现。

存储用量用聚合查询：

```sql
-- 已用存储（只算 ready 和 pending，deleted 不算）
select coalesce(sum(size_bytes), 0)::bigint as used
from public.files
where team_id = $1 and status <> 'deleted';

-- 单团队索引，让这个查询不会退化成全表扫描
create index if not exists files_team_status_idx on public.files (team_id, status);
```


`status <> 'deleted'` 是必须的。软删的文件不占配额，否则用户删了文件容量不降。

请求数用 Redis 的日计数，最近 31 天用 `mget` 一次取回。

```ts
// src/lib/usage.ts
import 'server-only'

import { redis } from '@/lib/redis'

function dayKey(teamId: string) {
  const day = new Date().toISOString().slice(0, 10) // 2026-11-15
  return `usage:req:${teamId}:${day}`
}

/** 每次成功处理一个需要计量的请求，就 +1 */
export async function recordRequest(teamId: string) {
  const key = dayKey(teamId)
  await redis.multi().incr(key).expire(key, 60 * 60 * 24 * 40).exec()
}

export async function getMonthlyRequests(teamId: string): Promise<number> {
  const now = new Date()
  const keys: string[] = []
  for (let i = 0; i < 31; i++) {
    const d = new Date(Date.UTC(now.getUTCFullYear(), now.getUTCMonth(), now.getUTCDate() - i))
    keys.push(`usage:req:${teamId}:${d.toISOString().slice(0, 10)}`)
  }
  const values = (await redis.mget<(number | null)[]>(...keys)) ?? []
  return values.reduce<number>((sum, v) => sum + (v ?? 0), 0)
}
```


## 21.9 组装 entitlements

三个指标合到一个对象里，加一层 React `cache`，一次请求只查一次。

```ts
// src/lib/entitlements.ts（续）
export const getEntitlements = cache(async (teamId: string): Promise<Entitlements> => {
  const supabase = await createClient()

  const [{ data: team }, { count: usedSeats }, { data: storage }] = await Promise.all([
    supabase.from('teams').select('id, plan').eq('id', teamId).single(),
    // head: true 时不会返回行，只返回 count，所以必须用 count，不能用 data.length
    supabase.from('team_members').select('user_id', { count: 'exact', head: true }).eq('team_id', teamId),
    supabase.from('files').select('size_bytes').eq('team_id', teamId).neq('status', 'deleted'),
  ])

  const plan = (team?.plan as Plan) ?? 'free'
  const limits = LIMITS[plan]
  const usedBytes = (storage ?? []).reduce((sum, f) => sum + (f.size_bytes ?? 0), 0)
  const usedRequests = await getMonthlyRequests(teamId)

  const enabled = new Set(PLAN_FEATURES[plan])
  const features = {
    pdf_export: enabled.has('pdf_export') && isFlagEnabled('pdf_export', teamId),
    ai_summary: enabled.has('ai_summary') && isFlagEnabled('ai_summary', teamId),
    webhooks: enabled.has('webhooks') && isFlagEnabled('webhooks', teamId),
  }

  return {
    plan,
    seats: { used: usedSeats, limit: limits.seats },
    storage: { usedBytes, limitBytes: limits.storageBytes },
    requests: { used: usedRequests, limit: limits.requests },
    features,
  }
})
```


返回结构固定：每个指标有 `used`、`limit`、`percent`。前端按 `percent` 显示进度条，后端按 `used >= limit` 判断超限。

`percent` 要 clamp 到 100 以内，显示用。判断超限不要用它，用原始数值。

## 21.10 超限的三种行为

超限不等于直接失败，按业务分三档。

软限制：允许继续，显示警告。适合请求数这类有弹性的指标。

硬阻断：直接拒绝。适合存储、席位这类资源型指标。

宽限期：付费用户过期后给 7 天缓冲。适合订阅状态变化。

```ts
// src/app/(app)/files/actions.ts
'use server'

import { requireUser } from '@/lib/auth'
import { requireMembership } from '@/lib/teams'
import { getEntitlements } from '@/lib/entitlements'
import { createClient } from '@/lib/supabase/server'

export async function createUploadTicket(input: {
  teamSlug: string
  name: string
  sizeBytes: number
  mime: string
}) {
  const user = await requireUser()
  const { team } = await requireMembership(user.id, input.teamSlug)
  const ent = await getEntitlements(team.id)

  // 1. 单文件大小限制（防单个巨文件）
  if (input.sizeBytes > 100 * 1024 * 1024) {
    return { ok: false as const, code: 'file_too_large', error: '单个文件不能超过 100MB' }
  }

  // 2. 配额检查
  const remaining = ent.storage.limitBytes - ent.storage.usedBytes
  if (input.sizeBytes > remaining) {
    return {
      ok: false as const,
      code: 'storage_quota_exceeded',
      error: `存储空间不足，还需 ${formatBytes(input.sizeBytes - remaining)}`,
      meta: {
        usedBytes: ent.storage.usedBytes,
        limitBytes: ent.storage.limitBytes,
        upgradeUrl: '/dashboard/billing',
      },
    }
  }

  // 3. 插入 pending 记录（第 12 章的流程）
  const supabase = await createClient()
  const { data, error } = await supabase
    .from('files')
    .insert({
      team_id: team.id,
      uploader_id: user.id,
      name: input.name,
      mime: input.mime,
      size_bytes: input.sizeBytes,
      storage_path: `${team.id}/${crypto.randomUUID()}`,
      status: 'pending',
    })
    .select('id, storage_path')
    .single()

  if (error) return { ok: false as const, code: 'db_error', error: '创建上传失败' }
  return { ok: true as const, file: data }
}

function formatBytes(n: number) {
  if (n >= 1024  3) return `${(n / 1024  3).toFixed(1)}GB`
  if (n >= 1024  2) return `${(n / 1024  2).toFixed(0)}MB`
  return `${Math.ceil(n / 1024)}KB`
}
```


错误返回答要带升级入口，前端才能引导。

## 21.11 前端显示

进度条显示百分比，上传按钮在超限时禁用，但删除入口要保留。

```tsx
// src/app/(app)/files/upload-form.tsx
'use client'

import { useState } from 'react'
import Link from 'next/link'
import { createUploadTicket } from './actions'

type Quota = { usedBytes: number; limitBytes: number }

export function UploadForm({ teamSlug, quota }: { teamSlug: string; quota: Quota }) {
  const [message, setMessage] = useState<{ text: string; upgrade?: string } | null>(null)
  const usedPct = Math.min(100, Math.round((quota.usedBytes / quota.limitBytes) * 100))
  const full = quota.usedBytes >= quota.limitBytes

  async function onSubmit(formData: FormData) {
    const file = formData.get('file') as File
    const result = await createUploadTicket({
      teamSlug,
      name: file.name,
      sizeBytes: file.size,
      mime: file.type,
    })

    if (!result.ok) {
      setMessage({ text: result.error, upgrade: result.meta?.upgradeUrl })
      return
    }
    setMessage(null)
    // 走第 12 章的直传流程
  }

  return (
    <div>
      <div className="mb-2 flex items-center justify-between text-sm">
        <span>
          已用 {formatBytes(quota.usedBytes)} / {formatBytes(quota.limitBytes)}
        </span>
        <span className={usedPct >= 80 ? 'text-amber-600' : 'text-gray-500'}>{usedPct}%</span>
      </div>
      <div className="h-2 rounded bg-gray-200">
        <div
          className={usedPct >= 100 ? 'h-2 rounded bg-red-500' : 'h-2 rounded bg-blue-500'}
          style={{ width: `${usedPct}%` }}
        />
      </div>

      {usedPct >= 80 && !full && (
        <p className="mt-2 text-sm text-amber-600">存储空间快满了，建议清理旧文件或升级套餐。</p>
      )}

      <form action={onSubmit} className="mt-4">
        <input type="file" name="file" disabled={full} required />
        <button type="submit" disabled={full}>
          {full ? '存储空间已满' : '上传'}
        </button>
      </form>

      {message && (
        <div className="mt-3 rounded border border-red-200 bg-red-50 p-3 text-sm">
          <p>{message.text}</p>
          {message.upgrade && (
            <Link href={message.upgrade} className="mt-1 inline-block underline">
              升级套餐
            </Link>
          )}
        </div>
      )}
    </div>
  )
}

function formatBytes(n: number) {
  if (n >= 1024  3) return `${(n / 1024  3).toFixed(1)}GB`
  return `${Math.ceil(n / 1024 ** 2)}MB`
}
```


三件事要一起做。数字精确到百分比，不显示小数。超限时说明原因和升级价格。删除操作永远可用，否则用户没法自救。

## 21.12 前后端一致

三个原则。

第一，同一个 `Entitlements` 对象驱动前端显示和后端判断。不要一边算一边另算一遍。

第二，不把 `price_id` 送给前端。前端只需要 `plan` 名称和 `limit` 数字。

第三，错误码统一。

```ts
// src/lib/error-codes.ts
export const ERROR_CODES = {
  storage_quota_exceeded: '存储空间不足',
  seats_quota_exceeded: '成员数已达上限',
  requests_quota_exceeded: '本月请求数已用完',
  feature_not_enabled: '功能未开启',
  file_too_large: '文件过大',
} as const

export type ErrorCode = keyof typeof ERROR_CODES
```


前端按错误码匹配文案，不解析错误信息里的字符串。

## 21.13 席位配额

邀请成员前查席位。

待处理的邀请不占席位，接受时才检查。这个差异会导致“邀请发出去了但满员加不进来”，所以邀请时也要提示剩余席位。

## 21.14 请求计量的三个坑

在 proxy 里计数会虚高，因为预取也走 proxy。一个页面十个链接就是十次计数。

在业务失败之前计数会多收。用户上传失败也占了一次配额。

客户端重试会重复计数。网络抖动时浏览器可能重发。

正确做法是在业务成功的分支里计数，一次操作记一次。

```ts
// src/lib/usage.ts（续）
export async function withMetering<T>(
  teamId: string,
  fn: () => Promise<T>
): Promise<{ result: T; remaining: number } | { error: 'quota' }> {
  const ent = await getEntitlements(teamId)
  if (ent.requests.used >= ent.requests.limit) return { error: 'quota' }

  const result = await fn() // 只有成功走到这里才计数
  await recordRequest(teamId)

  return { result, remaining: ent.requests.limit - ent.requests.used - 1 }
}
```


## 21.15 订阅状态与降级

`subscriptions.status` 有五个值：`active`、`trialing`、`past_due`、`canceled`、`incomplete`。

对应三档处理：`active` 和 `trialing` 按当前套餐；`past_due` 给 7 天宽限；`canceled` 到期后降到免费档。

`current_period_end` 是秒级时间戳，`new Date(x * 1000)` 才是正确时间。忘了乘 1000 会得到 1970 年，宽限期判断全部失效。

```ts
// src/lib/entitlements.ts（片段）
function resolvePlan(sub: { status: string; current_period_end: string } | null): Plan {
  if (!sub) return 'free'
  const active = ['active', 'trialing'].includes(sub.status)
  const withinPeriod = new Date(sub.current_period_end) > new Date()
  if (active && withinPeriod) return 'pro' // 这里简化了，真实映射看 price_id
  return 'free'
}
```


## 21.16 账单页

账单页要显示三样：当前套餐、下次扣费时间、用量。

```tsx
        <thead>
          <tr><th>项目</th><th>已用</th><th>上限</th><th>状态</th></tr>
        </thead>
        <tbody>
          <tr>
            <td>成员</td><td>{ent.seats.used}</td><td>{ent.seats.limit}</td>
            <td>{ent.seats.used >= ent.seats.limit ? '已满' : '正常'}</td>
          </tr>
          <tr>
            <td>存储</td><td>{formatBytes(ent.storage.usedBytes)}</td><td>{formatBytes(ent.storage.limitBytes)}</td>
            <td>{ent.storage.usedBytes >= ent.storage.limitBytes ? '已满' : '正常'}</td>
          </tr>
          <tr>
            <td>请求</td><td>{ent.requests.used.toLocaleString()}</td><td>{ent.requests.limit.toLocaleString()}</td>
            <td>{ent.requests.used >= ent.requests.limit ? '已满' : '正常'}</td>
          </tr>
        </tbody>
      </table>
    </section>
  )
}
```


用量部分复用 `getEntitlements`，不要另写一套查询。

## 21.17 开关的下线

功能稳定之后，开关要清理。

三件事。把默认值改成 `true`，把灰度改成 100。删掉判断分支，代码里不留 `if (isEnabled(...))`。从定义表里删掉这个开关。

留着开关的后果是：半年后没人知道它控制什么，也没人敢删。

## 21.18 灰度按团队还是按用户

按用户灰度适合界面改动：同一个团队的人看到不同版本，不影响协作。

按团队灰度适合影响数据的功能：AI 摘要、导出格式。同一个团队的人应该看到一致的界面和数据，否则客服解释不清。

分桶的 seed 用团队 id 还是用户 id，决定了这一点。影响数据的功能用 `teamId`，纯界面用 `userId`。

两种都要在开关定义里写清楚，别混用。

## 21.19 开关的命名

名字要说明控制什么，不要写成实现细节。

`pdf_export` 好过 `enable_export_v2`。前者是能力，后者是实现细节，实现换了一版名字就过期。

环境变量用大写下划线，和数据库里的名字一一对应：`ENABLE_PDF_EXPORT` 对应 `pdf_export`。

名字里不要带日期和版本号。要区分新旧实现，用两个开关，不要用 `_v2`。

## 21.20 用量的实时性

三种精度，成本不同。

实时：每次操作后立刻更新计数。准确，但每次写入多一次 Redis 调用。

准实时：每分钟聚合一次。延迟一分钟，成本低。

离线：每天跑批。延迟一天，够用于账单。

进度条用准实时就够。账单用离线数据，与支付平台对账。

三者混用时说清楚哪一个是真相。账单以离线为准，进度条只是参考。

## 21.21 提前预警

超限时才提示，用户体验差。

80% 时提示一次，站内信加顶部横幅。95% 时再提示一次。100% 时阻断并给升级入口。

提示文案要带具体数字：“已用 4.2 GB / 5 GB，剩余 0.8 GB”。

不要每次都弹窗。用户会关掉，之后就看不到了。用常驻的横幅，可以手动关闭。

## 21.22 与支付平台对账

账单金额以支付平台为准，应用数据库是副本。

每周对一次：拉支付平台的订阅列表，和 `subscriptions` 表比对。差异通常是 webhook 丢事件，或者用户在产品外改了订阅。

处理差异的原则是“以支付平台为准，补写数据库”。反向覆盖会改坏真实状态。

对账脚本用 `service_role`，只读不写，产出差异报告人工确认。

## 21.23 升级与降级的路径

升级是即时的，降级是延后的。

升级：用户付款后立即生效，`subscriptions.seats` 同步给支付平台，功能立刻可用。

降级：当前周期结束后生效。立即降级会导致用户已付的费用浪费。

降级时如果用量超过新套餐上限，给 30 天缓冲，提示用户清理。缓冲期结束仍然超限，按只读处理：能看能删，不能新增。

## 21.24 免费档的成本

免费用户不付费，但消耗资源。要控制单用户成本。

三个限制。存储上限小，请求数上限低，导出功能关闭。

另外两个手段：免费档不提供 API 密钥，减少脚本滥用；免费档的团队数量限制为 1 个，避免一个账号建几十个团队。

数字不用精确，目标是让单个免费用户的成本低于千分之一元。

## 21.25 按人计费的两个坑

席位计费有两处容易错。

第一，重复计费。用户被移除又加回来，`subscriptions.seats` 如果每次都加一，会多收。正确做法是按当前实际成员数同步，不做增减。

第二，离职员工的席位。移除成员后要立刻同步席位给支付平台，否则用户多付一个月。

同步做成幂等的：先 count 成员，再调用支付平台的更新接口，传绝对值，不传增量。

## 21.26 开关的测试

开关有两条路径要测：开和关。

测试里 mock 开关函数，两个分支都跑一遍。CI 里至少保证关闭状态下主流程不报错。

更实际的测试是“关掉开关之后，页面仍然能访问，只是功能入口消失”。很多 bug 出在这里：关掉开关后页面 500，因为某处直接读了开关才有的数据。

## 21.27 老用户与新配额

调整套餐上限时，已有用户可能立刻超限。

三种处理。老用户保持旧上限直到续费；给 30 天缓冲；直接按新上限执行。

推荐第二种。改上限的当天发一封邮件说明，缓冲期内不阻断，只提示。

数据库里要能区分“何时开始按新上限算”。用 `subscriptions.updated_at` 或单独的字段记录。

## 21.28 定价页与代码的同步

定价页写“20 个席位、50 GB”，代码里是 `LIMITS.pro`。

两处不一致是常见事故：销售改了定价页，代码没改，用户买了发现上限不对。

做法：定价页的文案从 `LIMITS` 生成，不手写数字。套餐名和价格的来源是支付平台的产品配置，用量从代码里读。

改套餐时只改一处，发版后两端一致。

## 21.29 试用期

试用期要处理三件事：到期提醒、到期降级、防止重复试用。

试用期用支付平台的 trial 机制，`status = 'trialing'`，`current_period_end` 是试用结束时间。

到期前三天发提醒。到期后自动降级到免费档，不删数据。

防重复试用按团队算，不按账号。同一团队用过一次试用，就不能再用。用 `subscriptions` 的历史记录判断。

## 21.30 取消与退款

取消订阅不立即降级，等到周期结束。用户已经付了钱，继续用到期末。

界面要写清楚：“当前周期到 3 月 1 日，之后不再续费”。不要写“已取消”就完事，用户会以为立刻不能用。

退款走支付平台的手工流程，不在应用里做。应用侧只处理 webhook 回来的状态变化。

## 21.31 用量导出

企业客户会要求导出用量明细。

导出接口用 `service_role`，按团队和时间范围聚合，输出 CSV。

导出本身也要限流和审计。大客户一次导一年的明细，可能几十万行，要异步生成，生成完发链接。

链接用签名 URL，有效期一小时。

## 21.32 开关与实验平台的区别

开关控制“这个功能是否对某个团队开放”。实验平台控制“这个改动的哪个版本表现更好”。

两者的差别在目标：开关是工程决策，实验是产品决策。前者不需要统计显著性，后者需要。

小团队用开关做灰度足够，不要一上来就搭实验平台。等有明确的转化率问题再用。

## 21.33 监控配额命中

配额超限的次数值得监控。

按错误码聚合，看 `storage_quota_exceeded`、`seats_quota_exceeded`、`rate_limited` 的数量。

数量突然上升，要么是产品增长（好事），要么是被人刷（坏事）。看对应的团队分布就能区分。

单个团队反复命中，说明上限设得不合理，或者用户在恶意使用。前者调上限，后者联系客户。

## 21.34 配额的错误码设计

错误码要能被前端直接映射到文案和动作，不要靠解析句子。

三个字段：`code`（机器读）、`message`（兜底文案）、`meta`（数字，比如当前用量和上限）。

```ts
// src/lib/error-codes.ts（片段）
export const QUOTA_ERRORS = {
  storage_quota_exceeded: { status: 413, upgrade: true },
  seats_quota_exceeded: { status: 409, upgrade: true },
  rate_limited: { status: 429, upgrade: false },
} as const;
```

`upgrade: true` 表示这个错误应该弹升级框，`false` 表示重试就行。前端不需要为每个码写一个 if。

## 21.35 从免费到付费的转化点

配额的价值在转化点上体现。

四个自然的转化点：席位加满、存储到 80%、用量过 1000 次、导出被拦。

在这些位置放升级入口，比在设置页放一个“升级”按钮有效得多。

提示语要具体。“你已用 4.2 GB，免费档上限 5 GB”比“升级解锁更多空间”有用。

## 21.36 用量数据的口径

同一个数字在不同页面要一致。

团队页显示的存储用量、账单页显示的存储用量、超限时的报错数字，必须来自同一个函数。

口径要写清楚：是否包含已删除文件、是否包含正在上传的文件、什么时候刷新。

teamstack 的口径：排除 `deleted`，包含 `pending`，每分钟刷新一次，实时值以最后一次同步为准。

## 21.37 开关与缓存的冲突

开关值如果被缓存，关掉之后要等缓存过期才生效。

页面用 `'use cache'` 时，开关判断必须放在缓存外面，或者把开关值作为缓存键的一部分。

更简单的做法：开关判断不放缓存函数里，缓存函数只接收已经确定好的布尔值。

这样关掉开关时，下一次请求就生效，不需要等缓存。

## 21.38 上线时的顺序

改配额或开关，按这个顺序发。

第一步，加新字段和新函数，不改行为。第二步，前端开始读新接口。第三步，切换后端判断。第四步，删旧逻辑。

顺序反了会出现“前端已经按新上限显示，后端还在用旧上限”，用户看到数字和实际不符。

四步可以分四次发版，也可以一次发版但用开关控制。后者的前提是开关本身可靠，第 21.6 节已经讲过怎么保证。

## 21.39 客户端怎么知道超限

服务端渲染时算好 `Entitlements`，作为 props 传进客户端组件。

不要在前端自己算。前端拿不到 `service_role` 的统计能力，也算不全（比如已删除文件）。

传三个字段就够：`used`、`limit`、`percent`。客户端组件据此显示进度条和禁用状态。

上传动作仍然会被服务端再拦一次。前端禁用只是体验，服务端判断才是防线。

## 21.40 特性开关的文档

每个开关要有一行说明：控制什么、默认值、谁负责、什么时候删。

写在 `src/lib/flags.ts` 的注释里，或者单独的表格。团队人数超过五个人就需要这份文档，否则没人敢删开关。

开关的生命周期通常是两到三个月。到期没删的，要么功能稳定了该删，要么功能失败了该删代码。

## 21.41 检查点

1. 把 `ENABLE_PDF_EXPORT` 设为 `false`，导航里没有入口，直接访问 `/export` 得到 404，action 返回 `feature_disabled`。
2. 把某个团队的存储用量填到上限，上传返回 `storage_quota_exceeded`，前端显示升级提示，删除仍然可用。
3. `getEntitlements` 的返回里，`percent` 与 `used / limit` 一致。
4. 邀请第 4 个人到免费档团队，返回 `seats_quota_exceeded`。
5. 同一个请求里调用两次 `getEntitlements(teamId)`，日志里只有一次 count 查询，说明 `cache` 生效。
6. `mget` 返回的 31 天计数里缺某一天时，用量按 0 处理，页面不报错。

## 21.42 常见错误

**1. 开关只在客户端判断**

现象：隐藏了按钮，但直接调接口仍然成功。原因：只在组件里判断。改法：action 里再判断一次。

**2. 配额数字写死在组件里**

现象：改了套餐定义，页面显示的还是旧上限。原因：组件里硬编码。改法：统一从 `LIMITS` 读。

3. `head: true` 时用 `data.length`

现象：席位用量永远显示 0。原因：`head: true` 不返回数据行。改法：用解构出来的 `count`。

**4. 忘了乘 1000**

现象：宽限期判断错误，付费用户被立刻降级。原因：`current_period_end` 是秒。改法：`new Date(x * 1000)`。

**5. 超限直接抛异常**

现象：日志里一堆 500，用户看到错误页。原因：用 `throw` 表达业务失败。改法：返回 `{ ok: false, code }`。

6. 在 proxy 里统计用量

现象：请求数比实际高一倍以上。原因：预取也触发 proxy。改法：在业务成功处计数。
