# 第 10 章 事务隔离级别与并发冲突

第 9 章把连接管住了：应用和服务端之间只留五条连接，用完归还。这一章处理这些连接上跑的东西。一条 SQL 单独看都对，两条 SQL 同时跑，结果就可能不对。

并发问题有三个来源。第一是原子性：一次业务动作写了三张表，写到第二张时进程崩了，前一张已经落库。第二是可见性：两个请求同时读一行，各自读到的东西不一样，或者一个读的瞬间另一个正在改。第三是冲突：两个请求都想写同一行，数据库该让谁说了算，另一个怎么知道自己没写成。

数据库提供了三组工具对付它们。事务把多条语句合成一个边界，要么全成，要么全不成。隔离级别规定事务里能看到别人改到哪一步。锁和约束规定同一行被同时写时谁排队、谁报错。这三组工具之外，应用层还要补三件事：冲突怎么翻译成用户能懂的结果，重复请求怎么保证只执行一次，翻页怎么在持续写入的表上做到不重不漏。

这一章按这个顺序讲：先建事务边界，再讲隔离级别和用它演示的四种异常，然后是行锁、死锁、唯一冲突与幂等键、乐观锁，最后是并发下的分页。代码都接着 teamstack 项目，路径与前几章一致，`src/lib/db.ts` 提供连接池和事务助手。

书里的 SQL 基于 Postgres 15，Supabase 本地实例的版本。演示用的两个 `psql` 会话在本地库上操作；本机没有安装 Supabase CLI 和 `psql`，涉及命令输出的步骤标「未验证」。

## 10.1 事务：一次业务动作画一个边界

事务是一组语句的执行单元。`begin` 开始，`commit` 全部生效，`rollback` 全部撤销。中间任何一条失败，前面已经执行过的语句都不会留下。

调用方看到的原子性来自这个边界。接受邀请这件事有四步写操作：邀请改为已接受、成员表插一行、写一条活动日志、给邀请人发通知。如果只做了前两步，数据就处在「邀请用掉了，人却没进来」的状态。数据库不报错，页面上也看不出问题，直到用户找不到自己的团队。

事务的边界要画在业务动作上，不画在函数上，也不画在 HTTP 请求上。判断标准是：这组写操作如果只完成一半，业务上是否可解释。接受邀请不可解释，所以四步必须在一个事务里。写活动日志和更新通知的已读状态没有关系，各走各的事务。

第二类边界错误是把外部副作用放进事务。下面这段是错的。

```ts
// 反例：把发邮件放进事务
await withTransaction(async (client) => {
  await client.query(`update public.invitations set status = 'accepted' where id = $1`, [invId])
  await client.query(`insert into public.team_members (team_id, user_id, role) values ($1, $2, 'member')`, [teamId, userId])
  await resend.emails.send({ to: email, subject: '你已加入团队' })
})
```

事务可以回滚，已经发出去的邮件回滚不了。邮件发送成功、后面一句 SQL 失败，用户收到「已加入」但库里没有；发送失败、事务回滚，用户没收到邮件但数据也没变。两种结果都必须靠人工补救。

正确做法是把「要发什么」写进数据库，发送动作交给事务之外的 worker。这就是 outbox。

```sql
-- 事务内只写意图，不调外部服务
insert into public.jobs (kind, payload)
values ('email.send', '{"template":"invite-accepted","to":"bob@example.com"}'::jsonb);
```

`jobs` 表在第 8 章已经建好，`status` 从 `queued` 开始，worker 用 10.3 的 `for update skip locked` 取任务。任务写进数据库与业务数据在同一个事务里，要么都有，要么都没有。worker 发送失败会重试，`attempts` 记账，超过上限进 `dead`。第 34 章会给出完整的 worker 循环。

事务的第三个边界是长度。事务越长，持锁时间越长，冲突概率越高，vacuum 越难回收。规则是事务里只做「读、判断、写、提交」，不等待用户输入，不调慢接口，不跑大循环。

### 事务助手

手写 `begin` 与 `commit` 的问题是错误分支容易漏掉回滚。`pg` 的 `PoolClient` 在事务出错后不会自动回滚，忘记回滚就归还连接，下个请求拿到的是「已中止」的事务。

下面这段在前一章的 `src/lib/db.ts` 上追加。

```ts
// src/lib/db.ts（追加）
import type { PoolClient } from 'pg'

type TxOptions = {
  isolation?: 'read committed' | 'repeatable read' | 'serializable'
  retries?: number
}

export function isRetryable(error: unknown): boolean {
  const code = (error as { code?: string }).code
  // 40001 序列化失败，40P01 死锁。两者都可以整个事务重来。
  return code === '40001' || code === '40P01'
}

export async function withTransaction<T>(
  fn: (client: PoolClient) => Promise<T>,
  options: TxOptions = {},
): Promise<T> {
  const { isolation = 'read committed', retries = 2 } = options

  for (let attempt = 0; ; attempt += 1) {
    const client = await pool.connect()
    try {
      await client.query(`begin isolation level ${isolation}`)
      const result = await fn(client)
      await client.query('commit')
      return result
    } catch (error) {
      await client.query('rollback')
      if (attempt < retries && isRetryable(error)) {
        // 退避几十毫秒，避免两个事务立刻再次相撞
        await new Promise((resolve) => setTimeout(resolve, 20 * (attempt + 1)))
        continue
      }
      throw error
    } finally {
      client.release()
    }
  }
}
```

三个细节决定了它能不能用。`begin isolation level ${isolation}` 用模板串拼接，值只能来自上面的联合类型，不接受用户输入；直接把外部字符串拼进 SQL 是注入。`catch` 里先用同一个 client 回滚，再决定是否重试，回滚失败的连接必须销毁而不是归还。`finally` 里 `release` 放在最后，`commit` 与 `rollback` 都走完才归还。

`retries` 的默认值是 2，含义是最多执行三次。重试要求 `fn` 可重复执行，即纯数据库操作。`fn` 里如果累加内存计数器、发邮件、调支付，重试就会重复副作用。这也是 10.1 开头把外部调用挪出事务的原因。

### 接受邀请的完整事务

这段把四步写操作收进一个边界，并顺手处理了并发。

```ts
// src/lib/invitations.ts
import { query, withTransaction } from './db'

export type AcceptResult =
  | { ok: true; teamId: string; role: 'owner' | 'member' }
  | {
      ok: false
      reason: 'invalid_token' | 'expired' | 'already_accepted' | 'seat_limit' | 'team_deleted'
    }

export async function acceptInvitation(
  token: string,
  userId: string,
): Promise<AcceptResult> {
  return withTransaction(async (client) => {
    // 1. 锁住邀请行。两个人同时点同一个链接时，第二个在这里排队。
    const invited = await client.query<{
      id: string
      team_id: string
      email: string
      role: 'owner' | 'member'
      status: string
      expires_at: Date
      invited_by: string | null
    }>(
      `select id, team_id, email, role, status, expires_at, invited_by
         from public.invitations
        where token = $1
        for update`,
      [token],
    )
    if (invited.rowCount === 0) return { ok: false, reason: 'invalid_token' } as const

    const inv = invited.rows[0]
    if (inv.status === 'accepted') return { ok: false, reason: 'already_accepted' } as const
    if (inv.status !== 'pending' || inv.expires_at.getTime() < Date.now()) {
      return { ok: false, reason: 'expired' } as const
    }

    // 2. 锁住团队行，座位数检查与后面插入成员在同一把锁下完成。
    const team = await client.query<{ plan: string; deleted_at: Date | null }>(
      `select plan, deleted_at from public.teams where id = $1 for update`,
      [inv.team_id],
    )
    if (team.rowCount === 0 || team.rows[0].deleted_at !== null) {
      return { ok: false, reason: 'team_deleted' } as const
    }

    const seatLimit = team.rows[0].plan === 'free' ? 3 : team.rows[0].plan === 'pro' ? 10 : 50
    const members = await client.query<{ n: number }>(
      `select count(*)::int as n from public.team_members where team_id = $1`,
      [inv.team_id],
    )
    if (members.rows[0].n >= seatLimit) return { ok: false, reason: 'seat_limit' } as const

    // 3. 插成员。唯一约束兜住「同一人重复接受」的残余窗口。
    const inserted = await client.query(
      `insert into public.team_members (team_id, user_id, role)
       values ($1, $2, $3)
       on conflict (team_id, user_id) do nothing
       returning user_id`,
      [inv.team_id, userId, inv.role],
    )
    if (inserted.rowCount === 0) return { ok: false, reason: 'already_accepted' } as const

    // 4. 邀请置为已接受。
    await client.query(`update public.invitations set status = 'accepted' where id = $1`, [inv.id])

    // 5. 审计与通知。
    await client.query(
      `insert into public.activity_logs (team_id, actor_id, action, target_type, target_id)
       values ($1, $2, 'member.joined', 'user', $2)`,
      [inv.team_id, userId],
    )
    if (inv.invited_by) {
      await client.query(
        `insert into public.notifications (user_id, team_id, kind, title, body)
         values ($1, $2, 'invite.accepted', '邀请已接受', $3)`,
        [inv.invited_by, inv.team_id, `${inv.email} 加入了团队`],
      )
    }

    // 6. 邮件进 outbox，worker 负责真正发送。
    await client.query(
      `insert into public.jobs (kind, payload) values ('email.send', $1::jsonb)`,
      [JSON.stringify({ template: 'invite-accepted', to: inv.email, teamId: inv.team_id })],
    )

    return { ok: true, teamId: inv.team_id, role: inv.role } as const
  })
}
```

第 1 步的 `for update` 是关键。没有它，两个请求同时用同一个 token 进来，都读到 `pending`，都通过检查，都尝试插成员。唯一约束会挡住第二个插入，代价是第二个人看到数据库异常，看不到「这个邀请已经被用了」这样的业务提示。加了行锁，第二个请求在第一步就排队，拿到锁时状态已经是 `accepted`，走 `already_accepted` 分支。

第 2 步锁团队行，是因为座位数检查跨越了 `team_members` 的整张集合。只锁邀请行挡不住「两个不同邀请同时把人加进同一个团队」。这一点 10.2 讲写偏斜时会再提。

第 5 步的 `activity_logs` 有两个字段值得说明。`actor_id` 是接受邀请的人，不是邀请人，日志读起来才是「某人加入了团队」。`metadata` 在这条记录里没写，用默认值 `{}`，因为动作本身已经把信息表达完整了。

### 事务不覆盖的地方

`supabase-js` 没有多语句事务。它的 `rpc` 可以调用数据库函数，函数体本身是一个事务；也可以直接走 `pg` 的 `withTransaction`。两者不要混用：`supabase-js` 的请求与 `pg` 的连接是两个客户端，各自开的事务互相看不见，也锁不到对方刚写的行。

两个 HTTP 请求也不能拼成一个事务。第 1 个请求建团队、第 2 个请求加创建者为 `owner`，中间失败就留下一个没有成员的团队。这类流程要么合并成一个请求，要么引入状态字段，让「未完成」可识别、可清理。

### 部分回滚用 savepoint

事务里有一段可选的写操作，失败不该拖垮整笔业务，可以打一个 savepoint。

```sql
begin;
update public.invitations set status = 'accepted' where id = $1;
insert into public.team_members (team_id, user_id, role) values ($1, $2, 'member');

savepoint notify;
insert into public.notifications (user_id, team_id, kind, title, body)
values ($1, $2, 'invite.accepted', '邀请已接受', 'xxx 加入了团队');
-- 通知失败只回滚这一段，邀请与成员照常提交
rollback to savepoint notify;

commit;
```

`rollback to savepoint` 不结束事务，后面的语句照常执行。用它要克制：每个 savepoint 都要维护事务内的状态，还容易让人误以为「失败也无所谓」，掩盖掉本该处理的问题。常规做法仍是让整段失败、整体回滚，savepoint 只留给明确可以降级的功能。

## 10.2 隔离级别：四个异常和三个级别

隔离级别规定一个事务能看到其他事务的哪些改动。Postgres 支持三个级别，默认 `read committed`。

四个并发异常是理解级别的基础。

脏读指读到了别人还没提交的改动，对方随后回滚，你读到的东西从未存在过。Postgres 的三个级别都禁止脏读，这一条不用操心。

不可重复读指同一个事务里先后读同一行，结果不一样。`read committed` 允许：每条语句开始时取一次快照，所以两次 `select` 之间别人提交的改动可见。

幻读指同一个事务里按条件查询两次，第二次多出（或少掉）了符合条件的行。`read committed` 允许，因为新插入的行满足条件。

丢失更新指两个事务都读一行、各自修改、后写的覆盖先写的。三个级别都不阻止，它属于应用层要解决的问题，10.6 用版本号处理。

| 级别 | 同一行读两次 | 按条件查两次 | 写同一行 | 适用场景 |
| --- | --- | --- | --- | --- |
| read committed | 可能变化 | 可能多出或减少行 | 后写者等待，基于新值 | 默认，绝大多数请求 |
| repeatable read | 固定 | 固定（同一快照） | 后写者报错 40001 | 导出、对账、结算 |
| serializable | 固定 | 固定 | 检测危险模式并报错 | 跨多行的业务不变量 |

### 在 psql 里看差别

开两个终端，各跑 `psql "$DIRECT_URL"`。左边执行：

```sql
begin isolation level read committed;
select count(*) from public.team_members where team_id = 'aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa';
```

记住这个数字，假设是 2。右边另开一个事务插一行成员并提交。左边再查一次，数字变成 3。同一个事务里两个不同的结果，这就是不可重复读。

换成 `repeatable read` 重来，左边第二次查询仍然是 2。整个事务用同一个快照，别人的提交看不到。

`repeatable read` 有两个代价。第一，两个事务改同一行时后者直接失败，报 `could not serialize access due to concurrent update`，错误码 `40001`，必须整个事务重来。第二，快照太旧：一个跑了几分钟的事务看到的是开始那一刻的数据，对报表是优点，对「用户点保存」是缺点。

`serializable` 在快照之上加了危险模式检测，叫 SSI。它防的是写偏斜：两个事务读同一组数据、各自基于读到的结果写不同行，结果违反业务不变量。例如 free 团队上限 3 人，当前 2 人，两个接受邀请的请求同时读到 2，各自插入一行，最后 4 人。它们写的是不同的 `team_members` 行，`for update` 也锁不住对方插入的行，只有 `serializable` 能发现「两个事务基于同一个计数做了决策」。

### 在代码里选级别

大多数请求用默认级别，热点行用锁或唯一约束处理。同一事务里要多次读同一批数据且结果必须一致时，换成 `repeatable read`：

```ts
// src/lib/reports.ts
import { withTransaction } from './db'

export async function monthReport(teamId: string) {
  return withTransaction(
    async (client) => {
      const logs = await client.query(
        `select count(*)::int as n from public.activity_logs
          where team_id = $1 and created_at >= date_trunc('month', now())`,
        [teamId],
      )
      const members = await client.query(
        `select count(*)::int as n from public.team_members where team_id = $1`,
        [teamId],
      )
      return { logs: logs.rows[0].n, members: members.rows[0].n }
    },
    { isolation: 'repeatable read' },
  )
}
```

跨多行的不变量又找不到合适锁时，用 `serializable`，并接受它必须重试：

```ts
const result = await withTransaction(
  async (client) => {
    const seats = await client.query<{ seats: number }>(
      `select seats from public.subscriptions where team_id = $1`,
      [teamId],
    )
    const members = await client.query<{ n: number }>(
      `select count(*)::int as n from public.team_members where team_id = $1`,
      [teamId],
    )
    if (members.rows[0].n >= seats.rows[0].seats) {
      return { ok: false as const, reason: 'seat_limit' as const }
    }
    // 基于上面两个数字做判断并写入
    return { ok: true as const }
  },
  { isolation: 'serializable' },
)
```

`withTransaction` 带 `40001` 重试，`fn` 必须可重复执行。重试次数耗尽后错误抛给调用方，接口返回 503 或 409，由业务决定。

不要把全站改成 `serializable`。它把冲突检测交给数据库，代价是失败率：热点行上每多一个并发写，「杀掉一个重试」的概率就上升，接口 p99 变差，数据库 CPU 却没有下降。失败还是随机的，压测很难稳定复现。合适的使用场景是结算、配额分配这类「不变量横跨多行、又找不到一把锁」的业务。

## 10.3 行锁：把并发排成队

`read committed` 下最常用的并发控制手段是显式加锁。

`select ... for update` 锁住查到的行。其他事务想改这些行、或对它们 `for update`，都会阻塞，直到持锁事务提交或回滚。锁在你 `commit` 的那一刻释放。

锁有四种写法，区别在挡住谁。`for update` 最强，改和删都挡。`for no key update` 挡改，但不挡外键检查，改非唯一列时波及面更小。`for share` 允许别人读和加共享锁，不允许改。`for key share` 最弱，只挡删除和改键，几乎不用手写。

改 `teams.name` 用 `for no key update` 就够了，它是非唯一列，没有必要挡住别人往子表插引用这个团队的行。

两个修饰符改变等待行为。`nowait` 拿不到锁立刻报错，错误码 `55P03`，适合「用户点了按钮，不要让他干等」的场景。`skip locked` 跳过被锁的行，直接用下一行，适合队列。

等待也要设上限。持锁的人如果忘了提交，等的人会一直等：

```sql
set local lock_timeout = '2s';
```

超时报 `canceling statement due to lock timeout`，错误码 `55P03`。快速失败好过无限等待：一个卡住的请求会占住连接池的一条连接，连锁到整站 500。

### 队列的标准写法

worker 取任务用 `skip locked`。

```ts
// src/lib/jobs.ts
import { withTransaction } from './db'

type Job = { id: string; kind: string; payload: unknown; attempts: number }

export async function claimJob(): Promise<Job | null> {
  return withTransaction(
    async (client) => {
      const picked = await client.query<Job>(
        `select id, kind, payload, attempts
           from public.jobs
          where status = 'queued' and run_at <= now()
          order by run_at
          limit 1
          for update skip locked`,
      )
      if (picked.rowCount === 0) return null

      const job = picked.rows[0]
      await client.query(
        `update public.jobs
            set status = 'running', attempts = attempts + 1
          where id = $1`,
        [job.id],
      )
      return { ...job, attempts: job.attempts + 1 }
    },
    {},
  )
}
```

十个 worker 同时调用，`skip locked` 让各拿各的，不会排队等同一行。`for update` 保证「选中」与「标记 running」之间没有别人插队。取任务那条查询匹配第 8 章的 `jobs_pick_idx`，部分索引里只有 queued 任务，通常几十条，取一次几乎不花时间。

如果去掉那个索引，队列一长，这条查询就会退化成全表扫。它带着 `for update`，扫过的行都要加锁，其他 worker 全被挡住。这一点和「有索引的锁」完全是两种行为。

### 锁的范围由执行计划决定

这是行锁最容易被低估的地方。`for update` 锁的是执行计划实际命中的行。写在 `where` 里的条件只有配合索引，才能把锁的范围收窄。

```sql
-- 先看计划，确认是 Index Scan 再上锁
explain select id from public.teams where slug = $1 for update;
```

`teams` 只有两行时，全表扫和索引扫看不出差别。等它有两万行，一次「按 slug 锁团队」如果走了全表扫，就会锁住所有团队。`slug` 上有唯一索引是运气好，换成按 `name` 做模糊匹配再 `for update`，整张表都会被锁。

锁的持有时间等于事务时间。`for update` 之后不要调外部接口，不要让用户思考，不要 `await` 一个慢查询。事务里只保留「读、判断、写、提交」。

热点行也要当心。同一个团队每秒被更新上百次时，行锁让这些更新串行执行。单次 2 毫秒看不出来，排到 100 个就是 200 毫秒。计数类字段（浏览数、点赞数）不要放在会被并发更新的业务行上，单独一张表，或者异步累加。

`statement_timeout` 和 `lock_timeout` 要一起设。前者管语句自己跑太久，后者管等锁太久。第 9 章在连接参数里设了前者，锁超时属于事务层，进入事务后按需 `set local`。

## 10.4 死锁：两把锁的方向相反

两个事务各持一把锁，又都在等对方手里的锁，就形成死锁。数据库只能杀掉一个。

两个 `psql` 会话可以复现。左边：

```sql
begin;
update public.teams set name = name || ' A' where slug = 'acme';
```

右边：

```sql
begin;
update public.teams set name = name || ' B' where slug = 'globex';
```

现在交叉：左边改 globex，右边改 acme。两个窗口都卡住。大约一秒后，其中一个打印：

```
ERROR:  deadlock detected
DETAIL:  Process 12345 waits for ShareLock on transaction 67890; blocked by process 67890.
Process 67890 waits for ShareLock on transaction 12345; blocked by process 12345.
HINT:  See server log for query details.
```

错误码 `40P01`。被选中的事务已经回滚，另一个继续执行完。死锁就是这样「解开」的：数据库替你挑了牺牲者。

一秒钟不是巧合。`deadlock_timeout` 默认 1 秒，事务等待超过它，数据库才去检查等待图里有没有环。死锁不会立刻被发现，要等一会儿。

### 用统一顺序消除死锁

生产环境最常见的死锁来源是批量操作。一个请求按客户端传来的数组顺序更新 100 个团队，另一个请求用另一种顺序更新同一批，一交叉就死。

修法是统一加锁顺序，让环不可能出现。

```ts
// src/lib/teams-batch.ts
import { withTransaction } from './db'

export async function renameMany(teamIds: string[], suffix: string) {
  return withTransaction(async (client) => {
    // 先按 id 排序再锁。所有调用方拿锁顺序一致，环就不存在。
    const locked = await client.query<{ id: string }>(
      `select id from public.teams
        where id = any($1::uuid[]) and deleted_at is null
        order by id
        for update`,
      [teamIds],
    )

    for (const row of locked.rows) {
      await client.query(
        `update public.teams
            set name = name || $2, version = version + 1, updated_at = now()
          where id = $1`,
        [row.id, suffix],
      )
    }

    return locked.rowCount ?? 0
  })
}
```

`order by id` 是全部关键。所有调用方按同一顺序取锁，就不可能「你拿 1 等 2、我拿 2 等 1」。我锁 2 之前必须先拿到 1，而 1 在你手里，我只能排队。

还有三个辅助手段。缩短事务，批量操作拆成小批，每批一个事务，锁少、持锁短，交叉概率低。用 advisory lock 保护跨行的逻辑不变量，`select pg_advisory_xact_lock(hashtext('team_seats:' || $1))` 锁一个逻辑名字，事务结束自动释放。最后是捕获 `40P01` 重试，`withTransaction` 已经做了，但重试有上限，一直重试说明锁设计有问题。

### 排查线上死锁

先看谁在等锁。

```sql
select pid, locktype, relation::regclass as relation, mode, granted
from pg_locks
where not granted;
```

`granted = false` 的行就是正在等待的锁。再查这些连接卡在哪一句：

```sql
select a.pid, a.state, now() - a.xact_start as tx_age, left(a.query, 80) as query
from pg_stat_activity a
where a.state <> 'idle'
order by tx_age desc;
```

死锁的原始 SQL 在数据库日志里，`DETAIL` 只给进程号和事务号。想留下现场，打开 `log_lock_waits`，等待超过 `deadlock_timeout` 的锁会写进日志，配合 `log_min_duration_statement` 就能还原谁在等谁。

别把 `deadlock_timeout` 调到几十毫秒来「更快发现死锁」。每次等待都要建等待图，检查本身有成本，默认 1 秒是权衡过的。

`40001` 和 `40P01` 的重试策略不一样。`40001` 多半是正常竞争，退避几十毫秒重试两三次合理；`40P01` 往往说明结构有问题，重试只是止血。死锁必须在日志里打出来，否则重试会把它变成「偶发慢请求」，永远没人去修根因。

## 10.5 唯一冲突 23505 与幂等键

有一类并发错误不该被避免，该被利用：唯一约束。

两个管理员同时给同一个邮箱发邀请，第二个请求撞上第 8 章建的部分唯一索引。

```
ERROR:  duplicate key value violates unique constraint "invitations_pending_email_uniq"
```

错误码 `23505`。这是约束在正常工作。应用层「先查有没有、没有就插」永远有窗口：查和插之间，别人可能已经插了。唯一约束把窗口关在数据库里。

标准写法是直接插，让约束说话：

```sql
insert into public.team_members (team_id, user_id, role)
values ($1, $2, 'member')
on conflict (team_id, user_id) do nothing
returning user_id;
```

`rowCount === 0` 就表示已存在。不需要额外查询，也不用担心并发。

`on conflict` 的谓词必须与索引谓词一致。索引建在 `where status = 'pending'` 上，语句里也要写同一个条件，否则 Postgres 找不到可用的唯一索引，报：

```
ERROR:  there is no unique or exclusion constraint matching the ON CONFLICT specification
```

```ts
// src/lib/invitations.ts（追加）
import { query } from './db'

export type InviteResult =
  | { ok: true; invitationId: string }
  | { ok: false; reason: 'already_invited' }

export async function createInvitation(input: {
  teamId: string
  email: string
  role: 'owner' | 'member'
  invitedBy: string
}): Promise<InviteResult> {
  const token = crypto.randomUUID()

  try {
    const inserted = await query<{ id: string }>(
      `insert into public.invitations
         (team_id, email, role, token, status, expires_at, invited_by)
       values ($1, lower($2), $3, $4, 'pending', now() + interval '7 days', $5)
       on conflict (team_id, lower(email)) where status = 'pending' do nothing
       returning id`,
      [input.teamId, input.email, input.role, token, input.invitedBy],
    )

    if (inserted.rowCount === 0) return { ok: false, reason: 'already_invited' }
    return { ok: true, invitationId: inserted.rows[0].id }
  } catch (error) {
    // 极窄窗口：插入的瞬间另一条同邮箱邀请刚好提交。约束会以 23505 抛出来。
    if ((error as { code?: string }).code === '23505') {
      return { ok: false, reason: 'already_invited' }
    }
    throw error
  }
}
```

捕获 `23505` 后返回业务结果，不要让它变成 500。用户看到「已经有一封待处理的邀请」，比看到「服务器错误」有用得多。

### 幂等键：同一动作只生效一次

唯一约束管「数据长什么样」。另一种问题是「同一动作被执行两次」：支付回调重投、用户连点提交、客户端超时重试。两次执行本身都合法，只是不该产生两次效果。

幂等键管这件事。记录「这个 key 已经处理过」，重复请求直接返回第一次的结果。

两者经常被混在一起，分工其实清楚。唯一约束建在业务表的索引上，冲突时抛 `23505`，应用自己翻译成业务错误。幂等键单独一张表，冲突时返回旧结果，不报错。唯一约束的 key 由数据本身决定（同一团队同一邮箱），幂等键的 key 由事件源或客户端提供（`event.id`、订单号、表单里的 UUID）。

```sql
-- supabase/migrations/20261116110000_idempotency_keys.sql
-- 并发控制的辅助设施，不属于九张业务表。
create table public.idempotency_keys (
  key          text primary key,
  -- 请求体哈希：同一个 key 配不同内容时要拒绝，不能返回旧结果
  request_hash text not null,
  status       text not null default 'done' check (status in ('done')),
  response     jsonb,
  created_at   timestamptz not null default now()
);

-- 清理任务按时间删除，7 天以上的键不会再被重投
create index idempotency_keys_created_idx
  on public.idempotency_keys (created_at);
```

`runOnce` 把「写 key」和「写业务数据」放进同一个事务。中途崩溃时两者一起回滚，重试安全。

```ts
// src/lib/idempotency.ts
import type { PoolClient } from 'pg'
import { withTransaction } from './db'

export class IdempotencyConflictError extends Error {
  constructor(key: string) {
    super(`idempotency key reused with a different payload: ${key}`)
    this.name = 'IdempotencyConflictError'
  }
}

export async function runOnce<T>(
  key: string,
  requestHash: string,
  fn: (client: PoolClient) => Promise<T>,
): Promise<T> {
  return withTransaction(async (client) => {
    const claimed = await client.query(
      `insert into public.idempotency_keys (key, request_hash, status)
       values ($1, $2, 'done')
       on conflict (key) do nothing
       returning key`,
      [key, requestHash],
    )

    if (claimed.rowCount === 0) {
      const existing = await client.query<{ request_hash: string; response: T }>(
        `select request_hash, response from public.idempotency_keys where key = $1`,
        [key],
      )

      // 同 key 不同内容：客户端 bug 或重放，不能把旧结果当成新结果返回
      if (existing.rows[0].request_hash !== requestHash) {
        throw new IdempotencyConflictError(key)
      }

      return existing.rows[0].response
    }

    const result = await fn(client)

    await client.query(
      `update public.idempotency_keys set response = $2::jsonb where key = $1`,
      [key, JSON.stringify(result)],
    )

    return result
  })
}
```

支付回调是它的典型用法。

```ts
// src/app/api/webhooks/payment/route.ts
import { createHash } from 'node:crypto'
import { NextResponse } from 'next/server'
import { IdempotencyConflictError, runOnce } from '@/lib/idempotency'

export async function POST(request: Request) {
  // 哈希必须基于原始字节。先 JSON.parse 再 stringify，键顺序和空格会变。
  const raw = await request.text()
  const requestHash = createHash('sha256').update(raw).digest('hex')
  const event = JSON.parse(raw)
  // 真实项目在这里先验签，验签失败返回 400。签名细节见订阅章节。

  if (event.type === 'checkout.completed') {
    try {
      await runOnce(`payment:${event.id}`, requestHash, async (client) => {
        const updated = await client.query(
          `update public.subscriptions
              set status = 'active', stripe_subscription_id = $2
            where stripe_customer_id = $1
          returning team_id`,
          [event.data.customer, event.data.subscription],
        )

        if (updated.rowCount === 0) {
          // 找不到客户：测试事件或旧库未同步。记结果，别让网关一直重投。
          return { ok: false, reason: 'unknown_customer' }
        }
        return { ok: true }
      })
    } catch (error) {
      if (error instanceof IdempotencyConflictError) {
        return NextResponse.json({ error: 'idempotency_conflict' }, { status: 422 })
      }
      throw error
    }
  }

  return NextResponse.json({ received: true })
}
```

这里没有写 `activity_logs`。webhook 里没有登录用户，`actor_id` 填谁都不对，填 `null` 等于制造一条查不到人的记录。机器事件记进业务表就够了。

同事务的实现带来一个额外好处：并发同 key 天然排队。两个请求同时带 `payment:evt_123` 进来，第二个的 `insert ... on conflict do nothing` 会等第一个事务结束才能判断冲突（唯一性检查要等对方提交或回滚）。拿到 0 行后再读 `response`，此时第一个的结果已随事务提交，读到的是真实数据。

`request_hash` 防的是另一种情况：同一个 key 配了不同 body。客户端重试时把金额拼错，或者有人拿别人的 `event.id` 重放改过的请求。返回旧结果是错的，用户以为改成了 B，实际是 A，还没有报错。比对哈希后返回 422，问题立刻暴露。

key 要带业务前缀。订单号和事件 id 可能都是纯数字，前缀让它们互不干扰，翻日志也能看出属于哪条链路。`payment:${event.id}` 用事件源给的唯一 id，最可靠。站内接口常用「用户 + 动作 + 业务 id」，例如 `invite:${teamId}:${email}`。不要用 `Date.now()` 或随机数当幂等键，那等于每次都算新操作。

清理要保守。只删确认不会再重投的旧键，7 天是常见值，支付网关的重投窗口一般在 3 天内。本书的实现没有 processing 状态，靠事务隔离，事务未提交时键不存在，所以不存在误删正在处理的键。改成两阶段提交的话，清理条件要加 `and status = 'done' and created_at < now() - interval '1 hour'`。

```sql
delete from public.idempotency_keys where created_at < now() - interval '7 days';
```

幂等键有一个管不到的地方：它保证数据库里的这次动作只做一次，不保证外部世界的副作用只发生一次。`fn` 里如果真调了支付接口扣款，而请求超时、事务回滚，键没留下，重试会再扣一次。外部调用仍然要走 outbox，或者用支付方自己的幂等机制。不要把它当万能保险。

## 10.6 乐观锁：用版本号挡住覆盖写

两个管理员同时打开团队设置页，都读到名字「Acme」。A 改成「Acme 设计」，B 改成「Acme Studio」，各自保存，后保存的覆盖先保存的。两个请求都返回成功，谁也不知道自己覆盖了别人。

这是丢失更新。事务帮不上忙，两个事务各自都成功，没有一个失败。`for update` 也帮不上忙，它要求从读到写都持锁，而用户读完要想三分钟，不能让一个 HTTP 请求持锁三分钟。

解法是在数据里加版本号。第 8 章的 `teams.version` 就是为这个准备的。

规则三条。读的时候把版本号带到前端；写的时候带回来，`update ... where version = $带回来的版本`；受影响行数为 0 就说明这期间别人改过，返回冲突。

```ts
// src/lib/teams.ts（追加）
import { query } from './db'

export type RenameResult =
  | { ok: true; version: number }
  | { ok: false; reason: 'conflict'; current: { name: string; version: number } }
  | { ok: false; reason: 'not_found' }

export async function renameTeam(input: {
  teamId: string
  name: string
  expectedVersion: number
}): Promise<RenameResult> {
  const updated = await query<{ version: number }>(
    `update public.teams
        set name = $2,
            version = version + 1,
            updated_at = now()
      where id = $1
        and version = $3
        and deleted_at is null
      returning version`,
    [input.teamId, input.name, input.expectedVersion],
  )

  if (updated.rowCount === 1) {
    return { ok: true, version: updated.rows[0].version }
  }

  // 0 行有两种可能：版本不对，或者这行已被删除。要分开告诉用户。
  const current = await query<{ name: string; version: number }>(
    `select name, version from public.teams where id = $1 and deleted_at is null`,
    [input.teamId],
  )
  if (current.rowCount === 0) return { ok: false, reason: 'not_found' }

  return { ok: false, reason: 'conflict', current: current.rows[0] }
}
```

`update ... returning` 一条语句完成检查、写入、返回新版本。不要写成「先 `select` 版本，再 `update`」，中间又有窗口。

Server Action 把冲突翻译成 409。

```ts
// src/app/(app)/teams/[slug]/settings/actions.ts
'use server'

import { revalidateTag } from 'next/cache'
import { requireUser } from '@/lib/auth'
import { getActiveTeam, requireMembership, renameTeam } from '@/lib/teams'

export async function renameTeamAction(formData: FormData) {
  const user = await requireUser()
  const team = await getActiveTeam()
  if (!team) return { ok: false, reason: 'not_found' as const }

  await requireMembership(team.id, user.id)

  const name = String(formData.get('name') ?? '').trim()
  if (name.length === 0 || name.length > 60) {
    return { ok: false, reason: 'invalid_name' as const }
  }

  const expectedVersion = Number(formData.get('version'))

  const result = await renameTeam({ teamId: team.id, name, expectedVersion })
  if (!result.ok) return result

  // 团队名在导航栏、页面标题、活动流里都出现，按团队 tag 统一失效
  revalidateTag(`team:${team.id}`, 'max')
  return { ok: true as const, version: result.version }
}
```

前端拿到 `conflict` 不要自动重试，也不要自动合并。告诉用户「别人刚改过，这是最新名字」，让他决定。自动重试的乐观锁等于没有锁，只是把冲突藏起来。

冲突之后有三条产品路。第一条是提示并保留输入，本书采用：返回 409 和最新值，弹出「这个团队刚被改名为 Globex，要保留你的名字吗」，两个按钮分别用新版本号重提、或刷新表单。输入不会悄悄丢，代价是多一个对话框。第二条是强制刷新、丢弃输入，实现最省事，适合冲突极少、重填成本低的字段。第三条是服务端自动合并，只有两人改的是不同字段才有意义，需要字段级版本号或者只更新本次提交的列，协作文档类产品才值得。

409 比 400 准确。`409 Conflict` 的字面意思就是「和服务器当前状态冲突」。前端按 `reason` 分流，不要把所有的非 ok 都弹成「请稍后重试」。

版本号必须随表单提交，例如 `<input type="hidden" name="version" value={team.version} />`。只存在 React state 里不行，JS 没加载时提交拿不到版本，服务端会当成缺失直接判冲突。凡是服务端要校验的状态，都要能随表单一起发出去。

### 乐观锁与悲观锁

冲突少、用户思考时间长，用版本号。冲突多、操作瞬间完成，用 `for update`。前者不持锁，能跨请求，冲突时返回 409；后者排队等待，持锁到事务结束，不能跨请求。

团队设置页是前者，抢任务队列是后者。

`version` 还有一个附带用途：它是这行被改过几次的计数。改名十次，version 就是 11，排查问题时能对上时间线。

为什么不用 `updated_at` 当版本号？它是 `timestamptz`，库里精确到微秒，但经过 JSON 序列化到前端再带回来通常只剩毫秒。两次更新落在同一毫秒，版本就分不出来。更麻烦的是这种「相等」偶尔发生，测试环境永远碰不到。整数版本号没有精度问题。

## 10.7 并发下的分页

翻页和事务同源，都是「同一批数据在两次读取之间变了」。

`offset 20 limit 20` 的前提是「前 20 条一直是那 20 条」。活动流每秒都在插入，用户读完第一页、点「下一页」的十几秒里，顶部进来 5 条新记录。第二页跳过的仍是最新 20 条，其中 5 条是新的，第一页看过的 5 条在第二页又出现。删除同理，前 20 条里删掉 3 条，第二页会跳过 3 条从没看过的记录，它们永远不出现。

表现是「第 3 页永远有几条重复，而且每次不一样」。它不报错，测试也难写，因为要求恰好在这几秒内有写入。

游标分页换一个锚点：不按「第几条」翻，按「上一页最后一条的排序键」翻。

```sql
-- 第一页
select id, action, created_at
from public.activity_logs
where team_id = $1
order by created_at desc, id desc
limit 20;

-- 下一页：带上第一页最后一行的 (created_at, id)
select id, action, created_at
from public.activity_logs
where team_id = $1
  and (created_at, id) < ($2::timestamptz, $3::uuid)
order by created_at desc, id desc
limit 20;
```

`(created_at, id) < (...)` 是行比较，Postgres 翻译成「时间更早，或时间相同但 id 更小」。这正好匹配第 8 章的复合索引 `(team_id, created_at desc, id desc)`，走索引区间扫描，取 20 条就停。

不重不漏的原因：「上一页最后一行」是一个具体锚点，不管中间插多少新记录，`< 锚点` 的集合只会变多，锚点本身不会移动。新记录时间更新，永远在锚点之后，挤不进下一页。

前提是排序键不可变。`(created_at, id)` 安全，创建时间不会变，id 不会变。按 `name` 排序，用户改个名字，那条记录就从第 3 页跳到第 1 页，锚点之后的全部错位，翻页会重复也会漏，而且是那种偶发、复现不了的 bug。

这里的「游标」是一个值，由 `created_at` 与 `id` 组成，不是数据库里的 `declare cursor`。它不占连接，不阻止 vacuum。真正拖住 vacuum 的是长事务，哪怕只读：`idle in transaction` 会让清理进程无法回收死元组，表只涨不缩。开一个事务慢慢翻页是坏主意。

代价是只能往后翻，不能跳到第 7 页。活动流、消息列表、搜索结果都是「继续加载」，产品上够用。真要跳页只能用 OFFSET，接受漂移，或者把跳页做成快照式的导出。

游标要进 URL，不能把时间戳和 UUID 原样拼进去。先把两个值序列化成 JSON，再做 base64url 编码；服务端解码时校验类型与格式，非法的游标一律当成第一页。游标内容不必加密，它只决定「从哪一行之后开始」，团队范围仍由服务端的 `team_id` 决定，改游标翻不出别的团队。完整的编码函数和翻页组件在第 13 章。

OFFSET 的成本随页码线性增长。`offset 16000` 要求数据库先读出 16020 行，再丢掉前 16000 行。页码越深越慢，而且慢得没有上限。第 13 章会给完整的实测对比，这里只需要记住它的复杂度不同。

还有一个隔离级别相关的细节。一个列表页往往查三次：列表、总数、当前用户权限。三次查询在 `read committed` 下是三个不同快照，极端情况下第一页显示 19 条、总数显示 20、权限显示「你已被移除」。这类矛盾不损坏数据，但会让用户截图发到群里。要页面自洽，用 `repeatable read` 把三次查询包进一个事务，几十毫秒的持锁可以接受。别在用户浏览的整个生命周期里开着事务。

## 10.8 检查点

1. 中途失败，两张表都没有新行

```js
// scripts/tx-check.mjs
import { Pool } from 'pg'

const pool = new Pool({ connectionString: process.env.DIRECT_URL, max: 2 })
const teamId = 'aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa'
const invId = 'cccccccc-cccc-4ccc-8ccc-cccccccccccc'
const bobId = '22222222-2222-4222-8222-222222222222'

const before = await pool.query(`select status from public.invitations where id = $1`, [invId])

const client = await pool.connect()
try {
  await client.query('begin')
  await client.query(`update public.invitations set status = 'accepted' where id = $1`, [invId])
  // bob 已经是成员，这一行会撞主键，报 23505
  await client.query(
    `insert into public.team_members (team_id, user_id, role) values ($1, $2, 'member')`,
    [teamId, bobId],
  )
  await client.query('commit')
  console.log('不应执行到这里')
} catch (error) {
  await client.query('rollback')
  console.log('第 2 步失败，已回滚:', error.code)
} finally {
  client.release()
}

const after = await pool.query(`select status from public.invitations where id = $1`, [invId])
const members = await pool.query(
  `select count(*)::int as n from public.team_members where team_id = $1`,
  [teamId],
)

console.log('邀请状态 前/后:', before.rows[0].status, after.rows[0].status)
console.log('成员数:', members.rows[0].n)
await pool.end()
```

```bash
node --env-file=.env.local scripts/tx-check.mjs
```

输出应为 `第 2 步失败，已回滚: 23505`，邀请状态前后都是 `pending`，成员数仍是 3。状态变成 `accepted` 说明没有用事务，或者在 `rollback` 之前就 `release` 了连接。

2. 并发改名，一方拿到冲突

```js
// scripts/rename-race.mjs
import { Pool } from 'pg'

const pool = new Pool({ connectionString: process.env.DIRECT_URL, max: 4 })
const teamId = 'aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa'

const current = await pool.query(`select version from public.teams where id = $1`, [teamId])
const expectedVersion = current.rows[0].version

const rename = (name) =>
  pool.query(
    `update public.teams
        set name = $1, version = version + 1, updated_at = now()
      where id = $2 and version = $3 and deleted_at is null
      returning version`,
    [name, teamId, expectedVersion],
  )

const [a, b] = await Promise.all([rename('Acme A'), rename('Acme B')])
console.log('第一个结果 rowCount:', a.rowCount)
console.log('第二个结果 rowCount:', b.rowCount)

await pool.query(
  `update public.teams set name = 'Acme', version = version + 1 where id = $1`,
  [teamId],
)
await pool.end()
```

```bash
node --env-file=.env.local scripts/rename-race.mjs
```

输出应为一个 `1`、一个 `0`。两个都是 `1` 说明漏了 `and version = $3`；两个都是 `0` 说明版本号传错。

**3. 演示一次死锁并解开**

两个终端各跑 `psql "$DIRECT_URL"`，按顺序执行：

```sql
-- 会话 A
begin;
update public.teams set name = name where slug = 'acme';

-- 会话 B
begin;
update public.teams set name = name where slug = 'globex';

-- 会话 A（阻塞）
update public.teams set name = name where slug = 'globex';

-- 会话 B（约 1 秒后报错）
update public.teams set name = name where slug = 'acme';
```

会话 B 收到 `ERROR: deadlock detected`（`40P01`），事务已回滚。A 执行 `commit;` 后两边都能继续。确认锁已清空：

```sql
select count(*) from pg_stat_activity where wait_event_type = 'Lock';
```

结果应为 0。

**4. 隔离级别的可见性差别**

按 10.2 的两会话步骤，先跑 `read committed` 再看 `repeatable read`，两次计数应分别为 2 变成 3、以及两次都是 2。

**5. 唯一约束挡住重复邀请**

连续两次调用 `createInvitation` 同一个团队、同一个邮箱，第一次返回 `ok: true`，第二次返回 `already_invited`，`invitations` 表里只有一条 `pending` 记录。

**6. 用一句话回答**

`repeatable read` 与 `serializable` 差了什么，为什么后者必须配重试。为什么发邮件不能进事务、写 `jobs` 表可以。乐观锁为什么不能用 `updated_at` 当版本号。

## 10.9 常见错误

`current transaction is aborted, commands ignored until end of transaction block`

错误码 `25P02`。事务里某条语句失败后，没有回滚就继续发下一条。Postgres 的事务一旦出错就进入中止状态，之后所有语句都被拒绝，直到 `rollback`。用 `withTransaction` 不会遇到，它在 catch 里先回滚。手写事务时每个 catch 分支都要回滚。

`could not serialize access due to concurrent update`

错误码 `40001`。`repeatable read` 或 `serializable` 下两个事务改了同一行。这是正常现象，把整个事务重试即可，不能只重试失败的那一条语句。绕过 `withTransaction` 自己写事务时，要补上同样的重试逻辑，并保证事务内操作可重复执行。

`deadlock detected`

错误码 `40P01`。两个事务交叉等待。短期重试，长期统一加锁顺序（批量操作先 `order by id for update`）、缩短事务、拆批。看到它不要只加 `retries`，要找出是哪两个事务在交叉，否则重试只是把问题变成偶发慢请求。

`duplicate key value violates unique constraint "invitations_pending_email_uniq"`

`23505`。两个请求同时邀请同一个邮箱，或用户连点两次发送。约束在工作。用 `on conflict do nothing` 判断 `rowCount`，或者捕获 `23505` 返回「已有待处理邀请」，别让它变成 500。

`canceling statement due to lock timeout`

`55P03`，自己设了 `lock_timeout`。有另一个事务持锁超过耐心上限。先查是谁：

```sql
select pid, now() - xact_start as age, left(query, 80)
from pg_stat_activity
where state = 'active' and now() - xact_start > interval '5 seconds';
```

找到长事务，看它是慢查询还是忘了提交。不要靠调大 `lock_timeout` 来处理它。

翻页时同一行出现两次，或有行永远不出现

`offset` 分页遇上并发插入或删除。换游标分页，用 `(created_at, id)` 做锚点，并确保排序键与索引一致，第 8 章的 `id desc` 就是这个用途。排序键只有 `created_at` 时，同一微秒的多行没有确定顺序，游标照样会重漏。`id` 作为第二列承担了 tie-breaker 的职责。

## 10.10 这一章在做什么

这一章把「代码没报错」和「结果正确」分开了。事务管原子性：一次用户动作要么全落，要么全不落。隔离级别和锁管可见性：事务里看到的世界有多新。唯一约束、幂等键、版本号管并发：两件事同时发生时谁说了算。

回顾四个决定。事务边界画在业务动作上，外部副作用走 outbox。默认 `read committed`，需要一致快照时升到 `repeatable read`，跨行不变量用 `serializable` 并配重试。行锁的范围由执行计划决定，批量加锁先排序。冲突用约束和版本号表达，再翻译成 409 或业务提示。

如果只记一件事：并发 bug 不报错。它只是让数据看起来正常，直到有人对账，或者两个管理员互相对照聊天记录。

现在的写入路径是安全的：有事务、有重试、有冲突返回。下一步是这些数据在界面上怎么显示，时区、金额、格式化。看起来是小事，但「账单差 0.01」和「用户看到昨天的时间」是最容易被投诉的两类问题。
