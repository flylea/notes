# 第 7 章 环境变量与密钥

这一章讲配置怎么进到代码里，以及怎么保证密钥不进浏览器。涉及四件事：环境变量文件的加载顺序、`NEXT_PUBLIC_` 的构建期替换、服务端边界、启动时校验。

需要专门讲，是因为这一块出错的代价很高。密钥写错前缀，会被打进浏览器包；变量名拼错，线上启动时才发现；多环境管理混乱，一次构建的产物连错了数据库。

涉及的概念有五个：加载顺序、构建期替换、运行时读取、服务端边界、启动校验。前两个决定变量值，后两个决定谁能看到，最后一个决定错误什么时候暴露。

## 7.1 变量的三种来源

环境变量的值有三个来源，优先级从高到低：进程环境、`.env` 系列文件、代码里的默认值。

进程环境由启动命令、容器平台或 CI 注入。它优先级最高，适合放部署环境相关的值，比如数据库地址与第三方密钥。

`.env` 系列文件放在项目根目录，按环境区分。它适合放本地开发用的值，也适合放不敏感的公共配置。

代码里的默认值只用于开发兜底。缺少默认值时直接抛错，比静默使用空字符串安全。

```ts
// src/lib/env.ts
export function required(name: string): string {
  const value = process.env[name];
  if (value === undefined || value === "") {
    throw new Error(`缺少环境变量 ${name}`);
  }
  return value;
}
```

变量分两类，处理方式完全不同。一类只在服务端使用，比如 `SUPABASE_SERVICE_ROLE_KEY`；一类需要进入浏览器，比如站点地址。前者永远不带前缀，后者必须带 `NEXT_PUBLIC_`。

前缀决定了编译器怎么处理变量。带前缀的变量在构建时被替换成字面量，不带前缀的变量只在服务端存在。

变量名统一大写、单词之间用下划线。名字里带上归属，比如 `SUPABASE_SERVICE_ROLE_KEY`、`STRIPE_SECRET_KEY`，一眼能看出属于哪个服务。

配置集中读取还有一层好处：排查时只有一个地方要找。变量散落在二十个文件里，改一个名字要全仓库搜索，漏掉一处就是运行期错误。

公开变量的读取也要集中。同一个站点地址在五个组件里各写一遍 `process.env.NEXT_PUBLIC_SITE_URL`，换域名时要改五处。抽成 `publicEnv` 对象，引用点只改一处。

## 7.2 加载顺序

Next.js 按固定顺序读取 `.env` 文件，找到第一个有该变量的文件就停止。

顺序从高到低：

1. `process.env` 中已有的值
2. `.env.$(NODE_ENV).local`
3. `.env.local`
4. `.env.$(NODE_ENV)`
5. `.env`

`NODE_ENV` 由命令决定。`next dev` 是 `development`，`next build` 与 `next start` 是 `production`，测试运行时是 `test`。

`NODE_ENV` 为 `test` 时不读取 `.env.local`。这条规则容易踩：单元测试里读不到本地开发的变量，需要在 `.env.test` 里另写一份。

文件只在项目根目录加载。仓库用了 `src/` 目录时，`.env.local` 仍然放在根目录，放在 `src/` 里不会生效。

值支持多行，RSA 私钥可以直接粘贴进去。值里出现 `$VAR` 会被展开成另一个变量的值；需要字面量的美元符号时写 `\$`。

`.env.local` 与 `.env.*.local` 要进 `.gitignore`，其余文件可以提交。团队协作时提交一份 `.env.example`，只写变量名与说明，不写值。

```text
# .env.example
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
NEXT_PUBLIC_SITE_URL=http://localhost:3000
NEXT_SERVER_ACTIONS_ENCRYPTION_KEY=
```

`.env.example` 的作用是让人知道需要哪些变量。新成员克隆仓库后，复制成 `.env.local` 再填值，不用去翻代码找变量名。

变量缺失的表现分散在运行期。请求进来才发现某个值是 `undefined`，日志里只有一行 `TypeError`。把变量集中读取并做校验，缺失会在启动时暴露。

排查加载顺序时，把前缀打印出来最快。在服务端组件里执行一次 `Object.keys(process.env).filter((k) => k.startsWith("NEXT_PUBLIC_"))`，能看出当前进程到底读到了哪些变量。

覆盖规则的实际表现：`.env` 里写了默认地址，`.env.local` 里写了本地地址，开发时读到本地地址。想临时验证生产值，改 `.env.local` 比重命名文件省事。

`.env.production` 要谨慎提交。它会在所有生产构建里生效，包括别人的机器与 CI。生产值更适合由平台注入，文件里只留示例。

## 7.3 服务端变量与边界

服务端变量放在没有前缀的变量里，读取时经过一个集中模块。

```ts
// src/lib/env.ts
import "server-only";

function required(name: string): string {
  const value = process.env[name];
  if (value === undefined || value === "") {
    throw new Error(`缺少环境变量 ${name}`);
  }
  return value;
}

export const serverEnv = {
  supabaseUrl: required("NEXT_PUBLIC_SUPABASE_URL"),
  serviceRoleKey: required("SUPABASE_SERVICE_ROLE_KEY"),
  siteUrl: required("NEXT_PUBLIC_SITE_URL"),
};
```

`import "server-only"` 保证这个模块不会被打进浏览器包。任何客户端组件直接 import 它，构建会失败并指出导入链。

```tsx
// 错误示范：客户端组件里读服务端变量
"use client";

import { serverEnv } from "@/lib/env";

export function DebugPanel() {
  return <pre>{serverEnv.serviceRoleKey}</pre>;
}
```

上面这段的构建报错指向 import 那一行：

```text
Error: 'server-only' cannot be imported from a Client Component module
It should only be used from a Server Component.
```

读取服务端变量有两种时机。模块加载时读，值在进程启动后固定，适合大多数配置。请求处理时读，每次请求都重新取值，适合需要按请求变化的场景。

运行时读取也有一个前提：页面处于动态渲染。页面被静态化时，渲染发生在构建期，读到的值是构建时的环境变量。需要按请求读变量的页面，要通过 `cookies()`、`headers()` 或 `await connection()` 让渲染变成按请求执行。

```ts
// src/lib/supabase/server.ts
import "server-only";
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";
import { serverEnv } from "@/lib/env";

export async function createClient() {
  const cookieStore = await cookies();

  return createServerClient(serverEnv.supabaseUrl, serverEnv.serviceRoleKey, {
    cookies: {
      getAll() {
        return cookieStore.getAll();
      },
      setAll(cookiesToSet) {
        for (const { name, value, options } of cookiesToSet) {
          cookieStore.set(name, value, options);
        }
      },
    },
  });
}
```

服务端的 Supabase 客户端用 `service_role` 密钥时绕过行级安全，写错会越权读取。多数页面应该用当前用户的会话与 RLS，只有后台任务与迁移脚本才用高权限客户端。

服务端边界有三道闸。第一道是模块图：客户端组件 import 的一切都会进浏览器包，`server-only` 让误用直接构建失败。第二道是变量前缀：没有 `NEXT_PUBLIC_` 的变量在客户端被替换成空字符串。第三道是产物检查：构建后搜索一遍，用结果确认前两道都生效。

需要把服务端数据传给客户端时，走 props。在服务端组件里读好变量、算好结果，作为普通数据传给客户端组件。客户端组件只负责显示与交互，不碰配置。

浏览器端的客户端只用公开的键：

```ts
// src/lib/supabase/client.ts
import { createBrowserClient } from "@supabase/ssr";

export function createClient() {
  return createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
  );
}
```

`anon` 密钥会进入浏览器包，这是设计如此。它的权限由 RLS 决定，暴露它不构成越权。

把公开键传给客户端组件时不要经过服务端模块。客户端组件直接读 `process.env.NEXT_PUBLIC_XXX`，或者在模块顶层读一次存成常量，都是允许的写法。

反过来，客户端组件不要 import 任何以 `serverEnv` 命名的模块。这类模块的导出会被整体带进浏览器包，构建失败还是轻的，替换成空字符串后界面异常更难查。

`service_role` 密钥会绕过 RLS，任何进入浏览器包的情况都是事故。

## 7.4 NEXT_PUBLIC 的替换规则

带 `NEXT_PUBLIC_` 前缀的变量在构建时被替换成完整字面量。构建产物里的代码是硬编码的值，不再读取环境变量。

```tsx
// src/app/(marketing)/pricing/page.tsx
const siteUrl = process.env.NEXT_PUBLIC_SITE_URL;

export default function PricingPage() {
  return <a href={`${siteUrl}/contact`}>联系我们</a>;
}
```

构建后，`siteUrl` 的位置是字符串字面量。改动 `.env` 文件不会影响已经构建的产物，重新部署必须重新构建。

这条规则带来两个后果。同一份镜像无法通过改环境变量切换环境；容器里改环境变量，前端代码读到的仍是构建时的值。

排查时先确认有没有重新构建。改了 `.env` 只重启进程，公开变量不会更新，因为旧值已经写进 JS 文件。看到“配置改了没生效”，第一步是看构建时间。

服务端与客户端读同一个公开变量，结果一致。两边都被替换成同一份字面量，不会出现服务端读新值、浏览器读旧值的情况。这种一致性由构建保证，不需要额外处理。

调试时注意替换发生在编译阶段。在源码里写 `console.log(process.env.NEXT_PUBLIC_SITE_URL)` 看不到变量名，浏览器里执行的是打印字面量。想确认真实值，直接看构建产物里的字符串。

动态访问不会被替换。下面两种写法在浏览器里拿到 `undefined`：

```ts
const key = "NEXT_PUBLIC_SITE_URL";
const value = process.env[key];

const env = process.env;
const value2 = env.NEXT_PUBLIC_SITE_URL;
```

编译器只处理 `process.env.NEXT_PUBLIC_XXX` 这种静态写法。需要按名字动态取值时，在服务端读好后传下去。

`next.config.ts` 的 `env` 字段也在构建时进包，效果与 `NEXT_PUBLIC_` 相同。密钥不能写进这个字段。

验证泄露有一个直接办法：在构建产物里搜索密钥片段。

```bash
grep -rIl "service_role" .next/static || echo "未命中"
```

```text
未命中
```

下面这段输出未验证：本机的安全策略拦截了包含密钥形态值的环境文件，命令没有实际执行，结果按文档中的替换规则推断。检查自己的项目时直接执行，命中就说明密钥进了浏览器包。

搜索的范围包括 `.next/static` 与 `.next/server`。前者是浏览器拿到的资源，后者是服务端产物。只有服务端产物里出现密钥，说明边界还在。

## 7.5 启动时校验

变量在用到时才检查，错误会晚到。更早的检查点是进程启动时。

`instrumentation.ts` 里的 `register()` 在服务器实例启动时执行一次，必须执行完成，服务器才开始处理请求。

```ts
// src/instrumentation.ts
export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    const { serverEnv } = await import("@/lib/env");
    console.log("环境变量校验通过", Object.keys(serverEnv));
  }
}
```

`NEXT_RUNTIME` 判断用来避免在 Edge 环境里加载 Node 专用模块。导入语句放在条件内部，未命中时不加载。

校验失败时进程直接退出，比带着空配置启动更好。带着空配置启动，错误会分散在每个请求里，排查成本高。

校验的内容包括必填变量是否存在、地址格式是否合法、密钥长度是否合理。

```ts
// src/lib/env.ts
function assertUrl(name: string, value: string) {
  try {
    new URL(value);
  } catch {
    throw new Error(`环境变量 ${name} 的地址格式不正确：${value}`);
  }
  return value;
}

export const serverEnv = {
  supabaseUrl: assertUrl("NEXT_PUBLIC_SUPABASE_URL", required("NEXT_PUBLIC_SUPABASE_URL")),
  serviceRoleKey: required("SUPABASE_SERVICE_ROLE_KEY"),
};
```

校验通过也不代表连得上。校验只检查格式，连通性要另外测：启动后请求一个健康检查接口，或者执行一次轻量查询。

三层校验可以这样分：构建期检查变量名，启动时检查必填与格式，首次请求时验证连通性。越靠前发现，修复成本越低。

校验失败的表现要区分两种。启动时校验失败，进程退出，部署平台标记为启动失败；请求时才发现，用户看到 500，日志里才有线索。前者在发布阶段挡住问题，后者把问题留给线上。

健康检查接口可以顺带验证连通性：查一条不需要权限的计数，返回状态码与耗时。部署流水线在切换流量前请求一次，失败就回滚。

部署平台通常只判断端口能否连接。端口通了、依赖没配好，流量照样打到坏实例上。健康检查要把关键依赖串进去，数据库、缓存、第三方鉴权各查一次，任何一项失败返回 503。

需要结构化校验时可以引入 zod。变量数量超过十个之后，手写检查会变得冗长，schema 更容易维护。

## 7.6 多环境

本地、CI、预发、生产各有一套变量值。区别在于值从哪里来。

本地开发用 `.env.local`，不提交。值通常是本地 Supabase 的地址与密钥。

CI 用平台的密钥管理注入环境变量。构建时只注入构建需要的值，运行时才注入密钥。

Vercel 在项目设置里配置环境变量，按 Production、Preview、Development 分环境。改动后要重新部署才生效。

Preview 环境建议接一套独立的数据库与第三方测试密钥。预览分支共享生产数据库时，一次误操作就会影响真实用户。

自托管用容器编排的环境变量或密钥文件。同一份镜像连不同环境时，构建期变量要一致，运行时变量才能切换。

```text
# 自托管：运行时注入
docker run --env-file /etc/teamstack/production.env teamstack:20260101
```

`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 有一个额外要求：多实例部署时必须一致。这个密钥用于加密 Server Action 的闭包变量，每个实例用不同的密钥，请求落到另一个实例时解密失败。

```bash
openssl rand -base64 32
```

生成一次，写进所有实例的环境变量。滚动部署期间新旧实例并存，密钥不一致时旧页面提交表单会报错：

```text
Failed to find Server Action
```

轮换密钥要按顺序来：先生成新密钥，写进环境变量但不部署；再滚动部署，让所有实例用同一把密钥；最后确认没有旧实例在线。中途新旧密钥并存，会有一段时间请求失败。

环境变量与镜像的对应关系要写进部署文档。哪个镜像对应哪一套变量，回滚时用哪一套，这些信息在事故里比代码更重要。

按环境维护一份变量清单，列出变量名、用途、是否公开、由谁注入。清单每加一个变量就更新一行，久了就是一份配置说明。

密钥轮换要做演练。在预发环境把 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 换一遍，走完整流程，记下耗时与失败点。真出事时按演练步骤执行，比现场摸索快。

## 7.7 密钥泄露的处理

泄露的迹象有几种：构建产物里搜到密钥、浏览器 Network 里看到密钥、第三方平台告警。

处理顺序固定：先轮换，再改代码，最后重新构建。

轮换放在最前面，因为旧密钥在代码里多留一分钟，泄露窗口就多一分钟。改代码可能花几小时，期间旧密钥已经作废，攻击者拿到的值无效。

```bash
grep -rIl "sb_secret" .next/static
```

```text
.next/static/chunks/app/page-1a2b3c.js
```

命中说明密钥进了浏览器包。找到来源通常是三种：变量名加了 `NEXT_PUBLIC_` 前缀、服务端模块被客户端组件 import、密钥写进了 `next.config.ts` 的 `env` 字段。

改完之后重新构建，再执行一次同样的搜索。确认没有命中才算处理完。

浏览器端只用公开键的场景下，泄露的代价有限。`anon` 密钥配合 RLS，能做的事与普通用户一致。真正危险的是 `service_role` 密钥，它绕过所有行级策略。

给密钥加上来源标记。Supabase 后台生成密钥时可以备注用途，日志里出现异常调用时能快速定位是哪一套环境。

轮换之后要检查用量的异常变化。旧密钥被调用的记录会留在平台日志里，调用来源与频率能帮助判断泄露范围。

把泄露事件记进事故记录：怎么发现的、影响了哪些环境、轮换用了多久、哪一步最慢。下一次同类事件按记录执行，处理时间会明显缩短。

## 7.8 边界与失败模式

**变量名拼错。** 拼成 `NEXT_PUBLIC_SUPABASE_URL` 少一个字母，读到 `undefined`，报错出现在第一次请求。用集中模块读取，启动时校验，能把错误提前。

构建期与运行期混淆。 在 `next build` 时设了变量，以为运行容器时能改。构建期变量已经写死在产物里，容器里的同名变量不影响它。

服务端变量被客户端组件间接读到。 客户端组件 import 了工具函数，工具函数里读了服务端变量，整条链进浏览器包。变量被替换成空字符串，界面显示异常，日志里才有线索。

`.env.local` 提交到了仓库。 本地配置包含密钥，推送到远端后需要按泄露处理。仓库的 `.gitignore` 里保留一行 `.env*.local`。

`NODE_ENV=test` 读不到 `.env.local`。 测试运行时只读 `.env.test`。变量缺失时测试报错，看起来像代码问题。

同一份镜像切环境。 前端代码里的公开变量已经固定，切环境只对服务端生效。需要按环境变化的公开配置，放运行时接口下发。

加密密钥不一致。 多实例部署时各用各的密钥，表单提交报 `Failed to find Server Action`。所有实例共用同一个值。

在模块顶层读浏览器对象。 客户端组件文件顶部直接访问 `window` 或 `localStorage`，构建时抛错，因为服务端渲染阶段这些对象不存在。读取放在 `useEffect` 或事件处理器里。

变量值带空格或换行。 复制粘贴时尾部多了空格，地址拼出来带着空格，请求失败。`.env` 文件里不要给值加引号，值本身的空格会被保留。

CI 里只配了构建变量。 构建通过，运行时缺密钥，健康检查失败。构建与运行两个阶段各有一份变量清单。

把变量值写进代码注释。 注释会随源码进仓库，密钥等于公开。示例值统一用占位符，真实值只放在环境变量里。

## 7.9 检查点

1. 把 `SUPABASE_SERVICE_ROLE_KEY` 临时改成 `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY`，重新构建，然后执行 `grep -rIl "service_role" .next/static`。判据：命中，产物里能搜到密钥片段。改回后重新构建，同样命令不再命中。
2. 删除 `.env.local` 里的 `NEXT_PUBLIC_SUPABASE_URL`，运行 `pnpm dev`。判据：启动时报“缺少环境变量 NEXT_PUBLIC_SUPABASE_URL”，进程不进入就绪状态。
3. 在 `.env.local` 与 `.env` 里给同一个变量写不同的值，运行 `pnpm dev`。判据：代码读到 `.env.local` 的值。
4. 在客户端组件里 import `@/lib/env`。判据：`pnpm build` 失败，报错指出 `server-only` 不能被客户端组件导入。
5. 用 `openssl rand -base64 32` 生成两个不同的值，分别设给两个实例。判据：提交表单时报 `Failed to find Server Action`；改成同一个值后恢复正常。
6. 在 `.env.local` 里写一个带 `NEXT_PUBLIC_` 前缀的测试变量，在页面里输出它，构建后搜索产物。判据：变量值以字面量出现在 `.next/static` 的 JS 里。
7. 在 `instrumentation.ts` 的 `register()` 里故意少传一个必填变量，启动服务。判据：进程启动失败，终端打印缺少的变量名，端口没有进入监听状态。

## 7.10 常见错误

1. `Error: 缺少环境变量 SUPABASE_SERVICE_ROLE_KEY`

现象：本地启动成功，部署后启动失败。
原因：部署环境没配这个变量，或者变量名拼错。
改法：在平台的环境变量设置里补上，注意大小写；用 `.env.example` 对照变量名清单。

2. `ReferenceError: process is not defined`

现象：浏览器控制台报错，页面白屏。
原因：在客户端组件里直接用了 `process.env` 之外的 Node 全局对象。
改法：客户端只读 `NEXT_PUBLIC_` 开头的变量，其他逻辑移到服务端组件。

3. `Error: 'server-only' cannot be imported from a Client Component module`

现象：构建失败，报错里有 import traces。
原因：客户端组件直接或间接导入了服务端模块。
改法：把变量通过 props 从服务端组件传下去，或者把该逻辑拆成服务端函数。

4. 环境变量改了但页面没变

现象：修改 `.env` 后重新请求，读到的还是旧值。
原因：公开变量在构建时已写死，运行期改环境变量不起作用。
改法：重新执行 `pnpm build` 再部署；需要运行时切换的值，用服务端接口下发。

5. `Failed to find Server Action`

现象：部署后旧页面提交表单报错。
原因：新旧实例的 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 不一致，或者客户端拿的是上一次部署的 action ID。
改法：所有实例统一密钥；部署期间提示用户刷新；保留一个版本的重试入口。

6. 本地能读到变量，测试里读到 `undefined`

现象：单元测试中读取公开变量为空。
原因：`NODE_ENV=test` 时不加载 `.env.local`。
改法：建 `.env.test` 并提交，测试专用的值写在那里；或用 `@next/env` 的 `loadEnvConfig(process.cwd())` 手动加载。

7. 构建产物里搜到了数据库密码

现象：`grep` 在 `.next/static` 中命中密钥片段。
原因：变量加了 `NEXT_PUBLIC_` 前缀，或者密钥写进了 `next.config.ts` 的 `env`。
改法：先轮换密钥，再去掉前缀与配置，重新构建并再次搜索确认。

## 7.11 这一章在做什么

这一章把配置分成两类：构建期写死的公开值和只在服务端存在的密钥。前者用于浏览器可见的配置，后者必须留在服务端。

三条判断可以带走：

- 变量名带 `NEXT_PUBLIC_`，值就当作公开信息处理。
- 服务端模块入口加 `import "server-only"`，让误用变成构建期错误。
- 启动时校验必填与格式，比在第一个请求里发现更省时间。
- 构建产物要搜一遍，命令比约定可靠。

变量清单按环境维护，回滚时先对照清单确认值来自哪一套。
