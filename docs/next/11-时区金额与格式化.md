# 第 11 章 时区、金额与格式化

第 10 章保证了写进数据库的值正确。这一章处理这些值怎么显示出来，以及为什么同一行数据在不同设备上会显示成两个样子。

要解决的是三件事。时间只有一种正确的存储方式，就是一个绝对瞬间；显示成哪年哪月哪日几点，取决于看的人在哪个时区。金额只有一种正确的存储方式，就是整数分；显示成带符号和小数位的文本，取决于语言和币种。文本的生成交给 `Intl`，拼接字符串在多数语言下都会出错。

为什么这三件事必须放在一章里：它们的错误形状相同。存错了不会报错，算错了不会报错，拼错了也不会报错，只会在对账那天、或者用户截图来问的时候一起出现。三者的修复思路也相同：事实用一种与环境无关的形式存，表示交由运行时按环境生成。

涉及的概念有 `timestamptz`、会话时区、`at time zone`、`date`、整数分、`Intl.NumberFormat`、`Intl.DateTimeFormat`、`locale` 与 `timeZone` 的分离、夏令时。基线是 Postgres 15 与 Node 20 以上。本章的命令若涉及本地数据库，需要在项目根目录执行；本机没有安装 Supabase CLI，`psql` 相关步骤标「未验证」。

## 11.1 时间：存绝对时刻，显示本地文本

Postgres 有三个与时间相关的类型，用途不同。

`timestamptz` 存一个绝对瞬间，内部按 UTC 微秒记。这个类型名有误导性，它不存时区，也无法存时区。2026-11-15T15:40:00Z 这一刻在全世界是同一个时刻，只是各地墙上钟的读数不同。

`timestamp` 存不带时区的墙上时间，例如「2026-11-15 09:00」。它不知道这个 09:00 属于哪个时区。应用按北京时间写入、服务器按新加坡时间读出，就偏了一小时，而且不报错。

`date` 存日历上的一天，例如生日、账期、排班日。它没有时刻，比较时不涉及时区。

第 8 章的 DDL 里，所有「发生了什么」的时间列都是 `timestamptz`：`created_at`、`updated_at`、`expires_at`、`read_at`、`run_at`。这条规则在全书不变。

### 在 psql 里确认存储与显示的分工

```sql
set time zone 'Asia/Shanghai';
select now(), now()::text, extract(epoch from now())::bigint;

set time zone 'America/Los_Angeles';
select now(), now()::text, extract(epoch from now())::bigint;
```

两次 `now()::text` 相差 16 小时，`extract(epoch ...)` 的结果完全相同。会话的 `TimeZone` 只影响文本输出、`::date`、`date_trunc` 这类「取表示」的操作，不影响存进去的值。

服务器自己用的时区要查一下：

```sql
show timezone;
select current_setting('TimeZone');
```

托管环境通常给 UTC，本地 `supabase start` 的容器跟随宿主机。生产环境固定成 UTC，把所有转换放在应用层，好处是本地与线上行为一致，出问题只需要怀疑一处代码。

时区清单来自操作系统的时区数据库，不是 Postgres 自己维护的：

```sql
select name from pg_timezone_names where name like 'Asia/%' order by name limit 10;
```

这份数据会随系统更新变化。别在代码里抄一份时区列表，需要下拉框时用 `Intl.supportedValuesOf('timeZone')`，校验时用 `Intl` 构造函数。

### 时间的默认值与比较

`created_at timestamptz not null default now()` 比让应用传 `new Date()` 可靠。应用服务器的时钟会漂，`TZ` 会配错，多台机器之间的时间还会差几百毫秒。`now()` 取的是事务开始时间，同一个事务里调多次都是同一个值，同一批写入的时间天然一致。

`now()` 与 `clock_timestamp()` 要分清。前者固定在整个事务里，适合记录「这件事发生在哪个逻辑时刻」；后者每次都取真实时钟，适合测量一段 SQL 跑了多久。用 `now()` 计时会得到一串 0 毫秒。

比较也用瞬间比较，不要转成字符串：

```sql
-- 正确：直接比较 timestamptz，可以走索引
where created_at >= now() - interval '7 days'

-- 错误：先转文本再比较，索引失效，结果还依赖会话时区
where created_at::text >= '2026-11-08'
```

`timestamptz` 的索引按绝对时间排序，`(team_id, created_at desc)` 这类复合索引对「最近七天」的范围查询最友好。第 8 章的 `activity_logs_team_created_idx` 就是这个形状。

## 11.2 按天、按周切分数据

账单页要做每天收入的柱状图。第一版写法是：

```sql
select issued_at::date as day, sum(amount_cents) as cents
from public.invoices
where team_id = $1
group by 1
order by 1;
```

`::date` 依赖会话时区。服务器是 UTC 时，北京时间 00:30 开的账单会落进 UTC 的前一天，也就是统计里的「昨天」。

按天切属于产品决策：按谁的日历算。定了之后 SQL 要显式写出时区：

```sql
select (issued_at at time zone $2)::date as day, sum(amount_cents) as cents
from public.invoices
where team_id = $1
  and issued_at >= $3
  and issued_at <  $4
group by 1
order by 1;
```

`at time zone` 把瞬间解释成指定时区的墙上时间，返回不带时区的 `timestamp`，再 `::date` 才是那本日历上的一天。参数顺序要记牢：`$2` 是时区名，`$3` 与 `$4` 是 UTC 区间。

区间用半开区间。`between $3 and $4` 两端都包含，如果 `$4` 是「某天 00:00」，下一天的第一条会被算进今天，月底对账时这种偏移很难查。

按周、按月统计要用 `date_trunc` 配合时区：

```sql
-- 按用户时区的周一切周
select date_trunc('week', issued_at at time zone $2) as week_start,
       sum(amount_cents) as cents
from public.invoices
where team_id = $1
group by 1
order by 1 desc;
```

`at time zone` 之后类型变成 `timestamp`，`date_trunc` 才按那本日历切。少了这一步，周一的边界落在 UTC 的周日晚上，国内用户看到的「本周」从周日下午开始。

如果字段本身就是「一天」，存 `date` 而不是 `timestamptz`。`due_on date` 比较时不需要时区，`due_on < current_date` 就是过期，索引也更小。反过来，把 `date` 存进 `timestamptz` 列等于给这一天凭空指定了一个 UTC 零点，之后每个时区的用户看到的时间都不同，而业务根本不关心几点。

夏令时的处理也落在这一节。切换那天只有 23 或 25 小时，按「每天 86400 秒」累加做报表，切换日会多算或少算一小时。按日历切天没有这个问题，因为 `date` 的单位是天，不是秒。

## 11.3 时区与语言从哪里来

存 UTC 只解决一半，另一半是格式化时用哪个时区、哪种语言。候选有三个：浏览器时区、用户资料、团队设置。

浏览器时区在服务端渲染时拿不到，用它容易产生 hydration 不一致。`profiles` 表没有时区列，本书不擅自加。团队时区适合「全团队按同一时区对账」的产品，但用户出差时会别扭。

本书用 cookie `tz` 与 `locale`：服务端与客户端都能读，换设备重新写一次即可，不需要改表结构。不用 `localStorage` 的原因是服务端读不到，只能先渲染占位再让 JS 改写，那就是闪烁。cookie 随请求到达服务器，第一份 HTML 就是对的时间。

代价要说清：读 cookie 属于请求时 API，带它的部分会变成动态渲染。开了 Cache Components 之后，`cookies()` 必须包在 `<Suspense>` 里，只有那棵子树在请求时流式渲染。这一点在官方 `cookies` 文档里写明。

cookie 属性也要定。`tz` 不需要 `httpOnly`，它不是凭证，前端有时要读它来决定日期选择器的默认值。需要 `sameSite: 'lax'`，防止别的站点带着它发请求；`secure` 在生产环境打开，本地 http 关闭。

### 读取与校验

cookie 的值来自浏览器，不可信。非法时区会让 `Intl` 抛 `RangeError`，整页 500。

```ts
// src/lib/timezone.ts
import { cookies } from 'next/headers'

const FALLBACK_TIME_ZONE = 'UTC'
const FALLBACK_LOCALE = 'en-US'

export function isValidTimeZone(value: string | undefined | null): value is string {
  if (!value) return false
  try {
    // 时区非法时构造函数抛 RangeError
    new Intl.DateTimeFormat('en-US', { timeZone: value })
    return true
  } catch {
    return false
  }
}

export function isValidLocale(value: string | undefined | null): value is string {
  if (!value) return false
  try {
    // getCanonicalLocales 对 "en_US" 这类下划线写法直接抛错
    Intl.getCanonicalLocales(value)
    return true
  } catch {
    return false
  }
}

export async function getUserTimeZone(): Promise<string> {
  const store = await cookies()
  const raw = store.get('tz')?.value
  return isValidTimeZone(raw) ? raw : FALLBACK_TIME_ZONE
}

export async function getUserLocale(): Promise<string> {
  const store = await cookies()
  const raw = store.get('locale')?.value
  return isValidLocale(raw) ? raw : FALLBACK_LOCALE
}
```

用构造函数做校验最省事，IANA 时区数据库本来就在运行时里。有人会传 `Asia/Beijing`，这个名字不存在，北京对应 `Asia/Shanghai`。

### 写入只能在 Server Action 或 Route Handler

`cookies().set()` 只能在这两处调用。下面是设置页的 action。

```ts
// src/app/(app)/settings/actions.ts
'use server'

import { cookies } from 'next/headers'
import { isValidLocale, isValidTimeZone } from '@/lib/timezone'

export type PreferenceState = { ok: boolean; error?: string }

export async function savePreferences(
  _prev: PreferenceState,
  formData: FormData,
): Promise<PreferenceState> {
  const timeZone = String(formData.get('tz') ?? '')
  const locale = String(formData.get('locale') ?? '')

  if (!isValidTimeZone(timeZone)) {
    return { ok: false, error: '请选择一个有效的时区' }
  }
  if (!isValidLocale(locale)) {
    return { ok: false, error: '请选择一个有效的语言' }
  }

  const store = await cookies()
  const options = { path: '/', maxAge: 60 * 60 * 24 * 365, sameSite: 'lax' as const }
  store.set('tz', timeZone, options)
  store.set('locale', locale, options)

  return { ok: true }
}
```

这个签名用的是第 12 章展开的 `useActionState` 形状，先照抄可以跑。附带一个好处：Server Action 里 `cookies().set()` 会自动重渲染当前页与 layout，改完时区点保存，页面上的时间立刻整体平移，不需要手动刷新。

### 第一次访问没有 cookie

两条路。第一条是给默认值，本书用 `UTC` 加 `en-US`，并在页头放一个明显的「时区：UTC，点击设置」，而不是假装知道用户在哪。按 `Accept-Language` 只能猜语言，猜不出时区。

第二条是让浏览器上报时区，用一个 Server Action 写进 cookie：

```tsx
// src/app/(app)/components/timezone-sync.tsx
'use client'

import { useEffect } from 'react'
import { saveTimezone } from '@/app/(app)/settings/actions'

export function TimezoneSync() {
  useEffect(() => {
    const tz = Intl.DateTimeFormat().resolvedOptions().timeZone
    if (tz && document.cookie.indexOf(`tz=${tz}`) === -1) {
      void saveTimezone(tz)
    }
  }, [])
  return null
}
```

代价是第一屏仍然是 UTC，JS 启动之后才纠正，表现为闪烁。想彻底不闪，只能在反向代理层按 IP 猜，或者要求用户先设置。选一种能向用户解释清楚的做法。

官方还有一种方案：内联脚本在首次绘制前改写 DOM，元素加 `suppressHydrationWarning`，React 保留 DOM 文本并丢弃不一致的 RSC 文本。它能消除闪烁，代价是代码绕，还要处理客户端导航时脚本不重新执行。能用 cookie 就用 cookie。

时区还会泄露大致位置。客服系统、公开分享页这类场景，不要把接收方看到的时间按发送方时区显示，用接收方自己的 cookie，或者统一显示 UTC 并标注。

## 11.4 金额：只存整数分

JavaScript 的数值是 IEEE 754 双精度浮点。0.1 在二进制里是无限循环小数，存进去就被舍入，每运算一次误差放大一点。

```js
0.1 + 0.2          // 0.30000000000000004
19.99 * 3          // 59.97000000000001
(0.1 + 0.2) === 0.3 // false
```

几十张账单累加，财务就会看到那五毛七。存储金额有四种常见做法。

| 做法 | 列类型 | 问题 |
| --- | --- | --- |
| 浮点 | `double precision` | 误差累积，不能用于钱 |
| 定点 | `numeric(12,2)` | 精确，但 JS 侧读出字符串，容易忘转 |
| 整数分 | `integer` | 全整数运算，零误差，展示时除 100 |
| 字符串 | `text` | 把算术推给应用层，无人愿意维护 |

本书选整数分。规则三条：用户输入的 `19.99` 解析成 `1999` 存库；加减乘除全用整数，除法只在最后一步并明确舍入；展示用 `Intl.NumberFormat`，不要手写 `"$" + (cents / 100)`。

`integer` 上限 2,147,483,647 分，约 2147 万美元。单张账单够用。要做上亿金额再换 `bigint`，但 node-postgres 会把 `bigint` 读成字符串，记得转换。

### 账单表

`invoices` 不在九张核心表里，属于订阅业务的扩展表。

```sql
-- supabase/migrations/20261117090000_invoices.sql
-- 金额一律以分为单位存整数，货币单独一列。
create table public.invoices (
  id           uuid primary key default gen_random_uuid(),
  team_id      uuid not null references public.teams (id) on delete restrict,
  -- 发票号由业务生成，例如 INV-2026-0001
  number       text not null unique,
  -- 单位：分。19.99 美元存 1999
  amount_cents integer not null check (amount_cents >= 0),
  -- ISO 4217 三位大写代码
  currency     char(3) not null default 'USD' check (currency = upper(currency)),
  status       text not null default 'open'
               check (status in ('open', 'paid', 'void')),
  issued_at    timestamptz not null default now(),
  due_at       timestamptz,
  paid_at      timestamptz,
  created_at   timestamptz not null default now()
);

-- 列表页：按团队加时间倒序翻页，第 13 章使用
create index invoices_team_issued_idx
  on public.invoices (team_id, issued_at desc, id desc);
```

`on delete restrict` 是刻意的：团队名下还有账单时不能删除团队，必须先处理账单。

到期日的两种理解要区分。`issued_at + interval '30 days'` 是 30 个 24 小时，跨夏令时那天会落到 23:00 或 01:00；`interval '1 month'` 是日历运算，1 月 31 日加一个月得到 2 月 28 日或 29 日。业务说的是「30 天后同一时刻」还是「30 天后那一天」，必须在需求里写清楚，两种实现的结果在月底会同时出现差异。

### 解析输入与格式化输出

不要用 `parseFloat`。`parseFloat('19.99abc')` 返回 19.99，`parseFloat('1e3')` 返回 1000，`parseFloat('0.1')` 内部还是浮点。用字符串切分。

```ts
// src/lib/money.ts
const CURRENCY_PATTERN = /^[A-Z]{3}$/

export function isValidCurrency(value: string): boolean {
  return CURRENCY_PATTERN.test(value)
}

/**
 * 把用户输入的金额字符串转成分。只接受 0 到 2 位小数，
 * 不接受负号、科学计数法、欧洲小数逗号。返回 null 表示非法。
 */
export function parseAmountToCents(input: string): number | null {
  const trimmed = input.trim()

  // 两种合法写法：1234.56 与 1,234.56。
  // 19,99 不合法，那是欧洲的小数逗号，含义是 19.99。
  const plain = /^\d+(\.\d{1,2})?$/
  const thousands = /^\d{1,3}(,\d{3})*(\.\d{1,2})?$/

  let normalized: string
  if (plain.test(trimmed)) {
    normalized = trimmed
  } else if (thousands.test(trimmed)) {
    normalized = trimmed.replace(/,/g, '')
  } else {
    return null
  }

  const [whole, fraction = ''] = normalized.split('.')
  const cents = Number(whole) * 100 + Number(fraction.padEnd(2, '0'))

  // 超过 integer 上限会在数据库层报错，提前拦住
  if (!Number.isSafeInteger(cents) || cents > 2_147_483_647) return null
  return cents
}

export function formatMoney(cents: number, currency: string, locale: string): string {
  if (!isValidCurrency(currency)) {
    throw new Error(`invalid currency: ${currency}`)
  }
  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency,
    minimumFractionDigits: 2,
    maximumFractionDigits: 2,
  }).format(cents / 100)
}

/** 整数相加，不会出现 59.97000000000001 */
export function sumCents(values: number[]): number {
  return values.reduce((total, value) => total + value, 0)
}

/** 按比例算金额，百分比以千分之一为整数单位传入，先乘后除并四舍五入 */
export function applyRateCents(cents: number, permille: number): number {
  return Math.round((cents * permille) / 1000)
}
```

`19,99` 被拒绝，这一点值得强调。德国用户写 19,99 意思是十九块九毛九，如果代码把所有逗号删掉再解析，会变成 1999，收款金额放大一百倍，还没有任何报错。

### 分摊与退款

100 分钱分给 3 个人，每人 33 分，还剩 1 分。直接 `Math.floor` 会丢一分，直接 `Math.round` 会多一分。用最大余数法保证总和不变。

```ts
export function splitCents(total: number, parts: number): number[] {
  const base = Math.floor(total / parts)
  let remainder = total - base * parts
  return Array.from({ length: parts }, () => {
    if (remainder > 0) {
      remainder -= 1
      return base + 1
    }
    return base
  })
}
```

退款、冲正会出现负数。`amount_cents` 带 `check (amount_cents >= 0)` 时，退款只能另开一行负数，或者用状态字段。本书选状态字段 `status = 'void'`，金额永远非负。负数会让「合计」这类查询需要判断语义，状态是明确的。

币种要随账单一起存。今天的 100 美元改天汇率变了仍然是 100 美元，不要换算成基准货币再存，也不要只留一个数字。

不同货币的小数位不同。日元、韩元没有小数，科威特第纳尔有三位。`formatMoney` 写死两位只适合单币种，多币种时按货币取默认值：

```ts
const fractionDigits = new Intl.NumberFormat(locale, {
  style: 'currency',
  currency,
}).resolvedOptions().maximumFractionDigits
```

`formatMoney` 里的 `cents / 100` 回到了浮点，但它发生在展示的最后一刻，`Intl` 只保留两位，误差在肉眼和账目上都看不出。存储与累计路径上不要做这个除法。

SQL 里同理。`sum(amount_cents)` 出来的单位还是分，要显示成元就在应用层除。在 SQL 里写 `sum(amount_cents) / 100`，Postgres 的整数除法会截断，`5997 / 100` 得到 59，少掉七毛。需要小数就写 `sum(amount_cents) / 100.0`，但那已经是浮点，只适合展示查询。

约束两侧都要有。数据库的 `check (amount_cents >= 0)` 是最后一道门，应用层的 `parseAmountToCents` 是第一道门。只有应用层校验，后台脚本迟早绕过它；只有数据库校验，用户看到的是 500，看不到「金额格式不对」。

## 11.5 Intl：文本交给运行时生成

手写 `"$" + amount.toFixed(2)` 会在几处出错：欧元符号在法语里放在数字后面，德语用逗号做小数点，日元没有小数位，阿拉伯语用另一套数字，印度按「万」分组。`Intl` 就是为这些差异存在的。

```ts
// src/lib/format.ts
export function formatDateTime(
  iso: string,
  locale: string,
  timeZone: string,
  options: Intl.DateTimeFormatOptions = {},
): string {
  const date = new Date(iso)
  // 非法日期得到 NaN，Intl 随后抛 RangeError，提前给可读的兜底
  if (Number.isNaN(date.getTime())) return '—'

  return new Intl.DateTimeFormat(locale, {
    dateStyle: 'medium',
    timeStyle: 'short',
    timeZone,
    ...options,
  }).format(date)
}

export function formatDateOnly(iso: string, locale: string, timeZone: string): string {
  const date = new Date(iso)
  if (Number.isNaN(date.getTime())) return '—'
  return new Intl.DateTimeFormat(locale, { dateStyle: 'medium', timeZone }).format(date)
}

export function formatRelative(iso: string, locale: string, now: Date = new Date()): string {
  const target = new Date(iso)
  if (Number.isNaN(target.getTime())) return '—'

  const diffSeconds = Math.round((target.getTime() - now.getTime()) / 1000)
  const units: [Intl.RelativeTimeFormatUnit, number][] = [
    ['year', 60 * 60 * 24 * 365],
    ['month', 60 * 60 * 24 * 30],
    ['day', 60 * 60 * 24],
    ['hour', 60 * 60],
    ['minute', 60],
    ['second', 1],
  ]

  const formatter = new Intl.RelativeTimeFormat(locale, { numeric: 'auto' })
  for (const [unit, seconds] of units) {
    if (Math.abs(diffSeconds) >= seconds || unit === 'second') {
      return formatter.format(Math.round(diffSeconds / seconds), unit)
    }
  }
  return ''
}
```

三个参数必须显式传。`locale` 不传就用运行环境默认值，服务端是 `en-US`、浏览器是用户的语言，SSR 与 hydration 必然不一致。`timeZone` 同理。`currency` 必须是三位大写 ISO 4217 代码，`usd` 会抛 `RangeError`。

构造函数不便宜，要加载 locale 数据。长列表里每行 `new` 一个，几百行会明显变慢。按 `locale` 与 `timeZone` 缓存：

```ts
const cache = new Map<string, Intl.DateTimeFormat>()

function getDateTimeFormatter(locale: string, timeZone: string) {
  const key = `${locale}|${timeZone}`
  let formatter = cache.get(key)
  if (!formatter) {
    formatter = new Intl.DateTimeFormat(locale, {
      dateStyle: 'medium',
      timeStyle: 'short',
      timeZone,
    })
    cache.set(key, formatter)
  }
  return formatter
}
```

模块级缓存是安全的，它只依赖入参，不依赖请求，不会把 A 用户的数据带到 B 用户。第 14 章会讲清模块级状态在什么条件下才安全。

`Intl.DateTimeFormat.prototype.formatRange` 用来显示「11 月 15 日 至 11 月 20 日」，会自动省略重复部分，比手拼两个日期加连字符更符合各语言习惯。`Intl.supportedValuesOf('timeZone')` 列出运行时支持的全部时区，做下拉框时用它，注意这个列表跟 ICU 版本走，校验仍然要靠 `try` 加 `catch`。

`locale` 是语言加地区，不是国家。`zh-CN` 与 `zh-TW` 都写中文，日期格式、货币符号、一周从周几开始不同。用户选的是语言偏好，用英文界面的中国用户可能仍希望金额按 `en-US` 显示，所以本书把 `locale` 与 `timeZone` 拆成两个 cookie。

`<time dateTime={iso}>` 里放原始 ISO，文本里放本地化结果。屏幕阅读器、日历应用、浏览器的复制时间读的都是 `dateTime` 属性。

导出 CSV 时反过来，只给 ISO。表格软件的时区设置各不相同，给 `2026-11-16T03:00:00.000Z` 它自己会转；给 `2026-11-16 11:00` 就是一段没有出生地的字符串。表头可以标注 `issued_at (UTC)`。

多语言排序用 `Intl.Collator`，不要裸用 `localeCompare`：

```ts
const collator = new Intl.Collator(locale, { numeric: true, sensitivity: 'base' })
const sorted = teams.toSorted((a, b) => collator.compare(a.name, b.name))
```

`numeric: true` 让「团队 2」排在「团队 10」前面，`sensitivity: 'base'` 让大小写与重音不影响顺序。`toSorted` 是 ES2023 的方法，不支持时用 `[...teams].sort(...)`，不要直接 `sort` 改到 props 上。

需要拆出年月日时用 `formatToParts`，不要切字符串：

```ts
const parts = new Intl.DateTimeFormat(locale, { timeZone, month: 'short', day: 'numeric' })
  .formatToParts(new Date(iso))

const month = parts.find((part) => part.type === 'month')?.value
const day = parts.find((part) => part.type === 'day')?.value
```

`formatToParts` 给结构化结果，词序、12 小时制、阿拉伯语数字都是对的。字符串切割在英文下能跑，换一种语言就失效。

## 11.6 边界与失败模式

`new Date('2026-11-15')` 按 UTC 解析。只有日期没有时间的字符串，ECMAScript 规定按 UTC 处理，UTC-5 的用户看到的是 11 月 14 日。日期选择器传来 `2026-11-15` 时，要么当 `date` 列存，要么显式补上时区。`<input type="date">` 的 value 就是 `YYYY-MM-DD`，没有时区信息，存进 `timestamptz` 之前要先决定这一天从哪个时区的 00:00 开始，这是产品决策。

`toISOString()` 只用于传输。它永远输出 UTC，拿它切前十位当日期显示，UTC+8 的用户在晚上九点之后会看到「明天」。列用 `timestamptz`，传给前端 ISO 字符串，展示交回 `Intl`。

`getDate()`、`getMonth()`、`getHours()` 用的是运行环境的本地时区。浏览器里是用户时区，Node 里是服务器 `TZ`。同一个组件在两端跑，数字会不同。

夏令时会让「加 24 小时」算错。美国 2026 年 3 月 8 日凌晨 2:30 不存在，11 月 1 日凌晨 1:30 出现两次。

```js
// 在切换日会落到 3:00 或 1:00，而不是「明天同一时刻」
const tomorrow = new Date(date.getTime() + 24 * 60 * 60 * 1000)
```

正确做法是按日历加一天，在目标时区里做加减再转回 UTC。存 UTC 瞬间、只在展示时转换，日常读写不受影响，这也是不用 `timestamp` 的理由之一。

`Date.now()` 在静态壳里会被冻结。开了 Cache Components 之后，静态壳里的时间戳是构建那一刻的值，用户明天访问看到的还是建构时的「现在」。需要每请求的当前时间，用 `await connection()` 或把这段放进 `Suspense`；需要稳定值就接受它是构建时间。

月份从 0 开始。`new Date(2026, 10, 15)` 是 11 月 15 日。

Node 的 ICU 数据可能不全。官方镜像默认带 full-icu，某些精简镜像只有 small-icu，`Intl` 会退化：`zh-CN` 的日期格式化退回英文，货币符号变成代码。部署前在容器里跑一次：

```bash
node -e "console.log(new Intl.DateTimeFormat('zh-CN').format(new Date()))"
```

输出中文才算正常。

`<input type="datetime-local">` 传来的是墙上时间，没有时区。用户在东京填 `2026-11-15T09:00`，服务端按 UTC 解释就成了北京时间下午五点。这类输入要么同时收一个时区字段，要么存成字符串并在展示时按同一个时区解释。

开发时至少在两个时区环境下各跑一次：`TZ=UTC pnpm dev` 与 `TZ=America/New_York pnpm dev`。这个变量只改进程环境，不影响机器设置。

## 11.7 装进页面

账单页需要四样东西：当前用户、当前团队、用户的时区与语言。前两个来自前面的模块，后两个来自 cookie。

```tsx
// src/app/(app)/teams/[slug]/invoices/page.tsx
import { Suspense } from 'react'
import { query } from '@/lib/db'
import { requireUser } from '@/lib/auth'
import { requireMembership } from '@/lib/teams'
import { getUserLocale, getUserTimeZone } from '@/lib/timezone'
import { formatDateTime, formatRelative } from '@/lib/format'
import { formatMoney, sumCents } from '@/lib/money'
import { InvoiceListSkeleton } from './invoice-list-skeleton'

type Invoice = {
  id: string
  number: string
  amount_cents: number
  currency: string
  status: string
  issued_at: string
  due_at: string | null
}

async function InvoiceList({ slug }: { slug: string }) {
  // 三个请求时数据源：鉴权、cookie、数据库。放进 Suspense，外层仍是静态壳。
  const user = await requireUser()
  const team = await requireMembership(slug, user.id)
  const [locale, timeZone] = await Promise.all([getUserLocale(), getUserTimeZone()])

  const { rows: invoices } = await query<Invoice>(
    `select id, number, amount_cents, currency, status, issued_at, due_at
       from public.invoices
      where team_id = $1
      order by issued_at desc, id desc
      limit 50`,
    [team.id],
  )

  const total = sumCents(invoices.map((invoice) => invoice.amount_cents))
  const currency = invoices[0]?.currency ?? 'USD'

  return (
    <section>
      <p>
        共 {invoices.length} 张账单，合计 <strong>{formatMoney(total, currency, locale)}</strong>
      </p>

      <ul>
        {invoices.map((invoice) => (
          <li key={invoice.id}>
            <span>{invoice.number}</span>{' '}
            <strong>{formatMoney(invoice.amount_cents, invoice.currency, locale)}</strong>{' '}
            <time dateTime={invoice.issued_at}>
              {formatDateTime(invoice.issued_at, locale, timeZone)}
            </time>{' '}
            <span>{formatRelative(invoice.issued_at, locale)}</span>
            {invoice.due_at ? (
              <span>（到期 {formatDateTime(invoice.due_at, locale, timeZone)}）</span>
            ) : null}
          </li>
        ))}
      </ul>
    </section>
  )
}

export default async function InvoicesPage({
  params,
}: PageProps<'/(app)/teams/[slug]/invoices'>) {
  const { slug } = await params

  return (
    <main>
      <h1>账单</h1>
      <Suspense fallback={<InvoiceListSkeleton />}>
        <InvoiceList slug={slug} />
      </Suspense>
    </main>
  )
}
```

`PageProps<'...'>` 是 Next.js 16 的全局类型助手，按路由字符串推导参数类型。`params` 是 Promise，必须 `await`。

时间与金额都依赖 cookie，所以整块列表进 `Suspense`；页面标题、导航这些不依赖请求的内容留在外层，静态壳照常预渲染。用户看到的是骨架屏先出现，列表随后流式补上。

```tsx
// src/app/(app)/teams/[slug]/invoices/invoice-list-skeleton.tsx
export function InvoiceListSkeleton() {
  return (
    <ul aria-hidden className="animate-pulse space-y-2">
      {Array.from({ length: 5 }).map((_, index) => (
        <li key={index} className="h-6 rounded bg-neutral-200/60" />
      ))}
    </ul>
  )
}
```

fallback 用骨架屏，因为骨架屏不需要翻译。`aria-hidden` 让读屏用户不必听五遍占位提示。

## 11.8 检查点

1. 同一个瞬间，三个时区显示不同，机器值相同

```bash
node -e "
const iso='2026-11-14T15:40:00Z';
for (const tz of ['UTC','Asia/Shanghai','America/Los_Angeles']) {
  console.log(tz, new Intl.DateTimeFormat('en-US',{dateStyle:'short',timeStyle:'short',timeZone:tz}).format(new Date(iso)));
}
console.log('epoch', new Date(iso).getTime());
"
```

输出三行分别为 `11/14/26, 3:40 PM`、`11/14/26, 11:40 PM`、`11/14/26, 7:40 AM`，最后一行 epoch 每次执行都相同。再把设置页的时区改成 `Asia/Shanghai`，账单页时间整体平移 8 小时，`<time dateTime>` 属性不变。

**2. 金额没有浮点误差**

```bash
node -e "
console.log('float:', 19.99*3, 0.1+0.2);
console.log('int  :', 1999*3/100, 10+20);
"
```

输出第一行是 `59.97000000000001` 与 `0.30000000000000004`，第二行是 `59.97` 与 `30`。再插一张 `amount_cents = 1999` 的账单，页面显示 `$19.99`，三张合计 `$59.97`。

**3. 非法输入被挡住**

用表单依次提交 `19.999`、`1e3`、`-5`、`19,99`，期望全部被 `parseAmountToCents` 拒绝并给出字段错误，数据库没有新行。再试币种 `usd`，期望在 `isValidCurrency` 或数据库 check 处失败。

**4. 夏令时边界不报错**

```bash
node -e "
const fmt=new Intl.DateTimeFormat('en-US',{timeZone:'America/New_York',dateStyle:'short',timeStyle:'long'});
for (const iso of ['2026-03-08T06:30:00Z','2026-03-08T07:30:00Z','2026-11-01T05:30:00Z','2026-11-01T06:30:00Z']) {
  console.log(iso, '->', fmt.format(new Date(iso)));
}
"
```

`2026-03-08T06:30:00Z` 显示 `1:30:00 AM EST`，`07:30:00Z` 显示 `3:30:00 AM EDT`，中间那一小时不存在。`2026-11-01` 的两个时刻都显示 `1:30 AM`，一次 EDT 一次 EST。格式化函数不传 `timeZone` 时，这四条会给出四个不同的错误答案。

5. 数据库里的时间与页面上的时间能对上

在 `psql` 里查一条账单的 `issued_at`，拿它的 ISO 值跑 `node -e "console.log(new Date('...').toISOString())"`，两者应完全一致。页面上显示的是同一个瞬间按 `tz` 换算后的文本，不是另一个值。

## 11.9 常见错误

`RangeError: Invalid time zone specified: Asia/Beijing`

北京对应 `Asia/Shanghai`，`Asia/Beijing` 不存在。`Intl` 的时区名来自 IANA 数据库，不是首都清单。用 `isValidTimeZone` 包住构造函数，非法就落回 UTC 并记一条日志。

`RangeError: Currency code is required with currency style.`

用了 `style: 'currency'` 却没给 `currency`。反过来 `currency: 'usd'` 会抛 `RangeError: Invalid currency code : usd`，必须是三位大写。

`Warning: Text content did not match. Server: "11/14/2026" Client: "2026/11/14"`

服务端与浏览器的 locale 或时区不一致，根因是格式化时没有传这两个参数。把 `locale` 与 `timeZone` 改成必传参数。确实拿不到时按官方 `preventing-flash-before-hydration` 的方案用内联脚本加 `suppressHydrationWarning`，不要用 `useEffect` 二次渲染，那只是把闪烁推迟。

`RangeError: Invalid time value`

`new Date('')`、`new Date('2026-13-01')`、`new Date(undefined)` 都是 `NaN`，随后 `format(NaN)` 抛这个错。所有来自数据库或 URL 的时间，格式化前先判断 `Number.isNaN(date.getTime())`。

`ERROR: invalid input syntax for type integer: "19.99"`

往 `amount_cents` 里写了小数。说明某条路径还在用 `parseFloat`，或者把表单字符串直接传给了数据库。应用内部金额只该有一种表示：要么全是分，要么全是字符串。

`ERROR: date/time field value out of range: "2026-02-30 00:00:00+00"`

2026 年没有 2 月 30 日。闰年规则是能被 4 整除，整百年要能被 400 整除，2100 年不是闰年。Postgres 会拒绝不存在的日期，JS 的 `new Date('2026-02-30')` 却会悄悄滚到 3 月 2 日。前端校验必须比 `new Date()` 严：用 `input type="date"` 管格式，服务端用正则加日历规则再查一遍。

## 11.10 这一章在做什么

这一章解决的是「存事实，还是存表示」。

时间的事实是一个 UTC 瞬间，存 `timestamptz`；表示是用户所在时区的人类可读文本，只在渲染那一刻生成，依赖 cookie 里的 `tz`。金额的事实是一个整数分，存 `integer`；表示是带货币符号与小数位的字符串，只在渲染那一刻由 `Intl` 生成。

两条规则背后是同一个错误：把表示当成事实存下来。存了本地时间字符串，就丢失了时区信息；存了浮点金额，就丢失了精确值。它们都不会立刻报错，会在对账那天一起出现。

判断字段该存哪种类型，问一句话：它是一个时刻还是一天，是一个可计算的数还是一段给人看的文本。`created_at` 是时刻，`due_on` 是一天；`amount_cents` 是可计算的数，`formatted_price` 是文本且不该存。分不清时，选那个不依赖展示环境的形式，它总是更耐用。

下一章处理这些数据怎么被写进来：表单、Server Action、错误怎么显示，以及服务端动作的安全边界。
