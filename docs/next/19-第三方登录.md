# 第 19 章 第三方登录

这一章讲 OAuth 登录：用户点“用 GitHub 登录”，走完四次跳转，回来时你的应用有一个可信的会话，并且拿到了已验证的邮箱。

需要它的原因是邮箱注册的两道门槛：输密码、等验证邮件。第三方登录把这两步省掉，并且拿到一个已验证的邮箱。

涉及四个概念。授权码（code）是一次性凭证，用过即废。`state` 是防跨站请求伪造的随机串，回来时必须对得上。回调地址（`redirect_uri`）必须与后台登记的完全一致。身份标识用 `provider` 加 `provider_user_id`，邮箱只能做展示。

这一章以 GitHub 为例写透一条完整链路，再讲 Google 的差异、账号合并、解绑、以及不需要会话的例外场景。

## 19.1 四次跳转

一次 OAuth 登录有四次跳转，每一步都可能失败。

```
浏览器                   你的应用                 Supabase Auth              GitHub
  │                        │                        │                        │
  │ 点「用 GitHub 登录」    │                        │                        │
  ├───────────────────────►│ signInWithOAuth        │                        │
  │                        ├───────────────────────►│ 生成 state + PKCE       │
  │                        │◄───────────────────────┤ 返回 authorize URL      │
  │ 302 到 GitHub           │                        │                        │
  ├─────────────────────────────────────────────────┼───────────────────────►│
  │ 用户点「Authorize」                                                    │
  │◄───────────────────────────────────────────────────────────────────────┤
  │ 302 到 Supabase 的 /auth/v1/callback?code=...&state=...                │
  ├─────────────────────────────────────────────────►│ 校验 state             │
  │                                                  │ 用 code 换 GitHub token│
  │                                                  ├───────────────────────►│
  │                                                  │◄───────────────────────┤
  │ 302 到你的 /auth/callback?code=<supabase code>   │                        │
  │◄─────────────────────────────────────────────────┤                        │
  ├───────────────────────►│ exchangeCodeForSession │                        │
  │                        ├───────────────────────►│ 校验 PKCE verifier      │
  │                        │◄───────────────────────┤ Set-Cookie: sb-...     │
  │ 落地页                 │                        │                        │
```


第一次：浏览器跳到 GitHub 的授权页，带上 `client_id`、`redirect_uri`、`scope`、`state`、`code_challenge`。

第二次：用户在 GitHub 点“授权”，GitHub 跳回 Supabase 的回调地址，带一个 `code`。

第三次：Supabase 用这个 `code` 换 GitHub 的 access token，读用户信息，建立或更新 auth 用户，然后跳回你的 `/auth/callback`，再带一个 `code`。

第四次：你的回调 route 用这个 `code` 调 `exchangeCodeForSession`，得到会话，写 cookie，跳回业务页面。

容易记错的一点：GitHub 后台填的回调地址是 Supabase 的，形如 `https://<ref>.supabase.co/auth/v1/callback`，指向 Supabase 而非你的 `/auth/callback`。



## 19.2 Supabase 做了哪些事

Supabase Auth 承担了中间两层：换 token、读用户信息、建用户、管 identity。

它给你三个东西：一个 `identities` 记录（provider + provider_user_id + 邮箱）、一个 `auth.users` 行、一个会话。

你要做的只有两件：发起登录时把 `redirectTo` 传对，回调时换会话并落业务数据。

这个分工意味着：不要在应用里自己存 provider 的 access token 来判断身份。身份由 Supabase 的会话决定。



## 19.3 登录按钮

按钮是一个客户端组件，点击后调 `signInWithOAuth`。

```tsx
// src/app/login/oauth-buttons.tsx
'use client'

import { useState } from 'react'
import { createClient } from '@/lib/supabase/client'

export function OAuthButtons({ next }: { next: string }) {
  const [loading, setLoading] = useState<string | null>(null)

  async function signIn(provider: 'github' | 'google') {
    setLoading(provider)
    const supabase = createClient()

    const { error } = await supabase.auth.signInWithOAuth({
      provider,
      options: {
        // 回来后落在哪：带上 next，Supabase 会原样拼在回调地址后面
        redirectTo: `${window.location.origin}/auth/callback?next=${encodeURIComponent(next)}`,
        scopes: provider === 'github' ? 'read:user user:email' : 'email profile',
      },
    })

    if (error) {
      setLoading(null)
      // 一般到不了这里：成功时浏览器已经被带走了
      console.error(error.message)
    }
  }

  return (
    <div>
      <button onClick={() => signIn('github')} disabled={loading !== null}>
        {loading === 'github' ? '跳转中…' : '用 GitHub 继续'}
      </button>
      <button onClick={() => signIn('google')} disabled={loading !== null}>
        {loading === 'google' ? '跳转中…' : '用 Google 继续'}
      </button>
    </div>
  )
}
```


三个参数要注意。`redirectTo` 必须指向你的回调 route，并带上 `next`，登录后回到原页面。`scopes` 按 provider 要求填，GitHub 至少需要 `read:user` 和 `user:email`。

`redirectTo` 的域名必须在 Supabase 的白名单里。不在白名单时，Supabase 会把它改写成配置里的 Site URL，表现为“登录后总是回到首页”。



## 19.4 回调 route

回调 route 只做三件事：换会话、落业务数据、跳转。三件事的顺序不能换，会话没拿到就落业务数据，会写到错误的用户上。

```ts
// src/app/auth/callback/route.ts
import { NextResponse, type NextRequest } from 'next/server'
import { createClient } from '@/lib/supabase/server'
import { safeNext } from '@/lib/safe-redirect'

export async function GET(request: NextRequest) {
  const { searchParams, origin } = new URL(request.url)
  const code = searchParams.get('code')
  const next = safeNext(searchParams.get('next'), '/dashboard')
  const providerError = searchParams.get('error')

  // 情况一：provider 那边用户点了拒绝，或者 GitHub 自己出错
  if (providerError) {
    return NextResponse.redirect(
      `${origin}/login?error=${encodeURIComponent(
        searchParams.get('error_description') ?? '第三方登录被取消'
      )}`
    )
  }

  // 情况二：没有 code。可能是直接访问，或者页面被刷新过
  if (!code) {
    return NextResponse.redirect(`${origin}/login?error=${encodeURIComponent('登录参数缺失，请重试')}`)
  }

  const supabase = await createClient()
  const { error } = await supabase.auth.exchangeCodeForSession(code)

  if (error) {
    // 最常见：code 已经用过（刷新回调页），或者 PKCE verifier 丢了
    return NextResponse.redirect(
      `${origin}/login?error=${encodeURIComponent('登录已失效，请重新点击第三方登录')}`
    )
  }

  // 成功：补一次资料，防止 profiles 里没有这一行
  const { data } = await supabase.auth.getClaims()
  const userId = data?.claims?.sub
  if (userId) {
    await supabase.from('profiles').upsert(
      {
        id: userId,
        email: data?.claims?.email ?? null,
        full_name: (data?.claims?.user_metadata as { full_name?: string } | undefined)?.full_name ?? null,
      },
      { onConflict: 'id', ignoreDuplicates: true }
    )
  }

  return NextResponse.redirect(`${origin}${next}`)
}
```


`exchangeCodeForSession(code)` 是核心。code 一次性，刷新这个页面会报 `invalid request: both auth code and code verifier should be non-empty`。

`upsert profiles` 是兜底。正常情况下有数据库触发器在注册时建 profile，但第三方登录的用户可能绕过触发器，或者触发器失败。

`getClaims()` 拿用户，不要用 `getSession()`。后者不验签，第 15 章讲过原因。

`next` 参数要清洗，用 `safeNext`。

```ts
// src/lib/safe-redirect.ts（回顾）
export function safeNext(raw: string | null, fallback = '/'): string {
  if (!raw) return fallback
  // 必须以单个 / 开头：//evil.com 和 /\evil.com 都不行
  if (!raw.startsWith('/') || raw.startsWith('//') || raw.startsWith('/\\')) return fallback
  return raw
}
```




## 19.5 state 与 PKCE

`state` 防的是登录 CSRF：攻击者先在自己的浏览器发起登录，拿到一个带 code 的回调地址，再诱导受害者打开。受害者会在自己的账号下建立攻击者的关联。

防护方式是发起登录时生成随机 state，存进 cookie，回来时比对。

PKCE 防的是 code 被截获。发起时生成 `code_verifier`，把哈希（`code_challenge`）带给授权服务器，换 token 时再带上原文。

Supabase 的 `signInWithOAuth` 内置了这两步。手写时（19.13 节）要自己做。

state 不匹配时的报错是 `invalid flow state, no valid flow state found`。看到这个错误，先检查 cookie 是否被清掉。



## 19.6 next 参数

`next` 从哪来、怎么传、怎么校验，三处都要对。

来源是当前页面路径。用户从 `/t/acme/billing` 点登录，`next` 就是 `/t/acme/billing`。

传递路径有三段：登录页把它放进 `redirectTo`，Supabase 回调时原样带回，你的回调 route 读出来再跳到 `next`。

校验统一用 `safeNext`：只允许站内相对路径，拒绝 `//evil.com`、`https://evil.com`、`@evil.com` 这类写法。



## 19.7 GitHub 后台的三处配置

OAuth App 要填三个值。

`Homepage URL` 填站点地址。`Authorization callback URL` 填 Supabase 的回调地址。`Client ID` 和 `Client secret` 填进 Supabase Dashboard 的 Provider 设置。

```bash
# GitHub → Settings → Developer settings → OAuth Apps → New OAuth App
# Application name:        TeamStack
# Homepage URL:            https://teamstack.app
# Authorization callback URL:
#   https://<project-ref>.supabase.co/auth/v1/callback
```


回调地址写错时 GitHub 会报 `The redirect_uri MUST match the registered callback URL for this application`。

**未验证**：GitHub OAuth App 的界面文案随版本变化，以上字段名以当前控制台为准。



## 19.8 白名单与预览部署

Supabase 的 Redirect URLs 支持通配符。预览部署的域名是 `teamstack-<hash>.vercel.app`，可以配一条 `https://*-teamstack.vercel.app/**`。

不配的后果是预览环境登录后回到生产站点，看起来像“登录成功了但状态不对”。

生产环境的回调地址和预览环境是两套，两个都要配。



## 19.9 账号合并

同一个人可能先用邮箱注册，后来改用 GitHub 登录。两次是两个不同的 `auth.users` 行，还是同一行？

取决于 provider 返回的邮箱是否匹配已有用户。Supabase 的行为随版本和配置变化，**未验证**：当前版本在邮箱匹配时的默认动作需要实测确认。

三种策略。

拒绝：邮箱已存在时直接报错，让用户用原来的方式登录。安全，体验差。

自动合并：把新 identity 挂到已有用户上。方便，但有风险：如果 provider 返回的邮箱未验证，攻击者可以抢注。

手动合并：要求用户先登录已有账号，再在设置里绑定第三方。最稳，多一步操作。

teamstack 选第三种，绑定入口在安全设置里。



## 19.10 绑定与解绑

绑定是给已登录用户加一条 identity。

```ts
// src/app/(app)/settings/security/link-identity.ts（未验证：依赖 auth-js 版本是否提供 linkIdentity）
'use client'

import { createClient } from '@/lib/supabase/client'

export async function linkGithubIdentity() {
  const supabase = createClient()
  const { error } = await supabase.auth.linkIdentity({
    provider: 'github',
    options: { redirectTo: `${window.location.origin}/auth/callback?next=/settings/security` },
  })
  if (error) throw new Error(error.message)
}
```


解绑有三条规则。不能解掉最后一个 identity，否则账号没有登录方式。解绑前要求二次验证。解绑写审计。

最后一条的 action：

## 19.11 stateless 的例外

并非所有 OAuth 场景都需要会话。有些只需要“证明这次请求来自某个 provider”。

可以无状态的场景：webhook 回调（用签名验证）、服务间调用（用签名令牌）、公开页的“用 GitHub 评论”（用 provider token 直接调 API）。

不能无状态的场景：任何需要“谁在用什么身份”的功能、一次性凭证、授权判断。

判断标准：如果后续请求还要知道“这是谁”，就需要会话。



## 19.12 第三方登录的取舍

省掉注册表单，换来两个依赖：provider 的可用性、provider 的账号政策。

好处是明确的。用户少输一次密码，你少存一份密码哈希，邮箱已验证。转化率通常比邮箱注册高一截。

代价也明确。GitHub 挂了用户就登不进来；GitHub 封了某个账号，你的应用也跟着失去这个用户；企业客户可能不允许员工用个人 GitHub 登录。

所以多数产品同时保留邮箱登录和第三方登录。第三方登录是加速通道，邮箱是兜底。



## 19.13 OAuth 2.0 与 OIDC 的区别

两个名字经常混着说。

OAuth 2.0 是授权协议：让应用拿到一个 access token，用它访问资源。它不规定“用户是谁”。

OIDC 是在 OAuth 之上加的一层身份协议：多返回一个 ID token，里面有 `sub`、`email`、`iss`。它回答“用户是谁”。

GitHub 只实现 OAuth，你调 `/user` 接口才知道身份。Google 同时支持 OIDC，可以直接从 ID token 读身份。

实际影响不大，因为 Supabase 把两种都封装成同一种结果。了解区别是为了看懂报错里的 `id_token` 字段。



## 19.14 provider token 与你的会话不同

登录成功后，`session.provider_token` 里是 GitHub 的 access token。它可以调 GitHub API，比如读仓库列表。

它与你应用的会话不同。不要拿它判断用户身份，不要把它当登录凭证，不要存进 cookie。

它的有效期由 provider 决定，GitHub 默认不过期，Google 一小时。它也不能被你的应用吊销。

需要长期调用 provider API 时，单独存一份加密的 token，并且告诉用户你在存什么。



## 19.15 未验证邮箱的风险

provider 返回的邮箱可能没有验证。

GitHub 允许用户把邮箱设为私有，也允许添加未验证的邮箱。`user:email` scope 拿到的列表里，`verified` 字段要检查。

如果不检查，攻击者可以把自己的 GitHub 邮箱改成受害者的邮箱，然后登录你的应用，拿到受害者账号。

Supabase 在建立用户时会看 `email_confirmed`。**未验证**：它是否拒绝未验证邮箱，取决于 Dashboard 的 provider 设置，需要在项目里实测。

稳妥做法：登录成功后检查 `email_confirmed_at`，为空时跳到“请验证邮箱”页面。



## 19.16 一个用户多个 provider

同一个 `auth.users` 行可以挂多条 identity：`github`、`google`、`email`。

查当前的绑定情况：

```sql
select provider, provider_id, identity_data->>'email' as email
from auth.identities
where user_id = auth.uid();
```

`provider_id` 是 provider 那边的用户标识，`identity_data` 里有邮箱和头像。

登录按钮的文案要随绑定状态变：已绑定的显示“已连接”，未绑定的显示“连接”。不做这个区分，用户会重复点。



## 19.17 provider 挂了怎么办

GitHub 的可用性有记录可查，历史上出现过多次短时故障。

三件事。登录页在发起请求失败时给明确提示，不要一直转圈。保留邮箱登录作为兜底。监控登录成功率，低于阈值就告警。

`signInWithOAuth` 返回的 `error` 要处理，常见的是网络错误和 provider 配置错误。区分方式看 `error.message`。

如果 provider 长期不可用，可以在配置里临时禁用它，登录页只显示可用的方式。



## 19.18 首次登录之后做什么

第三方登录成功，用户第一次进你的应用时，数据库里可能只有 `auth.users` 一行。

要补齐三样东西。`profiles` 行，带姓名和头像（从 provider 的 `user_metadata` 取）。个人的默认团队，或者引导页。一条欢迎通知。

`profiles` 用 `upsert`，不要用 `insert`，避免并发时主键冲突。字段允许空，姓名取不到就留空，不要阻塞登录。

默认团队不要自动创建。多数产品让用户先看引导页，选“创建团队”或“加入团队”。自动创建一个“我的团队”看起来贴心，实际会让用户困惑：他要的可能是加入公司已有的团队。



## 19.19 client secret 的管理

OAuth App 的 Client secret 是密钥，泄漏等于别人可以冒充你的应用。

存放位置只有一个：Supabase Dashboard 的 Provider 设置。它存在服务端，不进入你的代码仓库。

不要在 `next.config.ts` 里写，不要放环境变量文件，不要写进文档截图。需要轮换时在 GitHub 后台重新生成，再更新 Supabase，中间有几秒的窗口。

**未验证**：Supabase 是否在密钥更新后立即生效，以实测为准。稳妥做法是在低峰期操作，并准备回滚。



## 19.20 回调白名单要最小

Supabase 的 Redirect URLs 允许通配符，方便预览部署。通配符也是一条攻击面。

`https://*.vercel.app/**` 这种配置，任何人部署一个 vercel 应用都能成为回调地址。攻击者可以构造一个登录链接，让 `redirectTo` 指向他的站点，受害者的 code 就送到他那里。

正确做法是精确到项目：`https://teamstack-*.vercel.app/**`，或者干脆只用固定的预览域名。

白名单越小越安全，这条规则对所有 OAuth 配置都成立。GitHub 后台的回调地址同理，只填必要的那一个。



## 19.21 日志与审计

登录成功要记一条审计：`auth.login`，`metadata` 里放 `{ provider: "github" }`。

不要记 provider 的 token，不要记完整的回调 URL（里面有 code）。

失败也要记：`auth.login_failed`，带错误码。连续失败是配置问题的信号，比如回调地址写错、client secret 过期。

审计写入不影响登录。写日志失败只打 `console.error`。



## 19.22 移动端与无 cookie 场景

移动端没有 cookie，OAuth 流程要换一种走法。

推荐用系统浏览器加深链接回调。应用内 WebView 会被 provider 拒绝（Google 明确禁止），而且无法共享 cookie。

流程是：应用打开系统浏览器，完成授权后 provider 重定向到你的 `/auth/callback`，这个页面再重定向到 `teamstack://auth?code=...`，应用捕获深链接，用 code 换会话。

PKCE 在这里是必须的，因为 code 会经过浏览器和应用的边界。`code_verifier` 存在应用的本地存储里。

**未验证**：深链接的配置依赖移动端框架，本节只给流程，不给代码。



## 19.23 企业 SSO 与 OAuth 的区别

企业客户常问“支持 SAML 吗”。SAML 与 OAuth 解决的是不同层面的问题。

OAuth 面向消费者，用户用个人账号登录。SAML 面向企业，员工用公司账号登录，身份由公司的 IdP 管理。

Supabase 的 SSO 在付费档提供，走 SAML。它和第三方登录的区别在于：域名可以绑定到某个 IdP，员工用公司邮箱登录时自动走 SSO。

实现上不用自己写协议，配置 IdP 的元数据即可。本节只说明边界：个人 GitHub 登录不能替代企业 SSO，两者在合规审计里的地位不同。



## 19.24 测试与本地开发

本地开发时，回调地址是 `http://localhost:3000/auth/callback`。它必须加进 Supabase 的 Redirect URLs，否则登录后跳不回本地。

GitHub 后台的回调地址不用改，因为它指向 Supabase，与你的本地地址无关。

**未验证**：Supabase CLI 的本地实例是否默认允许 localhost 回调，以 `supabase start` 的输出为准。

测试登录流程时用无痕窗口，避免已有 cookie 干扰。改完 OAuth 配置后必须重试一次，配置缓存可能导致旧值生效。



## 19.25 OAuth App 与 GitHub App

GitHub 提供两种应用形态，登录场景用 OAuth App，够用。

OAuth App 的权限是用户级的，用户授权后拿到他的公开资料。GitHub App 的权限是仓库级的，可以细化到某个仓库的某个操作，适合做集成。

登录只需要读用户信息，OAuth App 的 `read:user` 和 `user:email` 两个 scope 足够。不要申请 `repo`，用户看到会犹豫，审核也更慢。

scope 一旦申请，用户授权时看到的是完整列表。申请越少，授权率越高。



## 19.26 退出第三方登录

用户点“退出登录”时，你的应用清掉自己的会话即可。

不要试图吊销 provider 的 token。GitHub 的 token 不能通过 API 主动吊销，Google 可以但要额外调接口。用户退出你的应用，不意味着他要退出 GitHub。

真正需要“退出并断开”的场景是账号设置里的“解绑”。那是另一条流程，要二次确认，并写审计。



## 19.27 登录失败率监控

值得监控两个数字：发起次数、成功次数。

失败率突然上升，通常是三类原因：provider 故障（看状态页）、配置被改（回调地址、client secret）、代码发布引入了 bug。

按 provider 分开统计。GitHub 挂了不影响 Google，混在一起看不出问题。

埋点在回调 route：进入时记一次“开始”，拿到会话时记一次“成功”。两者的差值就是失败。



## 19.28 同邮箱两个 provider 的冲突

用户先用 GitHub 登录，后来又用 Google 登录。两个 provider 返回同一个邮箱。

如果做了自动合并，两条 identity 挂在同一个用户下，正常。

如果没做合并，会创建两个 `auth.users` 行，同一个邮箱两条记录。后续邮箱唯一性检查会冲突，用户也会困惑：为什么我的团队不见了。

处理原则：在登录成功之后检查这个邮箱是否已存在，存在时提示用户“用原来的方式登录，然后在设置里绑定新的登录方式”。



## 19.29 删除账号与 identity

用户注销账号时，`auth.users` 行删除，identity 行跟着级联删除。

要额外做两件事。清理 `profiles` 行（外键级联或手动删）。写一条审计，记录注销时间和方式。

provider 侧的数据不归你管。GitHub 上那次授权记录还在，用户可以在 GitHub 的授权列表里自己撤销。

如果用户要求“删除所有数据”，记得把 `activity_logs` 里的个人信息也匿名化，`actor_id` 改成 null 或保留 id 但清空 metadata。



## 19.30 回调 route 要有超时与重试

`exchangeCodeForSession` 是一次网络请求。网络抖动时它会失败，用户看到的是一个空白页。

处理方式：捕获错误，跳到登录页并带上错误码，不要抛出 500。

```ts
// src/app/auth/callback/route.ts（错误处理片段）
const { error } = await supabase.auth.exchangeCodeForSession(code);
if (error) {
  const url = new URL("/login", request.url);
  url.searchParams.set("error", "oauth_callback_failed");
  return NextResponse.redirect(url);
}
```

不要自动重试。code 是一次性的，重试一定失败，只会浪费一次请求。



## 19.31 第三方登录的隐私披露

登录页要写清楚会拿到哪些信息。

“使用 GitHub 登录”旁边一行小字，说明会读取你的公开资料和邮箱。这既是合规要求，也降低用户的犹豫。

不要写“一键登录，安全无忧”这类文案。用户见过太多，反而警惕。

隐私政策里要列出第三方登录作为数据处理场景，写清 provider 名称、读取的字段、保存时长。



## 19.32 邀请与 OAuth 的组合

被邀请人没有账号，也没有密码，最顺的路径是第三方登录。

链路是：邮件里的邀请链接打开预览页，提示登录，用户点 GitHub 登录，回调时带上 `next=/invite/<token>`，登录成功后回到邀请页，点“加入团队”。

三处要检查。`next` 要带住 token。回调 route 清洗 `next` 时不能把 `/invite/...` 当成非法路径。登录成功后邮箱要和邀请邮箱一致，不一致时按 18 章的逻辑拒绝。

这条链路里，邀请的 token 和 OAuth 的 code 都是一次性的，两者互不影响。



## 19.33 登录按钮的三种状态

按钮要能表示三种状态：未发起、跳转中、失败。

跳转中禁用按钮，避免连点产生多个 `state` cookie 互相覆盖。失败时显示错误文案，并保留重试入口。

`signInWithOAuth` 是同步发起跳转的，返回之后页面已经在导航。所以“跳转中”的状态在开始调用前设置，不要把成功回调写在后面。

失败最常见的是网络问题和配置问题，文案要分开：前者提示重试，后者提示联系管理员。



## 19.35 手写一遍

不用 Supabase 的封装，自己走一遍流程，能看清每一步在做什么。用 `arctic` 这个库。

```ts
// src/app/auth/github/route.ts
import { cookies } from 'next/headers'
import { NextResponse } from 'next/server'
import { generateState, GitHub } from 'arctic'

const github = new GitHub(
  process.env.GITHUB_CLIENT_ID!,
  process.env.GITHUB_CLIENT_SECRET!,
  `${process.env.NEXT_PUBLIC_SITE_URL}/auth/github/callback`
)

export async function GET() {
  const state = generateState()
  const url = github.createAuthorizationURL(state, ['read:user', 'user:email'])

  const cookieStore = await cookies()
  cookieStore.set('github_oauth_state', state, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax', // 必须是 lax：从 GitHub 跳回来是一次顶层 GET 导航
    path: '/',
    maxAge: 60 * 10, // 10 分钟，覆盖一次登录尝试的生命周期
  })

  return NextResponse.redirect(url)
}
```

```ts
// src/app/auth/github/callback/route.ts
import { cookies } from 'next/headers'
import { NextResponse, type NextRequest } from 'next/server'
import { GitHub } from 'arctic'

const github = new GitHub(
  process.env.GITHUB_CLIENT_ID!,
  process.env.GITHUB_CLIENT_SECRET!,
  `${process.env.NEXT_PUBLIC_SITE_URL}/auth/github/callback`
)

export async function GET(request: NextRequest) {
  const url = new URL(request.url)
  const code = url.searchParams.get('code')
  const state = url.searchParams.get('state')
  const cookieStore = await cookies()
  const savedState = cookieStore.get('github_oauth_state')?.value

  cookieStore.delete('github_oauth_state') // 一次性，用完立刻销毁

  if (!code || !state || !savedState || state !== savedState) {
    return NextResponse.redirect(`${url.origin}/login?error=state_mismatch`)
  }

  let tokens
  try {
    tokens = await github.validateAuthorizationCode(code)
  } catch {
    return NextResponse.redirect(`${url.origin}/login?error=code_invalid`)
  }

  const res = await fetch('https://api.github.com/user', {
    headers: { Authorization: `Bearer ${tokens.accessToken()}` },
  })
  const ghUser = (await res.json()) as { id: number; login: string; email: string | null }

  // 到这里你只拿到了「某个 GitHub 账号」，还没有自己的会话
  // 后续要做：查 identities 表 → 没有就建 user → 签发自己的 session cookie
  return NextResponse.redirect(`${url.origin}/dashboard`)
}
```


**未验证**：`arctic` 的 API 随版本变化，以上代码没有在写作环境里跑过。

三个要点。state 存 cookie，`httpOnly`、`secure`、`sameSite=lax`、`maxAge` 600 秒。`code_verifier` 也要存，PKCE 需要。回调时先校验 state，再换 token。

手写一遍之后会发现：OAuth 协议本身不难，难的是会话。Supabase 省掉的正是这一块。



## 19.36 换成 Google 的差异

同一个流程，四处不同。

`scopes` 用 `email profile`，两个空格分隔。Google 一定返回邮箱，GitHub 可能不返回（用户设为私有）。标识字段 Google 用 `sub`，GitHub 用 `id`。

Provider 设置里填的是 Google Cloud Console 的 Client ID 和 Secret，回调地址同样是 Supabase 的。

`identities` 里 `provider` 是 `google`。同一用户用两种方式登录时，会有两行 identity，指向同一个 `auth.users` 行。



## 19.37 头像与 next/image

GitHub 头像的域名是 `avatars.githubusercontent.com`，Google 是 `lh3.googleusercontent.com`。

`next/image` 默认只允许本站域名。不配 `remotePatterns` 时头像报 400。

```ts

    { protocol: 'https', hostname: 'lh3.googleusercontent.com' },
```

## 19.38 排查顺序

四步，从日志开始。

第一步看 Supabase 的 Auth 日志，有没有 `provider` 相关的错误。第二步看浏览器 Network，回调请求的状态码和重定向地址。第三步看 callback route 的日志，`exchangeCodeForSession` 的返回值。第四步看数据库，`auth.users` 和 `identities` 有没有新行。

常见错误分布在四步里，按顺序查比猜快。



## 19.39 检查点

1. 从 `/t/acme/billing` 点 GitHub 登录，登录后回到 `/t/acme/billing`，没有跳到首页。
2. 手动改回调 URL 里的 `state` 参数，登录失败，报 `invalid flow state`。
3. 刷新 `/auth/callback?code=...` 页面，报 `both auth code and code verifier should be non-empty`。
4. `identities` 表里这个用户有一行 `provider = 'github'`。

5. 在预览环境登录一次，确认回到预览域名，没有跳去生产域名。
6. 用同一个 GitHub 账号登录两次，`auth.users` 只有一行。

## 19.40 常见错误

1. 回调地址填成了自己的域名

现象：GitHub 报 `redirect_uri_mismatch`。原因：后台填的应该是 Supabase 的回调地址。改法：填 `https://<ref>.supabase.co/auth/v1/callback`。

2. 刷新回调页面

现象：报 `invalid request: both auth code and code verifier should be non-empty`。原因：code 一次性，刷新等于重用。改法：回调失败时跳登录页，让用户重新发起。

3. state 不匹配

现象：报 `invalid flow state, no valid flow state found`。原因：cookie 被清掉，或用户在别的标签页发起了登录。改法：检查 cookie 的 `SameSite` 与域名，只保留一个登录入口在跳转。

4. 登录后总是回到首页

现象：`next` 参数失效。原因：`redirectTo` 不在 Supabase 的白名单里，被改写成 Site URL。改法：把域名加进 Redirect URLs。

5. 邮箱未验证也能登录

现象：未验证邮箱的账号直接进入应用。原因：没检查 `email_confirmed_at`。改法：登录成功后判断，为空时跳验证页。

6. profiles 没有行导致 500

现象：登录成功但页面报错。原因：第三方登录的用户没有经过注册流程，profile 没建。改法：回调里 `upsert profiles`，并把姓名头像设为可空。
