# 第 17 章 行级安全与角色

这一章讲数据库层的访问控制：行级安全（Row Level Security，RLS）。它决定一个已登录用户能读到哪些行、能写哪些行。

需要它的原因是应用层判断挡不住直接访问。Supabase 的匿名密钥会进入浏览器产物，这是设计如此。任何人拿到它，加上自己的登录 token，就能直接请求 REST 接口，绕过你写的页面、Server Action、proxy。应用层每一处判断都还在，但用户不走那条路。

RLS 把判断放进数据库。policy 挂在表上，Postgres 在执行查询时自己过滤。应用层写错了、漏了、被人绕过，数据库仍然只返回该返回的行。

涉及四个概念。policy 是挂在表上的表达式，决定哪些行可见。角色分三种：`anon`、`authenticated`、`service_role`。grant 是表级权限，policy 是行级过滤，两者都要配。`security definer` 函数是绕过 RLS 的合法通道，用错会变成后门。

这一章按“语法 → 建表流程 → 十张表的完整 policy → 失败模式 → 验证方法”展开。第 8 章的建表脚本是数据契约，这一章是它的权限部分。

## 17.1 三层防线里的最后一层

应用有三层权限判断，各管一段。

proxy 判断有没有会话，挡掉未登录的请求。它在每个请求上执行，不能查库。

页面和 Server Action 判断这个人有没有权限，挡掉已登录但越权的请求。它可以查库，但只覆盖走 UI 的路径。

RLS 判断这一行能不能读，挡掉所有直接访问数据库的请求，包括绕过 UI 的、脚本调的、第三方工具连的。

三层的关系是包含关系：能通过第一层的请求，未必能通过第二层；能通过第二层的，未必能通过第三层。反过来，跳过第一层的请求，仍然要过第三层，这一层不受应用代码影响。

只有 RLS 这一层是数据库强制的。前两层都可以被绕过。

## 17.2 RLS 的语法

一张表要开 RLS，先执行 `alter table ... enable row level security`。开启之后，默认拒绝所有访问，除非有 policy 允许。

policy 由四个部分组成：作用范围（`for select`、`for insert`、`for update`、`for delete`、`for all`）、适用角色（`to authenticated`）、过滤条件（`using`）、写入条件（`with check`）。

```sql
-- 语法骨架
create policy "名字" on public.files
  for select
  to authenticated
  using ((select auth.uid()) = uploader_id);
```

四条规则要记住。

`using` 管“哪些行能被看到”，`with check` 管“能写入什么样的行”。select 和 delete 只需要 `using`，insert 只需要 `with check`，update 两个都要。

`to` 不能省。不写时默认 `public`，包含 `anon`。写上 `to authenticated` 才是只对登录用户生效。

`auth.uid()` 从 JWT 的 `sub` 取用户 id。未登录时返回 `null`，`null = user_id` 永远不成立，所以未登录用户看不到任何行。这是预期行为。

多个 policy 之间是 OR 关系。同一条命令上有多条 policy，满足任意一条就通过。要收紧权限用 `as restrictive`，它是 AND 关系。

## 17.3 两个默认值陷阱

RLS 有两个默认行为，与直觉相反，出事故大多出在这里。

第一个：SQL Editor 建表不会自动开 RLS。

用 Dashboard 的表格编辑器建表，RLS 默认开启。用 SQL Editor、`psql`、迁移脚本建表，RLS 默认关闭。同一个数据库，两种建表方式，结果不同。

关闭状态下，表对所有持有 grant 的角色完全开放。匿名密钥能读能写。

自查一条 SQL，看哪些表没开：

```sql
select relname, relrowsecurity
from pg_class
where relnamespace = 'public'::regnamespace
  and relkind = 'r'
  and relname in ('files', 'teams', 'team_members', 'activity_logs')
order by relname;
```


`relrowsecurity` 为 `f` 就是没开。新项目建完表跑一次，应该全是 `t`。

第二个陷阱更隐蔽：已有的 grant 不会因为加 policy 而收回。

Supabase 初期项目的 `public` schema 有一条默认授权：新建的表自动给 `anon`、`authenticated`、`service_role` 授予 `select`、`insert`、`update`、`delete`、`truncate`、`references`、`trigger`，Postgres 17 还多一个 `maintain`。

```
select, insert, update, delete, truncate, references, trigger
```


这条默认授权意味着：即使你写了 policy，`anon` 角色仍然有表的 `insert` 权限。policy 只过滤行，不收回 grant。没有 policy 的表，grant 就是全部权限。

查看当前 grant：

```sql
select grantee, string_agg(privilege_type, ', ' order by privilege_type) as privs
from information_schema.role_table_grants
where table_schema = 'public' and table_name = 'files'
  and grantee in ('anon', 'authenticated', 'service_role')
group by grantee;
```


如果结果里 `anon` 有 `INSERT`、`DELETE`，说明表级权限没收。

两个陷阱加起来，就是“以为开了 RLS，其实没有”和“以为 policy 挡住了写，其实 grant 还开着”。

## 17.4 建表的标准流程

五步，顺序固定，缺一步都有对应的失败模式。

第一步，开 RLS。

```sql
alter table public.files enable row level security;
```

第二步，收回默认授权。只留给 `authenticated`，`anon` 什么都不给。

```sql
revoke all on table public.files from anon, authenticated;
```

第三步，按需授予。只给业务真正需要的操作。

```sql
grant select, insert, update, delete on table public.files to authenticated;
```

第四步，写 policy。过滤条件里用到的列都建索引。

第五步，跑一次验证，确认 `anon` 拿不到数据。

五步写成迁移文件，一次执行完。手工执行容易漏第二步，而漏了它，现象是“policy 都写了，但匿名请求仍能写入”。

完整的迁移片段：

```sql
-- supabase/migrations/20261118090000_teams.sql（节选）
create table if not exists public.teams (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  slug text not null unique,
  plan text not null default 'free',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  deleted_at timestamptz
);

-- 1. 开 RLS
alter table public.teams enable row level security;

-- 2. 收回默认授权（这一步最常被忘）
revoke all on table public.teams from anon, authenticated;

-- 3. 按需重新授权：只给该给的操作
grant select, insert, update on table public.teams to authenticated;

-- 4. 建索引（policy 里用到的列，见 17.15）
create index if not exists teams_slug_idx on public.teams (slug);

-- 5. 写 policy（见 17.9）
```


注意 `grant` 的粒度。`grant all` 会带出 `truncate`，那是一个破坏性权限，业务上通常不需要。列级权限可以更细，比如只允许改 `full_name` 和 `avatar_url`：

```sql
grant update (full_name, avatar_url) on table public.profiles to authenticated;
```

## 17.5 角色与权限矩阵

三种数据库角色，权限范围不同。

`anon` 是未登录请求。它应该只能读公开数据，比如落地页用的内容。业务表一律不给权限。

`authenticated` 是已登录用户。它的权限由 policy 决定，行级过滤在它身上生效。

`service_role` 是后台任务用的角色。它有 `bypassrls` 属性，绕过所有 policy。只能在服务端用，密钥不能进浏览器。

团队内的角色是另一层概念，存在 `team_members.role` 里，值是 `owner` 或 `member`。它和数据库角色分属两个层面：一个 `authenticated` 用户，在 A 团队是 owner，在 B 团队是 member。

权限矩阵按操作排：

| 操作 | owner | member | 未登录 |
| --- | --- | --- | --- |
| 读团队数据 | 可以 | 可以 | 不可以 |
| 邀请成员 | 可以 | 不可以 | 不可以 |
| 改账单 | 可以 | 不可以 | 不可以 |
| 删除团队 | 可以 | 不可以 | 不可以 |
| 读账单 | 可以 | 可以 | 不可以 |

矩阵落在 policy 上，就是 `using` 里多一个 `exists` 子查询，检查当前用户在 `team_members` 里的角色。

## 17.6 辅助函数与 private schema

每张表的 policy 都要判断“当前用户是否这个团队的成员”。这段逻辑重复写十遍，改起来容易漏。抽成函数，放在 `private` schema 里。

`private` schema 不暴露给 Data API，所以里面的函数不能被 PostgREST 直接调用。这是它相对 `public` 的价值。

```sql
-- supabase/migrations/20261118090500_helpers.sql
create schema if not exists private;

-- 注意：security definer 函数必须固定 search_path，否则有被劫持的风险
create or replace function private.is_team_member(target_team uuid)
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1
    from public.team_members m
    where m.team_id = target_team
      and m.user_id = (select auth.uid())
  );
$$;

create or replace function private.is_team_owner(target_team uuid)
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1
    from public.team_members m
    where m.team_id = target_team
      and m.user_id = (select auth.uid())
      and m.role = 'owner'
  );
$$;

revoke all on function private.is_team_member(uuid) from public;
revoke all on function private.is_team_owner(uuid) from public;
grant usage on schema private to authenticated;
grant execute on function private.is_team_member(uuid) to authenticated;
grant execute on function private.is_team_owner(uuid) to authenticated;
```


三个细节。

函数用 `security definer`，以创建者的权限执行，绕过 RLS。这是必须的，否则函数内部查 `team_members` 时会再次触发 RLS，形成递归。

`set search_path = ''` 防止 search path 攻击。函数体里的表名要用全限定名 `public.team_members`。

`stable` 告诉查询规划器这个函数在一条语句内结果不变，可以缓存。写 `volatile` 会让每行都执行一次。

policy 里调用函数时要包一层 `select`：

```sql
using ((select public.is_team_member(team_id)))
```

`(select ...)` 让 Postgres 把它当成 initPlan，一次查询只算一次。不包的话，每行都算一次。

## 17.7 十张表的 policy

十张表按“谁能读、谁能写”分类，policy 一次写完。SQL 较长，按表拆开看。

`profiles` 只允许本人读写，邮箱公开可读。

```sql
alter table public.profiles enable row level security;
revoke all on table public.profiles from anon, authenticated;
grant select on table public.profiles to authenticated;
-- 只允许改这两列：邮箱是认证系统管的，别让前端改
grant update (full_name, avatar_url) on table public.profiles to authenticated;

create policy "profiles_select_self_or_teammate"
on public.profiles for select
to authenticated
using (
  id = (select auth.uid())
  or exists (
    select 1
    from public.team_members me
    join public.team_members other on other.team_id = me.team_id
    where me.user_id = (select auth.uid())
      and other.user_id = public.profiles.id
  )
);

create policy "profiles_update_self"
on public.profiles for update
to authenticated
using (id = (select auth.uid()))
with check (id = (select auth.uid()));
```


`teams` 团队内可见，创建和改名限 owner，删除是软删。

```sql
alter table public.teams enable row level security;
revoke all on table public.teams from anon, authenticated;
grant select, insert, update on table public.teams to authenticated;
create index if not exists teams_slug_idx on public.teams (slug);

create policy "teams_select_member"
on public.teams for select
to authenticated
using (public.is_team_member(id) and deleted_at is null);

-- 建团队：任何登录用户都能建，但只能建「自己」的
create policy "teams_insert_authenticated"
on public.teams for insert
to authenticated
with check ((select auth.uid()) is not null);

create policy "teams_update_owner"
on public.teams for update
to authenticated
using (public.is_team_owner(id))
with check (public.is_team_owner(id));
```


`team_members` 只在团队内可见，写操作全部走 RPC 函数，不给直接写权限。

```sql
alter table public.team_members enable row level security;
revoke all on table public.team_members from anon, authenticated;
grant select on table public.team_members to authenticated;
-- 这个索引必须加，见 17.15
create index if not exists team_members_user_id_idx on public.team_members (user_id);

create policy "team_members_select_member"
on public.team_members for select
to authenticated
using (public.is_team_member(team_id));
```


`invitations` 只给 owner 看，insert 时限制角色为 `member`，防止提权。

```sql
alter table public.invitations enable row level security;
revoke all on table public.invitations from anon, authenticated;
grant select, insert, update on table public.invitations to authenticated;
create index if not exists invitations_token_idx on public.invitations (token);

create policy "invitations_select_owner_or_invitee"
on public.invitations for select
to authenticated
using (
  public.is_team_owner(team_id)
  or lower(email) = lower((select auth.jwt() ->> 'email'))
);

create policy "invitations_insert_owner"
on public.invitations for insert
to authenticated
with check (public.is_team_owner(team_id) and role = 'member');

create policy "invitations_update_owner"
on public.invitations for update
to authenticated
using (public.is_team_owner(team_id))
with check (public.is_team_owner(team_id));
```


`activity_logs` 只增不改，`actor_id` 必须是当前用户。

```sql
alter table public.activity_logs enable row level security;
revoke all on table public.activity_logs from anon, authenticated;
grant select, insert on table public.activity_logs to authenticated;
create index if not exists activity_logs_team_created_idx
  on public.activity_logs (team_id, created_at desc);

create policy "activity_logs_select_member"
on public.activity_logs for select
to authenticated
using (public.is_team_member(team_id));

-- 只能以「自己」的身份写自己团队的日志
create policy "activity_logs_insert_member"
on public.activity_logs for insert
to authenticated
with check (
  public.is_team_member(team_id)
  and actor_id = (select auth.uid())
);
```


`files` 团队内可见，上传者的 id 必须是当前用户，删除限 owner 且要求 AAL2。

```sql
alter table public.files enable row level security;
revoke all on table public.files from anon, authenticated;
grant select, insert, update on table public.files to authenticated;
create index if not exists files_team_created_idx
  on public.files (team_id, created_at desc);

create policy "files_select_member"
on public.files for select
to authenticated
using (public.is_team_member(team_id) and status <> 'deleted');

create policy "files_insert_member"
on public.files for insert
to authenticated
with check (
  public.is_team_member(team_id)
  and uploader_id = (select auth.uid())
  and status = 'pending'
);

create policy "files_update_uploader_or_owner"
on public.files for update
to authenticated
using (
  public.is_team_member(team_id)
  and (uploader_id = (select auth.uid()) or public.is_team_owner(team_id))
)
with check (public.is_team_member(team_id));
```


`subscriptions` 只给读，改由 service_role 的后台任务做。

```sql
alter table public.subscriptions enable row level security;
revoke all on table public.subscriptions from anon, authenticated;
-- 注意：不给 insert / delete
grant select, update on table public.subscriptions to authenticated;

create policy "subscriptions_select_member"
on public.subscriptions for select
to authenticated
using (public.is_team_member(team_id));

create policy "subscriptions_update_owner"
on public.subscriptions for update
to authenticated
using (public.is_team_owner(team_id))
with check (public.is_team_owner(team_id));
```


`jobs` 完全不给 `authenticated`，只有后台任务能碰。

```sql
-- jobs：只给 service_role 用，authenticated 什么都不给
alter table public.jobs enable row level security;
revoke all on table public.jobs from anon, authenticated;

-- notifications：自己的才能看，只能改 read_at
alter table public.notifications enable row level security;
revoke all on table public.notifications from anon, authenticated;
grant select, update on table public.notifications to authenticated;

create policy "notifications_select_own"
on public.notifications for select
to authenticated
using (user_id = (select auth.uid()));

create policy "notifications_update_own"
on public.notifications for update
to authenticated
using (user_id = (select auth.uid()))
with check (user_id = (select auth.uid()));
```


`notifications` 只给本人。

```sql
create policy "notifications_select_own" on public.notifications
for select to authenticated
using (user_id = (select auth.uid()));
```


十张表有一个共同点：每条 policy 都写了 `to authenticated`，每条都用 `(select auth.uid())` 包一层。这两个写法是性能和安全的分界线。

## 17.8 六个常用模式

绝大多数 policy 落在六个模式里，记住形状比记住语法有用。

第一个：本人行。`using ((select auth.uid()) = user_id)`。用于 `profiles`、`notifications`。

第二个：团队内。`using (public.is_team_member(team_id))`。用于 `files`、`activity_logs`。

第三个：能看不能改。只给 `select` 的 policy，不给 `update`。用于 `activity_logs`。

第四个：只增不改。给 `insert` 加 `with check`，不给 `update` 和 `delete`。用于审计类表。

第五个：软删除。`using (deleted_at is null)` 加进所有读 policy。

第六个：AAL2。`using ((select auth.jwt()->>'aal') = 'aal2')`，用于敏感操作。

```sql
create policy "files_select_member" on public.files
for select to authenticated
using (public.is_team_member(team_id));
```

```sql
create policy "subscriptions_select_member" on public.subscriptions
for select to authenticated using (public.is_team_member(team_id));

create policy "subscriptions_update_owner" on public.subscriptions
for update to authenticated
using (public.is_team_owner(team_id))
with check (public.is_team_owner(team_id));
```

```sql
create policy "files_delete_requires_aal2" on public.files
for delete to authenticated
using (public.is_team_owner(team_id) and (select auth.jwt() ->> 'aal') = 'aal2');
```


第六个模式值得展开。用户开了两步验证，但登录之后拿到的是 AAL1 会话，必须再输一次动态码才升到 AAL2。policy 里判断 `aal` 就能让“没输动态码不给看”。

## 17.9 policy 还是 RPC

有些写操作不适合用 policy 表达，比如“转让所有权”要同时改两行，还要保证只有一个 owner。

判断标准三个问题。操作是否跨多张表？是否需要保证原子性？是否需要复杂校验？

三个问题有一个是“是”，就写成 Postgres 函数，用 `security definer`，在函数里做完整校验，然后 `grant execute` 给 `authenticated`。

policy 适合表达“这一行能不能被这个人看到或改”，函数适合表达“这个业务动作合不合法”。

两者配合的方式：表上不给直接写权限，函数里用 `security definer` 绕过 RLS，函数内部自己校验权限。

## 17.10 六个写法错误

第一个：漏 `to authenticated`。policy 默认对所有角色生效，包括 `anon`。`auth.uid()` 是 null，条件不成立，看似安全，但 `with check` 里如果有 `is not null` 的反向写法就会漏。

第二个：insert 写了 `using`。insert 只认 `with check`，写 `using` 直接语法错误。

第三个：update 只写 `with check`。update 需要两条：`using` 决定能改哪些行，`with check` 决定改成什么样。只写一条时，Postgres 用另一条兜底，行为与预期不同。

第四个：在 SQL Editor 里用 `postgres` 角色测。`postgres` 有 `bypassrls`，测什么都是通过。要用 `set local role authenticated` 加 `request.jwt.claims`。

第五个：用 JWT 里的 email 做条件。email 可以改，应该用 `sub`。

第六个：以为多条 policy 取交集。同一命令上多条 policy 是 OR，要收紧得用 `as restrictive`。

## 17.11 42P17 递归

两张表的 policy 互相查对方，会形成无限递归。

```
ERROR: infinite recursion detected in policy for relation "team_members"
```

```sql
-- 反例：查 team_members 的 policy 里又查 team_members
create policy "members_select_member" on public.team_members
for select to authenticated
using (
  exists (select 1 from public.team_members me where me.team_id = team_members.team_id and me.user_id = (select auth.uid()))
);
```


原因：policy 查 `team_members` 时触发它的 RLS，它的 policy 又查 `teams`，`teams` 的 policy 又查 `team_members`。

解决办法是抽一个 `security definer` 函数，函数内部绕过 RLS。这也是 17.6 节那两个函数存在的原因。

排查方式：把 policy 逐条 `drop`，看哪一条开始报错。或者看错误信息里的关系名，`for relation "team_members"` 已经指明了起点。

## 17.12 索引

policy 的过滤条件里出现的列，都要有索引。否则每次查询都全表扫描。

最容易漏的是 `team_members`。它的主键是 `(team_id, user_id)`，复合索引只对第一列 `team_id` 有效。按 `user_id` 过滤“我加入了哪些团队”时用不上这个索引。

```sql
-- team_members 的 PK 是 (team_id, user_id)，只有第一列能独立用
create index if not exists team_members_user_id_idx on public.team_members (user_id);
-- 按 slug 找团队（每个页面都要）
create index if not exists teams_slug_idx on public.teams (slug);
-- 列表页按团队 + 时间倒序
create index if not exists files_team_created_idx on public.files (team_id, created_at desc);
create index if not exists activity_logs_team_created_idx on public.activity_logs (team_id, created_at desc);
-- 邀请链接按 token 查
create index if not exists invitations_token_idx on public.invitations (token);
```


几条经验。`files` 建 `(team_id, status)`，因为用量查询按这两个字段过滤。`activity_logs` 建 `(team_id, created_at desc)`，列表页按时间倒序。`notifications` 建 `(user_id, created_at desc)`。

索引要克制。每个索引都会拖慢写入，还会占空间。只给 policy 和数据查询真正用到的列建。

## 17.13 service_role 的边界

`service_role` 绕过所有 RLS，用错等于没有权限系统。

三条纪律。

第一，密钥只在服务端。变量名不能有 `NEXT_PUBLIC_` 前缀，不能出现在客户端组件、不能进浏览器 bundle。

第二，每个查询都带 `team_id` 条件。因为 RLS 不生效，函数必须自己过滤。

```ts
// src/lib/admin/export.ts（只能在 Server Action / Route Handler 里被调用）
import 'server-only'

import { createClient } from '@supabase/supabase-js'

function adminClient() {
  return createClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.SUPABASE_SECRET_KEY!, // 不带 NEXT_PUBLIC_ 前缀，永远不会进浏览器包
    { auth: { persistSession: false, autoRefreshToken: false } },
  )
}

export async function exportTeamFiles(teamId: string, requesterId: string) {
  const supabase = adminClient()

  // 手动补偿：service_role 绕过了 RLS，所以「这个人是否这个团队的成员」得自己查
  const { data: membership } = await supabase
    .from('team_members')
    .select('role')
    .eq('team_id', teamId)
    .eq('user_id', requesterId)
    .maybeSingle()

  if (!membership) throw new Error('not a member')

  // 每一个查询都带 team_id，不给「忘了加条件」留机会
  const { data: files, error } = await supabase
    .from('files')
    .select('name, size_bytes, created_at')
    .eq('team_id', teamId)
    .eq('status', 'ready')
    .order('created_at', { ascending: false })

  if (error) throw error
  return files ?? []
}
```


第三，用完就扔。`createAdminClient()` 每次调用新建，不要做成模块级单例，避免连接泄漏。

后台任务、导出、清理这类场景用 `service_role`。用户请求一律不用。

## 17.14 两条绕过 RLS 的路

除了 `service_role`，还有两条路会绕过 RLS，都容易被无意打开。

第一条：`security definer` 函数。函数默认以创建者权限执行，绕过 RLS。用它做辅助函数没问题，但不要用它返回业务数据给前端，除非函数内部做了完整校验。

第二条：视图。Postgres 15 之前，视图以创建者权限执行，绕过 RLS。15 之后可以用 `security_invoker` 选项恢复调用者权限。

```sql
create view public.team_file_stats
with (security_invoker = true)   -- 关键：以查询者的身份执行
as
select team_id, count(*) as file_count, sum(size_bytes) as total_bytes
from public.files
where status = 'ready'
group by team_id;
```


建视图时一律加 `with (security_invoker = true)`，除非你明确知道自己在做什么。

## 17.15 RLS 与缓存

`'use cache'` 的函数如果读的是按用户过滤的数据，会把第一个用户的结果缓存给所有人。

错误写法是在缓存函数里读会话。构建期会失败，运行期会串号。

正确写法是把用户 id 当参数传进去：

```ts
// src/app/(app)/dashboard/files/page.tsx（反例）
import { createClient } from '@/lib/supabase/server'

export default async function FilesPage() {
  'use cache' // 错：缓存结果会被发给所有人

  const supabase = await createClient()
  const { data } = await supabase.from('files').select('*')
  return <FileList files={data ?? []} />
}
```

```ts
// src/app/(app)/dashboard/files/page.tsx（正例）
import { Suspense } from 'react'
import { requireUser } from '@/lib/auth'
import { getTeamFiles } from '@/lib/files'

export default async function FilesPage() {
  const user = await requireUser()
  return (
    <Suspense fallback={<FileListSkeleton />}>
      <Files user={user.id} />
    </Suspense>
  )
}

async function Files({ user }: { user: string }) {
  'use cache: private'
  const files = await getTeamFiles(user)
  return <FileList files={files} />
}
```


缓存键由参数决定，每个用户一份。数据变更之后用 `updateTag` 失效。

`'use cache: private'` 是例外，它的结果只存在浏览器，可以读 cookie。代价是只在客户端命中。

## 17.16 三个必须进事务的操作

建团队、转让所有权、移除成员，这三个操作要改多张表，必须在一个事务里。

建团队要同时插 `teams` 和 `team_members`，后者要写 owner。中途失败会留下一个没有成员的团队。

```sql
create or replace function public.create_team(team_name text, team_slug text)
returns uuid
language plpgsql
security definer
set search_path = ''
as $$
declare
  new_team_id uuid;
begin
  if (select auth.uid()) is null then
    raise exception 'not authenticated';
  end if;

  insert into public.teams (name, slug)
  values (team_name, lower(team_slug))
  returning id into new_team_id;

  insert into public.team_members (team_id, user_id, role)
  values (new_team_id, (select auth.uid()), 'owner');

  insert into public.activity_logs (team_id, actor_id, action, target_type, target_id)
  values (new_team_id, (select auth.uid()), 'team.created', 'team', new_team_id);

  return new_team_id;
end;
$$;

revoke all on function public.create_team(text, text) from public;
grant execute on function public.create_team(text, text) to authenticated;
```


转让所有权要先把自己降成 member，再把对方升成 owner。顺序反了会触发唯一约束：一个团队只能有一个 owner。

```sql
create or replace function public.transfer_ownership(target_team uuid, new_owner uuid)
returns void
language plpgsql
security definer
set search_path = ''
as $$
begin
  if not exists (
    select 1 from public.team_members
    where team_id = target_team and user_id = (select auth.uid()) and role = 'owner'
  ) then
    raise exception 'only owner can transfer';
  end if;

  -- 先降级自己，再升级对方：顺序反了会撞上 one_owner_per_team
  update public.team_members set role = 'member'
  where team_id = target_team and user_id = (select auth.uid());

  update public.team_members set role = 'owner'
  where team_id = target_team and user_id = new_owner;

  insert into public.activity_logs (team_id, actor_id, action, target_type, target_id, metadata)
  values (target_team, (select auth.uid()), 'member.transferred_ownership', 'member', new_owner,
          jsonb_build_object('from', (select auth.uid()), 'to', new_owner));
end;
$$;

revoke all on function public.transfer_ownership(uuid, uuid) from public;
grant execute on function public.transfer_ownership(uuid, uuid) to authenticated;
```


这个约束用部分唯一索引实现：

```sql
-- supabase/migrations/20261118091000_one_owner.sql
create unique index if not exists one_owner_per_team
  on public.team_members (team_id)
  where role = 'owner';
```


移除成员要检查不能让团队变成零成员。函数里先 count，再删。

三个函数都是 `security definer`，都要 `grant execute` 给 `authenticated`。

## 17.17 自查与验证

三条命令，覆盖三个层面的问题。

第一条，看哪些表没开 RLS：

```sql
select relname
from pg_class
where relnamespace = 'public'::regnamespace
  and relkind = 'r'
  and relrowsecurity = false
order by relname;
```


第二条，看默认授权有没有收回：

```sql
select
  case d.defaclobjtype
    when 'r' then 'tables'
    when 'S' then 'sequences'
    when 'f' then 'functions'
  end as object_type,
  a.grantee::regrole as role,
  string_agg(a.privilege_type, ', ' order by a.privilege_type) as privileges
from pg_default_acl d
cross join lateral aclexplode(d.defaclacl) a
where d.defaclrole = 'postgres'::regrole
  and d.defaclnamespace = 'public'::regnamespace
  and a.grantee in ('anon'::regrole, 'authenticated'::regrole, 'service_role'::regrole)
group by 1, 2
order by 1, 2;
```


没有行，说明新建的对象不给 Data API 角色任何权限。有行，按需撤销：

```sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on functions from anon, authenticated, service_role;
```


第三条，检查 Supabase Dashboard 的 Security Advisors，它会列出“开了 RLS 但没有 policy 的表”和“policy 太宽”两类问题。

## 17.18 手动验证 B 看不到 A

写完之后必须自己验一遍，用两个账号。

准备两个用户和两个团队，A 团队的文件属于用户 A，B 团队属于用户 B。

用用户 B 的 token 查 A 团队的文件：

```bash
curl "https://<ref>.supabase.co/rest/v1/files?select=id,team_id,name" \
  -H "apikey: <publishable key>" \
  -H "Authorization: Bearer <B 的 access token>"
```


返回 `[]` 是对的。返回数据就是 policy 写错了，或者表没开 RLS。

再试一次写入，应该报 `new row violates row-level security policy`：

```bash
curl -X PATCH "https://<ref>.supabase.co/rest/v1/subscriptions?team_id=eq.<A 的团队 id>" \
  -H "apikey: <publishable key>" \
  -H "Authorization: Bearer <B 的 access token>" \
  -H "Content-Type: application/json" \
  -d '{"status":"active","price_id":"price_xxx"}'
```


在 SQL Editor 里模拟更直接：

```sql
-- 事务里做，最后 rollback，不会留脏数据
begin;

-- 假设 A 和 B 是两个真实用户 id，A 是 team1 的成员，B 无成员关系
set local role authenticated;
set local request.jwt.claims = '{"sub":"<B 的 uuid>","role":"authenticated"}';

-- B 查 team1 的文件：预期是 0 行，不会报错
select count(*) from public.files where team_id = '<team1 的 uuid>';

-- B 查 team1 的成员：必须 0 行
select count(*) from public.team_members where team_id = '<team1 的 uuid>';

rollback;
```

```sql
begin;
set local role authenticated;
set local request.jwt.claims = '{"sub":"<member 的 uuid>","role":"authenticated"}';

-- member 改账单：应该报「new row violates row-level security policy」
update public.subscriptions set seats = 999 where team_id = '<team1 的 uuid>';
rollback;
```


`set local role authenticated` 切到登录角色，`set local request.jwt.claims` 注入用户身份，`set local request.jwt.claim.sub` 是旧写法，两者都试一下。查询结果为 0 行是 policy 过滤，报 `42501` 是缺 grant，两者原因不同。

## 17.19 应用层仍然要写

RLS 是最后一道防线，不能替代应用层判断。

四个理由。第一，RLS 只能过滤行，不能表达“这个操作是否合法”。第二，错误信息对用户不友好，直接暴露给用户是信息泄漏。第三，RLS 在数据库执行，业务规则（比如计费状态）查不到。第四，有些操作要跨多个表，policy 表达不了。

应用层的写法：

```ts
// src/lib/teams.ts
import 'server-only'

import { cache } from 'react'
import { notFound } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export type Role = 'owner' | 'member'

export const getActiveTeam = cache(async (slug: string | undefined) => {
  const supabase = await createClient()
  const { data, error } = await supabase
    .from('teams')
    .select('id, name, slug, plan')
    .eq('slug', slug ?? '')
    .is('deleted_at', null)
    .maybeSingle()

  // 非成员时，RLS 已经把行过滤掉了，这里拿到的就是 null
  if (error || !data) notFound()
  return data
})

export const requireMembership = cache(
  async (userId: string, slug: string | undefined, opts: { role?: Role } = {}) => {
    const team = await getActiveTeam(slug)
    const supabase = await createClient()

    const { data, error } = await supabase
      .from('team_members')
      .select('role')
      .eq('team_id', team.id)
      .eq('user_id', userId)
      .maybeSingle()

    if (error || !data) notFound()
    if (opts.role === 'owner' && data.role !== 'owner') notFound()

    return { team, role: data.role as Role }
  },
)
```


`requireMembership` 做三件事：查成员行、校验角色、不存在时 `notFound()`。用 `notFound()` 代替 403，避免暴露“这个团队存在但你没权限”。

## 17.20 怎么测 RLS

手动验证之外，还要有自动化测试。pgTAP 是 Supabase 推荐的方式，测试文件放 `supabase/tests/`。

```bash
supabase test db
```

**未验证**：这条命令依赖本地 Supabase 实例和 pgTAP 扩展，写作环境里没有执行。

测试的写法是 `set local role` 加 `set local request.jwt.claims`，然后断言查询结果。断言要具体：`is_empty` 检查 0 行，`throws_ok` 检查 `42501`。

一个团队至少要三条测试：本人能读自己的行，别人读不到，写操作被拒。

## 17.21 PostgREST 怎么执行 policy

Supabase 的 REST 接口由 PostgREST 提供。它把 HTTP 请求翻译成 SQL，用请求头里的 JWT 决定角色。

`Authorization: Bearer <access_token>` 决定 `role` 和 `request.jwt.claims`。没有 token 时角色是 `anon`，有 token 时是 `authenticated`。`apikey` 头只决定能否访问这个项目，不决定行级权限。

一次 `GET /rest/v1/files?select=*` 实际执行的 SQL 大致是 `select * from files`，外面套上 PostgREST 生成的权限检查。RLS 的 policy 会自动追加成 `where` 条件。

所以 policy 写错，表现是“明明有数据，接口返回空数组”。SQL 执行成功了，只是被过滤成 0 行。这一点与报错不同，排查时要区分。

## 17.22 auth.jwt() 里有什么

policy 里能读到 JWT 的字段，通过 `auth.jwt()` 取。

常用字段五个。`sub` 是用户 id，最可靠。`email` 是邮箱，可以改，不要拿它做权限判断。`role` 固定是 `authenticated`。`aal` 是认证等级，`aal1` 或 `aal2`。`session_id` 标识这次会话。

`app_metadata` 和 `user_metadata` 也在里面。`app_metadata` 只能服务端写，适合放套餐等级这类不可自改的字段。`user_metadata` 用户可以自己改，不能用于授权。

policy 里取字段的写法是 `(select auth.jwt()->>'aal')`。注意 `->>` 返回文本，比较时要带引号。

## 17.23 anon 该有什么权限

`anon` 是未登录请求，多数业务表一律不给。少数内容表要放开读。

公开内容表需要读权限，比如落地页的定价、博客文章、公开的团队介绍页。这类表的 policy 条件是 `using (published = true)`，grant 只给 `select`。

```sql
-- 公开只读内容表
alter table public.posts enable row level security;
revoke all on table public.posts from anon, authenticated;
grant select on table public.posts to anon, authenticated;

create policy "posts_select_published" on public.posts
  for select
  to anon, authenticated
  using (published_at is not null and published_at <= now());
```

三个细节。`to anon, authenticated` 一行写两个角色，省一条 policy。时间条件用 `now()`，避免未来文章提前出现。不给 `insert`、`update`、`delete`，写操作只走后台。

## 17.24 多租户的三种隔离模型

租户隔离有三种做法，代价不同。

第一种是共享表加 `team_id` 列，用 RLS 过滤。teamstack 用这种。优点是迁移简单、跨团队统计方便；缺点是一条 policy 写错就泄露全部租户。

第二种是每个租户一个 schema。隔离更强，但迁移要在每个 schema 上跑一遍，连接池也要按 schema 切换。

第三种是每个租户一个数据库。隔离最强，运维成本最高，适合有强合规要求的客户。

选型的判断标准是数据敏感度和租户数量。几十个租户、普通业务数据，第一种够用；上千租户、医疗或金融数据，考虑第二种。

## 17.25 软删除与 RLS

`teams` 有 `deleted_at` 字段，删除是软删。所有读 policy 都要加 `deleted_at is null`。

漏加的表现是用户删了团队，列表里还在。问题出在 policy 没过滤，与缓存无关。

```sql
create policy "teams_select_member" on public.teams
  for select
  to authenticated
  using (deleted_at is null and public.is_team_member(id));
```

软删还有一个副作用：唯一约束。`slug` 上如果有唯一索引，软删之后同一个 slug 不能再创建。解决办法是把唯一索引改成部分索引：

```sql
create unique index teams_slug_active_idx on public.teams (slug) where deleted_at is null;
```

## 17.26 policy 的性能账

policy 每条都要执行，慢一点就乘以行数。三个优化点。

第一，用 `(select auth.uid())` 代替 `auth.uid()`。包一层之后，Postgres 把它当 initPlan，整条查询只算一次。

第二，辅助函数标 `stable`。标错成 `volatile` 会每行执行一次。

第三，别在 policy 里 join 大表。需要关联时先抽成函数，函数里只查关键列。

用 `explain (analyze, buffers)` 看实际执行计划。policy 的条件会出现在 filter 里，看看它是否每行都调用了一次函数，以及调用的次数。

## 17.27 审计日志的设计

`activity_logs` 记录“谁在什么时候做了什么”。字段不多，设计要点在 `metadata`。

`action` 用点号命名，`team.member_invited`、`subscription.canceled`。前缀是领域，方便按领域筛选。

`target_type` 和 `target_id` 指向被操作的对象。没有具体对象时留空。

`metadata` 是 jsonb，放变化的细节，比如 `{"from":"member","to":"owner"}`。不要在里面放密码、token、完整请求体。

写入只走应用层，policy 只给 `insert`。查询给 owner，member 看不到别人的操作记录。

## 17.28 Storage 的 policy

文件存在 Supabase Storage 里，它也有 RLS，policy 建在 `storage.objects` 表上。

权限判断和业务表一样，但路径要能反推出团队。常见做法是把 `team_id` 放在路径第一段：`{team_id}/{file_id}.pdf`。

取第一段的写法是 `(storage.foldername(name))[1]`。用它去比对 `team_members`。

```sql
-- 只允许团队成员读自己团队的目录
create policy "objects_select_team_member" on storage.objects
  for select
  to authenticated
  using (
    bucket_id = 'team-files'
    and public.is_team_member(((storage.foldername(name))[1])::uuid)
  );
```

**未验证**：`storage.foldername` 的行为以 Supabase 文档为准，这里没有在实例上跑过。

路径设计错了，policy 就没法写。上传时用文件名当路径，等于放弃隔离。

## 17.29 迁移与回滚

policy 也是代码，要进迁移文件，要有命名规范，要能重复执行。

命名用 `表_操作_对象`，例如 `files_select_member`、`files_delete_owner`。看名字就知道作用。

每条 policy 前面加 `drop policy if exists`，保证重复执行不报错：

```sql
drop policy if exists "files_select_member" on public.files;
create policy "files_select_member" on public.files ...
```

回滚靠迁移文件本身。不要手动在 Dashboard 里改 policy，改了之后迁移文件和线上不一致，下次迁移就冲突。

## 17.30 团队切换与 RLS 无关

用户可能属于多个团队，页面顶部有切换器。切换的结果存在 cookie 里，叫 `active_team`。

这个 cookie 不参与 RLS。RLS 只看“当前用户是否这一行的团队成员”，不看当前选中的是哪个团队。

后果是：用户切到 A 团队，但请求里手动带上 B 团队的 id，RLS 仍然放行，因为他对 B 团队也有权限。这是正确行为，只是应用层通常还要再判断一次“这个 id 在不在我的团队列表里”，避免越权访问不该出现的页面。

反过来说，如果只靠 `active_team` cookie 做过滤，攻击者改 cookie 就能看别人的数据。cookie 是用户可控的，不能当权限依据。

## 17.31 profiles 的可见范围

`profiles` 存邮箱、姓名、头像。哪些字段给谁看，要单独设计。

邮箱默认只给本人看。团队页要显示成员名字和头像，不需要邮箱。

实现用列级 grant 加视图。`authenticated` 只能 `select (id, full_name, avatar_url)`，邮箱列的读权限只给本人。

```sql
-- 邮箱只给本人
revoke select on table public.profiles from authenticated;
grant select (id, full_name, avatar_url) on table public.profiles to authenticated;
grant select (email) on table public.profiles to authenticated;
```

第二条 grant 仍然给了所有人读邮箱的权限。要真正限制，得用视图加 `security_invoker`，或者把邮箱放到单独的私有表。

多数产品的取舍是：邮箱放 `auth.users`，业务表不存。需要展示时由服务端查一次，返回给前端。

## 17.32 invitations 的约束放在哪

邀请表的防重与防提权，一部分在 policy，一部分在约束。

policy 负责“谁能插”：只有 owner 能插，且 `role` 必须是 `member`。

约束负责“不能重复”：同一个团队、同一个邮箱，只能有一条 pending。

```sql
create unique index invitations_pending_unique
  on public.invitations (team_id, lower(email))
  where status = 'pending';
```

这是一个部分唯一索引。`where` 子句让它只对 pending 生效，历史记录可以有多条。

`lower(email)` 解决大小写问题。`Owner@x.com` 和 `owner@x.com` 是同一个人，不加 `lower` 会产生两条邀请。

约束和 policy 的分工：policy 防恶意请求，约束防并发与逻辑错误。两者都要有。

## 17.33 jobs 表与队列

`jobs` 是任务队列表，存异步任务。它不给 `authenticated` 任何权限，只有后台任务能碰。

```sql
-- jobs：只给 service_role
alter table public.jobs enable row level security;
revoke all on table public.jobs from anon, authenticated;
grant all on table public.jobs to service_role;
```

没有 policy 的表配合收回 grant，效果是“谁都进不来”。这是有意为之：队列由后台进程用 service_role 操作。

取任务时用 `for update skip locked`，多个 worker 并发取任务不会重复：

```sql
update public.jobs
set status = 'running', attempts = attempts + 1
where id = (
  select id from public.jobs
  where status = 'queued' and run_at <= now()
  order by run_at
  limit 1
  for update skip locked
)
returning *;
```

失败次数到上限之后转 `dead`，不再重试。`last_error` 存最后一次的错误信息，排查时用。

## 17.34 团队删除与级联

团队软删之后，关联数据要处理。三种策略。

级联删除：直接删团队，关联表用 `on delete cascade` 一起删。数据不可恢复，合规场景常用。

保留数据：团队标记 `deleted_at`，数据留着。30 天后由定时任务清理。

归档：数据搬到归档表，主表清理。成本最高，只在有合规要求时做。

teamstack 用第二种。清理任务是一个 `security definer` 函数，按 `deleted_at` 加时间条件删除，`grant execute` 只给 `service_role`。

级联删除的风险是误删。删团队前要二次确认，并写审计。

## 17.35 物化视图与 RLS

物化视图存的是查询结果，不参与 RLS。用普通视图或物化视图暴露数据给前端，等于绕过 policy。

Supabase 的 Security Advisors 会列出这类对象。看到 `materialized view` 在 `public` schema 里就要检查。

如果确实需要物化视图做统计，把它放在不暴露的 schema，用一个 `security definer` 函数封装查询，函数里校验团队权限。

统计类查询通常按团队聚合，只返回数字，风险比明细数据小。但仍然要校验“这个团队是否属于你”，这一步不能省。

## 17.36 policy 写多复杂算过头

policy 里可以写子查询、`exists`、函数调用，写多了会变慢，也会难维护。

三个信号说明该拆了。第一，单条 policy 超过 10 行。第二，policy 里出现两个以上的 `exists`。第三，`explain` 显示 policy 条件是执行计划里最慢的部分。

拆分方式是把判断抽成函数，函数只查关键列，返回布尔值。函数标 `stable`，加索引。

另一个方向是降低 policy 数量。同一条命令上的多条 policy 是 OR，写三条不如写一条覆盖三种情况。

## 17.37 从零到一的落地顺序

按这个顺序做，每一步都能验证。

第一步，开 RLS 并收回 grant。此时所有表都不可访问，应用会报错，这是预期的。

第二步，按业务重要度依次给表加 policy。先 `teams`、`team_members`，再 `files`、`activity_logs`，最后到辅助表。

第三步，每加一张表就跑一次手动验证，确认 B 看不到 A。

第四步，补齐辅助函数和索引。

第五步，接 CI，跑 pgTAP 测试。

顺序反了会很难调：先写 policy 后开 RLS，中间状态看不出来；先写函数后建表，函数报错。

## 17.38 上线前的检查清单

十条，逐条勾。

1. 每张业务表 `relrowsecurity` 为 `t`。
2. 每张表对 `anon` 没有业务权限。
3. 每条 policy 都写了 `to authenticated`。
4. policy 条件里的列都有索引。
5. `service_role` 只在服务端出现。
6. 辅助函数都有 `set search_path = ''`。
7. 视图都带 `security_invoker = true`。
8. `pg_default_acl` 里没有意料外的行。
9. Security Advisors 没有红色告警。
10. 手动验证过“B 看不到 A”和“member 改不了账单”，两条都能复现。

## 17.39 policy 的调试日志

policy 不生效时，先确认 SQL 到底执行了什么。

临时打开语句日志：

```sql
alter database postgres set log_statement = 'all';
```

日志里能看到 PostgREST 生成的 SQL，以及 policy 追加的 `where` 条件。看完记得关掉，日志量很大。

另一个手段是 `explain`。`explain (verbose, costs off)` 的输出里，policy 条件会以 `Filter` 的形式出现。看看它是否每行都调用了一次函数。

这两个手段合起来，能定位 90% 的“policy 为什么没过滤”问题。

## 17.40 服务端组件用哪个客户端

服务端组件里查数据，必须用带用户会话的客户端，不能图省事用 admin 客户端。

带会话的客户端由 `src/lib/supabase/server.ts` 的 `createClient()` 创建，内部读 cookie，带上用户的 JWT。RLS 按这个身份过滤。

admin 客户端用 secret key，绕过 RLS。它在服务端组件里用，等于这一页所有查询都不受行级限制。一旦查询条件写错，就是全量泄漏。

规则简单：用户请求链路里只用 `createClient()`，`createAdminClient()` 只出现在后台任务、导出、清理这类代码里。

## 17.41 密钥的两种边界

Supabase 提供两个密钥，名字容易混。

publishable key 可以公开，它只用于标识项目。它不授予行级权限，权限由用户的 JWT 决定。所以它出现在浏览器里是正常设计。

secret key 相当于数据库管理员，绕过 RLS。它只能存在服务端，泄漏等于数据库失守。

早期版本里这两个叫 anon key 和 service_role key，行为一样。看到旧文档时按这个对应关系理解。

密钥轮换的窗口期通常是几分钟，轮换期间新旧都能用。轮换之后要重启部署，让新密钥生效。

## 17.42 角色变更什么时候生效

团队角色存在 `team_members.role` 里。改了之后，下一次查询立即生效，因为 policy 每次查表。

如果为了性能把角色放进 JWT（`app_metadata`），就有延迟。JWT 在有效期内不变，改了角色要等 token 刷新才生效。

两种做法的取舍：查表准确但有开销，放 JWT 快但有延迟。teamstack 选查表，因为团队规模小、查询有索引。

有个中间方案：把角色放 `app_metadata`，同时在敏感操作前强制刷新一次 token。复杂度不值当，除非性能是瓶颈。

## 17.43 policy 的测试用例设计

每张写操作的表，至少三个用例。

第一个，角色正确且资源属于自己：应该成功。

第二个，角色正确但资源属于别人：应该 0 行或报 `42501`。

第三个，角色不足：应该被拒。

再加一个边界：资源不存在。此时返回 0 行，前端要能区分“没有”和“没权限”。

用例用 pgTAP 写在 `supabase/tests/` 里，`supabase test db` 一次跑完。

## 17.44 代码评审时的检查点

新增一张表或一条 policy，评审时看五个地方。

第一，迁移文件里有没有 `enable row level security`。第二，有没有 `revoke` 和 `grant`。第三，policy 有没有 `to authenticated`。第四，policy 条件里用到的列有没有索引。第五，新表有没有对应的测试。

五条都是机械检查，但漏一条就是一个洞。可以写成脚本在 CI 里跑，扫迁移文件里的关键字，命中缺失就直接失败。

## 17.45 与后面几章的关系

这一章是权限的底座，后面几章都建在它上面。

第 18 章的邀请，写操作走 `accept_invitation` 事务函数，函数里用 `security definer` 绕过 RLS，自己能校验权限。邀请表的 policy 只允许 owner 插入。

第 19 章的第三方登录，登录成功后创建 `profiles` 行。这一步发生在认证回调里，用用户的会话写入，RLS 保证只能写自己的行。

第 20 章的 AAL2 门禁，最终落在 policy 上。`aal` 低于 `aal2` 时，敏感表的读操作被过滤。

第 21 章的用量统计，走 `service_role` 读全量数据，业务查询走用户会话。两种客户端分开用，不能混。

## 17.46 删账号时的级联

用户注销账号，要删 `auth.users` 里的行。`profiles.id` 引用它，外键加上 `on delete cascade` 之后，profile 行自动删除。

`team_members` 也要处理。用户是某个团队的唯一 owner 时，直接删会让团队没有 owner。正确做法是先转让或解散团队，再删账号。

实现写在函数里：检查所有 owner 身份，有则报错并提示用户先处理；没有则删除成员行和 profile。

`activity_logs` 里的 `actor_id` 不要级联删除。审计记录要留着，外键改成 `on delete set null`，或存 actor 的快照。

## 17.47 Realtime 也受 RLS 约束

Supabase Realtime 推送数据变更时，会按订阅用户的身份过滤。RLS 对它有约束作用。

但要注意两点。第一，`postgres_changes` 订阅需要表在 publication 里，加表时确认没有把敏感表加进去。第二，变更事件的 payload 可能包含整行数据，policy 允许读的行才会推。

**未验证**：Realtime 的 RLS 行为随版本变化，实际项目里建议只推送不敏感的字段，或者改成自定义广播。

## 17.48 policy 放错 schema

`public` 之外的 schema 里的表，policy 写法一样，但 Data API 默认访问不到。

`private` schema 不暴露，`storage`、`auth` 是 Supabase 自己的。业务表一律放 `public`，辅助函数放 `private`。

把业务表放进 `private` 再通过函数暴露，是一种加固手段，但会让所有查询都要经过函数，维护成本高。普通业务不需要。

检查有没有这种混放：`select schemaname, tablename from pg_tables where schemaname not in ('pg_catalog','information_schema');`，业务表应该都在 `public`。

## 17.49 policy 与团队规模

团队只有几个人时，policy 的开销可以忽略。团队上百人时，成员表变大，每条 policy 的子查询都要命中索引。

`team_members` 的主键是 `(team_id, user_id)`，按这两列查很快。`is_team_member(team_id)` 的查询是 `select 1 from team_members where team_id = $1 and user_id = auth.uid()`，正好用上主键。

如果 policy 里写的是 `exists (select 1 from team_members where user_id = auth.uid() and team_id = team_id)`，列顺序反了就用不上索引。写成函数，把列顺序固定下来。

团队规模大到几千人时，考虑把成员关系缓存进 JWT 的 `app_metadata`，或者用独立的授权服务。多数产品到不了这个量级。

## 17.50 检查点

六条，按顺序跑一遍，每条都有明确判据。

1. 用 B 的 token 请求 A 团队的文件列表，返回 `[]`。
2. 用 member 角色的 token 改 `subscriptions`，返回 `[]` 或 `new row violates row-level security policy`。
3. 跑 `select relname, relrowsecurity from pg_class ...`，业务表全是 `t`。
4. 跑 `pg_default_acl` 查询，没有行，或者只有预期内的行。
5. 在 SQL Editor 里 `set local role authenticated` 后查 `files`，看不到别的团队的行。
6. `grep -rn "SUPABASE_SECRET_KEY" src/`，只在 `src/lib/supabase/admin.ts` 里出现。

## 17.51 常见错误

**1. 建表后忘了开 RLS**

现象：匿名密钥能读到全部数据。原因：SQL Editor 建表默认不开 RLS。改法：执行 `alter table ... enable row level security`，再用 `pg_class.relrowsecurity` 确认。

2. policy 写了，但报 `42501 permission denied`

现象：查询报 `42501`。原因：缺表级 grant，或者 `anon` 角色没有权限。改法：`grant select on table ... to authenticated`。

3. 查询返回空数组，以为 policy 生效了

现象：返回 `[]`，没有报错。原因：policy 的 `using` 条件不成立，行被过滤。改法：确认 `auth.uid()` 的取值，用 `set local request.jwt.claims` 复现。

4. `42P17 infinite recursion`

现象：查询报 `infinite recursion detected in policy for relation ...`。原因：两张表的 policy 互相查。改法：抽 `security definer` 函数。

5. 函数里报 `relation "team_members" does not exist`

现象：函数执行时报表不存在。原因：`set search_path = ''` 之后必须用全限定名。改法：写 `public.team_members`。

6. `service_role` 泄漏到客户端

现象：浏览器 Network 里能看到 secret key。原因：变量名加了 `NEXT_PUBLIC_`，或者模块被客户端组件导入。改法：改名、加 `import "server-only"`、轮换密钥。
