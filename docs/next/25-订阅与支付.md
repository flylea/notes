# 第 25 章 订阅与支付

前四章的功能都在你的数据库里完成，这一章不一样：钱和订阅状态由 Stripe 管，你的系统只是跟着它同步。用户点升级，浏览器跳到 Stripe 的 Checkout 页面付款，付完之后 Stripe 通过 webhook 通知你，你再把 `subscriptions` 表写成对应状态。

这条链路有三个容易做错的地方：付款成功的页面回调不能当成“已订阅”的证据；webhook 会被重复投递；订阅状态的权威来源是 Stripe，并非你的数据库。

涉及五个概念：Checkout Session、Customer Portal、webhook 签名、事件去重、席位同步。

用到四张表。`subscriptions` 在第 8 章已定义，这一章新增 `stripe_events` 用于去重。团队和成员来自第 22 章，席位上限与第 23 章的存储配额共用一套 `plan` 字段。

前置条件：Stripe 测试模式账号、`stripe` CLI、SDK 版本 23.x。

订阅比文件上传更难，因为对面是一个你控制不了的系统。Stripe 什么时候发事件、发几次、按什么顺序发，你都决定不了。你的代码只能在“收到事件”这个动作上做好三件事：验明来源、挡住重复、以对方的状态为准。这三件事做对了，链路就有最终一致性；做错一件，就会出现“用户付了钱但没有权限”或者“取消了还在扣费”这类事故。

这一章的顺序是：先认得链路上的对象，再定数据模型与上限，然后从创建 Checkout 一路写到回调、去重、状态落库，最后处理席位、对账和重放。

## 25.1 链路上有哪几个对象

订阅功能在 Stripe 侧由四个对象支撑。

**Customer**：一个团队对应一个客户，存在 `subscriptions.stripe_customer_id`。客户可以没有订阅，先建客户再开 Checkout 可以减少重复。

**Price**：价格的标识，比如 `price_xxx`，代表“每月 20 美元”。测试模式和生产模式各有一套 price id，不能混用。

**Subscription**：订阅本身，有状态、有周期、有数量。`seats` 对应订阅里 `quantity` 字段。

**Event**：Stripe 每次状态变化都发一个事件，webhook 收到的是事件的 JSON 加签名。

对象之间存在引用关系：Session 属于某个 Customer，付款成功后生成 Subscription，Subscription 的条目引用 Price。事件是对这些对象变化的快照，并非命令。理解这一点，才能明白为什么“处理事件”等于“用快照覆盖本地”，并非“执行一个操作”。

测试模式与生产模式是两套独立的世界。两边的 Customer、Price、Subscription、事件都不共享，密钥也不共享。最容易犯的错是把测试的 price id 写进生产环境变量，症状是所有 Checkout 请求返回 `No such price`。

本地开发的顺序是：建产品与价格、配 webhook 转发、写 Checkout、写回调。生产的顺序一样，只是价格和 webhook 端点换一套。

事件对象长这样，字段只列关键的：

```json
{
  "id": "evt_1Qx...",
  "type": "customer.subscription.updated",
  "data": {
    "object": {
      "id": "sub_1Qx...",
      "status": "active",
      "customer": "cus_1Qx...",
      "metadata": { "team_id": "3f2a..." },
      "items": {
        "data": [
          { "id": "si_1Qx...", "quantity": 5, "current_period_end": 1790000000 }
        ]
      }
    }
  }
}
```

`metadata` 是你自己写进去的，`items.data[0]` 是数量与周期所在的位置，这两个位置在第 25.7 节会反复用到。

一个常见误区是把 Checkout 的成功跳转当成支付完成。`success_url` 只是浏览器被重定向回来的地址，用户手动改地址栏也能到达。真正的结论在 `checkout.session.completed` 事件里，或者在服务端主动查一次 session 状态。这一章以事件为准。

## 25.2 数据模型

`subscriptions` 表在第 8 章已经建好，字段如下：

```sql
-- supabase/migrations/20261115090000_init_schema.sql（节选）
create table public.subscriptions (
  id uuid primary key default gen_random_uuid(),
  team_id uuid not null unique references public.teams (id) on delete cascade,
  stripe_customer_id text not null unique,
  stripe_subscription_id text unique,
  status text not null default 'incomplete'
    check (status in ('trialing','active','past_due','canceled','incomplete','unpaid')),
  price_id text,
  seats int not null default 1 check (seats > 0),
  current_period_end timestamptz
);
```

几个设计点。

`team_id` 唯一，一个团队只有一条订阅记录。多订阅、按人头叠加这类复杂计费不在这一章的范围。

`status` 只有六个值。Stripe 的订阅状态有八个，多出来的两个在同步时折叠，25.7 会讲。

`seats` 存的是本地快照，真实数量以 Stripe 的 `quantity` 为准。本地这份是为了在列表和限额判断时少一次 API 调用。

`plan` 字段在 `teams` 表上，是冗余。它只能由 webhook 处理逻辑写，不能让用户表单直接改。这条规则要写在代码注释里，否则迟早有人从前端加一个“切换套餐”的下拉。

六个状态的含义要能对上界面文案。

`incomplete` 表示第一次付款还没成功，常见于 3DS 验证没走完，或者卡被拒。这个状态不给权限，页面提示“付款未完成，请重试”。

`trialing` 表示试用期，给权限。`active` 表示正常订阅，给权限。`past_due` 表示最近一次扣款失败，Stripe 还在重试，给宽限期权限。`canceled` 表示已取消，周期结束后不再续费。`unpaid` 表示多次扣款失败后放弃，停止服务。

界面只需要两句话：“你的订阅有效”与“订阅已失效，原因是……”。把六个状态直接翻译成六句话，用户看不懂，客服也背不下来。

订阅记录不存在时，团队按免费档处理。不要给每个团队预先插入一条 `canceled` 行，那样会让“有没有订阅”这个判断多一种状态。

## 25.3 定价与上限

定价写在代码里，和 Stripe 后台的 price 对应。

```ts
// src/lib/billing/plans.ts
export const PLANS = {
  free: {
    name: '免费',
    priceId: null,
    seatLimit: 3,
    storageLimitBytes: 5 * 1024 * 1024 * 1024,
  },
  pro: {
    name: 'Pro',
    priceId: process.env.STRIPE_PRICE_PRO!,
    seatLimit: 20,
    storageLimitBytes: 100 * 1024 * 1024 * 1024,
  },
} as const

export type PlanId = keyof typeof PLANS
```

席位上限和存储上限放在同一张配置里，因为它们是同一个商业决策的两面。升级卖的是“更多人加更多空间”，两处数字对不上会让用户觉得被坑。

单价 20 美元每月，按席位计费。三个人的团队每月 60 美元。年付价格是另一个 price id，逻辑相同。

试用期由 `subscription_data.trial_period_days` 设置，试用期间状态是 `trialing`，到期后 Stripe 自动扣款。试用不需要本地定时任务，状态变化会通过事件同步。给不给试用是产品决定，技术上只是多一个参数和一条状态。

按比例计费（proration）由 Stripe 处理，默认策略是立即生效并按剩余天数结算。举三个例子：

- 月中从 3 人加到 5 人，Stripe 收剩余天数的差价，本地 `seats` 同步到 5。
- 月中从 5 人减到 3 人，Stripe 生成抵扣额度，下个周期抵扣。
- 月中从月付切年付，Stripe 把剩余额度折成年付的一部分。

这些计算不需要在代码里重现，只要把 `quantity` 传对，剩下的看 Stripe 账单。

算一笔真实的账，确认定价能覆盖成本。Pro 每月 20 美元一个席位，20 个席位是 400 美元。对应的资源是 100GB 存储加峰值并发。按对象存储每 GB 每月几分钱算，100GB 不到 5 美元；数据库和计算按小团队估算几十美元。毛利够，才有空间处理退款和坏账。

免费档定 3 个席位、5GB 存储，并非随意写的。3 个人的团队刚好能体验邀请、角色、日志这些功能；5GB 够放几十张高清图或一批 PDF。超过这两个数，团队要么已经认真在用，要么在滥用，都该升级。

存储上限和席位上限一起升级，是因为它们服务于同一个使用场景。只给席位不给空间，用户传几张图就满了；只给空间不给席位，邀请第三个同事就卡住。两处数字要成对出现，升级文案也成对写。

## 25.4 创建 Checkout

升级按钮调一个 Server Action。它做三件事：确保客户存在、防止重复下单、创建 Checkout Session。

```ts
// src/lib/stripe.ts
import Stripe from 'stripe'

// 不传 apiVersion：让 SDK 用它内置的版本，避免和后台账户对不上。
export const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!, {
  typescript: true,
})
```

```ts
// src/lib/billing/checkout.ts
import 'server-only'
import { db } from '@/lib/db'
import { stripe } from '@/lib/stripe'
import { PLANS } from './plans'

export async function ensureCustomer(teamId: string, email: string) {
  const existing = await db
    .selectFrom('subscriptions')
    .select(['stripe_customer_id'])
    .where('team_id', '=', teamId)
    .executeTakeFirst()

  if (existing) return existing.stripe_customer_id

  const customer = await stripe.customers.create({
    email,
    metadata: { team_id: teamId },
  })

  try {
    await db
      .insertInto('subscriptions')
      .values({
        team_id: teamId,
        stripe_customer_id: customer.id,
        status: 'incomplete',
      })
      .execute()
  } catch (error) {
    // 并发时另一个请求已经插入：唯一约束冲突，重新读一次即可。
    if ((error as { code?: string }).code !== '23505') throw error
  }

  return customer.id
}

export async function startCheckout(input: {
  teamId: string
  email: string
  seats: number
  origin: string
}) {
  const existing = await db
    .selectFrom('subscriptions')
    .select(['status', 'stripe_subscription_id'])
    .where('team_id', '=', input.teamId)
    .executeTakeFirst()

  const live =
    existing?.stripe_subscription_id &&
    ['active', 'trialing', 'past_due'].includes(existing.status)
  if (live) return { error: '这个团队已经有订阅了' }

  const customerId = await ensureCustomer(input.teamId, input.email)

  const session = await stripe.checkout.sessions.create({
    mode: 'subscription',
    customer: customerId,
    line_items: [{ price: PLANS.pro.priceId!, quantity: input.seats }],
    success_url: `${input.origin}/settings/billing?checkout=success`,
    cancel_url: `${input.origin}/settings/billing?checkout=cancel`,
    client_reference_id: input.teamId,
    subscription_data: {
      metadata: { team_id: input.teamId },
    },
  })

  return { url: session.url }
}
```

`ensureCustomer` 里的 `23505` 处理是必须的。用户双击升级按钮，两个请求同时发现没有客户，同时创建，第二个插入必然撞唯一约束。捕获后重新读，不要直接报错。

`client_reference_id` 和 `subscription_data.metadata` 都带 `team_id`。前者方便在 Checkout 事件里找回团队，后者挂在订阅上，之后的 `customer.subscription.updated` 事件也能找到团队。两个都写，是因为不同事件里可用的字段不同。

`line_items` 的 `quantity` 用当前成员数。Checkout 完成后 Stripe 会按这个数量建订阅，之后成员变化再同步。

`session.url` 在 hosted 模式下一定存在，embedded 模式下要读 `client_secret` 在前端初始化。这里判空只是防御：如果未来改成 embedded，`redirect(session.url!)` 会拿 `null` 崩掉。打开 Checkout 的按钮要做 pending 状态，用户连点两次会创建两个 Session，虽然第二个会被“已有订阅”拦住，但第一次还没完成时数据库里并没有订阅，两个 Session 都能打开。

`existing.status` 也要参与判断。`incomplete` 的旧订阅不算“已有订阅”，允许重新发起；否则用户第一次 3DS 失败后就永远卡住。`canceled` 与 `unpaid` 同理，可以重新订阅，但要注意老的 `stripe_subscription_id` 会被新值覆盖，历史订阅在 Stripe 侧仍然存在。

不给 `idempotencyKey` 是有意的。用户双击时，我们希望第二个请求被“已有订阅”拦住，并非靠幂等键把两次请求合并。拦截发生在数据库查询这一步，比幂等键更早。

跳转用 `redirect(session.url)`。Session 的 URL 有效期是 24 小时，页面刷新不会重新创建，除非用户再点一次按钮。

Checkout 有三种形态：hosted、embedded、custom。hosted 是把用户送到 Stripe 托管的页面，代码最少，3DS、地址、税率都由 Stripe 处理。embedded 是把表单嵌进你的页面，视觉统一，但要处理加载状态与尺寸。custom 是用 Payment Element 自己拼界面，可定制程度最高，工作量也最大。

这一章选 hosted。订阅场景的表单字段固定，用户体验的差异不大，而 hosted 省掉了支付表单的兼容性和 PCI 相关工作量。等产品需要深度定制支付页时再换。

3DS 的处理不用写代码。Stripe 会在 Checkout 里弹出验证，验证完成后自动跳回。用户中途关掉页面时，订阅停在 `incomplete`，下一次进来重新点升级，会复用同一个客户，产生一条新的 Checkout Session，旧的那条过期作废。

试用期可以在这里加 `subscription_data.trial_period_days: 14`。试用期内 `status` 是 `trialing`，到期自动扣款。要注意试用期也需要绑卡，否则到期没有支付方式，订阅会直接进 `incomplete`。

## 25.5 Webhook：原始体与验签

Stripe 把所有事件 POST 到一个固定路由。这个路由有三个硬性要求：读原始请求体、验签、快速返回 2xx。

```ts
// src/app/api/stripe/webhook/route.ts
import { headers } from 'next/headers'
import { handleStripeEvent } from '@/lib/billing/webhook'
import { stripe } from '@/lib/stripe'

export async function POST(request: Request) {
  const body = await request.text()
  const signature = (await headers()).get('stripe-signature')

  if (!signature) {
    return new Response('missing signature', { status: 400 })
  }

  let event
  try {
    event = stripe.webhooks.constructEvent(
      body,
      signature,
      process.env.STRIPE_WEBHOOK_SECRET!,
    )
  } catch (error) {
    console.error('webhook 验签失败', error)
    return new Response('invalid signature', { status: 400 })
  }

  try {
    await handleStripeEvent(event)
  } catch (error) {
    // 返回 5xx，让 Stripe 重试。
    console.error('webhook 处理失败', event.id, error)
    return new Response('handler failed', { status: 500 })
  }

  return new Response('ok', { status: 200 })
}
```

`await request.text()` 是关键。不能用 `request.json()`，JSON 解析会重排空白和键顺序，字节变了签名就不匹配。验签用的是原始字节加 `Stripe-Signature` 头和 endpoint secret，任何重新序列化都会失败。

签名算法是 HMAC-SHA256，签的内容是 `timestamp.body`。Stripe 默认允许 5 分钟的时间偏差，超过就判失败。不要把这个窗口设成 0，服务器时钟稍微慢一点就会全部失败。

验签失败返回 400，不要返回 200。返回 200 等于告诉 Stripe“收到并处理了”，它不会重试，事件就丢了。

Stripe 对响应时间有要求，处理过慢会被判超时，然后重试。具体上限未在本机验证，稳妥的做法是把邮件、通知这类副作用放进队列，webhook 只做入库。加人、发信、写日志都放到事件处理之后异步做。

处理逻辑失败返回 5xx，让 Stripe 重试。线上最多重试三天，sandbox 重试三次。这也意味着处理逻辑必须幂等，25.6 去重就是为此。

本地没有公网地址，Stripe 无法直接访问 `localhost`。`stripe listen` 的原理是让你的机器主动连到 Stripe，建一条反向通道，事件从 Stripe 推给 CLI，CLI 再转发给本地端口。所以它能在没有公网 IP 的情况下工作，也不需要内网穿透。

验签失败的排查顺序是固定的。先看 `stripe-signature` 头在不在，代理或框架可能把它丢掉。再看 endpoint secret 是否属于当前这个端点，`stripe listen` 每次重启如果重新生成 secret，环境变量要同步更新。最后看请求体有没有被中间件处理过，任何读取并重新序列化 body 的中间件都会让签名失效。

这里不用 Server Action：Server Action 走的是 Next.js 自己的协议，请求体会被框架解析，拿不到原始字节。而且 webhook 是服务器对服务器，不需要 CSRF 保护，用 Route Handler 更合适。

事件订阅四个就够：`checkout.session.completed`、`customer.subscription.created`、`customer.subscription.updated`、`customer.subscription.deleted`。前两个覆盖“第一次付款成功”，第三个覆盖续费、数量变化、状态变化，第四个覆盖取消与到期。

不要在 `checkout.session.completed` 里直接写 `active`。这个事件的 session 对象里有 `subscription` id，但订阅当时可能还是 `incomplete`，比如 3DS 还没走完。正确做法是拿 id 再查一次订阅，用查到的状态写库。

2xx 要尽快返回。官方建议在几秒内响应，复杂逻辑放到异步任务里。这一章的处理器只做数据库写入，通常在几十毫秒内完成；如果以后加了发邮件、写审计之类的动作，改成入队，让 webhook 只负责落库。

路由要排除在登录校验之外。Stripe 不会带你的会话 cookie，中间件里要把 `/api/stripe/webhook` 加进白名单，验签本身就是它的认证。

## 25.6 事件去重

Stripe 的投递是“至少一次”。网络抖动、你的服务超时、部署重启，任何一次都可能让同一个事件到达两次。处理逻辑必须能承受重复。

只靠“先查有没有处理过”不够，两个请求可能同时查到“没有”。要让它变成一次原子操作。

```sql
-- supabase/migrations/20261122100000_billing.sql
create table public.stripe_events (
  id text primary key,
  type text not null,
  processed_at timestamptz not null default now()
);

alter table public.stripe_events enable row level security;
revoke all on public.stripe_events from anon, authenticated;

create index stripe_events_processed_idx
  on public.stripe_events (processed_at);
```

`id` 直接用 Stripe 事件的 id，比如 `evt_xxx`。主键冲突天然去重。

处理时把“记录事件”和“更新订阅”放进同一个事务：

```ts
// src/lib/billing/webhook.ts
import 'server-only'
import type Stripe from 'stripe'
import { db } from '@/lib/db'
import { applySubscription } from './subscription'

export async function handleStripeEvent(event: Stripe.Event) {
  switch (event.type) {
    case 'checkout.session.completed':
    case 'customer.subscription.created':
    case 'customer.subscription.updated':
    case 'customer.subscription.deleted':
      break
    default:
      return
  }

  await db.transaction().execute(async (trx) => {
    const inserted = await trx
      .insertInto('stripe_events')
      .values({ id: event.id, type: event.type })
      .onConflict((oc) => oc.column('id').doNothing())
      .returning('id')
      .executeTakeFirst()

    // 没插进去说明这个事件已经处理过。
    if (!inserted) return

    await applySubscription(trx, event)
  })
}
```

`onConflict doNothing` 加 `returning` 是这套去重的核心。第一个请求插进去并拿到返回行，第二个请求插不进去、返回空，直接退出。整个过程在一个事务里，订阅更新失败会连事件记录一起回滚，Stripe 重试时还能重新处理。

不先 `select` 再 `insert`：两个请求可能同时 select 到空，然后都尝试处理。用唯一约束让数据库裁决，比应用层判断可靠。

事件顺序不保证。`customer.subscription.updated` 可能比 `created` 先到，也可能一个旧事件在新事件之后到达。应对办法是让处理逻辑以事件里的对象为准，整体覆盖本地状态，并非做增量计算。`applySubscription` 直接把 Stripe 返回的订阅写成本地行，顺序错了也只是暂时不一致，最终一致。

去重的前提是事件 id 全局唯一。Stripe 的事件 id 以 `evt_` 开头，重试同一个事件时 id 不变，这是它能当主键的原因。不要把 `created` 时间戳或对象 id 当去重键，同一个订阅一天内可能产生多个事件。

清理去重表要小心。删掉一条记录，等于允许这个事件再次生效。30 天是折中：Stripe 的重试窗口远小于 30 天，人工重放也通常发生在几天内。清理语句要写在定时任务里，不要手动执行，避免误删刚处理完的事件。

去重表还有一个作用：排查。用户说“我付了钱但没有升级”，第一件事是查这个事件 id 在不在表里。在，说明收到过，问题在状态写入；不在，说明投递失败，去找 Stripe 的重试记录。没有这张表，你只能靠日志翻，而日志通常只保留几天。

`stripe_events` 会一直增长，每天几千条。定时任务删掉 30 天前的记录就够了，重放窗口远小于这个时间。

## 25.7 把订阅状态写进表

```ts
// src/lib/billing/subscription.ts
import 'server-only'
import type { Transaction } from 'kysely'
import type Stripe from 'stripe'
import type { Database } from '@/lib/db'

const STATUS_MAP: Record<string, string> = {
  incomplete: 'incomplete',
  incomplete_expired: 'canceled',
  trialing: 'trialing',
  active: 'active',
  past_due: 'past_due',
  canceled: 'canceled',
  unpaid: 'unpaid',
  paused: 'past_due',
}

export async function applySubscription(
  trx: Transaction<Database>,
  event: Stripe.Event,
) {
  let subscription: Stripe.Subscription

  if (event.type === 'checkout.session.completed') {
    const session = event.data.object as Stripe.Checkout.Session
    if (!session.subscription) return
    subscription = await stripe.subscriptions.retrieve(
      session.subscription as string,
    )
  } else {
    subscription = event.data.object as Stripe.Subscription
  }

  const item = subscription.items.data[0]
  const teamId =
    subscription.metadata.team_id ??
    (event.data.object as { client_reference_id?: string }).client_reference_id

  if (!teamId) return

  const status = STATUS_MAP[subscription.status] ?? 'past_due'

  await trx
    .insertInto('subscriptions')
    .values({
      team_id: teamId,
      stripe_customer_id: subscription.customer as string,
      stripe_subscription_id: subscription.id,
      status,
      price_id: item?.price.id ?? null,
      seats: item?.quantity ?? 1,
      current_period_end: item ? new Date(item.current_period_end * 1000) : null,
    })
    .onConflict((oc) =>
      oc.column('team_id').doUpdateSet({
        stripe_subscription_id: subscription.id,
        status,
        price_id: item?.price.id ?? null,
        seats: item?.quantity ?? 1,
        current_period_end: item
          ? new Date(item.current_period_end * 1000)
          : null,
      }),
    )
    .execute()
}
```

三个细节。

`current_period_end` 在订阅的 `items.data[0]` 上，不在订阅对象顶层。这是 Stripe API 近期版本的变化，从顶层读会得到 `undefined`，然后你的“到期时间”永远是空的。

状态映射把八个值折成六个。`incomplete_expired` 表示第一次付款就失败并过期，按 `canceled` 处理；`paused` 是暂停计费，按 `past_due` 处理，都不给 Pro 权限。`?? 'past_due'` 是兜底：Stripe 以后加了新状态，默认按“没有付费”处理，不能默认按 `active`。

事件里没带 `team_id` 时用 `client_reference_id` 兜底。两个字段只要有一个在，就能定位团队。

订阅取消与到期要分开看。`customer.subscription.deleted` 在取消生效时发来，此时 `status` 是 `canceled`，`plan` 要降回免费。用户点“取消订阅”但选择周期结束生效时，会先收到一个 `updated` 事件，`cancel_at_period_end` 为 `true`，状态仍是 `active`。这两种情况在界面上文案不同，在数据上只差一个布尔值。

`cancel_at_period_end` 在订阅对象顶层，不在 `items` 里。它不进本地表，需要时现查，或者从事件里读。不要为了一个布尔值加一列，它和 `status` 的组合会让人反复困惑。

团队套餐的 `plan` 字段也要跟着改。在同一事务里更新 `teams.plan`，但只改这一列，别让 webhook 碰 `deleted_at` 之类的字段。

权限判断单独写一个函数：

```ts
// src/lib/billing/entitlement.ts
export const PRO_STATUSES = ['active', 'trialing', 'past_due'] as const

export function isProEntitled(status: string) {
  return (PRO_STATUSES as readonly string[]).includes(status)
}
```

`past_due` 给宽限期。用户卡过期、银行拒付时，Stripe 会持续重试扣款，这期间断掉服务体验很差。宽限期一般是 3 到 7 天，由 Stripe 的催款设置决定，本地跟着 `past_due` 走就行。

## 25.8 Customer Portal 动态配置

让用户自己改支付方式、取消订阅，不用自己写页面。Stripe 的 Customer Portal 提供现成界面，默认配置是后台手动设的，多档价格需要动态配置。

```ts
// src/lib/billing/portal.ts
import 'server-only'
import { db } from '@/lib/db'
import { stripe } from '@/lib/stripe'
import { PLANS } from './plans'

export async function createPortalSession(teamId: string, returnUrl: string) {
  const sub = await db
    .selectFrom('subscriptions')
    .select(['stripe_customer_id'])
    .where('team_id', '=', teamId)
    .executeTakeFirst()

  if (!sub) return { error: '这个团队还没有客户记录' }

  const configuration = await stripe.billingPortal.configurations.create({
    business_profile: { headline: '管理你的订阅' },
    features: {
      subscription_update: {
        enabled: true,
        default_allowed_updates: ['price', 'quantity'],
        proration_behavior: 'create_prorations',
        products: [
          {
            product: process.env.STRIPE_PRODUCT_PRO!,
            prices: [PLANS.pro.priceId!],
          },
        ],
      },
      subscription_cancel: {
        enabled: true,
        mode: 'at_period_end',
        cancellation_reason: {
          enabled: true,
          options: ['too_expensive', 'missing_features', 'switched_service', 'other'],
        },
      },
      payment_method_update: { enabled: true },
      invoice_history: { enabled: true },
    },
  })

  const session = await stripe.billingPortal.sessions.create({
    customer: sub.stripe_customer_id,
    return_url: returnUrl,
    configuration: configuration.id,
  })

  return { url: session.url }
}
```

只列一档价格。`products` 数组里只放 Pro，用户能改数量，不能改到别的产品。以后加团队档，在这里追加，不要开放自由选择。

`mode: 'at_period_end'` 让取消在当前周期结束时生效，用户付过的钱不白花。立即取消会产生退款问题，25.11 明确不做退款。

Portal 里能做的事由动态配置决定。取消、改支付方式、看发票是默认开着的；改套餐要显式列出产品与价格，否则用户看不到“升级到年付”这类选项。升级到年付需要一个年付的 price，加到 `prices` 数组里，`default_allowed_updates` 保持 `price` 和 `quantity`。

税额不在 Portal 里配。Stripe Tax 是单独的能力，按地址和产品类型计算，涉及注册国家和税率表。这一章不接，25.11 会说明。

配置对象每次调用都新建一个，Stripe 会累积配置记录。量不大没问题；调用频繁时应该创建一次、把 id 存进环境变量或数据库，再用 `stripe.billingPortal.configurations.update` 改。

这个接口只允许 owner 调用。成员看到的是“请让团队所有者操作”。权限检查用第 22 章的 `requireTeam()` 返回的角色。

## 25.9 席位与上限联动

席位来自成员数，邀请时要检查上限。

```ts
// src/lib/billing/seats.ts
import { db } from '@/lib/db'
import { PLANS, type PlanId } from './plans'

export async function assertSeatAvailable(teamId: string, plan: PlanId) {
  const members = await db
    .selectFrom('team_members')
    .select((eb) => eb.fn.countAll<number>().as('count'))
    .where('team_id', '=', teamId)
    .executeTakeFirst()

  const pending = await db
    .selectFrom('invitations')
    .select((eb) => eb.fn.countAll<number>().as('count'))
    .where('team_id', '=', teamId)
    .where('status', '=', 'pending')
    .where('expires_at', '>', new Date())
    .executeTakeFirst()

  const used = Number(members?.count ?? 0) + Number(pending?.count ?? 0)
  return used < PLANS[plan].seatLimit
}
```

待接受的邀请也要占位。只算成员，用户可以先发十个邀请、全部接受时才发现超了，那时候拒绝谁都很麻烦。

成员变化后同步 Stripe 的数量：

```ts
// src/lib/billing/seats.ts（追加）
import { stripe } from '@/lib/stripe'

export async function syncSeatQuantity(teamId: string) {
  const sub = await db
    .selectFrom('subscriptions')
    .select(['stripe_subscription_id', 'status', 'seats'])
    .where('team_id', '=', teamId)
    .executeTakeFirst()

  if (!sub?.stripe_subscription_id) return
  if (!['active', 'trialing', 'past_due'].includes(sub.status)) return

  const members = await db
    .selectFrom('team_members')
    .select((eb) => eb.fn.countAll<number>().as('count'))
    .where('team_id', '=', teamId)
    .executeTakeFirst()

  const quantity = Math.max(1, Number(members?.count ?? 1))

  const current = await stripe.subscriptions.retrieve(sub.stripe_subscription_id)
  const item = current.items.data[0]
  if (!item || item.quantity === quantity) return

  await stripe.subscriptionItems.update(item.id, { quantity })
}
```

同步失败要有兜底。`stripe.subscriptionItems.update` 可能因为网络、限流、订阅已取消而失败。失败时不要静默吞掉，写一条 `activity_logs` 记录，让对账脚本和人工都能看到。用户下次加人时会再次触发同步，多数临时故障会自愈。

先拉一次订阅，读 `items.data[0].id` 和当前 `quantity`。数量没变就不调更新接口，省一次调用，也避免无意义的账单记录。

只改 Stripe，不改本地 `seats`。本地会在 `customer.subscription.updated` 事件到达时更新。这样只有一个写入方向，不会出现“本地改了、Stripe 没改”的分叉。

先权限后计费：加人的顺序是先检查席位、加入团队、再同步数量。如果先同步再检查，超员的成员会先被写进数据库。同步失败时记一条活动日志，等对账脚本发现。

减员与降级要分别处理。成员离开时，先 `syncSeatQuantity` 再改本地，因为 Stripe 的 `quantity` 是计费依据，晚改一天就多收一天的钱。降级到免费档不经过 Portal，而是取消订阅，周期结束后 `plan` 回到 `free`；这时如果成员数超过 3，邀请接口会拦住新增，已有人不受影响，给用户留出移除成员的时间。

邀请被撤销或过期时，占位自动释放。`assertSeatAvailable` 只统计 `pending` 且未过期的邀请，所以不需要额外的清理动作。

并发仍然有窗口：两个人同时被邀请，都通过检查，最后多一个。严格要锁团队行，`select ... from teams where id = $1 for update`。这一版接受偶发超员，超出的部分 Stripe 按实际数量计费，用户不会被多收。

降级比升级麻烦。20 人团队降到免费档，席位上限变成 3，多出来的 17 人只有三个选项：立刻踢人、只读、延后到周期结束。产品上通常选第三个，代码上要做的是降级前检查成员数，超出时提示先移除成员，并非先改套餐再报错。

## 25.10 对账脚本

Webhook 会丢。部署重启、隧道断开、签名密钥配错，任何一次都可能让本地状态落后。写一个只读脚本定期比对。

```js
// scripts/reconcile-billing.mjs
// 用法：node --env-file=.env.local scripts/reconcile-billing.mjs
import { Pool } from 'pg'
import Stripe from 'stripe'

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY)
const pool = new Pool({ connectionString: process.env.DATABASE_URL })

const { rows } = await pool.query(
  `select team_id, stripe_subscription_id, status, seats, current_period_end
   from public.subscriptions
   where stripe_subscription_id is not null`,
)

let drift = 0
for (const row of rows) {
  const sub = await stripe.subscriptions.retrieve(row.stripe_subscription_id, {
    expand: ['items'],
  })
  const item = sub.items.data[0]
  const remoteSeats = item?.quantity ?? null
  const remoteStatus = sub.status

  if (remoteSeats !== row.seats || remoteStatus !== row.status) {
    drift += 1
    console.log(
      `[drift] team=${row.team_id} seats ${row.seats}->${remoteSeats} status ${row.status}->${remoteStatus}`,
    )
  }
}

console.log(`扫描 ${rows.length} 行，发现 ${drift} 处漂移`)
await pool.end()
```

输出类似：

```text
[drift] team=3f2a... seats 3->5 status active->past_due
扫描 128 行，发现 1 处漂移
```

三类差异的处理方式不同。席位差：Stripe 是权威，本地跟着改。状态差：以 Stripe 为准，但要先确认事件是否真的丢了，用 Dashboard 的事件日志查。`current_period_end` 差：重新拉一次订阅覆盖，这类偏差最常见，原因是本地没收到续费事件。

还有一个反向检查：本地有订阅、Stripe 侧已经不存在。这通常是切换了模式，或者客户被删。脚本会对 `retrieve` 抛 `resource_missing`，把它单独归类，不要和“状态不一致”混在一起。

脚本只读，不自动写。自动修会在事件丢失和大范围配置错误之间分不清，人工看一眼再决定。

对账的结果要能告警。漂移数量大于 0 就值得看一眼，连续两周增长说明 webhook 有系统性问题，并非偶发丢包。最简单的告警是把脚本接到定时任务里，输出非空时发一条邮件，第 26 章会用到同样的通知通道。

生产上每周跑一次就够，跑之前确认用的是同一套模式（测试或生产）的密钥。把测试密钥对生产数据跑，所有 `stripe_subscription_id` 都会报 `resource_missing`。

## 25.11 重放与人工修复

事件丢了要重放。Stripe Dashboard 的事件详情页有 Resend 按钮，也可以命令行：

```bash
stripe events resend evt_xxx
```

重放同一个事件，去重表会拦住。要先删掉 `stripe_events` 里那条记录，再重放：

```sql
delete from public.stripe_events where id = 'evt_xxx';
```

只重放四类事件：`checkout.session.completed`、`customer.subscription.created`、`customer.subscription.updated`、`customer.subscription.deleted`。其他类型即使重放也不会被处理。

重放有三个坑。一是去重表会拦住，必须先删记录；二是事件里的对象可能已经又变了，重放旧事件会把状态写回去，所以重放前先 `retrieve` 一次确认当前状态；三是同一事件的多个副本可能同时到达，去重表能挡住，但删记录这步要单独做一次。

批量修复用拉取式：遍历 `subscriptions` 表，对每一条调 `retrieve` 再覆盖。这比逐个重放历史事件快，也不会受去重表影响。

明确不做的功能：退款、税额计算、中国区发票。退款走 Stripe Dashboard 人工处理，退款后订阅状态变化会通过事件同步回来。税额依赖地址和税率表，接入成本远高于这个项目的目的，测试模式下也不产生真实税务。发票同理，需要额外的开票服务。

把“不做”写进文档比藏在代码里好。用户会问，客服要知道怎么答。

退款为什么不做：测试模式下退款没有真实资金流动，做了也验不出关键路径；生产环境的退款涉及金额计算、审批、对账，属于财务系统。把入口留在 Stripe Dashboard，让财务按流程处理，代码只同步状态变化。

税额为什么不做：税率取决于客户地址、产品类型、注册国家。Stripe Tax 能算，但要先配置税务注册和产品税码。这个项目不涉及真实报税，接进来只会多一套配置错误。真要做时，在 Checkout 里打开 `automatic_tax`，事件里会带税额，本地再加一列存。

发票同理。Stripe 能开英文发票，中国区的增值税发票需要另外的服务商。两者不要混进订阅逻辑：订阅负责状态与金额，票据是下游。

订阅取消有两种时机，Portal 只开放周期结束生效。立即生效涉及按比例退款，流程是调 `stripe.subscriptions.cancel`、算已用天数、人工在 Dashboard 退款。不要写自动退款，金额规则写错一次，纠正成本比人工高。

## 25.12 本地联调

本地起一个转发，把 Stripe 的事件送到 `localhost`：

```bash
stripe listen --forward-to localhost:3000/api/stripe/webhook
```

终端会打印 `whsec_xxx`，把它填进 `.env.local` 的 `STRIPE_WEBHOOK_SECRET`。重启开发服务器后，监听进程重新连上，secret 不变。

记得让监听进程和开发服务器同时运行。关掉终端里的 `stripe listen`，事件就停了，页面上的“升级成功”仍然会显示，因为跳转是浏览器行为，和事件无关。这正是“成功页不能当证据”的现场演示。

测试卡：

- `4242 4242 4242 4242`：成功。
- `4000 0025 0000 3155`：需要 3D Secure 验证。
- `4000 0000 0000 9995`：余额不足，订阅进入 `incomplete`。
- `4000 0000 0000 0341`：附加卡时失败。

六个要手动验的场景：正常升级、3DS 验证、拒卡、取消订阅、加人触发数量更新、重放事件。每个场景都去看一眼 `subscriptions` 表和 Stripe Dashboard。

`stripe trigger customer.subscription.updated` 可以造事件，但它生成的对象没有你的 `metadata.team_id`，处理逻辑会直接返回。用它测验签和去重可以，测业务状态要用真实操作。

测试时钟（test clocks）能模拟“过了一个月”，未在本机验证过，行为以 Stripe 文档为准。需要测续费、逾期、自动取消时再用。

联调阶段别用真实银行卡。测试模式的卡号不会产生真实扣款，生产模式的第一笔要用可退款的金额试。

上线检查清单有五项。环境变量配齐 `STRIPE_SECRET_KEY`、`STRIPE_WEBHOOK_SECRET`、`STRIPE_PRICE_PRO`、`STRIPE_PRODUCT_PRO`。Dashboard 里创建生产 webhook 端点，勾四个事件，复制签名密钥。中间件白名单放行 `/api/stripe/webhook`。价格在产品里配置正确（月付与年付各一个）。用测试卡在生产模式跑一遍 3DS，确认状态落库。

回滚策略也要想好。webhook 处理出问题时，最安全的动作是让接口返回 5xx，Stripe 会在三天内持续重试，期间修复代码、重新部署，事件不会丢。最危险的动作是返回 200 但没写库，等于主动丢弃事件。签名密钥和本地不同，环境变量分开配。

## 25.13 边界与失败模式

**事件丢失**。webhook 端点短暂不可用、部署期间重启、隧道断开，都会导致事件没送到。Stripe 会重试，但如果重试窗口也用完了，就只能靠对账脚本发现。对账脚本是最后一道网，并非可选项。跑得勤，比写得巧更重要。

**事件乱序**。Stripe 不保证顺序。`updated` 可能先于 `created` 到达，`deleted` 可能先于最后一次 `updated`。处理逻辑必须整体覆盖，不能做“在现有状态上加一”的增量计算。`applySubscription` 每次都用事件里的完整对象写库，顺序错了也只是短暂不一致。

**重复写入与并发**。两个 worker 同时处理同一个事件，去重表挡住第二个。但如果两个事件指向同一个团队，比如续费和数量变化同时到，数据库行锁会让它们串行，最后写入的那个生效。这里依赖的是“以 Stripe 为准”，并非“按时间戳取最新”。

**客户与团队对不上**。一个团队换了所有者、团队被删除，`subscriptions` 行还在。删除团队时应该级联删除订阅记录，或者至少标记取消。Stripe 侧的订阅不会因为你删了数据库行而自动取消，需要显式调 `stripe.subscriptions.cancel`，否则用户继续被扣费。

**价格变更**。Stripe 的 price 是不可变的，改价要建新 price，再让用户切过去。老订阅继续用老 price，直到用户主动切换或你批量迁移。不要在代码里写死金额，只认 price id。

Webhook 与 Server Action 的鉴权差异。webhook 没有会话，不能调 `requireUser()`。它靠签名认证，处理逻辑里只信事件内容。把带会话检查的函数复用到 webhook 里，会在生产环境报“未登录”，但本地用 curl 测不出来。

争议与拒付（chargeback）。用户找银行发起拒付时，Stripe 会发 `charge.dispute.created`，钱被冻结，可能还要交处理费。这一章不处理争议，上线后要人工跟进，并在产品里记录。订阅状态不一定会立刻变化，直到争议结果出来。

**多币种与税务**。Stripe 支持多币种定价，每个币种一个 price。本地只认 price id，所以代码不用改，但报表要对得上。税务不接，意味着价格里不含税，面向企业客户时要在合同里写清楚。

**成员被移除后的订阅残留**。团队降级或取消订阅后，成员可能还看到旧的“Pro”标签。标签要由 `isProEntitled(status)` 实时算，不要在成员表上存一份布尔值。

**本地与生产的两套密钥**。测试密钥、测试 price、测试 webhook secret 是一套；生产是另一套。混用的表现是 `No such price` 或者所有事件验签失败。环境变量分文件管理，不要在一个 `.env` 里同时放两套并靠注释切换。

## 25.14 检查点

1. 同一个事件用 `stripe events resend` 发两次：`subscriptions` 只有一行，`stripe_events` 只有一条记录，第二次的响应是 200 但没有任何写入。
2. 免费团队已有 3 人时再发邀请：提示席位已满，`invitations` 表没有新行；把它改到 Pro 后重试成功。
3. 手动把 `subscriptions.status` 改成 `active`，再触发一次 `customer.subscription.updated`：状态被事件里的真实值覆盖，说明本地写入方向只有一个。

4. 打开 Customer Portal：只能看到当前这一档价格，切到另一档会被拒绝；取消订阅的选项是“在当前周期结束时取消”。
5. 把 `STRIPE_WEBHOOK_SECRET` 改错一位再发事件：接口返回 400，日志里有 `No signatures found matching the expected signature`，`stripe_events` 没有新行。
## 25.15 常见错误

`StripeSignatureVerificationError: No signatures found matching the expected signature for payload`

验签失败。三个常见原因：用了 `request.json()` 并非 `request.text()`；用了另一个 endpoint 的 secret；本地用 `stripe listen` 打印的 secret，但环境里填的是 Dashboard 的。解法：确认拿到的是原始字节，secret 和监听进程输出一致。

`StripeInvalidRequestError: No such price: 'price_xxx'`

price id 属于另一套模式。测试密钥配了生产的 price，或者反过来。解法：测试模式的价格在 Dashboard 切换到“测试模式”后再复制。

`TypeError: Cannot read properties of undefined (reading 'current_period_end')`

从订阅对象顶层读周期字段。这个字段在 `subscription.items.data[0]` 上。解法：用 `items.data[0].current_period_end`，并判空。

`Error: Stripe: Argument "payload" must be a string`

`constructEvent` 第一个参数传了对象。它要原始字符串。解法：`await request.text()` 的结果直接传进去，不要 parse。

`new row violates check constraint "subscriptions_status_check"`

写入了一个表里没有的状态。Stripe 的状态集合和本地不一致，比如 `paused`。解法：在 `STATUS_MAP` 里折叠，保持本地只有六个值。

`NEXT_REDIRECT`（出现在 webhook 日志里）

webhook 路由里调用了会 `redirect` 的函数，或者复用了带鉴权的工具函数。解法：webhook 路由只用纯数据函数，不碰 `redirect()`、`notFound()`，不依赖会话。

## 25.16 这一章在做什么

这一章把订阅状态从 Stripe 同步到本地，只有一个写入方向：事件到达，去重，覆盖本地行。

关键决定有五个。付款结果以 webhook 为准，成功跳转不算证据。原始请求体验签，任何 JSON 解析都会让签名失败。事件 id 做唯一键，同事务插入实现原子去重。`current_period_end` 从 `items.data[0]` 读。席位数量以 Stripe 的 `quantity` 为准，本地只存快照。

明确不做的是退款、税额和发票。这些功能要么人工处理，要么依赖外部服务，接入成本和这一章的目标不成比例。

下一章处理与支付相关的另一条链路：邮件通知。邀请、付款成功、订阅即将到期，这些通知不能卡在用户请求里发，需要一个任务队列来保证“最终会发出去”。

第 26 章解释为什么 queued 等于“接受它可能延迟”、指数退避解决什么问题、重试多少次算死信、发件人域名怎样配置才算对。

回过头看，这一章真正难的地方不在调 API，而是承认两件事：你不能控制事件什么时候到，也不能假设它只到一次。所有设计都围绕这两个事实展开。把状态判断放在服务端、把写入收敛到一个函数、把重复处理挡在事务里，剩下的问题交给对账脚本定期检查。
