# 第 9 章 迁移与连接池

这一章讲两件常被归到「运维」名下的东西：数据库结构怎么进仓库，应用怎么连数据库。前者决定别人拉下代码能不能得到同一个库，后者决定线上流量涨十倍时数据库会不会被连接挤死。

需要它的原因很直接。结构只存在于某台电脑上的项目，第二个人加入就会白屏，报 `relation "profiles" does not exist`。连接在每个请求里新建的项目，第一次扩容就会收到 `sorry, too many clients already`。两个故障的根因都一样：把本该是代码的东西留成了手动操作。

这一章涉及四个概念：迁移文件的执行与回滚纪律、幂等种子、池化地址与直连地址的区别、模块级连接池单例。前两个管结构，后两个管连接。

基线：Supabase 本地默认端口 54322（直连）与 54321（HTTP API），CLI 版本随项目。本机没有安装 Supabase CLI，凡是依赖 `supabase` 命令的输出都标「未验证」，需要你在自己的环境跑一次核对。

## 9.1 结构属于代码：三种改库方式

改数据库只有三种方式，区别在于改动对谁可见。

第一种是在 Dashboard 的 Table Editor 里点鼠标。加一列、改一个默认值、建一条策略，都能点出来。改动只存在于当前这个库，同事的库、CI 的库、线上库都不会有。它适合临时排查，不适合留下任何需要复现的东西。

第二种是 `supabase db push`，把本地库结构直接推到远程。命令能跑通，问题在于推上去的内容没人说得清：本地可能积累了几周的手动改动，一次 push 全带上去，代码评审里看不到任何一行。

第三种是把 SQL 写成文件放进 `supabase/migrations/`，由所有人和 CI 一起执行。判断标准只有一条：别人 clone 仓库、跑一条命令，能不能得到一模一样的结构。能得到才叫迁移，得不到就是私货。

迁移文件按文件名的时间戳顺序执行。`supabase db reset` 的动作是删库、从头重放每个迁移、最后执行 `supabase/seed.sql`。第 8 章那份 `init_schema` 就是第一个文件。

日常用到的命令有五个，输出标「未验证」：

- `supabase migration new add_team_plan` 生成一个带时间戳的空文件。文件名不要手敲，时间戳错一位，执行顺序就错。
- `supabase db reset` 本地全量重放。改完迁移先跑它，再写业务代码。
- `supabase migration list` 打印本地文件与远程执行记录的对照表。出问题先看它。
- `supabase db push` 把尚未执行的迁移推到远程库。
- `supabase db diff -f add_team_plan` 比对当前库与迁移记录，反推一个迁移文件。

`db diff` 要克制使用。它是救急工具：在 Dashboard 点了一堆东西，用它把差异补成文件。日常顺序应该反过来，先写 SQL 再 reset 验证。点出来的对象往往没有约束、没有索引、没有注释，反推只是把错误固化成文件。

一个迁移文件只装一件事。加索引就只写一条 `create index`，不写 down，不写背景说明，背景放进 commit message。凡是「线上缺了它就不能正确工作」的东西，包括列、约束、索引、函数、触发器、RLS 策略，都必须出现在某个迁移文件里。

Dashboard 改动里最难发现的是策略和授权。列少了一眼就能看出来，报错也直接；RLS 策略少一条，页面只表现为「数据变少了」，没人会把它和昨天点过的按钮联系起来。用 `db diff` 补完文件后，回头核对一次策略条数：

```sql
select tablename, count(*) from pg_policies where schemaname = 'public' group by 1;
```

和迁移文件夹里的策略数量对一遍，数量对不上说明有对象只活在线上。

## 9.2 迁移的纪律

下面五条各自对应一次事故，属于硬规则。

已合并的迁移不再改。 迁移历史是单向的。把 `20261115090000_init_schema.sql` 里的列名改掉，本地 `db reset` 是对的，线上库早已按旧版本执行过，不会回头重跑。从此本地和线上是两套结构，代码只有一套。写错了就新加文件修。

一个文件只做一件事。 加表、加索引、改权限、回填数据塞进同一个文件，失败时看不出哪一步挂的，也没法回滚半步。拆成四个文件，各跑各的。

加列带默认值要分清常量与函数。 Postgres 11 之后，`add column ... default <常量>` 只写元数据，毫秒级完成。默认值是 volatile 函数（`gen_random_uuid()`、`random()`）时会重写整张表并锁住它。`now()` 是 stable，走快路径。回填时间戳没有问题，回填 uuid 要单独写 `update`。

大表建索引用 `create index concurrently`。 普通 `create index` 锁写，百万行的表能锁几十秒。并发建索引不阻塞写入，代价是更慢，并且不能放在事务块里：

```
ERROR:  CREATE INDEX CONCURRENTLY cannot run inside a transaction block
```

迁移工具是否把整个文件包在一个事务里，取决于工具与版本，**未验证**。真遇到这堵墙时，把这个索引拆成单独文件，用直连 URL 手动执行一次，再在迁移里写注释说明它已在线上。这也是不建议在迁移里放飞 `concurrently` 的原因。

删东西分两步。 先让代码停止读写它，观察一周，确认没有慢查询和报错，再写迁移删除。一步到位的删除在回滚时是灾难：旧代码还在读那个列，列已经没了。

五条拼起来就是一次安全的加列：给 `teams` 加 `billing_email` 并要求非空。不能直接 `add column billing_email text not null`，老数据没有值，加非空约束会立刻失败。拆成三个文件。

```sql
-- supabase/migrations/20261116100000_teams_add_billing_email.sql
alter table public.teams add column billing_email text;
```

```sql
-- supabase/migrations/20261116100100_backfill_billing_email.sql
-- 用 owner 的邮箱回填，空值只影响演示数据
update public.teams t
set billing_email = p.email
from public.team_members m
join public.profiles p on p.id = m.user_id
where m.team_id = t.id
  and m.role = 'owner'
  and t.billing_email is null;
```

```sql
-- supabase/migrations/20261116100200_teams_billing_email_not_null.sql
-- 回填完才加约束。如果还剩空行，这一步会失败，这就是保护。
alter table public.teams
  alter column billing_email set not null;
```

第三个文件跑完没有输出。如果报 `column "billing_email" contains null values`，说明回填漏了行，这正是需要的信号，问题被留在小步里，不会拖到一条大 SQL 第四十分钟才炸。

表大到几十万行时，第二段的 `update` 会长时间锁住整表。这时拆细：每次 `update ... where id in (select id from teams where billing_email is null limit 5000)`，跑几十次。第三段也别直接 `set not null`，改成两段：

```sql
alter table public.teams
  add constraint teams_billing_email_not_null check (billing_email is not null) not valid;
alter table public.teams validate constraint teams_billing_email_not_null;
```

`not valid` 表示只约束以后写入的行，已有行先不检查；`validate` 再用一把轻锁扫一遍确认。两步之间若有新写入的空值，`validate` 会失败，正好暴露漏回填。代价是多一个约束对象，换来停机时间从分钟级降到秒级。

迁移文件里不要自己写 `begin;` 与 `commit;`。执行工具通常已把整个文件包在事务里，再包一层，外层失败时内层已经提交，回滚不动，库里停在两半都不对的状态。要控制事务边界，用工具提供的开关。这个坑本地很难复现，因为本地不会在迁移跑到一半时杀进程。

## 9.3 回滚：多数时候是往前修

回滚分三种情况。本地库玩坏了、数据无所谓，`supabase db reset` 从头重放。刚 push 到远程、还没有数据，写一个反向迁移把列或表改回去。远程已经有数据，只能往前修：加列回填、双写过渡、最后再删。

第三种是常态。线上有真实数据时，一个 `drop table` 式的「回滚」和删库没有区别。

所以正确姿势是向前修复：发现迁移写错，再加一个迁移把状态改对。回滚 SQL 几乎不会被测过，写的时候觉得对，真出事时没人敢跑一条从没执行过的 `delete`。团队里更常见的约定是迁移只前进，出问题用新迁移修，备份靠 `pg_dump`。push 之前先 dump 一份，一份半小时前的备份比任何回滚脚本都可靠。

远程记录与本地文件对不上时，`supabase migration list` 两边会错位，push 被拒绝。这时才用 `supabase migration repair --status reverted <版本号>` 把远程记录标成已回退，再重新推。它是改记录，不改数据，执行前先确认版本号。

repair 有一个容易忽略的后果：记录标成 reverted 之后，远程库里的对象还在。于是库里处于「记录说没跑、结构已经改了」的状态，再推同一个迁移会撞 `relation already exists`。补救要么手动清理对象，要么写一个新迁移绕过。没有干净的解法，只能少发生，例如迁移文件进仓库后不要在本地重命名或删除。

## 9.4 幂等种子

`supabase/seed.sql` 在每次 `db reset` 之后自动执行。一天 reset 十次，它就跑十次。不幂等的种子第二次就撞：

```
ERROR:  duplicate key value violates unique constraint "teams_pkey"
```

修法是两条：主键写死，冲突时更新。固定主键还有一个好处，文档与截图能对上：种子里的团队 id 永远是 `aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa`，写测试、贴报错都能直接引用。

种子的量刚好够走通主要流程。`jobs`、`notifications`、`files` 各一条，队列页面与通知红点有东西可看。多到看不清哪条是自己造的数据时，种子就失去意义。

固定 UUID 的代价是要自己保证不撞，用不同前缀的序号最省事。若种子每次随机，文档里贴的 id 第二天就错了。

顺序也不能反：先插 `auth.users`，第 8 章的 `handle_new_user` 触发器会替我们建 profile；再 `update profiles` 补 `full_name`，因为触发器从 `raw_user_meta_data` 读取，格式对不上就是空值。先插 profiles 会撞 `auth.users` 的外键。

种子写错时，报错往往不出现在 seed 里。`auth.users` 少了 `instance_id`，登录时 Supabase Auth 返回 `Database error saving new user`，根因在 seed 或触发器里，不在登录页。

`on conflict (team_id)` 那一行说明 `subscriptions.team_id` 上有唯一约束，第 8 章 DDL 写的是 `team_id uuid not null unique`。种子必须尊重真实约束，否则会在本地制造出线上一秒就失败的数据。

`db reset` 的顺序是删库、按时间戳跑迁移、跑 seed。seed 能看到全部表，看不到任何运行时数据，别在 seed 里假设某张 `jobs` 已经有 worker 写入的记录。

CI 里只跑 `db push` 而不跑 seed，测试库就没有演示数据。要么在流水线里执行一次 `psql -f supabase/seed.sql`，要么让测试自己造数据。选一种，不要让「本地能过、CI 挂」变成谜。

## 9.5 两条 URL：池化与直连

`supabase start` 之后 CLI 会打印一堆地址。最容易搞混的是数据库 URL 有两个，用途不同。

| 类型 | 本地 | 托管 | 给谁用 |
| --- | --- | --- | --- |
| 直连（direct） | `...@127.0.0.1:54322/postgres` | `db.<ref>.supabase.co:5432` | 迁移、`psql`、脚本、长任务 |
| 连接池（pooled） | 端口看 `supabase status` | `...pooler.supabase.com:6543` | 应用运行时 |

本地直连的固定写法是用户 `postgres`、密码 `postgres`、端口 `54322`、库 `postgres`：

```
postgresql://postgres:postgres@127.0.0.1:54322/postgres
```

本地是否默认起连接池、在哪个端口，取决于 CLI 版本与 `config.toml`，**未验证**，跑 `supabase status` 看。托管项目的池化地址形如：

```
postgresql://postgres.<项目ref>:<密码>@aws-0-<区域>.pooler.supabase.com:6543/postgres
```

注意用户名是 `postgres.<项目ref>`，漏掉项目后缀会得到 `password authentication failed`，然后容易去重置一个根本没问题的密码。

托管的直连面向「一个进程长期持有连接」的场景。serverless 函数每个请求可能起一个新实例，几百并发就是几百个连接，`max_connections` 很快用完。连接池在中间复用，应用侧看到几百个「连接」，落到 Postgres 上可能只有十几个。

池化模式的代价来自 6543 端口是 transaction 模式，一个事务结束连接就还给池子。这带来三个限制。第一，不能跨语句保持会话状态，`set search_path`、临时表、`listen`、会话级 advisory lock 都失效。第二，不能依赖命名 prepared statement，部分驱动默认开启。第三，迁移不要在池化 URL 上跑，事务边界、advisory lock、长时间锁表的行为都不受你控制。

规则是应用运行时用 pooled，迁移与脚本用 direct，两个环境变量各司其职。不要写成 `if (process.env.NODE_ENV === 'production')`，preview 环境在 `NODE_ENV` 上看起来和生产一样，会用错地址。

用错的症状有三个。迁移跑一半报锁相关错误，或者跑完线上没生效，多半是在池化 URL 上跑的。`prepared statement "s0" already exists` 是池化加驱动预编译。应用偶尔 `too many clients`、页面却能正常打开，说明只换了自己 `pg` 那条路的 URL。

最后一条需要解释。`supabase-js` 走 HTTP，PostgREST 那边自己有池，换成直连之后「页面能打开」说明不了任何问题，坏掉的只是 `pg` 池那条路。看到 `too many clients` 时，先去数 `pg_stat_activity` 里按 `application_name` 分组的连接。

```bash
# .env.local

# 应用运行时：池化地址（本地与直连相同，本地没有池化层）
DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:54322/postgres"

# 迁移、seed、psql、后台脚本：直连
DIRECT_URL="postgresql://postgres:postgres@127.0.0.1:54322/postgres"

# Supabase JS 客户端（HTTP，不走上面两条）
NEXT_PUBLIC_SUPABASE_URL="http://127.0.0.1:54321"
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY="<supabase start 输出里的 anon key>"
```

部署到托管时，`DATABASE_URL` 换 6543 的池化地址，`DIRECT_URL` 保持 5432。

池化层本身也有参数。Supabase 托管项目在 Dashboard 的 Database 设置里能看到 pooler 的 mode 与 pool size，可调范围**未验证**。transaction 模式还有一个副作用：`set` 只能活到事务结束，想改会话级参数会被静默丢弃，包括写在连接串 `options` 里的那些。所以 `statement_timeout` 这类参数要么在每条连接上设，要么写进角色默认值：

```sql
alter role authenticated set statement_timeout = '8s';
```

本地直连没有这个问题，每个请求独占一条连接。这也是「本地正常、线上偶尔超时」的常见成因：SQL 没变，连接的生命周期变了。

## 9.6 连接池写成模块级单例

最常见的写法错误是每个请求新建一个池：

```ts
// 错误示范：每个请求建一个池
export async function getTeams() {
  const pool = new Pool({ connectionString: process.env.DATABASE_URL })
  return pool.query('select * from teams')
}
```

这段代码看起来每次用完就释放，实际不会。`Pool` 是懒连接的，第一次查询才建连接，之后一直留着。函数被调一百次，进程里就有一百个连接。症状是页面刷新十几次之后：

```bash
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres" \
  -Atc "select count(*) from pg_stat_activity where application_name='teamstack-web'"
# 30、40、50，一路往上；刷新停下来也不掉
```

正确写法是模块级单例，并且必须挂到 `globalThis`，因为开发环境的热重载会重新执行模块。Next.js 改一个文件只重新加载受影响的模块图，旧的 `Pool` 对象不会自动销毁。改二十次代码就攒了二十个池子，这是「开发环境连接数一直涨、生产正常」的原因。

```ts
// src/lib/db.ts
import { Pool, type QueryResultRow } from 'pg'

const connectionString = process.env.DATABASE_URL
if (!connectionString) {
  throw new Error('DATABASE_URL 未设置')
}

const globalForDb = globalThis as unknown as { teamstackPool?: Pool }

export const pool =
  globalForDb.teamstackPool ??
  new Pool({
    connectionString,
    max: 5,
    idleTimeoutMillis: 10_000,
    connectionTimeoutMillis: 5_000,
    application_name: 'teamstack-web',
    options: '-c statement_timeout=8000',
  })

// 生产环境进程只启动一次，不需要挂到 globalThis；
// 开发环境必须挂，否则热重载会不断新建池子。
if (process.env.NODE_ENV !== 'production') {
  globalForDb.teamstackPool = pool
}

// 池里的空闲连接被服务端掐断时，pg 会在这里抛错。
// 不监听就是 unhandled error，进程直接退出。
pool.on('error', (err) => {
  console.error('[db] idle client error', err)
})

export async function query<T extends QueryResultRow = QueryResultRow>(
  text: string,
  params?: unknown[],
) {
  const startedAt = Date.now()
  const result = await pool.query<T>(text, params)
  const elapsed = Date.now() - startedAt

  if (process.env.NODE_ENV !== 'production' && elapsed > 200) {
    console.warn(`[db] slow query ${elapsed}ms: ${text.slice(0, 120)}`)
  }
  return result
}
```

如果用的是 `postgres` 驱动，transaction 模式下必须关掉预编译：

```ts
// src/lib/db.ts（postgres 驱动版）
import postgres from 'postgres'

const globalForSql = globalThis as unknown as { sql?: postgres.Sql }

export const sql =
  globalForSql.sql ??
  postgres(process.env.DATABASE_URL!, {
    max: 5,
    idle_timeout: 10,
    connect_timeout: 5,
    prepare: false, // 池化 transaction 模式必须关
  })

if (process.env.NODE_ENV !== 'production') {
  globalForSql.sql = sql
}
```

`prepare: false` 是兼容性要求，属于优化之外的事。开启它会报 `prepared statement "s0" already exists`，因为池子在事务之间换掉了底层连接，驱动以为仍是同一根。

三个参数需要单独解释。`max` 是池子上限，并非数据库上限；`idleTimeoutMillis` 太大会让空闲连接长期占着名额，一万毫秒是折中值；`connectionTimeoutMillis` 一定要设，不设时池满后请求会无限等待，用户看到转圈，日志里什么都没有。设了才会快速失败，能在日志里看到 `timeout exceeded when trying to connect`。`options: '-c statement_timeout=8000'` 给每条 SQL 一个八秒上限，防止一条慢查询把池里的连接占死。

两套通道的分工也要定清楚。

- 普通增删改查用 `supabase-js`，它自动带 JWT，RLS 按当前用户过滤。
- 多表写入和事务用 `pg`，`supabase-js` 只能通过 `rpc` 调数据库函数。
- 后台 worker 取任务用 `pg`，`for update skip locked` 这类语法 PostgREST 表达不了。
- `explain` 与运维查询用 `pg` 加 `DIRECT_URL`。
- 上传、登录、发邮件用 `supabase-js`。

这里藏着本书最容易犯的安全错误：RLS 只在带 JWT 的那条路上生效。用 `pg` 直连时，身份是数据库用户（本地是 `postgres`），并非终端用户，RLS 默认不拦。所以 `pg` 里的每条 SQL 都必须自己写 `where team_id = $1`。第 15 章讲 RLS 会说「防的是前端」，同一句话的另一面是「防不住你的服务端代码」。

还有一条：不要在同一个业务逻辑里混用 `supabase-js` 与 `pg` 的事务。两者是不同的物理连接，`supabase.rpc()` 与 `pool.query()` 不在一个事务里，回滚其中一个不影响另一个。要事务就全用 `pg`，要纯 CRUD 就全用 `supabase-js`。

手动开事务时必须把连接还回去：

```ts
// src/lib/db-tx.ts（第 10 章的 withTransaction 就是从这里长出来的）
const client = await pool.connect()
try {
  await client.query('begin')
  await client.query('update public.teams set plan = $1 where id = $2', ['pro', teamId])
  await client.query('commit')
} catch (err) {
  await client.query('rollback')
  throw err
} finally {
  client.release() // 少这一行，连接永远回不到池子
}
```

`pool.query()` 是借一次还一次，`pool.connect()` 借了不还。漏掉 `release()` 的症状与漏 `commit` 很像：`pg_stat_activity` 里 `idle` 或 `idle in transaction` 慢慢涨到上限，然后所有请求排队。漏 `release` 比漏 `commit` 更常见，因为 `commit` 在业务逻辑里，`release` 在样板代码里。

## 9.7 边界与失败模式

热重载泄漏。 验证单例是否生效，数连接即可：

```sql
select application_name, state, count(*)
from pg_stat_activity
where datname = 'postgres'
group by 1, 2
order by 3 desc;
```

`teamstack-web` 那一行最多 5 条，state 以 `idle` 为主。改十次文件后数字从 5 涨到 15、30，说明 `globalThis` 那段没生效，或者哪里又写了 `new Pool()`。

事务中空闲。 比连接数上涨更隐蔽的是 `idle in transaction`：

```sql
select pid, state, now() - state_change as idle_for, left(query, 60) as query
from pg_stat_activity
where state like 'idle in transaction%'
order by idle_for desc;
```

事务 `begin` 之后去调外部 API，忘了 `commit`，连接就挂在「事务中空闲」，锁还拿着。这种连接挡着 vacuum，也挡着别人改同一行。超过五分钟基本可以断定是代码漏了 `commit` 或 `rollback`，用 `select pg_terminate_backend(pid);` 释放。

多实例的算术。 总连接数约等于实例数乘 `pool.max`，再加迁移脚本、PostgREST 自己的池、psql、Studio、备份任务。四个容器每池 5 条就是 20 条，加上零散连接，三四十条一般库扛得住。serverless 上实例数不归你管，流量涨十倍实例可能涨二十倍，`max: 5` 就变成 100 条。所以 serverless 的 `max` 调到 2 到 3，并且一定设 `connectionTimeoutMillis`，宁可快速失败。

`max` 按并发查询数估，不按 QPS。一个请求在事务里连发三条 SQL，只占一条连接，但占用时长是三条之和。看的是同一瞬间有多少条 SQL 在跑。

用下面这条判断池子大小是否合适：

```sql
select state, count(*)
from pg_stat_activity
where application_name = 'teamstack-web'
group by state;
```

两种形状。`active` 长期贴着 `max`、请求开始排队，该调大池子或查慢 SQL。`active` 长期在 0 到 1、`idle` 一堆，说明池子开太大，白占 Postgres 的连接名额，调到 3 也行。

两种超时要分清。 `timeout exceeded when trying to connect` 是等连接超时，SQL 一个字都没执行；`statement timeout` 是 SQL 执行太久被掐。前者调池子，后者调索引或语句。不要把它们混成同一个问题去调 `statement_timeout`，那只是把症状藏起来。

别人的连接也占名额。 `pg_stat_activity` 里会出现几个陌生的 `application_name`：`postgrest` 是 Supabase 的 REST 层，`supabase_admin` 是 CLI 与 Studio，`pgbouncer` 是池化器。它们的数量与你的代码无关，但都占 `max_connections`。只盯 `teamstack-web` 会低估总量，连接用满时最先报错的往往是连接池。排障时按 `application_name, usename` 分组，比逐条翻 pid 快。

杀掉连接的副作用。 被 `pg_terminate_backend` 杀掉的连接在应用侧会抛一次错误，日志里是 `terminating connection due to administrator command`，或者一条正在跑的查询突然失败。`pg` 的池把这个错误交给 `pool.on('error')`，所以那句 `console.error` 有实际作用，删掉它进程会因为这个错误直接退出。

池化模式下的会话状态。 在 6543 上执行 `set search_path`、建临时表、用会话级 advisory lock，都不能保证下一条语句还看得见。需要这些能力时切到直连，或者把逻辑收进一个事务。

迁移记录与远程对不上。 `Remote migration versions not found in local migrations directory` 表示远程执行过某个迁移，本地文件缺失，多半是别人推了迁移你没 pull，或者你删过文件。先从 git 找回来，确实找不回才用 `repair`。

## 9.9 常见错误

`error: relation "profiles" does not exist`

新环境没跑迁移，或者连错了库。查两件事：`supabase migration list` 的本地与远程是否一致；`DATABASE_URL` 指向的是否为预期的库（本地 54322，托管是 pooler 域名）。在代码里跑 `select current_database(), inet_server_addr();` 能直接看到连的是谁。

`Remote migration versions not found in local migrations directory`

远程执行过某个迁移，本地缺这个文件。先 `supabase migration list` 看缺哪个版本号，再从 git 找回；确实找不回才用 `supabase migration repair --status reverted <版本号>`。不要一上来就 repair，它改的是记录。

`sorry, too many clients already`

三个原因按概率排：每个请求 `new Pool()`；开发热重载攒了几十个池子；`max` 设得太大。先按 9.6 改成单例，再把 `max` 降到 5 以内，然后用 9.7 的 SQL 数连接，确认没有 `idle in transaction` 泄漏。

`prepared statement "s0" already exists`

用了 transaction 模式的池化 URL（6543），驱动默认开了预编译。`postgres` 驱动加 `prepare: false`；`pg` 驱动一般不会出现，出现时检查是否在池化连接上用了命名 statement。

`duplicate key value violates unique constraint "teams_pkey"`

种子不幂等，第二次执行撞主键。所有 `insert` 都要有 `on conflict`，主键写死。另一种可能是重放了旧种子而没重放迁移，两边固定 UUID 不一致。

`password authentication failed for user "postgres"`

托管环境的池化用户名是 `postgres.<项目ref>`，漏掉项目后缀就会落到这个报错。另一种可能是密码正确但连的是池化端口，密码相同，用户名不同。

## 9.10 这一章在做什么

这一章把两件容易被当成运维事务的东西拉回代码：结构是迁移文件，连接是单例加池化。

它们的共同点是都能用一条命令复现。`db reset` 能从零长出整个库，`pg_stat_activity` 能一眼看出连接属于谁。不能复现的改动不叫迁移，不设上限的连接不叫池。

现在有了一个可被任何人重放出来的库，稳定的演示数据，以及不会在热重载里泄漏的连接池。下一章处理另一个维度：一个请求要改两张表，第二张失败时第一张怎么办。那是事务的领域。
