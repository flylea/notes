# 第 39 章 测试

测试在这套技术栈里有一条清晰的边界：能跑在 Node 里的逻辑用单元测试，依赖数据库和 HTTP 的部分用集成测试，需要真实浏览器的部分用端到端测试。越过这条边界写测试，会得到跑得慢、经常红、没人维护的测试集。

本章讲三件事：工具怎么选，四类测试各写什么，以及怎么放进 CI。涉及的概念有测试分层、`vitest` 配置、`playwright` 配置、数据库夹具、签名验证和可访问性断言。

先给一个数量参考。teamstack 现在的测试分布是四十个单元测试、十个集成测试、六条端到端用例。单元测试跑一次两秒，集成测试十秒，端到端一分钟。

测试金字塔在这套栈里有变形。顶端的端到端仍然最贵，中间层被拉厚：数据库、RLS、签名验证都靠集成测试覆盖。底端的单元测试覆盖纯函数，占比最大。这个比例让 `pnpm test` 适合在每次保存文件后跑，端到端只在提交前和 CI 里跑。

## 39.1 测试的分工

单元测试测一个函数或一个组件，不碰网络和数据库。它跑得快，失败时能定位到具体分支。适合放纯逻辑：权限判断、表单校验、金额换算、日期处理。

集成测试测多个模块一起工作，允许连真实数据库。它慢一些，但能发现单元测试看不到的问题，比如 RLS 策略写错、事务边界写错、序列化字段丢失。

端到端测试从浏览器出发，点真实的按钮，走真实的登录流程。它最慢、最脆，只用来覆盖少数关键路径：注册、建团队、邀请、上传、升级订阅。

三类测试的替代关系很弱。权限函数有单元测试，不代表接口不会被绕过；接口有集成测试，不代表按钮绑错了事件。

有一条官方限制要提前知道。App Router 的异步服务端组件目前没有测试工具能完整渲染，Vitest 和 Jest 都不支持。官方文档的建议是：异步组件用端到端测试覆盖，同步组件可以写单元测试。

这个限制影响的是「渲染」，不影响「逻辑」。把异步组件里的取数和计算抽成普通函数，函数就能单测，渲染交给端到端。第 39.5 节给具体做法。

有些东西不值得写测试：布局组件的样式、第三方库的行为、一次性的迁移脚本、还在频繁改结构还没定的页面。给这些写测试，改一次代码要改三次测试，最后大家绕开测试跑。

优先级由损失决定。身份隔离、钱、数据删除这三类出问题代价最高，先给它们写测试。样式错位、文案不对这类问题，发现了再修，不值得为它维护断言。

写测试的顺序建议倒过来。先写集成测试确认接口和 RLS 的行为，再补单元测试覆盖分支，最后写端到端。反过来的顺序是先写一堆单元测试，联调时发现接口约定不一致，全部返工。

## 39.2 工具取舍

四个工具都能用，分工不同。

| 工具 | 定位 | 适合 | 代价 |
| --- | --- | --- | --- |
| Vitest | 单元与组件测试 | 新项目，和 Vite 生态一致 | 异步服务端组件不支持 |
| Jest | 单元与组件测试 | 已有 Jest 基建的老项目 | 配置比 Vitest 重，ESM 支持绕 |
| Playwright | 端到端测试 | 跨浏览器，CI 稳定 | 首次安装要下浏览器 |
| Cypress | 端到端与组件测试 | 调试体验好，团队熟悉 | 13.6.3 之前不支持 TS 5 的 `bundler` 解析 |

选 Vitest 的理由是配置短。它和 `vite-tsconfig-paths` 一起用，`@/lib/...` 这类别名不用额外映射。没有这个插件，测试文件里的别名解析失败，报 `Cannot find module`，和真实代码无关。Jest 需要 `next/jest` 包一层，还要处理 `transformIgnorePatterns`。

选 Playwright 的理由是并行和重试做得好，`webServer` 配置能让它自己起服务。Cypress 的交互式调试更顺手，团队里有人熟悉就继续用。

Cypress 的组件测试和 Vitest 的组件测试不共存。两套都维护时，选一套覆盖组件，另一套只做端到端。

工具选型定下来之后别频繁换。迁移测试的成本远高于工具之间的差异，换一次要让所有用例重新跑通。

版本要锁死。Vitest 和 Playwright 的次版本升级偶尔改默认行为，锁文件能保证 CI 和本地跑同一套。

Jest 值得留的情况只有一种：仓库里已经有几百条 Jest 用例，迁移成本高于收益。新写的测试仍然可以用 Jest，配置沿用 `next/jest` 即可，两套测试在一个仓库里并行跑。

两个工具都装也没问题，`test` 脚本跑 Vitest，`test:e2e` 跑 Playwright。前提是两边的测试目录分开，别让 Vitest 扫到 `e2e/` 下的文件。

## 39.3 Vitest 上手

装依赖。

```bash
pnpm add -D vitest @vitejs/plugin-react jsdom \
  @testing-library/react @testing-library/dom \
  @testing-library/jest-dom vite-tsconfig-paths dotenv
```

配置文件放在项目根。

```ts
// vitest.config.mts
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";
import tsconfigPaths from "vite-tsconfig-paths";

export default defineConfig({
  plugins: [tsconfigPaths(), react()],
  test: {
    environment: "jsdom",
    setupFiles: ["./src/test/setup.ts"],
    include: ["src/**/*.test.{ts,tsx}"],
    exclude: ["e2e/", "node_modules/"],
    testTimeout: 30_000,
    fileParallelism: false,
  },
});
```

`environment` 选 `jsdom`，组件测试需要 DOM。纯 Node 的测试文件可以在文件顶部用 `// @vitest-environment node` 单独覆盖。

`fileParallelism: false` 是为集成测试准备的。多个测试文件同时连一个数据库，会互相踩数据。代价是集成测试串行，十秒左右能接受。

`setupFiles` 里做两件事：加载断言扩展，读取 `.env.local`。

```ts
// src/test/setup.ts
import "@testing-library/jest-dom/vitest";
import { config } from "dotenv";

config({ path: ".env.local" });
```

断言扩展让 `expect(el).toBeVisible()` 这类匹配器可用。不装它，用 `getByRole` 查到的元素只能断言 `toBeTruthy`，可读性差很多。

`package.json` 里加两个脚本。

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest",
    "test:e2e": "playwright test"
  }
}
```

测试文件的位置有两种约定：与源文件同目录，或者集中在 `src/test/`。同目录的好处是改代码时顺手看到测试，删模块时不会漏掉测试文件。集成测试放 `src/test/`，它们跨模块，和某个源文件没有一对一关系。

`vitest` 不带参数会进 watch 模式，CI 里会挂住。`vitest run` 跑一次就退出，CI 用这个。

## 39.4 单元测试：权限与校验

先写一个能测的权限模块。把判断从页面和接口里抽出来，集中到一个文件。

```ts
// src/lib/permissions.ts
import "server-only";

export type Role = "owner" | "member";

const rank: Record<Role, number> = { member: 1, owner: 2 };

export function isAtLeast(role: Role, required: Role) {
  return rank[role] >= rank[required];
}

export function canInvite(role: Role) {
  return isAtLeast(role, "owner");
}

export function canRemoveMember(actor: Role, target: Role) {
  if (target === "owner") return false;
  return isAtLeast(actor, "owner");
}

export function canTransferOwnership(role: Role) {
  return role === "owner";
}

export function canChangePlan(role: Role) {
  return isAtLeast(role, "owner");
}
```

测试文件放在旁边，命名 `permissions.test.ts`。

```ts
// src/lib/permissions.test.ts
import { describe, expect, it } from "vitest";
import {
  canInvite,
  canRemoveMember,
  canTransferOwnership,
  canChangePlan,
} from "./permissions";

describe("权限判断", () => {
  it("member 不能邀请", () => {
    expect(canInvite("member")).toBe(false);
  });

  it("owner 能邀请", () => {
    expect(canInvite("owner")).toBe(true);
  });

  it("谁都不能移除 owner", () => {
    expect(canRemoveMember("owner", "owner")).toBe(false);
    expect(canRemoveMember("member", "owner")).toBe(false);
  });

  it("只有 owner 能转移所有权和改套餐", () => {
    expect(canTransferOwnership("member")).toBe(false);
    expect(canChangePlan("member")).toBe(false);
    expect(canTransferOwnership("owner")).toBe(true);
  });
});
```

```bash
pnpm test
```

输出里应看到 `Test Files 1 passed (1)` 和 `Tests 4 passed (4)`。

写这类测试的第一个收益是发现散落的判断。项目里常见的写法是 `role === "owner"` 直接写在页面里，一共二十几处。抽成函数之后，`grep -rn "role === 'owner'" src` 的输出应该只剩 `permissions.ts` 一处。清不干净，说明还有地方在绕过规则。

权限函数和 RLS 是两层防线，测的东西不同。权限函数管界面显示，决定按钮出不出现；RLS 管数据，决定越权请求能不能拿到行。两层都要测，只测一层会留下绕过路径。

第二个可测的区域是表单校验。

```ts
// src/lib/invitations.ts
export const emailPattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

export type InviteInput = { email: string; role: "owner" | "member" };
export type InviteResult = { ok: true; email: string; role: string } | { ok: false; error: string };

export function validateInvite(input: InviteInput): InviteResult {
  const email = input.email.trim().toLowerCase();

  if (!emailPattern.test(email)) {
    return { ok: false, error: "邮箱格式不正确" };
  }
  if (email.length > 254) {
    return { ok: false, error: "邮箱过长" };
  }
  return { ok: true, email, role: input.role };
}
```

```ts
// src/lib/invitations.test.ts
import { describe, expect, it } from "vitest";
import { validateInvite } from "./invitations";

describe("邀请校验", () => {
  it("去掉首尾空格并转小写", () => {
    const result = validateInvite({ email: "  A@Example.COM ", role: "member" });
    expect(result).toEqual({ ok: true, email: "a@example.com", role: "member" });
  });

  it("拒绝没有 @ 的输入", () => {
    expect(validateInvite({ email: "a.example.com", role: "member" })).toEqual({
      ok: false,
      error: "邮箱格式不正确",
    });
  });

  it("拒绝空字符串", () => {
    expect(validateInvite({ email: "   ", role: "member" }).ok).toBe(false);
  });

  it("拒绝超过 254 字符的邮箱", () => {
    const long = `${"a".repeat(250)}@ex.com`;
    expect(validateInvite({ email: long, role: "member" }).ok).toBe(false);
  });
});
```

校验函数有一个隐性的坑：大小写规范化放在哪个环节。放在校验里，调用方拿到的就是规范化之后的邮箱；放在数据库唯一索引上，大小写不同的两条记录会同时存在。测试把这个约定固定住，后面换实现时不会悄悄改掉。

这类函数的测试成本很低，一个函数五到十条断言，改实现时几乎不用改测试。测试写起来便宜的模块，优先覆盖。

## 39.5 组件测试与异步组件的绕法

客户端组件可以直接测。渲染、查询、模拟交互，用 Testing Library 的语义查询。

```tsx
// src/components/invite-button.tsx
"use client";

import { useRouter } from "next/navigation";

export function InviteButton({ teamSlug }: { teamSlug: string }) {
  const router = useRouter();
  return (
    <button onClick={() => router.push(`/teams/${teamSlug}/invite`)}>
      邀请成员
    </button>
  );
}
```

组件里用了 `next/navigation`，测试时要 mock。

```tsx
// src/components/invite-button.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, expect, it, vi } from "vitest";
import { InviteButton } from "./invite-button";

const push = vi.fn();
vi.mock("next/navigation", () => ({
  useRouter: () => ({ push }),
}));

describe("InviteButton", () => {
  it("点击后跳到邀请页", async () => {
    render(<InviteButton teamSlug="acme" />);
    await userEvent.click(screen.getByRole("button", { name: "邀请成员" }));
    expect(push).toHaveBeenCalledWith("/teams/acme/invite");
  });
});
```

`vi.mock` 会被提升到文件顶部，`push` 用 `const` 声明，别用 `let`。用 `let` 时提升之后变量还没初始化，运行时报 `Cannot access 'push' before initialization`。

异步服务端组件测不了，绕不过去。三种尝试都会失败。

用 `render(await Page())` 渲染，返回的是 React 元素树，`await` 之后拿到的仍是未解析的 `Promise` 组件，Testing Library 报找不到容器。

用 `act` 包住，React 的 `act` 不处理服务端组件的异步边界，控制台警告一串，断言还是失败。

把组件改成同步、在测试里传数据，等于测了一个克隆，原组件的取数逻辑一行都没覆盖。

mock 的范围要小，只 mock 模块边界：导航、`fetch`、环境变量。把组件内部函数也 mock 掉，测到的就只剩 mock 自己的行为。

可行的做法是抽函数。把异步组件里的取数搬进普通函数，测试这个函数。

```ts
// src/lib/activity.ts
import "server-only";
import { createClient } from "@/lib/supabase/server";

export type ActivityRow = {
  id: string;
  action: string;
  actorEmail: string | null;
  createdAt: string;
};

export async function loadActivityLogs(teamId: string, limit = 50) {
  const supabase = await createClient();
  const { data, error } = await supabase
    .from("activity_logs")
    .select("id, action, created_at, profiles(email)")
    .eq("team_id", teamId)
    .order("created_at", { ascending: false })
    .limit(limit);

  if (error) throw new Error(error.message);

  return (data ?? []).map((row) => ({
    id: row.id,
    action: row.action,
    actorEmail: row.profiles?.email ?? null,
    createdAt: row.created_at,
  }));
}
```

这个函数依赖 Supabase 客户端，用集成测试覆盖。真正适合单测的是它周围的纯逻辑，比如把 `created_at` 转成相对时间、按 action 分组。

覆盖率不建议设阈值。设了之后最常见的动作是给容易测的文件补空断言，数字上去了，bug 一个没少。看覆盖率要反着看：哪些关键文件是零覆盖。

抽出取数函数之后，可以单测的边界变清楚了：空数组、actor 为 null、limit 到上限。这三个各写一条，比给渲染组件写十条断言有用。

## 39.6 集成测试：RLS

RLS 的策略写在数据库里，mock 数据库就测不到。这类测试必须连真实库，用两个真实用户各查一次。

准备三步。起本地 Supabase，重置数据库，把服务端密钥写进 `.env.local`。

```bash
supabase start
supabase db reset
echo "SUPABASE_SERVICE_ROLE_KEY=$(supabase status -o env | grep SERVICE_ROLE_KEY | cut -d= -f2)" >> .env.local
```

本地 Supabase 的启动时间约二十秒，`db reset` 要重放全部迁移。测试跑完不要停服务，下一次跑能省这段时间。

测试的骨架是：用 service role 建两个用户和一个团队，把 A 拉进团队，然后用 A 和 B 各自的会话查同一张表。

```ts
// src/test/rls.test.ts
// @vitest-environment node
import { afterAll, beforeAll, describe, expect, it } from "vitest";
import { createClient } from "@supabase/supabase-js";

const url = process.env.NEXT_PUBLIC_SUPABASE_URL!;
const anonKey = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!;
const serviceKey = process.env.SUPABASE_SERVICE_ROLE_KEY!;

const stamp = Date.now();
const ownerEmail = `owner-${stamp}@example.com`;
const otherEmail = `other-${stamp}@example.com`;
const password = "test-password-123";

const admin = createClient(url, anonKey, { auth: { persistSession: false } });
const service = createClient(url, serviceKey, { auth: { persistSession: false } });

let teamId: string;
let ownerId: string;
let otherId: string;
let ownerClient: ReturnType<typeof createClient>;
let otherClient: ReturnType<typeof createClient>;

async function signUp(email: string) {
  const { data, error } = await service.auth.admin.createUser({
    email,
    password,
    email_confirm: true,
  });
  if (error) throw error;
  const client = createClient(url, anonKey, { auth: { persistSession: false } });
  const { error: signInError } = await client.auth.signInWithPassword({ email, password });
  if (signInError) throw signInError;
  return { id: data.user.id, client };
}

beforeAll(async () => {
  const owner = await signUp(ownerEmail);
  const other = await signUp(otherEmail);
  ownerId = owner.id;
  otherId = other.id;
  ownerClient = owner.client;
  otherClient = other.client;

  const { data: team, error } = await service
    .from("teams")
    .insert({ name: `测试团队 ${stamp}`, slug: `test-${stamp}`, plan: "free" })
    .select("id")
    .single();
  if (error) throw error;
  teamId = team.id;

  await service.from("team_members").insert({ team_id: teamId, user_id: ownerId, role: "owner" });
  await service.from("activity_logs").insert({
    team_id: teamId,
    actor_id: ownerId,
    action: "team.created",
  });
}, 60_000);

afterAll(async () => {
  await service.from("teams").delete().eq("id", teamId);
  await service.auth.admin.deleteUser(ownerId);
  await service.auth.admin.deleteUser(otherId);
});

describe("teams 表的 RLS", () => {
  it("团队成员能看到自己的团队", async () => {
    const { data } = await ownerClient.from("teams").select("id").eq("id", teamId);
    expect(data).toEqual([{ id: teamId }]);
  });

  it("非成员查同一行拿到空数组，不报错", async () => {
    const { data, error } = await otherClient.from("teams").select("id").eq("id", teamId);
    expect(error).toBeNull();
    expect(data).toEqual([]);
  });

  it("非成员改不动这一行", async () => {
    const { data } = await otherClient
      .from("teams")
      .update({ name: "被篡改" })
      .eq("id", teamId)
      .select("id");
    expect(data).toEqual([]);
  });

  it("非成员看不到成员列表和日志", async () => {
    const members = await otherClient.from("team_members").select("user_id").eq("team_id", teamId);
    const logs = await otherClient.from("activity_logs").select("id").eq("team_id", teamId);
    expect(members.data).toEqual([]);
    expect(logs.data).toEqual([]);
  });

  it("非成员插不进 team_members", async () => {
    const { error } = await otherClient
      .from("team_members")
      .insert({ team_id: teamId, user_id: otherId, role: "member" });
    expect(error?.code).toBe("42501");
  });
});
```

断言用 `toEqual([])`，不用 `rejects`。RLS 拦截查询时返回空结果，不抛异常；只有写操作才会返回 `42501`（权限不足）。

跑完应看到 `Test Files 1 passed`，用例五个全绿。

再验证测试本身有效。手动改坏一条策略，把 `team_members` 的 select 策略条件改成 `true`，重新跑，第 2、4 条用例应该红。看到红之后再改回来。

这个反向验证很重要。测试一直绿，可能因为策略写得太严，也可能因为断言写错了表。只有故意破坏一次，才知道测试真的在读数据。

RLS 写错有四种常见形态，每一种都值得一条「B 看不到」的用例。

只写了 `using`，没写 `with check`。查询被拦住，插入照样成功。

函数用了 `security definer`，没设 `search_path`。函数以所有者身份执行，绕过调用者的 RLS。

把 `grant` 当成 RLS。收回权限能挡住整张表，挡不住行，两者要分开配。

策略写在了错误的表上。复制粘贴时表名没改，看起来有策略，实际不生效。

九张带 `team_id` 的表都要覆盖：`teams`、`team_members`、`invitations`、`activity_logs`、`files`、`subscriptions`、`jobs`、`notifications`，加上 `profiles` 的可见性。漏一张，就是一条越权路径。

这套用例跑一遍十秒上下，大部分时间花在三个用户会话的登录上。会话可以复用：`beforeAll` 里登录一次，五种断言共用一个客户端。两个用户的客户端要分开创建，共用一个实例会让第二次登录覆盖第一次的会话。测试之间要隔离，靠的是每次新建团队，别指望客户端状态被清空。

## 39.7 webhook 的验签与幂等

webhook 的测试不启动服务器，直接调用导出的处理函数。

```ts
// src/app/api/webhooks/stripe/route.test.ts
// @vitest-environment node
import { describe, expect, it } from "vitest";
import Stripe from "stripe";
import { POST } from "./route";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY ?? "sk_test_dummy");
const secret = process.env.STRIPE_WEBHOOK_SECRET ?? "whsec_test_dummy";

function buildRequest(body: string, signature?: string) {
  return new Request("http://localhost/api/webhooks/stripe", {
    method: "POST",
    body,
    headers: signature ? { "stripe-signature": signature } : {},
  });
}

describe("Stripe webhook", () => {
  it("签名不对返回 400", async () => {
    const res = await POST(buildRequest('{"id":"evt_1"}', "t=1,v1=bad"));
    expect(res.status).toBe(400);
  });

  it("没有签名头返回 400", async () => {
    const res = await POST(buildRequest('{"id":"evt_1"}'));
    expect(res.status).toBe(400);
  });

  it("签名正确返回 200", async () => {
    const payload = JSON.stringify({ id: "evt_test", type: "invoice.paid", data: { object: {} } });
    const signature = stripe.webhooks.generateTestHeaderString({ payload, secret });
    const res = await POST(buildRequest(payload, signature));
    expect(res.status).toBe(200);
  });
});
```

`generateTestHeaderString` 生成的是合法的 `t=...,v1=...` 头，和真实请求一致。用它比手写 HMAC 更稳，时间戳和编码细节都不用管。

处理函数里如果需要在模块加载时读环境变量，测试文件必须先把变量准备好。做法是用 `??` 给一个假值兜底，或者把变量读取挪进函数内部。模块加载即抛错，会让所有用例在导入阶段就失败，报错信息还看不出原因。

幂等的测试查副作用次数。

```ts
// 同一个事件重复投递两次
await POST(buildRequest(payload, signature));
await POST(buildRequest(payload, signature));

const { count } = await service
  .from("jobs")
  .select("id", { count: "exact", head: true })
  .eq("kind", "stripe.invoice.paid");
expect(count).toBe(1);
```

Stripe 会重复投递事件。去重键用 `event.id`，插进 `jobs` 表时加唯一约束，第二次投递被数据库挡住，处理函数返回 200。测试固定这个行为，后面改去重逻辑时不会退化成「每次都插一条」。

webhook 测试不覆盖三件事：Stripe 后台的事件格式变化、真实网络的重试、签名密钥轮换。前两件靠 Stripe 的 webhook 日志排查，第三件靠密钥版本配置。测试只保证当前格式下验签和幂等是对的。

## 39.8 端到端测试

Playwright 的配置只需要几项。

```ts
// playwright.config.ts
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  reporter: process.env.CI ? "github" : "list",
  use: {
    baseURL: "http://127.0.0.1:3000",
    trace: "on-first-retry",
  },
  projects: [{ name: "chromium", use: { ...devices["Desktop Chrome"] } }],
  webServer: {
    command: "pnpm build && pnpm start",
    url: "http://127.0.0.1:3000",
    reuseExistingServer: !process.env.CI,
    timeout: 180_000,
  },
});
```

`webServer` 让 Playwright 自己构建并启动服务，跑完自动关掉。`reuseExistingServer` 在本地复用已经开着的服务，省掉每次构建。CI 里从零开始，保证跑的是构建产物。

端到端跑构建产物，不跑开发服务器。dev 模式下 React 会做重复渲染检查，行为和生产有差异，拿 dev 跑端到端会漏掉只在生产出现的问题。

一条关键路径的用例。

```ts
// e2e/team.spec.ts
import { expect, test } from "@playwright/test";

test("注册后能建团队并看到空状态", async ({ page }) => {
  const email = `e2e-${Date.now()}@example.com`;

  await page.goto("/signup");
  await page.getByLabel("邮箱").fill(email);
  await page.getByLabel("密码").fill("test-password-123");
  await page.getByRole("button", { name: "注册" }).click();

  await page.waitForURL("**/onboarding");
  await page.getByLabel("团队名称").fill(`端到端 ${Date.now()}`);
  await page.getByRole("button", { name: "创建团队" }).click();

  await expect(page.getByRole("heading", { name: "文件" })).toBeVisible();
  await expect(page.getByText("还没有文件")).toBeVisible();
});
```

定位元素优先用角色和标签：`getByRole`、`getByLabel`。这两个查询同时也在验证可访问性：按钮没有可读名字、输入框没关联 label，查询就失败。用 CSS 选择器定位，测试和可访问性都测不到。

等待用 `waitForURL`、`expect(...).toBeVisible()` 这类可重试的断言，别用 `waitForTimeout`。固定等待在慢机器上会偶发失败，加长又会拖慢整套测试。

Playwright 在失败时自动保存 trace，用 `pnpm exec playwright show-trace` 打开。trace 里有每一步的 DOM 快照和网络请求，排查比日志快。

可访问性断言单独一条用例。

```ts
// e2e/a11y.spec.ts
import AxeBuilder from "@axe-core/playwright";
import { expect, test } from "@playwright/test";

test("团队首页没有严重可访问性问题", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("邮箱").fill(process.env.E2E_EMAIL!);
  await page.getByLabel("密码").fill(process.env.E2E_PASSWORD!);
  await page.getByRole("button", { name: "登录" }).click();
  await page.waitForURL("**/dashboard");

  const results = await new AxeBuilder({ page }).analyze();
  const serious = results.violations.filter(
    (v) => v.impact === "serious" || v.impact === "critical",
  );
  expect(serious).toEqual([]);
});
```

只筛 `serious` 和 `critical`。`minor` 和 `moderate` 常见于颜色对比度，一次会有几十条，全部修完成本高。先把键盘不可达、按钮没有名字这类问题清掉。

端到端不覆盖像素级样式。视觉回归靠截图对比，维护成本高，当前项目没做。

端到端的数据要可辨识、可清理。邮箱和团队名带时间戳，别和真实数据混淆。

六条端到端用例的清单：注册并建团队、邀请成员、上传文件、升级订阅、越权访问被拒、空状态显示。每条独立，不依赖前一条留下的数据。越权那条用两个账号，一个建团队，另一个直接访问 URL 断言 404。

测试账号用环境变量传，别写死在仓库里。CI 用 secrets，本地用 `.env.test`，`.env.test` 加进 `.gitignore`。清理靠定时任务或者测试账号定期重置，别在用例里删数据，删除动作本身可能触发别的逻辑。

## 39.9 放进 CI

流水线做四件事：装依赖、跑单元与集成测试、跑端到端、失败时留下证据。

```yaml
# .github/workflows/test.yml
name: test

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 10

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm

      - run: pnpm install --frozen-lockfile

      - uses: supabase/setup-cli@v1
        with:
          version: latest

      - run: supabase start

      - run: supabase status -o env >> $GITHUB_ENV

      - run: pnpm test

      - run: pnpm exec playwright install --with-deps chromium

      - run: pnpm exec playwright test
        env:
          E2E_EMAIL: ${{ secrets.E2E_EMAIL }}
          E2E_PASSWORD: ${{ secrets.E2E_PASSWORD }}
          NEXT_PUBLIC_SUPABASE_URL: ${{ env.API_URL }}
          NEXT_PUBLIC_SUPABASE_ANON_KEY: ${{ env.ANON_KEY }}

      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 7
```

`supabase status -o env` 输出的是本地实例的地址和密钥，追加进 `GITHUB_ENV` 之后，后续步骤都能读到。这一步容易写错成 `>> .env`，那样只对当前步骤有效。

本地模拟 CI 的做法：`pnpm install --frozen-lockfile && supabase start && pnpm test && pnpm exec playwright test`。和 CI 的差别只有浏览器缓存，行为一致。提交前跑一遍，能少一轮推送等待。

`--frozen-lockfile` 确保 CI 装的依赖和锁文件完全一致。第 44 章会展开讲锁文件。

缓存 Playwright 浏览器能省一分钟，加一段带 `actions/cache` 的步骤，`path` 指向 `~/.cache/ms-playwright`。

CI 里不要跑的东西：`next analyze`、压测、完整的依赖审计。这些耗时以分钟计，放在本地或专门的定时任务里。

CI 时间预算按五分钟算。装依赖四十秒，单元与集成二十秒，构建四十秒，端到端五十秒，浏览器安装命中缓存，整体两分半。超过五分钟查两件事：每个步骤有没有重复安装，端到端有没有跑全量。用例多到十分钟以上时，用 `--shard` 拆成多个 job 并行。

## 39.10 边界与失败模式

测试跑得慢，往往是因为分层没做。单元测试里连了数据库，或者集成测试里起了浏览器，整套就会从几秒涨到几分钟。

偶发失败（flaky）不能靠重试掩盖。看到一个用例三次里红一次，先查三件事：有没有固定等待、有没有依赖执行顺序、有没有并发写同一行数据。三种都排除之后，才是框架或环境的问题。

测试数据要唯一。用固定邮箱建用户，第二次跑就撞唯一约束。用时间戳加随机后缀，测试之间互不干扰。

清理顺序有讲究。先删子表再删父表，或者在外键上设 `on delete cascade`。清理失败会留下脏数据，下一次测试可能因为「团队已存在」失败。

时区差异会让本地绿、CI 红。断言时间字段时统一转成 UTC 再比，别依赖机器默认时区。

不要在测试里 `truncate`。本地库里可能有你手动造的数据，CI 里 truncate 又会和并行用例冲突。按 ID 删自己建的数据。

断言要写到能定位问题的程度。`expect(res.status).toBe(200)` 和 `expect(data).toEqual([])` 都算精确断言。`expect(data).toBeDefined()` 永远为真，等于没测。

用例名字要写清楚失败的场景，`it("非成员看不到成员列表")` 比 `it("RLS 测试 2")` 有用。失败时 CI 日志直接给出结论，不用翻代码。

## 39.11 检查点

1. `pnpm test` 全绿，输出里单元测试与集成测试分开统计，总耗时在十五秒以内。
2. 把 `team_members` 的 select 策略条件改成 `true`，`pnpm test` 必须红，报错指向「非成员看不到成员列表」这条用例。改回去恢复绿。
3. `pnpm test:e2e` 全绿。把登录按钮上的 `aria-label` 删掉，`getByRole("button", { name: "登录" })` 应该超时失败。
4. `grep -rn "role === 'owner'" src` 只命中 `src/lib/permissions.ts`，其余调用点都走 `canInvite()` 这类函数。
5. `grep -rn "waitForTimeout" e2e` 结果为空，所有等待都用了可重试断言。
6. 新建一个空测试文件 `src/lib/empty.test.ts`，`pnpm test` 输出 `No test found` 并退出码非零，说明配置没有把不该扫的目录扫进来。

## 39.12 常见错误

1. 找不到 `@/lib/supabase/server`

现象：`Cannot find module '@/lib/supabase/server'`。原因是 Vitest 不认识 `tsconfig.json` 里的 `paths`。装 `vite-tsconfig-paths`，把它加进 `plugins` 数组。

**2. expect 未定义**

现象：`ReferenceError: expect is not defined`。测试文件没被 Vitest 收集，或者用了 Jest 的全局函数却没导入。从 `vitest` 显式 `import { expect }`，并确认文件名匹配 `include` 的 glob。

3. 集成测试连不上本地 Supabase

现象：`Neither apiKey nor config.authenticator provided`。`.env.local` 没加载，或者变量名拼错。检查 `setup.ts` 里的 dotenv 路径，以及 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 是否为空。

**4. 取会话拿到 null**

现象：`TypeError: Cannot read properties of null (reading 'user')`。测试里用的是未登录的客户端，或者登录还没完成就发了查询。`signInWithPassword` 要 `await`，会话写入完成后再查数据。

**5. 浏览器没安装**

现象：`browserType.launch: Executable doesn't exist`。Playwright 的浏览器二进制没下。跑 `pnpm exec playwright install --with-deps chromium`，CI 里漏了这一步就每个用例都失败。

6. AxeBuilder 构造失败

现象：`AxeBuilder is not a constructor`。导入方式写错了。`@axe-core/playwright` 用默认导入，写成 `import AxeBuilder from "@axe-core/playwright"`，不要用命名导入。

六条都满足之后，再进入下一章。

## 39.13 这一章在做什么

这一章把测试分成三层：单元测纯逻辑，集成测数据库和 RLS，端到端测关键路径。工具用 Vitest 加 Playwright，配置尽量短。异步服务端组件测不了渲染，就把取数逻辑抽成函数，渲染交给端到端。RLS 和 webhook 这两块必须连真实环境测，故意改坏一次，确认测试真的会红。

测试的价值在它挡住回归的那一刻，不在覆盖率数字上。数量按关键路径来定，四十个单元测试加六条端到端用例，足够覆盖当前的功能面。

第 40 章换一个角度：功能正确之后，系统能同时服务多少人，什么先垮，怎么用压测把答案量出来。
