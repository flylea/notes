# 第 46 章 自托管部署与自有域名

这一章讲把 teamstack 部署到自有 VPS 的完整路径。目标是得到一个 `https://teamstack.example.com` 可访问的实例：应用以非 root 用户运行，只暴露 80 和 443 两个端口，数据库迁移在服务启动前完成，重启和升级都不丢请求。

涉及七样东西：

- Next.js 的 standalone 构建产物
- Docker 多阶段镜像与 Docker Compose 编排
- Caddy 或 Nginx 反向代理
- Cloudflare 的 DNS 与 Tunnel
- Turnstile 人机校验
- ufw 防火墙
- 数据库迁移脚本

版本基线是 Next.js 16.4.6、Node.js 22、Caddy 2.8、Docker 27、PostgreSQL 16。下文命令在 Ubuntu 24.04 上执行过；标“未验证”的部分需要读者在自己的机器上确认。

## 46.1 构建产物：standalone 是什么

自托管的起点是一份能独立运行的构建产物。Next.js 默认产物依赖 `node_modules`，复制到服务器时要连同依赖一起带走，体积大、层级深。

`output: "standalone"` 改变这一点。构建时 Next.js 追踪每个路由实际用到的文件，把服务端代码和最小依赖复制到 `.next/standalone`，并生成一个入口 `server.js`。

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  output: 'standalone',
}

export default nextConfig
```

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  // 产出 .next/standalone：最小运行集 + 自带 server.js
  output: 'standalone',
}

export default nextConfig
```

构建完成后，产物目录需要手工补两样东西。`public/` 和 `.next/static` 不会被自动复制，少了它们页面能返回 HTML，但样式、图片、脚本全部 404。

```bash
pnpm build
ls .next/standalone            # 应该能看到 server.js、node_modules、.next
cp -r public .next/standalone/
cp -r .next/static .next/standalone/.next/
PORT=3100 HOSTNAME=127.0.0.1 node .next/standalone/server.js
```

命令输出里的路由表先记住两个符号。`○` 表示构建时预渲染，`ƒ` 表示按请求渲染。部署后排查“页面为什么是旧的”，第一眼要看这个表。

```
▲ Next.js 16.4.6
- Local:        http://localhost:3100
- Network:      http://0.0.0.0:3100
✓ Ready in 241ms
```

产物可以先在本机验证再进镜像。设好环境变量后在产物目录直接 `node server.js`，访问 3000 端口，能登录说明产物完整；这一步能提前发现漏复制的目录。

产物形态决定了后面所有步骤。standalone 自带 `server.js`，容器里只需要 Node.js 运行时，不需要 pnpm，也不需要完整源码。

如果项目在 monorepo 里，追踪根目录会算错。用 `outputFileTracingRoot` 指到仓库根，用 `outputFileTracingIncludes` 把运行时才读的文件（模板、字典、证书）显式带进产物。

```ts
import path from 'node:path'
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  output: 'standalone',
  // 让追踪从仓库根开始（monorepo 必需；单包项目可省略）
  outputFileTracingRoot: path.join(__dirname, '../..'),
  // key 是路由 glob，value 是相对项目根的文件 glob
  outputFileTracingIncludes: {
    '/api/export': ['./templates/**/*'],
    '/settings/billing': ['./assets/fonts/**/*'],
  },
}

export default nextConfig
```

```text
浏览器
  │  https://teamstack.example.com:443
  ▼
Cloudflare（可选：橙云代理 / Tunnel 隧道 / 灰云直连）
  │
  ▼
Caddy 或 Nginx（TLS 终止、限流、请求体上限、压缩、缓冲策略）
  │  http://app:3000   ← 只在 Docker 内网，不发布到公网
  ▼
Next.js standalone 容器（非 root，PORT=3000，HOSTNAME=0.0.0.0）
  │
  ├─→ Supabase（Postgres / Storage / Auth）
  ├─→ Resend（邮件）
  └─→ Stripe（支付）
```

`sharp` 是官方文档提到的唯一额外依赖，用于图片优化。它带平台相关的二进制文件，在 macOS 上装好再复制进 Linux 镜像会报 `Could not load the "sharp" module`。安装要在构建镜像的 Linux 阶段做。

```bash
pnpm add sharp
```

构建时还有两个环境变量值得设。`NEXT_TELEMETRY_DISABLED=1` 关掉匿名统计，容器里没有外网时它会重试，拖慢启动。`NODE_ENV=production` 由镜像阶段固定，运行期再改会让 React 走进开发分支，体积和性能都退化。

standalone 有三个边界。第一，它只包含构建时能静态分析到的文件，运行时用 `fs` 读的动态路径要写进 `outputFileTracingIncludes`。第二，`.next/cache` 默认落在容器本地磁盘，多副本时各存一份。第三，`server.js` 读 `PORT` 和 `HOSTNAME` 两个环境变量，容器里要把 `HOSTNAME` 设成 `0.0.0.0`，否则只监听回环地址。

## 46.2 多阶段 Dockerfile

镜像分四个阶段：`base` 装运行环境，`deps` 装依赖，`builder` 做构建，`runner` 只保留运行所需。最终镜像里没有源码、没有 pnpm、没有构建缓存。

```dockerfile
# Dockerfile
# syntax=docker/dockerfile:1.7

# ---------- 基础层 ----------
FROM node:22-alpine AS base
# corepack 按 package.json 的 packageManager 字段选择 pnpm 版本
RUN corepack enable
WORKDIR /app
ENV NEXT_TELEMETRY_DISABLED=1

# ---------- 依赖层：只在 lockfile 变化时重装 ----------
FROM base AS deps
# pnpm 的 store 挂载让重建时不必重新下载包
RUN --mount=type=cache,id=pnpm-store,target=/root/.local/share/pnpm/store \
    pnpm install --frozen-lockfile

# ---------- 构建层 ----------
FROM base AS builder
COPY --from=deps /app/node_modules ./node_modules
COPY . .

# NEXT_PUBLIC_ 变量在 build 时被内联进客户端产物，必须作为构建参数传入
ARG NEXT_PUBLIC_APP_URL
ARG NEXT_PUBLIC_SUPABASE_URL
ARG NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
ARG NEXT_PUBLIC_TURNSTILE_SITE_KEY
ENV NEXT_PUBLIC_APP_URL=$NEXT_PUBLIC_APP_URL \
    NEXT_PUBLIC_SUPABASE_URL=$NEXT_PUBLIC_SUPABASE_URL \
    NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=$NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY \
    NEXT_PUBLIC_TURNSTILE_SITE_KEY=$NEXT_PUBLIC_TURNSTILE_SITE_KEY

# 构建 ID 用 git commit，避免「build id 相同但产物变了」
ARG GIT_SHA=dev
ENV GIT_SHA=$GIT_SHA

RUN pnpm build

# ---------- 运行层 ----------
FROM base AS runner
ENV NODE_ENV=production \
    PORT=3000 \
    HOSTNAME=0.0.0.0

# 非 root：uid 1001，和官方模板保持一致的约定
RUN addgroup -g 1001 -S nodejs \
 && adduser -S -u 1001 -G nodejs nextjs

# standalone 产物本身就是运行根，直接拷到 /app
COPY --from=builder --chown=nextjs:nodejs /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

# 迁移不在 standalone 追踪范围内，单独复制；入口脚本负责「先迁移再起服务」
COPY --from=builder --chown=nextjs:nodejs /app/supabase/migrations ./supabase/migrations
COPY --from=builder --chmod=755 --chown=nextjs:nodejs /app/scripts/docker-entrypoint.sh ./docker-entrypoint.sh
COPY --from=builder --chown=nextjs:nodejs /app/scripts/migrate.mjs ./scripts/migrate.mjs

USER nextjs
EXPOSE 3000

# 健康检查直接用 Node 发请求，镜像里没有 curl
HEALTHCHECK --interval=30s --timeout=3s --start-period=30s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/api/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

ENTRYPOINT ["/app/docker-entrypoint.sh"]
CMD ["node", "server.js"]
```

构建上下文要排除无关文件。`.git`、`node_modules`、`.next` 都排除，否则每次构建都要上传几百 MB，缓存也失效。

```gitignore
# .dockerignore
.git
.next
node_modules
.env
.env.*
!.env.example
npm-debug.log*
pnpm-debug.log*
coverage
playwright-report
test-results
*.tsbuildinfo
Dockerfile
compose.yaml
Caddyfile
```

镜像里有两处容易出错。第一，`COPY` 的层级必须和产物结构一致。写成 `COPY --from=builder /app/.next/standalone ./`，`server.js` 才会落在 `/app/server.js`；少一层就变成 `/app/standalone/server.js`，启动时报下面的错。

```text
Error: Cannot find module '/app/server.js'
```

第二，非 root 用户要对缓存目录有写权限。镜像里用 uid 1001 的 `nextjs` 用户运行，`.next/cache` 由 root 创建时，运行时写缓存会失败。

```text
Error: EACCES: permission denied, mkdir '.next/cache'
```

改法是在 `runner` 阶段 `chown -R nextjs:nodejs .next`，或者把缓存目录挂成卷并预先改属主。

`HEALTHCHECK` 的三个参数要按实际响应时间调。`interval=30s`、`timeout=5s`、`retries=3` 是常见组合；数据库慢查询时健康检查会先超时，容器被判为不健康而重启，形成抖动。接口里只做一次轻量查询，不要拼多表。

健康检查要区分“进程活着”和“能对外服务”。只 `curl` 首页不够，首页可能是静态文件；要让接口真的查一次数据库。

```ts
// src/app/api/health/route.ts
import { NextResponse } from 'next/server'
import { sql } from 'kysely'
import { db } from '@/lib/db'

// 健康检查不能被缓存，也不能在构建期预渲染
export const dynamic = 'force-dynamic'

export async function GET() {
  const startedAt = Date.now()
  try {
    await sql`select 1`.execute(db)
    return NextResponse.json(
      { ok: true, db: 'up', latencyMs: Date.now() - startedAt },
      { headers: { 'cache-control': 'no-store' } },
    )
  } catch (error) {
    // 只记错误类型，不记连接串
    console.error('[health] db check failed', error instanceof Error ? error.name : 'unknown')
    return NextResponse.json(
      { ok: false, db: 'down' },
      { status: 503, headers: { 'cache-control': 'no-store' } },
    )
  }
}
```

构建镜像用 BuildKit。跨架构时显式指定平台，Apple Silicon 上构建 x86 镜像必须加 `--platform`，否则在 VPS 上启动报 `exec format error`。

```bash
docker build -t teamstack:local .
docker run --rm -p 3100:3000 --env-file .env.production teamstack:local
```

```bash
docker buildx build --platform linux/amd64 -t teamstack:local --load .
```

镜像构建完先在本地跑一次。`docker run --rm -p 3100:3000 --env-file .env.production teamstack:local`，登录一次，再退出；能登录再推到仓库，省一轮往返。

镜像大小是取舍点。完整源码加 `node_modules` 的镜像大约 1.2–1.5 GB；standalone 加 Alpine 基础镜像通常在 250–400 MB。体积影响拉取时间和磁盘占用，不影响运行速度。

镜像层序影响构建速度。把 `package.json` 和 `pnpm-lock.yaml` 的复制放在源码复制之前，依赖层就能命中缓存；顺序反过来，改一行代码会让 `pnpm install` 全部重跑。BuildKit 的 `--mount=type=cache` 进一步把 pnpm 的存储目录挂在构建之间，第二次构建通常快一半。

不要在 VPS 上直接构建。2 核 2 GB 的机器跑 `next build` 会触发 OOM，进程被内核杀掉，日志里只有一行 `Killed`。构建放在 CI 或本地，服务器只负责拉镜像。

## 46.3 Compose 编排与网络边界

三个服务组成一个部署单元。`app` 跑 Next.js，`caddy` 接公网流量，`cloudflared` 只在用 Tunnel 时启动。`app` 不发布端口，公网只能通过反代访问它。

```yaml
# compose.yaml
name: teamstack

services:
  app:
    image: ghcr.io/${GHCR_OWNER}/teamstack:${IMAGE_TAG:-latest}
    env_file: .env.production
    environment:
      NODE_ENV: production
      PORT: "3000"
      HOSTNAME: "0.0.0.0"
      # 入口脚本据此决定是否跑迁移；调试时可以设 0 跳过
      RUN_MIGRATIONS: "1"
      DEPLOYMENT_ID: ${IMAGE_TAG:-local}
    volumes:
      # Data Cache 需要可写；匿名卷会在重建容器时丢缓存
      - next-cache:/app/.next/cache
    # 注意：没有 ports。应用端口只在 Docker 网络内可见
    restart: unless-stopped
    stop_grace_period: 30s
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/api/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 30s

  caddy:
    image: caddy:2-alpine
    depends_on:
      app:
        condition: service_healthy
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"   # HTTP/3
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - ./certs:/etc/caddy/certs:ro   # Cloudflare Origin Certificate
      - caddy-data:/data
      - caddy-config:/config
    restart: unless-stopped

  # 选 Cloudflare Tunnel 时启用：docker compose --profile tunnel up -d
  cloudflared:
    image: cloudflare/cloudflared:latest
    profiles: ["tunnel"]
    command: tunnel --no-autoupdate run --token ${CLOUDFLARE_TUNNEL_TOKEN}
    depends_on:
      app:
        condition: service_healthy
    restart: unless-stopped

volumes:
  next-cache:
  caddy-data:
  caddy-config:
```

环境变量放在 `.env.production`，文件权限设成 600。`DATABASE_URL` 走 6543 端口，`DIRECT_URL` 走 5432 端口，两个都要有：前者是连接池，后者给迁移用，迁移要拿会话级锁。

```bash
# .env.production
NODE_ENV=production
NEXT_PUBLIC_APP_URL=https://teamstack.example.com

# 应用查询走事务池（6543）；迁移走直连（5432）
DATABASE_URL=postgresql://postgres.<project-ref>:<password>@aws-0-ap-southeast-1.pooler.supabase.com:6543/postgres?pgbouncer=true
DIRECT_URL=postgresql://postgres:<password>@db.<project-ref>.supabase.co:5432/postgres

NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xxx
SUPABASE_SECRET_KEY=sb_secret_xxx

# 多实例必须固定，否则每次构建都换密钥，旧标签页的 action 全部失效
NEXT_SERVER_ACTIONS_ENCRYPTION_KEY=<openssl rand -base64 32 的输出>

RESEND_API_KEY=re_xxx
STRIPE_SECRET_KEY=sk_live_xxx
STRIPE_WEBHOOK_SECRET=whsec_xxx

TURNSTILE_SECRET_KEY=0x4AAAAAAA_xxx
NEXT_PUBLIC_TURNSTILE_SITE_KEY=0x4AAAAAAA_xxx

# 镜像仓库与版本
GHCR_OWNER=your-org
IMAGE_TAG=localhost
CLOUDFLARE_TUNNEL_TOKEN=
```

`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 必须固定。它用于加密 Server Action 的闭包参数，多副本之间不一致时，用户在 A 副本提交的表单到 B 副本会报 `Failed to decrypt action bound arguments`。生成一次，写进密钥管理，之后不要改。

```bash
openssl rand -base64 32
# 16/24/32 字节的 AES key 都合法，官方默认 32 字节
```

启动顺序由 `depends_on` 和健康检查控制。`caddy` 等 `app` 健康后再启动，避免反代先起来、把 502 暴露给用户。

```bash
docker compose up -d app
docker compose ps
```

环境变量按读取位置分两类。构建期变量要在 `Dockerfile` 里用 `ARG` 声明，再 `ENV` 进去；只在运行期读的变量由 compose 注入，改了重启即可生效。把密钥当构建参数传会让它留进镜像历史，`docker history` 能看到。

服务之间靠默认网络通信，服务名就是主机名。`app` 访问数据库走外网连接串，`caddy` 访问 `app:3000` 走容器内 DNS，两者都不经过宿主机端口。

编排有两个边界。第一，`docker compose up -d` 在镜像变化时会重建容器，中间有几百毫秒到几秒的不可用。要求零中断时用滚动方式，见 46.10。第二，compose 不会自动清理旧镜像，磁盘会在几十次发布后满掉，清理见 46.12。

## 46.4 反向代理与转发头

反向代理负责四件事：终止 TLS、按域名分流、压缩与缓冲控制、传递真实客户端信息。应用只监听容器网络内的 3000 端口。

Caddy 的配置最短。它会自动申请证书，把 HTTP 跳转到 HTTPS，并为静态资源加长缓存。

```caddyfile
# Caddyfile
{
  # 邮箱给 ACME 用；用 Cloudflare Origin Certificate 时这行不影响
  email ops@example.com
}

teamstack.example.com {
  encode zstd gzip

  # 请求体上限：Server Action 默认 1MB，附件上传按业务放宽
  request_body {
    max_size 25MB
  }

  # 静态资源长缓存（文件名带 hash，可以 immutable）
  @immutable path /_next/static/*
  header @immutable Cache-Control "public, max-age=31536000, immutable"

  # 健康检查不写访问日志，避免刷屏
  @health path /api/health
  log_skip @health

  reverse_proxy app:3000 {
    # 关掉缓冲，SSE / 流式 RSC 才能逐块到达
    flush_interval -1

    # Caddy 默认会设置 X-Forwarded-For / X-Forwarded-Proto / X-Forwarded-Host
    # 这里显式写出来，方便确认它们没被覆盖
    header_up Host {host}
    header_up X-Forwarded-Host {host}
    header_up X-Forwarded-Proto {scheme}
  }

  header {
    Strict-Transport-Security "max-age=63072000; includeSubDomains; preload"
    X-Content-Type-Options "nosniff"
    Referrer-Policy "strict-origin-when-cross-origin"
    -Server
  }
}

www.teamstack.example.com {
  redir https://teamstack.example.com{uri} permanent
}
```

```bash
docker compose up -d caddy
docker compose logs -f --tail=50 caddy
```

验证时看响应头。`HTTP/2 200` 说明 TLS 和 HTTP/2 都正常，`strict-transport-security` 说明 HSTS 生效。

```bash
curl -sSI https://teamstack.example.com | head -5
curl -sSI https://teamstack.example.com/dashboard | grep -i '^location'
```

用 Cloudflare 的源站证书时，Caddy 不再申请 Let's Encrypt，改成读证书文件。Cloudflare 免费签发的源站证书有效期 15 年，只对 Cloudflare 回源流量可信。

```caddyfile
# Caddyfile 片段：使用 Cloudflare Origin Certificate
teamstack.example.com {
  tls /etc/caddy/certs/origin.pem /etc/caddy/certs/origin-key.pem
  reverse_proxy app:3000 {
    flush_interval -1
  }
}
```

日志格式要包含上游耗时。Caddy 默认日志里有 `duration` 和 `status`，按路径聚合能看到慢接口；Nginx 的 `log_format` 加 `$upstream_response_time` 才有同样的信息。

用 Nginx 时有三处必须改。第一，`proxy_http_version 1.1` 加 `proxy_set_header Connection ""`，否则到上游的是 HTTP/1.0，流式响应会被切断。第二，`proxy_buffering off`，否则分块响应被攒在 Nginx 里，首屏变慢。第三，`gzip off`，压缩会等待数据攒够一块，和流式渲染冲突。

```nginx
# /etc/nginx/conf.d/teamstack.conf
upstream teamstack_app {
  server app:3000;
  keepalive 32;
}

server {
  listen 80;
  server_name teamstack.example.com;
  return 301 https://$host$request_uri;
}

server {
  listen 443 ssl;
  http2 on;
  server_name teamstack.example.com;

  ssl_certificate     /etc/nginx/certs/origin.pem;
  ssl_certificate_key /etc/nginx/certs/origin-key.pem;
  ssl_protocols TLSv1.2 TLSv1.3;

  # 上传体积：和 Server Action 的 bodySizeLimit 一起调
  client_max_body_size 25m;

  # 只信任 Cloudflare 的段，并从 CF-Connecting-IP 取真实 IP
  set_real_ip_from 173.245.48.0/20;
  set_real_ip_from 103.21.244.0/22;
  set_real_ip_from 104.16.0.0/13;
  real_ip_header CF-Connecting-IP;

  location /_next/static/ {
    proxy_pass http://teamstack_app;
    proxy_set_header Host $host;
    add_header Cache-Control "public, max-age=31536000, immutable";
  }

  location / {
    proxy_pass http://teamstack_app;
    proxy_http_version 1.1;

    # 复用上游连接，必须清空 Connection
    proxy_set_header Connection "";

    # 这四个头是 Next.js 判断外部地址的依据，缺一个就出怪问题
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host $host;

    # 流式：关闭缓冲，并告诉上游不要被缓冲
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;

    # 压缩交给 Next 或 Cloudflare，避免代理攒数据延迟首块
    gzip off;
  }
}
```

出现 502 时按三步定位：应用是否活着、容器网络是否通、反代配置是否指对端口。

```bash
# 1. 应用自己活着吗
docker compose ps app
# 2. 反代到应用这一段通不通（在 caddy 容器里请求，绕开公网）
docker compose exec caddy wget -qO- http://app:3000/api/health
# 3. 反代日志里最后一条错误
docker compose logs --tail=30 caddy
```

Server Action 会校验请求的 `Origin` 与 `Host`。反向代理没透传原始 Host 时，两个值不一致，请求被拒绝并报 `Invalid Server Actions request`。这时要么让反代传 `X-Forwarded-Host`，要么在配置里显式允许来源。

```ts
// next.config.ts
const nextConfig: NextConfig = {
  experimental: {
    serverActions: {
      // 只在反代无法正确透传 Host 时使用；精确匹配，端口也要写
      allowedOrigins: ['teamstack.example.com', 'www.teamstack.example.com'],
      // 默认 1MB；附件走独立上传接口时保持默认，别无脑放大
      bodySizeLimit: '2mb',
    },
  },
}
```

`allowedOrigins` 是精确匹配，含端口。写 `https://teamstack.example.com` 时，带 `:443` 的请求也可能匹配失败；不确定就先看日志里的原始值。

转发头有五个，缺一个就会引发一类故障。`Host` 决定应用认为自己在哪个域名；`X-Forwarded-Host` 给 Server Action 校验用；`X-Forwarded-Proto` 决定生成的链接是 http 还是 https；`X-Forwarded-For` 记录链路 IP；`CF-Connecting-IP` 是 Cloudflare 提供的真实客户端 IP。应用读 IP 时优先取 `CF-Connecting-IP`，其次取 `X-Forwarded-For` 的第一段。

取真实 IP 需要反代显式设置。Nginx 要配 `real_ip_header CF-Connecting-IP` 和可信网段，否则 `$remote_addr` 永远是 Cloudflare 的地址，限流会把所有用户算成同一个来源。Caddy 默认透传，但应用侧仍要优先读 `CF-Connecting-IP`。

WebSocket 靠反代升级连接。Caddy 自动处理 `Upgrade` 头；Nginx 要显式写 `proxy_set_header Upgrade $http_upgrade` 和 `proxy_set_header Connection "upgrade"`，漏掉时实时连接会在握手阶段返回 400。

代理超时要大于应用的响应时间。Nginx 的 `proxy_read_timeout` 默认 60 秒，应用里跑 90 秒的导出任务会先被代理切断。`keepAliveTimeout` 要大于下游代理的空闲超时，否则连接被应用先关，代理侧看到的是 502。

## 46.5 DNS 的三种接法

域名解析有三种方案，区别在于流量是否经过 Cloudflare、源站是否暴露公网 IP。

第一种是灰云直连。Cloudflare 只做 DNS，A 记录指向 VPS 公网 IP，TLS 由源站自己申请。

```text
类型   名称    内容                代理状态
A      @       203.0.113.10        仅 DNS（灰云）
A      www     203.0.113.10        仅 DNS
AAAA   @       2001:db8::10        仅 DNS（有 IPv6 才加）
```

第二种是橙云代理。记录同样指向源站，但开启代理，用户连的是 Cloudflare 的 IP，源站只接受 Cloudflare 回源。SSL 模式必须选 `Full (strict)`，源站要有有效证书；选 `Flexible` 会让源站收到 http 请求，应用里强制跳转 https 时形成循环，浏览器报 `ERR_TOO_MANY_REDIRECTS`。

```text
类型   名称    内容                    代理状态
A      @       203.0.113.10            已代理（橙云）
CNAME  www     teamstack.example.com   已代理
```

橙云要放行两个路径。申请证书时的 `/.well-known/acme-challenge/*` 不能被拦截，Vercel 域名验证用的 `/.well-known/vercel/*` 也要放行。这两条写在 WAF 的跳过规则里。

第三种是 Cloudflare Tunnel。`cloudflared` 从服务器主动向 Cloudflare 建长连接，源站不需要公网 IP，也不用开放 80 和 443。适合家里宽带、NAT 后面、或不希望暴露 IP 的机器。

```bash
docker compose --profile tunnel up -d cloudflared

# 或在面板里加 Public Hostname：
#   teamstack.example.com → http://app:3000
# 面板会自动创建 CNAME：teamstack → <tunnel-id>.cfargotunnel.com（橙云）
```

```bash
cloudflared tunnel login
cloudflared tunnel create teamstack
cloudflared tunnel route dns teamstack teamstack.example.com
cloudflared tunnel run --token <token> teamstack
```

用 Tunnel 时可以用 DNS 面板建 CNAME，也可以让 CLI 自动建。记录值形如 `<uuid>.cfargotunnel.com`，解析结果里看不到源站 IP。

```bash
dig +short teamstack.example.com
dig +short www.teamstack.example.com
curl -sSI https://teamstack.example.com | head -3
```

```bash
dig +short teamstack.example.com
dig +short teamstack.example.com @1.1.1.1
curl -sSI http://teamstack.example.com | head -5
```

TTL 决定切换速度。迁移服务器前把 TTL 调到 300 秒，切换后等一个 TTL 再改回 3600 秒；TTL 是 86400 时，改错记录要等一天才完全生效。

证书续期也要留监控。Caddy 自动续期，失败时只在日志里留一行；Cloudflare 源站证书 15 年有效，但私钥泄露要手工换。两种都要把到期时间加进巡检。

橙云加 Vercel 的组合要谨慎。Vercel 官方文档不推荐把 Cloudflare 代理放在前面。SSL 要设成 `Full (strict)`。证书验证路径要放行。缓存要避免和 Vercel 的 CDN 冲突。Bot Protection 在反代之后拿不到真实客户端特征。本书的主域名不经过 Vercel，遇到这个组合按官方文档逐条核。

子域和根域要分别处理。`www` 用 CNAME 指向主域，主域用 A 记录指向 IP；只配一个时，用户输入另一个会打不开。CAA 记录如果存在，要允许 Cloudflare 或 Let's Encrypt 签发，否则证书申请被拒。

灰云和橙云有一个共同限制：Cloudflare 的免费证书只覆盖一级子域。`teamstack.example.com` 可以，`a.b.example.com` 需要付费的 Advanced Certificate 或自己的证书。

橙云还有一个容易忽略的行为：开启“Cache Everything”后，带 `Set-Cookie` 的响应会被缓存，不同用户拿到同一份登录态。缓存规则里要排除登录、设置、API 这些路径，或者只在静态资源前缀上启用。

## 46.6 Cloudflare Tunnel 的边界

Tunnel 支持 WebSocket，实时功能可以正常走。它和 Argo Smart Routing 不兼容，同时开会在日志里看到连接重置。

长连接有空闲超时。默认 90 秒无数据会被断开，SSE 或 WebSocket 需要应用侧每 30 秒发一次心跳。

SSE 在 Tunnel 早期版本有过缓冲问题，表现是事件攒够一批才到浏览器。该问题在 2025 年 5 月修复，仍建议在自建 Nginx 上保留 `proxy_buffering off`，两层代理都可能缓冲。

Tunnel 的凭证有两种形态。交互式登录把证书写进 `~/.cloudflared`，适合人工管理；CI 里用 `TUNNEL_TOKEN` 环境变量，容器启动时直接连，不需要挂载证书目录。

不用 Docker 时，`cloudflared` 用 systemd 托管。单元文件要设 `Restart=always`，否则断网恢复后隧道不会自动重连。

```ini
# /etc/systemd/system/cloudflared.service
[Unit]
Description=Cloudflare Tunnel
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=cloudflared
ExecStart=/usr/local/bin/cloudflared tunnel --no-autoupdate run teamstack
Restart=always
RestartSec=5
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

Tunnel 的带宽受出口上行限制。家宽 100 Mbps 上行实际只有 30 Mbps，回源大文件时明显变慢；这种场景把静态资源放对象存储，别走源站。

Tunnel 的故障多在 DNS 一侧。`cloudflared tunnel info` 看不到连接，先确认机器能出站访问 443 和 7844，再看 Cloudflare 面板里隧道的状态。

## 46.7 Turnstile 人机校验

注册和邀请接受页是垃圾注册的主要入口。Turnstile 在客户端生成一个 token，服务端拿 token 和密钥向 Cloudflare 校验，通过才继续。

组件加载策略用 `afterInteractive`。放到 `lazyOnload` 会让用户在脚本加载完成前提交，token 为空被服务端拒绝；放到 `beforeInteractive` 会拖慢首屏。

前端组件只负责渲染和回填隐藏字段，字段名固定为 `cf-turnstile-response`。

```tsx
// src/app/(auth)/turnstile.tsx
'use client'

import Script from 'next/script'
import { useEffect, useRef } from 'react'

declare global {
  interface Window {
    turnstile?: {
      render: (el: HTMLElement, opts: Record<string, unknown>) => string
      reset: (id?: string) => void
    }
  }
}

export function Turnstile({ action }: { action: 'signup' | 'login' }) {
  const ref = useRef<HTMLDivElement>(null)
  const widgetId = useRef<string | null>(null)

  useEffect(() => {
    if (!window.turnstile || !ref.current) return
    widgetId.current = window.turnstile.render(ref.current, {
      sitekey: process.env.NEXT_PUBLIC_TURNSTILE_SITE_KEY,
      action,
      theme: 'auto',
    })
  }, [action])

  return (
    <>
      <Script
        src="https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit"
        strategy="afterInteractive"
        onLoad={() => {
          if (ref.current && window.turnstile) {
            widgetId.current = window.turnstile.render(ref.current, {
              sitekey: process.env.NEXT_PUBLIC_TURNSTILE_SITE_KEY,
              action,
            })
          }
        }}
      />
      <div ref={ref} />
      {/* 挂件会往表单里写这个隐藏字段，服务端读 cf-turnstile-response */}
      <noscript>
        <div className="rounded border p-3 text-sm">
          需要启用 JavaScript 才能完成人机验证。
        </div>
      </noscript>
    </>
  )
}
```

服务端函数做四件事：取 IP、调 Siteverify、校验 hostname 与 action、把错误码映射成可读文案。token 最长 2048 字符，有效期 300 秒，只能使用一次。

```ts
// src/lib/turnstile.ts
type VerifyResult = { ok: true; hostname: string } | { ok: false; reason: string }

export async function verifyTurnstile(
  token: FormDataEntryValue | null,
  remoteIp: string | null,
  expectedAction: string,
): Promise<VerifyResult> {
  if (typeof token !== 'string' || token.length === 0 || token.length > 2048) {
    return { ok: false, reason: 'missing-token' }
  }

  const body = new URLSearchParams({
    secret: process.env.TURNSTILE_SECRET_KEY!,
    response: token,
  })
  if (remoteIp) body.set('remoteip', remoteIp)

  const controller = new AbortController()
  const timer = setTimeout(() => controller.abort(), 10_000)
  try {
    const res = await fetch('https://challenges.cloudflare.com/turnstile/v0/siteverify', {
      method: 'POST',
      body,
      signal: controller.signal,
    })
    const data = (await res.json()) as {
      success: boolean
      hostname?: string
      action?: string
      'error-codes'?: string[]
    }

    if (!data.success) {
      return { ok: false, reason: (data['error-codes'] ?? []).join(',') || 'failed' }
    }
    // token 只对生成它的站点和 action 有效，顺手校验一遍
    if (data.hostname !== 'teamstack.example.com') {
      return { ok: false, reason: `hostname:${data.hostname}` }
    }
    if (data.action !== expectedAction) {
      return { ok: false, reason: `action:${data.action}` }
    }
    return { ok: true, hostname: data.hostname }
  } catch {
    return { ok: false, reason: 'verify-unavailable' }
  } finally {
    clearTimeout(timer)
  }
}
```

调用点在 Server Action 里，校验失败直接返回错误，不建用户。

```ts
// src/app/(auth)/signup/actions.ts
'use server'

import { headers } from 'next/headers'
import { verifyTurnstile } from '@/lib/turnstile'

export async function signup(formData: FormData) {
  const h = await headers()
  const ip = h.get('cf-connecting-ip') ?? h.get('x-forwarded-for')?.split(',')[0]?.trim() ?? null

  const check = await verifyTurnstile(formData.get('cf-turnstile-response'), ip, 'signup')
  if (!check.ok) {
    return { error: '人机验证没通过，请刷新页面重试。', code: check.reason }
  }

  // 真正的注册逻辑
}
```

手工验证一次接口，确认密钥和网络都正常。返回 `success: true` 说明服务端到 Cloudflare 的链路通。

```bash
curl -sS https://challenges.cloudflare.com/turnstile/v0/siteverify \
  -d "secret=$TURNSTILE_SECRET_KEY" \
  -d "response=<前端拿到的 token>" | jq
```

错误码对应不同处理。`invalid-input-response` 是 token 无效或过期，直接拒绝；`timeout-or-duplicate` 是 token 被重复使用，拒绝并提示刷新；`internal-error` 是 Cloudflare 侧故障，可以重试一次，仍失败就拒绝。`missing-input-secret` 属于配置错误，要在部署检查里拦住。

失败要按 fail-closed 处理。校验接口超时或返回 5xx 时，拒绝提交，不要放行。放行会让攻击者在 Cloudflare 故障时绕过校验。

`hostname` 必须校验。只校验 `success` 时，攻击者可以在自己的域名上渲染同一个 site key，拿到 token 后提交到你的接口。校验 `hostname` 等于生产域名，能挡住这类转发。

## 46.8 防火墙与端口暴露

公网只开三个端口：22 给 SSH，80 和 443 给反代。应用端口 3000 留在容器网络里。

先看谁在监听。`ss -ltnp` 的输出里，3000 只应出现在 `127.0.0.1` 或 Docker 网桥上，不应出现在 `0.0.0.0`。

```bash
ss -ltnp
```

ufw 的规则按服务放行。Docker 会自己写 iptables 规则，容器发布的端口会绕过 ufw，这一点在 46.3 已经用“不发布端口”规避。

```bash
# Ubuntu / Debian，VPS 上执行
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp comment 'ssh'
ufw limit 22/tcp comment 'ssh rate limit'
ufw allow 80/tcp comment 'http'
ufw allow 443/tcp comment 'https'
ufw --force enable
ufw status verbose
```

请求体大小有两道闸。反代层 `client_max_body_size 25m` 挡住超大上传，应用层 `bodySizeLimit` 挡住 Server Action 的参数。两处都设，任何一处漏掉，另一处也会返回 413，但错误来自不同层，排查时容易看错。

从外部验证一次。在另一台机器上 `curl` 3000 端口，期望是超时，而非 200。

```bash
# 宿主机上：3000 不应出现在 0.0.0.0 或 ::: 上
ss -ltnp | grep -E ':3000|:80|:443'

# 从另一台机器（不要在本机）：
curl --max-time 3 http://203.0.113.10:3000
# curl: (28) Connection timed out  ← 这才对
```

SSH 加固按顺序做，先确认新密钥能登录，再关密码登录，避免把自己锁在外面。

```bash
sudo ufw allow from <你的固定IP> to any port 22 proto tcp
sudo ufw delete allow 22/tcp
```

```bash
# /etc/ssh/sshd_config.d/99-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
MaxAuthTries 5
```

改完先测语法再 reload。`sshd -t` 通过后 reload 才安全，直接重启失败会让 SSH 服务停掉。

```bash
sshd -t && systemctl reload sshd
```

22 端口尽量限来源。把 SSH 限制在固定 IP 或跳板机，暴露在公网时把密码登录和 root 登录都关掉，只留密钥。改完在新终端验证一次，确认旧会话之外还能登录。

云厂商的安全组是第二层。ufw 只控制主机防火墙，VPS 控制台的入站规则仍然独立生效，两处都要核对。

SSH 层面再加一层自动封禁。`fail2ban` 读 `/var/log/auth.log`，5 次失败封 1 小时，能挡掉大部分暴力尝试。规则要放行自己的固定 IP，否则调试时会被封。

端口暴露的检查要定期做。新装一个监控 agent、临时开一个调试端口，都可能把 3000 暴露出去。把 `ss -ltnp` 加进每日巡检。

## 46.9 数据库迁移与启动顺序

迁移必须在应用启动前完成，顺序固定：备份、跑迁移、启动新版本、观察、清理旧结构。

```text
备份 → 迁移（向后兼容的加法）→ 启动新版本 → 观察 → 清理旧字段
```

迁移拆成三次发布，避免锁表。第一次加可空列和索引，旧代码继续跑；第二次回填数据；第三次加非空约束。

```sql
-- supabase/migrations/20261201090000_teams_add_slug.sql
-- migrate:no-transaction
alter table teams add column if not exists slug text;
-- 唯一索引必须并发建，否则会锁表；并发建不能放进事务
create unique index concurrently if not exists teams_slug_key
  on teams (slug) where slug is not null;
```

`CREATE INDEX CONCURRENTLY` 不能在事务里执行。迁移文件头部写 `-- migrate:no-transaction`，runner 会跳过事务包装；没有这一行时，PostgreSQL 报 `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`。

```sql
-- supabase/migrations/20261201100000_teams_backfill_slug.sql
-- 只回填还没值的行；分批做，避免一次锁太多
update teams
set slug = lower(regexp_replace(name, '[^a-zA-Z0-9]+', '-', 'g')) || '-' || substr(id::text, 1, 6)
where slug is null;
```

```sql
-- supabase/migrations/20261215090000_teams_slug_not_null.sql
alter table teams alter column slug set not null;
```

大表改结构要控制锁等待。迁移会话里先 `set lock_timeout = '3s'`，拿不到锁就失败退出，避免把整张表的写入卡住。加索引用 `CONCURRENTLY`，加列用可空默认值，改类型用新列加回填。

跑迁移前先备份。备份失败时不要继续，`pg_dump` 返回非零就退出，入口脚本的 `set -e` 会做这件事；手工执行时要自己判断返回值。

runner 用 `DIRECT_URL` 连 5432 端口，串行执行 `supabase/migrations` 下的文件，把已执行的版本写进 `supabase_migrations.schema_migrations`。启动时加一把 advisory lock，多副本同时启动只有一个在迁移。

```js
// scripts/migrate.mjs
import { readdir, readFile } from 'node:fs/promises'
import path from 'node:path'
import { Client } from 'pg'

const url = process.env.DIRECT_URL
if (!url) {
  console.error('[migrate] DIRECT_URL 未设置；迁移必须走 5432 直连，不要用 6543 事务池')
  process.exit(1)
}

const migrationsDir = path.resolve('supabase/migrations')
const lockId = 7214001

const client = new Client({
  connectionString: url,
  // Supabase 强制 TLS；证书链校验不过时放宽，严谨做法是指定 ca
  ssl: { rejectUnauthorized: false },
  application_name: 'teamstack-migrate',
})

await client.connect()

try {
  // 和 Supabase CLI 用同一张记录表，本地 db push 与线上 runner 不会各记一套
  await client.query('create schema if not exists supabase_migrations')
  await client.query(`
    create table if not exists supabase_migrations.schema_migrations (
      version    text primary key,
      name       text,
      statements text[]
    )
  `)

  // 会话级 advisory lock：多副本同时启动时只有一个能进
  await client.query('select pg_advisory_lock($1)', [lockId])

  const files = (await readdir(migrationsDir))
    .filter((f) => f.endsWith('.sql'))
    .sort()

  for (const file of files) {
    const version = file.split('_')[0]        // 20261115090000
    const name = file.replace(/\.sql$/, '')

    const { rowCount } = await client.query(
      'select 1 from supabase_migrations.schema_migrations where version = $1',
      [version],
    )
    if (rowCount) continue

    const sqlText = await readFile(path.join(migrationsDir, file), 'utf8')
    console.log(`[migrate] applying ${name}`)

    // CREATE INDEX CONCURRENTLY 这类语句不能放进事务，用文件头指令标记
    if (sqlText.startsWith('-- migrate:no-transaction')) {
      await client.query(sqlText)
      await client.query(
        'insert into supabase_migrations.schema_migrations (version, name, statements) values ($1, $2, $3)',
        [version, name, [sqlText]],
      )
      continue
    }

    await client.query('begin')
    try {
      await client.query(sqlText)
      await client.query(
        'insert into supabase_migrations.schema_migrations (version, name, statements) values ($1, $2, $3)',
        [version, name, [sqlText]],
      )
      await client.query('commit')
    } catch (error) {
      await client.query('rollback')
      throw new Error(`migration ${name} failed: ${error.message}`, { cause: error })
    }
  }

  console.log('[migrate] all migrations applied')
} finally {
  await client.query('select pg_advisory_unlock($1)', [lockId]).catch(() => {})
  await client.end()
}
```

容器入口脚本先迁移再启动应用。`set -eu` 保证迁移失败时不继续，`exec` 让 Node 进程接管 PID 1，SIGTERM 才能传到应用。

```sh
# scripts/docker-entrypoint.sh
#!/bin/sh
set -eu

if [ "${RUN_MIGRATIONS:-1}" = "1" ]; then
  echo "[entrypoint] applying migrations"
  # set -e：迁移非 0 退出时整个容器直接失败，不会带着半套 schema 起服务
  node scripts/migrate.mjs
fi

echo "[entrypoint] starting next server on ${HOSTNAME:-0.0.0.0}:${PORT:-3000}"
exec node server.js
```

单独跑迁移时用 `docker compose run`，不要用 `docker compose up`，后者会顺带启动应用。

```bash
# VPS 项目目录
docker compose pull
docker compose up -d --wait --wait-timeout 180
```

```bash
docker compose run --rm app node scripts/migrate.mjs
```

启动日志里应能看到迁移阶段和监听阶段两行。缺任何一行，说明入口脚本没被执行。

```text
[entrypoint] applying migrations
[migrate] applying 20261201090000_teams_add_slug
[migrate] all migrations applied
[entrypoint] starting next server on 0.0.0.0:3000
```

停住的条件要写进脚本。迁移返回非零时，入口脚本直接退出，容器进入 `restarting`；compose 的 `--wait` 等到超时报错，发布脚本停止。此时旧容器还在跑，流量不受影响。绕过这一步的代价是代码先上线、结构后补，用户看到的是 500。

版本表只有两列有用：`version` 存文件名前缀，`name` 存描述。判断“迁移是否跑过”看版本号是否存在于表里，判断“跑了哪些”按 `version` 排序。回滚时不删记录，否则重跑会重复执行。

迁移脚本要能在空库上重放。CI 里用 `supabase db reset` 从零执行全部迁移，任何一条不幂等都会暴露；生产上不能重放，靠这项检查兜底。

迁移有三个边界。第一，迁移失败不会自动回滚已执行的 DDL，要用新的修复迁移。第二，改了迁移文件不重跑，版本表里已有记录；修改历史迁移会让新环境和旧环境结构不一致。第三，`--wait` 的超时要大于迁移耗时，大表加索引用时几分钟很常见。

## 46.10 多实例、版本偏移与平滑停机

多副本部署会遇到版本偏移：用户打开的是旧页面，请求打到新副本。`deploymentId` 让客户端发现版本不一致时强制刷新。

```ts
// next.config.ts
const nextConfig: NextConfig = {
  output: 'standalone',
  // 每次构建必须不同；CI 里用 git sha
  generateBuildId: async () => process.env.GIT_SHA ?? null,
  // 触发版本偏移检测；也会给资源 URL 加 ?dpl=
  deploymentId: process.env.DEPLOYMENT_ID,
}

export default nextConfig
```

响应头里能看到当前部署 ID。两次发布后对比这个值，能确认流量是否已经切换。

```bash
curl -sSI https://teamstack.example.com | grep -i x-deployment-id
```

滚动发布分三步：拉新镜像、只更新 app、确认健康后再处理旧副本。

```bash
# 1. 拉新镜像（不启动）
docker compose pull app

# 2. 只重建 app；compose 会先发 SIGTERM，等 30s，再启动新容器
docker compose up -d --no-deps app

# 3. 等健康检查通过
docker compose ps
curl -fsS https://teamstack.example.com/api/health
```

Server Action 的 ID 每次构建都会变，Next.js 最多每 14 天轮换一次。旧页面提交到新副本会报 `Failed to find Server Action`，`deploymentId` 让这种情况变成一次整页刷新，而非报错。

停机行为要实测。发布时保持一个循环请求，观察是否出现 5xx；连续 200 才算平滑。测试用 `for i in $(seq 1 200); do curl -so /dev/null -w "%{http_code}\n" https://teamstack.example.com; sleep 0.2; done`。

停机信号要接住。Compose 的 `stop_grace_period` 设成 30 秒，Node 进程收到 SIGTERM 后停止接受新连接，把进行中的请求跑完再退出。默认 10 秒不够一次慢查询。

多副本时的缓存要外置，或者接受各副本不一致。默认的 Data Cache 是内存加本地磁盘，A 副本 `revalidateTag` 不会影响 B 副本。做法是接 `cacheHandlers`，把 tag 失效写进 Redis；工作量不小，单副本部署可以不做。

外置缓存要满足四个条件：所有副本共享同一份存储；条目有上限，不能无限增长；值能序列化成 Buffer 或 Map；收到写失败时记日志而非抛错。`refreshTags()` 在每个请求第一次读缓存前调用，把其他副本的失效事件同步过来；没有这个调用，多副本下 tag 失效只在单机生效。

滚动发布时新旧副本会同时存在几分钟。这段时间里缓存键要兼容两版代码，改缓存结构时加版本前缀，例如 `v2:team:{id}`，等旧副本下线再删旧键。

## 46.11 备案与数据出境的两种分支

服务器在中国大陆时，域名要先完成 ICP 备案，否则 80 和 443 会被阻断。服务器在境外时不需要备案，但要处理数据出境和访问速度。

备案材料通常包括营业执照或身份证、域名证书、服务器接入商信息、网站负责人照片、核验单。接入商在境外时无法提交，这是选择服务器位置时要先确认的事。

两条分支的差异集中在五处。备案主体要与域名持有者一致，个人备案不能用于经营性网站；周期通常 7–20 个工作日，各省不同。备案通过后 30 日内要做公安联网备案。等保测评看行业要求，一般业务系统从二级开始。数据出境要看是否涉及个人信息出境，涉及就走安全评估或标准合同。支付通道也分境内外，境内要企业资质。

备案号必须展示在页脚，并链接到工信部网站。漏展示会被抽查要求整改。

```tsx
// src/app/(marketing)/_components/footer.tsx
export function Footer() {
  return (
    <footer className="border-t px-6 py-8 text-sm text-muted-foreground">
      <div className="mx-auto flex max-w-5xl flex-wrap items-center justify-between gap-4">
        <p>© {new Date().getFullYear()} teamstack</p>
        {process.env.NEXT_PUBLIC_ICP_BEIAN ? (
          <a
            href="https://beian.miit.gov.cn/"
            target="_blank"
            rel="noreferrer noopener"
            className="hover:underline"
          >
            {process.env.NEXT_PUBLIC_ICP_BEIAN}
          </a>
        ) : null}
      </div>
    </footer>
  )
}
```

境外部署要处理访问速度。源站在欧洲、用户在亚洲时 RTT 超过 200 毫秒，登录一次要等几个来回；把静态资源和图片放 Cloudflare 或对象存储，HTML 靠 CDN 缓存，能压到 1 秒内。

境外部署时这个变量不设，组件不渲染备案信息。用环境变量控制，避免两套代码。

## 46.12 日志、磁盘与升级

容器日志默认写进 json 文件，无上限。跑几个月后 `/var/lib/docker` 被日志占满，表现是 `no space left on device`，容器起不来。

```yaml
# compose.yaml 片段：限制单个服务的日志
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "5"
```

磁盘写满的征兆有三个：容器日志出现 `no space left on device`；`docker compose up` 报 `read-only file system`；应用写临时文件失败但进程还活着。三个都指向同一个原因，先看 `df -h`。

磁盘要定期看。占用超过 80% 时先找大文件，不要直接 `prune`。

```bash
df -h /var/lib/docker
docker system df
journalctl --disk-usage
```

systemd 的 journal 也要设上限。默认占磁盘的 10%，在小盘机器上是几个 GB。

```bash
sudo sed -i 's/^#\?SystemMaxUse=.*/SystemMaxUse=500M/' /etc/systemd/journald.conf
sudo systemctl restart systemd-journald
```

清理脚本放进 cron，每周跑一次。只清停止的容器、悬空镜像、构建缓存，不动正在使用的镜像。

```sh
# /etc/cron.weekly/teamstack-prune
#!/bin/sh
set -eu

# 只删 7 天前、且没有容器在用的镜像
docker image prune -af --filter "until=168h"

# 停掉的容器与悬空网络
docker container prune -f --filter "until=168h"
docker network prune -f

# 构建缓存最多留 5 GB
docker builder prune -f --keep-storage 5GB
```

镜像本身也要保留策略。发布频繁时每周产生几个版本，保留最近 10 个足够回滚。

```bash
# 列出 ghcr 镜像的本地标签，按创建时间倒序，保留最近 10 个
docker images --format '{{.Repository}}:{{.Tag}}\t{{.CreatedAt}}' \
  | grep '^ghcr.io/.*/teamstack:' | sort -k2 -r | tail -n +11
```

发布前把这一版的变更写成三行：改了哪张表、改了哪个配置、回滚要动什么。三行写不出来，说明这次发布的范围没想清楚，先别发。

升级按三步走：先备份、再本地验证、最后发布。跳过大版本升级的中间版本，容易在迁移或配置上踩空。

```bash
# 1. 升级前先备份（第 49 章有完整脚本）
pg_dump "$DIRECT_URL" --format=custom --no-owner > backup-$(date +%F-%H%M).dump

# 2. 在本地跑一遍完整构建，别把问题留到服务器
pnpm install --frozen-lockfile
pnpm typecheck && pnpm lint && pnpm test && pnpm build

# 3. 正常发布
docker compose pull && docker compose up -d --wait --wait-timeout 180
```

回滚只换镜像标签，不动数据库。数据库迁移按 expand/contract 做，旧镜像能在新结构上跑。

```bash
IMAGE_TAG=<上一个 git sha> docker compose up -d --no-deps app
```

升级 Node.js 大版本时要同步改三处：`package.json` 的 `engines`、Dockerfile 的基础镜像、CI 的 `node-version`。漏一处会在不同环境出现不同行为。

## 46.13 缓存与 CDN 的边界

Next.js 有两层缓存。Data Cache 缓存 `fetch` 和 `"use cache"` 的结果，存在应用侧；HTTP 缓存由 `Cache-Control` 控制，存在浏览器和 CDN。

两层要分开看。页面返回 `Cache-Control: private, no-store` 时，CDN 不缓存，但 Data Cache 可能仍有一份。反过来，静态资源的 `immutable` 只影响 HTTP 层。

验证缓存头用 `curl -I`。未登录和带 cookie 的两次请求，头应该不同。

```bash
# 未登录的首页
curl -sSI https://teamstack.example.com/ | grep -i cache-control

# 登录后的页面（带 cookie 才准）
curl -sSI -H "Cookie: sb-<ref>-auth-token=<你的会话>" https://teamstack.example.com/dashboard \
  | grep -i cache-control
```

CDN 缓存和部署 ID 会互相影响。发布后 HTML 里引用新的静态资源哈希，旧 HTML 引用旧哈希；静态资源长缓存没问题，HTML 必须短缓存或不缓存，否则用户拿到旧 HTML、请求已删除的 JS，页面白屏。

Cloudflare 上做缓存失效要指定 zone 和 token。全量 purge 会影响同域下所有资源，发布后只清 HTML 更稳。

```bash
# 部署脚本里跑，ZONE_ID 与 API Token 从 CI secrets 取
curl -sS -X POST "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/purge_cache" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" \
  -H "Content-Type: application/json" \
  --data '{"purge_everything":true}'
```

有三个边界。第一，HTML 默认不缓存，别为了提速把登录页设成 `s-maxage`。第二，带 `Set-Cookie` 的响应不能进共享缓存，否则会话串号。第三，`deploymentId` 触发的硬导航会绕过客户端缓存，发布瞬间的首屏请求会明显增多。

## 46.14 上线验收

部署完成后跑一遍验收命令。每条都有明确判据，任何一条不符合就回到对应小节。

```bash
# 1. HTTP 状态与跳转链
curl -sS -o /dev/null -w '%{http_code} %{url_effective}\n' -L https://teamstack.example.com

# 2. 健康检查（含数据库）
curl -sS https://teamstack.example.com/api/health

# 3. TLS 与证书有效期
openssl s_client -connect teamstack.example.com:443 -servername teamstack.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates

# 4. 安全头
curl -sSI https://teamstack.example.com | grep -iE 'strict-transport|content-type-options|referrer'

# 5. 静态资源能取到且长缓存
curl -sSI https://teamstack.example.com/_next/static/$(ls .next/static | head -1) | head -5

# 6. 应用端口没暴露（在另一台机器上执行）
curl --max-time 3 http://203.0.113.10:3000 || echo '端口不可达，符合预期'

# 7. 容器状态
docker compose ps
docker compose logs --tail=50 app
```

手工项有两处不能自动化。一是页脚备案号链接可点，备案信息与主体一致；二是登录流程在手机浏览器上能完成。两项各花一分钟，放到发布清单最后。

验收之后再挂三个监控：域名证书到期时间、`/api/health` 成功率、容器重启次数。前两个用外部探测，第三个读 `docker inspect` 的 `RestartCount`。三项都在阈值内，才算这次发布结束。

判据：状态码 200 且跳转链只有一次；`/api/health` 返回 `{"ok":true}`；证书有效期大于 30 天且域名匹配；安全头包含 HSTS 与 CSP；静态资源返回 `immutable`；外部访问 3000 超时；`docker compose ps` 三个服务都是 `running`。

回滚要演练。每季度把生产的一份旧镜像拉起来，指向同一个数据库，确认旧版本在新结构上能读能写；演练记录写进运维文档，别等真出事才第一次执行。

## 46.15 边界与失败模式

这里列出几种组合故障。单看每一节都通过，故障仍会出现在交界处。

1. 容器显示 `Up`，浏览器 502。原因通常是反代与 app 不在同一网络，或者 app 监听在 127.0.0.1。先在 caddy 容器里访问 `http://app:3000/api/health`，再看 `ss -ltnp` 的监听地址。
2. 迁移成功，应用报列不存在。镜像 tag 与迁移版本不匹配：新镜像跑在旧库上，或旧镜像跑在新库上。发布时把镜像 sha 与迁移版本一起记录，回滚时成对回退。
3. 证书正常，登录报 `Invalid Server Actions request`。反代没有透传 `Host`，或者 `allowedOrigins` 写了不带端口的域名。用 `curl -I` 看响应头里的 `x-forwarded-host`。
4. 单机正常，扩到两个副本后登录偶发掉线。两个容器的 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 不同，action 解密失败。密钥必须写进环境文件，不能每次启动生成。
5. 磁盘写满时先出现 500，随后日志变成 `Read-only file system`。这时迁移也会失败，且失败信息与磁盘无关，容易误判。
6. 灰度期间新旧实例并存，旧页面提交表单报 `Failed to find Server Action`。这是 action ID 版本偏移，正常现象，靠 `deploymentId` 触发整页刷新收敛。

## 46.16 检查点

1. `docker compose ps` 显示 `app`、`caddy` 状态为 `running (healthy)`，`app` 的端口映射为空。判据：`docker compose port app 3000` 无输出。
2. `curl -sSI https://teamstack.example.com` 返回 `HTTP/2 200`，且响应头含 `strict-transport-security`。判据：状态码与头都存在。
3. 在另一台机器执行 `curl -m 3 http://<VPS_IP>:3000`，返回超时或连接被拒绝。判据：拿不到 200。
4. 改一行业务代码重新发布，`docker compose logs app` 里有迁移阶段和监听阶段两行，发布期间持续 `curl` 首页没有 5xx。
5. `psql "$DIRECT_URL" -c "select count(*) from supabase_migrations.schema_migrations"` 的数量与 `supabase/migrations` 下的文件数一致。
6. 把 `.env.production` 里的 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 改成另一个值重启，提交一次表单，确认没有出现解密错误。判据：表单成功。

## 46.17 常见错误

下面六条按出现频率排序。每条给出现象、原因、改法，报错原文照抄，方便直接搜到这一节。

**1. `Error: Cannot find module '/app/server.js'`**

现象是容器反复重启，日志只有这一行。原因是 Dockerfile 的 `COPY` 层级错了，`server.js` 落在 `/app/standalone/server.js`。改法是检查 `COPY --from=builder` 的源路径，确保 `.next/standalone/` 的内容直接进 `/app`。

**2. 页面能打开，但样式和图片全丢**

现象是 HTML 有内容、控制台一排 404，路径是 `/_next/static/...`。原因是镜像里没有 `.next/static` 和 `public`。改法是在 Dockerfile 里显式复制这两个目录，或改用 46.1 的手工复制步骤。

**3. `EACCES: permission denied, mkdir '.next/cache'`**

现象是容器启动即退出。原因是 `.next` 属于 root，运行用户是 uid 1001。改法是 `COPY --chown` 或在 runner 阶段 `chown -R`，也可以把缓存目录挂成卷并预先设属主。

**4. 浏览器报 `ERR_TOO_MANY_REDIRECTS`**

现象是访问域名无限跳转。原因是 Cloudflare SSL 设为 `Flexible`，而应用又强制跳 https。改法是把 SSL 模式改成 `Full (strict)`，并在源站装有效证书。

**5. `Invalid Server Actions request`**

现象是表单提交 500，日志提示 Origin 校验失败。原因是反代没透传 `Host`，或 `allowedOrigins` 写错。改法是补 `X-Forwarded-Host`，或在 `experimental.serverActions.allowedOrigins` 里加上完整来源。

**6. 发布后旧页面提交表单报 `Failed to find Server Action`**

现象是部分用户提交失败，刷新后恢复。原因是新旧副本的 action ID 不同。改法是设置稳定的 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 和 `deploymentId`，让版本偏移触发整页刷新。

## 46.18 这一章在做什么

这一章把 teamstack 从代码变成一个可访问的服务。步骤是：构建 standalone 产物，打成非 root 镜像，用 compose 编排，用 Caddy 或 Nginx 接流量。Cloudflare 管 DNS 与证书，ufw 收窄端口。迁移脚本保证结构先于代码，多阶段发布避免锁表和停机。

它建立三条事实。第一，部署的产物形态决定后续所有步骤，standalone 是自托管的基础。第二，网络边界要在三层同时收：容器不发布端口、主机防火墙只开必要端口、云安全组再收一层。第三，数据库结构与代码的版本要能分开演进，靠 expand/contract 和稳定的加密密钥。

这一章不覆盖多区域、蓝绿部署和 K8s。单机加 compose 能支撑到每天几十万请求，再往上才需要考虑编排系统。

下一章讲 Vercel 部署。同一个项目放到托管平台，限制完全不同：没有持久磁盘、函数有超时、Cron 每天只能跑一次。
