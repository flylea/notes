# 第 49 章 备份、恢复与账号注销

这一章讲两件相关的事：数据丢失后怎么恢复，用户离开时怎么删干净。两件事共用同一张“数据存在哪、留多久”的清单。

备份解决的是意外：误删、迁移写错、项目被暂停。注销解决的是义务：用户行使删除权时，系统要能真的删掉，并且留下必要的记录。

涉及的组件有四个：Supabase 的 Postgres 数据库、Supabase Storage 的对象、VPS 上的备份脚本与对象存储、应用里的导出与删除接口。

前提要讲清楚。Supabase 免费项目没有自动备份，也没有时间点恢复（PITR）。控制台里看不到“恢复到某个时刻”的按钮，误删一张表就是永久丢失，除非自己备过。

## 49.1 免费档给了什么，没给什么

免费项目提供数据库、Storage、Auth 和有限的日志。日志保留 1 天，出问题要当天看。

不提供的东西要记住四条。没有自动备份；没有 PITR；项目连续一周不活跃会被暂停，暂停后连接串不变，恢复要进控制台点；每个账号最多两个活跃项目，第三个建不了。

备份本身就是数据治理的一部分，和注销、保留期一起设计。隐私政策里写了“数据保留 30 天”，备份的保留期就不能超过这个数；写 30 天、实际留一年，是常见的不一致。

暂停与删除是两件事。暂停后数据还在，恢复后继续用；删除项目不可逆，控制台会要求输入项目名确认。备份脚本要能发现“库连不上”，别等用户报错才知道。

数据库大小可以在控制台看到，也可以用 SQL 查：`select pg_size_pretty(pg_database_size(current_database()));`。免费档 500 MB，超过后写入会被拒，备份策略要一并考虑清理历史数据。

判断备份是否够用，看两个数字：可接受丢多少数据、多久能恢复。丢一天可以接受，日备份就够；恢复要在一小时内完成，平时就要把恢复脚本跑熟。

免费档的限制还会影响“备份放哪”。数据库 500 MB、Storage 1 GB，备份文件通常比库大，不能塞回 Supabase；放对象存储，按量付费更便宜。

自建备份是唯一可靠的还原手段。备份频率按可接受的数据丢失量定：每天一次，最坏丢一天；每小时一次，最坏丢一小时。

## 49.2 备份清单：只备数据库会少半个应用

只备份数据库是常见做法，也是最容易在恢复时才发现缺东西的做法。恢复的目标是“应用能用”，表里有数据只是其中一步。

一个完整的备份包含五样东西。

恢复顺序与备份顺序相反。先建库与角色，再导数据，最后恢复对象存储；每一步验证通过再继续，出错能停在一个明确的状态。

数据库的 public schema 与 auth schema。业务表在 public，用户与会话在 auth；只备 public，恢复后所有人登不进去。

Storage 的备份有两种做法。每天全量同步到 R2，简单但费流量；按 `updated_at` 增量同步，省流量但要处理删除。免费档 1 GB，全量同步成本可以接受。

Storage 里的对象。附件、头像存在对象存储，不在 dump 里；数据库只存路径。恢复时路径对、对象没了，页面全是坏图。

环境变量与迁移文件。前者决定连哪个库、用哪个密钥，后者决定结构怎么演进。两者都在仓库或密码管理器里，备份时确认是最新的。

部署配置。`compose.yaml`、`Caddyfile`、Cloudflare 的 DNS 与 Tunnel 配置。恢复整台机器时，这些比重装系统更费时间。

第三方侧的配置。Resend 的域名验证、Stripe 的 webhook、Turnstile 的站点密钥。它们不在你的库里，但应用依赖它们。

备份清单整理成一张表，放在运维文档里，每季度核对一次。

| 对象 | 位置 | 频率 | 保留 |
| --- | --- | --- | --- |
| 数据库 public + auth | R2 | 每天 | 30 天 |
| Storage 对象 | R2 | 每天增量 | 30 天 |
| 环境变量 | 密码管理器 | 变更时 | 长期 |
| 迁移与配置 | Git 仓库 | 每次提交 | 长期 |

备份文件不要放在同一台机器上。VPS 的系统盘坏了，备份跟着丢；放对象存储，顺便满足异地要求。

auth schema 的恢复没有公开流程。Supabase 官方不建议直接改 auth 表，恢复时先恢复到临时库，再通过管理 API 迁移用户；这一步要在演练里验证，不能等真出事才试。

这两件事都要有清单与负责人。备份没人检查就会静默失败，删除没人复核就会留下残留；流程比工具更容易被忽略。

## 49.3 备份脚本与定时

备份窗口要避开业务高峰。全量导出会占 I/O，大库导出的几分钟里查询会变慢；凌晨执行对用户影响最小。

脚本用 `pg_dump` 的 custom 格式，自带压缩、支持选择性恢复、能并行。客户端版本要与服务端一致，服务端是 17 就用 17 的镜像。

连接用 5432 的直连，不用 6543 的连接池。事务模式的连接池会让 `pg_dump` 的一致性快照失效，导出的数据可能跨多个事务。

```bash
# VPS 上，用与服务端同大版本的客户端；17 换成你项目的实际版本
docker pull postgres:17-alpine
```

脚本要有锁。两次备份同时跑会互相覆盖临时文件，用 `flock` 加一把文件锁，拿不到锁就退出。

脚本做四件事：导出、校验、上传、清理。校验不能省，空文件与损坏文件都能“上传成功”。

```sh
# /srv/teamstack/scripts/backup-db.sh
#!/bin/sh
set -eu

# 从 .env.production 读直连串（5432），不要用 6543 事务池
. /srv/teamstack/.env.production

STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
DIR="/var/backups/teamstack"
FILE="${DIR}/db-${STAMP}.dump"
mkdir -p "$DIR"

# custom 格式：自带压缩、可选择性恢复、可并行
docker run --rm \
  -e PGPASSWORD="${DB_PASSWORD}" \
  -v "${DIR}:/backup" \
  postgres:17-alpine \
  pg_dump \
    --host="${DB_HOST}" \
    --port=5432 \
    --username="${DB_USER}" \
    --dbname="${DB_NAME}" \
    --format=custom \
    --no-owner \
    --no-privileges \
    --file="/backup/db-${STAMP}.dump"

# 校验：文件非空，且 pg_restore 能读出目录
test -s "$FILE"
docker run --rm -v "${DIR}:/backup" postgres:17-alpine \
  pg_restore --list "/backup/db-${STAMP}.dump" > /dev/null

# 上传到 R2（rclone 已配置 remote: r2）
rclone copy "$FILE" "r2:teamstack-backups/db/"

# 本地留 3 天，远端留 30 天
find "$DIR" -name 'db-*.dump' -mtime +3 -delete
rclone delete --min-age 30d "r2:teamstack-backups/db/"

echo "[backup] ok: ${STAMP} $(du -h "$FILE" | cut -f1)"
```

脚本失败要能定位。每一步输出带前缀，`set -eu` 让错误立即退出；日志写文件并保留 30 天，方便回溯。

定时任务放在 VPS 的 crontab 里。时间选在业务低峰，UTC 18:30 对应北京时间凌晨 02:30。

```bash
# crontab -e，每天 UTC 18:30（北京时间 02:30）
30 18 * * * /srv/teamstack/scripts/backup-db.sh >> /var/log/teamstack-backup.log 2>&1
```

成功时输出一行摘要，包含时间戳、大小、耗时。没有这行输出就说明失败。

```text
[backup] ok: 20261116T183002Z 96M
```

第二天要检查昨天是否成功。检查做成命令，进每日巡检脚本，连续两天失败要告警。

```bash
# 昨天有没有成功备份？没有就该告警了
grep "$(date -u -d yesterday +%Y-%m-%d)" /var/log/teamstack-backup.log
```

加密用非对称方案。公钥可以放在服务器上，泄露也无所谓；私钥离线保存，恢复时才取出来。

备份文件要加密再上传。对象存储的权限配错、链接泄露都会导致数据外流；加密后拿到文件也读不出内容。

## 49.4 恢复演练

演练要计时。恢复一次要多久、卡在哪一步，数字写下来；超过目标的，优化容器启动或改用增量恢复。

演练环境要和生产隔离。用同一份备份、不同的数据库实例，端口、库名、密钥都换掉，避免演练时误连生产。

没恢复过的备份不能算备份。演练要有负责人。写清谁执行、谁复核、结果记录在哪；没有负责人的演练通常只做一次。

演练每季度一次，在本地或 VPS 上起一个临时库，端口用 55432，避开已有服务。

```bash
# 本地或 VPS 上，用 55432 避免和已有服务冲突
docker run --rm -d \
  --name pg-drill \
  -e POSTGRES_PASSWORD=drill \
  -p 55432:5432 \
  postgres:17-alpine
```

演练库可以用 Docker 起，不污染宿主机。容器删掉数据就没了，适合反复演练。

从对象存储拉最新一份，解密，恢复到演练库。`--clean --if-exists` 让重复演练也能跑。

```bash
# 从 R2 拉最新一份
rclone copy r2:teamstack-backups/db/ /tmp/drill/ --include '*.dump'

LATEST="$(ls -t /tmp/drill/*.dump | head -n 1)"

docker run --rm \
  -v /tmp/drill:/backup \
  postgres:17-alpine \
  pg_restore \
    --host=host.docker.internal \
    --port=55432 \
    --username=postgres \
    --dbname=postgres \
    --no-owner \
    --no-privileges \
    --clean --if-exists \
    "/backup/$(basename "$LATEST")"
```

恢复完做三项核对：行数、最新业务数据的时间戳、迁移版本。三项都对，才说明这份备份可用。

```bash
# 1. 行数对不对（和备份时的记录比，或者至少大于 0）
psql "postgresql://postgres:drill@127.0.0.1:55432/postgres" -c "
  select 'teams' as t, count(*) from teams
  union all select 'team_members', count(*) from team_members
  union all select 'attachments', count(*) from attachments
  union all select 'audit_logs', count(*) from audit_logs;
"

# 2. 最近一条业务数据在不在（时间戳应该接近备份时间）
psql "postgresql://postgres:drill@127.0.0.1:55432/postgres" -c "
  select max(created_at) from audit_logs;
"

# 3. 迁移状态对不对（最后一个版本号应该等于仓库里最新的迁移）
psql "postgresql://postgres:drill@127.0.0.1:55432/postgres" -c "
  select version from supabase_migrations.schema_migrations order by version desc limit 3;
"
```

行数表按表列出，和备份时的记录对比；没有记录时至少确认大于 0。

```text
   t       | count
-----------+-------
 teams     |    42
 members   |   187
```

演练发现的问题要修脚本，不要只记在文档里。修完立刻再演练一次，确认问题消失。

最后用演练库启动一次应用，走一遍登录、列表、写入。数据在但应用不能用，等于没恢复。

```bash
# 用演练库启动本地应用，验证恢复的数据能被应用使用
DATABASE_URL="postgresql://postgres:drill@127.0.0.1:55432/postgres" \
NEXT_PUBLIC_SUPABASE_URL="http://127.0.0.1:54321" \
pnpm dev
```

恢复耗时的大头常在下载与解压。备份文件几十 MB 时，本地盘恢复几分钟；上 GB 时要预先算好带宽，别在事故中才发现要等半小时。

演练记录写进文档：日期、备份文件、恢复耗时、发现的问题。下次演练先看上次的问题有没有修。

演练之外，每月抽查一份备份：随机挑一个日期，恢复、启动、登录。抽查能发现“某几天的备份全是空的”这类规律性问题。

## 49.5 用户数据导出

导出的数据格式要稳定。字段名与结构写进文档，用户拿到的文件两年后还能读懂；改结构时保留旧字段或升版本号。

导出是注销的前置能力。用户要求删除前，通常先要一份自己的数据；没有导出，删除请求会变成人工客服工单。

导出接口按团队维度，只允许 Owner 调用，返回 JSON 或 CSV，带 `Content-Disposition` 让浏览器直接下载。

```ts
// src/app/api/teams/[teamId]/export/route.ts
import { NextResponse } from 'next/server'
import { db } from '@/lib/db'
import { requireTeamOwner } from '@/lib/teams'

export const dynamic = 'force-dynamic'
export const maxDuration = 60

export async function GET(
  _request: Request,
  { params }: { params: Promise<{ teamId: string }> },
) {
  const { teamId } = await params
  await requireTeamOwner(teamId)

  const [team, members, logs] = await Promise.all([
    db.selectFrom('teams').selectAll().where('id', '=', teamId).executeTakeFirstOrThrow(),
    db.selectFrom('team_members').selectAll().where('team_id', '=', teamId).execute(),
    db.selectFrom('audit_logs').selectAll().where('team_id', '=', teamId).orderBy('created_at').execute(),
  ])

  const payload = {
    exported_at: new Date().toISOString(),
    team,
    members,
    audit_logs: logs,
  }

  return new NextResponse(JSON.stringify(payload), {
    headers: {
      'content-type': 'application/json; charset=utf-8',
      'content-disposition': `attachment; filename="team-${teamId}.json"`,
      'cache-control': 'no-store',
    },
  })
}
```

导出失败要给可读的错误。超时、数据过大、权限不足分别返回不同提示，前端据此引导用户缩小范围。

导出要限流。大团队一次导出几十 MB，并发几个就能把数据库拖慢；按用户加每分钟一次的限额。

导出的实现要注意流式返回。一次查全部行会占内存，按团队与时间分批查，边查边写；数据量大时生成一个 zip，放进对象存储，给一个 24 小时有效的下载链接。

导出内容要覆盖用户在界面上能看到的一切：团队信息、成员、项目、附件元数据、活动日志。附件本身给签名链接，不塞进 JSON。

## 49.6 删除的四个层次

软删的状态要能查。列表默认过滤 `deleted_at is null`，设置页单独列已删除团队；两种视图用同一个查询参数控制，避免两套逻辑走偏。

恢复入口只处理软删。硬删之后没有行可恢复，接口要返回明确的 410，让用户知道数据已不可找回。

查一个团队的删除状态用一条 SQL，`deleted_at` 非空表示已软删。

```sql
select id, deleted_at from teams where id = '8f3a...';
                  id                  |         deleted_at
--------------------------------------+----------------------------
 8f3a2c4e-...                         | 2026-11-10 02:14:33.481+00
```

删除分成四层，顺序不能乱。对象存储、业务表、auth 用户、审计日志。

```text
用户点删除团队
  → 二次确认（输入团队名）
  → teams.deleted_at = now()
  → 团队从所有成员的列表里消失，页面 404
  → 30 天内 Owner 可以在「回收站」恢复
  → 30 天后 cleanup 任务：
      1. 先删 Storage 里 teamId/ 前缀下的所有对象
      2. 再删 teams 行（FK cascade 删 team_members、attachments 记录）
      3. audit_logs 保留，但 actor 匿名化
```

对象存储先删。数据库行删掉后，对象还在，路径却找不回来，成为永远清不掉的孤儿。反过来，先删对象、后删行，最坏情况是用户看到坏图，可以重试。

清理脚本按团队遍历对象，分页拉取，逐个删除，最后删数据库行。脚本要能重复执行，中途失败再跑一遍能收敛。

```js
// scripts/cleanup-deleted-teams.mjs
import { createClient } from '@supabase/supabase-js'
import pg from 'pg'

const { Client } = pg
const db = new Client({ connectionString: process.env.DIRECT_URL })

// service role，能绕过 Storage 的 RLS
const admin = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.SUPABASE_SECRET_KEY,
  { auth: { persistSession: false } },
)

await db.connect()

const { rows } = await db.query(
  `select id from teams
   where deleted_at is not null
     and deleted_at < now() - interval '30 days'
   limit 20`,
)

for (const { id } of rows) {
  // Storage 的 list 默认分页，必须循环取完
  let offset = 0
  for (;;) {
    const { data, error } = await admin.storage
      .from('attachments')
      .list(id, { limit: 100, offset })
    if (error) throw error
    if (!data.length) break

    const paths = data.map((f) => `${id}/${f.name}`)
    const { error: removeError } = await admin.storage.from('attachments').remove(paths)
    if (removeError) throw removeError

    offset += data.length
    if (data.length < 100) break
  }

  // 对象删完再删行；audit_logs 不级联，保留
  await db.query('delete from teams where id = $1', [id])
  console.log(`[cleanup] removed team ${id}`)
}

await db.end()
```

恢复入口只对 30 天内的软删有效。判断写在 SQL 里，不能靠界面隐藏按钮；界面藏了，接口还能调。

```ts
// src/app/(app)/teams/[teamId]/settings/actions.ts
'use server'

import { revalidatePath } from 'next/cache'
import { sql } from 'kysely'
import { db } from '@/lib/db'
import { requireTeamOwner } from '@/lib/teams'

export async function restoreTeam(teamId: string) {
  await requireTeamOwner(teamId)

  const result = await db
    .updateTable('teams')
    .set({ deleted_at: null })
    .where('id', '=', teamId)
    .where('deleted_at', 'is not', null)
    .where(sql<boolean>`deleted_at > now() - interval '30 days'`)
    .returning('id')
    .executeTakeFirst()

  if (!result) {
    return { error: '超过 30 天，无法恢复' }
  }

  revalidatePath('/settings/teams')
  return { ok: true }
}
```

## 49.7 账号注销

注销是“删人，不删证据”。用户数据要删，安全与计费记录按法规保留，且不能反向识别到个人。

注销入口要二次确认。让用户输入邮箱或团队名，确认后发送一封“注销已受理”的邮件，附撤回链接与生效时间。

流程分三步：标记删除、吊销会话、延迟硬删。标记后用户立即无法登录；硬删在 30 天后执行，期间可以撤回。

```sql
-- 禁用 + 吊销会话（service role 执行）
update profiles set deleted_at = now(), disabled = true where id = $1;
delete from auth.sessions where user_id = $1;
delete from auth.refresh_tokens where user_id = $1::text;
```

注销请求要留记录。谁在什么时候请求、处理到哪一步、什么时候硬删，写进审计日志；这是合规检查最常要的材料。

会话吊销要覆盖两张表。`auth.sessions` 与 `auth.refresh_tokens` 都清掉，否则旧的 refresh token 还能换新会话。

硬删用管理 API，不直接删 `auth.users`。直接删会留下孤立的 identity 与 session 记录，后续登录报奇怪的错误。

```ts
// scripts/purge-deleted-users.mjs
const { data, error } = await admin.auth.admin.listUsers()
// 逐个判断 profiles.deleted_at
await admin.auth.admin.deleteUser(userId)
```

审计日志要匿名化。把 `actor_id` 换成哈希，保留行为与时间，去掉能定位到人的字段。

## 49.8 最后一个 Owner 不能走

团队必须至少有一个 Owner。成员退出、被移除、账号注销，三条路径都要检查。

检查放在数据库函数里，用事务保证“检查 + 删除”原子执行。放到应用层，两个请求并发时都能通过检查。

```sql
-- supabase/migrations/20261212090000_leave_team.sql
create or replace function public.leave_team(p_team_id uuid)
returns void
language plpgsql
security definer
set search_path = public
as $$
declare
  v_role text;
  v_owner_count int;
begin
  select role into v_role
  from team_members
  where team_id = p_team_id and user_id = auth.uid();

  if v_role is null then
    raise exception 'not a member of this team';
  end if;

  if v_role = 'owner' then
    select count(*) into v_owner_count
    from team_members
    where team_id = p_team_id and role = 'owner';

    if v_owner_count <= 1 then
      raise exception 'last owner cannot leave; transfer ownership first';
    end if;
  end if;

  delete from team_members
  where team_id = p_team_id and user_id = auth.uid();
end;
$$;
```

函数抛出的错误信息要能直接展示给用户。

```text
ERROR:  last owner cannot leave; transfer ownership first
```

账号注销时，该用户是所有 Owner 的团队要先转移或解散。注销接口在标记删除前检查一遍，有阻塞就返回清单，让用户先处理。

## 49.9 审计日志留多久

查审计时按 actor 与时间过滤。表上建 `(team_id, created_at)` 与 `(actor_id, created_at)` 两个索引，180 天的数据量在百万行级，没索引的查询会拖垮库。

审计日志不要写业务正文。只记动作、对象、时间、结果；正文里可能有用户隐私，删起来更麻烦。

审计日志用于追责与合规，保留 180 天。超过期限的分批删除，每批 1000 行，避免长事务锁表。

```sql
delete from audit_logs
where created_at < now() - interval '180 days';
```

删除按时间分批，夜里跑。

```sql
delete from audit_logs
where id in (
  select id from audit_logs
  where created_at < now() - interval '180 days'
  limit 1000
);
```

日志里不能出现的东西要提前排掉：密码、令牌、完整 IP、身份证号、银行卡号。写入前统一过一层脱敏函数，别指望每个调用点都记得。

## 49.10 保留策略与加密

周备份与月备份从日备份复制，避免重复导出。复制用服务端拷贝，不下载再上传；对象存储支持 server-side copy，几秒完成。

保留期要和合规要求对上。合同、发票类记录留 10 年，日志类留 180 天，用户数据在注销后 30 天内清掉；每个期限在文档里写清依据。

备份按 3-2-1 原则：三份副本、两种介质、一份异地。落到操作上是日、周、月三层。

日备份保留 7 天，周备份保留 4 周，月备份保留 12 个月。三层各自清理，互不影响。

```sh
# 备份成功后，按日期复制到周/月目录
DOW="$(date -u +%u)"    # 1=周一 … 7=周日
DOM="$(date -u +%d)"

if [ "$DOW" = "7" ]; then
  rclone copy "$FILE" "r2:teamstack-backups/weekly/"
fi

if [ "$DOM" = "01" ]; then
  rclone copy "$FILE" "r2:teamstack-backups/monthly/"
fi

# 各层独立清理，互不影响
rclone delete --min-age 7d  "r2:teamstack-backups/db/"
rclone delete --min-age 35d "r2:teamstack-backups/weekly/"
rclone delete --min-age 400d "r2:teamstack-backups/monthly/"
```

加密用 age，公钥放服务器，私钥离线保存。密钥丢了备份等于没有，私钥要存两份，放在不同地方。

```bash
# 生成密钥对（只做一次，私钥离线保存）
age-keygen -o backup-key.txt

# 备份时加密，公钥可以放服务器上
age -r "$(grep '^# public key:' backup-key.txt | cut -d' ' -f5)" \
  -o "${FILE}.age" "$FILE"
rm "$FILE"  # 明文不要留在磁盘上
```

每个加密文件附带 sha256，恢复前先校验。

```bash
sha256sum "${FILE}.age" > "${FILE}.age.sha256"
rclone copy "${FILE}.age" "${FILE}.age.sha256" "r2:teamstack-backups/db/"
```

单团队恢复用中间库。把备份恢复到临时库，导出该团队的行，再导回生产；直接改生产容易碰到主键冲突。

```bash
# 1. 把三天前的 dump 恢复到 scratch 库（49.5 的容器）
# 2. 从 scratch 导出目标团队的数据
psql "postgresql://postgres:drill@127.0.0.1:55432/postgres" \
  -c "\copy (select * from teams where id = '8f3a...') to '/tmp/team.csv' csv header"

psql "postgresql://postgres:drill@127.0.0.1:55432/postgres" \
  -c "\copy (select * from team_members where team_id = '8f3a...') to '/tmp/members.csv' csv header"

# 3. 导回生产（先确认主键不冲突；teams 行可能还在，只补子表）
psql "$DIRECT_URL" \
  -c "\copy team_members from '/tmp/members.csv' csv header"
```

## 49.11 事故处置

事故沟通要有人在。技术负责恢复，另一个人负责对外说明；同一个人既修又解释，容易两头都做不好。

事故的第一动作是停止写入，第二动作是保留现场，第三动作才是恢复。

停止写入用维护模式：非 GET 请求一律返回 503，带 `Retry-After`。这样数据库不再变化，恢复出来的数据不会二次丢失。

```ts
// src/lib/maintenance.ts
export function isMaintenanceMode() {
  return process.env.MAINTENANCE_MODE === '1'
}
```

代理层按开关拦截，GET 放行，其余返回 503。

```ts
// src/proxy.ts 片段
if (isMaintenanceMode() && request.method !== 'GET' && request.method !== 'HEAD') {
  return new Response('维护中，请稍后再试', {
    status: 503,
    headers: { 'retry-after': '600' },
  })
}
```

现场快照单独存一份，别用日常备份的目录；恢复过程中可能把日常备份覆盖掉。

```bash
# 事故现场快照，别用日常备份的目录
pg_dump "$DIRECT_URL" --format=custom --no-owner > /var/backups/incident-$(date +%s).dump
```

恢复顺序是数据库、对象存储、应用。先恢复库，再同步对象，最后启动应用；顺序反了，应用会读到半套数据。

恢复完成先验证再解除维护模式。验证包括登录、列表、写入、关键接口状态码，全部通过再放开。

备份与删除跑顺之后，运维的重心从“救火”转到“核对”：每周看备份是否成功，每月抽查一次恢复，每季度演练一次完整流程。

## 49.12 边界与失败模式

备份系统的风险集中在“以为有”和“真能用”之间。

1. 备份文件存在，从没恢复过。文件大小正常也可能是空库，只有恢复演练能证明可用。
2. 数据库备了，对象存储没备。恢复后附件记录存在，文件 404。备份清单要覆盖数据库、存储、环境变量三处。
3. 演练用错 Postgres 版本。低版本 dump 导入高版本可以，反向会失败；演练环境固定与生产同版本。
4. 软删窗口过期，数据不可恢复。窗口写在 SQL 里，也写在用户协议里，两边要一致。
5. 清理脚本先删行后删对象。删行成功、删对象失败时，对象成为孤儿，占用配额。顺序反过来，失败可重试。
6. 备份密钥与备份文件放在同一台机器。机器丢了两样一起丢，密钥要离线保存。

## 49.13 检查点

1. 手动跑一次备份脚本，输出里有时间戳与大小。判据：R2 上出现对应文件，`pg_restore --list` 能读出目录。
2. 把备份恢复到演练库，三张核心表的行数与生产相差在 1% 内。判据：行数对比表打印出来。
3. 演练库启动应用并登录成功。判据：能看到团队列表，登录页没有报错。
4. 软删一个团队，24 小时内能在回收站恢复；超过 30 天后恢复接口返回 410。判据：两种状态都试一次。
5. 注销一个测试账号，登录返回凭据错误，`auth.sessions` 中无该用户记录。判据：数据库查询为空。
6. 最后一个 Owner 尝试退出，返回 `last owner cannot leave`。判据：错误文案与函数里一致。

六条里前三条验备份、后三条验删除。备份的三条每月跑一次，删除的三条每次改相关代码后跑一次。

## 49.14 常见错误

**1. `pg_restore: error: unsupported version (1.15) in file header`**

现象是恢复时报版本不支持。原因是客户端版本低于服务端。改法是换与服务端同大版本的 `pg_dump` 与 `pg_restore`，用官方镜像最省事。

**2. `ERROR: role "postgres" does not exist`**

现象是恢复到新库时角色不存在。原因是 dump 里带了 owner 信息。改法是导出时加 `--no-owner --no-privileges`，恢复后再补授权。

**3. `ERROR: extension "pgcrypto" is not available`**

现象是恢复在 `CREATE EXTENSION` 处失败。原因是目标库没装扩展。改法是先装扩展再恢复，或用 Supabase 支持的扩展清单核对。

**4. 注销后用户仍能登录**

现象是提交注销，第二天还能进。原因是只删了业务表，没吊销 `auth.sessions` 与 `refresh_tokens`。改法是先禁用、再吊销、最后硬删，三步都做。

**5. 团队删了但对象存储还有文件**

现象是数据库行没了，账单里存储量没降。原因是清理脚本只删了行。改法是按团队前缀列出对象并删除，删除前记录数量，删后核对。

**6. 恢复后旧 cookie 仍能进入**

现象是恢复完成，旧会话仍有效。原因是会话是签名 cookie，不查库就能通过。改法是恢复后轮换 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 与 Supabase 的 JWT secret。

## 49.15 这一章在做什么

这一章把“数据不会丢”和“用户能离开”落成两套流程。备份靠脚本与定时任务，恢复靠演练；注销靠软删、吊销、硬删三步，配合数据库层的 Owner 检查。

它建立三条判断。第一，免费档没有自动备份，自建备份是唯一手段。第二，没演练过的备份不可信，季度演练是必须项。第三，删除要考虑对象存储与认证系统，只删业务表会留下残留。

这一章不覆盖跨区域容灾与付费版 PITR。升级到 Pro 后有 7 天时间点恢复，用法在官方文档的 Backups 一节；自建备份仍然要做，两者互补。

下一章讲成本与限额。备份、日志、对象存储都会产生费用，知道每个服务的边界，才能避免月底收到意外账单。
