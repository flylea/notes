# 第 18 章 邀请机制

这一章讲把一个人加进团队的那条链接：怎么生成、怎么发、怎么校验、怎么在失败时不留脏数据。

需要它的原因是“加成员”看起来只有一步，实际上有五个失败点。链接可能被转发、可能过期、可能被同一封邮件点两次、可能被人改角色提权、可能在写库和发信之间断掉。

邀请的本质是一条有状态、有时效、一次性的凭证。它涉及四个概念。token 是随机串，库里只存哈希。状态机有四个值：pending、accepted、expired、revoked。事务用于接受邀请时同时改两张表。部分唯一索引保证同一个团队、同一个邮箱只能有一条待处理邀请。

这一章先给表结构和 token 的存法，再写创建、发送、预览、接受四条链路，最后是过期清理、撤销、防滥用和验证方法。

## 18.1 状态机

邀请有四个状态，五条转移。

```
            ┌─────────────┐
  创建 ───► │   pending   │
            └──┬───┬───┬──┘
               │   │   │
      被接受   │   │   │  被撤销
               ▼   │   ▼
        ┌──────────┐│ ┌─────────┐
        │ accepted ││ │ revoked │
        └──────────┘│ └─────────┘
                    │ 过期
                    ▼
              ┌─────────┐
              │ expired │
              └─────────┘
```


`pending` 是初始状态。可以转移到 `accepted`（被接受）、`expired`（过期）、`revoked`（被撤销）。

`accepted`、`expired`、`revoked` 都是终态，不再变化。撤销之后重新邀请要插一条新行，不要改旧行的状态回 `pending`，否则历史记录失真。

状态字段用 `text` 加 `check` 约束，不要用布尔。布尔只能表达“有效/无效”，无法区分“过期”和“被撤销”，排查时看不出来是哪种。

## 18.2 表结构与三个索引

邀请表在 `supabase/migrations/20261119090000_invitations.sql` 里建。

```sql
-- supabase/migrations/20261119090000_invitations.sql
create extension if not exists pgcrypto with schema extensions;

-- 沿用第 8 章的结构，这里只补齐索引
create index if not exists invitations_token_idx on public.invitations (token);
create index if not exists invitations_team_status_idx on public.invitations (team_id, status);

-- 同一个团队、同一个邮箱，最多只能有一条待处理的邀请
create unique index if not exists invitations_pending_unique
  on public.invitations (team_id, lower(email))
  where status = 'pending';
```


三个索引各有用途。

`token` 上的唯一索引保证一个 token 只能对应一条邀请。查询时按 token 查，命中索引。

`(team_id, lower(email)) where status = 'pending'` 是部分唯一索引，保证同一个团队对同一个邮箱只有一条待处理邀请。`where` 子句让它只覆盖 pending，历史记录可以有任意多条。

`(team_id, status)` 用于成员页列出待处理邀请。

索引名带 `_pending_unique` 后缀，看到名字就知道是部分索引。

## 18.3 token 只存哈希

token 是一个 32 字节的随机串，用 base64url 编码后 43 个字符。

```ts
// src/lib/invitations.ts（片段）
import { randomBytes, createHash } from "node:crypto";

export function createInviteToken() {
  return randomBytes(32).toString("base64url");
}

export function hashInviteToken(token: string) {
  return createHash("sha256").update(token).digest("hex");
}
```

数据库里存 `hashInviteToken(token)` 的结果，64 个十六进制字符。原始 token 只出现在邮件链接里。

三个理由。第一，数据库泄漏时攻击者拿不到可用的 token。第二，日志里不会出现明文 token。第三，支持人员看不到 token，只能重发，减少了社工路径。

不加盐。token 有 256 位熵，暴破不可行，加盐只会让查询变复杂。

```sql
insert into public.invitations (team_id, email, role, token, status, expires_at, invited_by)
values (
  '<你的 team_id>'::uuid,
  'lin@example.com',
  'member',
  'plain-token-123',
  'pending',
  now() + interval '7 days',
  '<你的 user_id>'::uuid
);
```

```bash
psql "$DATABASE_URL" -c "select id, email, token, status from public.invitations;"
```


手插明文 token 之后查一次，能看到明文就在库里。这是错误示范，用来体会“能直接看到”的风险。

## 18.4 创建邀请

创建分两步：先写库，再发信。

```ts
// src/app/(app)/dashboard/members/actions.ts
'use server'

import { revalidatePath } from 'next/cache'
import { z } from 'zod'
import { requireUser } from '@/lib/auth'
import { requireMembership } from '@/lib/teams'
import { createClient } from '@/lib/supabase/server'
import { createInviteToken } from '@/lib/invitations'
import { sendInviteEmail } from '@/lib/email'

const schema = z.object({
  teamSlug: z.string().min(1),
  email: z.string().email().max(254),
})

export async function inviteMember(formData: FormData) {
  const user = await requireUser()
  const parsed = schema.safeParse({
    teamSlug: formData.get('teamSlug'),
    email: formData.get('email'),
  })
  if (!parsed.success) return { ok: false, error: '邮箱格式不对' }

  const email = parsed.data.email.trim().toLowerCase()
  const { team } = await requireMembership(user.id, parsed.data.teamSlug, { role: 'owner' })

  const supabase = await createClient()
  const { token, tokenHash } = createInviteToken()
  const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000).toISOString()

  const { data: invitation, error } = await supabase
    .from('invitations')
    .insert({
      team_id: team.id,
      email,
      role: 'member', // 写死。不接受前端传入
      token: tokenHash,
      status: 'pending',
      expires_at: expiresAt,
      invited_by: user.id,
    })
    .select('id')
    .single()

  if (error) {
    // 23505 = 唯一约束冲突，说明已经有 pending 邀请
    if (error.code === '23505') {
      return { ok: false, error: '这个邮箱已经有一条待处理的邀请了' }
    }
    return { ok: false, error: '邀请创建失败' }
  }

  const inviteUrl = `${process.env.NEXT_PUBLIC_SITE_URL}/invite/${token}`

  try {
    await sendInviteEmail({ to: email, teamName: team.name, inviteUrl, inviterName: user.email })
  } catch (err) {
    // 邮件失败不删邀请：让 owner 能点「重发」，省去重头再填一遍
    console.error('send invite email failed', invitation.id, err)
    return { ok: false, error: '邀请已创建，但邮件发送失败，请稍后重发' }
  }

  revalidatePath('/dashboard/members')
  return { ok: true }
}
```


顺序不能反。先发信后写库，写库失败时用户收到一条点不开的链接。

几个细节。角色写死 `member`，邀请人不能通过这个接口发出 owner 邀请。`role` 也写在 policy 的 `with check` 里，双保险。

重复邀请时 `insert` 会撞部分唯一索引，返回错误码 `23505`。捕获之后给用户一句“已经邀请过了”，不要抛 500。

邮件发送失败时不删记录。用户看到“已发送”，链接实际没到；这时管理员可以重发，记录还在。

`NEXT_PUBLIC_SITE_URL` 用来拼链接，不要用请求头里的 host，反向代理下会拼错。

## 18.5 发信

邮件用 Resend 发，模板是一个简单的 HTML。

```ts
// src/lib/email.ts
import 'server-only'

import { Resend } from 'resend'

const resend = new Resend(process.env.RESEND_API_KEY)

export async function sendInviteEmail(input: {
  to: string
  teamName: string
  inviteUrl: string
  inviterName: string
}) {
  const { error } = await resend.emails.send({
    from: 'TeamStack <noreply@teamstack.app>',
    to: input.to,
    subject: `${input.inviterName} 邀请你加入 ${input.teamName}`,
    html: `
      <p>${input.inviterName} 邀请你加入 <strong>${input.teamName}</strong>。</p>
      <p><a href="${input.inviteUrl}">接受邀请</a></p>
      <p>链接 7 天内有效，只能使用一次。若非你本人操作，忽略这封邮件即可。</p>
    `,
  })
  if (error) throw new Error(error.message)
}
```


三条注意。

链接里的 token 是明文，邮件正文里也只出现一次。不要写“请妥善保管”，用户没法保管一个点开就失效的链接。

HTML 里插入用户可控内容（团队名、邀请人名字）必须转义。不转义时，团队名里带标签就能注入。

`replyTo` 设成邀请人的邮箱。收件人回复时直接到人，不用经过客服。

## 18.6 预览页

被邀请人点开链接，先看到预览：团队名、邀请人、自己的邮箱。

```tsx
// src/app/invite/[token]/page.tsx
import Link from 'next/link'
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'
import { getCurrentUser } from '@/lib/auth'
import { hashInviteToken } from '@/lib/invitations'
import { AcceptButton } from './accept-button'

export default async function InvitePage({ params }: { params: Promise<{ token: string }> }) {
  const { token } = await params
  const user = await getCurrentUser()

  if (!user) {
    redirect(`/login?next=${encodeURIComponent(`/invite/${token}`)}`)
  }

  const supabase = await createClient()
  const { data: invite } = await supabase
    .from('invitations')
    .select('email, role, status, expires_at, teams(name)')
    .eq('token', hashInviteToken(token))
    .maybeSingle()

  // 查不到：token 不对，或者 RLS 拦了（与自己那条无关的邀请）
  const expired = invite ? new Date(invite.expires_at) < new Date() : false
  const usable = !!invite && invite.status === 'pending' && !expired

  return (
    <main>
      <h1>加入团队</h1>
      {!usable ? (
        <p>这个邀请链接无效、已过期，或者已经被使用过了。</p>
      ) : invite.email !== user.email ? (
        <p>这个邀请是发给 {invite.email} 的，请用那个邮箱登录后再打开。</p>
      ) : (
        <>
          <p>你被邀请加入 {invite.teams?.name}，角色是{invite.role === 'owner' ? '管理员' : '成员'}。</p>
          <AcceptButton token={token} />
        </>
      )}
      <Link href="/dashboard">返回控制台</Link>
    </main>
  )
}
```


页面要处理四种访问者。

已登录且邮箱匹配：显示“加入”按钮。

已登录但邮箱不匹配：提示“这条邀请是发给另一个邮箱的”。

未登录：显示“登录后加入”，登录后回到这个页面。

token 无效或过期：显示错误，不给任何操作。

预览数据由 `get_invite_preview` 函数提供。被邀请人此时尚无成员身份，`teams` 表的 policy 不让他读团队名，所以要用 `security definer` 函数。

```sql
-- supabase/migrations/20261119092000_invite_preview.sql
create or replace function public.get_invite_preview(p_token text)
returns table (
  team_name text,
  inviter_email text,
  invitee_email text, -- 已打码
  status text,
  expires_at timestamptz
)
language sql
stable
security definer
set search_path = ''
as $$
  select
    t.name,
    coalesce(inviter.email, '已离开的成员'),
    regexp_replace(i.email, '^(.).*(@.*)$', '\1***\2'),
    i.status,
    i.expires_at
  from public.invitations i
  join public.teams t on t.id = i.team_id
  left join public.profiles inviter on inviter.id = i.invited_by
  where i.token = extensions.digest(p_token, 'sha256')
    and t.deleted_at is null
  limit 1;
$$;

revoke all on function public.get_invite_preview(text) from public;
grant execute on function public.get_invite_preview(text) to anon, authenticated;
```


函数里对邮箱打码：`a***@example.com`。预览页不需要完整邮箱。

## 18.7 接受邀请

接受是唯一会改数据的动作，放在事务函数里。

```sql
-- supabase/migrations/20261119091000_accept_invitation.sql
create or replace function public.accept_invitation(p_token text)
returns uuid
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_uid uuid := (select auth.uid());
  v_email text;
  v_inv public.invitations;
begin
  if v_uid is null then
    raise exception 'not authenticated';
  end if;

  select p.email into v_email from public.profiles p where p.id = v_uid;

  -- 关键：for update 锁住这一行，两个并发请求只有一个能往下走
  select * into v_inv
  from public.invitations
  where token = extensions.digest(p_token, 'sha256')
    and status = 'pending'
  for update;

  if not found then
    raise exception 'invitation not found or already used';
  end if;

  if v_inv.expires_at <= now() then
    update public.invitations set status = 'expired' where id = v_inv.id;
    raise exception 'invitation expired';
  end if;

  if lower(v_inv.email) <> lower(coalesce(v_email, '')) then
    raise exception 'invitation belongs to another email';
  end if;

  insert into public.team_members (team_id, user_id, role)
  values (v_inv.team_id, v_uid, v_inv.role)
  on conflict (team_id, user_id) do nothing;

  update public.invitations set status = 'accepted' where id = v_inv.id;

  insert into public.activity_logs (team_id, actor_id, action, target_type, target_id, metadata)
  values (
    v_inv.team_id, v_uid, 'member.joined', 'invitation', v_inv.id,
    jsonb_build_object('email', v_inv.email, 'role', v_inv.role)
  );

  return v_inv.team_id;
end;
$$;

revoke all on function public.accept_invitation(text) from public;
grant execute on function public.accept_invitation(text) to authenticated;
```


函数做五件事：锁行、校验状态、校验邮箱、插入成员、更新邀请状态。全部在一个事务里，任何一步失败都回滚。

`for update` 锁住这一行，防止两个标签页同时点。

邮箱比较用 `lower()`，大小写不影响。

`on conflict do nothing` 处理“已经是成员”的情况。重复点接受不会报错，也不会插重复行。

审计日志在同一个事务里写。中途失败时，邀请状态和成员行都不变，日志也不会留下。

## 18.8 用过的链接必须失败

一次性是邀请的核心属性。三层保证。

第一层，状态检查。函数里判断 `status = 'pending'`，`accepted` 的直接返回错误。

第二层，唯一约束。成员表的主键是 `(team_id, user_id)`，重复插入被约束挡掉。

第三层，token 哈希。接受成功后把 token 置空或保留但状态改变，再次查询拿不到 pending 记录。

```sql
update public.invitations
set status = 'expired'
where status = 'pending' and expires_at <= now();
```


三层里任何一层单独都能挡住重复使用，三层叠加是为了防并发和防绕过。

## 18.9 过期与清理

过期有两种处理方式：懒过期和定时清理。

懒过期在读取时判断：查询里加 `expires_at > now()`。过期的邀请自然不出现，不需要改状态。

定时清理把状态改成 `expired`，让统计准确。用 `pg_cron` 每天跑一次。

```sql
-- supabase/migrations/20261119093000_expire_invitations.sql
create or replace function public.expire_stale_invitations()
returns integer
language plpgsql
security definer
set search_path = ''
as $$
declare
  affected integer;
begin
  update public.invitations
     set status = 'expired'
   where status = 'pending'
     and expires_at < now();
  get diagnostics affected = row_count;
  return affected;
end;
$$;

revoke all on function public.expire_stale_invitations() from public;
```


清理函数只处理 pending 且已过期的行。`updated_at` 也一起更新，方便看什么时候被清理。

**未验证**：`pg_cron` 的启用方式随 Supabase 版本变化，以 Dashboard 的 Database → Extensions 为准。

## 18.10 撤销与重发

撤销是把状态改成 `revoked`，链接立即失效。

```ts
// src/app/(app)/dashboard/members/actions.ts（追加）
export async function revokeInvite(formData: FormData) {
  const user = await requireUser()
  const teamSlug = String(formData.get('teamSlug'))
  const invitationId = String(formData.get('invitationId'))

  const { team } = await requireMembership(user.id, teamSlug, { role: 'owner' })
  const supabase = await createClient()

  const { error } = await supabase
    .from('invitations')
    .update({ status: 'revoked' })
    .eq('id', invitationId)
    .eq('team_id', team.id) // 不能省：防止改到别的团队的邀请
    .eq('status', 'pending') // 不能省：只能撤销待处理的

  if (error) return { ok: false, error: '撤销失败' }
  revalidatePath('/dashboard/members')
  return { ok: true }
}
```


重发是插一条新行，不把旧行改回 `pending`。旧行保持原状态，历史记录完整。

重发前可以先撤销旧的，避免两条 pending 同时存在。部分唯一索引会挡住第二条，报 `23505`。

成员页列出待处理邀请：

```sql
-- 成员页的待处理列表
select i.id,
       i.email,
       i.role,
       i.created_at,
       i.expires_at
from public.invitations i
where i.team_id = $1
  and i.status = 'pending'
order by i.created_at desc
limit 50;
```


## 18.11 不能提权

邀请接口的入参里有 `role`，攻击者可以改成 `owner`。

三道防线。第一，action 里写死 `role: "member"`，不接受客户端传值。第二，policy 的 `with check` 里限制 `role = 'member'`。第三，接受邀请的函数里再检查一次。

表结构允许 `owner` 是有原因的：`transfer_ownership` 需要写 owner 行。但邀请通道不能写。

角色提升只能通过转让所有权完成，那是另一个函数，要求当前用户是 owner 且经过二次确认。

## 18.12 防滥用

邀请会发邮件，滥用就是邮件轰炸器。

三个限制。每个 owner 每小时最多 20 条邀请，用 SQL 统计 `invitations` 表的插入数。同一个邮箱 24 小时内最多 3 条。全站每小时上限，防止新注册账号刷。

不透露邮箱是否存在。无论对方有没有账号，接口都返回“已发送”。

域名白名单是可选项。企业版可以限制只能邀请公司域名，减少误发。

## 18.13 边界场景

六个场景，每个都有明确处理。

已经是成员：`on conflict do nothing`，返回成功。

团队已软删：函数里查 `teams.deleted_at`，非空时报错。

邀请人离开了团队：邀请仍然有效。邀请记录里有 `invited_by`，但权限判断看的是团队本身。

邮箱大小写不同：用 `lower()` 比较。

被邀请人还没有账号：先注册，注册流程保留 `next` 参数，注册完回到邀请页。

撤销与接受并发：`for update` 保证只有一个成功。

## 18.14 邮件扫描器

企业邮箱会预取链接，检查是否钓鱼。预取是一个 GET 请求。

GET 请求不能产生副作用。预览页只读，接受动作在按钮后面，用 POST 提交。这样扫描器预取不会消耗邀请。

如果接受写成“打开链接即加入”，扫描器会把邀请用掉，用户点开时已经失效。

## 18.16 邀请表的 policy

邀请表的行只有 owner 能看。被邀请人看的是预览函数返回的摘要，读不到表里的行。

```sql
-- supabase/migrations/20261119090000_invitations.sql（policy 片段）
alter table public.invitations enable row level security;
revoke all on table public.invitations from anon, authenticated;
grant select, insert, update on table public.invitations to authenticated;

create policy "invitations_select_owner" on public.invitations
  for select to authenticated
  using (
    exists (
      select 1 from public.team_members m
      where m.team_id = invitations.team_id
        and m.user_id = (select auth.uid())
        and m.role = 'owner'
    )
  );

create policy "invitations_insert_owner" on public.invitations
  for insert to authenticated
  with check (
    role = 'member'
    and invited_by = (select auth.uid())
    and exists (
      select 1 from public.team_members m
      where m.team_id = invitations.team_id
        and m.user_id = (select auth.uid())
        and m.role = 'owner'
    )
  );
```

`role = 'member'` 写在 `with check` 里，是防提权的第二道防线。第一道在 action 里。

被邀请人没有成员身份，读不到这一行。这也是为什么预览要用 `security definer` 函数。

## 18.17 过期时间定多长

默认 7 天。理由有三个。

太短（比如 1 小时）：用户可能第二天才看到邮件，尤其是发到公司邮箱之后被规则拦了一下。

太长（比如 30 天）：链接在邮箱里长期有效，转发风险变大。离职员工的邮箱里还留着可用的邀请。

7 天覆盖了绝大多数情况，超过 7 天没用上的，重发一次的成本很低。

`expires_at` 用 `timestamptz`，存绝对时间。不要存“创建时间 + 天数”，那样每次查询都要算。

时间比较一律用数据库的 `now()`，不要用应用服务器时间。两者时钟可能有偏差。

## 18.18 token 放在路径里还是查询串里

链接有两种形状：`/invite/<token>` 和 `/invite?token=<token>`。

路径形式更好。第一，日志里更清楚，Nginx 的 access log 默认记录路径但不记录查询串。第二，分析工具能按路径分桶。

风险是 Referer 泄漏。页面里如果有外链，浏览器会把完整 URL 带到第三方。预览页不要放外链，或者加 `Referrer-Policy: no-referrer`。

查询串形式的风险是历史记录和分享面板会带上参数，反而更容易被误转发。

两种都有风险，路径形式配合 `no-referrer` 是常见选择。

## 18.19 对方已经有账号

被邀请人可能已经注册过。这时接受流程要跳过注册，直接登录。

判断方式：预览页显示“登录后加入”，用户登录后回到同一页面，按钮变成“加入团队”。

不要试图在服务端判断邮箱有没有账号。那个信息不该暴露，判断本身也会泄露。

登录后回到原页面的实现，靠 `next` 参数，第 15 章里有 `safeNext` 的写法。

## 18.20 席位配额

团队套餐限制人数时，邀请前要查配额。

第 21 章会给 `getEntitlements(teamId)`，返回 `{ seats: { used, limit } }`。邀请前判断 `used >= limit` 就返回错误码 `seats_quota_exceeded`。

待处理的邀请不占席位。只有真正加入的人才算。所以判断用 `used`，不用 `used + pending`。

接受邀请时也要查一次。邀请发出之后对方可能过了几天才接受，期间团队可能已经满了。

## 18.21 通知与审计

三个动作要留审计：`invitation.created`、`invitation.revoked`、`member.joined`。

审计写 `activity_logs`，`metadata` 里放 `{ email, role }`。不要放 token。

要不要给 owner 发通知？如果邀请是别人发的，owner 通常想知道。写一条 `notifications` 记录，`kind = 'member_invited'`。

被邀请人不需要站内通知，他用的是邮件。

## 18.22 批量邀请

一次粘贴多个邮箱是常见需求。

实现方式：逐个插入，每个独立事务。一个失败不影响其它，最后汇总结果返回给前端。

不要用一个事务包住全部。中间一个邮箱格式错，整批回滚，用户要重来。

单次上限建议 20 个，超过就让用户分批。批量邀请同样受限流约束。

返回结构用 `{ ok: [...], failed: [{ email, reason }] }`，前端逐条显示。

## 18.23 送达率

邀请邮件进垃圾箱，是这类功能最常见的问题。

三件事影响送达率。第一，发信域名要配 SPF、DKIM、DMARC。第二，`From` 地址用子域名，比如 `invite@teamstack.app`，与主站域名分开，避免主站信誉被拖累。第三，正文里不要有大量链接和短链。

Resend 的域名验证会给三条 DNS 记录，配好之后发一封测试信，看 `Authentication-Results` 头是否通过。

**未验证**：具体 DNS 记录的字段名以 Resend 控制台为准。

## 18.24 邀请的转化率

值得看的两个数字：发出多少条、接受多少条。

查询用 `activity_logs` 或 `invitations` 的 `created_at`，按周聚合。30 天窗口够看趋势。

```sql
-- 过去 30 天的邀请转化
select
  count(*) filter (where status = 'accepted') as accepted,
  count(*) as total,
  round(100.0 * count(*) filter (where status = 'accepted') / nullif(count(*), 0), 1) as rate
from public.invitations
where created_at > now() - interval '30 days';
```

转化率低通常是三个原因：邮件进了垃圾箱、邀请人没通知对方、链接过期。三个原因对应三种改法。

## 18.25 链接里不带团队标识

邀请链接只放 token，不放 `team_id` 或团队 slug。

理由是可枚举性。`/invite/<team-slug>/<token>` 这种形状，攻击者能先探测哪些团队存在，再专注于猜 token。只放 token 时，没有 token 就没有任何信息。

还一个理由：重命名团队时 slug 会变，链接里带 slug 会让旧链接失效。

预览页需要团队名时，由 `get_invite_preview` 函数按 token 查。团队名不进入 URL。

## 18.26 链接被转发

邀请邮件可能被转发给同事。同事点开，邮箱不匹配。

处理方式是明确提示“这条邀请是发给 xxx 的”，并给一个“让管理员重新邀请我”的按钮。不要静默失败。

不要做成“谁点谁进”。那样转发就等于授权，邀请人无法控制谁能加入。

邮箱匹配的判断在 `accept_invitation` 函数里，用 `lower(auth.jwt()->>'email')` 与 `lower(invitations.email)` 比较。

注意：JWT 里的 email 可能是旧的。用户改过邮箱之后，旧 token 里的 email 还没刷新。这种情况让用户重新登录一次。

## 18.27 什么时候该撤销

三种情况要主动撤销：发错邮箱、成员已经在别的团队、邀请对应的项目取消。

撤销的实现是把状态改成 `revoked` 并写审计。不要直接删行，删了之后没法解释“这条邀请去哪了”。

撤销之后链接立即失效。已经打开的预览页再点“加入”会报“邀请已失效”。

界面上的撤销按钮放在成员页的待处理列表里，每条一行，带撤销和重发两个操作。

## 18.28 两个 owner 同时邀请

两个 owner 在同一秒给同一个邮箱发邀请。

部分唯一索引会挡住第二条，报 `23505`。捕获之后有两种处理：返回“已邀请”，或者把旧邀请撤销再插新的。

推荐第一种。第二条邀请多半是无意的，重发新链接反而会让已经收到第一封的人困惑。

并发下还有一个小坑：两条请求都通过了“先查有没有 pending”的判断，然后同时插入。唯一索引是最终防线，应用层的检查只用来给友好提示。

## 18.29 邀请数据的保留期限

邀请表里有邮箱，属于个人信息。

保留策略：`accepted` 的记录保留 90 天，用于转化统计；`expired` 和 `revoked` 的保留 90 天；超过之后删除或匿名化（把 email 改成 `deleted@example.com`）。

实现是一个 `security definer` 函数，按时间和状态删除，`grant execute` 只给 `service_role`，每天跑一次。

删除之前先确认没有被审计日志引用。`activity_logs.metadata` 里如果存了邮箱，那部分也要一起处理。

## 18.30 注册流程怎么带住邀请

被邀请人没有账号时，走注册流程。注册完要回到邀请页，并且邮箱要和邀请一致。

两个做法。第一，注册页把邮箱预填进去并设为只读。第二，注册成功后不自动登录，让用户去点邀请链接。

推荐第一个。邮箱只读防止填错，注册成功后直接回邀请页，减少一次跳转。

实现上，注册 action 接收一个隐藏字段 `invite_token`，注册时用它查一次预览，拿到邮箱，作为注册邮箱。这个字段不能由前端决定邮箱，否则等于任意注册。

`invite_token` 也要校验：状态是 pending、没过期。校验失败就当普通注册处理。

## 18.31 一条 SQL 看邀请健康度

上线之后定期跑，能提前发现邮件问题。

```sql
-- 待处理邀请的状态分布
select
  count(*) filter (where expires_at <= now()) as expired_pending,
  count(*) filter (where expires_at > now()) as live_pending,
  min(expires_at) as next_expiry
from public.invitations
where status = 'pending';
```

`expired_pending` 长期大于 0，说明清理任务没跑，或者用户根本没点。

`live_pending` 突然变多，说明有人批量发邀请，要么是业务增长，要么是滥用。

再看一眼转化率的分母，就能判断是邮件问题还是产品问题。

## 18.32 邀请与订阅状态

团队订阅失效时，邀请要不要停？

产品上的选择是：订阅过期进入宽限期，邀请仍然可用；宽限期结束之后降级到免费档，超过免费档席位的邀请被拒绝，提示升级。

实现上，邀请前查 `getEntitlements`，它内部按 `subscriptions.status` 和 `current_period_end` 判断当前套餐。过期但有 7 天宽限的，按付费档算。

`current_period_end` 在数据库里是秒级时间戳，`new Date(x)` 之前要乘 1000。这个坑在第 21 章会再提一次。

## 18.33 检查点

1. 用已经接受过的 token 再调一次 `accept_invitation`，返回错误，`team_members` 没有新行。
2. 人为让接受过程失败（比如把函数里插入成员的语句改成非法 SQL），确认 `invitations` 状态仍是 `pending`，`team_members` 没有新行。
3. 用 owner 的 token 调邀请接口并传 `role: "owner"`，插入的仍是 `member`。
4. 同一个邮箱连发两次邀请，第二次报 `duplicate key`，返回给用户的文案是“已邀请”。
5. 把一条 `pending` 邀请的 `expires_at` 改到昨天，再打开链接，预览页显示“已失效”，按钮消失。
6. 查一次 `invitations.token` 的长度，是 64 个十六进制字符，库里没有 43 字符的明文 token。

## 18.34 常见错误

1. token 明文存库

现象：数据泄漏时攻击者可以直接用库里的 token 登录。原因：存了原始 token。改法：只存 sha256，原始 token 只出现在邮件里。

2. 先发信后写库

现象：用户收到点不开的链接。原因：写库失败但信已发出。改法：先写库，再发信，发送失败只记日志。

3. 接受时没有事务

现象：成员加进去了，邀请状态还是 pending，或者相反。原因：两条语句分开执行。改法：写成一个 `security definer` 函数，单事务执行。

4. 用 `updated_at` 判过期

现象：刚创建的邀请被判成过期。原因：`updated_at` 在状态变化时更新，不代表创建时间。改法：用 `expires_at` 判断。

5. 邮箱大小写导致重复邀请

现象：同一个邮箱出现两条 pending。原因：比较时没统一大小写。改法：索引用 `lower(email)`，插入前也 `lower()`。

6. 邀请接口能被 member 调用

现象：普通成员也能发邀请。原因：action 里只判断了登录，没判断角色。改法：`requireMembership(teamId, { role: "owner" })`，policy 里再限一次。

## 18.35 这一章在做什么

这一章把邀请的四条链路写完整：创建、发信、预览、接受，也把滥用与清理讲清。核心是四件事：token 只存哈希、状态机不可逆、接受必须在一个事务里、用过的链接必须失败。

下一章讲第三方登录。OAuth 也有一次性凭证（code）和状态参数（state），失败模式与这一章相似：code 用过即废，state 不匹配要拒绝。
