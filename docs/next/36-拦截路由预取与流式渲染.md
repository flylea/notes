# 第 36 章 拦截路由、预取与流式渲染

这一章讲三组机制：拦截路由让同一个 URL 有两种呈现形态，预取让下一次导航提前准备好，流式渲染让页面分块到达。三者配合，导航时就没有空白期。

需要这些机制的原因在于首屏之后的时间。页面加载完成后，用户所有动作都在客户端完成，点一个链接，浏览器要等服务端算完才能显示新内容。这段时间通常几百毫秒，慢查询下会到两三秒，屏幕上是空白或者不动的旧页面。

涉及的概念较多，按顺序是下面几项：

- 拦截路由与平行路由插槽
- 预取的触发阶段与 `staleTimes`
- App Shell 与静态 shell
- Partial Prefetching 与 `prefetch()`
- 即时导航与 `instant`、`io()`
- React `<Activity>` 的状态保留
- 水合前的闪烁

这些机制彼此衔接，下面逐个说明。

## 36.1 一次导航经历了什么

点击一个链接到内容出现，中间有四步。

第一步，Next.js 检查客户端缓存里有没有这份路由数据。有就直接渲染，这一步是毫秒级。

第二步，没有缓存时预取是否命中。链接进入视口后，框架可能已经在后台请求过这份数据，命中时同样很快。

第三步，都没命中就发请求。请求带 `RSC: 1` 头，服务端只返回组件树序列化结果，不返回 HTML。

第四步，服务端开始渲染。同步部分立刻发回，异步部分在 `<Suspense>` 边界处先发占位内容，数据好了再补发。

四步里能优化的有三处：让第二步多命中，让第三步少等，让第四步先出骨架。

白屏有三种来源，对应三种修法。客户端缓存为空，导航要等完整请求，这是第三步的问题。请求发出去了，服务端整页都在等一个慢查询，这是第四步的问题。数据都回来了，首次渲染的 JS 还没下载完，这一处要靠减少首屏 JS 的体积解决。

三种来源在 Network 面板里能分开看。请求时长、等待首字节、脚本下载各占一段时间，先量清哪一段最长，再决定改哪里。这一章的结构就是围绕这三处展开。

客户端缓存与浏览器 HTTP 缓存是两套东西。前者存组件树的序列化结果，只在当前会话里有效，刷新页面就清空。后者由浏览器按响应头管理，存 HTML 和静态资源。调导航速度主要靠前者，调重复访问速度靠后者。

客户端导航取回的 payload 只包含变化的部分。共享布局不会重新渲染，页面段替换掉旧的。这条规则解释了很多现象：布局里做的请求不会因为切换页面而重跑，页面里做的请求每次都要重新走一遍。

## 36.2 拦截路由：一个 URL 两种形态

文件列表点进某个文件，常见做法是整页跳到详情页。用户回来时列表滚动位置丢了，筛选条件也没了。

拦截路由把详情页“拦截”成一个模态，覆盖在当前列表上。URL 变成 `/files/abc`，页面还是列表，模态浮在上面。

目录结构：

```text
src/app/(app)/files/
├── layout.tsx              列表与模态两个插槽
├── page.tsx                列表页 /files
├── [id]/
│   ├── page.tsx            整页详情 /files/abc
│   └── file-detail.tsx     详情内容，两个形态共用
└── @modal/
    ├── default.tsx         插槽不活跃时返回 null
    └── (.)[id]/
        └── page.tsx        拦截版：/files/abc 渲染成模态
```

`@modal` 是平行路由插槽，不算路由段。它的目录不进 URL，只决定同一层可以并行渲染几块内容。

插槽的名字可以随便起，`@modal`、`@panel`、`@detail` 都行。框架按名字把内容交给同层的 layout，layout 决定放在页面的哪个位置。一个 layout 可以接多个插槽，每个插槽独立匹配、独立渲染。

插槽的另一个作用是把「可选的一块界面」从页面结构里拆出来。页面的 `children` 只管列表，模态只管覆盖层，两者的加载失败互不影响。

一次站内点击会同时算两棵树：一棵是当前路由的 `children`，一棵是插槽。拦截目录匹配上时，插槽里渲染详情，`children` 保持列表；匹配不上时，插槽走 `default`，只剩下列表。渲染结果里两个插槽并排出现，谁覆盖谁由 CSS 决定。

这也解释了为什么模态里的数据请求不会拖住列表。两个插槽各自流式输出，谁先好谁先出现。

```tsx
// src/app/(app)/files/layout.tsx
export default function FilesLayout({
  children,
  modal,
}: {
  children: React.ReactNode;
  modal: React.ReactNode;
}) {
  return (
    <>
      {children}
      {modal}
    </>
  );
}
```

```tsx
// src/app/(app)/files/@modal/default.tsx
export default function Default() {
  return null;
}
```

`default.tsx` 在插槽没有匹配内容时渲染。没有它，刷新非拦截地址会 404。

列表页用 `<Link>` 打开，加 `scroll={false}` 保留滚动位置：

```tsx
// src/app/(app)/files/page.tsx
import Link from "next/link";
import { listFiles } from "@/lib/files";

export default async function FilesPage() {
  const files = await listFiles();

  return (
    <ul className="divide-y divide-neutral-200">
      {files.map((file) => (
        <li key={file.id}>
          <Link href={`/files/${file.id}`} scroll={false} className="flex min-h-11 items-center gap-3 px-4">
            <span className="truncate">{file.name}</span>
          </Link>
        </li>
      ))}
    </ul>
  );
}
```

两个形态共用一个内容组件，避免写两遍：

```tsx

        <dt className="text-neutral-600">状态</dt>
        <dd>{file.status}</dd>
      </dl>
    </div>
  );
}
```

```tsx

import { FileModal } from "./file-modal";
```

```tsx
// src/app/(app)/files/@modal/(.)[id]/file-modal.tsx
"use client";

import { useRouter } from "next/navigation";
import { useCallback, useEffect, useRef } from "react";

export function FileModal({ children }: { children: React.ReactNode }) {
  const router = useRouter();
  const ref = useRef<HTMLDialogElement>(null);
  const close = useCallback(() => router.back(), [router]);

  useEffect(() => {
    const dialog = ref.current;
    if (dialog && !dialog.open) dialog.showModal();
    return () => {
      if (dialog?.open) dialog.close();
    };
  }, []);

  return (
    <dialog
      ref={ref}
      onClose={close}
      aria-labelledby="file-modal-title"
      className="w-full max-w-lg rounded-lg p-0 backdrop:bg-black/50"
    >
      <div className="border-b border-neutral-200 p-4">
        <h2 id="file-modal-title" className="text-lg font-semibold">文件详情</h2>
      </div>
      <div className="p-4">{children}</div>
    </dialog>
  );
}
```

拦截语法的四种前缀：

- `(.)` 匹配同级路由段。
- `(..)` 匹配上一级。
- `(..)(..)` 匹配上两级。
- `(...)` 从 `app/` 根开始匹配。

判断依据是路由段，文件系统层级不算。`@modal` 插槽目录要跳过，所以 `@modal/(.)[id]` 里的 `(.)` 只上升一层，落到 `files`。

`(..)` 用在跨一层的场景。团队列表点成员，详情挂在团队下面，这时列表页在 `teams/[teamId]/members`，拦截目录写成 `@modal/(..)members/[userId]`，从 `members` 段往上一级落到 `[teamId]`。

数错层级是这类报错的主要来源：目录建对了，前缀写错一级，页面能打开，但永远走不到拦截分支。排查方法是把 URL 和段名对一遍，中间跳过所有 `@slot` 目录。

## 36.3 拦截路由的边界

同一个地址，四种进入方式，结果不同：

| 进入方式 | 结果 |
| --- | --- |
| 站内点击链接 | 列表保持，模态浮在上面，URL 变成详情地址 |
| 刷新页面 | 模态消失，整页详情 |
| 直接粘贴地址 | 整页详情 |
| 从详情页后退 | 回到列表，滚动位置与筛选条件保留 |

第二种和第三种是设计结果，并非缺陷。模态只是“从列表进入”的一种呈现，地址本身仍要能独立打开。

分享链接给别人，对方看到整页详情，这是对的。放到收藏夹里，下次打开也是整页。

整页形态还有一个作用：搜索引擎与社交平台的抓取器只会拿到整页 HTML，它们不执行客户端导航。所以详情页的标题、描述、结构化数据都要写在整页那一支里，写在模态里等于没写。

模态只影响站内点击的体验，地址本身仍然是完整页面。这条约束反过来限制了用法：内容必须有独立地址，模态里不适合放只能从列表进入、无法独立渲染的东西。

模态状态的保存依赖浏览器历史。用户按浏览器后退，URL 回到 `/files`，插槽失去匹配，模态自动关闭。这个行为由路由驱动，不需要在代码里额外监听。

前进也成立。用户按后退关掉模态，再按前进，地址回到详情，插槽重新匹配，模态再次打开。列表状态一直在，因为它从来没有被卸载。

这条规则有个前提：关闭模态必须走 `router.back()`。用 `router.push('/files')` 关的话，历史里多一条记录，用户要多按一次后退才能离开列表页。

打开模态时别切换列表的内容。列表重新渲染会丢滚动位置，模态关闭后回到列表顶部，体验像是重新加载。

模态打开期间要锁住背景滚动，否则滚轮会滚到列表上。`<dialog>` 的 `showModal()` 会自己处理这一层：背景元素被标记为惰性，点击与滚动都不再响应。手写遮罩层时要自己做这两件事，漏一件就会出现「滚动穿透」。

模态的关闭按钮要有名字。图标按钮配 `aria-label="关闭"`，否则读屏软件只会念出「按钮」。Esc 键的关闭由 `dialog` 提供，不用另外监听。

拦截路由只对第一层链接生效。模态里再点一个链接，会正常整页跳转，因为拦截规则只匹配了一层。要在模态里继续拦截，得再加一层 `(.)` 目录。

多层拦截的复杂度上升很快。用户在两层的模态里按后退，要按两次才能回到列表，注意力也会分散。实践里一层够用，第二层信息直接放进第一层的滚动区域。

拦截目录不影响直接访问。删掉 `@modal` 整个插槽，站内点击就会整页跳转，地址与内容都不变。这也是一种回退手段：拦截逻辑出问题时，先摘掉插槽，功能仍然可用。

## 36.4 预取：三个阶段

预取在浏览器空闲时提前请求路由数据。触发顺序是：

1. 链接进入视口。
2. 鼠标悬停或触摸开始。
3. 新的链接替换旧的，旧的预取请求可能被取消。
4. 链接滚出视口，预取被丢弃。

自动预取只在生产构建里跑。`pnpm dev` 不预取，因为开发服务器要按需编译，预取会把编译时间放大。看预取效果必须 `pnpm build && pnpm start`。

预取的范围和路由类型有关。静态路由整页预取。动态路由没有 `loading.tsx` 时框架不预取，因为它不知道要等多久；有 `loading.tsx` 时预取到第一个 loading 边界为止。

`<Link>` 的 `prefetch` 属性控制得细一些：

| 值 | 行为 |
| --- | --- |
| 不写或 `"auto"` | 静态路由整页预取，动态路由预取到最近的 loading 边界 |
| `true` | 一律整页预取，包括动态路由 |
| `false` | 进入视口和悬停都不预取 |

列表项不要加 `prefetch={true}`。一屏五十行，每行都整页预取，等于把五十个请求同时打给服务端。默认行为已经够用。

预取的副作用要小心。预取会执行服务端渲染逻辑，写在 layout 顶层的副作用会被重复触发。渲染函数必须只读，发请求、写日志、扣额度这类动作放到 Server Action 或事件处理里。

预取会带上当前用户的 cookie。已经登出的用户在客户端切换账号后，旧的预取结果仍留在缓存里，直到页面刷新或缓存过期。涉及权限的内容不要依赖预取结果做判断，最终校验放在服务端读取那一刻。

预取的并发由框架调度，不需要手动排队。五十个链接同时在视口里时，请求会按优先级发，不会把服务端打满。手动 `router.prefetch()` 才需要自己控制频率。

预取命中的判断依据是路由与参数，不比对数据内容。同一地址在缓存有效期内不会重复请求，哪怕服务端数据已经变了。所以缓存时间要按数据的更新频率设置，不按用户的感受设置。

```tsx
// src/components/prefetch-on-hover.tsx
"use client";

import Link from "next/link";
import { useRouter } from "next/navigation";

export function PrefetchOnHover({ href, label }: { href: string; label: string }) {
  const router = useRouter();
  return (
    <Link href={href} onMouseEnter={() => router.prefetch(href)}>
      {label}
    </Link>
  );
}
```

`router.prefetch()` 是手动预热，适合从交互信号能提前判断去向的场景，比如搜索框选中结果之后。

预取请求在 Network 面板里能看到，形如 `GET /files/abc?_rsc=1x2y3`。返回的是 RSC payload，内容是组件树的序列化结果，没有 HTML 文档。预取只取数据，不执行水合，也不触发页面上的副作用。

预取失败不会报错，也不会重试。网络断了、服务端 500，用户点进去时照常走完整请求，只是慢一点。所以预取不能当作数据加载成功的保证。

观察预取时关掉浏览器的 Disable cache。开着这个选项，预取请求会被立刻丢弃，看不出来效果。

预取与 CDN 缓存是两层。CDN 缓存的是服务端响应，命中时预取请求很快返回；未命中时那个请求要等源站渲染。所以首屏之后的第一批导航耗时，取决于 CDN 命中率，与预取是否发生无关。

## 36.5 staleTimes：缓存多久

预取来的数据能复用多久，由 `staleTimes` 决定。

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  experimental: {
    staleTimes: {
      dynamic: 30,
      static: 180,
    },
  },
};

export default nextConfig;
```

单位是秒。`static` 默认 300 秒，作用于静态预渲染的页面、`prefetch={true}` 的全量预取、`router.prefetch()`。`dynamic` 默认 0，表示不缓存，每次导航重新请求。

改完配置要重新构建。`staleTimes` 在构建期确定，`pnpm dev` 的热更新不会重新读它。只在 dev 里改、直接切到生产，会发现设置没生效。

两个值不要一起调大。`dynamic` 调大的影响面比 `static` 广得多，它覆盖所有按需渲染的页面，包括带权限判断的后台。先只看 `static`，确有需要再动 `dynamic`。

Next.js 15 起 `dynamic` 的默认值从 30 改成 0。旧教程里写“默认 30 秒”是当时的默认值，照抄会出现“明明没配却在缓存”的困惑。

调大这两个值的效果是导航更快，代价是数据更旧。适合调的页面是内容变化慢的：定价、文档、帮助中心。不适合调的是权限相关页面，成员被移出团队后还能看三分钟后台，属于事故。

`staleTimes` 不影响三件事：服务端缓存、共享布局的重复渲染、浏览器前进后退的恢复。前进后退走的是浏览器的 bfcache，与这个配置无关。

要清理某一页的客户端缓存，用 `router.refresh()`。它会重新请求当前路由的数据，并替换掉现有内容。表单提交成功后调它，列表里就能看到新数据。

服务端那层缓存是另一套机制。`revalidateTag(tag, profile)` 与 `revalidatePath(path)` 清理的是数据缓存，客户端缓存的过期仍由上表两个数字决定。两者都配好，用户才能既看到新数据，又不至于每次导航都等。

## 36.6 Partial Prefetching 与 App Shell

开启 Cache Components 之后，预取的粒度变了。

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
};

export default nextConfig;
```

两个都是顶层配置，不放在 `experimental` 里。只开 `cacheComponents` 不设 `partialPrefetching`，控制台会提示需要显式指定。

开启后的行为：链接预取的是这一页的 App Shell，也就是静态外壳加会话相关内容。同一路由下的多个链接共用一个 shell，不再每个链接各预取一份整页数据。

`prefetch={true}` 的语义也变了。它从“整页预取”变成“App Shell 加上依赖这个链接 URL 数据的缓存内容”。只有页面内容真的依赖 `params` 或 `searchParams` 时才需要它。

迁移规则按内容性质分五类：

- 完全静态或已经 `'use cache'` 的内容：删掉 `prefetch={true}`。
- 未缓存但可缓存的内容：先加 `'use cache'`，再删掉 `prefetch={true}`。
- 依赖 `cookies()`、`headers()` 的内容：把查询包进 `'use cache'`，会话值作为参数传入，再删。
- 依赖 URL 数据的内容：保留 `prefetch={true}`。
- 实时内容：删掉 `prefetch={true}`，让它流式到达。

迁移按页进行，一次改一页。改完在开发环境看有没有 `instant-shell-url-data` 提示，在生产构建里对一遍导航耗时，确认变快再动下一页。

官方提供 codemod 做批量清理：

```bash
npx @next/codemod@canary remove-partial-prefetch ./src/app
```

路径写错时它只输出 `0 ok`，什么也不改。跑之前先提交一次，跑完用 `git diff` 核对。

需要把某段运行时工作挡在 App Shell 之外时，用 `prefetch()`：

```tsx
// src/components/recommendations.tsx
import { prefetch } from "next/cache";

async function getRecommendations() {
  const res = await fetch("https://api.example.com/recommendations", { cache: "no-store" });
  return res.json();
}

export async function Recommendations() {
  await prefetch();
  const items = await getRecommendations();
  return (
    <ul>
      {items.map((item: { id: string; title: string }) => (
        <li key={item.id}>{item.title}</li>
      ))}
    </ul>
  );
}
```

`await prefetch()` 之前的工作留在 shell 里，之后的工作推到预取阶段或导航时刻。它需要 Cache Components，没有开启时调用会抛错；必须在 `<Suspense>` 里用，否则开发环境会给出即时导航的提示。

`ensureStatic` 用声明的方式要求某一段必须静态。它适合给关键路径上保险：首页、定价页、登录页这些必须快的页面，写上一行，将来有人加了请求时数据，构建就会失败，不会悄悄变慢。

```ts
// src/app/(marketing)/pricing/page.tsx
export const ensureStatic = "shell";
```

上面这行只要求外壳静态，页面里仍可以流式加载数据。要求更严时写 `"navigation"`，代价是这一页的每个动态参数都必须能预先生成。

不要给整站铺这个配置。它是约束，写得越密，后续加功能的阻力越大。挑五到十个关键页面即可。

```ts
// src/app/(app)/pricing/page.tsx
export const ensureStatic = "navigation";
```

取值有五种：`'auto'`、`'shell'`、`'prefetch'`、`'navigation'`、`false`。这一项只在开启 Cache Components 时可用，写在客户端组件里会抛错。子段的要求不能比父段更宽松，违反时报：

```text
A child segment cannot override a parent segment with a less-constrained `ensureStatic`.
```

`'navigation'` 是最严的一档，要求这一页在导航时立即可用，动态路由还必须导出 `generateStaticParams()`。

开启 Partial Prefetching 后，同一路由下的多个链接共用一个 App Shell。列表页有五十行，每行的链接指向同一路由模板，预取时只取一份外壳，不再取五十份整页数据。带宽与内存都按这个比例下降。

全局开关关掉、又想逐页试用时，用段配置打开：

```ts
// src/app/(app)/files/page.tsx
export const prefetch = "partial";
```

这段配置只在开启 Cache Components 时有效，写在客户端组件里会抛错。有价值的值只有 `'partial'` 与 `'force-disabled'`，`'auto'` 是默认值，显式写出来没有意义。开发环境会提示 `instant-link-prefetch-partial`，属于配置提醒，不阻断构建。

## 36.7 静态 shell 与 Suspense 的摆放

静态 shell 指首屏异步工作完成之前就能发出去的那部分 HTML：布局、导航、Suspense 的 fallback。它决定了用户点下链接后多快能看到东西。

页面组件顶层 `await` 数据，整页都会变慢：

```tsx
// 反例
export default async function DashboardPage() {
  const stats = await getSlowStats();
  return (
    <main>
      <h1>概览</h1>
      <Stats data={stats} />
    </main>
  );
}
```

标题本来可以立刻出现，现在要等 `getSlowStats()`。修法是把 `await` 下沉到子组件，用 `<Suspense>` 包住只有它需要慢数据的那块：

```tsx
// src/app/(app)/dashboard/page.tsx
import { Suspense } from "react";
import { ActivityDigestSection } from "./activity-digest-section";

export default function DashboardPage() {
  return (
    <main id="main" tabIndex={-1} className="space-y-6 p-4 lg:p-8">
      <h1 className="text-2xl font-semibold">概览</h1>
      <Suspense fallback={<div className="h-32 animate-pulse rounded-lg bg-neutral-100" />}>
        <ActivityDigestSection />
      </Suspense>
    </main>
  );
}
```

```tsx
// src/app/(app)/dashboard/activity-digest-section.tsx
import { getActivityDigest } from "@/lib/activity";

export async function ActivityDigestSection() {
  const rows = await getActivityDigest();
  return (
    <ul className="divide-y divide-neutral-200 rounded-lg border border-neutral-200">
      {rows.map((row) => (
        <li key={row.id} className="p-3 text-sm">{row.summary}</li>
      ))}
    </ul>
  );
}
```

`cookies()`、`headers()`、`params` 也是同一类问题。在 layout 顶部 `await cookies()`，整棵子树退出静态 shell。正确做法是不 `await`，把 Promise 往下传，在就近的 Suspense 边界里解包：

```tsx
// src/app/(app)/layout.tsx
import { cookies } from "next/headers";
import { Suspense } from "react";
import { UserMenu } from "@/components/user-menu";

export default function AppLayout({ children }: { children: React.ReactNode }) {
  const cookieStore = cookies();
  return (
    <div className="flex min-h-dvh flex-col lg:flex-row">
      <nav aria-label="主导航">{/* 静态导航，不读 cookie */}</nav>
      <Suspense fallback={<div className="size-9 rounded-full bg-neutral-200" />}>
        <UserMenu cookiePromise={cookieStore} />
      </Suspense>
      <main id="main" tabIndex={-1} className="min-w-0 flex-1">
        {children}
      </main>
    </div>
  );
}
```

```tsx
// src/components/user-menu.tsx
import { Suspense, use } from "react";

type CookieStore = ReturnType<typeof import("next/headers").cookies>;

function Menu({ cookieStore }: { cookieStore: CookieStore }) {
  const store = use(cookieStore);
  const name = store.get("display_name")?.value ?? "未登录";
  return <span className="text-sm">{name}</span>;
}

export function UserMenu({ cookiePromise }: { cookiePromise: CookieStore }) {
  return (
    <Suspense fallback={<span className="text-sm text-neutral-500">……</span>}>
      <Menu cookieStore={cookiePromise} />
    </Suspense>
  );
}
```

`cookies()` 返回的 Promise 传进客户端边界之后，只有解包它的那个组件需要 Suspense，导航和 `{children}` 都留在静态 shell 里。

判断一块内容该不该进 shell，只看一个问题：这块内容对每个用户都一样吗。一样就留在 shell 里，不一样就包进 Suspense。

按这个标准过一遍页面，常见的划分是：标题、导航、表格骨架属于 shell；用户名、未读数、权限按钮属于 Suspense 里。划分对了，首屏的 HTML 里就有骨架，标签页的加载指示器也会更早消失。

`loading.tsx` 和 `<Suspense>` 的分工：

`loading.tsx` 是约定文件，放在哪个段，就覆盖哪个整段，写完即生效。`<Suspense>` 要显式包住组件，作用域由你自己划定。前者省事，后者精确。

`loading.tsx` 还有一个副作用：导航时它会被当作即时 fallback 预取，等于整页先出一层骨架。数据只影响页面下半部分时，这个代价偏大。

优先用靠近动态访问点的 `<Suspense>`。预渲染器遇到动态工作会向上找最近的边界，找不到就构建失败，报错类似：

```text
Route "/dashboard" used `cookies()` without a Suspense boundary.
```

高处的 `loading.tsx` 也算合法边界，但整页会退化成整页骨架，等于放弃了静态 shell 的大部分价值。

已经缓存过的数据可以整块进 shell。给查询加 `'use cache'`，并指定缓存周期与标签：

```tsx
// src/app/(app)/dashboard/team-stats.tsx
import { cacheLife, cacheTag } from "next/cache";
import { activityCache } from "@/lib/cache-keys";
import { getTeamStats } from "@/lib/teams";

export async function TeamStats({ teamId }: { teamId: string }) {
  "use cache";
  cacheLife("minutes");
  cacheTag(activityCache.tag(teamId));

  const stats = await getTeamStats(teamId);
  return (
    <dl className="grid grid-cols-3 gap-4">
      <div>
        <dt className="text-sm text-neutral-600">成员</dt>
        <dd className="text-2xl font-semibold">{stats.members}</dd>
      </div>
      <div>
        <dt className="text-sm text-neutral-600">文件</dt>
        <dd className="text-2xl font-semibold">{stats.files}</dd>
      </div>
      <div>
        <dt className="text-sm text-neutral-600">本周活动</dt>
        <dd className="text-2xl font-semibold">{stats.activities}</dd>
      </div>
    </dl>
  );
}
```

`cacheLife("minutes")` 给这段结果一个缓存周期，`cacheTag` 给它一个可失效的标签。成员变动时调 `revalidateTag(activityCache.tag(teamId), "max")`，这一块与依赖它的页面一起失效。

三条限制要记牢。`cacheLife` 与 `cacheTag` 不能写在模块顶层，只能写在 `'use cache'` 函数内部。作用范围是整个函数的返回值，函数里任何一处读请求时数据都会让缓存失效。会话相关的值必须作为参数传进来，否则不同用户会看到同一份缓存。

## 36.8 即时导航与校验

即时导航指点击后立刻能看到新页面的一部分，其余内容流式补齐。判断标准很具体：导航发生的那一帧，屏幕上有属于新页面的内容。

开启 Cache Components 之后，开发环境跑一组校验，把它认为不够即时的页面报出来。校验级别默认 `warning`：

```ts
// next.config.ts
const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
  experimental: {
    instantInsights: { validationLevel: "warning" },
  },
};
```

一个关键区别要记住：直接访问地址时，服务端渲染整棵树；客户端导航时，只有共享布局以下的部分重渲染。所以把 Suspense 放在 root layout，客户端导航时用不上它。

修法是把 Suspense 放进每一页里，用正在加载的那块内容做 fallback。

难点在于位置。放在组件外层的 Suspense 只能盖住它内部的部分，盖不住兄弟节点。页面有三个慢块时，要么给每块各包一个 Suspense，要么把最慢的那块单独下沉，其余同步渲染。

判断位置是否合适，看点击链接后第一帧屏幕上有什么。有标题与导航，说明 shell 生效；只有满屏骨架，说明 Suspense 放得太高；什么都没有，说明外壳本身还在等数据。

页面上有一块实时数据、又不想让它拖慢导航时，用 `io()`：

```tsx
// src/components/live-visitors.tsx
import { io } from "next/cache";

async function getVisitorCount() {
  const res = await fetch("https://api.example.com/live", { cache: "no-store" });
  const data = await res.json();
  return data.count as number;
}

export async function LiveVisitors() {
  await io();
  const count = await getVisitorCount();
  return <p className="text-sm text-neutral-600">当前在线 {count} 人</p>;
}
```

`await io()` 告诉框架“后面是外部 IO”，预渲染时在这里挂起，把后面的工作排除出静态 shell。真实请求里它立刻返回，不产生额外开销。

它有四个限制。必须在 Suspense 边界里调用，否则开发环境给提示。不能写在 `'use cache'`、`use cache: private`、`unstable_cache` 作用域里，这几处要求结果可复用。不能写在 `after()` 或 `generateStaticParams` 里。客户端组件里要写成 `use(io())`。

放在页面顶部调用没有意义，它只会把整页变成动态。它的价值在于把一小块实时数据从外壳里摘出来，位置越靠近数据越有效。

`io()` 和 `connection()` 的差别在缓存作用域：`io()` 在 `'use cache'` 里是空操作，结果仍可复用；`connection()` 在缓存作用域里会抛错。官方现在推荐前者。

把整段工作推迟到导航时刻还有另一个入口，`navigation()`。它与 `io()` 的区别在语义：`io()` 声明后面有外部 IO，`navigation()` 声明后面属于导航阶段的工作。本书项目未实测这两个函数的组合效果，签名与行为以官方文档为准，此处标记未验证。

有些页面确实做不到即时。退出校验用段配置：

```ts
// src/app/(app)/reports/page.tsx
export const instant = false;
```

`instant` 接受 `true`、`false`，也可以写成 `{ level: "warning" }`。只在 Cache Components 下生效。这一项向下继承，树里最高的 `false` 生效，所以放在尽量低的层级。某一页退出校验，不影响它的兄弟页面。

退出校验也退出了另一条要求：每个页面必须产出非空的静态 shell。所以它只适合真的做不到的页面，比如必须读请求头才能决定渲染分支的报表页。

写在校验最上层的 `false` 会连带整棵子树。放在 layout 里等于给整个分组关掉校验，结果通常不符合预期。

校验只在开发环境给提示，构建不因此失败。要把它变成 CI 的硬门槛，用 `@next/playwright` 提供的断言：

```ts
// e2e/instant-nav.spec.ts
import { test } from "@playwright/test";
import { instant } from "@next/playwright";

test("成员页导航即时", async ({ page }) => {
  await page.goto("/dashboard");
  await instant(page, async () => {
    await page.getByRole("link", { name: "成员" }).click();
  });
});
```

`instant()` 断言的是“导航之后立即可用的那部分内容”。在生产构建上跑需要开启 `experimental.exposeTestingApiInProductionBuild`。自动预取在开发环境不生效，所以基线要在生产构建上取。

校验一共两条，名字要记住。`instant-shell-url-data` 表示 URL 数据没有包在 Suspense 里，外壳被绑死在单个地址上；`instant-link-prefetch-partial` 表示预取配置与全局开关不一致。两条都是提示，不会让构建失败。

开发环境的校验跑得比生产勤。每次页面加载与热更新都会跑一遍，改一处配置可能刷出十几条提示。先按严重程度从高到低处理，剩下的确认是误报再用 `instant = false` 退出。

## 36.9 状态保留

导航离开再回来，表单里填了一半的内容、列表的滚动位置、展开的分组，默认都会丢。

开启 Cache Components 后，路由层自动用 React 的 `<Activity>` 处理：页面不卸载，只被隐藏，DOM 和组件状态都保留。保留上限是三条路由，超出后淘汰最旧的一条。

自己写的组件也能用这套机制：

```tsx
// src/components/expandable-panel.tsx
"use client";

import { Activity, useState } from "react";

export function ExpandablePanel({ children }: { children: React.ReactNode }) {
  const [expanded, setExpanded] = useState(false);
  return (
    <div>
      <button type="button" aria-expanded={expanded} onClick={() => setExpanded((v) => !v)}>
        {expanded ? "收起" : "展开"}
      </button>
      <Activity mode={expanded ? "visible" : "hidden"}>{children}</Activity>
    </div>
  );
}
```

状态保留了，但有些状态保留下来是错的。

表单草稿属于该留的：用户切到别的页面查个数据，回来还能接着写。选中项、弹窗开合、错误提示属于不该留的：它们与当前页面的数据强绑定，数据变了还留着会误导。

区分标准是状态的归属。属于用户输入的留下，属于某次数据加载的丢掉。前者是草稿，后者是派生结果。批量操作工具栏在离开页面时应该重置，否则回来时还显示“已选 3 项”，而那 3 项已经不在当前列表里。

```tsx
// src/components/batch-toolbar.tsx
"use client";

import { useLayoutEffect, useState } from "react";

export function BatchToolbar({ onClear }: { onClear: () => void }) {
  const [selected, setSelected] = useState<string[]>([]);

  useLayoutEffect(() => {
    return () => {
      setSelected([]);
      onClear();
    };
  }, [onClear]);

  return <div className="text-sm">已选 {selected.length} 项</div>;
}
```

`useLayoutEffect` 的清理函数在组件被隐藏前执行，用它在离开时重置瞬时状态。

第二个坑是弹窗开合不要用 `useState`。用状态控制时，页面被保留后状态还是 `true`，回来时弹窗不显示，但打开它的副作用也不会再跑一次。把开合绑定到 `searchParams` 上，地址变化驱动状态，逻辑自然正确。

```tsx
// src/components/invite-dialog-trigger.tsx
"use client";

import { useRouter, useSearchParams } from "next/navigation";

export function InviteDialogTrigger() {
  const router = useRouter();
  const params = useSearchParams();
  const open = params.get("dialog") === "invite";

  return (
    <button
      type="button"
      aria-haspopup="dialog"
      aria-expanded={open}
      onClick={() => router.push(open ? "/members" : "/members?dialog=invite")}
    >
      邀请成员
    </button>
  );
}
```

第三个坑是提交成功后要显式清空表单。状态保留了，输入框里还是上一次的草稿，用户以为没提交成功。

`useRouter().bfcacheId` 可以给子树换一个 key，强制重建。它主要给迁移场景用，新代码优先用前面几招。

保留上限是三条路由，这个数字与内存有关。每条保留的路由都留着一份 DOM 与组件状态，保留越多，内存占用越大。三条覆盖了绝大多数「列表到详情再返回」的路径，再往上收益递减。

保留的是组件树，服务端数据不在其中。回到旧页面时，页面里的 `'use cache'` 结果按缓存周期复用，请求时数据重新请求。所以状态保留与数据新鲜是两件独立的事，别指望回到旧页面能看到别处刚改的数据。

## 36.10 水合前的闪烁

首屏渲染到水合完成之间有一段空窗。这段时间里，依赖浏览器状态的内容会显示错。

主题色是最典型的例子。`localStorage` 里存的是深色，服务端不知道，首屏按浅色渲染，水合之后才切过去，中间闪一下白。

修法是在 `<head>` 里放一段同步脚本，在水合之前就把 class 加上：

```tsx
// src/app/layout.tsx
const themeScript = `
(function () {
  try {
    var stored = localStorage.getItem("theme");
    var dark = stored ? stored === "dark" : window.matchMedia("(prefers-color-scheme: dark)").matches;
    document.documentElement.classList.toggle("dark", dark);
  } catch (e) {}
})();
`;

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN" suppressHydrationWarning>
      <head>
        <script dangerouslySetInnerHTML={{ __html: themeScript }} />
      </head>
      <body>{children}</body>
    </html>
  );
}
```

三个细节：`suppressHydrationWarning` 抑制 class 不一致的警告；`try/catch` 兜住隐私模式下 `localStorage` 抛错；脚本必须内联，外链会晚一步。

时间显示是第二类。服务端时区与用户时区不同，直接渲染本地时间会不匹配，水合时报警告。做法是服务端先输出一个占位，客户端挂载后再格式化：

```tsx
// src/components/local-date.tsx
"use client";

import { useEffect, useId, useState } from "react";

export function LocalDate({ iso }: { iso: string }) {
  const id = useId();
  const [text, setText] = useState<string | null>(null);

  useEffect(() => {
    setText(new Intl.DateTimeFormat("zh-CN", { dateStyle: "medium", timeStyle: "short" }).format(new Date(iso)));
  }, [iso]);

  return (
    <time id={id} dateTime={iso} suppressHydrationWarning>
      {text ?? iso.slice(0, 10)}
    </time>
  );
}
```

服务端渲染 `iso.slice(0, 10)`，客户端挂载后换成完整格式。两边第一次渲染的结果一致，所以没有不匹配警告。

`suppressHydrationWarning` 只压制这一层的文本差异，不修复结构差异。元素嵌套不一致、属性值不同这类问题照旧会报错，修法仍然是让两边渲染同一棵树。

首屏闪动的另一处来源是 CSS 变量的初始化。主题变量写在 `:root` 里，脚本加上 `dark` 类之后才生效。脚本必须在样式之前执行，所以放 `<head>` 的最前面。

主题存 `localStorage` 而不用 cookie，是为了保住静态渲染。根布局 `await cookies()` 会让所有页面退出预渲染，为了一处主题放弃整站静态化，代价太大。

水合不一致的来源集中在三类。时间是第一类，服务端与客户端时区不同。随机数与自增 id 是第二类，服务端生成一次，客户端再生成就变了。视口相关是第三类，服务端拿不到窗口宽度，按宽度分支渲染的组件必然不匹配。

三类问题有统一的处理方式：服务端先输出一个与设备无关的占位，客户端挂载后再换成真实值。占位与最终值不能差太多，否则首屏会出现明显跳动。

id 用 `useId()` 生成。它在服务端与客户端产生同一个值，可以直接用在 `aria-describedby` 这类关联属性上，手写随机数则两边对不上。

## 36.11 边界与失败模式

以下几类问题在实际项目里出现频率最高。

拦截路由的插槽与同层路由段重名。`@modal/(.)files` 与已有的 `files` 目录冲突时报错，提示两个平行页面解析到同一个路径。插槽名要避开真实路由段。

刷新拦截地址返回 404。多半是插槽缺 `default.tsx`。刷新时插槽没有匹配项，没有默认导出就会找不到页面。

构建报 `Route "/x" used cookies() without a Suspense boundary`。布局或页面在顶层读了请求时数据。把读取下沉到 Suspense 里，或者给这一页加 `loading.tsx`。

预取请求返回 404。拦截目录的前缀层数写错，或者插槽的 `default.tsx` 没加。两种原因表现一样，先在浏览器地址栏直接打开目标地址，能打开说明是拦截层数的问题。

开发环境出现“页面不够即时”的提示。导航后第一帧没有属于新页面的内容。检查页面里有没有包住慢数据的 Suspense，以及它是否在共享布局之上。

`ensureStatic` 在客户端组件里导出。配置文件里的段导出只能出现在服务端文件里。把它从 `"use client"` 文件里移出去。

`cacheLife` 或 `cacheTag` 报作用域错误。两者只能写在 `'use cache'` 函数内部的第一层，写在模块顶层或嵌套函数里都会报错。

`prefetch() requires Cache Components to be enabled`。配置文件里没开 `cacheComponents`。开了之后记得把 `partialPrefetching` 也显式写上。

`ensureStatic` 冲突。父段要求 `'navigation'`，子段写了 `'shell'`。子段只能收紧，不能放宽。

水合报 `Text content did not match`。服务端与客户端渲染的时间、随机数、`Date.now()` 不一致。用 `suppressHydrationWarning` 加挂载后再渲染。

## 36.12 检查点

1. `pnpm build && pnpm start` 之后打开 `/files`，点一个文件，地址变成 `/files/<id>`，模态浮在列表上，列表滚动位置没变。刷新该地址，得到整页详情；按后退，回到列表。
2. 打开 Network 面板，切到别的页面再回来，能看到 `?_rsc=` 的预取请求在链接进入视口时发出。把链接改成 `prefetch={false}` 后重新构建，这些请求消失。
3. 打开 `/dashboard`，在慢网络下限速，标题与导航立刻出现，慢数据那块先是骨架。检查页面源码，静态部分的 HTML 与骨架都在初始响应里。
4. 开发环境控制台没有 `Instant Insight` 警告；`pnpm build` 输出里各路由的符号与预期一致。
5. 在成员页填一半表单，切到别的页面再回来，输入内容还在；批量工具栏的选中状态已清空。
6. 系统设为深色模式，硬刷新页面，首屏没有白色闪动；`<html>` 的 class 在首次绘制前就是 `dark`。

七条全部通过，说明这一页在慢网络下也能给出可用的第一帧。任何一条没过，先回到对应小节，别靠调大 `staleTimes` 掩盖问题。

这一章的配置项都在 `next.config.ts` 里集中管理，改一次要重新构建。拦截路由、Suspense 摆放、状态重置属于代码层面，改完热更新即可验证。两类改动混在一起调试时，先确认配置已经生效，再看代码行为。

## 36.13 常见错误

1. 报两个平行页面解析到同一路径。 插槽里拦截了已有的同级段。改用不同插槽名，或把被拦截段移到插槽内部。

2. 刷新拦截路由的地址返回 404。 插槽缺 `default.tsx`。补上并返回 `null`。

3. `used cookies() without a Suspense boundary`。 请求时数据在顶层被读取。把读取挪进 Suspense 边界，或把 Promise 往下传。

4. `prefetch() requires Cache Components to be enabled`。 没开 `cacheComponents`，或者开启后没重启构建。改完配置必须重新 `pnpm build`。

5. `A child segment cannot override a parent segment with a less-constrained ensureStatic`。 子段放宽了静态要求。改成与父段相同或更严，或者去掉子段这一行。

6. `Text content did not match. Server: "2024-03-11" Client: "2024-03-11 09:30"`。 服务端与客户端格式化时间方式不同。服务端先输出占位，客户端挂载后再格式化。

## 36.14 这一章在做什么

这一章建立三条判断。拦截路由用同一份内容组件加两个路由入口，解决“点进去再回来”的上下文丢失。预取与 `staleTimes` 决定导航时有没有现成数据。静态 shell 与 Suspense 的摆放决定用户多快看到属于新页面的内容。

三条判断都指向同一个验收动作：把网络限速到 Slow 4G，点一遍主要导航，看每一处空白有多长。

下一章处理导航的视觉层面：页面之间怎么过渡，视频怎么嵌，以及草稿内容怎么只给编辑看。
