# 第 26 章 邮件投递与任务队列

用户点一次“发送邀请”，后端要做两件事：把邀请写进数据库，把邮件交给 Resend 发出去。第一件事在你的控制范围内，第二件事不在。网络会慢，服务商会限流，会 5xx，也会在你进程重启时把正在进行的请求掐断。

如果两件事写在同一个请求里，用户点一次按钮就等于同时押注两个系统成功。邮件发不出去，邀请行却已经写入，用户看到“已发送”，收件人什么也收不到。这是这一类功能最典型的失败形态：数据一致，行为不一致。

这一章把发信移出请求路径：请求只向 `jobs` 表写一行，立刻返回；真正的发送由消费者异步完成，失败按类型重试或进死信，退信后不再发。

涉及五个概念：任务队列、任务租约、指数退避、死信的语义、幂等键。前置条件是第 8 章的 `jobs` 表、第 21 章的 Redis 连接、第 25 章的团队与订阅数据。

## 26.1 任务队列解决什么问题

队列的作用是解耦“接受请求”和“完成工作”。用户点按钮时，系统只承诺“这件事会被处理”，不承诺“现在就处理完”。这个承诺要落在一个持久化的地方，进程重启不丢，才叫承诺。

数据库表可以当队列用。现成的队列服务（BullMQ、SQS、Cloud Tasks）在大规模系统里更合适，但这一章用 `jobs` 表，原因有三个。

任务和业务数据在同一个 Postgres 里。入队语句可以和业务写入放进同一个事务：邀请行插入失败，任务行也不存在；任务行插入失败，邀请行回滚。换成外部队列，这一步只能靠补偿逻辑。

排查不需要额外控制台。一条 `select * from jobs where status = 'dead'` 就能看到所有发不出去的信和原因。

每天几千封的量，数据库完全撑得住。真正的瓶颈在发信 API 的限流，不在数据库。

代价也要认。轮询有延迟，最长等于轮询间隔。高频任务会浪费空查询。表大了要清理。等任务量到每天几十万，应该换专用队列，`enqueue` 的签名和 handler 的分派表不用改，换的是投递方式。

`jobs` 表第 8 章已经建好，这里只解释三个字段的语义，因为它们很容易被误用。

`run_at` 不只是“什么时候开始跑”，它同时是租约的到期时间。消费者领取任务时，把 `status` 改成 `running`，把 `run_at` 改成当前时间加十分钟。消费者崩溃时没人回来改状态，但十分钟后 `run_at` 过期，清理任务会把“`running` 且 `run_at < now()`”的行改回 `queued`，任务被重新领取。一个字段承担两个职责，省掉了 `locked_until` 和 `locked_by` 两列。

`attempts` 在领取时加一，不在失败时加。执行到一半进程崩溃也算一次尝试，否则一个必然让进程崩溃的任务会被无限重领。

`done` 的行只用于统计，保留七天足够。`dead` 的行是待处理的问题，至少保留三十天，并且要有人看。清理脚本为了“让表小一点”把 `dead` 删掉，故障就永远不会被发现。

任务状态只有五个，流转关系如下。

| 状态 | 含义 | 谁写入 |
| --- | --- | --- |
| `queued` | 等待领取，`run_at` 是下次可领取时间 | 入队、重试 |
| `running` | 正在执行，`run_at` 是租约到期时间 | 消费者领取 |
| `done` | 执行成功 | 消费者 |
| `failed` | 已达到最大尝试次数，等待转死信 | 消费者 |
| `dead` | 不再自动重试，需要人工处理 | 消费者、清理任务 |

`failed` 在状态约束里存在，实际流程会直接写 `dead`。保留它是为了兼容早期数据，也为了区分“这次失败但还会重试”和“不再重试”两类事件。写入 `dead` 时把 `last_error` 存下来，长度截到 2000 字符，避免把整段 HTML 错误堆栈塞进表。

## 26.2 入队：一行、够快、可去重

入队函数做三件事：写一行 `jobs`、允许指定执行时间、允许指定去重键。

```ts
// src/lib/jobs.ts
import 'server-only'
import { db } from '@/lib/db'
import type { Executor } from '@/lib/db'

export type JobKind = 'email.send'

export interface EnqueueOptions {
  runAt?: Date
  dedupeKey?: string
}

export async function enqueue(
  executor: Executor,
  kind: JobKind,
  payload: Record<string, unknown>,
  options: EnqueueOptions = {},
) {
  await executor
    .insertInto('jobs')
    .values({
      kind,
      payload: { ...payload, dedupe_key: options.dedupeKey ?? null },
      run_at: options.runAt ?? new Date(),
    })
    .onConflict((oc) => oc.doNothing())
    .execute()
}
```

第一个参数是执行器。传 `db` 是独立提交，传事务对象就跟着事务一起回滚。这个设计的意义全在“同事务”上：先提交邀请、再入队失败，用户看到“邀请已发送”，收件人永远收不到，没有任何任务会被重试。界面一切正常，问题只在收件人的邮箱里。

去重依赖一个部分唯一索引，写在迁移里。

```sql
-- supabase/migrations/20261123090000_email_and_jobs.sql
create unique index jobs_dedupe_uniq
  on public.jobs (kind, (payload->>'dedupe_key'))
  where status in ('queued', 'running') and payload->>'dedupe_key' is not null;
```

索引条件里带了 `status in ('queued','running')`，任务变成 `done` 之后，同一个键可以重新入队。这正是需要的行为：邀请被撤销后重新发给同一个人，应该能再发一封。

去重键放在 `payload` 里而不单独建列，因为它属于业务语义，不同 `kind` 的去重维度不同。代价是表达式索引，写入稍慢，任务量不大的系统可以接受。

`payload` 是 jsonb，写进去就定型。如果模板参数在排队期间需要变化，比如团队改了名字，消费者读到的是旧值。两种处理方式：入队时把渲染所需的字段全部快照进去，或者只放 id 让消费者现查。前者简单，代价是“发出去的信可能反映几秒前的世界”；后者最新，但多一次查询，也多一个“查不到怎么办”的分支。邀请邮件属于前者。

调用方与业务写入放在一个事务里。

```ts
// src/app/(dashboard)/team/invite-actions.ts（片段）
await db.transaction().execute(async (trx) => {
  const invitation = await trx
    .insertInto('invitations')
    .values({ team_id: team.id, email, role, token, expires_at, invited_by: user.id })
    .returningAll()
    .executeTakeFirstOrThrow()

  await enqueue(
    trx,
    'email.send',
    {
      template: 'invitation',
      to: invitation.email,
      data: {
        teamName: team.name,
        inviterName: user.email,
        acceptUrl: `${process.env.NEXT_PUBLIC_APP_URL}/invite/${invitation.token}`,
        expiresAt: invitation.expires_at.toISOString(),
      },
    },
    { dedupeKey: `invitation:${invitation.id}` },
  )

```

写完之后可以直接查库确认。

```bash
psql "$DATABASE_URL" -c "select kind, status, payload->>'dedupe_key' as dedupe, run_at from jobs order by created_at desc limit 3;"
```

```text
   kind    | status  |        dedupe        |          run_at
-----------+---------+----------------------+----------------------------
 email.send | queued | invitation:9f2c...   | 2026-11-23 10:12:31.442+08
```

邮件还没有发，但“该发”这件事已经落库。这就是队列的核心承诺。

表达式索引对 `null` 不生效。忘记传 `dedupeKey` 时，`on conflict` 永远不会触发，同一件事可以入队多次。需要保证去重的地方必须显式传键。

## 26.3 消费者：领取、执行、记录结果

消费者是一个循环。核心在“领取”这一步必须防并发，两个进程同时领到同一个任务，邮件就发两封。

```ts
// src/lib/jobs.ts（追加）
const LEASE_MS = 10 * 60 * 1000
const MAX_ATTEMPTS = 5

async function claimOne() {
  return db.transaction().execute(async (trx) => {
    const row = await trx
      .selectFrom('jobs')
      .selectAll()
      .where('status', '=', 'queued')
      .where('run_at', '<=', new Date())
      .orderBy('run_at')
      .limit(1)
      .forUpdate('jobs')
      .skipLocked()
      .executeTakeFirst()

    if (!row) return null

    return (
      (await trx
        .updateTable('jobs')
        .set({
          status: 'running',
          attempts: row.attempts + 1,
          run_at: new Date(Date.now() + LEASE_MS),
        })
        .where('id', '=', row.id)
        .returningAll()
        .executeTakeFirst()) ?? null
    )
  })
}

export async function runDueJobs(limit = 10) {
  let processed = 0
  for (let i = 0; i < limit; i += 1) {
    const job = await claimOne()
    if (!job) break
    await executeJob(job)
    processed += 1
  }
  return processed
}
```

`for update skip locked` 是这一段的关键。事务 A 锁住第一行时，事务 B 的查询跳过它去拿第二行。两个消费者不互相等待，也不抢同一个任务。

也可以用一条 `update ... where status = 'queued' returning *` 领取。单实例下完全正确，也短。多实例下的区别在锁等待行为：多个 update 抢同一批行，落败的事务要等锁或空转；`skip locked` 明确让 Postgres 跳过被锁的行。任务量大时这个区别会变成吞吐量差别。

执行与失败处理。

```ts
// src/lib/jobs.ts（追加）
interface JobRow {
  id: string
  kind: string
  payload: Record<string, unknown>
  attempts: number
  run_at: Date
}

async function executeJob(job: JobRow) {
  try {
    await handle(job)
    await db
      .updateTable('jobs')
      .set({ status: 'done', last_error: null })
      .where('id', '=', job.id)
      .execute()
  } catch (error) {
    const message = error instanceof Error ? error.message : String(error)
    const dead = error instanceof NonRetryableError || job.attempts >= MAX_ATTEMPTS

    await db
      .updateTable('jobs')
      .set({
        status: dead ? 'dead' : 'queued',
        last_error: message.slice(0, 2000),
        run_at: dead ? job.run_at : nextRunAt(job.attempts),
      })
      .where('id', '=', job.id)
      .execute()
  }
}

// 1、2、4、8 分钟，加 0 到 30% 抖动，上限 1 小时。
function nextRunAt(attempts: number) {
  const base = Math.min(60 * 2 ** (attempts - 1), 3600) * 1000
  return new Date(Date.now() + base + Math.random() * 0.3 * base)
}
```

退避必须有抖动。一批任务同时失败时，比如服务商刚恢复，它们会在同一秒一起重试，把刚恢复的服务再打挂。抖动把重试时间打散。

上限一小时是因为第五次重试已经该进死信，继续往后推没有意义。

`executeJob` 的 catch 里数据库操作也可能失败。这时任务停在 `running`，租约到期后被重新领取，这是租约机制不能省的原因。

多实例还有另一个副作用：瞬时并发变高。发信 API 的限流按账户算，十个实例同时发很容易撞 429。用 Redis 做跨实例的发信闸门。

```ts
// src/lib/jobs.ts（追加）
import { redis } from '@/lib/redis'

// 每分钟最多 60 封，所有实例共享。
async function acquireSendSlot() {
  const key = `rate:email:${Math.floor(Date.now() / 60_000)}`
  const count = await redis.incr(key)
  if (count === 1) await redis.expire(key, 120)
  if (count > 60) throw new Error('email rate limited locally')
}
```

这里抛普通错误并非 `NonRetryableError`。闸门满了意味着这封信应该晚点发，退避会把它推到下一分钟，正好符合限流语义。

按 `kind` 分派用一张注册表，这是这类基础设施的扩展点。后续章节的清理任务、出站 webhook、数据导入，都是加一种 `kind`、加一行 handler，领取与退避的语义全部复用。

```ts
// src/lib/jobs.ts（追加）
const handlers: Record<string, (payload: Record<string, unknown>) => Promise<void>> = {
  'email.send': (payload) => handleEmailSend(payload as EmailPayload),
}

async function handle(job: JobRow) {
  const handler = handlers[job.kind]
  if (!handler) throw new NonRetryableError(`unknown job kind: ${job.kind}`)
  await handler(job.payload)
}
```

未知 `kind` 直接进死信，不重试。重试一百次也不会突然出现一个 handler，只会让代码不一致的问题晚几天暴露。

## 26.4 哪些错误应该重试

重试的前提是“再试一次可能成功”。地址不存在、模板参数缺失，重试一百次结果一样，只会推迟死信到达的时间，还可能触发服务商的滥用检测。

```ts
// src/lib/email/errors.ts
export class NonRetryableError extends Error {
  constructor(message: string) {
    super(message)
    this.name = 'NonRetryableError'
  }
}
```

```ts
// src/lib/email.ts（片段）
import { NonRetryableError } from '@/lib/email/errors'

function classifyResendError(error: { name?: string; statusCode?: number }): Error {
  const name = error.name ?? `http_${error.statusCode}`

  // 限流与服务端错误值得再试。
  if (error.statusCode === 429 || (error.statusCode ?? 0) >= 500) {
    return new Error(`resend: ${name}`)
  }

  // 其余 4xx 是请求本身有问题，重试不会变好。
  return new NonRetryableError(`resend: ${name}`)
}
```

分类依据只有两条：限流与服务端错误可重试，请求内容错误不可重试。

落到具体返回码上：429 重试；5xx 重试；400 `validation_error` 进死信；400 `invalid_idempotency_key` 进死信，说明代码 bug；401、403 进死信并告警。

401 和 403 的处理值得单独说。密钥错时，按可重试处理，运维看到的是每两分钟一次的 401 重试日志；按不可重试处理，看到的是“一堆死信加一条 401”，能定位。密钥错误重试没有意义，它是配置问题。

想看重试行为，把 `EMAIL_TRANSPORT` 指向一个没启动的 SMTP 端口，连发几次，然后查库。

```bash
psql "$DATABASE_URL" -c "select status, attempts, last_error, run_at from jobs order by created_at desc limit 1;"
```

```text
 status  | attempts |            last_error             |          run_at
---------+----------+-----------------------------------+----------------------------
 queued  |        3 | connect ECONNREFUSED 127.0.0.1:1026 | 2026-11-23 10:26:04.118+08
```

`attempts` 会从 1 涨到 5，`run_at` 每次往后推一到两分钟，第五次之后状态变 `dead`。把收件人改成 `not-an-email` 再试，`attempts` 停在 1 直接进死信，因为这类错误不可重试。

## 26.5 死信：可见、可重放

死信并非垃圾桶，是一个待处理队列。至少要有两个能力：能看到、能重放。

```sql
select id, kind, attempts, last_error, created_at
from public.jobs
where status = 'dead'
order by created_at desc
limit 50;
```

重放一个任务，把它改回 `queued` 并清零计数。

```sql
update public.jobs
set status = 'queued', attempts = 0, run_at = now(), last_error = null
where id = '<job id>' and status = 'dead';
```

重放安全的前提是幂等。如果失败的是一次“其实已经发出去但响应超时”的邮件，重放会再发一封。所以每封邮件的幂等键必须是稳定的业务标识，不能用任务 ID。

死信率比死信绝对数有用。

```sql
select
  count(*) filter (where status = 'dead')::float
    / nullif(count(*), 0) as dead_ratio
from public.jobs
where created_at > now() - interval '1 day';
```

刚上线的系统允许这个数字高一点。稳定后超过 1% 就该有人看。业务增长后死信自然变多，只看绝对数看不出问题。

重放之前先看 `last_error` 属于哪一类，处理方式不同。`validation_error` 是地址或参数非法，改数据，不要重放同一份 payload。密钥缺失或 401 是配置错误，修配置后批量重放。`rate limited`、`timeout`、`ECONNRESET` 直接重放，退避会处理。`unknown email template` 或 `unknown job kind` 是代码 bug，修完部署再重放。

批量重放最好写成脚本，不要在 SQL 客户端里粘贴一堆 id。手工操作漏一个就少一封邮件，这种遗漏没人会发现。

死信如果永远没人看，它和“没发”没有区别。上线前至少要有一种等价物：管理后台的任务页，或者每天发到运维群的一条 SQL 结果。

## 26.6 幂等：三层防线

“同一封邮件不发两次”要在三个层面各挡一次。

第一层，入队去重。`dedupe_key` 保证同一个业务事件在排队或执行期间只有一行任务。它挡住的是逻辑被触发两次。

第二层，发信请求的幂等键。Resend 支持 `Idempotency-Key` 请求头，24 小时内同一个键只真正发送一次，重复请求返回第一次的结果。用业务键，不用任务 ID。

```ts
// src/lib/email.ts（片段）
await resend.emails.send(
  { from: FROM, to: input.to, subject: input.subject, html: input.html, text: input.text },
  { idempotencyKey: input.idempotencyKey },
)
```

24 小时窗口有一个边界。一封邮件在 24 小时内被“取消后重新发送”，第二次会被第一次的键挡掉，用户收不到新邀请。解法是把业务键做细：用邀请 token 并非邀请 id，撤销重发就是新 token、新键。这类细节只有在按业务语义设计键时才会想到。

第三层，抑制名单。下一节的退信表决定“这封信根本不该发”。

三层各自处理的场景不同。一个真实的组合故障：用户连点两次，第一次入队，第二次被去重键挡住。消费者执行到一半进程崩溃，租约到期重新领取，第二次调用发信 API 时服务商其实已经发出去了，只是响应没回来。第二层幂等键挡住重复发送。没有第二层，收件人会收到两封一模一样的邀请，点第一个链接进去，第二个显示已被使用。

第三层的场景是地址被永久退信后管理员点重发。去重键不冲突，幂等键超过 24 小时也不冲突，只有抑制名单拦得住。

## 26.7 退信抑制

永久退信之后继续发，会持续损害发件域名的信誉。发件信誉是共享资源，给一个死地址发一百次，同一域名下所有邮件的送达率都会下降。

退信要落成一张表，发送前必须查。

```sql
-- supabase/migrations/20261123090000_email_and_jobs.sql（续）
create table public.email_suppressions (
  email text primary key,
  reason text not null check (reason in ('bounced', 'complained', 'manual')),
  detail text,
  created_at timestamptz not null default now()
);

alter table public.email_suppressions enable row level security;
revoke all on public.email_suppressions from anon, authenticated;
```

主键用邮箱本身。抑制的是地址，并非用户。同一个人有两个账号，或者换个账号邀请同一个邮箱，都不该发。

检查放在 handler 里，不在入队时。入队时邮箱还合法，退信可能发生在排队期间。

```ts
// src/lib/jobs.ts（追加）
async function handleEmailSend(payload: EmailPayload) {
  const email = payload.to.trim().toLowerCase()

  // 地址格式错属于数据问题，重试不会变好。
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) {
    throw new NonRetryableError(`invalid recipient: ${email}`)
  }

  const suppressed = await db
    .selectFrom('email_suppressions')
    .select('email')
    .where('email', '=', email)
    .executeTakeFirst()

  if (suppressed) {
    console.log('skip suppressed email', email)
    return
  }

  await acquireSendSlot()
  const content = renderTemplate(payload.template, payload.data)
  await sendEmail({
    to: email,
    subject: content.subject,
    html: content.html,
    text: content.text,
    idempotencyKey: payload.dedupe_key ?? `job:${email}:${content.subject}`,
  })
}
```

命中抑制名单时返回正常，任务记 `done`。这封信按规则不该发，不算发失败。两者的运维含义不同，混在一起会让死信率失真。

退信事件从 Resend 的 webhook 进来。webhook 用 raw body 验签，字段名与第 25 章 Stripe 的验签逻辑同构。

```ts
// src/app/api/resend/webhook/route.ts
import { Resend } from 'resend'
import { db } from '@/lib/db'

const resend = new Resend(process.env.RESEND_API_KEY)

interface ResendEvent {
  type: string
  data: { to?: string[]; bounce?: { type?: 'Permanent' | 'Transient'; message?: string } }
}

export async function POST(request: Request) {
  const payload = await request.text()

  let event: ResendEvent
  try {
    event = resend.webhooks.verify({
      payload,
      headers: {
        id: request.headers.get('svix-id') ?? '',
        timestamp: request.headers.get('svix-timestamp') ?? '',
        signature: request.headers.get('svix-signature') ?? '',
      },
      webhookSecret: process.env.RESEND_WEBHOOK_SECRET!,
    }) as ResendEvent
  } catch {
    return new Response('invalid signature', { status: 400 })
  }

  const permanent = event.type === 'email.bounced' && event.data.bounce?.type === 'Permanent'
  const complained = event.type === 'email.complained'

  if (permanent || complained) {
    const email = event.data.to?.[0]?.trim().toLowerCase()
    if (email) {
      await db
        .insertInto('email_suppressions')
        .values({
          email,
          reason: permanent ? 'bounced' : 'complained',
          detail: event.data.bounce?.message ?? null,
        })
        .onConflict((oc) => oc.column('email').doNothing())
        .execute()
    }
  }

  return new Response(null, { status: 200 })
}
```

`event.data.bounce.type` 的字段名来自 Resend 的事件文档，本机没有接入线上 webhook，字段名以账户里收到的事件原文为准，webhook 日志能看到原始 JSON。

验签失败返回 400。签名错是配置问题，重试没有用。

运营动作要配套。抑制了不代表用户知道，管理员在成员列表里应该看到“该邮箱已退信”，手动改邮箱或走人工渠道，并非反复点重发。

## 26.8 模板

两三封邮件不需要模板引擎。用 TypeScript 函数返回字符串，还能享受类型检查。

```ts
// src/lib/email/templates.ts
import { NonRetryableError } from '@/lib/email/errors'

export interface EmailContent {
  subject: string
  html: string
  text: string
}

function escapeHtml(value: string) {
  return value
    .replaceAll('&', '&amp;')
    .replaceAll('<', '&lt;')
    .replaceAll('>', '&gt;')
    .replaceAll('"', '&quot;')
}

export function invitationEmail(vars: {
  teamName: string
  inviterName: string
  acceptUrl: string
  expiresAt: string
}): EmailContent {
  const team = escapeHtml(vars.teamName)
  const inviter = escapeHtml(vars.inviterName)
  const url = escapeHtml(vars.acceptUrl)
  const expires = new Date(vars.expiresAt).toLocaleDateString('zh-CN')

  return {
    subject: `加入 ${vars.teamName} 的邀请`,
    html: `
      <div style="font-family:system-ui,sans-serif;max-width:520px;margin:0 auto;padding:24px">
        <h2 style="margin:0 0 16px">加入 ${team}</h2>
        <p>${inviter} 邀请你加入团队 <strong>${team}</strong>。</p>
        <p style="margin:24px 0">
          <a href="${url}" style="background:#111;color:#fff;padding:12px 20px;border-radius:6px;text-decoration:none">接受邀请</a>
        </p>
        <p style="color:#666;font-size:14px">链接在 ${expires} 前有效。</p>
      </div>
    `,
    text: `${vars.inviterName} 邀请你加入团队 ${vars.teamName}。\n\n接受邀请：${vars.acceptUrl}\n\n链接在 ${expires} 前有效。`,
  }
}

export function renderTemplate(name: string, data: Record<string, unknown>): EmailContent {
  switch (name) {
    case 'invitation':
      return invitationEmail(data as Parameters<typeof invitationEmail>[0])
    default:
      throw new NonRetryableError(`unknown email template: ${name}`)
  }
}
```

两条必须遵守的规则。用户输入必须转义，团队名是用户填的，直接拼进 HTML 就是邮件里的 XSS，部分客户端会执行脚本。同时要给纯文本版，它影响送达率评分，文本里不转义但要保证链接完整。

品牌化模板可以用 React Email，它把组件渲染成 HTML，维护性更好。这一章不用，是为了不引入额外构建步骤。

## 26.9 发件域名

邮件能不能进收件箱，取决于域名配置，不取决于代码。三样东西：SPF、DKIM、DMARC。

| 类型 | 名称示例 | 值示例 | 作用 |
| --- | --- | --- | --- |
| TXT（SPF） | `send` 子域 | `v=spf1 include:amazonses.com ~all` | 允许哪些服务器用这个域发信 |
| MX | `send` 子域 | `feedback-smtp.<region>.amazonses.com` 优先级 10 | 接收退信通知 |
| TXT（DKIM） | `resend._domainkey` | `p=MIGfMA0GCSq...` | 给邮件签名，收件方验证内容未被改 |
| TXT（DMARC） | `_dmarc` | `v=DMARC1; p=none; rua=mailto:dmarc@example.com` | 验证失败时如何处理，并接收报告 |

具体值与名称以 Resend Dashboard 为准，逐字复制。上面的 `amazonses.com` 是 Resend 底层使用 SES 时的通用形态，不同区域、不同域名可能不同。手动改一个字符，验证就不过。

DMARC 从 `p=none` 起步。直接上 `p=reject` 会把所有没通过验证的邮件打掉，包括还没配置好的业务通知。跑一两周 `p=none`，看 `rua` 报告里的来源，确认都是自己的，再升到 `quarantine`，最后 `reject`。

CNAME 记录必须关掉 Cloudflare 的橙云代理。Resend 给的验证记录如果是 CNAME，把代理状态设成灰云（DNS only）。橙云会让查询走 Cloudflare 边缘，返回 Cloudflare 的 IP 并非记录的原值，Resend 验证时读不到那条记录，会一直 pending，永远验证不过。官方文档的原话是不要使用代理功能，例如 Cloudflare 的 orange cloud。

验证卡住时先查 DNS 实际返回什么。

```bash
dig TXT resend._domainkey.send.example.com
dig CNAME <resend 给的记录名>
```

返回空说明记录没生效或名字拼错。返回 Cloudflare 的 IP 段说明橙云没关。返回对但 Resend 仍 pending，通常是缓存，等十五分钟再点一次验证。这三步能解决大部分验证问题。

验证通常十五分钟内完成，DNS 生效慢时最长 72 小时。

配置好之后还有两件事影响送达率，和代码无关。用子域发信：记录挂在 `send.example.com` 并非 `example.com`，通知邮件万一被大量投诉，损害的是子域信誉，主域的密码找回、账单通知不受牵连。新域名要预热：全新域名一天发几千封，收件方会按可疑处理，从每天几十封开始，一两周再放开。

发件人显示名用产品名，例如 `TeamStack <no-reply@send.example.com>`，不要只用裸地址。设置 `Reply-To` 指向真实有人看的邮箱。这两项不影响送达率评分，但影响投诉率，而投诉率会影响送达率。

传输开关负责在 Mailpit 与 Resend 之间切换。

```ts
// src/lib/email.ts
import 'server-only'
import nodemailer from 'nodemailer'
import { Resend } from 'resend'
import { classifyResendError, NonRetryableError } from '@/lib/email/errors'

const FROM = process.env.EMAIL_FROM ?? 'TeamStack <no-reply@example.com>'

export async function sendEmail(input: {
  to: string
  subject: string
  html: string
  text: string
  idempotencyKey: string
}) {
  if (process.env.EMAIL_TRANSPORT === 'mailpit') {
    const transport = nodemailer.createTransport({
      host: '127.0.0.1',
      port: 1025,
      secure: false,
    })
    await transport.sendMail({
      from: FROM,
      to: input.to,
      subject: input.subject,
      html: input.html,
      text: input.text,
    })
    return
  }

  if (!process.env.RESEND_API_KEY) {
    throw new NonRetryableError('RESEND_API_KEY is not set')
  }

  const resend = new Resend(process.env.RESEND_API_KEY)
  const { error } = await resend.emails.send(
    { from: FROM, to: input.to, subject: input.subject, html: input.html, text: input.text },
    { idempotencyKey: input.idempotencyKey },
  )

  if (error) throw classifyResendError(error)
}
```

## 26.11 边界与失败模式

轮询间隔是这一章唯一需要调的参数。本地设 1 秒，生产设 5 到 10 秒。太小，空查询占满连接池；太大，用户点完邀请要等很久才收到信。5 秒是“人察觉不到”和“数据库无感”的平衡点。

`payload` 快照会过期。团队名在排队期间改了，邮件里还是旧名字。邀请邮件可以接受，账单通知不行。需要最新数据的模板应该只存 id，在 handler 里现查，并处理“记录已删除”的分支。

抑制检查与发信之间存在竞态。检查通过、发信之前用户恰好被退信，这封信还是会发出去。概率很低，且不影响正确性，不值得为它加锁。

多实例的限流闸门依赖 Redis。Redis 挂掉时 `incr` 抛错，任务按可重试处理，会退避重试。这时发信会停，但没有信被丢。要接受这个取舍，或者在闸门故障时降级为“不限制”，两种都可以，必须选一个并写清楚。

邮件服务商切换会改变错误码。`classifyResendError` 只认 Resend 的形态，换成 SES 或 Postmark 时需要重写这一段。把它隔离在一个函数里，就是为了让替换只影响一个文件。

模板里出现新变量但 handler 没传，渲染结果会是 `undefined`。这类错误不会抛异常，只能在测试里覆盖。每加一封邮件模板，就加一个渲染快照测试。

死信表会增长。`dead` 保留三十天，之后由清理任务删掉。删之前要确认已经有人处理过，否则这条记录就消失了，下次再出同样的错又要从头查。稳妥的做法是先归档到一张历史表，再删。

## 26.12 检查点

1. Mailpit 收到信。发一个邀请，打开 `http://localhost:8025`，能看到主题、收件人、HTML 与纯文本版，点“接受邀请”能打开邀请页。清空 Mailpit 后重发，只收到一封。
2. 不可重试错误不进重试队列。收件人改成 `not-an-email`，`select status, attempts, last_error from jobs order by created_at desc limit 1` 显示 `dead`、`attempts = 1`、`last_error` 为 `invalid recipient`，等两分钟不会变回 `queued`。
3. 退信后不再发。手动往 `email_suppressions` 插一条 `bounced`，再给这个地址发邀请，任务直接 `done`，Mailpit 没有新邮件，日志里有 `skip suppressed email`。

4. 死信可重放。把一条 `dead` 的 `email.send` 改回 `queued` 并清空 `last_error`，下一轮消费后变成 `done`，Mailpit 收到信。
5. 同一封邀请重复入队只有一行：连点两次发送，`select count(*) from jobs where payload->>'dedupe_key' = '<invitation-token>'` 返回 1。
## 26.13 常见错误

`Error: connect ECONNREFUSED 127.0.0.1:1025`

Mailpit 没启动，或端口被占。解法：前台运行 `mailpit`，或 `docker ps` 看容器；确认 `EMAIL_TRANSPORT=mailpit` 时 SMTP 端口是 1025，8025 是 Web UI。

`Error: getaddrinfo ENOTFOUND smtp.resend.com`

本地网络访问不了服务商，或开发环境把传输开关设成了 Resend。解法：开发统一用 Mailpit；生产确认出口网络允许 HTTPS 出站。

`Resend 422: validation_error - Invalid to field`

收件人并非合法邮箱，常见原因是空格、全角符号，或拼接时多了一个逗号。解法：入队前 `trim().toLowerCase()` 并校验格式；已入队的这类错误会进死信，改完地址重新入队。

`Svix: no matching signature found`

webhook 验签失败。用了 `request.json()` 并非 `request.text()`，或 `RESEND_WEBHOOK_SECRET` 与当前 endpoint 不匹配，本地和线上是两个 secret。解法：读原始文本；密钥按环境配置。

`duplicate key value violates unique constraint "jobs_dedupe_uniq"`

入队用了普通 `insert` 并非 `onConflict(...).doNothing()`，或 `dedupe_key` 不在 payload 顶层，而索引表达式是 `payload->>'dedupe_key'`。解法：统一走 `enqueue()`，别手写 insert；检查 payload 里确实是顶层 `dedupe_key`。

`Error: Cannot find module 'nodemailer'`

依赖没装，或装在了别的 workspace 包。解法：项目根目录 `pnpm add nodemailer`，重启 dev server，Node 的模块缓存不会热加载新依赖。

## 26.14 这一章在做什么

这一章把发信从一次 HTTP 请求变成一条可重试的流水线。入队快、可去重、和业务写入同事务。消费者用 `for update skip locked` 领取，租约兜住进程崩溃，`attempts` 在领取时加一。失败按类型分流：可重试的走指数退避加抖动，不可重试的直接进死信。幂等有三层：入队去重、服务商幂等键、抑制名单。域名侧配齐 SPF、DKIM、DMARC，CNAME 不开橙云。

`jobs` 表现在是通用基础设施。下一章让它在没有人点按钮的时候也跑起来：回收卡住的任务、清理孤儿文件、对账订阅漂移，并且多个实例同时跑时只能跑一次。
