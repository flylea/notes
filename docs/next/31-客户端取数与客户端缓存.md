# 第 31 章 客户端取数与客户端缓存

服务端渲染把首屏数据送到浏览器，之后就交给客户端。用户切路由、改数据、回到列表页，这些动作都发生在浏览器里，服务端渲染帮不上忙。

客户端取数库解决这个问题。它在浏览器里缓存请求结果，按 key 复用，在焦点回到页面时重验，在数据变更后让相关缓存失效。

本章讲四件事：什么时候真的需要这类库；SWR 的用法和它的缓存模型；首屏数据怎么从服务端传进客户端缓存；数据变更后，服务端缓存和浏览器缓存怎么一起更新。

顺带对照 TanStack Query，说明两者在缓存身份、失效方式、首屏水合上的差别。这个项目选 SWR，理由在最后一节。

## 31.1 三层缓存

Next.js 应用里有三层缓存，作用范围不同，失效方式也不同。

第一层是服务端缓存，缓存的是数据或整段 React 组件输出。用 `"use cache"` 标记，配合 `cacheTag` 和 `cacheLife` 控制生命周期。

第二层是路由缓存，缓存的是一次导航拿到的 RSC payload。用户点返回时直接复用，不再请求服务端。这一层由 `staleTimes` 配置控制存活时间。

第三层是取数库的浏览器缓存。SWR 按 key 存，TanStack Query 按 queryKey 存，生命周期由库自己的重验规则决定。

三层缓存相互独立，时长可以不同。写代码时容易误判的点在于：让数据变新，要同时处理三层。只刷服务端缓存，用户看到的还是浏览器里的旧值；只改浏览器缓存，刷新页面又回到旧数据。



举例说明差别。用户在设置页改名，Server Action 里调 `updateTag`，服务端缓存立刻失效。此时用户点回活动页，路由缓存如果还有效，浏览器直接复用旧的 RSC payload，页面上仍是旧名字。这就是“服务端已经更新，用户还是看到旧值”的典型原因。要解决，得同时让路由缓存失效，或者用 `router.refresh()`。

前面还有一层 CDN，缓存的是完整响应。它的键包含 URL 和一部分请求头，失效要靠 `Cache-Control` 或主动清理。应用层的 `updateTag` 管不到它。带用户数据的响应要设 `no-store` 或 `private`，别让 CDN 缓存下来。

三层缓存的时长可以不同，收敛时要把它们当成三个独立的问题看。先确认层，再决定手段。这是排查这类问题的基本顺序。

## 31.2 什么时候需要客户端取数库

大多数页面不需要。服务端取一次数据，传给客户端组件渲染，结束。

客户端组件只读一次服务端数据时，把 Promise 传进去用 `use()` 解包：

```tsx
// src/app/(app)/t/[slug]/members/page.tsx
import { getMembers } from "@/lib/teams";

export default async function MembersPage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const membersPromise = getMembers(slug);  // 不 await

  return (
    <Suspense fallback={<p>加载中…</p>}>
      <MemberList membersPromise={membersPromise} />
    </Suspense>
  );
}
```

```tsx
// src/components/member-list.tsx
"use client";

import { use } from "react";
import type { Member } from "@/lib/teams";

export function MemberList({ membersPromise }: { membersPromise: Promise<Member[]> }) {
  const members = use(membersPromise);
  return (
    <ul>
      {members.map((m) => (
        <li key={m.userId}>{m.fullName}</li>
      ))}
    </ul>
  );
}
```

这条路径没有客户端缓存，也没有重验。页面数据只来自那一次服务端渲染。对只读页面足够。

轮询属于第四类，但要和第 28 章的实时能力对比。数据变化频率低于每分钟一次，轮询够用；高于这个频率，用订阅更省。取数库的 `refreshInterval` 适合前者。

需要客户端取数库的场景有四类：

- 同一个数据在多个组件里用，希望只发一次请求，并在失效时一起更新。
- 需要在窗口聚焦、网络恢复时自动重验。
- 需要轮询，或者按条件启用、停用请求。
- 需要乐观更新，点击后先改界面，等请求回来再确认。



手写客户端取数会遇到三个坑。请求竞态：先发的请求后返回，把新数据覆盖成旧的。重复请求：两个组件各自请求一次。卸载后写状态：组件已经没了，回调还在跑。

这三个坑取数库都处理了。竞态用请求 id 或 AbortController，重复请求用 key 去重，卸载用清理标记。自己写一遍要花的时间，比引入一个库多。这四条都指向同一个问题：浏览器里有一份跨组件共享的状态。用 `useState` 加 `useEffect` 自己写，等于重写一遍取数库，还容易漏掉并发和卸载。

## 31.3 服务端读与缓存标记

先让服务端读带上缓存标记。没有标记，后面的失效无从下手。

```ts
// src/lib/cache-keys.ts
export const activityCache = {
  list: (teamId: string) => `/api/activity?team=${teamId}`,
  tag: (teamId: string) => `activity:${teamId}`,
};
```

一个模块同时导出浏览器缓存的 key 和服务端缓存的 tag。两端都从这里引用，字符串不会写歪。

```ts
// src/lib/activity.ts
import "server-only";
import { cacheLife, cacheTag } from "next/cache";
import { createClient } from "@/lib/supabase/server";
import { activityCache } from "@/lib/cache-keys";

export type ActivityItem = {
  id: string;
  action: string;
  actorName: string;
  createdAt: string;
};

export async function getRecentActivity(teamId: string): Promise<ActivityItem[]> {
  "use cache";
  cacheTag(activityCache.tag(teamId));
  cacheLife("minutes");

  const supabase = await createClient();
  const { data, error } = await supabase
    .from("activity_logs")
    .select("id, action, created_at, actor_id, profiles(full_name)")
    .eq("team_id", teamId)
    .order("created_at", { ascending: false })
    .limit(50);

  if (error) throw error;

  return (data ?? []).map((row) => ({
    id: row.id,
    action: row.action,
    actorName: row.profiles?.full_name ?? "系统",
    createdAt: row.created_at,
  }));
}
```

`"use cache"` 放在函数体第一行。它把函数返回值存进服务端缓存，参数参与缓存键。

`cacheTag` 打的标记是后面失效的依据。一个团队一个 tag，改这个团队的数据只失效这个团队的缓存。



`cacheLife` 的参数可以是一个档位名，也可以是对象。档位有 `seconds`、`minutes`、`hours`、`days`、`weeks`、`max`，分别对应一组 `stale`、`revalidate`、`expire` 的默认值。对象写法更精确：

```ts
cacheLife({ stale: 60, revalidate: 300, expire: 3600 });
```

三个字段的含义：`stale` 是客户端可以继续用旧值的时间，`revalidate` 是后台重算的间隔，`expire` 是强制过期的上限。写太短，缓存等于没有；写太长，用户看到旧数据。

`"use cache"` 函数里不能读 cookie 和 headers。读请求相关的数据会让缓存键无法确定，一个用户的数据可能被发给另一个用户。需要按用户区分的缓存，把用户 id 当作参数传进来。`cacheLife("minutes")` 给一个默认的过期策略。不写这一行，缓存不会过期，只能靠手动失效。

## 31.4 浏览器里的订阅

客户端要自己取数据，需要一个同源接口。对外接口用 API Key，内部接口用 cookie 会话，两者不能混。

```ts
// src/app/api/activity/route.ts
import { NextRequest } from "next/server";
import { createClient } from "@/lib/supabase/server";
import { getRecentActivity } from "@/lib/activity";

export async function GET(request: NextRequest) {
  const supabase = await createClient();
  const { data: auth } = await supabase.auth.getClaims();
  if (!auth?.claims) {
    return Response.json({ error: "unauthorized" }, { status: 401 });
  }

  const teamId = request.nextUrl.searchParams.get("team");
  if (!teamId) {
    return Response.json({ error: "invalid_request" }, { status: 400 });
  }

  // 会话有效不等于有权限，显式查一次成员关系
  const { data: member } = await supabase
    .from("team_members")
    .select("user_id")
    .eq("team_id", teamId)
    .eq("user_id", auth.claims.sub)
    .maybeSingle();

  if (!member) {
    return Response.json({ error: "forbidden" }, { status: 403 });
  }

  const items = await getRecentActivity(teamId);
  return Response.json({ items }, { headers: { "Cache-Control": "no-store" } });
}
```

服务端鉴权用 `getClaims()`，不用 `getSession()`。`getSession()` 读的是 cookie 里的内容，客户端可伪造；`getClaims()` 会验证签名。

行级安全已经保证查不到别的团队的数据，这里再查一次成员关系，是为了把“无权限”和“不存在”区分开，返回 403，避免把无权限伪装成空列表。

为什么用接口取数，而不用 Server Action。Server Action 是排队执行的，同一时间只跑一个，用它取数会让请求串行。取数走 GET，浏览器和 CDN 都能参与缓存。

组件里用 SWR 订阅：

```tsx
// src/components/activity-feed.tsx
"use client";

import useSWR from "swr";
import { activityCache } from "@/lib/cache-keys";
import type { ActivityItem } from "@/lib/activity";

async function fetcher(url: string) {
  const response = await fetch(url, { signal: AbortSignal.timeout(8000) });
  if (!response.ok) throw new Error(`请求失败：${response.status}`);
  return (await response.json()) as { items: ActivityItem[] };
}

export function ActivityFeed({
  teamId,
  initial,
}: {
  teamId: string;
  initial: ActivityItem[];
}) {
  const { data, error, isLoading } = useSWR(activityCache.list(teamId), fetcher, {
    fallbackData: initial,
    revalidateIfStale: false,
    keepPreviousData: true,
    onErrorRetry: (err, key, config, revalidate, opts) => {
      if (opts.retryCount >= 3) return;
      setTimeout(() => revalidate({ retryCount: opts.retryCount + 1 }), 2000);
    },
  });

  if (error) return <p>读取活动失败，请稍后重试。</p>;
  if (isLoading) return <p>加载中…</p>;

  return (
    <ul>
      {(data?.items ?? []).map((item) => (
        <li key={item.id}>
          {item.actorName} {item.action}
        </li>
      ))}
    </ul>
  );
}
```

几个行为值得说清。



`AbortSignal.timeout(8000)` 给请求设上限。浏览器原生的超时不会自动重试，超过八秒的连接留着没有意义，早断早重试。同一个 key 的并发请求会被去重。两个组件同时挂载，只发一次请求。

重试策略要控制次数。默认的指数退避在接口持续 500 时会让请求越积越多，配合 `onErrorRetry` 限制三次，之后显示错误提示。

`isLoading` 表示正在请求且还没有数据。`isValidating` 表示任何请求进行中，包括后台重验。刷新的转圈用后者，首屏骨架用前者。

`revalidateIfStale: false` 关掉挂载时的重验。首屏数据来自服务端，紧接着再请求一次是浪费。代价是别的标签页改了数据，这一页不会自动变。



其余常用的配置项：`dedupingInterval` 控制同一 key 的去重窗口，默认 2 秒；`focusThrottleInterval` 控制聚焦重验的节流，默认 5 秒；`refreshInterval` 开启轮询，单位毫秒；`shouldRetryOnError` 控制是否自动重试。

默认值大多够用。改之前先想清楚要解决什么问题，乱调会让排查变难。例如把 `dedupingInterval` 改成 0，两个组件同时挂载就会发两次请求。`keepPreviousData: true` 让 key 变化时保留旧数据。切团队时列表不会先变空再填满。

## 31.5 首屏数据从服务端喂进来

首屏由服务端渲染，数据已经拿到了。客户端库应该直接用它，不再请求一次。

SWR 的做法是给整棵树配 `fallback`：

```tsx
// src/components/swr-provider.tsx
"use client";

import { SWRConfig } from "swr";

export function SWRProvider({
  fallback,
  children,
}: {
  fallback: Record<string, unknown>;
  children: React.ReactNode;
}) {
  return <SWRConfig value={{ fallback }}>{children}</SWRConfig>;
}
```

```tsx
// src/app/(app)/t/[slug]/activity/page.tsx
import { getRecentActivity } from "@/lib/activity";
import { activityCache } from "@/lib/cache-keys";
import { SWRProvider } from "@/components/swr-provider";
import { ActivityFeed } from "@/components/activity-feed";

export default async function ActivityPage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const teamId = await getTeamIdBySlug(slug);
  const items = await getRecentActivity(teamId);

  return (
    <SWRProvider fallback={{ [activityCache.list(teamId)]: { items } }}>
      <ActivityFeed teamId={teamId} initial={items} />
    </SWRProvider>
  );
}
```

`fallback` 的 key 必须与 `useSWR` 的 key 完全一致，一个字符都不能差。不一致时 SWR 忽略这条 fallback，水合后自己去请求，首屏就多一次网络往返。



Provider 的位置也影响行为。放在根布局，所有页面共享同一个缓存；放在某个页面，离开页面缓存就没了。这个项目放在页面级，因为不同团队的数据不该互相污染。

`fallback` 的值必须是可序列化的普通对象。放了 `Date` 会在水合时报警告，客户端收到的是字符串还是对象取决于序列化，结果不稳定。日期统一转成 ISO 字符串。这就是把 key 放进 `cache-keys.ts` 的原因。两边都调 `activityCache.list(teamId)`，拼错的概率降到零。

流式渲染时，`fallback` 会随着 RSC 流分块下发。用户先看到骨架，数据到了再替换。SWR 拿到 `fallback` 后不会立刻重验，`revalidateIfStale: false` 保证这一点。

`fallback` 与 `fallbackData` 的区别：前者按 key 挂在整个 Provider 上，适合一个页面多处使用；后者挂在单个 `useSWR` 调用上，只影响那个 hook。两者同时存在时，`fallbackData` 优先。

TanStack Query 的等价做法是 `initialData` 或 `HydrationBoundary`：

```tsx
// 等价写法（项目未采用，仅对照）
const { data } = useQuery({
  ...activityCache.options(teamId),
  initialData: { items },
  initialDataUpdatedAt: Date.now(),  // 不写这一行，挂载时立刻重取
});
```

`initialDataUpdatedAt` 对应 SWR 的 `revalidateIfStale`。TanStack 不写这个时间戳就认为初始数据已经过期，水合后立刻重验。这是从 SWR 迁过来时最容易漏的一行。

## 31.6 变更之后两套缓存一起动

数据变更发生在 Server Action 里。服务端缓存要失效，浏览器缓存也要失效。

```ts
// src/app/(app)/t/[slug]/settings/actions.ts
"use server";

import { revalidatePath, updateTag } from "next/cache";
import { createClient } from "@/lib/supabase/server";
import { requireUser } from "@/lib/auth";
import { activityCache } from "@/lib/cache-keys";

export async function renameTeam(teamId: string, name: string) {
  const user = await requireUser();
  const supabase = await createClient();

  const { error } = await supabase.from("teams").update({ name }).eq("id", teamId);
  if (error) throw error;

  // 服务端数据缓存失效，下一次读会重新查库
  updateTag(activityCache.tag(teamId));

  // 路由缓存失效，当前页面重新渲染
  revalidatePath("/t/[slug]/activity", "page");

  return { ok: true };
}
```

三种失效手段的语义不同：

- `updateTag(tag)`：立刻让标记为这个 tag 的数据过期，下一次读等新数据。适用于自己改完要马上看到结果的场景。
- `revalidateTag(tag, "max")`：标记为过期，先返回旧数据再在后台更新。适用于别人改的、晚一点看到没关系。
- `revalidateTag(tag, { expire: 0 })`：立刻过期，下一次请求必须等新数据。适用于外部系统回调要求立刻生效。



`updateTag` 只能在 Server Action 和 Route Handler 里调用。在渲染期间调用会报错，因为它修改的是缓存的全局状态，渲染过程要保持可重复。

失效之后不代表下一次渲染一定会重新算。如果页面走的是路由缓存，用户拿到的仍是旧的 payload。这就是为什么 Server Action 里还要配 `revalidatePath`。`revalidateTag` 的第二个参数必填，不传会报类型错误。这一点在 Next.js 16 是硬性要求。

客户端那一半：

```tsx
// src/app/(app)/t/[slug]/settings/rename-form.tsx
"use client";

import { useSWRConfig } from "swr";
import { useRouter } from "next/navigation";
import { activityCache } from "@/lib/cache-keys";
import { renameTeam } from "./actions";

export function RenameForm({ teamId, initialName }: { teamId: string; initialName: string }) {
  const { mutate } = useSWRConfig();
  const router = useRouter();

  async function onSubmit(formData: FormData) {
    await renameTeam(teamId, String(formData.get("name") ?? ""));
    // 浏览器缓存失效，触发一次重新请求
    await mutate(activityCache.list(teamId));
    // 让 RSC 数据也更新，页面上其他服务端渲染的部分跟着变
    router.refresh();
  }

  return (
    <form action={onSubmit}>
      <input name="name" defaultValue={initialName} />
      <button type="submit">保存</button>
    </form>
  );
}
```

三件事都要做，缺一件就有一处显示旧值。



不 `await` 也能用，但拿不到新数据，也无法在失败时处理错误。要提示用户，就 `await`。`mutate(key)` 让浏览器缓存失效并重新请求。它是异步的，`await` 之后数据已经回来了。

`router.refresh()` 重新请求当前路由的 RSC payload，服务端渲染的部分跟着更新。它不碰 SWR 的缓存。

顺序也有讲究。先 `mutate` 再 `router.refresh()`，浏览器拿到的数据与 RSC 重渲染的结果一致；反过来，`router.refresh()` 先跑，页面上的服务端部分会先更新，客户端部分还是旧的，出现短暂错位。

如果 `mutate` 抛错（网络断了），后面的 `router.refresh()` 不该执行。用 try/catch 包起来，失败时提示用户重试。

`revalidatePath` 在 Server Action 里已经把服务端缓存标记为失效，`router.refresh()` 时拿到的就是新数据。

Server Action 里不能用 `revalidatePath` 的场景要记住：路由保护脚本里不行，`proxy.ts` 里也不行，它只能出现在服务端渲染路径和 Server Action 里。

tag 的粒度决定了失效范围。按团队打 tag，改一个团队不会影响其他团队；按用户打 tag，会影响这个用户的所有团队。粒度太细要记很多 tag，太粗会让无关缓存一起失效。这个项目按团队。如果漏了它，刷新拿到的还是旧值。

## 31.7 乐观更新

点击“全部标记已读”，用户希望立刻看到结果。等请求回来再改，会有明显的延迟。

```tsx
// src/components/mark-all-read.tsx
"use client";

import useSWR, { useSWRConfig } from "swr";
import { activityCache } from "@/lib/cache-keys";

export function MarkAllRead({ teamId }: { teamId: string }) {
  const { data } = useSWR(activityCache.list(teamId));
  const { mutate } = useSWRConfig();

  async function onClick() {
    await mutate(
      activityCache.list(teamId),
      async () => {
        await fetch("/api/activity/read-all", { method: "POST" });
        return { items: [] };
      },
      {
        optimisticData: { items: [] },
        rollbackOnError: true,
        revalidate: false,
        throwOnError: false,
      },
    );
  }

  return (
    <button onClick={onClick} disabled={!data?.items?.length}>
      全部标为已读
    </button>
  );
}
```

`optimisticData` 是立刻写进缓存的值。`rollbackOnError` 在请求失败时把旧值恢复。`revalidate: false` 表示请求成功后不再重取一次，直接用返回值。

缓存在写入前会保存快照，失败时用它回滚。这个快照是 SWR 内部做的，不需要自己管理。

并发点击要防。按钮在请求完成前禁用，或者给每次点击生成一个临时 id，避免两次乐观更新互相覆盖回滚快照。

乐观更新只用于能承受短暂错误的操作。删除、支付这类动作不要乐观，等确认再改界面。

## 31.8 router.refresh 与缓存的分工

`router.refresh()` 做的事很窄：重新请求当前路由的 RSC payload，替换页面上的服务端渲染部分。

它不刷新浏览器里已经拿到的数据，也不清 SWR 的缓存。反过来，SWR 的 `mutate` 也不会触发 RSC 重新渲染。

两者的分工可以概括成：服务端渲染的内容归 `router.refresh()`，客户端取数库的内容归 `mutate()`。页面同时有两类内容时，两个都要调。

路由缓存的时长由 `staleTimes` 控制，配置在 `next.config.ts` 的 `experimental.staleTimes` 下。默认的 `dynamic` 是 0 秒，`static` 是 5 分钟。团队切换、权限变化之后，旧的路由缓存可能带着上一份数据，这时候用 `router.refresh()` 主动作废。

`router.refresh()` 有成本。它重新执行页面的服务端组件，包括所有数据查询。高频操作（输入联想、拖拽排序）不要用它，用 SWR 的局部更新。

`router.refresh()` 之后组件状态保留，表单里没提交的输入不会丢。`router.push()` 到同一路径则可能重挂组件，输入会清空。需要保留输入时用前者。

`redirect()` 与它不同。`redirect()` 发起导航，改变 URL；`router.refresh()` 留在当前页面，只更新数据。

## 31.9 SWR 与 TanStack Query 的取舍

两个库解决同一类问题，差别在 API 风格和默认行为。

SWR 更小，API 更简洁。`useSWR(key, fetcher)` 两个参数就能用，缓存身份由 key 决定，天然与 URL 一致。首屏数据用 `fallback` 注入，配置集中。

TanStack Query 功能更全。`queryKey` 是数组，支持按前缀批量失效；`staleTime`、`gcTime`、`retry` 分开配置；`useMutation` 提供完整的生命周期回调；devtools 能看到每个查询的状态。

两条具体差异会影响选型。

缓存身份的写法。SWR 用字符串 key，键的拼接要自己保证一致；TanStack 用数组，`['activity', teamId]` 这种结构不容易拼错，还能用 `['activity']` 前缀失效一批。

水合的方式。SWR 的 `fallback` 是同步的，服务端拿到数据直接塞进去；TanStack 的 `HydrationBoundary` 需要 `dehydrate`，配合 `shouldDehydrateQuery` 可以处理还没完成的查询，流式渲染更细。

这个项目选 SWR。原因有三个：客户端取数的位置只有三处（活动列表、通知角标、全局搜索），用不上批量失效；团队对包体积敏感；`fallback` 的写法与现有的服务端取数代码贴合，改动最小。

官方文档也给过建议：大多数交互不需要客户端取数库，只在需要共享浏览器缓存时才引入。这个项目的三处取数都有共享需求，所以引入了 SWR。

不选的代价也要说清：SWR 没有 devtools，排查缓存问题靠 `console.log` 和 Network 面板；条件请求用 `null` key，语义不如 `enabled` 直白；批量失效要自己维护 key 前缀约定。



选型还要考虑团队熟悉度。两个库的文档都很全，SWR 的示例更少但更集中。新成员上手，SWR 半小时能读懂，TanStack 要半天。这是工程决策里真实存在的一项，写进文档比争论哪个更强有用。换成 TanStack 也不难，两者的失效逻辑与 Server Action 的衔接方式一致，主要是改 hook 与 Provider。

## 31.10 什么时候才需要状态管理

客户端取数库管的是服务端数据在浏览器里的副本。状态管理库管的是纯客户端状态：主题、侧边栏开合、多步骤表单的临时草稿、选中的行。

一个常见的错误是给全局 store 写一个 `refresh()` 方法，让所有页面调它重新取数。这正是取数库的职责，交给库做，别自己造一套通知机制。

引入状态管理库的另一个信号是：同一份界面状态被超过五个组件读写，且这些组件分布在不同路由。三个以内的组件之间传 props 就够。

两者不要混。把服务端数据抄进 Zustand，等于维护两份副本，还要自己写同步逻辑。取数库提供的重验、去重、回滚全用不上。

URL 也是一种状态。分页的页码、筛选条件、搜索词放 URL，刷新和分享都能还原，也不需要状态管理库。判断标准同样简单：这个状态要不要被分享或被浏览器记住。

判断方法：这个状态刷新页面之后该不该保留？该保留，它在数据库里，用取数库。不该保留，它是界面状态，用 `useState` 或状态管理。

有一类状态常被误放进状态管理库：表单草稿。多步骤表单的中间值确实要跨路由保留，但它更适合放在 URL 参数里，或者提交后存进草稿表。放进内存的全局 store，刷新就丢，用户会抱怨。

多数项目不需要状态管理库。主题用 CSS 变量，侧边栏用 `useState`，表单草稿存在 URL 或表单本身。真的需要时（跨路由共享的复杂状态、撤销重做），再引入。

## 31.11 检查点

1. 打开 `/t/teamstack/activity`，Network 面板里第一次加载没有 `/api/activity` 请求，说明 `fallback` 生效。
2. 在另一个窗口改名，回到活动页，列表出现新记录，不按 F5。
3. 把 `cache-keys.ts` 里 `list` 的返回值改一个字符，重新加载，Network 里出现一次 `/api/activity` 请求，说明 key 与 `fallback` 不一致时 SWR 会自己取。
4. 注释掉 Server Action 里的 `updateTag`，改名后按 F5，活动列表仍是旧数据，恢复后正常。
5. 点“全部标为已读”，界面立刻清空；断网再点，界面回滚到原状态。
6. 两个标签页打开同一页面，一个改名，另一个聚焦时数据更新。

## 31.12 常见错误

1. `Warning: Prop 'fallback' did not match` 或首屏多一次请求

`fallback` 的 key 与 `useSWR` 的 key 不一致。两处都从 `cache-keys.ts` 取值，不要手写字符串。

2. `Error: Only plain objects can be passed to Client Components`

服务端把 `Date`、`Map`、类实例传给了客户端组件。在服务端序列化成字符串或普通对象再传。

3. `useSWRConfig must be used within a SWRConfig`

在 Server Component 里调了客户端 hook，或者 Provider 放在了错误的层级。

判据很简单：文件第一行有 `"use client"` 才能调 hook。把 Provider 提到根布局，所有页面都能用。`useSWRConfig` 只能出现在客户端组件里，并且要在 Provider 之内。

4. 改完数据，列表还是旧的

只调了 `router.refresh()`，没失效 SWR 缓存。两者管不同的数据，客户端取数的那部分要 `mutate`。

5. `Route "/activity" used "use cache" without cacheLife`

`"use cache"` 函数里没配 `cacheLife`，缓存永不过期。加 `cacheLife("minutes")` 或对应的策略。

**6. 两个标签页数据不同步**

SWR 的缓存按页面独立，另一个标签页要靠自己的重验。开启 `revalidateOnFocus`（默认开启），或者在 `visibilitychange` 时手动 `mutate`。

## 31.13 这一章在做什么

这一章把浏览器里的数据流接上。

三层缓存要分清：服务端缓存、路由缓存、取数库缓存。失效时要一起处理，只动一层会留下旧数据。

三条规则可以复用：

- 首屏数据从服务端注入，别让客户端再请求一次；注入的 key 必须与订阅的 key 完全一致。
- 变更之后，`updateTag` 管服务端，`mutate` 管浏览器，`router.refresh` 管 RSC。三者的作用范围不同，不能互相替代。
- 状态管理库管界面状态，服务端数据的副本交给取数库。

还有一个细节：`updateTag` 与 `router.refresh()` 配合时，刷新拿到的是新数据；只用 `revalidatePath` 时，路由缓存失效但页面不重渲染，用户要等下一次导航。两者的区别在实测里很明显，检查点第 4 条就是测这个。

下一个问题是数据从哪来。第 32 章处理导入导出：外部文件进来，数据出去，两条路径都要校验和转义。
