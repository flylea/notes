# 第 4 章 服务器组件与客户端组件

这一章讲组件在哪里跑。同一个 `.tsx` 文件，有的只在服务端执行，有的会被打包发到浏览器，区别由一行指令决定。

需要分清这件事，是因为三类问题都出在这条边界上：页面里用了 `useState` 却构建失败、首屏 JS 包莫名变大、数据库查询和密钥被带进浏览器。

涉及的概念有五个：服务端组件、客户端组件、`"use client"` 指令、序列化边界、客户端模块图。前三个决定代码跑在哪，后两个决定什么数据能过去、打进去多少代码。

## 4.1 两个渲染环境

`app/` 下的 `page.tsx`、`layout.tsx` 默认是服务端组件。它们在服务器上执行，返回的 React 元素会变成 RSC Payload，代码本身不进入浏览器包。

加了 `"use client"` 的文件是客户端组件。它们在服务端渲染一次生成 HTML，在浏览器里再执行一次完成水合。代码会进入浏览器包。

| 能力 | 服务端组件 | 客户端组件 |
| --- | --- | --- |
| 读数据库、文件系统 | 可以 | 不可以 |
| 使用密钥 | 可以 | 不可以 |
| `useState`、`useEffect` | 不可以 | 可以 |
| 事件处理器 | 不可以 | 可以 |
| `window`、`localStorage` | 不可以 | 可以 |
| 进入浏览器 JS 包 | 不进入 | 进入 |

这张表只有一条容易记：跟浏览器有关的东西放客户端，跟数据有关的东西放服务端。

服务端组件里写 `useState` 会直接构建失败，报错指向 import 那一行，指向的位置容易让人误判：

```text
./src/app/(app)/teams/page.tsx:1:10
Error: You're importing a module that depends on `useState` into a React Server Component module.
This API is only available in Client Components.
To fix, mark the file (or its parent) with the `"use client"` directive.
```

原因是 `useState` 由 React 的客户端实现提供。服务端组件的环境里没有这个导出，导入时就失败了，所以报错在 `import` 那一行。

两个环境来自两段历史。早期 React 在浏览器里渲染，页面要等 JS 下载完才有内容，首屏白屏时间长。SSR 解决了首屏可见，但服务端只负责拼字符串，组件代码照样整包发到浏览器，水合时再执行一遍。

服务端组件把“只在服务端跑”的代码真正留在服务端。数据库查询、格式化、权限判断都不再进入浏览器包，代价是这些代码不能有交互。

同一个组件在两端各执行一次，是客户端组件的常态。在客户端组件里写 `console.log`，服务端终端和浏览器控制台各打印一次。两行日志来自两个环境，别急着怀疑被渲染了两遍。

## 4.2 “use client” 划的是模块图边界

`"use client"` 写在文件第一行，标记的是整个模块图的入口，而不只是这一个文件。

一个文件被标记后，它 import 的所有东西都会进入客户端包。它直接渲染的子组件也在里面。

```tsx
// src/app/(app)/teams/team-card.tsx
"use client";

import { format } from "date-fns";
import { Avatar } from "@/components/avatar";

export function TeamCard({ team }: { team: Team }) {
  return (
    <div>
      <Avatar url={team.avatarUrl} />
      <span>{team.name}</span>
      <span>{format(new Date(team.createdAt), "yyyy-MM-dd")}</span>
    </div>
  );
}
```

`date-fns` 整套被带进浏览器包，只是为了格式化一个日期。这是一行指令最容易被忽略的代价。

替代方案是把格式化放到服务端，客户端组件只接收字符串：

```tsx
// src/app/(app)/teams/page.tsx
import { format } from "date-fns";
import { TeamCard } from "./team-card";

export default async function TeamsPage() {
  const teams = await listTeams();

  return (
    <div>
      {teams.map((team) => (
        <TeamCard
          key={team.id}
          team={{ id: team.id, name: team.name, avatarUrl: team.avatarUrl }}
          createdAtText={format(new Date(team.createdAt), "yyyy-MM-dd")}
        />
      ))}
    </div>
  );
}
```

```tsx
// src/app/(app)/teams/team-card.tsx
export function TeamCard({ team, createdAtText }: {
  team: { id: string; name: string; avatarUrl: string };
  createdAtText: string;
}) {
  return (
    <div>
      <Avatar url={team.avatarUrl} />
      <span>{team.name}</span>
      <span>{createdAtText}</span>
    </div>
  );
}
```

客户端包少了 `date-fns`。这一改动的收益可以量化：日期库通常一两百 KB，压缩后仍有几十 KB，对一个列表页来说相当于多下载半秒的脚本。

判断有没有生效，可以在构建之后搜产物：

```bash
grep -rl "date-fns" .next/static/chunks
```

没有输出说明没打进去。

这条边界会传染。客户端组件里渲染的子组件，即使没有标记，也会被当作客户端组件。因此指令要加在真正需要交互的最外层，越深越好。

```text
页面（服务端）
└── 表格（服务端）
    ├── 行（服务端）
    └── 下拉菜单（客户端）← 只有这里需要 use client
```

反过来，如果整页都加上 `"use client"`，页面里的 `cookies()`、数据库查询全部失效，因为这些 API 在浏览器里不存在。

边界加在哪一层，有三种常见粒度。

页面级：整个 `page.tsx` 标成客户端。写法最省事，代价是这一页所有数据都要通过接口或 props 拿，服务端直读数据库的能力没了。

功能级：页面保持服务端，把一块交互区域（筛选栏、编辑器、弹窗）单独拆文件标记。这是默认选择，本书大部分页面用这档。

叶子级：只有输入框、开关这类最小交互单元标记，外层的列表、卡片仍是服务端组件。包体积最省，代价是 props 要一层层往下传。

粒度越细，包越小，传参越啰嗦。功能级是折中点，先按这一档拆，发现某个库太大再往叶子级压。

## 4.3 什么能过边界

服务端向客户端组件传数据，数据要能序列化。React 会把 props 写进 RSC Payload，浏览器再读出来。

可以传：字符串、数字、布尔、`null`、`undefined`、数组、纯对象、`Date`、`Map`、`Set`、Promise、React 元素。

不能传：函数、class 实例、`Symbol`、正则对象。

函数过不去，原因在于两端执行环境不同。服务端函数里可能读数据库、读环境变量，把它序列化到浏览器等于把服务端代码发过去。框架的选择是直接拒绝，让问题在构建期暴露。

class 实例过不去，原因是反序列化后拿不到原型方法。数据传过去只剩字段，`instance.getTotal()` 这类方法在浏览器里不存在，调用就报 `is not a function`。

把事件处理器传给客户端组件，构建期就会报错：

```text
Error: Event handlers cannot be passed to Client Component props.
{onPick: function onPick}
If you need interactivity, consider converting part of this to a Client Component.
```

这条报错里还有一个 `digest`，它是服务端生成的错误编号，用来在日志里找到对应记录。

传 class 实例的报错更直接：

```text
Error: Only plain objects, and a few built-ins, can be passed to Client Components from Server Components.
Classes or null prototypes are not supported.
```

修法是把实例转成普通对象再传。

```ts
// 错误示范
return <Chart series={new TimeSeries(points)} />;

// 正确写法
return <Chart series={{ points }} />;
```

Promise 可以传。服务端不 await，把 Promise 直接交给客户端组件，客户端用 `use` 读：

```tsx
// src/app/(app)/teams/[slug]/page.tsx
import { Suspense } from "react";
import { getTeamActivity } from "@/lib/teams";
import { ActivitySection } from "./activity-section";

export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const activity = getTeamActivity(slug);

  return (
    <div>
      <h1>团队详情</h1>
      <Suspense fallback={<p>加载活动……</p>}>
        <ActivitySection activity={activity} />
      </Suspense>
    </div>
  );
}
```

```tsx
// src/app/(app)/teams/[slug]/activity-section.tsx
"use client";

import { use } from "react";

export function ActivitySection({ activity }: { activity: Promise<Activity[]> }) {
  const items = use(activity);
  return <ul>{items.map((item) => <li key={item.id}>{item.action}</li>)}</ul>;
}
```

服务端不用等查询完成就能把页面发出去，客户端拿到 Promise 后继续渲染。

序列化有一个容易忽略的成本：props 全部写进 Payload，会增大传输体积。把一个包含二十个字段的数据库记录直接传下去，Payload 就多出二十个字段的文本，其中多半只有两个字段在界面上用。

```tsx
// 错误示范：整条记录进 payload
<div>{team.name}</div>
<TeamMenu team={team} />;

// 正确写法：只传界面需要的字段
<TeamMenu teamId={team.id} name={team.name} />;
```

序列化还有两个细节。`undefined` 在对象属性上会被丢掉，取值时变成 `undefined`，看起来没差别；`Date` 实例会保留类型，浏览器里拿到的仍是 `Date`，但时区以服务端为准，直接 `toLocaleString()` 会和浏览器本地时间不一致。

## 4.4 服务端组件放在客户端组件里面

客户端组件里不能再 `import` 服务端组件。`import` 属于模块图，客户端组件的 import 会进客户端包，服务端组件一旦进去就失去意义。

这条限制的原因在模块图。`import` 是静态依赖，打包器沿依赖向下把所有文件收进包里。客户端组件 import 服务端组件，等于把服务端代码拉进浏览器图，里面的数据库客户端、密钥读取都会跟着过去。

`children` 走的是另一条路。它在运行期作为已经渲染好的元素传进来，模块之间没有 import 关系，打包器看不到这条依赖。

但服务端组件可以作为 `children` 传进去：

```tsx
// src/app/(app)/teams/[slug]/invite-dialog.tsx
"use client";

import { useState } from "react";

export function InviteDialog({ children }: { children: React.ReactNode }) {
  const [open, setOpen] = useState(false);

  return (
    <>
      <button onClick={() => setOpen(!open)}>邀请成员</button>
      {open && (
        <dialog open>
          {children}
          <button onClick={() => setOpen(false)}>关闭</button>
        </dialog>
      )}
    </>
  );
}
```

```tsx
// src/app/(app)/teams/[slug]/page.tsx
import { listInvitableUsers } from "@/lib/teams";
import { InviteDialog } from "./invite-dialog";
import { InviteForm } from "./invite-form";

export default async function TeamPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const users = await listInvitableUsers(slug);

  return (
    <InviteDialog>
      <InviteForm users={users} />
    </InviteDialog>
  );
}
```

`InviteForm` 里可以直接读数据库、可以用密钥，因为它在服务端渲染完成，传进 `InviteDialog` 的是渲染结果。

交错的写法有两种。一种是 `children`，适合“外壳是交互的、内容是服务端渲染的”结构，弹窗、抽屉、折叠面板都属于这一类。

另一种是命名 slot，适合一个客户端组件要接收多块服务端内容：

```tsx
// src/app/(app)/teams/[slug]/team-shell.tsx
"use client";

export function TeamShell({ header, body }: { header: React.ReactNode; body: React.ReactNode }) {
  return (
    <div className="grid">
      <header>{header}</header>
      <section>{body}</section>
    </div>
  );
}
```

页面上这样用：`<TeamShell header={<TeamHeader />} body={<TeamBody />} />`。两块内容都在服务端渲染，`TeamShell` 只负责布局和交互。

这两种写法的共同点是：服务端组件始终由页面（服务端）创建，客户端组件只接收结果。只要遵守这条，客户端组件的代码再复杂也不会把服务端代码带进浏览器。

理解这一点要看两个词：owner 和 parent。

owner 是在源码里写 JSX 的那个组件。parent 是渲染树里直接包含子组件的那个组件。

`InviteForm` 的 owner 是页面（服务端），`InviteDialog` 只是 parent。所以 `InviteDialog` 拿到的是渲染好的结果，拿不到 `InviteForm` 的代码。

这条规则有一个副作用：客户端组件里不能通过 `import` 拿到服务端组件的静态成员。复合组件 `Menu.Item` 这种写法跨边界会得到 `undefined`，React 报：

```text
Element type is invalid. Received a promise that resolves to: undefined.
```

修法是把复合组件改成具名导出，或者只在客户端组件之间使用。

## 4.5 server-only 与密钥

服务端组件里出现密钥是正常的。危险的是这份文件被客户端组件 import，密钥随代码进入浏览器包。

`server-only` 包把这类误用变成构建错误：

```ts
// src/lib/db.ts
import "server-only";
import { createClient } from "@supabase/supabase-js";

export const db = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_SERVICE_ROLE_KEY!);
```

客户端组件一旦 import 这个文件，构建直接失败：

```text
Error: 'server-only' cannot be imported from a Client Component module
It should only be used from a Server Component.
Import traces:
  Client Component Browser:
    ./src/app/(app)/teams/team-card.tsx
```

`server-only` 不用安装，Next.js 自带解析。对应的还有 `client-only`，用于标记只能在浏览器里用的模块。

另一个常见的泄露通道是 props。服务端把密钥当 props 传给客户端组件，key 会以明文出现在 Payload 里：

```tsx
// 错误示范
return <Preview token={process.env.SUPABASE_SERVICE_ROLE_KEY} />;
```

构建之后的 `.next/server/app/` 目录里，能看到这一行：

```text
7:[["children",{"s":"__PAGE__",...["$","$L9",null,{"token":"sb_secret_FAKE_1234567890"}],...]
```

同一份 payload 也会内联在 HTML 里，所以打开“查看源代码”就能搜到。检查方法：

```bash
grep -rl "sb_secret" .next/server/app .next/static
```

三条命令可以当提交前的自检：

```bash
grep -rl "sb_secret" .next/server/app .next/static
grep -rl "service_role" .next/static
grep -rl "server-only" .next/static
```

第一条查服务端产物里有没有明文密钥，第二条查浏览器包里有没有服务端密钥名，第三条确认 `server-only` 标记有没有真的生效。三条都空，才是干净的。

模块顶层的常量也会泄露。服务端文件里 `const KEY = process.env.SUPABASE_SERVICE_ROLE_KEY`，只要这个常量被传给客户端组件，它的值就进了 Payload。泄露发生在“传”这一步，和变量前缀无关。

环境变量还有一条规则：只有 `NEXT_PUBLIC_` 前缀的变量会进客户端包，其他前缀在客户端被替换成空字符串。于是含密钥的函数在客户端“能 import 但跑不对”，返回 `undefined`，看起来像配置问题，实际是环境变量被剥掉了。第 7 章展开。

`NEXT_PUBLIC_` 变量的替换发生在构建时：代码里的 `process.env.NEXT_PUBLIC_SITE_URL` 被替换成一个字符串字面量。所以在浏览器里读到的值是构建那一刻的值，改环境变量要重新构建。


## 4.6 什么时候才需要 “use client”

判断标准只有一条：这段代码需不需要在浏览器里响应交互。

需要的情况有四类：用 `useState`、`useReducer` 管理状态；用 `useEffect` 处理生命周期；读 `window`、`localStorage`、`navigator` 这类浏览器 API；用自定义 hook 封装了上述逻辑。

不需要的情况常常被误判。下面这些交互，用原生 HTML 加 Server Action 就够了：

- 展开收起，用 `<details>` 和 `<summary>`。
- 表单提交，用 `<form action={serverAction}>`。
- 视频播放，用 `<video controls>`。

真正需要客户端组件的场景是“状态随时间变化”：受控输入、实时筛选、拖拽排序、轮询刷新。

常见误判有三类。

把 `onClick` 当成必须用客户端组件的证据。如果点击的结果是提交表单或跳转，`<form action={...}>` 和 `<Link>` 都能在服务端组件的输出里工作。

把“会变的内容”当成客户端。倒计时、在线人数、最新订单这些随时间变的内容，用服务端按请求渲染加轮询刷新，同样不需要客户端组件。

把“用了第三方 UI 库”当成必须整页加指令。库里的表格、弹窗多数可以把指令加在包装层，页面其余部分保持服务端。

反过来的误判也存在：给一个真正需要输入状态的小组件硬套表单提交，结果每敲一个字都要提交一次。判断标准仍是“状态变不变”。

客户端组件有三项固定成本：代码进浏览器包、下载后要执行一次、水合时再执行一次。前两项直接拉长 TTI，第三项在低端设备上能占掉几百毫秒。

服务端组件也有固定限制：不能有状态、不能有事件、不能读浏览器 API、不能拿 Context。此外它的重新渲染只能靠服务端再渲染，改一个受控输入的值不能靠它。

判断顺序建议这样走：

1. 这个组件要读数据库或密钥吗？要，放服务端。
2. 它有事件处理器或状态吗？没有，放服务端。
3. 它的事件能换成表单提交吗？能，放服务端加 action。
4. 以上都不行，才加 `"use client"`。

一个文件里只有第一个 `"use client"` 生效，写在子组件前面没有意义。一个目录里也只用标记入口文件，被它 import 的文件自动成为客户端模块。

`"use client"` 必须是文件的第一条语句。注释写在前面可以，`import` 写在前面会失效：

```tsx
// 错误示范
import { useState } from "react";
"use client";
```

指令失效时，构建报错会指向文件里的 hook 调用，提示信息里让你加指令。按提示加在正确位置即可。

## 4.7 把一页从客户端改回服务端

改造顺序是固定的，按这个顺序走不会乱。

第一步，删掉页面顶部的 `"use client"`，跑 `pnpm build`。构建会停在第一个需要客户端能力的语句上，报错里的行号就是改造起点。

第二步，把那段交互拆成单独文件，加上 `"use client"`。页面只负责取数和传数据，交互组件只接收数据和回调不接收函数。

第三步，把 `useEffect` 加 `fetch` 的取数搬到页面顶层，用 `await` 直接取。

改造前：

```tsx
// 改造前：src/app/(app)/teams/page.tsx
"use client";

import { useEffect, useState } from "react";

export default function TeamsPage() {
  const [teams, setTeams] = useState<Team[]>([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch("/api/teams")
      .then((res) => res.json())
      .then((data) => {
        setTeams(data);
        setLoading(false);
      });
  }, []);

  if (loading) return <p>加载中……</p>;
  return <ul>{teams.map((team) => <li key={team.id}>{team.name}</li>)}</ul>;
}
```

改造后：

```tsx
// 改造后：src/app/(app)/teams/page.tsx
import { Suspense } from "react";
import { listTeams } from "@/lib/teams";
import { SearchBox } from "./search-box";
import { TeamList } from "./team-list";

export default async function TeamsPage({ searchParams }: {
  searchParams: Promise<{ q?: string }>;
}) {
  const { q = "" } = await searchParams;
  const teams = await listTeams(q);

  return (
    <div>
      <SearchBox defaultValue={q} />
      <Suspense fallback={<p>加载中……</p>}>
        <TeamList teams={teams} />
      </Suspense>
    </div>
  );
}
```

```tsx
// src/app/(app)/teams/search-box.tsx
"use client";

import { useRouter } from "next/navigation";
import { useState, useTransition } from "react";

export function SearchBox({ defaultValue }: { defaultValue: string }) {
  const router = useRouter();
  const [value, setValue] = useState(defaultValue);
  const [pending, startTransition] = useTransition();

  return (
    <input
      value={value}
      disabled={pending}
      onChange={(event) => {
        const next = event.target.value;
        setValue(next);
        startTransition(() => {
          router.replace(next ? `/teams?q=${encodeURIComponent(next)}` : "/teams");
        });
      }}
    />
  );
}
```

这次改造里有三个判断，每个都可以复用。

状态能不能放进 URL。搜索关键字、页码、排序方向都属于“别人贴个链接应该看到同样结果”的状态，放进 `searchParams`。放进去之后，服务端能直接读到，还能被缓存和预取。

状态能不能删。改造前的 `loading` 状态可以整段删除，加载态交给 `Suspense` 和 `loading.tsx`。凡是“正在请求”这类由框架管理的状态，都不该自己维护。

状态必须留在客户端。焦点、展开的菜单、拖拽中的临时位置，只在当前会话有意义，留在客户端组件的 `useState` 里。

两个细节容易踩。一是 `defaultValue` 只在首次挂载时生效，URL 变了输入框不会跟着变，需要 `key={q}` 强制重建。二是 `router.replace` 用 replace 而不用 push，否则每敲一个字都往历史记录里塞一条。

鉴权要放在数据层，不能依赖页面。改造前页面是客户端，靠接口挡权限；改造后页面在服务端渲染，如果 `listTeams` 不校验 membership，直接访问 URL 就能读到数据。第 9 章的统一做法是在 `src/lib/teams.ts` 里调 `requireMembership()`。

### 4.7.1 客户端怎么读路由

服务端组件从 props 拿 `params` 和 `searchParams`。客户端组件没有这个入口，改用 `next/navigation` 的钩子：

```tsx
// src/app/(app)/teams/[slug]/_components/tabs.tsx
"use client";

import { useParams, usePathname, useSearchParams, useSelectedLayoutSegments } from "next/navigation";
```

四个钩子各管一件事。`useParams()` 返回动态段对象，`{ slug: "acme" }`，同步可读，不需要 await。`useSearchParams()` 返回 `URLSearchParams`，读查询串。`usePathname()` 返回当前路径。`useSelectedLayoutSegments()` 返回从根到当前的段名数组，做面包屑和侧栏高亮时用它，不用自己切字符串。

`useSearchParams()` 有一个代价：静态页面里一旦用了它，从最近的 `Suspense` 边界往下都会改成客户端渲染。包一层 `<Suspense>` 能把影响收敛到一个组件；不包，构建时可能报错。这条限制在 31 章讲客户端取数时还会遇到。

搜索框另有一个省事的写法，用 `next/form` 的 `<Form>`：

```tsx
// src/app/(app)/teams/_components/search-form.tsx
import Form from "next/form";

export function SearchForm({ defaultValue }: { defaultValue: string }) {
  return (
    <Form action="/teams">
      <input name="q" defaultValue={defaultValue} />
      <button type="submit">搜索</button>
    </Form>
  );
}
```

提交时表单字段自动拼成查询串，并做客户端导航，不用写 `onChange` 和 `useTransition`。它只适合“提交即改 URL”的表单。需要校验、错误回显、乐观更新的表单仍走 Server Action，见第 12 章。

## 4.8 边界与失败模式

边界向上传染。 客户端组件引入的组件都变成客户端组件，不管有没有标记。一个“小交互组件”把整棵子树拖进浏览器包，是首屏变慢的常见原因。用 `grep -rl` 搜产物能确认某个库有没有进包。

服务端组件里不能用 Context。 React Context 依赖客户端的渲染机制。需要共享状态时，建一个客户端 Provider，只包住需要它的子树，不要包在 `<html>` 外层。

```tsx
// src/app/(app)/providers.tsx
"use client";

import { createContext, useContext, useState } from "react";

type Toast = { id: number; text: string };
const ToastContext = createContext<Toast[]>([]);

export function ToastProvider({ children }: { children: React.ReactNode }) {
  const [toasts] = useState<Toast[]>([]);
  return <ToastContext.Provider value={toasts}>{children}</ToastContext.Provider>;
}

export function useToasts() {
  return useContext(ToastContext);
}
```

第三方组件没有标记。 有些库依赖浏览器 API，却没有写 `"use client"`，在服务端组件里直接 import 会报错。包一层把指令放在自己的文件上：

```tsx
// src/components/carousel.tsx
"use client";

export { Carousel } from "acme-carousel";
```

共享模块会编译两份。 纯展示组件被服务端和客户端都 import 时，会各编译一份。这通常没问题，但如果它 import 了很大的库，客户端那份会进包。给数据层文件加 `server-only` 能提前发现误用。

共享模块的数据请求会重复。 服务端和客户端共用的组件如果自己发请求，两端各发一次。数据请求放在服务端页面，共享组件只接收数据。

客户端组件的 props 里带了大对象。 一张图表要十个点，却把整月的数据传下去，Payload 和序列化时间都翻倍。传之前先裁字段。

模块顶层读浏览器对象，服务端直接崩。 客户端组件也会在服务端先渲染一次，模块加载时读 `window` 或 `localStorage`，服务端没有这些对象，页面 500。把这类读取放进 `useEffect` 或事件处理器里。

dev 与 build 的报错时机不同。 有些边界错误在 `pnpm dev` 下只显示警告，`pnpm build` 才失败。边界类的改动一定要跑一次构建。

副作用执行两次。 客户端组件的 `useEffect` 在开发模式下会挂载、卸载、再挂载，这是 Strict Mode 的行为。生产模式只执行一次。看到请求发了两次，先确认环境，再查代码。

async 客户端组件。 客户端组件写成 `async` 函数时，构建在 16.4 下可以通过，运行时行为与普通函数组件不同。数据获取放在服务端组件里，客户端组件保持同步。

## 4.9 检查点

1. 在 `src/lib/db.ts` 顶部加 `import "server-only";`，再在任意客户端组件里 import 它。判据：`pnpm build` 失败，报错含 `'server-only' cannot be imported from a Client Component module`。
2. 构建之后执行 `grep -rl "date-fns" .next/static/chunks`。判据：把日期格式化移到服务端后，命令没有输出。
3. 在服务端页面里把 `process.env.SUPABASE_SERVICE_ROLE_KEY` 当 props 传给客户端组件，构建后执行 `grep -rl "sb_secret" .next/server/app`。判据：能搜到含该值的 payload 文件。
4. 在客户端组件里 `import { db } from "@/lib/db"` 并调用。判据：构建报 `server-only` 错误，删掉后恢复。
5. 用 `<InviteDialog>` 包一个读数据库的服务端组件。判据：页面能正常渲染，浏览器包体积不因该服务端组件增加。
6. 把页面顶部的 `"use client"` 删掉。判据：如果页面里没有 hook，构建通过；如果有 `useState`，报 `You're importing a module that depends on useState`。

## 4.10 常见错误

1. `You're importing a module that depends on useState into a React Server Component module`

现象：页面保存后构建失败，报错指向 `import` 行。
原因：文件在服务端组件里用了客户端 hook。
改法：确认交互部分拆成单独文件，加上 `"use client"`；不要在页面顶层加指令，否则整页数据能力失效。

2. `Event handlers cannot be passed to Client Component props`

现象：构建期报错，附带 `{onClick: function onClick}`。
原因：服务端组件把函数当 props 传给了客户端组件。
改法：事件处理器写在客户端组件内部；服务端只传数据，不传函数。

3. `Only plain objects, and a few built-ins, can be passed to Client Components`

现象：页面渲染失败，报错提到 class 实例或 null 原型。
原因：把 Prisma 记录、ORM 模型实例、类实例直接传给客户端组件。
改法：转成普通对象，只传需要的字段。

4. `Error: 'server-only' cannot be imported from a Client Component module`

现象：构建失败，`Import traces` 指向某个客户端组件。
原因：客户端组件链路上引用了标了 `server-only` 的数据层文件。
改法：把数据获取上移到服务端页面或布局，客户端组件只接收数据。

5. 首屏 JS 包异常变大

现象：构建通过，但首屏加载时间从 1 秒涨到 3 秒。
原因：某个大库（日期、图表、编辑器）被客户端组件 import，整包进了浏览器。
改法：用 `grep -rl "库名" .next/static/chunks` 定位；把计算移到服务端，或者改成动态 import。

6. `Element type is invalid`

现象：页面运行时报错，组件位置显示 undefined。
原因：客户端组件里用了服务端组件的静态成员，例如 `Menu.Item`，跨边界后属性丢失。
改法：改成具名导出，或者把这部分组件都放在客户端。

## 4.11 这一章在做什么

这一章划组件的边界。服务端组件是默认值，客户端组件按需声明。`"use client"` 标的是模块图入口，被它 import 的一切都会进浏览器包。跨边界的数据要能序列化，函数和类实例不行。服务端组件可以当 `children` 传进去，靠 owner 与 parent 的区别保住服务端执行。

三条可以带走的判断：

- 一行 `"use client"` 的成本是“它 import 的一切”。
- 密钥和数据库客户端只出现在标了 `server-only` 的文件里。
- 交互优先找原生 HTML 加 Server Action，找不到再上客户端组件。

下一章讲服务端取数：并行还是串行、请求去重、Suspense 边界怎么摆，以及怎么让首屏不等一串瀑布。
