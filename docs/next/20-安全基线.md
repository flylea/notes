# 第 20 章 安全基线

这一章讲一个上线的应用至少要有五样东西：限流、CSP、数据出口控制、审计日志、两步验证。

需要它们的原因是前几章各自守住一段，但都假设“请求是正常的”。真实流量里还有撞库、脚本刷接口、注入脚本窃取 cookie、内部人员越权导出数据。

五样东西对应五个面，缺任意一个，另外四个的效果都会打折。限流限制单位时间的请求次数，把暴力破解的成本抬高。CSP 限制页面能加载和执行什么，把 XSS 的影响压小。taint 标记敏感数据，阻止它被序列化到客户端。审计记录敏感操作，出事后能复盘。两步验证在密码之外再加一层，让撞库拿到的密码不够用。

这一章按这五个面展开，每个面给可用的实现，再讲边界与验证方法。所有实现都建立在前面几章的会话与 RLS 上，不依赖额外的商业服务。

## 20.1 限流为什么必须共享状态

限流的计数必须放在进程之外，这是限流能不能生效的前提。

部署在多个实例上时，每个实例各自计数。用户连发十次请求，落在十个实例上，每个实例只记了一次，限流等于没有。

Serverless 环境更糟。每个请求可能在不同的实例里执行，进程内存生命周期只有几百毫秒，计数根本累积不起来。

反例是进程内的 Map：

```ts
// 反例：进程内计数
const attempts = new Map<string, number>()

export async function POST(req: Request) {
  const { email } = await req.json()
  const n = (attempts.get(email) ?? 0) + 1
  attempts.set(email, n)
  if (n > 5) return new Response('too many', { status: 429 })
  ...
}
```


正确的做法是 Redis。所有实例共享同一份计数，`INCR` 是原子操作，天然适合做计数器。

## 20.2 固定窗口计数器

最简单的限流是固定窗口：以分钟或秒为单位分桶，每个桶一个计数。

```ts
// src/lib/rate-limit.ts
// 教学版实现；仓库里的产品版是 src/lib/api/rate-limit.ts（同一套逻辑，接口更全）
import 'server-only'

import { createHash } from 'node:crypto'
import { redis } from '@/lib/redis'

export type RateLimitResult = {
  ok: boolean
  limit: number
  remaining: number
  resetAt: number // 毫秒时间戳
}

/**
 * 固定窗口计数。简单、够用，边界处会有 2 倍突发（见后文）。
 * key 里只放哈希，不放明文邮箱，避免 Redis 变成一个 PII 库。
 */
export async function rateLimit(input: {
  key: string
  limit: number
  windowSeconds: number
}): Promise<RateLimitResult> {
  const bucket = Math.floor(Date.now() / (input.windowSeconds * 1000))
  const redisKey = `rl:${input.key}:${bucket}`

  const [count] = (await redis
    .multi()
    .incr(redisKey)
    .expire(redisKey, input.windowSeconds * 2)
    .exec()) as [number, unknown]

  const resetAt = (bucket + 1) * input.windowSeconds * 1000
  return {
    ok: count <= input.limit,
    limit: input.limit,
    remaining: Math.max(0, input.limit - count),
    resetAt,
  }
}

export function hashKey(raw: string) {
  return createHash('sha256').update(raw).digest('hex').slice(0, 32)
}
```


关键点在 `bucket` 的计算：`Math.floor(now / (window * 1000))` 把时间切成等长的桶。桶号进 key，过期时间设成窗口长度，旧桶自动清理。

`multi().incr().expire()` 放在一个事务里，避免 `INCR` 成功但 `EXPIRE` 失败导致 key 永不过期。

返回三个值：是否允许、剩余次数、重置时间。前两个给前端显示，第三个用来算 `Retry-After`。

固定窗口的实现在十行以内，适合绝大多数接口。它有一个已知缺陷：窗口边界处可能出现两倍突发。1 分 59 秒打 5 次，2 分 0 秒再打 5 次，两秒内打了 10 次。对登录接口这个误差可以接受，对计费接口不行，那要用滑动窗口或令牌桶。

## 20.3 登录接口的双维度限流

登录要同时按邮箱和按 IP 限流。

只按 IP：同一个 IP 后面可能是一个公司，一个人输错就把全公司挡住。

只按邮箱：攻击者换邮箱继续试，同一 IP 不受限制。

两个维度都做，任意一个超限就拒绝：

```ts
// src/app/api/auth/login/route.ts
import { NextResponse, type NextRequest } from 'next/server'
import { z } from 'zod'
import { createClient } from '@/lib/supabase/server'
import { hashKey, rateLimit } from '@/lib/rate-limit'

const schema = z.object({
  email: z.string().email(),
  password: z.string().min(8).max(72),
})

export async function POST(request: NextRequest) {
  const body = await request.json().catch(() => null)
  const parsed = schema.safeParse(body)
  if (!parsed.success) {
    return NextResponse.json({ error: '参数不合法' }, { status: 400 })
  }

  const email = parsed.data.email.trim().toLowerCase()
  const ip =
    request.headers.get('x-forwarded-for')?.split(',')[0]?.trim() ??
    request.headers.get('x-real-ip') ??
    'unknown'

  // 双维度：同一个邮箱每分钟最多 5 次；同一个 IP 每分钟最多 20 次
  const [byEmail, byIp] = await Promise.all([
    rateLimit({ key: `login:email:${hashKey(email)}`, limit: 5, windowSeconds: 60 }),
    rateLimit({ key: `login:ip:${hashKey(ip)}`, limit: 20, windowSeconds: 60 }),
  ])

  if (!byEmail.ok || !byIp.ok) {
    const resetAt = Math.max(byEmail.resetAt, byIp.resetAt)
    const retryAfter = Math.max(1, Math.ceil((resetAt - Date.now()) / 1000))
    return NextResponse.json(
      { error: '尝试过于频繁，请稍后再试' },
      {
        status: 429,
        headers: {
          'Retry-After': String(retryAfter),
          'X-RateLimit-Limit': String(byEmail.limit),
          'X-RateLimit-Remaining': '0',
          'X-RateLimit-Reset': String(Math.floor(resetAt / 1000)),
        },
      }
    )
  }

  const supabase = await createClient()
  const { error } = await supabase.auth.signInWithPassword({
    email,
    password: parsed.data.password,
  })

  // 注意：登录失败的原因不能告诉调用方是「邮箱不存在」还是「密码错了」
  if (error) {
    return NextResponse.json(
      { error: '邮箱或密码不正确' },
      {
        status: 401,
        headers: {
          'X-RateLimit-Limit': String(byEmail.limit),
          'X-RateLimit-Remaining': String(byEmail.remaining),
        },
      }
    )
  }

  return NextResponse.json({ ok: true })
}
```


响应细节。超限返回 429，带 `Retry-After` 和 `X-RateLimit-*` 头。认证失败统一返回 401，文案不区分“邮箱不存在”和“密码错误”。

取 IP 时用 `x-forwarded-for` 的第一个值。这个头可以被伪造，所以在可信代理后面才有意义。

## 20.4 哪些接口必须限流

按风险排序，前六个必须有。

登录：5 次/分（按邮箱）、20 次/分（按 IP）。

注册：3 次/小时（按 IP），防止批量注册。

找回密码：3 次/小时（按邮箱），防止邮件轰炸。

邀请：20 次/小时（按团队），第 18 章讲过。

上传：10 次/分（按用户），防止存储滥用。

公开 API：按密钥或 IP，具体数值看业务。

两步验证的验证码：5 次/5 分钟（按用户），防止暴力猜六位数字。

## 20.5 CSP 的基本形状

CSP 是一个响应头，列出页面允许加载哪些资源。

七个常用指令。`default-src` 是兜底。`script-src` 限制脚本来源。`style-src` 限制样式。`img-src` 限制图片。`connect-src` 限制 fetch 和 WebSocket 的目标。`frame-ancestors` 限制谁能用 iframe 嵌你。`form-action` 限制表单提交目标。

`frame-ancestors 'none'` 防点击劫持。`base-uri 'none'` 防 `<base>` 标签篡改相对路径。`object-src 'none'` 禁用插件。

```
Content-Security-Policy: default-src *
```


一个只有 `default-src *` 的 CSP 等于没有 CSP。

## 20.6 nonce 与动态渲染

`'unsafe-inline'` 允许所有内联脚本，等于给 XSS 留门。要禁掉它，就得给每个内联脚本发一个 nonce。

nonce 每次请求随机生成，写进 CSP 头和 `<script>` 标签，两者一致才执行。

```ts
// src/proxy.ts（CSP 部分）
import { NextResponse, type NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64')

  const isDev = process.env.NODE_ENV === 'development'
  const csp = [
    `default-src 'self'`,
    // 开发环境 React 调试需要 eval，生产环境不要
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? " 'unsafe-eval'" : ''}`,
    `style-src 'self' 'unsafe-inline'`,
    `img-src 'self' blob: data: https://*.supabase.co https://avatars.githubusercontent.com`,
    `font-src 'self'`,
    `connect-src 'self' https://*.supabase.co wss://*.supabase.co${isDev ? ' ws://localhost:* http://localhost:*' : ''}`,
    `frame-ancestors 'none'`,
    `base-uri 'none'`,
    `form-action 'self'`,
  ].join('; ')

  // 请求头：给 Next 渲染用，它能从中解析 nonce
  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-nonce', nonce)
  requestHeaders.set('Content-Security-Policy', csp)

  const response = NextResponse.next({ request: { headers: requestHeaders } })
  // 响应头：给浏览器执行用
  response.headers.set('Content-Security-Policy', csp)
  response.headers.set('x-nonce', nonce)
  return response
}

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico).*)'],
}
```


Next.js 会自动把 nonce 加到框架脚本和内联脚本上。前提是它能在 CSP 头里读到 `'nonce-...'`。

两个约束。第一，用了 nonce 必须动态渲染，静态页在构建期没有请求头，拿不到 nonce。第二，PPR 与 nonce CSP 不兼容，因为预渲染的部分没有请求上下文。

`'strict-dynamic'` 可以省掉一长串域名白名单：有了它，由受信脚本动态插入的脚本自动受信。代价是 `'self'` 失效，配置要一并调整。

## 20.7 在组件里读 nonce

nonce 通过请求头传给渲染层，layout 里读出来给 `<Script>` 用。

```tsx
// src/app/layout.tsx
import { headers } from 'next/headers'
import Script from 'next/script'

export default async function RootLayout({ children }: { children: React.ReactNode }) {
  const nonce = (await headers()).get('x-nonce') ?? undefined

  return (
    <html lang="zh-CN">
      <head>
        <Script
          nonce={nonce}
          id="theme-init"
          dangerouslySetInnerHTML={{
            __html: `document.documentElement.dataset.theme = localStorage.getItem('theme') || 'light'`,
          }}
        />
      </head>
      <body>{children}</body>
    </html>
  )
}
```


`headers()` 是异步的，要 `await`。nonce 只对服务端渲染的脚本有效，客户端动态插入的脚本拿不到。

没有 nonce 的内联脚本会被浏览器拦掉，控制台报：

```
Refused to execute inline script because it violates the following
Content Security Policy directive: "script-src 'self' 'nonce-abc123'".
```


这条报错是 CSP 生效的证据。

## 20.8 分阶段上线 CSP

一上来就用强制模式，容易把页面打挂。分三步走。

第一步，Report-Only 模式。只报告不拦截，收集一周的违规。

```ts
response.headers.set('Content-Security-Policy-Report-Only', csp)
```


第二步，修掉报告里的真实违规，比如漏配的图片域名、内联样式。

第三步，切成强制模式。

接报告需要一个接口：

```ts
// src/app/api/csp-report/route.ts
import { NextResponse, type NextRequest } from 'next/server'

export async function POST(request: NextRequest) {
  const report = await request.json().catch(() => null)
  console.warn('[csp]', JSON.stringify(report).slice(0, 2000))
  return new NextResponse(null, { status: 204 })
}
```


生产环境不要用 `'unsafe-eval'`，开发环境需要，因为 React 的调试工具用到 `eval`。

## 20.9 taint：阻止敏感数据流出

React 的 Taint API 可以给对象打标记，标记过的值不能被序列化传给客户端组件。

开启方式是在 `next.config.ts` 里打开实验开关：

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    taint: true,
  },
}

export default nextConfig
```


两个 API。`experimental_taintObjectReference` 标记整个对象，`experimental_taintUniqueValue` 标记单个值。

```ts
// src/lib/taint.ts
import 'server-only'

import { experimental_taintObjectReference, experimental_taintUniqueValue } from 'react'

// 整个对象都不许传给客户端
export function markUserPrivate(user: { id: string; email: string }) {
  experimental_taintObjectReference('不要在客户端组件里使用完整的 user 对象', user)
  return user
}

// 单个值（比如内部成本价、邀请 token）
export function markSecret(value: string, name: string) {
  experimental_taintUniqueValue(`不要把这个值传给客户端：${name}`, globalThis, value)
}
```


标记之后，把这个对象作为 props 传给客户端组件会直接抛错：

```
Error: Cannot pass a tainted value to a Client Component.
```


taint 是兜底，不能替代设计。正确的做法是在数据访问层就把不需要的字段裁掉，返回 DTO。

## 20.10 审计日志

敏感操作要留记录：谁、什么时候、做了什么、结果如何。

```ts
// src/lib/audit.ts
import 'server-only'

import { headers } from 'next/headers'
import { createClient } from '@/lib/supabase/server'

export async function audit(input: {
  teamId: string | null
  actorId: string
  action: string
  targetType?: string
  targetId?: string
  metadata?: Record<string, unknown>
}) {
  const supabase = await createClient()
  const h = await headers()

  const { error } = await supabase.from('activity_logs').insert({
    team_id: input.teamId,
    actor_id: input.actorId,
    action: input.action,
    target_type: input.targetType ?? null,
    target_id: input.targetId ?? null,
    metadata: {
      ...input.metadata,
      ip: h.get('x-forwarded-for')?.split(',')[0]?.trim() ?? null,
      ua: h.get('user-agent')?.slice(0, 200) ?? null,
    },
  })

  // 审计失败不能拖垮业务，但必须留下痕迹
  if (error) console.error('[audit] insert failed', input.action, error.message)
}
```


四个设计点。写入失败不影响主流程。`metadata` 里不放密码和 token。IP 和 User-Agent 从请求头取。超过保留期归档，不要无限增长。

哪些操作要记：登录、退出、改密码、改邮箱、邀请、移除成员、改套餐、删除团队、导出数据、开启或关闭两步验证。

```ts
// src/app/(app)/settings/security/actions.ts
'use server'

import { createClient } from '@/lib/supabase/server'
import { requireUser } from '@/lib/auth'

export async function startTotpEnroll() {
  await requireUser()
  const supabase = await createClient()

  const { data, error } = await supabase.auth.mfa.enroll({
    factorType: 'totp',
    friendlyName: `Authenticator ${new Date().toISOString().slice(0, 10)}`,
  })

  if (error) return { ok: false as const, error: error.message }

  // data.id 后面要用来 challenge；data.totp.qr_code 是 SVG data URL
  return {
    ok: true as const,
    factorId: data.id,
    qrCode: data.totp.qr_code,
    secret: data.totp.secret, // 给不能扫码的用户手输
  }
}
```

  const user = await requireUser()
  const supabase = await createClient()

## 20.11 两步验证的基本流程

TOTP 是最常见的形式：服务端给一个密钥，客户端用它生成 30 秒一变的六位数字。

注册分两步：生成密钥并显示二维码，用户输入一次验证码确认。

```ts
// src/app/(auth)/mfa/page.tsx（片段）
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export default async function MfaPage() {
  const supabase = await createClient()
  const { data } = await supabase.auth.mfa.getAuthenticatorAssuranceLevel()

  if (data?.currentLevel === 'aal2') redirect('/dashboard')
  if (!data || data.nextLevel !== 'aal2') redirect('/dashboard')

  const { data: factors } = await supabase.auth.mfa.listFactors()
  const totp = factors?.totp?.[0]
  if (!totp) redirect('/dashboard')

  return <MfaChallengeForm factorId={totp.id} />
}
```


确认之后，用户下次登录会进入 AAL1 状态（只验了密码），必须再输一次动态码才升到 AAL2。

**未验证**：`mfa.enroll` 返回的 `totp.qr_code` 是 SVG 的 data URI，可以直接放进 `<img src>`，这一行为以 auth-js 版本为准。

## 20.12 AAL2 的三层门禁

AAL 是认证保证等级。`aal1` 表示只验证了一种因素，`aal2` 表示验证了两种。

三层门禁。第一层，页面：判断当前 AAL，不够就跳 `/mfa`。第二层，action：每个敏感操作再查一次。第三层，RLS：policy 里判断 JWT 的 `aal` 字段。

第三层最可靠，因为它挡得住绕过应用的请求：

```sql
create policy subscriptions_billing_aal2 on public.subscriptions
  as restrictive
  for all
  to authenticated
  using ((select auth.jwt() ->> 'aal') = 'aal2')
  with check ((select auth.jwt() ->> 'aal') = 'aal2');
```


三层都做，是因为每一层都可能被绕过。页面被绕过还有 action，action 被绕过还有数据库，数据库这一层挡得住所有非 service_role 的请求。

## 20.13 备用码

用户丢了手机，需要备用码。

生成十个一次性码，存哈希，用掉一个删一个。

```ts
// src/lib/mfa-recovery.ts
import 'server-only'

import { createHash, randomBytes } from 'node:crypto'
import { createAdminClient } from '@/lib/supabase/admin'

const ALPHABET = '23456789ABCDEFGHJKLMNPQRSTUVWXYZ' // 去掉容易混的 0/O/1/I

function generateCode() {
  const bytes = randomBytes(10)
  let out = ''
  for (let i = 0; i < 10; i++) {
    out += ALPHABET[bytes[i] % ALPHABET.length]
    if (i === 4) out += '-'
  }
  return out
}

function hashCode(code: string) {
  return createHash('sha256').update(code.replace('-', '').toUpperCase()).digest('hex')
}

export async function generateRecoveryCodes(userId: string) {
  const codes = Array.from({ length: 10 }, generateCode)
  const admin = createAdminClient()

  const { error } = await admin.auth.admin.updateUserById(userId, {
    app_metadata: { recovery_codes: codes.map(hashCode) },
  })
  if (error) throw new Error(error.message)

  // 只有这一次能看到明文，之后库里只有哈希
  return codes
}
```


**未验证**：把备用码存在 `app_metadata` 里是一个妥协方案，因为表结构已定。更干净的做法是单独建表，带 `used_at` 字段。

## 20.14 密钥卫生

四条纪律。

第一，`service_role` 的密钥不加 `NEXT_PUBLIC_` 前缀，只在服务端使用。

第二，分环境。开发、预览、生产三套密钥，不共用。

第三，确认 `.env.local` 没有被提交过：

```bash
git check-ignore -v .env.local   # 应该输出命中规则，不能为空
git log -p -- .env.local | head  # 应该是空的（历史上也没提交过）
```


第四，可轮换。所有密钥都要有轮换步骤，写在运维文档里。

## 20.15 撞库与密码策略

撞库是用别处泄漏的邮箱密码组合来试你的站点。它的成功率取决于两件事：限流是否有效、用户的密码是否在别处也用过。

密码策略按 NIST 的建议做，四条。

第一，长度优先于复杂度。最少 12 位，不强制大小写混合和特殊字符。

第二，不做定期强制更换。强制更换会让用户改成 `Password1!`、`Password2!` 这种可预测的序列。

第三，检查常见弱密码。用一份 top 10 万的泄漏密码表，注册和改密码时比对。

第四，支持粘贴。禁止粘贴会逼用户设短密码。

## 20.16 响应头的全家桶

CSP 之外还有五个头，都是低成本高收益。

`Strict-Transport-Security` 强制 HTTPS，`max-age` 至少半年，加上 `includeSubDomains`。

`X-Content-Type-Options: nosniff` 禁止浏览器猜测 MIME 类型，防止把上传的图片当脚本执行。

`Referrer-Policy: strict-origin-when-cross-origin` 跨站时不带完整路径，减少 URL 里的 token 泄漏。

`Permissions-Policy` 关掉不需要的浏览器能力，比如 `camera=()`、`microphone=()`。

`X-Frame-Options: DENY` 与 CSP 的 `frame-ancestors` 重复，保留它是为了兼容老浏览器。

## 20.17 限流放在哪一层

限流可以放在三个位置，各有用途。

CDN 或 WAF 层：挡掉明显的洪水攻击，成本最低。Vercel 自带基础的 DDoS 防护，Cloudflare 可以配更细的规则。

应用层：业务相关。按用户、按邮箱、按团队限流，WAF 做不到。

数据库层：连接数限制，防止一个慢查询拖垮整个库。

三层配合：WAF 挡量，应用层挡行为，数据库层兜底。只在应用层做限流，遇到大流量时请求已经打到进程上了。

## 20.18 日志本身也要安全

审计日志里有 IP、邮箱、操作内容，本身就是敏感数据。

三条。日志表不给 `anon` 任何权限，member 也读不到。日志的保留期有限，超过归档或删除。日志导出要审批，不能随手下载全量。

另一个常见错误是把完整请求体写进日志。登录失败的日志里如果带了密码，日志系统就变成了密码库。

## 20.19 出事之后的一小时

有人报告“数据好像被看了”，第一小时做五件事。

第一，确认范围。查审计日志，看这个账号在什么时间做了什么。

第二，切断。禁用账号或轮换密钥，先止血再分析。

第三，保留证据。导出相关日志，别在修复过程中把现场覆盖了。

第四，评估影响。哪些数据、多少人、是否涉及个人信息。

第五，通知。涉及个人信息的泄漏，多数地区有法定的通知时限。

事后写复盘，落到具体改动上，不要停在“加强安全意识”。

## 20.20 依赖与供应链

第三方包的漏洞是最常见的入口之一。

三条。锁文件进仓库，构建用 `--frozen-lockfile`。每周跑一次 `pnpm audit`，高危立即处理。依赖数量控制在必要范围，一个包引入几十个传递依赖。

`pnpm audit --prod` 只看生产依赖。开发依赖的漏洞不会进生产包，但会进构建环境，仍然要管。

**未验证**：`pnpm audit` 的输出格式随版本变化，CI 里的解析逻辑要跟着调。

## 20.21 威胁建模四问

设计一个新功能时，按四个问题过一遍。

第一，谁能访问这个入口？未登录、成员、owner、外部系统。

第二，攻击者能得到什么？数据、权限、还是只是消耗资源。

第三，防线在哪一层？入口、应用、数据库。

第四，失败时怎么发现？日志、告警、还是用户投诉。

四个问题写在 PR 描述里，评审的人就能看懂攻击面。

## 20.22 客户安全问卷常问的六条

企业客户采购时会发一份问卷，六条出现频率最高。

数据存在哪、是否加密（传输和静态）。谁能访问、是否有最小权限。多久备份、恢复演练做过没有。有没有两步验证、能不能强制开启。审计日志保留多久。漏洞怎么响应、有没有 SLA。

这六条要能一句话答出来。答不出来的，说明内部没定。

## 20.23 安全维护的节奏

按固定节奏做，别等出事。

每周：看限流命中率、登录失败率、`pnpm audit`。

每月：轮换一次非关键密钥，看 Security Advisors，复查 CSP 报告。

每季度：复测两步验证流程、备份恢复、审计日志保留策略。

每年：威胁建模重做一次，安全问卷更新一次。

## 20.24 上传的安全边界

文件上传是最容易被忽视的入口。

四条。校验 MIME 与扩展名，两者都要，都不可信时以魔数为准。限制大小，前端限制只是体验，服务端必须再限。文件名不落盘，用随机 id，原始文件名只存数据库。下载用签名 URL，有效期以秒计，单链接不可吊销。

图片要做二次处理，重新编码能去掉大部分嵌在元数据里的脚本。SVG 特殊处理，它可以内嵌脚本，要么禁止，要么用 `<img>` 加载并加 CSP。

存储桶的 policy 按路径第一段判断团队，第 17 章讲过写法。

## 20.25 签名 URL 的边界

签名 URL 把访问权限编码进 URL 本身，任何拿到链接的人都能访问。

三个后果。链接会出现在日志、Referer、聊天记录里。链接在有效期内无法吊销。链接可以被无限次使用。

所以有效期要短，几分钟到一小时。长期访问用服务端代理读流，不把存储地址暴露给浏览器。

`expiresIn` 的单位是秒。写 3600 是一小时，写 60 是一分钟。传毫秒会得到一个几十年的链接，这个错误很常见。

## 20.26 定时任务的安全

后台任务用 `service_role`，绕过 RLS，出错代价大。

三条。任务入口要鉴权，用独立的密钥头，不要复用用户会话。任务要幂等，重复执行不产生重复数据。任务失败要有告警，不能静默重试到死。

`jobs` 表用 `for update skip locked` 取任务，多 worker 并发安全。

任务日志单独记，包含任务 id、开始时间、耗时、结果。排查时按 id 查。

## 20.27 恢复演练

备份没有演练过，等于没有备份。

每季度做一次：从备份恢复到一个临时库，跑一遍关键查询，确认数据完整。

演练要覆盖两种场景：误删单条记录、整库故障。前者用时间点恢复，后者用全量备份。

恢复时间目标先定下来。小时级和天级是完全不同的架构，成本差一个量级。

## 20.28 免费档能做的安全项

预算有限时，按性价比排序。

先做限流（Redis 免费档够用）、CSP、审计日志、两步验证。这四项都不花钱，覆盖大部分实际风险。

再做备份与恢复演练。Supabase 免费档有基础备份，频率低，要自己额外导出关键表。

最后考虑 WAF 和商业扫描工具。它们有用，但在基础项做完之前都排不上优先级。

## 20.29 错误信息怎么给

错误信息在安全与可用之间取舍。

登录失败统一文案：“邮箱或密码不正确”。分开说“邮箱不存在”会给攻击者一个枚举工具。

注册接口同理。邮箱已注册时返回成功，同时给对方发一封提示信。

但是调试信息要给。内部日志记录具体原因，用户看到统一文案，两者分开。

## 20.30 会话与 CSRF 的配合

`SameSite=lax` 挡住了跨站 POST，但挡不住同站内的伪造。

接口如果是 `application/json`，跨站表单发不出来，因为表单只能发三种 content-type。这一层已经过滤掉大部分 CSRF。

剩下的风险来自 `text/plain` 和简单 POST。加一层 `Origin` 校验：请求的 `Origin` 必须是本站，缺失时拒绝。

Server Action 自带 Origin 校验，这也是它比手写 Route Handler 更安全的原因之一。

## 20.31 安全与性能的平衡

安全措施大多有性能成本，要挑成本低的。

CSP 头几乎没有成本。限流是两次 Redis 往返，约 1 毫秒。`getClaims()` 验签 0.1–0.5 毫秒。审计写入是一次 insert，可以异步。

成本高的是全量加密、逐请求的第三方风控调用。这些按业务重要性选择性使用。

先做低成本项，再评估高成本项。多数团队在第一步就能拿掉八成风险。

## 20.32 该设的三个告警

告警太多等于没有告警。启动阶段设三条够用。

登录失败率：连续 5 分钟超过 20%，可能是撞库。按 IP 聚合能看到是否单一来源。

限流命中：某个接口的 429 比例突然翻倍，可能是脚本在刷，也可能是阈值设太低误伤。

审计异常：service_role 的查询量突增，或者某个账号在深夜批量导出数据。这条最难设，但价值最高。

三条都落到具体的查询或指标上，不要设“有异常就告警”这种没法执行的规则。

## 20.33 检查点

1. 连续输错 6 次密码，第 6 次返回 429，响应头有 `Retry-After`。
2. 在页面里加一段没有 nonce 的内联脚本，控制台报 `Refused to execute inline script`。
3. 开启两步验证的账号，登录后停在 AAL1，访问账单页被跳到 `/mfa`。
4. `curl -I` 看响应头，有 `Content-Security-Policy`，且不含 `unsafe-inline`。
5. 触发一次改密码，`activity_logs` 里有一行 `auth.password_changed`。

## 20.34 常见错误

1. 限流计数放在进程内存里

现象：多实例部署下限流不生效。原因：每个实例各算各的。改法：用 Redis 共享计数。

2. CSP 里留了 `'unsafe-inline'`

现象：CSP 配了但 XSS 仍能执行。原因：`'unsafe-inline'` 允许内联脚本。改法：换 nonce，去掉 `'unsafe-inline'`。

3. 用了 nonce 但页面是静态的

现象：构建失败或脚本被拦。原因：静态页没有请求头。改法：相关页面改为动态渲染，或用 `<Suspense>` 隔离。

4. taint 没开就以为有保护

现象：敏感字段出现在客户端 props 里。原因：`experimental.taint` 没开，或没调用标记函数。改法：开开关，在 DAL 里标记。

5. 审计日志写入失败导致主流程失败

现象：改密码成功但页面 500。原因：审计写在 `try` 之外。改法：包 `try/catch`，失败只打日志。

6. 两步验证只做了页面层

现象：直接 POST 敏感 action 能绕过 AAL2。原因：action 里没查 AAL。改法：action 和 RLS 各加一层。

## 20.35 这一章在做什么

这一章把安全基线补齐：限流、CSP、taint、审计、两步验证。这些工作没有终点，上线之后要按周看日志、按月轮换密钥、按季度复测。

下一章讲特性开关与配额。它和这一章的交点是：限流防滥用，配额防超支，两者都在“请求量”这个维度上做控制，一个在入口，一个在业务规则里。
