# 第 50 章 成本与限额

这一章讲 teamstack 依赖的五个外部服务各自免费到什么程度、超了会发生什么、怎么提前发现，以及什么时候该付钱。

免费档的问题不在“额度小”，在“边界不清楚”。数据库 500 MB 是只算数据还是含索引，出网 5 GB 算不算静态资源，函数超时是报错还是计费，这些细节决定项目会不会在某个凌晨突然停掉。

涉及的服务有五家：Supabase（数据库、Storage、Auth）、Vercel（对照部署）、Resend（邮件）、Cloudflare（DNS、CDN、Turnstile）、VPS 供应商。Stripe 按交易抽成，不在免费档讨论范围内。

文中额度以各家 2026 年 11 月的官方定价页为准。平台会调整，动手前核一次。

## 50.1 先知道用了多少

成本管理的起点是计量。说不清当前用量，告警与预算都无从谈起。

数据库大小用一条 SQL 查。`pg_database_size` 返回整个库的字节数，包含索引与 TOAST；`pg_total_relation_size` 查单表含索引的大小。

```sql
-- 整个库的大小（含索引、TOAST）
select pg_size_pretty(pg_database_size(current_database())) as db_size;

-- 每张表的大小，按从大到小排
select
  relname as table_name,
  pg_size_pretty(pg_total_relation_size(relid)) as total_size,
  pg_total_relation_size(relid) as total_bytes
from pg_catalog.pg_statio_user_tables
order by pg_total_relation_size(relid) desc
limit 10;
```

Storage 的大小要遍历 bucket。管理 API 的 `list` 分页返回，单页上限 100，递归目录；对象多时这个操作不便宜，巡检一天一次即可。

```js
// scripts/storage-size.mjs
import { createClient } from '@supabase/supabase-js'

const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.SUPABASE_SERVICE_ROLE_KEY,
  { auth: { persistSession: false } }
)

async function storageBytes(bucket) {
  let total = 0
  let offset = 0
  const limit = 100

  for (;;) {
    const { data, error } = await supabase.storage
      .from(bucket)
      .list('', { limit, offset, sortBy: { column: 'name', order: 'asc' } })

    if (error) throw error
    if (!data.length) break

    for (const item of data) {
      // 目录项没有 metadata，跳过；文件在 metadata.size 里
      total += item.metadata?.size ?? 0
    }

    if (data.length < limit) break
    offset += limit
  }

  return total
}
```

出网流量从反向代理日志估。Caddy 的访问日志有字节数字段，按月求和；没有日志时只能看 Cloudflare 的统计，精度差一些。

```bash
# 从 Caddy 访问日志估算当月出网字节（假设日志里有 size 字段）
awk '{sum += $NF} END {printf "%.2f GB\n", sum/1024/1024/1024}' /var/log/caddy/access.log
```

按 GB 汇总：

```bash
jq -s 'map(.size) | add / 1024 / 1024 / 1024' /var/log/caddy/access.log
```

用量数据要能追溯到日期。只留当前值，出问题时无法判断是突变还是长期增长；至少保留 90 天。

记录要自动化。手工填的数字会被忘记，巡检脚本每天写一行，格式固定：日期、库字节、Storage 字节、出网字节、邮件数。半年后回看，能算出增长率。

三个数字每天记录一次，存进一张表或一个 JSON 文件。有趋势才能判断“这个月会不会超”，单点数字没有意义。

## 50.2 免费档的边界

五家服务的关键额度列在一起，单位统一。

| 服务 | 免费额度 | 关键限制 |
| --- | --- | --- |
| Supabase | 500 MB 库、1 GB Storage、5 GB 出网 | 50,000 MAU，两个活跃项目，一周不活跃暂停 |
| Vercel Hobby | 函数 300 秒、请求体 4.5 MB | 每日一次 Cron，无持久磁盘，单区域 |
| Resend | 3,000 封/月、100 封/天 | 3 个域名，超出直接拒发 |
| Cloudflare | 无限带宽、Turnstile 免费 | Workers 每天 100,000 次请求 |
| R2 | 10 GB 存储 | 出网不收流量费 |

Supabase 的免费档按项目给额度，同一个项目里数据库、Storage、Auth 共享限制；开第二个项目不会让第一个项目变大，只会多一份独立的 500 MB。

Vercel 的免费档按人给额度，团队里每个成员一份构建与带宽。个人账号只有一个成员，团队账号会叠加，但函数执行时长仍按账户总量算。

Resend 的免费档按发送量算，收件人不计费。3 个域名指可以验证的发送域名，验证失败时域名不能用于发信。

Supabase 的 5 GB 出网包含数据库查询返回的字节，不限于下载文件。Vercel 的 300 秒只计单次函数执行，与整条请求链路无关。Resend 的 100 封/天是硬上限，月额度没用完也发不出去。

出网的计算还要注意压缩。反向代理开了 gzip 后，日志里记录的是压缩后的字节；数据库返回的 JSON 没压缩，按原始大小算更接近真实计费。

MAU 按认证用户数算，与访问量无关。团队协作工具的用户增长慢，50,000 这个数字通常够用；做面向公众的注册站要提前算。

## 50.3 超限之后的行为

超限有四种结果，处理方式完全不同。

四种结果里，只有第一种对用户友好。其余三种要么全站不可用，要么账单不可控，都要靠监控提前发现。

超限的判定以对方系统为准。自己的统计与账单差 10% 以内属于正常，差一倍要查是否有别的项目共用了账号。

第一种是报错。请求被拒，返回 4xx 或 5xx。Resend 超额、Vercel 请求体超限属于这类，应用层能感知，能给用户提示。

报错类的处理相对简单：给用户可读提示，记录日志，避免重试风暴。重试要有上限，429 之后指数退避。

第二种是暂停。服务整体不可用，Supabase 项目一周不活跃被暂停属于这类。恢复要进控制台手动操作，期间所有请求失败。

暂停类的恢复掌握在服务商手里。能做的事只有两件：提前发现（每天连一次库），以及准备好恢复步骤。

第三种是停服。免费额度耗尽后服务停止，直到下个周期。Cloudflare Workers 每天 10 万次请求用完就是 429。

第四种是计费。绑了支付方式后，超出直接扣钱，没有硬停。Vercel 与 Supabase 的付费档都是这样，“不会被停”意味着“会收到账单”。

第五种是部分降级。邮件延迟、索引变慢、连接被拒，介于正常与故障之间。这类最难发现，要靠监控。

## 50.4 每天跑的巡检

巡检脚本要能独立运行。不依赖应用启动、不依赖 Web 服务，`node scripts/check-quota.mjs` 直接跑；应用挂了也要能知道资源还剩多少。

巡检要在业务低峰跑。遍历 Storage 与查库大小都会占资源，白天跑会和用户请求抢 I/O。

巡检脚本检查三项：数据库大小、Storage 大小、磁盘剩余。超过阈值时发邮件，带当前值与阈值。

```js
// scripts/check-quota.mjs
import { execSync } from 'node:child_process'
import { readFileSync, writeFileSync, existsSync } from 'node:fs'
import { createClient } from '@supabase/supabase-js'
import { Resend } from 'resend'

const STATE_FILE = '/var/lib/teamstack/quota-state.json'
const ALERT_TO = process.env.ALERT_EMAIL
const resend = new Resend(process.env.RESEND_API_KEY)

const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.SUPABASE_SERVICE_ROLE_KEY,
  { auth: { persistSession: false } }
)

async function dbBytes() {
  const { data, error } = await supabase.rpc('db_size_bytes')
  if (error) throw error
  return Number(data)
}

async function storageBytes(bucket) {
  const { data, error } = await supabase.rpc('storage_size_bytes', { bucket_name: bucket })
  if (error) throw error
  return Number(data)
}

function diskUsedPercent() {
  const out = execSync("df -P / | tail -1 | awk '{print $5}'").toString()
  return Number(out.replace('%', '').trim())
}

const checks = [
  { key: 'db', label: '数据库', value: await dbBytes(), limit: 500 * 1024 ** 2 },
  { key: 'storage', label: 'Storage', value: await storageBytes('attachments'), limit: 1024 ** 3 },
  { key: 'disk', label: '磁盘使用率', value: diskUsedPercent(), limit: 85, unit: '%' },
]

const alerts = checks.filter(c => c.value / c.limit >= 0.8)
if (alerts.length === 0) process.exit(0)

// 24 小时内同一指标只告警一次
const state = existsSync(STATE_FILE) ? JSON.parse(readFileSync(STATE_FILE, 'utf8')) : {}
const now = Date.now()
const fresh = alerts.filter(a => now - (state[a.key] ?? 0) > 24 * 3600 * 1000)

if (fresh.length === 0) process.exit(0)

const lines = fresh.map(a => {
  const pct = ((a.value / a.limit) * 100).toFixed(1)
  const val = a.unit === '%'
    ? `${a.value}%`
    : `${(a.value / 1024 ** 2).toFixed(1)} MB / ${(a.limit / 1024 ** 2).toFixed(0)} MB`
  return `- ${a.label}：${val}（${pct}%）`
})

await resend.emails.send({
  from: 'alerts@teamstack.dev',
  to: ALERT_TO,
  subject: `[teamstack] 额度告警 ${new Date().toISOString().slice(0, 10)}`,
  text: `以下指标超过 80%：\n\n${lines.join('\n')}\n\n检查：https://supabase.com/dashboard`,
})

for (const a of fresh) state[a.key] = now
writeFileSync(STATE_FILE, JSON.stringify(state))
```

脚本读环境变量取连接串。数据库用直连端口，Storage 用 service_role 密钥；两者都只放在 VPS 的 `.env.production` 里，不进仓库。

脚本的退出码要区分“正常”“接近阈值”“已超限”。cron 只看退出码，三者分别是 0、1、2，邮件正文说明是哪一档。

脚本依赖两个数据库函数，用 `security definer` 让巡检账号能读大小，同时只授给 `service_role`。

```sql
-- supabase/migrations/20261220091000_quota_helpers.sql
-- 返回当前库大小（字节），给巡检脚本用
create or replace function public.db_size_bytes()
returns bigint
language sql
security definer
set search_path = public
as $$
  select pg_database_size(current_database());
$$;

-- 返回某个 bucket 的占用（字节），数据来自 storage.objects 的元数据
create or replace function public.storage_size_bytes(bucket_name text)
returns bigint
language sql
security definer
set search_path = public
as $$
  select coalesce(sum((metadata->>'size')::bigint), 0)
  from storage.objects
  where bucket_id = bucket_name;
$$;
```

```sql
revoke execute on function public.db_size_bytes() from public, anon, authenticated;
revoke execute on function public.storage_size_bytes(text) from public, anon, authenticated;
grant execute on function public.db_size_bytes() to service_role;
grant execute on function public.storage_size_bytes(text) to service_role;
```

定时任务放在 VPS 上，每天一次。容器里跑 Node，环境变量从 `.env.production` 读。

```cron
# /etc/cron.d/teamstack-quota
0 9 * * * root cd /srv/teamstack && /usr/bin/docker run --rm --env-file /srv/teamstack/.env.production -v /var/lib/teamstack:/var/lib/teamstack ghcr.io/teamstack/ops:latest node scripts/check-quota.mjs >> /var/log/teamstack-quota.log 2>&1
```

输出是四行摘要，直接看最后一行也能判断。

```text
- 数据库：96.0 MB / 500 MB（19.2%）
```

阈值要按容量倒推。数据库到 80% 时开始清理，到 95% 时禁止新写入；Storage 同理。留 20% 的缓冲，因为删除数据后空间不会立刻释放。

## 50.5 告警分三层

第一层是日检。每天跑一次，超阈值发邮件，收件人是值班的人。

第二层是周报。每周汇总趋势，包括库大小、Storage、出网、邮件发送量、MAU。周报用来看方向，不要求即时响应。

第三层是硬停前的告警。数据库到 95%、邮件到 90%、VPS 磁盘到 90% 时，除了邮件还要发到群里；这类告警一年可能只响一次，响了就要处理。

告警内容要包含“下一步做什么”。只写“数据库 85%”，值班的人还是要查文档；写“清理 audit_logs 旧分区”，能直接执行。

告警要能升级。发出去两小时没人处理时，再发给负责人；一直没人处理，说明告警设置有问题，或者值班表失效。

告警要有去重。同一个指标 24 小时内只发一次，否则巡检脚本每小时跑一次时会刷屏。状态存在文件里，键是指标名加日期。

## 50.6 成本结构

免费档撑不住时，钱主要花在三个地方。

域名与证书是固定成本，每年十几美元。免费证书三个月一续，自动化没配好时会过期，过期当天全站报证书错误。

还有一类成本容易被忽略：时间。自托管每月花几小时维护，按人力成本折算可能比托管费高；选择自托管的前提是这些时间有产出，比如可控性与数据位置。

数据库最先到顶。500 MB 对团队协作工具大约是一年的量，附件元数据、活动日志、审计记录都在涨。升级到 Pro 是每项目每月 25 美元。

邮件第二。3,000 封/月对几百人的团队够用，用户量上千后邀请、通知、摘要会把它吃满。Resend 的付费档 20 美元 5 万封，单价约 0.0004 美元。

VPS 第三。2 核 2 GB 的机器一年几十美元，比同规格的托管服务便宜。真正贵的是时间：自己维护要处理升级、备份、监控。

Vercel 在对照场景下不产生费用。Hobby 免费，超出后按用量计费；把它当生产会很快遇到 300 秒与 4.5 MB 的限制。

成本优化的顺序是：先删无用数据，再改写法，最后才谈升级。反过来的顺序是先付钱，再发现问题还在。

## 50.7 什么时候该升级

判断要不要升级，先算账。升级费与停机损失比：一小时停机影响多少用户、损失多少收入，超过月费就升。

四个信号，出现两个就该升级。

数据库连续两周超过 70%，且清理后降不下来。附件增长是刚性的，删不掉。

邮件退信率超过 2%，或每天有用户说收不到邀请。免费档没有专属 IP，送达率靠域名配置。

函数超时每月超过十次。业务在长，300 秒不够用，说明该拆任务或换执行环境。

团队人数超过 20 人，或开始有付费客户。免费档没有 SLA，出问题时只能等社区回复。

## 50.8 升级之后风险从停服变成账单

免费档的超限是停服，付费档的超限是扣钱。两种风险的处理方式不同：前者靠监控恢复，后者靠预算。

预算告警要有人接。发到只有自己看的邮箱，出差一周就会错过；发到群里，至少有人看到。

预算告警要开。Supabase 与 Vercel 都支持设置用量提醒，阈值设在实际预算的 50% 与 80%；提醒发到能决定是否继续花钱的人。

按项目分账。团队有多个项目时，每个项目单独看用量；混在一起时，一个实验项目能把预算吃光。

用量与收入挂钩。付费用户带来的收入要覆盖其资源成本，毛利率低于 50% 时先优化存储与查询，再考虑涨价。

## 50.9 降级预案

升级可以退回。业务收缩或迁移时，要能退回免费档。

归档文件要能单独恢复。按团队导出、按时间分区，别做成一整个几十 GB 的 dump；恢复单个团队时，整库 dump 用不上。

降级前先归档。把历史数据导出到对象存储，数据库只留活跃数据；导出文件按团队分，便于按需恢复。

再删。清理孤儿对象、过期日志、重复附件；删除后 `VACUUM FULL` 回收空间，否则库大小不会降。

然后降级。Supabase 从 Pro 降回 Free 前要确认库小于 500 MB，否则降级失败；Vercel 降级不影响已部署的函数，但会失去日志保留。

降级会让功能退化。Vercel 降级后日志保留变短，Supabase 降级后没有备份，Resend 降级后发送量减半；这些退化要提前告诉用户。

最后观察一周。降级后第一周最容易出问题，连接数、冷启动、邮件额度都要盯。

## 50.10 限额不要写死进代码

代码里判断大小要用常量，集中在一个文件；不要在每个上传入口写 `1024 * 1024 * 1024`。

```ts
// src/lib/limits.ts
export const LIMITS = {
  // 单个附件最大 50 MB，Supabase Storage 免费档单文件上限
  attachmentMaxBytes: 50 * 1024 * 1024,
  // 单个团队最多 1 GB，免费档 Storage 总量 / 团队数预留
  teamStorageMaxBytes: 1024 ** 3,
  // 每次导出最多 10000 行
  exportMaxRows: 10_000,
  // 邀请链接 7 天过期
  inviteTtlDays: 7,
} as const
```

上传前先软检查。超过团队配额时直接返回可读的错误，别等 Supabase 返回 413。

```ts
// src/app/(app)/teams/[teamId]/attachments/actions.ts 片段
const size = file.size
if (size > LIMITS.attachmentMaxBytes) {
  return { error: '单个文件不能超过 50 MB' }
}

const used = await getTeamStorageUsage(teamId)
if (used + size > LIMITS.teamStorageMaxBytes) {
  return { error: '团队存储已满，请删除旧附件或升级' }
}
```

软检查只是体验优化，真正的限制在服务端。客户端可以绕过，服务端的 RLS 与配额检查不能省。

## 50.11 一张年度成本表

按三档规模估算，单位是美元/年。

个人项目：VPS 72、域名 12、其余免费，合计约 84。

小团队：VPS 72、Supabase Pro 300、Resend 240、域名 12，合计约 624。

有付费客户：VPS 480（4 核 8 GB）、Supabase Pro 300、Resend 240、R2 与监控 120、域名与证书 60，合计约 1,200。

三档之间差在服务等级。免费档没有 SLA、没有专属支持，出问题靠文档与社区；付费档买的是这些，磁盘大小只占小部分。

数字会随汇率与促销变，但量级不会。决定成本的是数据库与邮件，服务器只占小头。

## 50.12 规格表上没写的限额

规格页只写容量，不写连接数与速率。这些数字在文档深处，超了报错很突然。

| 项目 | 数值 | 超了会怎样 |
| --- | --- | --- |
| Supabase 直连 | 约 60 | 连接被拒 |
| Supabase 连接池 | 约 200 | 排队后超时 |
| Realtime 并发 | 200 连接 | 新连接被拒 |
| Realtime 速率 | 每秒 100 条 | 连接被断开 |
| Storage 单文件 | 50 MB | 上传失败 |
| Actions 私有仓库 | 2,000 分钟/月 | 排队或拒绝 |

连接数是硬限制里最容易撞的。函数实例一多，每实例一个池，很快到 60；把池设小、接连接池端口，比升级计划便宜。

这些数字还会随计划变化。升级或降级后重新核对一遍，别沿用旧值做容量规划。

Docker Hub 匿名拉取限每 6 小时 100 次，CI 里频繁拉基础镜像会撞上；换 GHCR 或登录后拉取能解决。

这三种行为在一次账单里可能同时出现，先按金额排序，处理最贵的那一项。

## 50.13 对账

每月把三个月的用量摊开看，比看单月数字有用。

一条真实的增长曲线。数据库 40 MB 到 180 MB，Storage 120 MB 到 1.4 GB，出网 1.2 GB 到 6.8 GB，邮件 300 封到 2,900 封，MAU 60 到 610。三个月里 Storage 超限一次，邮件接近上限两次。

这次超限没有造成故障，原因是 Storage 超限只影响新上传，已有文件照常读；如果换成数据库超限，写入会整体失败。

超限的直接原因是重复附件。同一个文件被不同成员上传了七次，每份都存；加了内容哈希去重后，Storage 回到 400 MB。

对账要落到具体对象。Storage 涨了 1 GB，是哪几个团队、哪类文件；定位不到对象的增长，通常意味着有孤儿数据。

对账要看的是“哪一项在加速”。线性增长可以预测，指数增长要立刻查原因。

## 50.14 计费单位决定成本怎么涨

五家的计费单位不同，混着看会算错。

Supabase 按项目：一个项目一份钱，项目内所有用量共享额度。Vercel 按人：每个成员一份钱，用量另计。Resend 按量：按发送封数。Cloudflare 按域名：每个 zone 一份。VPS 按台：配置决定价格。

计费周期也不同。Supabase 按月订阅，中途升级按比例补差；Vercel 按用量月底结算；Resend 按订阅档位，超额直接拒发。

这意味着扩容时该动哪个：用户多但项目少，Vercel 的人头费涨得快；项目多但用户少，Supabase 的项目费涨得快。

## 50.15 三种自己写出来的超支

这三种超支的共同点是“没有上限”。任务、表、图片都在无约束增长，直到撞上服务商的硬限制。

第一种是定时任务空跑。每分钟一次的任务，实际没有数据也执行，一年 52 万次调用。改法是加前置检查，没有新数据就跳过。

第二种是日志表无上限增长。请求日志、审计日志、事件日志写进同一张表，从不清理。改法是按时间分区，定期删旧分区。

第三种是图片未压缩直接走 Supabase。原图 5 MB，列表页一次加载十张就是 50 MB 出网；用 `next/image` 转 WebP 后降到 200 KB。

三种都不需要改架构，改的是写法。

三种超支都能在巡检里看到迹象：调用次数、表大小、出网流量。看到异常增长就查，别等到撞限制。

## 50.16 每月十分钟

清单要能打勾。做成一个 Markdown 文件，每项后面写日期与结果；连续三个月都“没问题”的项，可以考虑降频。

每月固定做六件事：看账单、看用量趋势、清孤儿对象、查重复附件、核对邮件退信、确认备份还在跑。

账单看总额与环比，涨了 20% 以上要找原因。用量趋势看四项：库、Storage、出网、邮件。

清孤儿对象用脚本，按团队遍历，删除数据库里没有记录的对象。查重复附件按内容哈希分组，保留一份。

邮件退信率超过 2% 要查域名配置。备份是否还在跑，看最近一次成功的时间。

这套流程跑顺之后，成本变成可预测的数字：每月固定支出加按量增长，超出预期时能定位到具体资源。

下面五条覆盖计量、告警、账单、限额与核对五个环节，每月抽一次。

## 50.17 边界与失败模式

超支很少来自单一服务，多是几个用量同时涨。

1. 免费额度按项目算。多开一个测试项目，额度翻倍消耗；测试项目用完要暂停或删除。
2. 出网流量被静态资源放大。一张 2 MB 的图被首页引用，每次访问都算一次出网；图片要压缩并走 CDN。
3. 定时任务空跑。没有数据也执行查询与发信，函数调用次数照算，邮件额度照扣。
4. 日志与审计表没有上限。写入量随用户增长，磁盘与备份体积一起涨，清理策略要提前定。
5. 邮件退信率高。地址无效仍反复发送，额度消耗快，域名信誉下降，后续正常邮件也进垃圾箱。
6. 降级之后项目暂停。免费项目一周不活跃会暂停，恢复要手动操作，期间所有请求失败。

## 50.18 检查点

1. 跑一次巡检脚本，输出四行摘要。判据：数据库、Storage、磁盘三项都有数字与百分比。
2. 数据库到 80% 时收到过一封告警邮件。判据：邮件里有当前值与阈值。
3. 账单页能看到本月各服务用量。判据：五项都能对上，没有未知费用。
4. 上传一个超过团队配额的文件，返回可读错误码与文案。判据：返回 4xx，没有 500。
5. `select pg_database_size(current_database())` 与巡检脚本记录的数字一致。判据：误差小于 1%。

## 50.19 常见错误

**1. `ERROR: could not extend file ... No space left on device`**

现象是写入失败，日志里出现磁盘满。原因是数据库所在卷满了，或 VPS 磁盘满。改法是先清日志与旧镜像，再扩卷；数据库侧删历史数据后 `VACUUM FULL`。

**2. Resend 返回 `429 rate_limit_exceeded`**

现象是邮件发送失败，重试仍失败。原因是当天 100 封额度用完。改法是队列延后到次日，或升级付费档；不要无限重试。

**3. Storage 上传报 `Payload too large`**

现象是大于 50 MB 的文件传不上去。原因是免费档单文件上限。改法是分片上传，或换对象存储直传。

**4. 项目被暂停，接口全部超时**

现象是连接串不变但连不上。原因是一周不活跃被暂停。改法是进控制台恢复；日常巡检每天连一次库，能避免误判。

**5. `remaining connection slots are reserved`**

现象是高峰期连接被拒。原因是并发连接超过上限。改法是改用连接池端口，函数侧池大小设 3–5。

**6. 账单突然翻倍**

现象是本月费用远超上月。原因是某个功能上线后调用量激增，或预览部署产生了大量构建。改法是按项目看用量，定位到具体资源再优化。

## 50.20 这一章在做什么

这一章把五个服务的免费边界、超限行为、计量方法放在一起，形成一套可执行的成本管理：每天巡检、每周看趋势、每月对账。

它建立三条判断。第一，免费档的风险是停服，付费档的风险是账单，两者的监控重点不同。第二，计量先于优化，说不清用量就无法判断该不该升级。第三，超支多数来自写法，业务增长只占小部分。

这一章不覆盖企业合同、预留实例、税务。规模到几十万美元一年时，这些比技术优化更影响成本。

这套方法的成本是每月半小时。不做的话，代价是一次意外的停服，或一张解释不清的账单。

下一章讲合规最小集。成本与合规的共同点是“都要有记录”：用量有记录才能对账，数据处理有记录才能证明合规。
